# cd06 · Suspicious Users Sliding Window：从暴力 O(n²) 到排序+双指针的标准升级路径

> [!tldr]
> - 这题考的是：对每个用户的交易时间线，判断是否存在任意锚点交易 `t` 的 60 秒回看窗口 `[t-60, t]`
>   里塞了超过 3 笔交易；Part 1 允许暴力，Part 2 要求排序后用双指针把复杂度从 O(n²) 降到 O(n log n)
> - 三步套路：先写一个"对每笔交易都数一遍窗口"的暴力版本把语义钉死 → 观察"窗口右端点单调前进时，
>   左端点也只可能单调前进，绝不回退" → 把两个独立的循环合并成一次双指针扫描
> - 最值得带走的一个模式：**任何"窗口计数超阈值"的滑动窗口题，暴力解和优化解本质是同一个循环，
>   只是暴力版每次都从头数，优化版把"数"这个动作换成了"维护一个只进不退的区间"**

## 1. 题目在说什么（人话版）
Stripe Radar 要抓"疑似盗刷"：如果同一个用户在任意 60 秒内连续刷了超过 3 笔交易（也就是 4 笔以上），
这个用户就要被标记。输入是一堆交易记录，每行 `user_id,amount,timestamp`，顺序完全打乱——同一个用户
的交易在文件里可能东一笔西一笔，先后顺序也不保证。

小例子：用户 `alice` 有 4 笔交易，时间戳是 `1000, 1015, 1030, 1050`。以最后一笔 `1050` 为锚点往前
看 60 秒，窗口是 `[990, 1050]`，四笔全部落在里面 → `alice` 可疑。如果时间戳里最后一笔是 `1200` 而
不是 `1050`，那么以 `1200` 为锚点的窗口 `[1140, 1200]` 一笔都不包含前三笔，但以 `1030` 为锚点的窗口
`[970, 1030]` 只包含 `1000, 1015, 1030` 三笔——不够 4 笔——所以要检查的是**每一笔交易各自的窗口**，
不是只看最后一笔。

Part 1 只要判断"这个用户是不是可疑"（能过 O(n²) 暴力）；Part 2 要求同样的判断结果，但复杂度必须是
O(n log n)，并且额外要报告"最早触发"的那个窗口——`user_id: 4 in [1000, 1050]` 这种格式。

## 2. 读题：把文字变成模型
- **实体**：只有用户（`user_id`）和交易（`amount`、`timestamp`）。`amount` 在核心规则里完全不用，
  纯粹是给后续 follow-up（"窗口内金额也要超阈值"）留的接口噪声，读题时要能一眼认出它是噪声字段。
- **输入长什么样**：第一行 `PART n`，其余每行 `user_id,amount,timestamp`，逗号分隔，顺序不保证——
  这句话直接决定了"必须先分组、必须先排序"，不是可优化的细节。
- **输出要什么**：只输出真正可疑的用户，按 `user_id` 字符串序；Part 1 只报 `user_id`，Part 2 额外
  报"最早触发窗口"的计数和边界。两个 Part 的字段是**不同形状**，不是一个包含另一个。
- **状态**：要记住"每个用户按时间排好序的时间戳列表"——这是唯一需要维护的状态。窗口本身不需要额外
  数据结构（不像限流器那种要真的维护一个 deque），因为可以证明双指针足够。
- **一句话建模**：这是一个 **按用户分组、时间排序后，在每个用户自己的时间线上找"最早满足计数阈值
  的定长回看窗口"** 的问题——本质上和"最短/最长满足条件子数组"是同一类滑动窗口题。

> [!note] 为什么选双指针而不是别的
> 候选方案有三种：①对每笔交易暴力数窗口内有几笔（Part 1 允许，O(n²)）；②维护一个 `deque`，模拟
> "事件流式到达"，进一队出一队（在线场景更自然，追问 3 会问到）；③排序后双指针，一次线性扫描出
> 所有窗口（Part 2 要求的离线最优解）。三者对**同一批已知数据**给出完全相同的答案，选③是因为数据
> 是一次性给全的（不是流），排序之后双指针不需要额外的数据结构，代码最短，也最容易证明复杂度。

## 3. 下笔顺序（面试里就按这个顺序敲）
1. **骨架先行**：`main()` 读 stdin → 按 `PART n` 分发 → `part1`/`part2` 都先 `return []` 跑通。
2. **Part 1 最小可用**：写一个 `_parse` 把每行变成 `user_id -> [timestamp, ...]`；对每个用户的每笔
   交易 `t`，暴力数一遍"有几笔落在 `[t-60, t]`"，只要有一次 `>= 4` 就标记这个用户。立刻用样例自测。
3. **观察可优化的性质**：把"暴力数"换成"排序后双指针"之前，先在纸上/口头证明一句话——时间戳排序
   后，随着锚点 `t`（右指针）前进，窗口左边界（左指针）只可能前进不可能后退，因为一个已经"太老"被
   踢出窗口的时间戳，对后面任何更大的 `t` 也一定还是太老。这句证明是 Part 2 的全部正确性基础。
4. **Part 2 叠加**：复用 `_parse` 分组的结果，每个用户的时间戳先 `sort()`，然后一次线性扫描：右指针
   `j` 前进时窗口计数 `j - i + 1` 跟着涨，只要超过窗口就把左指针 `i` 前移。计数第一次达到阈值就立刻
   返回并停止——不能扫完整个用户去找"最大"的窗口，题目要的是**第一个**触发的窗口。
5. **收尾**：确认输出排序 key（`user_id` 字符串序）、Part 1/2 输出格式各自独立、空输入直接返回空、
   跑一遍所有样例和边界（恰好 60 秒 vs 61 秒、重复时间戳收缩成单点、一个用户两次触发只报第一次）。

## 4. 代码怎么组织
```
_parse(lines) -> dict[user, [timestamp,...]]     # 只管分组，不排序
_first_trigger(sorted_timestamps) -> (start,end,count)|None   # 一个用户的双指针扫描
_first_triggers(lines) -> dict[user, (start,end,count)]        # 分组 -> 排序 -> 逐用户调用
part1(lines) -> list[str]                         # 复用 _first_triggers，只取 key
part2(lines) -> list[str]                         # 复用 _first_triggers，格式化 value
main(stdin, stdout)                               # 只做分发
```
拆分原则很简单：**分组和排序只写一次，双指针核心逻辑只面对"一个用户已排序的时间戳列表"**，
Part 1 和 Part 2 因此可以共用同一个 `_first_triggers`——Part 1 只是把 Part 2 的结果"丢掉窗口细节，
只留 user_id"。这也是为什么参考实现里 Part 1 没有真的写一份 O(n²) 代码：暴力版是面试时用来验证语义
的脚手架，一旦你确认了优化版和暴力版在样例上给出相同答案，脚手架就可以拆掉，两个 Part 共用一套引擎
反而更不容易让两份实现的语义悄悄分叉。

## 5. 核心代码（骨架，≤ 40 行，带注释）
```python
# 只放主线：分组 -> 排序 -> 双指针 -> 输出。省略逗号解析细节和空行过滤。
WINDOW_SECONDS = 60
MIN_COUNT = 4  # "more than 3" == ">= 4"

def _parse(lines):
    by_user = defaultdict(list)
    for raw in lines:
        user, _amount, ts = raw.split(",")
        by_user[user].append(int(ts))
    return by_user

def _first_trigger(timestamps):                    # timestamps 已按升序排好
    i = 0
    for j, t in enumerate(timestamps):
        while t - timestamps[i] > WINDOW_SECONDS:   # 左指针只前进，绝不回退
            i += 1
        count = j - i + 1
        if count >= MIN_COUNT:
            return timestamps[i], t, count          # 第一次达标立刻返回
    return None

def _first_triggers(lines):
    by_user = _parse(lines)
    triggers = {}
    for user, timestamps in by_user.items():
        timestamps.sort()
        trigger = _first_trigger(timestamps)
        if trigger is not None:
            triggers[user] = trigger
    return triggers

def part1(lines):
    return sorted(_first_triggers(lines))

def part2(lines):
    triggers = _first_triggers(lines)
    return [f"{u}: {c} in [{s}, {e}]" for u, (s, e, c) in sorted(triggers.items())]
```

## 6. 面试里怎么说（边写边讲）
- 开始前：「我先确认一下：窗口是以每笔交易为锚点往前看 60 秒的闭区间，不是任意滑动窗口；输入不保证
  按用户或按时间排序，所以分组和排序是必须步骤。」
- 写 Part 1 时：「我先写一个能跑的版本——对每个用户的每笔交易都数一下它前 60 秒窗口里有几笔，这一步
  是 O(n²) 但先把语义钉死，样例过了我再优化。」
- 过渡到 Part 2 时：「这里的关键观察是，时间戳排完序之后，窗口左边界只会前进不会后退——一笔交易一旦
  因为太老被移出窗口，对后面任何更靠右的锚点它也还是太老，所以左右指针各自最多移动 n 次，整体是
  O(n log n)（排序是瓶颈），不是 O(n²)。」
- 讲"first trigger"语义时：「我在计数第一次达到阈值的地方就立刻返回，不继续扫完整个用户找最大的
  窗口——因为题目要的是最早触发，不是最密集的那次。」
- 交付时：「Part 1 和 Part 2 共用同一个双指针引擎，Part 1 只是丢掉了窗口细节；如果时间允许，我会把
  `60` 和 `4` 改成参数，双指针算法本身完全不用动。」
- 被追问复杂度时：「排序是 O(n log n)，双指针扫描每个用户是均摊 O(1) 每笔交易，整体 O(n log n)，
  瓶颈在排序，不在窗口逻辑本身。」

## 7. 常见跑偏（方法层面，3 条）
- **没证明就直接写双指针**：双指针正确的前提是"左指针单调不减"这条性质，如果没想清楚就照着模板敲，
  遇到追问"为什么左指针不用回退"答不上来。先在草稿纸上证明一句话，再写代码。
- **混淆"first trigger"和"max window"**：找到第一个满足阈值的窗口就该立刻停，很多人会顺手把扫描
  逻辑写成"记录所有满足条件的窗口，最后取最大的那个"，这是完全不同的语义，题目明确要最早的。
- **暴力版和优化版各写一套解析**：Part 1 单独 split 一次逗号，Part 2 又写一次分组排序，两份实现容易
  在处理空行、重复时间戳等边界上悄悄产生不一致。先写好 `_parse`/分组逻辑，两个 Part 都调它。

## 8. 同族题 / 延伸
- 其他轮：ps01 `transaction_stream_levels` 的 Part 2（任意 60 秒内累计金额超阈值，报第一次触线时的
  窗口）是这题的"简化版"——同一套 `[t-60, t]` 闭区间约定，但那题按金额求和、这题按笔数计数；cd06 是
  加强版：阈值从任意 `T` 固定成 `>3`，并且要求精确报告最早触发的窗口边界，不只是"命中了没有"。
  ps04 `data_validation_fraud` 的 Part 3 同样是"每个用户按时间线扫描、和历史行为比对"的变体。
- 延伸思考：如果交易是实时流进来而不是一次性给全，双指针的"排序"这一步就做不了了，要换成"每用户
  一个 `deque`，新事件 append、同时从队首弹出所有过期时间戳"，队列长度就是当前窗口计数，均摊 O(1)
  每事件——这正是 problem.md「面试官会怎么追问」第 3 条问的东西，本质上和双指针是同一个思路的在线版。
