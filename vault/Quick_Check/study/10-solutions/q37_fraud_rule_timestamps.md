# q37 · 风控规则的生效时间（授权请求 vs 规则版本）

> `problems/q37_fraud_rule_timestamps/` · 4 个 part
> **主题：这道题考的是"时间"，不是表达式解析（那是 q12）。**

## 一句话题意

规则有 `effective_from`（和 Part 3 的 `effective_to`）。
一条授权请求在时刻 `t` 是否被拒，取决于**当时生效的那个版本**的规则。

## 核心考点

`S02` 解析 · `S03` 建模 · **`S05` 严格 vs 非严格比较** · `S08` 确定性排序 ·
`S10` 事件流 · **`S12` 时间处理** · **`S13` 闭/开区间**

## 直觉 / Intuition

把每个 `name` 想象成一部"法律"：`effective_from` 是修订生效日，`effective_to`（如果有）是废止日。
判断一条授权请求是否违法，等价于问"案发时刻 `t`，现行的是哪一版法律" —— 而不是"现在最新的是哪一版"。
这就决定了解法的形状：**不能按行到达顺序处理**（法律和案件谁先写进档案无所谓），必须先把同名规则的所有版本按 `effective_from` 排好序，对每个 `t` 做一次"历史查询"（找 `effective_from <= t` 中最大的那个），再检查它当时是否已被更晚的修订废止（`effective_to`）。
一旦把问题看成"時间点上的版本查找"，Part 2/3/4 的坑就自动消解了：不追溯（旧法不能管新案）、不回退（新版本过期了不代表旧版本复活）、乱序输入不影响结果 —— 都是"法律生效以文本记录的时间戳为准，不以档案顺序为准"的自然推论。

## 解题思路

### Part 1

请求在 `t` 被 `REJECT` ⟺ 存在一条 `effective_from <= t` 且匹配的规则（**`==` 也算生效**）。
规则生效前的请求即使匹配也 `APPROVE` —— **不追溯**。

### Part 2 — 多规则与规则版本

- **不同 name 的规则相互独立**：**任何**一条在生效中且匹配的规则就拒绝。
- **同 name 的行是同一条规则的多个版本**。时刻 `t` 生效的版本是
  **`effective_from <= t` 中最大的那个**（平手取**后面那行**）。
- **只评估那一个版本**（不是所有版本的并集）。
- 条件为 `none` 表示该规则从这个版本的生效时间起**关闭**。

### Part 3 — 过期

5 字段的 `RULE` 行在 `effective_from <= t < effective_to` 内生效（**右端开**）。
**版本选择规则不变**：选中的版本如果在 `t` 已过期，规则就是关的 —— **不回退到更老的版本**。

### Part 4 — 乱序到达

`RULE` 和 `AUTH` 行在文件里可以任意顺序出现；
**版本按 `effective_from` 排序，绝不按行位置**；输出按 `(timestamp, id)` 排序。

## 坑

1. **`timestamp == effective_from` → 规则生效**；**`timestamp == effective_to` → 已过期**。
2. 一条请求匹配**旧版本**但不匹配**当前生效的版本**（以及反过来）。
3. **过期的新版本不会让旧版本复活。**
4. `none` 版本；`!=` 和 `<=` 操作符；**`amount` 按数值比较**（`900 > 1000` 为假）。
5. 两条规则里只有第二条匹配。
6. **规则行出现在请求行之后**（Part 4）。
7. 输出平手：同 timestamp → id 的**字符串序**（`b2` < `b3`，`a10` < `a2`）。
8. 完全没有规则 → 全部 `APPROVE`；没有请求 → 无输出。

## 变体
