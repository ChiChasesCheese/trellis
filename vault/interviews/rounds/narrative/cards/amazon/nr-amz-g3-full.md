## Q
<p class="title">GenAI 不必要的时候<span class="meta">01 完整故事</span></p>

先在心里把前因后果过一遍，再用英文完整讲一遍。

## A
<span class="label">前因后果</span>

- 背景：还是同一个项目。我的第一反应是把所有事都交给代理，包括数数和修小的评审意见。
- 目标：找出哪些地方让代理做反而花得比省得多。
- 我做了什么，第一步是计数：切分线、覆盖率百分比、正文里的「N 道题」，手工数曾经错过两次。所以现在每个计数都由脚本产生，模型永远不数数。
- 第二步是小修：一轮代理修订实测要 5 到 6 分钟、多 4 万到 6 万 token，所以一行的修改我就地改，只有实质性修改才回到代理。第三步是并行度：一个问题一个代理浪费上下文，一次性开四个代理又破了上限，最后定为每个代理两道题、同时三个代理。后来我的 Amazon 备考覆盖矩阵也改成由脚本从一份映射生成，不会漂移。
- 结果与学到：审阅一对完成的题只需要三到六次工具调用，用的是脚本而不是模型。模型用在输出开放且可检查的地方，答案确定的地方，写十行代码。

<span class="label">英文口述（60–90 秒）</span>

Same build. My first instinct was to hand everything to an agent, including counting things and fixing small review comments, and I wanted to find where that actually cost more than it saved. First, counts. Cut lines, coverage percentages and the N problems in prose had been wrong by hand, twice, so now every count comes from a script and a model never counts. Second, small fixes. An agent revision round measured five to six minutes and forty to sixty thousand extra tokens, so a one-line fix I edit in place, and the agent round trip is for substantive changes. Third, parallelism. One agent per problem wasted context, and four agents just this once broke my cap, so I settled on two problems per agent, three agents at a time. Later, my Amazon-prep coverage matrix is generated by a script from one mapping, so it cannot drift. Now reviewing a finished pair takes three to six tool calls, using a script, not a model. I use a model where the output is open-ended and checkable. Where the answer is deterministic, I write ten lines of code.
