# 06 · 三轮技术面：每轮考什么、怎么准备

经理面之后是三轮技术面，每轮约 45 分钟，面试官是工程师，代码写在 HackerRank 的共享编辑器里，视频走 Microsoft Teams。公司对这三轮的说法是"编码（语言自选）+ 和岗位相关的技术深挖，考你每天要用的东西，不考抽象难题"，这个组织还明说"偏 Python"。三轮最可能的分工是：一轮 Python 编码，一轮测试、发布与排错，一轮机器学习与 LLM 推理基础加一点系统知识；其中任何一轮都可能换成提前通知、允许用 AI 的实战题。每轮开头几分钟都会让你讲一个过去的项目。这页按轮讲：形式、45 分钟怎么分、出过的题和追问、怎么准备、复习哪部分卡片。

## 一屏总结

| 轮 | 形式 | 考什么 | 最该准备 |
|---|---|---|---|
| 1 Python 编码 | HackerRank 实时共享编辑器 | LeetCode 简单到中等，常一轮两题；或面试官自己出的、和工作相关的小任务；追问复杂度、并行、稀疏、边界测试 | 32 道高频题 + 两个"解析测试结果"和"并行跑测试"的实战练习 |
| 2 测试、发布与排错 | 口头深挖，可能夹一段读代码 | "你怎么测 X"（拿日常物品打比方）、测试框架、不稳定测试（flaky，同一代码时过时挂）、失败分诊、发布门 | `软件测试与发布工程` 牌组 + 三个场景题的口述稿 |
| 3 ML、推理与系统 | 口头快问快答 + 可能一个小设计 | L1 与 L2、分类指标、过拟合、Transformer；预填充与解码、KV 缓存、延迟指标；调度与共享内存；GPU 与 CPU；"设计一个类似 Bugsnag 的错误追踪系统" | `LLM 推理与 AI 加速器` 牌组的 ml、phases、metrics、numerics 部分 |
| 可能替换任何一轮：允许用 AI 的实战 | 提前通知，真实代码库或数据集 | 先框问题、给工具上下文、逐步验证、抓出看起来对的错误、讨论上生产 | 把 Model Quality & Performance 挑战按第 4.2 节练一遍 |

- **编码不难，难在说清楚和自测。** 出过的题几乎都是简单或中等，题不难也会挂。差别在：先说思路、写完自己举边界用例、被追问时能把单线程版本改成并行或流式。
- **测试岗的深挖题没有题库。** 只出现过"奇怪的测试类比题"和"做过什么测试框架"。按职责准备：怎么测、怎么分档、flaky 怎么管、失败怎么分诊、发布能不能放行。
- **机器学习基础测试岗也会问。** 测试岗出现过整场都是机器学习基础题加测试类比题、没有算法题的情况。
- **公司给模型质量与性能岗出的带回家题，考的正是发布验证的思路**：用最少的评测样本给出"够不够好"的判断，再把性能数据变成客户能用的放行结论。

## 0. 三轮共同的规则

### 0.1 HackerRank 怎么用

- **是实时面，不是无人监考的机考。** 面试官在 Teams 上和你通话，HackerRank 是共享编辑器（HackerRank Interview，也叫 CodePair）。可以运行代码、自己加输入。
- **语言自选**：全部用 Python。出现过指定用 C++ 从零写二分的情况；被指定语言就照办，否则用 Python。
- **有时不让跑**：出现过"白板式"的编码，以及"不写代码，口头讲清楚"的二维前缀和。准备时练"不运行，靠手推例子验证"。
- **提前准备**：装好 Teams；在 HackerRank 的练习页试一次 Python 环境，确认 `from collections import ...`、`heapq`、`bisect`、`concurrent.futures` 能用；知道怎么在编辑器里写 `if __name__ == "__main__":` 自测。

### 0.2 每轮开头的项目题（每轮 3–8 分钟）

- 问法："讲一个你做过的东西，为什么那样设计。"这是这家公司出现最多的问题（8 次）。
- 每轮挑一个和本轮主题对口的项目：编码轮讲 D3 质量门的实现；测试轮讲 D1 行为一致性测试或 D2 静默 bug；推理轮讲 D5 确定性环境。故事见 [04-hm-screen.md](04-hm-screen.md) 第 3 节。
- 60 秒讲完就停，等追问。

## 1. 第一轮：Python 编码

**考什么**：能不能在 45 分钟里写出正确、可读的 Python，自己发现边界错误，被追问时把方案扩展到并行、稀疏或更大的规模。

### 1.1 时间分配

| 分钟 | 做什么 |
|---|---|
| 0–5 | 寒暄 + 一个项目 |
| 5–10 | 读题；复述输入输出；问 2 个澄清问题；手写 2 个例子 |
| 10–28 | 写代码，边写边说为什么用这个结构 |
| 28–35 | 跑例子；自己说出并跑 3 个边界用例（空、一个元素、重复或并列） |
| 35–42 | 追问：复杂度、规模变大、改成并行或流式、换成稀疏数据 |
| 42–45 | 反问 |

如果一轮两题：第一题 15 分钟内收尾，留 20 分钟给第二题。

### 1.2 出过的题

| 题族 | 出过的例子 | 出现次数 | 面试官接着问 |
|---|---|---:|---|
| LeetCode 简单到中等（数组、字符串、哈希、栈、二分） | Two Sum（low priority）；3Sum（low priority）；括号是否平衡（low priority）；从零写二分查找（low priority）；HackerRank 上的二维数组操作（low priority）；"两道中等题"；"一道很基础的编码题" | 13 | 复杂度；不用库重写；自己补测试；二维数组题时间很紧，先写出能过的版本再优化 |
| 手写一个数据结构 | 实现一个简单的链表（low priority） | 1 | 插入、删除的边界；为什么用哨兵节点；各操作复杂度 |
| 数值计算 + 并行 | 二维前缀和，只口述（low priority）；多线程的二维前缀和（low priority）；向量点乘 → 为并行架构优化 → 换成稀疏向量（low priority）；矩阵乘法与并行编程（low priority）；GPU 矩阵运算的分块（low priority）；晶圆上的 Top-K 最近邻，带回家题，见 4.3（low priority） | 5 | 怎么把数组切给多个线程再合并；Python 里线程和进程怎么选；SIMD、对齐、缓存；稀疏用什么存；怎么证明并行结果和串行一致 |

| 面试官自己出的系统题 | 多频道消息队列：消息带多个频道标签，消费者订阅频道；加频道；给定一组生产者和消费者的通信关系，最少要几个频道；用并查集找共享频道；各操作复杂度（low priority） | 2 | 频道 ID 怎么表示才能快速求并集和交集（位集合）；运行时加频道；复杂度 |
| 和工作相关的小任务 | 机器学习测试岗：不是 LeetCode，而是"和工作相关的一个用例" | 1 | 你的代码怎么测；输入脏了怎么办 |

公司标签下还有 23 道 LeetCode，按频率从高到低：Flood Fill、Make String a Subsequence Using Cyclic Increments、Roman to Integer、Word Search、Continuous Subarray Sum、Subsets II、High Five、Best Time to Buy and Sell Stock、Reverse Words in a String、Analyze User Website Visit Pattern、Maximize Amount After Two Days of Conversions、Reverse Integer、Remove All Adjacent Duplicates in String II、Split Array Largest Sum、Linked List Cycle、Remove All Occurrences of a Substring、All Nodes Distance K in Binary Tree、Zigzag Conversion、Maximum Nesting Depth of the Parentheses、Adding Spaces to a String、Find Score of an Array After Marking All Elements、Next Permutation、Find Leaves of Binary Tree（全部 low priority）。

### 1.3 测试岗最可能拿到的"工作题"

出过"和工作相关的用例"，但没有具体题面。按这个岗位每天的活，最可能是下面三种，各练一次，限时 30 分钟：

1. **解析测试结果**：给多次运行的结果行（测试名、状态、耗时、错误信息），输出每个测试的失败次数；同一测试有时过有时挂的标为不稳定；按错误信息归成"失败签名"（去掉数字、地址、时间戳后相同的算一类）。追问：文件 10 GB 怎么办（流式读）；签名怎么设计才不把不同的 bug 合成一类。
2. **并行跑测试**：给一组测试命令，最多同时跑 N 个，每个有超时，失败重试一次，最后打印汇总。追问：重试为什么会掩盖缺陷；超时后子进程怎么清理；结果顺序怎么保证确定。
3. **读一段代码找 bug**：给 30–60 行 Python 和一个失败的测试。先复现，再缩小输入，再改；最后补一个能抓住它的测试。

### 1.4 怎么准备

1. **高频 LeetCode，全部用 Python 重写一遍**（题解在 `core/leetcode/problems/`）：
   - 数组与哈希：[two-sum](../../core/leetcode/problems/two-sum.md)、[3sum](../../core/leetcode/problems/3sum.md)、continuous-subarray-sum、best-time-to-buy-and-sell-stock、reverse-words-in-a-string。
   - 栈：[valid-parentheses](../../core/leetcode/problems/valid-parentheses.md)、minimum-add-to-make-parentheses-valid、remove-all-adjacent-duplicates-in-string-ii。
   - 二分：[binary-search](../../core/leetcode/problems/binary-search.md)、search-a-2d-matrix、split-array-largest-sum。
   - 二维数组：spiral-matrix、rotate-image、set-matrix-zeroes。
   - 链表：reverse-linked-list、linked-list-cycle、lru-cache。
   - 图与网格：[flood-fill](../../core/leetcode/problems/flood-fill.md)、number-of-islands、rotting-oranges、word-search、course-schedule、course-schedule-ii。
   - 并查集：number-of-provinces、accounts-merge、redundant-connection。
   - Top-K：kth-largest-element-in-an-array、top-k-frequent-elements、k-closest-points-to-origin。

   - 对应的算法知识树节点：`grid.1` 网格图 DFS、`graph.2.1` 拓扑排序、`data-structures.1` 前缀和、`data-structures.3.4` 合法括号、`data-structures.7.1` 并查集、`binary-search.1` 二分基础。
2. **数值与并行的追问**：Code Core 牌组 `performance.numeric-arrays`（二维前缀和、点乘与稀疏、CSR、矩阵乘法循环顺序、分块、numpy 向量化）和 `performance.parallel-split`（切块合并、GIL 下线程与进程、多线程二维前缀和、两遍前缀和、和串行结果对比）。这 11 张卡就是上面"数值计算 + 并行"那一行的全部追问。
3. **解析与自测**：Code Core 牌组 `input.*`（行协议、CSV、脏数据）、`verification.tests`、`verification.edge-catalog`、`round.debugging`；Python 牌组 `concurrency.executors`、`concurrency.queues`。

## 2. 第二轮：测试、发布与排错深挖

**考什么**：你是不是真的会做测试和发布这份工作：拿到一个东西知道先测什么、不测什么；一个失败出来知道怎么定位到哪一层、哪次提交；发布前知道看什么证据、敢不敢叫停。这是这个岗位和普通软件工程师面试差别最大的一轮。

### 2.1 时间分配

| 分钟 | 做什么 |
|---|---|
| 0–8 | 一个测试相关的项目：你建的框架、质量门或排查过的 bug，追问到第三层 |
| 8–20 | "你怎么测 X"：先问需求，再按层次给测试计划 |
| 20–35 | 场景题：夜间回归红了、一个测试偶尔失败、明天发布还有一个阻断 |
| 35–42 | 可能：读一段代码找 bug，或给一个函数现场写测试 |
| 42–45 | 反问 |

### 2.2 出过的题和最可能的题

| 题族 | 例子 | 出现次数 | 面试官接着问 |
|---|---|---:|---|
| 用日常物品打比方的测试题 | "很奇怪的测试类比题"，具体物品不固定；常见形式：怎么测电梯、自动售货机、一支笔（low priority） | 1 | 先测哪三样；什么不测、为什么；哪些能自动化 |
| 测试自动化经验 | 做过什么测试框架、框架里的概念、具体工具的问题（low priority） | 1 | 框架分几层；怎么让别人加测试很容易；结果怎么汇总 |
| 测试计划与风险 | 按职责必问：给一个新功能（例如新上线一个模型到推理接口）写测试计划 | 0 | 准入准出条件；按风险排序；资源只够一半怎么砍 |
| 回归分档 | 按职责必问：每次提交、合入后、夜间、发布前各跑什么 | 0 | 每档的时间预算；一个测试该放哪档 |
| 不稳定测试（flaky） | 按职责必问：一个测试每 100 次挂 1 次怎么办 | 0 | 怎么量化；重试的代价；隔离区的规则和期限 |
| 失败分诊与根因 | 按职责必问：主干红了，第一步做什么；跨栈的失败怎么判断是哪一层 | 0 | 产品回归、不稳定、环境、测试缺陷怎么分；`git bisect`；指派给谁 |
| 发布放行 | 按职责必问：发布前看哪些证据决定放不放；什么算阻断 | 0 | 豁免谁批；挑拣（cherry-pick）怎么验证；推迟发布你怎么说服人 |
| 读代码找 bug | 按职责很可能：给一段 Python 和测试，找出问题 | 0 | 怎么复现；怎么缩小；修完补什么测试 |

"出现次数 0"表示这类题在这家公司还没出现过具体题面，但这个岗位的职责就是这些，经理面也会往这里带。

### 2.3 三个场景题的答法骨架

1. **夜间回归红了 40 个测试**：先看是不是同一个失败签名 → 看同一时间其他套件和基础设施是否也红（环境问题）→ 和上一次绿的构建之间有哪些提交 → 能稳定复现的用二分定位 → 按签名开一个缺陷、指派给改动所在的组件负责人 → 主干上先回滚再修。
2. **一个测试每 100 次挂 1 次**：先重跑 200 次量出失败率 → 按失败签名看是不是同一种错 → 常见原因（时序、执行顺序、共享状态、资源竞争、非确定性的数值）逐个排除 → 修不好就隔离并设负责人和期限，隔离不等于删除 → 绝不把"重试 3 次"当修复。
3. **明天发布，还有一个未定的阻断**：说清影响面（哪些模型、哪些配置、多少用户）→ 有没有绕过办法 → 修复的风险和验证时间 → 给出放行、带条件放行或推迟的建议和证据，由发布负责人拍板 → 事后补一个能更早抓住它的测试。

### 2.4 怎么准备

1. `软件测试与发布工程` 牌组，按这个顺序：`strategy.*`（测试计划、风险、怎么测 X）→ `regression.tiers` → `flaky.*` → `triage.*`（第一轮分诊、失败分类、二分、失败签名）→ `release.qualification-gates`、`release.blockers`、`release.cherry-picks` → `test-infra.framework-architecture`、`test-infra.results`。
2. 低层设计牌组：`debugging.bisect`、`debugging.heisenbugs`（时序和共享状态的 bug）；测试层级 `testing.test-levels`。
3. Python 牌组 `engineering.testing`（pytest 夹具、参数化、mock）。
4. 把 2.3 的三个骨架各说出声两遍，每个控制在 2 分钟。
5. 给 [04-hm-screen.md](04-hm-screen.md) 第 4 节"测一个推理端点"再练一遍：这一轮最可能的"怎么测 X"就是它。

## 3. 第三轮：机器学习、LLM 推理与系统

**考什么**：测试岗也要懂被测的东西。机器学习基础出现了 6 次，测试岗也被问过整场；推理岗位还会问被测系统的性能和正确性怎么判断。另外可能有一段操作系统、体系结构或一个小设计。

### 3.1 时间分配

| 分钟 | 做什么 |
|---|---|
| 0–5 | 一个项目 |
| 5–18 | 机器学习基础快问快答，每题 1 分钟内答完 |
| 18–32 | LLM 推理：一次请求经过哪些阶段、性能指标、精度怎么验证 |
| 32–42 | 操作系统或体系结构几问，或一个小的系统设计 |
| 42–45 | 反问 |

### 3.2 出过的题

| 题族 | 出过的例子 | 出现次数 | 面试官接着问 |
|---|---|---:|---|
| 机器学习基础 | 什么是正则化，L1 和 L2 的区别（low priority）；怎么评价一个分类模型、你偏好哪些指标（low priority）；监督与无监督（low priority）；过拟合与欠拟合（low priority）；常见算法比较；网络结构、调参、训练难点、评估指标；Transformer 与优化（low priority） | 6 | 为什么 L1 让权重变稀疏；类别不平衡时看什么指标；怎么看出过拟合 |
| 计算机体系结构 | GPU 的指令流水线和 CPU 有什么不同（low priority）；体系结构与优化；编译器基础 | 3 | 为什么生成 token 卡在内存带宽；屋顶线模型 |
| 操作系统与数据结构内部 | 调度和共享内存资源（low priority）；为什么 `std::unordered_map` 很少是最好的哈希表、`absl` 和 `tbb` 的版本好在哪（low priority） | 2 | 进程和线程；锁和死锁；开放寻址和拉链法 |
| 系统设计 | 设计一个类似 Bugsnag 的错误追踪系统，题目很模糊（low priority）；另有两次设计轮没有给出题面 | 3 | 错误怎么分组；突发流量怎么办；怎么告警又不刷屏 |
| LLM 推理 | 按职责必问：预填充与解码、KV 缓存、批处理、TTFT 与每 token 间隔、为什么同一输入两次结果不同、量化后精度怎么验 | 0 | 批变大为什么吞吐升、单请求变慢；怎么判断精度回退不是噪声 |

### 3.3 Bugsnag 类错误追踪系统：答题骨架

- **需求先问清**：多少个应用、每秒多少条错误、要多快看到、保留多久、要不要源码映射（把压缩后的栈还原成源码行，symbolication）。
- **数据流**：客户端 SDK 采样并批量上报 → 接入层限流、校验 → 消息队列削峰 → 处理服务：还原栈、算指纹（fingerprint：异常类型 + 去掉行号和变量后的栈帧）→ 按指纹并入已有问题（issue）或新建 → 问题表存计数和首末次时间，原始事件存对象存储或列存 → 告警服务按"新问题、回归、突增"通知，同一问题合并通知。
- **难点**：指纹太粗会把不同 bug 合成一个，太细会把一个 bug 拆成几百个；突发时按问题采样而不是按事件丢；一个已关闭的问题再出现要标为回归。
- **和这个岗位的关系**：这就是测试失败的"失败签名 + 自动归类 + 回归检测"，放大到线上。答完主动提这一点。

### 3.4 怎么准备

1. `LLM 推理与 AI 加速器` 牌组：`ml.*`（7 个知识点，28 张）先过完；然后 `phases.*`、`serving.batching`、`metrics.latency-throughput`、`numerics.nondeterminism`、`numerics.accuracy-validation`；体系结构 `accelerators.gpu`、`accelerators.roofline`。
2. `ML 与 LLM 系统设计` 牌组：`evaluation.llm-eval`、`evaluation.regression-gates`、`llm-platform.model-release`、`llm-platform.eval-platform`。
3. 系统设计牌组：`q.metrics`（指标监控与聚合）、`q.notification`（通知去重）、`q.github-cicd-workflow`（CI/CD 平台）；`软件测试与发布工程` 的 `triage.signatures`。用它们拼出 3.3 的答案，说一遍，控制在 15 分钟。
4. 操作系统：Python 牌组 `concurrency.multiprocessing`、`concurrency.locks-races`；哈希表内部看 under-the-hood 牌组的 Python dict 与 Go swiss table 两张。

## 4. 允许用 AI 的轮次与带回家的题

### 4.1 允许用 AI 的轮次

- **形式**：提前通知你可以用、而且希望你用 AI。先给一个具体目标，做完再展开讨论改进、假设和上生产要什么。
- **题目类型**：读一个小代码库；给已有服务加一个功能；调查一份运维数据；改进一个开发工具；把一个不完整的需求做成能跑的原型。
- **面试官接着问**：你会改进什么、哪些假设要回头看；上生产前要改什么；解决的是不是用户真正的问题；先测哪部分；负载上来会怎样；安全和隐私风险在哪；怎么让下一个工程师好接手。
- **评分看什么**：把问题框清楚再交给工具；给工具足够的上下文和约束，把活拆成能逐步验证的小步；**验证**（早跑代码、读报错、看数据、判断测试有没有意义、抓住改掉的接口、被忽略的约束、只处理正常路径、多余的复杂度）；能解释、修改、调试生成的代码；测关键行为和边界；知道什么时候信工具、什么时候顶回去；讲清楚；想到可靠性、安全、可观测、扩展和可维护。不看你用哪种提示词写法。高级岗要求更强的问题定义、更清楚的取舍、更关注系统长期行为。
- **最强的信号**：抓住并改正一个"看起来很对"的错误。

**45 分钟怎么分**

| 分钟 | 做什么 |
|---|---|
| 0–5 | 读需求，问 2–3 个问题，说出你理解的目标和不做什么 |
| 5–10 | 读代码库或数据：入口、数据结构、现有测试；说出计划 |
| 10–30 | 一小步一小步交给 AI；每步读 diff、跑测试、自己补一个边界用例 |
| 30–40 | 讨论：上生产缺什么、怎么监控、怎么测 |
| 40–45 | 总结：哪些部分你没交给 AI、为什么；还剩什么风险 |

### 4.2 Model Quality & Performance 挑战（low priority）

这是公司给模型质量与性能方向的 AI 工程师出的带回家题，内容就是发布验证的核心问题：**花最少的测试成本，给出一个可信的"能不能放行"的判断**。两个任务互相独立。

**任务 1：把性能预测表变成两种人能用的工具**

- **输入**：性能工程师的 `.xlsx` 性能扫描表，模型 A–K，每个模型 7 种流量画像（traffic profile，即输入长度、输出长度、缓存比例等组合），每张表是一个模型在一种画像下的一组扫描结果，列一般是：输入和输出长度、缓存命中比例、并发（批大小）、每用户每秒 token 数、首个 token 时间（TTFT）、端到端延迟、总吞吐。
- **两种用户**：
  - 客户或面向客户的产品经理：要一个放行或不放行（go/no-go）的结论：这个模型够不够快、够不够我的负载；用他认得的数字（tok/s、TTFT、上下文长度、成本含义）。
  - 内部部署工程师：要能核对预测是否合理、看配置变化怎么影响结果、在给客户前发现异常。
- **硬要求**：
  - 上传一个或多个扫描表，在线直接出图，不重新构建、不改代码。
  - 多个模型并排比较是主路径，不是附加功能。
  - 唯一能依赖的契约是 `Model_<X>_profile_<N>/...xlsx` 的文件名和列结构；会用一个新的模型 L 来测，不改代码必须能正确显示。
  - 部署一个公开网址；附运行说明。
- **明确不及格的做法**：把表格直接转成网页；所有列给所有人看还称之为"可配置"；写死模型名单；所谓上传其实是重新跑构建脚本。
- **视频要回答（5 分钟内）**：你理解的每类用户的问题是什么、砍掉了什么；选了什么框架、排除了什么；对数据、用户、部署环境的假设；有更多数据、有真实生产测量、有更多时间各会改什么；**根据性能数字猜 A–K 各是多大的模型；根据流量画像猜 1–7 各是什么用途**。
- **好答案的样子**：
  - 解析按列名同义词表匹配，不按列序号；模型名从文件名取，没有任何写死的名单。
  - 客户视图：输入他的负载（输入输出长度、并发）和要求（最低每用户速度、最大 TTFT），匹配最接近的画像和最近的实测并发点，并说明"取了最近的点"，给红黄绿结论和关键数字。
  - 工程师视图：每个模型随并发的曲线，自动标出异常：吞吐随并发反而下降、TTFT 随负载变小、每用户速度乘以并发和总吞吐对不上、缺点。
  - 猜模型大小：解码速度大致和每生成一个 token 要读的参数量成反比，最快的是最小的模型。猜画像用途：长输入短输出是检索问答或摘要，短输入长输出是生成或推理，高缓存比例是多轮对话或智能体。

**任务 2：给一个真实客户压缩评测集**

- **场景**：客户的产品依赖代码生成和长上下文推理，想快速知道"这个模型够不够用"。全量跑评测太贵。把评测集剪到最小、但仍能给出可信的好坏判断。还要设计一个便宜的多模态探针，以备客户下季度加图像输入。
- **数据**：已经算好的模型输出和逐题得分。

| 评测集 | 能力 | 样本 | 模型 | 打分方式 |
|---|---|---:|---|---|
| LiveCodeBench v5 | 写代码 | 315 | gpt-oss-120b、kimi-k2.5、minimax-m2.5 | 沙箱跑测试，过或不过 |
| AA-LCR | 长上下文推理 | 100 | 同上三个 | 大模型当评委，打分有随机性 |
| MMMU | 多模态（前瞻） | 660 条参考（22 个学科 × 30） | glm-4.5v-fp8 | 大模型当评委 |

- **A 部分（重点）**：剪 LiveCodeBench 和 AA-LCR，既要让销售判断够不够用，也要让工程团队拿来做测试。
- **B 部分**：针对完整的约 1.2 万条 MMMU，选一个能专门暴露**图像编码器退化**的探针集，而不是泛泛的能力差距；只能通过标准的 OpenAI 接口和模型交互。
- **硬要求**：剪枝代码必须写成开源评测框架 `evalscope` 的扩展，按上游能接受的 PR 标准写，固定你开发时的 commit。
- **明确不及格的做法**：均匀随机抽样；按分数取最简单或最难的前 k 题；人工挑题；只对给的三个模型有效、换第四个就不成立的方法。
- **两份讲义**：A 给工程师（1 页）：为什么这样做、剪了多少、为什么够、B 部分怎么做、假设、有更多数据或实时接口或时间会怎么改。B 给销售、测试、产品（半页）：对客户沟通有什么改变、销售工程师明天怎么在 evalscope 里跑出放行结论、多模态探针比随机抽样多给了什么信号、产品经理为什么要关心。
- **好答案的样子**：
  - **选题**：每道题算两样东西：难度（几个模型平均得分）和区分度（模型之间分数差多大）。三个模型都对或都错的题不提供区分信息，优先砍。按难度分层，每层按区分度选，保证剪完后难度分布和全集相近。
  - **验证剪完还可信**：比较三件事：剪后分数和全集分数的差；模型排名是否不变（Kendall τ：两两比较排序一致的比例减不一致的比例，1 表示完全一致）；在客户的及格线上"放行或不放行"的结论是否一致。用自助法（bootstrap：从选中的题里有放回地重抽很多次）给剪后分数一个置信区间。
  - **防过拟合三个模型**：只有三个模型就只有三对排序，Kendall τ 只能取 −1、−1/3、1/3、1 四个值，"τ = 1" 证据很弱。做留一法：用两个模型选题，看第三个模型的结论是否保持；选题只用题目本身的特征（难度、类别、长度）做分层，少依赖具体模型的对错。
  - **评委噪声**：AA-LCR 是大模型打分，同一答案重打可能不同。同一批答案重打几次，量出评委自己的波动；剪后分数的变化小于这个波动就不该解读为差异。
  - **多模态探针**：按图像类型分层（图表、表格、小字、公式、化学结构、高分辨率细节图），这些最考验编码器；同一组题分别带图和只给文字各跑一次，"带图比不带图多答对的部分"就是视觉增益，增益下降才说明编码器退化；再对图做降采样、裁剪、压缩，看准确率掉多少。
- **和你要面的岗位的关系**：剪评测集 = 回归套件分档（用最少的测试拿到可信信号）；红黄绿结论 = 发布门；异常标记 = 性能回归检测；评委噪声 = flaky。面试里被问到"你怎么在有限的硬件时间里做发布验证"，就用这套说法。

### 4.3 其他团队的带回家题（low priority）

| 题 | 要做什么 | 怎么评分 |
|---|---|---|
| 晶圆上的 Top-K 最近邻，72 小时，鼓励用 AI | 用 Cerebras 自己的内核语言，把数据分到 P×P 个处理单元上，算出和查询向量最近的 K 行，距离相同按原始下标排序；每个单元约 48 KB 内存 | 100 分：基础用例正确 25、5 个边界用例 25、三次运行结果逐位相同 10、性能 20、一页设计说明 15、代码清晰 5；基础用例错直接 0 分。设计说明要写路由、局部 Top-K 算法和每元素周期估算、带宽账、并列排序的正确性论证、多一倍时间会做什么 |
| 资产追踪（实习） | Next.js 做扫码流程、经理看板、三个系统（运营、设施、财务）的对账报告，10–12 小时 | 不打分表，看六件事：扫码体验、对账是分类还是只做差异、经理页的信息取舍、代码判断、主动不做什么、沟通；README 要写"三个差点做反的决定"，对题目提出质疑算加分 |
| EEPROM 读写（C） | 在一个按 32 字节分页的 8192 字节存储上实现按偏移和长度读写，自己写测试函数 | 没有公开的评分标准；关键在跨页的读写拆分和边界测试 |
