# Kaiju Cats：地图模型 + 模拟器 + 搜索

Kaiju Cats 是 Roblox 官方给候选人的练习游戏（Roblox 游戏 ID `13977123257`），和正式的游戏化测评是同一类玩法。
正式测评会换关卡，所以这里真正要练的是一套流程：**先建模、再确认、然后模拟、对账，最后才搜索**。

```bash
cd vault/interviews/companies/roblox/games/kaiju_cats
python3 -m unittest test_sim -v                            # 每条规则一条测试，外加两张真实地图的基线
uv run --no-project --with matplotlib python3 render_board.py            # board.py 的当前地图 → board.png
python3 solve.py --rebound stay                            # 搜索 → plan_stay.json（约几分钟）
uv run --no-project --with matplotlib python3 render_board.py plan_stay.json   # 方案图：指令 + 三猫路线
```

## 流程（v1 失败后定下的规矩）

1. **转录地图**，写进 `board.py`（地图的唯一来源），用 `render_board.py` 渲染，再和截图逐格对照。
2. **列规则**：分成“游戏原文写明的”“Chi 确认的”“待校准的”三类，逐条请 Chi 确认。
3. **写模拟器**：每条规则一条测试，测试用小地图，让这条规则成为地图上唯一在发生的事。
4. **对账**：拿一个在游戏里真实测过的方案，比较模拟出的分数和游戏里的分数。待校准的规则就在这一步定下来。
5. **最后才搜索**，并且搜到的方案要在游戏里跑一次确认。

v1（PR #41）跳过了第 1、2、4 步：地图认错了一半以上的格子，规则也是猜的，所以搜出来的方案在游戏里完全不能用。

## 搜索（`solve.py`）

1. **单猫穷举**：每只猫单独在地图上跑，在它拆的每一层上，把 7 种选择全部展开：不挂指令、四个转向、Stomp、Power Up。
   每一回合合并相同的状态，只保留花钱最少的那条路径。一只猫大约 30 秒。
2. **三猫组合**：拆的楼层互不重叠、任何回合都不在同一格、不迎面交换、总花费不超过 $200 的三元组，
   在完整模拟里的结果就等于三次单猫运行的组合，所以这一步得到的分数是精确的。从上界最高的组合开始扫描，一旦上界低于当前最好分数就停止。
3. **逐猫打磨**：在完整的三猫模拟里，固定两只猫的指令，重新搜第三只猫，三只猫轮流做，直到谁都改不出更高分。
   这一步能找到第 2 步漏掉的方案，比如两只猫分别拆同一栋楼的两层。

**局限**：第 2 步只覆盖“互不干扰”的方案；第 3 步是局部最优。所以结果是**已知最好**，不是证明过的全局最优。
每个结果都会在报告之前用 `sim.simulate` 重放一遍，确认分数。

## 思路总结

1. **分数几乎全部来自一只主力猫乘上 ×2 的次数。** 电厂 ×2 和进窝 ×5 是乘法，楼层的 +250 / +500 和 Power Up 的 +1000 是加法。
   所以要先加后乘：Power Up 放在早期，后面每过一个电厂，这 +1000 就跟着翻一倍；电厂尽量留到后面。
2. **进窝顺序由规则自动排好**：同一回合到达时，power 低的先进。让三只猫都在最后一回合同时进窝，最强的那只自然拿到 ×5。
3. **没进窝的活猫也计分。** 有时候让一只猫在外面来回拆楼，比花钱给它规划进窝路线更划算。
4. **撞墙会原地掉头**，而且不花钱，等于免费的“调头”指令。好方案会大量用边界反弹，省下转向指令的钱。
5. **搜索方法**：单猫穷举生成候选路线，再在完整模拟里做多起点的轮流最佳应对。一次最佳应对大约 1 秒，比“单猫结果组合 + 上界剪枝”快得多，后者在这里会组合爆炸。

## 教训（按代价从高到低）

1. **地图认错一半，全盘作废（v1）。** 地图必须先渲染成图，和截图逐格对照；规则分成“游戏原文 / Chi 确认 / 待校准”三类，确认后再写代码。
2. **规则靠猜，结果就不能用。** v1 猜了拆楼规则和计分规则。这次的“没进窝的猫算不算分”一开始也答错了，是 Chi 事后纠正的。
   规则一变，最优策略就变，所以任何“待定”都要做成开关，并在结果里写出不同读法下的分数。
3. **计价要和游戏一致。** 模拟器只在指令被触发时扣钱，但游戏是挂上就收钱。搜索因此留下了死指令，总价超过预算，最后导致崩溃。
4. **搜索不能超过 5 分钟。** “组合 + 上界剪枝”阶段跑了 10 多分钟没出结果。改成“随时可以交出结果”的结构后：硬性时间上限，每次刷新最好分数立刻存盘，
   第 10 秒就有第一个可用方案。
5. **渲染直接做更快。** 把渲染交给 subagent 花了约 4 分钟；本地一条命令只要几秒。只有需要写说明文档时才值得交给 subagent。
6. **等待脚本的匹配条件要精确。** 用 `grep "best "` 等搜索结束，却匹配到了 `best raw`，导致提前结束；应该匹配行首的 `^best`。
