# qA14 LC 150 Evaluate Reverse Polish Notation — report

## Summary
栈求值的经典热身题：LeetCode 150，"用栈求逆波兰表达式的值"。核心考点是除法的取整方向——
Python 的 `//` 向负无穷取整，这道题（和大多数语言的原生整数除法一样）要求**向零截断**，
两者在恰好有一个操作数为负时会给出不同结果，这是本题最经典的坑，也是三个 part 里反复
被测的主线。Part 1 是 LC 原题签名；Part 2 加一个"每步计算过程"的 trace 输出（调试工具
常见需求）；Part 3 把"假设输入合法"这个前提去掉，要求任何畸形输入都返回诊断码而不是抛
异常。

## 逐 part 思路
1. **Part 1**：标准单栈求值，`_apply` 分派四则运算，除法单独走 `_truncate_divide`——用
   `abs(a) // abs(b)` 再按符号决定要不要取负，而不是直接用 `int(a / b)`（浮点在数值很大
   时会丢精度）或 `a // b`（方向错误）。
2. **Part 2**：完全复用 Part 1 的求值逻辑，只是在每次应用运算符时多记一行
   `"<a> <op> <b> = <result>"`（用运算发生时弹出的原始 `a`、`b`，不是之后任何再加工过的
   值），最后统一加一行 `RESULT <value>`——即使输入只有一个操作数、一次运算符都没有，也要
   有这行 `RESULT`，保证下游工具永远能从输出里读到最终答案。
3. **Part 3**：同样的算术逻辑，但假设输入可能是任何东西。用一个正则
   `^-?[0-9]+$` 区分"合法操作数"和"未知 token"（注意单独的 `"-"` 不会匹配这个正则，因为
   它已经在 `OPERATORS` 集合里被识别成运算符，两者不冲突）。五种错误按"从左到右扫描，
   第一个触发的错误胜出"的优先级返回：`empty_input`（扫描前就能判定）> `unknown_token`
   （非法 token）> `insufficient_operands`（运算符出现时栈里不够两个数）>
   `division_by_zero`（除号且被弹出的除数是 0）> `trailing_operands`（扫描结束后栈里
   不多不少剩一个才算成功，剩多个是这一类）。

## Hidden tests 会打的坑
- 除法向零截断：`(-7)/2` 应该是 `-3`（截断），不是 `-4`（`//` 会给的地板除结果）——测试
  专门构造了四种符号组合（`--`、`-+`、`+-`、`++`）以及一个"恰好整除"的对照组（这种情况下
  两种取整方式结果相同，不能用来区分实现对不对）。
- 多位数和负数字面量必须整 token 解析（`-13` 是一个操作数 token，不是运算符 `-` 后面跟
  `13`）——因为 token 本来就是按空白分隔的，不会有歧义，但正则必须精确到"不接受裸的
  `-`"，否则 Part 3 会把合法的减号运算符也误判成畸形操作数。
- 减法/除法的操作数顺序：先弹出的是 `b`（栈顶），后弹出的是 `a`（次栈顶），结果是
  `a op b` 而不是 `b op a`——`["10","3","-"]` 是 `10-3=7`，`["3","10","-"]` 是
  `3-10=-7`，顺序反了会两个测试都过一半、错一半。
- Part 2 的零运算符情形（单操作数表达式）：trace 输出只有一行 `RESULT <v>`，没有任何
  运算符行——容易被忽略的边界。
- Part 3 的错误优先级不是"哪个错误听起来更严重"，而是"从左到右第一个真正触发的"：
  `["/", "0"]` 在第一个 token 就因为栈空触发 `insufficient_operands`，永远不会走到"剩下
  一个 `0` 没被消费"这个 `trailing_operands` 的判断；`["1","0","/","9","9"]` 在第三个
  token 就因为除以 0 提前返回，根本不会扫到后面那对 `"9","9"`。
- `insufficient_operands`（运算符想要两个数，栈里不够）和 `trailing_operands`（扫描完了，
  栈里剩多个数）是两类互斥的失败原因——运算符本身不会触发 `trailing_operands`，光有多余
  操作数也不会触发 `insufficient_operands`。

## 复杂度与实测
三个 part 都是 `O(n)`（`n` = token 数），单次栈扫描，栈的峰值大小与嵌套深度相关但受
LC 约束（`n <= 10^4`）限制，空间上界也是 `O(n)`。实测（`random.Random(0)` 构造一条
9999-token、5000 个操作数、左结合的加法链，跑 Part 1 全流程）：`test_perf_1e4_tokens`
通过 `run_script` 子进程测量，预算 2s / 256MB，实测远低于预算（这个规模下运行在毫秒
级）。

## 本题覆盖的知识点
- **S02**（token 级解析）：用正则精确区分"操作数"和"运算符"两类 token，尤其是裸 `-`
  （运算符）和 `-13`（负数操作数）不能混淆。
- **S09**（字节级精确输出格式）：`RESULT <v>`、`ERROR <code>`、`<a> <op> <b> = <result>`
  三种输出行格式全部固定，不做任何多余修饰。
- **S18**（校验与错误路径）：Part 3 把"假设输入合法"这个前提整个撤掉，要求五种不同的
  畸形原因都有唯一且确定的诊断码，且有明确的优先级顺序而不是"随便报一个错就行"。
- **S21**（stdlib/栈 熟练度）：单栈线性扫描完成四则运算求值；除法取整方向用整数运算
  （`abs`/`//`/符号判断）而不是浮点或 Python 原生 `//`，避免精度问题和方向错误。

## 面试官会怎么追问
- "如果要支持括号和运算符优先级（中缀表达式）呢？"——把候选人引向 LC 224/227，说明这题
  只是"栈做全部工作"的最简形态，加括号和优先级需要 Shunting-yard 或递归下降解析器，
  是完全不同的复杂度量级。
- "Part 3 的错误码要不要合并成一个统一的 `ERROR malformed_input`？"——可以借此讨论
  "调试信息的颗粒度换来的复杂度值不值"，本题选择"five distinct, testable reasons"是刻意
  设计，为了让隐藏测试能锁定候选人是不是把每种情况都想到了，而不是用一个大而化之的
  异常吞掉所有情况。
- "为什么不用 `math.trunc(a / b)`？"——引导候选人注意到浮点数在大整数场景下会丢精度，
  纯整数运算（`abs(a)//abs(b)` 加符号判断）在任意大小的输入下都是精确的。
