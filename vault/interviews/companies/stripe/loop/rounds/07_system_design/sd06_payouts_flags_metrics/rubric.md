# 评分 rubric（Exponent 五维，1–4 分/维，满分 20；三道短题分别评分后取整体印象分）

> 依据 `loop/LOOP_GUIDE.md` §7、`loop/raw/system_design.md` §4.6（Connect 分账/payout）与培训站转述（feature flag、metrics）。三道题各自独立，但面试官通常会在每道题上都用同一套五维标准快速判断，重点考察"能不能在短时间内切中要害"，而不是每道题都要求生产级完整度。

## 1. Problem framing

- **1 分（任一子题）**：Connect 分账题一上来就画 transfer/payout 的表结构，没有先说"平台资金和商户资金必须账目分开、转账要么完全发生要么完全不发生"；Feature flag 题没有区分"配置管理"和"运行时判定"两个不同性质的问题；Metrics 题没有区分"写路径要能扛住高吞吐"和"读路径要支持灵活查询"这两个相反的优化方向。
- **4 分（任一子题）**：每道题都能在 1–2 分钟内用一两句话点出核心矛盾——分账题："这是资金原子性 + 防止透支的问题"；Feature flag 题："这是判定延迟要求极低、但配置变更相对不频繁的读多写少问题，要把慢路径（配置管理）和快路径（判定）分开"；Metrics 题："写入量远大于读取量，要在采集端做好本地聚合，不能每条原始数据都直接写入中心存储"。

## 2. API & data model

- **1 分**：分账题没有区分"转账（transfer）"和"提现（payout）"两个不同的对象；Feature flag 题的 API 只考虑了"读一个开关值"，没考虑 SDK 怎么本地缓存、怎么处理默认值和降级；Metrics 题没有设计聚合前后的两种数据形态（原始事件 vs 聚合后的时间序列点）。
- **4 分**：分账题给出 `POST /v1/transfers`、`POST /v1/payouts`、`GET /v1/balance`（区分 pending/available）等资源化 API，数据模型里有独立的 `balance_transactions` 记录每一笔余额变化的来源；Feature flag 题给出 SDK 侧的 `is_enabled(flag_key, context) → bool` 本地判定接口和管理侧的规则配置接口，讲清楚规则如何从中心配置分发到各服务实例；Metrics 题区分客户端本地聚合的计数器/直方图结构与服务端接收后的时间序列存储结构。

## 3. Failure modes & scale

- **1 分**：分账题没考虑"提现几天后被银行退回"这种异步失败；Feature flag 题没考虑"配置中心不可用时判定组件怎么办"；Metrics 题没考虑"采集端和聚合端之间网络不通时数据怎么办，会不会因为等待上报而拖慢业务请求"。
- **4 分**：分账题讲清楚"银行退回"要走反向分录恢复余额并通知商户，负余额场景下如何触发 debit payout；Feature flag 题明确判定组件要 **fail-open 到一个预设默认值**（配置中心挂了不能让所有请求判断报错甚至阻塞），且 SDK 本地缓存最近一次成功拉取的规则；Metrics 题讲清楚上报必须是异步、非阻塞的（哪怕丢失几条指标数据也不能拖慢业务请求本身），并讨论采样/降精度应对超高基数场景。

## 4. Separation of concerns

- **1 分**：三道题里任意一道把"判定/计算逻辑"和"配置管理/数据存储"揉在一起，改一个规则/开关需要重新部署业务代码。
- **4 分**：分账题里"资金移动的记账"复用独立的 ledger 服务（不重新发明）；Feature flag 题里"规则怎么配"（管理后台/慢路径）与"规则怎么判定"（SDK 内嵌逻辑/快路径）清楚分离；Metrics 题里"采集端本地聚合"与"服务端存储/查询/告警"是两个独立可扩展的组件。

## 5. Delivery beyond the diagram

- **1 分**：三道题都没有提上线怎么验证、怎么监控这套系统本身是否工作正常。
- **4 分**：Feature flag 题提到新 flag 上线要有"先小流量灰度、可一键全部关闭"的能力；Metrics 题提到系统本身的健康度也要被监控（比如上报丢失率）；分账题提到 payout 批次生成有明确的 cut-off 时间和失败重跑策略。

## 一条相关提醒

三道题都属于置信度 medium 的组合题（培训站转述为主），但每一道都对应 Stripe 真实存在的系统（Connect、内部 feature flag 平台、内部 metrics/APM 系统）。这类"短题三连"最考验的其实是**时间管理**——如果第一题就讲了 20 分钟画出一个非常完整的架构，后面两题会被严重压缩甚至讲不完，这本身在"delivery"维度会被扣分（面试官会认为你不懂得在受限时间内做优先级取舍）。
