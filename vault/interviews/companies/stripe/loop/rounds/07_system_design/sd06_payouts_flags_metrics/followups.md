# 追问预案（≥8 条，覆盖三道短题）

> 取材：Stripe 文档 Payouts；`loop/raw/system_design.md` §4.6；培训站转述（feature flag、metrics 部分置信度 medium）。

## Connect 分账 / Payout

### 1. 两个账户在不同分片上，怎么保证转账的原子性？

**期望要点**：不用跨分片分布式事务；用 saga——源账户先"预留"金额（`available -= amount`，`held += amount`），目标账户入账成功后源账户再正式终结这笔转账；任一步失败在已完成的一侧追加补偿分录回滚。用 `external_id` 保证每一步都幂等、可安全重放。

### 2. `pending` 余额和 `available` 余额有什么区别，为什么要分开？

**期望要点**：`pending` 是已经产生但尚未完成结算周期（如 T+2/T+3）的资金，`available` 是已经完成结算、可以自由提现的资金；分开的目的是防止商户在资金还没真正到账前就把钱提走，一旦后续出现退款/争议，平台还有缓冲空间可以从未结算的部分扣回，而不需要向已经提现的商户追讨。

### 3. Payout 提现之后三天，银行说账户不存在，钱退回来了，怎么处理？

**期望要点**：这是异步失败，写一条反向的 `balance_transaction` 恢复该账户的 `available` 余额，同时通过 Webhook 通知商户提现失败及原因（如 `no_account`），必要时暂停该账户的自动提现计划直到商户更新银行信息。

### 4. 怎么防止商户把还没有真正结算完成的钱提走？

**期望要点**：提现接口只允许操作 `available` 余额，`pending` 余额在结算周期完成之前不可被提现接口访问到；如果风控需要额外保留一部分资金，可以引入一个独立的 reserve（保留金）账户，在计算真正可提现金额时先扣除保留金部分。

## Feature Flag SDK

### 5. 配置中心挂了，所有服务实例的功能开关判断会不会跟着挂？

**期望要点**：不会。SDK 在本地内存里缓存最近一次成功拉取的规则，配置中心不可用时继续用本地缓存做判定；如果服务刚启动还从未成功拉取过配置，回退到预设的静态默认值。判定逻辑本身是纯本地计算，不依赖一次实时的网络请求，这是保证低延迟和高可用的核心设计。

### 6. 同一个用户在灰度百分比不变的情况下，会不会这次刷到功能、下次又刷不到？

**期望要点**：不会。判定用一致性哈希把 `user_id`（或其他维度）映射到一个稳定的数值区间，只要灰度百分比配置本身没变，同一个输入每次计算出的结果都是确定的，不依赖随机数或者请求到达的先后顺序。

### 7. 紧急情况下需要立刻把一个出问题的新功能全部关掉，多快能生效？

**期望要点**：kill switch 设计成独立于常规灰度规则、优先级最高的字段，一旦置位判定逻辑直接短路返回"关闭"；生效速度取决于配置从中心分发到各服务实例本地缓存的延迟（通常是秒级到数十秒级，可以通过推送而不是纯轮询拉取来进一步缩短），这个延迟应该被明确告知使用方，不能承诺"瞬间全局生效"。

## Metrics Counter Library

### 8. 为什么客户端要先本地聚合，而不是每次调用都直接上报一条原始数据？

**期望要点**：业务系统的调用频率通常远高于我们真正需要的指标粒度（比如"每 10 秒的调用总数"远比"每一次调用各发一条数据"要有效得多）；客户端本地在一个时间窗口内先做求和/计数/近似直方图聚合，能把上报的数据量降低几个数量级，避免采集本身成为业务系统和网络的额外负担。

### 9. 指标上报和业务请求之间如果网络抖动，会不会拖慢业务本身？

**期望要点**：不会，前提是设计成异步、非阻塞——指标数据先写入本地内存缓冲，由独立的后台线程/进程批量异步发送，发送失败时在有限缓冲内重试，超过缓冲上限直接丢弃最旧的数据，绝不能让指标上报的失败或延迟反过来阻塞正在处理的业务请求。

### 10. 某个维度的组合数量（基数）爆炸式增长，会对系统造成什么影响，怎么应对？

**期望要点**：高基数会导致服务端需要存储和索引的时间序列数量呈爆炸式增长，拖慢查询、增加存储成本；应对方式是在客户端库层面限制可以用来打标签（tag）的字段种类（比如禁止把用户 ID 这种高基数字段直接作为 tag），或者对高基数维度做采样/聚合降维，把细粒度的数据只保留较短时间，聚合后的粗粒度数据保留更长时间。
