# 评分 rubric（Exponent 五维，1–4 分/维，满分 20）

> 依据 `loop/LOOP_GUIDE.md` §7、`loop/raw/system_design.md` §4.4（含 Stripe 官方博客《Scaling your API with rate limiters》的四层限流设计）。这道题看似是"背算法"，但 Stripe 真正想看的是"限速组件自己挂了怎么办"这个反直觉的失败模式思考。

## 1. Problem framing

- **1 分**：一上来就讲"token bucket 还是 sliding window"，没有先厘清题目里混在一起的几种诉求——按客户端限速、按操作类型/端点限速、并发请求数限制、系统整体过载时的优先级降级，这是四个不同粒度的问题。
- **4 分**：先拆解需求："这里其实是四个不同粒度的保护机制"，并确认哪些是必须做的（按客户端限速是核心）、哪些是加分项（分级降级）；显式说出不变量——限速判断延迟要足够低（不能成为请求路径的瓶颈）、限速组件自身故障不能拖垮整体可用性（fail-open 而不是 fail-closed）。

## 2. API & data model（权重最高）

- **1 分**：只说"用 Redis 存计数器"，没有给出具体的 key 设计、没有说清楚响应里怎么告诉客户端"你被限速了、什么时候可以重试"。
- **4 分**：给出清晰的内部判定接口（`allow(key, rule) → {allowed, remaining, retry_after}`）与对外的 429 响应契约（`Retry-After` 头 + 一个说明限速原因的头，比如"全局限速"还是"并发限制"还是"端点级限速"）；限速规则的配置（每客户端/每端点的具体阈值）与执行路径解耦，配置变更走独立的管理接口而不是硬编码。

## 3. Failure modes & scale

- **1 分**：默认限速组件（如 Redis）永远可用，没有讨论它挂了怎么办；固定窗口算法且没意识到窗口边界的双倍流量问题；多实例场景下用本地内存计数器却声称"实现了限速"。
- **4 分**：明确选择 token bucket 或 sliding window counter 并说清为什么不用固定窗口（边界处理不当会让允许的流量在窗口交界处翻倍）；用 Redis + 原子脚本（如 Lua）保证多实例并发读写的正确性；**重点讨论限速组件本身故障时的策略——fail-open（放行）配合告警，而不是 fail-closed（全部拒绝）**，并能说清楚为什么在这个场景下 fail-open 是正确默认（支付类 API 的可用性优先于严格限速）；讨论本地令牌桶吸收热点 + 远端定期校准的两级架构应对多区域场景。

## 4. Separation of concerns

- **1 分**：把限速规则的存储、判定逻辑、和降级策略全部耦合在网关的同一段代码里，改一个客户端的限额需要重新部署网关。
- **4 分**：策略管理（慢路径：规则存储在数据库，变更后推送到网关本地缓存）与请求执行（快路径：网关读本地缓存做判定，不必每次请求都查数据库）清楚分离；不同粒度的保护机制（per-client rate、per-endpoint rate、并发数限制、全局过载降级）是独立的层，可以分别开关和调参，而不是揉在一起。

## 5. Delivery beyond the diagram

- **1 分**：没有提怎么上线一个新的限速策略，好像配置改了就立刻生效没有任何风险。
- **4 分**：提到新策略上线要先"只记录不拒绝"（dark launch）观察一段时间的误杀率，确认没有意外拒绝合法流量后再真正启用；提到关键监控（按客户端/端点的 429 率、限速组件的错误率与 fail-open 触发次数、判定延迟）；提到给限速器整体加一个可以紧急关闭的开关（kill switch）。

## 一条相关引用（反直觉的正确答案）

> Stripe 官方博客《Scaling your API with rate limiters》（2017）里的设计思路强调：限速器本身要能被功能开关一键关闭，且面对自身故障时的默认行为是**放行**而非拒绝——直觉上"限速器挂了应该拒绝所有请求以策安全"是错的，因为对 Stripe 而言，"因为保护机制自己出故障而拒绝所有正常支付请求"造成的损失，远大于"暂时放过一些原本该被限速的流量"。候选人如果坚持"限速器挂了就该 fail-closed"且说不出这个权衡背后的业务逻辑，这一维通常拿不到满分。
