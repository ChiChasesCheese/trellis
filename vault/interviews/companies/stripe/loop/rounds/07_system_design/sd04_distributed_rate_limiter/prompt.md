# Distributed rate limiter

我们对外的 API 网关每天要承接来自成千上万个不同商户的请求，这些商户用的是各自的 API 密钥，他们的调用模式千差万别——有的商户业务很小，几乎不怎么调用；有的商户是大型平台，正常情况下每秒稳定打几百个请求，但偶尔也会因为自己代码里的 bug 或者促销活动突然在短时间内打出去几万个请求。我们不希望某一个商户的异常流量把我们整个 API 网关的资源占满，进而影响到其他所有商户的正常调用，也不希望因为某个客户端的重试逻辑写得不好（比如遇到失败就立刻疯狂重试）而导致这种情况被放大。同时我们的网关是部署在很多台机器上的集群，一个商户的请求可能这次落到这台机器、下次落到那台机器，所以限速这件事没办法简单地在单台机器内部用一个计数器解决，必须是所有机器共享同一份限速状态。反过来，我们也很清楚，用来做限速判断的那个组件本身也可能出故障、变慢，如果因为限速组件挂了就导致所有正常的 API 请求全部被拒绝，那代价比"暂时放过一些本该被限速的请求"要严重得多。除此之外，不同类型的操作对我们系统的压力是不一样的——有些是简单的只读查询，有些则会触发比较重的计算或者外部调用，我们希望限速策略能够区分对待，并且在真正遇到大规模突发流量、系统整体压力很大的时候，还能有一层机制优先保障最关键的业务操作能正常进行，牺牲掉一些不那么紧急的请求。请设计这样一套限速系统。

---

**面试环境说明**：Stripe onsite System Design 轮，45 分钟（含开场与结尾提问，真正设计时间约 30–35 分钟），Whimsical 白板作图，无代码环境。题面里刻意混杂了"按客户端限速""按操作类型限速""系统整体过载时的降级"这几种不完全相同的诉求，你需要自己在开场把它们拆解清楚并确认优先级，而不是笼统地设计成一个万能的"限流器"。面试官后续会重点考察算法选择的权衡、限速组件自身故障时的降级策略、以及多实例共享状态下的一致性代价。
