# 模型答案：设计分布式 Rate Limiter（API 网关）

> 取材：Stripe《Scaling your API with rate limiters》（2017-03-30）；Stripe 文档 Rate limits；`loop/raw/system_design.md` §4.4。按 `LOOP_GUIDE.md` §7 主线组织（本题不涉及"账要平"这类记账不变量，主线相应调整为"判定正确、组件自身不能成为单点故障"）。

## 0. 两句话复述 + 不变量

**复述**：API 网关面对成千上万个商户的多样化调用模式，需要一套能防止单一客户端异常流量拖垮整个系统、同时在系统整体承压时能优先保障关键业务的限速机制；网关本身是多实例集群，限速状态必须在实例间共享。

**核心不变量**：

1. **判定延迟必须足够低**：限速判断本身不能成为请求路径上的显著瓶颈（目标毫秒级以内）。
2. **限速组件的故障不能拖垮业务可用性**：限速器挂了，默认放行请求（fail-open）而不是拒绝所有请求（fail-closed），因为保护机制自己出故障造成的损失要远小于错误拒绝所有合法流量的损失。
3. **限速是近似保护，不是精确计费**：允许在多实例并发场景下出现少量超出配额的情况，不追求绝对精确。
4. **策略可以动态调整**，不需要重新部署网关就能改变某个客户端的限额。

明确不做什么：限速不用来做计费依据（计费走独立的、精确的用量统计系统）；不追求跨全球所有区域的强一致计数。

## 1. 需求拆解（这道题最容易漏的一步）

题面里其实混杂了四种不同粒度的保护机制，开场就要拆开说清楚：

1. **按客户端限速**（request rate limiter）：每个 API key 每秒/每分钟允许的请求数，处理绝大多数正常场景。
2. **并发请求数限制**（concurrent requests limiter）：某些操作本身耗时较长或消耗资源较多，即便请求速率不高，同时在途的请求数也要有上限，防止客户端的重试风暴在慢端点上无限堆积。
3. **端点/操作类型级限速**：不同操作对系统的压力不同，需要能单独配置阈值。
4. **系统整体过载时的分级降级**（load shedding）：在真正的大规模异常流量或基础设施事故下，按请求的重要程度分级丢弃，优先保障最关键的操作（如发起支付）而牺牲次要操作（如列表查询）。

## 2. API 契约

```
内部判定接口（网关调用）：
  allow(key, rule[]) → {allowed: bool, remaining: int, retry_after_ms: int, reason: str}

配置管理接口（慢路径，管理员/自动化调用）：
  PUT /internal/ratelimits/{account}
    {global_rps, endpoint_overrides: {...}, concurrency_limit}

对客户端的响应契约：
  429 Too Many Requests
  Headers:
    Retry-After: <秒数>
    X-Rate-Limit-Reason: global-rate | endpoint-rate | global-concurrency | endpoint-concurrency
```

契约细则：

- `reason` 字段很重要——客户端能区分"我这个账户整体超限了"还是"我调用的这个具体端点超限了"还是"我的并发请求数太多了"，从而采取不同的应对策略（前者应该整体降速，后者可能只需要减少并发）。
- 限速规则的配置存储与判定执行完全解耦：配置变更走独立的管理接口写入持久化存储，网关定期拉取或订阅变更，本地缓存后在请求路径上直接读缓存，避免每次请求都查一次配置存储。

## 2.5 四层防护（Stripe 官方博客的真实架构，讲出来加分）

Stripe 公开博客里描述的实际做法是把保护机制拆成四层，各自应对不同规模的异常：

1. **Request rate limiter**：每客户端每秒请求数限制，用 token bucket 实现，处理绝大多数日常场景。
2. **Concurrent requests limiter**：每客户端同时在途请求数上限（如 ≤20），专门针对"重试风暴打在一个本来就慢的端点上"这种场景——速率可能没超，但堆积的在途请求已经很危险。
3. **Fleet usage load shedder**：为关键请求（如创建支付）预留一部分处理容量，非关键请求（如列表查询）在整体负载升高时先被削减。
4. **Worker utilization load shedder**：在真正的重大事故场景下，按优先级从低到高逐级丢弃负载——先削测试模式流量、再削普通 GET 查询、最后才会影响到最核心的写操作。

这四层是层层递进的关系：前两层解决"某一个客户端行为异常"，后两层解决"系统整体承压，需要在所有客户端之间做优先级排序"，两类问题不应该用同一套机制解决。

## 3. 算法选择

- **Token bucket**（Stripe 实际采用）：每个客户端维护一个令牌桶，固定速率补充令牌，请求消耗令牌；允许一定程度的突发流量（桶的容量决定突发上限），实现上用 Redis 存 `{tokens, last_refill_ts}`，配合 Lua 脚本把"计算补充量 + 尝试扣减"打包成一次原子操作，避免并发请求之间出现竞态。
- **固定窗口计数器**：实现简单但有明显缺陷——窗口边界附近可能出现允许流量翻倍的问题（比如窗口末尾涌入一批请求，紧接着新窗口开始又涌入一批，两批加起来远超预期速率），不推荐作为主要方案。
- **滑动窗口计数器**：用两个相邻固定窗口加权平均近似滑动窗口的效果，内存开销比精确的滑动窗口日志小很多，是一个工程上性价比较高的折中方案。
- **并发数限制**：用 Redis 的 `INCR`/`DECR` 在请求开始和结束时分别记录在途请求数，为防止请求异常中断导致计数泄漏，配合较短的 TTL 或者用带过期时间的记录结构。

## 4. 数据模型 / 存储

```
Redis（集群）：
  key = "rl:{account}:{scope}"
  按 account 做一致性哈希分片，保证同一个账户的所有相关 key
  落在同一个分片上，这样 Lua 脚本能在单分片内完成原子操作

规则配置（持久化存储，如关系数据库）：
  rate_limit_rules(account_id, scope, limit_value, window, updated_at)
  变更后推送/失效通知给网关，网关本地缓存 TTL 到期或收到失效通知后刷新
```

存储细节：每个 key 的值是一个小型结构（当前令牌数 + 上次补充时间戳），不需要为每一次请求单独存一条记录；TTL 设置为略长于窗口周期，避免长期不活跃的客户端在 Redis 里累积永久占用内存的僵尸 key。

**两级架构（应对多区域和降低远端依赖）**：每个网关实例先用本地内存令牌桶吸收绝大部分判定请求（吸收热点、降低对 Redis 的访问压力），Redis 只做跨实例的全局校准，允许本地判定与全局状态之间存在短暂的不一致——这是"限速是近似保护"这个不变量在架构上的直接体现。

## 4.5 幂等性的一点补充说明

限速判定本身不需要幂等键——同一个业务请求即便因为客户端重试被限速器判定了两次，最坏结果也只是"这次判定的宽严程度有微小出入"，不会造成任何业务后果。但**限速规则的配置变更接口**（`PUT /internal/ratelimits/{account}`）应该设计成幂等的（同样的配置提交多次结果一致），这是所有管理类接口的通用最佳实践，值得在面试里顺带提一句以体现设计的一致性。

## 5. 一致性与多区域

- **单区域内**：Redis 集中存储计数状态，多个网关实例并发访问时通过 Lua 脚本保证判定的原子性；允许因为网络延迟等因素出现极少量的轻微超限，可接受。
- **多区域**：不追求全局强一致（跨区域同步计数的延迟代价对限速判断这种要求低延迟的场景不划算）；采用"每个区域独立配额"（按预期流量分布把全局配额切分到各区域）或者"本地近似判定 + 异步向中心汇总校准"的方式，明确告诉面试官这是有意为之的权衡：宁可略微放过一点流量，也不接受为了精确同步而增加请求路径的延迟。

## 6. 失败处理

- **限速组件（Redis）不可用**：默认 **fail-open**（放行所有请求）并触发告警，同时可以降级到网关本地内存计数作为退而求其次的保护（虽然精度和跨实例一致性都会下降，但好过完全没有任何限速）。这是本题最核心的反直觉设计点：直觉上"保护机制挂了应该更保守地拒绝"，但对支付类 API 而言，因为保护机制自身故障而拒绝所有合法请求的代价远大于暂时放过一些流量。
- **判定本身超时/变慢**：给 Lua 脚本执行设置很短的超时（如个位数毫秒级），超时直接判定为放行，不能让限速判断本身成为请求延迟的主要来源。
- **客户端重试风暴**：这是并发数限制器专门要治理的场景——即便速率限制没超，短时间内堆积大量在途请求本身就是一种异常模式，需要客户端配合实现指数退避加抖动的重试策略（我们在文档里要求，服务端的并发限制作为兜底）。
- **系统整体过载**：分级降级——为关键业务操作（如创建支付）预留专门的资源配额，非关键操作（如列表查询）在整体压力大时优先被削减；极端情况下甚至可以按优先级逐级降级到"只保留最核心的写操作"。
- **上线风险控制**：新的限速规则或算法变更先以"只记录判定结果、不真正拒绝请求"的方式跑一段时间（dark launch），确认误杀率可接受后再真正启用拒绝逻辑。

## 7. 对账 / 一致性验证

限速不是记账系统，没有"必须精确平账"的要求，但仍然需要：定期核对判定日志与实际业务流量分布，发现"某个客户端一直被误判超限"或者"某类请求完全没有被限速覆盖到"这类配置遗漏，作为持续调优限速规则的依据。

## 8. 可观测性 + rollout

**监控指标**：按客户端/按端点的 429 触发率、限速判定的 p99 延迟、Redis 错误率与 fail-open 触发次数、分级降级的触发频率、因为限速被拒绝后客户端的申诉/工单量（用于发现规则设置得过于激进）。

**rollout**：任何新规则先 dark launch 观察；给整个限速系统一个可以快速关闭的总开关；规则配置变更走审计留痕的管理接口，避免"谁改的限额、什么时候改的"无法追溯。

## 9. 规模估算（简要）

假设网关整体承接 10 万 rps 量级的请求，Redis 单分片可以承载数万级别的操作/秒，按账户维度分若干个分片；每个客户端的限速状态占用几十字节，即便账户数达到百万级别，总状态量也在可控的百兆量级，Redis 集群完全可以承载。

## 9.5 与其他题的关联

限速器是 API 网关的一部分，和 sd01（Webhook 投递）里讨论的"per-tenant 隔离、fail-open"是同一类思路在不同场景下的复用；和 sd02（幂等支付 API）不同的是，限速判断本身**不需要幂等**——同一个请求被判定两次是可以接受的（最多是保护力度略有出入），不像支付那样"判断两次"可能意味着"扣款两次"。面试时如果能主动点出"这道题的正确性要求比支付题松，所以可以用近似算法而不是强一致方案"，是对权衡本身的清晰认知。

## 10. 追问预演

- **"固定窗口和滑动窗口的核心区别，一句话讲清楚"**：固定窗口在窗口边界处会因为两个窗口首尾相接而允许瞬时流量翻倍；滑动窗口（或者用两个固定窗口加权近似）能平滑这个边界效应，代价是实现和状态存储稍微复杂一点。
- **"多实例场景下，两个实例几乎同时判定同一个客户端的请求，会不会都放行导致超限？"**：短暂的、小幅度的超限是可以接受的（这正是"近似保护"的含义），核心手段是把同一个客户端的所有判定都路由到 Redis 里的同一个 key 上并用原子脚本处理，把不一致的窗口尽量缩小到网络延迟级别而不是完全不做任何同步。
- **"大商户提前告知要做一次流量高峰（比如促销活动），怎么处理？"**：提前联系并临时调高该商户的限额配置（走慢路径的配置管理接口），同时建议商户自己的客户端也实现类似令牌桶的自限速逻辑，从两端共同平滑流量峰值，而不是完全依赖服务端硬扛。
- **"限速要不要考虑公平性，比如小商户和大商户之间会不会互相影响？"**：这正是"per-client 独立计数状态"这个设计的意义——每个客户端的令牌桶完全独立，一个大商户打满自己的配额不会消耗掉小商户的配额；如果面试官进一步问"共享基础设施资源（比如同一个 Redis 分片）会不会成为隐性的相互影响"，可以讨论按账户哈希分片、避免单一分片被少数超大客户端压垮，必要时对极少数超大客户端单独分配专属分片。
- **"429 之后客户端应该怎么做，我们需要在协议层面给出什么指导？"**：响应头里的 `Retry-After` 明确告诉客户端最短等待时间；`X-Rate-Limit-Reason` 让客户端知道是哪一层限制触发的，从而决定是"降低整体调用速率"还是"减少并发请求数"；官方 SDK 应该内置遵循这些头做指数退避加抖动的默认重试逻辑，减少客户端自己写出"失败就立刻重试"这种放大问题的代码。

## 11. 规模估算的补充推演

如果面试官继续追问"如果一个客户端的限速状态需要在数十个数据中心之间保持大致同步，架构会有什么变化"：可以讨论把"独立配额"细化为"按预期区域流量占比静态切分全局配额到各区域"，配合定期（如分钟级）的异步跨区域汇总来动态再平衡，而不是让每一次判定都跨区域同步——跨区域同步的网络延迟（通常几十到上百毫秒）远超判定本身需要的延迟预算，用这种异步再平衡的方式把"强一致的代价"转移到不在请求关键路径上的后台任务中。

## 12. 测试计划（delivery 维度的加分项）

- **单元/属性测试**：针对 token bucket 的补充与消耗逻辑做属性测试（例如"任意补充/消耗序列后剩余令牌数不应为负"）。
- **并发正确性测试**：模拟多个网关实例同时对同一个 key 发起判定，验证 Lua 脚本的原子性没有被破坏。
- **故障注入测试**：主动模拟 Redis 不可用、Lua 脚本执行超时，验证系统确实按预期 fail-open 并触发告警，而不是级联性地让所有请求都失败。
- **误杀率验证**：新规则上线前用 dark launch 模式跑一段时间，离线分析"如果真的启用拒绝会误杀多少合法请求"，确认在可接受范围内再真正切换。

## 13. 和"按角色/权限限流"的区别（容易被面试官拿来混淆的相邻话题）

如果面试官把这道题和内部授权系统（IAM）绕到一起问"限速要不要感知调用者的权限级别"：可以说明这是两个独立的关注点——限速回答的是"这个客户端调用得太快/太多了吗"，而授权回答的是"这个客户端有没有权限做这个操作"；两者可以组合使用（比如对高权限操作单独设置更严格的限额），但判定逻辑和数据模型应该保持独立，不要因为要支持"按权限限流"这种特殊需求就把两个本该正交的系统耦合在一起。这也呼应了第 4 维"separation of concerns"——策略管理与执行路径要分开，不同关注点的策略也要分开，不能因为都叫"策略"就合并成一套配置。

## 14. 一句话总结（用于开场或收尾复述）

"这套限速系统的核心权衡是：用近似正确换取低延迟和高可用，用分层的保护机制应对从单客户端异常到系统级过载的不同规模的风险，并且始终记住保护机制自身故障时，正确的默认行为是放行而不是拒绝。"

## 15. 常见误区小结（自查用）

- 误区一：认为限速必须做到绝对精确，为此引入跨实例的强一致方案，牺牲了判定延迟——这道题里精确性从来不是优先级最高的目标。
- 误区二：把"限速器挂了"和"业务系统挂了"同等对待，两者都想着 fail-closed——前者应该 fail-open，因为限速器只是保护层而不是业务本身。
- 误区三：只设计了单一层的按客户端限速，没有区分"客户端异常"和"系统整体过载"这两类需要不同应对策略的问题。
