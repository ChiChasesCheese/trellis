# 追问预案（≥8 条）

> 取材：Stripe《Scaling your API with rate limiters》（2017-03-30）；Stripe 文档 Rate limits；`loop/raw/system_design.md` §4.4。

## 1. 限速组件（比如 Redis）挂了，网关应该怎么做？

**期望要点**：默认 **fail-open**（放行请求）并立即触发告警，而不是 fail-closed（拒绝所有请求）。理由是对支付类 API 而言，因为一个保护机制自身出故障而拒绝所有合法请求，代价远大于暂时放过一些本该被限速的流量。可以补充：同时降级到网关本地内存计数，作为退而求其次的保护手段，而不是完全放弃限速。

## 2. 固定窗口计数器有什么问题？

**期望要点**：窗口边界处理不当会导致允许的流量在两个相邻窗口交界处翻倍——比如窗口结束前一瞬间涌入一批请求都被判定通过，紧接着新窗口开始又涌入一批同样被判定通过，短时间内实际通过的流量是设定速率的两倍。滑动窗口（或者用两个固定窗口加权近似）能显著缓解这个问题。

## 3. 多个网关实例并发判定同一个客户端的请求，怎么保证不会超发？

**期望要点**：把同一个客户端的所有判定路由到 Redis 里的同一个 key，用 Lua 脚本把"读取当前状态 + 计算是否允许 + 更新状态"打包成一次原子操作，避免多个实例之间出现"读到旧状态、都判定为允许"的竞态。可以补充：即便如此，短暂的、小幅度的超限仍然可能发生（网络延迟无法完全消除），这是限速作为"近似保护"必须接受的代价。

## 4. 为什么限速组件故障时不能简单地拒绝所有请求以求"安全"？

**期望要点**：这里的"安全"要看站在谁的角度——对支付平台来说，把所有正常商户的合法请求（包括发起真实支付）全部拒绝掉，造成的业务损失和信任损失，远大于因为限速失效而多放过一些原本该被限速的流量。限速器的角色是"锦上添花的保护层"而不是"业务本身的必要条件"，二者混淆是这道题最容易踩的坑。

## 5. 大客户临时有一次可预期的流量高峰（比如促销活动），怎么处理？

**期望要点**：提前和商户沟通，通过配置管理接口临时调高该商户的限额（这是"策略管理慢路径"存在的意义之一）；同时建议商户自己的客户端实现类似令牌桶的自限速逻辑，从两端共同平滑峰值流量，而不是完全依赖服务端硬扛瞬时压力。

## 6. 如果要支持跨多个数据中心的限速，架构上有什么变化？

**期望要点**：不追求跨数据中心的强一致同步计数（延迟代价太高）；可以按预期流量分布把全局配额静态切分到各数据中心，配合定期（如分钟级）的异步汇总做动态再平衡，把"跨区域一致性"这个较重的操作放到不在请求关键路径上的后台任务里完成。

## 7. 限速和熔断（circuit breaker）有什么区别，是不是同一个东西？

**期望要点**：不是同一个东西。限速是"主动限制调用方的请求速率，防止对方压垮我方"，保护的是被调用方；熔断是"当某个依赖持续失败/超时时，主动停止继续调用它一段时间"，保护的是调用方自己不被一个已经出问题的下游拖垮。两者可以在同一个系统里共存，分别解决不同方向的问题。

## 8. 客户端一直收到 429，但看起来自己的调用量并没有超过预期限额，可能是什么原因？

**期望要点**：可能是限速状态的分片/key 设计有问题（比如多个客户端错误地共享了同一个 key）；可能是客户端自己的重试逻辑没有遵循 `Retry-After` 而进行了更激进的重试，反而放大了限速触发；也可能是配置本身设置得不合理（比如把并发限制和速率限制的阈值搞反了）。回答里能提出"先看判定日志、按 reason 字段定位是哪一层触发的"这个排查思路是加分项。

## 9. 需要给某些"关键操作"（比如发起支付）设置比普通查询更宽松的限速，具体怎么实现？

**期望要点**：在配置模型里区分不同 `scope`（比如按端点或按操作类型），关键操作单独配置更高的阈值或者单独的令牌桶，甚至在整体系统过载触发分级降级时被排除在"优先削减"的名单之外，体现"不同关注点的策略要能独立配置"这一分离原则。

## 10. 上线一个全新的限速规则，怎么确保不会误伤大量正常商户？

**期望要点**：先以 dark launch 方式运行——限速判定照常执行并记录结果，但不真正拒绝请求；离线分析这段观察期内"如果真的启用会拒绝多少流量、涉及哪些客户端"，确认误杀率在可接受范围内后，再灰度到小比例流量真正生效，最后全量打开，全程保留可以快速关闭规则的开关。
