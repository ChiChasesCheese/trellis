# 追问预案（≥8 条）

> 取材：Stripe 官方 Ledger 博客（2024-02-16）；Alex Xu Vol.2 支付章；ByteByteGo reconciliation guide；`loop/raw/system_design.md` §4.3。

## 1. 为什么不直接在账户表上 UPDATE 余额，而要搞一套"分录"的复杂设计？

**期望要点**：直接 UPDATE 丢失了历史（无法回答"某一时刻余额是多少""这笔钱经过了哪些步骤"）、无法审计（无法证明某个余额是怎么算出来的）、且高频账户会因为行级锁而成为写路径瓶颈。追加式的分录设计牺牲了简单性，换来可审计、可重建、可高并发写入的能力，这是"钱"这个领域必须的权衡，普通业务数据未必需要付出同样的代价。

## 2. 多币种账户之间怎么保证"平"？

**期望要点**：不能跨币种直接相加对比。每一种货币在自己的维度上独立校验 Σdebit == Σcredit；跨币种兑换通过专门的 FX clearing 账户中转，汇率产生的差额落到单独的损益账户，任何单一货币都不会因为一笔跨币种交易而凭空增减。

## 3. 某个热点账户（比如平台自己的手续费收入账户）每秒被写入几千次，怎么应对？

**期望要点**：写路径只追加 entries，不在写路径上更新这个账户的单行余额；余额通过异步聚合物化，读取时接受一定的新鲜度延迟（除非明确需要强一致的场景，比如判断"能不能动用这笔钱"，那种场景可以对这一个账户单独用乐观锁把强一致性代价限制在真正需要的地方）。

## 4. 怎么查询某个账户在一个月前某一天的余额？

**期望要点**：从最近的一次快照（`balance_snapshots`）出发，加上快照之后到目标时间点之间的所有 entries 求和，避免从账本创立之初重放全部历史；快照生成频率是可调参数，根据历史查询的访问模式做权衡。

## 5. 上游业务系统的某个事件因为网络问题没有成功发布到账本，怎么发现？

**期望要点**：依赖"完整性"校验——定期把上游业务系统数据库里应该产生资金记录的 ID 集合，与账本里实际存在的 transaction 的 external_id 集合做比对，缺失的部分触发补发流程或人工介入，而不是被动等待账目对不上才发现问题。

## 6. clearing 类账户不为零意味着什么？怎么处理？

**期望要点**：意味着某处的资金流转没有走完整个闭环——可能是一笔交易缺失、延迟、或者记错了金额。处理流程是定位这个 clearing 账户下未配对的分录，追溯到对应的业务事件，判断是"延迟到达，稍后会自动归零"还是"确实出了错，需要人工介入 + 追加反冲交易修正"。

## 7. 发现半年前的一条分录记错了金额，应该怎么改？

**期望要点**：永远不直接修改或删除原记录；追加一条新的 transaction，引用原始 transaction，用一组反冲分录抵消原来的错误金额，再补一组正确的分录。修正之后，账本的历史是"曾经记错了、后来被谁在什么时候修正为多少"的完整叙事，而不是一条被悄悄改写、外界无从得知曾经出错的记录。

## 8. 平台账户向连接账户（不同主体）转账，如果两者的账本数据分属不同分片，怎么保证原子性？

**期望要点**：不用跨分片分布式事务，用 saga 思路——先在源账户分片记一笔"转出"分录并标记为处理中，成功后再到目标账户分片记"转入"分录，全部完成后两边状态一起终结；任一步失败则在已完成的一侧追加补偿分录回滚。全过程通过统一的 transaction_id 关联，即使中途失败，也能从账本记录本身重建出完整的处理轨迹。

## 9. 账本系统本身要不要做灰度/AB 测试？

**期望要点**：账本的写入路径和平衡校验逻辑的任何变更都应该先做双写/影子验证——新旧逻辑并行处理同一批事件，对比两边产生的结果是否一致，确认无误后才真正切换，因为这里一旦出 bug，代价是真实资金记录出错，不能用"先上线观察、出问题再回滚"的常规灰度思路来对待。

## 10. 如果面试官问"这套系统和普通的事件溯源（event sourcing）架构有什么关系"？

**期望要点**：账本本质上是事件溯源思想在"资金"这个特定领域的应用——不可变的事件日志（entries）是唯一事实源，当前状态（balances）是可以从事件重建的派生视图；区别在于账本额外强制了"借贷恒等"这条领域特定的强约束，并且围绕"完整性、及时性、清账"设计了专门的持续校验机制，这是通用事件溯源框架不会自带的。
