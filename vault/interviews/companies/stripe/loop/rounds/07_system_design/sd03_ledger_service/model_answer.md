# 模型答案：设计 Ledger / Bookkeeping 服务（含多币种）

> 取材：Stripe《Ledger: Stripe's system for tracking and validating money movement》（2024-02-16）；Alex Xu Vol.2 支付章；ByteByteGo reconciliation guide；`loop/raw/system_design.md` §4.3。按 `LOOP_GUIDE.md` §7 主线组织。

## 0. 两句话复述 + 不变量

**复述**：公司内多个业务系统会产生各种资金移动（扣款、手续费、退款、结算、汇兑），我们需要一个中心化的记账系统，把每一笔资金移动都记录成不可篡改的历史，能够在任意时间点回答"某个账户有多少钱""所有钱现在分布在哪里"，并且能自动发现任何"对不上"的情况。

**核心不变量**：

1. **借贷恒等**：每一笔交易（transaction）内部，按币种分组后，Σdebit == Σcredit，不允许钱凭空出现或消失。
2. **历史不可变**：账本条目（entries）一旦写入永不修改或删除；发现错误只能通过追加一条反冲（reversal）交易来修正，原始记录原样保留。
3. **完整性（completeness）**：每一个上游业务系统里产生资金变化的对象，都必须最终在账本里有对应记录，缺失即视为数据质量问题。
4. **清账（clearing）归零**：过渡性质的 clearing 类账户在完成一轮资金流转后应当归零，非零意味着某处出现了缺失、延迟或错误的交易。

明确不做什么：账本不是给终端用户直接查询余额的实时缓存层（那是上层业务系统的职责，可以用账本的物化视图加速）；账本本身不做风控决策，只负责如实记录。

### 不变量 → 设计决策映射（面试中口述这张表能快速证明"想清楚了"）

| 不变量 | 落地到的设计决策 |
|---|---|
| 借贷恒等 | 写入路径强制校验 `entries` 按币种分组 Σdebit == Σcredit，不满足直接拒绝写入 |
| 历史不可变 | `entries` 表只允许 INSERT，没有 UPDATE/DELETE 路径；修正用反冲交易追加 |
| 完整性 | 定期比对上游系统数据库与账本记录的 ID 集合，缺失即报警 |
| 清账归零 | 对 `type=clearing` 的账户设置专门的余额监控，非零即报警并定位缺失/延迟/错误交易 |

## 1. API 契约

账本主要是内部服务，对外只暴露极少的只读接口：

```
POST /ledger/transactions        Idempotency-Key（同时也是 external_id）
  {external_id, event_type, occurred_at,
   entries: [{account_id, direction: debit|credit, amount, currency}],
   metadata}
  校验：entries 按币种分组后 Σdebit == Σcredit，不满足则拒绝（422）

GET  /ledger/accounts/:id/balance?at=<timestamp>&currency=
GET  /ledger/accounts/:id/entries?cursor=&limit=
GET  /ledger/transactions/:id

对外（面向商户，经过一层业务封装）：
GET /v1/balance                 -- 当前可用/待结算余额
GET /v1/balance_transactions    -- 分页的资金变动流水
```

契约细则：

- 写入接口要求调用方提供 `external_id`，账本据此做幂等摄取，重复投递直接确认成功但不重复记账。
- 校验借贷平衡是写入路径上**唯一**允许拒绝请求的业务规则，其他资金决策（要不要扣这笔钱、扣多少）在上游系统里已经做完，账本只负责如实记录结果。
- 查询接口支持按时间点 `at` 查历史余额，以及游标分页遍历某个账户的全部分录，避免深分页扫描代价过高。

## 2. 数据模型

```
accounts(
  id, owner_type, owner_id,
  type[asset|liability|revenue|expense|clearing],
  subtype,      -- 如 merchant_pending / merchant_available / stripe_fee_revenue
  currency, created_at
)
-- "资金的桶"，按类型和属性区分；不同 subtype 决定了它在资金生命周期里的角色

transactions(
  id, external_id UNIQUE, event_type,
  occurred_at, posted_at, producer, metadata jsonb
)
-- 每一次业务事件对应一条；external_id 唯一约束是幂等摄取的关键

entries(
  id, transaction_id, account_id, direction, amount BIGINT,
  currency, seq
)
-- 不可变；同一个 transaction 内按币种分组借贷必须相等，
-- 由写入路径校验 + 数据库层的 CHECK 约束兜底

balances(account_id, currency, balance, as_of_seq, updated_at)
-- 物化余额，理论上任何时刻都可以从 entries 重新计算得到；
-- 或者用 balance_snapshots(account_id, date, balance) 做按日快照 + 增量
```

**修正错误的唯一方式是追加，不是更新**：发现某条 transaction 记错了，写一条内容相反的 reversal transaction，引用原 transaction_id，两条记录都永久保留，从审计角度看"发生过什么、后来又怎么被修正"是完整可追溯的。

**金额与多币种**：一律用整数最小货币单位；多币种场景下，**每一种货币在自己的维度上独立平衡**，不同货币之间不能直接相加。一笔跨币种兑换通过一个 `fx_clearing` 账户中转：借记账户扣掉的 USD 部分单独平衡，贷记账户收到的 EUR 部分单独平衡，两者之间的差额（汇率损益）落到一个专门的损益账户，而不是让两种货币在同一笔分录里"直接兑换"。

## 3. 典型分录示例（口述时用来展示对领域的理解）

- 客户付款 $100，平台抽取手续费 $3：`借 charge_unsubmitted(asset) 100 / 贷 merchant_pending 97 / 贷 stripe_fee_revenue 3`。
- 资金完成结算，进入平台的银行账户：`借 bank_settlement 100 / 贷 charge_unsubmitted 100`（此时 clearing 类账户归零）。
- pending 资金转为可提现（T+n 之后）：`借 merchant_pending 97 / 贷 merchant_available 97`。
- 退款：不修改原分录，追加一组方向相反的新分录。
- 商户提现（payout）：`借 merchant_available / 贷 bank_outgoing_clearing`，银行确认到账后再清空 clearing。

## 4. 一致性 / 写路径设计

- **摄取方式**：上游业务系统通过 outbox 模式发布事件，账本作为消费方摄取，不是被上游系统直接开事务写入的共享数据库——这样账本的可用性和一致性不会被上游系统的实现细节绑死。
- **写入幂等**：`external_id` 唯一约束，重复的摄取请求直接确认成功（ACK）但不产生第二条 transaction。
- **热点账户问题**：如果每笔交易都要更新某个高频账户（比如平台自己的手续费收入账户）的余额这一行，这个账户会成为写路径的串行化瓶颈。对策是**写路径只追加 entries，绝不在写路径上更新单行余额**，余额通过异步聚合物化，或者在需要"实时防止透支"的场景下对这一个账户单独加乐观锁/版本号，把强一致性的代价限制在真正需要它的地方，而不是让所有账户都付出这个代价。
- **分片**：按账户所属主体（如商户）分片；一笔跨主体的交易（比如平台向连接账户转账）用 saga 或者让 clearing 账户在两边各自记一笔的方式处理，避免跨分片强一致事务。

## 5. 读路径设计

- **当前余额**：直接读物化 `balances` 表，是最高频的读路径，要求低延迟。
- **历史某一时刻余额**：最近的快照加上快照之后到目标时间点之间的增量 entries 求和，避免每次都从账本创立之初重放全部历史。
- **报表 / 大范围对账**：走独立的 OLAP 副本（如通过变更数据捕获同步到数据仓库），不与实时余额查询共享同一套数据库压力。

## 5.5 失败处理

- **上游重复投递**：`external_id` 唯一约束天然吸收重复摄取，不需要额外的去重层。
- **上游漏发/延迟发**：这正是"完整性"校验要抓的问题——账本自己不会主动去问上游"你是不是漏了什么事件"，而是依靠定期比对上游数据库与账本记录的 ID 集合，发现差集后触发补发或人工排查。
- **摄取过程中账本自身崩溃**：由于消费的是持久化的消息队列/outbox，重启后从上次的消费位点继续，配合 `external_id` 幂等，不会因为崩溃重启而丢失或重复记账。
- **跨主体交易的原子性**：平台账户与连接账户之间的转账如果分属不同分片，不适合用跨分片分布式事务，而是用 saga 思路——先在源账户一侧记一笔"转出"分录，成功后再在目标账户一侧记"转入"分录；任一侧失败则记一笔补偿分录回滚，整个过程通过 `transaction_id` 关联，保证即便中途失败也能从账本记录本身重建出完整的处理过程。
- **区域故障**：账本的写路径按主体（如商户）绑定到一个 home region，故障切换时必须先 fence 掉旧 region 的写入能力，防止两个 region 同时摄取同一批事件产生分叉的账本状态。

## 6. 对账 / 数据质量（Stripe 官方三项校验）

- **及时性（timeliness）**：数据从产生到进入账本有硬性的时间窗口，超过阈值即视为异常。
- **完整性（completeness）**：上游业务系统数据库里的每一个应该产生资金记录的 ID，都要能在账本里找到对应的 transaction；缺失、延迟或记录错误的交易通过定期比对发现。
- **清账（clearing）**：过渡性质的 clearing 账户在一个业务周期结束后理应归零，任何非零余额都意味着"某处有钱去向不明"，这是最直接的自动报警信号。
- **外部对账**：账本记录还要定期与银行/卡组织的结算文件核对，发现的差异按"可自动修复""需人工介入""暂时无法分类"分类处理，避免所有异常都堆积成人工排查的负担。

## 7. 可观测性 + rollout

**监控指标**：摄取延迟 p99、clearing 类账户非零的数量与金额、completeness 缺失率、写入失败/幂等冲突率、物化余额与从 entries 重新计算结果之间的差异（用于发现物化逻辑本身的 bug）。

**rollout**：账本是所有资金正确性的最后防线，任何写入路径或平衡校验逻辑的变更都要经过双写/影子验证（新逻辑与旧逻辑并行跑一段时间对比结果）才能切换；发现 clearing 类账户异常时要有明确的升级/止血流程（比如暂停相关业务系统继续摄取，直到差异定位清楚）。

## 8. 规模估算（简要）

参考 Stripe 官方数字量级，账本每日处理事件数可以达到数十亿条；每条 entry 约百字节量级，日增数据量在 TB 级别，需要按时间做分区并对历史数据做冷归档；物化余额表本身远小于全量 entries，可以承受更高的查询并发。主要瓶颈在写路径的吞吐（用只追加设计规避热点账户）和历史查询的效率（用快照 + 增量规避全量重放）。

进一步拆解瓶颈：
- **写吞吐**：分片键选账户所属主体，配合"只追加"避免行级锁竞争；单个超大商户如果本身就是热点，可以在其内部再按时间窗或子账户做二级拆分。
- **存储增长**：entries 表按月分区，超过合规要求的历史窗口后归档到更廉价的冷存储，查询时对冷数据走单独路径，不影响热数据的索引效率。
- **查询延迟**：当前余额查询命中物化表；历史查询命中"快照 + 增量"，快照的生成频率是一个可调参数——快照越密集，历史查询越快，但快照本身的存储和生成成本越高，需要根据实际的历史查询模式（是否集中在近期）来调优。

## 9. 追问预演

- **"为什么不直接 UPDATE 一行余额，这样不是更简单吗？"**：直接 UPDATE 会丢失历史、无法审计、且高频账户会因为行级锁成为写路径瓶颈；追加式设计牺牲了"读一次拿到答案"的简单性，换来了可审计、可重建、可并发写入的能力，这在"钱"这个领域是必须的权衡。
- **"多币种账要怎么证明是平的？"**：不能把不同货币直接相加对比，必须每种货币独立验证 Σdebit == Σcredit；跨币种兑换通过专门的 FX clearing 账户和汇率损益账户处理，让"钱的种类"本身也成为平衡校验的一个维度。
- **"发现一条分录记错了，怎么改？"**：永远不直接修改或删除，追加一条内容相反的反冲交易，引用原始交易，两条记录都保留，账本的历史因此始终是"曾经发生过什么，后来又如何被修正"的完整叙事，而不是被悄悄改写过的记录。
- **"账本自己的数据库会不会也出错？"**：会，这也是为什么"完整性""清账"这两项校验必须是持续、自动运行的，而不是一次性设计完就假设永远正确；账本对自己也保持怀疑，把"发现异常"本身当成系统的一等公民能力，而不是事后补救的手段。
- **"读写分离之后，报表读到的数据和实时余额不一致算不算 bug？"**：不算，只要在可接受的复制延迟范围内。报表/对账走的是异步同步的 OLAP 副本，天然存在一定的滞后；真正要求强一致的只有"当前可用余额"这类判断"能不能动用这笔钱"的读请求，这类请求必须直接读主库或强一致的物化视图，而不能容忍复制延迟。
- **"如果两个不同团队各自往账本写了同一笔业务事件，只是 external_id 生成方式不统一，会不会重复记账？"**：会，这属于上游集成规范的问题而非账本本身的设计缺陷；解决方式是在摄取协议里明确规定 `external_id` 的生成规则（通常绑定到产生该事件的业务对象主键），并通过完整性校验发现"同一个业务对象在账本里出现了两条本不该重复的记录"这类异常模式。
- **"账本要不要支持删除测试数据？"**：不支持任意删除，即便是测试环境也应该用独立的测试账本实例而不是在生产账本上"删几条测试记录"，一旦允许任何形式的删除，"历史不可变"这个不变量就名存实亡，审计与对账的可信度也随之瓦解。
- **"这套设计和普通的数据库审计日志（audit log）有什么本质区别？"**：审计日志通常是"业务表之外附加的一份变更记录"，业务表本身仍然可以被直接更新；而这里的账本本身就是唯一的事实源——业务系统看到的余额是从账本派生出来的物化视图，而不是反过来账本去记录业务表的变更历史，这个"谁是主、谁是派生"的关系倒置正是双记账设计的核心。
