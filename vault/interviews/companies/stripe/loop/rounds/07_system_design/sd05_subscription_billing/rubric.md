# 评分 rubric（Exponent 五维，1–4 分/维，满分 20）

> 依据 `loop/LOOP_GUIDE.md` §7、`loop/raw/system_design.md` §4.5（Stripe 官方 Subscriptions 文档 + 培训站转述）。这道题本质上是 sd02（幂等支付）和 sd03（Ledger）两道题在"周期性、有状态的业务对象"场景下的组合应用，考察的是候选人能不能把已经建立的幂等/记账思路迁移到一个新的业务领域。

## 1. Problem framing

- **1 分**：把订阅计费简化成"一个定时任务，每月扣一次钱"，没有意识到升降级、试用期、扣款失败重试、取消这几种状态变化会互相交织，也没有提炼出"每个周期最多一张账单、最多一次扣款"这条核心不变量。
- **4 分**：两句话复述题目并显式说出不变量——**每个计费周期恰好一张正式发票、恰好一次成功扣款**（幂等）；订阅状态、发票状态、支付结果三者必须保持一致，不允许出现"订阅显示有效但已经好几个周期没扣到钱"这种脱节；主动确认试用期、比例计费、取消策略等属于本题需要覆盖的功能范围。

## 2. API & data model（权重最高）

- **1 分**：只有一张 `subscriptions` 表，价格、周期、发票全部塞在同一张表里；升降级时直接原地修改金额字段，没有留痕；没有单独的发票/账单对象。
- **4 分**：区分 `subscriptions`（订阅本身的生命周期）、`invoices`（每个周期一张，唯一约束 `(subscription_id, period_start)` 防止重复开票）、`invoice_line_items`（组成一张发票的具体条目，区分正常周期费用和比例计费产生的调整项）；能讲清楚升级/降级时如何生成"退回旧价 + 补收新价"两条调整分录并入正确的发票；扣款接口复用 sd02 的幂等 PaymentIntent 机制，幂等键与发票 ID 绑定。

## 3. Failure modes & scale

- **1 分**：假设扣款总是要么立刻成功要么立刻失败，没有考虑"扣款结果未知"的情况；月初大量订阅同时到期这件事完全没有对策，暗示"扫全表定时跑一遍"。
- **4 分**：讲清扣款失败后的重试规则（dunning，如 3/5/7 天后再试）与宽限期设计；讲清"扣款结果未知"时复用 sd02 的"先查询再决定"思路，不武断改变订阅状态；讲清月初洪峰的应对——提前预生成草稿发票、把真正扣款的时间点错峰分散到一个时间窗口内，而不是所有订阅在同一毫秒被处理；讨论调度器本身故障时如何避免重复处理同一个订阅（租约/幂等）。

## 4. Separation of concerns

- **1 分**：把"判断该不该续费""生成发票""发起扣款""处理扣款结果"全部写成一个巨大的定时任务函数，没有清晰的组件边界。
- **4 分**：清楚划分——调度器（定期扫描到期订阅，只负责触发，不做业务逻辑）、发票生成组件（负责按订阅当前的价格/数量/比例计费规则生成发票草稿）、支付发起组件（复用幂等支付 API）、状态同步组件（根据支付结果推动订阅状态机前进）；这几个组件之间通过事件/消息解耦，而不是同步调用链层层嵌套。

## 5. Delivery beyond the diagram

- **1 分**：没有提怎么测试比例计费的计算逻辑是否正确，也没有提怎么监控续费是否健康。
- **4 分**：讲到关键监控（续费成功率、催收/dunning 的回收率、发票生成延迟、长期停留在草稿态的发票数量）；讲到比例计费这种容易出金额错误的逻辑要有专门的测试用例覆盖各种边界（比如月份天数不同、订阅在周期正中间升级）；讲到新计费规则上线前要能在不影响真实扣款的情况下先跑一遍"模拟账单"验证结果。

## 一条相关提醒

> 这道题在 Stripe 六大 SD 题里置信度相对较低（主要来自培训站转述而非逐问一手面经），但它考察的核心能力和 sd02、sd03 完全一致——**把"绝不重复扣款、状态最终一致、失败要有明确的收尾路径"这几条原则迁移到一个新场景的能力**。如果面试官临场把题目从"订阅计费"换成别的周期性计费场景（比如按用量计费），能不能快速识别出"这还是同一套骨架，只是发票生成的计算规则变了"，是检验候选人是否真正理解原则而不是背了一套模板的关键。
