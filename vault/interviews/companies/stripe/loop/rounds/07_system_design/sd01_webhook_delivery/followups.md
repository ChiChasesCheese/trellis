# 追问预案（≥8 条，含四条必答的一手追问）

> 前四条是一手面经（Emily，Medium，2026-05-20）里明确记录的面试官追问，Stripe 面试官反复用这几个问题检验"失败模式推理能力"——本题的拒因原话就是这方面不足，务必逐条能脱口而出。

## 1（必答）商户端点持续返回 500，怎么办？

**期望要点**：不是无限重试。用指数退避 + 抖动（如 1min → 5min → 30min → 2h → 8h → 24h），设一个总时长上限（如 3 天），超过后转入死信队列（DLQ），通知商户并可以自动禁用该 endpoint 防止继续浪费资源；商户可以在修好之后通过 `resend` 接口或 Dashboard 手动重发历史事件补漏。加分点：提到抖动是为了防止大量同时失败的重试请求在同一时刻打过去（thundering herd）。

## 2（必答）商户端点 hang 住（比如卡 30 秒不返回），而且这个商户事件量很大，怎么保证不影响到其他商户？

**期望要点**：这是"noisy neighbor"问题。核心对策是**租户级资源隔离**——per-endpoint 并发上限、per-tenant 队列或令牌桶，配合较短的连接/读超时（如 2s/5s），一旦超时立刻释放资源转入重试队列而不是占着 worker 干等；进一步可以对连续超时的 endpoint 触发熔断，直接把它的事件转入延迟队列不占用实时 worker，定期半开探测恢复。反例：如果面试者的方案是"加大 worker 数量硬扛"，说明没理解隔离的本质。

## 3（必答）商户填的回调地址可能是内网地址，怎么防止 SSRF / DNS rebinding？

**期望要点**：两层防护。① 注册/更新 endpoint 时解析域名 IP，拒绝私网段、保留地址段、云 metadata 地址（如 169.254.169.254）；② 关键点在于**真正投递时不能重新走一次 DNS 解析再连接**——否则攻击者可以把 TTL 设得很短，注册校验时解析到公网 IP、真正投递时域名的解析结果已经改成内网 IP（这就是 DNS rebinding），所以要在投递时直连"注册校验时确认过的 IP"，Host 头带原始域名；③ 禁止跟随任何重定向（重定向目标同样不可信）；④ 出站流量走独立隔离的 egress 网段，即使前面的校验有疏漏也控制爆炸半径。只答出①而漏掉②的候选人视为部分掌握。

## 4（必答）商户要求"能不能保证 exactly-once"，怎么答？

**期望要点**：明确说"不能"，并说清楚为什么——发出请求后如果没在超时内收到响应，我们无法从网络层面区分"对方没收到"和"对方收到了但响应包丢了"，因此重试是唯一安全的默认动作，重试就必然意味着"可能重复投递"。我们能提供的是 **at-least-once + 商户侧按不可变的 `event.id` 去重**，业务效果上等价于 exactly-once。反例：如果候选人试图用"分布式事务"或"两阶段提交"去解决这个问题，说明没理解这是一个跨网络边界、对方系统不受我们控制的问题，2PC 在这里既不现实也不必要。

## 5. 如何保证商户能收到事件但不会重复处理，即便我们这边发生了重复投递？

**期望要点**：`event.id` 一旦生成永不改变，即便是重试导致的第 N 次投递，body 里的 `id` 也和第一次完全一样；商户侧只需要维护一个"已处理 event.id"的集合（或者按 `(event_id)` 加唯一约束防止业务动作被执行两次）即可安全去重。可以补充：Stripe 官方文档也明确要求商户"track event IDs to identify duplicate deliveries"。

## 6. 密钥泄露或需要轮换时怎么处理，不影响正在投递的事件？

**期望要点**：`webhook_endpoints` 同时保留 `secret_current` 与 `secret_previous`，轮换后一段时间内（如 24 小时）两把密钥并存，出站请求可以同时或分别用两把密钥各签一份 `v1` 签名，让商户有充分时间在自己那边完成密钥切换后再让旧密钥失效，避免"硬切"导致签名验证突然失败。

## 7. 商户坚持要求事件按发生顺序送达，怎么办？

**期望要点**：默认不承诺顺序，因为并发的多 worker 投递本身就难以保证严格顺序，而且会牺牲吞吐。如果一定要支持：按 `object_id`（而不是全局）做分区键，同一分区内单线程/单 worker 顺序消费，但要讲清代价——一个卡住的事件会阻塞同一分区后面所有事件（head-of-line blocking），吞吐也会显著下降。更推荐的替代方案是引导商户"收到事件后主动查询对象的最新状态"，而不是依赖事件本身的顺序来推断状态演变。

## 8. 系统规模扩大 10 倍（10 万 events/s）时，哪里最先撑不住，怎么扩容？

**期望要点**：先识别瓶颈——事件队列的分区数/吞吐、Dispatcher 匹配阶段查 endpoint 配置的 QPS（应有 Redis 缓存兜底）、worker 池的出站连接数、`deliveries`/`delivery_attempts` 表的写入吞吐与索引维护成本。扩容方向：事件队列按 `account_id` 增加分区；worker 无状态水平扩展；数据库按 `endpoint_id`/时间做分片和分区；如果延迟队列用 DB 轮询实现，10 倍规模下要评估切换到专门的延迟队列组件（如分层的 Kafka delay topic 或 Redis ZSET 集群）。

## 9. 如果 Dispatcher（匹配事件与 endpoint 的组件）本身崩溃重启，会不会丢事件或产生重复投递？

**期望要点**：不会丢——事件本身来自持久化的 outbox/消息队列，Dispatcher 重启后从上次的消费位点继续处理；可能会重复消费（at-least-once 消费语义），但由 `(event_id, endpoint_id)` 的唯一约束保证不会生成重复的 `deliveries` 记录，从而不会造成重复投递。这体现了"DB 唯一约束是真相源"的一致性设计原则。

## 10. 如何测试和上线这套系统，怎么知道新版本没有引入回归？

**期望要点**：新的匹配/重试逻辑先以 dark launch（只记录判定结果、不真正改变投递路径）方式跑一段时间对比新旧行为差异；灰度先在小流量商户或非核心事件类型上验证；监控关键指标（投递成功率、p99 延迟、DLQ 增长率）在灰度期间是否劣化；准备好快速回滚开关（feature flag）。
