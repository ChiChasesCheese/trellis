# Webhook delivery

我们内部有几十个业务系统（支付、账户、争议、结算……），每个系统每天都会产生大量业务事件——一笔付款成功了、一笔退款到账了、一个账户的资质被冻结了。商户没办法一直轮询我们的 API 来知道这些事情发生没发生，他们希望我们主动通知他们：商户在自己的后台注册一个或多个 HTTPS 地址，说明自己关心哪些事件类型，我们这边一旦产生了匹配的事件，就应该把事件内容用 HTTP POST 发到商户登记的地址上去。商户的服务器收到之后，可能会去更新自己的订单状态、发货、给用户发邮件之类的动作，所以这个通知本身要尽量快、尽量可靠，但同时我们心里要清楚，商户那台服务器完全不受我们控制——它可能写得很好，秒级返回，也可能挂了、卡住、返回一堆 500、甚至压根不存在（域名解析到什么奇怪的地方）。现在整个公司这类事件峰值大概是每秒一万条，每条事件可能对应一到多个商户端点，我们要求的是「只要事件被系统接受了，就必须尽力把它送到」，而不是「送不到就算了」；但同时也不能因为某一个商户的端点卡死或者疯狂重试，就把整个投递系统的资源耗尽，进而影响到其他所有商户收通知的时效性。有的商户还会问我们能不能保证他们的业务系统不会因为我们重试而被同一个事件处理两次，能不能保证事件是按发生顺序到的，也有人问过我们，如果他们不小心把回调地址填成了内网地址会怎么样、我们会不会不小心把内部数据打过去。这个系统需要覆盖从商户注册/管理端点，到事件产生、匹配、投递、重试、最终放弃或者人工介入的全过程，商户那边理想情况下应该能在自己的后台看到每次投递的历史和结果，必要的时候还能手动要求我们重发某个事件。请设计这个系统。

---

**面试环境说明**：这是 Stripe onsite 的 System Design 轮，时长 45 分钟（含开场寒暄与结尾提问，真正留给设计讨论的时间约 30–35 分钟）。使用 Whimsical 在线白板作图，不是物理白板，也没有代码编辑器——全程口头 + 画框图线。面试官不会给你结构化的需求列表，题面就是上面这样一段业务描述，需要你自己在开场的几分钟里把功能性/非功能性需求、核心不变量提炼出来，并大声说出你的理解让面试官确认或补充。后面的大部分时间面试官会通过追问把你往失败模式、规模、权衡上带，画图本身不是重点。
