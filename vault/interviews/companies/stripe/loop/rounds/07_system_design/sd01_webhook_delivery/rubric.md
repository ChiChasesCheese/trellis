# 评分 rubric（Exponent 五维，1–4 分/维，满分 20）

> 依据 `loop/LOOP_GUIDE.md` §7 与 `loop/raw/system_design.md` §3.1（Exponent 五维）。Stripe 的 SD 轮不是「画完架构图就结束」，10 分钟看完图之后剩下的时间全部在压 failure modes——本题尤其如此，因为这是六题里唯一有多条一手面经、且已知一位 Staff 面试官给出过具体拒因的题。

## 1. Problem framing（需求抽取）

- **1 分**：直接开始画框图（网关 → 队列 → worker → 商户），没有先复述题目、没有提炼不变量；面试官问"你觉得这个系统最重要的保证是什么"答不上来，或者答成"高并发"。
- **4 分**：开场用两句话复述题目（"内部事件产生后，要把它可靠地投递给商户注册的 HTTPS 端点；商户端点不可信、可能慢/挂/恶意，我们不能因为一个商户拖累所有人"），并显式说出关键不变量——**至少一次投递**（接受了就必须尝试）、**不保证严格顺序**、**不可能做到端到端 exactly-once**、**租户隔离**；主动确认规模（10k events/s）、延迟目标（p99 首次尝试 < 1s 量级）、是否需要商户可见的投递历史与手动重发。

## 2. API & data model（权重最高）

- **1 分**：只画了"事件表"和"投递表"两个框，没有具体字段；没有谈到幂等键/事件 ID 怎么让商户端去重；把签名验证、版本、分页当作可以跳过的细节；商户注册端点的 API 形状没有设计（谁调用、传什么、返回什么）。
- **4 分**：给出商户侧管理 API（注册/更新/禁用 endpoint、拉取历史事件补漏、手动 resend）与出站请求契约（`Stripe-Signature` 头、body 里不可变的 `event.id`、`api_version`），明确 event 对象一旦生成对某个账户就不再变化；数据模型区分 **`events`（不可变，事实源）**、**`webhook_endpoints`（可变配置）**、**`deliveries`/`delivery_attempts`（每次尝试独立一行，可审计）**；能说清"商户怎么去重"这件事的落地方式（幂等键 = event.id，交给消费方持久化）。

## 3. Failure modes & scale（本题权重实际上也很高）

- **1 分**：只说"重试几次""加缓存"，没有具体退避策略；没有意识到"一个商户的端点慢"会拖累别的商户（noisy neighbor）；没提到 SSRF/DNS rebinding 这种商户端点本身是攻击面的问题；被问到"商户要求 exactly-once 怎么办"时答不出"不可能"或者说不清为什么。
- **4 分**：讲清指数退避 + 抖动 + 上限（如最长重试 3 天后进 DLQ）；讲清**租户级隔离**——per-endpoint 并发上限、per-tenant 队列或令牌桶，配合熔断，防止一个卡死的商户吃光全局 worker；主动提出 SSRF 防护（注册时解析域名拒绝私网/保留段/云 metadata IP，投递时用校验过的 IP 直连、Host 头带原域名、禁止跟随重定向）；能正面回答"能不能 exactly-once"——不能，只能 at-least-once + 消费方按 event.id 去重，并说明为什么网络本质上做不到更强的保证。

## 4. Separation of concerns

- **1 分**：把"匹配商户订阅的事件类型""签名""HTTP 投递""重试调度"全部塞进一个"投递服务"里，没有边界；策略变更（商户改配置）与执行路径（真正发请求的 worker）没有分开。
- **4 分**：清楚分层——事件产生方通过 outbox/消息队列与投递系统解耦；一个"匹配/扇出"组件负责查 endpoint 配置（慢路径，可缓存）并生成待投递记录；一个无状态、可水平扩展的 worker 池负责真正的 HTTP 发送（快路径）；重试调度（延迟队列/ZSET）是独立组件，不与 worker 的请求处理逻辑耦合。

## 5. Delivery beyond the diagram（rollout / 测试 / 监控）

- **1 分**：画完图就结束，没有提怎么上线、怎么测试、怎么知道系统在生产环境里工作正常。
- **4 分**：讲到关键监控指标（全局/分商户投递成功率、p99 首投延迟、队列深度、DLQ 增长率）；讲到商户可见的投递日志与手动重发作为兜底；讲到灰度/新版本先小流量或先只读观察（dark launch 思路）；讲到密钥轮换这种运维动作怎么做到不中断（新旧密钥双活一段时间）。

## 一条真实拒因（警示）

> 一位 **Staff 面试官**对这道 Webhook 投递题给出的拒绝原因原话是：**"insufficient reasoning about failure modes and system abuse"**（对失败模式和系统被滥用的可能性推理不足）。—— Emily, Medium, 2026-05-20；见 `loop/raw/system_design.md` §2 表格第 1 行、§3.2。
>
> 换句话说：这道题**画对架构图只是及格线**，真正拉开分数的是第 3 维——你能不能在压力下把"商户端点是不可信的、会被攻击者利用的外部系统"这个事实贯穿到设计的每一个角落。
