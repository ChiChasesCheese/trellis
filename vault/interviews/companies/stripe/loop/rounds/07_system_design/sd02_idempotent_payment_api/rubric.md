# 评分 rubric（Exponent 五维，1–4 分/维，满分 20）

> 依据 `loop/LOOP_GUIDE.md` §7、`loop/raw/system_design.md` §4.2、§3.2（Medium h7w 的 senior/staff 分水岭分析）。这道题是 Stripe「幂等性是生产可用的最低门槛，不是加分项」这句话的最直接体现。

## 1. Problem framing

- **1 分**：直接讨论"怎么调卡组织的 API"这种实现细节，没有先说清"绝不能双扣""绝不能因为超时就武断标记失败"这两个不变量；没有区分"我们对商户的承诺"和"我们对卡组织的承诺"是两件不同的事。
- **4 分**：用两句话复述题目并显式说出不变量——一个幂等键对应至多一次真正的外部扣款；系统的默认响应必须是"可安全重试"而不是"猜一个结果"；金额用整数最小单位存储、绝不用浮点数。主动确认关键假设：幂等键由客户端生成并通过 header 传入、有效期多长、并发同 key 请求如何处理。

## 2. API & data model（权重最高）

- **1 分**：只画了一个 "charges" 表，没有单独设计幂等记录的存储；没有说清楚 `Idempotency-Key` 应该保存什么（结果码 + body，还是只存一个"已处理"标记）；错误响应没有区分"参数不同导致的冲突"和"请求还在处理中"。
- **4 分**：给出资源化的 PaymentIntent 状态机 API（`requires_payment_method → confirm → processing → succeeded`），要求 `Idempotency-Key` header；数据模型里 `idempotency_keys` 表保存首次请求的完整响应（含状态码），同 key 重放直接返回缓存结果；同 key 不同参数返回 `idempotency_error`；同 key 并发在途返回"in flight"式的 409/暂不保存结果；能讲清楚"为什么要连响应体一起存"（否则重放请求会因为并发状态不同而拿到不一致的结果）。

## 3. Failure modes & scale

- **1 分**：假设卡组织调用永远成功或永远及时失败，没有考虑"调用超时、我们自己也不知道到底扣没扣成功"这种最棘手的情况；没有讨论进程崩溃后如何恢复到正确状态。
- **4 分**：讲清"先在数据库里原子地 claim 这个幂等键，再对外发起调用"的顺序，保证两个并发请求不会同时对外发起两次调用；讲清"调用卡组织超时"时的正确动作是**先查询卡组织确认是否已经授权，再决定是否需要真正重试**，而不是盲目重试或直接告诉用户失败；引入 recovery point / 状态机的思路，让任何阶段的崩溃都能通过读取当前状态恢复到正确的下一步；讨论区域故障和账户级分片。

## 4. Separation of concerns

- **1 分**：把"幂等键校验""调卡组织""记账""发通知"全部塞进一个单体事务/单个函数里，没有边界；DB 唯一约束和 Redis 缓存的职责混淆，把 Redis 当成真相源。
- **4 分**：清楚划分——幂等层（DB 唯一约束是真相源，Redis 只是加速缓存已完成结果的读取）、核心状态机（PaymentIntent 的生命周期管理）、外部调用适配层（对接卡组织，自身也要传一个我们生成的幂等标识给对方）、记账/通知（通过 outbox 异步发出，不阻塞主流程）。

## 5. Delivery beyond the diagram

- **1 分**：没有提到监控、没有提到对账，好像系统上线后就不用管了。
- **4 分**：讲到关键监控（幂等冲突率、`processing` 状态滞留数量、授权成功率与延迟）；讲到每日对账（卡组织结算文件 vs 我们自己的 charges 记录）用来兜底任何设计上没覆盖到的边角情况；讲到幂等键的过期清理策略（reaper）、版本兼容策略（只加字段不删字段）。

## 一条相关警示（Senior vs Staff 分水岭）

> Medium 作者 h7w（2026-04-03）的分析原话（大意）：一个只说得出"网关查 Redis 幂等键 → 处理 → 缓存结果"的答案，在三种情况下会崩——**并发的 cache miss**（两个请求同时没查到缓存，都跑去发起了调用）、**外部授权成功但记账失败的部分失败**、**因为重复扣款而被商户 webhook 触发的连锁问题**。能通过这道题拿到 staff 级别评价的答案，把整个支付处理看作一个**持久化的状态机**：DB 幂等表 upsert 先 claim → 外部调用 → 双记账 ledger → outbox 发事件 → 每日对账 → 必要时用 saga 补偿。
