# Idempotent payment / charge API

我们要给商户提供一个用来对一张卡收款的核心接口，商户后台点一下"收款"按钮，或者他们自己的服务端在结账流程里调用我们的 API，把金额、币种、这张卡的信息（或者说是一个已经 tokenize 过的支付方式标识）传给我们，我们负责去联系卡组织完成授权和扣款，然后把结果告诉商户。这个接口每天要被调用非常多次，商户的网络环境千差万别，经常会出现请求发出去了，但是商户那边因为网络抖动、超时、或者代码里写的重试逻辑，同一笔"用户点了一次支付按钮"的意图被重复发送了好几次 HTTP 请求过来——这时候我们绝对不能因为收到了两次请求就真的从用户卡里扣两次钱，哪怕这两次请求打到了我们不同的机器实例上、哪怕第一次请求还没处理完第二次就已经到了。同时我们也不能因为过度谨慎而把一笔本来该扣款成功的请求随便标记成失败，因为一旦告诉商户"失败了"，商户很可能会引导用户换一种支付方式或者重新下单，如果这时候实际上第一次的扣款已经在卡组织那边成功了，那用户就会遇到重复扣款或者商户账目对不上的麻烦。除此之外我们联系卡组织本身也可能超时或者连接中断，这时候我们自己都不知道钱到底扣没扣成功，还有商户在收到我们的响应之前自己的服务器就崩溃重启了、或者他们会拿相同的一笔业务意图但传了不同的金额过来问我们该怎么处理这种情况，我们的系统需要能优雅地处理所有这些情况，同时把每一笔钱的流向记得清清楚楚方便后续对账和审计。请设计这个收款系统的核心部分。

---

**面试环境说明**：Stripe onsite System Design 轮，45 分钟（含开场与结尾提问，真正设计时间约 30–35 分钟），使用 Whimsical 白板，无代码编辑器。题面刻意不给结构化需求列表，需要你自己从这段业务描述里抽取"绝不能双扣""绝不能丢单"这类核心不变量，并在开场简要复述确认后再进入设计。面试官后半段时间会持续追问各种并发和失败场景，重点考察 API 与数据模型设计，以及你能否把"正确性优先于吞吐"贯彻到底。
