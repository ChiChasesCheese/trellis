# 追问预案（≥8 条）

> 取材：Medium h7w（2026-04-03）；brandur《Implementing Stripe-like Idempotency Keys in Postgres》；Stripe 官方 Idempotent requests 文档；techinterview.org。

## 1. 重试请求打到了另一个实例，而第一个请求还没写完幂等记录，会不会两边都真的去扣款？

**期望要点**：不会。用数据库唯一约束（`(account_id, key)` 上的唯一索引）做原子的"claim"操作（`INSERT ... ON CONFLICT`），这个操作在数据库层面是串行化的，两个并发请求里只有一个能拿到"处理权"并继续往下执行外部调用，另一个会立刻拿到"处理中"的响应（如 409），绝不会两边各自去调用卡组织。回答里如果只提到"用 Redis 加锁"而不提数据库唯一约束作为最终真相源，视为不完整。

## 2. 同一个幂等键，但请求参数（比如金额）不一样，怎么处理？

**期望要点**：视为客户端错误，直接拒绝（返回 `idempotency_error`，如 400），不执行任何业务逻辑，也不修改已有的幂等记录。这是 Stripe 官方文档明确的行为，能说出这一点说明读过官方文档而不是凭空设计。

## 3. 幂等键要保存多久？存储一直增长怎么办？

**期望要点**：至少保留一个能覆盖客户端合理重试窗口的时长（如 24 小时以上），用后台的 reaper/清理任务定期批量删除过期记录；如果面试官问"能不能存久一点保证更安全"，可以讨论权衡——保留越久越安全，但存储和索引维护成本越高，实际策略应基于观测到的客户端重试窗口分布来定。

## 4. 调用卡组织超时了，我们自己都不知道钱扣没扣，怎么办？

**期望要点**：这是最考验候选人的问题。正确答案是**先查询，再决定**——用之前生成的 charge_id 向卡组织发起幂等查询接口，确认真实状态（成功/失败/仍未知）；查询结果不确定时把 PaymentIntent 标记为 `processing`，交给后台任务持续跟进或走每日对账兜底，绝不能立即武断地告诉商户"失败了"（可能导致真实的重复扣款），也不能盲目地当作"成功"直接记账（可能导致平账错误）。反例：如果候选人的答案是"直接重试一次扣款"，说明没有意识到重试可能造成双重扣款。

## 5. 授权在卡组织那边成功了，但我们这边写记账/ledger 的时候崩溃了，恢复后怎么处理？

**期望要点**：依赖 `recovery_point` 字段——重启或后台 completer 进程读取到该幂等键的 `recovery_point` 停在"外呼已完成、记账未完成"的阶段，接下来应该做的是**直接续写记账**（因为已经确认外部调用成功，不需要也不应该重新发起一次外呼），而不是重新走一遍整个流程。体现"持久化状态机、每一步都可从任意中断点恢复"的设计思路。

## 6. 系统需要支持多个地理区域，一个用户的请求应该落到哪个区域处理？

**期望要点**：每个商户账户固定一个 home region（单写者），所有涉及该账户资金状态变化的写请求都路由到该 region；其他 region 只提供只读副本用于查询加速。如果需要做 region 切换/容灾，必须先 fence 掉旧 region 的写入能力，防止新旧 region 同时可写造成脑裂式的双写。

## 7. 3DS 或其他需要用户额外操作的强验证流程，怎么和幂等机制配合？

**期望要点**：PaymentIntent 进入 `requires_action` 中间状态，返回 `client_secret` 交给前端完成用户交互，用户完成验证后前端再次调用 `confirm`（同样带 `Idempotency-Key`），流程继续沿着同一个状态机往下走；不需要为强验证单独设计一套幂等逻辑，它复用的是同一套"先 claim、可恢复"的框架。

## 8. 银行/卡组织自己因为网络问题重复给我们发了一次回调（webhook），会不会导致我们重复处理？

**期望要点**：这是"对方系统触发我们重复处理"的场景，不同于"我们的商户重复调用我们"。处理方式类似——每个外部回调也应该带一个可用于去重的标识（如卡组织自己的事件 ID），我们这边同样维护一张已处理事件的记录表并加唯一约束，收到重复回调时直接返回成功但不重复执行业务逻辑。

## 9. 如果面试官要求把 QPS 从 1 万提升到 10 万，系统里最先出问题的是哪个组件？

**期望要点**：先分析瓶颈——幂等键表的写入与唯一索引维护（可能需要更细粒度的分片）、ledger 的写吞吐（同一热点账户的记账可能成为瓶颈，需要"只追加不更新单行余额"的设计配合分片）、下游 outbox/Webhook 通知的扇出压力。给出具体扩容方向而不是笼统地说"加机器"。

## 10. 客户端没有正确实现幂等键（比如每次都随机生成新的 key），我们的系统能不能兜底？

**期望要点**：不能完全兜底，这是客户端集成正确性的责任，但系统可以通过监控发现异常（例如同一账户短时间内出现大量相似金额但不同幂等键的请求，可能提示客户端集成有问题）并主动告警提醒商户排查；同时在文档和 SDK 层面尽量降低集成错误的概率（如官方 SDK 默认自动生成并复用幂等键）。
