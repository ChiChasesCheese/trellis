# sd06 · 短题三连（Connect 分账/Payout · Feature Flag · Metrics）：练的是时间管理和模式识别

> [!tldr]
> - 这题考的是：一次面试给三道独立短题，每题约 10 分钟，考的不是任何一道题的生产级完整度，而是能
>   不能快速抓住每道题的核心矛盾，以及在受限时间内做优先级取舍。
> - 三步套路：拿到题立刻用一句话点出核心矛盾（不追求完整架构） → 给最小可用的 API/数据模型 → 挑
>   1–2 个最典型的失败场景讲透就收，绝不为了面面俱到拖慢整体节奏。
> - 最值得带走的一个模式：**慢路径管配置、快路径管执行**——这一个模式在分账（记账 vs 转账执行）、
>   feature flag（规则配置 vs 本地判定）、metrics（聚合规则 vs 采集上报）三道题里原样复用。

## 1. 题目在说什么（人话版）

有些面试官不会用整整 45 分钟只问一道大题，而是准备三道相对独立、彼此不相关的短题，每道给大概十分
钟深入讨论。第一道：平台代表第三方商户收款后要按比例分给一个或多个连接账户，连接账户定期提现到银
行，中间要准确反映"有多少钱、有多少在结算中不能动"，还要处理提现失败、银行退回、余额意外变负的情
况。第二道：几十个团队想要一种不用重新部署就能动态开关功能的能力，支持按用户百分比灰度、按地区定
向、一键全部关闭，判断本身要在每次请求里被高频调用，延迟必须很低。第三道：大量服务实例想上报简单的
数字指标（调用次数、耗时分布、错误数），最终要能聚合起来供工程师看趋势、设告警。

一个 3 行小例子：分账场景里，商户 A 收款 $100，平台按 90/10 分账，`POST /v1/transfers
{amount:9000, destination:"acct_B"}` 把 $90 转给连接账户 B；B 的 `available` 余额 +$90，等结算周期
过后 B 才能 `POST /v1/payouts` 把这 $90 提现到银行。

## 2. 读题：把文字变成模型

- **功能性需求**：三道题分别是资金分账+提现、动态功能开关、指标采集聚合，各自独立评分但共用同一
  套五维 rubric。
- **非功能性需求**：**时间**是这道题最特殊的一项非功能性需求——每题只有约 10 分钟，讲得太完整反而
  会在 delivery 维度被扣分（面试官会认为你不懂优先级取舍）。
- **核心不变量**（每道题各自一条，开场各花 1 分钟点出）：
  1. 分账：转账是"一方扣、一方加"的原子操作；`available` 才能提现，`pending` 不能。
  2. Feature flag：判定延迟必须是本地内存量级；配置中心挂了必须 fail-open 到预设默认值。
  3. Metrics：写入量远大于读取量，采集必须异步非阻塞，绝不能拖慢业务请求本身。
- **一句话建模**：这是三道 **各自独立但共享同一个"慢路径配置/快路径执行"分离模式** 的短题——考的
  是模式识别速度而不是任何单题的完整度。

> [!note] 为什么三道题要用同一套时间管理策略而不是分别"尽力而为"
> 候选方案是"每道题都认真展开、能讲多深讲多深"，或者"每道题严格控制在 8–10 分钟：1 分钟点出核心矛
> 盾、3–4 分钟 API/数据模型、3–4 分钟讨论 1–2 个关键失败场景、1 分钟收尾"。前者的风险是第一题讲了
> 20 分钟画出非常完整的架构，后面两题被严重压缩甚至讲不完——这本身在"delivery"维度会被扣分，因为
> 面试官认为你不懂得在受限时间内做优先级取舍；后者能保证三道题都有基本的、成体系的覆盖，即使深度有
> 限。这道题的时间管理本身就是被评分的能力之一，不是画完图之后才开始的"软技能"。

## 3. 下笔顺序（45 分钟怎么走，每题约 10–12 分钟）

**通用模板（三题各套一遍）**：1 min 点出核心矛盾 → 3–4 min API + 数据模型骨架 → 3–4 min 1–2 个关
键失败场景 → 1 min 收尾一句话总结。

1. **分账/Payout（约 12 min）**：核心矛盾"资金原子性 + 防止透支"；API 给 `transfers`/`payouts`/
   `balance(pending vs available)`；失败场景讲"银行退回"（异步失败,反向分录恢复余额）和"负余额触
   发 debit payout"。
2. **Feature Flag（约 10 min）**：核心矛盾"判定延迟要求极低但配置变更不频繁,读多写少";API 给
   `is_enabled(flag_key, context)` 本地判定 + 管理侧规则配置;失败场景讲"配置中心挂了 fail-open 到
   默认值"和"一致性哈希保证同一用户判定结果稳定"。
3. **Metrics（约 10 min）**：核心矛盾"写入量远大于读取量,要在采集端本地聚合";数据形态区分"客户端
   本地聚合结构"和"服务端时间序列存储";失败场景讲"上报必须异步非阻塞,哪怕丢失几条也不能拖慢业务
   请求"和"高基数维度要限制或降维"。
4. **收尾（约 3 min）**：一句话点出三道题共通的"慢路径/快路径分离"模式,证明不是孤立作答三道题。

## 4. 代码怎么组织

三道题各自的组件边界（同一个模式的三次复用）：

```
分账/Payout：
  记账（复用 sd03 的 ledger，不重新发明）── 转账原子性（saga/单分片事务）── 提现批处理（cut-off+重跑）

Feature Flag：
  规则存储（中心配置,慢路径） → 推送/拉取 → SDK 本地缓存（快路径,is_enabled 纯本地计算,不发网络请求）

Metrics：
  客户端本地聚合（时间窗口内求和/近似直方图) → 批量异步上报 → 服务端二次聚合 → 时间序列存储/查询
```

拆分原则：三道题都遵循同一条线——**"配置/规则怎么定"可以有延迟、要灵活可审计；"运行时怎么执行判
定/上报"必须低延迟、非阻塞、能优雅降级**，把这条原则在三道题里各讲一遍，就是这道题真正的得分点。

## 5. 核心图与契约骨架

```
Connect 分账：
[Charge] --分账比例--> [Transfer: platform_available → connected_available]（记账走 sd03 ledger）
[Payout: connected_available → bank_outgoing_clearing] --银行确认--> clearing 归零
                                                        --银行退回--> 反向分录恢复余额+Webhook通知

Feature Flag：
[管理侧 PUT /internal/flags/{key} {rules,default_value,kill_switch}] --推送/拉取(秒级)-->
[SDK 本地缓存] --is_enabled(key,context)纯本地计算,一致性哈希--> bool

Metrics：
[counter.increment/histogram.record] --本地按时间窗口聚合--> [批量异步上报]
--服务端二次聚合--> [(metric_name,tags,timestamp)→{count,sum,p50,p90,p99}]
```

关键 API 契约（每题各挑最核心的几条）：

1. 分账：`POST /v1/transfers Idempotency-Key {amount,destination}`；`GET /v1/balance →
   {available,pending}`；`POST /v1/payouts Idempotency-Key {amount,method}`。
2. Feature flag：`is_enabled(flag_key, context) → bool`（纯本地,无网络调用）；
   `PUT /internal/flags/{key} {rules,default_value,kill_switch}`。
3. Metrics：`counter.increment(name, tags)`、`histogram.record(name, value, tags)`（客户端库接
   口）；服务端查询按 `name+tags+时间范围`。

## 6. 面试里怎么说（边写边讲）

- 拿到第一题就先说：「我先用一句话点出这三道题的通用做法——每道题我会先讲核心矛盾,再给最小可用的
  API 和数据模型,最后挑一两个关键失败场景讲透,不会追求生产级完整度,这样能保证三道题都覆盖到。」
- 分账题被问"跨分片怎么保证转账原子性"：「用 saga——源账户先预留金额,目标账户入账成功后源账户再
  正式终结,任一步失败在已完成的一侧追加补偿分录回滚。」
- Feature flag 题被问"配置中心挂了怎么办"：「SDK 继续用本地缓存的最近一次成功拉取的规则做判定,从
  未成功拉取过就用预设默认值,判定本身不发网络请求所以不会被配置中心的故障拖慢或拖垮。」
- Metrics 题被问"为什么不直接每次调用都发一条原始数据"：「客户端本地先做时间窗口聚合能把上报频率
  降低几个数量级,这是应对'写入量远大于读取量'的核心手段。」
- 每道题收尾都用一句话："这道题的核心是……"，帮助面试官感知你已经讲完这道题、准备进入下一道，而不
  是含糊地拖着。

## 7. 常见跑偏（真实挂点，逐个给答法）

- **第一题就讲了 20 分钟画出非常完整的架构**：后面两题被严重压缩甚至讲不完,面试官会认为你不懂优先
  级取舍。破解:开场就明说"我会控制每题在 10 分钟左右",给自己也给面试官一个时间锚点。
- **分账题一上来就画 transfer/payout 表结构**：没先说"这是资金原子性+防止透支的问题",直接进细节。
- **Feature flag 题没区分"配置管理"和"运行时判定"两个不同性质的问题**：把两者耦合在一起,意味着改
  一个开关规则需要重新部署业务代码。
- **Metrics 题没区分"写路径要扛高吞吐"和"读路径要支持灵活查询"这两个相反的优化方向**：设计成每次
  调用都直接写中心存储,没有客户端本地聚合这一层。

## 8. 同族题 / 延伸

- 分账题的记账部分直接复用 sd03（Ledger）；如果面试官追问"两个连接账户能不能直接互转",答案是"不
  允许,所有资金流动都要经过平台账户留痕,方便对账合规"。
- Feature flag 和 Metrics 之间也有联动：flag 的判定结果本身可以用 metrics 的能力低成本打点上报,用
  来验证"灰度百分比是否符合预期"。
- 练习命令：对照
  `loop/rounds/07_system_design/sd06_payouts_flags_metrics/{rubric.md,model_answer.md,followups.md}`
  按 10 分钟一题的节奏计时口述三遍，重点自查有没有在任何一题上超时。
