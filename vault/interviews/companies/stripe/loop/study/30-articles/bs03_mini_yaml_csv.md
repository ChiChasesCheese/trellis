# bs03 · miniyaml：两个"没有异常、只有错值"的 bug，练"用相邻通过测试做差分定位"

> [!tldr]
> - 这轮考的不是"你会不会写缩进解析器"，是能不能在**完全没有 traceback 可追**的情况下，靠对比
>   通过/失败的相邻测试把范围缩小到一个常量
> - 三步套路：跑测试看红几个 → 两条都是"值不对没异常" → 找形状最接近但通过的测试，逐项对比"它们
>   到底哪里不一样"，差集就是嫌疑范围
> - 最值得带走的一个信号：**没有栈可以往上追的时候，去找一个"几乎一样但是绿的"测试，用它反推
>   "这条边界条件具体是什么"**——这比通读整个函数更快

## 1. 题目在说什么
`miniyaml` 是一个缩进敏感的 YAML 子集解析器：`lexer.py` 把每行文本变成带缩进信息的 `Line`
记录，`parser.py` 按缩进递归下降，把 `Line` 流变成嵌套的 `dict`/`list`/标量，`csvio.py` 再把
"顶层是一串映射的列表"这种文档跟 CSV 文本互转。两条 issue：

```
Bug report 1 — 列表项的第二个及之后的 key 全部丢失（连带后面所有内容也丢了）
> "- name: Alice\n  age: 30\n  active: true\n- name: Bob\n..." 解析出
> [{'name': 'Alice'}]——age/active 没了，第二条记录也整个消失。
> 单行的列表项（"- id: 1"）解析正常；不涉及列表的纯嵌套映射，任意深度都解析正常。

Bug report 2 — 复用同一个 Parser 实例解析第二份文档，返回空结果
> p = Parser(); p.parse("a: 1\nb: 2\n"); p.parse("x: 9\n") 第二次调用返回 {}，
> 期望 {"x": 9}。用一个全新的 Parser() 单独解析 "x: 9\n" 每次都是对的。
```

注意：这两条报告**都没有异常**，只是结果不对——这道题的排查手法和栈跟踪类的题目不一样。

## 2. 读库：3 分钟摸清结构
1. **README 的 Layout**：`lexer.py`（文本行 → `Line`）→ `parser.py`（`Parser` 递归下降）→
   `scalars.py`（文本 → 类型）；`csvio.py` 独立于 YAML，只认"顶层是一串 dict 的 list"这种形状。
2. **入口**：`parse_text(text)`（一次性用一个新 `Parser`）和 `Parser().parse(text)`（可复用同一
   个实例）——两条 bug report 分别对应这两种用法。
3. **跑测试**：`python -m pytest tests`，25 个测试，2 红，**都不是异常**。

## 3. 下手顺序（面试里就按这个来）
1. **跑失败测试，记录失败的形状**：`test_parse_top_level_list_of_multi_key_mappings` 报
   `[{'name': 'Alice'}]` 而不是两条完整记录；`test_parser_reused_across_calls_does_not_leak_state`
   报 `{}` 而不是 `{"x": 9}`。两条都是"值不对"，没有栈可以往上追。
2. **没有栈的时候，找"几乎一样但是绿的"测试**：`test_parse_list_of_single_key_mappings`（单
   key 的列表项）和 `test_parse_nested_mapping_two_levels`（任意深度的纯嵌套映射，不涉及列表）
   都是绿的——这把 bug 1 的范围缩小到"列表项的映射有第二个及以后的 key"这一种情况。
   `test_fresh_parser_instance_per_call_is_unaffected_by_reuse_bugs`（同样的文档，但每次用
   全新 `Parser()`）是绿的，跟失败测试对比"唯一的差异是不是复用了同一个实例"，把 bug 2 的范围
   缩小到"实例复用"本身，不是文档内容的问题。
3. **对着 worked example 手算，验证具体的数字**：bug 1 光靠"缩小到列表项的续行"还不够，要真的
   数一遍列——`"- name: Alice"` 里 `n` 在第几列？dash 占一列、空格占一列，所以是第 2 列（从 0
   计数），不是第 1 列。这一步不能靠读代码猜，要手动数。
4. **对着构造函数和这个方法各自做了什么，逐项列出来**：bug 2 没有 traceback，最快的路径是并排
   看 `Parser.__init__` 设置了什么、`Parser.parse()` 又碰了什么——`__init__` 设了
   `self.pos = 0`，`parse()` 重新做了 `self.lines = tokenize(text)` 但没碰 `self.pos`。
5. **假设，然后验证**：验证 bug 1 用一个只含两行的最小 repro（一个两 key 的列表项），打印
   `content_indent` 的实际值和期望值对比；验证 bug 2 直接打印两次 `parse()` 调用之间
   `self.pos` 的值。
6. **最小修复 + 回归**：这题两个 bug 加起来只有一个改错的常量 + 一行重置，改完重跑全部 25 个。

## 4. 调试工具怎么用
这道题**两个 bug 都没有异常可以进 pdb post-mortem**，pdb 命令表见
`loop/rounds/04_bug_squash/DEBUG_101.md`，这里只说这道题该怎么落地：

- 对"值不对没异常"的情况，`breakpoint()` 要主动插在你怀疑的那一行**之前**（不像有异常时可以用
  `--pdb` 自动停在崩溃点），比如插在 `_parse_list_block` 里 `content_indent = indent + 1` 后面，
  `p content_indent` 对照手数的列号。
- `pytest tests -k reused --pdb` 配合在 `Parser.parse()` 入口插 `breakpoint()`，`p self.pos`
  看第二次调用进来时这个值到底是多少，比脑内模拟"应该是 0 吧"可靠。
- 改完用 `pytest tests --lf` 只跑上次失败的两个，确认变绿了再跑全量。

## 5. 本题两个 bug 的排查实录

**Bug 1 — 列表项续行的缩进常量差了 1（off-by-one）**
- 现象：`test_parse_top_level_list_of_multi_key_mappings` 得到 `[{'name': 'Alice'}]`，缺
  `age`/`active`，第二条记录也没了——没有异常。
- 定位路径：先用两条相邻的绿测试划定范围——单 key 列表项正常、任意深度纯嵌套映射正常，说明 bug
  只在"列表项的映射有续行"这一种组合里。读 `_parse_list_block()`：`content_indent = indent + 1`
  是它算出来的"续行应该在哪一列"。手数 `"- name: Alice"` 这一行：`-` 占第 0 列，空格占第 1 列，
  `name` 从第 2 列开始——所以续行的正确列数应该是 `indent + 2`，不是 `indent + 1`。
- 根因分类：**off-by-one**——一个应该等于"dash + 空格"两个字符宽度的常量，被写成了 1。
- 为什么会"顺带丢掉后面所有内容"：`content_indent` 算错之后，`_parse_map_block()` 会把续行的
  缩进判定为"不属于这个块"，直接返回一个空 dict，**不消费这一行**；这一行没被消费，会被外层的
  `_parse_list_block` 循环当成下一个列表项去解析，从这里开始整个游标就乱了，后面所有内容都跟着
  错位——这也是为什么"缩小到哪个函数"和"理解为什么后果这么大"是两件事，前者靠差分测试，后者要
  读一遍递归调用关系。
- 修复：一个常量，`indent + 1` 改成 `indent + 2`。

**Bug 2 — `Parser.parse()` 忘了重置游标（跨调用残留状态）**
- 现象：`test_parser_reused_across_calls_does_not_leak_state` 得到 `{}`，期望 `{"x": 9}"`——
  没有异常。
- 定位路径：紧邻的 `test_fresh_parser_instance_per_call_is_unaffected_by_reuse_bugs` 用同样的
  文档、但每次都用全新 `Parser()`，是绿的——两个测试的唯一差异就是"复不复用同一个实例"，这就
  把 bug 锁定在"实例状态"上，不是文档解析逻辑本身的问题。并排看 `__init__`（设
  `self.pos = 0`）和 `parse()`（只重新赋值 `self.lines`，从不碰 `self.pos`）——第一次调用能对
  是因为 `pos` 恰好还停在初始值 0，第二次调用时 `pos` 已经停在上一份文档解析完之后的位置，对
  一份更短的新文档来说，`_parse_block()` 自己的边界检查会立刻判定"没有更多行了"，静默返回 `{}`。
- 根因分类：**跨调用残留状态**——`self.pos` 是应该在"开始一次新的 `.parse()`"时重置的字段，
  却只在构造函数里设置了一次。
- 一个可迁移的信号：**单独跑一个测试是绿的，但和另一个测试合起来跑（或者对象被复用）就变红** →
  第一嫌疑就是"哪个实例字段该在这次调用开始时重置却没重置"。
- 修复：一行，`Parser.parse()` 一开始加 `self.pos = 0`。

## 6. 面试里怎么说
- 复现完先说清楚这轮的特殊之处：「两个测试都没有异常，是值不对——没有栈可以往上追，我打算用
  相邻的通过测试来缩小范围，而不是通读整个 `parser.py`。」
- 定位 bug 1 时点出手算过程：「我数了一下 `'- name: Alice'` 这一行，`name` 从第 2 列开始，代码
  里算的是 `indent + 1`，应该是 `indent + 2`——我不只是把 1 换成 2 让测试过，是真的数过这个
  数字。」
- 定位 bug 2 时点出差分依据：「这两个测试用的是同一份文档，唯一的差别是要不要复用 `Parser`
  实例——所以我先看 `__init__` 和 `parse()` 各自碰了哪些字段，而不是怀疑文档本身有问题。」
- 交付时说清楚这轮跟别的轮次的差异：「这两个 bug 都是安静的错值，不是崩溃——我确认过修复之后
  全部 25 个测试都过，而不是只看那两个原来失败的。」

## 7. 常见跑偏
- **给"列表项的第二个 key"单独加一个特判分支**：功能上能让测试过，但没有修到根因（那个算错的
  常量），改动范围比实际的 bug 大得多，而且下一个新的边界情况（比如第三个 key）还是会踩坑。
- **让 `parse_text()` 而不是 `Parser.parse()` 自己去重置状态**：只是把"必须记得重置"这件事甩给
  了调用方的某一个用法，`Parser().parse()` 直接复用的场景依然是坏的——修复应该落在缺陷本身
  （`parse()` 不该依赖上次调用的残留状态）。
- **改测试放宽断言**：接受被截断的列表、或者删掉复用测试——测试就是这道题的 spec。
- **把递归下降解析器重写成显式栈**：两个 bug 分别是一个写错的常量和一处缺失的重置，现有的
  递归结构本身没有问题，"为了修一个常量而重新设计整个解析器"是过度工程。

## 8. 真实库对应 + 延伸练习
这两个 bug 没有对应到某一条具体编号的上游 issue（不像 bs01 的 Mako 路径穿越那样能指到一个
commit），但它们的**类别**是 `loop/LOOP_GUIDE.md` §4 明确列出的四类典型 bug 里的两类：

- **off-by-one**：一个"应该固定、代表某种字符宽度/边界关系"的常量算错了——这类 bug 在任何
  自己维护列宽/偏移量的解析器（缩进敏感语言、定长字段解析、分页逻辑）里都可能出现。
- **跨调用残留状态**：对象的某个字段"应该在下次调用开始时重新初始化"却只在构造函数里赋值过——
  这类 bug 的共同信号是"单独跑正常、连着跑/复用对象就不正常"，跟 `bs04`/`bs05` 里并发场景下的
  "该重置没重置"是同一个根因家族，只是这里不需要并发就能稳定复现。
- 延伸练习：`python3 loop/mock.py start bs03` → `test` → `ref`，第二遍练习时刻意不看 traceback
  提示（反正也没有），专门练"用一个几乎一样但是绿的测试做差分对比"这个动作的速度。
