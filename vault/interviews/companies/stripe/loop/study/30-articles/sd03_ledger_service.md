# sd03 · Ledger 记账服务：用双记账 + 只追加设计，证明每一分钱去哪了

> [!tldr]
> - 这题考的是：设计一个中心化的资金记账系统，能对任何一分钱回答"现在在哪、经历过什么"，且历史记
>   录任何人（包括自己）都不能悄悄修改——这是"钱"这个领域和普通业务数据本质不同的地方。
> - 三步套路：从题面认出这是"双记账不可变账本"而不是"一张余额表" → 定 accounts/transactions/entries
>   三层数据模型 → 讲清"只追加不更新单行余额"怎么应对热点账户，以及"完整性/及时性/清账"三项持续
>   校验怎么自动发现账不平。
> - 最值得带走的一个模式：**修正错误永远是追加反冲，不是 UPDATE**——历史记录只能增长，不能改写，
>   这条约束反过来决定了整个写路径和存储设计。

## 1. 题目在说什么（人话版）

公司里很多系统会产生跟钱有关的动作：扣款、手续费、退款、结算到商户银行账户、货币兑换……这些系统各
自维护自己的业务状态就够了，但公司整体需要有一个地方能回答"到底每一分钱现在在哪里、经历过什么"这种
问题——不管是财务报表、审计，还是哪天银行说"钱对不上"时我们要拿出可信记录来解释。这个系统每天承接
海量资金变动，很多账户资金变动极其频繁，我们不希望更新某个账户余额把这个账户的所有写操作串行化变成
瓶颈。钱有多种货币，一笔涉及汇率兑换的交易不应该让任何一种货币凭空多出来或消失，即便上游数据出错，
我们也要能第一时间自动发现"哪里对不上"，而不是等季度审计才发现。历史记录一旦生成，即便后来发现记
错了，也不能直接改，要用大家都能理解和追溯的方式去"修正"它。

一个 3 行小例子：客户付款 $100，平台抽取手续费 $3——这一笔业务事件对应三条不可变分录：`借
charge_unsubmitted 100 / 贷 merchant_pending 97 / 贷 stripe_fee_revenue 3`；三条分录的借贷之和相
等（100 = 97 + 3），这就是"账是平的"最小可验证单位。

## 2. 读题：把文字变成模型

- **功能性需求**：摄取各业务系统产生的资金移动事件；能查任意账户当前余额和历史某一时刻余额；支持
  多币种；发现异常要能自动报警而不是等审计。
- **非功能性需求**：高吞吐（数十亿事件/天量级）；热点账户不能成为写瓶颈；历史查询要高效。
- **核心不变量**（题面没有直接说"双记账"三个字，要靠"任何人都不能悄悄改历史""钱不能凭空出现或消
  失"这些描述识别出来）：
  1. **借贷恒等**：每笔交易内部按币种分组，Σdebit == Σcredit。
  2. **历史不可变**：`entries` 只能追加，不能改写；修正用反冲交易。
  3. **完整性**：每一个上游产生资金变化的事件都必须最终在账本里有对应记录。
  4. **清账归零**：过渡性质的 clearing 账户在一轮资金流转完成后应当归零，非零即报警。
- **一句话建模**：这是一个 **不可变双记账账本** 问题——摄取是被动的，余额是可以从 entries 重建的
  派生视图，"钱平不平"必须能被系统自己持续验证，而不是靠人工审计发现。

> [!note] 为什么不能直接在 accounts 表上 UPDATE 余额
> 候选方案是"一张 accounts 表存 balance 字段，转账时 UPDATE 两行"，或者"accounts（桶）+
> transactions（事件）+ entries（不可变借贷分录）三层，余额是异步物化的派生数据"。前者丢失历史、无
> 法审计、且高频账户会因为行级锁成为写路径瓶颈；后者牺牲了"读一次拿答案"的简单性，换来可审计、可重
> 建、可高并发写入的能力。这是"钱"这个领域必须的权衡——普通业务数据未必需要付出同样的代价，但面试
> 官期待你能一句话说出为什么这里必须付。

## 3. 下笔顺序（45 分钟怎么走）

1. **0–5 min 读题确认**：两句话复述 + 显式说出 4 条不变量，主动点破"这是双记账不可变账本"这个识别
   结果，别等面试官提示。
2. **5–15 min API + 数据模型**：先给内部写入接口（`POST /ledger/transactions`，要求
   `external_id` 作为幂等摄取的键），再画三层数据模型（`accounts`/`transactions`/`entries`），当场
   口述一个真实分录示例证明理解领域（第 1 节的手续费例子）。
3. **15–25 min 一致性/写路径**：讲清楚"写路径只追加 entries，不更新单行余额"怎么应对热点账户；讲
   `external_id` 唯一约束怎么吸收上游重复投递；讲跨主体转账用 saga 而不是跨分片分布式事务。
4. **25–32 min 读路径**：当前余额读物化表；历史某时刻余额用"最近快照 + 增量 entries 求和"；报表走
   独立 OLAP 副本，不与实时查询抢资源。
5. **32–40 min 对账**（本题招牌考点）：讲 Stripe 官方三项持续校验——及时性、完整性、清账；讲修正错
   误只能追加反冲交易。
6. **40–45 min 收尾**：抛出"这套设计和事件溯源的关系"这类延伸话题，展示知识的迁移能力。

## 4. 代码怎么组织

```
业务系统（支付/退款/结算/汇兑）→ outbox → 账本摄取层
                                              │ INSERT transactions(external_id UNIQUE, ...)
                                              │ ON CONFLICT DO NOTHING（幂等摄取）
                                              ▼
                                        entries（只追加，CHECK 约束校验借贷平衡）
                                              │
                          ┌───────────────────┼────────────────────┐
                          ▼                    ▼                    ▼
                 balances（物化，快路径读）  balance_snapshots   OLAP 副本（报表/对账）
                                          （按日快照，历史查询用）
```

拆分原则：**账本是被动摄取方，不是被业务系统随意直接写的共享数据库**。业务系统通过 outbox 发布事
件，账本消费并校验（唯一校验规则是借贷平衡），除此之外不做任何业务判断（要不要扣钱、扣多少是上游系
统已经做完的决定）。这样面试官问"账本要不要感知具体业务逻辑"，你能明确说"不需要，账本只验证平衡、
如实记录"。

## 5. 核心图与契约骨架

```
文本架构图：

[业务系统 A/B/C] --outbox--> [账本摄取(幂等: external_id唯一)] --校验借贷平衡--> [entries(只追加)]
                                                                                      │
                                                          ┌───────────────────────────┼─────────────┐
                                                          ▼                            ▼             ▼
                                                   [balances 物化表]        [balance_snapshots]  [OLAP 副本]
                                                   (当前余额,快路径)         (按日快照)           (报表/对账,慢路径)
```

关键 API 契约：

1. `POST /ledger/transactions  Idempotency-Key(=external_id)`
   `{external_id, event_type, entries:[{account_id, direction, amount, currency}]}`
   校验：按币种分组 Σdebit == Σcredit，不满足 → `422`，这是写入路径**唯一**允许拒绝请求的业务规则。
2. `GET /ledger/accounts/:id/balance?at=<timestamp>&currency=` → 支持任意历史时间点查询。
3. `GET /ledger/accounts/:id/entries?cursor=&limit=` → 游标分页，避免深分页全表扫描。
4. 错误修正没有 `PUT`/`DELETE`：只能再发一笔 `POST /ledger/transactions` 引用原 `transaction_id`
   的反冲交易。
5. 对外简化视图：`GET /v1/balance`、`GET /v1/balance_transactions`（分页流水）。

## 6. 面试里怎么说（边写边讲）

- 开场：「题面虽然没说'双记账'这几个字，但'任何人都不能悄悄改历史记录''钱不能凭空出现或消失'这两
  句话直接指向了双记账不可变账本——我按这个模型来设计。」
- 讲数据模型时：「我把'账户'和'分录'分开，账户是资金的桶，分录是不可变的借贷记录；举个例子，客户付
  款 $100 平台抽 3% 手续费，会拆成三条分录……」（带出第 1 节例子，证明真正理解领域而不是背模板）。
- 被问"为什么不直接 UPDATE 一行余额"时：「直接 UPDATE 丢失历史、无法审计，而且高频账户会因为行级
  锁成为写路径瓶颈；只追加分录换来可审计、可重建、可高并发写入，这是钱这个领域必须的权衡。」
- 被问"多币种怎么保证平"时：「不能跨币种直接相加，每种货币在自己的维度上独立校验借贷相等；跨币种
  兑换通过 FX clearing 账户中转，汇率差额落到单独的损益账户。」
- 被问"发现半年前一条分录记错了怎么改"时：「永远不直接改，追加一条内容相反的反冲交易，引用原始交
  易，两条记录都保留——账本的历史因此是'曾经发生什么、后来怎么被修正'的完整叙事。」
- 交付时：「核心的双记账模型和只追加设计我讲完了；如果时间允许我想展开讲完整性/及时性/清账这三项持
  续校验具体怎么跑。」

## 7. 常见跑偏（真实挂点，逐个给答法）

- **把这道题当成普通"账户余额表+转账"设计**：第一反应是"用一张 accounts 表存 balance，转账时
  UPDATE 两行"，没有识别出不可变性和可审计性这两个隐藏需求。破解：读题时专门找"不能悄悄改""不能凭
  空出现或消失"这类句子，它们就是在暗示双记账。
- **不先框需求就画图**：直接画"transactions(from,to,amount)"一张表，没有区分"账户"和"分录"的概
  念，没考虑多币种下怎么平账。
- **对热点账户没有对策**：默认所有写入都要更新同一行余额。破解：主动讲"只追加、不更新单行余额，余
  额异步物化"这条核心手段，必要时对个别真正需要强一致的账户单独加乐观锁，把代价限制在真正需要的地
  方。
- **全程用"最终一致就行"这种通用分布式系统思路，不讨论怎么证明账是平的**：钱这个领域"最终一致"不是
  一种策略而是一种负债，必须主动讲完整性/及时性/清账这三项持续校验，而不是轻描淡写带过。
