# sd04 · 分布式限流器：算法是次要的，"限流器自己挂了怎么办"才是主考点

> [!tldr]
> - 这题考的是：给多实例 API 网关设计限速系统，题面混杂了"按客户端限速""按端点限速""并发数限
>   制""系统过载降级"四种不同粒度的诉求，考的不是"背算法"而是失败模式下的反直觉权衡。
> - 三步套路：先拆开题面里揉在一起的四种保护机制并确认优先级 → 选算法（token bucket）+ 讲清楚多实
>   例共享状态怎么原子化 → 重点讲"限流组件自己挂了要 fail-open 而不是 fail-closed"这个反直觉但正确
>   的默认行为。
> - 最值得带走的一个模式：**保护机制的故障处理和业务本身的故障处理不是一回事**——业务系统挂了要保
>   守，保护层挂了要放行，把两者混为一谈是这题最容易丢分的地方。

## 1. 题目在说什么（人话版）

API 网关每天承接成千上万个商户的请求，调用模式千差万别——小商户几乎不调用，大平台正常每秒几百个请
求，但偶尔因为代码 bug 或促销活动短时间打出几万个请求。我们不希望一个商户的异常流量占满整个网关的
资源、影响到别的商户，也不希望客户端写得不好的重试逻辑（失败就立刻疯狂重试）把问题放大。网关是多实
例集群，一个商户的请求这次落这台机器、下次落那台，限速状态没法只在单机内存里解决，必须所有机器共享
同一份状态。反过来，用来做限速判断的组件本身也可能故障或变慢，如果它挂了导致所有正常请求全部被拒
绝，代价比"暂时放过一些本该被限速的流量"严重得多。不同操作对系统压力不一样，限速策略要能区分对待，
在真正大规模异常流量下还要有一层机制优先保障最关键的业务操作。

一个 3 行小例子：商户 A 的令牌桶容量 100、每秒补充 50 个令牌；正常调用消耗令牌立即放行；某一秒突然
打进 200 个请求，前 100+50=150 个（视桶内已有令牌数）放行，剩下的返回 `429` 并带
`Retry-After: 1`。

## 2. 读题：把文字变成模型

- **功能性需求**：按 API key（客户端）限速；按操作类型/端点限速；并发在途请求数限制；系统整体过载
  时按优先级降级。这是**四个不同粒度**的问题，开场必须先拆开说，而不是笼统设计成一个"万能限流器"。
- **非功能性需求**：判定延迟要足够低（毫秒级，不能成为请求路径瓶颈）；多实例共享状态；限流组件自
  身故障不能拖垮整体可用性。
- **核心不变量**：
  1. **判定延迟必须足够低**，不能成为请求路径上的显著瓶颈。
  2. **限速组件故障时默认放行（fail-open）**，而不是拒绝所有请求（fail-closed）。
  3. **限速是近似保护，不是精确计费**——允许多实例并发下出现少量超出配额。
  4. **策略可以动态调整**，不用重新部署网关。
- **一句话建模**：这是一个 **近似正确换低延迟和高可用** 的问题——四层防护（按客户端/按端点/并发
  数/整体降级）各自独立，慢路径管配置、快路径做判定，且判定组件自己出故障时要向着"业务可用性"倾斜
  而不是"限速精确性"。

> [!note] 为什么限速组件挂了要 fail-open 而不是 fail-closed
> 候选方案是"限流器挂了拒绝所有请求以求安全"，或者"限流器挂了放行所有请求并触发告警,必要时降级到本
> 地内存计数兜底"。直觉上前者更"安全"，但要看站在谁的角度——对支付类 API 而言，因为一个保护机制自
> 己故障就拒绝所有商户的合法请求（包括真实支付），造成的业务损失和信任损失远大于暂时放过一些本该被
> 限速的流量。Stripe 官方博客明确把这条作为设计原则，面试官会用这一问直接检验候选人是否只会套"故障
> 要保守"这一句通用套话而不做场景区分。

## 3. 下笔顺序（45 分钟怎么走）

1. **0–5 min 需求拆解**：这一步是本题特有的、比其他题更重要的开场动作——先说"这里其实是四个不同粒
   度的保护机制"，确认哪些必须做（按客户端限速）、哪些是加分项（分级降级）。
2. **5–15 min API 契约 + 算法选择**：内部判定接口 `allow(key, rule) → {allowed, remaining,
   retry_after}`；对外 `429 + Retry-After + X-Rate-Limit-Reason`；选 token bucket 并说清为什么不用
   固定窗口（边界处翻倍问题）。
3. **15–25 min 数据模型 + 两级架构**：Redis 存 `{tokens, last_refill_ts}` + Lua 脚本原子操作；本地
   内存令牌桶吸收热点、Redis 只做跨实例校准；配置（规则阈值）与判定执行解耦。
4. **25–38 min 失败处理**（本题真正的得分点）：限流组件挂了 fail-open + 降级本地计数；判定超时给
   短超时直接放行；噪声邻居用并发数限制单独治理；系统整体过载用分级降级（关键操作预留容量）。
5. **38–43 min rollout**：新规则先 dark launch 观察误杀率；给整个系统一个 kill switch。
6. **43–45 min 收尾**：主动提"和熔断的区别""公平性"这类延伸问题，展示对边界的清晰认知。

## 4. 代码怎么组织

```
配置管理（慢路径）                          请求执行（快路径）
PUT /internal/ratelimits/{account}   →   网关本地缓存（TTL/订阅失效通知）
  {global_rps, endpoint_overrides,          │
   concurrency_limit}                       ▼
                                    本地令牌桶（吸收大部分判定，降低对 Redis 的访问）
                                             │ 命中率不足/需要跨实例校准
                                             ▼
                                    Redis + Lua 脚本（原子读取补充量+扣减）
                                             │ Redis 不可用/超时
                                             ▼
                                    fail-open：放行 + 告警 + 降级到本地内存计数
```

拆分原则：**策略"怎么配"和"怎么判定"是两个完全不同风险等级的操作**，前者可以有秒级延迟、要审计留
痕；后者必须毫秒级、必须能优雅降级。四层防护（按客户端/端点/并发/整体降级）也各自独立开关，不要因为
都叫"限流"就合并成一套配置。

## 5. 核心图与契约骨架

```
文本架构图：

[网关实例 1..N] --本地令牌桶(吸收热点)--> [Redis 集群(按account一致性哈希分片)+Lua原子脚本]
        │                                         │
        │ Redis超时/不可用                         │ 正常
        ▼                                         ▼
   fail-open：放行+告警                    allow(key,rule)→{allowed,remaining,retry_after}
        │                                         │
        └─────────────────┬───────────────────────┘
                           ▼
                 429 + Retry-After + X-Rate-Limit-Reason
```

关键 API 契约：

1. 内部判定：`allow(key, rule[]) → {allowed, remaining, retry_after_ms, reason}`——`reason` 让客户
   端区分是全局限速/端点限速/并发限制中的哪一种，从而采取不同应对策略。
2. 对外响应：`429` + `Retry-After: <秒>` + `X-Rate-Limit-Reason: global-rate|endpoint-rate|
   global-concurrency|endpoint-concurrency`。
3. 配置管理：`PUT /internal/ratelimits/{account}`，幂等（同样配置提交多次结果一致）。
4. Redis key：`rl:{account}:{scope}`，按 account 一致性哈希分片，保证 Lua 脚本单分片内原子操作。
5. 限速判定本身**不需要幂等键**——同一请求被判定两次最多是宽严有微小出入，不会造成业务后果，这一
   点是和 sd02 幂等支付最大的区别，值得主动点出来。

## 6. 面试里怎么说（边写边讲）

- 开场：「题面里其实混了四种不同粒度的保护——按客户端、按端点、并发数、整体过载降级，我先分别说清
  楚，这样后面讨论权衡的时候不会混在一起。」
- 选算法时：「我选 token bucket 而不是固定窗口，因为固定窗口在两个相邻窗口交界处会让允许流量翻
  倍；滑动窗口能缓解但实现复杂一点，工程上 token bucket 配合 Redis + Lua 脚本是性价比较高的选择。」
- 被问"限流组件挂了怎么办"时（本题必答题）：「默认 fail-open，放行所有请求并触发告警，同时可以降
  级到网关本地内存计数兜底。这里的关键判断是站在谁的角度看'安全'——因为保护机制自己故障而拒绝所有
  合法请求，代价远大于暂时放过一些流量。」
- 被问"多实例并发判定同一个 key 会不会超发"时：「会有短暂小幅超限，这是'近似保护'必须接受的代价；
  核心手段是把同一 key 的判定路由到 Redis 里的同一个位置，用 Lua 脚本把读取和更新打包成一次原子操
  作，把不一致窗口压缩到网络延迟级别。」
- 被问"限流和熔断有什么区别"时：「限流是主动限制调用方速率、保护被调用方；熔断是调用方发现依赖持
  续失败后主动停止调用一段时间、保护自己不被拖垮，两者方向相反，可以共存。」
- 交付时：「四层防护和限流组件自身故障处理我讲完了；如果时间允许，我想展开讲多区域场景下怎么切全局
  配额。」

## 7. 常见跑偏（真实挂点，逐个给答法）

- **一上来就讲 token bucket 还是 sliding window**：没有先拆开题面里混杂的四种诉求，直接扎进算法细
  节。破解：开场先用一句话拆需求，算法选择放在第二步。
- **默认限速组件永远可用**：没有讨论 Redis 挂了怎么办；固定窗口算法且没意识到边界翻倍问题；多实例
  场景下用本地内存计数器却声称"实现了限速"（这在多实例下根本不生效）。
- **限流组件挂了坚持要 fail-closed**：说不出这个权衡背后的业务逻辑，把"保护机制的故障"和"业务系统
  的故障"混为一谈——业务系统挂了应该保守（fail-closed 式的降级），但限速器只是保护层，它的故障不应
  该拖累业务本身。
- **把限速规则的存储、判定逻辑、降级策略全部耦合在网关同一段代码里**：改一个客户端限额需要重新部署
  网关，说明没有把"配置慢路径"和"执行快路径"分开。

## 8. 同族题 / 延伸

- sd01（Webhook 投递）里的"per-tenant 隔离、fail-open"和这题是同一类思路在不同场景下的复用；两题连
  续被问到时，主动点出"这里和 Webhook 投递的租户隔离是同一个模式"是加分项。
- 和 sd02（幂等支付）的对比本身就是一个好话术：限速判断不需要幂等，因为判定两次的代价远小于扣款两
  次，正确性要求的松紧程度不同,决定了能不能用近似算法。
- 练习命令：对照
  `loop/rounds/07_system_design/sd04_distributed_rate_limiter/{rubric.md,model_answer.md,followups.md}`
  口述一遍，重点自查"限流组件挂了怎么办"这条能不能在 10 秒内给出 fail-open 的答案和理由。
