# sd05 · 订阅计费与开票：把幂等支付 + 记账迁移到"周期性有状态对象"这个新场景

> [!tldr]
> - 这题考的是：设计按周期自动开票、扣款、升降级按比例计费、失败重试的订阅系统，本质是把 sd02（幂
>   等支付）和 sd03（Ledger）已经建立的原则迁移到一个新的、周期驱动的业务对象上。
> - 三步套路：两句话复述 + 说出"每个周期恰好一张发票、恰好一次扣款"这条不变量 → 画订阅和发票两个
>   状态机及其联动关系 → 讲清楚比例计费怎么算、扣款失败怎么重试、月初洪峰怎么错峰。
> - 最值得带走的一个模式：**周期性计费系统 = 调度器(只触发) + 计算组件(算金额) + 幂等支付(已有机
>   制) + 状态机联动**——新计费模式（比如按用量计费）只需要换"算金额"这一层，骨架不变。

## 1. 题目在说什么（人话版）

商户希望把自己的产品做成按月/按年收费的订阅服务卖给用户，用户订阅后我们要在每个计费周期自动生成账
单并扣款，扣款成功订阅继续有效，失败要按规则重试几次、给用户宽限期，实在收不到钱可能暂停或取消订
阅。用户随时可能升降级套餐或改变订阅数量（比如按坐席收费新增坐席），周期中间发生的变化理论上要按时
间比例补收或退还。有的商户想给新用户试用期，试用期结束才开始扣款；有的用户要求立刻取消并退款,有的
商户选择周期结束才停止服务。每个月月初会有大量订阅同时到期需要生成账单和扣款,不希望所有操作挤在同
一瞬间冲击系统和下游支付能力。无论规则怎么调整，都必须保证每个订阅每个计费周期最多一张正式账单、最
多真正扣一次款。

一个 3 行小例子：用户 5 月 15 日从 $10/月套餐升级到 $30/月套餐，当前周期是 5 月 1 日–31 日；比例计
费按剩余 16/31 天计算：退回旧价 `10 × 16/31 ≈ $5.16`，补收新价 `30 × 16/31 ≈ $15.48`，这两笔调整生
成独立的发票行项目，取整规则固定并留痕。

## 2. 读题：把文字变成模型

- **功能性需求**：周期自动生成发票并扣款；升降级按比例计费；试用期；扣款失败重试+宽限期；取消
  （周期末 vs 立即）。
- **非功能性需求**：月初洪峰不能压垮系统；金额计算要可复现审计。
- **核心不变量**：
  1. **每个计费周期恰好一张正式发票**：不因调度器重跑或并发处理而重复开票。
  2. **每张发票恰好一次成功扣款**：复用 sd02 的幂等支付机制，绝不双扣。
  3. **三者状态最终一致**：订阅状态、发票状态、实际扣款结果不允许长期脱节。
  4. **金额计算可复现**：任何比例调整费用事后都能根据变更历史重新推导。
- **一句话建模**：这是一个 **按周期驱动、复用已有幂等/记账机制的状态机组合** 问题——真正的难点不
  是"定时扣一次钱"，而是让发票生成、比例计费、重试、状态推进在任意时序组合下都保持幂等一致。

> [!note] 为什么这题不是"从零发明一套新机制"
> 候选方案是"给订阅计费单独设计一套扣款/记账/通知逻辑"，或者"扣款复用 sd02 的幂等 PaymentIntent、
> 记账复用 sd03 的账本、状态通知复用 sd01 的 Webhook,这道题只新增'发票生成的周期调度'和'比例计费的
> 计算规则'两块"。前者会在面试里显得像是重新发明轮子，且容易漏掉幂等支付里已经踩过的坑（比如"调用
> 超时不知道扣没扣"）；后者能让面试官看到你对整个 Stripe 领域体系的理解是成体系的,而不是每道题孤立
> 作答。面试官如果临场把题目换成"按用量计费",能不能立刻反应"这还是同一套骨架、只是发票行项目的计
> 算规则变了",是检验真懂还是背模板的关键。

## 3. 下笔顺序（45 分钟怎么走）

1. **0–5 min 读题确认**：复述+说出不变量,主动确认试用期/比例计费/取消策略这些都在本题范围内。
2. **5–12 min 状态机**：画订阅状态机（`incomplete→active→past_due→canceled/unpaid`）和发票状态机
   （`draft→open→paid/void/uncollectible`），讲清楚两者怎么联动（扣款结果推动订阅状态）。
3. **12–20 min API + 数据模型**：`POST /v1/subscriptions`、`proration_behavior` 参数;数据模型区分
   `subscriptions`/`invoices`（唯一约束 `(subscription_id, period_start)`）/`invoice_line_items`。
4. **20–30 min 核心流程**：周期滚动怎么触发发票；比例计费公式；dunning 重试节奏；取消的两种模式。
5. **30–38 min 失败处理**（本题真正得分点）：扣款结果未知复用 sd02 的"先查询再决定"；调度器故障用
   租约防重复处理；月初洪峰把"生成草稿"和"真正扣款"错峰。
6. **38–43 min 对账 + rollout**：核对已支付发票金额 vs 记入 ledger 的收入分录；新计费规则先"模拟开
   票"验证再上线。
7. **43–45 min 收尾**：主动说"这道题不是从零发明,是组合应用前面几道题的机制",体现体系化理解。

## 4. 代码怎么组织

```
调度器（只负责触发,不做业务逻辑）
  按时间分桶扫描 current_period_end<=now 的订阅（不是每次全表扫描）
       │
       ▼
发票生成组件（按订阅当前价格/数量/比例计费规则生成草稿）
  INSERT invoices(draft) 唯一约束 (subscription_id, period_start) ← 幂等核心
       │ finalize（定稿窗口,商户可追加一次性费用）
       ▼
支付发起组件（复用 sd02 幂等 PaymentIntent,幂等键=invoice_id+attempt_count）
       │
       ▼
状态同步组件（扣款结果推动 invoice/subscription 状态机前进）
       │
       ▼
outbox → Webhook（复用 sd01）：invoice.paid / invoice.payment_failed
```

拆分原则：**调度（何时触发）、计算（算多少钱）、支付（怎么扣）、状态同步（结果怎么反映）四个组件各
管一段**，通过事件/消息解耦而不是同步调用链层层嵌套。这样新增一种计费模式只需要替换"计算"这一层。

## 5. 核心图与契约骨架

```
订阅状态机：
incomplete →(首张发票23h内付清)→ active →(扣款失败/未尝试)→ past_due →(重试成功)→ active
     │                                          │(重试用尽,按策略)
     └→ incomplete_expired                      ├→ canceled
trialing →(结束+有支付方式)→ active             └→ unpaid →(补齐)→ active
trialing →(结束+无支付方式)→ paused
任意状态 → canceled（终态）

发票状态机：
draft →(finalize)→ open →(扣款成功)→ paid
                       ├→(作废)→ void
                       └→(重试用尽仍未付)→ uncollectible
```

关键 API 契约：

1. `POST /v1/subscriptions {customer, items, trial_period_days?, proration_behavior}`。
2. `POST /v1/subscriptions/:id {items?, proration_behavior[create_prorations|none|always_invoice],
   cancel_at_period_end?}`——升降级要不要按比例计费必须显式表达，不能隐式决定。
3. `invoices` 唯一约束 `(subscription_id, period_start)`——防重复开票的核心手段，比应用层判断可
   靠,因为它在数据库层面兜底并发场景。
4. 所有写操作支持 `Idempotency-Key`（复用 sd02）。
5. 比例计费公式：`金额 × 剩余秒数 / 周期总秒数`，取整规则固定并落到行项目里留痕。

## 6. 面试里怎么说（边写边讲）

- 开场：「核心不变量是每个周期恰好一张发票、恰好一次扣款,这个我打算完全复用 sd02 的幂等支付机制,不
  重新发明。」
- 讲防重复开票时：「`(subscription_id, period_start)` 的数据库唯一约束是核心防线,不管调度器重跑还
  是多实例并发处理同一订阅,只会成功插入一条发票记录——应用层判断在并发下不可靠，必须数据库兜底。」
- 讲比例计费时：「升级发生在周期中间,生成两条调整行项目——退回旧价剩余部分、补收新价剩余部分,公式
  是金额乘以剩余秒数除以周期总秒数,取整规则固定下来并留痕,保证事后能重新推导计算过程。」
- 被问"扣款调用超时怎么办"时：「和 sd02 一样,先查询再决定,不武断标记成功或失败,标记为待确认交给后
  台任务收尾。」
- 被问"月初洪峰会不会压垮系统"时：「把'生成草稿发票'和'真正扣款'两个动作分开安排时间,提前批量生成
  草稿,把真正扣款的时间点用分桶或抖动分散到一个更宽的时间窗口。」
- 交付时：「订阅计费的核心骨架我讲完了,想强调一下这道题不是发明新机制,而是把 sd01/sd02/sd03 已经
  建立的机制组合应用到一个新的周期性对象上。」

## 7. 常见跑偏（真实挂点，逐个给答法）

- **把订阅计费简化成"一个定时任务每月扣一次钱"**：没意识到升降级、试用期、失败重试、取消这几种状
  态会互相交织，也没提炼出"每个周期最多一张发票"这条核心不变量。
- **只有一张 subscriptions 表,价格/周期/发票全塞在一起**：升降级时直接原地改金额字段没有留痕,没有
  独立的发票/行项目对象,事后无法审计一笔调整费用是怎么算出来的。
- **假设扣款总是要么立刻成功要么立刻失败**：没考虑"扣款结果未知"的情况,月初洪峰完全没对策，暗示
  "扫全表定时跑一遍"。
- **把"判断该不该续费""生成发票""发起扣款""处理结果"全部写成一个巨大定时任务函数**：没有清晰的
  组件边界,改一处逻辑要重新理解整个函数。

## 8. 同族题 / 延伸

- 扣款完全复用 sd02 的幂等支付 API 设计；记账完全复用 sd03 的双记账账本；状态变化通知完全复用 sd01
  的 Webhook 投递——面试时主动指出这种复用关系，是对整个领域体系融会贯通的直接证明。
- 如果面试官把题目换成"按用量计费"：订阅/发票状态机骨架不变,只需要替换"发票行项目怎么算金额"这一
  层,这正是 separation of concerns 这一维的设计价值所在。
- 练习命令：对照
  `loop/rounds/07_system_design/sd05_subscription_billing/{rubric.md,model_answer.md,followups.md}`
  口述一遍,重点自查"防重复开票"和"扣款结果未知"这两条能不能立刻联系到 sd02 的既有结论。
