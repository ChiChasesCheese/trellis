# sd01 · Webhook 投递系统：给不可信的商户端点做"尽力必达但绝不拖累别人"的通知管道

> [!tldr]
> - 这题考的是：把"内部事件 → 商户 HTTPS 端点"这条通知链路，在"端点完全不受我们控制、可能慢/挂/
>   恶意"的前提下设计成可靠、隔离、可审计的投递系统——不是画框图，是对失败模式的系统性推理。
> - 三步套路：两句话复述 + 抠出"至少一次/不保证顺序/租户隔离/不可变审计"四条不变量 → 先定 API 契约
>   和数据模型 → 再把失败模式（重试退避、噪声邻居、SSRF）一条条讲透，最后收尾对账和监控。
> - 最值得带走的一个模式：**商户端点是攻击面，不是"下游服务"**——凡是"发请求给外部提供的 URL"这
>   类设计，SSRF/DNS rebinding 防护和租户级资源隔离是默认必答项，不是加分项。

## 1. 题目在说什么（人话版）

公司内部几十个系统（支付、账户、争议……）每天产生大量事件——一笔付款成功了、一个账户被冻结了。商户
不想一直轮询我们查状态，所以他们在后台注册一个或多个 HTTPS 地址，声明自己关心哪些事件类型；事件产生
后，我们要主动把事件内容用 HTTP POST 打到这些地址上去。麻烦在于：商户那台服务器完全不受我们控制——
可能秒回，也可能挂了、卡死、返回一堆 500，甚至域名解析到内网地址。公司整体事件峰值约每秒一万条，我们
的承诺是"只要事件被接受了就必须尽力送到"，但绝不能因为一个商户的端点卡死就拖累其他所有商户。商户还会
问：能不能保证不重复处理、能不能保证顺序、如果他们把回调地址填成内网地址会怎样。

一个 3 行小例子：商户注册 `POST /v1/webhook_endpoints {url: "https://m.example.com/hook",
enabled_events: ["payment_intent.succeeded"]}`；我们这边一笔付款成功后生成
`event.id = "evt_123"`；投递时对该 URL 发 `POST {id: "evt_123", type: "payment_intent.succeeded",
data: {...}}`，商户返回 200 即算成功，返回 500 或者超时就要进入重试队列，而不是当场放弃。

## 2. 读题：把文字变成模型

这是这一轮**分数拉开差距最快**的一步——面试官不会给你结构化需求列表，一段业务白话砸过来，你必须在开
场几分钟内自己把它切成三块，大声说出来让面试官确认或补充：

- **功能性需求**：商户能注册/管理多个端点，按事件类型订阅；事件产生后要投递；投递失败要重试；商户能
  看到投递历史；商户能手动要求重发某个事件。
- **非功能性需求**：10k events/s 峰值；p99 首次投递尽量快（秒级量级）；一个商户的端点异常不能影响其
  他商户；系统本身要能水平扩展。
- **核心不变量**（这几条要显式说出口，后面所有设计决策都要能回溯到它们）：
  1. **至少一次投递**——事件一旦被接受，必须尝试到成功或明确放弃（进 DLQ），不能"送不到就算了"。
  2. **不保证顺序、不保证端到端 exactly-once**——网络本质上做不到，我们提供的是 at-least-once +
     商户侧按 `event.id` 去重的组合等价物。
  3. **租户隔离**——任何一个商户端点的行为都不能影响别的商户收通知的时效性。
  4. **不可变审计**——事件内容一旦生成不再改变，每一次投递尝试都要留痕。
- **一句话建模**：这是一个 **面向不可信外部端点的 at-least-once 投递系统**——匹配、签名、投递、重
  试、放弃五个环节各管各的，隔离和幂等贯穿始终。

拿到题面的前 5 分钟，具体动作是：把上面这段业务描述在脑子里过一遍，圈出所有"应该/必须/不能"这类词，
分类进"功能性"和"不变量"两个桶；凡是句子里出现"绝不能""无论如何都要"，几乎都是不变量而不是普通需
求——这题里"不能因为一个商户拖累所有人"就是这样一句话，直接对应租户隔离这条设计主线。

> [!note] 为什么不能一上来就画"网关 → 队列 → worker"
> 候选方案是"先画架构图再补需求"，或者"先说两句话复述 + 显式列不变量，再画图"。选前者的问题是：图
> 画到一半面试官问"你这个系统最重要的保证是什么"，答不上来就已经把 problem framing 这一维的分丢了；
> 选后者，后面每一个组件（per-tenant 隔离层、重试调度器、DLQ）都能一句话说清楚"它是为了满足哪条不变
> 量存在的"，面试官压力测试的时候你永远有话可回。这也是 rubric 里 1 分和 4 分的直接分界线。

## 3. 下笔顺序（45 分钟怎么走）

1. **0–5 min 读题确认**：两句话复述 + 显式说出 4 条不变量；主动确认规模（10k events/s）、延迟目标、
   商户是否需要投递历史和手动重发这几个假设。
2. **5–15 min API 契约**：先写商户侧管理 API（注册/更新/禁用 endpoint、`GET /v1/events` 补漏拉取、
   `POST /v1/events/:id/resend` 手动重发），再写出站请求契约（`Stripe-Signature` 头、`event.id` 作
   为幂等键、TLS-only、不跟随重定向）。这一步定的字段会被后面所有环节引用，先写对比后面改省时间。
3. **15–22 min 数据模型**：区分**可变配置**（`webhook_endpoints`）和**不可变事实**（`events` →
   `deliveries` → `delivery_attempts` 三层审计链），画出来，标注唯一约束（`(event_id, endpoint_id)`
   防止重复生成投递记录）。
4. **22–35 min 失败模式**（本题权重最高的一段，压分点集中在这）：重试退避+抖动+DLQ → 噪声邻居隔离
   （per-tenant 并发上限/队列 + 熔断）→ SSRF/DNS rebinding 防护（注册时校验 + 投递时直连校验过的 IP
   + 禁止跟随重定向）→ exactly-once 为什么做不到。这四块建议按这个固定顺序讲，因为它们是面试官最常
   按这个次序追问的（见第 6 节话术）。
5. **35–42 min 对账 + 可观测性**：商户侧补漏拉取、平台侧每日核对"应生成 vs 实际成功"的差异、DLQ 复
   盘；监控指标（分商户成功率、p99 延迟、队列深度、DLQ 增长率）；rollout（dark launch、密钥轮换新旧
   并存）。
6. **42–45 min 收尾**：主动抛一两个还没展开的方向（比如顺序保证的代价），让面试官带着问题继续追问，
   而不是干巴巴地说"讲完了"。

## 4. 代码怎么组织

系统设计轮不写代码，但组件边界要像代码模块一样能被一句话描述清楚：

```
Producer 系统（支付/账户/…）→ outbox（同事务写） → relay → 事件总线（如 Kafka，按 account_id 分区）
                                                              │
                                                              ▼
                                                       Dispatcher（匹配 endpoint 订阅，慢路径查配置走 Redis 缓存）
                                                              │  幂等：INSERT deliveries ON (event_id, endpoint_id)
                                                              ▼
                                              deliveries(pending) ──> 延迟队列/ZSET（按 next_attempt_at 调度）
                                                              │
                                                              ▼
                                       Worker 池（无状态、per-tenant 并发上限 + 熔断）── HTTP POST ──> 商户端点
                                                              │ 成功/失败都写 delivery_attempts
                                                    超过最大重试 ─▶ DLQ ─▶ 商户 Dashboard / 人工介入
```

拆分原则：**"谁负责决策、谁负责执行"是最高优先级的分割线**。Dispatcher 只回答"这个事件该发给哪些
endpoint"（慢路径，可以缓存）；Worker 只回答"把这一条 delivery 真正发出去"（快路径，必须快速失败并
释放资源）；重试调度是独立组件，不和 Worker 的请求处理逻辑耦合。这样面试官问"如果匹配逻辑要改，要不
要重启 Worker"，你能直接说"不需要，两者物理隔离"。

## 5. 核心图与契约骨架

```
文本架构图（面试白板同款画法，左到右四层）：

[业务系统 outbox] → [relay] → [事件总线(按 account 分区)] → [Dispatcher] → [deliveries(pending) 队列]
                                                                                    │
                                                            [Worker 池，per-tenant 隔离+熔断]
                                                                     │成功           │失败(<3天)
                                                                     ▼                ▼
                                                            delivery_attempts    延迟重试队列(指数退避+抖动)
                                                                                       │超过3天
                                                                                       ▼
                                                                                 DLQ + 商户可见 + 人工介入
```

关键 API 契约（面试口述时逐条带出）：

1. `POST /v1/webhook_endpoints {url, enabled_events[]}` → 幂等注册；`url` 只接受 https，注册时做 SSRF
   预检（拒绝私网/保留段/metadata IP）。
2. 出站请求：`Stripe-Signature: t=<ts>,v1=<HMAC>` + body 里 `event.id` 永不改变——这就是商户侧的幂
   等键，商户按它去重，不需要我们做任何额外协调。
3. `GET /v1/events?created[gte]=&cursor=&limit=` → 游标分页（不用 offset，避免深分页全表扫描）。
4. `POST /v1/events/:id/resend?endpoint=` → 手动补发，创建后 N 天内有效。
5. 错误码：投递响应非 2xx（含 3xx，不跟随重定向）一律判失败进入重试；管理 API 的错误统一结构化
   `{error:{type, code, message}}`。

## 6. 面试里怎么说（边写边讲）

- 开场：「我先用两句话复述一下——我们要把内部事件可靠地投递给商户注册的、我们完全不控制的 HTTPS 端
  点，核心不变量是至少一次投递、不保证顺序、租户隔离、审计不可变。我确认一下规模和延迟目标……」
- 画数据模型时：「我把`events`设计成不可变的事实源，`webhook_endpoints`是可变配置，`deliveries`和
  `delivery_attempts`分开是因为一次投递可能重试很多次，我要能看到每一次尝试的独立记录，这是审计要
  求。」
- 讲失败模式时（这是本题真正的考场）：「重试用指数退避加抖动，抖动是为了防止大量失败请求同时重试造
  成 thundering herd；一个端点连续失败会被熔断，避免占用全局 worker 资源——这是租户隔离在执行层的落
  地。」
- 被问 SSRF 时：「商户填的 URL 是不可信输入。两层防护：注册时解析域名拒绝内网/metadata 地址；但更关
  键的是投递时**不能重新走一次 DNS 解析再连接**，因为 TTL 可以被设得很短，攻击者可以在注册校验通过
  之后把域名重新解析到内网——这是 DNS rebinding，所以要用注册时校验过的 IP 直连，Host 头带原域名，
  并且禁止跟随重定向。」
- 被问 exactly-once 时：「做不到。我们发出请求后如果没在超时内收到响应，没法区分'对方没收到'和'对方
  收到了但响应丢了'，所以重试是唯一安全的默认动作。我们提供的是 at-least-once，配合商户按不可变的
  `event.id` 去重，业务效果上等价于 exactly-once。」
- 交付时：「核心投递链路和三条失败模式我已经讲完；如果时间允许，我想展开讲讲对账怎么发现 Dispatcher
  本身的 bug。」

## 7. 常见跑偏（真实挂点，逐个给答法）

- **单 region 单库，没人问也没主动提**：面试官不一定问多区域，但主动说一句"写路径按商户绑定 home
  region，跨区域切换要先 fence 掉旧 region"能体现你想到了这一层，而不是等被追问才想起来。
- **不先框需求就画图**：直接开始画"网关→队列→worker"，被问"这个系统最重要的保证是什么"答不上来。
  破解方法就是第 2 节那套动作——两句话复述 + 显式念出不变量，画图前先说完。
- **webhook 四问答不上**（这题的招牌坑，Staff 面试官的原话拒因就是"failure modes and system abuse
  推理不足"）：
  1. 商户端点持续 500 → 指数退避+抖动+3天上限进DLQ，可自动禁用端点。
  2. 商户端点 hang 住拖累别人 → per-endpoint并发上限 + per-tenant队列/令牌桶 + 短超时(2s/5s) + 熔断。
  3. 回调地址填成内网 → 注册时校验IP段 + 投递时直连校验过的IP（防DNS rebinding）+ 禁止跟随重定向。
  4. 能不能exactly-once → 不能，网络无法区分"没收到"和"响应丢了"，只能at-least-once+商户侧按
     event.id去重。
- **30 分钟讲完，图画得很漂亮，却全程没有主动提出任何 concern，仍然被拒**：面试官期望你像"审查自己
  的设计"一样主动找茬（"这里如果 Dispatcher 崩了会不会丢事件？不会，因为消费的是持久化队列，但可能
  重复消费，靠唯一约束兜底"）。不要等被问才防御，要主动进攻式地暴露你想到的风险点。
