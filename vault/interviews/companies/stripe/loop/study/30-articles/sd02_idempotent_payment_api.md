# sd02 · 幂等支付 API：让"同一个意图"无论重试几次都只扣一次钱

> [!tldr]
> - 这题考的是：设计一个对卡收款的核心接口，商户网络环境不可控导致同一笔业务意图被重复发送多次
>   HTTP 请求，系统必须保证绝不双扣、也不因为过度保守而误判成功请求为失败。
> - 三步套路：两句话复述 + 显式说出"一个幂等键最多一次外部扣款"这条不变量 → 先定幂等键的 API 语
>   义（存什么、冲突怎么答）→ 把"先 claim 再外呼"的三段式状态机讲透，尤其是"调用超时不知道扣没扣"
>   这个最难的场景。
> - 最值得带走的一个模式：**幂等不是"查一下缓存"，是一个持久化状态机**——DB 唯一约束原子 claim 处
>   理权 → 外部调用 → 记账 → 写回响应，每一步都要能从崩溃点恢复，而不是重新跑一遍。

## 1. 题目在说什么（人话版）

商户后台点一下"收款"，或者商户自己的服务端在结账流程里调用我们的核心接口，把金额、币种、卡信息传给
我们，我们联系卡组织完成授权扣款再把结果告诉商户。这个接口调用量很大，商户网络环境千差万别，经常出
现请求发出去了但因为超时/重试，同一笔"用户点了一次支付按钮"的意图被重复发了好几次 HTTP 请求——哪怕
打到不同机器、哪怕第一个请求还没处理完第二个就到了，我们绝对不能因此真的扣两次钱。同时不能因为过度
谨慎把本该成功的请求错误标记为失败（商户可能因此引导用户换支付方式重新下单，造成真实的重复扣款）。
更棘手的是：我们联系卡组织本身可能超时，这时候我们自己都不知道钱到底扣没扣。

一个 3 行小例子：商户带着 `Idempotency-Key: k1` 发起 `POST /v1/payment_intents {amount:1000,
currency:"usd"}`；网络抖动导致商户 5 秒后带着**同一个** `k1` 重发；第二次请求应该直接拿到和第一次一
模一样的响应（无论第一次是成功还是失败），而不是再发起一次真实扣款。

## 2. 读题：把文字变成模型

- **功能性需求**：对卡发起授权扣款；返回明确结果（成功/失败/需要用户操作）；支持退款；把每一笔钱的
  流向记清楚方便对账审计。
- **非功能性需求**：高频调用（假设 1 万 TPS 量级）；正确性优先于吞吐——这题**不是**一道"怎么扛住高
  并发"的题，是一道"高并发下怎么保证不出错"的题，这个定位偏差是本题最容易踩的第一个坑。
- **核心不变量**（开场必须显式说出）：
  1. **一个幂等键 ↔ 至多一次外部扣款**：无论重试多少次、打到哪台机器。
  2. **不丢单**：一个被接受的请求最终一定有确定性结果，不会永远卡在"不确定"而没有收尾路径。
  3. **金额精确**：一律用整数最小货币单位，绝不用浮点数。
  4. **记账与授权最终一致**：授权成功一定有对应记账，反之亦然，不允许"钱动了账没记"或"账记了钱没
     动"的中间态长期存在。
- **一句话建模**：这是一个 **外部资金调用的持久化幂等状态机** 问题——claim、外呼、记账、写回响应
  四步中的任何一步崩溃，都要能从记录的状态精确恢复到下一步，而不是从头重来。

> [!note] 为什么"查 Redis 幂等键 → 处理 → 缓存结果"这个直觉答案会崩
> 候选方案是"网关层用 Redis 存幂等键，查到就直接返回缓存"，或者"用数据库唯一约束原子 claim 处理权,
> Redis 只做已完成结果的读缓存"。前者在三种情况下会崩：并发的 cache miss（两个请求同时没查到缓存，
> 都跑去发起了调用）、外部授权成功但记账失败的部分失败、Redis 缓存丢失后无法判断是否已处理。后者把
> DB 唯一约束当作真相源，Redis 只是加速，即便 Redis 完全失效，正确性也不受影响，只是性能下降。这正
> 是 senior 和 staff 级别答案的分水岭。

## 3. 下笔顺序（45 分钟怎么走）

1. **0–5 min 读题确认**：复述 + 说出 4 条不变量；主动确认幂等键由客户端生成、通过 header 传入、有
   效期多长、并发同 key 请求怎么处理这几个关键假设。
2. **5–15 min API 契约**：`POST /v1/payment_intents` 要求 `Idempotency-Key`；先讲清楚**幂等键要保存
   首次请求的完整响应（状态码+body），不是一个布尔值**——这一点最容易被面试官追问"为什么"，要提前
   想好答案（否则重放可能因为系统状态变化返回不一致结果）。
3. **15–20 min 状态机**：画 PaymentIntent 生命周期（`requires_payment_method → processing →
   succeeded`），标出唯一两个终态。
4. **20–35 min 一致性/幂等实现**（本题真正的得分点）：讲"先 claim 再外呼"的三段式流程和
   `recovery_point` 崩溃恢复机制，重点展开"调用卡组织超时，我们自己都不知道扣没扣"——正确动作是**先
   查询确认真实状态，再决定下一步**，绝不盲目重试也绝不武断报失败。
5. **35–42 min 失败处理 + 对账**：并发操作用乐观锁；区域故障单写者+fencing；每日对账卡组织结算文件
   vs 自己的 charges 记录；`processing` 滞留监控。
6. **42–45 min 收尾**：主动说一句"如果时间允许我想展开讲 saga 补偿"，抛出还没展开的方向。

## 4. 代码怎么组织

```
API 层：POST /v1/payment_intents（要求 Idempotency-Key）
  │
  ▼
幂等层（DB 唯一约束是真相源，Redis 只做已完成结果的读缓存）
  │ INSERT idempotency_keys(account_id, key, ...) ON CONFLICT DO NOTHING
  │  ├─ 插入成功 → 本次请求拥有处理权，recovery_point=started
  │  ├─ 冲突且已完成 → 直接返回缓存的 response_code/body
  │  ├─ 冲突且处理中 → 409
  │  └─ 冲突且参数不一致 → 400 idempotency_error
  ▼
核心状态机（PaymentIntent 生命周期管理，本地事务）
  ▼
外部调用适配层（对接卡组织，自己生成的 charge_id 作为幂等标识传给对方）
  ▼
记账 / 通知（outbox 异步发出，不阻塞主流程）
```

拆分原则：**幂等判断、业务状态机、外部调用、记账通知是四个不同信任级别的层**，幂等层只关心"这个请
求处理过没有"，完全不知道"扣款"这个业务概念；外部调用层只关心"怎么和卡组织通信"，不知道幂等键的存
在。这样面试官问"如果外部调用换一家卡组织"，你能说"只改适配层"。

## 5. 核心图与契约骨架

```
文本时序图（三段式，面试白板同款）：

T1 原子 claim（DB 事务）
  INSERT idempotency_keys(account_id, key, params_hash, recovery_point='started')
  ON CONFLICT DO NOTHING
       │ 冲突 → 按 recovery_point/params_hash 分支返回（见上）
       ▼ 成功
T2 本地事务：payment_intents(status=processing), recovery_point='pi_created'
       ▼
外部调用（不在数据库事务内）：用 charge_id 作为传给卡组织的幂等标识
       ▼
T3 本地事务：charges + ledger_entries + outbox 写入；status=succeeded；
   recovery_point='finished'；response_body 写回 idempotency_keys
```

关键 API 契约：

1. `POST /v1/payment_intents  Header: Idempotency-Key`，body 含整数金额 + 币种 + payment_method。
2. 同 key 重放 → 返回首次的完整响应（含状态码）；同 key 不同参数 → `400 idempotency_error`；同 key
   并发在途 → `409`。
3. 错误结构：`{error:{type, code, message, param}}`，`type` 让客户端判断能不能重试。
4. `POST /v1/payment_intents/:id/confirm`、`/cancel`、`POST /v1/refunds` 同样要求幂等键。
5. 幂等键有效期 ≥24 小时，后台 reaper 清理过期记录。

## 6. 面试里怎么说（边写边讲）

- 开场：「我先确认——绝不能双扣，也不能因为超时就武断标记失败，金额一律整数最小货币单位。幂等键由
  客户端生成，我假设通过 header 传入，有效期我先按 24 小时设计。」
- 写幂等层时：「我用数据库唯一约束做原子 claim，因为两个并发请求打到不同实例，只有数据库能保证串
  行化；Redis 只是加速已完成结果的读取，不参与'是否已处理'的判断，这样即便 Redis 挂了正确性也不受
  影响。」
- 被问"为什么要存整个响应体而不是一个布尔标记"时：「因为如果只存'处理过'这个标记，重放请求执行到
  的系统状态可能已经变化，两次会拿到不一致的结果，破坏幂等的语义——幂等要求的是'完全相同的响应'，不
  是'不要重复执行'。」
- 被问"卡组织调用超时怎么办"时（这是本题最考验候选人的问题）：「不能直接重试，也不能直接报失败。正
  确做法是用之前生成的 charge_id 向卡组织发起幂等查询，确认真实状态；查询结果不确定时把状态标成
  processing，交给后台任务或对账收尾，绝不武断下结论。」
- 交付时：「核心的三段式幂等流程和崩溃恢复我讲完了；如果时间允许，我想展开讲 saga 怎么处理'风控→授
  权→记账→通知'这个多步骤编排。」

## 7. 常见跑偏（真实挂点，逐个给答法）

- **一上来讨论怎么调卡组织的 API**：没有先说清"绝不能双扣""绝不能因为超时就武断标记失败"这两条不
  变量，直接进实现细节。破解：开场先复述+念不变量,再进 API。
- **只画一个 charges 表，没设计单独的幂等记录存储**：面试官会追问"幂等键存哪、存什么"，答不出"要存
  完整响应体"就是 rubric 里的 1 分档。破解：主动讲清楚`idempotency_keys`表和它为什么要存
  `response_code`+`response_body`。
- **假设外部调用永远成功或永远及时失败**：没考虑"调用超时、自己也不知道扣没扣"这种最棘手的情况。这
  是本题唯一必答的核心追问，答案就是"先查询、再决定"——绝不盲目重试、绝不假设成功也不假设失败。
- **30 分钟画完图无 concern 仍被拒**：这道题的"staff 分水岭"就在于有没有主动提出"并发的 cache
  miss""外部成功但记账失败的部分失败"这类边角场景，而不是等着被问。
