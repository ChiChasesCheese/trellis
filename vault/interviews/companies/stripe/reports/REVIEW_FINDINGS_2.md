## q06_atlas_company_name — verdict: SOUND

Method: 2500 random inputs (`random.Random(2)`; optional REGISTERED block, 2-12 requests/RECLAIMs, names built from a 33-token vocabulary of articles/`and`/every suffix spelling/`&`/`,`/`-`/`'`/tabs/double spaces, joined by `,`/`, `/` & `/nothing, accounts with stray whitespace) vs an independent regex-based normalizer + registry oracle, for `part1`, `part1(persist=True)`, `part2`, `part3` and `normalize(..., strip_punctuation=True/False)` on all 12,964 generated names: 0 mismatches. All 16 normalization edge cases from problem.md match. 10 stdin cases (Examples 1-4, no trailing newline, CRLF, no PART line, empty, blank-only, `PART 2` alone) match byte-for-byte. Perf: 10^4 requests 0.034 s, 10^5 0.165 s (4.8x for 10x, linear). Template: 29/34 fail. Suite: 34 passed.

Findings:
1. (medium, spec) Step order 6-then-7 means an `and` that is glued to a neighbour by punctuation survives: `Salt and-Pepper` -> `salt and pepper`, whereas `Salt And Pepper` -> `salt pepper`, so the two are "distinct". This follows the literal step order in problem.md, but step 7 is flagged *reconstructed*, so a grader that strips punctuation before dropping `and` would disagree. Not changed; the `strip_punctuation=False` flag already exists for the other reading.
2. (low, spec) A REGISTERED-block name that is literally `REQUESTS` / `REGISTERED` (any case) is consumed as a section header: `REGISTERED / Requests / REQUESTS / 1|requests` -> `1|Name Available`. Unaddressed by the spec.
3. (low) Header-less mode: a first request whose account id starts with `part` (`party|Zed`) trips `lines[0].upper().startswith("PART")` and raises IndexError. Account ids are numeric in every source, so out of contract; `re.fullmatch(r"PART\s+(\d+)", ...)` would harden it.
4. (low, tests) The 5 `test_normalize_cases` rows whose expected value is `""` pass on the empty template (`normalize` stub returns `""`).

## q10_payment_intent_commands — verdict: BUG FOUND (fixed)

Method: 2500 random command streams (`random.Random(2)`; 3-18 lines over 3 merchants / 3 payments, amounts from {0,5,-3,x,1.5,+7,100,10}, INIT with a 3rd token 30% of the time, unknown merchant, BOGUS word, one-too-many / one-too-few arguments, and a timestamped variant with `x` / missing timestamps) vs an independent oracle written from the Rules section with **per-part arity**, for part1 / part2 / part3 / part4 (version C) / part4(immediate_credit=False) (version B). Before the fix: 509/2500 streams differed in each of Parts 1-3, 0 in both Part 4 modes. After the fix: 0 mismatches in all 5 configs. 10 stdin cases (Examples 1-5, Example 1 with and without header, no trailing newline, CRLF, empty, `PART 3` alone) byte-for-byte. Perf: 10^4 lines 0.025 s, 10^5 0.088 s (3.6x, linear). Template: 25/25 fail (no vacuous tests). Suite: 25 passed.

Findings:
1. (high, FIXED) `ARITY["INIT"] = (2, 3)` applied to every part, so in Parts 1-3 a 3-token `INIT` was not "wrong argument count -> ignored" (Rules, Edge cases) but executed, and its third token silently became a refund window. Repro A: `PART 1` / `INIT m 5 10` -> printed `m 5`; expected: no output. Repro B: `PART 3` / `INIT m 5 0` / `CREATE p m 10` / `ATTEMPT p` / `SUCCEED p` / `REFUND p` -> printed `m 15` (REFUND refused by the phantom `refund_limit 0`); expected: INIT ignored -> no merchants -> no output. Fix in `solution.py`: `ARITY["INIT"] = (2,)`, new `ARITY_TIMESTAMPED = {**ARITY, "INIT": (2, 3)}`, `Ledger` takes an `arity` table and `_run` selects it by `timestamped` (both Part 4 modes keep the optional limit). Regression test `test_init_with_extra_argument_is_ignored_in_parts_1_to_3` added (fails on the template).
2. (low, spec) Command words are upper-cased before dispatch, so `init m 5` is accepted. problem.md only shows uppercase words and says unknown words are ignored; a hidden test feeding a lowercase word and expecting a no-op would differ.
3. (low, spec) `_int` uses `int()`, which accepts `1_000`, `+7` and non-ASCII digits (`INIT m ٥` -> `m 5`). Stricter than the spec's "non-integer number -> ignored" would be `re.fullmatch(r"[+-]?[0-9]+", s)`.
4. (low, spec) A negative `refund_limit` (`1 INIT m 0 -1`) never refunds (`t - t_create > -1` for every in-order refund). Unspecified; documented so it is diagnosable.

## q17_datacenter_router_haversine — verdict: SPEC AMBIGUITY

Method: 2500 random command streams (`random.Random(2)`; 5-25 commands over 5 region names on a coarse lat/lon grid that forces exact distance ties, invalid coordinates 91/-91/181/-181/1.5/x/+5, capacities 0/-1/x, `SET_HEALTHZ` with TRUE/False/maybe/ghost, malformed ROUTE/DISTANCE/RELEASE, lowercase `route`, blank lines) vs an independent oracle (own Haversine, regex integer check, own tie handling) for `tie="name"` and `tie="registration"`: 0 mismatches. Float check: `haversine_km` vs the oracle's formula on 10^6 random integer coordinate pairs -> 0 rounding differences; the ROUTE inline formula vs `DISTANCE` on 2*10^5 pairs -> 0 differences. Example 4 values re-derived independently (20015.09 / 111.19 / 10007.54 / 1477.80). 8 stdin cases (Examples 1-4, no trailing newline, CRLF, empty, blank-only) byte-for-byte. Perf (test mix, 50 regions): 10^4 commands 0.094 s, 10^5 0.769 s (8.2x). Template: 23/24 fail. Suite: 24 passed.

Findings:
1. (medium, spec) `ROUTE` does not range-check its coordinates: `REGISTER a 0 0 1` / `ROUTE 100 200` -> `a 8963 a`. problem.md range-checks `REGISTER`, explicitly exempts `DISTANCE`, and is silent on `ROUTE`; a grader that validates the client position prints `ERROR`. Suggest one sentence in Part 3 either way. Not changed (the no-check reading is at least consistent with DISTANCE).
2. (low, perf) `ROUTE` is O(#regions), so the worst case within "up to 10^5 commands" is quadratic: 5,000 REGISTER + 5,000 ROUTE (10^4 lines) takes 11.9 s, 10^4 + 10^4 takes 49.5 s. Inherent to the spec (no spatial index is expected in an OA) and the perf test only uses 50 regions; a ~2x cheaper inner loop is available by ranking on `a` (strictly monotonic in `d`) and calling `sqrt`/`asin` only for the chosen region. Not changed.
3. (low, tests) `test_route_no_regions_and_all_unhealthy` asserts `out == [..., "ERROR"] or out[:6] == [...]`. The 7th expectation (`ERROR` for `ROUTE 1 2`) is wrong — the solution prints `NONE 0 a` (region full) — and the `or` hides it. Drop the first alternative and assert `NONE 0 a`.
4. (low) `DISTANCE` (`radians(lat2 - lat1)`) and `ROUTE` (`radians(lat2) - radians(lat1)`) use slightly different float paths; measured to never disagree after rounding on integer inputs. Documented only.

## q18_collusion_ring — verdict: SPEC AMBIGUITY

Method: 2500 random inputs (`random.Random(2)`; 0-8 records over 5 customers with 1-3 identifier fields (ragged 20% of the time) from small per-position pools incl. empty values and a value shared across positions, whitespace noise, blank lines) vs an independent O(n^2) pairwise-adjacency + DFS oracle for `direct_links` (6 targets incl. unknown), `groups`, `ring_size`, `should_block` (random K), `largest_ring`; Part 3 records with risks from {0,0,10,50,100,7,1,2} vs a `fractions.Fraction` mean; Part 4 records with mixed-case / empty fields, 4 targets incl. a ghost, thresholds from {0,0.2,0.3,0.49,0.5,0.51,0.7,0.8,1.0} vs Fraction arithmetic: 0 mismatches. 12 stdin cases (Examples 1-4 across PART 1/2/3/4, `NONE`, unknown target for PART 1 and 2, no trailing newline, CRLF, empty, `PART 3` with no records) byte-for-byte. Perf: 10^4 records 0.100 s, 10^5 0.594 s (5.9x). Template: 22/22 fail (no vacuous tests). Suite: 22 passed.

Findings:
1. (medium, spec) Ring risk is printed with `f"{risk:.2f}"`, i.e. round-half-even on the binary double, and problem.md says only "risk two decimals". Any ring whose scored-member count divides into an exact `.xx5` mean (8, 40, 200 ... members) prints differently from a HALF_UP grader (Java `String.format`, C# `F2`): 8 members with risks 1,1,1,1,1,1,1,2 -> mean 1.125 -> `1.12` here vs `1.13` half-up; risks summing to 21 -> `2.62` vs `2.63`. Either rule is a guess from the sources; not changed, but the rule should be stated in problem.md (CONVENTIONS.md asks for an explicit rounding mode) and `Decimal(sum) / n` with `ROUND_HALF_UP` is a one-line switch if HALF_UP is wanted.
2. (low, spec) Part 4 duplicate `user_id`: the last record silently replaces the earlier one (`u2,a,,` then `u2,zz,,` -> u2 no longer matches on name). Parts 1-3 treat repeated customers as multi-record (documented); Part 4's behaviour is unstated.
3. (low, spec) `PART 2` with an unknown target prints `0 ALLOW` (consistent with "unknown target -> 0" and `0 >= K` false for K >= 1); with `K = 0` it would print `0 BLOCK`. Not spelled out for stdout.
4. (low) `main` for PART 3 builds the components twice (`groups(...)` for the member lists, again inside `ring_risks`); harmless at 0.6 s for 10^5 records.
