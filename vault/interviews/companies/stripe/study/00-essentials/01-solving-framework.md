# 01 · 60 分钟通用解题框架

> 适用于：Stripe HackerRank OA、任何"一道大题分 3–5 个 part"的机考、45–60 分钟 phone screen。
> 不适用于：纯 LeetCode 竞速（那种题跳过第 1、2 步直接进第 3 步）。

---

## 0. 先认清这类题不是 LeetCode

| | LeetCode | 这类 OA |
|---|---|---|
| 输入 | 已解析好的 `List[int]` | stdin 上的原始文本，你自己解析 |
| 难点 | 想出算法 | **把规格翻译成没有歧义的代码** |
| 失分点 | 超时 / 想不出来 | 边界、舍入、排序 tie-break、输出多一个空格 |
| 评分 | 全过 or 不过 | 隐藏测试 17–25 个，**部分通过也能进下一轮** |

所以：**能拿的分先拿满**。Part 1 全绿比 Part 4 写一半值钱得多。

---

## 1. 分钟表（60 分钟版）

| 分钟 | 阶段 | 产出 | 绝不做的事 |
|---|---|---|---|
| 0–5 | **通读全部 part** | 一句话：最后一个 part 需要什么状态 | 写任何代码 |
| 5–10 | **定状态 + 写解析** | `parse()` 完成，能把输入变成记录 | 想优化 |
| 10–20 | **Part 1** | 跑通样例，**锁死** | 开始看 Part 2 |
| 20–32 | **Part 2** | 跑通样例，锁死 | 重构 Part 1 |
| 32–45 | **Part 3 / 4** | 跑通样例 | 追求优雅 |
| 45–55 | **边界扫描** | 空输入 / 单条 / 重复 / 乱序 / 0 / 负数 / 恰好等于阈值 | 写新功能 |
| 55–60 | **格式复核 + 交卷** | 删掉所有 debug 输出，样例逐字节对照 | 任何"再改一点" |

90 分钟的机考轮把每段按比例拉长，比例不变。

**"锁死"的含义**：这一 part 的样例全过 + 你自己编的 2–3 个边界过 + 你不会再动它。
没锁死就往下写，是这类题最贵的错误 —— 后面的 part 复用前面的函数，前面错了后面全错。

---

## 2. 第 0–5 分钟：从最后一个 part 倒着设计

**规则：状态的形状由最后一个 part 决定。**

典型的 5-part 结构长这样：

```
Part 1  解析 setup，把配置读进来
Part 2  处理事件流，累计每个实体的计数
Part 3  按阈值判定，输出满足条件的实体
Part 4  引入"撤销"事件（dispute / cancel / refund），撤销要能反向修改 Part 2 的计数
Part 5  边界：重复撤销、撤销不存在的 id、撤销后归零
```

如果你在 Part 2 只存了 `fraud_count`（一个整数），Part 4 要求"撤销某一笔具体的 charge"时，
你会发现**你不知道那笔 charge 是不是 fraud** —— 只能推倒重写。

正确做法：Part 2 就存 `charges[charge_id] = Charge(account, amount, is_fraud)`，
计数是从它派生的。多写 3 行，省下 15 分钟。

**倒着设计的三个问句**（读完全部 part 之后问自己）：
1. 最后一个 part 会**回头修改**已经处理过的东西吗？→ 会，就必须保留原始记录，不能只留聚合。
2. 最后一个 part 会**按不同的键**查询吗？→ 会，就现在建第二个索引。
3. 最后一个 part 的输出**顺序**是什么？→ 现在就把 tie-break 想清楚，别最后再补。

## 3. 四段式骨架（每道题都长这样）

```python
def parse(lines):    # 文本 → 记录。只做解析和归一化，不做业务判断。
    ...
def build(records):  # 记录 → 状态。建索引、按顺序放事件。
    ...
def compute(state):  # 状态 → 结果。所有业务规则只在这里。
    ...
def render(result):  # 结果 → 输出行。所有格式化只在这里。
    ...
```

四个函数各自可测，互不知道对方的细节。这不是"工程洁癖"，是**省时间**：

- 样例过不了时，你能一眼定位是解析错了还是规则错了（分别打印中间产物）。
- 下一个 part 通常只改 `compute`，`parse`/`render` 原样复用。
- 格式只在 `render` 里出现一次 → 改一次全对；散落在 8 个 `print` 里 → 改一次漏三处。

对应 `problems/` 里的公开 API 约定（见 `CONVENTIONS.md`）：
每个 part 一个纯函数 `part1(lines) -> list[str]`，加一个 `main(stdin, stdout)` 负责 dispatch。
**后面的 part 直接调用前面的 part**，这是设计意图，不是偷懒。

## 4. 读题时要抠死的六件事

读规格的时候，用笔（或注释）把这六件事**写下来**，不要"记在脑子里"：

1. **比较是严格还是非严格。** "exceeds 3" = `> 3`；"at least 3" / "3 or more" = `>= 3`。
   规格里含糊时，两种都写，用一个常量开关切换（见 `07-pitfalls.md` §1）。
2. **排序键的完整 tie-break。** "sorted by score" 后面一定跟着"平手怎么办"。
   没说 → 用 id 升序，并在注释里写明这是你的假设。
3. **钱的单位和舍入。** 分（整数）还是元（小数）？half-up 还是 truncate？在哪一步舍入？
4. **重复 / 未知 id 怎么办。** 忽略、报错、还是覆盖？三种都可能，规格通常在 "Edge cases" 里说。
5. **空结果输出什么。** 空行？`NONE`？什么都不输出？这三个是三个不同的测试。
6. **事件是否有序。** 输入按时间序给的吗？还是要你自己排？排了之后同一时刻的怎么办？

这六件事就是隐藏测试的取材库。抠死了，17–25 个隐藏测试里至少 8 个是白送的。

## 5. 每个 part 写完立刻做的三件事

```
① 把题面的 worked example 一字不差地跑一遍（复制粘贴，不要手敲）
② 自己编 2 个边界：一个"恰好等于阈值"，一个"空/单条"
③ 确认输出是逐字节相同，不是"看起来一样"
```

第 ③ 点的做法：

```python
assert actual == expected, repr(actual) + " != " + repr(expected)
```

用 `repr` 是关键 —— 尾随空格、`\r\n`、全角空格，肉眼看不出来，`repr` 一眼就看出来。

## 6. 落后于计划时的取舍顺序

时间不够了，按这个顺序放弃（从最先放弃到最后放弃）：

1. **性能**。先写 O(n²) 的正确版本。大多数隐藏测试是正确性测试，perf 测试只有 1–2 个。
2. **代码整洁**。复制粘贴一段改改，比抽象出一个函数快，而且不会引入新 bug。
3. **最后一个 part**。留一个能跑的、只实现前 N-1 个 part 的程序，比留一个跑不起来的全功能版本强。
4. **绝不放弃**：输出格式、已经写完的 part 的正确性。

**永远不要**：为了赶时间跳过样例验证。没验证的代码等于没写。

## 7. 交卷前 5 分钟清单

- [ ] 所有 `print(..., file=sys.stderr)` 的调试输出删掉或注释掉（stdout 上多一行 = 全挂）
- [ ] 每个 part 的样例重跑一遍（改后面的 part 可能碰坏了前面的）
- [ ] 空输入不崩（`parse([])` 会怎样？）
- [ ] 输出末尾的换行符符合要求（`print` 自带一个，`sys.stdout.write` 没有）
- [ ] 没有半个重构留在那里（要么改完，要么 `git checkout` 式地退回上一个能跑的版本）
- [ ] 浮点数没有出现在任何金额路径上

## 8. 这套框架为什么可迁移

换成 Amazon 的 OA（两道算法题 + work simulation）、换成 quant 的 OA（概率 + 模拟），
第 1、3、5、7 节原样成立；第 2 节的分钟表按题量重排；第 4 节的六件事里，
"钱和舍入"换成"数值精度"，其余不变。

**唯一真正题目专属的，只有业务规则本身。** 框架、边界纪律、输出纪律、时间纪律，
是同一套东西 —— 这也是 `code-core` 牌组存在的理由。
