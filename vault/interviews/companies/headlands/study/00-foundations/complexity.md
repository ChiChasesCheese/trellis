# 基础课 · 复杂度分析（Big-O）从零开始

> 本章配套代码：[`examples/ComplexityDemo.java`](examples/ComplexityDemo.java)（本章所有数字来自它，Apple Silicon、12 核、JDK 21）。
> 读者设定：会写循环和 `ArrayList`/`HashMap`，但没系统学过复杂度；本章不假设你见过 `O(...)` 之外的任何符号。

## 0. 这一章在讲什么

面试官几乎每道题都会问：「你这个解法的复杂度是多少？n 到一百万能跑吗？」背后是三个问题：

1. **你会不会数步数？**（能不能算出 `n(n-1)/2` 这种东西）
2. **你知不知道 Big-O 藏起来了什么？**（常数、缓存、内存分配——岗位强调 performance，这些才是重点）
3. **你能不能不跑代码就估出「大概几秒」？**（面试没有 IDE，只有脑子）

顺序：数步数（第 2 节）→ 记号 Big-O（3）→ 最好/平均/最坏（4）→ `log n`（5）→ 摊还分析（6）→ 运行时间估算及其何时骗你（8）。

## 1. 为什么需要复杂度：两个都「对」的程序，一个跑完要一年

### 1.1 一个手算例子

任务：在 n 条**已按编号排好序**的记录里查编号为 `x` 的那条。

**程序 A（线性查找）**：从第 1 条起逐条比较，直到找到。
**程序 B（二分查找）**：先看正中间那条：比 `x` 大就丢掉后一半，比 `x` 小就丢掉前一半，在剩下的一半里重复。

n = 10 时 A 最多比 10 次，B 最多 4 次，都「立刻」跑完。

n 更大时（`ComplexityDemo` 第 1 部分，数的是最坏情况下的比较次数）：

```text
           n         linear         binary
          10             10              4
        1000           1000             10
     1000000        1000000             20
   100000000      100000000             27
```

A 要比一亿次，B 只要 27 次。每次比较 1 纳秒（1 ns = 10⁻⁹ 秒）的话，A 要 0.1 秒，B 要 27 纳秒——**差约 400 万倍**。若每秒要查一百万次（行情系统很常见），A 需要 10 万秒才能做完一秒钟的活，根本做不到。

**复杂度描述「输入变大时代价怎么涨」**：不告诉你跑多少秒，告诉你「n 变成 10 倍，时间变成几倍」：

| 复杂度 | n 变成 10 倍 | n 变成 100 倍 |
|---|---|---|
| O(1) | 不变 | 不变 |
| O(log n) | 多加几步（约 +3） | 多加几步（约 +7） |
| O(n) | 10 倍 | 100 倍 |
| O(n log n) | 约 11–13 倍 | 约 130–150 倍 |
| O(n²) | **100 倍** | **10,000 倍** |

最后一行是关键：n² 的程序数据多 10 倍就慢 100 倍——「小数据测试全过，上线一跑就挂」的典型原因。

## 2. 数步数（counting steps）：一切复杂度分析的起点

### 2.1 是什么、为什么需要

**一步**（step）= 一个「花费固定时间」的基本操作：一次算术、一次比较、一次赋值、一次数组下标读写。复杂度分析就是**数程序一共做了多少步，写成输入规模 n 的函数 T(n)**。

只靠计时会受机器、JIT 预热、别的进程干扰，也没法在白板上计时；数步数**与机器无关、可以在纸上算**。

### 2.3 怎么数：四个基本形状

**形状 1：没有循环 → 步数固定 → O(1)**

```java
static int middle(int[] a) {
    return a[a.length / 2];       // 一次除法 + 一次数组读，不管数组多长都是这么多步
}
```

**形状 2：一层循环 → 步数 ∝ n → O(n)**

```java
static long sum(int[] a) {
    long s = 0;                   // 1 步
    for (int x : a) {             // 循环 n 次
        s += x;                   // 每次 1 步
    }
    return s;                     // T(n) = n + 2，写成 O(n)
}
```

**形状 3：两层嵌套循环 → n × n → O(n²)**

```java
static int countEqualPairs(int[] a) {
    int count = 0;
    for (int i = 0; i < a.length; i++) {
        for (int j = 0; j < a.length; j++) {   // 内层每次都跑满 n 次
            if (i != j && a[i] == a[j]) count++;
        }
    }
    return count;                              // 内层体执行 n × n 次
}
```

**形状 4：内层循环范围依赖外层 → 三角形求和**

```java
static int countEqualPairsOnce(int[] a) {
    int count = 0;
    for (int i = 0; i < a.length; i++) {
        for (int j = i + 1; j < a.length; j++) {   // j 从 i+1 开始：每对 (i,j) 只看一次
            if (a[i] == a[j]) count++;
        }
    }
    return count;
}
```

内层体执行次数：i = 0 时 n−1 次，i = 1 时 n−2 次，……，i = n−1 时 0 次，总数是

```text
(n-1) + (n-2) + ... + 1 + 0  =  n(n-1)/2
```

**为什么等于 n(n−1)/2？**（高斯配对法）把和写两遍，一遍正着一遍倒着，上下相加：

```text
   (n-1) + (n-2) + ... +   1   +   0
 +   0   +   1   + ... + (n-2) + (n-1)
 = (n-1) + (n-1) + ... + (n-1) + (n-1)      ← 一共 n 项，每项 n-1
```

所以两倍的和 = n(n−1)，和 = n(n−1)/2 = n²/2 − n/2。n = 20,000 时约 2 × 10⁸ 次——正好是 `ComplexityDemo` 第 4 部分跑的例子。

**形状 5：每次把问题缩小一半 → log n**（第 5 节详讲）

```java
static int binarySearch(int[] sorted, int target) {
    int lo = 0, hi = sorted.length - 1;
    while (lo <= hi) {
        int mid = (lo + hi) >>> 1;          // 为什么不写 (lo + hi) / 2？见下面「常见误区 1」
        if (sorted[mid] == target) return mid;
        if (sorted[mid] < target) lo = mid + 1; else hi = mid - 1;
    }
    return -1;
}
```

**组合规则**：

* **顺序执行 → 相加**：先 O(n) 再 O(n²)，总共 O(n + n²) = O(n²)。
* **嵌套 → 相乘**：外层 n 次、每次内层 log n 步，总共 O(n log n)。
* **调用函数 → 代入那个函数的复杂度**：循环 n 次、每次 `list.contains(x)`（O(n)），总共 O(n²)。**最容易漏掉**（误区 3）。

### 2.4 小练习：手数一个

```java
static int mystery(int n) {
    int steps = 0;
    for (int i = 1; i <= n; i *= 2) {      // i 取 1, 2, 4, 8, ...
        for (int j = 0; j < n; j++) {
            steps++;
        }
    }
    return steps;
}
```

外层 i 每次翻倍，从 1 涨到超过 n 需要 ⌊log₂ n⌋ + 1 次；内层每次 n 步。steps = n × (⌊log₂ n⌋ + 1)，复杂度 **O(n log n)**。n = 8 时 i = 1, 2, 4, 8 共 4 轮，每轮 8 步，steps = 32。

## 3. Big-O 记号：把「n + 2」和「3n² + 5n + 7」说成一个词

### 3.1 是什么

**Big-O** 是「忽略细节」的写法：只保留 T(n) 里**增长最快的一项**，并**去掉它前面的常数系数**。

| 精确步数 T(n) | Big-O |
|---|---|
| n + 2 | O(n) |
| 3n² + 5n + 7 | O(n²) |
| n(n−1)/2 = n²/2 − n/2 | O(n²) |
| 100 | O(1) |
| 5 n log n + 40n | O(n log n) |

### 3.2 为什么这样「忽略」是合理的

* **去低阶项**：n = 1,000,000 时 3n² = 3 × 10¹²，而 5n = 5 × 10⁶，只占百万分之二；n 越大越可忽略。
* **去常数**：换机器、换语言，「一步」的时间会差几倍，但 n 变 10 倍时「慢多少倍」不变。Big-O 描述的是与机器无关的**增长形状**。

代价：第 8 节会看到，n 不大时常数差 100 倍足以让 O(n) 输给 O(n²)。

> T(n) = O(g(n))：存在常数 c > 0 和 n₀，使得对所有 n ≥ n₀ 都有 T(n) ≤ c · g(n)。

**验证**：3n² + 5n + 7 = O(n²)。取 c = 15，n₀ = 1。n ≥ 1 时 n ≤ n² 且 1 ≤ n²，所以

取 c = 15，n₀ = 1。当 n ≥ 1 时 n ≤ n² 且 1 ≤ n²，所以

```text
3n² + 5n + 7  ≤  3n² + 5n² + 7n²  =  15 n²
```

对所有 n ≥ 1 成立。**c 和 n₀ 不唯一**，找到一对即可。

**同族的记号**：`Ω(g)`（下界）：T(n) ≥ c · g(n)，「至少这么慢」；`Θ(g)`（紧界）：既是 O(g) 又是 Ω(g)，「恰好这个量级」。

**口语习惯**：数学上 `O` 只是上界，「线性查找是 O(n²)」严格也对；但**面试里 O(·) 默认指最紧的那个**（即 Θ），实际紧界是 O(n) 却说 O(n²)，面试官会认为你没分析对。

### 3.4 常见量级，按增长速度排队

```text
O(1) < O(log n) < O(√n) < O(n) < O(n log n) < O(n²) < O(n³) < O(2ⁿ) < O(n!)

n = 1,000,000 时，每个量级大约是多少步：
  O(1)        1
  O(log n)    20
  O(√n)       1,000
  O(n)        1,000,000            (10⁶)
  O(n log n)  20,000,000           (2 × 10⁷)
  O(n²)       1,000,000,000,000    (10¹²)    ← 按 10⁸/秒算，需要约 3 小时
  O(2ⁿ)       一个有 301,030 位的数  ← 宇宙寿命也不够
```

### 3.5 Java 里怎么「看」出复杂度：先认集合类的常见操作

面试里 80% 会用到的集合操作：

| 操作 | 复杂度 | 说明 |
|---|---|---|
| `ArrayList.get(i)` / `set(i, x)` | O(1) | 数组下标 |
| `ArrayList.add(x)`（末尾） | 摊还 O(1) | 第 6 节 |
| `ArrayList.add(0, x)` / `remove(0)` | **O(n)** | 要整体挪动 |
| `ArrayList.contains(x)` / `indexOf(x)` | **O(n)** | 逐个 `equals` |
| `HashMap.get/put/containsKey` | 平均 O(1) | 最坏见第 4 节 |
| `TreeMap.get/put/floorKey/…` | O(log n) | 红黑树 |
| `PriorityQueue.offer/poll` | O(log n) | 二叉堆 |
| `PriorityQueue.peek` | O(1) | 堆顶 |
| `PriorityQueue.remove(Object)` / `contains` | **O(n)** | 要线性找 |
| `ArrayDeque.addLast/pollFirst` | 摊还 O(1) | 环形数组 |
| `LinkedList.get(i)` | **O(n)** | 要顺着指针走 |
| `Collections.sort` / `Arrays.sort(Object[])` | O(n log n) | TimSort |

## 4. 最好、平均、最坏：同一个程序，不同的输入，不同的步数

### 4.1 是什么

对**同一个 n**，不同输入可能让程序走不同步数：**最坏**（worst case）= 步数最多的输入；**最好**（best case）= 最少的；**平均**（average case）= 在**某个假设的输入分布**下的期望步数。

### 4.2 例子：线性查找

```java
static int linearSearch(int[] a, int target) {
    for (int i = 0; i < a.length; i++) {
        if (a[i] == target) return i;
    }
    return -1;
}
```

* 最好：target 在 `a[0]`，1 次比较 → O(1)。
* 最坏：target 在最后或不存在，n 次 → O(n)。
* 平均：**假设** target 等可能在 n 个位置之一，平均 (1 + 2 + … + n)/n = (n+1)/2 次 → O(n)。

「平均」必须先说清假设：若 target 几乎总在开头（热点数据），平均就是 O(1)。**不说假设就报平均复杂度是不严谨的。**

### 4.3 例子：快速排序（quicksort）与最坏情况

快排每次选一个「主元」（pivot），把数组分成「比它小」和「比它大」两堆再递归。

* 主元总接近中位数：每次折半，log n 层、每层处理 n 个元素 → O(n log n)。
* 主元总是最小（数组已排好序而你总选第一个）：每次只去掉 1 个 → n + (n−1) + … = O(n²)。

朴素快排：最好/平均 O(n log n)，最坏 O(n²)。修补：随机选主元、三数取中。Java 的 `Arrays.sort(int[])` 是 dual-pivot quicksort，靠保护措施（检测到劣化转堆排序）避开最坏输入；对象数组 `Arrays.sort(Object[])` 用 TimSort（归并类），保证 O(n log n) 且**稳定**。

### 4.4 例子：HashMap

`HashMap` 平均 O(1)：键散到桶里，每个桶平均常数个元素。**最坏**：

* 所有键哈希到同一个桶：JDK 7 以前是链表，查找 O(n)；JDK 8 起桶太长（≥ 8 个且表够大）转成红黑树，最坏 O(log n)（前提：键实现 `Comparable`，否则退化更厉害）。
* 不只是理论：对外服务若用用户输入当键，攻击者可构造大量哈希冲突的键（hash flooding）。

**面试怎么答**：「`HashMap.get` 平均 O(1)，最坏 O(log n)（JDK 8+，冲突桶树化）。」两个都说。

### 4.5 面试时说哪个？

* 默认说**最坏**（最保险），再补**平均/摊还**（更接近实际）。例：「快排平均 O(n log n)，最坏 O(n²)；我用随机主元避免最坏输入。」
* 低延迟系统里**最坏情况和尾延迟（tail latency）比平均更重要**：一千次里有一次慢 100 倍，平均看着很好，那一次可能就是亏钱的那一次。

## 5. log n 的直觉：「一次砍掉一半，要砍几次才剩 1 个」

### 5.1 是什么

`log n`（默认底数 2）= **n 不断除以 2，除到 1 需要几次**。

```text
n = 16 :  16 → 8 → 4 → 2 → 1       4 次      log₂ 16 = 4
n = 1000: 1000 → 500 → 250 → 125 → 62 → 31 → 15 → 7 → 3 → 1   约 10 次   log₂ 1000 ≈ 9.97
```

等价说法：**2 的几次方等于 n？** 2¹⁰ = 1024 ≈ 1000，所以 log₂ 1000 ≈ 10。

### 5.2 为什么「折半」的算法这么重要

猜数游戏：我想一个 1 到 1000 的数，你每次猜，我只说「大了」或「小了」。最聪明的猜法是每次猜剩余范围的中点：

```text
范围 [1, 1000]   猜 500  → "小了"
范围 [501, 1000] 猜 750  → "大了"
范围 [501, 749]  猜 625  → "小了"
...
```

每猜一次候选范围砍掉一半，**最多 10 次**一定猜中；一百万个数只要 20 次，十亿个数 30 次。

```text
候选范围的缩小（每行是一轮比较之后还没排除的区间，# 代表还可能的候选）：

  轮 0  ################################   32 个
  轮 1  ################                     16 个
  轮 2  ########                              8 个
  轮 3  ####                                  4 个
  轮 4  ##                                    2 个
  轮 5  #                                     1 个   log₂ 32 = 5 轮
```

### 5.3 log n 到处都是

* **二分查找**：每次丢一半。
* **平衡二叉树/堆的高度**：每往下一层节点数翻倍，n 个节点只有约 log₂ n 层。`TreeMap`、`PriorityQueue` 的 O(log n) 就是「从根走到叶子」。
* **数字的位数**：n 有 log₁₀ n + 1 位十进制、log₂ n + 1 位二进制。
* **分治递归的层数**：归并排序每层拆半，共 log n 层。

### 5.4 为什么我们不写底数

`log₂ n` 与 `log₁₀ n` 差一个固定倍数（≈ 3.32），Big-O 忽略常数倍，所以统称 O(log n)。

### 5.5 一张要背下来的表

| n | log₂ n（取整） |
|---|---|
| 10³ (一千) | 10 |
| 10⁶ (一百万) | 20 |
| 10⁹ (十亿) | 30 |
| 10¹² (一万亿) | 40 |
| 2⁶⁴ ≈ 1.8 × 10¹⁹ | 64 |

直觉：**工程里 log n ≤ 64，O(log n) 几乎等价于「很小的常数」**；O(n log n) 通常只是比 O(n) 慢 20–30 倍，不是慢得离谱。

### 5.6 Java 里怎么写

```java
// 数一数 n 要折半几次才到 1（等价于 floor(log2 n)）
static int floorLog2(long n) {
    int k = 0;
    while (n > 1) { n >>= 1; k++; }
    return k;
}

// 内置的更快写法：前导零个数
static int floorLog2Fast(long n) {
    return 63 - Long.numberOfLeadingZeros(n);
}
```

## 6. 摊还分析（amortized analysis）：偶尔很贵，但平均下来很便宜

### 6.1 是什么

有些操作**大部分时候 O(1)，偶尔 O(n)**。只看最坏那次会说它 O(n)；但关心**一连串操作的总代价**时，平均到每次仍是 O(1)。「把偶尔的贵操作平摊给前面许多便宜操作」的分析叫**摊还分析**。

> **定义**：一个操作的摊还代价 = 对**任意**一连串 m 个操作，总代价 ÷ m 的上界。

与「平均情况」不同：平均情况**假设输入随机分布**；摊还分析对**最坏的操作序列**也成立，不需要随机假设。

### 6.2 为什么需要它：先看一个「看着可怕」的数据结构

`ArrayList` 内部是 `Object[] elementData`，长度创建后不能改。`add` 超过容量时**分配更大的新数组，把旧元素全抄过去**：

```text
容量 4，已满：
  旧数组  [a][b][c][d]
                 │ add(e) 发现满了
                 ▼
  新数组  [a][b][c][d][e][ ]        容量扩到 6（1.5 倍），抄了 4 个元素
```

**这一次 `add` 抄 n 个元素，O(n)。**若每次 add 都这样，n 次就是 O(n²)，`ArrayList` 没法用。大家说 `ArrayList.add` 是 O(1)，是因为扩容时**容量成倍增长**，下一次扩容要等很久。

### 6.3 它怎么工作：逐步演示（容量每次翻倍，初始容量 1）

```text
add 次数   当时容量   这次 add 的代价
   1          1       写 1 次                           (容量 1 → 满了)
   2          1→2     抄 1 + 写 1 = 2
   3          2→4     抄 2 + 写 1 = 3
   4          4       写 1 次
   5          4→8     抄 4 + 写 1 = 5
   6,7,8      8       各写 1 次
   9          8→16    抄 8 + 写 1 = 9
  10..16      16      各写 1 次
  17          16→32   抄 16 + 写 1 = 17
```

贵的 add 出现在第 2、3、5、9、17、33 次……间隔每次翻倍。前 16 次 add：写 16 次 + 抄 (1 + 2 + 4 + 8) = 15 次 = 31，平均每次约 2。

### 6.4 证明（核算法 / accounting method）：翻倍扩容，每次 add 摊还 ≤ 3

**想法**：每次 `add` 你**付 3 个硬币**：

* 1 个付这次「写入新元素」的代价；
* 1 个存在**这个新元素**身上，将来扩容时付「抄它」的代价；
* 1 个存在**容量前半部分的某个旧元素**身上，将来扩容时付「抄那个旧元素」的代价。

**为什么够用**：容量 C 全满时触发扩容，要抄 C 个元素。上次扩容（C/2 → C）之后恰好 add 了 C/2 个新元素，每个手里存着 2 个硬币，共 C 个——**恰好够抄 C 个元素**，任何时刻都不赤字。

结论：对任意 m 次 `add`，总代价 ≤ 3m，摊还 **O(1)**，且**不依赖任何随机假设**。

### 6.5 证明（聚合法 / aggregate method）：任意增长因子 g > 1

增长因子 g（翻倍 g = 2；`java.util.ArrayList` 是 g = 1.5，源码 `newCapacity = oldCapacity + (oldCapacity >> 1)`）。n 次 add 后，最后一次扩容的容量 ≤ n，上一次 ≤ n/g，再上一次 ≤ n/g²……所有扩容的抄写总量

```text
copies ≤ n + n/g + n/g² + ...  =  n · 1/(1 − 1/g)  =  n · g/(g − 1)
```

* g = 2：copies ≤ 2n。
* g = 1.5：copies ≤ 3n。

每次 add 本身再写 1 次，所以总代价 ≤ n + 3n = 4n（g = 1.5），摊还 O(1)。

**验证**（`ComplexityDemo` 第 2 部分，n = 1,000,000，只数抄了多少元素，从容量 10 开始）：

```text
growth rule                  total copies   copies / n
x1.5 (java.util.ArrayList)        2430972         2.43
x2.0                              1310710         1.31
+10 each time                   499950000      4999.50   (n = 100000)
```

实测 2.43 ≤ 3、1.31 ≤ 2，与上界一致（上界是最坏的容量对齐，实际略低）。

### 6.6 反例：如果每次只加固定大小，会怎样

最后一行：**每次只扩 10 格**（`cap + 10`），扩容发生在容量 10, 20, 30, …, n，总抄写量 = 10 + 20 + … + n ≈ n²/20。n = 100,000 时约 5 × 10⁸（实测 499,950,000，每个元素平均被抄 5000 次），摊还变成 O(n)。

**教训：摊还 O(1) 依赖「几何增长」（容量乘以常数），不是「加常数」。** 所以 `ArrayList`、`StringBuilder`、`HashMap`、`ArrayDeque` 都是乘性扩容。

### 6.7 势能法（potential method，一句话）

给数据结构定义「势能」Φ（如 Φ = 2 × 元素数 − 容量），摊还代价 = 实际代价 + ΔΦ。扩容时势能骤降，正好抵消那次 O(n) 的实际代价。与核算法本质相同，势能法在复杂结构里更方便。

### 6.8 摊还 O(1) ≠ 每次都快：低延迟系统里的「毛刺」

摊还只说**平均**。扩容那一次仍要抄 n 个元素（n = 一千万时几十毫秒），还要分配大块新内存、产生待回收的垃圾——低延迟系统里不可接受的毛刺（spike）。

**解法：预分配。**

```java
// 事先知道大概规模：一次性开够，之后不会再扩容
List<Long> prices = new ArrayList<>(1_000_000);

// 更低延迟的做法：根本不用 ArrayList<Long>，用原始类型数组，启动时开好
long[] priceRing = new long[1 << 20];
```

这也是用 `long[]` 环形缓冲（容量固定，满了才扩）的出发点。

## 7. 空间复杂度与递归深度（简短）

* **空间复杂度**：**额外**用的内存，也用 Big-O。`sum(int[] a)` 只用几个变量，O(1)；复制数组 O(n)；建 `HashMap` 存 n 个元素 O(n)。
* **递归的空间**：每层递归占一个栈帧，深度 d 占 O(d) 栈。二分查找递归写法深度 log n，空间 O(log n)；朴素链表递归到 10⁵ 层可能 `StackOverflowError`。
* **时间和空间常常互换**：`HashMap` 多花 O(n) 空间，换来 O(n²) → O(n) 的时间。

## 8. 面试里怎么估算运行时间，以及这种估算什么时候会骗你

### 8.1 估算的方法：数 → 乘 → 看是不是 10⁸

**第一步：从 n 反推「允许的复杂度」。**

经验法则：现代机器上简单 Java 循环每秒约 10⁸ 次「基本操作」（保守值）。面试题时限通常 1–几秒，所以**总操作数别超过 10⁸ 到 10⁹**。

| n 最大是 | 一般要求的复杂度 | 为什么 |
|---|---|---|
| ≤ 10 | O(n!) 可以 | 10! = 3.6 × 10⁶ |
| ≤ 20 | O(2ⁿ) 可以 | 2²⁰ = 10⁶ |
| ≤ 500 | O(n³) 可以 | 1.25 × 10⁸ |
| ≤ 5,000 | O(n²) 可以 | 2.5 × 10⁷ |
| ≤ 10⁵ | 要 O(n log n) 或更好 | n² = 10¹⁰，太慢 |
| ≤ 10⁶ | O(n log n) 可以 | 2 × 10⁷ |
| ≤ 10⁸ | 只能 O(n) | 一遍扫描，且常数要小 |
| ≥ 10¹⁸ | 只能 O(log n) 或 O(1) | 比如大数求和公式、二分 |

**第二步：对「一步」的定义要诚实。**

* 一次数组读 + 一次比较 + 一次加法 ≈ 一步。
* 一次 `HashMap.put` 是几十步（算哈希、找桶、可能分配 `Node`）。
* 一次系统调用（读写文件/网络）是几百到几千步。

### 8.2 「10⁸/秒」到底准不准？

`ComplexityDemo` 第 3、4 部分的输出：

```text
dependent multiply-add loop     : 0.64 s for 1e9 iterations -> 1.6e+09 iters/s
HashMap<Integer,Integer> put 60 ns, get 10 ns  (1e6 random keys)
TreeMap<Integer,Integer> put 239 ns, get 215 ns  (1e6 random keys)

n=   2000: 2.00e+06 pairs,   0.002 s -> 8.24e+08 pairs/s (cnt=999025)
n=  20000: 2.00e+08 pairs,   0.098 s -> 2.04e+09 pairs/s (cnt=99991764)
n= 100000: 5.00e+09 pairs,   2.372 s -> 2.11e+09 pairs/s (cnt=2499950961)
```

读法：

1. **纯算术紧循环比 10⁸/秒快 10–20 倍**（1.6 × 10⁹ 次/秒；二重循环里 2 × 10⁹ 对/秒），所以 10⁸ 是**保守**估计，要覆盖「每步不是纯算术」的情形。
2. **每步涉及数据结构就远低于 10⁸**：`HashMap.put` 60 ns ≈ 1.7 × 10⁷ 次/秒；`TreeMap.put` 239 ns ≈ 4 × 10⁶ 次/秒。「一百万次操作」`HashMap` 0.06 秒，`TreeMap` 0.24 秒——O(1) 与 O(log n) 的差被放大成 4 倍（20 层树 × 每层一次可能的缓存未命中）。
3. **O(n²) 在 n = 10⁵ 时花 2.4 秒**，限时 1 秒就超时；n = 2 × 10⁴ 只要 0.1 秒。与 8.1 的「n ≤ 5000 可以 O(n²)」对比：表**偏保守，方向对**。

### 8.3 10⁸ 法则的六个局限（说出两三个会很加分）

1. **常数因子**：O(n) 且每步 100 ns，可输给 O(n log n) 且每步 1 ns（n 小于约 10⁶ 时）。小数据下排好序的 `ArrayList` + 二分常比 `TreeMap` 快。
2. **缓存未命中**：顺序读数组一步 ≈ 0.3 ns；随机读一个不在缓存里的地址一步 ≈ 50–100 ns。同样 10⁸ 步，前者 0.03 秒，后者 5–10 秒。
3. **内存分配与 GC**：每步 `new` 对象，累积的垃圾触发 GC 暂停；`List<Long>` 里每个 `Long` 都是一次分配。
4. **I/O 和系统调用**：读一行 CSV、打一行日志、发一个网络包都是微秒到毫秒级；「一百万行」的瓶颈常是读入本身，而不是你的 O(n) 算法。
5. **JIT 预热**：JVM 刚启动在解释器里跑，慢 10–50 倍，热点方法被 JIT 编译后才快；短小测试测不准。
6. **并行与硬件**：多核可把 O(n) 的实际时间除以核数；但共享数据会引入伪共享和锁。

### 8.4 三个手算估算练习（带完整过程）

**练习 1**：一百万个订单各做一次 `TreeMap.put`，要多久？

* n = 10⁶，每次 O(log n)，log₂ 10⁶ ≈ 20 层。
* 理论 10⁶ × 20 = 2 × 10⁷ 步，按 10⁸/秒 → 0.2 秒。
* 校对：239 ns × 10⁶ = 0.24 秒，吻合。**结论：约 0.2–0.3 秒，可接受。**

**练习 2**：n = 10⁵ 个价格，找出所有「和为 0 的数对」。暴力 O(n²)。

* n²/2 = 5 × 10⁹ 对。按 10⁸/秒 → 50 秒（保守）；按实测 2 × 10⁹/秒 → 2.5 秒。
* 都超过常见限时，要改：排序 + 双指针 O(n log n)，或哈希 O(n)。
* **说出口的话**：「暴力 5 × 10⁹ 次，每次一纳秒也要 5 秒，不行；用哈希表一遍扫，O(n)。」

**练习 3**：每秒 100 万条行情，每条要在有序 Map 里更新一档，每条的处理预算？

* 100 万条/秒 → 每条预算 1 微秒 = 1000 ns。
* `TreeMap.put` 239 ns，占四分之一，还没算解码、风控、下单。
* 所以真正低延迟的订单簿把价格映射成数组下标，每次更新 O(1) 且命中缓存，约几 ns。**O(log n) 与 O(1) 之外，常数才是关键。**

## 9. 常见误区

1. **用 `(lo + hi) / 2` 求二分中点。**`lo + hi` 超过 `Integer.MAX_VALUE`（约 21 亿）时溢出成负数、下标越界。这个 bug 在 JDK 的 `Arrays.binarySearch` 里真实存在多年（2006 年发现修复）。正确写法：`lo + (hi - lo) / 2` 或 `(lo + hi) >>> 1`（无符号右移，加法溢出了符号位结果也正确）。

2. **把 O(n) 和「n 次」混淆。**「我只用了一个循环所以 O(n)」不对，要看循环体每次做什么。

3. **漏掉隐藏的循环。**

   ```java
   static int slow(List<Integer> list, int[] queries) {
       int hits = 0;
       for (int q : queries) {               // n 次
           if (list.contains(q)) hits++;     // 每次 contains 是 O(list.size())
       }
       return hits;                          // 整体 O(n × m)，不是 O(n)
   }
   ```

   把 `list` 换成 `HashSet<Integer>`，`contains` 平均 O(1)，整体 O(n + m)。循环里 `s += x` 也是隐藏的 O(n)（每次复制整个字符串），整体 O(n²)，要用 `StringBuilder`。

4. **混淆摊还和平均。**摊还不需随机假设（对最坏操作序列成立），平均要对输入分布做假设。「摊还和平均有什么区别」是常见题。

5. **认为 O(n log n) 一定比 O(n²) 快。**只对足够大的 n 成立。n = 20 时插入排序（O(n²)）常比归并排序快——所以 JDK 的 `TimSort` 对短片段用二分插入排序。

6. **忽略「n」是什么。**`BigInteger` 加法若数有 d 位，每次是 O(d) 不是 O(1)。先说清 n 是行数？字符数？价位数？

7. **只报一个 O。**两个独立规模 n 和 m 的双重循环是 O(n × m)，不能简化成 O(n²)。订单簿题尤其常见（价位数 L、订单数 n、事件数 k 各是各的）。

## 10. 面试追问预演

**Q1：你的解法复杂度是多少？**
先说清 n 是什么：「设订单数为 n。建表 O(n)，每次查询 `HashMap.get` 平均 O(1)，总共 O(n + q)，空间 O(n)。」

**Q2：`ArrayList.add` 是 O(1) 吗？**
答：「单次最坏 O(n)——满了要复制到 1.5 倍的新数组；但几何增长使 n 次 add 总复制量 ≤ 3n（等比数列 n·g/(g−1)，g=1.5），摊还 O(1)。知道规模我会用 `new ArrayList<>(n)` 预分配避免毛刺。」

**Q3：n 是 10⁶，选 O(n log n) 还是 O(n²)？**
答：「n² 是 10¹² 次，按 10⁸/秒要三个小时，不行；n log n 约 2 × 10⁷，百毫秒量级，可以。」

**Q4：O(1) 的 `HashMap` 一定比 O(log n) 的 `TreeMap` 快吗？**
答：「渐近上是；实际看常数——100 万随机 key，`HashMap.put` 60 ns，`TreeMap.put` 239 ns，约 4 倍；而且 `TreeMap` 能做范围查询和有序遍历，`HashMap` 不能。选哪个取决于是否需要有序。」

## 11. 自测题

**Q1（概念）** 判断：「这个函数是 O(n²)」和「这个函数是 Θ(n²)」有什么区别？

<details><summary>答案</summary>

`O(n²)` 只是上界：步数最多按 n² 增长，实际可能远小于它（线性函数也是 O(n²)）。`Θ(n²)` 是紧界：上下界都是 n²，恰好平方量级。面试里说 O 一般默认指最紧的。

</details>

**Q2（手算）** 下面代码内层 `count++` 一共执行多少次？复杂度是什么？

```java
static long q2(int n) {
    long count = 0;
    for (int i = 0; i < n; i++)
        for (int j = i; j < n; j++)
            count++;
    return count;
}
```

<details><summary>答案</summary>

i = 0 时内层 n 次，i = 1 时 n−1 次……i = n−1 时 1 次，总数 n + (n−1) + … + 1 = n(n+1)/2，O(n²)。n = 4 时 4 + 3 + 2 + 1 = 10。

</details>

**Q3（手算）** 第 2.4 节 `mystery(n)`，n = 16 时返回多少？

<details><summary>答案</summary>

外层 i = 1, 2, 4, 8, 16 共 5 轮（⌊log₂ 16⌋ + 1 = 5），每轮 16 步，返回 80，O(n log n)。

</details>

**Q4（证明）** 一个动态数组每次满了就扩容为原来的 **4 倍**。n 次 add 的总复制量上界是多少？摊还代价呢？

<details><summary>答案</summary>

g = 4：copies ≤ n · g/(g−1) = 4n/3 ≈ 1.33n。每次 add 写 1 次 + 摊还复制 ≤ 1.33，总摊还 ≤ 2.33，仍是 O(1)。代价是内存：扩容后最坏有 3/4 空间闲置（g 越大浪费越多，时间/空间的折中）。

</details>

**Q5（实现）** 写一个函数，数出 `1..n` 的二进制位数（不用 `Math.log`），并说明复杂度。

<details><summary>答案</summary>

```java
static int bitLength(long n) {
    int bits = 0;
    while (n > 0) { n >>= 1; bits++; }   // 每次右移一位 = 除以 2，共 ⌊log2 n⌋ + 1 次
    return bits;
}
```

复杂度 O(log n)。内置做法 `64 - Long.numberOfLeadingZeros(n)` 是 O(1)（一条 CPU 指令）。

</details>

**Q6（辨析）** `ArrayDeque.addLast` 摊还 O(1)，`ArrayList.add(0, x)` 是 O(n)。如果要频繁在头部插入，为什么 `ArrayDeque` 可以而 `ArrayList` 不行？

<details><summary>答案</summary>

`ArrayList` 是普通数组，元素必须从下标 0 紧密排列，头部插入要把所有元素后移一位，O(n)。`ArrayDeque` 是环形数组，用 `head`、`tail` 两个下标，头部插入只需 `head` 回退一格（模容量），不挪元素；满了才扩容，摊还 O(1)。

</details>

**Q7（估算）** 有 2 × 10⁵ 个整数，问有多少对 `i<j` 满足 `a[i] + a[j]` 是偶数。暴力解会超时吗？有没有 O(n) 的做法？

<details><summary>答案</summary>

暴力是 n²/2 = 2 × 10¹⁰ 对，按 2 × 10⁹ 对/秒也要约 10 秒，超过常见 1–2 秒限时。和为偶数 ⇔ 两数奇偶相同：数出偶数个数 e 和奇数个数 o，答案 = e(e−1)/2 + o(o−1)/2，一遍扫描 O(n)。

</details>
