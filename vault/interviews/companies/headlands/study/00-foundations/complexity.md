## 0. 这一章在讲什么、为什么 Headlands 的面试绕不开它

面试官几乎每道题都会问一句：「你这个解法的复杂度是多少？n 到一百万能跑吗？」

这句话背后其实是三个问题：

1. **你会不会数步数？**（能不能算出 `n(n-1)/2` 这种东西）
2. **你知不知道哪些细节被 Big-O 藏起来了？**（常数、缓存、内存分配——Headlands 的 JD 强调 performance，这些恰恰是重点）
3. **你能不能不跑代码就估出「大概几秒」？**（面试里没有 IDE，只有你的脑子）

本章按这个顺序讲：先学「数步数」（第 2 节），再学记号 Big-O（第 3 节）、最好/平均/最坏（第 4 节）、`log n`（第 5 节）、摊还分析（第 6 节），最后学怎么估算运行时间以及这种估算什么时候会骗你（第 8 节）。

## 1. 为什么需要复杂度：两个都「对」的程序，一个跑完要一年

### 1.1 一个手算例子

任务：在一张有 n 条记录的、**已按编号排好序**的表里，查编号为 `x` 的那一条。

**程序 A（线性查找）**：从第 1 条开始，一条一条比，直到找到。

**程序 B（二分查找）**：先看正中间那条。比 `x` 大，就丢掉后一半；比 `x` 小，就丢掉前一半；然后在剩下的一半里重复。

n = 10 时，A 最多比 10 次，B 最多比 4 次。差别不大，两个都「立刻」跑完。

n = 100,000,000（一亿）时（这是 `ComplexityDemo` 第 1 部分的实测输出，数的是「最坏情况下比较了几次」）：

```text
           n         linear         binary
          10             10              4
        1000           1000             10
     1000000        1000000             20
   100000000      100000000             27
```

A 要比一亿次，B 只要比 27 次。如果每次比较是 1 纳秒（1 ns = 10⁻⁹ 秒），A 要 0.1 秒，B 要 27 纳秒——**差了约 400 万倍**。如果这个查询每秒要做一百万次（行情系统很常见），A 需要 10 万秒才能做完一秒钟的活，也就是根本做不到。

**复杂度就是用来描述「输入变大时，代价怎么跟着涨」的语言。** 它不告诉你「跑多少秒」，它告诉你「n 变成 10 倍，时间变成几倍」：

| 复杂度 | n 变成 10 倍 | n 变成 100 倍 |
|---|---|---|
| O(1) | 不变 | 不变 |
| O(log n) | 多加几步（约 +3） | 多加几步（约 +7） |
| O(n) | 10 倍 | 100 倍 |
| O(n log n) | 约 11–13 倍 | 约 130–150 倍 |
| O(n²) | **100 倍** | **10,000 倍** |

最后一行是关键：n² 的程序，数据多 10 倍就慢 100 倍。这就是「小数据测试全过，上线一跑就挂」的典型原因。

## 2. 数步数（counting steps）：一切复杂度分析的起点

### 2.1 是什么

**一步**（step）= 一个「花费固定时间」的基本操作：一次算术、一次比较、一次变量赋值、一次数组下标读写。

复杂度分析的做法是：**数程序一共做了多少「步」，写成输入规模 n 的函数 T(n)**。

### 2.2 为什么需要它

「这个程序快不快」如果只靠计时，会受机器、JIT 预热、别的进程干扰；而且你没法在面试白板上计时。数步数是**与机器无关**、**可以在纸上算**的。

### 2.3 怎么数：四个基本形状

**形状 1：没有循环 → 步数固定 → O(1)**

```java
static int middle(int[] a) {
    return a[a.length / 2];       // 一次除法 + 一次数组读，不管数组多长都是这么多步
}
```

**形状 2：一层循环 → 步数 ∝ n → O(n)**

```java
static long sum(int[] a) {
    long s = 0;                   // 1 步
    for (int x : a) {             // 循环 n 次
        s += x;                   // 每次 1 步
    }
    return s;                     // T(n) = n + 2，写成 O(n)
}
```

**形状 3：两层嵌套循环 → n × n → O(n²)**

```java
static int countEqualPairs(int[] a) {
    int count = 0;
    for (int i = 0; i < a.length; i++) {
        for (int j = 0; j < a.length; j++) {   // 内层每次都跑满 n 次
            if (i != j && a[i] == a[j]) count++;
        }
    }
    return count;                              // 内层体执行 n × n 次
}
```

**形状 4：内层循环范围依赖外层 → 三角形求和**

```java
static int countEqualPairsOnce(int[] a) {
    int count = 0;
    for (int i = 0; i < a.length; i++) {
        for (int j = i + 1; j < a.length; j++) {   // j 从 i+1 开始：每对 (i,j) 只看一次
            if (a[i] == a[j]) count++;
        }
    }
    return count;
}
```

这里内层体执行的次数是：i = 0 时 n−1 次，i = 1 时 n−2 次，……，i = n−1 时 0 次。总数是

```text
(n-1) + (n-2) + ... + 1 + 0  =  n(n-1)/2
```

**为什么等于 n(n−1)/2？**（高斯小时候的配对法）把这个和写两遍，一遍正着一遍倒着，上下相加：

```text
   (n-1) + (n-2) + ... +   1   +   0
 +   0   +   1   + ... + (n-2) + (n-1)
 = (n-1) + (n-1) + ... + (n-1) + (n-1)      ← 一共 n 项，每项 n-1
```

所以两倍的和 = n(n−1)，和 = n(n−1)/2。展开是 n²/2 − n/2。当 n = 20,000 时，约 2 × 10⁸ 次。这个数字你以后会反复遇到——它正好是 `ComplexityDemo` 第 4 部分跑的例子。

**形状 5：每次把问题缩小一半 → log n**（第 5 节详讲）

```java
static int binarySearch(int[] sorted, int target) {
    int lo = 0, hi = sorted.length - 1;
    while (lo <= hi) {
        int mid = (lo + hi) >>> 1;          // 为什么不写 (lo + hi) / 2？见下面「常见误区 1」
        if (sorted[mid] == target) return mid;
        if (sorted[mid] < target) lo = mid + 1; else hi = mid - 1;
    }
    return -1;
}
```

**组合规则**（把上面几种拼起来）：

* **顺序执行 → 相加**：先 O(n) 再 O(n²)，总共 O(n + n²) = O(n²)。
* **嵌套 → 相乘**：外层 n 次，每次内层 log n 步，总共 O(n log n)。
* **调用函数 → 代入那个函数的复杂度**：循环 n 次，每次调用 `list.contains(x)`（O(n)），总共 O(n²)。**这是最容易漏掉的一种**——见第 9 节误区 3。

### 2.4 小练习：手数一个

```java
static int mystery(int n) {
    int steps = 0;
    for (int i = 1; i <= n; i *= 2) {      // i 取 1, 2, 4, 8, ...
        for (int j = 0; j < n; j++) {
            steps++;
        }
    }
    return steps;
}
```

外层 i 每次翻倍，从 1 涨到超过 n 需要 ⌊log₂ n⌋ + 1 次；内层每次 n 步。所以 steps = n × (⌊log₂ n⌋ + 1)，复杂度 **O(n log n)**。n = 8 时：i = 1, 2, 4, 8 共 4 轮，每轮 8 步，steps = 32。（答案同时也在第 11 节自测题里。）

## 3. Big-O 记号：把「n + 2」和「3n² + 5n + 7」说成一个词

### 3.1 是什么

**Big-O** 是一种「忽略细节」的写法：只保留 T(n) 里**增长最快的那一项**，并且**去掉它前面的常数系数**。

| 精确步数 T(n) | Big-O |
|---|---|
| n + 2 | O(n) |
| 3n² + 5n + 7 | O(n²) |
| n(n−1)/2 = n²/2 − n/2 | O(n²) |
| 100 | O(1) |
| 5 n log n + 40n | O(n log n) |

### 3.2 为什么这样「忽略」是合理的

* **去低阶项**：n = 1,000,000 时，3n² = 3 × 10¹²，而 5n = 5 × 10⁶，后者只占前者的百万分之二。n 越大，低阶项越可以忽略。
* **去常数**：换一台机器、换一种语言，「一步」的时间会差几倍，但 n 变成 10 倍时「慢多少倍」不会变。Big-O 描述的正是这种与机器无关的**增长形状**。

但这个「忽略」是**有代价的**——第 8 节会看到常数差 100 倍足以让 O(n) 输给 O(n²)（在 n 不大时）。先把记号学会。

### 3.3 正式定义（只需要看一遍）

> 说 T(n) = O(g(n))，意思是：存在常数 c > 0 和 n₀，使得对所有 n ≥ n₀ 都有 T(n) ≤ c · g(n)。

**用定义验证一个例子**：证明 3n² + 5n + 7 = O(n²)。

取 c = 15，n₀ = 1。当 n ≥ 1 时 n ≤ n² 且 1 ≤ n²，所以

```text
3n² + 5n + 7  ≤  3n² + 5n² + 7n²  =  15 n²
```

对所有 n ≥ 1 成立，定义满足。注意**c 和 n₀ 不是唯一的**，只要找到一对就行。

**同族的另外两个记号**（面试里很少严格区分，但读书时会遇到）：

* `Ω(g)`（下界）：T(n) ≥ c · g(n)。「至少这么慢」。
* `Θ(g)`（紧界）：既是 O(g) 又是 Ω(g)。「恰好这个量级」。

**重要的口语习惯**：数学上 `O` 只是上界，所以「线性查找是 O(n²)」严格说也对（上界松）。但**面试里说 O(·) 默认指最紧的那个**，也就是 Θ。如果你说「O(n²)」而实际紧界是 O(n)，面试官会认为你没分析对。

### 3.4 常见量级，按增长速度排队

```text
O(1) < O(log n) < O(√n) < O(n) < O(n log n) < O(n²) < O(n³) < O(2ⁿ) < O(n!)

n = 1,000,000 时，每个量级大约是多少步：
  O(1)        1
  O(log n)    20
  O(√n)       1,000
  O(n)        1,000,000            (10⁶)
  O(n log n)  20,000,000           (2 × 10⁷)
  O(n²)       1,000,000,000,000    (10¹²)    ← 按 10⁸/秒算，需要约 3 小时
  O(2ⁿ)       一个有 301,030 位的数  ← 宇宙寿命也不够
```

下表是你面试里 80% 会用到的（具体到 Javadoc 的出处，见每章讲）：

| 操作 | 复杂度 | 说明 |
|---|---|---|
| `ArrayList.get(i)` / `set(i, x)` | O(1) | 数组下标 |
| `ArrayList.add(x)`（末尾） | 摊还 O(1) | 第 6 节 |
| `ArrayList.add(0, x)` / `remove(0)` | **O(n)** | 要整体挪动 |

## 4. 最好、平均、最坏：同一个程序，不同的输入，不同的步数

### 4.1 是什么

对**同一个 n**，不同的输入可能让程序走不同的步数。于是有三种说法：

* **最坏情况**（worst case）：所有长度为 n 的输入里，步数最多的那个。
* **最好情况**（best case）：步数最少的那个。
* **平均情况**（average case）：在**某个假设的输入分布**下的期望步数。

### 4.2 例子：线性查找

```java
static int linearSearch(int[] a, int target) {
    for (int i = 0; i < a.length; i++) {
        if (a[i] == target) return i;
    }
    return -1;
}
```

* 最好：target 恰好在 `a[0]`，1 次比较 → O(1)。
* 最坏：target 在最后或不存在，n 次比较 → O(n)。
* 平均：**假设** target 等可能出现在 n 个位置之一，平均比较 (1 + 2 + … + n)/n = (n+1)/2 次 → O(n)。

注意「平均」必须先说清假设。如果实际使用中 target 几乎总是在开头（热点数据），平均就是 O(1)。**不说假设就报「平均复杂度」是一种不严谨。**

### 4.3 例子：快速排序（quicksort）与最坏情况

快排每次选一个「主元」（pivot），把数组分成「比它小」和「比它大」两堆，再递归。

* 如果主元总是接近中位数：每次问题折半，层数 log n，每层总共处理 n 个元素 → O(n log n)。
* 如果主元总是最小（比如数组已排好序、而你总选第一个当主元）：每次只去掉 1 个元素 → n + (n−1) + … = O(n²)。

所以朴素快排是「最好/平均 O(n log n)，最坏 O(n²)」。实际的修补方法：随机选主元（让最坏情况的概率变得极小）、三数取中。Java 的 `Arrays.sort(int[])` 用的是 dual-pivot quicksort，仍然理论上有 O(n²) 的最坏输入，JDK 的实现靠一些保护措施（检测到劣化时转为堆排序）避开；而对象数组的 `Arrays.sort(Object[])` 用 TimSort（归并类），保证 O(n log n) 且**稳定**。

### 4.4 例子：HashMap

`HashMap` 平均 O(1)：把键散到桶里，每个桶平均只有常数个元素。**最坏**呢？

* 所有键哈希到同一个桶：这个桶里挂了 n 个元素。JDK 7 以前是链表，查找 O(n)；JDK 8 起桶太长（≥ 8 个且表够大）会转成红黑树，最坏变成 O(log n)（前提：键实现了 `Comparable`，否则树内只能靠 `hashCode` + 类名等打破平局，退化得更厉害）。
* 这不只是理论：对外暴露的服务如果用用户输入当键，攻击者可以构造大量哈希冲突的键（hash flooding）。

**面试怎么答**：「`HashMap.get` 平均 O(1)，最坏 O(log n)（JDK 8+，冲突桶树化）。」两个都说，就显得你懂。

### 4.5 面试时说哪个？

* 默认说**最坏**（最保险），然后补一句**平均/摊还**（更接近实际）。
* 例：「快排平均 O(n log n)，最坏 O(n²)；我用随机主元避免最坏输入。」
* 低延迟系统（Headlands 就是）里**最坏情况和尾延迟（tail latency）比平均更重要**：一千次里有一次慢 100 倍，平均看着很好，但那一次可能就是亏钱的那一次。

## 5. log n 的直觉：「一次砍掉一半，要砍几次才剩 1 个」

### 5.1 是什么

`log n`（本章默认底数 2，写作 log₂ n）= **n 不断除以 2，除到 1 需要几次**。

```text
n = 16 :  16 → 8 → 4 → 2 → 1       4 次      log₂ 16 = 4
n = 1000: 1000 → 500 → 250 → 125 → 62 → 31 → 15 → 7 → 3 → 1   约 10 次   log₂ 1000 ≈ 9.97
```

等价的另一种说法：**2 的几次方等于 n？** 2⁴ = 16，所以 log₂ 16 = 4；2¹⁰ = 1024 ≈ 1000，所以 log₂ 1000 ≈ 10。

### 5.2 为什么「折半」的算法这么重要

猜数游戏：我心里想一个 1 到 1000 的数，你每次猜一个，我只告诉你「大了」还是「小了」。最聪明的猜法是每次猜剩余范围的中点：

```text
范围 [1, 1000]   猜 500  → "小了"
范围 [501, 1000] 猜 750  → "大了"
范围 [501, 749]  猜 625  → "小了"
...
```

每猜一次，候选范围砍掉一半。1000 → 500 → 250 → …，**最多 10 次**一定猜中。一百万个数只要 20 次；十亿个数只要 30 次。

```text
候选范围的缩小（每行是一轮比较之后还没排除的区间，# 代表还可能的候选）：

  轮 0  ################################   32 个
  轮 1  ################                     16 个
  轮 2  ########                              8 个
  轮 3  ####                                  4 个
  轮 4  ##                                    2 个
  轮 5  #                                     1 个   log₂ 32 = 5 轮
```

### 5.3 log n 到处都是（你以后会反复遇到）

* **二分查找**：每次丢一半。
* **平衡二叉树/堆的高度**：每往下一层节点数翻倍，所以 n 个节点的树只有约 log₂ n 层。`TreeMap`、`PriorityQueue` 的 O(log n) 就是「从根走到叶子」。
* **数字的位数**：一个 n 有 log₁₀ n + 1 位十进制数字；二进制则是 log₂ n + 1 位。
* **分治递归的层数**：归并排序每层把数组拆半，共 log n 层。

### 5.4 为什么我们不写底数

`log₂ n` 和 `log₁₀ n` 之间差一个固定倍数：log₂ n = log₁₀ n / log₁₀ 2 ≈ 3.32 × log₁₀ n。Big-O 本来就忽略常数倍，所以 O(log₂ n) = O(log₁₀ n) = O(ln n)，统称 O(log n)。

### 5.5 一张要背下来的表

| n | log₂ n（取整） |
|---|---|
| 10³ (一千) | 10 |
| 10⁶ (一百万) | 20 |
| 10⁹ (十亿) | 30 |
| 10¹² (一万亿) | 40 |
| 2⁶⁴ ≈ 1.8 × 10¹⁹ | 64 |

由此得到一个重要直觉：**在工程里，log n ≤ 64，所以 O(log n) 几乎等价于「很小的常数」。**O(n log n) 通常就是「比 O(n) 慢 20–30 倍」，而不是「慢得离谱」。

### 5.6 Java 里怎么写

```java
// 数一数 n 要折半几次才到 1（等价于 floor(log2 n)）
static int floorLog2(long n) {
    int k = 0;
    while (n > 1) { n >>= 1; k++; }
    return k;
}

// 内置的更快写法：前导零个数
static int floorLog2Fast(long n) {
    return 63 - Long.numberOfLeadingZeros(n);
}
```

## 6. 摊还分析（amortized analysis）：偶尔很贵，但平均下来很便宜

### 6.1 是什么

有些操作**大部分时候 O(1)，偶尔 O(n)**。如果你只看最坏的那一次，会说它是 O(n)；但如果你关心的是**一连串操作的总代价**，会发现平均到每次操作上仍是 O(1)。这种「把偶尔的贵操作的代价平摊给前面许多次便宜操作」的分析叫**摊还分析**。

> **定义**：一个操作的摊还代价 = 对**任意**一连串 m 个操作，总代价 ÷ m 的上界。

注意它和「平均情况」不一样：平均情况要**假设输入的随机分布**；摊还分析**对最坏的操作序列**也成立，不需要任何随机假设。

### 6.2 为什么需要它：先看一个「看着可怕」的数据结构

`ArrayList` 内部是一个数组 `Object[] elementData`。数组的长度创建后不能改。那 `add` 超过容量时怎么办？**分配一个更大的新数组，把旧元素全抄过去**：

```text
容量 4，已满：
  旧数组  [a][b][c][d]
                 │ add(e) 发现满了
                 ▼
  新数组  [a][b][c][d][e][ ]        容量扩到 6（1.5 倍），抄了 4 个元素
```

**这一次 `add` 要抄 n 个元素，是 O(n)。**如果每次 add 都这样，n 次 add 就是 O(n²)，`ArrayList` 就没法用了。那为什么大家都说 `ArrayList.add` 是 O(1)？因为扩容时**容量成倍增长**，所以下一次扩容要等很久。

### 6.3 它怎么工作：逐步演示（容量每次翻倍，初始容量 1）

```text
add 次数   当时容量   这次 add 的代价
   1          1       写 1 次                           (容量 1 → 满了)
   2          1→2     抄 1 + 写 1 = 2
   3          2→4     抄 2 + 写 1 = 3
   4          4       写 1 次
   5          4→8     抄 4 + 写 1 = 5
   6,7,8      8       各写 1 次
   9          8→16    抄 8 + 写 1 = 9
  10..16      16      各写 1 次
  17          16→32   抄 16 + 写 1 = 17
```

贵的 add 出现在第 2、3、5、9、17、33 次……间隔越来越大（每次翻倍）。把前 16 次 add 的总代价加起来：写 16 次 + 抄 (1 + 2 + 4 + 8) = 15 次 = 31，平均每次约 2。

### 6.4 证明（核算法 / accounting method）：翻倍扩容，每次 add 摊还 ≤ 3

**想法**：想象每次 `add` 你**付 3 个硬币**。这 3 个硬币的用途：

* 1 个硬币：付这次 add 自己「写入新元素」的代价。
* 1 个硬币：存在**这个新元素**身上，将来扩容时用来付「抄这个元素」的代价。
* 1 个硬币：存在**一个旧元素**身上（容量的前半部分里的某个元素），将来扩容时用来付「抄那个旧元素」的代价。

**为什么够用**：设容量为 C（C 个格子，全满）时触发扩容，要抄 C 个元素。从上一次扩容（容量由 C/2 变成 C）之后，一共 add 了 C/2 个新元素（填满后半部分）。每个新元素手里存着 2 个硬币（一个给自己，一个给一个旧元素），共 C/2 × 2 = C 个硬币——**恰好够抄 C 个元素**。所以 3 个硬币的摊还代价在任何时刻都不会「赤字」。

结论：对任意 m 次 `add`，总代价 ≤ 3m，摊还代价 **O(1)**，而且这个结论**不依赖任何随机假设**。

### 6.5 证明（聚合法 / aggregate method）：任意增长因子 g > 1

设增长因子为 g（翻倍是 g = 2；`java.util.ArrayList` 是 g = 1.5，源码里 `newCapacity = oldCapacity + (oldCapacity >> 1)`）。

n 次 add 后，最后一次扩容时的容量 ≤ n，上一次的容量 ≤ n/g，再上一次 ≤ n/g²……所以所有扩容的抄写总量

```text
copies ≤ n + n/g + n/g² + ...  =  n · 1/(1 − 1/g)  =  n · g/(g − 1)
```

* g = 2：copies ≤ 2n。
* g = 1.5：copies ≤ 3n。

每次 add 本身再写 1 次，所以总代价 ≤ n + 3n = 4n（g = 1.5），摊还 O(1)。

**实测验证**（`ComplexityDemo` 第 2 部分，n = 1,000,000，只数「抄了多少个元素」，从容量 10 开始）：

```text
growth rule                  total copies   copies / n
x1.5 (java.util.ArrayList)        2430972         2.43
x2.0                              1310710         1.31
+10 each time                   499950000      4999.50   (n = 100000)
```

实测的 2.43 ≤ 3、1.31 ≤ 2，和上界一致（上界是最坏的容量对齐，实际略低）。

### 6.6 反例：如果每次只加固定大小，会怎样

最后一行：**每次只扩 10 格**（`cap + 10`）。设扩容发生在容量 10, 20, 30, …, n 时，总抄写量 = 10 + 20 + … + n ≈ n²/20。n = 100,000 时就是约 5 × 10⁸（实测 499,950,000，即每个元素平均被抄了 5000 次）。摊还代价变成 O(n)。

**教训：摊还 O(1) 依赖「几何增长」（容量乘以常数），不是「加常数」。** 这也是为什么 `ArrayList`、`StringBuilder`、`HashMap`、`ArrayDeque` 都是乘性扩容。

### 6.7 势能法（potential method，一句话）

给数据结构定义一个「势能」Φ（比如 Φ = 2 × 元素数 − 容量），摊还代价 = 实际代价 + ΔΦ。扩容时势能骤降，正好抵消那次 O(n) 的实际代价。核算法和势能法本质一样，势能法在复杂结构里更方便。完整讲解见 CLRS 第 3 版第 17 章（第 4 版第 16 章）。

### 6.8 摊还 O(1) ≠ 每次都快：低延迟系统里的「毛刺」

摊还只说**平均**。扩容那一次仍然要抄 n 个元素（n = 一千万时是几十毫秒），而且还要分配一块新的大内存、产生一块待回收的垃圾。这在 Headlands 这类低延迟系统里是不可接受的毛刺（spike）。

**解法：预分配。**

```java
// 事先知道大概规模：一次性开够，之后不会再扩容
List<Long> prices = new ArrayList<>(1_000_000);

// 更低延迟的做法：根本不用 ArrayList<Long>，用原始类型数组，启动时开好
long[] priceRing = new long[1 << 20];
```

这也是 hc04 讲义里 `long[]` 环形缓冲「容量固定、满了才扩」的出发点，hc08 讲义里「压缩」的摊还分析也是同一个模式。

## 7. 空间复杂度与递归深度（简短）

* **空间复杂度**：程序**额外**用了多少内存，也用 Big-O 表示。`sum(int[] a)` 额外只用几个变量，空间 O(1)；复制一份数组是 O(n)；建 `HashMap` 存 n 个元素是 O(n)。
* **递归的空间**：每层递归占一个栈帧，递归深度 d 就占 O(d) 栈空间。二分查找递归写法深度 log n，空间 O(log n)；一个朴素链表递归到 10⁵ 层可能 `StackOverflowError`（见 hc03 讲义）。
* **时间和空间常常互换**：用 `HashMap` 多花 O(n) 空间，换来 O(n²) → O(n) 的时间（见 oa01 讲义的 Job Chain）。

## 8. 面试里怎么估算运行时间，以及这种估算什么时候会骗你

### 8.1 估算的方法：数 → 乘 → 看是不是 10⁸

**第一步：从 n 反推「允许的复杂度」。**

经验法则：现代机器上一个简单的 Java 循环大约每秒做 10⁸ 次「基本操作」（保守值）。面试题的时限通常是 1–几秒，所以**总操作数不要超过 10⁸ 到 10⁹**。

| n 最大是 | 一般要求的复杂度 | 为什么 |
|---|---|---|
| ≤ 10 | O(n!) 可以 | 10! = 3.6 × 10⁶ |
| ≤ 20 | O(2ⁿ) 可以 | 2²⁰ = 10⁶ |
| ≤ 500 | O(n³) 可以 | 1.25 × 10⁸ |
| ≤ 5,000 | O(n²) 可以 | 2.5 × 10⁷ |
| ≤ 10⁵ | 要 O(n log n) 或更好 | n² = 10¹⁰，太慢 |
| ≤ 10⁶ | O(n log n) 可以 | 2 × 10⁷ |
| ≤ 10⁸ | 只能 O(n) | 一遍扫描，且常数要小 |
| ≥ 10¹⁸ | 只能 O(log n) 或 O(1) | 比如大数求和公式、二分 |

**第二步：估算时对「一步」的定义要诚实。**

* 一次数组读 + 一次比较 + 一次加法 ≈ 一步。
* 一次 `HashMap.put` 不是一步，是几十步（计算哈希、找桶、可能分配 `Node`）。
* 一次系统调用（读写文件/网络）是几百到几千步。

### 8.2 在这台机器上实测：「10⁸/秒」到底准不准？

`ComplexityDemo` 第 3、4 部分的真实输出（JDK 21.0.12，Apple M 系列，12 核）：

```text
dependent multiply-add loop     : 0.64 s for 1e9 iterations -> 1.6e+09 iters/s
HashMap<Integer,Integer> put 60 ns, get 10 ns  (1e6 random keys)
TreeMap<Integer,Integer> put 239 ns, get 215 ns  (1e6 random keys)

n=   2000: 2.00e+06 pairs,   0.002 s -> 8.24e+08 pairs/s (cnt=999025)
n=  20000: 2.00e+08 pairs,   0.098 s -> 2.04e+09 pairs/s (cnt=99991764)
n= 100000: 5.00e+09 pairs,   2.372 s -> 2.11e+09 pairs/s (cnt=2499950961)
```

读法：

1. **纯算术的紧循环，比 10⁸/秒快 10–20 倍**（1.6 × 10⁹ 次/秒；二重循环里 2 × 10⁹ 对/秒）。所以 10⁸ 是**保守**的估计——因为它想覆盖「每步不是纯算术」的一般情形。
2. **但一旦每步涉及数据结构，就远低于 10⁸**：`HashMap.put` 60 ns ≈ 1.7 × 10⁷ 次/秒；`TreeMap.put` 239 ns ≈ 4 × 10⁶ 次/秒。同样是「一百万次操作」，`HashMap` 花 0.06 秒，`TreeMap` 花 0.24 秒。Big-O 里 O(1) 与 O(log n) 的差别在这里被放大成了 4 倍（20 层树 × 每层一次可能的缓存未命中）。
3. **O(n²) 在 n = 10⁵ 时花了 2.4 秒**——如果面试官限时 1 秒，这就超时；n = 2 × 10⁴ 时只要 0.1 秒就没问题。这和第 8.1 节「n ≤ 5000 可以 O(n²)」的保守表对比，说明表**偏保守，但方向对**。

### 8.3 10⁸ 法则的六个局限（面试里把其中两三个说出来，会很加分）

1. **常数因子**：O(n) 且每步 100 ns，可以输给 O(n log n) 且每步 1 ns（n 小于约 10⁶ 时）。小数据下，排好序的 `ArrayList` + 二分，常常比 `TreeMap` 快——见 [cpu_cache_locality](cpu_cache_locality.md)。
2. **缓存未命中**：「一步」不是等价的。顺序读数组一步 ≈ 0.3 ns；随机读一个已不在缓存里的地址一步 ≈ 50–100 ns（见 cpu_cache_locality 第 2 节的实测）。同样是 10⁸ 步，前者 0.03 秒，后者 5–10 秒。
3. **内存分配与 GC**：每步 `new` 对象，累积的垃圾会触发 GC 暂停。`List<Long>` 里每个 `Long` 都是一次分配。
4. **I/O 和系统调用**：读一行 CSV、打一行日志、发一个网络包，都是微秒到毫秒级，不是纳秒级。「一百万行」的瓶颈经常是读入本身，而不是你的 O(n) 算法。
5. **JIT 预热**：JVM 刚启动时在解释器里跑，慢 10–50 倍，热点方法被 JIT 编译后才快（见 hc03 讲义 2.8）。短时间的小测试测不准。
6. **并行与硬件**：多核可以把 O(n) 的实际时间除以核数；但共享数据会引入伪共享和锁（见 [os_processes_threads_ipc](os_processes_threads_ipc.md)）。

### 8.4 三个手算估算练习（带完整过程）

**练习 1**：一百万个订单，每个订单做一次 `TreeMap.put`，需要多久？

* 操作数 n = 10⁶；每次 O(log n)，log₂ 10⁶ ≈ 20 层。
* 理论步数 10⁶ × 20 = 2 × 10⁷，按 10⁸/秒 → 0.2 秒。
* 实测校对：239 ns × 10⁶ = 0.24 秒。吻合。**结论：约 0.2–0.3 秒，可接受。**

**练习 2**：n = 10⁵ 个价格，要找出所有「和为 0 的数对」。暴力是 O(n²)。

* n²/2 = 5 × 10⁹ 对。按 10⁸/秒 → 50 秒（保守）；按实测 2 × 10⁹/秒 → 2.5 秒。
* 两个估计都超过面试常见限时，所以要改：排序 + 双指针 O(n log n)，或哈希 O(n)。
* **说出口的话**：「暴力 5 × 10⁹ 次，即使每次一纳秒也要 5 秒，不行；用哈希表一遍扫，O(n)。」

**练习 3**：每秒 100 万条行情，每条要在有序 Map 里更新一档，每条的处理预算是多少？

* 100 万条/秒 → 每条预算 1 微秒 = 1000 ns。
* `TreeMap.put` 239 ns，占了预算的四分之一，还没算解码、风控、下单。
* 所以真正的低延迟订单簿（hc05 Part 4）会把价格映射成数组下标，每次更新 O(1) 且命中缓存，约几 ns。**这就是「同为 O(log n) 和 O(1) 之外，常数才是关键」的现实。**

## 9. 常见误区

1. **用 `(lo + hi) / 2` 求二分的中点。**当 `lo + hi` 超过 `Integer.MAX_VALUE`（约 21 亿）时溢出成负数，下标越界。这个 bug 在 JDK 的 `Arrays.binarySearch` 里真实存在过多年（2006 年被发现并修复）。正确写法：`lo + (hi - lo) / 2` 或 `(lo + hi) >>> 1`（无符号右移，即使加法溢出了符号位，结果也仍正确）。

2. **把 O(n) 和「n 次」混淆。**「我只用了一个循环，所以 O(n)」——不对，要看循环体里每次做什么。

3. **漏掉隐藏的循环。**

   ```java
   static int slow(List<Integer> list, int[] queries) {
       int hits = 0;
       for (int q : queries) {               // n 次
           if (list.contains(q)) hits++;     // 每次 contains 是 O(list.size())
       }
       return hits;                          // 整体 O(n × m)，不是 O(n)
   }
   ```

   把 `list` 换成 `HashSet<Integer>`，`contains` 变成平均 O(1)，整体 O(n + m)。字符串拼接 `s += x` 在循环里也是隐藏的 O(n)（每次复制整个字符串），整体 O(n²)；要用 `StringBuilder`。

4. **混淆摊还和平均。**摊还不需要随机假设（对最坏的操作序列也成立）；平均需要对输入的分布做假设。面试官问「摊还和平均有什么区别」是常见题。

5. **认为 O(n log n) 一定比 O(n²) 快。**只对足够大的 n 成立。n = 20 时，插入排序（O(n²)）常常比归并排序快——所以 JDK 的 `TimSort` 对短片段用二分插入排序。

6. **忽略输入的「大小」是多大。**一个做 `BigInteger` 加法的算法，如果数有 d 位，每次加法是 O(d) 而不是 O(1)。「n」要先说清是什么：行数？字符数？价位数？

7. **只报一个 O。**比如两个独立的输入规模 n 和 m：双重循环是 O(n × m)，不能简化成 O(n²)。图/订单簿的题尤其常见（价位数 L、订单数 n、事件数 k 各是各的）。

## 10. 面试追问预演

**Q1：你的解法复杂度是多少？**
先说清 n 是什么，再答：「设订单数为 n。建表 O(n)，每次查询 `HashMap.get` 平均 O(1)，所以总共 O(n + q)，空间 O(n)。」

**Q2：`ArrayList.add` 是 O(1) 吗？**
思考：先说「摊还 O(1)」，再解释为什么。答：「单次最坏是 O(n)——满了要复制到 1.5 倍的新数组；但是几何增长，n 次 add 总复制量 ≤ 3n（等比数列 n·g/(g−1)，g=1.5），摊还 O(1)。如果知道规模我会用 `new ArrayList<>(n)` 预分配避免毛刺。」

**Q3：n 是 10⁶，你选 O(n log n) 还是 O(n²)？**
答：「n² 是 10¹² 次，按 10⁸/秒要三个小时，不行；n log n 约 2 × 10⁷，百毫秒量级，可以。」

**Q4：O(1) 的 `HashMap` 一定比 O(log n) 的 `TreeMap` 快吗？**
答：「渐近上是；实际上要看常数——我实测过 100 万随机 key，`HashMap.put` 60 ns，`TreeMap.put` 239 ns，大约 4 倍；而且 `TreeMap` 能做范围查询和有序遍历，`HashMap` 不能。选哪个取决于是否需要有序。」

## 11. 自测题

**Q1（概念）** 判断：「这个函数是 O(n²)」和「这个函数是 Θ(n²)」有什么区别？

<details><summary>答案</summary>

`O(n²)` 只是上界：步数最多按 n² 的速度增长，可能实际远小于它（线性函数也是 O(n²)）。`Θ(n²)` 是紧界：上界和下界都是 n²，增长恰好是平方量级。面试里说 O 一般默认指最紧的那个。

</details>

**Q2（手算）** 下面代码内层 `count++` 一共执行多少次？复杂度是什么？

```java
static long q2(int n) {
    long count = 0;
    for (int i = 0; i < n; i++)
        for (int j = i; j < n; j++)
            count++;
    return count;
}
```

<details><summary>答案</summary>

i = 0 时内层跑 n 次，i = 1 时 n−1 次……i = n−1 时 1 次，总数 n + (n−1) + … + 1 = n(n+1)/2。复杂度 O(n²)。n = 4 时 4 + 3 + 2 + 1 = 10。

</details>

**Q3（手算）** 第 2.4 节 `mystery(n)`，n = 16 时返回多少？

<details><summary>答案</summary>

外层 i = 1, 2, 4, 8, 16，共 5 轮（⌊log₂ 16⌋ + 1 = 5），每轮 16 步，返回 80。复杂度 O(n log n)。

</details>

**Q4（证明）** 一个动态数组每次满了就扩容为原来的 **4 倍**。n 次 add 的总复制量上界是多少？摊还代价呢？

<details><summary>答案</summary>

按 6.5 节的公式，g = 4：copies ≤ n · g/(g−1) = 4n/3 ≈ 1.33n。每次 add 写 1 次 + 摊还复制 ≤ 1.33，总摊还 ≤ 2.33，仍是 O(1)。代价是内存：扩容后最坏有 3/4 的空间闲置（g 越大浪费越多，是时间/空间的折中）。

</details>

**Q5（实现）** 写一个函数，数出 `1..n` 的二进制位数（不用 `Math.log`），并说明复杂度。

<details><summary>答案</summary>

```java
static int bitLength(long n) {
    int bits = 0;
    while (n > 0) { n >>= 1; bits++; }   // 每次右移一位 = 除以 2，共 ⌊log2 n⌋ + 1 次
    return bits;
}
```

复杂度 O(log n)。内置做法 `64 - Long.numberOfLeadingZeros(n)` 是 O(1)（一条 CPU 指令）。

</details>

**Q6（辨析）** `ArrayDeque.addLast` 摊还 O(1)，`ArrayList.add(0, x)` 是 O(n)。如果要频繁在头部插入，为什么 `ArrayDeque` 可以而 `ArrayList` 不行？

<details><summary>答案</summary>

`ArrayList` 用普通数组，元素必须从下标 0 紧密排列，头部插入要把所有元素后移一位，O(n)。`ArrayDeque` 是环形数组，用 `head` 和 `tail` 两个下标，头部插入只需 `head` 回退一格（模容量），不挪动元素；满了才扩容，摊还 O(1)。

</details>

**Q7（估算）** 有 2 × 10⁵ 个整数，问有多少对 `i<j` 满足 `a[i] + a[j]` 是偶数。暴力解会超时吗？有没有 O(n) 的做法？

<details><summary>答案</summary>

暴力是 n²/2 = 2 × 10¹⁰ 对。按本机实测 2 × 10⁹ 对/秒也要约 10 秒，超过常见 1–2 秒限时，会超时。和为偶数 ⇔ 两数奇偶相同：数出偶数个数 e 和奇数个数 o，答案 = e(e−1)/2 + o(o−1)/2，一遍扫描 O(n)。

</details>
