## Q
事件溯源（event sourcing）是什么？为什么重放要求状态机决定性，有哪些破坏者和对策？

## A
不直接保存「当前状态」，而保存所有改变状态的**事件（输入）**；当前状态 = 对事件序列的一遍归约（fold）：`状态ₙ = f(f(f(状态₀, e₁), e₂), … eₙ)`。

好处：
- **崩溃恢复**：读日志重放，状态原样回来；
- **复盘**：当天事件喂给调试版本；
- **回测**：同一份代码喂历史行情，研究和生产同一份逻辑；
- **主备一致**：备机重放同一日志。

前提是 `f` **决定性**：同样输入永远同样输出，否则重放结果与崩溃前不同，恢复 / 复盘 / 回测都失去意义。破坏者与对策：
| 破坏者 | 例子 | 办法 |
|---|---|---|
| 读时钟 | `System.currentTimeMillis()` | 状态机不读时钟，时间戳作为事件字段 |
| 遍历顺序 | 遍历 `HashMap` 决定先处理谁 | 输出前排序（`open()` 按 id 排序），检查顺序写死 |
| 浮点 | 运算顺序不同结果不同 | 全整数 |
| 随机数 | 无种子 `Random` | 不用 |
| 多线程竞态 | 线程交错顺序每次不同 | 单线程使用（单写者），实际处理顺序要记进日志 |

**「先记日志，后处理」（journal before process）**：每个输入先追加到日志，再改内存状态——任何状态改变都有日志里一条事件对应；先改状态再记日志，崩在中间就丢一条事件。撮合引擎也这样。我们作为交易所客户，订单真相在交易所，日志主要用于重建和复盘。

**异常输入**：非法输入（如对不存在的订单发 `Ack`）已经在日志里，处理时抛异常，**状态未变**；重放时同样抛，必须像第一次一样**吞掉**，否则一个坏输入让整个恢复失败。这依赖「先验证、后修改」。

输出（风控结论、被拒订单、仓位）全是输入的函数，不在日志里，重放时重算——两次不相等就是有非决定性的东西混进来了。

持久化：journal 追加写文件；定期快照（序列化当前状态，记下日志位置，须与日志位置原子对应）；恢复 = 读快照 + 重放其后的日志，恢复时间由日志尾长度决定；日志格式：定长头 + 二进制载荷、校验和、按大小切段；恢复后要对账交易所。

重放结果与线上不一致怎么排查：对日志做二分，比较状态摘要（哈希），找第一个产生分叉的事件；常见原因：读时钟 / 随机数、`HashMap` 遍历顺序、浮点、外部可变状态、多线程。预防：线上定期记录状态摘要进日志，发布前用生产日志做重放回归。
