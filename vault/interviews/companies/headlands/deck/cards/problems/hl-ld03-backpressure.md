## Q
背压（backpressure）是什么？这个通道里「满」是怎样一路传导的，Little 定律怎么说明必须有界？

## A
下游处理不过来时让上游**慢下来**，而不是中间堆积。没有背压：快生产者 + 慢消费者 = 队列无限增长 = 内存耗尽或延迟爆炸。**每层缓冲区都要有上限，满了向上游表达「满了」。** Little 定律 `L = λ·W`：缓冲区里的消息数 = 到达速率 × 停留时间，停留时间无上限则 L 无上限。

四层缓冲：应用 `offer` → 出站环 →（I/O 线程 write）内核发送缓冲区 → 网络 → 内核接收缓冲区 →（I/O 线程 read）入站环 → `poll` → 应用。

**出站方向**：对端不读 ⟹ 内核发送缓冲区满 ⟹ `write` 返回 0 ⟹ 出站环渐满 ⟹ `offer` 返回 `false`。`offer(msg, timeoutMs)` 等到放得下或超时。**接受过的每一条消息，在对端开始读之后必须按序、不丢、不重地到达**。

**入站方向**：应用不 `poll` ⟹ 入站环满 ⟹ I/O 线程**停止监听 `OP_READ`** ⟹ 内核接收缓冲区满 ⟹ TCP 向对端通告窗口 = 0 ⟹ 对端内核发送缓冲区满 ⟹ 对端 `write` 返回 0 ⟹ 对端出站环满 ⟹ 对端 `offer` 返回 `false`。「一个应用的没空读，穿过六层，变成另一个应用的满了。」应用 `poll` 腾出空间后必须 `wakeup` I/O 线程恢复读，否则通道永久卡住（去掉 `poll()` 里的 `wakeup`，自旋 `poll()` 的消费者会永远停在几条消息之后）。

**有界性**：出站环 + 内核缓冲区 + 入站环之外，不能有任何随消息数增长的内存。**最小缓冲区**：`inCapacity = outCapacity = maxFrame + 4` 时仍必须工作（2 万条随机长度消息，每条都在环的回绕边界上被切开）。

**实测**（macOS 回环）：两端环都 4 KB：发送端堵住前接受约 16,500 条（约 593 KB），接收端事后收到同样条数；64 KB：约 18,200 条（约 656 KB）。请求 `SO_*BUF = 4096`，读回发送 65,328 B、接收约 0.5 MB，**真正的缓冲主要在内核里**。出站环加大 60 KB，多接受约 1,700 条（符合预期）；加大接收端入站环却没多接受消息（内核接收缓冲区同时缩小约 57 KB，原因不明）。教训：多层缓冲相加，总量由最大那层（这里是内核）决定；想让背压早生效要有意设小内核缓冲区（Linux 上手动设置 `SO_RCVBUF/SO_SNDBUF` 会关闭自动调优）。

测试细节：压力测试中 `offer` 返回 false 可能只是 I/O 线程还没腾出空间，必须等 200 ms 仍放不下才算真堵死；接收方收到的条数 = 发送方接受的条数（没丢没重）。

应用一直不 `poll`：同一线程既 `offer`（等空间）又不 `poll`，对端也如此 → 死锁。接口约定：收发放不同线程，或用非阻塞 `offer`。

行情 vs 订单的背压策略不同：订单不能丢，满了停止接收并报警（fail closed）；行情可合并（conflation，只留最新）；通道只报告「满了」，丢什么由业务决定。
