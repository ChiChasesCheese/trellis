## Q
追问：为什么选 Fenwick 不选线段树或平衡树？多线程怎么办？id 很大很稀疏怎么办？

## A
- **Fenwick vs 线段树**：只有单点修改 + 前缀求和（可逆运算）；Fenwick 一个数组、常数小、十几行；需要区间最值 / 区间修改才用线段树。口述：「只有单点修改 + 前缀求和，Fenwick 更简单更快；要区间最大值我会换线段树。」限制：运算要有逆元。
- **为什么不用平衡树按序存**：查询是「按插入顺序的前缀」，key 是顺序而不是 id；平衡树要 order-statistic（子树大小），自己写；Fenwick 是现成的数组。
- **多线程**：树状数组是普通数组，无同步。(1) `ReentrantReadWriteLock`（读多写少）；(2) 单线程所有者 + 命令队列（交易系统常见，这题本来就是 event-sourcing 的形态）；(3) 按 id 分片行不通，因为前缀跨分片。不能只说「用 `ConcurrentHashMap`」：一个线程更新两棵树、另一个线程查询会读到改了一半的状态。C++：一把 `std::mutex`，读多写少 `std::shared_mutex`。
- **id 很大很稀疏**：`HashMap` 不依赖 id 取值范围，Fenwick 按插入下标建，不需要离散化；若要按 id 或价格大小做前缀，要先离散化或用动态开点线段树。
- **撤销（undo）**：记录反向操作（`put` ↔ `remove`），或每个版本存快照（持久化），或重放日志。
- **总量溢出时为什么要状态不变**：调用者可以捕获异常继续用对象；半修改的状态（树改了、map 没改）会让后续查询给错误答案，比抛异常更难发现。
