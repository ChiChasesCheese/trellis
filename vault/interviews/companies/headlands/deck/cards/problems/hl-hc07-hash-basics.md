## Q
哈希表为什么能做到近似 O(1)？好的哈希函数要满足什么，为什么容量取 2 的幂？

## A
数组按下标取值 O(1)，但只认整数；`List<Entry>` 查一个代码要从头比到尾（8000 个代码平均比 4000 次）。把键变成整数再当下标，就又 O(1)：这个函数叫**哈希函数**（hash function），用它结果当下标的数组叫**哈希表**。

好的哈希函数：**确定**；**相等的 key 得相等的值**（`equals` 与 `hashCode` 契约：equals 的两个对象 hashCode 必须相同，反之不要求）；**均匀**；**快**。

`String.hashCode()` 是 31 进制：`s[0]·31^(n-1) + … + s[n-1]`，`"AAPL" = 2001436`。

到格子编号：`h % 8` 慢（除法）且 `h` 为负时余数也可能为负。**容量取 2 的幂**时用 `h & (容量 - 1)`：一条与运算，快且非负，这是 `HashMap` 和这里所有实现用 2 的幂的原因。

**冲突**（collision）躲不掉：鸽巢原理；生日悖论说 23 个人就约一半概率同生日，8000 个 ticker 放进 16384 个格子几乎一定大量冲突。核心不是避免冲突而是冲突了怎么办。

**翻倍扩容为什么摊还 O(1)**：翻倍时 C → 2C 搬 C/2 个条目，之前的翻倍搬 C/4、C/8…，总共 < C；插入 n 个条目总搬运 < 2n。每次只加 100 格则总搬运 n²/200 级，变 O(n²)。resize 必须全部重新哈希，因为下标由哈希高位决定，数组大小变了下标全变，不能直接复制数组。
