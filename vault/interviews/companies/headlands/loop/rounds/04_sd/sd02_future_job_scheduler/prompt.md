# sd02 · 未来时刻任务调度器（Future-time Job Scheduler）

> 系统设计题，可能出现在 onsite。这类「定时任务」题面在多家公司都出现，当作「很可能出」来准备。

## 题面

> 设计一个调度服务。调用方提交一个**一次性任务**，指定未来的某个时刻 `fireAt`（以及任务内容 / 目标）。服务必须**持久化**任务（机器崩溃、重启后任务仍在），并保证任务在 `fireAt` **之后的有界延迟 Δ 内**被触发（durable one-time jobs… within a bounded delay after its requested time）。支持取消。描述数据模型、触发机制、故障恢复，以及你怎么保证「有界延迟」和「不会丢 / 不会重复触发（或明确重复语义）」。

关键词拆解：

| 词 | 含义 | 设计后果 |
|---|---|---|
| **one-time** | 不是 cron / 周期任务 | 一个任务只有一次触发，生命周期短；周期任务可以归约成「触发后再调度下一次」 |
| **durable** | 提交成功返回后，即使整机崩溃也不会丢 | 先写日志再确认；崩溃恢复要能重建 |
| **future-time** | 触发时刻在未来，范围可能从秒到年 | 近期与远期要用不同的结构（时间轮 + 分层存储） |
| **bounded delay after its requested time** | 触发时间 ∈ [fireAt, fireAt + Δ]，不早、不过晚 | 服务等级目标（SLO）要量化；时钟、突发（thundering herd）、故障切换都要算进 Δ |

## 面试官大概会这样推进

| 阶段 | 面试官说 / 问 | 你要做的 |
|---|---|---|
| 开场 | 「设计一个调度器，到点触发任务」 | 澄清：Δ 是多少？规模？触发=调用谁？取消？重复语义？ |
| 5–10 分钟 | 「怎么存？怎么找到到期的任务？」 | 估算 + 对比：轮询数据库 vs 优先队列 vs 时间轮；分层（近期内存 + 远期落盘） |
| 15–25 分钟 | 「机器挂了怎么办？」 | 日志 + 快照 + 重放；主备 / Raft；fencing |
| 25–35 分钟 | 「每个整点有几十万个任务同时到期呢？」 | 突发估算、容量、公平性、smear |
| 35–45 分钟 | 「会不会触发两次？」 | at-least-once + 幂等键；claim / 取消竞态；僵尸 worker |
| 收尾 | 「怎么测？怎么监控？」 | 虚拟时间的确定性测试；延迟直方图 |

## 开场必问的澄清问题（及可采用的假设）

| 问题 | 为什么问 | 若没答案，假设 |
|---|---|---|
| Δ（有界延迟）是多少？是 p99 还是绝对上界？ | 决定粒度、故障切换预算 | 正常情况 p99.9 ≤ 1 s；单节点故障期间 ≤ 10 s（两档） |
| 允许提前触发吗？ | 决定时钟误差处理 | 不允许；允许推迟到 Δ |
| 规模？ | 决定一台还是多台 | 10⁸ 个任务/天，3×10⁸ 个未触发（假设） |
| 任务触发=做什么？执行时长？ | 调度器 vs 执行器的边界 | 调度器只负责「到点把消息可靠地交出去」（发布到队列 / 回调），执行由下游完成 |
| 语义：至多一次 / 至少一次 / 恰好一次？ | 决定日志写入顺序和幂等键 | 至少一次 + 幂等键（任务 id）；解释为什么不承诺 exactly-once |
| 取消 / 改期？ | 状态机 | 取消；改期=取消+新建（或原地改 fireAt） |
| 远期范围？ | 时间轮层数、分层存储 | 最远 1 年 |
| 多租户？ | 公平性 | 有，按租户限流 |
| 可用性要求？ | 复制策略 | 99.95%；单机故障不丢数据，延迟变长但有上界 |

## 约束与不变量（写在白板上）

* **I1 持久**：`schedule` 返回成功 ⟹ 任务记录已在 ≥2 份持久化副本（或等价的复制日志）中。
* **I2 不早**：任何任务触发时刻 ≥ `fireAt`（以服务端经过校准的时钟衡量）。
* **I3 有界迟**：无故障时 触发时刻 − `fireAt` ≤ Δ（p99.9）；故障时有第二档上界。
* **I4 不丢**：已确认的、未取消的任务最终必被触发（即使因为故障而迟到）。
* **I5 重复语义**：同一任务最多被「交付」多次但带同一个幂等键，下游去重；调度器自己不会对同一任务创建两个活动的触发记录。
* **非目标**：任务内容的执行与重试语义（属于下游）；复杂依赖 DAG；周期任务的日历规则（可提及如何归约）。
