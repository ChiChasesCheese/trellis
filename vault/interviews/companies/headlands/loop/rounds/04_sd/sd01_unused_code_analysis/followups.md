## F1 反射、依赖注入、`ServiceLoader`、序列化：静态分析看不见怎么办？

**思考**：这是静态分析的天花板问题。不要说「处理不了」，要说「分类、保守、记录 blocker、从失败中学习」。
**要点**：
1. 把动态入口**建模成规则化的根**：Spring 注解（`@Component`、`@Bean`、`@Scheduled`）、`META-INF/services`、`readObject/readResolve`、Jackson / Protobuf 反射字段、JNI 导出名。
2. **字符串命中当弱根**：常量池 + 仓库文本文件里出现该类 FQN → 记为 blocker，降低置信度，不直接保活（避免过度保守）。
3. **输出里写 blocker**，让审阅者知道这条为什么是 MEDIUM。
4. **闭环学习**：owner 拒绝某个候选并说"其实是被 X 机制用的"→ 新增一条根规则，下次所有同类自动受保护。
5. 动态证据兜底（类是否在生产加载过）。
**可以说**：「静态分析永远是保守的近似，所以我用规则化的根模型 + 字符串弱根，并把每次误报变成一条新规则。」

## F2 虚调用和接口：怎么避免把活的实现类判成死的？为什么不用更精确的指向分析？

**思考**：想 CHA / RTA 的精度-成本曲线，以及「误判活为死」的方向要保守。
**要点**：CHA = 接口所有实现都可能被调用（过度保守）；RTA = 只考虑可达的 `new X()` 的类，不动点迭代，仍近线性；points-to 精度更高但规模和实现复杂度不划算。偏保守：无法确定的虚调用目标一律保活。lambda / 方法引用靠 `invokedynamic` 的引导参数恢复。
**可以说**：「我选 RTA：近线性、比 CHA 精度好得多；精度不够的地方宁可漏报。」

## F3 怎么证明某个候选"可以安全删除"？

**思考**：不可判定问题，不能「证明」，只能叠加证据 + 缩小爆炸半径。
**要点**：证据叠加（静态不可达 + 非导出 + 无字符串命中 + 生产类加载日志 N 天无 + 无近期修改）；影响面控制（软删除：`@Deprecated(forRemoval)` + 调用时打日志；小 PR；CI 全量构建；可一键 revert）；对 L2（公共 API）额外查外部消费者（制品下载日志、其他仓库依赖扫描）；对 L3 永不自动。
**可以说**：「我不说'证明'，我说'叠加证据 + 限制爆炸半径'，并且让回滚成本接近零。」

## F4 规模：一亿行代码，多久跑完？瓶颈在哪？

**思考**：拆阶段估算（见 model_answer §3）。
**要点**：索引：10⁸ / 5×10³ LOC/s/核 = 2×10⁴ 核·秒；1,000 核约 20 秒（若每核只有 1,000 LOC/s 则约 100 秒）——取决于是否用字节码路线与构建缓存。图：E ≈ 8×10⁷，CSR ≈ 400 MB，一台机器；标记 ≈ 8×10⁷ × 10 ns ≈ 0.8 s。真正的瓶颈：构建产物是否可得（构建时间）、跨模块对齐、人审。
**可以说**：「分布式只在索引；图 400 MB 一台机器亚秒标记；瓶颈是精度和人审。」

## F5 每次提交都要跑吗？增量怎么做？

**思考**：增量算法的正确性风险 vs. 全量的便宜。
**要点**：索引按（文件内容哈希 + 分析器版本）缓存；图重建亚秒，所以**不做图的增量更新**，每次全量标记——省掉增量正确性风险。PR 上只做轻量检查：改动是否让符号变死 / 复活（只算受影响的反向可达集）；全量报告每夜一次。
**可以说**：「索引增量，标记全量——因为标记比维护增量结构还便宜。」

## F6 生产里收集运行数据：开销、偏差、能说明什么？

**思考**：区分类级（便宜、保守）和方法级（贵、有偏）。交易系统热路径不能装探针。
**要点**：类加载日志启动期一次性成本，生产安全；方法级需要 agent / JFR 采样，采样漏稀有路径（假阴性），所以**只能当正证据**（命中=用过），不能当负证据的唯一来源；稀有但必要路径（熔断、灾备）要用 `@KeepAlive` + 演练。组合规则见 model_answer §7。
**可以说**：「运行数据只用来加分——'加载过'一定是活的，'没看到'只是佐证。」

## F7 死环和死簇：为什么 `grep` 找不到，你怎么处理？

**要点**：两个都无用的类 A、B 互相引用，每个都"有引用"。标记法从根出发，两者都不可达；输出整个不可达连通分量（或 SCC 凝聚后的 DAG），**按簇一起删**，连同它们独有的测试 / 配置 / 资源，否则删一个会让另一个编译失败。
**可以说**：「引用计数是错的模型，可达性才是；就像 GC 里的循环引用。」

## F8 测试代码怎么算？只被测试使用的代码是不是死代码？

**要点**：跑两次：测试作根 vs 不作根，差集 = "仅测试使用"。这类代码通常是候选（测试它是为了测试而存在），但要由 owner 判断；同时，没有任何非测试引用但有测试的代码常是"曾经上线、后来被摘掉但测试留下"。另一方向：被删除的生产代码对应的测试必须同簇一起删，否则 CI 失败。
**可以说**：「测试是一类单独的根，两种口径各跑一次，差集给出'只被测试使用'的类别。」

## F9 怎么衡量精度和召回？

**要点**：精度 = owner 接受率 / revert 率（目标 revert < 1%，抽样 100 条的标准误约 1.4%）；召回：回测（在历史"删除死代码"提交的父提交上跑，统计命中）、种子注入；对照 IDE / ProGuard 的差集；回归（固定快照输出逐字节相同）。
**可以说**：「没有基准的静态分析器没有意义，所以我先用 git 历史造一个基准。」

## F10 为什么 HFT 公司很少删代码？你怎么说服 owner？

**思考**：这是文化 / 风险问题，不是技术问题。先承认合理性，再给出降低风险的流程。
**要点**：每次变更都是风险；冷路径（熔断、灾备）看起来死但必需；代码冻结窗口；验证成本高。对策：L3 不碰；L0/L1 HIGH 才直接删；软删除 + 观察期；让价值可见（构建 / 测试时间、依赖更新负担、事故排查噪声）；每个 PR 小、证据全、一键拒绝；拒绝理由反哺根模型。
**可以说**：「我不会说服他们承担风险，我会把风险降到他们愿意接的程度，并给每次拒绝一个可学习的出口。」

## F11 公共 API / 对外发布的库怎么办？

**要点**：L2 开放世界：快照里零引用不等于没人用。查：制品仓库下载 / 依赖扫描（其他仓库、其他团队的 `pom.xml` / `build.gradle`）、版本发布说明；先 `@Deprecated(forRemoval=true)` 并发出弃用通知，等一个或多个发布周期；内部库收紧可见性（`public` → 包私有）本身就是对 L2 → L0 的转化，值得单列为一种低风险的"瘦身"。
**可以说**：「最便宜的删除是收窄可见性——它把 L2 变成编译器可证明的 L0。」

## F12 多语言（Java + C++ + Python + 脚本）怎么统一？

**要点**：统一符号 ID 与图格式（Kythe / SCIP 的思想），各语言有自己的索引器；跨语言边：JNI（符号名规则）、IDL（protobuf / SBE）、脚本与配置（字符串命中）；C++ 免费证据：链接器 `--gc-sections --print-gc-sections`；Python 动态强，置信度整体降一级；覆盖率不够则不下结论。
**可以说**：「各语言一个索引器，一个图格式；跨语言边靠命名规则和 IDL，缺口 fail closed。」

## F13 多个构建配置（`#ifdef`、Maven profile、平台专用代码）？

**要点**：对所有配置取并集——任一配置下可达就是活的。没有覆盖到的配置（如只在生产机上构建的 profile）是最大的假阴性来源，所以把"索引覆盖了哪些配置"写进证据卡。
**可以说**：「死 = 在所有配置里都死。」

## F14 如果分析器自己有 bug，大规模删除造成事故，怎么设计"刹车"？

**要点**：每次运行有"预算"（单次最多出多少 PR / LOC）；先影子运行（只报告不开 PR）几个周期并与人工评审对比；金丝雀：先在低风险模块（内部工具）；revert 率超阈值自动暂停；所有运行可复现（固定快照 + 版本），便于事后复盘。
**可以说**：「分析器是一个会批量改代码的系统，它自己需要熔断开关。」
