# hc03 · 思路与追问（C++20 版）

递归求和本身一分钟就能写完，分数都在追问里：面试官每问一句，就是在看你对 C++ 的某一层有没有概念，包括整数表示和 UB、调用栈、优化器能做什么和不能保证什么、线程的成本。下面按 Part 写清三件事：怎么写、面试官在探什么、该说出口的那句话。详细的推导和可运行的示例在讲义 [[hc03_recursive_sum_cpp]]。

## 30 秒版本

- **结果类型**：`std::variant<Ok, Overflow>`，而不是抛异常、返回 `-1` 或者让它回绕。
- **溢出检查**：用 `__builtin_add_overflow` 在加的时候判断，因为有符号溢出是 UB，加完之后再检查已经晚了。
- **栈**：C++ 不保证尾调用消除，栈溢出是信号、接不住。要稳定的栈深就写循环，或者用 trampoline 把栈换成堆。
- **闭式公式**：中间量溢出不等于结果溢出，用 `__int128` 做一次乘法就够了。
- **并行**：128 位累加器满足结合律，最后只判一次放不放得下；线程池大小等于核数，不要一块一个线程。

## Part 1 · 递归 + 带检查的加法

**写法**

```cpp
inline std::optional<long long> add(Width w, long long a, long long b) {
    long long s;
    if (__builtin_add_overflow(a, b, &s)) return std::nullopt;
    if (w == Width::Int && (s < INT_MIN || s > INT_MAX)) return std::nullopt;
    return s;
}
```

`sum_recursive` 在入口检查 `n < 0`，递归内部只返回 `std::optional<long long>`，到了最外层再转成 `Ok` 或 `Overflow{exact_to(n)}`。`exact_to` 用 `__int128`：n·(n+1) < 2^126，一定放得下。

**面试官在探什么**

1. **返回类型**。返回裸的 `long long` 时，放不下只有三种坏选择：抛异常（调用方会忘记 catch）、返回 `-1`（区间里有负数时 `-1` 是合法的和）、静默回绕（最糟：答案错了没人知道）。`std::variant` 加 `std::visit`，两种情况调用方都必须处理。
2. **UB**。`if (a + b < a)` 这种「加完再看」的写法在 C++ 里是错的：有符号溢出是 UB，优化器可以直接把这个判断删掉。正确的办法是 `__builtin_add_overflow`，或者先加宽到 `__int128`，或者加之前比较 `a > LLONG_MAX - b`。要能说出无符号溢出是有定义的回绕，有符号溢出不是。
3. **数字**。`int` 的和在 n = 65536 溢出（65535 时是 2147450880，比 `INT_MAX` = 2147483647 小）；`long long` 在 n = 2^32 溢出。
4. **栈比整数先出事**。65536 层递归在 512 KiB 的线程栈上放不下，所以 `Int` 溢出的测试要放在大栈线程里跑。

**该说出口的话**：「C++ 里有符号溢出是 UB，所以我在加的时候用 builtin 检查，而不是加完再判断符号。」

## Part 2 · 栈深：编译器会不会帮你消掉递归

**实测深度**（`measure_depth`，Apple clang，这台 Mac）：

| 线程栈 | `-O0` | `-O2` | `-O2` + ASan/UBSan（测试用的构建） |
|---|---|---|---|
| 512 KiB | 7 679 | 30 717 | 15 354 |
| 64 MiB | 1 048 063 | 4 192 253 | 2 096 122 |

同样的栈，帧越大，能走的层数越少：`-O0` 每帧约 64 字节，`-O2` 约 16 字节，ASan 会把帧撑大。所以「能递归多深」没有固定答案，取决于帧有多大和编译选项。

**编译器会不会把递归变成循环**（一亿层，clang）：

| | 尾调用 `f(n-1, acc+n)` | `[[clang::musttail]]` | 非尾调用 `n + f(n-1)` |
|---|---|---|---|
| `-O0` | 栈溢出崩溃 | 正常 | 栈溢出崩溃 |
| `-O2` | 正常 | 正常 | 正常 |

- `-O2` 下 clang 连 `n + f(n-1)` 都变成了循环：加法满足结合律，编译器自己引入了累加器。
- **标准不保证这些**。换个编译选项，同一份代码就会崩。带溢出检查的 `sum_recursive` 在递归返回后还要判断 `optional`，编译器没法把它变成循环，所以 `-O2` 下它照样会爆栈。
- `[[clang::musttail]]` 让尾调用变成强制的，做不到就编译报错，代价是只有 clang 支持。

**三种解法**

1. **迭代**：一个局部变量 `acc` 就是递归在各层栈帧里保存的全部等待状态。栈空间 O(1)。
2. **Trampoline**（蹦床）：每一步不直接递归调用，而是返回「下一步要做什么」（`more(next)`）或者「做完了」（`done(value)`）；`run` 用 `while` 循环一步步执行。栈空间换成了堆上的 `std::function`。它也能处理互递归（`is_even / is_odd`），这一点循环改写不容易做到。
3. **加大栈**：`run_with_stack` 用 pthread 属性指定栈大小（`std::thread` 不能设置栈大小）。这只是把上限往后推，不是真正的解决办法。

**C++ 专属坑**

- `measure_depth` 不能一路递归到崩溃，因为栈溢出是 `SIGSEGV`，进程直接死掉。做法是用 `__builtin_frame_address(0)` 算已经用了多少栈，离底部还剩 32 KiB 时停下。还要用 `[[gnu::noinline]]` 加上递归调用之后的一条 `asm volatile("" ::: "memory")`，防止 `-O2` 把探测递归本身变成循环。
- `Trampoline` 的构造函数不能写成 `template<class... A> Trampoline(A&&...)`：拷贝一个非 const 左值时，`A&&` 推导成 `Trampoline&`，比拷贝构造函数 `const Trampoline&` 更匹配，结果被它劫持，然后编译失败。用带 `std::in_place_index` 标签的私有构造函数可以避开。
- `run` 取结果时要 `std::move(t).take()`，否则 `std::unique_ptr` 这种只能移动的结果没法返回。

**该说出口的话**：「我不会依赖尾调用消除，标准不保证，`-O0` 就不做。要稳定的栈深就写循环；需要保留递归结构，或者有互递归，就用 trampoline。」

## Part 3 · 区间 [a, b] 与闭式公式

**写法**：和 = (a+b)·(b−a+1)/2，全部在 `__int128` 里算。a+b 和 b−a 不可能同时很大：a ≥ −2^63、b < 2^63，所以 |a+b| + (b−a) ≤ 2^64，两个因子的乘积不超过 2^126 + 2^63 < 2^127，这一次乘法不会溢出。最后判断结果在不在 `[LLONG_MIN, LLONG_MAX]` 里。

**面试官在探什么**

1. **为什么不直接 `n*(n+1)/2`**：n = 2^32 − 1 时 n·(n+1) = 2^64 − 2^32，放不进有符号 64 位。Java 里它回绕成负数，除 2 得 −2^31；C++ 里这个有符号乘法本身就是 UB。`naive_closed_form` 用无符号乘法把回绕写明白，只用来做对比。
2. **一奇一偶**：(a+b) 和 (b−a+1) 的奇偶性相反，所以乘积一定是偶数，除 2 是精确的。没有 `__int128` 时，可以先把偶数那个除 2，再用 `__builtin_mul_overflow` 相乘。
3. **中间量溢出不等于结果溢出**：`LLONG_MIN..LLONG_MAX` 的项数是 2^64，放不进 `long long`，但和恰好是 `LLONG_MIN`。中间量溢出时不能直接报 `Overflow`，要算出精确值再判断。
4. **不用 `__int128` 怎么办**：用两个 64 位数拼成 128 位，低位做无符号加法，回绕了就给高位进位。

**该说出口的话**：「公式是 O(1)，但先乘后除会让中间量溢出。我在 128 位里算一次乘法，最后只判断一次结果放不放得下。」

## Part 4 · 并行求和

**写法**：每块用 `Wide`（`__int128`）累加，块之间 `merge`，最后 `to_result()` 只判断一次。三种并行方式：

| 实现 | 结构 | 要点 |
|---|---|---|
| `parallel_sum_fork_join` | 分治，左半 `std::async`，右半自己算 | 标准库没有 work-stealing 线程池。`threshold = 1` 时一个节点一个线程就是 10 万个线程，所以只有顶上 `bit_width(核数)` 层开线程，下面是普通递归 |
| `parallel_sum_async` | `核数 × 4` 块，每块一个 `std::async` | 相当于 Java 的 parallel stream |
| `parallel_sum_workers` | `chunks` 块，最多核数个线程从 `std::atomic` 计数器领块号 | Java 可以一块一个虚拟线程；C++ 没有便宜的线程，创建一个要几十微秒、占一块栈，所以池子大小要自己定 |

**面试官在探什么**

1. **为什么要 128 位累加**：逐步做带检查的加法，结果取决于求和顺序。`{MAX, 1, -1}` 在第二个元素就报溢出，可真实总和是 `MAX`；并行时每块内部的顺序更是任意的。128 位加法满足结合律，怎么切块都得到同一个答案。
2. **加速比**：求和受内存带宽限制，一个核就能吃掉大部分带宽，核再多收益也有限；数据少的时候，创建线程比计算本身还贵。
3. **`memory_order_relaxed` 为什么够用**：计数器只负责分发块号，不用来发布别的数据；数据的可见性由 `join()` 保证。
4. **线程的生命周期**：一个还能 `join` 的 `std::thread` 被析构会调用 `std::terminate`，所以要用 RAII（`JoinAll`）保证每条路径都 join。线程函数里逃出的异常也会 `std::terminate`；`std::async` 的 `future::get()` 才会把异常带回调用方。
5. **`std::async` 的坑**：不保存返回值的 `std::async(...)`，临时的 `future` 在语句结束时析构，析构会等待任务完成，看起来是并行，实际是串行。
6. **`std::reduce(std::execution::par, …)`**：标准有这个接口，但能不能用取决于标准库实现（libstdc++ 依赖 TBB，libc++ 还是实验性的）。面试里说清楚这一点，然后手写 `std::async` 或 `std::thread` 版本。
7. **`double` 求和**：浮点加法不满足结合律，不同的切法得到不同的结果。要确定性，就固定切块方式和合并顺序，或者用 Kahan 补偿求和。

**该说出口的话**：「每块用 128 位累加，满足结合律，最后只判断一次。CPU 密集的任务，线程数等于核数，用原子计数器分发任务块。」

## 和 Java 版的区别

| 话题 | Java | C++ |
|---|---|---|
| 溢出 | 有定义的回绕，`Math.addExact` 抛异常 | 有符号溢出是 UB，用 `__builtin_add_overflow` |
| 结果类型 | `sealed interface` + `record` | `std::variant` + `std::visit` |
| 栈溢出 | `StackOverflowError`，能 catch（但不该吞） | 信号，进程直接死掉 |
| 尾调用 | JVM 永远不做 | 优化器可能做，标准不保证；`-O2` 做，`-O0` 不做 |
| 大整数 | `BigInteger` | `__int128`（编译器扩展） |
| 并行 | ForkJoinPool（有 work-stealing）、虚拟线程 | 没有标准线程池；`std::async` / `std::thread`，自己控制线程数 |
