# hc14 · 思路与追问

## 概要

成交日志加工是量化公司面试里最常见的「小而真实」题型：解析 → 汇总 → 流式化 → 提速。题目本身十分钟写完，面试官要看的是规则有没有说清楚
（什么算坏行、怎么舍入、溢出怎么办、窗口边界开还是闭）、流式化时有没有想到「队列 + 增量累计」而不是重扫，以及追问到性能时知不知道代价在哪。

## 逐 Part 思路

1. **解析与汇总**：`indexOf(',')` 找三个逗号（第四个逗号 = 坏行），每个字段一个小循环，只认 `'0'..'9'`。价格：整数部分 ≤ 9 位、小数 ≤ 4 位，补零到 4 位后 `whole × 10000 + frac`；> 0 才合法。
   `Trade` 是 record，紧凑构造器校验所有字段并 `multiplyExact(price, qty)`，所以「手里有 Trade ⇒ 乘积不溢出」；`parseLine` 捕获构造器的异常变成 empty。
   汇总用 `TreeMap<String, Acc>`（天然按代码升序），累加用 `addExact`。VWAP 舍入用 `q + (r ≥ v − r ? 1 : 0)`，永不溢出。
2. **滑动窗口 VWAP**：一个全局 `ArrayDeque<Trade>`（活的成交，队头最老）+ `HashMap<String, Acc>`（笔数 / 数量 / 名义金额）。`advance(t)`：时钟只进不退；
   从队头弹出 `now − ts ≥ W` 的成交并从累计里减掉；笔数归 0 就把代码从表里删掉。`onTrade` 先算好新的累计（`addExact`，可能抛）再改状态，所以溢出时这笔不计入。
3. **top-k**：`PriorityQueue` 做大小为 k 的最小堆，堆顶是保留集合里最差的；比较器是全序（金额降序、代码升序），结果排序后返回不可变列表。
4. **FastLog**：整块 `byte[]` 一遍扫；symbol 每字符 6 位打包进 `long` 作键，开放寻址表 + 并行 `long[]`（笔数、数量、名义金额、min、max），装填率 > 1/2 就翻倍重哈希；
   乘积用 `multiplyHigh` 判断溢出（不抛异常）；结果最后才解码成 `String` 并排序。

## 隐藏测试会打的坑

* 价格 `5.` / `.5` / `0.0000` / 5 位小数 / 10 位整数被误收；`Character.isDigit` 收下了 Unicode 数字；`trim()` 吞掉了本该算坏行的空白。
* 空行被算成坏行；全空白行被当空行跳过。
* 第四个逗号没检查（`1,A,1,1,2` 被收）；尾逗号。
* `price × qty` 在解析时没检查，结果在汇总里才溢出或回绕成负数；`3037000500²` 与 `3037000499²` 的边界。
* VWAP 用 `(2 × n + v) / (2 × v)` 或 `2 × r ≥ v`：`Long.MAX_VALUE` 附近溢出；用 `double` 除法丢精度。
* 窗口：`now − ts > W`（差一）；同一时刻的多笔只弹一笔；时钟倒退没拒绝；查询没有推进时钟；代码过期后留着 0 值的空条目，`liveSymbols` 不对。
* `onTrade` 先改状态再检查溢出，抛异常后状态已坏。
* top-k：只按金额比较，并列的代码顺序不确定；`k` 很大时按 `k` 预分配。
* Part 4：用有符号 `byte` 当数组下标（`0xE9` → 负数）；`split("\n")` 吞掉了行尾空串之外的差别；最后一行没有换行就漏处理；符号表不扩容。
* 快慢两个版本不一致——测试用随机改坏的日志对拍，任何一条语法规则漏掉都会暴露。

## 复杂度与实测

n = 行数，m = 代码数，k = top-k 的 k。

| 操作 | 复杂度 | 实测 |
|---|---|---|
| `analyze`（Part 1） | O(n log m)（TreeMap）或 O(n)（HashMap + 最后排序） | 100 万行：约 100 ms（预热后） |
| `onTrade` + `vwap`（Part 2） | 摊还 O(1) | 100 万笔，窗口常驻 10 万笔，每笔都查：约 40 ms |
| `topK`（Part 3） | O(m log k) | 50 万笔、5000 个代码、每 500 笔查一次 top-10：远小于 1 s |
| `FastLog.analyze`（Part 4） | O(字节数) | 100 万行（约 35 MB）：约 30–40 ms；总分配只有哈希表和结果 |

时间上 `String` 版只比字节版慢约 3 倍（JIT 之后）；真正拉开差距的是分配量：String 版处理 100 万行约分配 150 MB；测试用「总分配 < 4 MB」来卡掉每行建对象的写法，用 1 s 的限时卡掉正则 / `BigDecimal`。
C++ 版（`-O2`）100 万行不到 0.1 s。

## Java 21 特性

| 特性 | 用在哪 | 比旧写法好在哪 |
|---|---|---|
| record（紧凑构造器） | `Trade`（校验字段、`multiplyExact`）、`SymbolStats`、`Report`、`SymbolNotional` | 非法成交构造不出来；`equals` 按字段，测试直接 `assertEquals(new SymbolStats(…), …)` |
| 未命名变量 `_`（预览） | `by.computeIfAbsent(sym, _ -> new Acc())` | 明说不用这个参数 |
| `Math.multiplyExact` / `addExact` / `multiplyHigh` | 构造器校验、汇总累加、FastLog 的溢出判断 | 溢出直接抛 / 直接判断，而不是静默回绕 |
| Sequenced Collections | `ArrayDeque` 的 `getFirst` / `removeFirst`；`List.copyOf` 返回不可变快照 | 队头操作语义直接 |
| `String.formatted`、文本块 | `formatPrice`、`render`；测试里的多行日志样例 | 样例原样可读 |
| `Comparator` 组合子 | `comparingLong(…).reversed().thenComparing(…)` 写全序 | tie-break 一眼可见 |
| switch 表达式 | 测试里的模糊改坏（`case 0 -> … ; default -> …`） | 无 fallthrough |

## 面试官可能的追问

1. **为什么价格不用 `double`？** 浮点存不准十进制小数，同一个价格可能有两种表示，累加还有误差；定点 `long` 精确、可比较、可当 key。代价是要自己管小数位数与舍入，并检查溢出。
2. **舍入为什么这样写？** 要求半数向上：`q = n / v`、`r = n % v`、`r ≥ v − r` 则加一。写成 `2r ≥ v` 在 `v` 接近 `Long.MAX_VALUE` 时 `2r` 会溢出。
3. **窗口里的成交乱序到达怎么办？** 约定时间不降，乱序直接拒绝。真实系统：设水位线（watermark）+ 允许迟到时间，水位线之前的丢弃或走补偿路径；窗口内用按时间排序的结构（堆 / 有序表）代替 FIFO，出队代价从 O(1) 变成 O(log n)。
4. **top-k 查询很频繁怎么办？** 维护一个按 (金额 desc, 代码 asc) 排序的有序集合，成交 / 过期时「删旧键、插新键」O(log m)，查询 O(k)。注意不能只用堆：金额会变小（过期），要改任意元素的键。
5. **一亿行怎么提速？** 先量；mmap 文件、避免拷贝；按行边界切块并行，每块自己一张表，最后合并（加法与 min / max 满足结合律与交换律，合并顺序不影响结果；溢出判断需用单调性论证）；
   解析本身可以用 SIMD 找换行与逗号。
6. **坏行太多时怎么办？** 计数之外再记前 N 条样本与行号，超过阈值（如 1%）告警或整批拒收；不要静默吞。
7. **用 `int` 存数量行不行？** 单笔上限 12 位十进制（1e12 − 1），已超过 `int`；累加更要 `long`；乘积要先用 `multiplyHigh` / 128 位判断。
