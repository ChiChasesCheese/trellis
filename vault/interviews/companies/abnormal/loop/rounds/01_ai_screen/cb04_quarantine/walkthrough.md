### 追问与答（来自 interviewer.md 的追问）
- "How do you know you have found them all?" 不知道。我 grep 了所有 `WHERE`、读了每个 `except`，并把 B5 和 CLI 的 `finally` 写进 known gaps；没覆盖的是 `display_name_spoof` 的边界。
- "Why a unique index and not a lock?" 部署是多进程，进程内锁只保护一个进程；唯一索引是跨进程唯一的串行化点，败者读到已有 report 就按"重复报告"处理。代价：已有重复行时迁移会失败，要先去重。
- "Why NEEDS_REVIEW and not QUARANTINE when the lookup is down?" 供应商抖动时全部隔离会误杀正常邮件，放行又会漏掉钓鱼；人工复核是成本最低的中间态，并且 `analyzer.error` 计数能告诉我们故障频率。

### 翻车点
- 把 `except Exception` 改成 `except Exception: raise` 或只在 `link_reputation` 里局部捕获 → 其它 analyzer 与其它 lookup 实现（测试里的 `BrokenLookup`）仍无统一处理，也没有 `analyzer.error` 计数。
- 用 `threading.Lock` 修竞态 → 本系统多进程部署，且 CONTRIBUTING 要求靠 schema 约束；测试通过但生产不安全。
- 只修 `GET /reports/<id>` 的 `get` 调用点（在路由里手写 `if report.tenant_id != req.tenant`）→ `release` 路径与 CLI `show` 仍用同一个泄露的 `ReportRepository.get`。
- 把测试里的期望改成 bug 的行为（或删掉红测试）→ 违反 T6 规则与 X6。

### 追问与答（来自 interviewer.md 的追问）
- "Two `drain-outbox` processes run at the same time?" 现在会重复发送，语义是至少一次。修法是让每批用 `UPDATE ... WHERE status='PENDING'` 认领，或保证 cron 单实例；v1 选后者并写进 known gaps。
- "Why not wrap `send_receipt` in try/except?" 回执会丢，也没有计数和补发的办法；outbox 让"晚到"和"丢失"区分开，且失败有 `attempts` / `last_error`。
- "What goes on the dashboard on day one?" `analyzer.error`、`outbox.failed`、`intake.created`，以及 `PENDING` 积压量。

### 翻车点
- 给 `Mailbox` 加重试装饰器或后台线程 → 请求仍可能被拖住，也没有持久化；本系统的已有模式是"落库 + 命令"（`ActionLogRepository`、`cli`）。
- 在路由里手写 400/409 body → 违反 CONTRIBUTING "handlers never build error bodies by hand"，错误形状会漂移。
- 另起 `if len(links) > 50` 常量 → `config.IntakeSettings.max_links` 早已存在（配置优于常量），且租户可覆盖。
- 一上来做鉴权/角色 → 题目说 "your call on what matters most"；35 分钟耗在不是本客户风险的东西上，且没有一个 milestone 收口。

## t3 · burst scale（QRN-244）
### 题
钓鱼攻击期间，同一封邮件几分钟内被成千上万人报告，API 撑不住；审核员还想看到有多少人报告了它（`reporter_count`）。

### 参考答案
- 设计：去重键 `(tenant, message_id)` 已经让 report 只有一条，问题在 `IntakeService._repeat`：每个重复报告都重跑 4 个 analyzer，且重复的报告人没被记录。接缝在 `_repeat`：不再重新分析（结果早已存在 `reports.verdicts` 里，就是"按 message 缓存"），只记录报告人并入队回执；`reporter_count` 用 `report_reporters` 表的子查询算出，经 `Report.to_dict` 暴露，路由不用改。放弃的东西要说出口：重复报告不再触发重新评估（v2：按独立报告人数阈值升级）。
- 改动：
  - `store/migrations/0004_reporters.sql` — `report_reporters`（PK = tenant_id, report_id, reporter）并回填已有 report 的首位报告人。
  - `store/repositories.py:ReportRepository.add_reporter` / `reporter_count`；`_SELECT` 子查询让 `get` / `list` / `find_by_message` 一次带出 `reporter_count`；`insert` 写入首位报告人。
  - `models.py:Report.reporter_count` 与 `to_dict`。
  - `intake/service.py:IntakeService._repeat` — 删除重跑与重新决策，改为 `add_reporter` + 新报告人才入队回执。
- 关键测试：`acceptance/test_t3.py::test_three_reporters_make_a_count_of_three`；`::test_analyzers_run_once_however_many_people_report`（50 个报告人，`metrics.get("analyzer.run", analyzer=...) == 1`）；`::test_a_burst_of_two_thousand_is_one_incident_and_fast`（2000 条 `reporter_count == 2000`、耗时 < 2 s、`quarantine` 一次）；`::test_the_same_person_reporting_twice_counts_once`（stretch）。

### 追问与答（来自 interviewer.md 的追问）
- "The campaign sends each recipient a different Message-ID but the same links. What now?" 去重键不再生效。v2 引入内容指纹（发件人 + 排序后的链接集合）→ analyzer 结果缓存，带 TTL；风险是误合并，所以只缓存分析而不合并 report。
- "Should the 50th reporter change the verdict?" 可以：配置 `escalate_at` 个**独立**报告人把 NEEDS_REVIEW 升到 QUARANTINE；防刷要求报告人是租户内的不同地址。v1 不做，已说出口。
- "Why count in SQL instead of a counter column?" 子查询读时一致，写时只插一行；计数列在 2000 次写入时变成热点行，还要保证和明细一致。读放大用 PK 前缀索引兜住。

### 翻车点
- 重新设计去重键（按内容哈希合并）→ `(tenant, message_id)` 已经是约定，且合并 report 会丢掉"每个报告人"的信息。
- 用 `lru_cache` / 模块级 dict 缓存 analyzer 结果 → 进程内、重启丢失、多进程不一致；`reports.verdicts` 已经持久化了同一份结果。
- `list` 里逐行再查报告人数（N+1）→ 50 条一页就是 51 次查询；应当在同一个 `SELECT` 里带出。
- 用线程池/异步队列"加速" → 瓶颈是重复分析，不是并发；而且新依赖与 CONTRIBUTING "标准库、快速测试"冲突。
