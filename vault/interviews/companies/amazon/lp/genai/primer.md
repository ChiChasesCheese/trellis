# GenAI 原理速查

被追问到第三层时不露怯，需要知道这些：大语言模型（Large Language Model，LLM）怎么生成文本、为什么会一本正经地出错、怎么用测试和编译器当判定器、怎么放信息进上下文、agent 怎么调工具、怎么评测、怎么防注入和泄露、成本与延迟怎么算。下面每条是一个事实加一句为什么。示例数字都由脚本算过；价格和模型规格不凭记忆报，面试时说「按当时的价目表」。与故事的对应：§2 ↔ 「一个自信的错数字」，§3 ↔ 「不依赖 agent 自述的正确性」，§4–§5 ↔ 「不依赖 agent 自述的正确性」 / 「什么时候信任 LLM」，§6 ↔ 「什么时候信任 LLM」，§7 ↔ 「GenAI 不必要的时候」。

## §1 LLM 在干什么：预测下一个 token

- LLM 把文本切成 token（词片段；英文约 3–4 个字符一个，中文常一两个字一个），对每个位置输出「下一个 token 的概率分布」。
- 预训练目标是最大化真实下一个 token 的概率（等价于最小化交叉熵）。为什么：文本本身就是答案，不需要人工标注，所以能做到海量规模。
- 自回归（autoregressive）：采样一个 token → 接在输入后面 → 再算下一个。生成的每个 token 都成为后续的条件，**包括模型自己犯的错**。
- 采样：模型输出 logits \(z_i\)，用 softmax 转概率：\(p_i = e^{z_i/T} / \sum_j e^{z_j/T}\)，T 是温度。
  - logits = [2.0, 1.0, 0.1]：T=1.0 → [0.659, 0.242, 0.099]；T=0.5 → [0.864, 0.117, 0.019]；T=2.0 → [0.502, 0.304, 0.194]。
  - T 低 ≠ 更真实：只让输出更集中；最高概率的 token 若是错的，低温只会更稳定地给出同一个错答案。
- 后训练（post-training）：监督微调（SFT）+ 基于人类 / AI 反馈的强化学习，把「会续写」变成「会听指令」。它优化「人觉得好的回答」，所以学到听起来自信、结构完整的风格，这是自信地出错的原因之一。
- 无状态（stateless）：每次调用只看见这次放进上下文窗口（context window）的 token，不记得上一次，除非你再放进去。

自测：
- 为什么降低 temperature 不能消除 hallucination？ → 它只改变采样集中度，不改变模型对「什么是真的」的知识。
- 为什么模型自己的早期错误会放大？ → 自回归：已生成的 token 是后续的条件，模型倾向与前文一致。
- T=0.5 时第一项概率为什么更大？ → logits 放大 2 倍 → [4, 2, 0.2]，差距变大，softmax 更尖。

## §2 Hallucination 怎么产生

- 定义（可直接说）：模型生成**流畅、自信、但没有依据（或与依据矛盾）**的内容。
- 根因：训练目标是序列似然，不是命题真假；模型没有「这条是不是真的」的通道，也不能在生成时查世界。
- 因果链：
  - 提问涉及长尾 / 过时 / 不存在的事实
  - 模型没有该信息，但目标函数要求输出某个序列（除非后训练教过它拒答）
  - 后训练偏好自信、完整的答案 → 语气不带不确定
  - 自回归把填出来的内容当作前提 → 后文自洽地延伸
  - 读者无法从语气区分真假
- 类型与检测：
  - 事实编造（不存在的论文、API、包名）→ 一手来源核对、包管理器查是否存在
  - 过时知识（Numba 0.59 起 `@jit` 默认不再回退 object 模式，需 `forceobj=True`）→ 对照当前版本文档
  - 数值 / 推理错误（碰撞概率 38% vs 必然）→ 脚本复算
  - 指令 / 规格误读 → 对照需求；验收命令
  - 对工具输出误读（把报错当成功）→ 让 harness 给结构化结果；重跑命令
  - 附和前提（sycophancy）→ 问中性问题；让它找反例
- 数值例（示意）：键空间 \(N = 62^7\)（7 位 base62），n 个键至少一次碰撞概率 ≈ \(1 - e^{-n(n-1)/(2N)}\)：
  - n=10⁵ → 0.14%；n=10⁶ → 13.2%；n=10⁷ → 0.9999993（几乎必然）
  - 数量级错 6 个量级就是 「一个自信的错数字」 的错误形态
  - 「至少一次碰撞」与「这次插入碰撞」是两个不同的概率
- 缓解三层（说得出每层挡什么）：
  - 减少发生：给来源（检索 / RAG）、要求引用、给工具（计算器、代码执行）而不是心算、允许说「不知道」
  - 检测：oracle、一手来源核对、不同路径对拍
  - 限制后果：高风险动作要人批准；读 diff；爆炸半径小

自测：
- 一句话解释为什么 LLM 会 hallucinate？ → 训练目标是预测最可能的下一个 token，不是最真的；没有真值通道，不知道时仍生成高似然的「听起来对」的续写，且后训练让语气自信。
- Numba 的例子属于哪一类？ → 过时知识（版本行为变了）。
- 「RAG 能消除 hallucination」对吗？ → 不对：检索没命中、文档本身错 / 被投毒、模型忽略检索内容时仍会错。
- 7 位 base62、10⁷ 个键，至少一次碰撞多大？ → ≈ 0.9999993；n=10⁶ 时约 13.2%。

## §3 测试、类型、编译器为什么是 verifier

- oracle（判定器）：独立于被检验对象、能给出对 / 错信号的东西。LLM 输出是待验证的候选，oracle 把「信不信」变成「过没过」。
- 为什么行得通：验证常常比生成便宜（写出满足规格的程序要搜索巨大空间；检查一个程序是否过 N 个测试只需跑 N 次）。不是定理：规格错或测试弱时验证同样难。
- oracle 阶梯（从便宜强到贵弱）：
  - 编译器 / 类型检查：抓语法、类型、不存在的符号；抓不到语义错。例：Java 21 示例 `case Order(var id, Side.BUY, …)` 非法，record 模式里不能写常量，要用 `when` 守卫。
  - 单元测试：抓测试覆盖到的行为；抓不到没写进测试的。例：parcel-tracking kata，10 个测试全绿，拼 key 的错误写法也过。
  - 差分测试：抓两种实现不一致；两个实现犯同一个错时抓不到。例：双向 BFS 对拍普通 BFS，400 个随机图零不一致。
  - 已知值：例：国际象棋 perft 深度 4 = 197,281。
  - 随机 + 差分对拍：例：200 种子 × 1500 操作。
  - 变异测试：抓测试太弱；11 个手写 bug，11/11 被杀。
  - 人读 diff：抓假设错、设计不合理；疲劳时会漏。money code 逐 diff 读。
- 变异测试（mutation testing）：
  - 是什么：往正确代码里故意放一个小 bug（变异体），看测试能否变红；变红 = 被杀，仍绿 = 存活。
  - 为什么需要：全绿只证明「代码通过了这些测试」，不证明「这些测试足以发现错误」。
  - 例：把 `parcel_id` 和 `tag` 直接拼接，`"ab"+"c"` 与 `"a"+"bc"` 撞成同一个 key；写法 A 通过全部 10 个测试，补一个断言后被抓到。
  - 变异得分 = 被杀 / 总数；该 kata 11/11。
  - 「空模板必须红」是最小的变异：整个实现换成空的，测试必须失败，否则测试什么也没测。
- oracle 的盲区（senior 必讲）：
  - 相关错误：同一个模型写代码和测试，常带同一个误解，一起绿 → 规格先于代码、独立路径对拍、变异测试。
  - 规格错：测试断言了错的行为 → 从一手需求或文档写断言；人读。
  - 合理假设上的错误结论：每个数字都对，但两个假设互相矛盾（1,560 倍峰均比）→ gate 看形状，只有读才看实质。
  - 验收 gate 只抓被写进去的东西 → 每个新发现的缺陷变成新规则或新检查。

自测：
- 为什么 "tests pass" 不够？ → 测试可能太弱、可能与代码同源出错、可能断言了错的规格；要验证测试本身。
- 编译器作为 verifier 的边界？ → 只证明类型 / 语法层面的性质，但最便宜最快，能抓到幻觉出来的符号和 API。
- 差分测试何时失效？ → 两个实现共享同一个误解；改用独立来源或已知值。
- 变异得分 8/11 说明什么？ → 3 个变异体存活，对应 3 类未覆盖的行为；为每个补断言再复跑。

## §4 Prompt engineering vs context engineering

- Prompt engineering：怎么措辞（指令、角色、few-shot 示例、输出格式如 JSON schema、分步要求）；让模型在已有信息下更准。
- Context engineering：每次调用窗口里放什么（系统提示、规则文件、检索文档、工具返回、历史摘要、示例）；决定模型**能看到什么**。agent 场景尤其关键，因为每个工具结果都进窗口。
- 失败模式：
  - prompt：歧义指令、格式漂移
  - context：相关信息没进窗口、无关信息挤掉预算、过时信息误导、被注入的文本
- 为什么 context 是工程问题：
  - 窗口有限，且越满越不可靠（长上下文中间的信息更容易被忽略，因模型而异）
  - 成本与延迟随输入长度增长
  - 无状态：规则必须每次随上下文带上，所以写成文件
- 实例：规则文件每次会话都读；一组 agent 一份指令文件；一个 agent 一个目录和一个可由命令验证的交付物；简报由调研结果生成；agent 先检查已有产出再续做；用子会话隔离「读大量材料」的上下文消耗。
- Prompt / RAG / Fine-tuning 怎么选：
  - 更好的 prompt + 示例：适合格式、风格、任务澄清；起点；受限于模型已有知识；会漂移
  - RAG：适合知识频繁变化或私有、要引用来源；要建索引与评测；检索未命中、分块切断、文档被投毒
  - Fine-tuning：适合稳定的风格 / 格式 / 行为且有足量高质量数据；数据与训练成本、知识更新慢、过拟合、回归风险
  - 规则：从最便宜的开始，用 eval 决定是否升级
- RAG 流水线：文档切块（chunk）→ 向量化（embedding）→ 存入索引 → 查询时把问题也向量化，取最相似的 top-k 块 → 拼进 prompt → 模型基于它们回答。失败点：切块边界、嵌入对术语不敏感、top-k 太小漏召回、太大挤占窗口。

自测：
- prompt 与 context engineering 一句话区分？ → prompt = 怎么措辞这条指令；context = 窗口里放哪些信息、顺序与预算。
- 为什么 agent 场景下 context engineering 更重要？ → 多步执行，每步工具输出都进窗口，会被噪声占满、早期规则被挤出；需要摘要、隔离、只传必要内容。
- 知识库每天更新，RAG 还是 fine-tune？ → RAG：更新索引即可；仍需评测检索质量。

## §5 Agent、工具调用、评测

### 5A. Agent
- Agent = 模型 + 工具 + 循环：模型读上下文 → 产出「调用某工具 + 参数」（结构化输出）→ harness（运行时）执行 → 结果写回上下文 → 模型再决定下一步，直到最终答案或超限。
- **模型从不直接执行任何东西**：权限、沙箱、审批都在 harness，不在模型里。
- 工具的 schema = 函数名 + 参数 + 说明；说明含糊，模型就选错工具或传错参数。
- 多 agent（orchestrator–workers）：主会话拆任务、派 worker、验收。好处：并行、各自上下文小。代价：协调成本、agent 间不一致、成本成倍。
- 失败模式 → 对策：
  - 自报「完成」但没完成 → 独立重跑验收；never accept an agent's "done"
  - 部分完成后崩溃（额度耗尽）→ 恢复规则；抢救而非重来
  - agent 互相覆盖文件 → 一个 agent 一个目录
  - 失控并行 / 递归 → 硬上限；不得派 agent
  - 把缺陷写进文档当契约 → 发现即修复并加回归测试
  - 自信的数字错误 → 脚本复算

### 5B. 评测（eval）
- 为什么要 eval：输出是概率性的；没有评测，「我觉得变好了」无法证伪，改一个 prompt 可能悄悄让别处变差。
- 评测集（golden set）：典型输入、边界、对抗输入（注入、超长、噪声）、历史上出过错的用例（每个缺陷变成一条用例）。
- 指标按失败模式选：
  - 有确定答案：exact match / 单元测试通过率
  - 代码：pass@k = \(1 - \binom{n-c}{k}/\binom{n}{k}\)；例：n=10、c=3：pass@1 = 0.3，pass@3 = 1 − 35/120 = **0.708**，pass@2 = 1 − 21/45 = **0.533**
  - 分类 / 抽取：precision、recall
  - 开放式文本：人工评分或 LLM-as-judge
- LLM-as-judge 的坑：位置偏好、自我偏好、偏爱更长的答案。对策：随机换位、用标注样本校准与人的一致率、能用 oracle 就不用裁判。
- 样本量：比例的标准误 \(\sqrt{p(1-p)/n}\)；n=50、p=0.8：SE ≈ 0.057，95% 区间约 ±11 个百分点；**50 条样本分不出 80% 和 85%**，82% vs 78% 也不能说谁更好。
- 线下防回归；线上看分布漂移、成本、延迟、用户反馈；两者都要，并有回滚路径。
- 验证 AI 辅助的开发工作 = 小型 eval：参考解绿 + 空模板红是确定性 eval；变异得分是对 eval 本身的评测。

自测：
- 为什么权限不能靠「在 prompt 里告诉模型不要做 X」？ → 模型可能被注入、误解或出错；真正的边界必须在 harness 里强制执行。
- LLM-as-judge 为什么要用人工标注样本校准？ → 裁判有位置 / 自我 / 长度偏好，且可能与你的标准不一致；低于一致率阈值就不能用。

## §6 安全：prompt injection 与数据泄露

- Prompt injection：模型把系统提示、你的指令、网页、文件、工具结果都当成**同一条 token 序列**，没有硬的「指令 / 数据」边界；攻击者把指令写进数据里，模型可能当作命令执行。
  - 直接注入：用户自己输入恶意指令（越狱）。
  - 间接注入：恶意指令藏在 agent 读取的第三方内容里（网页、邮件、README、issue、工具返回）；对读网页、读仓库的 agent 是主要威胁。
- 危害组合（常称「致命三要素」）：同时具备 (1) 访问私有数据 (2) 接触不可信内容 (3) 能对外通信。对策：**打断其中一条**，比「让模型识别恶意指令」可靠。
- 缓解清单：
  - 最小权限：只给完成任务所需的工具和路径
  - 不可逆或外发动作要人批准（发邮件、推送、删除、支付）
  - 沙箱执行代码；网络出口白名单
  - 不可信内容与指令分区标注并限制其可触发的工具；输出做校验
  - 记录工具调用以便审计；把注入做成红队用例放进 eval
  - 密钥不进 prompt；用环境注入与短期凭据
- 数据泄露：
  - 发到第三方模型 API 的内容，先问留存（保存多久）、训练（是否用于训练）、合规（地区、合同）；企业协议与个人账号不同
  - 最小化：不放客户数据、密钥、未公开内部信息；脱敏或合成数据
  - 模型可能复述训练数据；生成的代码可能有许可证问题
  - 供应链：模型可能编造不存在的包名，攻击者抢注同名恶意包（slopsquatting）；安装前核对包是否真实存在
- 你的真实控制手段：
  - 公开仓库规则：不放招聘人员姓名、邮件内容、个人数据；商业站点内容只链接不存档
  - 爆炸半径 guard：测试夹具曾写进真实 Anki 集合，所以测试里让真实客户端拒绝；推送从不改已复习卡的到期时间
  - agent 不能改自己的权限 / 隔离设置
  - 【待补：工作中的做法（公司数据怎么处理、用哪个企业版工具）；只说你确知的】

自测：
- 为什么 prompt injection 比 SQL injection 更难根治？ → SQL 有参数化查询把代码与数据在语法上隔开；LLM 里指令与数据都是自然语言 token，没有等价的硬隔离，只能靠权限与设计限制后果。
- agent 能读邮件、读内部文档、发外部 HTTP 请求，风险与改法？ → 三要素齐全，恶意邮件可诱导它外发内部文档；去掉外发能力，或外发需人批准 / 白名单域名，或限制可读范围。
- 一句话回答「你的数据怎么不泄露」？ → "Nothing sensitive goes into a prompt, tools are least-privilege, any outbound or irreversible action needs approval, and I treat everything the agent reads as untrusted input."

## §7 成本与延迟

- 成本 ≈ 输入 token × 输入单价 + 输出 token × 输出单价（输出通常更贵）；总成本 = 单次成本 × 调用次数。agent 的调用次数随步数和重试增长，上下文随步数累积，所以长任务的输入 token 增长很快（总输入近似步数的平方量级，除非摘要、压缩、隔离上下文）。
- 延迟 ≈ 首 token 时间（time-to-first-token，与输入长度、排队有关）+ 输出 token 数 × 每 token 时间。例：输出 500 token、50 token/s → 约 10 s。
- 降延迟：流式输出、缩短输出、缩短输入、并行调用互相独立的子任务（墙钟≈最慢一个，成本≈总和）。
- 提示缓存（prompt caching）：复用相同前缀已计算的内部状态，重复调用更便宜更快；稳定内容（系统提示、规则、文档）放前面，变化的放后面。
  - 例：20k token 稳定前缀调用 100 次：无缓存 = 100P；有缓存 = P(1 + 99r)，r=0.1 时 = 10.9P，约省 89%。
- 模型分档：便宜小模型做高量、易验证的活；贵模型做难推理或最终审查。
- 你的实测成本：

| 工作 | 墙钟 | tokens |
|---|---|---|
| 一个调研 agent | 4–6 分钟 | 85–145k |
| 一题单独（试点） | 8–10 分钟 | 130–145k |
| 一个 agent 两题 | 17–29 分钟 | 180–345k |
| 一轮修订 | 5–6 分钟 | +40–60k |

- 整库（3 调研 + 3 试点 + 23 对）：3×115k + 3×137.5k + 23×262.5k ≈ **6.8M** tokens（区间中值）。
- 取舍框架：
  - 这一步有 oracle 吗？有 → 便宜地多生成多验证；没有 → 要贵的人工或贵模型
  - 用户在等吗？在 → 延迟优先（流式、小模型、缓存）；不在 → 吞吐 / 成本优先（批处理、异步）
  - 确定性问题别用模型（「GenAI 不必要的时候」）
  - 并行只用于互相独立的任务，受上限和审查带宽限制；瓶颈常常是你的验收，不是生成

自测：
- 为什么 agent 长任务 token 增长比「步数 × 单步成本」更快？ → 每步输入含此前所有历史与工具输出。
- 5 个互相独立的子任务各 10 s，并行 vs 串行？ → 墙钟 10 s vs 50 s；成本相同；并行换时间不换钱。

## §8 AI 聊天机器人的系统设计骨架

- 完整题解：题库里的 LLM 聊天服务题（GPU 批处理、KV cache、流式、配额、安全过滤）。口述骨架：
  - 需求澄清：自己托管模型还是调用第三方 API？是否带检索 / 工具？上下文多长？免费 / 付费配额？
  - 路径：客户端 → 网关（认证、限流、配额）→ 会话服务（权威对话存储，上下文裁剪 / 摘要）→（可选）检索 → 模型推理（流式）→ 安全过滤 → 客户端
  - 难点：生成延迟（首 token + 每 token）→ 流式 + 缓存前缀；GPU 稀缺 → 准入控制和分档配额；断线语义 → 生成不因客户端断线而停止
  - 质量与安全：golden set 回归、注入红队用例、输出过滤、日志与审计、成本监控
  - 演进：多区域、模型分档路由、缓存、离线批处理
- 为什么要流式？ → 总生成时间长；流式让用户在首 token 后就开始读，感知延迟大降。
- 用户问内部文档的问题加什么？ → 检索：索引 + 权限过滤 + 引用来源 + 注入防护（文档是不可信输入）。

## §9 说法：5 句话骨架

- **Where**：I use it for [planning, scaffolding, refactor, tests, review], not for [numbers, external facts, security decisions].
- **Control**：plan → TDD → gates; I own every diff.
- **Verify**：oracle ladder (compiler, tests, differential, known values), then test the tests (mutation, empty starter must fail).
- **Evidence**：one concrete artifact (「一个自信的错数字」: 38% → certainty; 「不依赖 agent 自述的正确性」: 11/11 mutants).
- **Limits**：where it wasn't worth it (counts → script; one-line fixes in place) and what I'd add for production (evals, injection tests, monitoring).

自测：
- 60 秒回答 "How do you verify an AI-generated solution is correct?" → 第 3 点：oracle 阶梯，再验证验证者，再人读假设；落到 「不依赖 agent 自述的正确性」 的证据（空模板红、11/11 变异体、400 个随机图对拍零不一致）。
- "Isn't that overkill for a side project?" → "It's cheap relative to the cost of a wrong number reaching a learner, and the same mechanisms — a gate that's a command, a rule per defect — are what I'd apply to production code; the rigor scales with the blast radius." 再补 「GenAI 不必要的时候」：我也知道什么时候不用模型。
- 不确定某个细节（如某模型的上下文长度）？ → 直说 "I'd check the current docs for the exact number"，然后讲原理；不要凭记忆报数字。
