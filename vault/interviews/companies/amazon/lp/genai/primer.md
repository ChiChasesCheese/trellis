## §1 LLM 到底在干什么：下一个 token 的概率分布

**是什么。** 大语言模型（Large Language Model, LLM）把文本切成 token（词片段，英文大致 3–4 个字符一个，中文常常一两个字一个），然后对每个位置回答一个问题：「给定前面所有 token，下一个 token 是哪个的概率各是多少？」输出是词表上的一个概率分布 \(P(x_t \mid x_{<t})\)。

**为什么这样设计。** 预训练（pretraining）的目标是让模型在海量文本上最大化「真实下一个 token」的概率（等价于最小化交叉熵损失）。这个目标不需要人工标注，文本本身就是答案，所以能做到海量规模。

**怎么生成一段话。** 自回归（autoregressive）：采样出一个 token → 接在输入后面 → 再算下一个分布 → 重复。生成的每个 token 都成为后续 token 的条件，**包括模型自己犯的错**。

**采样与 temperature。** 模型先输出每个候选的原始分数 logits \(z_i\)，再用 softmax 变成概率：\(p_i = e^{z_i/T} / \sum_j e^{z_j/T}\)。T 是温度。

| T | logits = [2.0, 1.0, 0.1] 的概率 | 含义 |
|---|---|---|
| 1.0 | [0.659, 0.242, 0.099] | 默认分布 |
| 0.5 | [0.864, 0.117, 0.019] | 更集中，更"确定" |
| 2.0 | [0.502, 0.304, 0.194] | 更平，更随机 |

T 低 ≠ 更真实：它只让输出更集中在模型已有的最高概率上；如果最高概率的那个 token 是错的，低温度只会让你更稳定地得到同一个错答案。

**后训练（post-training）。** 预训练模型会续写文本但不听指令；后训练（监督微调 SFT + 基于人类/AI 反馈的强化学习等）让它变成会遵循指令的助手。后训练优化的是「人觉得好的回答」，所以它会学到**听起来自信、结构完整**的风格——这是 §2 里"自信的错误"的原因之一。（机制层面的概括，细节因模型而异。）

**无状态（stateless）。** 每次调用模型只看见这一次放进上下文窗口（context window）的 token；它不"记得"上一次对话，除非你把内容再放进去。这是 §4 上下文工程的前提。

### 自测 §1
**Q1. 为什么降低 temperature 不能消除 hallucination？**
<details><summary>答案</summary>temperature 只改变采样集中度，不改变模型对"什么是真的"的知识。若最高概率的续写本身是错的（长尾事实、过时知识），低温度会稳定地输出这个错误。</details>

**Q2. 为什么模型自己的早期错误会放大？**
<details><summary>答案</summary>自回归：已经生成的 token 是后续 token 的条件，模型倾向于与前文保持一致，把前面的错误当作事实继续展开。</details>

**Q3. logits [2.0, 1.0, 0.1]，T=0.5 时第一项概率为什么比 T=1 大？**
<details><summary>答案</summary>除以 0.5 相当于把 logits 放大 2 倍 → [4, 2, 0.2]，差距变大，softmax 更尖：0.864 vs 0.659。</details>

## §2 Hallucination 是怎么产生的（因果链）

**定义（面试可直接说）。** Hallucination = 模型生成流畅、自信、但没有依据（或与依据矛盾）的内容。

**根因：没有"真值"通道。** 训练目标是 token 序列的似然，不是命题的真假。模型内部没有一个"这条是不是真的"的位，也不能在生成时去查世界。当事实在训练数据里出现很多次，似然和真实高度相关，模型通常对；当事实稀有、含糊或不存在，**最像真话的续写**仍然是一个高似然的续写——于是它平滑地填空。

**因果链：**
1. 提问涉及长尾/过时/不存在的事实（例：一个库在 0.59 版本才改变的行为）。
2. 模型没有该信息，但目标函数要求输出**某个** token 序列（它不会"沉默"，除非后训练教过它拒答）。
3. 后训练偏好自信、完整的答案 → 填空时语气不带不确定。
4. 自回归把填出来的内容当作前提 → 后文自洽地延伸。
5. 读者无法从语气区分真与假。

**类型（分清楚，面试官会追问你到底遇到哪一种）：**

| 类型 | 例 | 检测手段 |
|---|---|---|
| 事实编造 | 引用不存在的论文、API、包名 | 一手来源核对；包管理器查是否存在 |
| 过时知识 | "`@jit` 在 Numba 里会退回 object 模式"——0.59 起默认不再回退，需 `forceobj=True`（本仓库 `c43532cb`） | 对照当前版本文档 |
| 数值/推理错误 | 碰撞概率 38% vs 必然（G1） | 脚本复算 |
| 指令/规格误读 | 做了你没要求的事 | 对照需求；验收门 |
| 对工具输出误读 | 把报错当成功 | 让 harness 提供结构化结果；重跑命令 |
| 附和前提（sycophancy） | 你的提问里含错误前提，它顺着答 | 问中性问题；让它找反例 |

**数值例（示意，不是 G1 试点的配置）。** 生日问题：键空间 \(N = 62^7\)（7 位 base62）。n 个键时，至少一次碰撞概率 ≈ \(1 - e^{-n(n-1)/(2N)}\)：n=10⁵ → 0.14%，n=10⁶ → 13.2%，n=10⁷ → 0.9999993（几乎必然）。数量级错 6 个量级就是 G1 的错误形态；**"至少一次碰撞"与"这次插入碰撞"是两个不同的概率**（仓库 AGENT.md 要求写作时区分）。

**缓解手段分三层（说得出"每层挡什么"）：**
1. **减少发生**：给来源（检索/RAG）、让它引用、给工具（计算器、代码执行）而不是让它心算、要求"不确定就说不知道"。
2. **检测**：oracle（§3）、一手来源核对、不同路径对拍。
3. **限制后果**：高风险动作要人批准；读 diff；爆炸半径小。

## §3 为什么测试、类型、编译器是 verifier

**核心概念：oracle（判定器）。** 一个能独立于被检验对象给出对/错信号的东西。LLM 的输出是"待验证的候选"，oracle 把"信不信"变成"过没过"。

**为什么这行得通：验证比生成便宜（常常）。** 写出一个满足规格的程序要搜索巨大空间；检查一个给定程序是否通过 N 个测试只要跑 N 次。这个不对称让"便宜地大量生成 + 机器验证"成为可行的工程模式。（不对称不是定理——规格本身错或测试太弱时，验证同样困难。）

**oracle 的阶梯（从便宜、强到贵、弱）：**

| 层 | 抓得到 | 抓不到 | 例 |
|---|---|---|---|
| 编译器 / 类型检查 | 语法、类型、不存在的符号 | 语义错 | Java 21 示例不能编译：`case Order(var id, Side.BUY, …)` 非法，record 模式里不能写常量，要用 `when` 守卫（`277ff22a`，`headlands-kit`） |
| 单元测试 | 测试覆盖到的行为 | 没写进测试的行为 | Airbnb kata：10 个测试全绿，拼 key 的错误写法也过 |
| 差分测试（differential） | 两种实现不一致 | 两个实现犯同一个错 | 双向 BFS 对拍普通 BFS，400 个随机图零不一致（LLD BUILD.md） |
| 已知值 | 实现错 | — | 国际象棋 perft 深度 4 = 197,281 |
| 随机 + 差分对拍 | 对随机输入两条路径不一致 | 不变量没想到 | 差分对拍 200 种子 × 1500 操作（Airbnb REPORT） |
| 变异测试（mutation） | 测试太弱 | — | 11 个手写 bug，11/11 被杀 |
| 人读 diff | 假设错、设计不合理 | 疲劳时漏 | money code 逐 diff 读（S7） |

**变异测试（mutation testing），从零讲。**
- 是什么：故意往正确代码里放一个小 bug（一个变异体 mutant），看测试能不能变红。变红 = 变异体被杀；仍绿 = 存活，说明测试没覆盖这个行为。
- 为什么需要：测试全绿只证明"代码通过了这些测试"，不证明"这些测试足以发现错误"。
- 例（真实）：包裹追踪 kata，把 `parcel_id` 和 `tag` 直接拼成 `"ab"+"c"`——它与 `"a"+"bc"` 撞成同一个 key。写法 A 通过了全部 10 个测试，说明测试漏了撞 key；补了 case_07 的断言后被抓到（`b4c507c8`，`vault/interviews/companies/airbnb/study/q01_parcel_tracking.md`）。
- 变异得分 = 被杀 / 总数。该 kata：11/11。
- "空模板必须红"是最小的变异：把整个实现换成空的，测试必须失败，否则测试什么也没测（`tools/verify_suites.py`）。

**oracle 的盲区（senior 必须会讲）：**
1. **相关错误**：让同一个模型写代码和测试，两者常带同一个误解，一起绿。对策：规格先于代码、独立路径对拍、变异测试。
2. **规格错**：测试断言了错的行为。对策：从一手需求/文档写断言；人读。
3. **合理假设上的错误结论**：每个数字都对，但两个假设互相矛盾（G1 的 1,560 倍）。门禁看形状，只有读才看实质（`building-problem-banks` skill）。
4. **验收门只抓它被写进去的东西**：所以每个新发现的缺陷要变成新规则/新检查。

### 自测 §3
**Q1. 为什么 "tests pass" 不够？**
<details><summary>答案</summary>测试可能太弱（变异体存活）、可能和代码同源出错、可能断言了错的规格。需要验证测试：空实现必须红、变异体必须死、独立实现对拍。</details>

**Q2. 编译器作为 verifier 的边界？**
<details><summary>答案</summary>只证明类型/语法层面的性质，不证明行为正确；但它是最便宜、最快的第一层，能抓到幻觉出来的符号和 API。</details>

**Q3. "差分测试"在什么情况下失效？**
<details><summary>答案</summary>两个实现共享同一个误解（例如都由同一模型写出且依据同一个错误规格）。要用独立来源的实现或已知值（perft）。</details>

**Q4. 变异得分 8/11 说明什么？该怎么做？**
<details><summary>答案</summary>有 3 个变异体存活，对应 3 类未被覆盖的行为；为每个存活体补一个能杀死它的断言，再复跑。</details>

## §4 Prompt engineering vs Context engineering

**Prompt engineering：怎么措辞**。指令、角色、示例（few-shot）、输出格式（如 JSON schema）、分步要求。作用：让模型在**已有信息**下更准确地做你要的事。

**Context engineering：放什么进窗口**。每次调用时窗口里的全部 token——系统提示、项目规则文件、检索到的文档、工具返回、历史对话摘要、示例。作用：决定模型**能看到什么**。对 agent 尤其关键，因为每个工具调用的结果都进窗口。

| | Prompt engineering | Context engineering |
|---|---|---|
| 问题 | 怎么说清楚 | 给它哪些信息、以什么顺序、占多少预算 |
| 典型手段 | few-shot、格式约束、拆步骤 | 检索、规则文件（CLAUDE.md）、摘要/压缩、子代理隔离上下文、只传需要的文件 |
| 失败 | 歧义指令、格式漂移 | 相关信息没进窗口、无关信息挤掉预算、过时信息误导、被注入的文本 |

**为什么 context 管理是个工程问题：**
1. **窗口有限，且越满越不可靠**：可用长度有上限；信息淹没在长上下文中间时更容易被忽略（经验现象，因模型而异）。
2. **成本与延迟随输入长度增长**（§7）。
3. **无状态**（§1）：规则必须每次随上下文带上，所以写成文件。

**本仓库就是 context engineering 的实例：**
- 规则文件：`/CLAUDE.md` 是每次会话都读的持久上下文。
- 一组代理一份指令文件，而不是写在每次调用里（"put long shared instructions in one prompt file per group rather than in the Agent call"）。
- 一个代理一个目录、一个可由命令验证的交付物（上下文小、边界清楚）。
- 简报由调研结果生成（`proposals/design-problems/<slug>.prompt.md`），不让代理凭空回忆。
- 可恢复：每个代理先检查已有产出，跳过已通过的（resume rule）；`CHECKPOINT.md` 让新会话零上下文接手。
- 子代理隔离：用代理把"读大量材料"的上下文消耗关在子会话里，只带回结论。

**Prompt / RAG / Fine-tuning 怎么选（变体 C6）：**

| 手段 | 适合 | 代价 / 失败 |
|---|---|---|
| 更好的 prompt + 示例 | 格式、风格、任务澄清；起点 | 受限于模型已有知识；提示漂移 |
| RAG（检索增强生成） | 知识频繁变化或私有；要引用来源 | 要建索引与评测；检索未命中、分块切断、文档被投毒 |
| Fine-tuning | 稳定的风格/格式/行为，有足量高质量数据 | 数据与训练成本；知识更新慢；过拟合；回归风险 |

经验规则：从最便宜的开始，用 eval 决定是否升级（§5B）。

**RAG 流水线，从零：** 文档切块（chunk）→ 向量化（embedding）→ 存入索引 → 查询时把问题也向量化，取最相似的 top-k 块 → 拼进 prompt → 模型基于它们回答。每一步都有失败模式：切块边界、嵌入对术语不敏感、top-k 太小漏召回、太大挤占窗口。

### 自测 §4
**Q1. 用一句话区分 prompt 与 context engineering。**
<details><summary>答案</summary>prompt = 怎么措辞这条指令；context = 窗口里放哪些信息、顺序与预算。</details>

**Q2. 为什么 agent 场景下 context engineering 更重要？**
<details><summary>答案</summary>agent 多步执行，每一步的工具输出都进窗口，窗口会被噪声/过长输出占满，早期规则被挤出；需要摘要、隔离、只传必要内容。</details>

**Q3. 知识库每天更新，选 RAG 还是 fine-tune？**
<details><summary>答案</summary>RAG：更新索引即可，不用重训；fine-tune 更新慢且昂贵。仍需评测检索质量。</details>

## §5 Agent 与工具调用；评测基础

### 5A. Agent 的工作方式

**是什么。** Agent = 模型 + 工具 + 循环。循环：模型读上下文 → 产生"调用某工具 + 参数"（结构化输出）→ **harness（运行时）**执行工具 → 结果写回上下文 → 模型再决定下一步，直到给出最终答案或超限。

**关键点：模型从不直接执行任何东西。** 它只产出文本；是 harness 解析并执行，并决定要不要先问人。所以**权限、沙箱、审批全在 harness**，不在模型里。（本仓库：agent 不能修改自己的权限/隔离设置，只能把确切片段交给 Chi；worktree guard 拒绝 heredoc 等。）

**工具的 schema** 是函数名 + 参数 + 说明，写在上下文里；说明写得含糊，模型就会选错工具或传错参数。

**多代理（orchestrator–workers）。** 主会话拆任务、派子代理、验收。优点：并行、各自的上下文小。代价：协调成本、代理之间的不一致（仓库的失败表："两篇题解对同一组件的上限不一致"）、成本成倍。

**常见失败模式 → 对策（对应仓库规则）：**

| 失败 | 对策 | 仓库里的规则 |
|---|---|---|
| 自报"完成"但没完成 | 独立重跑验收 | "Never accept a subagent's done" |
| 部分完成后崩溃（429 额度） | 台账 + 恢复规则；抢救而非重来 | "salvage and finish them, don't respawn from scratch" |
| 代理互相覆盖文件 | 一个代理一个目录 | "No shared files between parallel agents" |
| 失控并行/递归 | 硬上限、不得派代理 | "at most 3… never spawn their own agents"（`9429f863`） |
| 把缺陷写进文档当契约 | 发现即修复并加回归测试 | `a15a15bd` |
| 自信的数字错误 | 脚本复算 | `proposals/design-problems/AGENT.md` |

### 5B. 评测（eval）基础

**为什么要 eval。** LLM 输出是概率性的；没有评测，"我觉得变好了"无法证伪，改一个 prompt 可能悄悄让别处变差（回归）。

**评测集（golden set）。** 一组有标准答案或判定规则的输入。要包含：典型输入、边界、对抗输入（注入、超长、噪声）、以及历史上出过错的用例（每个缺陷变成一条用例）。

**指标按失败模式选：**
- 有确定答案：exact match / 单元测试通过率。
- 代码：测试通过。pass@k：采样 k 次至少一次通过的概率；n 次中 c 次通过时，pass@k = \(1 - \binom{n-c}{k}/\binom{n}{k}\)。例：n=10、c=3，pass@1 = 0.3，pass@3 = 1 − C(7,3)/C(10,3) = 1 − 35/120 = **0.708**。
- 分类/抽取：precision（报出来的有多少是对的）、recall（该报的报出来多少）。
- 开放式文本：人工评分，或用另一个 LLM 当裁判（LLM-as-judge）。

**LLM-as-judge 的坑：** 位置偏好（偏爱先出现的答案）、自我偏好（偏爱自己家模型的风格）、偏爱更长的答案。对策：随机换位、用已标注样本校准裁判与人的一致率、能用 oracle 就不用裁判。

**样本量与噪声（一定要会算一个数）。** 比例的标准误 \(\sqrt{p(1-p)/n}\)。n=50、p=0.8：SE ≈ 0.057，95% 区间约 ±11 个百分点——**50 条样本分不出 80% 和 85%**。所以小评测集上的"提升 5%"可能只是噪声；需要更大 n、重复运行或配对比较。

**线下 vs 线上。** 线下 eval 防回归；线上监控看真实分布漂移、成本、延迟、用户反馈；两者都要，并有回滚路径。

**验证 AI 辅助的开发工作 = 小型 eval。** 门禁（参考解绿 + 空模板红）就是一个确定性的 eval；变异得分是对 eval 本身的评测。

### 自测 §5
**Q1. 为什么权限控制不能依赖"在 prompt 里告诉模型不要做 X"？**
<details><summary>答案</summary>模型可能被注入、误解或出错；真正的边界必须在 harness（沙箱、白名单、审批）强制执行。prompt 里的禁止只是建议。</details>

**Q2. n=10、c=3，pass@2 是多少？**
<details><summary>答案</summary>1 − C(7,2)/C(10,2) = 1 − 21/45 = 0.533。</details>

**Q3. 两个 prompt，在 50 条样本上 82% 对 78%，能说谁更好吗？**
<details><summary>答案</summary>不能。SE 约 0.055–0.06，差 4 个点在噪声内；要更多样本、重复运行或配对检验。</details>

**Q4. LLM-as-judge 为什么要用人工标注样本校准？**
<details><summary>答案</summary>裁判有位置/自我/长度偏好，且可能与你的标准不一致；用标注样本测它与人的一致率，低于阈值就不能用。</details>

## §6 安全：prompt injection 与数据泄露

**Prompt injection 从零讲。** 模型把系统提示、你的指令、网页内容、文件内容、工具结果都当成**同一条 token 序列**，没有硬的"指令/数据"边界。攻击者把指令写进数据里（网页、邮件、README、issue、工具返回），模型可能当作命令执行。
- **直接注入**：用户自己输入恶意指令（越狱）。
- **间接注入**：恶意指令藏在 agent 读取的第三方内容里。——对读网页、读仓库的 agent 是主要威胁。

**危害组合（常被称为"致命三要素"的框架）：同时具备 (1) 访问私有数据 (2) 接触不可信内容 (3) 能对外通信（发请求、写外部系统）。** 三者齐备就可能被诱导把私有数据发出去。**对策：打断其中一条**——这是比"让模型识别恶意指令"更可靠的设计。

**缓解清单（说得出每条挡什么）：**
1. 最小权限：agent 只拿完成任务所需的工具和路径。
2. 不可逆/外发动作要人批准（发邮件、推送、删除、支付）。
3. 沙箱执行代码；网络出口白名单。
4. 不可信内容与指令分区标注，并限制其可触发的工具；输出做校验（schema、白名单）。
5. 记录工具调用以便审计；对注入做红队用例（放进 eval）。
6. 密钥不进 prompt/上下文；用环境注入与短期凭据。

**数据泄露。**
- 发到第三方模型 API 的内容：先问 **留存**（保存多久）、**训练**（是否用于训练）、**合规**（地区、合同）。企业协议与个人账号不同。
- 最小化：不放客户数据、密钥、未公开内部信息；脱敏或用合成数据。
- 模型可能复述训练数据；生成的代码可能带许可证问题——按公司政策审查。
- 供应链：模型可能"编造"并不存在的包名，攻击者可抢注同名恶意包（"slopsquatting"）——安装前核对包是否真实存在、是否是预期的包。

**本仓库的真实控制手段（可作例子，别夸大）：**
- 公开仓库规则：不放招聘人员姓名、邮件内容、个人数据（`AGENT_RULES.md` 规则 4）；商业站点内容只链接不存档（`no-archive`）。
- 爆炸半径 guard：测试夹具曾写进真实 Anki 集合 → `tests/conftest.py` 让真实客户端拒绝（`965dbc89`）；`anki-push` 从不改已复习卡的 `due`。
- agent 不能自己改权限/隔离设置（`/CLAUDE.md`）。
- 工作中的做法（公司数据怎么处理、用哪个企业版工具）`【待 Chi 补】`——只说你确知的。

## §7 成本与延迟取舍

**成本模型。** 调用成本 ≈ 输入 token × 输入单价 + 输出 token × 输出单价（输出通常更贵；具体单价看当时价目表，我不凭记忆写）。总成本 = 单次成本 × 调用次数；agent 的调用次数随步数和重试增长，上下文随步数累积，所以长任务输入 token 增长很快。

**延迟模型。** 延迟 ≈ 首 token 时间（time-to-first-token，与输入长度、排队有关）+ 输出 token 数 × 每 token 时间。例（示意）：输出 500 token、50 token/s → 约 10 s 生成时间。降延迟：流式输出（用户先看到开头）、缩短输出、缩短输入、并行调用互相独立的子任务（墙钟时间≈最慢一个，成本≈总和）。

**提示缓存（prompt caching）。** 复用相同的前缀已计算的内部状态，重复调用时便宜、快。含义：**把稳定的内容（系统提示、规则、文档）放前面，变化的放后面**。例（示意，r = 缓存读取相对价格，从价目表取）：20k token 的稳定前缀调用 100 次：无缓存 = 100P；有缓存 = P(1 + 99r)，r=0.1 时 = 10.9P。

**模型分档。** 便宜小模型做高量、易验证的活；贵模型做难推理或最终审查。本仓库：子代理用 sonnet，额度打满时回退到 opus（`/CLAUDE.md`）；复核由主会话做。

**本仓库实测（`building-problem-banks` skill "Measured cost"）：**

| 工作 | 墙钟 | tokens |
|---|---|---|
| 一个调研代理 | 4–6 分钟 | 85–145k |
| 一题单独（试点） | 8–10 分钟 | 130–145k |
| 一个代理两题 | 17–29 分钟 | 180–345k |
| 一轮 SendMessage 修订 | 5–6 分钟 | +40–60k |

整库（3 调研 + 3 试点 + 23 对）：3×115k + 3×137.5k + 23×262.5k ≈ **6.8M** tokens（区间中值，脚本算），与 skill 里"≈ 6–7M"一致。

**取舍框架（senior 回答用）：**
1. 这一步有 oracle 吗？有 → 可以便宜地多生成多验证；没有 → 要贵的人工或贵模型。
2. 用户在等吗？在 → 延迟优先（流式、小模型、缓存）；不在 → 吞吐/成本优先（批处理、异步）。
3. 确定性问题别用模型（G3）。
4. 并行：互相独立才并行，且受上限（仓库：3）和审查带宽限制——**瓶颈常常是你的验收，而不是生成**。

### 自测 §7
**Q1. 为什么 agent 长任务的 token 增长比"步数 × 单步成本"更快？**
<details><summary>答案</summary>每一步的输入包含此前所有的历史与工具输出，输入随步数累积；所以总输入近似步数的平方量级，除非摘要/压缩/隔离上下文。</details>

**Q2. 20k token 稳定前缀调用 100 次，缓存读取价是原价的 0.1 倍，节省多少？**
<details><summary>答案</summary>无缓存 100P；有缓存 P(1+99×0.1)=10.9P，约省 89%（示意假设）。</details>

**Q3. 5 个互相独立的子任务各 10 s，并行 vs 串行的墙钟与成本？**
<details><summary>答案</summary>墙钟 ≈ 10 s vs 50 s；成本相同（总和）；并行换时间不换钱，还增加同时需要的验收带宽。</details>

## §8 一个「AI 聊天机器人」的系统设计骨架（面经 JC-qbgerq：architect an AI chat bot）

完整题解：`vault/domains/system-design/readings/problems/solution-llm-chat-service.md`（Chi 的 SD 题库，含 GPU 批处理、KV cache、流式、配额、安全过滤）。口述骨架：

1. **需求澄清**：自己托管模型还是调用第三方 API？是否带检索/工具？上下文多长？免费/付费配额？
2. **路径**：客户端 → 网关（认证、限流、配额）→ 会话服务（权威对话存储，上下文裁剪/摘要）→（可选）检索 → 模型推理（流式返回）→ 安全过滤 → 客户端。
3. **关键难点**：生成延迟（TTFT + 每 token）→ 流式 + 缓存前缀；GPU 是稀缺资源 → 准入控制和分档配额；断线语义 → 生成不因客户端断线而停止（题解"Token 流式传输与断线语义"）。
4. **质量与安全**：golden set 回归、注入红队用例、输出过滤、日志与审计、成本监控。
5. **演进**：多区域、模型分档路由、缓存、离线批处理。

### 自测 §8
**Q1. 为什么 chat 服务要流式输出？**
<details><summary>答案</summary>总生成时间长（输出 token 数 × 每 token 时间），流式让用户在首 token 时间后就开始阅读，感知延迟大幅降低。</details>

**Q2. 如果用户问内部文档的问题，加什么？**
<details><summary>答案</summary>检索（RAG）：索引 + 权限过滤（只检索该用户有权访问的文档）+ 引用来源 + 注入防护（文档是不可信输入）。</details>

## §9 面试里的说法：一个 5 句话骨架

1. **Where**：I use it for [planning, scaffolding, refactor, tests, review], not for [numbers, external facts, security decisions].
2. **Control**：plan → TDD → gates; I own every diff.
3. **Verify**：oracle ladder (compiler, tests, differential, known values), then test the tests (mutation, empty-starter must fail).
4. **Evidence**：one concrete artifact (`stories.md`: G1 38% → certainty; G2 11/11 mutants).
5. **Limits**：where it wasn't worth it (counts → script; one-line fixes in place) and what I'd add for production (evals, injection tests, monitoring).
