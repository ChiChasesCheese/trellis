# q02 · Vowel-Run DP：一个状态机数三种东西，练的是"同一个 DP 换三张皮"

> [!tldr]
> - 这题考的是：用"结尾连续元音游程长度"这一个状态，数抽象字符串（精确大整数 / 取模高效两版）和数具体字符串的子串
> - 三步套路：先把 DP 状态 `dp[j]`（结尾恰好 j 个连续元音）想清楚 → Part 1 不取模验证转移对不对 → Part 2 加模数和性能约束 → Part 3 把同一个"游程"概念搬到具体字符串上
> - 最值得带走的一个模式：**状态设计定了，剩下的都是工程约束的排列组合**——大整数精度、取模、O(n) 扫描本质上是同一个 DP 换了三种落地方式

## 1. 题目在说什么（人话版）
26 个小写字母，5 个是元音（aeiou）。三个 part 都围绕"连续元音游程"这个概念：

1. Part 1：长度为 `n` 的字符串里，任意一段连续元音都不超过 `k` 个，这样的字符串有多少种？（精确数字，不取模）
2. Part 2：同一问题，但要对 `1e9+7` 取模，且 `n` 最大到 2500，必须快。
3. Part 3：给一个具体字符串 `s`，数有多少个子串**完全由元音组成**，并且**5 个元音各出现至少一次**。

三行小例子：
```
part1(1, 0) == 21     # 完全不许元音，只能选 21 个辅音
part2(4, 1) == 412776 # FastPrep 官方样例
part3("aeioub") == 1  # "aeiou" 凑齐 5 元音贡献 1 次；'b' 之后不再有元音游程
```

## 2. 读题：把文字变成模型
- **实体**：字母（元音/辅音二分类）、连续元音游程（长度）。
- **输入长什么样**：`PART n` + 一行 payload——Part 1/2 是 `n k`（两个整数），Part 3 是原始字符串（可能是空行）。
- **输出要什么**：一行整数；Part 1 精确大整数，Part 2 取模，Part 3 精确整数。
- **状态**：Part 1/2 是"到当前长度为止、结尾连续元音游程长度是几"的一个计数向量 `dp[0..k]`；Part 3 是"当前
  游程内，每个元音最后一次出现在哪个下标"的一个最多 5 项的字典。
- **一句话建模**：这是一个 **以"结尾游程长度"为状态的计数 DP**，Part 1/2 数抽象字符串的方案数，Part 3 把
  同一个"游程"概念用在真实字符串的子串计数上（不是同一个 DP，但是同一个"游程"心智模型）。

> [!note] 为什么选这个数据结构
> `dp[j]` 只需要知道"结尾游程多长"就能决定下一步转移（追加辅音清零、追加元音游程+1），不需要记住更早的历史，
> 所以一个长度 `k+1` 的向量就够，不需要二维表。Part 3 的"游程内 last-seen 字典"同理：一旦 5 个元音都出现过，
> 只要知道**最早**那个"最后出现位置"就能算出当前右端点有多少个合法左端点，不需要存整个子串。

## 3. 下笔顺序（面试里就按这个顺序敲）
1. **骨架先行**：`main()` 读 `PART n`，第二行按 part 解析成 `(n,k)` 或字符串，调对应函数，打印一行整数。
2. **Part 1 最小可用**：写共享核心 `_count_strings(n, k, mod)`——`dp=[1,0,...,0]`（空串），每步 `new_dp[0] = 21*sum(dp)`，
   `new_dp[j] = 5*dp[j-1]`（`j` 从大到小更新避免覆盖）。用 `n=1,k=0 -> 21` 和 `n=1,k>=1 -> 26` 手算验证。
3. **Part 2 叠加**：给 `_count_strings` 加一个 `mod` 参数，每步取模；不改变 DP 结构，只是套一层取模。用
   FastPrep 官方样例（`calculateWays(4,1)==412776`）验证，并断言 `part1(4,1)==part2(4,1)` 做交叉验证。
4. **Part 3 叠加**：不复用 Part 1/2 的 DP（这是不同的问题），单独写"按辅音切游程 + 游程内维护 last 字典"。
5. **收尾**：`cap = min(k, n)` 裁剪状态向量长度，避免为用不到的状态分配空间；确认 `sum(dp)` 用内置函数而非手写循环（性能坑）。

## 4. 代码怎么组织
```
_count_strings(n, k, mod) -> int   # Part1/2 共用的 DP 核心，mod=None 时精确大整数
part1(n, k) -> int                 # 调 _count_strings(mod=None)
part2(word_len, max_vowels) -> int # 调 _count_strings(mod=1e9+7)
part3(s) -> int                    # 独立逻辑：切游程 + 游程内 last 字典
main(stdin, stdout)                # 解析 PART，分发
```
Part 1/2 共享一个核心函数，靠一个 `mod` 参数区分"要不要取模"，这样两处转移逻辑不会走岔；Part 3 完全独立，
因为它是"在具体字符串上扫描"而不是"数抽象方案数"，硬凑成同一个函数只会让代码更绕。

## 5. 核心代码（骨架，≤ 40 行，带注释）
```python
VOWELS = frozenset("aeiou")

def _count_strings(n, k, mod):                  # Part1(mod=None) / Part2(mod=1e9+7) 共用
    cap = min(k, n)
    dp = [0] * (cap + 1)
    dp[0] = 1                                    # 空串：辅音桶
    for _ in range(n):
        total = sum(dp) % mod if mod else sum(dp)
        for j in range(cap, 0, -1):              # 从大到小，避免用新值覆盖还没读的旧值
            v = dp[j - 1] * 5
            dp[j] = v % mod if mod else v
        dp[0] = (total * 21) % mod if mod else total * 21
    total = sum(dp)
    return total % mod if mod else total

def part1(n, k):
    return _count_strings(n, k, mod=None)

def part2(word_len, max_vowels):
    return _count_strings(word_len, max_vowels, mod=1_000_000_007)

def part3(s):
    total, run_start, n, i = 0, 0, len(s), 0
    while i <= n:
        if i == n or s[i] not in VOWELS:         # 游程在 i 处被打断（或字符串结束）
            last = {}
            for j in range(run_start, i):
                last[s[j]] = j - run_start        # 局部下标：run_start 记为 0
                if len(last) == 5:                # 5 个元音都出现过
                    total += min(last.values()) + 1
            run_start = i + 1
        i += 1
    return total
```

## 6. 面试里怎么说（边写边讲）
- 开始前：「我先确认：字母表 26 个，元音 5 个；Part 1 不取模、Part 2 取模且 `n` 到 2500 要快、Part 3 是
  在具体字符串上找子串，三问看起来像同一题但落地约束不一样。」
- 写 Part 1 时：「状态是`dp[j]` = 结尾恰好 j 个连续元音的方案数，转移就两条：追加辅音全部清零、追加元音
  从 j-1 挪到 j。我先不取模验证转移对不对，再加模数。」
- 写 Part 2 时：「和 Part 1 完全一样的转移，只是每步取模；用内置 `sum()` 而不是手写循环求和，因为
  `word_len=2500` 时纯 Python 双重循环可能顶到 2 秒预算，`sum()` 是 C 级别实现更快。」
- 写 Part 3 时：「这题不是同一个 DP——我先按辅音切出所有最大元音游程，游程内维护一个『每个元音最后
  出现位置』的字典，凑齐 5 个之后，当前右端点的贡献就是 `min(最后出现位置) + 1`，因为再往左的起点都会
  丢掉那个最晚出现的元音。」
- 交付时：「三个样例都过了；Part 1 我特意用 `n=30` 无约束场景验证结果精确等于 `26**30`（远超模数），
  确保没有不小心复制 Part 2 的取模逻辑进来。」

## 7. 常见跑偏（方法层面，3 条）
- **写 Part 2 时复制 Part 1 的代码却忘了去掉/加上取模**：容易导致 Part 1 意外取模（大 n 时结果远小于
  应有的大整数）或 Part 2 忘记取模（数值虽然对但没有满足题目约定）。用一个共享核心函数、一个 `mod` 参数
  从根上避免这个问题。
- **Part 2 用手写双重 for 循环求和而不是内置 `sum()`**：在 `word_len=k=2500` 的最坏情形下可能顶满甚至
  超过 2 秒的性能预算。
- **Part 3 里"凑齐 5 元音之后"的边界算错**：辅音紧跟在刚好凑齐之后不该产生额外贡献，辅音把一个本可能凑齐
  的游程从中间斩断也不该被误算——这两种情况都要在样例里显式验证（`"aeioub"==1` 而不是 2，`"aeiobu"==0`）。

## 8. 同族题 / 延伸
- 变体：把"最多连续 k 个元音"换成"最少连续 k 个元音"，同一个状态机，只是转移条件反过来。
- Part 3 的变体（LC 1987/2062 形态）是"子串包含全部 5 个元音，但不要求纯元音"，是完全不同的滑窗题，
  本题特意保留了"纯元音"这个更强约束，别把两者的算法搬混了。
- 如果 `word_len` 上限从 2500 提到 `1e5+`，Part 2 的 `O(n·k)` 会超时，需要换成 `O(n)` 的滑动窗口线性递推。
