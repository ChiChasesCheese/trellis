# q03 Tree Height Reduction — report

## 摘要

"树高压缩"题族的三合一：删叶子（输出 id）、剪子树（只计数）、换根（求最小高度）。三个 part 来自
三个不同来源，节点编号和深度基准各不相同（1-indexed 根深度1 / 0-indexed 根深度0 / 1-indexed 高度
按边数），本身就是一个"契约先行"的坑——很多候选人会把三种约定搞混。Part 3 的换根 DP 是本题真正的
技术难点，也是我在实现过程中发现并修了两个真实 bug 的地方。

## 来源与置信度

MED-HIGH（综合）——三个独立来源主题高度一致："树高压缩"反复出现在 Snowflake 的 OA 和电面题库里，
但个别来源未逐字验证细节：
- https://www.fastprep.io/problems/snowflake-minimum-nary-tree-deletions（Part 1，MED）
- https://prachub.com/coding-questions/prune-a-multiway-tree-to-a-maximum-depth（Part 2，MED）
- https://www.fastprep.io/problems/snowflake-minimum-height（Part 3，MED）

## 逐 part 思路

- **Part 1**：深度沿路径严格递增 ⇒ 一个节点该不该删只取决于自己的深度是否 > k（可以证明：不存在
  只删更浅祖先就能救它的办法，而它自己总能在更深后代都被删完后作为叶子被删掉）。答案 = 所有
  深度 > k 的节点 id，升序。BFS 求深度即可，O(n)。
- **Part 2**：每次删除是删一整棵子树，所以只数"顶层"超标节点：深度 > k 且父节点深度 <= k。BFS
  求深度后一次遍历，O(n)。
- **Part 3**：二分答案高度 H，对每个候选 H 用递归 `fix(v,d,H)` 判断可行性（cut 现在 vs 把决定权
  交给孩子，取更便宜的）。

## 隐藏测试针对的坑

1. **三个 part 的编号/深度约定不能混用**——这是本题设计上刻意保留、而非统一掉的坑，problem.md
   开头专门用一张对照表说明。
2. Part 2："顶层超标点"去重：同一个已超标祖先下的一串超标后代只算 1 次；同样的叶子挂在未超标
   父节点下则要分别计数（worked examples 2 vs 3，两个数字分别是 1 和 3，容易被想当然地都算错成
   "叶子数量"）。
3. Part 3："剪中间节点救不了更深的后代"：剪节点 v 之后 v 的孩子深度变成 2，如果 v 的孩子自己
   还是超标，剪 v 完全没用，必须逐个剪孩子（wider-branching-tree 例子：`max_operations=1` 时
   仍然不能把高度从 2 降到 1，需要恰好 3 次操作才行）。
4. **Part 3 的 `H=0` 特判——这是我实现时真实发现并修复的算法 bug，不是编出来的**（见下节）。

## 复杂度与实测（含对给定算法设计的偏差说明）

**发现的问题 1 —— `H=0` 时朴素伪代码的隐含假设是错的**：换根操作把节点接到根下面，新深度**恒为
1**，不可能是 0（只有根节点深度是 0）。原始伪代码 `if d > H: return 1 + fix_children_only(v, 1, H)`
隐含假设"换根就能让 v 合规"，但没检查换根后的新深度 `1` 是否真的 `<= H`。实测：`part3(4, [1,1,1],
[2,3,4], 1000)`（根带 3 个叶子，给了 1000 次操作预算）按朴素实现会返回 `0`，但这是错的——根的
孩子已经在深度 1，不管给多少次操作，非根节点永远不可能降到深度 0。已在 `_total_ops` 里加了显式
特判：`H == 0` 时只有"树只剩根节点"才可行，否则直接判定为不可行（用 `math.inf`），修复后
`part3(4, [1,1,1], [2,3,4], 1000) == 1`（正确答案：原始高度 1，且 1 无法再降）。这个坑和它的
修复已经写进 `problem.md` 的 Part 3 算法段落，并有专门的回归测试
（`test_part3_generous_budget_reaches_zero_only_if_root_has_no_children`、
`test_part3_height_zero_only_for_single_node`）。

**发现的问题 2 —— 声称的"O(n) per total_ops(H) call"对链状树不成立**：题目描述认为"每个
`total_ops(H)` 调用只访问每个节点一次，为 O(n)"，但这只在树"矮胖"（分支多、高度低）时成立。对于
**链状树**，`fix(v,d,H)` 的 `d`（进入 v 时假设的深度）会因为"是否在某个更高的祖先处剪过"而在
不同调用路径下取到 O(depth) 个不同值，即使加了 `(v,d)` 记忆化，单次 `total_ops(H)` 调用访问的
状态数在链状树上会退化到 `~O(n²)`（等价于所有子树大小之和）。实测（链长 n，`max_operations=n/4`，
含二分搜索的完整 `part3` 调用）：

| n（链长） | 用时 |
|---|---|
| 1000 | 0.26s |
| 1500 | 0.66-1.01s |
| 2000 | 1.29s |
| 3000 | 4.4s |
| 5000 | 19.8s |

而 Part 1/Part 2 在"矮胖"（宽度 10^5、高度 2）的树上依然是干净的 O(n)（perf 测试里验证了
`n=100000` 均在 2s 预算内轻松通过）——只有 Part 3 的换根 DP 会因为树形（链 vs 矮胖）而复杂度
差异巨大。没有找到已知的次二次精确算法能处理链状最坏情况。**因此把链状 stress test 的规模定在
n=1500**（实测约 0.66-1.0s，留有约 2× 余量），符合题目允许的"n up to ~1000 起步、2000-5000 为
上限"区间的下限，但没有触及上限——这是有实测数据支撑的、明确写在
`test_q03.py::test_perf_part3_skewed_chain` 注释里的偏离。

复杂度总结：Part1/Part2 `O(n)`（单趟 BFS + 线性扫描）；Part3 `O(log(height))` 次
`total_ops(H)` 调用，每次在"矮胖"树上 `~O(n)`，在链状树上经验退化到 `~O(n²)`。
