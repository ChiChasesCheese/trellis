# q20 · Sequential String — 磁带只能顺序读，前缀最短要多长才能拼出排列

> OA 题（2024，JoeBao22/SDE-OA-2024 仓库一手转述）。Part 1 为原题；Part 2 **(reconstructed)**：
> 把 Part 1 的做法从"每次查询二分"换成"O(1) 直接索引"，把总复杂度降到 O(总查询长度)。

## 背景

来源仓库 [`JoeBao22/SDE-OA-2024`](https://github.com/JoeBao22/SDE-OA-2024) 的
`SnowFlakes/SequentialString.md` 转述了这道 2024 年 OA 题：字符串 `s` 只能"顺序读"——
把它想象成一台磁带，读头只能往右走，一次读一个前缀。对查询数组 `arr` 里的每个字符串，
求最短需要读多少个字符（即 `s` 的最短前缀长度），这个前缀里包含的数字**恰好够拼出
`arr[i]` 的某个排列**，做不到就输出 `-1`。

**该来源自带的参考实现是错的**：它把 `arr[i]` 的字符按顺序当成"子序列"去 `s` 里顺着找
（先找第 1 个字符出现的位置，再从那之后找第 2 个字符……），这是完全不同的题目。真正的题
目只要求前缀的**数字多重集合**覆盖 `arr[i]` 的数字多重集合，跟顺序无关。反例见下面
"边界清单"第一条——这是本题的教学点：**"能不能构成某个排列"从来不是顺序问题，是计数
问题**，一旦读成子序列匹配，答案就会系统性地偏小（更容易判定"不可能"）。

## 输入

- `s`：数字字符串（可以为空），`0 ≤ len(s) ≤ 10⁵`；
- `m` 条查询，每条是数字字符串，`0 ≤ m ≤ 2×10⁴`，所有查询长度之和 `≤ 5×10⁵`。
- `s` 或任一查询里出现非数字字符 → 抛 `ValueError`。

## API 契约（英文签名）

```python
def sequential_prefix_lengths_binary(s: str, queries: list[str]) -> list[int]
def sequential_prefix_lengths_fast(s: str, queries: list[str]) -> list[int]
```

## 规则

对每个查询 `q`，设 `need[d]` = `d` 在 `q` 里出现的次数（`d` 取遍出现过的数字）。答案是
最小的前缀长度 `L`，使得 `s[:L]` 里每个数字 `d` 出现次数都 `≥ need[d]`；不存在这样的
`L` 就是 `-1`。空查询的 `need` 为空，答案恒为 `0`（不需要读任何字符）。

### Part 1 — 逐查询二分（对每个数字建前缀计数表）

对每个数字 `0..9`维护一张前缀计数列 `counts[d][i]` = `s[:i]` 里 `d` 的个数（长度 `n+1`，
单调不减）。对查询里出现的每个数字 `d`，在 `counts[d]` 上二分查找第一个 `≥ need[d]` 的
下标——那就是"凑够 `need[d]` 个 `d`"所需的最短前缀长度。查询答案是这些下标的最大值
（因为前缀必须同时满足所有数字的需求）；只要有一个数字永远凑不够就是 `-1`。

预处理 `O(10n)`，每次查询 `O(len(q) log n)`。

### Part 2 — 出现位置表，O(总长度) **(reconstructed)**

Part 1 的二分其实是在多余地"搜索"一个本可以直接算出来的下标：对每个数字 `d`，把它在
`s` 里出现的位置（0-based）按顺序存成 `occ[d]`。需要 `need[d]` 个 `d`，那么恰好是
`occ[d][need[d] - 1]`（第 `need[d]` 次出现的位置，0-based），前缀长度就是它 `+1`；如果
`len(occ[d]) < need[d]` 就是 `-1`。查询答案还是取各数字所需长度的最大值。

预处理 `O(n)`，总查询处理 `O(总查询长度)`，不再有 `log n` 因子——因为不需要"搜索"，
数组下标直接给出答案。

两个 Part 在任何输入上答案必须完全一致（测试里做了随机交叉验证）。

## Worked examples（全部由 `solution.py` 实际运行得出）

| s | queries | Part 1 / Part 2 |
|---|---|---|
| `"064819848398"` | `["088", "364", "071"]` | `[7, 10, -1]`（题面原例） |
| `"21"` | `["12"]` | `[2]`（**顺序匹配的错误解法会判 `-1` 或更长**，见下方边界清单） |
| `""` | `["1", ""]` | `[-1, 0]` |
| `"11"` | `[""]` | `[0]` |
| `"11111"` | `["17"]` | `[-1]`（数字 `7` 从不出现） |
| `"321"` | `["123"]` | `[3]`（要用满整个 `s`） |
| `"064819848398"` | `["88"]` | `[7]`（第 2 个 `8` 出现在下标 6，前缀长度 7） |

## `main()` 命令流

```
PART 1                    PART 2
064819848398               064819848398
3                          3
088                        088
364                        364
071                        071
→ 7                        → 7
  10                         10
  -1                         -1
```

## 边界清单

- **顺序匹配 vs 多重集合**：`s = "21"`, `q = "12"`。多重集合正确答案是 `2`（前缀 `"21"`
  里有一个 `1` 和一个 `2`，顺序无所谓）。如果按查询字符顺序在 `s` 里顺着找子序列（先找
  `'1'` 在下标 1，再从下标 2 往后找 `'2'`——找不到），会得出"不可能"或更大的长度，这正
  是来源仓库参考解法的 bug。
- 空 `s`：除空查询外全部 `-1`。
- 空查询：答案恒为 `0`。
- 需要的数字在 `s` 里从未出现：`-1`。
- 需要用满整个 `s`（答案 `= len(s)`）。
- 某数字需要出现多次（重复计数，不是"出现过就行"）。
- 非法输入（非数字字符）→ `ValueError`。
- 性能：`n = 10⁵`、`m = 2×10⁴`、总查询长度 ≈ `5×10⁵` 时两个 Part 均 `< 2s`。

## 追问

1. **为什么"最大的最高需求下标"就是答案？** 前缀长度单调：越长的前缀，各数字计数只增
   不减。要同时满足所有数字的需求，前缀长度取"最迟被满足的那个数字"所需的长度即可，其
   余数字在这之前已经被满足。
2. **能不能把 26 个字母（而不是 10 个数字）的版本一起做？** 完全一样，只是把计数表/出现
   位置表的"维度"从 10 换成字母表大小，不影响复杂度形状。
3. **多个查询能不能共享计算？** 可以按查询去重，或者按 `need` 的字典序排序做增量比较，
   但本题量级下直接对每个数字取 `O(1)` 索引已经是最优复杂度，去重只是常数优化。
4. **如果 `s` 是流式到达（边读边有新查询）呢？** 出现位置表可以增量追加（`occ[d].append`
   保持有序），二分或直接索引都仍然成立，只是不能一次性预处理到底。

## 考什么

多重集合 vs 顺序匹配的正确性论证（"一眼像子序列题，其实是计数题"）· 前缀单调性 + 二分 ·
用"出现位置表"把二分降成 O(1) 索引，去掉不必要的 log 因子。
