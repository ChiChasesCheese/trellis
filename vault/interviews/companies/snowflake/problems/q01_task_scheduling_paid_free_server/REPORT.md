# q01 Task Scheduling: paid vs free server — report

## 摘要

一台付费机、一台免费机抢任务；付费机空闲时新任务必须上付费机，忙碌时可以选免费机（免费、固定1
单位时间）或排队付费机。表面是贪心，实际是"要不要花钱买未来的空闲"的 DP：把成本和"付费机何时空闲"
的状态一起搜索。Snowflake 从 2022 到 2026 反复出这题（OA），核心考点是**状态设计**（S02）——多数
候选人会把它当纯贪心做错，因为"排队反而更便宜"这种情形（本题 worked example 4）打破了直觉。

## 来源与置信度

HIGH — LeetCode Discuss 逐字题面（2022-09-08，Core/Data Engineering Intern OA）；MED 佐证——
linkjob.ai 2026-03-16 独立提到同一题族；MED 佐证——2023 Canada intern 题目索引（仅链接）。

## 逐 part 思路

- **Part 1**：直接按模型写记忆化搜索，状态 `(i, free_at)`。不追求性能，只求清晰、正确，用来
  交叉验证 Part 2。
- **Part 2**：对 `free_at` 维护一个 Pareto 前沿 `{free_at: min_cost}`。每步把前沿拆成"强制"
  （`free_at<=i`，只留最小成本的一个新状态）和"忙碌"（`free_at>i`，各自分裂出免费/排队两个后继），
  合并后剪枝。

## 隐藏测试针对的坑

1. **"排队反而更便宜"**：`cost=[1,1,1000], time=[2,1,1]` → `2`。如果只贪心地"能白嫖就白嫖"，
   任务1选免费机会导致任务2被强制以 `cost[2]=1000` 付费机结算，总成本 `1001`；正确做法是任务1
   排队（多花 `1`），把付费机的空闲点推过任务2，总成本只要 `2`。这是本题 skills matrix 标注的
   "S02 计数 DP"里最容易被想成贪心而做错的地方。
2. **剪枝方向反了会直接算错**（见下一节，这是我在实现过程中真实踩到、修正过的坑，不是编出来的）。
3. `time[i]=0` 导致连续强制付费；`cost[i]/time[i]` 到 `1e9` 级别必须保持精确整数。

## 复杂度与实测（含对给定算法设计的偏差说明）

**发现的问题 1 —— 剪枝方向写反**：题目给的剪枝规则原文是"`free_at` 更小、成本更低或相等的状态
支配 `free_at` 更大、成本更高或相等的状态"（sort ascending, keep strictly decreasing cost）。
实测：用交叉验证测试（`part1` vs 按此方向剪枝的 `part2`）在随机小规模输入上会出现真实的数值分歧
（例如 `cost=[13,1,8,16,15,12], time=[2,3,2,4,1,4]`：`part1=22`，按原方向剪枝的 `part2=48`，
剪枝剪掉了本该保留的最优状态）。手推可得**支配方向是反的**：`free_at` 更大（更忙）在未来只会给
你更多选择——它总能"也选择付费"来模拟一个 `free_at` 更小的状态接下来的强制转移，而 `free_at` 更
小的状态可能会被强制付费、丧失选择权。改成"按 `free_at` 降序排序，只保留成本严格低于目前见过的
最小成本"之后，5000 组随机小规模交叉验证（`n<=12`）全部一致，问题解决。这个方向问题已经写进
`problem.md` 的 Part 2 算法段落里，并有专门的注释/测试防止回归。

**发现的问题 2 —— 声称的"frontier 实际很小"不成立，复杂度达不到 n=1e5 的通用预算**：即便剪枝
方向修正后，实测发现 Pareto 前沿大小会随 `n` **近似线性增长**——不仅是对抗性构造，**均匀随机数据
（`random.Random(0)`）本身就会触发这个增长**（例如 `time` 值域仅 `0..5` 时，`n=10000` 的前沿峰值
约 `14933`，接近 `1.5n`）。这使得整个算法是 `O(n · frontier_size)`，经验上接近 `O(n²)`，而不是
题目描述里暗示的"频谱很小、接近线性"。真实测算：

| n | value range | 用时 |
|---|---|---|
| 1200 | cost∈[1,1e6], time∈[0,9] | 0.55s |
| 1500 | 同上 | 0.89s |
| 1800 | 同上 | 1.28s |
| 2500 | cost∈[1,1e3], time∈[0,1000] | 6.3s（更大的 time 值域让前沿增长更快）|

没有找到已知的次二次精确算法能处理这个具体形式化下的最坏情况（也没有在合理时间内找到反例说明存在
更聪明的等价算法）。**因此 perf 测试把 n 定在 1200**（`cost∈[1,1e6], time∈[0,9]`，实测 0.55s，
留了约 3.6× 余量），而不是 CONVENTIONS.md 通用建议的 `1e5-1e6`——这是对通用指引的一个明确、有实测
数据支撑的偏离，写在 `test_q01.py::test_perf_part2` 的注释里。

复杂度总结：Part1 `O(状态数)`（未剪枝，仅供小规模交叉验证）；Part2 `O(n · frontier_size)`，
`frontier_size` 经验上 `~O(n)`，故整体经验复杂度 `~O(n²)`。
