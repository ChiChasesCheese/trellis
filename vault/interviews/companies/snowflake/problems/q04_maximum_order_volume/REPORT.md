# q04 Maximum Order Volume — report

## 摘要
经典加权区间调度（weighted interval scheduling），题面把区间叫作"电话"、权重叫作
"订单量"。核心考点是排序 + 二分找最近不冲突前驱 + DP 转移，以及一个容易被题面文字带偏的
陷阱：`duration=0` 的"零时长电话"必须被特殊处理为"无条件可选"，而不是套用通用的
`end<=start` 判定式。

## 来源与置信度
中等 — 主源 https://www.fastprep.io/problems/phone-calls（题面、函数签名、样例范围）；
标题被 2021 LeetCode 讨论帖（原帖已 404，仅标题可查）与 2023 Canada OA 索引交叉印证。
端点相接、zero-duration 的具体处理规则是本题作者按区间调度的标准数学定义补全的。

## 逐 part 思路
- **Part 1**：先把 `duration==0` 的电话拆出来，其 volume 无条件累加为 `free`；剩下的电话
  按结束时间排序，对每个电话线性向前扫描找最近满足 `end[j] <= start[i]` 的前驱下标
  `pred`，`dp[i] = max(dp[i-1], volume[i] + dp[pred])`；最终答案 `= free + dp[n]`。允许
  `O(n^2)` 最坏复杂度。
- **Part 2**：完全相同的框架，但预处理排序后的 `ends` 数组，对每个电话用
  `bisect_right(ends, start[i], 0, i-1)` 在 `O(log n)` 内查到前驱计数，整体 `O(n log n)`。

## 隐藏测试针对的坑
1. **端点相接不算重叠**：`end==start` 时必须允许两通电话都入选（否则会漏掉一半最优解）。
2. **`duration=0` 的"假重叠"**：如果直接套用 `end<=start` 两两判定式，一个零时长电话若
   落在另一个正常区间"内部"，会被误判为冲突。必须先把它们摘出来无条件计入。
3. **并列开始时间 / 并列结束时间**：排序必须稳定，但由于二分只依赖结束时间的单调性，并列
   不影响正确性——测试里专门构造了并列开始的场景来确认没有因为排序 tie-break 漏解。
4. **大数值下的整数运算**：`start`/`duration` 到 `1e9`，`volume` 到 `1e3`，测试里用
   `10**9` 量级验证没有 float 参与、没有精度丢失。
5. **part1 与 part2 必须给出完全一致的答案**：用随机化交叉验证（`random.Random(0)`，50
   组随机小规模输入）作为除官方样例外的主要正确性防线。

## 复杂度与实测
- Part 1：`O(n^2)` 最坏（线性前驱扫描），仅用于正确性参照，测试中 n 保持很小。
- Part 2：`O(n log n)`（排序 + 二分），perf 测试用 `random.Random(0)` 生成 `n=100,000`
  条电话记录，实测远低于 2s 的预算（本机 <0.3s）。

## 测试清单
共 20 个测试：
- `part1`：10 个（含 1 个 `edge` 覆盖官方样例、全重叠、全不重叠、空输入、单元素、并列开始、
  端点相接、单个/多个零时长电话、大数值）
- `part2`：3 个（官方样例、与 part1 交叉验证的固定 edge shapes、50 轮随机交叉验证）+ 1 个
  `perf`（1e5 条记录，wall time < 2s）
- `io`：3 个（`run_script` 端到端验证 PART 2 主样例、PART 1 dispatch、`n=0` 空场景）
