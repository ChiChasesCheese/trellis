# q06 Patching Array — report

## 摘要
LeetCode 484 原题精确复用，2019 年在 Snowflake 电面中原样出现过（同一场电面还问了
inorder→Morris traversal，见 q07）。核心是标准贪心：维护"当前保证可覆盖区间的上界+1"
(`miss`)，能用真实元素扩展就用，否则打补丁令区间翻倍。`part2` 是本题作者重建的自然追问：
不仅要计数，还要吐出具体打了哪些补丁。

## 来源与置信度
高 — https://leetcode.com/problems/patching-array/ 是原题精确复用；2019 年电面面经帖
（同帖含 q07 的姊妹题）与 2023 Canada OA 索引（直接引用 LeetCode 链接）两个独立来源交叉
印证这道题在 Snowflake 面试/OA 池子里出现过。`part2` 返回值列表是常见追问模式的重建，非
面经逐字给出。

## 逐 part 思路
- **Part 1**：`miss=1, i=0, patches=0`；当 `miss<=n` 时，若 `nums[i]<=miss` 则消费该元素
  `miss+=nums[i]`，否则打补丁 `miss*=2, patches+=1`；循环至 `miss>n`，返回 `patches`。
- **Part 2**：完全相同的循环，唯一差异是打补丁前把当前 `miss` 值 append 进结果列表，再
  翻倍。两者共享同一份贪心逻辑，保证 `len(part2(...)) == part1(...)` 恒成立。

## 隐藏测试针对的坑
1. **`n=0`**：循环条件 `miss<=n` 一开始就是 `1<=0`，恒为假，不论 `nums` 是什么都是
   `0`/`[]`——容易被误写成"先处理一次"的 off-by-one。
2. **空数组 `nums=[]`**：必须完全靠补丁覆盖，验证补丁序列是 `1,2,4,...`（每次翻倍）。
3. **`nums` 中比 `n` 还大的元素永远不被消费**：贪心必须正确"跳过"它们（下标 `i` 永远不
   前进），而不是提前终止或抛异常。
4. **大 `n`（到 `2**31`）要求 `O(log n)`**：暴力枚举 `[1..n]` 逐个检查会直接超时/爆内存；
   正确贪心只需约 `log2(n)` 次循环，测试里专门验证了 `n=2**31-1` 时补丁数恰好是 31 且
   耗时可忽略。
5. **`part1`/`part2` 一致性**：对多组随机输入（含手工构造的关键 case）断言
   `len(part2(nums,n)) == part1(nums,n)`，防止两份实现在重构时悄悄分叉。

## 复杂度与实测
`O(len(nums) + log n)`——贪心每一步要么消费一个真实元素（最多 `len(nums)` 次），要么让
`miss` 翻倍（最多 `log2(n)` 次）。perf 测试用 20 个元素的 `nums` + `n=2**31-1`，实测
远低于 2s 预算（本机 <0.01s，纯粹是循环次数少）。
