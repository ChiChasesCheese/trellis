# od12 · Top K Book Sales — 累计销量榜的懒失效堆

> TrueInterview 同步清单第 47 题 "Top K Book Sales"（LLD，2026-02 报告）。题面付费，预览只给出
> API 形状："`BookSalesTracker()`，`bestSellers(books, counts, k)` 累加销量并即时返回前 k"。这与
> LeetCode 1244 "Design A Leaderboard"（`addScore` 累加、`top(K)`）是同一套机制的变体（这里返回
> 书名而不是分数总和）；除这一最小骨架外，效率要求、退货语义、`rank()` 全部 **(reconstructed)**。

## 背景

一个实时销量榜：每次调用同时提交一批"书名 + 本次销量增量"，先把增量累加进每本书的总销量，再
返回当前总销量最高的 k 本书。真实场景（Snowflake 这类数据平台经常给客户提供的"实时 TopN 聚
合"）要求这个查询在数据量增长后仍然高效，而不是每次都对全部书重新排序。

## API 契约（英文签名）

```python
class BookSalesTracker:
    def best_sellers(self, books: list[str], counts: list[int], k: int) -> list[str]: ...
    def rank(self, book: str) -> int: ...          # Part 3, raises KeyError if book unknown
```

## 规则

### Part 1 — 正确性

- `best_sellers(books, counts, k)`：先把 `counts[i]` 累加进 `books[i]` 的运行总销量（同一次调
  用里出现多次的书名，增量先合并再应用一次），然后返回**当前总销量最高的 k 本书**，排序键是
  **总销量降序，总销量相同按书名升序**。
- `k` 大于已知书籍数时返回全部（按同样排序）；`k <= 0` 返回 `[]`。
- 空的 `books`/`counts`（本次调用不产生任何新增量，只是查询）合法，直接返回当前榜单前 k。

### Part 2 — 高效实现（禁止使用第三方库）**(reconstructed)**

- 场景是"频繁调用"：`best_sellers` 被调用 10 万次量级（大部分只更新 1~2 本书），查询也有 1
  万次量级——如果每次查询都对全部书排序，是 O(calls × distinct_books × log distinct_books)，
  在大数据量下会超时。
- 解法：**懒失效堆**（lazy-invalidation max-heap）——用 `heapq` 维护 `(-total, name)` 的最小堆
  模拟最大堆；每次某本书总销量变化，只管往堆里 `push` 一条新记录，**不去堆里找旧记录删除**
  （`heapq` 不支持高效删除任意元素）。查询时不断 `pop`，用一个 `name -> 当前真实总销量` 的字
  典校验弹出的记录是否仍然有效：总销量对不上就说明这是一条"过期"记录，直接丢弃、永不放回；
  凑够 k 个有效记录后，把这些**校验过的有效记录塞回堆里**（因为后面的查询大概率还需要它们）。
  分摊下来，一条记录从被 push 到最终被判定过期丢弃，最多被"验证"一次，所以 N 次更新 + Q 次查
  询的总代价是 O((N + Q·k)·log N)，不会随书籍数量的增长而退化成对全量排序。
- `rank(book)` 走一条独立的简单路径（对全部书排序找位置），因为效率要求只落在
  `best_sellers` 这条热路径上——面试追问会问"如果 `rank` 也要走懒失效堆呢"（见下方追问）。

### Part 3 — 退货与排名 **(reconstructed)**

- `best_sellers` 的 `counts` 允许出现**负数**，代表"退货"：先把本次调用里同一本书的所有增量
  合并成一个净变化量，**预先校验**——如果任何一本书应用后的总销量会变成负数，**整批调用全部
  拒绝**（`ValueError`，不产生任何副作用，不会出现"一部分书更新了、另一部分没更新"的半成品状
  态），总销量允许降到恰好 0（只有严格小于 0 才拒绝）。
- `rank(book)`：返回 `book` 在当前榜单里的**从 1 开始的名次**（同样按总销量降序、书名升序排序
  后取位置）；`book` 从未在任何 `best_sellers` 调用里出现过 → `KeyError`。

### 命令流

```
BEST <k> <n> <book1> <count1> ... <bookn> <countn>   Part 1/2：更新 n 对 (book, count) 再查询前 k
BEST <k> <n> ...                                     Part 3：count 可以是负数；批量拒绝 → ERROR
RANK <book>                                          Part 3：书名的当前名次，未知书名 → -
```
`BEST` 输出空格分隔的书名列表，为空则输出 `-`；批量因退货被拒绝则输出 `ERROR`（且不产生副作
用）。`RANK` 输出整数或 `-`。

```
BEST 2 1 a 10             → a b        (a 累加到 15，跃升第一；b、c 仍并列 7，b 字母序在前)
```

```
PART 3
BEST 1 1 a 15             → a          (a 总销量 15，独占第一)
BEST 1 1 a -100           → ERROR      (a 只有 15，减 100 会变负数，整批拒绝，a 总量不变)
BEST 1 1 a -15            → a          (ERROR 调用没有副作用，a 仍是 15；这次减 15 后总量变成

                                          然是 a)
RANK a                    → 1

```

## 边界清单

- `k <= 0`：返回 `[]`
- `k` 超过已知书籍总数：返回全部书籍，仍按总销量降序、书名升序排序
- 同一次调用里同一本书出现多次：增量先合并再应用一次（不是分别累加两次触发两次堆 push 那种
  会重复计数的写法——合并后只 push 一条最终记录）
- 总销量并列：按书名字典序升序打平，`rank()` 与 `best_sellers()` 用同一套排序键
- Part 2：懒失效堆里允许存在过期记录，但 `best_sellers` 的返回结果必须永远等于"对全部当前总
  销量重新排序"这一朴素做法的结果——用随机操作序列与朴素实现交叉验证
  （见 `test_od12.py::test_random_cross_check_against_naive_model`）
- Part 3：退货把总销量精确减到 0 允许；减到负数整批拒绝，且**不产生任何副作用**（哪怕批次里
  其它书的净变化是非负的）
- Part 3：`rank()` 对从未见过的书名抛 `KeyError`；命令流里表现为 `-`
- 性能：10 万次 `best_sellers` 更新（多数只更新 1~2 本书）+ 1 万次查询，2 秒预算内完成

## 追问

1. **为什么 `rank()` 不复用懒失效堆？** 因为堆只对"取最高的 k 个"这种部分排序高效，回答"某本特
   定书当前排第几"本质上需要知道它前面还有多少本书，堆结构本身不维护"名次"这个信息——如果
   `rank()` 也要做到 O(log n)，需要换成一棵支持"按值域二分/求秩"的平衡树（如按 (total, name)
   排序的顺序统计树），这是比懒失效堆更重的数据结构，本题只在 `best_sellers` 这条被测出高频调
   用的路径上做这个投入，`rank()` 用简单实现即可，体现"先测哪条路径热、再决定优化哪条"的判断。
2. **懒失效堆的内存会不会无限增长？** 会——每次更新都在堆里留一条新记录，旧记录只有在被弹出
   校验时才会被清理；如果某本书被反复更新但从来没有进入过任何一次查询的候选集，它的历史记录
   会一直堆积在堆里。缓解办法：定期起一个后台任务扫一遍整堆重建（丢弃所有过期记录），或者给
   每本书的堆记录数设置一个上限，超过就强制触发一次全量重建——这是空间/实现复杂度的权衡，面
   试官通常想听到候选人主动提出这一点而不是假装堆会一直很小。
3. **如果退货的批量校验本身需要跨线程原子（多个客户端同时提交批次）怎么办？** 需要把"预校验 +
   应用"这一整段包在一把锁里（或者用乐观并发：先在本地快照上校验，提交时用版本号做 CAS，冲突
   则重试），否则两个并发批次可能各自校验通过（分别看到的都是"减完还是非负"），但两个都应用
   之后总销量却变成了负数——这是"先检查再执行"模式在并发下的经典陷阱（TOCTOU）。
