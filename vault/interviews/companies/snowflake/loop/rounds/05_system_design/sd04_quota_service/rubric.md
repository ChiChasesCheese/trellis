# 评分 rubric（五维，1–4 分/维，满分 20）

> 依据 `loop/LOOP_GUIDE.md` §6 与 `catalog/raw/system_design.md` §1.2。追问汇总原文点名"强一致 vs 最终一致的取舍""本地缓存 + 定期同步 vs 每次打中心服务""多区域全局配额如何不产生单点"——这三条基本决定了第 3 维的满分线。

## 1. Problem framing（需求抽取）

- **1 分**：直接说"加个 Redis 缓存计数器就行"，没有先辨析"强一致"在这道题里具体是什么含义（不能超发）与"高频调用"之间的根本张力；没有问清楚不同业务场景对一致性的容忍度是不是一样的（配额超一点点是否可接受，取决于场景）。
- **4 分**：两句话复述——"多个上游服务需要对同一个租户的资源使用做统一的配额检查与扣减，扣减必须防止并发超发，但检查这个动作本身调用频率极高，且是多区域部署，不能让每次调用都变成一次跨区域强一致操作"；显式说出关键不变量——**扣减操作不能超发**（并发场景下最终消耗量不能超过配额，允许通过"预留少量余量"来换延迟，但不能无原则超发）、**配额是全局的**（跨区域的同一租户共享同一份配额，不是每区域各算各的）；主动提出"配额检查要不要卡在关键路径上"这个设计选择，并确认业务对短暂超发的容忍度（例如"文件上传"场景下超发几个字节是否可接受）。

## 2. API & data model（权重最高）

- **1 分**：只有一个 `checkQuota(user)` 返回 true/false，没有"扣减"这个动作，导致 check 和真正消耗资源之间存在竞态（TOCTOU）；没有设计 `SET quota` 的管理接口。
- **4 分**：给出**原子的"检查并扣减"合一接口**（如 `TryConsume(tenant_id, resource, amount) -> {allowed: bool, remaining}`），而不是分离的 check + consume 两步（分离会有竞态）；给出配额管理接口 `SetQuota(tenant_id, resource, limit)`；数据模型区分**配额定义**（`quotas(tenant_id, resource, limit, period)`）与**用量状态**（`usage(tenant_id, resource, period_window, consumed, version)`，`version` 用于乐观锁的条件更新）；能说清楚扣减的原子性怎么落地——单条 SQL 的条件更新（`UPDATE usage SET consumed = consumed + amount WHERE consumed + amount <= limit`）或者原子的分布式计数器（Redis `INCRBY` + Lua 脚本做条件判断）。

## 3. Failure modes & scale（本题权重也很高）

- **1 分**：说"每次调用都打中心数据库做强一致检查"就结束，没意识到这在高 QPS 下会把中心服务打垮；多区域部分只说"多加几个副本"，没有回答"副本之间怎么保证不超发"；被问"能不能接受一点点超发"答不出取舍。
- **4 分**：讲清**分层限流架构**——真正的强一致扣减发生在一个权威的中心存储（每个 tenant+resource 的配额状态由一个明确的"权威分片"负责，类比给每个 key 固定一个 Raft leader 或分区），但为了不让每次业务调用都打这个中心存储，客户端（上游服务）侧维护一个**本地令牌桶/租借的配额份额**——中心服务定期把总配额的一部分"批发"租借给某个区域/实例（如租借 100 个单位的使用权，本地在这 100 个单位内可以本地扣减不用请求中心），本地额度快用完时提前向中心请求续借；这样把大部分请求的延迟降到本地内存操作，只有"续借"这个低频操作才走跨区域强一致路径；能主动指出这个方案的代价——本地额度在极端情况下可能造成**小幅度超发**（本地额度还没来得及归还，租户就已经把本地和别处加起来超过总配额），需要显式讨论这个折衷对业务是否可接受，对于"绝对不能超发"的场景（如计费类配额），本地额度要设置得足够小并配合较短的续借周期来控制超发上限；讲清多区域场景下，权威状态应该只有一份（或用跨区域强一致的复制协议，如 Raft/Paxos 复制的存储），不能让每个区域各自维护一份独立的用量计数器。

## 4. Separation of concerns

- **1 分**：把"配额定义管理""本地缓存""中心扣减""跨区域同步"全部糅在一个"Quota Service"黑盒里。
- **4 分**：分层清楚——**配额定义管理**（管理员/租户设置 quota 的 CRUD，低频）；**中心权威扣减层**（对每个 tenant+resource 维护强一致的用量状态，是唯一的真相源）；**本地代理/SDK 层**（部署在各上游服务旁边，负责本地额度的租借、快速判断、周期性向中心同步与续借，是延迟优化的关键组件，与中心层通过明确的租借协议交互）；**多区域同步**（中心层本身如果分区部署，各区域的写入需要路由到权威分片，而不是各区域本地各写各的）。

## 5. Delivery beyond the diagram（rollout / 测试 / 监控）

- **1 分**：画完图不谈上线和监控。
- **4 分**：讲到监控指标（各租户的配额使用率、被拒绝请求占比、本地额度续借频率与延迟、任何检测到的超发事件量）；讲到怎么测试并发扣减不超发（并发压测验证扣减的原子性）；讲到 rollout 时新的本地租借策略先在低风险租户上灰度，观察超发容忍度是否符合预期；讲到告警——某个租户使用率接近上限时提前通知业务方而不是等到被拒绝才发现。
