# 模型答案：设计 Quota Service

> 取材：1p3a thread-1137616 一手摘要；staffengprep.com 聚合站细节版；`catalog/raw/system_design.md` §1.2。按 `LOOP_GUIDE.md` §6 主线组织。

## 0. 两句话复述 + 不变量

**复述**：多个上游业务系统需要对同一个租户共享同一份配额做检查与扣减，扣减必须防止并发场景下超发，但这个检查动作调用频率极高，而且系统是多区域部署——不能让每次业务调用都变成一次跨区域强一致操作，也不能让各区域各算各的用量导致全局超发。

**核心不变量**：

1. **不超发**（在业务能接受的范围内）：并发的多次扣减，最终消耗量不能明显超过配额上限。
2. **配额是全局唯一的**：同一个租户跨区域共享同一份配额定义与用量统计，不是"每区域各自 100"。
3. **检查/扣减是原子的**：check 和 consume 必须是一个原子操作，不能分成两步（否则存在 TOCTOU 竞态）。
4. **绝大多数调用走本地快路径**：高频调用不能都打中心强一致存储，否则中心存储会成为吞吐瓶颈和单点延迟来源。

明确"不做什么"：不追求"绝对零超发"——对大多数配额场景（如上传流量），允许极小幅度、有界的超发换取延迟，前提是这个折衷要显式讨论并让业务方确认可接受；对于确实不能超发一分一毫的场景（如计费扣款），需要单独讨论走完全同步的路径，代价是延迟。

## 1. API 契约

```
POST /v1/quotas                      {tenant_id, resource, limit, period}
                                      # 管理接口：设置/更新配额定义

GET  /v1/quotas/:tenant_id/:resource -> {limit, period, consumed, remaining}

POST /v1/quota/consume                {tenant_id, resource, amount}
                                      -> {allowed: bool, remaining}
                                      # 核心接口：原子的"检查并扣减"，不是分离的 check+consume

POST /v1/quota/release                {tenant_id, resource, amount}
                                      # 可选：预留后实际未消耗的量归还（如预留了但上传失败）
```

- `consume` 是唯一的核心接口，语义是"要么这次扣减成功且没有超过 limit，要么失败并告知调用方",拒绝把 check 和 consume 拆成两次调用给上游业务系统，从根源上消灭 TOCTOU 竞态。
- `release` 用于"预留后未实际使用"的场景（比如上传中途失败），把预留的额度还回去，避免因为失败请求导致配额被无谓占用。

## 2. 数据模型

```
quotas(tenant_id, resource, limit, period, updated_at)
-- 配额定义，低频更新，管理员/租户自服务修改

usage(tenant_id, resource, period_window, consumed, version)
-- 用量状态，是这个系统里读写最频繁的数据
-- (tenant_id, resource, period_window) 唯一定位一行
-- version 字段用于乐观锁的条件更新，防止并发扣减互相覆盖

lease(tenant_id, resource, region, borrowed_amount, borrowed_at, expires_at)
-- 本地代理向中心"租借"的一小份额度，记录哪个区域借了多少、什么时候要归还/续借
```

**权威扣减的原子性怎么落地**：中心层对 `usage` 表做条件更新——`UPDATE usage SET consumed = consumed + amount, version = version + 1 WHERE tenant_id=? AND resource=? AND consumed + amount <= limit AND version = expected_version`，更新影响行数为 0 就说明要么超过限额要么被并发修改抢先，重新读取最新状态后决定是否重试或拒绝。如果用 Redis 做中心存储，用 `INCRBY` 配合 Lua 脚本做"读取当前值 + 判断 + 递增"的原子组合，效果等价。

## 3. 核心流程

**分层限流架构（本题的核心设计）**：

1. 中心层维护每个 `(tenant_id, resource)` 的权威用量状态（`usage` 表），是唯一的真相源。
2. 本地代理（部署在每个区域、跟上游业务服务同机房甚至同进程内的 SDK）向中心**批量租借**一小份配额（如"借 100 个单位给这个区域用"），写入 `lease` 表并从中心的 `usage.consumed` 里预先扣掉这 100 个单位（相当于把额度的所有权临时转移给这个区域）。
3. 本地代理收到业务系统的 `consume` 请求后，**在本地内存里对租借到的额度做扣减**（不需要网络往返），只要本地额度够用就直接返回 `allowed=true`，延迟是纯内存操作级别。
4. 本地额度使用到阈值（如剩余 20%）时，本地代理**提前**异步向中心发起续借请求，避免额度耗尽时业务请求被迫同步等待网络往返。
5. 本地额度实在不够且续借还没到账时，本地代理才退化成同步调用中心层做一次真正的强一致扣减（保底路径，牺牲这一次请求的延迟换正确性）。

**多区域下的全局配额**：中心层的 `usage` 表本身必须是全局唯一的权威状态（可以是单一强一致存储集群，或者用类似本题 sd01 KV store 的"每个 key 固定路由到一个分区的 Raft leader"模式，把 `(tenant_id, resource)` 作为 key 路由到确定的权威节点）——**关键是任何一个区域的本地代理最终都要和同一个权威节点对话去借额度**，不能出现"欧洲区域和美洲区域各自维护一份独立的用量计数器"，那样加起来必然超发。

## 4. 失败模式与规模

**本地额度导致的有界超发**：这是本设计最重要的权衡——本地代理拿到的 100 个单位如果最终没有用完就要归还（`release`）或者到期自动释放，但在额度被租借出去、尚未使用完、也还没归还之前，理论上租户的"实际可用总量"短暂地看起来比配额上限更宽松；控制这个超发上限的手段是**控制单次租借的额度大小和续借周期**——批发额度越小、续借越频繁，超发上限越小，但本地快路径的收益（减少打中心的次数）也越小，这是一个需要根据具体资源的"超发代价"来调的旋钮：文件上传流量场景可以容忍租借额度大一点（超发几百 MB 问题不大），计费类场景需要租借额度小到几乎可忽略（甚至干脆不做本地租借，直接走中心强一致路径，用延迟换绝对正确）。

**中心层的可用性**：中心层如果不可用，本地代理的续借请求会失败——策略上应该允许本地代理在中心层短暂不可用时，继续消耗剩余本地额度（宁可短暂超发也不要让所有业务请求全部失败），额度耗尽后再决定是拒绝新请求还是（如果业务允许）临时放宽限制并在中心层恢复后做事后对账修正。

**租户配额被并发多个区域同时申请续借**：多个区域各自向中心发起续借请求时，中心层的扣减仍然要走前面提到的原子条件更新，不会因为并发续借请求导致总租借量超过配额剩余量。

**规模估算**：假设有数千个活跃租户、每租户多种资源类型，`usage` 表的行数是租户数 × 资源类型数量级，写入频率取决于续借频率而不是原始业务请求频率（因为大部分请求走本地快路径）——这正是分层设计的收益所在：把可能是每秒数万次的业务请求，收敛成中心层每秒数百次的续借请求。

## 5. 分层与组件

- **配额定义管理层**：低频的 CRUD，管理员/租户自服务设置 limit。
- **中心权威扣减层**：对每个 tenant+resource 维护强一致用量状态，是租借协议的服务端。
- **本地代理/SDK 层**：部署在上游业务服务旁，负责本地额度管理、快速判断、周期性续借，是这个系统延迟优化的核心，也是复杂度集中的地方。
- **对账/审计层**（可选但建议）：定期核对"中心层记录的总消耗"与"各区域本地额度使用量之和"，发现异常超发时告警，而不是完全信任设计假设永远成立。

## 6. rollout/测试/监控

- **监控**：各租户配额使用率、被拒绝请求占比、本地额度续借的延迟与失败率、检测到的超发事件（金额/数量）。
- **测试**：并发压测验证中心层扣减不超发（多线程同时打同一个 tenant+resource 的 consume）；模拟中心层不可用时本地代理的降级行为是否符合预期。
- **rollout**：新的本地租借策略（额度大小、续借阈值）先在低风险的租户/资源类型上灰度，观察实际超发量是否在预期范围内，再推广到计费敏感的资源类型（或者干脆对这类资源永远不启用本地租借）。

## 7. 用 Snowflake 自己的原语作参照

这道题的核心张力——"高频调用 vs 强一致中心状态"——正是 Snowflake 真实计量体系需要解决的问题：Snowflake 的 credits 按秒计费、Cloud Services 有"仓库消耗 10% 的每日免费额度"这类配额规则（`01-company-brief.md` §2「计量与计费」），这些计量判断显然不可能对每一次内部操作都去问一个全局强一致的中心服务，而是采用类似"批量结算 + 定期对账"的思路。此外，本题"本地代理租借一小份额度、用完再续借"的模式，本质上与 Snowflake **Execution Anchor** 机制里"绑定关系存 FDB、但绝大多数操作不需要每次都去问 FDB"的设计哲学同构——都是"把权威状态集中存放，但通过局部缓存/租借把高频路径的延迟降下来"。面试时可以说："这类似 Snowflake 把 credits 消耗记账做成准实时批量结算而不是每次操作都同步扣费，用一个可控的滞后窗口换取吞吐。"

## 8. 45 分钟口述时间表

- **0–5 min**：复述题目 + 不变量（不超发、全局唯一、原子扣减、快路径为主），确认业务对短暂超发的容忍度。
- **5–12 min**：API 契约（consume 合一接口、release、管理接口）+ 数据模型（quotas/usage/lease）。
- **12–22 min**：核心流程——分层限流架构（中心权威层 + 本地代理租借协议），多区域下的全局唯一权威状态。
- **22–35 min**：失败模式——本地额度导致的有界超发及其控制手段、中心层不可用时的降级、并发续借的原子性、规模估算。
- **35–42 min**：分层图 + rollout（灰度租借策略）+ 监控指标 + 对账层。
- **42–45 min**：总结这是"正确性 vs 延迟"的权衡问题，类比 Snowflake 计量体系，反问面试官。
