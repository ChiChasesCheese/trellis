# 评分 rubric（五维，1–4 分/维，满分 20）

> 依据 `loop/LOOP_GUIDE.md` §6 与 `catalog/raw/system_design.md` §1.4/§1.5。这题的原始一手报告里面试官全程沉默——候选人被动等提示会直接冷场，rubric 里特别看重"主动暴露假设"这一点。

## 1. Problem framing（需求抽取）

- **1 分**：直接画"调度器 → 执行引擎"两个框就开始讲存储，没有先说清楚"分钟级精度"和"1e6 任务规模"这两个数字对设计的含义（意味着不能用一个进程内的定时器/优先队列扛所有任务，必须分片）；说不出"这个系统最核心的保证是什么"。
- **4 分**：开场复述——"这是一个要在分钟级精度下，从百万量级注册任务中找出到点该跑的任务并派发给执行引擎的调度系统，调度器本身多实例部署，任务失败要重试但不能重复执行、不能漏跑"；显式说出不变量——**at-least-once 触发**（漏跑不可接受，重复触发好过漏跑）、**同一次触发不能被两个调度器实例同时执行**（互斥）、**调度器重启后既不全量补跑也不全部丢失**；主动确认 cron 表达式的时区处理、任务执行时长上限、失败重试的最大次数与退避策略。

## 2. API & data model（权重最高）

- **1 分**：只有一张"任务表"，没有区分"任务定义（cron 规则）"和"每次触发的运行记录"；`next_run_at` 怎么算、谁来算没讲清楚；没有设计任务注册/暂停/删除的管理接口。
- **4 分**：给出任务管理 API（`register/pause/resume/delete(job_id, schedule, task_ref)`）与内部数据模型；数据模型区分 **`jobs`（任务定义，含 cron 表达式、`next_run_at`、状态 active/paused）** 与 **`job_runs`（每次触发一行，含 lease 持有者、状态 pending/running/succeeded/failed、重试次数、开始/结束时间）**；`next_run_at` 字段上建索引，调度器扫描的核心查询就是 `WHERE next_run_at <= now() AND status = active`；能说清"谁负责把 cron 表达式换算成下一次触发时间"——注册/每次触发完成后都要重新计算 `next_run_at` 并写回。

## 3. Failure modes & scale（本题权重也很高）

- **1 分**：多实例分工只说"用一致性哈希分一下"就结束，说不清具体怎么防止同一任务被两个实例同时执行；调度器崩溃恢复说"重启后重新读任务表就行"，没有讲清楚"重新读了之后怎么知道该不该补跑"；没有意识到 1e6 任务不能被单个扫描循环线性扫一遍。
- **4 分**：讲清**分片**——按 `job_id` 哈希或范围分片，每个调度器实例只负责一部分分片，分片分配本身用一个协调服务（可以是简单的租约表：`shard_id -> owner_instance, lease_expires_at`）动态管理，实例心跳续租，心跳断了分片被别的实例抢占；讲清**互斥/lease 机制**——调度器实例扫到一个到点的 job 后，先用一次原子的条件更新（`UPDATE ... SET status=claimed, owner=me, lease_expires_at=now()+30s WHERE status=pending AND job_id=X`）抢占这个 `job_run`，抢占成功才真正派发给执行引擎，租约到期还没完成才允许别的实例重新抢占（这是防止重复执行的关键，唯一约束/条件更新是真相源，不是"大家商量好谁来跑"）；讲清**崩溃恢复**——调度器不维护内存态的"下一步该跑什么"，每次都是无状态地查询 `job_runs`/`jobs` 表决定动作，重启后从数据库读到的状态本身就是权威状态，不会因为进程重启而丢失或重复计算；讲清**失败隔离**——单个任务反复失败（如连续失败 N 次）应该自动暂停（类比 `SUSPEND_TASK_AFTER_NUM_FAILURES`），不能让一个坏任务的重试风暴拖累调度器扫描其他健康任务的吞吐。

## 4. Separation of concerns

- **1 分**：把"算下一次触发时间""抢占任务""真正执行 SQL""重试退避"全部塞进一个"调度器"大循环里。
- **4 分**：分层清楚——**扫描/触发层**（无状态，定期扫描到点任务，负责 lease 抢占）；**执行层**（真正调用执行引擎跑 SQL 的 worker，与扫描层解耦，可以独立扩容）；**调度计算**（cron 表达式 → next_run_at 的纯函数，注册时和每次运行完成后调用，不掺杂在扫描循环里）；**分片协调**（谁负责哪些 job_id，独立的租约表，扫描层只需要查"我负责的分片里有没有到点的"）。

## 5. Delivery beyond the diagram（rollout / 测试 / 监控）

- **1 分**：画完图不谈上线和监控。
- **4 分**：讲到监控指标（调度延迟——`实际触发时间 - next_run_at` 的分布、失败率、分片再平衡频率、单实例负载）；讲到怎么测试调度精度（把时钟往前拨的集成测试，验证分钟级误差在可接受范围）；讲到 rollout 时新调度算法先跑影子模式（只记录判定不真正触发）对比新旧行为；讲到告警——某个分片长期无人认领（所有实例都挂了）要能被发现。
