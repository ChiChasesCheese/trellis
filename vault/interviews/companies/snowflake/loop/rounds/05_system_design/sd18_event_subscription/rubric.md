# 评分 rubric（五维，1–4 分/维）

## 1. Problem framing
- **1 分**："用 Kafka 发消息"，不区分匹配与投递，不谈重复与隔离。
- **4 分**：拆成三段——**摄取**（1M/s 事件）→ **匹配**（事件 × 1000 万订阅）→ **投递**（多渠道、外部不可靠）；不变量：同事件同订阅对"不可重复渠道"（邮件、站内）恰好一次、对 webhook 至少一次并带去重键；租户隔离（慢客户不拖累别人）；订阅变更 ≤ 1 分钟生效；明确估算：匹配是 CPU 瓶颈、投递是 I/O 与外部依赖瓶颈。

## 2. API & data model
- **1 分**：订阅是一张表，事件来了全表扫描。
- **4 分**：`POST /subscriptions {account, event_type, filter, channel, target, throttle}`；事件 `{event_id, account, type, ts, attributes}`；订阅索引按 `(account, event_type)` 分组——绝大多数过滤条件都带账号与类型，先用它们把候选从 1000 万缩到几十条，再逐条求值 filter 表达式；投递记录 `(event_id, subscription_id) → state` 作为去重键。

## 3. Failure modes & scale
- **1 分**：投递失败无限重试，或者直接丢弃。
- **4 分**：事件日志按 `account` 分区保证同账号有序、并行扩展；匹配服务无状态、订阅索引本地缓存 + 变更流增量更新（≤ 1 分钟）；投递按**渠道 × 目标**分独立队列，慢 webhook 只堵自己的队列（隔离舱）；重试指数退避，超过上限进死信队列并通知用户；每目标限流与熔断；邮件先写去重记录再发（发送前检查），webhook 带 `event_id` 让对端去重；热点账号（单账号每秒几万事件）按 `(account, 子键)` 再拆分区；突发事件风暴时做合并（digest：同订阅 1 分钟内多条合成一封邮件）。

## 4. Separation of concerns
- **1 分**：一个服务既收事件又匹配又发邮件。
- **4 分**：事件网关（校验、打 `event_id`）→ 事件日志（分区）→ 匹配服务（订阅索引、filter 求值、产出投递任务）→ 投递调度（按目标分队列、限流、重试、死信）→ 渠道适配器（webhook / 邮件 / 站内 / 客户队列）；订阅服务（CRUD + 变更流）独立。

## 5. Delivery beyond the diagram
- **1 分**：没提验证与监控。
- **4 分**：端到端合成事件探针测投递延迟；指标：匹配延迟、每渠道投递延迟与成功率、死信量、每租户队列积压；订阅 filter 语法做沙箱与复杂度上限（防止一条订阅拖垮匹配）；新渠道先影子投递再切流。
