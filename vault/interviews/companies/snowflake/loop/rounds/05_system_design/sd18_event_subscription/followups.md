# 追问预案（8 条，全部（推断））

## 1. 1000 万订阅，每个事件怎么不全扫？
**期望要点**：按 `(account, event_type)` 建索引取候选；filter 是受限表达式；更进一步可对常见谓词建倒排（如 `database = PROD`）。
**反例**：每个事件遍历全部订阅。

## 2. 邮件怎么做到恰好一次？
**期望要点**：外部发送本身无法原子化；在发送前用 `(event_id, subscription_id)` 做条件写入占位，崩溃窗口里宁可少发也不多发，并对"占位但未确认"的记录做人工 / 延迟对账。
**反例**："Kafka exactly-once 就行"（消息系统的恰好一次管不到外部邮件）。

## 3. 一个大客户的 webhook 挂了一小时会怎样？
**期望要点**：按目标独立队列只积压它；熔断减少无效尝试；积压上限后暂停并通知；恢复后按顺序补发或跳过过期事件（订阅可配置）。
**反例**：共享队列，全部客户都被拖慢。

## 4. 用户改了订阅，一分钟内怎么保证生效？
**期望要点**：变更流推送到匹配服务增量更新 + 周期版本号校验兜底；变更对"正在匹配中的事件"是否生效要定义清楚（以事件处理时刻的版本为准）。
**反例**：匹配服务每小时重载一次全量。

## 5. 同账号事件要有序吗？代价是什么？
**期望要点**：按账号分区天然有序；热点账号会过热，需要按子键再拆，只保证子键内有序；多数通知场景只需"不乱到反直觉"。
**反例**：全局有序。

## 6. 突然出现事件风暴，比如某客户一分钟失败十万次查询？
**期望要点**：订阅级限流 + digest 合并；渠道级全局令牌桶；告警类高优先级不被信息类挤掉。
**反例**：十万封邮件。

## 7. 用户写了一个极其复杂的 filter？
**期望要点**：表达式白名单、深度与大小上限、求值时间预算、超限的订阅被隔离到慢路径并告知用户。
**反例**：允许任意脚本。

## 8. 推模式和 Snowflake Alerts 的拉模式怎么选？
**期望要点**：推模式延迟低、适合离散事件；拉模式适合"聚合条件"（过去一小时失败率 > 5%）且不需要事件管道；两者可组合：拉模式的结果作为事件进入推模式投递。
**反例**：只说一种。
