# 模型答案：事件订阅与通知系统

## 0. 复述 + 估算 + 不变量

**复述**：1M events/s 进来，与 1000 万条订阅匹配，匹配上的通过 webhook / 邮件 / 站内 / 客户队列在几秒内送达；邮件与站内不可重复，webhook 至少一次；慢客户不能拖累别人；订阅变更 ≤ 1 分钟生效。

**估算**：事件 1 KB → 1 GB/s ≈ 86 TB/天原始量，日志保留 3 天。假设 1% 事件命中至少一个订阅 → 投递任务约 1 万/s，但分布极不均匀（大账号、事件风暴）。匹配是每秒百万次的 CPU 活；投递是每秒万级的外部 I/O。

**不变量**：邮件 / 站内对 `(event_id, subscription_id)` 恰好一次；webhook 至少一次并带 `event_id`；同账号事件有序处理；一个目标的故障只影响该目标。

## 1. API 与数据模型

```
POST   /v1/subscriptions  {account, event_type, filter, channel, target, throttle}
DELETE /v1/subscriptions/{id}
事件：{event_id, account, type, ts, attributes{...}}
投递记录：(event_id, subscription_id) → {state, attempts, last_error}
```

订阅索引：`(account, event_type) → [subscription…]`。每个事件先用这两个字段取候选（通常几十条），再求值 filter（受限表达式：比较、与或、IN，禁止任意代码）。

## 2. 核心流程

1. **事件网关**：校验、分配 `event_id`、写入按 `account` 分区的事件日志。
2. **匹配服务**（无状态，按分区消费）：本地缓存订阅索引 → 取候选 → 求值 filter → 为每个命中产出投递任务 `(event_id, subscription_id, channel, target)`，写入投递日志；提交消费位点。崩溃后从位点重放，产生的重复投递任务由下游去重键吸收。
3. **订阅变更**：订阅服务写库并发变更事件；匹配服务订阅变更流增量更新缓存；每分钟全量校验一次版本号，保证 ≤ 1 分钟收敛。
4. **投递调度**：按 `(channel, target)` 路由到独立队列；每队列独立限流、熔断、重试（指数退避 + 抖动，最多 24 小时）；超过上限进死信并给用户站内告警。
5. **渠道适配器**：
   - 邮件 / 站内：先条件写入投递记录 `state=SENDING`（已存在则跳过），发送，再标 `SENT`——去重在发送前。
   - webhook：带 `X-Event-Id` 与签名，2xx 视为成功；对端自行去重。
   - 客户消息队列：用云队列的去重 ID。

## 3. 失败模式

| 问题 | 处理 |
|---|---|
| 某客户 webhook 慢或挂 | 按目标独立队列 + 熔断，只积压自己；积压超阈值暂停并通知 |
| 匹配服务崩溃重放 | 投递任务重复 → 去重键吸收 |
| 事件风暴（同订阅一分钟上万条） | 订阅级 throttle + digest 合并 |
| 热点账号单分区过热 | 按 `(account, hash(子键))` 拆分区，放弃该账号的全序、保留子键内有序 |
| 恶意 / 超复杂 filter | 表达式白名单 + 复杂度上限 + 每订阅求值耗时预算 |
| 订阅缓存与库不一致 | 变更流 + 周期版本校验 |
| 邮件服务商限流 | 渠道级全局令牌桶，优先级：告警类 > 信息类 |

## 4. 分层

```
事件源 → 事件网关 → 事件日志(按 account 分区)
                        ↓
                   匹配服务 ← 订阅索引缓存 ← 订阅服务(CRUD + 变更流)
                        ↓
                   投递日志 → 投递调度(按 channel×target 分队列：限流/熔断/重试/死信)
                                  ↓
                   webhook / 邮件 / 站内 / 客户队列 适配器
```

## 5. 测试与监控

合成探针账号每分钟发一条测试事件，端到端测"事件 → 送达"延迟；指标：匹配 p99、每渠道成功率与延迟、每租户队列积压、死信量、filter 求值耗时分布；新渠道先影子投递对比再切流。

## 6. Snowflake 参照

Snowflake 的 Alerts（周期执行条件查询、满足则动作）+ Notification Integration（邮件 / webhook / SNS / Event Grid / Pub/Sub）就是"订阅规则 + 多渠道投递"；resource monitor 的 credit 阈值通知是本题里"账单超过 80%"的原型。面试里可以对比：Alerts 是**拉模式**（定时查询），本题是**推模式**（事件驱动匹配），各自适合什么。
