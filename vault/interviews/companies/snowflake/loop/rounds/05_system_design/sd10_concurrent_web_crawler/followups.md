# 追问预案（≥8 条）

> 该题没有一手候选人报告留下追问逐字稿（`catalog/raw/system_design.md` §1.13 标注置信度 LOW-MED），以下均为基于经典分布式爬虫设计的高概率追问，不标(一手)。

## 1. 用 HashSet 存储所有见过的 URL 做去重，规模涨到百亿级会有什么问题？怎么解决？

**期望要点**：HashSet 存完整 URL 字符串的内存开销是 O(URL 数量 × 平均长度)，百亿级规模下会达到 TB 级别，单机内存根本装不下；解决方案是用 Bloom Filter 做近似判重，内存开销降到位级别（O(URL 数量) 量级的固定 bit 数），代价是接受一个可控的假阳性率（极少数没抓过的 URL 被误判为抓过而漏抓），这是一个需要主动提出并证明理解的空间/召回率权衡。

**反例**：说"把 HashSet 存到磁盘/数据库里就行"——只是把内存问题转移成了 I/O 延迟问题，每次判重都要一次磁盘/网络往返，会显著拖慢整个抓取吞吐，没有从根本上解决"结构本身该怎么设计"这个问题。

## 2. Bloom Filter 会有假阳性（误判为见过导致漏抓），业务上能接受吗？有没有办法降低影响？

**期望要点**：假阳性率是一个可以通过位数组大小、哈希函数个数调节的设计参数，工程实践里通常控制在很小的比例（如 0.1% 量级）；对绝大多数爬虫场景（追求覆盖率但不要求 100% 完整），这个损失是可接受的工程妥协；如果某类关键种子 URL 要求绝对不能漏抓，可以对这部分 URL 单独维护一个精确的小规模 Set 兜底。

**反例**：认为"假阳性完全不可接受，必须用精确结构"——这样就回到了问题 1 的内存爆炸困境，说明没有理解"近似结构换取数量级效率提升"是分布式系统设计里的常见且合理的权衡，而不是不能接受的缺陷。

## 3. 怎么保证对同一个域名不会发起过于密集的请求，即使这个域名的链接在多台不同的抓取机器上同时被发现？

**期望要点**：把同一个域名的节流状态（最近抓取时间/令牌桶）固定路由到某一台节点/分区（按域名做一致性哈希），所有发现了该域名 URL 的机器，在真正发起抓取前都要先向这个固定的权威节点申请节流令牌，而不是各自在本地维护一份独立的节流状态。

**反例**：说"每台机器自己维护一份节流状态，各自控制自己的请求速率"——如果 10 台机器都独立限制自己"对这个域名每秒最多 1 个请求"，对方域名实际收到的总请求速率是 10 倍于预期的，完全没有达到"礼貌性是全局约束"的要求。

## 4. 系统怎么水平扩展，加机器的时候会不会打乱已有的去重/节流状态？

**期望要点**：用一致性哈希对 URL（去重）和域名（节流）分别分片，加减节点时只需要重新分配环上邻近的一小部分分片范围，不需要全量重新哈希；再平衡期间需要处理数据迁移的过渡状态（比如新节点接管某个分片前，判重请求继续路由到旧节点，数据迁移完成后原子切换路由），避免中间态下出现"同一个 URL 短暂地被两个节点各自判重"的问题。

**反例**：说"加机器后把所有 URL 重新哈希一遍分配到新的机器数量上"——简单取模哈希（而不是一致性哈希）在节点数量变化时会导致几乎所有 URL 的归属都发生变化，需要大规模的数据迁移，代价远高于一致性哈希的增量再平衡。

## 5. 如果一个页面存在无限重定向链（A 重定向到 B，B 又重定向回 A），爬虫会不会陷入死循环？

**期望要点**：`Fetcher` 需要对单次抓取设置最大重定向跳数上限，超过上限直接判定该 URL 抓取失败并放弃，不做无限跟随；同时重定向目标本身也要走一遍去重判断（避免同一个重定向环里的 URL 被反复当作"新发现"重新入队）。

**反例**：完全没有考虑重定向的边界情况，假设每个 URL 只需要一次简单的 HTTP GET 就能拿到最终内容——这在真实网络环境下是不现实的简化假设，面试官很可能主动引导到这类边界条件。

## 6. 怎么优先抓取"重要"的页面（比如站点首页），而不是简单按发现顺序 BFS？

**期望要点**：Frontier 的调度不必是纯 FIFO，可以引入优先级（比如基于 URL 深度——离种子越近优先级越高，或者基于外部信号如反向链接数量的估计）；调度层从多个域名的子队列里选任务时，域名内部也可以按优先级排序而不是简单先进先出，这是一个开放的策略问题，可以和面试官讨论具体的优先级信号来源。

**反例**：坚持"必须严格按发现顺序抓取，不能有优先级"——没有回应"重要页面优先"这个常见的业务诉求，也没有意识到 Frontier 的调度策略是一个独立于去重/节流机制、可以单独优化的维度。

## 7. 如果某个域名的服务器返回大量 429（Too Many Requests）或者临时不可达，爬虫应该怎么反应？

**期望要点**：应该把 429/503 这类信号当作"当前节流预算设置过于宽松"的反馈，动态收紧该域名的节流参数（类似指数退避）；持续不可达的域名应该降低其在 Frontier 里的调度优先级或者暂时挂起一段时间再重试，而不是持续以固定速率反复尝试拖累整体吞吐。

**反例**：忽略对方返回的限流/错误信号，继续按原定节流参数机械地重试——这既没有真正做到"礼貌"（对方已经明确表示压力过大），也浪费了爬虫自身的抓取资源在大概率会失败的请求上。

## 8. 抓取到的页面内容要怎么存储和后续处理，这部分和爬虫本身的调度是什么关系？

**期望要点**：抓取和解析产出的页面内容应该异步写入独立的存储/下游管道（对象存储 + 索引服务），与 Frontier/去重/节流这套调度机制解耦——爬虫本身只关心"抓到了、发现了新链接"，不应该等待下游索引/处理完成才能继续调度下一个任务，否则下游处理的延迟会直接拖慢整体抓取吞吐。

**反例**：把"抓取网页"和"建索引"耦合在同一个同步流程里（抓完必须等索引写完才能继续）——这违反了关注点分离原则，也会让下游处理系统的任何抖动直接传导成爬虫吞吐的下降。
