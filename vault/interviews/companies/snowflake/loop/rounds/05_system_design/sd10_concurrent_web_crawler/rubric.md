# 评分 rubric（五维，1–4 分/维，满分 20）

> 依据 `loop/LOOP_GUIDE.md` §6 与 `catalog/raw/system_design.md` §1.13。这是经典分布式系统设计题，证据薄弱（无一手追问记录），rubric 按行业标准的"BFS 抓取 + 去重 + 礼貌性 + 分片扩展"四要素来定，重点考察候选人能否把"单机 BFS 爬虫"里几个隐含的简化假设，逐一替换成分布式环境下站得住脚的机制。

## 1. Problem framing（需求抽取）

- **1 分**：直接说"起一堆线程去抓网页就行"，没有意识到"去重""礼貌性""水平扩展"三者在单机场景下都很好实现（一个 HashSet、一个全局限流器），但放到多机场景下都需要重新设计。
- **4 分**：两句话复述——"要构建一个能高并发抓取网页、持续发现并入队新链接的爬虫，要防止对同一域名的请求过于密集，要在见过的 URL 总量增长到百亿级时依然高效去重，且整个系统要能水平扩展到多机"；显式说出不变量——**去重是全局的**（多台抓取机器之间不能各自独立判断"这个 URL 我没见过"导致重复抓取）、**礼貌性是按域名维度的**（不是全局限流，是每个域名各自有自己的节流预算）、**去重结构的内存占用有界**（不能随见过的 URL 数量无限增长而线性增长到不可接受）；主动确认抓取范围（是否要遵守 robots.txt、是否有深度/规模上限）。

## 2. API & data model（权重最高）

- **1 分**：只有一个"待抓取队列"和一个"已抓取集合"两个数据结构，没有考虑按域名分片的路由设计；没有区分"URL 去重的判断"和"URL 真正被调度抓取"两个独立的关注点。
- **4 分**：给出清晰的组件接口——`Frontier`（待抓取 URL 的调度队列，按域名分区）、`SeenSet`（判断某 URL 是否已经处理过，用于去重）、`Fetcher`（真正发起 HTTP 请求，受 per-domain 节流约束）、`Extractor`（解析页面提取新链接，产出候选 URL 交回 Frontier）；数据模型上明确 URL 在进入系统时先经过 SeenSet 的判重（用 Bloom Filter 做内存高效的近似判重——允许极小概率的假阳性即"误判为已见过而漏抓"，但换来内存占用从 O(URL 数量 × URL 平均长度) 降到 O(URL 数量) 量级的常数级 bit）；只有判重通过（大概率是新 URL）的才真正被路由进对应域名的 Frontier 分区排队。

## 3. Failure modes & scale（本题权重也很高）

- **1 分**：去重用一个全局 HashSet 存储所有见过的完整 URL 字符串，没有意识到百亿级 URL 下这个结构本身就装不下（内存爆炸）；礼貌性用一个全局的固定延迟（"每次请求间隔 1 秒"），没有考虑到这样对高并发的多域名场景吞吐太低（不该在域名 A 上等待的时候连域名 B 都不能抓）；水平扩展说"多起几台机器就行"，没有回答"多台机器怎么协调同一份去重状态和同一套礼貌性预算"。
- **4 分**：**去重**——用 **Bloom Filter** 做内存高效的近似判重，接受极小概率的假阳性（代价是极少数应该抓取的新 URL 被误判为"已见过"而漏抓，这是用完整性换内存的合理妥协，需要显式说明这个权衡）；Bloom Filter 本身如果单机装不下，可以按 URL 哈希做**分片**，每个分片各自维护一部分 URL 空间的过滤器。**礼貌性**——per-domain 的独立节流（每个域名一个令牌桶或者最小请求间隔），域名之间互不影响，域名 A 在冷却期不应该阻塞对域名 B 的抓取；进一步要考虑 robots.txt 里域名自己声明的抓取延迟（`Crawl-delay`）与并发限制。**多机协调**——把整个 URL 空间按域名（而不是随机）做**一致性哈希分片**，同一个域名的所有 URL 固定路由到同一台抓取节点/分区（这样这台节点内部维护的"这个域名的最近抓取时间"状态天然就是权威的，不需要跨机器同步礼貌性状态）；SeenSet 的 Bloom Filter 分片同样按 URL 哈希路由到固定节点，保证同一个 URL 的判重请求总是打到同一个持有权威判重状态的节点。**规模扩展**——节点增减时需要重新分片（一致性哈希的增量再平衡），要讨论再平衡期间新旧分片如何过渡而不丢失/重复判重状态。

## 4. Separation of concerns

- **1 分**：把"URL 去重""域名节流""抓取""解析提取新链接"全部糅在一个"爬虫 worker"循环里。
- **4 分**：分层清楚——**Frontier 调度层**（按域名分区管理待抓取队列，决定"现在轮到哪个域名的哪个 URL"）；**去重层**（Bloom Filter 分片服务，独立于调度逻辑，只回答"这个 URL 见过没有"）；**节流层**（per-domain 的令牌桶/最小间隔状态，与调度层配合决定一个域名的下一次抓取何时被允许）；**抓取/解析层**（无状态的 worker，负责真正发 HTTP 请求和解析 HTML 提取链接，产出的新链接回流到去重层判重后再进 Frontier）。

## 5. Delivery beyond the diagram（rollout / 测试 / 监控）

- **1 分**：画完图不谈测试和监控。
- **4 分**：讲到监控指标（各域名的抓取速率是否符合节流预算、Bloom Filter 的假阳性率是否在预期范围、Frontier 各分区的积压深度、抓取失败率/超时率）；讲到怎么测试——验证同一个 URL 通过不同路径被发现时只会被抓取一次（Bloom Filter 假阳性率在测试环境下用小规模精确 Set 做对拍验证）；讲到 rollout 时新的分片/节流策略先在小范围域名上灰度观察是否触发对方反爬限制；讲到需要处理的边界——死链接、重定向链、抓取超时的重试与放弃策略。
