# 模型答案：设计 Concurrent Web Crawler

> 取材：PracHub "Design a Concurrent Web Crawler"；`../../raw/process_research.md` §3.2 #11；`catalog/raw/system_design.md` §1.13。按 `LOOP_GUIDE.md` §6 主线组织。该题证据薄弱，按行业标准分布式爬虫设计打法组织。

## 0. 两句话复述 + 不变量

**复述**：要构建一个从种子 URL 出发、持续发现并抓取新页面的高并发爬虫，要在高吞吐的同时对每个域名保持"礼貌"（不能短时间内密集打同一个域名），要在见过的 URL 总量增长到百亿级时依然高效去重，并且整个系统要能水平扩展到多台机器上抓取。

**核心不变量**：

1. **同一个 URL 不重复抓取**（在可接受的误判概率范围内）：去重是全局的，不能因为多机各自独立判断而导致重复。
2. **礼貌性是按域名维度的**：一个域名的节流状态与另一个域名完全独立，不能互相拖累。
3. **去重结构的内存占用有界**：不能随着见过的 URL 数量线性无限增长。
4. **水平扩展不破坏前两条不变量**：加机器时去重和礼貌性状态要能正确地重新分布，不产生"某台新机器不知道这个 URL 之前已经被抓过"的问题。

明确"不做什么"：不追求 100% 精确的去重（用 Bloom Filter 接受极小概率的假阳性换取内存效率是一个显式的、值得主动提出的权衡）；不承诺抓取"完整"的互联网（种子集合和抓取深度/规模有边界，需要跟面试官确认范围）。

## 1. API 契约

```
Frontier.Enqueue(url, discovered_from, depth)     # 候选 URL 提交给调度层
Frontier.Dequeue(domain?) -> {url, depth}         # worker 拉取下一个允许抓取的 URL

SeenSet.CheckAndMark(url) -> bool                 # 原子的"判重并标记为已见过"，Bloom Filter 实现

DomainThrottle.TryAcquire(domain) -> bool         # per-domain 节流令牌，不满足则该域名暂不可抓
```

- `SeenSet.CheckAndMark` 设计成原子的"检查并标记"（而不是分离的两步），避免并发场景下同一个 URL 被两个 worker 同时判断为"没见过"而重复入队。

## 2. 数据模型

```
Frontier（按域名分区的优先队列/多队列结构）:
  每个域名一个逻辑子队列，调度器在多个域名之间做公平轮询
  队列项: (url, depth, discovered_at)

SeenSet（分布式 Bloom Filter，按 URL 哈希分片）:
  每个分片是一个 bit 数组 + 若干哈希函数
  只回答"可能见过"/"一定没见过"，接受极小假阳性率

DomainThrottle（per-domain 节流状态）:
  domain -> {last_fetch_at, min_interval 或 token_bucket_state, robots_crawl_delay}
```

**为什么用 Bloom Filter 而不是精确的 HashSet 存完整 URL**：百亿级 URL 如果用 HashSet 存完整字符串，内存开销是 O(URL 数量 × 平均 URL 长度)，轻松达到 TB 级别；Bloom Filter 只需要 O(URL 数量) 量级的固定 bit 数（每个元素几个 bit），代价是有一个可控的假阳性率（比如设计成 0.1%）——极少数真正没抓过的 URL 会被误判为"已抓过"而漏抓，这是一个需要主动向面试官提出并证明理解的工程权衡：为了把内存开销从字节级降到位级，接受万分之一量级的召回率损失。

## 3. 核心流程

**发现与去重**：`Fetcher`/`Extractor` 从页面里解析出新链接后，调用 `SeenSet.CheckAndMark(url)`；返回"没见过"（或者说"至少目前没有被判定为见过"）的 URL 才会被路由进 `Frontier`；`CheckAndMark` 内部对每个哈希函数计算出的 bit 位做原子的"读取全部为 1 则判重命中，否则全部置 1"操作，保证并发调用下不会有两个 worker 都认为某个新 URL 是"没见过"。

**礼貌抓取**：调度器从 `Frontier` 取任务时，先调用 `DomainThrottle.TryAcquire(domain)` 检查该域名当前是否还有抓取配额（基于该域名声明的 `robots.txt` `Crawl-delay` 或者系统默认的最小间隔计算令牌桶状态）；没有配额就跳过这个域名的任务，改为处理其他域名的任务（域名之间互不阻塞），有配额的任务才真正交给 `Fetcher` 发起 HTTP 请求。

**抓取与解析**：`Fetcher` 发起请求（遵守超时、重定向次数上限等边界约束）拿到页面内容后交给 `Extractor` 解析出所有链接，规范化 URL（去掉锚点片段、统一大小写域名部分等，减少"同一资源不同表示形式"造成的重复判重失败），提交回"发现与去重"流程。

## 4. 失败模式与规模

**Bloom Filter 分片与多机协调**：整个 URL 空间按哈希做**一致性哈希分片**，同一个 URL 总是路由到同一个分片节点做判重——这保证了多台抓取机器发现同一个 URL（来自不同页面的链接）时，都会打到同一个权威的判重分片，不会出现"机器 A 判定没见过、机器 B 也判定没见过、两边各自抓了一次"的重复。域名的节流状态同理，**按域名（不是随机哈希）做一致性哈希分片**，同一个域名的所有抓取请求固定路由到同一个节点/分区处理，这台节点内部维护的"这个域名最近一次抓取时间"天然就是唯一权威状态，不需要跨机器同步（这是从"全局互斥"问题转化为"局部权威"问题的关键设计决策）。

**节点增减时的再平衡**：一致性哈希的标准优势——增删节点时只需要重新分配环上邻近的一小部分分片，不需要全量重新哈希所有 URL/域名；再平衡期间要考虑短暂的过渡状态（新节点还没接管完整的判重数据前，暂时允许该分片范围内的判重请求走到旧节点，等数据迁移完成后原子切换路由，避免中间态下出现重复判重放行）。

**Bloom Filter 假阳性率的调优**：假阳性率与位数组大小、哈希函数个数、预期存储的元素总量三者相关；随着实际抓取规模增长，需要监控实际假阳性率是否偏离设计目标（超出预期通常意味着位数组容量不足，需要扩容或做分片再哈希）。

**域名节流的进一步细化**：除了简单的最小间隔，还要考虑并发连接数上限（同一域名同时只允许若干个飞行中的请求，避免瞬间并发多个请求即使间隔够长也造成对方服务器的瞬时压力）；对声明了明确 `Crawl-delay` 的域名，节流参数应该以对方声明为准（更保守）而不是用系统默认值覆盖。

**规模估算**：假设整体抓取吞吐目标是每秒数千到数万个页面，Bloom Filter 总位数按预期 URL 总量（百亿级）乘以每元素几个 bit 估算，大概是可以接受的内存量级（远小于精确存储完整 URL 字符串）；Frontier 各域名子队列的深度需要监控，防止某些域名的链接发现速度远超其节流允许的抓取速度导致该域名队列无限堆积（可以对单个域名的排队上限做截断，超过部分丢弃或降低优先级）。

## 5. 分层与组件

- **Frontier 调度层**：按域名分区管理待抓取队列，决定调度顺序（跨域名的公平性、深度优先还是广度优先的策略）。
- **去重层**：Bloom Filter 分片服务，只回答"这个 URL 见过没有"，与调度逻辑完全解耦。
- **节流层**：per-domain 的令牌桶/最小间隔状态，独立维护每个域名自己的礼貌性预算。
- **抓取/解析层**：无状态 worker，只关心"发请求、解析页面、产出候选链接"，具体调度到哪个域名、这个 URL 有没有见过都不由它决定。

## 6. rollout/测试/监控

- **监控**：各域名实际抓取速率是否符合节流配置（避免真的触发对方反爬限制）；Bloom Filter 实际假阳性率是否偏离设计目标；Frontier 各分区的积压深度；抓取失败率/超时率、重定向链过长的异常页面占比。
- **测试**：在小规模测试环境下用一个精确的 HashSet 与生产的 Bloom Filter 做对拍，验证实际假阳性率符合预期；模拟节点增减触发一致性哈希再平衡，验证再平衡过程中没有出现同一 URL 被重复抓取或某个域名节流状态被意外重置。
- **rollout**：新的分片/节流参数调整先在小范围、低风险的域名子集上灰度，观察是否意外触发对方站点的反爬机制（如返回大量 429/403），确认稳定后再推广到全量域名。

## 7. 用 Snowflake 自己的原语作参照

本题"按域名做一致性哈希分片、把跨机器的礼貌性协调问题转化为单节点内的局部权威状态"这个设计模式，与 Snowflake 的 **Execution Anchor**（`01-company-brief.md` §1）——每个查询绑定恰好一个 GS 实例，绑定信息集中存在 FoundationDB，~99% 的查询终生不需要跨节点转移——是同一类工程哲学：**与其为一个资源（这里是"域名的节流状态"，那里是"一次查询的执行上下文"）做昂贵的跨节点分布式协调，不如把这个资源固定路由到一个确定的权威节点，让局部状态天然保持一致**。另外，本题去重结构选用 Bloom Filter 接受极小假阳性率换取常数级内存开销，这种"用可控的近似换取数量级的效率提升"的思路，也与 Snowflake **Streams** 用轻量的 offset 书签（而不是保留完整的历史副本）追踪表的变更位置类似——都是刻意选择一个更省资源的近似/摘要结构，而不是追求绝对精确但代价高昂的完整存储。面试时可以说："域名分片路由到固定节点这个设计，和 Snowflake Execution Anchor 把查询绑定到单一权威执行者、避免昂贵跨节点协调的思路是一致的。"

## 8. 45 分钟口述时间表

- **0–5 min**：复述题目 + 不变量（全局去重、按域名礼貌、去重内存有界、扩展不破坏前两条），确认抓取范围与深度上限。
- **5–12 min**：API 契约（Frontier/SeenSet/DomainThrottle）+ 数据模型（Bloom Filter 分片、per-domain 节流状态）。
- **12–22 min**：核心流程——发现去重的原子 CheckAndMark、礼貌抓取的令牌获取、抓取解析产出新候选。
- **22–35 min**：失败模式——一致性哈希分片解决多机去重与节流协调、再平衡的过渡处理、假阳性率调优、规模估算。
- **35–42 min**：分层图 + rollout（灰度节流参数）+ 监控指标。
- **42–45 min**：总结 + 类比 Snowflake Execution Anchor 的局部权威模式，反问面试官。
