# 模型答案：设计分布式限流器（per-second、多规则叠加）

> 取材：FastPrep 滑窗限流器题面（标注 Snowflake Onsite）；staffengprep.com 分布式版；`../../raw/process_research.md` §3.2 #13；`catalog/raw/system_design.md` §1.12。按 `LOOP_GUIDE.md` §6 主线组织。

## 0. 两句话复述 + 不变量

**复述**：要在一个多节点组成的限流集群上，对多条可能同时生效的规则（如"每个 API key 每秒 100 个请求"和"全局每秒 10 万请求"）做精确的每秒级限流判断，请求必须所有规则都还有余量才放行，且要在 hot key 和 thundering herd 这两种典型坏场景下保持稳定，系统压力过大时能优雅降级。

**核心不变量**：

1. **状态是全局共享的**：请求打到集群里任意一个限流节点，判断依据必须是同一份权威状态，不能出现"各节点各算各的"。
2. **多规则是"与"关系**：一次请求要所有相关规则都满足才放行，任一规则不满足就拒绝（一票否决）。
3. **判断本身的开销远小于被保护后端的开销**：限流器不能自己成为新的瓶颈。
4. **系统压力过大时有明确的降级行为**：不能因为限流服务本身故障就导致后端被无限流量打垮，也不能因为限流服务故障就误伤所有正常流量。

明确"不做什么"：不追求绝对精确到毫秒级的窗口边界（滑窗算法本身有一定的近似，令牌桶允许短时突发）；不承诺限流服务 100% 不可能被绕过（降级路径本身是一种有意识的妥协）。

## 1. API 契约

```
CheckAndConsume(rules: [
  {scope: "api_key", key: "abc123", limit: 100, window_seconds: 1},
  {scope: "global",  key: "*",       limit: 100000, window_seconds: 1}
]) -> {allowed: bool, retry_after_ms?, per_rule_result: [...]}
```

- 一次调用传入所有需要同时满足的规则，服务端原子地检查+扣减，避免调用方自己分多次调用不同规则产生的中间态问题。
- `retry_after_ms` 建议客户端下次重试的时间，且这个建议值本身要带随机抖动（见"失败模式"一节的 thundering herd 对策）。

## 2. 数据模型

```
Redis 中，每条规则对应一个 key：
  滑动窗口规则：ZSET  rate:{scope}:{key}  member=request_id  score=timestamp_ms
    -- 检查时：ZREMRANGEBYSCORE 清理窗口外的旧记录，ZCARD 数当前窗口内的数量
    -- 若 < limit，则 ZADD 新记录，原子性由 Lua 脚本保证

  令牌桶规则：HASH  bucket:{scope}:{key}  {tokens, last_refill_ts}
    -- 检查时：按 (now - last_refill_ts) * refill_rate 计算应补充的令牌数，
    --         更新 tokens（不超过桶容量），若 tokens >= 1 则扣减 1 并放行
    -- 全部逻辑在一个 Lua 脚本内完成，避免"读取-计算-写回"之间的并发窗口
```

**为什么两种结构都要讲**：滑动窗口更精确（不会有令牌桶那种"两个窗口边界各自放完额度、中间瞬间叠加成两倍流量"的突发问题），但内存开销大（每个允许的请求都要存一条记录，ZSET 会随限流量线性增长）；令牌桶内存开销小（固定大小的一个哈希），但允许一定程度的突发（桶里囤积的令牌可以在极短时间内被瞬间用完）。per-key（如 API key 级别）规则数量多、单条限额不高，适合用令牌桶控制内存；全局规则只有一条但限额很大，用滑动窗口的精度收益更明显，可以按规则类型分别选型。

## 3. 核心流程

**检查+扣减的原子性**：每条规则的判断逻辑（读取当前状态 → 判断是否超限 → 如果没超限则更新状态）必须封装在**一个 Redis Lua 脚本**里原子执行，Redis 单线程执行脚本的特性保证了这个"读-判断-写"序列不会被其他并发请求的检查打断，这是防止"多个节点同时检查同一个 key、都以为自己没超限、结果加起来超发"的核心机制——本质上是把"分布式并发问题"收敛成"单个 Redis 实例内的原子操作问题"。

**多规则叠加**：一次 `CheckAndConsume` 需要检查多条规则时，用 Redis pipeline 或者把多条规则的检查逻辑写进同一个 Lua 脚本一次性提交——**关键设计点**：脚本内部先对所有规则做"是否会超限"的判断，只有全部规则都通过才真正执行扣减动作；如果任何一条规则会超限，直接返回拒绝且不对已经检查过的规则做任何状态修改（避免"规则 A 通过并已扣减，规则 B 才发现超限"这种需要回滚的半成功状态）。

**Hot key 的应对**：如果某个 API key 的请求量极高，每次都直接打 Redis 做原子检查会让这个 key 对应的 Redis 分片成为热点。对策是在限流网关节点本地维护一个**近似的、更保守的本地配额**（类似 sd04 quota 题的思路：中心 Redis 把该 key 的总限额"批发"一小部分给每个网关节点本地扣减，本地额度快用完时才异步向中心续借），把大部分判断收敛到本地内存操作，只有少数续借请求才打中心 Redis，代价是本地额度机制引入了小幅度的、有界的精度损失（换取热点抗压能力）。

## 4. 失败模式与规模

**Thundering herd（临界点/整点重试）**：如果限流窗口是固定对齐的自然时间边界（比如所有 key 都在每个整秒的 0 毫秒重置），会导致大量客户端在窗口刚重置的瞬间同时涌入。对策：① 滑动窗口本身天然没有这个问题（因为窗口是"过去 N 秒"而不是"当前这一秒"，不存在固定边界）；② 如果用固定窗口，给窗口重置时间加入 per-key 的随机抖动，避免所有 key 在同一毫秒对齐重置；③ 限流器拒绝请求时返回的 `retry_after_ms` 本身要加随机抖动建议，引导客户端分散重试时间，而不是让所有客户端都在同一个时刻重试造成新一轮的拥堵。

**降级策略**：中心 Redis 集群不可用是必须显式设计的场景——**fail-open（放行所有请求）**保证可用性但失去限流保护，**fail-close（拒绝所有请求）**保护后端但误伤所有正常流量；正确答案不是二选一，而是分场景讨论：对外部不可信流量（可能来自恶意攻击）倾向 fail-close 防止被打垮；对内部关键业务路径倾向 fail-open 避免因限流器故障连累核心业务。更好的折衷是**本地近似限流兜底**——各限流网关节点在检测到中心 Redis 不可用时，自动切换到本地内存维护的一个保守限额（比正常限额更严格，因为无法感知其他节点的消耗情况），在"完全不限流"和"完全拒绝"之间提供一个折衷的降级层。

**规模估算**：假设整体 QPS 峰值数万到数十万，Redis 单实例可以支撑很高的操作吞吐（Lua 脚本执行本身是微秒级），主要的扩展手段是按 `key` 哈希把不同 key 的状态分散到 Redis 集群的不同分片，避免所有 key 都打同一个分片；全局规则（如"系统整体每秒 10 万"）天然是单一热点 key，需要用前面提到的"本地批发额度"机制减少每个请求都直接打这一个 key 的频率，否则这一条全局规则会先于其他所有 per-key 规则成为瓶颈。

## 5. 分层与组件

- **规则配置层**：独立管理规则定义（scope、limit、window），支持动态更新且不需要重启限流网关节点。
- **状态存储层**：Redis 集群，只负责精确的原子计数，通过 Lua 脚本对外暴露"检查+扣减"这一个原子操作。
- **判断/编排层**：限流网关节点，负责把一次请求涉及的多条规则组织起来调用状态存储、聚合"是否全部通过"的最终结果，也承载本地近似限流的降级逻辑。
- **降级/熔断层**：独立的电路熔断组件，探测中心状态存储的健康状况，触发本地降级模式并在恢复后自动切回。

## 6. rollout/测试/监控

- **监控**：各规则维度的拒绝率、Redis 延迟与可用性、降级模式的触发频率与持续时长、检测到的 hot key 告警（某个 key 的 QPS 显著超出常规分布）。
- **测试**：并发压测验证 Lua 脚本原子性下确实不超发；模拟 Redis 短暂不可用验证降级路径按预期切换且恢复后能平滑切回中心状态。
- **rollout**：新规则/新阈值先以影子模式跑一段时间（记录"如果启用会拒绝哪些请求"但不真正拒绝），确认对真实流量的影响符合预期后再正式启用；限流阈值本身应该有周期性根据后端实际承载能力调整的机制，而不是一次设定后永久写死。

## 7. 用 Snowflake 自己的原语作参照

Snowflake 自己的计量与计费体系（`01-company-brief.md` §2「计量与计费」）里，**Cloud Services 每日免费额度 = 仓库消耗的 10%** 这类规则，本质上就是一种"多规则叠加限流"——一次操作既要看当前请求的即时资源消耗，又要看累计的每日额度，两个维度都要满足才不产生额外计费，这与本题"per-key + global 多条规则同时满足"的判断逻辑是同一个模式。另外，本题"中心 Redis 批发本地额度给网关节点"的 hot key 应对思路，与 sd04 quota 题里提到的"本地代理租借额度"以及 Snowflake **Execution Anchor**"绝大多数操作不需要每次都问权威存储"的设计哲学一脉相承——都是用局部缓存/预算把高频路径的压力从中心状态存储上卸载下来。面试时可以说："这个热点 key 的本地批发额度机制，和 Snowflake 计量体系里不是每次微小操作都同步扣费、而是准实时批量结算的思路是同一类工程模式。"

## 8. 45 分钟口述时间表

- **0–5 min**：复述题目 + 不变量（全局共享状态、多规则一票否决、判断开销可控、降级行为明确），确认降级默认策略（fail-open/fail-close）。
- **5–12 min**：API 契约（多规则一次调用）+ 数据模型（滑动窗口 ZSET vs 令牌桶 HASH，两种选型的取舍）。
- **12–22 min**：核心流程——Lua 脚本原子检查+扣减、多规则叠加的一票否决实现、hot key 的本地批发额度机制。
- **22–35 min**：失败模式——thundering herd 的抖动对策、降级策略的分场景讨论与本地近似限流兜底、规模估算与全局规则的热点问题。
- **35–42 min**：分层图 + rollout（影子模式验证新规则）+ 监控指标。
- **42–45 min**：总结 + 类比 Snowflake 计量体系的多维度规则叠加，反问面试官。
