# 追问预案（≥8 条）

> 前四条对应 `catalog/raw/system_design.md` §1.12 明确记录的"追问汇总"，标(一手)；其余基于题目结构推出。

## 1（一手）token bucket vs sliding window，精度和内存怎么权衡？

**期望要点**：滑动窗口更精确（用 ZSET 记录每个允许请求的精确时间戳，不存在令牌桶"两个窗口边界各自放完额度、瞬间叠加成两倍流量"的突发问题），但内存开销随限流量线性增长（每个允许的请求都要存一条记录）；令牌桶内存开销固定小（一个 tokens + last_refill_ts），但允许桶内囤积的令牌被瞬间用完造成短时突发。选型依据：对精度要求高、限额不大的场景（如全局规则）用滑动窗口；对 key 数量巨大、单条限额不高的场景（如 per-user）用令牌桶控制总内存占用。

**反例**：只知道"滑动窗口更准"就无脑选滑动窗口用于所有场景——没有考虑到如果有几百万个 API key 各自维护一个滑动窗口的 ZSET，内存开销会远超令牌桶方案，是没有权衡意识的表现。

## 2（一手）多台限流节点怎么共享状态，用什么原子操作？

**期望要点**：状态集中存在 Redis（或等价的原子共享存储），"检查是否超限 + 如果没超限则扣减"这个序列必须封装在一个 Lua 脚本里原子执行——Redis 单线程执行脚本的特性把"多节点并发检查同一个 key"这个分布式问题收敛成"单实例内的原子操作"问题，避免"先读后写"之间的窗口被其他并发请求插入导致超发。

**反例**：说"每个节点自己在本地维护计数器，定期跟其他节点同步"——这是最终一致模型，在两次同步之间完全可能出现多节点各自放行导致总量超发，不满足题目"不能出现各节点各算各的漏判"这条明确要求。

## 3（一手）多规则（per-user + per-IP + 全局）怎么叠加判断？

**期望要点**：多条规则之间是"与"关系，一次请求要所有规则都有余量才放行；实现上要把多条规则的检查打包进一个原子操作（一个 Lua 脚本或者一次 pipeline 的两阶段提交：先全部试探性检查，全部通过才真正扣减），避免"规则 A 先扣减成功、规则 B 才发现超限"这种半成功状态需要回滚的麻烦。

**反例**：依次检查每条规则，检查一条就立刻扣减一条，等到最后一条才发现超限——此时前面几条规则已经被实际扣减了配额，需要额外的回滚逻辑，且回滚本身在并发环境下也可能出错，是明显不如"先全部检查再统一扣减"优雅的设计。

## 4（一手）系统压力太大、限流服务本身撑不住了，怎么优雅降级？

**期望要点**：明确区分 fail-open（放行）和 fail-close（拒绝），根据流量的可信度和业务重要性分场景选择——对外部不可信流量倾向 fail-close 保护后端，对内部关键路径倾向 fail-open 避免误伤；更优的方案是本地网关节点在检测到中心存储不可用时自动切换到一个保守的本地近似限流（比正常限额更严格），作为"完全放行"和"完全拒绝"之间的折衷降级层，并在中心存储恢复后自动切回。

**反例**：只给出"要么全部放行要么全部拒绝"的二选一回答，没有意识到可以引入本地降级层作为中间折衷方案，也没有讨论"应该根据流量类型分场景决定"这个更细致的判断。

## 5. 如果客户端在被拒绝之后立刻疯狂重试，会不会把限流器自己打垮？

**期望要点**：`retry_after_ms` 建议值应该带随机抖动，引导客户端分散重试；限流器本身的"拒绝"判断路径（读取当前状态判断超限）本身开销要远小于"放行"路径（也需要写入状态），保证被拒绝的重试流量不会比正常流量更消耗系统资源；进一步可以在网关层对被限流的客户端做短暂的黑名单/更严格的临时限制，防止其无节制地重试。

**反例**：认为"限流器已经把请求拒绝了，所以不用再考虑这个问题"——被拒绝的请求仍然会打到限流器本身做判断，如果判断逻辑本身开销大（比如每次都要读写完整状态），高频重试仍然可能拖垮限流系统。

## 6. 某个 API key 的调用量突然暴涨（hot key），怎么防止它把 Redis 某个分片打爆？

**期望要点**：给热点 key 的限流状态引入本地近似——中心 Redis 把这个 key 的总限额批发一小部分给各网关节点本地扣减，大部分请求判断收敛到本地内存操作，只有少数续借请求才打中心 Redis；这个机制本身会引入小幅度的精度损失（本地额度换取热点抗压），需要显式讨论权衡。

**反例**：说"给这个 key 单独多分配几个 Redis 分片"——治标不治本，如果热点 key 持续增长，迁移到新分片后同样会把新分片打爆，没有从根本上减少对中心存储的请求频率。

## 7. 限流阈值应该怎么设定，写死一个固定数字够吗？

**期望要点**：初始阈值可以基于后端容量压测得出，但生产环境下后端的实际承载能力会随时间变化（扩容、代码优化、依赖服务变化），阈值应该有机制定期根据实际观测到的后端健康指标（如错误率、延迟）动态调整，而不是一次设定后永久写死；调整过程应该先以影子模式验证再正式生效。

**反例**：说"阈值定好了就不用管了"——没有考虑到系统容量会随时间演进，静态阈值要么过于保守浪费容量，要么过于宽松起不到保护作用。

## 8. 系统规模扩大 10 倍，哪里最先撑不住？

**期望要点**：先识别瓶颈——全局规则对应的单一热点 key（哪怕用本地批发额度缓解，续借请求的频率也会随整体流量增长）；Redis 集群单分片的操作吞吐上限（需要按 key 哈希增加分片数）；网关节点本身处理请求判断逻辑的 CPU 开销（Lua 脚本执行虽然快，但网络往返到 Redis 的延迟会在高并发下累积）。扩容方向：全局规则可以拆成多个近似独立的子限额（如按区域拆分全局配额，牺牲一点精度换取去中心化）；Redis 按 key 增加分片；网关节点水平扩展并用本地批发额度机制进一步减少对 Redis 的直接依赖。

**反例**："Redis 加内存就行"——没有识别到全局规则的单一热点 key 是比 Redis 整体容量更早触及的瓶颈，加内存不能解决单个 key 的操作吞吐上限问题。
