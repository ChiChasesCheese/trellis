# 评分 rubric（五维，1–4 分/维，满分 20）

> 依据 `loop/LOOP_GUIDE.md` §6 与 `catalog/raw/system_design.md` §1.12。追问汇总原文点名四个具体主题——token bucket vs sliding window、Redis 原子操作、多规则叠加、降级策略——基本就是这道题的满分四要素。

## 1. Problem framing（需求抽取）

- **1 分**：直接说"每个节点自己维护一个计数器就行"，完全没意识到多节点共享状态才是这道题的核心难点；没有区分"单一规则"和"多规则叠加"两种复杂度完全不同的场景。
- **4 分**：两句话复述——"要在多台限流节点组成的集群上，对多条同时生效的规则（如 per-key 和全局）做精确的每秒级限流判断，不能因为请求被分发到不同节点就出现各节点各算各的漏判"；显式说出不变量——**限流状态是全局共享的**（不是节点本地状态）、**多规则是"与"关系**（所有规则都有余量才放行，一票否决）、**限流判断本身的开销不能超过被保护后端的开销**（否则限流器自己成了新瓶颈）；主动确认精度要求（是否允许小幅度超发换取性能，比如令牌桶允许短暂突发）与降级策略的默认行为（限流系统故障时是"放行所有请求"还是"拒绝所有请求"，这是一个需要显式确认的业务选择）。

## 2. API & data model（权重最高）

- **1 分**：只设计了一个 `allow(key) -> bool` 接口，没有考虑多规则如何组合传参；数据结构选型没有说明白（"用个数据库存计数"这种笼统描述）。
- **4 分**：给出接口 `CheckAndConsume(rules: [{scope, key, limit, window}]) -> {allowed: bool, retry_after?}`，一次调用可以传入多条需要同时满足的规则（如 `{scope: "api_key", key: "abc", limit: 100, window: 1s}` 和 `{scope: "global", key: "*", limit: 100000, window: 1s}`）；数据模型上每条规则对应 Redis 里的一个计数结构，滑动窗口用 **有序集合（ZSET）** 存每个允许请求的时间戳（成员为请求 id，分数为时间戳），令牌桶用一个 **(tokens, last_refill_ts)** 的哈希结构配合 Lua 脚本原子刷新和扣减；能说清楚为什么滑窗更精确（不会有令牌桶在窗口边界的突发问题）但内存开销更大（每个允许的请求都要存一条记录），令牌桶内存开销小但边界处允许一定程度的突发。

## 3. Failure modes & scale（本题权重也很高——四个追问主题基本都落在这里）

- **1 分**：多规则叠加只判断第一条就返回，没有做到"全部满足才放行"；hot key 场景说"加缓存就行"没有具体机制；thundering herd 说"限流器扛住就行"没有主动降低冲击的手段；系统压力过大时怎么办完全没提。
- **4 分**：**Redis 原子操作**——每条规则的检查+扣减必须用一个 Lua 脚本原子完成（读取当前状态、判断是否超限、如果没超限则原子递增/滑窗插入，全部在一次脚本执行内完成，避免"先读后写"之间的并发窗口导致超发）；**多规则叠加**——多条规则要么全部通过一次 pipeline/脚本原子检查（推荐，避免"检查了规则 A 通过、检查规则 B 失败，但规则 A 已经被消耗了"这种半成功状态需要回滚的麻烦），要么设计成"先全部试探性检查、全部通过才真正扣减"的两阶段模式；**hot key**——对高频访问的单个 key，在限流节点本地做**短时窗口的近似聚合**（比如客户端/边缘节点本地先做一个粗粒度的令牌预算，类似 sd04 quota 题里"本地代理租借额度"的思路），减少每个请求都直接打中心 Redis 的次数；**thundering herd**——限流窗口的重置/刷新时间要加入随机抖动，避免所有客户端在整点同时涌入；对于客户端侧的重试，限流器返回的 `retry_after` 本身也应该带一定的随机化建议值；**降级策略**——Redis 集群不可用时，明确选择"fail-open（放行）"还是"fail-close（拒绝）"，这是一个需要与业务方确认的权衡（对外部不可信流量，fail-close 更安全；对内部关键路径，fail-open 避免误伤），可以进一步用本地节点的近似限流（各节点独立维护一个保守的本地限额）作为 Redis 不可用时的降级方案，而不是简单二选一。

## 4. Separation of concerns

- **1 分**：把"规则配置""状态存储""判断逻辑""降级策略"全部写死在同一段代码里。
- **4 分**：分层清楚——**规则配置层**（独立管理各种规则的定义，支持动态更新而不需要重启限流节点）；**状态存储层**（Redis 或等价的原子共享存储，只负责精确计数）；**判断/编排层**（负责把一次请求需要检查的多条规则组织起来、调用状态存储、聚合结果）；**降级层**（独立的电路熔断/本地近似限流逻辑，只在中心状态存储不可用时接管）。

## 5. Delivery beyond the diagram（rollout / 测试 / 监控）

- **1 分**：画完图不谈测试和监控。
- **4 分**：讲到监控指标（各规则的拒绝率、Redis 延迟与可用性、降级模式触发频率、hot key 检测告警）；讲到怎么测试精度（并发压测验证不超发、验证窗口边界的抖动是否真的分散了请求）；讲到 rollout 时新规则先以"影子模式"（只记录判定结果不真正拒绝）观察对真实流量的影响再启用；讲到限流阈值本身的动态调整机制（根据后端实际承载能力周期性调整，而不是写死一个固定值）。
