# 评分 rubric（五维，1–4 分/维，满分 20）

> 依据 `loop/LOOP_GUIDE.md` §6 与 `catalog/raw/system_design.md` §1.6。**这道题有一手 onsite 报告明确记录候选人未通过**——原始追问点名"故障时 enqueue 是否需要确认落盘再返回"，这类"要不要多等一次持久化确认"的问题最容易被含糊回答扣分，rubric 特别看重这里的坚决程度。

## 1. Problem framing（需求抽取）

- **1 分**：直接把 deque 的接口原样搬到"分布式版"，只是说"用多台机器存"，没有先说清楚从单机数据结构到云端服务之间，哪些不变量是全新出现的（持久化、故障恢复、消费语义、公平性、背压）。
- **4 分**：两句话复述——"要把一个内存里的 deque 变成一个多生产者多消费者、故障下不丢消息、消费语义明确、有公平调度和背压能力的云端队列服务"；显式说出关键不变量——**enqueue 成功即持久化承诺**（一旦返回成功，消息必须能被将来的消费者取到，即使服务器立刻断电）、**at-least-once 消费**（消息可能被重复处理，但不能丢）、**背压是显式的**（生产速度超过消费能力时系统要能表达"慢一点"而不是无限堆积）；主动确认消息的最大保留时间、优先级维度的具体需求（几个优先级、是否要严格优先还是加权公平）。

## 2. API & data model（权重最高）

- **1 分**：只写 `enqueue(msg)` / `dequeue() -> msg`，没有区分"取走消息"和"确认处理完成"两个动作；没有消息 id、没有可见性超时的字段。
- **4 分**：给出接口 `Enqueue(queue, payload, priority?) -> {message_id}`、`Receive(queue, max_messages, visibility_timeout) -> [{message_id, payload, receipt_handle}]`（取走消息但不立即删除）、`Ack(receipt_handle)`（确认处理完成，真正删除/标记完成）、`Nack(receipt_handle)` 或超时未 ack 则消息重新可见；数据模型区分**消息本体存储**（持久化的日志/表，`(message_id, queue, payload, priority, enqueued_at, status)`）与**可见性状态**（`invisible_until`、`receipt_handle`、`delivery_count`），能说清"取走"和"确认"分离正是解决"消费者处理到一半崩溃"这个问题的核心机制。

## 3. Failure modes & scale（本题权重也很高，是本题被压分最重的一节）

- **1 分**：对"enqueue 要不要等落盘确认再返回"这个问题回答含糊或者说"内存里先放着，异步刷盘就行"——这正是导致一手候选人挂掉的那类问题：如果 enqueue 返回成功但消息只在内存、还没复制/落盘，服务器断电这条消息就真的丢了，直接违反了"入队成功即持久化承诺"这条不变量；对 exactly-once 的追问答不出"做不到，只能 at-least-once + 消费者幂等"。
- **4 分**：**明确回答**：enqueue 必须等消息被复制到多数派副本（或落盘 + WAL）之后才能返回成功，这是不可协商的（可以讨论用 Raft/等价的复制协议做多副本持久化，牺牲一点写入延迟换取"确认成功即不丢"）；讲清**可见性超时机制**——`Receive` 取走消息后设置 `invisible_until`，在这段时间内其他消费者看不到这条消息，消费者处理完调用 `Ack` 真正删除，如果超时没有 `Ack`（消费者挂了/处理太慢），消息自动重新可见，可以被别的消费者取走——这就是 at-least-once 语义的来源，也解释了为什么无法做到 exactly-once（网络无法区分"消费者没收到"和"消费者处理完了但 ack 丢了"）；讲清**公平调度**——多优先级队列或加权轮询，防止高优先级消息洪峰完全饿死低优先级；讲清**背压**——队列深度或生产速率超过阈值时，`Enqueue` 显式返回限流错误或增加延迟（而不是无限堆积），配合消费者自动扩容的联动。

## 4. Separation of concerns

- **1 分**：把"消息持久化""可见性/租约管理""优先级调度""背压限流"全部塞进一个"队列节点"黑盒。
- **4 分**：分层清楚——**持久化层**（消息本体的多副本存储，独立于队列语义，只关心"这条消息写进去了、不会丢"）；**可见性/租约管理层**（负责 `invisible_until`、`receipt_handle`、重试计数，是实现 at-least-once 和消费者故障恢复的核心组件）；**调度/公平层**（决定 `Receive` 请求应该优先给出哪个优先级/哪个分区的消息，与持久化层解耦）；**背压/限流层**（独立观测队列深度和生产/消费速率差，与 `Enqueue` 的入口逻辑集成但逻辑上是单独一层，方便调整策略而不影响持久化正确性）。

## 5. Delivery beyond the diagram（rollout / 测试 / 监控）

- **1 分**：画完图不谈测试和监控。
- **4 分**：讲到监控指标（队列深度、消息平均等待时长、重试次数分布、DLQ 增长率、各优先级的饥饿情况）；讲到怎么测试持久化正确性（故障注入：写入确认后立刻杀掉节点，验证消息真的能被恢复）；讲到消费者长期无法处理某条消息（`delivery_count` 超过阈值）转入死信队列供人工介入；讲到 rollout 时新的调度/背压策略先在低风险队列上灰度观察积压和延迟指标。
