# 模型答案：从 deque 类到分布式队列服务

> 取材：1p3a thread-1185881 一手 onsite 报告（候选人未通过）；StaffEngPrep 归类页；`catalog/raw/system_design.md` §1.6。按 `LOOP_GUIDE.md` §6 主线组织。

## 0. 两句话复述 + 不变量

**复述**：要把一个单机内存里的 deque（简单的 enqueue/dequeue）改造成一个多生产者、多消费者的云端队列服务，核心是在故障（服务器断电、消费者崩溃）下不丢消息、消费语义明确（at-least-once），并且要有优先级公平调度和背压能力，防止生产速度超过消费能力时无限堆积。

**核心不变量**：

1. **enqueue 成功即持久化承诺**：`Enqueue` 一旦返回成功，这条消息之后一定能被某个消费者取到，即使服务器立刻断电。
2. **at-least-once 消费**：消息可能被处理多于一次，但绝不能丢；exactly-once 在网络分布式环境下做不到。
3. **消费者故障不导致消息丢失或永久卡死**：消费者取走消息后挂掉，消息必须能被别的消费者重新取到。
4. **背压是显式的**：生产速度长期超过消费能力时，系统要主动表达"减速"而不是无限堆积消息。

明确"不做什么"：不保证严格的全局 FIFO 顺序（多消费者并发处理天然难以保证严格顺序，公平调度和顺序保证是有张力的两个目标，需要显式讨论权衡）；不承诺 exactly-once。

## 1. API 契约

```
Enqueue(queue, payload, priority?)          -> {message_id}

Receive(queue, max_messages, visibility_timeout)
                                             -> [{message_id, payload, receipt_handle, delivery_count}]
                                             # 取走消息但不删除，进入"不可见"状态

Ack(receipt_handle)                         # 确认处理完成，真正标记完成/删除
Nack(receipt_handle, requeue_delay?)        # 显式放弃，可选延迟重新可见
```

- `Receive` 和 `Ack` **分离**是解决"消费者处理到一半崩溃"这个问题的核心机制：消息被取走后进入 `invisible_until` 状态，只有显式 `Ack` 才真正完成；如果消费者在 `visibility_timeout` 内没有 `Ack`，消息自动重新可见，可以被别的消费者（或同一个消费者重启后）再次取到。
- `delivery_count` 记录消息被取走的次数，超过阈值可以判定这条消息"反复处理失败"，转入死信队列（DLQ）。

## 2. 数据模型

```
messages(
  message_id, queue, payload, priority, enqueued_at,
  status[available|invisible|dead],
  invisible_until, receipt_handle, delivery_count
)
-- 消息本体 + 可见性状态在同一行，简化模型；持久化层要求多副本
-- 索引 (queue, priority, status, invisible_until) 供 Receive 扫描可用消息

dead_letters(message_id, all_delivery_attempts, moved_at)
-- delivery_count 超过阈值后落地，供人工介入
```

**故障时 enqueue 是否需要确认落盘再返回——这是本题一手报告里候选人翻车的关键点，必须明确回答**：`Enqueue` 必须等消息被**复制到多数派副本**（或等价的持久化确认，如写 WAL 并 fsync）之后才能向生产者返回成功；如果只是写进某个节点的内存就返回成功，这个节点断电，消息就真的凭空消失，直接违反了"入队成功即持久化承诺"这条最核心的不变量。这一步会牺牲一定的写入延迟（等待多数派确认的网络往返），但这是不可协商的正确性要求，不是可以为了性能牺牲的细节。

## 3. 核心流程

**Enqueue**：消息先路由到负责该队列（或该队列某个分片）的复制组；写入本地日志后复制到多数派副本，多数派确认后才返回 `message_id` 给生产者；消息状态初始为 `available`。

**Receive**：消费者请求时，调度层按公平策略从可用消息里挑出若干条（见"核心流程—调度"），把这些消息的状态原子地更新为 `invisible`，设置 `invisible_until = now() + visibility_timeout`，生成 `receipt_handle`（编码 message_id + 一个版本号，防止过期的 receipt 被误用来 ack 一条已经被别人重新取走的消息）返回给消费者。

**Ack**：消费者处理完成后调用，服务端校验 `receipt_handle` 有效（版本号匹配、还没过期），真正把消息标记为完成（删除或归档）。

**超时/Nack**：`invisible_until` 到期后台扫描任务把消息状态改回 `available`（`delivery_count += 1`），重新可以被 `Receive`；消费者主动 `Nack` 效果类似，可以指定延迟多久后再变可见（用于"这次处理失败了，晚点再试"的场景）。

**调度（优先级与公平）**：`Receive` 扫描时按优先级分层——不是简单的"高优先级永远优先"（会饿死低优先级），而是**加权轮询**：给每个优先级分配一个权重比例（如高:中:低 = 5:3:2），调度器按这个比例从各优先级队列里轮流取消息，保证低优先级消息在洪峰下也能拿到一定比例的处理机会。

**背压**：持续监控队列深度（`available` 状态消息数）和生产/消费速率差；深度超过阈值时，`Enqueue` 可以选择显式返回一个"系统繁忙，请稍后重试"的限流响应（配合生产者侧的退避重试），或者动态提高消费者自动扩容的信号；这个策略要显式告知调用方而不是让消息无限堆积到把持久化存储打满。

## 4. 失败模式与规模

**exactly-once 能不能做到**：不能。因为网络本质上无法区分"消费者根本没收到消息"和"消费者处理完了、但 Ack 请求在网络上丢了"，所以 `visibility_timeout` 超时后必须让消息重新可见，这就意味着消息有可能被处理多于一次。系统能提供的是 **at-least-once + 消费者侧幂等**（消费者按 `message_id` 做幂等去重），这与 sd01/stripe webhook 题里"不能保证 exactly-once"的论证是同一个网络本质原因。

**可见性超时设置过短/过长的权衡**：太短，正常处理还没完成消息就被判定超时、被别的消费者重复取走，制造不必要的重复处理；太长，一个真的挂掉的消费者拿着的消息要等很久才能被别人重新处理，影响整体处理时效。对策是允许消费者在处理过程中**主动续期**（`ExtendVisibility(receipt_handle, extra_time)`），处理时间可预测性差的场景可以边处理边续期而不是一开始就设一个很长的固定超时。

**死信与人工介入**：`delivery_count` 超过阈值（如 5 次）判定这条消息"反复处理失败"，转入 DLQ，停止继续投递，避免一条坏消息反复被取走、反复超时，浪费消费端资源且拖累整体吞吐。

**公平调度下的极端场景**：如果某个优先级队列长期空载而另一个持续爆满，加权轮询在"空闲优先级没有消息可取"时应该把这部分调度机会让渡给有消息的优先级，而不是死板地按权重空转浪费时间片。

**背压的联动**：背压信号可以驱动消费者自动扩容（如果消费能力是弹性的），也可以驱动生产者侧的限流（如果生产者本身可以延后产生消息，比如批处理任务可以调整批次间隔）；纯靠"无限堆积等消费者慢慢追上"在持久化存储有限的前提下终究会撑爆，必须有一个显式的压力反馈环。

**规模估算**：假设峰值 QPS 数万级，消息体较小（KB 级），持久化层的复制带宽是主要瓶颈之一；按 queue 或者按 message_id 哈希分片扩展写入吞吐；`invisible_until` 的超时扫描如果用轮询扫全表代价过高，应该用按 `invisible_until` 排序的索引（或延迟队列结构，如时间轮/ZSET）只扫描"即将到期"的一小部分。

## 5. 分层与组件

- **持久化层**：多副本复制存储消息本体，只关心"写进去了、不会丢"，与队列的可见性语义解耦。
- **可见性/租约管理层**：管理 `invisible_until`、`receipt_handle`、`delivery_count`，是 at-least-once 语义和消费者故障恢复的核心。
- **调度/公平层**：决定 `Receive` 优先给哪个优先级的消息，独立于持久化层实现，可以单独迭代调度算法。
- **背压/限流层**：观测队列深度和生产消费速率差，驱动 `Enqueue` 的限流与消费者扩容信号。

## 6. rollout/测试/监控

- **监控**：队列深度、消息平均/p99 等待时长、`delivery_count` 分布（异常高说明某类消息处理有问题）、DLQ 增长率、各优先级的实际处理占比（验证公平调度是否符合预期权重）。
- **测试**：故障注入——`Enqueue` 返回成功后立刻杀掉持有该消息的节点，验证消息仍能通过多数派副本恢复并被正常消费；模拟消费者处理到一半崩溃，验证消息在 `visibility_timeout` 后能被其他消费者正确重新取到。
- **rollout**：新的调度/背压策略先在低风险队列上灰度，对比积压时长和各优先级饥饿率是否改善，再推广。

## 7. 用 Snowflake 自己的原语作参照

这道题的"取走但不立即删除、需要显式确认"的可见性模型，与 Snowflake 的 **Streams**（`01-company-brief.md` §1）在"只有在 DML 事务里消费才推进 offset"这一点上是同一个思路——Streams 的 offset 书签只有在消费方真正把变更处理完并提交事务之后才会前移，如果事务失败/回滚，offset 不会前移，下次消费还能拿到同样的变更集，这正是"未确认就不算真正消费完成"的模式，与队列的 `Ack` 语义高度同构。另外，Snowflake **Snowpipe Streaming**（`01-company-brief.md` §1）用"行级 channel + offset token"做到单表级别的 exactly-once 摄入，其内部机制也是靠客户端持久化记录已确认的 offset 位置来避免重复摄入——这与本题"消费者按 message_id 做幂等去重"配合"at-least-once 投递"的组合思路是同一类工程模式在不同产品层面的体现。面试时可以说："这个可见性超时 + 显式 Ack 的模型，本质上是在实现一个简化版的 Streams offset 消费协议。"

## 8. 45 分钟口述时间表

- **0–5 min**：复述题目 + 不变量（持久化承诺、at-least-once、消费者故障恢复、显式背压），确认消息保留时长和优先级需求。
- **5–12 min**：API 契约（Enqueue/Receive/Ack/Nack，可见性分离设计）+ 数据模型。
- **12–22 min**：核心流程——Enqueue 的多数派确认、Receive/Ack 的可见性状态机、优先级加权调度、背压机制。
- **22–35 min**：失败模式——**明确、坚决地**回答"enqueue 要不要等落盘确认再返回"（要，这是不可协商的）、exactly-once 做不到的原因、可见性超时设置的权衡、死信与人工介入、规模估算。
- **35–42 min**：分层图 + rollout（灰度调度策略）+ 监控指标。
- **42–45 min**：总结 + 类比 Snowflake Streams offset 消费模型，反问面试官。
