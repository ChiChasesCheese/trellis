# 追问预案（≥8 条）

> 前四条对应 `catalog/raw/system_design.md` §1.3 明确记录的"追问汇总"，标(一手)；其余基于题目结构推出。

## 1（一手）查询要跑几分钟，前端怎么知道进度、怎么拿到最终结果？

**期望要点**：三段式异步模型——`POST` 提交立刻返回 `query_id`；前端轮询 `GET /queries/:id` 拿状态（pending/running/succeeded/failed），退避策略避免打爆后端；状态变成 succeeded 后再走单独的 `GET /queries/:id/results` 分页拉取。可以补充：有条件时用 WebSocket/SSE 做主动推送优化轮询延迟，但轮询必须始终可用作为兜底，因为不是所有客户端网络环境都支持长连接。

**反例**：设计成"一个 HTTP 请求同步等着查询跑完再返回"——完全没理解题目"查询可能跑几分钟，前端不能傻等"这句话的字面要求。

## 2（一手）结果集有几百万行，怎么分片/流式传给 notebook 前端？

**期望要点**：结果不放在关系表里，按分片写入对象存储（列式格式），`result_manifest` 记录每个分片的行数/位置；客户端用游标分页拉取，游标编码"哪个分片 + 分片内偏移"；worker 执行时可以边计算边流式写分片，支持"部分可用"的提前拉取（可选优化，需明确这不改变"整体结果以最终完成状态为准"的语义）。

**反例**：说"把结果全部序列化成一个大 JSON 返回"——这正是题目明确排除的做法，几百万行的 JSON 会撑爆前端内存和网络带宽。

## 3（一手）多个用户同时在各自 notebook 里跑查询，怎么做并发隔离？

**期望要点**：每次"运行"生成独立的 `query_id`，各自的执行状态、结果集完全隔离，互不覆盖；notebook 本身的多人协同编辑（如果存在）是文档层面的问题，与查询执行的并发隔离是两个不同维度，需要明确说清边界；执行层面的隔离还包括同一用户/租户的资源配额，防止一个用户开一堆 notebook 同时跑十个大查询占满全局资源。

**反例**：把"并发隔离"理解成"加锁让同一时间只有一个人能跑查询"——这既不符合业务需求（多用户应该能同时跑），也没有回答题目真正关心的"资源公平"问题。

## 4（一手）查询排队和底层计算资源调度是什么关系？

**期望要点**：类比 Snowflake virtual warehouse——多个查询共享一组计算资源，需要排队等待可用的执行槽；公平性设计上不能用简单全局 FIFO（一个大查询会让后面所有查询排很久），需要按预估代价分级排队（多级队列）或按用户/租户设置并发上限，防止某一方独占资源饿死其他人。

**反例**：说"资源不够就加机器，不需要排队策略"——回避了题目"多用户共享底层计算资源"这个明确的约束，加机器不能替代公平性策略的设计（成本、峰值容量都是有限的）。

## 5. 如果同一条 SQL 被反复提交（比如用户刷新页面误触了两次运行），系统怎么处理？

**期望要点**：默认不做自动去重（用户可能确实想重新跑一次，比如底层数据变了）；但可以引入类似 Snowflake result cache 的机制——如果 SQL 文本和依赖的数据在 TTL 内没有变化，第二次提交可以直接命中缓存的结果而不重新计算，作为性能优化而非正确性要求。

**反例**：强行说"用幂等键去重，第二次提交直接返回第一次的 query_id"——SQL 查询本身是幂等的读操作，两次独立执行产生两条独立记录是合理默认行为，除非面试官明确要求去重语义。

## 6. 查询执行到一半，用户关闭了 notebook 页面或断网了，会发生什么？

**期望要点**：查询在服务端继续跑到完成或超时（不因前端断连而被取消），结果按 TTL 保留一段时间；用户重新打开 notebook 后可以通过 `query_id` 恢复查询状态并继续拉取结果；只有用户显式调用 `cancel` 才会终止执行。

**反例**：说"前端断开连接就自动 kill 掉查询"——如果查询已经跑了很久快完成了，这样浪费掉的计算成本很高，也不符合"用户可能只是网络抖动"的现实情况。

## 7. 系统规模扩大后，哪里最先撑不住？

**期望要点**：先识别瓶颈——调度层的 `queue_state`（内存态，需要考虑单点或分片）；对象存储的写入吞吐（结果分片持续写入，一般不是瓶颈但要监控）；元数据表 `queries` 的写入/查询 QPS（可以按时间分区）。扩容方向：调度层按资源分组分片；元数据表读写分离；对象存储天然水平扩展。

**反例**："全部上更大的机器"——没有具体到瓶颈在哪一层。

## 8. 怎么保证一个用户不会通过开很多个小查询来绕过大查询的排队限制，变相占满资源？

**期望要点**：并发限制应该按用户/租户维度设置总并发查询数上限（而不仅仅是按查询大小分级），无论查询大小，超过并发上限的新查询都要排队；可以叠加基于历史资源消耗的动态限流（类似 Snowflake 的 resource monitor 思路），持续重度使用的租户获得更严格的并发上限。

**反例**：只讨论"大查询 vs 小查询"的分级排队，没有意识到"很多个小查询叠加起来"同样能造成资源独占，这是对"公平性"理解不完整的表现。
