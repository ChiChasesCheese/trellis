# 评分 rubric（五维，1–4 分/维，满分 20）

> 依据 `loop/LOOP_GUIDE.md` §6 与 `catalog/raw/system_design.md` §1.3。这是三条独立来源交叉印证的高置信度题，一手报告明确点名"结果怎么拿到"是讨论重点——这一维在本题里权重实际上超过其他维度。

## 1. Problem framing（需求抽取）

- **1 分**：直接开始设计"查询执行引擎"内部的优化器/调度器，没有先确认这是一个**前后端交互模型**问题（提交 → 异步执行 → 拉取结果），把重点放错了地方；没有问清楚结果集的典型/极端大小、排队公平性的具体诉求。
- **4 分**：两句话复述——"用户提交的 SQL 可能秒级也可能分钟级完成，前端不能同步等待；结果集可能有几百万行，不能一次性返回；多用户共享计算资源，需要公平排队又不能被大查询卡死"；显式说出不变量——**提交是异步的**（提交请求必须快速返回一个句柄）、**结果是可分页拉取的**（不能假设结果集能装进一次响应或一次内存）、**资源公平**（大查询不能无限期占用资源饿死小查询）；主动确认查询超时策略、结果保留多久可供后续拉取、是否需要主动推送（WebSocket/SSE）还是轮询即可。

## 2. API & data model（权重最高）

- **1 分**：只设计了一个"运行 SQL"的接口，没有区分"提交查询"和"拉取结果"两个动作；结果分页用 offset 而不是游标；没有考虑"结果还没算完时去拉取"应该返回什么。
- **4 分**：给出提交/查询状态/拉取结果三段式接口（`POST /queries` 提交返回 `query_id`；`GET /queries/:id` 查状态 pending/running/succeeded/failed，带进度信息；`GET /queries/:id/results?cursor=&limit=` 分页拉取，游标而不是 offset）；数据模型区分 **`queries`（元数据：SQL 文本、状态、提交者、所属 notebook/session、资源分组）** 与 **结果集的物理存储**（大结果集不适合直接放在关系表里，应该写到列式/分块的对象存储，`queries` 表只存指向结果分片的清单和每个分片的行数/字节数）；能说清"小结果集"和"大结果集"可以有不同的存取路径（小的直接内嵌返回，大的走分片文件）。

## 3. Failure modes & scale（本题权重也很高）

- **1 分**：轮询设计成"前端每 100ms 打一次"没有退避，会打爆后端；排队公平性只说"先进先出"，没意识到一个长查询会让后面所有查询都排很久（head-of-line blocking）；没有讨论查询超时/取消。
- **4 分**：轮询用指数退避（如 500ms → 1s → 2s → 5s 封顶），或者提供 WebSocket/SSE 推送作为优化路径；排队公平性用**多级队列 + 资源分组**——按用户/租户维度限制并发查询数（类似 warehouse 排队但加了公平性保证），大查询和小查询分开排队或者给小查询更短的排队上限，避免一个大查询卡住整个队列；结果集分片存储要考虑**过期回收**（结果集不能无限期占用存储，需要 TTL）；能正面回答"查询执行到一半用户关闭了 notebook 会怎样"——查询继续跑到完成或超时，结果按 TTL 保留一段时间供用户回来查看，而不是立刻取消（除非用户显式取消）。

## 4. Separation of concerns

- **1 分**：把"接收提交""排队调度""真正执行""结果落盘""分页读取"全部糅在一个服务里。
- **4 分**：分层清楚——**提交/网关层**（接收 SQL、生成 query_id、快速返回，不阻塞等执行）；**排队/调度层**（管理资源分组和公平性，决定什么时候把某个 query 派给计算集群）；**执行层**（无状态的计算 worker，跑完后把结果写到对象存储并更新元数据）；**结果读取层**（独立的读路径，直接从对象存储分片读取，不需要经过执行层，即使执行层繁忙也不影响已完成结果的读取）。

## 5. Delivery beyond the diagram（rollout / 测试 / 监控）

- **1 分**：画完图不谈监控和测试。
- **4 分**：讲到监控指标（排队时长分布、查询执行时长分布、结果集大小分布、并发查询数、资源分组的饥饿率）；讲到怎么测试大结果集分页的正确性（边界：0 行、恰好一页、跨越多个分片）；讲到 rollout 时新的排队算法先影子运行对比公平性指标；讲到结果集存储的容量规划与 TTL 清理任务的监控。
