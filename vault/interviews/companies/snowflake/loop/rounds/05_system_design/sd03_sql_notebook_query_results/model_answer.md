# 模型答案：设计 SQL Notebook / 查询结果分发系统

> 取材：1p3a thread-1187965 一手电面报告；聚合站 "Design an Interactive Query Execution Notebook"；`catalog/raw/system_design.md` §1.3。按 `LOOP_GUIDE.md` §6 主线组织。

## 0. 两句话复述 + 不变量

**复述**：用户在 notebook 里提交 SQL 查询，查询可能几百毫秒也可能几分钟完成，系统需要异步执行并让前端能够查询进度、拉取结果；结果集可能巨大（几百万行），不能一次性返回；多用户共享底层计算资源，需要公平排队且不能被大查询卡死其他人。

**核心不变量**：

1. **提交是异步的、非阻塞的**：提交请求必须立刻返回一个句柄（query_id），不能让 HTTP 连接挂着等查询跑完。
2. **结果是可分页拉取的**：无论结果集多大，客户端都能以恒定内存增量拉取，不假设一次性装下。
3. **资源分配是公平的**：任何单个查询或单个用户不能无限期占用计算资源，饿死其他人的查询。
4. **状态可查询、可恢复**：查询进度和结果在查询完成后一段时间内持续可访问，不因为前端断连或刷新页面而丢失。

明确"不做什么"：不追求所有查询都秒级完成（这是执行引擎优化器的问题，不是本题范围）；不保证结果的实时增量推送对每种客户端都有（轮询是保底方案，推送是优化）。

## 1. API 契约

```
POST /v1/queries                     {sql, notebook_id, warehouse_group?}
                                      -> {query_id, status: "pending"}

GET  /v1/queries/:id                 -> {status: pending|running|succeeded|failed|cancelled,
                                          progress?: {rows_scanned, elapsed_ms},
                                          result_meta?: {total_rows, chunk_count, schema}}

GET  /v1/queries/:id/results?cursor=&limit=200
                                      -> {rows: [...], next_cursor?}

POST /v1/queries/:id/cancel
```

- 提交立即返回 `query_id`，不阻塞。
- 状态查询默认轮询，退避策略 500ms → 1s → 2s → 5s 封顶；有条件的客户端可以升级到 WebSocket/SSE 订阅状态变化，减少轮询开销，但轮询必须始终可用作为兜底（浏览器网络环境不总是支持长连接）。
- 结果拉取用**游标分页**而不是 offset——结果物理上按分片存储，游标直接编码"下一个分片 + 分片内偏移"，避免 offset 分页在大结果集上退化成线性扫描。
- `warehouse_group` 允许用户/团队声明自己所属的资源分组，用于排队公平性。

## 2. 数据模型

```
queries(
  query_id, notebook_id, submitter, sql_text, status,
  submitted_at, started_at, finished_at, warehouse_group,
  result_manifest_ref, error
)
-- 元数据表，不存结果本身

result_manifest(query_id) -> [
  {chunk_id, storage_uri, row_count, byte_size}
  ...
]
-- 结果集实际存成一系列不可变分片文件（列式格式），存对象存储
-- 小结果集（如 < 1000 行）可以内嵌在 queries 表里直接返回，走快路径

queue_state(
  warehouse_group, queued_query_ids[], running_count, concurrency_limit
)
-- 每个资源分组的排队与并发状态，供调度层做公平性判断
```

**为什么结果不直接存关系表**：几百万行的结果集用行存关系表既浪费又慢（写入和后续分页读取都要走行级开销），列式分片文件按顺序追加写、按分片并行读，天然适合分页拉取和潜在的下游分析（用户可能要导出成 Parquet）。

## 3. 核心流程

**提交**：网关层接收 SQL，写入 `queries(status=pending)`，返回 `query_id`；这一步不涉及任何执行引擎调用，保证提交路径的低延迟。

**排队与调度**：调度层维护每个 `warehouse_group` 的并发上限（类比 Snowflake virtual warehouse 的排队机制）；一个后台调度循环从各分组的等待队列里按公平策略挑选下一个要执行的查询——公平策略不是简单的全局 FIFO，而是**多级队列**：给查询一个"预估代价"标签（可以基于历史同类查询的执行时长，或简单按扫描的表大小分级），小查询进入短队列、大查询进入长队列，调度器按一定比例（如 3:1）交替从两个队列取任务，防止大查询占满并发槽导致小查询长时间排不上。

**执行**：调度器把查询派给一个空闲的计算 worker；worker 执行完毕后把结果按分片写入对象存储，更新 `result_manifest` 和 `queries.status=succeeded`。

**结果拉取**：客户端轮询 `GET /queries/:id`，看到 `succeeded` 后带着 `result_meta` 开始翻页拉取 `GET /queries/:id/results`；这条读路径**直接读对象存储的分片文件**，不经过调度层或执行层——即使执行层此刻在处理其他排队查询，已完成查询的结果读取也不受影响。

## 4. 失败模式与规模

**轮询风暴防护**：前端轮询必须退避，后端也应该对短查询给出"快路径"提示——如果一个查询预估几百毫秒内能完成，服务端可以在提交响应里直接同步等待一个很短的时间窗口（如 200ms）尝试直接返回结果，避免典型的"提交 → 轮询 → 拉取"三次往返对简单查询造成不必要的延迟观感。

**大结果集流式传输**：结果分片文件本身在写入时就是流式追加的（worker 一边计算一边写分片，不需要等全部算完才落盘），这样即使查询本身要跑很久，前几个分片也可能提前可读——如果业务需要"边算边看"的体验，可以在 `result_manifest` 里标记"部分可用"的分片供客户端提前拉取；但要明确这只是优化，默认语义是"整个查询完成后结果才算最终确定"（否则用户可能看到之后被覆盖/撤销的中间结果）。

**排队公平性与饥饿**：多级队列本身仍可能在极端情况下出现某个分组长期得不到执行槽——需要给每个查询设置排队超时上限，超时后要么自动降级到更小的资源分组、要么直接失败并提示用户重试或稍后再试，而不是无限期挂在队列里。

**多用户并发编辑/执行隔离**：同一个 notebook 被多人同时打开时，每次"运行"都应该产生独立的 `query_id`，不同用户的查询互不干扰（notebook 本身的文档协同编辑是另一个问题，不在本题查询执行范围内，但要主动说明这个边界划分）。

**查询取消与超时**：用户显式取消或查询超过最大执行时长会被强制终止（execution engine 层面 kill 掉），`status -> cancelled/failed`；已经写出的部分结果分片按 TTL 自然过期清理，不需要额外的补偿逻辑。

**结果集生命周期**：结果分片有 TTL（如 24 小时），过期后由后台任务清理，用户超过 TTL 后重新拉取需要重新执行查询（如果 SQL 和数据都没变，可以命中类似 Snowflake result cache 的机制直接复用而不重新计算）。

**规模估算**：假设峰值并发查询数千级，每个查询结果集分片按 MB 到 GB 级别，对象存储的吞吐远高于典型关系数据库，是合理的选型；元数据表（`queries`）的写入频率远低于结果数据量，可以用普通的 OLTP 存储；调度层的状态（`queue_state`）需要低延迟读写，适合放内存态存储（如 Redis）并定期做持久化快照防止调度器重启后排队状态全部丢失。

## 5. 分层与组件

- **提交/网关层**：无状态，只负责快速接收和返回句柄。
- **排队/调度层**：维护资源分组的并发与公平策略，独立于执行层演进（未来换调度算法不影响 worker）。
- **执行层**：无状态计算 worker，只关心"给我一条 SQL，我算完写到指定位置"。
- **结果读取层**：直接读对象存储，与执行层解耦，保证已完成结果的可用性不受调度/执行层繁忙程度影响。

## 6. rollout/测试/监控

- **监控**：排队时长分布（p50/p99）、查询执行时长分布、结果集大小分布、各资源分组的并发利用率与饥饿率（超时被拒绝的查询占比）。
- **测试**：结果分页在边界情况下的正确性——0 行、恰好一页、跨越多个分片边界；轮询退避策略在网络抖动下不会造成雪崩式重试。
- **rollout**：新的排队/公平性算法先影子运行（记录"如果用新算法，这个查询会排多久"但不影响真实调度）对比公平性指标（如每分组的平均等待时长方差）是否改善，再切流量。

## 7. 用 Snowflake 自己的原语作参照

这题的排队/资源分组模型直接对应 Snowflake 真实的 **virtual warehouse** 机制（`01-company-brief.md` §1）——warehouse 是独立的计算集群按秒计费，查询提交后在 warehouse 内排队等待执行资源，多个查询共享同一个 warehouse 时天然存在"大查询卡住小查询"的公平性问题，这正是本题排队设计要解决的核心矛盾。另外，结果的"提交后可能命中缓存直接返回"对应 Snowflake 的 **result cache**（同 SQL + 数据没变，24 小时内直接返回不重新起 warehouse），本题在结果生命周期部分提到的"TTL 内可复用"正是这个机制的简化版。面试时可以说："这本质上是在设计一个简化版的 virtual warehouse 排队 + result cache 组合，公平性策略可以类比 Snowflake 多查询共享同一 warehouse 时的资源调度问题。"

## 8. 45 分钟口述时间表

- **0–5 min**：复述题目 + 不变量（异步提交、可分页结果、公平排队、状态可恢复），确认结果集规模、超时与 TTL 策略。
- **5–12 min**：API 契约（提交/状态/拉取/取消）+ 数据模型（queries 元数据 vs result_manifest 分片存储）。
- **12–22 min**：核心流程——提交、排队调度（多级队列公平性）、执行、结果读取路径与执行层解耦。
- **22–35 min**：失败模式——轮询风暴、大结果集流式写入、排队饥饿与超时降级、取消与 TTL 清理、规模估算。
- **35–42 min**：分层图 + rollout（影子运行验证公平性）+ 监控指标。
- **42–45 min**：总结 + 类比 Snowflake virtual warehouse 排队与 result cache，反问面试官。
