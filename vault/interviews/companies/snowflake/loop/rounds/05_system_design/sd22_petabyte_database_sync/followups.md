# 追问预案（8 条）

> 一手报告只记录了题面与"不许澄清"，没有记录具体追问；下面按题目结构与 CDC 系统的标准失败面推出，标注 **（推断）**。

## 1. 面试官一开始就说"不要问需求，直接设计"——你怎么开场？（一手情境）

**期望要点**：不停顿，直接声明假设与不变量（见 model_answer §0），并说"I'll proceed on these; stop me if any is wrong"。然后先讲数据模型再画框。
**反例**：连续问三个问题被拒后沉默；或不声明任何假设直接画"源 → Kafka → 目标"。

## 2. 全量搬运要好几天，这期间源端在持续写，怎么保证最后不丢不乱？（推断）

**期望要点**：记下 snapshot_lsn；增量从该 LSN 起缓冲；全量完成后回放；MERGE 以 LSN 比较决定覆盖，所以快照读到的旧值会被新事件覆盖、快照里意外读到的新值不会被旧事件回滚。
**反例**："先停写做全量"或"全量完了再开始抓增量"（中间窗口丢变更）。

## 3. apply worker 把同一批事件执行了两次会怎样？（推断）

**期望要点**：无害。MERGE 条件 `incoming.lsn > target._last_lsn`，第二次全部不满足；删除是带 LSN 的软删，同理。
**反例**："用 exactly-once 消息队列保证不重复"——把正确性押在传输层。

## 4. 同一行在不同分区的两个事件乱序到达？（推断）

**期望要点**：按 `hash(pk)` 分区保证同一 pk 在同一分区内有序；不同 pk 乱序不影响各自收敛；即使发生（重分区期间），LSN 比较兜底。
**反例**：全局单分区保证顺序（吞吐崩掉）。

## 5. 同步落后太多，源端 binlog 已经被清理了？（推断）

**期望要点**：检测 `applied_lsn < oldest_available_lsn`，该表进入 `Resync`（重新快照），告警；预防上监控 lag 与日志保留余量的比值。
**反例**："从最早能读到的地方继续"——静默丢数据。

## 6. 源端加了一列 / 改了一列类型？（推断）

**期望要点**：事件带 schema_version；加列先在目标加可空列再放行；改类型走影子列 + 回填 + 切换；不兼容事件暂停该表 apply 并告警，事件保留不丢。
**反例**：目标端自动 `ALTER` 跟随所有变更（类型收窄导致截断）。

## 7. 业务方问"这张表现在和源端一样吗"，你怎么回答、代价多大？（推断）

**期望要点**：选一个 LSN 做一致点；按 pk 范围分块算 checksum（行哈希 XOR / 求和），双端比对，不一致块下钻或重搬；在副本上跑、限速；增量表可只验最近分区。说出自己做过的 13.7M 行 day-level 对账。
**反例**：`SELECT COUNT(*)` 两边比一下。

## 8. 如何保证同步不把源端线上业务拖慢？（推断）

**期望要点**：读副本或存储快照；全量令牌桶限速；监控源端副本延迟 / CPU，自适应降速；CDC reader 只读日志不扫表；大表在低峰窗口加速。
**反例**："源端扛得住"。
