# 评分 rubric（五维，1–4 分/维，满分 20）

> 依据 `loop/LOOP_GUIDE.md` §6 与 `catalog/raw/system_design.md` §1.7。聚合站明确点名该题族的评分点是 **"tamper-evident retention, and efficiency"**——防篡改、保留策略、效率三个词基本框定了第 3 维的满分线；"哪些表/列没被访问过"这个反向查询是本题区别于普通日志系统的关键设计点。

## 1. Problem framing（需求抽取）

- **1 分**：把这题当成普通的"写日志表 + 查日志表"处理，没有意识到"防篡改"和"反向查询（哪些资源没被访问过）"是两个明显区别于一般日志系统的特殊要求。
- **4 分**：两句话复述——"要给多租户平台上的每一次数据访问行为留下不可篡改的记录，支持按资源正向查询访问历史，也要支持反向查询某段时间内完全没被访问过的资源，并且要有合规驱动的分级保留策略"；显式说出不变量——**只追加、不可变**（一旦写入的审计记录不能被修改或删除，包括被有权限的运维人员修改）、**租户强隔离**（任何查询都不能跨租户泄露）、**写入不能拖慢被审计的业务操作**（审计不能成为业务操作路径上的性能瓶颈）；主动确认"防篡改"的具体强度要求（是"应用层不提供修改接口"级别，还是要有密码学可验证的完整性证明）。

## 2. API & data model（权重最高）

- **1 分**：只有一张"日志表"按时间线性存储，没有为"反向查询"设计任何专门的索引结构；防篡改只字未提，写入接口和普通业务表的 CRUD 没有区别。
- **4 分**：给出写入接口（`RecordAccess(tenant_id, resource, accessor, action, timestamp) -> event_id`，只有 Create，没有 Update/Delete）与两类查询接口——正向 `GetAccessHistory(resource, time_range, cursor)` 和反向 `GetUnaccessedResources(tenant_id, resource_scope, since) -> [resource]`；数据模型上**正向查询**用按 `(tenant_id, resource, timestamp)` 排序的追加日志（类似 LSM，天然适合按资源+时间范围查询），**反向查询**用一张独立维护的**"每个资源的最后访问时间"物化视图**（`resource_last_accessed(tenant_id, resource) -> last_access_ts`，由日志写入异步更新），"哪些资源在 since 之后没有出现在这张表里（或 last_access_ts < since）"就是一个简单的范围查询，而不是对原始事件日志做全表扫描；能说清楚为什么两种查询模式需要不同的物理结构，而不是试图用一张表同时高效支撑两种查询模式。

## 3. Failure modes & scale（本题权重也很高——聚合站原文点名 "tamper-evident retention, and efficiency" 三个词）

- **1 分**：防篡改说"数据库权限控制一下就行，不给 UPDATE/DELETE 权限"——这只防住了"没有特权的普通用户"，没有回答"如果一个有 DBA 权限的人想篡改怎么办"这个更高强度的问题；保留策略说"就一直存着"或"简单设个 TTL 全部删"，没考虑合规客户需要的差异化保留期。
- **4 分**：**防篡改**分层回答——应用层不提供任何修改/删除审计记录的接口（基本防线）；存储层配置为真正的 WORM（write-once-read-many，如对象存储的对象锁/合规模式）或者数据库层面的不可变表约束；更强的证明力可以引入**哈希链/Merkle 树**——每条记录（或每个批次）计算哈希并把上一条的哈希纳入当前记录的哈希输入，形成链式结构，任何一条历史记录被篡改都会导致后续所有哈希对不上，这是"tamper-evident"（可检测篡改）而不仅仅是"tamper-resistant"（难以篡改）的关键区别，要能讲清楚两者的不同。**保留策略**——审计记录按租户/资源类型分级设置保留期（默认 90 天，合规客户可配置数年），到期后进入归档存储（更便宜但访问更慢）而不是直接物理删除，超过合规要求年限后才真正清除；哈希链在归档/清理时需要保留"锚点哈希"（即使原始记录被清理，仍能验证锚点之后没有中间记录被篡改）。**效率**——写入路径是异步的（业务操作先完成，审计事件通过消息队列异步落盘，不阻塞主路径），读路径正向/反向分别走专门优化的结构（如上一节所述）。

## 4. Separation of concerns

- **1 分**：把"接收审计事件""防篡改校验""正向查询""反向查询的物化视图更新""保留期归档"全部揉在一个服务里，没有分层。
- **4 分**：分层清楚——**采集/写入层**（从各业务系统异步接收审计事件，只做基本校验和排队，不阻塞业务路径）；**不可变存储层**（真正落盘的追加日志，负责哈希链计算与 WORM 约束）；**物化视图更新层**（异步消费写入的事件，维护"最后访问时间"等聚合视图，供反向查询使用）；**查询服务层**（正向/反向两套查询路径，各自命中为自己优化的物理结构）；**归档/保留管理层**（定期把过期数据迁移到归档存储或按合规策略清理，独立于实时写入路径运行）。

## 5. Delivery beyond the diagram（rollout / 测试 / 监控）

- **1 分**：画完图不谈怎么验证防篡改机制真的有效、怎么监控。
- **4 分**：讲到监控指标（写入延迟/积压、物化视图更新的滞后时长、哈希链校验失败告警——一旦触发意味着真的检测到篡改企图，这是严重级别的安全事件）；讲到怎么测试——定期后台任务重新计算哈希链校验历史数据完整性；讲到 rollout 时新的保留策略/归档规则先在非合规敏感的租户上验证再推广到合规客户；讲到审计系统自身的访问也需要被审计（"谁查询了审计日志"本身也是一条值得记录的事件，这是这类系统容易被忽略但面试官可能追问的点）。
