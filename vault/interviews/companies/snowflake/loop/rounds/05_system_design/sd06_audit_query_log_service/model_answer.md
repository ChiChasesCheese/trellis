# 模型答案：设计 Audit / Query-Event Log Service

> 取材：`../../raw/process_research.md` §3.2 #10 索引标题；PracHub 聚合站细节（"tamper-evident retention, and efficiency"）；`catalog/raw/system_design.md` §1.7。按 `LOOP_GUIDE.md` §6 主线组织。

## 0. 两句话复述 + 不变量

**复述**：要给多租户平台的每一次数据访问行为（谁、什么时候、访问了什么、做了什么）建立一个不可篡改的审计日志系统，支持"某资源被谁访问过"的正向查询，也要支持"哪些资源在过去一段时间完全没被访问过"的反向查询，并且要满足合规驱动的差异化保留策略。

**核心不变量**：

1. **只追加、不可变**：一旦审计记录写入，任何人（包括拥有高权限的运维人员）都不能修改或删除它。
2. **租户强隔离**：任何查询路径都不能跨租户泄露数据，隔离要在存储和查询两层都体现。
3. **审计不阻塞业务**：记录审计事件的动作不能成为被审计操作的性能瓶颈。
4. **完整性可验证**：不仅要"难以篡改"，还要能"检测到篡改"（tamper-evident），这是比单纯访问控制更高的要求。

明确"不做什么"：不追求实时（毫秒级）的反向查询结果，允许物化视图有秒级到分钟级的滞后；不承诺永久保留所有记录，保留期按合规要求分级。

## 1. API 契约

```
POST /internal/v1/audit_events        {tenant_id, resource, accessor, action, timestamp, metadata}
                                       -> {event_id}
                                       # 内部接口，业务系统异步调用，只有 Create

GET  /v1/audit/resources/:resource/history?time_range=&cursor=
                                       -> {events: [...], next_cursor}
                                       # 正向查询：某资源被谁访问过

GET  /v1/audit/unaccessed?resource_scope=&since=&cursor=
                                       -> {resources: [...], next_cursor}
                                       # 反向查询：哪些资源自 since 起没有被访问过

GET  /v1/audit/retention_policy/:tenant_id
POST /v1/audit/retention_policy/:tenant_id   {retention_days}
                                       # 合规客户配置保留期
```

- 写入接口没有 Update/Delete，语义上只允许 Create——这是"只追加"不变量在 API 层面的直接体现。
- 正向查询与反向查询是两个语义、性能特征完全不同的接口，刻意分开设计而不是试图用一个万能的"查询"接口覆盖两种场景。

## 2. 数据模型

```
audit_log(
  event_id, tenant_id, resource, accessor, action, timestamp,
  metadata, prev_hash, record_hash
)
-- 追加写入，按 (tenant_id, resource, timestamp) 排序存储（LSM 或按时间分区的列存）
-- prev_hash/record_hash 构成哈希链，见"失败模式"一节

resource_last_accessed(
  tenant_id, resource, last_access_ts
)
-- 物化视图，异步由 audit_log 的写入驱动更新（取每个 resource 的最大 timestamp）
-- 反向查询 "since 之后没被访问过的资源" = 全量资源列表 中 last_access_ts < since 或不存在的部分

retention_policies(tenant_id, resource_type, retention_days)
```

**为什么正向和反向查询需要不同的物理结构**：正向查询是"给定资源，找它的历史事件"，天然适合按资源分区、按时间排序的追加日志（一次范围扫描即可）；反向查询是"给定时间点，找哪些资源不在最近访问过的集合里"，如果直接在原始事件日志上做这个查询，等价于对全部历史事件做全表扫描再做差集运算，代价随日志增长线性上升。维护一张"每个资源的最后访问时间"物化视图，把反向查询转化为对**资源数量级**（远小于事件数量级）的一次范围查询，是效率的关键。

## 3. 核心流程

**写入路径**：业务系统在完成一次数据访问操作后，**异步**把审计事件发布到消息队列（不等审计系统确认就返回给业务调用方，保证审计不拖慢主业务路径）；采集层消费队列，计算该事件的哈希（纳入上一条记录的哈希，见下）后追加写入 `audit_log`；同一批消费流程异步更新 `resource_last_accessed` 物化视图。

**正向查询**：直接按 `(tenant_id, resource, timestamp)` 索引范围扫描 `audit_log`，游标分页返回。

**反向查询**：读 `resource_last_accessed`，筛选 `last_access_ts < since`（或该资源根本没有出现在这张表里，意味着从未被访问过）；这里需要一个"该租户名下所有资源的全集"作为对照（可能来自资源元数据服务），反向查询本质上是"全集减去在 since 之后有访问记录的子集"。

## 4. 失败模式与规模

**防篡改的分层落地（本题被压分最重的一节）**：
- **基本防线**：应用层不提供任何修改/删除审计记录的 API，这拦住了"没有特殊权限的正常调用路径"。
- **更强防线**：存储层配置为真正的 WORM——如果底层用对象存储，开启对象锁/合规保留模式，在保留期内即使拥有存储管理权限的人也无法删除或覆盖对象；如果用数据库，用不可变表/仅追加表的引擎特性。这一层拦住了"运维人员绕开应用层直接操作存储"的场景。
- **最强防线（可检测篡改，tamper-evident）**：给每条记录计算 `record_hash = Hash(record_content + prev_hash)`，形成一条哈希链——任何一条历史记录被篡改，都会导致从那条记录开始，后面所有记录的哈希值对不上。这与"防止篡改"（tamper-resistant）不同：前两层是让篡改**做不到或很难做到**，哈希链是让篡改**一旦发生就能被发现**——即使有人拥有足够高的权限绕过前两层直接改了存储里的字节，定期的哈希链校验任务也会发现从某条记录起链条断裂，从而定位到篡改发生的大致范围。三层防线要分开讲清楚，不能笼统地说"加密一下就行"。

**保留策略与归档**：默认保留期（如 90 天）后数据迁移到更便宜的归档存储（访问延迟更高但成本更低），而不是直接物理删除；合规客户可以配置更长的保留期（数年）；超过任何客户要求的最长年限后才真正物理清除。归档/清理时哈希链会被打断（早期记录不在了），需要保留一个"锚点哈希"（清理前最后一条被保留记录的哈希值，单独持久化且本身也受保护），后续校验可以从锚点开始验证，证明"锚点之后的记录没有被篡改"，即使更早的原始记录已经不在系统里。

**效率**：写入路径异步化是核心手段——业务操作的关键路径不等待审计系统确认；查询路径按访问模式拆成两套物理结构（如上），避免"一张表打天下"导致某一类查询退化成全表扫描。

**规模估算**：假设平台整体每秒产生数千到数万条审计事件，`audit_log` 按时间分区存储、按 `tenant_id` 做进一步分片，保证单租户的查询不会扫到其他租户的数据分区；`resource_last_accessed` 的行数是资源数量级（远小于事件数量级），即使租户和资源都很多，这张表也能用普通索引结构高效支撑范围查询。

## 5. 分层与组件

- **采集/写入层**：异步接收各业务系统的审计事件，只做基本校验和入队，不阻塞业务路径。
- **不可变存储层**：追加日志 + 哈希链计算 + WORM 约束，是"防篡改"三层防线里最重的部分。
- **物化视图更新层**：异步消费事件维护 `resource_last_accessed`，与写入层解耦，允许有一定滞后。
- **查询服务层**：正向/反向两套独立优化的查询路径。
- **归档/保留管理层**：定期迁移过期数据、维护锚点哈希，独立运行不影响实时写入和查询。

## 6. rollout/测试/监控

- **监控**：写入延迟与队列积压；物化视图更新滞后时长；哈希链校验失败告警（一旦触发是严重安全事件，需要立即人工介入排查）；各租户的保留策略合规状态。
- **测试**：定期后台任务重新计算并校验哈希链完整性；模拟归档流程验证锚点哈希机制在清理旧数据后仍能正确校验后续记录。
- **rollout**：新的保留/归档策略先在非合规敏感的租户上验证影响，确认正确后再推广到合规客户；额外提醒——审计系统本身的查询访问（谁查了审计日志）也应该被记录，形成"审计的审计"，这是容易被遗漏但体现设计完整性的细节。

## 7. 用 Snowflake 自己的原语作参照

Snowflake 官方有内建的 `SNOWFLAKE` 共享数据库暴露查询历史、访问历史等审计信息，客户增量导出这些审计数据时依赖时间戳列做增量拉取（`01-company-brief.md` §1 治理相关内容）——这与本题"按时间范围正向查询访问历史"的设计直接对应。更深一层，Snowflake 的 **Streams** 机制本身就是"只追加、按版本/offset 消费"的模式（`METADATA$ACTION` 记录变更类型，offset 单调前进不回退），这与审计日志"只追加、不可变"的核心不变量在实现哲学上是同一类思路——都是靠"只增不改"的存储模型天然获得防篡改和可审计性。另外，Snowflake 治理体系里的 **Horizon**（`01-company-brief.md` §1，含 AI Agent Identity）强调统一的治理与审计视图，也印证了这道题"多租户 + 防篡改 + 数据治理反向查询"的产品方向和 Snowflake 真实的 Horizon Catalog 团队所做的事情高度吻合。面试时可以说："这类似 Snowflake 自己给客户暴露的 `ACCESS_HISTORY`/`QUERY_HISTORY` 视图，只是这里额外要求了密码学可验证的防篡改能力。"

## 8. 45 分钟口述时间表

- **0–5 min**：复述题目 + 不变量（只追加不可变、租户隔离、不阻塞业务、可验证完整性），确认防篡改的具体强度要求。
- **5–12 min**：API 契约（写入 + 正向/反向查询 + 保留策略配置）+ 数据模型（audit_log + resource_last_accessed 物化视图）。
- **12–22 min**：核心流程——异步写入、正向查询范围扫描、反向查询命中物化视图，解释为什么两种查询需要不同物理结构。
- **22–35 min**：失败模式——防篡改三层防线（应用层限制/WORM/哈希链）、保留策略与归档、锚点哈希、规模估算。
- **35–42 min**：分层图 + rollout（灰度保留策略）+ 监控指标（尤其是哈希链校验告警）。
- **42–45 min**：总结 + 类比 Snowflake `ACCESS_HISTORY`/Streams/Horizon，反问面试官。
