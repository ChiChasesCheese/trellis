# 追问预案（8 条）

> 来源只有聚合站题面（且题面本身承认"需求模糊"），无一手追问记录；以下全部为按题目结构推出的
> **（推断）**。

## 1. 为什么 schema 和 manifest 都要做成"只增不改的版本"，而不是原地更新一行？

**期望要点**：原地更新会让"消费者 pin 住的旧版本"失去意义——你没法再回答"三天前这张表长什么
样"；不可变版本 + 指针切换让历史永远可查（Time Travel 式），也让读路径可以安全地读到"稍旧但
自洽"的快照，而不用担心读到一半写一半的中间状态。
**反例**："schema 变更频率低，原地更新省事"——忽略了历史可查与并发读写安全这两个核心需求。

## 2. 兼容性校验具体怎么判断"加一个字段是不是破坏性的"？

**期望要点**：backward compatibility 的核心规则——新加的字段必须可空或有默认值，这样用旧
schema 写的历史数据在新 schema 下读取时缺失字段能有合理取值；删除必填字段、收窄类型（int→
int8）、把可空改成必填都是破坏性变更。要能举一个具体例子说清楚，不能只说"看规则"。
**反例**："只要是加字段就一定兼容"——忽略了没有默认值的必填字段加进去，历史数据读出来会缺字段。

## 3. 两个摄取任务同时往同一张表提交新的文件清单，会发生什么？

**期望要点**：乐观并发——谁的 `base_version` 先匹配上当前版本谁先提交成功，指针原子推进；另一
个的 `base_version` 已经过期，收到冲突拒绝，需要重新读取最新版本、判断是否需要合并自己的文件
清单（通常是简单的追加，直接在新 base 上重试即可），而不是静默覆盖对方的更新。
**反例**："后提交的直接覆盖前一个"——会丢失前一个任务写入的文件清单。

## 4. 多区域部署下，目录的写权威放在哪个区域？其它区域怎么读？

**期望要点**：类比 Snowflake Execution Anchor——每个数据集的写权威绑定在一个区域（通常离主要
写入方最近），其它区域走异步复制的只读副本，读路径接受有界 staleness；跨区域写（比如另一个
区域的团队要给这个数据集提交新版本）走跨区域调用写权威区域，不在本地伪造一个"本地写"路径。
**反例**："每个区域都能独立写，最终一致就行"——会导致同一数据集在两个区域并发产生不同的
version 2，无法合并。

## 5. 外部引擎通过 Iceberg REST 协议提交的写，和内部服务自己的写路径是不是两套逻辑？

**期望要点**：不应该是两套——外部协议适配层只是把 REST 请求翻译成内部 `POST .../commit`，复用
同一个 `base_version` 乐观并发语义和同一个元数据存储；这样内部消费者和外部引擎看到的是同一个
一致的版本历史，不会出现"内部说是 v5，外部引擎以为是 v4"的分裂。
**反例**：给外部协议单独维护一份影子元数据，定期同步——引入了新的一致性问题。

## 6. 血缘图查询（"这张表的数据最终流向了哪些下游"）为什么不放进这个服务？

**期望要点**：血缘图的查询模式（多跳遍历、聚合、可能需要图数据库或专门索引）和目录的核心职责
（强一致的 schema/manifest 版本管理 + 高 QPS 点查）是两种完全不同的访问模式和一致性要求；耦合
在一起会让核心热路径的延迟被复杂图查询拖累。目录只负责可靠地存边，遍历交给独立服务消费这些边。
**反例**："都是元数据，放一起管理简单"——忽略了两种工作负载的性能特征完全不同。

## 7. 一个消费者 pin 在旧 schema 版本半年没有升级，风险是什么，应该怎么处理？

**期望要点**：只要该版本还在保留期内就必须继续兼容，否则会破坏那个消费者；但无限期保留旧版本
会让存储和兼容性校验的复杂度只增不减；应该监控"pin 时长超过阈值"的消费者并主动通知/报警，把
清理决策交给人（是否可以下线这个消费者的旧版本），而不是系统自己悄悄回收。
**反例**："超过一定时间自动删除旧版本"——会在没有协调的情况下直接破坏还在用它的消费者。

## 8. 这题官方就说需求模糊，你怎么知道你自己补的假设是对的？

**期望要点**：把每一个补的假设显式说出来并请面试官确认或反对（"我假设目录不管访问控制，这个
对吗？"），而不是悄悄假设了就往下讲；如果面试官保持沉默不回应，就把假设当作"我先按这个走，
面试官可以随时打断"明确讲出来，展示的是"主动暴露决策点"的能力，而不是"蒙对了模糊的需求"。
**反例**：一言不发地按自己脑补的需求往下画，等面试官在最后才发现理解偏了。
