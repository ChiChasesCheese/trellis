# 追问预案（8 条）

> 来源只有聚合站题面，无一手追问记录；以下全部为按题目结构推出的 **（推断）**。

## 1. 为什么不能只有 allow、没有 deny？

**期望要点**：角色继承会让"整体允许"和"局部例外"共存——比如给某角色整体授予读权限，但某张含
PII 的表要单独挡住；没有 deny 就只能反过来把这个角色拆得极碎（该角色能读除这张表以外的一切），
组合爆炸。deny 优先让"广泛授权 + 少量例外"能简单表达。
**反例**："不授予敏感表权限就行了，不需要 deny"——忽略了角色继承路径可能有多条，某条路径恰好
授予了它。

## 2. 吊销之后，缓存要多久才能反映？能做到"立刻"吗？

**期望要点**："立刻"在分布式系统里没有免费午餐；用推送失效尽量快，但正确性靠版本号比对，最坏
情况靠短 TTL 兜底（比如 5 秒）；这个数字要写进 SLA 并对外承诺，而不是含糊地说"很快"。
**反例**：声称能做到全局瞬时一致而不谈代价（要么牺牲可用性做同步失效，要么根本做不到）。

## 3. 角色继承图怎么防止出现环？

**期望要点**：写入新的角色继承边时做增量检测——只需要检查"能否从子角色反向到达父角色"，不需要
每次读的时候遍历判环；这是图论里"加边前查可达性"的标准手法，成本远低于每次授权检查都做环检测。
**反例**：只在读路径（授权检查时）做环检测，会导致遍历可能不终止或每次都要付出全图扫描的代价。

## 4. AI agent 的权限如果在创建时就固定快照，会有什么问题？

**期望要点**：用户权限后续被收紧（比如离职、换项目组、被发现违规），但 agent 仍然持有旧快照
权限，造成权限提升（privilege escalation）风险；agent 权限应该在每次决策时重新对齐"委托它的
用户此刻的权限"，取交集而不是并集。
**反例**："agent 权限审批时人工审一次就够了"——没有解决用户权限后续变化的问题。

## 5. 中心授权服务挂了，业务应该怎么办？

**期望要点**：不能一刀切；按资源敏感度分级——高敏感数据 fail-closed（拒绝好过误放行），低敏感
只读场景可以用断路器 + 上一次已知良好决策做短宽限期降级，超时仍然转 fail-closed；这个分级策略
本身要是配置项，让资源 owner 决定自己的风险偏好。
**反例**："为了可用性统一 fail-open"——把安全事故的责任转嫁给可用性目标。

## 6. 审计日志写失败了，这次授权决策还算数吗？

**期望要点**：决策不能等审计落盘（否则审计服务变成授权路径的单点瓶颈）；审计走本地持久化队列
异步 flush，失败重试；用"决策计数 vs 审计条目计数"的定期对账去发现漏审计，而不是假装"发出去
就算完成"。
**反例**：同步写审计再返回决策（延迟耦合）或者审计失败直接丢弃不重试（合规风险）。

## 7. 前端要渲染"我能看到哪些表"的列表，几千张表一个个点查会很慢，怎么办？

**期望要点**：不应该是 N 次 `/authorize` 调用；维护一个异步刷新的物化索引
`reachable_resources(principal)`，接受若干分钟的过期窗口去换取列表渲染的低延迟；这和单次点查
"必须实时正确"的 SLA 是两种不同的产品需求，不用同一套延迟保证。
**反例**：坚持"所有查询都要强一致"，把列表接口也做成同步聚合几千次点查。

## 8. 怎么验证一次策略模型改动没有意外放宽权限？

**期望要点**：影子模式下新旧两套决策逻辑并行跑生产流量，逐条 diff，专门标记"新逻辑允许、旧逻辑
拒绝"的差异并人工复核（这个方向的差异是唯一不能容忍的）；对角色继承图这类结构变更，用固定的
策略 fixture 做回归测试而不是只靠人工点击验证。
**反例**：只做人工 QA 点击测试几个账号，没有系统性 diff。
