# 追问预案（8 条）

> 来源只有聚合站题面，无一手追问记录；以下全部为按题目结构推出的 **（推断）**。

## 1. 为什么不直接用引用计数，删除时减一、到 0 就删？

**期望要点**：计数加减和元数据写入不在同一个原子操作里时，崩溃会让计数漂移；计数少了会误删仍被引用的块（数据丢失，不可恢复），多了只是泄漏空间。所以真相用可达性扫描（mark-and-sweep），计数最多作为估计；宁可漏回收不可错删。
**反例**："用分布式事务保证计数准确"——把全局一致性押在最热的写路径上。

## 2. 用户 A 刚确认某块已存在（跳过上传），回收器同时把这个块删了？

**期望要点**：宽限期：回收只删"创建时间早于 24 小时且上一轮 mark 就未被引用"的块；上传提交清单前再确认一次块存在，或给块刷新 `last_referenced_at`；清单提交成功之后下一轮 mark 必然标记它。
**反例**：没意识到这个窗口。

## 3. 固定大小分块和内容定义分块（CDC）怎么选？

**期望要点**：固定分块简单、元数据少，但文件头插入 1 字节后所有块都变；CDC（Rabin 滚动哈希找边界）让边界随内容移动，适合备份/增量快照；代价是块大小不均、计算开销。按负载类型选，或大文件默认 CDC。
**反例**："整文件一个 hash 就够了"——相似大文件完全无法去重。

## 4. 租户能不能通过"秒传"推断别人存过某个文件？怎么防？

**期望要点**：能，这是经典侧信道（上传速度或"已存在"响应泄露信息）。对策：去重域限定在租户内；或全局去重但客户端永远真实上传字节，服务端后台再合并；响应时间不因去重而改变。
**反例**："hash 不可逆所以安全"——攻击者本来就持有候选文件。

## 5. 覆盖一个 key 之后，旧内容什么时候真正释放？

**期望要点**：覆盖只写新版本；旧版本若开启版本保留则按保留策略过期；过期后清单不再可达，下一轮 mark 未标记，过宽限期后 sweep。与 Snowflake Time Travel + Fail-safe 类比。
**反例**："覆盖时立刻删旧块"——另一个 key 可能共享这些块。

## 6. 元数据有数百亿条，怎么分片？

**期望要点**：命名层按 `hash(bucket, key)`；LIST 需要按前缀的二级索引（范围分片 + 游标分页，最终一致）；块索引按内容 hash 分片天然均匀；清单按 manifest_id。热点 bucket 单独拆分。
**反例**：按 bucket 分片（大 bucket 成热点）。

## 7. 读一个 100 GB 的对象，延迟怎么保证？

**期望要点**：清单一次取回；按 range 并行拉块；客户端或边缘缓存热块；支持 Range 请求只取需要的部分；大对象可预取下一段。
**反例**：串行读块。

## 8. 去重比例不高（比如只有 5%），这套复杂度还值得吗？

**期望要点**：先影子模式统计去重率再决定；元数据与回收的成本要和节省的存储比较；可以只对特定 bucket（备份、导出）开启。展示"先测量再决定"的判断力。
**反例**："去重总是好的"。
