# 模型答案：地理位置搜索服务

## 0. 复述 + 不变量

**复述**：为五亿个带属性的点提供 kNN、半径、多边形三类查询，p99 < 100 ms；少量点高频移动，允许几秒可见延迟；租户隔离。

**不变量**：租户只能看到自己的点；返回结果按大圆距离严格排序；移动点位置可见延迟 ≤ 几秒；同一个点不会以两个位置同时出现在结果里。**不做**：路网 / 行车距离。

## 1. API

```
POST /v1/points            {tenant, id, lat, lng, type, attrs, ts}       # upsert，ts 旧于现存则丢弃
GET  /v1/nearby            ?lat&lng&k|radius_km&type&cursor               # 结果按距离，游标 (distance, id)
POST /v1/within            {polygon: GeoJSON, filters, cursor}
DELETE /v1/points/{id}
```

## 2. 数据模型

- `points(tenant, id) → {lat, lng, type, attrs, ts}`：主存储。
- 空间索引：`(tenant, cell_L) → [id…]`，cell 用 S2（或 H3）固定层级 L，使一个 cell 边长约 1–5 km；热点区域用更细层级的子索引。
- 移动点实时层：内存里按 `(tenant, cell)` 分片的哈希表 `id → (lat, lng, ts)`，每秒批量写回主存储。

## 3. 核心流程

**kNN**：算中心点所在 cell → 取该 cell 与第一环邻居的候选 → 精确算大圆距离、过滤属性 → 若已有 k 个且"下一环能出现的最小距离"大于当前第 k 个距离则停止，否则再扩一环。
**半径**：用 S2 `RegionCoverer` 求覆盖圆的 cell 集合 → 取候选 → 精确过滤 → 排序分页。
**多边形**：同上，覆盖多边形的 cell 集合，精确点在多边形内判断。
**移动点更新**：写入网关按 `ts` 防乱序 → 更新实时层（旧 cell 删除、新 cell 插入）→ 异步批量落主存储；查询同时读实时层与静态索引，同 id 以实时层为准。

## 4. 失败模式与规模

| 问题 | 处理 |
|---|---|
| 最近邻在隔壁 cell | 按环扩展 + 停止条件，不能只查一个 cell |
| 热点（市中心 cell 里百万点） | S2 层级自适应：点数超阈值的 cell 下沉到更细层级 |
| 移动点写放大 | 实时层内存 + 批量刷盘；只有跨 cell 才改索引 |
| 乱序更新 | 以 `ts` 为准，旧更新丢弃 |
| 经度 180° / 两极 | S2 在球面上天然处理；geohash 需要特判 |
| 深分页 | 游标 `(distance, id)`，不用 offset |
| 实时层节点宕机 | 从位置更新日志重放最近几秒；期间该分片读静态层（可能旧几秒，符合不变量） |

规模：五亿点 × ~200 字节 ≈ 100 GB 主数据；索引按 `(tenant, cell)` 分片，查询只触达覆盖到的分片。

## 5. 分层

```
写入网关 → 位置更新日志（按 cell 分区）→ 实时索引（内存）→ 批量落 → 主存储 + 静态空间索引
查询服务：cell 覆盖计算 → 并行读实时层与静态层 → 合并去重 → 精确过滤排序 → 分页
```

## 6. Rollout / 测试 / 监控

暴力扫描作为 kNN / 半径的 oracle 做随机对比测试；监控 p99、每查询扫描 cell 数与候选数、实时层可见延迟、热点 cell 点数；自适应细分先 dry-run 报告再启用。

## 7. Snowflake 原语参照

Snowflake 的 `GEOGRAPHY` 类型与 H3 函数（`H3_LATLNG_TO_CELL`、`H3_GRID_DISK`）就是本题"cell 化 + 环扩展"的 SQL 版本；分析侧的批量地理聚合适合放在 Snowflake 里做，而在线 p99 < 100 ms 的 kNN 需要本题这样的专用索引服务——面试里说清"在线服务 vs 分析仓库"的分工是加分项。
