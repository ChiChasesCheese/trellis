# 模型答案：Resilient Auth with Flaky Third-Party Tokens

> 取材：自签会话 token（本地 JWT）解耦持续鉴权与第三方可用性的通用做法；断路器（circuit
> breaker）模式；Snowflake **key-pair authentication**、**OAuth 支持**、**Trust Center**
> （`../../../01-company-brief.md` §1、§2）。本题来源为聚合站，按覆盖面练。

## 0. 两句话复述 + 不变量

**复述**：一个多区域 HTTP/JSON API 平台，身份鉴权依赖一个已知不可靠的第三方 IdP；要在第三方
降级时继续正确服务已认证用户、绝不放松安全校验、且故障不跨区域扩散。

**不变量**：
1. **正确性优先于可用性（针对"这个 token 是否有效"这个问题）**：绝不因为第三方降级就接受一个
   实际无效或已吊销的 token。
2. **持续鉴权不应与第三方健康状况强耦合**：已签发的自包含 token 的日常校验（签名 + 过期）不
   需要每次都问第三方。
3. **吊销在有界延迟内传播**：吊销永远不是"立刻全局生效"，但也不是"无限期继续信任"。
4. **故障域按区域隔离**：一个区域到第三方的链路问题不能拖垮其它区域的鉴权。

**不做**：不追求对第三方"零依赖"——初次登录 / OAuth 授权码换 token 这一步本来就必须经过第三方，
这是登录路径的固有属性；我们只把"持续鉴权对第三方的依赖"降到最低，而不是消灭登录路径本身的
依赖。

## 1. API 契约

```
POST /auth/oauth/callback     用授权码换第三方 token → 我方签发本地会话 token（JWT，短过期）
POST /auth/token/refresh      用 refresh token 换新的本地会话 token（视第三方健康状况而定）
POST /auth/revoke             吊销一个会话/token
（内部）verify_request(token) 网关本地调用：验签 + 查本地吊销缓存 → allow/deny，无网络调用
（可选）密钥对认证：客户端用私钥对请求签名，服务端用注册过的公钥验证——完全不经过第三方
```

## 2. 数据模型

- `sessions(session_id, principal, issued_at, expiry, third_party_token_ref)` —— 登录/刷新
  成功后我方**自己签发**的本地会话 token 记录；`third_party_token_ref` 只用于将来刷新时回查
  第三方，不参与日常请求校验。
- `jwks_cache(kid, public_key, fetched_at)` —— 本地缓存的验签公钥，长 TTL + 后台定期刷新 +
  断路器保护，绝不同步逐请求拉取。
- `revocation_list(token_id, revoked_at)` —— 强一致 source of truth；按区域复制的缓存副本，
  有界 staleness（同 sd13 的推送 + 短 TTL 兜底模式）。
- `circuit_breaker_state(region, endpoint, state: closed|open|half_open)` —— 按区域、按第三方
  端点分别维护，互不影响。

## 3. 核心流程

**登录**：客户端走第三方 OAuth 流程（这一步**必须**经过第三方，无法避免）→ 成功后我方验证第三方
返回的 token，**签发自己的本地会话 token**（自签 JWT，短过期时间，比如 15 分钟）→ 客户端此后
所有 API 调用都带这个本地 token。

**逐请求鉴权（热路径，完全本地）**：
1. 验证本地 JWT 签名（用 `jwks_cache` 里的公钥，不发网络请求）。
2. 检查过期时间，容忍一个小的时钟偏差窗口（如 ±2 分钟）。
3. 查本地吊销缓存副本（有界 staleness）；命中吊销 → 拒绝。
4. 三者都通过 → 放行。**整个热路径不依赖第三方是否健康**。

**刷新**：本地会话 token 快过期时，客户端调用 `/auth/token/refresh`；服务端检查底层的第三方
授权是否仍然有效——若第三方健康，正常刷新；若第三方降级：
- 默认（安全优先）：**fail-closed**，拒绝刷新，用户需要重新完整登录一次。
- 可配置（按业务风险决定）：给一个**保守、有界**的宽限期（比如再延长本地 token 15 分钟，且
  只允许一次），超过宽限期强制转 fail-closed。
两种策略都要显式配置、写进 SLA，不能默认"悄悄放行"。

**吊销传播**：吊销写入强一致存储，异步复制到各区域缓存（推送 + 短 TTL 兜底，同 sd13）；对高
敏感操作（比如转账、修改权限）可以要求**同步**回查吊销 source of truth 而不是信任本地缓存，
按操作敏感度分级校验强度。

**第三方降级检测**：每区域维护独立的断路器，监控到对第三方端点的调用连续超时/失败达到阈值 →
打开断路器，该区域后续调用直接走降级路径（用缓存的 JWKS、按配置处理刷新请求），不再同步阻塞
等待第三方；断路器周期性半开探测恢复情况。

## 4. 失败模式与规模

| 问题 | 处理 |
|---|---|
| 第三方登录入口整体不可用 | 新用户确实无法登录（登录路径固有依赖，无法规避）；**已登录用户完全不受影响**——两者要在设计里明确区分开来讲 |
| JWKS 端点抖动/超时 | 长 TTL 本地缓存 + 后台异步刷新 + 断路器；绝不同步逐请求拉取导致鉴权热路径被第三方拖慢 |
| 时钟偏差 | 过期校验容忍小窗口（如 ±2 分钟）；持续监控偏差量，发现系统性时钟漂移及时处理，而不是无限放宽窗口掩盖问题 |
| 吊销传播延迟 | 有界 staleness 写进 SLA（"降级期间一个已吊销 token 最坏 N 秒内仍可能被放行"）；高敏感操作走同步强校验兜底 |
| 一个区域链路抖动拖累其它区域 | 断路器状态按区域独立维护，绝不是全局一个开关 |
| 刷新时第三方降级，是否放行 | fail-closed 为默认；保守有界宽限期为可配置的显式风险决策，不是默默放行 |
| 第三方自己内部返回过期/模糊的"有效"结果 | 我方对第三方响应也要有合理性校验（比如返回的 token 元数据与我方记录的授权范围/过期时间做交叉检查），不能盲信第三方返回的任何"valid" |
| 规模：验签是本地 CPU 操作 + 缓存查询 | 鉴权热路径天然水平扩展，不受第三方吞吐限制 |

## 5. 分层与组件

```
客户端 SDK（持有本地会话 token；或用密钥对签名，完全不依赖第三方）
        ↓
认证网关 / 边缘校验（本地验签 + 本地吊销缓存查询，按区域部署，独立断路器）
        ↓ 仅登录/刷新边界
会话签发服务（与第三方 IdP 交互，签发本地会话 token）
JWKS/密钥缓存（长 TTL + 后台刷新 + 按区域断路器）
吊销服务（强一致 source of truth + 按区域复制缓存）
        ↓
第三方 IdP（外部、不可靠，被限定在窄且边界清晰的调用面之后）
```

## 6. Rollout / 测试 / 监控

- **灰度**：用历史第三方延迟/错误率数据先离线校准断路器阈值，避免上线后过于敏感或迟钝；逐
  区域启用新的本地会话签发路径。
- **混沌测试**：主动注入第三方超时/500 响应，验证降级路径（JWKS 缓存兜底、刷新宽限期、断路器
  打开）真的按预期工作，而不是等真实故障发生时才第一次被触发。
- **监控**：按区域的第三方调用延迟/错误率；断路器打开/半开事件；吊销传播 p99 延迟；"进入保守
  宽限期"的刷新决策频率（应该很少见，频繁出现要报警排查）；密钥对认证路径与 OAuth 路径各自的
  使用占比与错误率。
- **测试**：第三方完全不可用时已登录用户的请求全部正常通过；新登录请求得到明确的"暂时不可用"
  而不是挂起超时；吊销后在 staleness 窗口内的边界行为符合文档承诺；一个区域断路器打开不影响
  其它区域的鉴权延迟。

## 7. 用 Snowflake 自己的原语作参照

**Key-pair authentication** 正是本题"减少对不可靠第三方运行时依赖"这条思路的现成产品化答案
——客户端用私钥签名，服务端用注册过的公钥验证，完全不需要在请求路径上依赖任何第三方服务的
实时可用性。Snowflake 对 **OAuth** 的支持则对应本题"依赖第三方 token"的场景本身。**Trust
Center** 这类安全态势看板的思路可以直接搬过来：把"断路器打开次数""降级期间的鉴权决策"本身
当作安全信号持续监控，而不只是可用性指标。
