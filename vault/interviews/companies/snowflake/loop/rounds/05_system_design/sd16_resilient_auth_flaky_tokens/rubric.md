# 评分 rubric（五维，1–4 分/维，满分 20）

## 1. Problem framing

- **1 分**：方案是"第三方超时就默认放行"或者反过来"第三方一慢全平台鉴权跟着变慢/全挂"，没有
  区分"哪些校验必须实时问第三方"和"哪些校验可以本地做"。
- **4 分**：复述后说出不变量：**校验正确性优先于可用性**——绝不能因为第三方降级就接受一个实际
  无效/已吊销的 token（这条不能妥协）；**但正常请求的鉴权延迟不能和第三方的健康状况强耦合**
  ——已签发的自包含 token（如 JWT）签名 + 本地过期检查通常不需要每次请求都问第三方；**吊销要在
  有界延迟内传播**，不是无限期信任一个 token；**故障域按区域隔离**——一个区域到第三方的链路
  抖动不能拖垮其它区域，断路器状态是每区域独立的，不是全局一个开关。明确"不做"：不追求"零第
  三方依赖"（初次登录/OAuth 交换本来就需要第三方），只追求把"持续依赖"降到最低。

## 2. API & data model

- **1 分**：每次请求都同步调第三方校验 token，没有本地签发的会话 token，没有 JWKS 缓存，没有
  吊销列表。
- **4 分**：**登录时**换取第三方 OAuth token 后，本服务**自己签发一个本地会话 token**（自签
  JWT，短过期时间），之后所有请求鉴权只验证本地 token（签名 + 过期 + 吊销列表本地副本），不再
  依赖第三方；**密钥对认证**（key-pair auth）作为完全不依赖第三方运行时可用性的替代路径，适合
  service-to-service。数据模型：`jwks_cache(kid, public_key, fetched_at)`（本地缓存 + 定期
  刷新 + 断路器保护，不做同步逐请求拉取）；`sessions(session_id, principal, issued_at, expiry,
  third_party_token_ref)`；`revocation_list(token_id, revoked_at)`（强一致 source of truth +
  按区域复制的有界 staleness 缓存，同 sd13 的吊销传播模式）；`circuit_breaker_state(region,
  endpoint, state)` 按区域、按第三方端点分别维护。

## 3. Failure modes & scale

- **1 分**：断路器是全局一个状态；吊销要么假装能瞬时全局生效、要么干脆没有传播机制；时钟偏差
  没考虑；第三方 JWKS 端点被同步打爆。
- **4 分**：**第三方登录入口本身不可用**时新用户确实无法登录（这是预期且不可避免的——登录本来
  就必须经过第三方），但**已经登录的用户**因为持续鉴权走本地校验完全不受影响，这个区分要明确
  说出来；**JWKS 端点抖动**——长 TTL 本地缓存 + 后台异步刷新 + 断路器，绝不同步逐请求拉取；
  **时钟偏差**——过期校验容忍一个小的偏差窗口（如 ±2 分钟），并监控偏差量发现系统性时钟漂移；
  **吊销传播延迟是一个明确的安全权衡**，要写进 SLA（"降级期间一个已吊销的 token 最坏情况下
  还可能在 N 秒内被本地缓存放行"），对高敏感操作可以要求走一次同步的强吊销校验（按操作敏感度
  分级校验强度，同 sd13 的分级思路）；**故障域隔离**——断路器状态按区域维护，一个区域打开断路
  器不影响其它区域；**刷新时第三方降级**——是直接拒绝所有刷新（fail-closed）还是给一个保守的
  有界宽限期，要作为显式配置项讲清楚,不能含糊带过。

## 4. Separation of concerns

- **1 分**：登录、逐请求鉴权、JWKS 拉取、吊销检查全部耦合在一次同步的第三方调用里。
- **4 分**：**客户端 SDK**（持有本地会话 token，或用密钥对签名）→ **认证网关/边缘校验**（本地
  JWT 验签 + 本地吊销缓存查询，按区域部署）→ **会话签发服务**（只在登录/刷新边界才与第三方 IdP
  交互）→ **JWKS/密钥缓存**（带按区域断路器）→ **吊销服务**（强一致 source of truth + 按区域
  复制的缓存）→ **第三方 IdP**（外部、不可靠，被限定在一个很窄、边界清晰的调用面之后）。

## 5. Delivery beyond the diagram

- **1 分**：画完就停。
- **4 分**：用历史第三方延迟/错误率数据先做影子测试校准断路器阈值，再逐区域上线；主动混沌注入
  （故意让第三方调用超时/返回 500）验证降级路径真的按预期工作，而不是等真实故障才第一次触发；
  核心指标：按区域的第三方调用延迟/错误率、断路器打开事件、吊销传播 p99 延迟、"进入保守宽限期"
  的刷新决策频率（应该很少发生，频繁发生要报警）。能类比 Snowflake：key-pair authentication
  是本题"减少对不可靠第三方的运行时依赖"这条思路的现成产品化答案；Trust Center 类的安全态势
  看板可以把断路器状态、降级事件本身当作安全信号来监控。
