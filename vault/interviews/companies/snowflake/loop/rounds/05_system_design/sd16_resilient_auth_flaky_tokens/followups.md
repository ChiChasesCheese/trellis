# 追问预案（8 条）

> 来源只有聚合站题面，无一手追问记录；以下全部为按题目结构推出的 **（推断）**。

## 1. 为什么要自己签发一个本地会话 token，而不是每次请求都拿用户的 token 去第三方验证一次？

**期望要点**：每次请求都同步调第三方，会让平台自己的可用性和延迟直接被第三方的健康状况锁死
——第三方一慢，全平台跟着慢；一挂，全平台跟着挂。自签的本地 token（JWT）签名+过期检查完全在
本地完成，把"持续鉴权"和"第三方是否健康"彻底解耦，第三方只需要在登录/刷新这两个边界点上被
调用。
**反例**："每次都验证最新鲜，安全性更高"——混淆了"token 语义正确性"和"每次都要问第三方"，
本地校验签名和过期一样能保证 token 没被篡改、没过期，只是吊销检查需要走本地有界延迟的缓存。

## 2. 断路器为什么要按区域维护，而不是一个全局状态？

**期望要点**：不同区域到第三方的网络路径、延迟特征完全不同，一个区域出现链路抖动不代表其它
区域也在经历同样的问题；全局断路器会把局部问题放大成全局降级，违反"故障域隔离"这个不变量。
**反例**："简单起见用一个全局开关"——牺牲了本来可以保住的其它区域的正常服务。

## 3. 时钟偏差容忍窗口设多大合适？设得太宽松会有什么风险？

**期望要点**：窗口太窄，正常的时钟漂移（几十毫秒到几秒级）会导致合法 token 被误判过期；窗口
太宽（比如几十分钟），一个已经真正过期很久的 token 也可能被当作"还在容忍范围内"放行，变相
延长了 token 的实际有效期，是安全隐患。通常几分钟量级是合理起点，同时要监控实际观测到的偏差
分布来调整，而不是拍脑袋定一个数字。
**反例**：为了"图省事，避免误杀"直接把窗口设成一小时——本质上就是把过期时间放宽了一小时。

## 4. 某个操作特别敏感（比如转账、修改权限），怎么在不牺牲整体架构的前提下加强这次校验？

**期望要点**：按操作敏感度分级——大多数请求走本地缓存的吊销检查（有界 staleness 可接受），
但敏感操作可以额外要求一次同步的、直接查吊销 source of truth 的强校验，牺牲这一次请求的延迟
换取更强的实时性保证；这是防御纵深（defense in depth）思路，不需要把所有请求都提到同一个
（更贵的）校验强度。
**反例**：为了这一类敏感操作，把所有请求的吊销检查都改成同步强一致——不必要地拖慢了绝大多数
普通请求。

## 5. 如果第三方 IdP 自己内部就有问题——它明明该返回"已吊销"却因为自己的缓存过期返回了"有效"，我们能防住吗？

**期望要点**：这是第三方自身数据新鲜度的问题，我们只能做有限缓解——比如交叉校验第三方返回的
token 元数据（过期时间、授权范围）与我方记录是否合理，设置更保守的本地过期时间不完全依赖第
三方的长效期声明；但无法彻底杜绝第三方自身返回错误结果的风险，这个边界要诚实地讲清楚，而不是
声称"我们的系统能保证第三方数据一定新鲜"。
**反例**：假装本方架构能弥补第三方自身的数据一致性问题——这超出了本方系统设计能控制的范围。

## 6. 密钥对认证作为兜底路径，注册公钥这一步本身怎么防止被冒充？

**期望要点**：公钥注册本身需要一次带外的信任建立（比如通过已认证的会话或人工审核流程注册新
公钥，而不是任何人都能匿名提交一个公钥自称是某个客户端）；注册之后的每次认证不再需要这次信任
建立的过程，这也是它"运行时零第三方依赖"的原因——信任成本在注册时一次性付清，而不是每次请求
都重新验证。
**反例**："公钥可以随时通过 API 自助更新，不需要额外审核"——攻击者注册自己的公钥顶替合法
客户端。

## 7. 刷新请求撞上第三方降级期，应该 fail-closed 还是给宽限期？谁来决定？

**期望要点**：没有放之四海而皆准的答案——高安全要求的场景（金融、权限管理类客户端）应该默认
fail-closed，接受用户重新登录的不便；对用户体验优先、风险可接受的场景可以配置一个短的、有
上限的宽限期。关键是这个决策要显式暴露为配置项，由资源/客户端的风险等级决定，而不是系统写死
一种策略。
**反例**：统一写死"永远宽限"或"永远拒绝"，没有给不同风险场景留出差异化的余地。

## 8. 怎么在真实故障发生之前就验证"降级模式"确实能工作？

**期望要点**：混沌工程——主动对第三方调用注入超时、5xx、连接拒绝等故障，观察断路器是否按预期
打开、JWKS 缓存兜底是否生效、刷新宽限期逻辑是否按配置执行；这些验证要作为常规演练（比如季度
一次的故障演练）而不是等生产环境真的发生第三方大规模故障才第一次触发这条代码路径。
**反例**："降级逻辑写完测试通过就上线了，正式故障来了再看效果"——降级路径往往是代码里最少被
真实流量走到的分支，不主动演练几乎一定会在真正需要的时候暴露没被发现的 bug。
