# 评分 rubric（五维，1–4 分/维）

## 1. Problem framing
- **1 分**：直接画"应用 → Kafka → Elasticsearch"，不谈库本身。
- **4 分**：把问题分成**库（进程内）**和**管道（进程外）**两半，主战场是库；列出不变量：日志调用不阻塞业务线程、内存有上界、平台故障不影响应用、敏感数据不出机器、各语言字段语义一致；明确取舍：高压下**丢日志优于拖慢业务**，但要计数并上报丢了多少。

## 2. API & data model
- **1 分**：`log(String msg)`，字符串拼接。
- **4 分**：统一语义规范（级别枚举、字段名、时间戳 UTC 纳秒、`trace_id / span_id`、`service / host / version`）；结构化 API `logger.info("query finished", query_id=…, ms=…)`，延迟格式化（级别不够时不构造消息）；上下文传播（MDC / contextvars / context.Context）自动带 trace；记录格式选 OpenTelemetry log data model 或等价 schema；各语言用薄绑定 + 共享规范文档与一致性测试，而非共享一个 C 核心强绑所有语言（说明取舍）。

## 3. Failure modes & scale
- **1 分**：同步写网络；平台挂了就抛异常。
- **4 分**：热路径只做"写入有界无锁环形缓冲"；后台线程批量编码与发送；缓冲满时策略可配（丢 DEBUG 优先、按级别采样、最后丢最旧），并记录丢弃计数；发送失败指数退避 + 本地磁盘溢出队列（有大小上限、轮转）；进程退出时有限时间 flush；fork 安全（子进程重建后台线程）；时钟回拨用单调时钟排序；日志风暴时按"消息模板 + 调用点"限速去重；脱敏在**进入缓冲前**完成（规则：凭据字段名、token 正则、SQL 字面量掩码）。

## 4. Separation of concerns
- **1 分**：日志库里直接写 Elasticsearch 客户端。
- **4 分**：分层——API 层（级别判断、结构化、上下文）→ 处理器链（脱敏、采样、限速）→ 缓冲 → 导出器接口（stdout / 文件 / OTLP / 本地 agent）；推荐应用只写本机 agent（sidecar / daemon），由 agent 负责压缩、重试、平台鉴权与路由，库保持轻；动态配置由 agent 下发（按 logger 名调级别），库轮询或订阅。

## 5. Delivery beyond the diagram
- **1 分**：没提测试与发布。
- **4 分**：跨语言一致性测试（同一组调用在各语言产出逐字段相同的记录）；性能基准（热路径 p99 纳秒级开销、缓冲满时业务延迟不变）；故障注入（agent 挂、磁盘满、网络分区）；库自身指标（产生 / 丢弃 / 发送失败 / 缓冲水位）；脱敏规则有单测与"金丝雀敏感串"检测；版本兼容（新字段可选、旧 agent 忽略未知字段）。
