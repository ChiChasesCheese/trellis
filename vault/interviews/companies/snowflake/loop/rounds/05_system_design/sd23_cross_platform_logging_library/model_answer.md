# 模型答案：跨平台日志库

## 0. 复述 + 不变量

**复述**：Java / Go / Python / C++ 与客户机上的驱动共用一套日志规范；结构化、带追踪上下文；送中心平台检索；不拖慢热路径；平台故障不影响应用且内存有界；驱动日志脱敏；运行时调级别；单机峰值约 10 万条/秒。

**先问的问题**：能否在每台机器上跑一个 agent？客户机器（驱动）能否直连我们的平台？可接受的丢日志率？

**不变量**：日志调用不阻塞业务线程；内存与磁盘占用有上界；敏感数据在离开进程前已脱敏；丢弃必被计数；各语言记录字段语义一致。

## 1. 统一规范（先定义数据，再写库）

```
record := {
  ts_unix_nano, observed_ts, severity(TRACE..FATAL), body(模板字符串),
  attributes{k: v}, trace_id, span_id,
  resource{service, version, host, pid, language}
}
```

对齐 OpenTelemetry log data model，好处是现成的导出协议（OTLP）与生态；消息用"模板 + 参数"，便于按模板聚合与限速。

## 2. 库内结构

```
logger.info("query finished", query_id=q, ms=t)
  → 级别检查（原子读取当前阈值；不够直接返回，不构造参数）
  → 捕获上下文（trace_id / span_id，来自 MDC / contextvars / ctx）
  → 处理器链：脱敏 → 采样 → 按调用点限速
  → 有界无锁环形缓冲（写入 O(1)，满则按策略丢弃并计数）
后台线程：
  → 批量取出 → 编码（protobuf）→ 导出器
导出器：stdout | 本地文件（轮转） | 本机 agent（Unix socket / localhost OTLP）
```

**为什么不共享一个 C 核心**：绑定成本、崩溃半径、各语言运行时（GC、协程、fork）差异大；改为"规范 + 各语言薄实现 + 一致性测试"。C++ 查询引擎可以用更激进的实现（线程本地缓冲），只要产出同一 schema。

## 3. 管道

应用 → **本机 agent**（压缩、批量、鉴权、重试、磁盘溢出队列、路由）→ 摄取网关 → 日志流（按租户 / 服务分区）→ 索引存储 + 冷存储。
客户机上的驱动默认只写本地文件；用户显式开启时才经 agent 或直连上传，且上传前再脱敏一次。

## 4. 失败模式

| 问题 | 处理 |
|---|---|
| 平台或 agent 挂 | 库只写本机；agent 退避重试 + 磁盘队列（上限、最旧优先淘汰） |
| 缓冲写满 | 先丢 DEBUG / TRACE，再采样 INFO，WARN 以上最后丢；计数 `dropped{level}` |
| 日志风暴（同一行每秒几万次） | 按"模板 + 调用点"令牌桶，超出汇总成"已抑制 N 条" |
| 敏感数据泄露 | 进入缓冲前脱敏：字段名黑名单、token / 密钥正则、SQL 字面量掩码；金丝雀串测试 |
| 进程崩溃丢最后几秒 | 退出钩子有限时 flush；崩溃信号处理只做 async-signal-safe 写文件 |
| fork 后后台线程丢失 | 注册 fork 钩子，子进程重建缓冲与线程 |
| 动态调级别 | agent 下发 `{logger_prefix: level, ttl}`，库原子替换阈值表；TTL 到期自动恢复 |

## 5. 测试与运维

一致性测试：同一脚本在四种语言跑，比较输出记录；基准：热路径开销与缓冲满时业务 p99 不变；故障注入：kill agent、磁盘满、网络分区；库自身指标：产生、丢弃、发送失败、缓冲水位、脱敏命中数。

## 6. Snowflake 参照

Snowflake Event Tables 按 OpenTelemetry 模型存日志与追踪（`SYSTEM$LOG_INFO`、`RECORD_ATTRIBUTES`、`TRACE`），并有日志级别参数（账号 / 数据库 / 函数级）——本题"统一 schema + 分级 + 动态调级"的产品版；驱动的 `tracing` 参数与本地日志文件对应本题的"客户机日志默认留在本地"。
