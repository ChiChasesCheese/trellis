# 追问预案（8 条）

> 来源只有聚合站题面，无一手追问记录；以下全部为按题目结构推出的 **（推断）**。

## 1. 为什么要给每个租户专属计算资源，而不是一个大集群配公平调度算法？

**期望要点**：公平调度算法本质是"共享资源里少分一点"，一个足够大的重查询仍然会瞬间占满共享
集群的调度队列、内存或 I/O 带宽，影响到其它租户的排队延迟；专属计算资源是物理/虚拟机级别的
隔离，noisy neighbor 从"调度算法能不能压住"变成"压根不共享同一批资源"。
**反例**："我们把优先级设高一点、给小查询更高权重就行"——权重再高，共享资源终归是有限的。

## 2. 自动挂起/恢复怎么权衡成本和延迟？给不同租户不同 SLA 具体怎么做？

**期望要点**：闲置阈值可配置（比如 5 分钟无查询即挂起）；恢复延迟是冷启动代价（拉起新的计算
节点），对延迟敏感的租户可以选择"保留最小规模常驻池不缩到零"的更贵套餐；把这个权衡显式做成
产品的分层定价，而不是所有租户强制统一策略。
**反例**："所有租户都缩到零最省钱"——牺牲了对延迟敏感租户的体验且没有给他们选择权。

## 3. 如果结果缓存的 key 用查询提交的挂钟时间而不是快照版本号，会有什么问题？

**期望要点**：挂钟时间不能反映数据是否真的变了——用时间做 key 要么缓存粒度太粗（同一秒内数据
已经变了但仍命中旧结果，返回错误答案），要么太细（几乎每次都不命中，缓存形同虚设）；用快照
版本号做 key 是精确且天然版本化的，数据没变版本号就没变，缓存永远既正确又高效。
**反例**："缓存 TTL 设短一点就安全了"——TTL 只是缩小错误窗口，不能消除它，而版本化 key 能
彻底消除。

## 4. 同一个租户内部，一个巨大的批量查询占满了它自己的 warehouse，会不会拖慢它自己的 dashboard 查询？

**期望要点**：会，这是"租户内部的 noisy neighbor"，和跨租户隔离是两个不同粒度的问题；解法是
按工作负载类型（交互式 dashboard vs 批量报表）拆分成该租户内的多个 warehouse，或者靠
multi-cluster 在同一个逻辑 warehouse 下横向扩出独立集群承接突发的交互式并发。
**反例**："租户内部反正是他自己的资源，慢一点无所谓"——对交互式产品来说 dashboard 卡顿就是
体验问题，不能因为"同一个客户"就降低要求。

## 5. 长时间运行的查询和持续的摄取，怎么保证互不阻塞？

**期望要点**：查询在开始时绑定当前快照版本号，之后摄取产生的新文件对这个查询完全不可见，也
不需要等它；摄取只是往前推进指针、写新的不可变文件，不会去修改查询正在读的旧版本文件；两者
在时间线上并发无冲突，唯一需要协调的是"旧版本文件什么时候能被回收"（引用计数 + 宽限期）。
**反例**：摄取写入时给表加排它锁，等所有正在跑的查询结束才能提交——会让摄取被长查询无限期
卡住。

## 6. Multi-cluster warehouse 什么时候该扩出新集群，什么时候该让查询排队？

**期望要点**：监控当前集群的排队深度/等待时间，超过阈值（比如平均排队时间超过某个毫秒数）就
扩出新集群；扩容也要有上限（避免无限扩容导致成本失控）和冷却时间（避免抖动式反复扩缩）；对
成本敏感的租户可以选择"排队而不扩容"的套餐。
**反例**："只要有并发就扩容"——短暂的并发尖峰会导致频繁扩缩容，增加冷启动开销和成本抖动。

## 7. 计费怎么保证准确，不会因为系统 bug 导致租户被多收或少收钱？

**期望要点**：计量管道独立于计算路径，直接记录 warehouse 实际的启动/挂起时间戳；专门监控"应
该挂起但没挂起"的实例（这类 bug 会导致租户被系统性多收钱，是信任问题，必须能被主动发现而不是
等客户投诉）；定期用集群运行时长日志和账单记录做交叉审计。
**反例**："按查询数量估算计费"——和实际消耗的计算资源脱钩，规模大小不同的查询消耗差异巨大。

## 8. 计算已经按租户隔离了，存储层还会有 noisy neighbor 问题吗？

**期望要点**：会——如果多个租户的数据文件物理上放在共享的存储集群上，一个租户的超大扫描仍然
可能占满共享存储节点的 I/O 带宽，间接拖慢另一个租户的读取；需要在存储层也做 I/O 配额/QoS，或
者按租户物理分片存储资源，不能假设"计算隔离了，存储自动就公平"。
**反例**："存储是分布式的，节点足够多天然就分散了"——热点访问模式仍然可能集中在少数节点上。
