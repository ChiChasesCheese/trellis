# 评分 rubric（五维，1–4 分/维，满分 20）

## 1. Problem framing

- **1 分**：直接说"一个大集群，大家排队跑查询"，不提隔离、弹性伸缩、缓存、快照一致性、计费
  准确性。
- **4 分**：复述后说出不变量：**计算隔离**——一个租户的负载不能拖慢另一个租户的延迟/可用性，
  这是架构问题不是限流问题；**快照一致性**——单次查询在执行期间看到的是摄取开始前或完成后的
  完整快照，绝不会看到"写了一半"；**弹性伸缩**——闲时缩到零，并发高峰扩出去，按**实际消耗的
  计算资源**计费而不是按固定容量；**重复查询命中缓存**——SQL 与引用的数据快照都没变时不重新
  计算。明确"不做"：不是通用 OLTP 事务系统；不承诺摄取到可查询是零延迟，有明确的 SLA 窗口。

## 2. API & data model

- **1 分**：`POST /query` 直接跑在共享的一个大集群上，没有按租户划分计算资源，没有快照版本
  概念，没有缓存 key 设计。
- **4 分**：API：`POST /tenants/{t}/datasets/{d}/ingest`、`POST /tenants/{t}/query`（提交，
  绑定当前表快照版本执行）；架构分层——**存储层**（共享的不可变对象存储，按租户命名空间隔离，
  数据文件不可变，摄取 = 写新文件 + 原子推进快照版本指针，与目录/schema 服务共用"不可变版本
  化"这套底层模式）、**计算层**（每租户/每工作负载类一个独立的 **virtual warehouse**，专属计算
  节点，闲时自动挂起、下一次查询自动恢复，并发高峰时 **multi-cluster** 扩出额外集群）、**结果
  缓存**（key = 归一化查询文本 + 引用的表快照版本号）。

## 3. Failure modes & scale

- **1 分**：隔离靠 cgroup 限流在共享集群里做，noisy neighbor 本质没解决；查询绑定"当前时间"
  而不是快照版本，摄取和查询谁先谁后靠运气；缓存 key 用查询文本 + 挂钟时间，可能返回过期结果
  而不自知。
- **4 分**：**noisy neighbor** 用专属计算资源（每租户独立 warehouse）在架构层面解决，而不是
  共享池里限流；**同一租户内部**一个大查询也可能拖慢该租户自己的其它并发查询——需要每查询的
  资源上限/排队优先级，或用 multi-cluster 在同租户内部也做粒度更细的隔离；**摄取与长查询的
  竞态**——查询开始时绑定快照版本，之后摄取产生的新版本对这个查询不可见，旧版本文件在没有任何
  在途查询引用之后才回收（宽限期 + 引用检查，同 sd12 的 mark-and-sweep 思路）；**缓存正确性**
  ——key 必须是快照版本号而不是挂钟时间，这样缓存**天然版本化、永远不需要主动失效广播**，版本
  变了旧 key 自然不再命中（比 sd13 的推送失效更简单，因为读路径本来就带版本参数）；**计费准确
  性**——按 warehouse 实际的启动/挂起时间戳计量，"挂起失败卡住"必须能被发现，否则等于系统性
  多计费；**冷启动延迟**——闲时缩到零会有恢复延迟，要么分层 SLA（关键租户保留小规模常驻池），
  要么明确把这个延迟写进产品承诺，不能含糊带过。

## 4. Separation of concerns

- **1 分**：摄取、查询路由、计算资源调度、缓存、计费全部糅在一个服务里。
- **4 分**：**摄取服务**（写不可变文件 + 推进快照指针）→ **元数据/目录服务**（每租户表的快照
  版本，复用"不可变版本化"的目录模式）→ **查询路由**（解析查询、查结果缓存、绑定快照版本、
  分派到对应租户的 warehouse）→ **弹性计算池管理器**（每租户 warehouse 的 provision/挂起/恢复/
  multi-cluster 扩缩容）→ **结果缓存**（版本化 key，天然免失效广播）→ **计量计费管道**（独立
  记录每个 warehouse 实际的计算时长）。

## 5. Delivery beyond the diagram

- **1 分**：画完就停。
- **4 分**：灰度——新的查询路由先影子跑不接管真实流量，再逐租户切换；multi-cluster 自动扩缩容
  先在少数租户上金丝雀；核心指标：按租户的 p50/p99 查询延迟（重点看跨租户延迟是否相关联，
  关联说明隔离没做好）、结果缓存命中率、warehouse 挂起/恢复的可靠性（卡住未挂起 = 系统性多
  计费）、计费审计（抽查实际集群运行时长 vs 计费记录）。故障演练：某租户瞬间涌入大量并发查询、
  warehouse 恢复失败、摄取风暴下快照版本回收是否安全。能类比 Snowflake：virtual warehouse 的
  按秒计费与自动挂起/恢复、multi-cluster warehouse 的并发扩容、result cache 的"SQL+数据都没变
  就直接返回不起仓库"，本题几乎是这三个产品特性的重新推导。
