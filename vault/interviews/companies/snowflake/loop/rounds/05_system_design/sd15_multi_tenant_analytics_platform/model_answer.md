# 模型答案：Multi-Tenant Interactive Analytics Platform

> 取材：多租户 SaaS 分析平台的通用架构模式（存算分离 + 每租户专属计算池）；本题几乎是
> Snowflake **virtual warehouse / multi-cluster warehouse / result cache** 三个产品特性
> （`../../../01-company-brief.md` §1）的重新推导。本题来源为聚合站，按覆盖面练。

## 0. 两句话复述 + 不变量

**复述**：一个多租户交互式分析平台——持续摄取 + 即席交互查询并发进行，租户之间要互不拖累，
计算资源按需弹性伸缩且按实际消耗计费，重复查询命中缓存，单次查询始终看到一份自洽快照。

**不变量**：
1. **计算隔离**：一个租户的负载不能拖慢另一个租户的延迟或可用性——这是架构问题（专属资源），
   不是限流问题（共享资源里少分一点）。
2. **快照一致性**：单次查询在其整个执行期间看到的是查询开始时刻的一份完整快照，摄取并发推进
   不会让它看到"写了一半"的中间状态。
3. **弹性 + 按用计费**：闲置的计算资源要能缩到零，并发高峰要能扩出去，计费严格对应实际消耗的
   计算时长，不是按预留容量。
4. **重复查询命中缓存**：SQL 与其引用的数据快照都未变化时，直接返回缓存结果，不占用计算资源。

**不做**：不是通用 OLTP 事务系统（这里读远多于写，摄取以追加为主）；不承诺摄取到可查询是零
延迟——有一个明确的、写进 SLA 的"摄取可见延迟"窗口。

## 1. API 契约

```
POST /tenants/{t}/datasets/{d}/ingest    {rows | file_refs} → {snapshot_version}
POST /tenants/{t}/query                  {sql} → {query_id}    (提交，异步)
GET  /tenants/{t}/query/{query_id}       → {status, rows | cursor}
```
`query_id` 提交时就绑定了执行所依赖的表快照版本集合（下面第 3 节详述）。

## 2. 数据模型与架构分层

- **存储层**：共享的不可变对象存储，按租户命名空间物理隔离但基础设施可共享（存储便宜、可
  共享；计算贵、必须隔离——这是存算分离的核心理由）；数据文件只增不改。
- **元数据/目录层**：`table_snapshots(tenant, dataset, version, file_list_pointer,
  parent_version)` —— 与 sd14 的目录模式同构：不可变快照 + 原子指针切换，摄取 = 写新文件后
  把指针推进到新版本。
- **计算层**：每个租户（或租户内每个工作负载类，比如"BI dashboard"与"重批处理"分开）有一个
  独立的 **virtual warehouse**——一组专属计算节点，只服务这个租户/这个工作负载类的查询；闲置
  超过阈值自动挂起（缩到零，不计费）；下一次查询自动恢复（有文档化的冷启动延迟）；并发查询数
  超过单集群承载能力时，**multi-cluster** 自动扩出额外集群而不是排队。
- **结果缓存**：key = `hash(归一化 SQL 文本, 引用的每个表的 snapshot_version)`；不需要主动
  失效——版本号变了，旧 key 自然再也不会被命中，缓存本身永远"正确"，只是可能"不再被复用"。

## 3. 核心流程

**摄取**：写入方把新数据写成不可变文件，元数据服务原子地把该数据集的快照指针从版本 N 推进到
N+1；正在执行中、绑定在版本 N 上的查询完全不受影响（它们看到的文件集合从未变化）。

**查询**：
1. 查询提交时，对涉及的每个表读取"当前快照版本"并**锁定**（类似开启一个只读事务），后续整个
   执行期间都读这个版本，即使摄取并发推进到 N+1、N+2 也不影响这次查询。
2. 用 `(归一化 SQL, 锁定的快照版本集合)` 查结果缓存；命中直接返回，不占用任何计算资源。
3. 未命中：路由到该租户对应的 virtual warehouse；若已挂起则自动恢复；若当前集群排队过深则
   multi-cluster 扩出新集群执行。
4. 查询执行只读取被锁定版本引用的文件；执行完成后释放对该版本的引用。

**旧快照版本回收**：一个版本只有在"当前指针已经推进过它"且"没有任何在途查询还引用它"时才能
回收对应的旧文件——引用计数 + 宽限期（同 sd12 的 mark-and-sweep 思路），保证摄取与长查询永远
不会互相阻塞、也不会被过早回收的文件绊倒。

## 4. 失败模式与规模

| 问题 | 处理 |
|---|---|
| Noisy neighbor：一个租户的重查询拖慢另一个租户 | 每租户专属 virtual warehouse（架构级隔离），不是共享池里限流；物理上互不共享计算节点 |
| 同一租户内部一个大查询拖慢该租户自己的其它并发查询 | 同租户内按工作负载类拆分 warehouse（dashboard 类 vs 批量类）；单查询设资源上限与超时；必要时该租户自己的 multi-cluster 扩容吸收内部并发 |
| 摄取与长查询竞态 | 查询绑定快照版本，摄取推进指针不影响已绑定的查询；旧版本引用计数 + 宽限期回收 |
| 结果缓存返回过期结果 | key 直接是快照版本号，不是挂钟时间——版本变了旧 key 天然失效，不需要失效广播 |
| Warehouse 挂起失败卡在运行态 | 独立的健康检查发现"应挂起但未挂起"的实例，强制回收；这类故障必须能被发现，否则等于系统性多计费 |
| 冷启动延迟影响体验 | 分层 SLA：关键租户/工作负载保留小规模常驻池不缩到零；其余租户接受几秒级冷启动，作为成本换延迟的显式权衡写进产品文档 |
| 共享物理存储的 I/O 热点（计算隔离了，存储可能还是共享的） | 存储层按租户做 I/O 配额/QoS，不能只隔离计算而假设存储天然公平 |
| 计费准确性 | 按 warehouse 实际启动/挂起的时间戳计量，独立的计量管道，定期抽查审计 |

## 5. 分层与组件

```
摄取服务（写不可变文件 + 原子推进快照指针）
        ↓
元数据/目录服务（每租户表的快照版本，复用不可变版本化模式）
        ↓
查询路由（绑定快照版本 · 查结果缓存 · 分派到对应租户 warehouse）
        ↓ 缓存未命中
弹性计算池管理器（每租户/每工作负载类 virtual warehouse：挂起/恢复/multi-cluster 扩缩容）
        ↓
结果缓存（版本化 key，天然免失效广播）
计量计费管道（独立记录每个 warehouse 实际运行时长）
```

## 6. Rollout / 测试 / 监控

- **灰度**：新查询路由先影子跑（不接管真实流量，只对比结果与延迟），再逐租户切换；multi-cluster
  自动扩缩容先在少数中等规模租户上金丝雀，观察扩容触发是否过于敏感或迟钝。
- **监控**：按租户的 p50/p99 查询延迟（**重点看跨租户延迟相关性**——如果一个租户负载升高导致
  另一个租户延迟也升高，说明隔离没做好）；结果缓存命中率；warehouse 挂起/恢复可靠性；计费审计
  （抽查实际集群运行时长 vs 计费记录的差异）。
- **测试**：一个租户瞬间涌入大量并发查询不影响其它租户；长查询执行期间对应数据集持续摄取，
  查询结果自始至终自洽；warehouse 恢复失败时的降级路径；缓存 key 版本化后新旧版本各自命中
  互不干扰。

## 7. 用 Snowflake 自己的原语作参照

**Virtual warehouse** 就是本题"每租户专属计算资源、按秒计费、闲时自动挂起、下一次查询自动
恢复"的原型；**multi-cluster warehouse** 就是"并发高峰自动扩出额外集群而不是排队"；**result
cache**（SQL + 数据都未变时 24 小时内直接返回，完全不起仓库）就是本题"重复查询命中缓存、不
占用计算资源"的产品化实现；micro-partition 的不可变性是"摄取与查询并发下快照一致性"能够成立
的底层原因——这几乎是把 Snowflake 自己的核心架构决策重新推导了一遍。
