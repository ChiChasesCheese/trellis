# 追问预案（≥8 条）

> 该题没有一手候选人报告留下具体追问逐字稿（`catalog/raw/system_design.md` §1.10 标注置信度 LOW-MED，靠对 Snowflake 真实产品 Dynamic Tables 的推理补足），以下均为基于题目结构与 Dynamic Tables 真实机制推出的高概率追问，不标(一手)。

## 1. 什么样的视图定义可以做增量刷新，什么样必须全量？

**期望要点**：基于算子树做静态分析——过滤、投影、等值 JOIN、可加性聚合（SUM/COUNT 配合变更行的正负号）支持增量维护；非确定性函数（如 `RANDOM()`）、依赖全局排序位置的窗口函数、需要全表扫描才能算对的聚合（如 MEDIAN、去重计数在某些实现下）不支持增量，必须全量重算。这个判定是视图定义级别的静态属性，不是运行时临时决定的。

**反例**：说"简单的视图增量，复杂的视图全量"——"简单/复杂"不是一个可操作的判定标准，面试官会追问"具体什么算子算简单"，候选人需要能举出具体的算子类别而不是模糊的难度描述。

## 2. 怎么保证用户查询到的视图结果是一致的快照，不会出现依赖链条上新旧数据混杂？

**期望要点**：每个视图的每次物化都是不可变的新版本（不是原地更新），并且记录这次计算时依赖的上游具体版本（`source_versions_snapshot`）；查询时读到的是某个视图当前指向的版本，这个版本内部自洽（它依赖的上游也是计算时锁定的那个版本），不会因为上游后续又刷新了新版本而让已经产生的旧版本变得"不自洽"——这本质上是 DAG 结构上的 MVCC。

**反例**：说"每次上游一变，立刻原地更新所有下游"——原地更新在多层依赖图上无法避免"上游 B 已经更新完、依赖 B 的视图 A 还没来得及更新"这个时间窗口内被查询到的中间不一致状态，除非配合复杂的锁机制阻塞所有查询，代价过高。

## 3. 基础表的一次变更，怎么避免让整个下游依赖图瞬间级联触发大量重算？

**期望要点**：失效传播只是"标记待刷新"，不等于立刻执行；调度器按每个视图声明的新鲜度目标（`target_lag`）来决定什么时候真正触发刷新，同一个时间窗口内的多次上游变更可以被合并成一次刷新处理，从而把瞬时的级联冲击摊平到各自的刷新周期里。

**反例**：说"上游一变就立刻通知并触发所有下游立刻重算"——如果依赖图很深很宽，这会在瞬间产生大量并发的重算任务，把计算资源打爆，且大部分是不必要的（用户其实只需要 5 分钟内的新鲜度，不需要毫秒级更新）。

## 4. 如果某个视图的增量维护逻辑长期运行后出现了漂移（增量算出来的结果和真实全量结果不一样了），怎么发现？

**期望要点**：定期对拍——抽样对某些视图同时跑一次"继续增量维护"和"从头全量重算"，比较两者结果是否一致，发现漂移立刻报警并触发一次强制全量重算修正状态；这类漂移通常来自增量算子实现的边界 bug（比如某个聚合函数的增量维护逻辑没有正确处理删除操作）。

**反例**：完全没有验证机制，假设增量维护实现一旦写对就永远正确——软件系统长期运行难免有边界情况没覆盖到，没有对拍机制意味着漂移可能悄无声息地累积很久才被发现，而那时候可能已经产生了大量基于错误数据的下游决策。

## 5. 用户修改了一个视图的 SQL 定义（比如加了一个 JOIN），怎么处理正在进行的刷新任务和已有的历史物化版本？

**期望要点**：视图定义变更后要重新走一遍增量/全量判定（新的算子树可能改变了能否增量维护的结论），并且触发一次全量重算建立新定义下的第一个物化版本；正在进行中的、基于旧定义的刷新任务应该被允许完成或安全取消，不应该让新旧定义的计算逻辑混杂在同一次刷新里产生错误结果；旧定义下的历史物化版本可以保留一段时间供审计/回溯，但新的查询默认走新定义。

**反例**：说"直接把新 SQL 换上去，下次刷新自然就用新逻辑了"——没有考虑到"下次刷新"之前，用户查询到的可能还是旧定义算出来的结果，这本身没问题，但如果换 SQL 的动作和正在进行中的刷新任务之间没有明确的顺序保证，可能出现用一半旧逻辑一半新逻辑算出来的错误中间态。

## 6. 依赖图里出现循环依赖（A 依赖 B，B 又直接或间接依赖 A）怎么办？

**期望要点**：这在语义上是非法的（视图的计算必须能按拓扑序完成，循环依赖意味着无法确定计算顺序），系统应该在 `CreateView`/更新视图定义时就做环检测，检测到循环直接拒绝该操作并明确报错，而不是等到运行时才发现调度器陷入死锁。

**反例**：完全没有考虑这个边界情况，假设依赖图永远是合法的 DAG——面试官很可能会主动问"如果用户不小心定义出了循环依赖会怎样",不能被问到才想起来这个问题。

## 7. 系统规模扩大（视图数量从数千涨到数十万），哪里最先撑不住？

**期望要点**：先识别瓶颈——依赖图的拓扑序计算（如果每次变更都对全图重新排序，代价会随图规模增长，应该做增量式的拓扑序维护而不是每次全量重算）；调度器需要处理的待刷新队列吞吐（类比 sd02 cron scheduler 的分片扩展思路）；历史物化版本的存储量（需要更积极的版本回收策略）。扩容方向：依赖图按业务域/租户分片管理；调度器水平扩展并按视图 id 分片；历史版本保留期收紧。

**反例**："存储加大点就行"——没有识别到拓扑序计算和调度队列吞吐才是更早触及的瓶颈，而不是纯粹的存储容量问题。

## 8. 怎么测试这套系统，尤其是验证"失效传播精确、不多算也不少算"这个属性？

**期望要点**：构造已知结构的测试依赖图（包含菱形依赖——A 同时被 B 和 C 依赖，B 和 C 又都被 D 依赖），对基础表做变更，验证受影响的下游被正确标记刷新、不受影响的兄弟分支没有被误伤；对拍机制（增量结果 vs 全量结果）作为持续运行的正确性回归测试，而不只是上线前的一次性验证。

**反例**：只用一条线性依赖链（A → B → C）做测试——线性链条无法暴露"菱形依赖"这类更容易出 bug 的拓扑结构（比如 D 因为 B 和 C 都变了而被重复触发两次刷新，如果没有合并逻辑会做无谓的重复计算）。
