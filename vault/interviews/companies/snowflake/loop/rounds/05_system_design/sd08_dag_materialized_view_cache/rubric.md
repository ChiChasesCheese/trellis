# 评分 rubric（五维，1–4 分/维，满分 20）

> 依据 `loop/LOOP_GUIDE.md` §6 与 `catalog/raw/system_design.md` §1.10。这题明确要求"用 Snowflake 自己的原语作参照"——因为它本来就是 Dynamic Tables 的简化版，rubric 对"是否能主动把设计对照到 Dynamic Tables 的 `TARGET_LAG`/依赖图机制"给出明确加分。

## 1. Problem framing（需求抽取）

- **1 分**：把这题当成"给视图加个缓存"处理，没有意识到"依赖图""增量 vs 全量的判定"和"一致快照"是三个独立但互相牵扯的难点；直接开始画视图节点图不谈不变量。
- **4 分**：两句话复述——"多层依赖的视图要被物化缓存，底层数据变化时自动传播失效并按需重新计算，但用户任何时候查询到的视图快照必须是逻辑自洽的（不能一部分视图刷新到新版本、依赖它的视图还停在旧版本）"；显式说出不变量——**依赖图内的物化结果要么整体反映某个一致的时间点，要么明确标注为过时**（不允许"部分新、部分旧"被悄悄混在一起返回）、**失效传播是精确的**（只有真正受影响的下游才失效，不能过度失效导致不必要的重算）、**增量/全量的选择是可判定的**（基于视图定义的算子特征，不是拍脑袋）；主动确认新鲜度要求（类比 `TARGET_LAG`——用户能接受视图落后基础数据多久）。

## 2. API & data model（权重最高）

- **1 分**：只有一张"视图定义表"，没有单独建模依赖关系；没有区分"视图的定义"和"视图当前物化出来的具体版本"。
- **4 分**：数据模型区分 **`view_definitions`（视图 SQL/算子树、声明的新鲜度目标、依赖的父视图列表）**、**`dependency_graph`（边表：view_id -> depends_on_view_id，用于正向查失效传播、反向查"这个视图依赖谁"）**、**`materializations`（每个视图当前物化出来的具体版本：`view_id, version, data_ref, source_versions_snapshot, computed_at`，其中 `source_versions_snapshot` 记录了这次物化是基于哪些上游版本算出来的——这是保证一致快照的关键字段）**；API 上区分**声明式注册**（`CreateView(sql, target_lag)`）与**查询接口**（`Query(view_id, [as_of_version])`，默认返回最新的、依赖链条上版本自洽的物化结果）。

## 3. Failure modes & scale（本题权重也很高）

- **1 分**：增量 vs 全量的判断说"看情况"没有具体标准；一致快照说"尽量保证"没有具体机制；失效传播说"通知所有下游"没有讨论怎么避免级联爆炸式的重算。
- **4 分**：**增量 vs 全量判定**——基于视图定义的算子树做静态分析：如果算子链条只包含支持增量维护的操作（过滤、投影、等值 join、部分聚合等，且没有非确定性函数、没有依赖行位置的窗口函数），选择增量刷新（只处理上游变更的行）；一旦包含不可增量的算子，或者上游发生了结构性变更（schema 变了），退化为全量重算；还要考虑增量链条"退化"场景——如果上游连续多次微小变更、增量维护的中间状态碎片化到一定程度（类似 LSM 的碎片化），周期性做一次全量重算收敛状态。**一致快照**——每个视图的物化版本都要记录"这次计算基于哪些上游的哪个版本"（`source_versions_snapshot`），查询一个视图时，如果发现它依赖的某个上游有更新版本但自己还没消费，要么返回"自己当前这个虽旧但内部自洽的版本"（默认，保证自洽性优先于绝对新鲜度），要么按用户声明的 `TARGET_LAG` 阻塞等待刷新完成后再返回；这本质上是一个多版本并发控制（MVCC）问题在 DAG 结构上的推广。**失效传播**——用拓扑序处理，基础表变更后按依赖图的拓扑顺序逐层标记下游"待刷新"，但**不是立刻全部重算**，而是让每层的刷新任务按需调度（可以合并同一时间窗口内的多次上游变更，一次刷新处理掉，而不是每次上游变更都触发一次下游重算），避免级联爆炸。

## 4. Separation of concerns

- **1 分**：把"依赖图维护""增量/全量判定""调度触发重算""查询路由"全部揉在一起。
- **4 分**：分层清楚——**依赖图管理层**（维护 DAG 结构，提供拓扑序查询、正向/反向遍历）；**刷新判定层**（对每个视图独立判断增量还是全量，纯粹基于视图定义的静态分析，与调度时机无关）；**调度/触发层**（监听上游变更，按拓扑序、按需（可合并批处理）触发下游刷新任务，类比 sd02 的调度器设计）；**查询/一致性层**（响应用户查询，决定返回哪个物化版本，处理"依赖链条部分过时"的语义）。

## 5. Delivery beyond the diagram（rollout / 测试 / 监控）

- **1 分**：画完图不谈测试和监控。
- **4 分**：讲到监控指标（各视图实际新鲜度 vs 声明的 `TARGET_LAG` 的差距、增量刷新的处理行数/耗时、全量重算触发频率、依赖图的最大深度/宽度对刷新延迟的影响）；讲到怎么测试增量与全量计算结果的一致性（对拍：定期抽样对比增量维护结果和从头全量算一遍的结果是否一致，发现漂移就报警）；讲到 rollout 时新的增量判定规则先在允许离线验证的视图上跑影子对比；讲到依赖图变更（用户改了视图定义）如何安全地重新计算依赖关系而不影响正在进行的刷新。
