# 模型答案：设计 DAG Cache for Materialized Views

> 取材：PracHub "Design Cache for DAG-Based Query Views"；`../../raw/process_research.md` §3.2 #11；与 Snowflake Dynamic Tables 的产品对照见 `catalog/raw/system_design.md` §1.10。按 `LOOP_GUIDE.md` §6 主线组织。

## 0. 两句话复述 + 不变量

**复述**：多层依赖的视图（形成一个 DAG）需要被物化缓存，底层基础表变化时系统要自动判断增量还是全量重算受影响的下游视图，且用户任何时候查询到的视图结果必须是逻辑自洽的一致快照，不能出现"部分视图刷新到新版本、它依赖的视图还停在旧版本"这种自相矛盾的中间状态。

**核心不变量**：

1. **快照自洽**：一次查询看到的整条依赖链，要么全部反映某个一致的时间点，要么明确是"内部自洽但相对旧"的一个更早时间点，绝不允许新旧数据在同一次查询结果里混杂。
2. **失效传播精确**：只有真正依赖某个变更的下游才被标记为待刷新，不产生不必要的重算。
3. **增量/全量的选择可判定**：基于视图定义的算子特征做静态判断，而不是运行时的临时决策。
4. **刷新是异步的、可控速率的**：基础表持续变化不应该导致下游视图疯狂重算，新鲜度目标是可配置的（类比 `TARGET_LAG`）。

明确"不做什么"：不追求"实时"（毫秒级）的下游更新，新鲜度是用户可配置的目标而不是绝对承诺；不保证所有视图定义都能做增量维护（有些算子天然只能全量）。

## 1. API 契约

```
CreateView(sql, target_lag: "5 minutes") -> {view_id}
  # 声明式注册；系统解析 SQL 得到依赖的上游视图/表列表，加入依赖图

GetView(view_id, as_of_version?) -> {rows, materialized_version, computed_at, is_stale: bool}
  # 默认返回最新的、依赖链条自洽的物化版本；is_stale 标注该版本是否落后于 target_lag 声明的新鲜度目标

GetDependencyGraph(view_id) -> {upstream: [...], downstream: [...]}
```

- `target_lag` 是用户对新鲜度的声明性目标（类比 Dynamic Tables 的 `TARGET_LAG`），系统据此决定刷新调度的优先级和频率，不是每次上游一有变更就立刻触发刷新。

## 2. 数据模型

```
view_definitions(
  view_id, sql, operator_tree, target_lag, created_at
)

dependency_graph(
  view_id, depends_on_view_id
)
-- 边表，支持正向查"我依赖谁"和反向查"谁依赖我"（失效传播用反向）

materializations(
  view_id, version, data_ref, source_versions_snapshot(jsonb),
  computed_at, refresh_type[incremental|full]
)
-- 每个视图当前（及若干历史）物化版本
-- source_versions_snapshot: {upstream_view_id: upstream_version, ...}
-- 这是保证一致快照的关键——记录这次物化是基于上游的哪个具体版本算出来的

pending_refresh(view_id, triggered_by_version, status[queued|running|done])
-- 待刷新队列，按拓扑序调度
```

**`source_versions_snapshot` 的作用**：查询某个视图时，如果需要严格验证它依赖的上游是否也是"当时那个版本"，可以沿着这个字段递归核对整条链路的版本一致性——但实际实现中通常不需要每次查询都递归核验，而是让刷新调度器本身保证"一个视图开始刷新时，会把当时所有直接上游的最新已完成版本记录进快照"，从而保证物化出来的每个版本本身就是自洽的。

## 3. 核心流程

**增量 vs 全量的判定（发生在视图创建/更新时，是一次静态分析，不是每次刷新都重新判断）**：解析 `operator_tree`，检查是否只包含支持增量维护的算子——过滤（WHERE）、投影（SELECT 部分列）、等值 JOIN、可加性聚合（SUM/COUNT，配合变更行的正负号）——如果全部满足，标记该视图 `refresh_type=incremental`；一旦包含不支持增量的算子（非确定性函数如 `RANDOM()`、依赖全局排序位置的窗口函数、需要重新扫描全表才能算对的聚合如 MEDIAN），标记为 `full`。这个判定结果缓存在 `view_definitions` 里，视图定义不变就不需要重新判断。

**失效传播（拓扑序 + 按需调度，不是立刻级联重算）**：基础表变更产生一个变更事件，沿 `dependency_graph` 的反向边按拓扑序标记所有下游视图为"有新的上游变更待处理"（写入 `pending_refresh`，不是立刻触发计算）；调度器按每个视图声明的 `target_lag` 决定什么时候真正执行刷新——如果 `target_lag` 是 5 分钟，同一个 5 分钟窗口内上游即使变更了 100 次，也只需要触发一次刷新去处理这批累积的变更，而不是每次变更都级联触发一次重算（这是避免"级联爆炸"的关键设计）。

**刷新执行**：
- **增量刷新**：只读取上游自上次刷新版本以来的变更集（类比 Streams 的 offset 消费），应用到当前物化结果上做增量更新（如过滤算子直接判断新行是否满足条件、聚合算子对增量行做加减）。
- **全量刷新**：重新从头计算整个视图，替换掉旧的物化结果。
- 无论增量还是全量，刷新完成后产生一条新的 `materializations` 记录，`source_versions_snapshot` 记下这次计算基于的上游版本，原子地把该视图指向这个新版本（旧版本保留一段时间供正在进行中的查询继续读取，不强制打断）。

**查询路径**：`GetView` 默认返回该视图当前指向的最新物化版本；由于每个视图的刷新是独立调度的（依赖图深层的视图可能刷新得比浅层慢），"最新"未必等于"完全跟上了当前时刻的基础表状态"，但**它自己指向的这个版本内部是自洽的**——因为它的 `source_versions_snapshot` 锁定了计算时依赖的具体上游版本，不会出现"用了 B 的新版本却混入了 C 的旧版本"这种不自洽。

## 4. 失败模式与规模

**一致快照的本质是 DAG 上的 MVCC**：把每个视图的每次物化都当作一个不可变版本（而不是原地更新），配合"记录计算时依赖的上游版本"，天然获得类似 MVCC 的读一致性——读者永远读到某个完整的、内部自洽的版本组合，写者（刷新任务）产生新版本不会影响正在被读取的旧版本，这是避免"读到中间不一致状态"的核心手段，不需要对读路径加锁。

**增量链条的碎片化与周期性收敛**：连续多次小规模增量更新可能导致内部维护状态碎片化（类似 LSM 的 compaction 需求），系统应该周期性（或碎片化指标超过阈值时）主动触发一次全量重算收敛状态，避免增量维护的正确性和性能随时间退化。

**失效传播的扇出爆炸**：如果依赖图的某个节点扇出（被大量下游依赖）非常大，一次上游变更理论上要通知所有下游，但配合"按 `target_lag` 批量合并触发"的调度策略，可以把扇出爆炸的冲击平摊到各下游各自的刷新周期里，而不是瞬间全部触发。

**Schema 变更的处理**：上游视图的 schema 发生结构性变更（加列、改类型）时，增量判定要重新评估（之前判定为可增量的视图可能因为 schema 变了而不再满足增量条件），保守起见触发一次全量重算并重新走一遍静态分析。

**规模估算**：假设依赖图有数千到数万个视图节点，深度可能达到十几层；刷新调度器需要能高效计算拓扑序（增量维护拓扑序而不是每次变更都重新全图排序）；物化结果本身的存储量取决于视图基数，需要对历史版本做保留期管理（旧版本超过一定时间且没有正在进行的查询引用后清理）。

## 5. 分层与组件

- **依赖图管理层**：维护 DAG 结构，提供高效的拓扑序、正向/反向遍历接口，与具体的刷新逻辑解耦。
- **刷新判定层**：纯函数式的静态分析（视图定义 → 增量/全量判定），与调度时机完全无关，可以独立测试。
- **调度/触发层**：监听上游变更、按 `target_lag` 批量合并、按拓扑序派发刷新任务，架构上可以直接复用 sd02 cron scheduler 的调度器设计（"任务到点/到条件时执行"是同一个模式）。
- **查询/一致性层**：响应查询请求，返回内部自洽的物化版本，管理历史版本的生命周期。

## 6. rollout/测试/监控

- **监控**：各视图实际新鲜度（`now() - materializations.computed_at`）相对声明的 `target_lag` 的差距分布；增量刷新处理的行数/耗时 vs 全量重算的对比；全量重算触发频率（异常升高可能说明增量判定逻辑有问题或上游频繁做结构性变更）；依赖图深度/宽度对端到端刷新延迟的影响。
- **测试**：**对拍**——定期抽样对某个视图同时跑一次"从当前增量维护状态继续"和"从头全量重算"，对比结果是否一致，发现漂移立刻报警（这是验证增量维护正确性最直接也最重要的手段）。
- **rollout**：新的增量判定规则（比如决定放开支持某类之前认为不可增量的算子）先在允许离线对比的视图上跑影子验证，确认增量结果和全量结果长期一致后再推广。

## 7. 用 Snowflake 自己的原语作参照

这道题几乎是 Snowflake **Dynamic Tables**（`01-company-brief.md` §1）的重新发明：Dynamic Tables 把"stream + task + MERGE"这套手工编排声明化，用户只需要声明 `TARGET_LAG`，系统自动推导依赖图、自动判断增量还是全量刷新，2026-07 还加入了 **Adaptive Refresh**（动态调整增量/全量策略）。本题设计里的 `target_lag` 直接对应 `TARGET_LAG`，"基于算子树静态判断能否增量维护"对应 Dynamic Tables 底层判断"能否用 Streams 增量消费还是要退化成全表 MERGE"的机制，"failure/schema 变更时退化为全量"也是 Dynamic Tables 真实的行为模式。更底层地看，本题"增量刷新读取上游自上次版本以来的变更集"直接对应 **Streams**——offset 书签指向表版本、只有在消费事务里才推进 offset、消费得到的是净变化而不是全表；本题的 `source_versions_snapshot` 机制则类似 Streams 消费位点的推广（从单个流推广到整个 DAG 的多个上游）。面试时可以直接说："这本质上是在重新设计 Snowflake 自己的 Dynamic Tables——如果让我重新做一次，我会直接在真实产品里用 Dynamic Tables 而不是自建这套系统，但设计的核心难点（依赖图、增量判定、一致快照）是完全一致的。"

## 8. 45 分钟口述时间表

- **0–5 min**：复述题目 + 不变量（快照自洽、失效传播精确、增量/全量可判定、刷新可控速率），确认新鲜度目标（类比 `TARGET_LAG`）。
- **5–12 min**：API 契约（声明式注册 + 查询）+ 数据模型（view_definitions / dependency_graph / materializations，`source_versions_snapshot` 的关键作用）。
- **12–22 min**：核心流程——增量/全量的静态判定、拓扑序失效传播与按需批量刷新、查询路径的自洽性保证。
- **22–35 min**：失败模式——一致快照的 MVCC 本质、增量碎片化的周期性收敛、失效传播的扇出爆炸对策、schema 变更处理、规模估算。
- **35–42 min**：分层图 + rollout（增量判定的影子对拍）+ 监控指标。
- **42–45 min**：总结 + 明确对照 Snowflake Dynamic Tables 与 Streams，反问面试官。
