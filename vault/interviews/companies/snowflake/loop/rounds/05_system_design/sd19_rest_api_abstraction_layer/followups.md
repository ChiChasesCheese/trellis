# 追问预案（8 条，全部（推断））

## 1. 为什么不直接让每个团队用 HTTP 库？
**期望要点**：横切关注点重复实现、行为不一致、事故难追踪；统一层让重试、超时、鉴权一次做对。
**反例**："团队自己负责"。

## 2. 写操作超时了，到底执行没有？
**期望要点**：客户端无法知道；靠幂等键让重试安全；没有幂等键就不重试，把"结果未知"显式暴露给调用方。
**反例**：直接重试。

## 3. 重试会不会把一个半死的后端彻底打死？
**期望要点**：重试预算（比例上限）、指数退避 + 抖动、熔断器、尊重 `Retry-After`。
**反例**：固定间隔重试 3 次。

## 4. 后端把字段改名了，老调用方怎么办？
**期望要点**：IDL 版本化、旧版本端点保留弃用期、CI 做 IDL diff 拦截破坏性变更、SDK 语义化版本。
**反例**：通知所有团队一起升级。

## 5. 三种语言的 SDK 怎么保证行为一样？
**期望要点**：代码生成 + 共享规范；契约测试同一套用例跑三种 SDK；运行时核心逻辑尽量薄、规则写在配置里。
**反例**：各语言团队人工对齐。

## 6. 为什么要 deadline 传播？
**期望要点**：上游已经放弃等待时，下游继续干活是浪费；传播剩余时间，下游据此早停。
**反例**：每层各设一个固定超时。

## 7. 什么时候上中心网关？
**期望要点**：需要集中生效的策略（配额、审计、幂等存储）、需要不升级 SDK 就改策略时；代价是多一跳和网关高可用。
**反例**："网关一定更好"。

## 8. token 刷新在高并发下会出什么问题？
**期望要点**：大量请求同时发现过期、同时刷新造成雷群和鉴权服务过载；singleflight + 提前刷新 + 刷新失败时短暂复用旧 token（若未过期）。
**反例**：每个请求各自刷新。
