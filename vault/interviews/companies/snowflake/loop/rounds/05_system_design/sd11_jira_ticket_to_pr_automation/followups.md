# 追问预案（≥8 条）

> `catalog/raw/system_design.md` §1.14 记录了一手候选人报告"very unique"这个评价，但正文 403 只有摘要，没有留下具体追问逐字稿。以下均为基于"异步任务编排 + LLM 步骤失败模式 + 人工把关"这个题目结构推出的高概率追问，不标(一手)，但第 1、2 条是这类题几乎必问的核心边界。

## 1. 如果自动化流程连续多次都生成出高质量、测试全部通过的代码，能不能跳过人工 review 直接合并？

**期望要点**：**不能**，态度要坚决——不管自动化验证（编译、测试）表现多好，这些验证本身的覆盖率是有限的，不能替代人类对需求理解准确性、代码质量、潜在副作用的判断；"高置信度"是一个概率性系统给出的信号，不是正确性的证明，一旦允许"足够自信就自动合并"这个例外，"人工把关"这条不变量就形同虚设，题目本身也明确说"自动化系统本身没有权限直接合并代码"。

**反例**：回答"如果连续 5 次生成结果一致且测试都过，可以自动合并，这样能提高效率"——这正是这道题最想筛掉的回答，说明候选人把"效率优化"凌驾于题目明确给出的核心约束之上，没有理解为什么这条边界是刻意设计、不可协商的。

## 2. LLM 生成的代码"看起来没问题"但实际上理解错了需求，怎么发现？

**期望要点**：区分"硬失败"（调用报错、超时）和"软失败"——生成内容本身不会报错，必须靠独立的验证步骤（编译、lint、跑测试）才能发现问题；但也要坦诚承认自动化验证本身有局限（测试覆盖不到的逻辑错误可能蒙混过关），这正是为什么最终必须有人工 review 这道关卡，而不是指望纯自动化验证能兜住所有错误。

**反例**：说"只要能跑通所有测试就说明代码是对的"——过度信任自动化测试的覆盖率，没有意识到"测试通过"和"真正满足需求"之间仍然可能存在差距，这正是这道题想考察的关键认知。

## 3. 一个工单的自动化流程反复失败（比如生成的代码始终无法通过测试），会怎么样？

**期望要点**：设置重试上限（如连续 3 次生成都无法通过验证），超过上限后停止自动重试，转入需要人工介入的失败队列，并附带完整的尝试历史（每次生成了什么、测试失败原因是什么）供工程师参考；不能无限重试消耗计算资源，也不能默默放弃而不通知任何人。

**反例**：说"一直重试直到成功为止"——某些工单本身可能超出当前自动化系统的能力范围（需求描述不清楚、涉及的改动过于复杂），无限重试既浪费资源也不会产生更好的结果，需要一个明确的"放弃并转人工"的退出条件。

## 4. 人工 reviewer 拒绝了生成的 PR 并给了反馈，接下来会发生什么？

**期望要点**：reviewer 的反馈应该被当作比自动化测试失败信息质量更高的信号，重新喂给"生成代码"步骤作为下一轮尝试的额外上下文，而不是简单打回让流水线从零开始或者用完全相同的 prompt 重跑一次；这样每一轮迭代都应该比上一轮更接近人类真正想要的结果。

**反例**：把"拒绝"简单实现成"删除这次生成、清空所有上下文重新开始"——浪费了 reviewer 花时间写的反馈信息，也没有让系统从人类反馈中"学习"（至少是这次流水线实例内的上下文学习）。

## 5. 多个工单并发处理时，会不会互相抢占同一份代码库资源（比如都要在同一个仓库里改代码、跑测试）？

**期望要点**：每个工单的自动化流程应该在**隔离的工作副本/分支**上进行（类似每个 PR 都有自己独立的 feature branch 和测试沙箱），互相之间不共享可变状态；如果测试环境/编译资源本身是稀缺的共享资源，需要引入排队和公平调度机制（可以直接复用 sd03 SQL notebook 或 sd07 限流器的思路）管理多个流水线对这类资源的竞争，防止一个工单占满测试资源导致其他工单排队过久。

**反例**：假设所有工单可以共享同一份工作目录顺序处理——这既没有利用好并发处理的能力，也容易因为一个工单的中间状态（未完成的代码修改）污染另一个工单的处理环境。

## 6. 如果 Jira webhook 因为网络问题重复投递了同一个工单的触发事件，系统会不会启动两条重复的自动化流程？

**期望要点**：触发接口需要按 `jira_ticket_id` 做幂等检查——如果该工单已经有一条进行中或已完成的流程，直接返回已存在的 `automation_id`，不创建第二条流水线；这与 Stripe webhook 题"消费者按幂等键去重"、sd05 队列题"at-least-once 投递配合消费者幂等"是同一类问题的不同产品表现。

**反例**：没有任何幂等检查，每次收到 webhook 都创建一条新的自动化流程——会导致同一个工单被并发处理多次，产生多个冲突的 PR，是明显的设计疏漏。

## 7. 如果生成代码的编码 agent 本身超时或者不可用（比如上游服务临时故障），流水线应该怎么处理？

**期望要点**：这属于"硬失败"，按标准的指数退避重试策略处理（可以直接复用 sd02 调度器的失败重试设计）；如果编码 agent 服务持续不可用超过一定时长，应该暂停该阶段的所有待处理任务（而不是持续无效重试消耗资源），并触发告警通知系统本身出了问题，等服务恢复后再自动续跑，而不需要重新触发每一个受影响的工单。

**反例**：说"这一步失败就直接判定整个工单自动化失败，转人工"——如果只是上游服务临时抖动，没有必要让所有排队中的工单都被判定为失败，更合理的处理是暂停等待服务恢复后继续，只有真正超过重试/超时上限才转人工。

## 8. 系统规模扩大（同时有几百个工单在跑自动化流程）时，哪里最先撑不住？

**期望要点**：先识别瓶颈——编排层的并发调度能力（类比 sd02 调度器的分片扩展）；测试沙箱/编译资源的排队等待时长（稀缺共享资源，需要排队公平调度）；生成代码这一步本身如果依赖单一的模型服务实例，可能存在吞吐上限。扩容方向：编排层水平扩展并按工单 id 分片；测试资源池独立扩容并引入优先级/公平队列；生成步骤对接可水平扩展的模型服务集群。

**反例**："给自动化系统多分配点机器就行"——没有具体到"测试资源"和"模型调用吞吐"这两个更可能先触及上限的瓶颈，笼统地"加机器"不能解决这类依赖外部稀缺资源（测试环境、模型服务配额）的问题。
