# 评分 rubric（五维，1–4 分/维，满分 20）

> 依据 `loop/LOOP_GUIDE.md` §6 与 `catalog/raw/system_design.md` §1.14。一手候选人形容这题"very unique"——它不是一道能套用标准模板（KV store/队列/限流器）就能答完的题，rubric 特别看重候选人能不能把"LLM 步骤本身不确定、可能产生看似合理但错误的输出"这个新维度的失败模式，纳入到传统的异步任务编排设计里。

## 1. Problem framing（需求抽取）

- **1 分**：把这题当成普通的"异步任务队列"题，套用标准的任务调度模板，完全没有单独讨论"其中一步是 LLM/编码 agent"这件事带来的特殊性（输出不确定、可能"看似成功但实际错误"）。
- **4 分**：两句话复述——"工单被标记后，要触发一个多步骤、长耗时的自动化流程（理解需求→生成代码→跑测试→开 PR），过程可能在任意一步失败并需要重试，多个工单要能并发处理且互不影响，且无论流程多顺利，最终代码变更必须经过人工 review 才能合入，自动化系统没有直接合并权限"；显式说出不变量——**人工 review 是不可绕过的强制关卡**（这是本题最核心、面试官大概率会反复确认的一条）、**流程状态持久化、可恢复**（长耗时多步骤流程不能因为某个组件重启就从头再来或者彻底丢失进度）、**LLM 步骤的失败是"软失败"**（生成的代码不是"报错"就是"没报错"，而是需要额外验证——跑测试、检查编译——才能判断这一步是不是真的成功了）；主动确认失败重试的上限、是否需要给 LLM 生成的代码结果加置信度/风险分级。

## 2. API & data model（权重最高）

- **1 分**：只有一个"任务表"，把"理解需求""生成代码""跑测试""开 PR"这几个完全不同性质的步骤压缩成一个不透明的 status 字段；没有为"人工 review 关卡"设计任何数据结构。
- **4 分**：把整个处理流程建模成一个**显式的多阶段状态机/流水线**——`tickets(ticket_id, status[triaged|analyzing|generating|testing|pending_review|approved|merged|failed], current_step, retry_count)`，每个阶段有自己独立的产出记录（`analysis_result`、`code_diff`、`test_results`），阶段之间通过流水线顺序推进而不是一个大而化之的状态；**`pending_review` 是一个显式的、必须由人工动作才能推进出去的状态**（`ApproveForMerge(ticket_id, reviewer_id)` / `RejectWithFeedback(ticket_id, feedback)`），系统内部没有任何路径能绕过这个状态直接到达 `merged`；API 上区分触发（`TriggerAutomation(jira_ticket_id)`）、状态查询（`GetStatus(ticket_id)`）、人工介入（review 相关接口）。

## 3. Failure modes & scale（本题权重也很高——LLM 步骤的失败模式是本题的差异化难点）

- **1 分**：LLM/编码 agent 这一步的失败处理等同于普通网络调用失败——"超时就重试"，完全没意识到"生成的代码编译通过但逻辑是错的"这种**看似成功实际失败**的情况需要额外的验证步骤；人工 review 关卡说"最后加一步人审"就结束，没有讨论如果 review 被拒绝之后流程应该怎么办。
- **4 分**：**LLM 步骤的失败模式**——区分"硬失败"（调用超时、生成内容为空、接口报错，可以直接判定失败重试）和"软失败/需要验证的产出"（生成了看起来合理的代码，但必须经过独立的验证步骤——编译/lint/跑测试——才能判断这次生成是不是真的可用；测试失败本身也应该反馈给下一轮生成作为额外上下文，而不是简单重跑一次一模一样的 prompt）；对连续多次生成都无法通过验证的工单，转入需要人工介入的失败队列而不是无限重试消耗资源。**人工 review 是硬性关卡**——`pending_review` 状态下，系统不提供任何"自动批准/自动合并"的接口，`ApproveForMerge` 必须携带真实的 reviewer 身份，这条边界要讲得非常明确（面试官大概率会专门追问"如果自动化流程反复生成同一个高置信度的正确答案，能不能跳过人审"，标准答案是不能，这是设计上刻意保留的强制人类把关点）；`RejectWithFeedback` 应该把 reviewer 的反馈重新喂给生成步骤，作为下一轮尝试的额外上下文（而不是简单打回重新从零开始）。**并发隔离**——多个工单的自动化流程互相独立（每个工单一个独立的流水线实例），一个工单卡在某一步（比如测试环境资源不足导致跑测试排队很久）不应该阻塞其他工单的处理，这是典型的任务队列/调度器设计（可以直接复用 sd02 cron scheduler 或 sd05 队列服务里的分片/并发隔离思路）。
- **4 分（补充）**：**幂等与重复触发**——如果 Jira 工单的标签被重复触发（比如 webhook 重复投递），系统要能识别"这个工单已经有一个正在进行/已完成的自动化流程"，不重复启动第二条流水线。

## 4. Separation of concerns

- **1 分**：把"接收工单触发""调用 LLM 生成代码""跑测试""开 PR""等待人审"全部塞进一个巨大的处理函数里，任何一步的实现细节变化都要改动整个流程。
- **4 分**：分层清楚——**触发/接入层**（监听 Jira webhook 或轮询，识别符合条件的工单，做幂等检查）；**编排层**（管理多步骤流水线的状态机，决定"现在该跑哪一步、上一步失败了要不要重试、重试几次后该转失败队列"，本身不关心每一步具体怎么实现）；**执行层**（每个具体步骤——理解需求、生成代码、跑测试、开 PR——各自是独立的、可替换的执行单元，例如"生成代码"这一步未来可以换成不同的编码 agent 实现，不影响编排层）；**人工 review 层**（独立的审批接口和界面，是流水线里唯一需要人类主动介入才能推进的环节，与前面全自动化的步骤在权限模型上完全不同——只有这一层拥有"允许产生可合并代码"的权限）。

## 5. Delivery beyond the diagram（rollout / 测试 / 监控）

- **1 分**：画完图不谈怎么上线、怎么验证、怎么监控。
- **4 分**：讲到监控指标（各阶段的成功率——尤其是"生成代码通过验证"这一步的成功率、平均处理时长、人工 review 的通过率与平均等待时长、连续失败转人工介入的工单量）；讲到怎么测试——针对已知类型的工单构造回归测试集，验证流水线各阶段的正确性，尤其是失败重试路径（模拟测试失败后验证反馈确实被带入下一轮生成）；讲到 rollout——这类系统应该先在低风险的工单类型（比如小的文档修复）上灰度，观察生成质量和人工 review 的通过率，再逐步扩大到更复杂的工单类型；讲到需要有"自动化流程本身出问题"的告警（比如生成代码的通过率突然大幅下降，可能意味着上游模型或者代码库发生了不兼容变化）。
