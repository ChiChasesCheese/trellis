# 追问预案（≥8 条）

> 前两条对应 `catalog/raw/system_design.md` §1.1 明确记录的"追问汇总"（一手/多源一致），标(一手)；其余是基于该题族结构推出的高概率追问。

## 1（一手）单分区强一致好办，跨分区更新多个 key 要怎么做到 serializability？

**期望要点**：明确说单纯的 Raft 只解决单个分区（单个复制组）内的一致性，跨分区需要额外一层协调——2PC：协调者向所有涉及分区发 PREPARE，各分区把"prepared"状态写入自己的 Raft 日志再 ack，协调者收齐后发 COMMIT；讲清 prepared 期间要锁住相关 key，以及协调者本身的单点问题（可以让协调者自己也是一个 Raft group 来容灾）。

**反例**：回答"每个分区自己 Raft 保证一致就行，两个分区各自搞定不就行了"——这是没理解"跨分区原子性"要求的是"两个分区的结果必须同时可见或同时不可见"，单纯两个独立的 Raft 复制并不能保证这一点（会出现 A 已提交、B 还没提交的中间态被读到）。

## 2（一手）快照/time travel 怎么防止无限增长？

**期望要点**：设定一个保留窗口（如 90 天），超过窗口的历史 version 在 LSM compaction 时被物理裁剪；裁剪后如果还有 `as_of` 查询命中被裁剪的时间点，要显式返回"数据已超出保留窗口"而不是返回错误结果或悄悄返回最早可用版本；讲清 compaction 是存储引擎层的常规操作，不是为 time travel 单独加的机制。

**反例**：说"历史数据我们就一直存着，反正现在存储便宜"——没有回答"无限增长"这个问题的本质：即使存储便宜，索引结构（SSTable 数量、range scan 要扫的层数）也会随时间退化，且面试官问的就是这个退化点怎么处理。

## 3. 分布式版本号 vs 向量时钟，为什么选一个不选另一个？

**期望要点**：向量时钟能表达"因果关系不可比"的并发写，但代价是向量长度随参与者数量增长，且业务方需要自己处理"冲突合并"这件麻烦事；本题需要的是"确定性的全局顺序"（不允许两个副本对同一个 key 有不同的最终结果），所以用**分区内单调递增序列号 + 分区号**的复合版本号就够了——它本身依赖 Raft 日志顺序天然单调，不需要额外的合并逻辑。可以补充：如果未来要支持多主写入（不同分区都能写同一个 key），向量时钟才会变得必要，但那是另一个系统模型了。

**反例**：选择"用挂钟时间戳做版本号"——面试官会立刻追问"如果两台机器时钟不同步怎么办",候选人如果答不出需要 NTP 或逻辑时钟兜底，说明没意识到物理时钟不能做分布式系统里的排序依据。

## 4. Range scan 在你的存储结构上要怎么实现？

**期望要点**：LSM 的 SSTable 内部按 key 排序（如果是"当前值索引"层）或按 (key, version) 排序（版本历史层），range scan 就是对 memtable 和各层 SSTable 做**多路归并**（类似归并排序的多路合并），每一路都是有序的，合并出的结果再按 limit/cursor 截断；如果是 B-tree，则是标准的区间遍历。要提到大范围 scan 可能触碰多个 SSTable 文件，会有 I/O 放大，可以用布隆过滤器和分层压缩策略减少不必要的文件读取。

**反例**：说"起一个后台任务把所有匹配的 key 找出来"——没有说清楚这个"找"具体怎么在有序结构上高效完成，退化成了全表扫描的描述。

## 5. 如果某个分区的 Raft leader 一直选不出来（比如网络抖动导致频繁超时选举），怎么办？

**期望要点**：这是可用性下降但一致性不能妥协的场景（CP 系统的必然代价）；可以讨论用 pre-vote 机制减少无谓的选举风暴（follower 在真正发起选举前先"预投票"确认自己真的能拿到多数派支持，避免网络抖动下反复触发选举）；也可以讨论选举超时加随机化（jitter）避免多个 follower 同时超时导致选票分裂。

**反例**：说"允许没有 leader 时也能写"——这直接违反了"单 key 强一致"的不变量，是本题最不该踩的坑。

## 6. 如果 client 需要"读到自己刚写的值"（read-your-writes），但读请求被路由到了一个还没追平的 follower，怎么保证？

**期望要点**：两个方案——① 读默认路由到 leader（简单但 leader 成为热点）；② 允许读 follower，但用 read index/lease read 确保 follower 的应用进度不落后于自己写入时观察到的 version（client 可以把自己上次写入返回的 version 带在读请求里，follower 发现本地还没应用到那个 version 就等待或转发给 leader）。

**反例**："我们用最终一致就行，客户端多试几次总能读到"——这不满足题目明确要求的"单 key 强一致"不变量。

## 7. 系统规模扩大 10 倍，哪里最先撑不住？

**期望要点**：先识别瓶颈——单个 Raft group 的写吞吐上限（受日志复制的网络往返延迟约束，分区数量增加是主要扩容手段）；路由/元数据层的查询 QPS（客户端缓存 + 版本化失效可以缓解）；2PC 协调者的吞吐（如果跨分区事务比例高，协调者本身可能成为瓶颈，需要把协调者也做成可水平扩展的多实例集群，按事务 id 分片）。

**反例**：回答"加机器就行"——没有具体到"加在哪一层""为什么加了有用"。

## 8. 这套系统能不能做到 exactly-once 语义（比如 client 因为超时重试了一次 PUT）？

**期望要点**：网络层面无法区分"请求没到达"和"到达了但响应丢了"，client 重试是必然行为；对策是让 PUT 携带一个 client 生成的**幂等键**（如 (client_id, request_id)），分区在应用日志前检查这个幂等键是否已经处理过，处理过就直接返回上次的结果而不重复应用——这是 at-least-once 请求语义 + 服务端幂等去重，组合出业务上等价于 exactly-once 的效果。

**反例**：说"这个系统本来就是强一致的，所以天然 exactly-once"——强一致（linearizability）解决的是"多副本看到同一个顺序"，不解决"同一个客户端请求被处理两次"这个完全不同维度的问题，两者不能混为一谈。
