# 模型答案：设计 User Password Storage

> 取材：t.me/s/usinterview/28738 → 1p3a thread-1179571 一手报告（题面确认，追问细节未知）；`catalog/raw/system_design.md` §1.9。按 `LOOP_GUIDE.md` §6 主线组织。追问细节部分因一手材料缺失，基于密码存储领域公认工程实践（OWASP、NIST 密码存储指南）补足，面试时应实话实说"这部分是我基于行业标准实践的理解，不是死记某个具体数字"。

## 0. 两句话复述 + 不变量

**复述**：要设计存储用户密码的机制，使得即便数据库被整体拖库，攻击者也无法轻易还原明文密码；同时要支持哈希算法/参数的平滑升级迁移（不能要求全平台用户同时改密码配合迁移），要为泄露事件的响应留好设计基础，并且要防御针对登录接口的在线暴力破解。

**核心不变量**：

1. **明文密码永不落盘、永不出现在日志/监控里**：只在内存中短暂存在，用完立即丢弃。
2. **相同明文密码在不同用户之间产生不同的存储哈希**：靠唯一 salt 实现，防止彩虹表和"发现两个用户密码相同"这类横向信息泄露。
3. **哈希计算刻意昂贵**：拖慢攻击者离线批量试错的速度，而不是追求哈希函数本身"快"这个通常意义上的优点。
4. **算法可以演进**：今天认为安全的参数，几年后可能因为算力增长而不够，存储设计必须为未来升级留出路径。

明确"不做什么"：不追求"绝对防止暴力破解"（在线限流只能提高攻击成本，不能做到理论上不可能）；不假设用户密码本身足够强（弱密码即使被慢哈希保护，仍可能被针对性字典攻击破解，这是密码策略层面的问题，本题聚焦存储机制）。

## 1. API 契约

```
SetPassword(user_id, plaintext) -> void
  # 服务端用当前推荐算法计算哈希 + 生成随机 salt，写入存储；plaintext 用完立即从内存清除

VerifyPassword(user_id, plaintext) -> {valid: bool, locked: bool}
  # 取出存储的 algo_id/params/salt，用相同算法重算哈希后做常数时间比较
  # 验证成功且发现记录的算法版本落后，触发懒迁移（见"核心流程"）
  # 验证失败计入 failed_attempts，触发节流/锁定逻辑

ForceResetRequired(user_id) -> void
  # 泄露响应场景下，标记该用户下次登录必须重设密码
```

- `VerifyPassword` 是唯一对外暴露的验证入口，任何调用方都不能绕过这个接口直接读取/比较 `password_hash` 字段。

## 2. 数据模型

```
credentials(
  user_id, password_hash, salt, algo_id, algo_params,
  updated_at, failed_attempts, locked_until
)
-- algo_id/algo_params 是支持未来升级的关键字段
-- 例：algo_id="bcrypt", algo_params={"cost": 12}

algo_config(
  current_algo_id, current_algo_params, effective_since
)
-- 全局的"当前推荐算法"配置，SetPassword 和懒迁移都读这份配置
-- 独立于 credentials 表，允许灰度调整算法参数而不需要改代码
```

## 3. 核心流程

**注册/设置密码**：`SetPassword` 读取 `algo_config` 拿到当前推荐算法和参数，生成一个密码学安全的随机 salt，计算 `hash = Algo(plaintext, salt, params)`，把 `password_hash, salt, algo_id, algo_params` 一并写入 `credentials`；整个过程中 plaintext 只存在于这一次请求的处理内存里，函数返回前显式清零，不写入任何日志。

**登录验证**：`VerifyPassword` 取出该用户存储的 `algo_id/algo_params/salt`，用**存储时记录的那套算法和参数**（而不是当前的推荐配置）重新计算哈希，与存储的 `password_hash` 做**常数时间比较**（避免逐字节比较提前返回导致的时序旁路攻击，攻击者可以通过测量响应时间推断出哈希前几个字节是否匹配）。

**算法/参数迁移——本题最核心的设计难点**：服务端从来没有、也不应该有用户的明文密码（这正是这套存储机制的设计目标），所以**不可能批量重新计算所有用户的哈希去升级到新算法**。解决方案是**登录时懒迁移**：`VerifyPassword` 验证成功后，比较该记录的 `algo_id/algo_params` 与 `algo_config` 当前推荐值是否一致，如果不一致——此时函数刚好还持有这次登录携带的明文密码（用户主动提供的，用完即将丢弃）——立即用新算法重新计算哈希并覆盖 `credentials` 里的记录，同时更新 `algo_id/algo_params`。这样迁移会随着用户的自然登录行为逐步完成，不需要用户配合，也不违反"服务端不存明文"的设计原则。对长期不登录、永远不会触发懒迁移的休眠账户，可以设置一个宽限期，超过后要求下次登录前先走密码重置流程作为兜底。

**登录节流与账户锁定**：`VerifyPassword` 失败时累加 `failed_attempts`，超过阈值（如 5 次）设置 `locked_until`（指数退避——第一次锁 1 分钟，再失败锁 5 分钟，以此类推），锁定期内即使密码输入正确也拒绝验证（防止利用"锁定判断在密码校验之后"这个顺序漏洞绕过锁定）；这一层逻辑架构上可以直接复用限流器设计（sd07），按 `user_id` 和/或来源 `IP` 两个维度叠加节流规则，防止单纯换 IP 绕过账户级锁定。

## 4. 失败模式与规模

**为什么不能用 SHA-256/MD5 这类通用哈希**：这类算法专门为"快"设计（用于文件校验、数字签名等场景），对密码存储而言，快恰恰是缺点——攻击者一旦拿到哈希值，可以用现代 GPU/ASIC 每秒尝试数十亿次候选密码。密码哈希算法（bcrypt/scrypt/Argon2）刻意设计成计算昂贵（引入工作因子/内存硬性要求），把攻击者的离线试错成本拉高到不现实的范围，代价是服务端自己验证一次密码也要花费几十到上百毫秒——这个代价是有意的，且要通过参数（如 bcrypt 的 cost factor）显式控制，随着硬件算力提升定期上调。

**参数上调的 rollout 风险**：cost factor 调得太高会显著增加登录接口的 CPU 开销和延迟，在高并发登录场景下（比如全平台的早高峰）可能压垮验证服务；上调参数前需要做容量评估和小流量灰度，确认延迟增加在可接受范围内再全量切换 `algo_config`。

**泄露响应**：即使密码经过慢哈希保护，一旦数据库整体泄露，攻击者仍然可以针对性地对弱密码/常见密码做离线字典攻击（慢哈希只是拉高成本，不是不可能）。因此泄露响应流程应该包括：立即强制全平台密码重置（使当前所有存储的哈希失效，`ForceResetRequired` 批量标记）；对外披露事件并提醒用户如果在其他站点复用了相同密码也要修改（服务端无法检测用户在别处的密码复用情况，只能提醒）；事后复盘泄露成因（是否是本系统的漏洞导致，还是供应链/内部人员问题）。

**规模估算**：假设平台有千万级用户，`credentials` 表按 `user_id` 分片存储没有特殊难度（每行独立、不需要跨行事务）；懒迁移的额外计算开销分摊在正常登录流量里，不会形成突发的批量负载，这也是选择懒迁移而不是"后台批量任务重算"（本来就不可行，因为没有明文）的自然结果。

## 5. 分层与组件

- **凭证存储层**：只负责按记录里保存的算法配置计算/校验哈希，不感知登录业务流程的其他部分。
- **算法配置层**：独立维护"当前推荐算法与参数"，支持灰度调整，SetPassword 和懒迁移逻辑都从这里读取目标配置。
- **懒迁移组件**：挂载在验证成功的回调上，与凭证存储层解耦，可以独立开关（比如某次升级决定暂停自动迁移，人工评估后再开启）。
- **节流/锁定层**：复用通用限流器设计，与密码哈希算法本身完全解耦——即使哈希算法足够安全，仍然需要这一层防止在线暴力破解。

## 6. rollout/测试/监控

- **监控**：登录失败率异常升高（可能预示撞库攻击）、懒迁移完成进度（多大比例的账户已经迁移到最新算法版本）、账户锁定触发频率、验证接口的平均延迟（监控算法参数调整对性能的实际影响）。
- **测试**：验证相同明文密码在不同用户账户间产生完全不同的哈希（盐生效）；验证新旧两套算法/参数的记录都能被 `VerifyPassword` 正确验证（向后兼容，不能因为升级了推荐配置就让老记录验证失败）；验证常数时间比较确实消除了明显的时序差异。
- **rollout**：算法参数上调（如提高 bcrypt cost factor）先在小流量上验证登录延迟和服务器 CPU 负载没有显著劣化，再全量切换 `algo_config`；泄露响应流程应该提前写成 runbook 并演练，而不是等真的发生事件才现场决定步骤。

## 7. 用 Snowflake 自己的原语作参照

Snowflake 自己内部对凭证和密钥的管理实践可以类比本题——Snowflake 支持并推荐 **key-pair 认证**（RSA 密钥对）而非纯密码，且明确要求定期轮换密钥而不是一次性设置后永久不变（`01-company-brief.md` §2 提到 Trust Center/AI Agent Identity 等治理机制强调持续的凭证生命周期管理），这与本题"密码/密钥参数需要能周期性升级"的设计诉求是同一类工程原则：**任何长期存在的凭证材料都需要一个不依赖用户配合、能平滑演进的轮换机制**。另外，本题的"懒迁移"模式（登录时顺手升级）与 Snowflake `secret_current`/`secret_previous` 双密钥并存的轮换模式（见 stripe webhook 题的密钥轮换设计，是这类问题的通用解法）在思路上相通——都是承认"不能强制所有使用方立刻切换到新版本"，转而设计一个渐进式、由正常使用行为驱动的过渡期。面试时可以说："这和 Snowflake 建议的密钥轮换实践是同一个原则——凭证的生命周期管理必须假设不能强制所有人立刻切换，要靠渐进式迁移机制。"

## 8. 45 分钟口述时间表

- **0–5 min**：复述题目 + 不变量（明文永不落盘、唯一 salt、刻意慢哈希、算法可演进），确认是否有历史遗留弱哈希需要迁移。
- **5–10 min**：API 契约（SetPassword/VerifyPassword/ForceResetRequired）+ 数据模型（credentials + algo_config 分离设计）。
- **10–18 min**：核心流程——注册/验证的哈希计算、**懒迁移机制**（重点展开，这是本题区别于纯八股的核心设计）、登录节流与账户锁定。
- **18–32 min**：失败模式——为什么不能用通用哈希算法、参数上调的性能风险与灰度、泄露响应流程、规模估算。
- **32–40 min**：分层图 + rollout（灰度参数调整）+ 监控指标（登录失败率异常、懒迁移进度）。
- **40–45 min**：总结 + 类比 Snowflake key-pair 认证的轮换实践，反问面试官。
