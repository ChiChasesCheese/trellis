# 评分 rubric（五维，1–4 分/维，满分 20）

> 依据 `loop/LOOP_GUIDE.md` §6 与 `catalog/raw/system_design.md` §1.9。**这道题的一手报告没有留下追问细节**——意味着面试官具体会往哪个方向压分未知，rubric 按密码存储这个领域公认的工程标准来定，重点是"密钥/参数轮换"和"泄露响应"这两个能体现系统设计而不只是背安全知识的环节，这是本题区别于纯八股的地方。

## 1. Problem framing（需求抽取）

- **1 分**：一上来就说"用 bcrypt 就行"，把整道系统设计题答成了一个算法选型的八股题，没有展开成一个完整的系统（迁移、泄露响应、防暴力破解）。
- **4 分**：两句话复述——"要设计一套密码存储机制，使得数据库被整体拖库时攻击者也无法轻易还原明文密码，同时要支持算法/参数的平滑升级迁移、要为泄露事件的响应留好设计基础、要防御针对登录接口的暴力破解"；显式说出不变量——**明文密码永不落盘、永不出现在日志里**、**每个密码的哈希输入必须加唯一 salt**（防止相同密码产生相同哈希，防彩虹表）、**哈希算法必须是刻意慢的**（防止攻击者用其算力优势批量试错）；主动确认平台的用户规模和是否有历史遗留的弱哈希方案需要迁移。

## 2. API & data model（权重最高）

- **1 分**：只有一个字段 `password_hash`，没有单独存 salt（可能被错误地拼进 hash 字段里没有结构化）、没有算法版本标识，导致未来升级算法时无从下手。
- **4 分**：数据模型至少包含 `(user_id, password_hash, salt, algo_id, algo_params, updated_at, failed_attempts, locked_until)`——**`algo_id`/`algo_params` 是支持未来升级的关键字段**（记录这条记录当初是用哪个算法、哪组参数生成的）；接口上 `SetPassword(user_id, plaintext) -> void`（服务端立即用当前推荐的算法计算哈希、生成随机 salt 存下，plaintext 全程不落盘）与 `VerifyPassword(user_id, plaintext) -> bool`（取出存储的 algo_id/params/salt，用同样的算法重算哈希后做**常数时间比较**，防止基于响应时间差的旁路攻击）。

## 3. Failure modes & scale（本题权重也很高）

- **1 分**：算法选择用 MD5/SHA-256 这类快速通用哈希（没有意识到这类算法专为速度设计，恰恰是密码哈希要避免的特性）；被问"算法要升级怎么办"答不出方案，只会说"批量重新哈希所有密码"（做不到，服务端没有明文）；防暴力破解只说"加验证码"没有系统层面的节流设计。
- **4 分**：**算法选择**——用专门设计成计算昂贵、且对 GPU/ASIC 破解有抵抗力的算法（如 bcrypt/scrypt/Argon2），参数（如 bcrypt 的 cost factor）要能随硬件算力增长周期性上调；**盐**——每个用户独立、密码学随机生成，与哈希值一起存储（盐不需要保密，只需要唯一，其作用是让相同明文密码不会产生相同哈希，从根本上让预计算的彩虹表失效）；**算法/参数迁移（本题最能体现系统设计能力的环节）**——不能批量重算（服务端没有明文密码），采用"**登录时懒迁移**"：`VerifyPassword` 验证成功后，检查该记录的 `algo_id`/`algo_params` 是否已经是当前推荐版本，不是的话（此时正好拿到了这次登录携带的明文密码）立即用新算法重新计算并覆盖存储；对于长期不登录、始终不会触发懒迁移的用户，可以设置一个宽限期后强制要求下次登录时重设密码，作为兜底；**泄露响应**——如果检测到数据库被拖库，即使密码经过慢哈希保护，弱密码仍然可能被离线暴力破解，因此响应流程应包含强制全平台密码重置（使当前存储的所有哈希立即失效）、通知用户、检查是否有其他系统复用了同一密码（无法直接检测，但应在披露文案里提醒用户如果在别处用了相同密码也要修改）；**防暴力破解**——登录接口按 `(user_id 或 IP)` 做限流（可直接复用 sd07 的限流设计），连续失败次数超过阈值触发指数退避的账户临时锁定（`locked_until`），避免无限制的在线撞库尝试。

## 4. Separation of concerns

- **1 分**：把"哈希计算""迁移逻辑""登录限流""泄露响应流程"全部写在一个登录接口的处理函数里。
- **4 分**：分层清楚——**凭证存储层**（只负责按当前算法配置计算/校验哈希，不感知业务登录流程）；**算法配置层**（独立维护"当前推荐算法与参数"这一份配置，允许灰度调整而不需要改代码）；**懒迁移逻辑**（挂载在登录成功的回调上，与凭证存储层解耦，是一个独立的、可选开启/关闭的组件）；**登录节流/账户锁定层**（复用限流器设计，与密码验证逻辑本身解耦，即使哈希算法本身很安全也需要这一层防止暴力破解）。

## 5. Delivery beyond the diagram（rollout / 测试 / 监控）

- **1 分**：画完图不谈怎么上线、怎么验证。
- **4 分**：讲到监控指标（登录失败率异常升高——可能预示撞库攻击、懒迁移的完成进度/覆盖率、账户锁定触发频率）；讲到怎么测试——验证相同明文密码在不同用户之间产生完全不同的存储哈希（盐生效）、验证算法升级后新旧两种参数的记录都能被正确验证（向后兼容）；讲到 rollout——算法参数上调（如 bcrypt cost factor 提高）应该先小流量验证登录延迟没有显著劣化（哈希计算变慢本身是刻意的，但要确认没有慢到影响用户体验或压垮服务器 CPU）再全量推广；讲到需要有明确的泄露响应 runbook，而不是等真的出事才现场决定流程。
