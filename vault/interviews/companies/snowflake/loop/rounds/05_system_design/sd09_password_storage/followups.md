# 追问预案（≥8 条）

## 1. 为什么不能直接用 SHA-256 对密码做哈希？

**期望要点**：SHA-256 是通用密码学哈希函数，设计目标是"快"（用于文件完整性校验、数字签名等场景），这个特性用在密码存储上恰恰是弱点——攻击者用现代 GPU/ASIC 可以每秒计算数十亿次 SHA-256，一旦拿到哈希值就能高速做离线暴力破解或字典攻击。密码专用哈希算法（bcrypt/scrypt/Argon2）刻意引入工作因子（可调节的计算成本）或内存硬性要求（scrypt/Argon2 特意让哈希计算需要大量内存，进一步抵抗 ASIC/GPU 的并行优势），把攻击成本拉高到不现实的范围。

**反例**：回答"SHA-256 加个盐就够安全了"——加盐能防止彩虹表和"发现两个用户密码相同"这类问题，但不能改变 SHA-256 本身计算速度快这个特性，攻击者拿到哈希后针对单个用户的暴力破解速度不受盐的影响，盐和"哈希函数本身刻意慢"是两个独立的防御维度，缺一不可。

## 2. salt 需要保密吗？它的作用到底是什么？

**期望要点**：salt 不需要保密，可以和哈希值明文存在一起——它的作用不是"增加一个攻击者不知道的秘密"，而是保证**相同的明文密码在不同用户之间产生完全不同的哈希输出**，从根本上让"预先计算好的彩虹表"（针对常见密码的哈希值查找表）失效，因为攻击者无法为"所有可能的 salt 值"都预计算一张彩虹表。

**反例**：把 salt 当成秘钥一样单独加密存储、和 hash 分离存放在不同的安全存储里——这是对 salt 作用的误解，增加了系统复杂度但没有带来对应的安全收益，salt 只需要唯一和随机，不需要保密。

## 3. 服务端从来没有存过明文密码，那算法升级（比如从 bcrypt cost=10 升到 cost=14）要怎么做？

**期望要点**：不能批量重算（没有明文），采用"登录时懒迁移"——`VerifyPassword` 验证成功后，比较存储记录的算法参数与当前推荐配置是否一致，不一致就用这次登录携带的明文密码立即重新计算哈希并覆盖存储。这个迁移过程随用户自然登录行为逐步完成，不需要用户配合，也不违反"服务端不存明文"的原则。

**反例**：说"给所有用户发邮件要求重设密码来完成迁移"——这个方案确实可行，但用户体验很差且响应率通常不高，题目明确要求"不可能要求所有用户同时修改密码"，说明面试官期望的是懒迁移这类不需要用户主动配合的方案；直接说"没办法，只能等用户自己改密码"则完全没有提出主动方案。

## 4. 如果发生了真实的数据泄露事件（数据库被拖库），你的存储设计对响应流程有什么帮助？

**期望要点**：即使密码经过慢哈希保护，弱密码/常见密码仍可能被针对性字典攻击破解，慢哈希只是拉高成本不是绝对防线；响应流程应包括立即强制全平台密码重置（让当前所有哈希立即失效，不管强弱一律要求重设）、对外披露并提醒用户如果在其他站点复用了同一密码也要修改（服务端无法检测复用情况，只能提醒）；存储设计里的 `algo_id/algo_params` 字段也能帮助快速判断"哪些账户当时用的是较弱的旧算法参数，风险等级更高"，用于响应时的优先级排序。

**反例**：说"我们的哈希足够安全，泄露了也没关系，不用特别处理"——密码哈希的安全性只是拉高攻击成本，不是绝对安全保证，尤其是弱密码在拖库后仍有很高的被破解概率，声称"不用处理"是对密码存储安全边界的误解。

## 5. 怎么防止针对登录接口的暴力破解（撞库、字典攻击）？

**期望要点**：按 `user_id` 和/或来源 IP 维度对登录尝试做限流，连续失败超过阈值触发指数退避的账户临时锁定；锁定判断要在密码校验之前（或与校验结果无关地独立生效），避免"密码碰巧输对了但锁定检查在校验之后才做"这种时序漏洞被绕过；进一步可以引入行为异常检测（同一账户短时间内来自大量不同 IP 的登录尝试）触发额外验证（如二次验证码）。

**反例**：只依赖哈希算法本身"计算慢"来防御暴力破解——哈希慢主要针对**离线**批量试错（攻击者拿到哈希值后自己算），对**在线**逐次调用登录接口的暴力破解帮助有限（每次调用本身就要走一次网络请求和业务逻辑，哈希计算的几十毫秒相对不是主要瓶颈），必须有独立的接口级限流/锁定机制。

## 6. 常数时间比较（constant-time comparison）是什么，为什么密码验证要用它？

**期望要点**：普通的字符串比较（如逐字节比较，发现不匹配立即返回 false）的执行时间会因为"前几个字节匹配了多少"而有细微差异，攻击者理论上可以通过大量重复请求、测量响应时间的统计差异，逐字节推断出正确哈希值（时序旁路攻击）；常数时间比较无论输入是否匹配，比较操作的耗时都相同，消除了这个信息泄露渠道。

**反例**：认为"这个攻击太理论化，不用管"——虽然利用难度较高，但作为系统设计题里体现安全意识深度的一个细节，能主动提出并解释这个概念，比完全不提要显著加分；即使面试官没追问，主动提及也展示了对密码验证实现细节的完整理解。

## 7. 如果某个用户的密码哈希算法参数已经严重过时（比如还在用很弱的旧算法），但这个用户几年都不登录了，怎么办？

**期望要点**：懒迁移依赖用户主动登录触发，对长期休眠账户不生效；兜底方案是设置一个宽限期（比如距离上次密码更新超过若干年），超过后在该账户下次尝试登录时，验证通过旧密码后强制要求立即设置新密码才能继续使用（而不是静默完成迁移），确保这类高风险账户不会无限期停留在弱算法状态。

**反例**：完全没有考虑长期不登录账户的问题，认为懒迁移机制能覆盖所有情况——懒迁移的前提是用户会登录，休眠账户永远不会触发这个机制，需要显式的兜底策略。

## 8. 系统规模扩大后（比如全平台同时做一次登录早高峰），哈希计算的 CPU 开销会不会成为瓶颈？

**期望要点**：密码哈希算法故意设计得计算昂贵，这意味着登录验证服务本身需要为这部分 CPU 开销做容量规划（bcrypt/Argon2 的参数选择需要在"抗暴力破解强度"和"服务端能承受的验证吞吐"之间找平衡点）；可以把密码验证这个 CPU 密集操作放在独立的、可以水平扩展的验证服务里，与其他业务逻辑解耦，避免登录早高峰的哈希计算压垮承载其他业务逻辑的服务实例。

**反例**：说"哈希算法本来就该越慢越好，直接调到最高强度"——完全不考虑这会给验证服务的实际吞吐能力带来多大压力，是没有把"安全性"和"可用性/性能"放在同一个系统设计视角下权衡的表现。
