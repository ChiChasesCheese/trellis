# 库存管理：题解

**一句话。** 库存的账只有两个数，记在"仓库 x 商品"的格子里：在架（`on_hand`）和被有效预留占用的（`reserved`），可售 = 在架 - 占用；预留生命周期的每一步都只是在这两个数上做加减。过期靠"每次操作先结清"，不靠后台线程。参考实现见 `solution.py`。

**关键决策。**

- 占用和在架分开记，不直接扣库存。预留只增加 `reserved`，发货才减 `on_hand`；这样取消和过期只需要把 `reserved` 减回去，不用"恢复"库存。放弃的做法是预留时直接扣在架：确认、取消、过期三条路径都要写"加回去"，容易漏。
- 分配规则要确定：可售最多的仓库优先，同样多取仓库名小的。放弃的做法是随机或遍历顺序：测试和客服排查都没法复现。多取少拆单是这个规则的副产品，也是常见的业务偏好。
- 先计划、后提交。`_plan` 只读，算出从哪些仓库拿多少，不够就抛错；`_commit` 只做加法，不会失败。放弃的做法是一边拿一边减，库存不足时要回滚。`reserve_many` 就是对每件商品先各自算计划，全部通过再整体提交。
- 过期不起线程。放弃的做法是定时器或后台线程：多一类竞态，而且线程晚醒一点点，`available` 就是错的。每个公开操作开头先结清到点的预留，任何读到的数字已经算过期。
- 到点预留放在小根堆里，延期、确认、取消不删堆条目，只让它作废：弹出时发现状态不再是有效，或者过期时间对不上（被延期过），就丢掉。放弃的做法是在堆里查找并删除，那是 `O(n)`；或者每次扫全部预留，操作成本随预留数增长。
- 一把 `RLock`。临界区只有字典和堆操作，够用，而且多件商品的原子预留不用担心加锁顺序。需要更高吞吐时按商品分段加锁，那时 `reserve_many` 要按商品排序依次加锁，避免死锁。
- 重复确认、重复取消是无操作，状态不允许的转换抛 `InvalidState`。网络重试会让同一个确认到达两次，把它当错误会让调用方多一套兜底；而取消已发货的订单是真正的错误。

**写法。**

- `heapq` 加惰性删除。堆只管"最早到点的是谁"，作废的条目弹出时再丢，每次操作的摊还成本是 `O(log n)`；用列表排序或遍历检查是 `O(n)`，用堆再支持删除又需要额外的索引结构。模式：惰性删除堆。
- `_op` 装饰器：拿锁、结清过期、再执行。每个公开方法都要做这两步，写在装饰器里就不会有哪个方法忘记，读起来方法体只剩业务。手写在每个方法里，总有一个会漏掉结清。模式：横切关注点用装饰器。
- 冻结的 `Reservation` 加 `dataclasses.replace`：状态变化时造一个新对象换进字典。已经交给调用方的快照永远不变，也没有"内部对象与快照对象"两套类型。可变对象要再写一个 `snapshot()` 方法复制一份。模式：不可变记录与整体替换。
- `match entry.status`：每个状态一个 `case`，确认和取消对四种状态的处理一目了然，漏掉某个状态会在读代码时就显眼。`if/elif` 链很难看出是否覆盖了全部状态。模式：对枚举的分支。
- 注入时钟 `clock`：过期、延期的测试里换成假时钟，不需要 `sleep`，边界（恰好到点）可以精确测试。模式：注入时钟。

**每关怎么走。**

1. 第 1 关：先写 `Status`、`Allocation`、`Reservation` 和 `_Slot`，再写 `add_stock`、`available`，然后 `_plan` 和 `_commit`，最后 `confirm`、`cancel`。核心代码约 105 行（含异常类和数据类）。
2. 第 2 关：`reserve` 多一个 `ttl`，`_commit` 里把 `(过期时间, ID)` 压进堆；`_expire_due` 在每个操作开头弹出到点的条目；`extend` 重新压入新条目。
3. 第 3 关：给每个公开方法套上锁（装饰器），确认没有任何读改写发生在锁外；`reserve_many` 先全部 `_plan`，再全部 `_commit`。
4. 第 4 关：`transfer` 只动可售的部分；`snapshot` 在锁内一次性读完，返回不可变的行。

**易错。**

- 一边拿库存一边判断，不够时已经占走了一部分。
- 过期判断用 `>`，恰好到点的那一刻库存还被占着；或者用 `>=` 却在 `extend` 之后仍按旧期限过期。
- 取消或确认之后，这个预留的过期时间到了，又被"释放"一次，库存被多放回。
- 过期的预留不结清就读 `available`，数字偏小。
- `confirm` 之后 `on_hand` 减了，`reserved` 没减，可售被扣两次。
- `reserve_many` 逐件预留，中途失败再回滚；并发的另一个线程在回滚前已经看到了被占住的库存。
- `OutOfStock` 里的可售数量只算了单个仓库，不是总量。
- 返回内部可变对象，调用方改了字段，账就乱了。

**追问。**

- 分布式下的超卖：把"检查并占用"变成一条数据库语句（`UPDATE stock SET reserved = reserved + n WHERE sku = ? AND on_hand - reserved >= n`），受影响行数为零就是不足；热点商品按商品分片串行化，或者预先把库存切成多份。
- 幂等：预留带调用方给的幂等键，重复请求返回同一个预留（参见幂等转账）。
- 预留与订单：预留是订单的子资源，订单取消或超时要级联释放；支付回调晚于过期时，是延长、重新预留还是退款，要在业务上约定。
- 安全库存与补货：`available` 里再减去安全库存；低于阈值时触发补货事件。
- 在途库存：调拨不是瞬间完成，需要"在途"状态，到仓才进入在架。
- 超卖容忍：有的业务允许少量超卖加缺货补偿，那就是另一套权衡，要在需求里问清。

**级别期望。**

- 中级：多仓库存、预留、确认、取消，可售数量算对，库存不足不留半截状态。
- 高级：有效期与惰性结清、延期、状态机的重复调用语义、并发不超卖、多件商品原子预留。
- 资深：堆加惰性删除的论证、按商品分段加锁与排序避免死锁、数据库条件更新与分片、幂等与订单联动，并说清每项在 60 分钟里为什么先不写。
