# 计费 / 计税引擎：题解

**一句话。** 这是"带生效时间的版本化规则 + 可组合的规则链 + 金额只在边界取整一次"的组合：每个商户的规则版本按生效时间排序后二分查找，规则本身是对象排成链，加一种费用或一种税不用改引擎，并且任何一行金额都能被复现。参考实现见 `solution.py`。

**关键决策。**

- 按生效时间二分，不用"当前配置"。只保存当前配置，重算上个月的交易就会用今天的规则，账对不上；退款手续费复用了错误的价格计划是真实发生过的缺陷类型。放弃的另一个做法是只存差异、查询时重放：省空间，但每次查询变慢，也难以审计。一个商户一年也就几十个版本，空间不是问题。
- 规则对象加顺序链。每条规则统一接口 `apply(txn, prior)`，引擎只负责顺序运行。税建在费用之上，只是链上靠后的一条规则，从 `prior` 里按 `kind` 汇总。放弃的做法是在引擎里写 `if tax:`——每加一种费用就要改引擎。
- 取整只发生在 `_to_minor` 一处。规则内部用 `Decimal` 全精度，引擎在一行产出时取整一次；税看到的是已经取整的费用行，账面上每行相加就是总数。放弃的做法是每个中间步骤都取整（误差累积）和各规则各自选取整方式（同一笔交易换条路径结果就不同）。
- 发布时校验，不在报价时校验。环、缺依赖、重复 ID 在 `publish` 里当场拒绝，且校验发生在任何修改之前，所以失败不占用版本号。放弃的做法是报价时才发现规则写错，那时已经有交易在用这个版本。
- 依赖用 `needs` 声明，发布时做稳定拓扑排序。放弃的做法是"调用方保证书写顺序"：规则一多，顺序靠人记。依赖复杂到需要图时才值得更重的结构，两三条规则时顺序列表已经够用。
- 更正只追加调整行。发布了错误规则后，旧各行不改；`reprice` 算出新旧之差作为调整行。这与账本的冲正是同一个原则。

**写法。**

- `_Schedule` 是冻结的数据类，`publish` 造出新快照再换引用。`quote` 先取一次引用，之后用的是同一份完整的版本表，读路径不需要锁。边读边改共享列表则要么给读也加锁，要么偶尔读到只更新了一半的 `starts` 和 `versions`。模式：不可变快照（复制后替换）。
- `Protocol` 声明 `Rule`：有 `rule_id / kind / needs / apply` 就是规则。用抽象基类要求每条规则继承，数据类规则会多出一层没有收益的继承，测试里想写一条临时规则也得先导入基类。模式：结构化类型。
- `Bounded` 包住任意规则，只实现同一个接口。保底、封顶对哪种规则都成立，写成装饰器一次到位；给每种规则各加 `minimum / maximum` 参数则每个新规则都要重复。模式：装饰器（包装同一接口）。
- `decimal.Decimal` 加 `quantize(..., ROUND_HALF_EVEN)`。二进制浮点算不出 `0.1 + 0.2 == 0.3`，钱不能用；整数除法又会提前丢掉小数。单独一个 `_to_minor` 函数，意味着"换舍入方式"只改一处。模式：单点取整（数值精度只在边界收口）。
- `next((r for r in pending if ...), None)` 做稳定拓扑排序。生成器表达式加默认值，一行表达"找到第一条能跑的，找不到就是有环"，且天然保持书写顺序。手写入度表和队列要多十几行，还要另想怎么保持原顺序。模式：生成器加短路查找。

**每关怎么走。**

1. 第 1 关：先写 `Txn / Line` 两个冻结的数据类和 `_to_minor`，再写 `PercentPlusFixed / TaxOnFees`，最后写 `FeeEngine.publish / quote`。跑通"版本边界"和"44.5 取 44"两个例子再往下。核心代码约 75 行。
2. 第 2 关：新增 `Tiered` 和 `Bounded` 两个规则对象，引擎一行不改。`Tiered` 的各档先累加后取整。
3. 第 3 关：`publish` 里先排序校验再加锁；`PercentPlusFixed` 的固定费改成接受映射。并发测试靠"快照整体替换"就过。
4. 第 4 关：把 `quote` 里的循环抽成 `_run(rules, txn, version)`，`reprice` 复用它，再按 `rule_id` 汇总求差。

**易错。**

- 每个中间步骤都取整；或者费用和税合起来再取整一次，账面各行相加对不上。
- `bisect_left` 代替 `bisect_right`，恰好等于生效时间的交易落到旧版本。
- 没有版本时返回空结果，静默漏收。
- 税规则按规则名字猜哪些是费用，而不是按 `kind`。
- 阶梯写成"整笔金额按所在档的费率"，在档边界处费用跳变。
- 保底把不适用的规则硬凑出一行。
- 发布失败时已经改了一半状态（版本号被占用）。
- 把"缺币种"悄悄当成 0 固定费。

**追问。**

- 规则依赖更复杂（A 用 B 的结果，B 又用 C）：建成有向无环图，拓扑排序，有环拒绝发布。
- 错误规则的补救：发布更正后的规则，对受影响交易算调整行；多实例部署时规则是带版本号的数据，每行记录用的版本，生效时间设在未来几分钟，让所有实例有时间拉取。
- 退款：手续费按原交易所属的规则版本计算，把"计算依据的时间"作为显式参数，不在引擎里读当前时间。
- 多币种：固定费按币种配置，取整按该币种的小数位（日元 0 位，美元 2 位，科威特第纳尔 3 位）；跨币种换算放在引擎之外。
- 固定费分摊到多行：整数除法后把余数逐个分给前几行，保证守恒，而不是每行独立取整。
- 线程安全：读多写少，复制后替换，`quote` 只读不可变数据。

**级别期望。**

- 中级：按商户的规则算出费用和税，整数金额，没有规则时报错，核心例子跑通。
- 高级：版本按生效时间二分，规则对象可组合，取整只在边界一次，说清为什么不能用当前配置算历史交易，发布时校验。
- 资深：规则依赖图与拓扑排序、调整行与更正流程、多实例发布一致性、多币种与退款场景下的版本选择、审计与复现能力。
