# 幂等转账服务：题解

**一句话。** 幂等不是"检查一下是否做过"，而是先用唯一键原子地占住一条记录，再把"检查余额、扣款、保存结果"放进同一个临界区，并让并发的重复请求合并到第一个请求上，而不是各自再执行一遍。参考实现见 `solution.py`。

**关键决策。**

- 占位记录加事件，不是"完成后去重"。只在完成后记录键，会有一个窗口：两个相同请求同时到达，都查不到记录，都去执行，转两次。另一个放弃的做法是给整个 `transfer` 加全局锁：对了，但外部步骤一慢，所有转账都排队。占位记录让第一个请求持有记录，其余的等它，等待还能带超时。
- 两把锁，各管一件事。`_mu` 只保护键表，持有时间是几次字典操作；`_money` 保护"检查余额 + 扣款 + 存结果"。外部步骤 `on_execute` 在两把锁之外。锁的顺序固定为先 `_money` 后 `_mu`，且占键的路径只拿 `_mu`，所以不会死锁。
- 业务拒绝是结果，技术失败不是。余额不足是确定的业务结论：如果不记住，同一个键第二次到达时恰好有人充了值，就会成功，同一个键两次得到不同的结果，客户端无法推理。想在充值之后再试，必须用新键，因为这是新的业务意图。外部步骤抛异常没有结论，所以释放键。
- 指纹放在记录里，对比发生在等待之前。同键不同请求几乎总是客户端 bug，悄悄执行第二个会转出错误的金额，悄悄返回第一个结果会让调用方以为第二个请求成功了。它也不需要等第一个请求结束就能判定。
- 保留期只作用于已完成的记录。执行中的记录由租约管：用保留期去过期一个还在跑的请求，会让重试变成第二次转账。
- 租约接手沿用同一条记录，只把"第几轮"加一。这样等待者不用换对象；提交时在 `_money` 里先看 `rec.result` 是否已有结果，有就直接用，所以"钱最多动一次"由临界区保证，不靠旧拥有者自觉。接手的一轮如果失败并释放了键，旧拥有者提交前会发现记录已不在表里，抛 `LeaseLost`，不再动钱。放弃的做法是 fencing token 加外部校验：这里钱和键表在同一个进程里，用记录本身就够。

**写法。**

- `@contextmanager` 写 `_owning`：拥有者的善后（失败时释放键、无论如何唤醒等待者）集中在一处，`_run` 里只剩 `with self._owning(...)` 加业务代码。每个出口手写 `try / except / finally` 既长又容易漏一条路径，比如只在成功时唤醒等待者。模式：上下文管理器（资源获取与释放配对）。
- 冻结的数据类 `_Request` 当指纹。`@dataclass(frozen=True, slots=True)` 自带 `==` 和 `hash`，"同键是不是同一个请求"就是一个 `!=`，字段有名字。用裸元组 `(src, dst, amount, currency)` 要靠下标记顺序，改一个字段位置不会有任何提示；手写哈希字符串则多出编码和碰撞问题。模式：不可变值对象。
- `Literal["succeeded", "rejected"]` 标注 `status`。类型检查器能拦住拼错的状态，运行时仍是普通字符串，测试和 JSON 序列化都不用转换。枚举更重，裸 `str` 什么都拦不住。模式：封闭取值集合（用类型而不是约定表达）。
- 注入时钟：`clock: Callable[[], float] = time.monotonic`。保留期和租约都靠时间，测试里换成可手拨的假时钟，就不需要 `sleep`，也不会因为机器慢而偶发失败。直接调用 `time.time()` 的代码只能真等。模式：注入时钟。
- `threading.Event` 加循环重新竞争。等待者靠事件醒来，醒来后不假设有结果，回到循环再抢一次；用"等到就一定有结果"的写法，拥有者一失败等待者就拿到空结果。模式：条件等待加重试。

**每关怎么走。**

1. 第 1 关：一把锁，一个字典 `(client, key) -> (指纹, 结果)`。查键、检查余额、扣款、存结果都在锁里；校验放在锁之前，不合法的请求不占键。核心代码约 55 行。
2. 第 2 关：把"存结果"拆成两步：先在 `_mu` 下插入占位记录，再进 `_money`。后到的请求在记录的事件上等，醒来后有结果就返回，没有就回到循环重新竞争。`on_execute` 放在占键之后、`_money` 之前。
3. 第 3 关：执行异常时，若这一轮仍是当前拥有者且没有结果，就删掉记录；`finally` 里无论如何唤醒等待者。过期判断只看已完成的记录，到点即过期。
4. 第 4 关：`_abandoned` 判断执行中的记录是否超过租约；接手时加轮次、重置开始时间。失败路径和 `finally` 都按"轮次是否仍是我"决定要不要删记录、要不要唤醒等待者。

**易错。**

- 先查后写，中间没有原子占位，两个并发请求都执行。
- 在 `_money` 或全局锁里调用外部步骤，一个慢请求卡住所有转账。
- 余额不足时没有保存结果，或者当成异常抛出；外部步骤失败时却把它当结论保存了。
- 拥有者失败后没有唤醒等待者，或者唤醒后等待者直接读 `result`（为空）而不是回到循环重新竞争。
- 先唤醒等待者、后保存结果，等待者读到空结果。
- 把 `ttl` 当成对所有记录生效，执行中的请求被清掉。
- 租约接手后，旧拥有者再次提交，钱动了两次；或者接手的一轮失败后删掉了已经有结果的记录。
- 同键异请求没有拒绝，或者先等待再比较指纹。

**追问。**

- 崩溃恢复：记录带开始时间，恢复任务扫描超时的执行中记录，用同一个键重放第二步；第二步必须幂等，账本分录 ID 由键派生，重放要么发现已记账，要么记账。
- 外部支付渠道：不能放进数据库事务，用事务外盒（outbox）。事务里写业务数据和待发出的渠道请求，后台进程用同一个幂等键调用渠道；超时视为结果未知，用同一个键查询或重试，绝不当作失败重新下单。
- 三层幂等：客户端到平台靠调用方的键；平台到渠道靠平台传给渠道的键；崩溃窗口靠先记录意图再动手加重放。缺一层就会重复扣款。
- 多实例：内存锁换成数据库唯一约束与行锁，键表与账本放在同一个库、同一个事务；等待者轮询记录状态。
- 键存多久：至少覆盖客户端最长的重试窗口（常见 24 小时到几天），过期后按时间分区批量清理。
- 返回码：新建 201，重放返回同样的码和内容；`StillRunning` 用 409 加 `Retry-After`；`KeyReuse` 用 422。
- 高并发转出同一个账户：行锁上排队，可按账户路由到单一分区串行处理。

**级别期望。**

- 中级：键表加余额，检查是否做过，余额不足拒绝，同键异请求拒绝。
- 高级：占位记录合并并发重复，检查与扣款原子，拒绝也被记住，外部慢步骤不持全局锁，失败释放键。
- 资深：租约与"最多动一次"的论证、保留期的代价、事务外盒与结果未知、三层幂等、数据库层的唯一约束与条件更新。
