# 配送员薪资：题解

**一句话。** 只存每单的事件时间，钱每次从事件现算：一段的钱 = 单价 x 倍率 x 秒数 / 60，高峰窗口边界处切段，整单最后舍入一次。

**关键决策。**
- 存事实、算钱。放弃"每收到一个事件就累加到余额里"：累加的写法遇到乱序、重复、更正就必须回滚旧账，而现算的写法只要事件表是对的，钱就是对的，`correct_event` 因此只有几行。代价是每次查询都重新算，订单只有三段、事件只有四个，这个代价可以忽略；要规模化时再加缓存。
- 三段由相邻事件定义，两端都已知才计费。放弃"要求事件按顺序到达"：真实系统里事件由手机端上报，网络会乱序。用"时间落在已知事件之间"的校验代替顺序校验。
- 重复上报分两类：同一类事件同一时间是幂等的，直接忽略；同一类事件不同时间是冲突，必须报错，不能悄悄覆盖。
- 切段函数 `_price_span`：收集窗口边界点，排序后对每个小区间取中点判断落在哪个窗口。放弃"逐分钟循环"：循环既慢又在秒级精度上不准，取中点则不用关心边界属于左还是右。
- 窗口左闭右开，午夜用 `time(0)` 表示。放弃"支持跨午夜的单个窗口"：拆成两个窗口后，每个窗口都满足 `start < end`，校验和覆盖判断都不用处理环绕。
- 金额内部用 `Fraction` 精确计算，只在最后舍入到分。放弃每段先舍入：三段各 0.125 先舍入成 0.13 会得到 0.39，而正确答案是 0.38；放弃 `float`：二进制小数表示不了 0.1。
- 保底只对四个事件齐全的订单生效，比较的是高峰后的金额。放弃"未完成的订单也保底"：订单可能被取消或还在途中，保底会提前多付。
- 结算周期按送达时间把整单记入一个周期。放弃"每段按发生时间分别记入各自的周期"：同一单会被拆到两个周期，对账和配送员看到的单据都对不上；代价是跨天的单在送达那天一次性入账。

**写法。**
- 金额内部用 `fractions.Fraction`，只在整单最后转成 `Decimal` 舍入到分。`Decimal` 除以 60 会产生循环小数，多段相加后在 0.5 的边界上可能差一位；`float` 连 0.1 都表示不了。属于"精确算术，最后一步舍入"。
- `PayPlan` 的费率在 `__post_init__` 里拷成 `MappingProxyType`：只读视图，调用方之后改自己的字典不会影响已建好的方案。直接保存传入的字典，等于把可变状态交给了别人。属于"不可变快照"。
- 切段逻辑拿"每个小区间的中点"去判断落在哪个窗口，边界属于左边还是右边就不用操心。逐分钟循环既慢，又在秒级精度上不准。属于"区间切分取中点"。
- `itertools.pairwise` 遍历相邻事件和相邻边界点，比 `zip(xs, xs[1:])` 少一次切片拷贝，意图也更直接。属于"滑动窗口迭代"。
- 数据类用 `frozen=True, slots=True`，`record` 先校验再写入，`delivery_pay` 每次从事实现算。把钱累加进余额的写法，遇到乱序、重复和更正就得回滚旧账。属于"存事实，不存派生值"。

**每关怎么走。**
- 第 1 关：`State`、`EventType`、异常、`PayPlan`、`record` 与 `delivery_pay`。先写出校验，再写计价。
- 第 2 关：只新增切段和 `PeakWindow`；`delivery_pay` 里"一段算一次"改成"一段切成若干小段各算一次"，其他不动。
- 第 3 关：`delivery_pay` 末尾加保底；新增 `payout`，它只是对 `delivery_pay` 求和加上一个送达时间过滤。
- 第 4 关：`correct_event` 复用 `record` 的时间线校验；明细直接暴露切好的小段。

**易错。**
- 每段先舍入再相加。
- 高峰窗口的右端点算进窗口，或者零长度的段被乘上倍率。
- 跨天的段只处理了第一天的窗口。
- 校验写在改状态之后，抛异常时已经写进去了一半。
- 把同一类事件的重复上报当成冲突，或者把冲突当成重复悄悄吞掉。
- `driver_payout` 对不存在的配送员抛异常，而不是返回零。

**追问。**
- 配送员在不同时区、夏令时那一天怎么办？答：把事件时间统一成带时区的绝对时间，高峰窗口按订单所在地的本地时间判断，这一天"一小时"可能出现两次或不存在，所以要在本地日历日上切段，而不是在 UTC 上加 24 小时。
- 订单被取消怎么办？答：加一个终止事件，规定取消前已发生的段照付、之后的不付，也不适用保底。
- 想按单量给奖励（完成 10 单加 5 元）？答：奖励是 `payout` 之上的规则，作为独立的"奖励策略"对周期内的订单列表求值，不要写进 `delivery_pay`。
- 多个服务并发上报？答：以 `(delivery_id, event)` 为键的幂等写入，加按订单的锁；校验与写入在同一把锁里。
- 数据量大了怎么办？答：事实表按配送员和送达时间建索引，周期汇总按日预聚合，更正事件作废对应日的预聚合。

**级别期望。** 初级：第 1 关正确，能处理基础异常。中级：第 2、3 关正确，边界开闭区间和舍入时机无误。高级：主动提出"存事实不存钱"，说清乱序、幂等、更正为什么因此变简单，并能讨论时区与对账。
