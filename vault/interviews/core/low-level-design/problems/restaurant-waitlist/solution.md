# 餐厅候位：题解

**一句话。** 把"现在谁能坐哪张桌"写成一个纯函数 `_drain`，真实操作和等位推演都调用它；防饿死只是这个函数里多一条停止条件。

**关键决策。**
- 排队用一个按到达顺序的列表。放弃优先队列，因为规则是"第一个坐得下的人"，不是"最大"或"最小"；中间离开、改人数也要保持相对顺序，列表最直接。人数很大时才值得换成按桌型分桶的结构。
- 入座规则集中在 `_drain`，它就地修改传进来的队伍和空闲桌，不读实例状态。放弃"`join` 一份逻辑、`finish` 一份逻辑、估计再抄一份"：三份规则迟早出现不一致，估计就会与现实脱节。
- 入座选容量最小的够用桌（`_best_fit`）。放弃"编号最小的空桌"：它会让 2 个人占掉 6 人桌，后来的大团只能干等。代价是这不是全局最优，这是个贪心。
- 每个改变状态的入口都以 `_seat_everyone_possible` 收尾，它返回新入座的人。这样 `finish` 在第 3 关可以一次入座多个人，而不用改签名。
- 等位估计在复制品上推演（`_simulate`）：忙桌空出时刻 = 入座时间 + `dining_time`，超时的算现在。放弃"用平均等待时间乘队列位置"：它没法区分大桌和小桌，一个 6 人团前面排着 2 人团时估计会差很远。
- 防饿死用"被插队次数"，在 `_drain` 里遇到次数达标的人就停止。放弃"给等得久的人加优先级"：优先级会让规则变得难以预测，而计数器的行为可以直接写进测试。代价是挡路时桌子空着，这是公平与利用率的取舍，要在面试里说出来。

**写法。**
- `_drain` 是不读实例状态的纯函数：输入队伍、空闲桌和规则，就地修改传入的副本并返回结果。真实的 `join` / `finish` 传真状态，`_simulate` 传复制品，规则只写一遍。把逻辑写进方法里，估计就得复制一份，两份迟早不一致。属于"函数式核心，命令式外壳"。
- `for ... else` 表达"找遍整个队伍都没人能坐就结束"：`break` 后重新从头找，`else` 分支返回。用标志变量要多一个可变状态。属于"循环的 else 子句"。
- `_best_fit` 用 `min` 加生成器表达式和 `default=None`，键是 `(容量, 桌号)` 元组，一次比较同时解决"最小够用"和"编号小的优先"。先建列表再判空要多写分支。属于"元组键的最优选择"。
- 时钟作为构造参数 `clock: Callable[[], datetime]` 注入：测试里用一个可拨动的假时钟，完全不用 `sleep`。直接调 `datetime.now()` 的代码无法测试等位估计。属于"注入时钟"。
- 排队项 `_Waiting` 是 `@dataclass(slots=True)`，可变（要累加被插队次数），但只在模块内部使用。外部看到的只有 id 和桌号，内部可变性不外泄。属于"内部可变、外部只读"。

**每关怎么走。**
- 第 1 关：`_Waiting` 数据类、`_best_fit`、不带防饿死的 `_drain`、`join` / `leave` / `finish`。校验放在改状态之前，重复检查要同时看排队和已入座。
- 第 2 关：`_simulate` 复制队伍（包括被插队次数），用一个"忙桌 → 空出时刻"的字典往前推进，每到一个空出时刻就调用同一个 `_drain`；`quote` 是往复制品队尾追加一个探针客人。
- 第 3 关：`_drain` 里加一行停止条件，`leave` 末尾补一次入座；`_simulate` 因为复用了 `_drain`，自动遵守新规则。
- 第 4 关：`change_size` 先校验再改，改完调用同一个收尾步骤。

**易错。**
- 估计时直接改了真实队伍或真实空闲桌。
- 把"队伍里第一个人"当成唯一候选，忘了前面坐不下的人要被跳过且保持顺序。
- 被插队计数只数"被跳过"而不是"被后面的人真正越过"；或者复制队伍时没带上计数，估计与实际不符。
- `finish` 之后只入座一个人，漏了被解除阻挡的后续的人。
- 超时的桌子被算成"过去的时刻"，得到负的等待时间。
- 重复 id 只查了排队、没查已入座。

**追问。**
- 想让客人预订（定时间）？答：预订是对某张桌在某段时间的占用，`_drain` 之前要先扣掉被预订占住的桌，估计里也要把预订当成固定的忙时段。
- 想按人数估计不同的用餐时长？答：`dining_time` 换成按人数取值的函数，入座时记录预计结束时刻，而不是在推演里统一加常数。
- 想通知排队的客人"到你了"？答：`finish` 已经返回新入座的人，调用方据此发通知；不要在 `Restaurant` 里直接发。
- 多个前台并发操作？答：所有入口共用一把锁，因为每个入口都是"读队伍、改队伍、改桌子"的整体。
- 怎么证明估计靠谱？答：属性测试：同一个状态下 `quote(n)` 等于随后真的 `join` 再 `estimate_wait`；再用模拟的时钟按预计时间推进，检验实际入座时刻吻合。

**级别期望。** 初级：第 1 关正确。中级：第 2 关的推演复用了同一份规则，错误处理完整。高级：主动指出预测与现实必须共用同一条规则，能谈贪心入座的局限和防饿死的公平性取舍。
