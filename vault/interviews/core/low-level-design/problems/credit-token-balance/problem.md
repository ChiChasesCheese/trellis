# 额度账本（Credit Token Balance）

一个按量计费的产品给用户发"额度"（credits）：每次发放是一个额度包，可以设过期时间；每次使用要扣额度，且先扣快到期的，免得白白过期。扣费请求可能因为网络重试而重复到达，上报的时间也可能乱序。你要写这本账：`CreditLedger`。

所有时间都由调用方通过 `at` 传入（带时区的 `datetime`），账本不读系统时钟。额度是整数。

**分关要求**（做完一关再看下一关）
- 第 1 关（约 20 分钟）：额度包、扣费、余额。
  - `grant(grant_id, amount, at, expires_at=None) -> None`：额度包从 `at` 起（含）可用，到 `expires_at` 失效（不含），`None` 永不过期。`amount <= 0` 或 `expires_at <= at` 抛 `ValueError`。
  - `charge(charge_id, amount, at) -> tuple[Allocation, ...]`：在时刻 `at` 扣 `amount`，只能用 `at` 时刻有效的包。先到期的先扣，永不过期的最后；同一时刻到期的，先发放的先扣，再按 `grant_id`。一笔可以跨多个包，返回按扣减顺序排列的 `Allocation(grant_id, amount)`。`amount <= 0` 抛 `ValueError`；额度不够抛 `InsufficientCreditsError`，账本原封不动。
  - `balance(at) -> int`：`at` 这一刻可用的额度，只算 `at` 及之前发生的事件，已经过期的包不算。
  - 例：包 `soon`（100，第 10 天到期）、`late`（100，第 30 天到期）。第 1 天扣 60，得 `(soon, 60)`；第 2 天再扣 60，得 `(soon, 40), (late, 20)`。
- 第 2 关（约 15 分钟）：幂等。
  - 同一个 `charge_id` 用相同的参数重试，返回和第一次相同的分配，不再扣第二次；参数不同抛 `ConflictError`。被拒绝的扣费不被记住，补了额度之后可以用同一个 id 重试。
  - `grant` 同理：相同参数重复调用什么都不做，参数不同抛 `ConflictError`。
- 第 3 关（约 25 分钟）：乱序到达的事件。
  - `at` 可以早于已经处理过的事件。账本的行为等同于所有事件按 `(at, 额度包先于扣费, id)` 排好序后处理。
  - 新方法 `allocations(charge_id) -> tuple[Allocation, ...]`：这笔扣费在"事件全部排好序"的结果里用了哪些包；迟到的事件可能改变它，但总额不变。不认识的 id 抛 `UnknownChargeError`。
  - 接受迟到事件的条件：重放之后，每一笔已接受的扣费仍然能全额扣下。否则抛 `InsufficientCreditsError`，账本原封不动。
  - 例：包 `g1`（第 10 天到期）、`g2`（第 20 天到期）各 100。第 5 天的 `c2` 扣 100，用的是 `g1`。随后迟到的 `c1`（第 3 天，100）到达：`c1` 用 `g1`，`c2` 的分配改成 `g2`。
- 第 4 关（选做）：作废额度包。
  - `revoke(grant_id, at) -> None`：从 `at` 起这个包剩余的额度作废，等价于把到期时间提前到 `at`（已经更早失效则什么都不做）；已经扣掉的不追回。不认识抛 `UnknownGrantError`；`at <= 发放时间` 抛 `ValueError`；会让某笔已有扣费凑不够则抛 `InsufficientCreditsError` 并保持原样。

**评分点**
- 账本只存事件，余额和分配都是对排好序的事件重放得到的结果：乱序、迟到、作废都变成"改事件表再重放"，没有回滚逻辑。
- 重放是一个不碰实例状态的纯函数，接受新事件之前先在副本上重放，通过才提交。
- 先到期先扣用堆实现；因为重放里时间单调向前，过期的包可以在堆顶惰性弹出。
- 幂等和冲突分开：相同参数返回原结果，不同参数报错；被拒绝的请求不留痕迹。
- 区间的开闭处理一致：发放时刻含，到期时刻不含，同一时刻先发放后扣费。
- 金额用整数，没有浮点。
- 能说清迟到事件为什么会改变旧扣费的分配，以及为什么总额不变且仍保证已接受的扣费不被饿死。
- 能讲出重放的代价和增量方案：事件很多时，只从最早的迟到点重放，或定期做快照。
