# 额度账本：题解

**一句话。** 账本只存事件，余额和每笔扣费用了哪些包都是把事件按时间排序后重放得到的；接受新事件前先在副本上重放，所有扣费仍能全额扣下才提交。

**关键决策。**
- 存事件、重放出结果。放弃"每次操作直接扣减每个包的剩余额度"：那种做法假设事件按时间顺序到达，迟到的事件会让已经做出的分配变错，补救就要回滚再重做，等于在写一个临时拼凑的重放。第 1 关的测试按顺序到达，用重放同样能过，所以后两关不用推倒重来。
- 事件排序键是 `(at, 额度包先于扣费, id)`。同一时刻先发放后扣费，保证"发放时刻就能用"；`id` 兜底，让结果与到达顺序无关。
- 接受事件的条件是"重放后每笔已接受的扣费仍然能全额扣下"。放弃"迟到事件一律拒绝"：乱序是常态，一律拒绝会丢账。放弃"一律接受，让旧扣费变成欠款"：已经告诉调用方成功的扣费不应该事后失败。代价是迟到的扣费有时会被拒绝。
- 幂等键是 id，附带参数比较：参数相同返回原结果，不同就是冲突。被拒绝的扣费不入账，所以补额度后可以重试。放弃"只按 id 去重"：同 id 不同金额会被悄悄忽略，是难查的账务错误。
- 先到期先扣用最小堆，键是 `(永不过期?, 到期时间, 发放时间, id)`。重放里时间只往前走，过期的包不会再有效，所以可以在堆顶发现过期就弹出，不必每次扫描全部包。放弃"每笔扣费把所有包排序一遍"：每笔扣费 O(g log g)，包多时慢。
- 作废包就是把到期时间提前，复用同一套"副本重放、通过再提交"的机制。放弃为作废单写一套检查，那样同一个"别饿死已有扣费"的规则会有两份实现。

**写法。**
- 事件是 `@dataclass(frozen=True, slots=True)`：`Grant`、`Charge` 不可变，可以比较和哈希，幂等判断就是一句 `old != new`；`dataclasses.replace` 生成改过到期时间的副本。可变对象要手写比较，并防着别处改它。属于"不可变事件"。
- `_replay` 是纯函数，输入事件表、输出分配和剩余额度，不碰 `self`。`_commit` 先传副本给它，成功才替换。把重放写在方法里就没法对副本试跑，失败时要手工回滚。属于"事件溯源加试运行提交"。
- 重放里的 `match event:` 加 `case Grant():` / `case Charge():` 按事件类型分派：每个分支只处理一种事件，缺分支一眼可见。`isinstance` 链或类型标签字符串更啰嗦。属于"按类型分派"。
- `heapq` 加惰性删除：堆里的包过期后不立刻删，等它浮到堆顶再弹。因为时间单调，这个判断永远正确，且每个包最多进出堆各一次。属于"惰性删除堆"。
- 返回值用 `NamedTuple`（`Allocation`）：既能像元组一样比较、拆包，又有字段名。普通元组让调用方记位置，数据类又要多写比较。属于"轻量记录类型"。

**每关怎么走。**
- 第 1 关：两个事件类、`_expiry_key`、`_replay`，再写 `grant` / `charge` / `balance`。先写重放，其余都是对它的包装。
- 第 2 关：`grant` / `charge` 里先查 id：相同返回原结果，不同抛冲突。
- 第 3 关：`allocations` 与 `_commit` 的副本验证；排序键保证乱序也有确定结果。
- 第 4 关：`revoke` 就是 `replace` 出新的到期时间再 `_commit`。

**易错。**
- 到期时刻算成有效，或发放时刻算成无效。
- 同一时刻先扣费后发放，导致刚发放的额度用不上。
- 被拒绝的扣费仍被记住，后续用同一个 id 重试永远冲突。
- 迟到的扣费在原地改了状态，没有验证旧扣费是否仍然成立。
- `balance(at)` 把 `at` 之后的扣费也算进去。
- 不同 id 之间没有稳定的排序，导致同一批事件换个到达顺序结果不同。

**追问。**
- 事件有上百万条，重放太慢怎么办？答：只从最早的受影响时刻重放，或定期保存重放快照；迟到事件通常离现在不远。
- 想让迟到的扣费总能成功，宁可让旧扣费失败？答：改成"重放后如果不够，标记最晚的那笔扣费为欠款"，需要把欠款也作为一种可结算的状态。
- 多进程并发写？答：事件追加到日志，按 id 去重，重放结果由单个写入者提交；读者用快照。
- 想支持退款？答：退款是一种新事件，把额度退回原来被扣的包，但包已过期就不再有效，重放时在对应时间点处理。
- 为什么 `balance` 只重放到 `at`？答：这样它是时间的函数，而不是到达顺序的函数，可以回答"上周三的余额"。

**级别期望。** 初级：第 1 关正确，顺序到达即可。中级：第 2、3 关通过，幂等与冲突区分清楚。高级：主动提出事件溯源、纯函数重放、试运行再提交，并能讨论重放的规模化与迟到事件的取舍。
