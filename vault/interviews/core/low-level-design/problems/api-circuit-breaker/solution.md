# 熔断器：题解

**一句话。** 熔断器是一个小状态机：下游持续失败时快速失败、给下游喘息时间，再用少量探测请求判断是否恢复；难点在状态转换在并发下的正确性——半开期只放少量探测、迟到的旧结果不能污染新状态、不持锁调用下游。参考实现见 `solution.py`。

**关键决策。**

- 枚举加条件分支，不做"每个状态一个类"。三种状态的差别只在"放不放行"和"结果怎么回报"两处分支，状态类会把一个 100 行的类拆成四个文件。如果每个状态的行为很复杂，才值得拆。
- `call` 拆成"拿许可（锁内）-> 调用下游（锁外）-> 回报结果（锁内）"。放弃的做法是整个 `call` 持锁：一个慢调用让所有线程排队，熔断器自己成了瓶颈。代价是许可和结果不在同一个临界区，所以需要代号。
- 代号 `_gen`，每次状态转换加一，许可带着领取时的代号。回报时代号不一致，只计入指标。放弃的做法是回报时看"当前是不是半开"：线程 A 在关闭状态时发出慢请求，期间熔断器打开又恢复到关闭，A 此时失败会被当成新一轮的失败；半开期的在途数也会被旧结果减成负数。
- 半开期用"名额"限流，而不是让所有请求都过去试。冷却一结束，所有等待的线程会同时冲向刚恢复的下游。名额取 1 最保守但恢复慢，取多个恢复快但风险更大。
- 连续失败数是默认，滑动窗口是可选。连续失败简单，适合低流量内部调用；失败穿插成功时它永远触发不了，所以要有窗口失败率，并配 `min_calls` 防止样本太少时误判。
- 状态不随时间自己变化。放弃的做法是后台线程定时从 OPEN 切到 HALF_OPEN：多一个线程、多一类竞态，而冷却时间到了之后并没有人需要这个状态，直到下一次调用。
- 回调在锁外调用。锁内只记下状态变化，`call` 结束前再派发；回调里读 `state` 或再调用 `call` 都不会死锁，回调抛异常也只记日志。

**写法。**

- `match self._state` 加 `case State.HALF_OPEN` / `case State.CLOSED` 回报结果。每个状态一个分支，OPEN 状态下的迟到结果被代号拦在前面；`if/elif` 链看不出分支是否覆盖了所有状态。模式：对枚举的分支（让每个状态各占一个 case）。
- 转换表 `_TRANSITIONS`（`MappingProxyType` 包住只读字典）加 `_move` 里的断言。四条合法转换写成数据，写错转换会立刻 `AssertionError`，而不是悄悄进入非法状态；表也直接就是文档。模式：转换表状态机。
- 注入时钟 `clock`，状态不自己随时间变。测试里换成可手拨的假时钟，冷却、慢调用都不需要 `sleep`。直接调用 `time.monotonic()` 的实现只能真等。模式：注入时钟。
- `@dataclass(frozen=True, slots=True)` 的 `Metrics`，每次读取都是一份新的快照。调用方拿到的不会被后续调用悄悄改写，也不会读到只更新了一半的三个计数。可变字典要么共享内部状态，要么每次读都得手动复制。模式：不可变快照。
- 锁内记事件、锁外派发（`_events` 加 `_dispatch`）。持锁时调用外部代码，回调里再进入熔断器就会死锁。模式：收集后派发（outbox）。

**每关怎么走。**

1. 第 1 关：先写 `State`、`CircuitOpenError`、`Metrics` 和构造函数，再写 `call` 的两个分支（拒绝、放行），最后写 `_acquire` 与 `_record`。注入假时钟，把四条转换各跑一遍。核心代码约 70 行。
2. 第 2 关：加 `_gen` 和 `_probes`。先写代号核对，再写半开期名额。并发测试用事件排顺序，不用 `sleep`。
3. 第 3 关：`is_failure` 在 `call` 的 `except` 里改两行；窗口失败率是 `_record` 的 `CLOSED` 分支多一条路径；慢调用在成功分支里比较耗时。
4. 第 4 关：冷却时间变成实例状态 `_timeout`，探测失败时乘因子，恢复时复位；通知用 `_events` 列表，在 `call` 返回前派发。

**易错。**

- 在锁内调用下游。
- 迟到的结果直接改状态，或者把半开期在途数减成负数。
- 半开期不限名额，冷却一到就放全量。
- 探测失败后没有重新计时，下一个调用立刻又被放行。
- 回到关闭或打开时没有清零半开期计数和窗口，旧样本污染新一轮。
- 业务 4xx 当成下游故障，一个坏参数的用户就能把熔断器打开。
- 降级函数依赖同一个下游，或者自己抛异常。
- 回调在锁内调用，回调里读 `state` 就死锁。
- 把 `KeyboardInterrupt` 之类也当成下游失败。

**追问。**

- 与重试、超时的关系：超时是熔断的前提，不超时的慢调用永远不会被记为失败。顺序一般是限流 -> 熔断 -> 超时 -> 重试，关键是重试不能绕过熔断。
- 粒度：一个下游一个熔断器，还是一个接口一个？太粗，一个坏接口拖垮整个下游；太细，样本不足、配置繁多。通常按"下游加关键接口"划分，并配舱壁（bulkhead）隔离线程池。
- 多实例：每个进程各自维护，简单且互不依赖；共享状态要引入共享存储，多一个故障点，通常不做。
- 降级与可观测：降级要快、不依赖同一个下游（缓存的旧值、默认值）；对"进入打开状态"告警，拒绝数激增通常比失败数更早反映影响面。
- 无锁版本：用原子引用保存不可变状态对象做 CAS，适合极高并发；锁版本在多数场景足够，且更易验证。

**级别期望。**

- 中级：三状态机，失败阈值和冷却时间，能放行、拒绝、恢复，有降级和计数。
- 高级：线程安全、不持锁调用下游、半开只放有限探测、代号挡住迟到结果、失败判定可配置。
- 资深：滑动窗口与慢调用、退避冷却、回调的锁外派发、与限流重试超时舱壁的组合、分布式部署下的取舍，并说清每一项在 60 分钟里为什么先不写。
