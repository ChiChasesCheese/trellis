# 复式账本：题解

**一句话。** 账本由两样东西构成：一份只追加、永不修改的分录日志（唯一的事实来源），和一组随每次写入同步更新的派生索引（余额、历史、冻结）；所有正确性落在三条不变量上：每条分录按币种借贷平衡、余额等于腿之和、纠错只靠新分录。参考实现见 `solution.py`。

**关键决策。**

- 日志加派生索引，而不是只存一个余额字段。只存余额，改错无法追溯，崩溃时钱会凭空出现，也证明不了总账是平的。放弃的另一个极端是"只存日志、读时求和"：读是 O(腿数)。代价是索引必须和日志同时更新，所以写入放在同一个临界区（生产里是同一个数据库事务）。
- 金额用带符号整数，不拆借方和贷方两个字段。"每个币种的腿之和为 0"是最容易检查的不变量，`total` 恒为 0 就是它在全账户上的版本。代价是要记住每类账户的正常余额方向。
- 去重表放在校验之前，且比较完整内容。放弃的做法是"只看 ID 是否存在"：同 ID 不同内容是调用方的 bug，悄悄忽略它会让第二笔钱消失；报 `ConflictError` 才能暴露问题。
- 冲正是新分录，不是修改。原分录原样保留，下游从日志里看得到"错了、改了、改成什么"。"一条分录只能被冲一次"写在 `post` 里，不写在 `reverse` 里，这样手工构造的 `reverses` 也绕不过去。
- 下限检查和写入在同一把锁里。放弃的做法是"先 `available` 再 `post`"：两个并发转账各自检查通过，一起透支。数据库里对应 `UPDATE ... SET balance = balance - x WHERE balance >= x`，检查与扣减是一条语句。
- 冻结是独立的一张表，不进日志，也不动账面余额。可用余额 = 余额 - 冻结合计。"释放加写入"做成 `post` 的参数，是因为分成两次调用，中间一刻钱既没冻住也没花出去，别的线程能插进来。
- 单把全局锁（`RLock`，因为 `reverse` 重入 `post`）。临界区只有字典操作，够用；按账户加锁要按账户 ID 排序依次取，避免两个分录以相反顺序加锁而死锁。

**写法。**

- `@dataclass(frozen=True, slots=True)` 写 `Posting / Entry / StatementLine`。日志里的分录一旦写入就不许变，冻结让"改历史"在语言层面就是错误，而且 `==` 直接比较内容，幂等判断（同 ID 同内容）一行就够。手写类要自己写 `__eq__`，还拦不住有人改字段。模式：不可变值对象。
- `NamedTuple` 写 `Key(account, currency)`。它仍是 tuple，能做字典键，但字段有名字，`key.account` 比 `key[0]` 不会看错；普通 `tuple[str, str]` 满屏下标，换一下顺序也没有任何报错。模式：具名元组（带名字的复合键）。
- `functools.wraps` 写 `_synchronized` 装饰器。几乎每个公开方法整个方法体都是临界区，锁的作用域写在方法头上，一眼看全；每个方法里手写 `with self._lock:` 既啰嗦，也容易漏掉一个。`RLock` 配合它，`reverse` 才能重入 `post`。模式：装饰器横切关注点。
- `bisect_right(hist, seq, key=...)`。历史行按序号严格递增，天然有序，二分的 `key` 参数直接按字段查找，不用另存一份序号列表来同步。线性扫描是 O(n)，另存列表要保证两份数据一致。模式：有序序列上的二分查找。
- 先算再提交：`post` 先把所有会失败的检查做完，才进入"不会再失败"的提交段。把校验混在修改里，失败时就留下半截状态。模式：先校验后提交（两阶段写入）。

**每关怎么走。**

1. 第 1 关：先写 `Posting / Entry` 两个不可变值对象，再写 `post` 的骨架：查重 -> 校验 -> 追加 -> 更新余额。然后 `reverse`（取反腿，再调 `post`）。核心代码约 75 行。
2. 第 2 关：每次余额变动追加一行 `(序号, 变动后余额)`，序号严格递增所以天然有序，`balance_at` 用二分。下限检查放在"校验之后、提交之前"，提交部分不允许再失败。
3. 第 3 关：`hold` 与 `release` 各自幂等，以 `hold_id` 为键。`post` 里把"要释放的冻结"带进下限检查（释放后可用更多），提交时一并标记为已释放。并发测试靠已有的锁就能过，要做的是确认没有任何一个读改写发生在锁外。
4. 第 4 关：`exchange` 只是拼一条四条腿的分录，经由中转账户 `fx`，各币种分别平衡。账本代码不用改，这是第 1 关"按币种分别平衡"这个决定的回报。

**易错。**

- 先改余额再校验，失败时留下半截状态。
- 失败的 `post` 仍然占用了序号，后面的序号对不上。
- 把"总和为 0"当平衡：`USD +100` 加 `EUR -100` 总和为 0，但两个币种各自不平。
- 重复提交时返回新序号，或者再记一次账。
- 冲正改了原分录，或者没有挡住"冲两次"。
- 同一账户出现在两条腿里，分别检查下限，忽略了净额。
- 下限检查用的是账面余额，忘了减冻结。
- `balance_at` 在序号刚好等于某次变动时少算一次，或者对从未出现的账户抛 `KeyError`。

**追问。**

- 热点账户（手续费收入这类每秒几万笔）：不在每次写入时更新同一行。只追加腿，后台周期性折叠成快照，读余额 = 最近快照 + 快照之后的增量。代价是读略慢，换来写入水平扩展。
- 防篡改：存储层只开放追加；分录按块计算哈希链，改历史会让后续哈希对不上；定期把最新哈希发布到独立存储。
- 对账：账本里的"应收渠道款"和渠道的结算文件对账，余额结算后应回到 0，剩下的差异就是要解释的项。
- 日志无限增长：按时间分区，旧分区转冷存储；余额索引和快照保证读取不依赖旧分区。
- 跨币种：这里的 `exchange` 已经是正确形状；真实系统还要在分录里记录汇率和报价编号，汇兑差额进入汇兑损益账户。
- 数据库实现：分录表和腿表都只插入，`(分录 ID)` 唯一约束就是去重，余额表与分录在同一个事务里更新。

**级别期望。**

- 中级：只追加的分录加余额表，借贷平衡，能处理重复提交，冲正能用。
- 高级：先校验后修改，冲突与重放分清，下限与写入原子，冻结与可用余额，历史余额用二分。
- 资深：热点账户的分片追加与快照、按账户排序加锁、哈希链与对账闭环、数据库事务与条件更新的写法，以及能说清各项在 60 分钟里为什么不写。
