# sd03 · 追问（followups）

> 每条：问题 → 思考 → 答案要点 → 可以说出口的一段话。数字沿用参考答案（1M msg/s、5,000 品种、预算 ~6 µs）。

---

## F1 用 Java 写，GC 停顿怎么办？

**思考**：先算分配率和停顿的代价（1 ms ⟹ 1,000 条消息），再说"根治是不分配"，最后才谈收集器。
**要点**：稳态零分配（预分配环、flyweight 解码、对象池/结构体数组、原语集合、不用 `String`/装箱/流/捕获 lambda）；验证：交易时段 GC 次数 = 0（`-Xlog:gc`、JFR）；预热阶段完成所有类加载与分配；`-Xms=-Xmx` + `AlwaysPreTouch` 避免运行时扩堆和缺页；ZGC 把停顿压到亚毫秒但有读屏障与并发线程开销，不解决 µs 预算；"一天分配一次的大堆 + 夜里重启"是务实选项；堆外/`MemorySegment` 绕开 GC 管理。
**可以说**：「100 MB/s 的分配率意味着每 10 秒一次 minor GC，停顿几 ms，比预算大三个数量级。所以我不调 GC，我让热路径不分配。」

## F2 为什么单线程 run-to-completion，不是多线程流水线？怎么扩展？

**要点**：线程交接 = 至少一次跨核缓存行传递（~50–100 ns）+ 排队抖动；3 次交接约 0.3 µs，占 10 µs 预算 3%，且引入尾部；单线程一条消息 ~1 µs ⟹ ~10⁶ msg/s/核；扩展靠按品种分片（shared nothing），不靠加锁；流水线只用于必须换线程的 I/O 与持久化。局限：一个慢策略会拖慢同分片其他策略 ⟹ 时间预算 + 看门狗。
**可以说**：「并行度来自品种分片，不来自把一条消息的处理拆给几个线程。」

## F3 内核旁路是什么？Java 怎么用？

**要点**：绕过内核协议栈，应用直接轮询网卡环形队列：省系统调用（~0.1–1 µs）、中断、内核/用户拷贝、调度唤醒；典型内核栈单跳几 µs–十几 µs，旁路 ~1 µs 或更低（量级）。实现：DPDK 轮询驱动、Solarflare OpenOnload/ef_vi 一类用户态栈。代价：独占核心 100% 忙等、特殊网卡驱动、调试困难、功能受限（防火墙、`tcpdump` 等工具）。Java：多数通过对 socket 透明的用户态栈（`LD_PRELOAD`）或 JNI/FFM 调本地库；普通内核栈下用 NIO `Selector` + `TCP_NODELAY`。
**可以说**：「旁路省的是内核这一跳，不是网线；Java 用透明的用户态栈最省事。」

## F4 组播行情丢包、乱序、重复怎么办？

**要点**：序号 + A/B 双路"先到者胜"去重（已见序号位图）；任一路丢包无感；两路同缺 ⟹ 缺口：标记 STALE，请求重传或快照 + 增量重新对齐，对齐前禁止对该品种发新单；小窗口重排处理轻微乱序；监控缺口率、包间隔。
**可以说**：「缺口不是错误，是状态：该品种进入 STALE，策略看不到它也不能交易它。」

## F5 风控放在哪？为什么不只在进程内做？

**要点**：进程内内联 O(1) 检查最快（~0.3 µs），但与策略同进程/同内存，bug 或内存损坏可同源；所以三层：进程内闸门、独立风控进程/设备（独立仓位视图，可切断会话）、交易所/清算侧（cancel-on-disconnect、整体撤单、信用额度）。监管上要求对订单设置自己直接且排他控制的预交易风控（SEC 15c3-5，通识）。O(1) 靠增量维护的聚合量和数组查表。
**可以说**：「快的检查和独立的检查是两件事，我两个都要，所以是纵深防御。」

## F6 重启后怎么保证不重复发单、状态正确？

**要点**：订单真相在交易所；恢复 = 快照 + 重放日志 + 重新登录协商会话序号 + 与交易所对账（查未完成订单/当日成交/持仓）；ClOrdID 全局唯一且重启后继续单调递增；PENDING 状态的订单（无回报）主动查询，仍未知则保守处理（按可能已成交算仓位）并撤销；恢复期间所有品种 STALE，不交易，直到行情对齐。
**可以说**：「日志告诉我'我做了什么'，交易所告诉我'发生了什么'，两者差异就是对账要解决的。」

## F7 决定性：什么会破坏重放？怎么保证？

**要点**：非决定性的成因：读墙上时钟、`HashMap` 遍历顺序、浮点运算顺序、无种子随机数、线程调度/多输入源的顺序、内存地址相关。对策：时间来自事件时间戳；有序/数组结构；定点整数；**日志记录线程的消费顺序**（不是各源自己的顺序）；策略无 I/O；固定的初始化顺序。验证：每次发布前，用一整天的生产日志重放，输出与生产逐字节对比（回归）。
**可以说**：「决定性不是好习惯，是回测、复盘、崩溃恢复、主备一致的共同前提。」

## F8 日志要 fsync 吗？热路径等不等？

**要点**：热路径只写内存环，Journaler 异步追加到 mmap 文件。进程崩溃：页缓存里数据还在，不需要 fsync；掉电/内核崩溃：需要 fsync 或已复制到另一台机器；机房故障：靠交易所/清算行对账。fsync 本身在 NVMe 上几十 µs 到 ms 不定，不能放进 µs 预算；日志环满 ⟹ 告警/熔断，而不是丢事件。区分"交易所自己的撮合引擎必须先落日志再处理"与"客户端以交易所为真相"。
**可以说**：「持久性分三档，我只为热路径付最便宜的一档，剩下的靠复制和对账。」

## F9 熔断（kill switch）怎么设计？延迟多大？

**要点**：三层（进程内 `volatile` 标志 / 独立进程或设备 / 交易所 cancel-on-disconnect 与整体撤单）；自动触发条件：仓位/亏损超限、拒单率、下单速率异常、行情陈旧、日志落后、对账差异；每单检查一次标志（~ns，单写者控制面写，热线程读）；触发后撤销全部未完成订单、禁新单、保持行情接收；恢复需要确认；定期演练。
**可以说**：「熔断的第一原则是它不能依赖被熔断的东西。」

## F10 主备怎么切换才不会双发？

**要点**：备机热备（收行情，经复制日志/drop copy 得到回报，不发单）；发单权令牌带 epoch；切换：确认主机真停（STONITH）→ 交易所 cancel-on-disconnect 已撤单 → 备机获发单权 → 新会话登录 → mass cancel → 对账 → 恢复；不做 active-active 发单（除非按品种严格分区）；RTO 秒级，期间不报价是代价。
**可以说**：「宁可停几秒，也不让两个实例同时拥有同一个账户的发单权。」

## F11 怎么扩展到更多品种和跨品种风控？

**要点**：加分片；分片内无共享；跨品种全局限额拆成每个分片的预算（credit），分片内用本地计数器检查，周期性异步再平衡，预算保守；或全局视图放在独立 Risk Gateway（更慢但全局）；高流动性品种独占核心。
**可以说**：「局部检查通过但全局超限是预算滞后的代价，所以预算要保守，并且全局检查有独立兜底。」

## F12 怎么测量并证明 p99.99？协调遗漏是什么？

**要点**：线缆上测（tap + 硬件时间戳），不只是应用内；分段直方图（HdrHistogram 思想）；固定速率发送器，按"应发送时间"计延迟避免协调遗漏；分位数不能相加，必须端到端测；延迟-时间图找周期性毛刺的共同原因（GC、刷盘、THP、中断）；1M msg/s 时 p99.99 意味着每秒 100 条超标，所以要看 p99.99 之后的 max 与持续时间。
**可以说**：「我不信应用里的 `nanoTime`，我信线缆上的时间戳。」

## F13 时钟：时间戳从哪来？PTP 失步会怎样？

**要点**：网卡硬件时间戳 + PTP/GPS 同步，精度远优于 NTP；业务时间用事件里的时间戳（决定性）；监控偏移，失步 ⟹ 告警，对账与延迟度量降级（交易功能不应依赖绝对时间，只依赖单调与序号）；`System.nanoTime()` 只用于相对延迟。
**可以说**：「决定性要求时间是输入，不是环境。」

## F14 如果 Java 的下限不够，你怎么办？

**要点**：承认；分工：最短的报价-撤单环用 C++/FPGA，Java 做策略编排、风控监控、对账、研究回放、日志基础设施；用 FFM/共享内存（SPSC 环）在 Java 与本地进程间传递事件；先测量再迁移（别凭感觉重写）。
**可以说**：「我会先用测量告诉我 Java 的下限在哪，而不是预设它够不够。」

## F15 订单回报乱序 / 缺失 / 重复，OMS 怎么保持正确？

**要点**：execId 去重（重复）；会话序号检测缺失，请求补发；终态订单收到旧回报视为重复；非法转移（超量成交、成交价越限价、终态后再 Fill）不改状态并报警；PENDING 超时主动查询；仓位始终是成交事件的纯函数，所以修复 = 追加一条"对账修复"事件，而不是直接改数字。
**可以说**：「状态是事件的函数，修复也是事件。」
