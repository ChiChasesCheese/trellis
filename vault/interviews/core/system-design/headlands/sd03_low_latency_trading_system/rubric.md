# sd03 · 评分表（rubric）

> 三档：**strong**（senior 门槛）· **ok** · **weak**。strong = 数字 + 失败模式 + 验证方法。

| 维度 | strong | ok | weak |
|---|---|---|---|
| **1. 澄清** | 先问延迟目标（分位数）、品种数与消息速率、场所数、错单与丢行情的相对代价、RTO；判断这是热路径题还是平台题 | 问了速率，没问错误代价 | 不问数字；直接画微服务 |
| **2. 估算** | 把速率翻译成每条消息预算（1 µs ≈ 3,000 周期 ≈ 10 次未命中）；停顿 × 速率（1 ms = 1,000 条）；日志速率与每日体量；簿与风控状态大小；Little 定律 | 估算了吞吐与带宽 | 只有 QPS，没有 µs；认为瓶颈是带宽 |
| **3. 架构** | 分片 + 单写者 + run-to-completion；SPSC 环；Feed Handler / 分片 / 网关 / Journaler 分工；说明哪里必须交接、哪里不拆线程 | 有流水线图，但每段都是独立线程 | Kafka / 数据库 / 锁出现在热路径 |
| **4. 行情** | 组播、A/B 仲裁、序号、缺口 ⟹ STALE ⟹ 禁止交易、快照 + 增量恢复；flyweight 解码；数组订单簿；定点价格 | 知道序号和重传 | 把行情当 TCP 流 / 忽略丢包 |
| **5. 风控** | O(1) 内联检查清单；增量聚合；fail closed；三层熔断；独立性论证；监管背景 | 列了检查项 | 风控只在策略里 / 事后检查 |
| **6. 状态与恢复** | 谁是 source of truth；决定性 + 输入日志 + 快照重放；日志环不能丢；mmap 与 fsync 的故障层次；恢复流程含对账；ClOrdID 单调 | 提到日志与重启 | 状态存数据库、每单同步写；恢复=重启 |
| **7. 订单入口与对账** | 会话序号、心跳、cancel-on-disconnect、限速、重连；drop copy 独立对账；差异 ⟹ fail closed | 提到 FIX 与对账 | 忽略重复/缺失回报 |
| **8. 高可用** | 主备不双发；发单权 + fencing + STONITH；RTO 的代价明确 | 说"主备切换" | active-active 发单；没谈脑裂 |
| **9. Java 纪律** | 零分配证据（GC 次数 = 0）、预热与单态调用点、safepoint、堆外与数组、无锁、绑核；虚拟线程不进热路径；诚实说明 Java 的下限与分工 | 知道 GC 要调 | 认为调好 G1/ZGC 就行；或回避 Java |
| **10. 度量与测试** | 线缆上度量、分段直方图、协调遗漏、日回放回归、模拟交易所、故障注入、灰度 | 提到压测与监控 | 没有证明 p99.99 的办法 |
| **11. 沟通** | 先结论后展开；主动指出弱点与取舍；每个组件说失败模式 | 条理清楚但被动 | 只描述 happy path |

## 一票否决（出现任一条，整体降一档）

* 把消息队列/数据库/带锁结构放在 tick-to-trade 路径上而无量化论证。
* 没有任何 fail-closed 机制（熔断/行情缺口/对账差异）。
* 主备方案会让两个实例同时发单。
* 没有估算每条消息的预算，或认为"加机器"能解决延迟。
