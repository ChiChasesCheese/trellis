# sd01 · 评分表（rubric）

> 自评用。每个维度三档：**strong**（senior 门槛）· **ok**（能过但不拔尖）· **weak**（会被追问击穿）。
> 总原则：**strong = 有数字 + 有失败模式 + 有验证方法**。

| 维度 | strong | ok | weak |
|---|---|---|---|
| **1. 澄清与定义** | 开口先拆「没用」（静态不可达 / 动态未用 / 公共 API），问语言、构建系统、规模、误报与漏报哪个更贵；明确"产出候选而非自动删除" | 问了范围，但没有区分静态与动态 | 直接开始画系统图，或默认"没人引用就是没用" |
| **2. 核心模型** | 符号图 + 根 + 可达性标记（和 GC 类比）；能解释为什么 `grep` 找不到死环；指出根的定义决定成败 | 说到引用图和遍历，但根集合含糊 | 只有 `grep` / IDE 提示 / 覆盖率 |
| **3. 估算** | 推出符号数、边数、CSR 大小（~80 MB@2×10⁷ 行）、标记时间（亚秒）、索引核·秒；得出"分布式只用在索引，图是单机问题" | 估算了代码量或机器数，但没推出图的大小 | 默认上 Spark / 分布式图计算，没有数字 |
| **4. 精度的难点** | 反射 / DI / SPI / 序列化 / JNI / 配置里的类名 / 公共 API / 虚调用（CHA vs RTA）；每个都有对策与 blocker 记录 | 提到反射与公共 API，对策笼统 | 没提动态机制，或说"静态分析处理一切" |
| **5. 可解释性** | 每个候选带证据卡：见证、blockers、信号、置信度；活的符号有最短路径，死的符号有"所有入边来源均不可达"；死簇整体处理 | 说"附上原因"，但没讲具体是什么 | 输出一个布尔值或一个无来源的分数 |
| **6. 动态证据** | 类加载日志 vs 方法级探针的成本 / 偏差对比；知道采样的假阴性；稀有但必要的路径 `@KeepAlive` + 演练；组合规则 | 提到覆盖率 / 日志，没分析偏差 | 把"测试覆盖率低"当作死代码 |
| **7. 删除流程** | owner 拆分、小 PR、软删除、观察期、revert 路径、按风险分级（L0/L1 直接，L2/L3 慢）、熔断刹车 | 提到 PR 和审核 | 自动删除 |
| **8. 评估** | 回测 git 历史、种子注入、抽样人审（含置信区间）、对照现有工具、回归（确定性） | 提到"人工检查样本" | 没有评估办法 |
| **9. 增量与多语言** | 索引按内容哈希缓存、图全量重算；跨语言边（JNI / IDL）；覆盖率不足 fail closed；构建配置取并集 | 提到增量，没讲为什么图不用增量 | 假设单语言单配置 |
| **10. Java / 交易公司语境** | 在字节码上分析的理由；CSR + `int[]` + `BitSet`；交易系统冷路径（熔断 / 灾备）的特殊性；"change surface" 的价值主张 | 提到 Java 但没利用 | 与公司背景无关的通用答案 |
| **11. 沟通** | 先给 30 秒结论，再展开；每 10 分钟确认方向；主动指出自己方案的弱点 | 有条理但被动 | 一口气讲完不停；被打断就乱 |

## 一票否决（出现任一条，整体降一档）

* 提议"静态分析出结果就自动提交删除"。
* 没有说明如何处理反射 / 公共 API / 冷路径。
* 把"覆盖率低"当作"没用"的充分证据。
* 对 10⁸ 行规模给不出任何数量级。
