# sd02 · 评分表（rubric）

> 三档：**strong**（senior 门槛）· **ok** · **weak**。strong = 数字 + 失败模式 + 验证方法。

| 维度 | strong | ok | weak |
|---|---|---|---|
| **1. 澄清** | 把"有界延迟"量化（p99.9、两档 SLO）；问是否允许提前、触发=做什么、取消、重复语义、规模、远期范围；划清调度器与执行器边界 | 问了规模和延迟，没问不早/重复 | 不问直接设计；把 cron 平台的所有功能都塞进来 |
| **2. 估算** | 推出平均/峰值速率、积压、内存索引（~12 GB）、近期窗口、**整点突发 180 倍**、日志速率；得出"容量不是问题，突发与可用性才是" | 估算了 QPS 和存储，没发现突发 | 没有数字，或默认"需要几十台机器" |
| **3. 找到期任务的机制** | 先提出轮询数据库作基线并说明适用范围，再引入分层时间轮；解释 O(1) 插入/取消、层数与覆盖范围、近期窗口+远期分层 | 说用优先队列/时间轮，但没比较 | 全表扫描，或每任务一个线程 / `sleep` |
| **4. 持久化与恢复** | WAL 为真相，先日志后内存后回复；group commit；快照 + 重放；热备；崩溃窗口分析（交付与 Fired 的顺序） | 提到数据库/WAL，没分析崩溃窗口 | 只放内存，或认为"数据库事务就够了" |
| **5. 语义** | at-least-once + 幂等键；解释为何不承诺 exactly-once；outbox/inbox 的位置 | 说"用幂等"，没讲来源 | 声称 exactly-once 且没有机制 |
| **6. 一致性与故障转移** | 租约 + epoch fencing + 下游幂等两道防线；暂停进程的场景；故障切换时间算进 Δ | 提到选主，没讲脑裂 | 忽略脑裂；"用 Redis 锁" |
| **7. 突发与公平** | 容量不等式；批量分发；摊平（smear）；租户级限流与 EDF/加权公平；背压与指标 | 提到限流 | 假设均匀分布 |
| **8. 时钟** | UTC 瞬时点；单调 vs 墙上；ε_max；偏移监控；时区/夏令时；客户端时钟 | 提到 NTP | 用 `System.currentTimeMillis()` 推进一切 |
| **9. Java 与机械同情** | 并行数组/堆外代替对象；单写线程 + MPSC；`parkNanos` 绝对截止时间；`DelayQueue`/`ScheduledThreadPoolExecutor` 的边界；虚拟线程只用于外围 I/O | 知道 JDK 有定时器 | 把 3×10⁸ 个对象放进 `PriorityQueue` |
| **10. 测试与观测** | 虚拟时钟、属性测试、崩溃重放、故障注入；lateness 直方图与告警阈值 | 提到压测 | 没有测试和监控方案 |
| **11. 沟通** | 先结论后展开；主动说弱点（如"整点突发是最大风险"）；对追问有三层回答 | 条理清晰但被动 | 只画框图不算数 |

## 一票否决（出现任一条，整体降一档）

* 声称"恰好一次"而没有幂等/去重机制。
* 先通知调用方成功、后写日志（或无日志）。
* 没有考虑整点聚集/突发，或把 Δ 当作平均延迟。
* 用 `Thread.sleep` 循环 + 全表扫描作为最终方案。
