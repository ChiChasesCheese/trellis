# sd02 · 追问（followups）

> 每条：问题 → 思考 → 答案要点 → 可以说出口的一段话。数字沿用参考答案的假设（3×10⁸ 积压、平均 1,157/s、整点突发 2.08×10⁵）。

---

## F1 为什么不直接轮询数据库？

**思考**：先肯定它在小规模下是对的，再给出具体的失效点（延迟下界、热点索引、突发、精度），而不是说"不够快"。
**要点**：轮询周期 p 是延迟下界（Δ=1 s 要 p≈几百 ms）；所有 worker 读同一个索引热点，同时有随机时间的插入和大量"已触发"行的删除，B-tree 膨胀；整点 2×10⁵ 同时到期时 `LIMIT k` 批量领取要几十个来回，每次领取一个事务；毫秒级精度需要更高频率轮询。适用条件：Δ 分钟级、规模 < 10⁷、已有成熟 DB。
**可以说**：「如果 Δ 是分钟级我就用 `SKIP LOCKED` 轮询，简单且对。这里 Δ 是秒级、有 180 倍的整点突发，我把'找到期任务'从数据库查询变成内存里的 O(1) 出轮。」

## F2 时间轮 vs 优先队列（堆）：复杂度与实际差别？

**要点**：堆：插入/删除 O(log n)，取最小 O(1)；时间轮：插入/删除 O(1)，到期扫描 O(到期数)，分层后每个定时器最多降级 (层数−1) 次，均摊 O(1)。精度：时间轮最多晚 1 tick，要"不早"就向上取整。内存：堆通常每个定时器一个对象（`DelayQueue`/`ScheduledThreadPoolExecutor`）→ GC 压力；时间轮可用并行数组。取消：堆的随机删除 O(n) 或惰性删除（留墓碑），时间轮的双向链表 O(1) 摘除。堆的优点：任意精度、实现简单、n 小时更快。
**可以说**：「n 在 10⁵ 以下我用堆；10⁶ 以上、取消频繁、对象要零分配，用分层时间轮——复杂度和常数、GC 都更好。」

## F3 机器挂了会丢任务吗？恢复要多久？

**要点**：不丢：写路径"先日志（≥2 副本）后内存后回复成功"。恢复：最新快照 + 重放日志；12 GB 快照读 2 GB/s ≈ 6 s + 尾部日志；热备 follower 持续重放，切换近乎 0（受失败检测 3–5 s 主导）。宕机期间到期的任务恢复后立即补发（按 fireAt 升序），延迟超出 Δ 但满足第二档 10 s（若检测+选主 ≤ 10 s）。
**可以说**：「持久性来自'回复成功之前日志已有两份'；可用性来自热备；延迟上界是失败检测加选主，我把它单独列为第二档 SLO。」

## F4 会不会触发两次？怎么保证"恰好一次"？

**要点**：不承诺 exactly-once。at-least-once 的来源：交付成功与写 `Fired` 之间的崩溃窗口，恢复后会重发；反向顺序会丢触发（违反 I4），所以顺序固定。下游用 jobId 作幂等键去重；若下游是同一数据库，业务结果与"已处理 jobId"同事务提交才有效果上的 exactly-once。调度器自身保证同一任务在日志里只有一个活动状态。
**可以说**：「交付可以重复，效果靠幂等键去重。我宁可重复也不丢。」

## F5 取消和触发同时发生怎么办？

**要点**：同一分片的所有命令（cancel、到期出轮）由单写线程串行处理，不存在数据竞争，只有业务顺序：cancel 先 → CANCELLED，摘除 O(1)；到期先 → DISPATCHING，cancel 返回 TOO_LATE（幂等：重复 cancel 同样返回）。分布式角度：cancel 请求必须路由到同一分片 leader，并且与触发使用同一个日志序列。如果 cancel 已经确认成功，则不变量："确认取消之后不会再有新的触发"——除非已在途的交付（需要下游配合再检查，可选）。
**可以说**：「单写者把竞态变成顺序：谁先进入日志谁定义语义。」

## F6 整点有 20 万个任务同时到期，怎么保证 Δ？

**要点**：先算：平均 1,157/s，整点突发 2.08×10⁵/s = 180 倍平均；要 Δ=1 s，分发容量必须 ≥ 突发/Δ。方案：批量发布（批 1,000，多分区并行，41 MB/s 不重）；API 提供容忍窗口 `notAfter`，装载时确定性抖动 `hash(jobId) % slack` 摊平；租户级限流 + EDF 优先级（lateness 最大者优先）保证公平；背压告警。写出容量不等式：同时到期数 / Δ ≤ 分发容量。
**可以说**：「Δ 是承诺，所以要做容量规划；能和调用方协商容忍窗口就摊平，不能就买峰值容量。」

## F7 时钟：怎么保证不早？客户端时钟和服务端不一致呢？

**要点**：fireAt 是 UTC 瞬时点；服务端用校准后的墙上时钟比较，触发条件加误差上界 ε_max（NTP 局域网可优于 1 ms、公网通常几十毫秒以内 ≪ Δ=1 s）；推进时间轮用单调时钟，墙上时钟回拨时暂停推进；偏移监控 + 超阈值自我让位；时区/夏令时在 API 层解析并在装载前再解析一次；`fireAt ≤ now` 立即触发并告知。
**可以说**：「单调时钟推进，墙上时钟比较，误差上界写进触发条件；代价是几毫秒，换来'不早'。」

## F8 脑裂：旧 leader 暂停 30 秒后醒来继续分发，怎么办？

**要点**：fencing token（epoch）贯穿日志和下游交付，旧 epoch 被拒；leader 每次分发前用单调时钟检查租约，leader 租约时长短于 follower 认为的时长；下游幂等作为第二道防线；监控 fencing 拒绝次数。不要只依赖"租约超时"——暂停的进程不知道自己暂停过（《DDIA》第 8 章）。
**可以说**：「租约不足以防旧 leader；epoch 加下游幂等才是两道防线。」

## F9 任务有大负载或数量巨大、最远一年，内存放得下吗？

**要点**：索引 40 B × 3×10⁸ = 12 GB 放得下，负载不进内存（负载引用）；只有近期窗口（10 分钟，28–167 MB）在时间轮里；远期放按小时分段的磁盘桶，装载器提前装入。堆上用并行数组/堆外，避免 GC 扫描；也可用 ZGC 管大堆，但"数组不是对象"更根本。
**可以说**：「内存里是索引和近期窗口，不是全部数据。」

## F10 周期（cron）任务怎么支持？

**要点**：归约成一次性任务链：触发成功后（或触发时）按 cron 表达式计算下一次 fireAt，调度一个新的一次性任务；记录 `scheduleId` 与 `occurrence` 序号以幂等；错过的触发（宕机期间）的策略（补发全部/只补最近一次/跳过）要显式，由业务选择。
**可以说**：「周期任务 = 一次性任务 + 触发后调度下一次，不需要第二套机制。」

## F11 多租户公平：一个租户提交了一亿个任务怎么办？

**要点**：提交时按租户限流 + 配额；到期出轮后按租户分队列，加权公平分发（WFQ / DRR）；每个租户有"最大同时到期数"阈值，超出的任务视为 lateness 归因于租户自身；监控按租户的 lateness。
**可以说**：「调度器的公平性不在时间轮，而在出轮之后的分发队列。」

## F12 下游宕机或很慢，重试怎么设计？

**要点**：重试 = 再调度（`nextAt = now + backoff(attempt)`，指数退避 + 抖动，上限与次数），复用时间轮；超过上限进入死信队列并告警；按目标做断路器/舱壁，避免重试风暴压垮下游或耗尽本地线程（虚拟线程可以便宜地等待，但**不会**让下游更快，仍需并发上限）。
**可以说**：「重试不是新机制，只是把任务重新放回时间轮。」

## F13 怎么测试它是对的？

**要点**：虚拟时钟注入，纯函数状态机；属性测试（不早 / 不丢 / 不重 / 延迟 ≤ tick）；随机崩溃点 + 快照/重放，对照不崩溃的参考执行；故障注入（暂停的 leader、落后的 follower、磁盘满）；与排序 map 做差分测试。
**可以说**：「我把时间当成输入而不是环境，所以测试是确定性的。」

## F14 如果面试官说"规模再 ×100"，你的设计哪里先崩？

**要点**：先算：积压 3×10¹⁰ → 索引 1.2 TB，单机内存放不下 → 提高分片数（每片仍 ≤ 几十 GB）；分片是逻辑分片（例如 4,096 个）映射到物理节点，重平衡移动整个分片（日志 + 快照）；突发 ×100 → 分发容量与队列分区数、协调服务的选主压力、元数据服务；最先崩的通常是**分发层/下游**，而不是调度器核心。
**可以说**：「我会先问下游能不能吃下，再扩调度器；分片数在最初就设成'逻辑分片多于机器数'。」
