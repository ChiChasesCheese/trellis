# 消息队列八股：Kafka 分区与重平衡、顺序、不丢消息、积压、死信

消息队列（message queue）让生产者和消费者异步解耦：生产者把消息写进去就返回，消费者按自己的速度拿。主要用途是削峰填谷、解耦服务、异步处理和事件分发。面试里以 Kafka 为主，辅以 RabbitMQ / RocketMQ 的对比。典型问法是一条链：Kafka 为什么快 → 分区怎么定 → 顺序怎么保证 → 怎么不丢不重 → 重平衡为什么卡 → 积压了怎么办 → 毒消息怎么处理。每题按 **机制 → 为什么 → 数字或取舍 → 追问** 作答。Kafka 的系统性学习在 `kafka` 域；幂等消费与事务消息在 [[tiktok-idempotency-transactions]]。

## 速记：这一页的 12 个问题

| # | 问题 | 一句话答案 |
|---|---|---|
| 1 | Kafka 的整体结构 | topic → partition → replica；consumer group 内一个分区只给一个消费者 |
| 2 | 为什么快 | 顺序写 + page cache + 零拷贝 + 批量 + 压缩 |
| 3 | 分区数怎么定 | 目标吞吐 ÷ 单分区吞吐，只增不减，改分区会打乱 key 映射 |
| 4 | 怎么保证顺序 | 同一 key 到同一分区；幂等生产者；消费端不要乱并发 |

| 6 | 怎么不重复 | 至少一次 + 消费端幂等；Kafka 事务只覆盖 Kafka 内部 |
| 7 | 重平衡为什么卡、怎么避免 | 协作式分配 + 静态成员 + 控制处理时间 |
| 8 | 副本、ISR、高水位 | 只有 ISR 里的副本能当 leader；HW 之前的消息消费者才可见 |

| 11 | 延迟消息怎么做 | Kafka 没有原生；时间轮或分级 topic；RocketMQ 5.x 原生 |
| 12 | Kafka、RabbitMQ、RocketMQ 怎么选 | 吞吐与流处理选 Kafka，复杂路由选 RabbitMQ，事务消息选 RocketMQ |

## Q1. 说一下 Kafka 的整体结构

- **概念**：主题（topic）被切成多个分区（partition），每个分区是一个只追加的日志，消息有分区内递增的偏移量（offset）。每个分区有多个副本（replica），其中一个是 leader，负责读写，其余是 follower，从 leader 拉数据。
- **消费**：消费者组（consumer group）内，一个分区同一时刻只分给一个消费者；不同的组各自独立消费，互不影响。组内消费者数超过分区数，多出来的空闲。
- **存储**：每个分区在磁盘上是一串分段文件（log segment），每段有稀疏索引（offset 索引和时间索引），按 offset 二分查找；超过保留时间（`retention.ms`，默认 7 天）或大小的整段删除；`cleanup.policy=compact` 的 topic 只保留每个 key 的最新值。
- **控制面**：3.x 起可以用 KRaft（Kafka 自己的 Raft 元数据仲裁）取代 ZooKeeper，4.0 起完全移除 ZooKeeper。
- **追问 · 分区是并行度的单位，也是顺序的单位**：消费并行度的上限等于分区数；顺序只在分区内有。这句话要背下来。

## Q2. Kafka 为什么吞吐这么高？

- **顺序写**：消息追加到文件末尾，磁盘顺序写（几百 MB/s）接近内存随机写的速度。
- **页缓存**（page cache）：写入先到操作系统页缓存，由操作系统异步刷盘；读最近的数据时直接从页缓存出，不经过 JVM 堆，没有 GC 压力。
- **零拷贝**（zero-copy）：消费者读取用 `sendfile`，数据从页缓存直接到网卡，不经过用户态，省掉两次内存拷贝。
- **批量与压缩**：生产者攒批（`batch.size`、`linger.ms`），整批压缩（lz4、zstd、snappy），网络和磁盘字节数都少。
- **分区并行**：多个分区分布在多台 broker，读写并行。
- **取舍**：`linger.ms` 越大吞吐越高、延迟越大；`acks=all` 比 `acks=1` 延迟高。
- **追问 · 持久化和速度不矛盾吗？** 默认只写页缓存，不每条 fsync；可靠性靠多副本而不是单机刷盘。

## Q3. 分区数怎么确定？

- **公式**：`分区数 ≥ max(目标吞吐 ÷ 单分区生产吞吐, 目标吞吐 ÷ 单分区消费吞吐)`，再按期望的最大消费者数取上界。
- **算例（假设数字，要说明来自压测）**：目标 300MB/s，单分区生产 30MB/s、消费 15MB/s：生产需 10 个，消费需 20 个，取 20，再留 50% 余量约 30 个。
- **为什么不能随便多**：每个分区在 broker 上是目录和文件句柄；分区越多，leader 选举和重平衡越慢，端到端延迟增加（需要复制更多分区）；单 broker 的分区总数建议控制在几千个以内；客户端内存按分区分批缓冲。
- **只能增不能减**；而且**增加分区会改变 `hash(key) % 分区数` 的映射**，同一 key 的新旧消息会落到不同分区，破坏顺序。所以第一次要留余量，或者新建一个分区更多的 topic 迁移。
- **追问 · 消费者数量应该是多少？** 不超过分区数；分区数是消费者数的整数倍，分配最均衡。

## Q4. Kafka 怎么保证消息顺序？

- **分区内有序，分区间无序**。需要顺序的消息用同一个 key（比如订单 ID、用户 ID），按 key 哈希到同一个分区；全局严格顺序只能一个分区，吞吐降到单分区水平，通常不是好设计。
- **生产端**：重试会乱序。批次 1 失败重试，批次 2 已经成功，顺序就反了。解决：开启幂等生产者 `enable.idempotence=true`（Kafka 3.0 起默认开），此时 `max.in.flight.requests.per.connection ≤ 5` 也保证顺序，因为 broker 用序列号拒绝乱序批次。
- **消费端**：拿到消息后丢进线程池并行处理就乱了。解决：按 key 路由到固定的内部线程队列（同 key 串行、不同 key 并行）。
- **追问 · 分区数变了，顺序怎么保？** 见 Q3，变分区前先让该 topic 的消息排空，再切换；或者用新 topic。
- **追问 · 业务上能否不依赖顺序？** 更好的办法：消息里带版本号或状态机，消费者发现状态非法或版本落后就丢弃或延后，这样对乱序也安全。

## Q5. Kafka 怎么保证消息不丢？

不丢要三端一起看：

| 端 | 配置 / 做法 | 原因 |
|---|---|---|
| 生产者 | `acks=all`；`retries` 足够大；`enable.idempotence=true`；用带回调的发送并处理失败 | `acks=1` 时 leader 挂了，没复制出去的消息就丢 |
| Broker | `replication.factor=3`；`min.insync.replicas=2`；`unclean.leader.election.enable=false` | 保证至少两个副本有数据；不允许落后太多的副本当 leader |
| 消费者 | `enable.auto.commit=false`，处理完再手动提交 offset | 先提交后处理，处理失败消息就丢了 |

- **结果**：这些加起来得到「至少一次」（at-least-once），不丢但可能重复，所以消费端要幂等（Q6）。
- **代价**：`acks=all` + `min.insync.replicas=2` 时，两个副本不可用的话生产者写失败，选的是一致性而不是可用性。
- **RabbitMQ 的对应做法**：生产端发布确认（publisher confirms）；队列声明为持久化（durable），消息 `delivery_mode=2`；消费端手动 ack（`autoAck=false`）；高可用用仲裁队列（quorum queue，基于 Raft）而不是旧的镜像队列。
- **追问 · 生产者发送失败本地怎么办？** 先落本地表或 outbox 再异步发送，见 [[tiktok-idempotency-transactions]]；不要在业务事务里同步等待发送再决定是否回滚。

## Q6. 怎么避免重复消费？Kafka 的「恰好一次」是什么？

- **默认语义是至少一次**：消费者处理完但没来得及提交 offset 就崩溃或重平衡，下次会重复收到。
- **消费端幂等（通用做法）**：消息带全局唯一 ID（业务主键或生成的 messageId）；处理时在同一个本地事务里写「去重表」（唯一键 messageId）和业务数据，重复消息撞唯一键直接忽略；或业务本身是状态机的条件更新（`UPDATE ... WHERE status = 'PENDING'`）。
- **Kafka 的 EOS**（exactly-once semantics）：幂等生产者（producer ID + 序列号，防止同一分区重复写）加事务（`transactional.id`，原子地写多个分区并提交消费 offset），下游消费者设 `isolation.level=read_committed`。它只保证「读 Kafka → 处理 → 写 Kafka」整条链在 Kafka 内部恰好一次（Kafka Streams 用的就是这个）。
- **做不到什么**：写外部数据库、发 HTTP 请求这类副作用不在事务里，所以仍然需要幂等。
- **追问 · 为什么不能「恰好一次」？** 网络两端的确认丢失无法区分「没收到」和「收到但回复丢了」，所以分布式系统实际是「至少一次 + 幂等 = 效果上恰好一次」。

## Q7. 消费者组重平衡（rebalance）是什么？为什么会卡？怎么避免？

- **触发条件**：消费者加入或离开（包括崩溃、发布重启）；心跳超时（`session.timeout.ms`，3.0 起默认 45 秒，`heartbeat.interval.ms` 默认 3 秒）；两次 `poll` 间隔超过 `max.poll.interval.ms`（默认 5 分钟）；订阅的 topic 分区数变化。
- **为什么卡**：经典的「急切」（eager）协议下，所有消费者先撤销全部分区，等组协调器（group coordinator）重新分配后才恢复，整个组暂停消费（stop-the-world），组越大越久。
- **常见陷阱**：消费一批消息处理太慢，超过 `max.poll.interval.ms`，被判定死亡，触发重平衡，分区被别人接走，旧消费者提交 offset 失败，消息被重复处理，又处理太慢——恶性循环。
- **解决**：
  1. 缩短每批处理时间：减小 `max.poll.records`，或把耗时处理交给线程池后再提交；
  2. 合理增大 `max.poll.interval.ms`；
  3. **协作式粘性分配**（`CooperativeStickyAssignor`）：只迁移需要移动的分区，其余继续消费；
  4. **静态成员**（`group.instance.id`）：消费者重启时在 `session.timeout.ms` 内回来就保留原来的分区，滚动发布不触发重平衡；
  5. Kafka 4.0 的新消费者协议（KIP-848）把分配逻辑放到服务端，增量式，不再有全组暂停。
- **追问 · 重平衡后为什么会重复消费？** 已处理但未提交的消息，新的所有者从上次提交的 offset 开始读。所以要在 `ConsumerRebalanceListener.onPartitionsRevoked` 里提交已处理的 offset，并做幂等。

## Q8. 副本、ISR、高水位（HW）是什么？

- **ISR**（in-sync replicas）：与 leader 保持同步的副本集合（包含 leader）。follower 超过 `replica.lag.time.max.ms`（默认 30 秒）没有追上就被踢出。只有 ISR 里的副本能被选为新 leader（在 `unclean.leader.election.enable=false` 时）。
- **高水位**（high watermark）：ISR 里所有副本都已复制的最大 offset。消费者只能读到 HW 之前的消息，所以未充分复制的数据不会被读到再丢失。
- **leader epoch**：每次换 leader 加一，follower 用它截断自己多余的日志，避免旧版本的 HW 导致日志分叉。
- **`acks=all`** 的真实含义是「写入当前 ISR 中的所有副本」，不是所有副本；ISR 缩到只剩 leader 时就退化成 `acks=1`，所以必须配 `min.insync.replicas=2`。
- **追问 · 为什么不用多数派（Raft）？** Kafka 的 ISR 方案容忍 f 个副本故障只需要 f+1 个副本，多数派需要 2f+1；代价是 ISR 的判断依赖时间，而 KRaft 控制器本身用的是 Raft。

## Q9. 消息积压了怎么办？

1. **先判断**：看消费组的延迟（lag）是在涨还是稳定；是生产突增，还是消费变慢（下游慢、消费者崩溃重平衡、毒消息卡住）。
2. **止血**：
   - 消费者实例数 < 分区数：直接扩容实例（最多到分区数）；
   - 实例数已等于分区数：写一个临时消费者，快速把消息转发到一个分区数 10 倍的临时 topic（只转发不处理，几乎不耗时），再起 10 倍的消费者去消费临时 topic；
   - 紧急时对低价值消息直接丢弃或降级处理（日志、统计类）。
3. **提速**：批量处理，批量写库；异步化慢的下游调用；去掉不必要的同步远程调用；开多线程（注意顺序约束）。
4. **根因和预防**：对 lag 设告警（绝对值与增长速度）；容量规划预留生产峰值 2–3 倍的消费能力；毒消息走死信（Q10）。
- **算例**：积压 6000 万条，消费能力 5000/s，生产 3000/s，净消化 2000/s，要 60,000,000 ÷ 2000 = 30,000 秒 ≈ 8.3 小时；消费扩到 4 倍（2 万/s），净消化 1.7 万/s，约 3530 秒 ≈ 59 分钟。
- **追问 · 积压期间消息过期怎么办？** Kafka 保留时间之前未消费的数据会被删除，积压时间超过保留期就丢；要有 lag 告警，必要时临时延长 `retention.ms`。

## Q10. 死信队列（DLQ）和重试怎么设计？

- **问题**：毒消息（poison message，格式错误或触发 bug）一直失败会无限重试，卡死分区。
- **做法（Kafka 没有原生 DLQ，由应用实现）**：
  1. 本地先重试少数几次（2–3 次，短间隔）；
  2. 仍失败发到重试 topic，分级延迟（例如 `retry-1m`、`retry-10m`、`retry-1h`），到时间再消费；
  3. 超过最大次数发到死信 topic，主流程继续，不阻塞后面的消息。
- **死信消息要带**：原 topic / 分区 / offset、失败原因（异常栈）、重试次数、原始 key 和 headers。
- **死信不是垃圾桶**：要有告警（数量超阈值立即通知），要有回放工具（修复 bug 后把死信送回原 topic），要有保留期。
- **RabbitMQ**：死信交换机（DLX）。消息被拒绝且不重新入队、TTL 过期、队列满溢出时，自动路由到 DLX 对应的队列；用 TTL + DLX 也能做延迟队列。
- **追问 · 需要保持顺序时怎么重试？** 失败的那条会堵住同 key 的后续消息。选择：阻塞重试（保序但延迟大）；或把该 key 标记为「失败中」，后续同 key 消息先存起来，等第一条成功后再处理。

## Q11. 延迟消息怎么实现？

- **Kafka**：没有原生支持。常见做法：按延迟档位建多个 topic（1s、10s、1min……），一个转发服务读出消息、检查是否到期，到期则写回目标 topic；或把延迟任务存在 Redis ZSet（score 是到期时间）/ 数据库，由调度器扫描投递。
- **RabbitMQ**：TTL + 死信交换机，或延迟消息插件；TTL 方案有「队头阻塞」，TTL 长的消息会挡住后面 TTL 短的。
- **RocketMQ**：4.x 有 18 个固定延迟级别，5.x 支持任意时间的定时消息（用时间轮实现）。
- **时间轮**（timing wheel）：用一个环形数组，每格代表一个时间刻度，任务挂在到期的格子上，指针每过一格执行那一格的任务；插入和删除 O(1)，适合海量定时任务，Kafka 内部的延迟操作（比如 `acks` 超时）也用它。
- **追问 · 订单超时 30 分钟取消，用什么？** 数据量不大：数据库定时扫描加索引；量大：延迟消息或 Redis ZSet；不管哪种，到期处理必须**再次检查订单当前状态**（用户可能已经支付），并幂等。

## Q12. Kafka、RabbitMQ、RocketMQ 怎么选？

| | Kafka | RabbitMQ | RocketMQ |
|---|---|---|---|
| 吞吐 | 极高，百万条/s 级（集群） | 中，万到十万条/s | 高，十万级 |
| 模型 | 分区日志，消费者拉取，可重放 | 交换机 + 队列，推送，消费即删 | 类似 Kafka，另有 tag 过滤 |
| 路由 | 弱（只有 topic + key） | 强（direct / topic / fanout / headers） | 中（tag、SQL 过滤） |
| 顺序 | 分区内 | 单队列单消费者 | 队列内（顺序消息） |
| 事务消息 | 仅 Kafka 内部 EOS | 无 | 半消息 + 回查，原生支持 |
| 延迟消息 | 无原生 | 插件或 TTL+DLX | 有 |
| 适合 | 日志、埋点、流处理、大数据管道、事件溯源 | 业务异步、复杂路由、低延迟小规模 | 电商交易、金融类可靠消息 |

- **选型说法**：先看吞吐和是否要重放消费历史（选 Kafka）；再看有没有复杂路由或延迟、事务消息的刚需（RabbitMQ / RocketMQ）；最后看团队运维能力。
- **追问 · Kafka 能当数据库吗？** 带 compaction 的 topic 可以做变更日志的源（event sourcing），但查询能力弱，通常只做事件源，不做主存储。
