# MySQL 八股：索引、事务隔离、锁、慢查询、深分页

MySQL（默认存储引擎 InnoDB）是后端面试里被问得最深的一块。面试官的路线通常是：索引为什么用 B+ 树 → 联合索引怎么用 → 事务隔离级别和 MVCC → 间隙锁和死锁 → 一条慢 SQL 你怎么查、怎么改 → 深分页怎么办。答每个问题都按 **机制 → 为什么 → 数字或取舍 → 追问** 的顺序，数字要能当场算出来。缓存与数据库的一致性在 [[tiktok-cache-problems]]，分库分表后的分布式事务在 [[tiktok-idempotency-transactions]]。

## Q1. 为什么 MySQL 索引用 B+ 树，不用哈希、红黑树或 B 树？

- **机制**：InnoDB 以 16KB 的页（page）为单位读写磁盘。B+ 树的非叶子节点只存键和子页指针，叶子节点存数据且用双向链表连起来。
- **为什么**：磁盘一次 IO 读一页，树要尽量矮；非叶子节点不存数据，一页能放更多键，扇出（fan-out）大。哈希只支持等值，没有范围和排序；红黑树是二叉的，千万行要 20+ 层，每层一次 IO；B 树的非叶子节点也存数据，扇出更小，且范围扫描要中序遍历来回跳，B+ 树只要顺着叶子链表走。
- **数字（要能现场算）**：假设主键是 bigint，键 8 字节加指针 6 字节约 14 字节，一页非叶子节点约 16KB ÷ 14B ≈ 1170 个指针。叶子页按每行 1KB 算存 16 行。两层非叶子 + 叶子的三层树：1170 × 1170 × 16 ≈ 2190 万行。所以「单表两千万行左右树会变到四层」是经验值，不是硬上限。
- **追问 · 查一行要几次 IO？** 三层树最多 3 次，根节点和上层几乎总在缓冲池（buffer pool）里，实际常常只有 1 次叶子页的磁盘读取。
- **追问 · 什么时候哈希更好？** 纯等值查找、内存表；InnoDB 有自适应哈希索引（adaptive hash index），自动为热点页建哈希，不用手动管。

## Q2. 聚簇索引、二级索引、回表、覆盖索引、索引下推分别是什么？

- **聚簇索引**（clustered index）：主键索引的叶子节点就是整行数据。没有主键时选第一个非空唯一索引，再没有就用隐藏的 6 字节行 ID。
- **二级索引**（secondary index）：叶子存「索引列 + 主键值」。用它查完整行要再拿主键去聚簇索引查一次，这叫**回表**（lookup）。
- **覆盖索引**（covering index）：查询需要的列都在二级索引里，不用回表，`EXPLAIN` 的 Extra 显示 `Using index`。例：`SELECT user_id, status FROM orders WHERE user_id = ?`，建 `(user_id, status)`。
- **索引下推**（index condition pushdown, ICP，5.6+）：联合索引里无法用来定位的列，也先在存储引擎层用索引里的值过滤，再回表，减少无效回表。Extra 显示 `Using index condition`。
- **为什么主键建议自增**：随机主键（UUID）插入到页中间，引起页分裂（page split）和碎片，空间利用率降到约一半；自增主键总是追加到最右边。主键也别太长，因为每个二级索引叶子都要存一份主键。
- **追问 · 自增主键的坏处？** 分库分表后不能直接用；高并发插入时最右叶子成为热点；对外暴露会泄露业务量。分布式场景用雪花算法（snowflake）这类趋势递增 ID。

## Q3. 联合索引的最左前缀是什么？哪些写法会让索引失效？

- **最左前缀**：索引 `(a, b, c)` 按 a、再 b、再 c 排序。能用到索引的查询：`a=`、`a= and b=`、`a= and b= and c=`、`a=` 加 `b` 范围。只写 `b=` 或 `c=` 则不能定位（5.x 之后有时能做 index skip scan，不要依赖）。
- **范围查询之后的列不能再用来定位**：`a=1 and b>5 and c=3`，c 只能靠 ICP 过滤。
- **建索引的列顺序**：等值条件的列在前、范围条件的列在后；区分度高的在前（但要服从最左前缀的查询形态）；常用于排序的列放最后以免 filesort。
- **常见失效**：
  - 对索引列用函数或运算：`WHERE DATE(create_time) = ...`、`WHERE id + 1 = 5`。改成范围：`create_time >= ? AND create_time < ?`。
  - 隐式类型转换：字符串列 `phone` 用数字 `WHERE phone = 13800000000`，MySQL 把列转成数字，索引失效。反过来（数字列用字符串）不影响。
  - 左模糊 `LIKE '%abc'`；右模糊 `LIKE 'abc%'` 可以用索引。
  - `OR` 的两边有一边没索引；`!=`、`NOT IN` 常常放弃索引；优化器认为全表更便宜时（命中行数占比很高）也会放弃。
  - 字符集不一致的表 join，列被转码。
- **追问 · 索引越多越好吗？** 不是。每个索引占空间，每次写都要维护，写入慢，优化器选择也更难；一般一张表的索引控制在个位数，并定期用 `sys.schema_unused_indexes` 清理没用的。
- **追问 · 区分度低的列（性别）能建索引吗？** 单独建意义不大；放进联合索引的后面做覆盖或过滤是可以的。

## Q4. EXPLAIN 的输出要看哪几列？

| 列 | 好 → 坏 / 含义 |
|---|---|
| `type` | `const` / `eq_ref` > `ref` > `range` > `index`（全索引扫描） > `ALL`（全表扫描）；至少要到 `range` |
| `key` | 实际用的索引；`NULL` 表示没用索引 |
| `rows` | 预估扫描行数，越小越好 |
| `filtered` | 过滤后剩余的百分比 |
| `Extra` | `Using index`（覆盖索引，好）；`Using index condition`（ICP）；`Using filesort`（额外排序，要关注）；`Using temporary`（临时表，要关注）；`Using where` |

- **追问 · 怎么消除 filesort？** 让排序列和过滤列组成的联合索引顺序一致：`WHERE user_id = ? ORDER BY created_at` 建 `(user_id, created_at)`，索引本身就是有序的。
- **追问 · EXPLAIN 的 rows 不准？** 来自统计信息，可以 `ANALYZE TABLE` 更新；MySQL 8.0.18+ 有 `EXPLAIN ANALYZE`，执行并返回真实的行数和耗时。

## Q5. 事务的四个隔离级别分别解决什么？InnoDB 默认是哪个？

| 级别 | 脏读 | 不可重复读 | 幻读 |
|---|---|---|---|
| 读未提交（RU） | 可能 | 可能 | 可能 |
| 读已提交（RC） | 否 | 可能 | 可能 |
| 可重复读（RR）**默认** | 否 | 否 | 快照读下否，当前读靠 next-key 锁 |
| 串行化（Serializable） | 否 | 否 | 否 |

- **三个异常**：脏读（读到别人未提交的数据）；不可重复读（同一事务里两次读同一行，值变了）；幻读（同一事务里两次范围查询，行数变了）。
- **InnoDB 默认 RR**：快照读（普通 `SELECT`）读的是事务第一次查询时的快照，靠 MVCC；当前读（`SELECT ... FOR UPDATE`、`UPDATE`、`DELETE`）读最新数据，靠 next-key 锁防止别人往范围里插入。
- **为什么很多互联网公司用 RC**：RC 没有间隙锁，锁的范围小，死锁和锁等待更少；代价是同一个事务内多次读可能不一致，需要业务容忍；用 RC 时 binlog 格式要用 `ROW`。
- **追问 · RR 下完全没有幻读吗？** 不完全。事务里先快照读，再 `UPDATE` 另一个事务刚插入并提交的行（当前读会看到它），之后再快照读就能看到这行，这是 RR 里仍可能出现的幻读。需要保证时用当前读加锁。

## Q6. MVCC 是怎么实现的？

- **机制**：每行有隐藏列 `DB_TRX_ID`（最近修改它的事务 ID）和 `DB_ROLL_PTR`（指向 undo log 里的上一个版本），形成版本链。事务读的时候用一个 **ReadView** 判断版本链上哪个版本可见。
- **ReadView 包含**：`m_ids`（创建时活跃的未提交事务 ID 列表）、`min_trx_id`（最小活跃事务 ID）、`max_trx_id`（下一个要分配的 ID）、`creator_trx_id`（自己）。
- **可见性判断**，对版本上的 `trx_id`：
  1. 等于自己 → 可见；
  2. 小于 `min_trx_id` → 创建视图前已提交 → 可见；
  3. 大于等于 `max_trx_id` → 视图创建后才开始 → 不可见；
  4. 介于两者之间：在 `m_ids` 里（未提交）→ 不可见，不在（已提交）→ 可见；
  不可见就沿 `DB_ROLL_PTR` 找上一个版本，重复判断。
- **RC 与 RR 的区别只在 ReadView 何时生成**：RC 每条语句生成新的；RR 在事务第一次快照读时生成一次，之后复用。
- **为什么**：读不加锁，读写互不阻塞，这是 InnoDB 并发高的原因。
- **代价**：长事务会让旧版本不能被清理（purge），undo 空间膨胀，版本链变长，查询变慢；监控 `information_schema.innodb_trx` 里运行时间长的事务。
- **追问 · MVCC 能解决写写冲突吗？** 不能，写操作是当前读，要加行锁。

## Q7. 间隙锁、next-key 锁是什么？死锁怎么排查？

- **三种行锁**：记录锁（record lock，锁一行索引记录）；间隙锁（gap lock，锁两条记录之间的空隙，防止别人插入）；next-key 锁（记录锁 + 它前面的间隙，区间左开右闭）。间隙锁只在 RR 下生效。
- **规则（常考版本）**：
  - 唯一索引等值查询命中：只加记录锁；
  - 唯一索引等值查询没命中：锁住它所在的间隙；
  - 非唯一索引等值查询：命中的记录加 next-key 锁，再向右多加一个间隙锁到下一个不同值；
  - 范围查询：扫描过的每条记录都加 next-key 锁。
  - **没有索引的条件会锁全表所有记录和间隙**，所以 `UPDATE ... WHERE` 一定要走索引。
- **为什么要有间隙锁**：防止当前读期间有别人往范围里插入，也就是防幻读，保证 `SELECT ... FOR UPDATE` 两次结果一致。
- **死锁例子**：事务 A 和 B 先后对同一个间隙加间隙锁（间隙锁之间不互斥），然后各自往里插入，插入意向锁（insert intention lock）被对方的间隙锁挡住，互相等待。
- **排查**：`SHOW ENGINE INNODB STATUS` 看最近一次死锁（`LATEST DETECTED DEADLOCK`）；8.0 用 `performance_schema.data_locks` 和 `data_lock_waits`。InnoDB 默认开死锁检测（`innodb_deadlock_detect`），发现环就回滚代价小的事务；锁等待超时 `innodb_lock_wait_timeout` 默认 50 秒。
- **预防**：所有事务按相同顺序加锁；事务尽量短，不在事务里调用远程服务；批量更新分小批；用 RC；条件走索引缩小锁范围；应用层对死锁错误（1213）重试。
- **追问 · 秒杀扣库存会有什么锁问题？** 同一行热点更新会排队，吞吐上限约几千 TPS（取决于事务长短）；对策是 Redis 预扣、分桶库存（把一行拆成 N 行）、把更新语句放在事务最后一步缩短持锁时间。

## Q8. redo log、undo log、binlog 各是什么？两阶段提交为什么存在？

| 日志 | 层 | 内容 | 用途 |
|---|---|---|---|
| redo log | InnoDB | 物理页修改（循环写） | 崩溃恢复（crash-safe），实现持久性 D |
| undo log | InnoDB | 修改前的旧值 | 事务回滚、MVCC 旧版本 |
| binlog | Server 层 | 逻辑变更（ROW 格式记录行变化，追加写） | 主从复制、恢复到某个时间点（PITR） |

- **WAL**（write-ahead logging）：先写日志再慢慢刷脏页，顺序写日志比随机写数据页快得多。
- **两阶段提交**：更新数据 → redo log 写 prepare → 写 binlog → redo log 写 commit。目的是让 redo 与 binlog 一致：只有 binlog 存在且 redo 是 prepare 时，恢复阶段认为事务已提交；binlog 没写成则回滚。不一致会导致主从数据不同或恢复后丢数据。
- **不丢数据的配置**：`innodb_flush_log_at_trx_commit = 1`（每次提交刷 redo）和 `sync_binlog = 1`（每次提交刷 binlog）；吞吐有压力时可以用 2 或 N，承担机器掉电丢约 1 秒的风险。有组提交（group commit）把多个事务的刷盘合并。
- **追问 · 为什么有了 binlog 还要 redo？** binlog 是逻辑日志，没有「哪些页已经落盘」的信息，不能用来做崩溃恢复；redo 是物理的、循环覆盖，不能做历史恢复。两者分工不同。

## Q9. 线上一条 SQL 变慢，你怎么排查和优化？

按这个顺序讲：
1. **先定位**：慢查询日志（`slow_query_log`，`long_query_time` 设 0.5–1 秒），用 `pt-query-digest` 或 `performance_schema.events_statements_summary_by_digest` 汇总最耗时的 SQL 模板；看是单条一直慢，还是突然全部变慢（锁、磁盘、主从延迟、连接池）。
2. **看执行计划**：`EXPLAIN`，是否全表扫描、`rows` 是否很大、有没有 `Using filesort` / `Using temporary`。
3. **典型原因与处理**：

| 原因 | 处理 |
|---|---|
| 没有合适的索引 / 索引失效 | 建联合索引、改写条件（Q3） |
| 回表太多 | 覆盖索引 |
| 深分页 | 游标式分页（Q10） |
| 返回列太多 `SELECT *` | 只取需要的列 |
| 大事务 / 锁等待 | 拆小事务，查 `innodb_trx` |
| 统计信息过期，优化器选错索引 | `ANALYZE TABLE`，或 `FORCE INDEX` 临时顶住 |
| 单表太大 | 归档历史数据、分区、分库分表 |
| 连接数 / 磁盘 IO 瓶颈 | 看 `SHOW PROCESSLIST`、iostat |

4. **验证**：改完对比 `EXPLAIN` 前后的 `rows`、实际耗时；建索引用 Online DDL，大表用 gh-ost（Q13）。
5. **长期**：加慢查询告警；上线前对新 SQL 做 EXPLAIN 评审。
- **追问 · 突然所有查询都慢？** 先看是否有长事务或元数据锁（DDL 阻塞，`Waiting for table metadata lock`）堵住后面所有查询；其次看磁盘 IO、缓冲池命中率、主从延迟。

## Q10. 深分页（`LIMIT 1000000, 20`）为什么慢？怎么优化？

- **机制**：`LIMIT offset, n` 要先读出前 `offset + n` 行再丢掉前 `offset` 行。二级索引上排序，每一行都要回表取数据，扫了一百万次回表，只为丢掉。
- **方案一：游标式分页（keyset pagination / seek method）**，记住上一页最后一条的位置：

```sql
SELECT id, title FROM post
WHERE id < :last_id
ORDER BY id DESC
LIMIT 20;
```

  走索引直接定位，复杂度与页码无关。排序列不唯一时用元组比较：`WHERE (created_at, id) < (:t, :id) ORDER BY created_at DESC, id DESC`，索引建 `(created_at, id)`。缺点：不能跳到任意页，只能上一页下一页；这对信息流本来就合适。
- **方案二：延迟关联**（deferred join），先在覆盖索引上找出 id，再回表：

```sql
SELECT p.* FROM post p
JOIN (SELECT id FROM post ORDER BY created_at DESC LIMIT 1000000, 20) t
ON p.id = t.id;
```

  子查询只扫索引不回表，只对最后 20 行回表。仍然是 O(offset)，只是常数小很多。
- **方案三：产品约束**：限制最大页数（如只能翻前 100 页），搜索场景用 Elasticsearch 的 `search_after`。
- **追问 · 要跳页怎么办？** 先限制最大页码；必须跳页时用方案二，或者预先把「每 N 条的边界 id」缓存起来。

## Q11. 什么时候分库分表？怎么做？

- **先做的事**：加索引与优化 SQL → 读写分离 → 加缓存 → 归档冷数据，这些做完仍不够再拆，因为分表带来跨分片查询、分布式事务、运维成本。
- **何时拆**：单表过大使索引树变高且维护（改表、备份）困难（经验值数千万行到亿级）；单机写入 QPS 或磁盘容量到头。
- **怎么拆**：垂直拆分（按业务拆库，大字段拆表）；水平拆分（同一张表按分片键拆到多个库表）。
- **分片键选择**：选查询最常带的列，让绝大多数查询落在一个分片上；订单表按 `user_id` 分，商家要查订单就需要另建一份按 `merchant_id` 分的副本（异步同步）。避免热点：别用时间做分片键（所有新数据压在最后一个分片）。
- **分片算法**：取模（简单，扩容要迁移）；一致性哈希；预分 2^n 个逻辑分片（如 1024）映射到较少的物理库，扩容时只搬整个逻辑分片。
- **全局 ID**：雪花算法（41 位时间戳 + 10 位机器 + 12 位序列，每毫秒每机器 4096 个）；注意时钟回拨。
- **跨分片问题**：join 在应用层做或冗余字段；分页和排序用各分片取 Top-N 再归并；事务见 [[tiktok-idempotency-transactions]]。
- **在线迁移步骤**：存量全量拷贝 → 增量同步（binlog / CDC）→ 双写校验 → 灰度切读 → 切写 → 回滚预案保留一段时间。

## Q12. 主从延迟怎么产生？怎么处理？

- **机制**：主库提交事务写 binlog → 从库 I/O 线程拉取写入 relay log → SQL 线程回放。
- **延迟原因**：从库回放慢（早期单线程回放，5.7 起按组提交并行，8.0 用 WRITESET 并行度更高）；主库的大事务（一个事务更新百万行，从库要重放同样久）；从库硬件弱或有慢查询在占资源；网络。
- **处理**：拆大事务；开并行复制；从库配置不低于主库；监控 `Seconds_Behind_Source` 并告警。
- **业务层的「写后读」问题**：用户刚写完马上读，读到从库的旧数据。对策：关键读路由到主库；写后一小段时间内同一用户都读主库（会话级标记）；带位点读（等从库追到某个 GTID 再读）。
- **半同步复制**（semi-sync）：主库提交前等至少一个从库确认收到 binlog，主库宕机不丢已提交事务；代价是写延迟增加一个网络往返。
- **追问 · 主库宕机怎么切？** 选 GTID 最新的从库升主，其他从库改指向它；用 MHA、Orchestrator 或云厂商的高可用；异步复制可能丢最后几个事务，金融场景用半同步或 MGR（Group Replication）。

## Q13. `count(*)` 为什么慢？大表怎么加字段？

- **count**：InnoDB 因为 MVCC，不同事务看到的行数不同，所以不存总行数，只能扫描。`count(*)` 与 `count(1)` 性能一样，优化器选最小的二级索引扫；`count(列)` 要判断是否为 NULL，更慢。大表精确计数很贵：用 Redis 计数器、汇总表，或 `EXPLAIN` 的估算值。
- **大表加字段**：8.0.12+ `ALTER TABLE ... ADD COLUMN ..., ALGORITHM=INSTANT` 只改元数据，秒级；其他变更用 Online DDL（`INPLACE`，期间允许读写但会占 IO 和产生延迟）；超大表或要灰度控制用 gh-ost / pt-online-schema-change：建影子表，复制数据，追增量，原子改名。
- **风险**：DDL 需要拿元数据锁（MDL），前面有长事务时它排队，后面所有查询又排在它后面，造成整表不可访问；上线 DDL 前先查长事务，并设 `lock_wait_timeout` 让它失败而不是堵住。
