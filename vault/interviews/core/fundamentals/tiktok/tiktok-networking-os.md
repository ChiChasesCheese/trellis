# 网络与操作系统八股：TCP、TLS、DNS、打开 URL、虚拟内存（low priority）

网络和操作系统题测的是你对「一个请求从浏览器到服务器再回来」每一环的理解。面试官喜欢从一个开放问题（在浏览器里输入 URL 回车，发生了什么）开始，让你选一环往下讲，再追问细节：三次握手为什么是三次、TIME_WAIT 太多怎么办、TLS 握手几步、DNS 缓存在哪里、进程和线程的区别、虚拟内存是什么。每题按 **机制 → 为什么 → 数字或取舍 → 追问** 作答，先讲清楚主线，再根据追问加深。线上排查的命令在 [[tiktok-linux-troubleshooting]]，语言运行时在 [[tiktok-runtime-concurrency]]。

## Q1. TCP 为什么是三次握手、四次挥手？

- **三次握手**：
  1. 客户端发 `SYN, seq=x`；
  2. 服务端回 `SYN+ACK, seq=y, ack=x+1`；
  3. 客户端发 `ACK, ack=y+1`。
- **为什么是三次**：目的是双方互相确认**自己能发、对方能收**，并同步各自的初始序列号（ISN）。两次不够：服务端无法确认客户端收到了自己的序列号。更重要的是，防止**历史的重复 SYN**（网络里滞留的旧请求）让服务端误建连接：第三次握手客户端会对旧连接回 RST 拒绝。
- **四次挥手**：TCP 是全双工，每个方向要单独关闭。主动方发 `FIN`；被动方回 `ACK`（此时被动方可能还有数据要发）；被动方发完后发自己的 `FIN`；主动方回 `ACK`。被动方的 ACK 和 FIN 之间有间隔所以通常是四次；没数据要发时可以合并成三次。
- **半连接队列和全连接队列**：服务端收到 SYN 后连接放入半连接队列（SYN queue），三次握手完成后进入全连接队列（accept queue），应用 `accept()` 取走。大小受 `min(backlog, net.core.somaxconn)` 限制，满了新连接被丢弃，客户端看到连接超时。
- **SYN 洪泛攻击**：大量伪造 SYN 占满半连接队列。对策：SYN cookies（`net.ipv4.tcp_syncookies=1`，队列满时不占内存，把信息编码进序列号）、缩短重试次数、前端限流。
- **追问 · 初始序列号为什么随机？** 防止旧连接的包被新连接误认，也增加伪造连接的难度。

## Q2. TIME_WAIT 是什么？太多了怎么办？

- **机制**：主动关闭连接的一方，发出最后一个 ACK 后进入 TIME_WAIT，等待 **2×MSL**（最大报文生存时间）后才真正关闭。Linux 里这个值固定为 60 秒。
- **为什么要等**：
  1. 最后一个 ACK 可能丢了，对方会重发 FIN，这时本端还得在场回 ACK，否则对方一直重发然后超时；
  2. 让网络中残留的、属于旧连接的延迟报文自然过期，不会被相同四元组的新连接收到。
- **问题**：短连接场景（频繁调用下游的 HTTP 客户端）主动关闭方会积累大量 TIME_WAIT。每个占一个四元组；Linux 客户端默认临时端口范围 `32768–60999` 共 28,232 个，对同一个目标 IP:端口，每 60 秒最多约 470 个新连接（28232 ÷ 60），超出后报 `Cannot assign requested address`。
- **对策（按优先级）**：
  1. **复用连接**：HTTP keep-alive、连接池，根本上不产生这么多短连接；
  2. 开启 `net.ipv4.tcp_tw_reuse=1`（仅对**出站**连接，依赖 TCP 时间戳）；
  3. 扩大临时端口范围 `net.ipv4.ip_local_port_range`；增加目标 IP 或端口数；
  4. 让**客户端**而不是服务端主动关闭（服务端上积累 TIME_WAIT 吃的是内存，不是端口）。
- **不要做**：不要用 `tcp_tw_recycle`（在 NAT 下会丢包，Linux 4.12 已删除）；不要把 `SO_LINGER` 设成超时 0 强行发 RST，会丢失未发送的数据。
- **追问 · 服务器上 TIME_WAIT 很多正常吗？** 看是谁主动关。HTTP/1.0 或设置了 `Connection: close` 时服务端主动关，所以服务端有大量 TIME_WAIT；一般几万个对内存影响很小，不用急着调。

## Q3. CLOSE_WAIT 大量堆积是什么原因？

- **机制**：被动关闭方收到对端的 FIN 后进入 CLOSE_WAIT，等应用调用 `close()` 才会发出自己的 FIN。
- **原因**：几乎都是**应用程序 bug**：没有关闭连接（异常分支漏了 `close`，连接泄漏），或线程卡住没有处理到关闭。内核不会替你超时清理。
- **排查**：`ss -ant state close-wait` 看数量和对端；`lsof -p <pid>` 或 `ss -p` 找到进程；看代码里资源是否用 try-with-resources / defer 关闭；看线程栈有没有卡住。
- **后果**：文件描述符耗尽，报 `Too many open files`（见 [[tiktok-linux-troubleshooting]]）。
- **对照记忆**：TIME_WAIT 是「正常现象，调参缓解」，CLOSE_WAIT 是「必须改代码」。

## Q4. TCP 是怎么保证可靠传输和控制拥塞的？

- **可靠**：序列号 + 确认应答（ACK）；超时重传（RTO 根据测得的往返时间动态计算）；快速重传（收到 3 个重复 ACK 就立即重传，不等超时）；校验和；乱序重组；去重。
- **流量控制**：滑动窗口（sliding window）。接收方在 ACK 中通告接收窗口（rwnd），发送方未确认的数据不超过它，防止压垮接收方；窗口为 0 时发送方定期探测。
- **拥塞控制**：发送方维护拥塞窗口（cwnd），实际发送量 = min(cwnd, rwnd)。
  1. **慢启动**（slow start）：cwnd 从很小开始，每个 RTT 翻倍；
  2. 到达阈值 ssthresh 后进入**拥塞避免**：每个 RTT 加一个 MSS，线性增长；
  3. 丢包：超时则 cwnd 回到 1 重新慢启动；3 个重复 ACK 则折半进入**快速恢复**。
  - Linux 默认算法是 CUBIC（基于丢包）；BBR 基于带宽和 RTT 的估计，在高延迟、有随机丢包的链路（跨洋）上吞吐更好。
- **为什么跨洋慢**：RTT 大，慢启动每一轮翻倍要等一个 RTT，小文件传输大部分时间在爬升阶段；初始窗口 `initcwnd` 默认 10 个 MSS（约 14KB）。
- **追问 · 怎么降低首包延迟？** 就近接入（CDN、边缘节点）、复用连接、TLS 1.3 / 会话恢复、QUIC 0-RTT。

## Q5. Nagle 算法和延迟确认有什么坑？

- **Nagle**：有未确认的小包时，后续小数据先攒着，凑满一个 MSS 或收到 ACK 再发，减少小包数量。
- **延迟确认**（delayed ACK）：接收方收到数据后等一小段时间（Linux 最多约 40ms）看能否捎带回复数据，再发 ACK。
- **叠加问题**：写—写—读模式（先发两个小包，第二个包要等第一个包的 ACK 才能发，而对方在延迟确认）就会稳定地多出约 40ms 延迟。
- **做法**：低延迟的 RPC、交互式场景对 socket 设 `TCP_NODELAY` 关掉 Nagle；应用层合并成一次 `write`。多数 RPC 框架默认已开启。

## Q6. TCP 和 UDP 有什么区别？QUIC 是什么？

| | TCP | UDP |
|---|---|---|
| 连接 | 面向连接，三次握手 | 无连接 |
| 可靠 | 重传、有序、拥塞控制 | 不保证，由应用处理 |
| 开销 | 头部 20 字节起，状态多 | 头部 8 字节 |
| 适合 | HTTP、数据库、文件 | DNS、音视频、游戏、QUIC |

- **TCP 的队头阻塞**（head-of-line blocking）：一个包丢了，后面已到达的数据也要等它重传才能交给应用。HTTP/2 在一个 TCP 连接上复用多个流，一个丢包会卡住所有流。
- **QUIC**（HTTP/3 的传输层）：基于 UDP，在用户态实现可靠传输。关键点：每个流独立，一个流丢包不影响其他流；握手把传输和 TLS 1.3 合并，首次连接 1 个 RTT，恢复连接可以 0-RTT；用连接 ID 标识连接，手机从 Wi-Fi 切到蜂窝时连接不断（连接迁移）。
- **取舍**：QUIC 在用户态实现，CPU 开销更大；部分网络会限制 UDP；中间设备无法优化。

## Q7. HTTP/1.1、HTTP/2、HTTP/3 有什么区别？

| 版本 | 要点 | 解决了什么 | 剩下的问题 |
|---|---|---|---|
| 1.1 | 持久连接（keep-alive）、管道化 | 每次请求都新建 TCP 的开销 | 同一连接上请求串行，应用层队头阻塞；浏览器开 6 个连接 |
| 2 | 二进制分帧、多路复用、头部压缩（HPACK）、服务端推送 | 一个连接并发多个请求 | TCP 层队头阻塞 |
| 3 | QUIC 之上 | 去掉传输层队头阻塞，握手更快 | UDP 被限制、CPU 开销 |

- **追问 · HTTP 常用状态码？** 200 成功；301 永久、302 临时重定向；304 缓存仍有效；400 请求错误；401 未认证；403 无权限；404 不存在；429 限流；500 服务内部错误；502 网关收到上游无效响应；503 服务不可用；504 网关等上游超时。502 和 504 的区别：上游返回了坏响应 vs 上游没在时间内响应。
- **追问 · GET 与 POST 的区别？** 语义上 GET 幂等、安全，参数在 URL，可缓存；POST 提交数据、不幂等。技术上两者都是 TCP 上的 HTTP，大小限制来自服务器和浏览器配置，不是协议规定。

## Q8. TLS 握手是怎么进行的？

- **目的**：认证服务器身份、协商对称密钥、加密传输。非对称加密慢，只用来建立密钥；数据用对称加密（AES-GCM 或 ChaCha20-Poly1305）。
- **TLS 1.3 握手（1 个 RTT）**：
  1. 客户端 `ClientHello`：支持的版本和密码套件，并**直接带上自己的密钥交换公钥**（ECDHE 的 key share）；
  2. 服务端 `ServerHello`：选定的套件和自己的 key share；双方此时已能算出共享密钥，后面的消息都加密；服务端发**证书**、`CertificateVerify`（用私钥签名握手内容）、`Finished`；
  3. 客户端验证证书和签名，发 `Finished`，开始发送应用数据。
- **TLS 1.2** 需要 2 个 RTT（密钥交换和 Finished 要多一轮），且可用 RSA 密钥交换（没有前向保密）。
- **前向保密**（forward secrecy）：用临时的 ECDHE 密钥对，每次连接的密钥不同、用后即弃；即使服务器私钥以后泄露，也无法解密过去录下来的流量。
- **证书校验**：客户端检查证书链（服务器证书 → 中间 CA → 根 CA，根在系统信任库里）、每一级签名、有效期、域名与证书的 SAN 是否匹配、是否被吊销（OCSP 或 CRL）。
- **会话恢复**：会话票据（session ticket / PSK）让重连省去证书和密钥交换；TLS 1.3 的 0-RTT 可以在第一个包里带数据，但可能被**重放**（replay），只能用于幂等请求。
- **双向 TLS**（mTLS）：服务端也要求客户端出示证书，用于服务间认证。
- **追问 · 中间人攻击怎么防？** 证书由受信任的 CA 签发并绑定域名，攻击者没有合法证书和私钥；HSTS 强制 HTTPS 防降级；证书固定（certificate pinning）用于 App。
- **追问 · HTTPS 为什么还是慢？** 多一次握手往返、证书验证、加解密 CPU；用 TLS 1.3、会话恢复、OCSP stapling、HTTP/2 复用缓解。

## Q9. DNS 解析的过程是什么？

- **查找顺序**：浏览器缓存 → 操作系统缓存和 `/etc/hosts` → 本地**递归解析器**（运营商或 8.8.8.8 之类）→ 如果解析器没缓存，从根服务器开始：根服务器告诉你 `.com` 的 TLD 服务器地址 → TLD 服务器告诉你 `example.com` 的权威服务器 → 权威服务器返回 A 记录（IPv4）/ AAAA 记录（IPv6）。结果按 **TTL** 缓存在沿途各层。
- **记录类型**：A / AAAA（域名到 IP）、CNAME（别名）、NS（域名对应的权威服务器）、MX（邮件）、TXT。
- **传输**：默认 UDP 53，响应太大或区域传送时用 TCP；加密的有 DoT（TLS 853）和 DoH（HTTPS）。
- **CDN 和就近解析**：域名 CNAME 到 CDN 厂商的域名，权威 DNS 根据解析器的位置（或 EDNS 客户端子网）返回最近节点的 IP。
- **常见问题**：
  - 切换 IP 后旧用户还在访问旧地址，因为 TTL 内缓存还在；切换前提前把 TTL 调低；
  - Java 的 `InetAddress` 自带缓存（默认 30 秒，装了安全管理器时永久缓存），故障切换敏感的服务要显式设置 `networkaddress.cache.ttl`；
  - DNS 污染/劫持；解析器故障导致整个服务不可达。
- **追问 · 服务发现里的 DNS？** Kubernetes 内用集群内 DNS（CoreDNS），`service.namespace.svc.cluster.local`；Pod 里 `ndots:5` 会让外部域名多发几次无效查询，延迟敏感时写全域名（末尾加点）。

## Q10. 在浏览器输入 URL 回车，发生了什么？

先给 30 秒骨架，再根据面试官兴趣展开任意一环：

1. **解析 URL**，检查 HSTS 列表，决定用 HTTPS；先查浏览器缓存（强缓存 `Cache-Control` / `Expires` 命中则直接用，不发请求）。
2. **DNS 解析**（Q9）得到 IP。
3. **建立 TCP 连接**：三次握手（Q1）；HTTP/3 则是 QUIC 握手。
4. **TLS 握手**（Q8）。
5. **发送 HTTP 请求**：方法、路径、`Host`、Cookie、`Accept-Encoding` 等；可能先经过 CDN 或边缘节点，缓存命中就直接返回。
6. **服务端处理**：负载均衡（L4 / L7）→ 反向代理（Nginx）→ 应用服务 → 缓存 / 数据库 → 生成响应（状态码、头、正文）。
7. **浏览器接收响应**：协商缓存（`ETag` / `Last-Modified`，304）；解压；解析 HTML 构建 DOM，解析 CSS 构建 CSSOM，合成渲染树（render tree），布局（layout）、绘制（paint）、合成（composite）；遇到 JS、图片、CSS 等子资源再发请求，HTTP/2 下并发复用同一连接；JS 可能阻塞解析（`defer` / `async` 缓解）。
8. **连接复用或关闭**：keep-alive 保持连接供后续请求。

- **追问 · 重点往哪里展开？** 后端岗位把时间花在 5–6：负载均衡怎么选后端、网关做认证和限流、服务调用链、缓存与数据库、超时与重试（[[tiktok-service-protection]]）。每一层说出「可能出什么问题、怎么观测」。
- **追问 · L4 和 L7 负载均衡？** L4 按 IP + 端口转发（LVS、云 NLB），性能高、不看内容；L7 解析 HTTP，可按路径、头路由、做 TLS 终止和重试（Nginx、Envoy、云 ALB），更灵活、开销更大。

## Q11. I/O 多路复用和 epoll 是怎么回事？

- **背景**：一个线程处理一个连接，连接数上万时线程太多。I/O 多路复用（I/O multiplexing）让一个线程同时监听很多个文件描述符，哪个就绪处理哪个。
- **三代接口**：
  - `select`：fd 数量限制 1024，每次调用把整个 fd 集合在用户态和内核之间拷贝，并线性扫描 O(n)；
  - `poll`：没有数量限制，仍然是线性扫描；
  - `epoll`：内核用红黑树管理注册的 fd，用就绪链表存已就绪事件；`epoll_wait` 只返回就绪的 fd，复杂度 O(就绪数)，不随总连接数增长。
- **水平触发（LT）与边缘触发（ET）**：LT 只要还有数据可读就一直通知，编程简单；ET 只在状态变化时通知一次，必须一次读完直到 `EAGAIN`，减少系统调用，但要配合非阻塞 IO。
- **应用**：Nginx、Redis、Netty 都是 Reactor 模式 + epoll。Redis 因此能用单线程处理数万个连接。
- **五种 IO 模型**：阻塞、非阻塞、多路复用、信号驱动、异步 IO（Linux 的 io_uring）。
- **零拷贝**：`sendfile` 让数据直接从内核页缓存到网卡，省去用户态拷贝（Kafka、Nginx 静态文件），见 [[tiktok-message-queues]]。
- **追问 · 为什么 epoll 对文件不适用？** 普通文件总是「可读」，epoll 没意义；磁盘异步 IO 用 io_uring 或线程池。

## Q12. 虚拟内存是什么？进程、线程、协程怎么比较？

- **虚拟内存**：每个进程看到一整块连续的私有地址空间（64 位下实际可用 48 位，128TB），CPU 的 MMU 通过**页表**（page table）把虚拟页映射到物理页帧（页大小通常 4KB）。TLB 是缓存最近的页表项的硬件，命中则一次翻译很快，未命中要走多级页表。
- **缺页中断**（page fault）：访问的页不在物理内存中。次缺页（minor）：页在内存里只是还没映射，或首次分配，微秒级；主缺页（major）：要从磁盘（swap 或文件）读，毫秒级，会让延迟剧增。
- **带来的好处**：进程隔离（一个进程无法访问另一个的内存）；按需分配（`malloc` 只是划地址范围，真正触碰时才分配物理页）；写时复制（`fork` 后父子共享页，写入才复制，Redis 的 `bgsave` 依赖它）；文件映射 `mmap`；可用内存超过物理内存（换页）。
- **OOM Killer**：物理内存和 swap 都耗尽时，内核按 `oom_score` 杀掉占用大的进程。容器里超过 cgroup 内存限制同理，表现为进程被 `SIGKILL`（退出码 137）。
- **进程、线程、协程**：

| | 进程 | 线程 | 协程 |
|---|---|---|---|
| 地址空间 | 独立 | 同进程共享 | 同线程共享 |
| 切换开销 | 大（切页表、TLB 刷新） | 中（几微秒） | 小（用户态，几百纳秒） |
| 调度者 | 内核 | 内核 | 用户态运行时 |
| 通信 | IPC（管道、socket、共享内存） | 共享内存 + 锁 | channel、共享变量 |
| 崩溃影响 | 只死自己 | 整个进程 | 整个线程/进程 |

- **上下文切换**：保存和恢复寄存器、程序计数器、栈指针；进程切换还要换页表，使 TLB 失效，CPU 缓存变冷，这才是隐性的大头。线程过多时切换开销显著，用 `vmstat` 看 `cs` 一列。
- **追问 · 栈和堆的区别？** 栈由编译器管理，函数调用的局部变量，后进先出，大小有限（线程栈默认 8MB）；堆由程序员/运行时管理，大小灵活，会有碎片和 GC/释放问题。
- **追问 · 内存泄漏和内存溢出？** 泄漏是分配了不再使用但没有释放，持续增长；溢出（OOM）是申请不到内存。泄漏最终导致溢出。
