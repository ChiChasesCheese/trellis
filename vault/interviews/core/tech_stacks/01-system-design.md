# 01 · 系统设计（System Design）

> 知识层（想更深时去哪）：[[System Design MOC|system-design]]：[[storage.object]] · [[storage.encoding]] · [[distributed.partitioning.schemes]] · [[async.queues]] · [[async.log]] · [[analytics.warehouse]] · [[analytics.derived]] · [[reliability.slo]] · [[infra.delivery]] <!-- domain-links -->
> 适用于：系统设计轮；被问"讲讲你做过的系统"、"你会怎么设计 X"；以及任何需要在白板上画框和箭头的场合。
> 不适用于：超大规模 C 端系统的具体数量级（十亿日活、全球多活）——见第 5 节。

## 0. 这个栈在 JD 里到底在问什么

系统设计轮的评分点几乎从不是"你知不知道 Kafka"。面试官在找三样东西：

**一、你会不会先问约束再动手。** 上来就画框的人，和先问"多少量、什么延迟要求、能丢数据吗、钱相关吗"的人，第一分钟就分出来了。设计的质量取决于约束抓得准不准，而约束永远要问出来。

**二、你的边界画在哪，为什么。** 组件选型是次要的（大多数选择都能工作），切分才是主要的。一个把边界画错的设计，用最好的组件也会持续付代价。

**三、你能不能说清它怎么坏。** 只会讲 happy path 的设计不算设计。真实系统的价值有一大半体现在失败的那一刻：降级成什么样、数据会不会脏、多久能发现、怎么恢复。

## 1. 来龙去脉

系统设计不是一套模式的集合，它是一项**在约束下做取舍并为取舍负责**的活动。这一节讲这项活动本身。

### 1.1 为什么会有"系统设计"这件事

单机程序里不需要系统设计。函数调用不会失败一半、内存里的数据不会和自己不一致、进程要么活着要么死了。你只需要关心逻辑对不对。

一旦程序跨越了机器，三件事同时失效：

- **调用可能部分成功。** 请求发出去了，回应没回来。你不知道对方做没做。重试可能重复，不重试可能丢失。
- **时间不再是全序。** 两台机器的时钟不一样，"谁先发生"变成了一个需要专门机制才能回答的问题。
- **故障是常态而非例外。** 一台机器一年挂一次，一千台机器一天挂三次。设计必须假设故障正在发生，而不是可能发生。

**系统设计就是在这三件事成立的前提下，仍然让业务正确。** 所有的模式——重试、幂等、共识、对账——都是这三个问题的具体应对，而不是可以独立记忆的招式。

### 1.2 约束先行：设计从问题开始，不从组件开始

给定一个需求，动手之前要问清的约束大致是四类：

**量级。** 每秒多少请求、数据总量多大、读写比例。这决定了能不能单机、要不要分片、缓存值不值得。量级差一个数量级，正确的设计往往完全不同——所以"大概多少"这种答案不够，要逼出一个数。

**延迟。** 用户等得起多久，以及"必须同步完成"和"可以异步补上"的分界在哪。这条决定了哪些步骤在关键路径上。**把不必同步的事挪出关键路径，是系统设计里回报最高的单一动作。**

**正确性的等级。** 这是最容易被跳过、也最要命的一条。丢一条日志没关系，丢一笔钱是事故。能接受最终一致，还是必须读到自己刚写的？有没有一个必须能封口结账的时间点？**钱相关的系统和内容相关的系统，正确性的定义根本不是一回事。**

**演化方向。** 三个月后最可能加什么。不是为了现在就做，而是为了避免把那条路堵死。

约束问清之后，很多"设计选择"会自己塌缩成唯一解。反过来，**没问约束就开始选组件，是系统设计轮最常见的死法**。

### 1.3 分解：边界画在哪

把一个系统切成几块，判据不是"功能不同"，而是这三条：

**一、变化频率不同的东西应该分开。** 一天改一次的定价规则和一年改一次的打款渠道放在一起，前者的每次发布都在冒后者出问题的风险。

**二、正确性要求不同的东西应该分开。** 记账必须严格，报表可以最终一致。混在一起，要么报表拖累记账的性能，要么记账迁就报表放松了约束。

**三、失效影响不同的东西应该分开。** 挂了导致停止收款的模块，和挂了只是看不到图表的模块，不该共享命运。**切分的一大目的就是让故障有地方停下来。**

反过来，**不该切的地方切了，代价比不切更大**：本来一个事务能保证的东西，跨了边界就需要幂等、重试、对账三件套来近似，而且永远只是近似。所以"微服务拆得越细越好"是错的——每一刀都要有上面三条之一作为理由。

### 1.4 接缝：边界的实质是契约加上失效隔离

两个模块之间的边界，实际上是两样东西：

**契约** —— 传什么、什么形状、谁负责校验、加字段时对方会不会崩。这就是 schema 演化问题（[[storage.encoding]]），它决定了两边能不能独立发布。**不能独立发布的两个服务，本质上还是一个服务，只是多了网络故障。**

**失效隔离** —— 对方挂了我怎么办。同步调用意味着对方的可用性直接乘进我的可用性；异步（队列、日志、文件）意味着对方挂了我还能继续攒，但代价是数据有延迟、要处理堆积、要考虑顺序。

同步还是异步，本质上是在问：**这一步的失败，是应该立刻让用户知道，还是应该由系统自己扛下来后面补上？**

### 1.5 失效模式：设计的质量在故障时才显形

一个设计讲完 happy path 只能算讲了一半。要问的是：

- 上游挂了，我降级成什么样？（拒绝服务？用缓存的旧值？攒着等它回来？）
- 我挂了重启，会不会重复处理？（这就是为什么幂等不是可选项——见 [[10-correctness-idempotency]]）
- 数据错了，多久能发现？（这是监控和对账的分工：监控发现"不动了"，对账发现"动错了"）
- 发现之后怎么修？（能不能重跑？重跑会不会二次伤害？）

**最后一条最常被忽略：可恢复性要设计，不会自己出现。** 一个只能人工改库修复的系统，和一个能安全重跑某天分区的系统，运维成本差一个数量级。

### 1.6 分片与热点：规模上去之后绕不开的一课

数据大到单机装不下时要分片，分片方式只有两大类（[[distributed.partitioning.schemes]]）：

- **哈希分片** —— 按 key 的哈希取模。分布均匀，但范围查询要扫所有分片。
- **范围分片** —— 按 key 的区间切。范围查询快，但容易热点（按时间分片时，今天的分片承担全部写入）。

真正的难点从来不是选哪种，是**倾斜**：现实世界的 key 分布从不均匀。一个大商户的交易量可能是普通商户的一万倍，哈希分片也救不了——它和别人共享一个分片，那个分片就是热的。应对办法（复合 key 打散、单独隔离大 key、二级分片）都有代价，这是要在设计时就承认的。

## 2. 在我们这套系统里它怎么用

这是一套真实的支付清结算系统，三个服务组成一条流水线。它足够复杂到能展示上面每一条原则，也足够具体到每个论断都有路径可查。

### 2.1 三个系统的定位

| 系统 | 一句话职责 | 技术栈 |
|---|---|---|
| `pricing` | **规则的权威来源**：每个商户账号该怎么收费——费率、计费模式、结算方式 | Kotlin + Spring Boot + gRPC，PostgreSQL |
| `snowglobe` | **记账与计算引擎**：把交易事件变成 `TRANSACTIONS`，算出 Braintree fee 和 pass-through fee，汇总成每日余额 | Java 17 + Gradle，业务逻辑绝大部分是 Snowflake SQL（存储过程/函数/任务/流） |
| `funding` | **打款系统**：消费算好的余额，叠加争议与储备金调整，生成打款指令，走 ACH/Wire 把钱打给商户 | Ruby on Rails + gRPC + Qless |

关系不是对等的三角，是一条流水线：**pricing 定规则 → snowglobe 按规则算账 → funding 按算好的账打钱**，外加 funding 把商户配置变更反向同步回去。

**为什么是这三块，而不是一个大服务或者三十个小服务？** 对照 1.3 的三条判据：

- **变化频率**：定价规则天天在改（新商户、新费率、新促销），打款渠道极少变（接一家银行是季度级的事），记账逻辑介于两者之间。三者的发布节奏差一个数量级。
- **正确性要求**：`funding` 是真的在动钱，错一笔就是真实损失；`snowglobe` 算错了还能重算（数据都在，是派生的）；`pricing` 存的是配置，错了影响未来而不是已发生的交易。**这三档正确性要求不同，值得不同的发布门槛和不同的测试密度。**
- **失效影响**：`pricing` 挂了，新商户开不了户，但已有交易照常计费（规则已落库）；`snowglobe` 挂了，账停止更新但钱还能按昨天的余额打；`funding` 挂了，钱打不出去。故障半径清晰可分。

### 2.2 三条接缝，以及为什么边界在那

**接缝一：pricing → snowglobe，gRPC + 落库（同步契约，异步生效）**

`pricing` 通过 gRPC 暴露 `CreatePricingSchedule` / `GetPricingSchedule`（`pricing/src/main/proto/pricing.proto`），`PricingSchedule` message 里带着所有影响下游计算的开关：`pricing_model`（FLAT / IC_PLUS / IC_PLUS_PLUS）、`interchange_plus`、`pass_through_amex_ic`、`net_settlement`、`billing_cadence`、`fee_refund_policy`、`transaction_funding_delay`。

**边界为什么在这**：这里传的是**规则**不是**结果**。snowglobe 拿到规则自己算，而不是让 pricing 算好了给它。这个方向的选择很关键——如果反过来（pricing 提供"这笔交易收多少钱"的接口），那么 snowglobe 每算一笔账都要同步调用 pricing，pricing 的可用性直接乘进记账链路，而且批量重算历史数据会把 pricing 打死。

现在的形状是：**规则同步传递一次，落到 snowglobe 自己的 `PRICING_SCHEDULES` 表，之后的计算全在本地完成**。pricing 挂了不影响存量交易计费。代价是规则变更的生效有延迟，以及两边的 schema 必须协同演化（1.4 的契约问题）。

**接缝二：Gateway → snowglobe，Kafka（异步，日志形态）**

交易事件从 Gateway 走 Kafka topic `events_entity_transaction_global`，经 Snowflake Kafka Connector（Snowpipe Streaming）落到 `EVENTSTREAM_TRANSACTION_STATUS_EVENTS`，再由 CDC 流 + task 推进到 `TRANSACTIONS` 表。

**为什么是日志而不是同步调用**（[[async.log]] vs [[async.queues]]）：交易发生的速率不由记账系统决定，而且记账慢一点没人会死。用日志隔开之后，snowglobe 的维护窗口、重启、慢查询都不会反压到收单链路。更重要的是**日志可重放**——记账逻辑出了 bug，可以从某个位点重新消费，这在队列语义（消费即删除）下做不到。

**接缝三：snowglobe → funding，S3 上的 CSV 文件（异步，文件形态）**

snowglobe 把 `JOURNAL_ENTRIES` 按 cutoff time 聚合成 `SNOWGLOBE_BALANCES`，再写成 `balances/{region}/{date}/*.csv.gz` 传到 S3；funding 侧用 `Snowglobe::S3Client#fetch_balances` 取回来，经 Qless 任务流水线算出 `disbursement_records`，最后走 ACH/Wire。

**这条接缝最值得讲**。在 2026 年用 CSV 文件做服务间集成，看起来像是技术债，但对照约束它其实是合理的：

- **业务本身就是按天封口的。** 打款是离散事件（每天/每周期一次），不是连续流。文件的边界天然对应"这一天的账"这个业务概念（1.2 里"必须能封口"那条约束）。
- **文件是最好的审计单元。** 这是财务数据，出了问题要能回答"当时到底发的是什么"。一个 S3 上不可变的 `.csv.gz` 就是答案本身。换成 gRPC 流，这个能力要额外建。
- **跨技术栈的最低公共契约。** 一边是 Java + Snowflake SQL，一边是 Ruby on Rails。CSV 两边都不需要额外的序列化框架和版本协商（[[storage.object]] 和 [[storage.encoding]] 的现实解）。
- **隔离彻底。** snowglobe 停一天，funding 用昨天的文件照常运行；funding 停一天，文件在 S3 上等着。

代价也很实在：延迟是小时级；schema 变更靠约定不靠类型系统；文件迟到或缺失要专门的监控去发现（而不是像 RPC 那样立刻报错）。**这是一个明确的取舍，不是将就** —— 面试里讲清楚"我们知道代价是什么，为什么仍然选它"，比讲一个时髦的架构更有说服力。

### 2.3 从明细到派生：一层一层收敛

值得单独说的是数据的分层形状（[[analytics.derived]] / [[analytics.warehouse]]）：

```
TRANSACTIONS（交易明细）
  + BRAINTREE_FEES（自己收的费）
  + PASS_THROUGH_FEES（卡组织/收单行透传的费，来自 Fiserv）
  + DISPUTES（争议，来自 Arbiter 的 Kafka 事件）
      ↓
JOURNAL_ENTRIES（视图，汇总所有账本表）
      ↓  按 cutoff time 聚合
SNOWGLOBE_BALANCES（每商户每周期净额）
      ↓  CSV → S3
funding → disbursement_records → 银行
```

**每一层都是下一层的唯一输入，而且明细永远保留。** 这带来一个很强的性质：任何一层算错了，改掉逻辑重算即可，不需要从上游重新取数。余额是派生的，不是权威的——权威是明细。

这正是 1.5 里"可恢复性要设计"的具体形态。代价是存储成本和重算时间，在这个场景下远低于一次算错账的代价。

## 3. stripe kit 考到的点

系统设计轮和 OA 考的不是一回事，但 OA 里那些"多 part 递进"的题，内核就是一个微缩的系统设计：先定状态形状，再让后面的 part 复用它。

- [[s19-incremental-design-parse-model-compute-render|S19 增量式设计：parse → model → compute → render]] —— 分层的最小形态。上面 2.3 那条"明细 → 派生"的链路，和它是同一个思想在不同尺度上的展开
- [[s03-small-record-modeling|S03 用小记录 + 按 id 索引的字典建模]] —— 对应"保留明细而不是只存聚合"
- [[s10-event-stream-reversal|S10 事件流 + 反向事件]] —— 对应争议/退款进入账本的方式
- [[s24-payments-domain-vocab|S24 支付领域词汇]] —— 这套系统的领域语言，术语表见 本机 `raw/background/03-glossary`

Stripe OA 的经典结构是"第 4 part 引入撤销事件，要求能反向修改前面的计数"。**如果第 2 part 只存了聚合，第 4 part 就得推倒重写** —— 这和 2.3 里"明细永远保留"是同一条教训，只是一个在 60 分钟里体现，一个在三年的系统演化里体现。

## 4. 常见追问与答法

| 追问 | 一句话答 | 展开的抓手 |
|---|---|---|
| 为什么切成三个服务 | 变化频率、正确性要求、失效影响三者都不同 | 2.1 的三条对照 |
| 为什么服务间用文件不用 RPC | 业务本身按天封口；文件是天然的审计单元；跨栈的最低契约 | 2.2 接缝三，四条理由 |
| pricing 挂了会怎样 | 新商户开不了户，存量交易照常计费——规则已落在 snowglobe 本地 | 2.2 接缝一"传规则不传结果" |
| 算错账怎么办 | 明细永远在，改逻辑重算即可；余额是派生的不是权威的 | 2.3 的分层 |
| 为什么用 Kafka 不用队列 | 需要可重放：记账逻辑有 bug 时能从位点重新消费 | 队列消费即删除，日志不删 |
| **（三层）文件迟到或缺失怎么发现** | **不像 RPC 会立刻报错，必须专门监控。这是选文件付出的代价之一** | 引到 [[reliability.slo]]：对这条链路该定什么 SLI——文件到达时间？余额更新延迟？ |
| **（三层）单个大商户把某个分片打热了怎么办** | **哈希分片救不了倾斜，要么复合 key 打散要么单独隔离** | 1.6，并承认在我们的量级上还没到必须处理的地步 |
| **（三层）如果让你重新设计，哪条边界会变** | **snowglobe → funding 那条。文件的审计价值我会保留，但会在旁边加一条事件通道做"余额已就绪"的信号，而不是让下游轮询 S3** | 这是把 2.2 接缝三的代价单独拆出来解决，而不是推翻整个选择 |

**超大规模 C 端系统我没做过。** 十亿日活、全球多活、边缘计算这类量级，我只有读来的知识。
→ 我会说："我做的是 B 端金融数据系统，规模的挑战在数据量和正确性，不在 QPS。全球多活的一致性方案我能讲原理，但没有实操经验。"
→ 接回去："不过我做的系统有一个 C 端系统通常没有的约束——每一笔都必须对得上账，不能用'最终一致'搪塞过去，这方面的取舍我很熟。"

**在线服务的容量规划和性能调优不是我的强项。** 我的性能问题是查询和管道层面的（[[09-sql-data-modeling]]），不是 JVM 调优、连接池、GC 停顿那一类。
→ 我会说："我优化过的是 Snowflake 查询的剪枝和 MERGE 的扫描范围，不是服务端的延迟分位。"

**微服务治理的那套（服务网格、熔断、限流）我是使用者不是建设者。**
→ 我会说："这些基础设施在 PayPal 是平台团队提供的，我按规范用，但没有自己搭过。"
