# 10 · 分布式正确性：幂等与对账（Idempotency & Reconciliation）

> 知识层（想更深时去哪）：[[System Design MOC|system-design]]：[[correctness.idempotency]] · [[correctness.ledger]] · [[correctness.outbox]] · [[async.delivery.exactly-once]] · [[distributed.transactions.isolation]]；[[Code Core MOC|code-core]]：[[model.idempotency]] · [[model.reversal]] · [[model.event-stream]] <!-- domain-links -->
> 适用于：JD 上出现"idempotency"、"exactly-once"、"reconciliation"、"ledger" 的岗；被问"怎么保证同一个请求不被重复处理"、"分布式系统怎么保证数据一致"、"讲一个你排查过的数据正确性事故"。

## 0. 这个栈在 JD 里到底在问什么

JD 上写"idempotency"或"exactly-once"，面试官心里问的通常是三件事之一：**(a) 你知不知道网络本质上是不可靠的**（考"为什么需要幂等"这个第一性原理，而不是背定义）；**(b) 给你一个具体场景，你会怎么设计幂等键**（考自然键 vs 代理键的取舍，考虑发时的窗口问题）；**(c) 出了数据不一致，你怎么发现、怎么定位、怎么修**（考对账/reconciliation 的实际操作经验，这是比"设计一个幂等接口"更少人能答好的部分，因为它要求真实事故经验而不是背书）。这篇文章第 2 节的核心案例——一个 NULL 值在字符串拼接里悄悄传播、造成 196 个商户漏收手续费近两周才被发现——直接对应 (c)，是这类问题里最有教学价值的一种失败模式:不是系统崩溃,而是系统"安静地算错了"。

## 1. 来龙去脉

### 1.1 没有它的时候，人们怎么做，痛在哪

设想一个最朴素的支付系统：客户端发起一笔转账请求，服务端处理完毕，返回成功。如果网络在"服务端处理完"和"客户端收到响应"之间断开，客户端只会看到一个超时——它不知道钱到底转成功了没有。这时候客户端最自然的反应是**重试**：再发一次同样的请求。

问题来了：如果第一次请求其实已经处理成功了（只是响应丢失），第二次重试会不会再转一次钱？这就是分布式系统里一个绕不开的基本事实——**网络不可靠意味着"发送方不知道对方是否收到"，而唯一安全的应对策略是"可以重发，但重发不能造成重复效果"**。这不是一个可以靠"网络更稳定一点"来规避的问题：即使把丢包率降到万分之一，一个日均十亿请求的系统每天仍然会遇到十万次这种不确定状态。

早期没有这套机制的系统，要么选择"用户体验优先"——超时就默认失败,允许用户手动重试,代价是极小概率的重复扣款/重复发货,依赖事后人工客服处理;要么选择"正确性优先"——网络出问题就整个流程挂起等人工介入,代价是可用性差。两者都不是真正的解法，只是把问题往后推。

### 1.2 核心抽象

**幂等（idempotency）**：一个操作执行一次和执行多次，产生的效果完全相同。这个概念本身来自数学（$f(f(x)) = f(x)$），被借用到分布式系统里变成一个工程契约："如果你不确定一个请求有没有成功，尽管重发，我保证不会因为重发而产生额外的副作用"。

落地方式是**幂等键（idempotency key）**：客户端在第一次发起请求时生成一个唯一标识（通常是一个 UUID），把它和请求一起发给服务端。服务端第一次看到这个 key 时正常处理并记住"这个 key 已经被处理过，结果是 X"；之后再看到同一个 key，直接返回记住的结果 X，不重新执行业务逻辑。这把"网络层面的重试"和"业务层面的重复执行"彻底解耦——**重试可以随便做，因为幂等键这一层会把重复请求拦在业务逻辑之前**。

一个绕不开的选型问题是**幂等键用什么**：**自然键**（业务数据本身天然具有唯一性的字段，比如一张发票号、一笔交易的 `reference_number`）还是**代理键**（客户端显式生成、跟业务数据本身无关的 UUID）。自然键的好处是不需要额外的协调机制——只要两条记录的自然键相同，就代表它们是同一笔业务；坏处是必须确保这个字段真的唯一（现实世界的"发票号"有时会因为系统合并、跨地区拼接等原因产生冲突）。代理键的好处是唯一性由生成方保证、不依赖业务语义；坏处是客户端必须记住自己生成的 key 才能正确重试——如果客户端自己在生成 key 之后崩溃重启，它可能会用一个新 key 重发本该重试的请求，这时候幂等机制形同虚设。

当"防止重复"不是唯一目标，而是"如果已经发生了，怎么撤销"时，核心抽象换成**反转/补偿（reversal / compensation）**：不去修改或删除已经生效的记录，而是追加一条效果相反的新记录，两条记录的和抵消了原始效果。这是分布式事务里"没有跨系统的原子回滚"这一现实约束下的替代方案——**你不能指望一个分布式事务在多个系统间原子性地全部成功或全部失败（两阶段提交代价高、可用性差），所以干脆假设它会部分失败，用"事后补一条反向记录"来达到等效的正确性**，代价是任何读这份数据的下游都必须理解"净值 = 原始记录 + 所有反转记录的和"，而不能只看最新一条记录。

**账本 / 双式记账（ledger / double-entry）** 是把"反转"这个思想制度化的更进一步：任何一笔资金变动都必须同时记录"从哪来"和"到哪去"两条分录，两条分录的金额相等、方向相反，账本的正确性可以通过"所有分录求和必须为零"这样一条不变量随时验证——这是把"正确性"从"相信每一步计算逻辑都没写错"转变成"用一条可独立验证的数学约束持续检查"，后者远比前者更可靠，因为它不依赖信任任何一段具体代码。

**对账（reconciliation）**是这一整套体系里容易被忽略但同样关键的"外层循环"：幂等键、账本不变量这些都是防止错误**在处理的那一刻**发生的"内层"机制，但没有任何内层机制是完美的（本文第 2 节的事故正是一个内层机制"安静地"失败,而没有触发任何报错的例子）。对账的做法是定期（而不是实时）拿两份本该一致的数据源做独立比对——比如"我方系统算出的总额"与"银行/第三方账单里的总额"——如果对不上,说明内层的某个环节漏检了什么。对账是"事后诸葛亮",但它的价值恰恰在于它**不信任**任何一段处理逻辑,只信任"两份独立来源的数字应该相等"这条朴素的事实。

### 1.3 关键权衡

**买到什么**：幂等键让"网络层面的重试"变得绝对安全,不再需要精确控制"请求到底发出去几次";反转/补偿避免了对分布式事务的依赖,用最终一致代替强一致;对账提供了一层不依赖任何单一处理逻辑的独立校验,能捕获前面所有机制都没设计到的错误模式。

**代价是什么**：
- 幂等键需要**存储和查找**——服务端要保存"哪些 key 已经处理过、结果是什么",这本身是一个需要考虑过期策略、并发写入冲突的子系统。如果幂等键的存储介质本身也可能失败(比如写入幂等记录的事务和写入业务数据的事务不是原子的),幂等机制自己也会出现"业务已经执行但幂等记录没写上"的窗口。
- 反转/补偿要求所有下游消费者都理解"这不是一条独立记录,而是要跟原始记录一起看"——如果某个报表/看板只 `SELECT` 最新记录而不做"原始值+所有反转的和",会得出错误结论。
- 对账的**滞后性**是它的本质代价:它发现问题的时间点永远晚于问题发生的时间点,差距可能是几小时到几天,期间错误的影响可能已经扩散(比如已经据此打款、已经生成了下游报表)。
- **它拒绝服务的场景**:如果两份数据源在"应该比对什么"这件事上本来就没有共识(比如字段定义不一致、计算口径不一致),对账会持续报出"假阳性差异",反而消耗排查资源;这时候需要先做本文第 2 节 2.2 提到的"字段级 parity 验证",而不是直接上生产对账。

### 1.4 演化到今天

早期系统里"幂等"往往是每个团队各自发明一套(用某个业务字段查重、用数据库唯一约束报错后吞掉异常),没有统一契约。今天的默认选择已经收敛成几个清晰的模式:HTTP API 层面的 `Idempotency-Key` header(Stripe 把这个做成了行业事实标准,后文第 3 节会提到);消息队列消费侧的"idempotent consumer"模式(消费者自己维护已处理消息 ID 的记录,而不依赖消息队列保证 exactly-once,因为大多数消息系统只能保证 at-least-once);数据库层面的 `MERGE ... WHEN NOT MATCHED`/`INSERT ... ON CONFLICT DO NOTHING` 这类原子的"存在则跳过"语义,把幂等判断下推到存储引擎而不是应用代码里手动"先查后写"(后者有 TOCTOU 竞态)。分布式事务这条路(两阶段提交、Saga)今天更多被视为"能不用就不用"的重型方案——默认选择是能用幂等+补偿解决的就不引入跨系统事务协调。

## 2. 在我们这套系统里它怎么用

### 2.1 架构位置

我在 Braintree Pricing & Settlement 团队维护 `snowglobe`——一个批处理式的记账与费用计算引擎(Java + Snowflake SQL,Flyway 迁移)。它的核心工作就是"正确地算钱":把 Gateway 的交易事件、Fiserv 的对账文件、Amex 的结算文件汇总成每个商户的应收/应付费用,最终生成打款依据。这个领域对幂等和正确性的要求是天然刚性的——**算错一次费用不是"体验差",是真金白银的多收或少收**。整套系统里几乎每一个写入操作都是幂等 `MERGE`,而不是普通 `INSERT`;对账不是可选的事后动作,而是每一次数据源迁移前必须做的验证步骤。

### 2.2 关键 feature 与设计决策

**(1) 幂等 MERGE，键是业务自然键：`CONCAT_WS('_', 'INTERCHANGE', SETTLE.INVOICE_NR)`**

**机制**：PR #1615 的核心 procedure `COPY_FISERV_CREDIT_INTERCHANGE_FROM_SETTLE_TO_PASS_THROUGH_FEES_STAGING` 里，`UNIQUE_IDENTIFIER` 是一个合成的自然键——`'INTERCHANGE_' + INVOICE_NR`（发票号），`MERGE ... ON EQUAL_NULL(STAGING.UNIQUE_IDENTIFIER, SOURCE.UNIQUE_IDENTIFIER) ... WHEN NOT MATCHED THEN INSERT`。这个 procedure 被一个每小时跑一次、`6:15-9:15 America/Chicago` 之间反复触发的 task 调用，任务本身没有"跑没跑过"的外部状态记录，全靠这条 `WHEN NOT MATCHED` 的幂等语义防止调度系统重放时重复计费。

**替代方案**：可以引入一个外部状态机记录"这个任务这一轮跑没跑过"，但那需要额外的状态存储和一致性保证（状态机本身的更新和业务写入如果不是原子的，又会引入新的竞态）。

**为什么选自然键**：`INVOICE_NR` 是 Fiserv 数据源自带的、天然唯一的业务标识，不需要额外协调机制生成——这是 1.2 节说的"自然键不需要额外协调"的具体例子。

**代价**：`ON` 子句还叠加了一个时间窗口 `STAGING.CREATED_AT > DATEADD(MONTH, -1, :LOOKUP_DATE)`，把 MERGE 匹配范围限制在近一个月，用来防止 Snowflake 在全表历史范围内扫描匹配、随着表增长导致 MERGE 性能单调下降。这是用性能换正确性覆盖面的一个**显式风险敞口**：如果同一笔记录因为上游延迟极端异常、时隔超过一个月才被重新处理到，窗口外的旧记录不会被匹配到，会产生重复插入——概率极低但存在，团队接受了这个权衡。

**(2) 复合键处理"同一实体的多个状态"：`REFERENCE_NUMBER + TRANSACTION_REJECTED_INDICATOR`**

**机制**：Amex GRRCN 流水线里 `PROCESS_AMEX_GRRCN_TRANSACTIONS()` 的幂等键不是单纯 `REFERENCE_NUMBER`，而是 `REFERENCE_NUMBER` 加上 `TRANSACTION_REJECTED_INDICATOR`（用 `EQUAL_NULL` 而不是 `=` 比较，因为这个指示位在正常记录里可能是 NULL，标准 `=` 对 NULL 永远返回 UNKNOWN 会导致误判为"未匹配"从而重复插入）。

**为什么这么设计**：同一笔交易可能先来一条正常记录、后来又来一条被拒绝（REJ）的修正记录——如果幂等键只用 `REFERENCE_NUMBER`，第二条会被误判为"重复"而丢弃,漏掉状态变化。把状态字段也纳入键，两种状态可以共存于表中，由下游校验逻辑决定采信哪一条（PR #1988"REJ flag fix"专门处理了下游过滤拒绝态记录的逻辑）。

**代价**：这套幂等只防止"同一行重复插入"，不防止"同一个业务实体因为状态变化而在表里产生多行并存"——这是有意为之（留给下游决定取舍），但如果下游校验逻辑本身有 bug，两条互斥状态的记录都可能被误读。

**(3) 上游就绪握手：把"数据可信"从文档约定变成 SQL JOIN 条件**

**机制**：`TRIGGER_STATUS_V1` 是一套配置驱动的质量检查框架（`QUALITY_CHECK_CONTRACT_CONFIG` 表定义"这个 subject area 要跑哪些检查"，`EXECUTE_QUALITY_CHECK` 动态调度执行）产出的完成度信号——当某个 subject area（比如"Settlement"）当天所有必需检查都拿到 `PASS`，`POPULATE_TRIGGER_STATUS` 才把状态置成 `COMPLETED`。下游消费方式极其直接：`JOIN CLX_TRIGGER_STATUS_V1 T1 ON ... WHERE T1.STATUS = 'Completed'`——如果上游没完成验证，这条 JOIN 天然一行都不返回，不需要额外的"轮询等待"逻辑。

**为什么这样设计**：这是把"数据能不能安全读"这件事,从依赖运维人员口头约定或文档写的 SLA,变成一个下游查询自己就能判断的、机器可验证的**前置条件**——正确性检查不再是"希望上游按时交付"，而是"下游查询本身就自带了不吃到脏数据的保证"。

**代价**：`EXECUTE IMMEDIATE` 动态拼 SQL 有注入风险（`SUBJECT_AREA`/`VALIDATION_NAME` 直接字符串拼接而非参数绑定），框架接受这个风险的前提是配置表是内部可信输入；`EXCEPTION WHEN OTHER` 把任何校验内部异常都吞成一条 FAIL 记录，好处是一个校验挂了不影响其他校验，坏处是排查根因要读 `SQLERRM` 文本而非结构化错误码。

**(4) 从"表级阻塞"到"商户级阻塞"：一个诚实的"设计完成、未获批准"的正确性权衡**

Quality-Check 框架最初的校验粒度是整张表——任何一个商户数据有问题，整个 subject area 都被标记未完成，下游所有商户的数据都不可读。Confluence ADR（pageId `2894288991`）指出这个问题的量级："~50 个有问题的商户，挡住了多达 35,000 个商户（4% 失败率）"。ADR 对比了四个方案，最终选择方案 D（复用已有的 `QUALITY_CHECK_RESULTS_V1` 表,用"汇总行 + 逐商户失败行"摊平存储,而不是引入 VARIANT 列或新表），理由是这个模式已经在 `TRANSFERS` 这一个 subject area 里生产验证了 16 个月。

ADR 里最值得复述的正确性论证是"strictest wins"：读取逻辑先检查 `NOT EXISTS(table_level_blocks)` 再检查 `NOT EXISTS(merchant_blocks)`，只要存在任何表级 FAIL，无论商户级结果如何,一律全部阻塞——这保证了"部分 procedure 已经改造成商户级、部分还没改造"这种混合状态下,系统仍然安全（更严格的约束总是赢）。

**必须诚实指出的现状**：ADR 提议的关键标志位 `HAS_MERCHANT_DETAIL` 在代码里**不存在**——ADR 自身元数据写着 `Status: Proposed`、`Date Approved: [pending]`。也就是说：**核心模式（用已有列摊平存储商户级失败）已经在 TRANSFERS 里生产验证了 16 个月，但把它推广成全框架通用规则的这一步，仍然停留在设计草案阶段，没有进入 `EXECUTE_QUALITY_CHECK` 的实际代码路径。** 这是"设计已经做了完整正确性论证（四方案对比、量级分析），但因为优先级/资源尚未排上，还停在 approval 阶段"的真实工程状态,面试时如果被问"这个项目最终结果如何"，诚实的答案就是这两句话，而不是含糊说"做完了"。

**(5) [me] 两阶段核验方法论：验证逻辑与生产逻辑同源**

这是我在 PR #1615（Settle View 迁移）里用的方法，本质上是"对账"在上线前的应用——见 2.3。

### 2.3 我做的部分 `[me]`

**Settle View 迁移的两阶段验证（PR #1615，Confluence pageId `2698298357` / `2747965111`）**：发现阶段用 `FULL OUTER JOIN + EQUAL_NULL` 逐字段比对新旧数据源归一化后的记录，字段级不一致率约 0.07%；切换前验证用**即将上线的生产查询本身**（只是把 `SELECT ...` 换成 `SELECT count(*)`）对当天全量做行数比对，差异率 0.224%。这两个数字衡量的是不同的事,来自不同的文档,不能混用。这个方法论的核心是"用会上生产的那段代码去验证，而不是另外写一套抽样脚本"——降低了"验证时一套口径、上线后另一套口径"的错配风险，这也是对账思想在"上线前"而不是"上线后"的一次应用。

**S3 事故：ACH fee-calc 生产事故的根因定位（Confluence pageId `3029344728`，Slack `#snowglobe` 2026-07-29）**——这是本文最值得展开的一段，见下方独立小节。

**S3-followup：把根因精确到具体代码行（Confluence pageId `3052036330`）**——事故复盘之后，同一个健康检查在 8/8、8/11 再次报警，我把根因进一步锁定到 `R__create-eventstream-to-pending-transactions-with-source-stored-procedure.sql` 里 `GET_EVENTSTREAM_PAYMENT_INSTRUMENT_SUB_KIND()` 函数的**重载覆盖**问题——共享的 `MERGE INTO pending_transactions` 语句用了这个函数的 1-参数重载（没有 `us_bank_account` 分支，返回 NULL），覆盖掉了本该按分支各自算好的、来自 2-参数重载的正确值。止血用 PR #3316（只在 `STANDARD_ACH` 分支强制选用 2-参数重载）；根治用 PR #3390（彻底移除两个重载并存、靠动态 `SUB_KIND_EXPR` 选择的设计，这正是移除"造成 bug 的可能性本身"而不是只堵住已知的触发路径）。

**没做过的部分**：ADR `2894288991` 提议的 `HAS_MERCHANT_DETAIL` 商户级阻塞机制本身没有落地到代码里——这是设计层面的贡献（ADR 是我写的），不是"上线并生效"的贡献,两者要分开讲。

### S3 事故深度还原：一个 NULL 值怎么安静地吃掉了 196 个商户的手续费

这是我认为整个证据集里教学价值最高的一个真实案例，值得完整还原一遍推理链条。

**触发**：`CHECK_TRANSACTION_HAS_BRAINTREE_FEES` 健康检查（每天 13:30 America/Chicago 跑一次，断言昨天创建的每一笔销售交易都有对应的 Braintree 手续费记录）触发 PagerDuty 告警。我在 5 分钟内给出 TL;DR 根因（Slack `#snowglobe`，2026-07-29 17:33:03 PDT）。

**背景机制**：标准 ACH（`us_bank_account`，`ACH_FASTER_FUND` 标志关闭的商户）交易不会直接写入 `TRANSACTIONS`，而是先进 `PENDING_TRANSACTIONS`（`source_type = 'STANDARD_ACH'`），等网关确认结算（约 T+3）后才被"提升"（promote）进 `TRANSACTIONS`。这个提升路径在 2026-07-15（PR #2941）第一次在生产环境产生数据。

**根因链条**（三层，逐层都不是孤立的 bug，是三个正确的设计决策叠加出的一个意外交集）：

1. 标准 ACH 的 pending 摄入procedure（`VALIDATE_STANDARD_ACH_AND_CONSOLIDATE`）用 `GET_EVENTSTREAM_PAYMENT_INSTRUMENT_SUB_KIND(payment_method, ...)` 派生 `payment_instrument_sub_kind`。这个函数**确实有** `us_bank_account` 分支，但它的判断依据是结算事件里 `payment_method` 这个 VARIANT 字段的结构——而标准 ACH 的结算事件恰好不带这个结构，导致所有分支都落空,函数返回 NULL。100% 的 483,542 行受影响。
2. 提升 procedure**忠实地**把这个 NULL 复制进 `TRANSACTIONS`——这一步本身没有任何逻辑错误，它只是准确地传递了上一步产生的值。
3. 费用计算根据 `LOWER(payment_instrument_sub_kind)` 拼出定价品类（`'us_bank_account' → BT_US_BANK_ACCT`，否则 `UPPER('BT_' || sub_kind)`）。当 `sub_kind` 是 NULL 时，`'BT_' || NULL` 在 SQL 里的结果是 **NULL**——这条拼接不会报错，不会抛异常，只是安安静静地产出一个匹配不到任何 `product_sub_category` 的空值，于是 `discount_rate` 和 `settled_transaction_fee` 两条定价查询都落空,**既不产生 discount 手续费,也不产生 settled_transaction 手续费,而且不报任何错误**。

**这正是这类事故最危险的地方**：它不是系统崩溃、不是异常抛出、不是性能下降——如果没有那个每天跑一次的健康检查，这个问题可以无限期地持续下去而没有任何信号。量化影响：`settled_transaction` 手续费漏记 99,723 笔，`discount` 手续费漏记 5,487 笔，影响约 196 个商户，受影响交易日均 GMV 约 $11.3M，累计到发现时已经持续了两周（2026-07-15 至 2026-07-29）。

**为什么现有的端到端测试没抓到**：这是我认为最值得引用的部分——设计文档给出了四条具体原因,而不是笼统一句"测试覆盖不够"：(a) 现有的 `AchTransactionE2ETest` 只断言路由结果（进 PENDING 还是 TRANSACTIONS），从不运行"提升"这一步之后的手续费生成；(b) 测试用例里"标准 ACH"事件的 fixture 实际塞的是一个 VISA/DISCOVER 的 `payment_method` payload，导致测试里 `GET_EVENTSTREAM_PAYMENT_INSTRUMENT_SUB_KIND` 永远返回一个非 NULL 的卡类 sub_kind——生产环境里那个真正是 NULL 的字段，在测试夹具里从来没有 NULL 过；(c) pending 行的断言检查了 public_id、金额、商户、币种、`source_type`，唯独没有断言 `payment_instrument_sub_kind`；(d) 没有任何测试贯穿"提升 → 手续费生成"这条完整路径,摄入测试不跑费用计算,费用计算测试用的 fixture 本来就带着合法的 sub_kind。四条原因合在一起说明:这不是"测试少",而是**测试恰好在两个独立测试的边界上都留了一个盲区,而这个边界正是 bug 实际发生的地方**。

**修复与加固**（"止血"和"根治"分两步，这个区分本身值得在面试里讲清楚）：止血（PR #3316）只在 `STANDARD_ACH` 分支强制走 2-参数重载，恢复正确的 sub_kind；根治（PR #3390）移除两个重载并存、靠运行时动态选择 `SUB_KIND_EXPR` 的设计本身——因为只要这种"同名函数多个重载、选哪个靠隐式类型推断"的设计还在，同类 bug 就有再次发生的结构性可能。加固清单里还包括一条我认为最值得学的原则："一个支付方式无法映射到定价品类时，现在的行为是安静地不产生任何手续费——应该改成大声失败（在 CI 里捕获或直接报错），而不是默默地什么都不做"。**这条原则本身，就是把"1.3 节讲的对账滞后性代价"往前挪一步的具体手法：与其依赖每天一次的健康检查事后发现，不如让这类无法处理的情况在处理的当下就失败并被看见。**

## 3. stripe kit 考到的点

Stripe OA 里幂等/去重几乎是必考点：[[s11-idempotency-dedup|S11 幂等 / 去重]] 直接考"题面出现 'a repeated X is ignored'、'duplicate ids' 这类描述对应真实世界的哪个概念"——考点是**去重要在处理之前还是之后判断**，以及"忽略、覆盖、报错"三种重复语义的区分，这跟本文 2.2 节 (2) 的复合键设计（同一实体的不同状态如何共存而不是被误判为重复）本质是一回事,只是把"状态变化"换成了"重复请求"。[[s17-ledger-balance-tracking|S17 台账式余额跟踪]]考的是"台账式"设计——不变量优先、在每个方法末尾维持它——直接对应本文 1.2 节讲的账本/双式记账的核心思想（用可独立验证的不变量代替信任每一步计算）。这个栈的知识在 OA 里的出现形态通常不是"设计一个幂等 API"，而是藏在状态机题目的约束里："同一个 id 的第二次操作应该是 no-op"这类描述,一旦读出来这是幂等语义,就知道该往哪个方向设计数据结构（用一个已处理 id 的集合/表，而不是每次重新判断业务逻辑是否该执行）。

## 4. 常见追问与答法

| 追问 | 一句话答 | 展开的抓手 |
|---|---|---|
| 为什么需要幂等，网络更可靠不行吗？ | 网络不可靠是无法消除的物理现实，而不是当前技术水平不够；哪怕丢包率降到万分之一，日均十亿请求的系统每天仍有十万次不确定状态。 | 1.1 节 |
| 幂等键用自然键还是代理键？ | 有天然唯一的业务字段就用自然键（不需要额外协调），没有就用客户端生成的 UUID（但要处理客户端自己崩溃重发的边界情况）。 | 1.2 节 |
| 幂等和分布式事务是一回事吗？ | 不是，幂等解决的是"同一个操作重复执行"，分布式事务解决的是"多个操作要么全成功要么全失败"；补偿/反转是绕开分布式事务的常见替代方案。 | 1.2 节 |
| 你们的幂等键怎么设计的？ | 用业务自带的自然键（比如发票号）拼上前缀做合成键，MERGE 的 `ON` 子句额外加时间窗口限制匹配范围以控制性能。 | 2.2 节 (1) |
| 讲一个你排查过的数据正确性事故 | ACH 费用计算事故——一个 NULL 值通过字符串拼接安静地传播，196 个商户两周内手续费漏收，日均 GMV $11.3M，最后靠一个每日健康检查发现。 | 2.3 节 + 独立小节 |
| **[第三层]** 如果你的幂等键存储本身也可能失败怎么办？ | 幂等记录的写入和业务数据的写入如果不在同一个原子操作里，会出现"业务执行了但幂等记录没写上"的窗口——我们的做法是把幂等判断下推到 `MERGE ... WHEN NOT MATCHED` 这种数据库原子语义里,而不是应用代码里"先查表、再判断、再写",后者有 TOCTOU 竞态。规模再大十倍,单纯靠这张表做全表扫描匹配会退化,这也是我们在窗口化 `ON` 子句里做的取舍——用一个月的时间窗口换取查询性能,同时承担一个极小概率的重复计费风险敞口。 | 2.2 节 (1) |
| **[第三层]** 为什么这个 NULL 传播的 bug 不会在写入阶段就报错？ | 因为 SQL 的字符串拼接对 NULL 是"安静地"返回 NULL，不抛异常——这是 SQL 语言本身的语义特性，任何依赖字符串拼接做业务判断的地方都有这个隐患。真正的加固不是"检查这一处"，而是把"无法处理的情况必须报错而不是沉默"变成一条通用原则，写进 CI 门槛里。 | 独立小节的"加固"部分 |

## 5. 我的边界

**边界在哪**：我没有实现过严格的分布式事务协议（两阶段提交、Paxos/Raft 级别的共识算法的具体实现细节）；我们系统里"跨多个数据库/服务的一致性"完全靠幂等 + 反转/补偿 + 事后对账这条路线解决，从来没有引入过跨系统的分布式锁或两阶段提交。

**我怎么说**：我会直接说"我们的架构选择本身就是刻意避开分布式事务的——批处理 + 幂等 MERGE + 事后对账,是因为这套组合在我们的场景（每天固定几个批次的结算窗口,不要求实时强一致）下比分布式事务简单得多、也更容易调试。如果你要考的是两阶段提交或者共识算法的实现细节,我答不上来协议层面的东西"。

**能把话接到哪去**：能接回的是——我们选择的这条路线本身就是"绝大多数需要强一致性直觉的场景，其实用幂等+补偿+对账就能解决,不需要真正的分布式事务"这一行业共识的具体实践，而且是在一个日均处理真实资金流动的系统里践行的，不是纸上谈兵。如果面试官追问"那如果你真的需要跨系统原子性怎么办"，我会诚实说这超出我的一手经验，但会从第一性原理推：Saga 模式（把一个跨系统事务拆成一串带补偿动作的本地事务）是我理解的、跟我们现在做法（反转记录）思路上最接近的答案，只是我们的场景里从来没有真正需要跨系统原子性到必须引入 Saga 编排框架的程度。
