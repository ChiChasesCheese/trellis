## Q
**网络爬虫（Web Crawler）**｜系统设计

设计一个网络爬虫：从一批种子 URL 出发，下载页面、提取文本（或图片链接）、发现新链接并继续爬取，对重复 URL 去重，规模要到企业级。标准版本给出的量级是全网约 100 亿页、平均每页 2 MB（含内嵌资源的最坏估算，仅 HTML 约 30 KB）、要求 5 天内爬完，用于给大模型提供训练文本。常见变体有：只提取图片 URL 并把"种子 URL 到可达图片列表"的映射返回，接口是提交作业、查询进度（已完成与进行中的种子数）、查询结果，种子不超过十来个但要沿链接爬多层；10000 台机器爬一个有 10 亿个 URL 的站点；爬 Wikipedia 这类大站时怎么扩展；监控航班价格变化并告警；种子如何自动获得（域名注册商、DNS 提示）；前沿队列（URL frontier）的数据模型和如何取下一批 URL。

给出完整解答：需求、核心实体与接口、整体设计、深入问题、取舍、不同级别的期望。

## A
**一句话。** 爬虫的瓶颈不是计算而是礼貌：每个站点每秒只能被轻轻碰一下，而全网有上亿个站点，所以设计的核心是"按主机组织的前沿队列"，让成千上万个站点并行、每个站点串行；再加上不丢进度的流水线、URL 与内容两层去重，以及防止陷入爬虫陷阱。

**60 分钟路线。**

| 时间 | 做什么 |
|---|---|
| 0–5 分 | 需求和数字：100 亿页 5 天约 2.3 万页每秒，瓶颈是礼貌和带宽而不是计算 |
| 5–10 分 | 实体和接口：URL 记录、主机记录；系统边界是「输入种子，输出文本」 |
| 10–25 分 | 画流水线：前沿（优先级加每主机队列）→ 下载器 → 对象存储 → 解析器 → 规范化去重 → 回到前沿 |
| 25–50 分 | 深入：robots.txt 与每主机限速、容错与重试、URL 与内容去重 |
| 50–60 分 | 追问：爬虫陷阱、DNS、作业型变体的进度计数、单站点上限 |

**需求。**
- 功能：
  1. 从种子 URL 开始，递归发现并下载页面。
  2. 提取页面文本（或图片 URL）并持久化，供后续处理。
  3. URL 去重，不重复爬取；遵守 robots.txt。
  4. 作业型变体：提交作业返回作业 ID，查询进度，查询每个种子的结果。
- 非功能：
  - 规模与速度：100 亿页 ÷ (5 天 × 86400 秒) ≈ 2.3 万页每秒。
  - 带宽：按每页 2 MB 的最坏估算约 370 Gbps；若只下载 HTML（约 30 KB）约 5.6 Gbps。一台 200 Gbps 网卡的机器按 30% 利用率约 3750 页每秒，所以下载机器需要 7 到 8 台以上，实际再翻几倍留余量。
  - 并发连接：2.3 万页每秒乘以平均 0.5 秒耗时，约 1.2 万个同时在途的请求，不算大，说明瓶颈在带宽、DNS 与礼貌，而不在连接数。
  - 存储：10B 页 × 30 KB HTML ≈ 300 TB 原始数据（压缩后可降一半以上），文本和元数据另算。
  - 容错：下载器随时会挂，不丢进度；礼貌：同一主机默认不超过每秒 1 次请求，遵守 Crawl-delay。

**核心实体与接口。**
- 实体：
  - URL 记录（UrlRecord）：url_hash（规范化 URL 的 64 位指纹，作主键）、url、主机、深度（从种子经过的链接跳数）、状态（NEW、QUEUED、FETCHED、FAILED）、下载时间、HTML 与文本在对象存储的位置、内容哈希、重试次数。
  - 主机记录（Host）：主机名、robots.txt 解析结果与拉取时间、Crawl-delay、下次允许访问时间。
  - 作业（Job，变体用）：job_id、种子列表、最大深度、每个种子的未完成计数、结果位置。
- 接口：系统本身不是面向用户的服务，边界是"输入种子，输出文本"。作业型变体有三个接口：`POST /jobs`（种子数组，返回 job_id）、`GET /jobs/{id}/status`（已完成与进行中的种子数）、`GET /jobs/{id}/results`（种子到图片 URL 列表的映射）。

1. 前沿（frontier）：URL 队列，分两层。前层按优先级（站点权重、深度、更新频率）分队列；后层每个主机一个队列，并有一个按"下次允许访问时间"排序的堆。取 URL 时先从堆里取出到点的主机，再从该主机队列取一条，访问后把该主机的下次时间推后 Crawl-delay（至少 1 秒）。这样天然做到每主机串行、全局并行。
2. 下载器：按主机名哈希把主机分配给固定的下载节点，该节点本地持有这些主机的队列、robots 缓存和礼貌计时，不需要全局锁。下载器带本地 DNS 缓存，请求设置超时与最大响应体积，先查 robots.txt 再请求，响应原样写入对象存储，往解析队列投一条只含 URL 指纹的消息。
3. 解析器：从对象存储读取 HTML，提取文本、链接、图片，文本写回对象存储，更新元数据库；新链接经规范化后去重，再回到前沿。
4. 元数据库：保存 URL 状态与位置，按 url_hash 分片的 KV 或宽列存储。消息队列里只放指纹，绝不放 HTML，队列不适合大载荷。
5. 重试与失败：下载失败按指数退避重试，5 次后判定站点不可达，进入死信队列；下载器在确认写入对象存储前不确认队列消息，崩溃后消息会重新可见，由别的节点接手。

**深入。**
1. 【必讲】礼貌与 robots.txt。
   - robots.txt：每个主机首次访问前拉取并解析，缓存一天左右；`Disallow` 的路径直接丢弃；`Crawl-delay` 不是标准但值得遵守，下载节点把它换算成主机的下次允许时间。
   - 限速的实现：简单做法是用 Redis `SET NX` 加与延迟相同的 TTL 作为主机锁，抢不到就把消息延后；更好的做法是按主机哈希固定归属，主机状态完全本地化，省掉一次网络往返和锁竞争。节点宕机时哈希环重新分配主机，礼貌计时从零开始，最多造成一次略快的访问，可接受。
   - 避免同步：多个节点在同一秒重试同一主机会形成共振，给等待时间加随机抖动。
2. 【必讲】容错：怎样不丢进度。
   - 把单体爬虫拆成流水线阶段（下载、解析），各阶段通过队列和对象存储衔接。解析逻辑要改（比如文本里加图片替代文字）时，只需对已存的 HTML 重跑解析，不必重新下载。
   - 重试机制的选择：进程内定时器重试，进程崩溃就丢，而且几秒后多半还会失败，不可取；Kafka 没有内建延迟重试，要自己建重试主题并在消息里存下次时间；带可见性超时的托管队列（SQS）可以根据接收次数动态调整可见性超时来做退避，超过最大接收次数自动进死信队列，实现最省事。
   - 每一步都是幂等的：对象存储的键是 URL 指纹，重复写入同一对象无副作用。
3. 【必讲】去重：URL 级与内容级。
   - URL 规范化先行：主机名小写、去掉片段（`#` 之后）、解析相对路径、排序查询参数、去掉追踪参数、统一默认端口，否则同一页面会因写法不同重复爬取。
   - URL 已见集合：100 亿个 8 字节指纹共 80 GB，按指纹哈希分片放进内存或 RocksDB 毫无压力。布隆过滤器（Bloom filter）在 1% 误判率下约 9.6 比特每元素，100 亿个约 12 GB，更省，但会误判"已见"，导致少量新页面被永远漏掉。通用爬虫可接受；作业型变体要求结果完整，用精确集合。
   - 判重必须是"检查并插入"的原子操作：把已见集合与前沿放在同一个分片（按主机归属），一次本地操作完成，不需要跨节点调用。
   - 内容去重：不同 URL 可能返回同一内容。精确重复用内容哈希索引；近似重复（只差广告、时间戳）用 SimHash，汉明距离小于阈值视为重复，跳过解析与存储。
4. 【追问再讲】爬虫陷阱。
   - 日历页面无限翻页、会话 ID 嵌入 URL、动态生成的无限层级链接。防线：最大深度（从种子算起的链接跳数，15 到 20）、URL 长度上限、单主机页数上限、查询参数个数上限，以及按路径模式的重复率检测。
5. 【追问再讲】规模：100 亿页 5 天。
   - 用上面的 2.3 万页每秒推出机器数，再说明为什么每主机每秒 1 次请求不妨碍总吞吐：同时爬数亿个不同主机，每个主机速率很低。
   - DNS 是常被忽略的瓶颈：研究显示早期爬虫线程有很大比例时间花在 DNS 解析上。做法是节点本地缓存、同一主机的所有 URL 复用解析结果，必要时自建递归解析器或用多个解析服务商轮询。
   - 解析器集群按队列深度弹性伸缩，不需要精确估算。
6. 【追问再讲】作业型变体：种子到图片的映射与进度。
   - 页面只爬一次：存 `页面 → {外链, 图片}` 的图，页面被多个种子可达时不重复下载。查询某个种子的结果时，在存好的图上从该种子做深度受限的广度优先遍历，收集可达页面的图片，天然保证"二级、三级页面的图片算作第一级页面的"。
   - 进度计数：每个种子一个"未完成 URL 数"。发现并入队时加一，页面处理完成时减一，减到零即该种子完成；顺序必须是先把新链接的计数加上再减去当前页面，否则会在中途误判完成。计数用 Redis 原子加减或数据库行更新。
   - 图片只存 URL，不下载，也不需要大容量对象存储，元数据库就够了。
7. **【加分】单站点十亿 URL：** 单站点超大（10 亿个 URL，10000 台机器）。
   - 瓶颈在目标站点允许的速率，而不在我们的机器数：每秒 1 次需要 31 年；每秒 1000 次需要 11.6 天；每秒 1 万次需要约 28 小时。再多机器也不能突破礼貌上限。
   - 做法：用站点提供的数据转储、站点地图（sitemap）或官方 API 代替爬取；确需爬取时与站点协商更高速率，并用响应延迟做自适应限速（延迟升高就降速）；同一站点的请求不要分散到多个节点，否则礼貌无法统一控制。

**取舍与追问。** 按被问到的可能性排，通常口述就够：
- 追问"动态渲染页面"：需要无头浏览器渲染，成本高一个数量级。单独设一个渲染池，只对判定为客户端渲染的站点启用。
- 追问"怎么持续更新而不是一次爬完"：增加调度器，按页面历史变化频率和重要性计算下次下载时间，用条件请求（`ETag`、`If-Modified-Since`）省带宽；新链接先写元数据库，由调度器决定何时入队，而不是解析器直接入队。
- 追问"优先级爬取"：多优先级队列或前沿前层，高优先级先出；Kafka 没有原生优先级，用多主题模拟。
- 追问"大文件"：先发 HEAD 请求看 `Content-Length`，超过阈值（例如 10 MB）直接跳过。
- 追问"如何监控"：每主机错误率、队列深度、每阶段耗时、DNS 失败率、被站点封禁（429/403）的比例。
- 追问"航班价格变化告警"：本质是定向爬取加变化检测，不需要全网前沿；每个数据源有自己的刷新间隔，页面内容抽出价格，与上次比较，变化才投递通知。更像任务调度器加解析器。
- 追问"怎么自动获得种子"：公开的域名区域文件、站点地图、已有索引里的高权重链接、搜索引擎的热门站点列表。

**级别期望。**
- 中级：前沿队列、下载器、解析器、对象存储、元数据库的数据流，能说出 robots.txt 和重试。
- 高级：流水线拆分与队列重试、每主机礼貌与限速、100 亿页的容量推算、URL 与内容两层去重、爬虫陷阱。
- 资深（staff）：至少深入三个方向并给出判断，例如按主机分区取代全局锁、DNS 瓶颈、布隆过滤器的取舍、单站点上限的理论分析、增量重爬调度与优先级。
