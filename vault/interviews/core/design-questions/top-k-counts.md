## Q
**Top-K 热门榜（视频播放、歌曲、话题标签）**｜系统设计

设计一个系统，持续接收海量的互动事件（播放、点击、收听、发帖），并能随时返回某个时间窗口内最热门的 K 个对象，例如"最近 1 小时 / 1 天 / 1 个月 / 全部时间播放最多的前 K 个视频"。规模参考：短视频平台每天约 700 亿次播放（约 70 万事件每秒），视频总量几十亿。同一道题有大量变体：某个用户最近 7 天听得最多的 10 首歌；全站实时播放最多的 5 首歌（1000 万在线用户，结果延迟约 10 秒）；趋势话题标签（越新权重越高、按地区分榜）；任意起止时间的即席查询；每周重置的榜单；游戏排行榜里"我的全球名次与上下各 5 名"。

给出完整解答：需求、核心实体与接口、整体设计、深入问题、取舍、不同级别的期望。

## A
**一句话。** 难点在于对象数量（基数）极大、写入极猛、窗口还在滑动：必须把"算 Top-K"从查询路径挪到写入路径之后的预计算里，并在"精确 vs 近似"和"滚动窗口 vs 对齐窗口"这两个选择上先和面试官对齐需求，因为这两个选择会直接换掉整套架构。

**60 分钟路线。**

| 时间 | 做什么 |
|---|---|
| 0–5 分 | 要求和数字：70 万事件每秒，64 GB，先对齐精确与近似、滚动与对齐窗口 |
| 5–10 分 | 实体和接口，事件来自按对象 ID 分区的 Kafka |
| 10–25 分 | 整体设计：Kafka、流处理聚合、分片前 K、Redis 预计算 |
| 25–50 分 | 深入：预计算、写入量与热点、对齐窗口与滑动窗口 |
| 50–60 分 | 追问：窗口表、近似草图、变体 |

**需求。**
- 功能：
  1. 查询某个时间窗口（1 小时、1 天、1 个月、全部时间）内的前 K 名，K 最大 1000。
  2. 返回每个对象的计数。
  3. 变体里还可能要求：按维度（地区、用户、类目）分榜；任意时间范围；时间衰减加权。
- 非功能：
  - 新鲜度：事件发生后 1 分钟内要反映在榜单里。
  - 延迟：查询返回在几十毫秒内，所以必须预计算。
  - 精确性：先假设精确，再讨论近似是否可接受。
  - 规模：70 亿 / 天 ÷ 10 万秒（取整估算）≈ 70 万事件每秒；若按 86400 秒精确算约 81 万。视频 36 亿个，朴素的"对象 ID 8 字节加计数 8 字节"全表约 64 GB，这个数字要记住：每多维护一份全量计数就多 64 GB。

**核心实体与接口。**
- 实体：对象（Video）、事件（View，含对象 ID、时间戳、可选维度）、时间窗口（Window）。
- 接口：`GET /top-k?window=1h|1d|1m|all&k=100&region=` 返回 `[{id, count}]`。事件不走在线 API 写入，假设上游已经把事件写进一个按对象 ID 分区的 Kafka 主题。

1. 事件进入 Kafka，按对象 ID 分区，这样同一对象的所有事件落在同一个消费者上。
2. **Flink 分钟级本地聚合：** 流处理作业（Flink）对每个对象按分钟做本地聚合，设置约 30 秒的乱序容忍水位线（watermark），把"每次播放一条写入"压缩成"每个对象每分钟一条写入"，写入量通常降低 2 到 100 倍。
3. 聚合结果写入按对象 ID 分片的存储，保存"窗口桶 + 对象 → 计数"。
4. 每个分片维护自己的前 K，汇总任务每分钟把各分片的前 K 做归并，写入 Redis（有序集合或整段 JSON），键为 `topk:{窗口}:{对齐时间戳}`。
5. 查询服务只读 Redis，从不碰数据库。缓存条目保留几小时，预计算延迟时仍可返回略旧的结果而不是报错。

正确性要点：对象按 ID 分区，每个对象只属于一个分片，所以全局前 K 一定包含在"各分片前 K 的并集"里，归并是精确的。若改成按时间或随机分区，同一对象的计数会散在多个分片，这个结论就不成立了。

**深入。**
1. 【必讲】怎样不让每个查询都打到数据库。
   - 直接查询加缓存：命中时极快，但缓存过期瞬间所有请求涌向数据库，且这些请求违反延迟目标。可用请求合并（single flight）缓解涌入，解决不了慢。
   - 预计算（选用）：定时任务在窗口边界之前就算好并写入缓存，读路径只读缓存。代价是多了一个需要监控的定时任务，缓存留有余量即可兜底。
2. 【必讲】写入量太大怎么办。
   - 分片：Kafka 分区与数据库分片按同一个键对齐。单机写入按 1 万每秒算，70 万每秒需要约 70 个分片，太多。
   - 批量聚合：热门对象在一分钟内被播放成千上万次，先在流处理里按（对象, 分钟）求和再落库，分片数能降到个位到十几个。
   - 热点对象：一个爆款会让单个分区过热。在流处理第一级给热点键加随机盐（对象#0 到对象#N）分散计算，第二级再合并。
3. 【必讲】滑动窗口与对齐窗口。
   - 对齐（tumbling）窗口：窗口落在整点边界，只加不减，最容易。先向面试官建议"1 天、1 个月用对齐窗口，1 小时可以滑动"，符合产品直觉：月榜变化慢。
   - 滑动窗口：以分钟为粒度，每分钟加上新进入的增量、减去 60 分钟前离开的增量，需要保留分钟级数据到窗口长度。让两个消费者组错开读同一个 Kafka 主题，一组负责加、一组晚一个窗口长度负责减，就不必再自己存分钟级明细，但要求主题保留一个月以上。
   - 不要直接用滑动步长 1 分钟的原生窗口：一个月窗口会把状态放大 60×24×30 = 43200 倍。
4. 【追问再讲】窗口怎么算才快。
   - 朴素做法：每次查询对最近 N 个小时的行 `GROUP BY` 求和再排序，要扫上百 GB，几分钟起步。
   - 层级汇总：同时维护小时、天、月三个粒度，月窗口只加 30 个日桶。仍然有跨粒度同步的延迟。
   - 每个窗口一张当前值表（选用）：`views_last_hour`、`views_last_day` 等各一张表并在计数列建索引，查询就是 `ORDER BY count DESC LIMIT k`，代价是每次写要更新 4 张表，换来读的 O(k)。
5. 【追问再讲】近似：计数最小草图（Count-Min Sketch，CMS）。
   - 原理：d 行 w 列的计数器，用 d 个哈希函数各自定位一格并加一；查询取 d 个格里的最小值。估计值只会偏大不会偏小，超出真实值的量以高概率不超过 ε×总事件数，其中 w = ⌈e/ε⌉，d = ⌈ln(1/δ)⌉。
   - 估算：每小时 25.2 亿事件，取 ε = 10^-6（误差上界约 2520 次）、d = 5，需要 272 万列乘 5 行共 1359 万个 4 字节计数器，约 54 MB，对比全量计数的 64 GB。前几名的差距通常是成千上万次，误差可以接受。
   - 配合一个大小为 1000 的堆或有序集合保存候选对象，因为草图本身忘记了对象 ID，不能"列出前 K"。
   - 落地：Redis 的 CMS 命令可以实现，但每个事件要同时改草图和有序集合，崩溃时二者可能不一致；放进 Flink 状态里由检查点保护更稳。CMS 不能在 Redis 里做减法，滑动窗口需要自己实现带减法的版本，超出一般面试范围。
6. 【加分】专用存储要不要上。
   - 时间序列库（InfluxDB、Prometheus）：对象 ID 作标签会产生几十亿条序列，"跨所有序列取前 K"退化为全扫描，不适合。
   - TimescaleDB：本质还是上面的"分区表 + 预聚合"，连续聚合替你维护小时、天、月汇总，仍要加缓存。
   - 实时 OLAP（Druid、Pinot、ClickHouse）：写入时按（分钟, 对象）预聚合，直接支持 top-N 查询和任意时间范围，适合"任意起止时间"的变体，代价是运维复杂、尾延迟要盯。

**取舍与追问。** 按被问到的可能性排，通常口述就够：
- **追问：用户近 7 天榜：** 追问"某个用户最近 7 天听得最多的 10 首歌"：数据量与全站榜完全不同，单个用户的数据可以放一台机器。按（用户, 日）保存歌曲计数，查询时合并最近 7 个日桶并取前 10，结果缓存；写入侧按用户分区，事件量大但每个键很小。不需要草图。
- 追问"全站实时前 5，延迟 10 秒，1000 万在线"：窗口改为短的滑动窗口，用 10 秒到 1 分钟的流处理微批；因为只要 5 个，每个流处理实例保留本地前 N，再归并一次即可，不需要持久化大表。
- 追问"趋势标签，越新权重越高、按地区分榜"：用指数衰减分数 `s = s×2^(-Δt/半衰期) + 1`，只在更新和读取时惰性衰减，无需定时刷新；新颖度用当前速率与过去几天基线的比值；地区作为键的一部分，每个地区一个榜。
- 追问"任意起止时间的即席查询"：保存分钟级聚合到 OLAP；或为每分钟保存草图加该分钟的前 M 名候选，草图可以按位置相加合并，候选取并集后再用合并草图估计排序。
- 追问"精确还是近似"：先问清业务，不涉及金钱和名次纠纷的趋势榜用近似；排行榜奖励、反欺诈要精确。
- 追问"每周重置"：窗口按周对齐，周一零点切换新桶，旧桶留存作为历史。
- 追问"排行榜里我的名次和上下 5 名"：Redis 有序集合的 `ZRANK` 与 `ZRANGE` 按名次取一段；亿级用户时按分数区间分片，名次 = 更高分片的人数 + 片内名次。

**级别期望。**
- 中级：Kafka 消费者累加计数写库，用索引取前 K，能指出每次写库和全表聚合是瓶颈并加缓存。
- 高级：预计算加缓存、分片加批量聚合、对齐窗口与滑动窗口的差别、分片前 K 归并的正确性，并能估算 70 万每秒与 64 GB。
- 资深（staff）：主动比较精确与近似（草图尺寸推导）、热点键处理、故障恢复（检查点与 Kafka 重放）、不同变体下的架构切换，以及对专用存储适用与不适用的判断。
