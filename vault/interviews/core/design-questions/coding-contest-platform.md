## Q
**在线判题与编程竞赛平台（LeetCode）**｜系统设计

设计一个在线编程平台：用户浏览题库、在浏览器里选语言写代码、提交后几秒内得到判题结果，并能参加限时比赛、查看实时排行榜。参考量级：一场比赛最多 10 万人，90 分钟，10 道题，按解出题数排名、并列时按完成时间排；提交结果要在 5 秒内返回；整体可用性优先于强一致。常见追问：比赛开始与结束前后的流量尖峰，瓶颈在哪里、怎么缓解；怎样安全地运行不可信的用户代码；怎样让同一套测试用例跑在任意语言上；排行榜怎么做到又快又实时。

给出完整解答：需求、核心实体与接口、整体设计、深入问题、取舍、不同级别的期望。

## A
**一句话。** 这个系统的数据量很小（几千道题、几十万用户），真正的难题是两件事：怎样在共享机器上安全、公平、快速地执行不可信的代码，以及比赛瞬间 10 万人同时提交与刷新榜单的尖峰；所以重点放在沙箱隔离、异步判题队列与按计划预扩容、排行榜的有序集合上。

**需求。**
- 功能：
  1. 浏览题目列表（分页、按难度和标签筛选）。
  2. 查看题目详情，在编辑器里选语言写代码，得到各语言的代码模板。
  3. 提交代码，得到判题结果：通过、答案错误、超时、内存超限、运行错误、编译错误。
  4. 比赛：限时、多题，实时排行榜，按解题数降序、用时升序排名。
- 非功能：
  - 判题延迟：提交到返回结果 5 秒内（典型值 1 到 3 秒）。
  - 规模：比赛 10 万人；峰值同时在判的提交约 1 万个；题库约 4000 道。
  - 隔离与安全：用户代码不能读写宿主机、访问网络、耗尽资源或逃逸。
  - 可用性优先于一致性：排行榜可以延迟几秒，但提交不能丢。
  - 容量推算：1 万个提交 × 每个 100 个测试点 = 100 万个测试点；每点最坏 0.1 秒，共 10 万核秒；要在 60 秒内判完需要约 1667 个核。典型测试点只要 10 到 50 毫秒，且遇到第一个失败就停止，实际需求可降一个数量级，但仍说明单机纵向扩展不可行。

**核心实体与接口。**
- 实体：
  - 题目（Problem）：id、标题、难度、标签、描述、各语言代码模板、资源限制（时间、内存）、测试点位置（对象存储）、判题方式（逐字比较或特殊判题程序）。
  - 提交（Submission）：submission_id、user_id、problem_id、contest_id（可空）、语言、代码位置、状态（QUEUED、RUNNING、DONE）、判题结果、耗时、内存、提交时间（服务端生成）。
  - 比赛（Contest）：开始与结束时间、题目列表、参赛者。排行榜（Leaderboard）：比赛内每个用户的解题数与罚时。
- 接口：
  - `GET /problems?page=&limit=`、`GET /problems/{id}?language=`。
  - `POST /problems/{id}/submit`：请求体只有 `code` 和 `language`；用户 ID 来自登录态，时间戳由服务端生成，不信任客户端传入的任何身份与时间。返回 submission_id。
  - `GET /submissions/{id}`：客户端每秒轮询一次，直到状态为 DONE。
  - `GET /contests/{id}/leaderboard?page=&limit=`。

1. 浏览题目：无状态 API 服务读题库（文档型数据库或带索引的关系库），题目内容几乎不变，放 CDN 与应用内存缓存。
2. 提交：API 服务校验后把代码写入对象存储、插入状态为 QUEUED 的提交记录、向队列投递一条只含 submission_id 的消息，立即返回。
3. 判题 worker：按语言分池，从队列拉取任务，在沙箱中编译并逐个运行测试点，将结果以条件更新（状态为 QUEUED/RUNNING 才可写）写回提交表，再更新排行榜。
4. 结果获取：客户端轮询 `GET /submissions/{id}`；轮询间隔 1 秒就足够，不必引入 WebSocket。
5. 排行榜：Redis 有序集合保存比赛内每个用户的复合分数，API 读取前 N 名和某用户名次，客户端每 5 秒刷新。

**深入。**
1. 怎样安全地运行用户代码。
   - 直接在 API 服务器进程里运行：恶意代码可删数据、外传数据、挖矿，死循环拖垮服务，崩溃连带 API 一起宕机。不可接受。
   - 虚拟机：隔离最强，但启动慢、占资源大。
   - 容器：共享宿主内核，启动快，可复用预热的容器。需要加固：代码目录只读挂载，输出写临时目录；用 cgroup 限制 CPU、内存、进程数；每个测试点有墙钟与 CPU 时间上限（例如 5 秒），超时杀进程；关闭网络；用 seccomp 限制系统调用，仅允许必要的几十个。
   - 更强隔离：容器逃逸漏洞存在，对公开平台应在容器之上再加一层，用 gVisor（用户态内核拦截系统调用）或 Firecracker（轻量级微虚拟机），以少量启动开销换取内核隔离。
   - 无服务器函数：自动伸缩，但冷启动和资源上限限制了长时间运行与高并发的稳定性；本场景流量可预测，容器池更合适。
2. 怎样跑测试点：一套测试数据，任意语言。
   - 每道题只维护一份与语言无关的测试数据：输入和期望输出用统一序列化（例如二叉树用层序数组）。
   - 每种语言有一个测试驾驶程序（harness）：反序列化输入、调用用户的函数、序列化输出并与期望比较；链表、树等结构由 harness 里的类提供。
   - 结果不唯一的题（多个合法答案）用特殊判题程序（checker）按条件验证，而不是逐字比较。
   - 测试数据按版本放对象存储，worker 本地磁盘缓存，题目修改时版本号变化。
   - 提速：先编译一次再跑所有测试点；遇到第一个失败立即返回；按 CPU 时间而不是墙钟时间计时，并给判题进程独占核心，减少计时抖动。
3. 排行榜怎样又快又实时。
   - 每次请求都查提交表聚合：对 10 万人每 5 秒一次，数据库被打垮，不可取。
   - 定时缓存整张榜：数据库压力小，但榜单延迟取决于刷新周期。
   - Redis 有序集合（选用）：把"解题数降序、用时升序"编码成一个数字分数，例如 `score = 解题数 × 10^7 − 总用时秒数`（总用时小于 10^7 秒，所以不会进位）。有人通过一题时用 `ZADD` 写入分数；前 N 名用 `ZRANGE ... REV`；某用户名次用 `ZREVRANK`，都是 O(log N)。
   - 幂等：判题可能因 worker 重试而重复报告同一结果，所以不用 `ZINCRBY`，而是根据数据库里该用户每题首次通过的记录重新计算分数，再 `ZADD` 覆盖。
   - 读压力：10 万人每 5 秒轮询约 2 万次每秒；前 100 名在应用内存或 CDN 缓存 1 到 2 秒，所有人共享同一份，个人名次再单独 `ZREVRANK`。
   - 罚时：如果赛制加罚（每次错误提交加 20 分钟），在计算分数时加入，不需要改数据结构。
4. 比赛尖峰与容量。
   - 比赛是预先报名的，开始时间已知，所以不必被动等指标触发扩容：开赛前 10 分钟把判题 worker 池按预估峰值拉满，赛后缩容；同时保留按队列深度的自动伸缩作兜底。
   - 队列是缓冲：峰值提交先排队，worker 按自己的速度消费，超过 5 秒的尾部可以接受（体验降级），但不丢提交；worker 崩溃时消息重新可见，被别的 worker 重判。
   - 开赛瞬间 10 万人同时拉取题目：题目内容提前准备好，开赛时刻只翻转可见性，内容走 CDN；赛前存放的是不可读的状态（或加密，开赛时发放密钥）。
   - 数据库写入：每次提交至少两次写（创建、写结果），峰值数千次每秒，单个关系库主库可承受，若不够再按 contest_id 分片。
   - 限流：每用户每题每分钟限制提交数，防止刷接口和滥用判题资源。
5. 为什么用异步队列而不是同步直连容器。
   - 同步直连简单，API 线程占用到判题结束；队列使系统变成异步，要多一个轮询接口。
   - 队列带来的好处：削峰、重试、按语言和优先级分队列（比赛优先于练习）、worker 独立伸缩。对本规模来说从吞吐上看略显重，但重试与不丢提交的保证值得。

**取舍与追问。**
- 追问"为什么不用 WebSocket 推结果"：轮询间隔 1 秒，10 万用户同时等待也只是约 10 万次每秒的轻量读（按 DONE 状态走缓存或键值查询）；WebSocket 要维护十万级长连接，复杂度更高，收益只有不到一秒的延迟。
- 追问"题库用关系库还是文档库"：题目的测试点、代码模板天然嵌套，适合文档库；需要按标签、难度组合查询时，关系库加索引或搜索引擎更方便，两者都可行，要说明选择理由。
- 追问"作弊与抄袭"：赛后对通过代码做相似度检测（抽象语法树指纹）；提交时间由服务端生成；比赛期间限制并发会话。
- 追问"判题结果不一致（同样代码有时超时）"：独占核心、固定频率、预热容器、对临界超时的提交自动复判一次。
- 追问"多区域"：判题 worker 可就近部署，但比赛排行榜以单一区域的 Redis 为准，其他区域读副本。
- 追问"提交内容巨大或输出巨大"：限制代码长度，限制输出字节数并在超限时终止，防止撑爆磁盘或日志。

**级别期望。**
- 中级：画出 API、题库、判题容器和排行榜，能说出为什么不能在 API 服务器上直接运行代码。
- 高级：容器沙箱的具体加固措施、异步队列、Redis 有序集合排行榜、容量推算为何需要水平扩展。
- 资深（staff）：沙箱分层取舍（容器、gVisor、Firecracker）、测试驾驶程序与特殊判题、赛前预扩容与尖峰分析、排行榜的幂等与缓存分层，以及怎样在"够用"与"过度设计"之间说明判断依据。
