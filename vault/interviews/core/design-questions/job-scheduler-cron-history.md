## Q
**分布式任务调度器（含 cron 与一年执行历史）**｜系统设计

设计一个分布式任务调度器：峰值每秒 1 万个任务执行（10k jobs/s），既支持按 cron 表达式周期触发，也支持用户临时提交的一次性（ad hoc）任务；失败要自动重试；每次执行的历史要保留一年并能按任务查询。常见的变体有：任务声明所需 CPU/内存，系统要把它放到合适的机器上；任务可能跑几秒也可能跑几周，还允许中途修改；任务分多个阶段，某阶段失败不能丢掉前面阶段的进度；要支持超时与回调；要提供"任务状态"和"某次实例状态"两种查询；有的面试官明确要求不要直接套用现成的托管队列和托管数据库，要自己讲清楚队列和存储怎么做。

给出完整解答：需求、核心实体与接口、整体设计、深入问题、取舍、不同级别的期望。

## A
**一句话。** 难点不在"存一张任务表再定时查"，而在三件互相拉扯的事：在亿级待定任务里亚秒级找出"现在到期的那一小撮"，在 worker 随时会死的前提下保证每次触发至少执行一次且不会同时执行两次，以及把一年的执行历史和热的调度状态分开存放，让两边都不被对方拖垮。

**60 分钟路线。**

| 时间 | 做什么 |
|---|---|
| 0–5 分 | 需求和数字：约 1 万次执行每秒，一年约 1×10^11 条历史，调度延迟 P99 约 1 到 2 秒 |
| 5–10 分 | 实体和接口：Job、Run、Worker；worker 协议带 `run_id` 与 `attempt` |
| 10–25 分 | 画主链路：cron 只物化下一次 → 分片扫描加内存堆 → CAS 分发 → 队列 → worker 租约 → 重试 → 归档 |
| 25–50 分 | 深入：找到期任务、租约与围栏令牌、热表与历史库分离 |
| 50–60 分 | 追问：cron 语义（时区、错过、重叠）、长任务与多阶段、调度器高可用 |

**需求。**
- 功能：
  1. 创建、修改、删除任务，任务类型为一次性（指定时间）、周期性（cron 表达式加时区）、立即执行（ad hoc）。
  2. 到期后分发给 worker 执行，失败按退避策略重试，超过次数进死信队列（Dead Letter Queue，DLQ）。
  3. 查询任务定义、某个任务的执行历史、某次执行实例的状态，可以取消正在排队的执行。
  4. 执行历史保留一年，支持按任务与时间范围分页查询。
  5. 可选：优先级、超时与回调、多租户配额。
- 非功能：
  - 吞吐：峰值 1 万次执行每秒，约 8.6 亿次每天；平均按峰值的三分之一估算，一年约 1.05×10^11 条执行记录。
  - 准时性：到期时间到实际分发的延迟（调度延迟）P99 小于 1 到 2 秒。
  - 语义：至少一次（at-least-once）；同一次执行在任一时刻最多一个 worker 持有有效租约。
  - 可用性：调度节点、worker、单个存储分片宕机都不能让任务静默丢失。
  - 存储：热数据（待定与运行中）是 GB 级，冷数据（历史）是十 TB 级。

**核心实体与接口。**
- 实体：
  - 任务定义（Job）：job_id、owner、类型、cron 表达式与时区、执行入口（handler 与 payload 引用）、重试策略（最大次数、退避基数）、超时、优先级、资源需求、状态（启用/暂停）。
  - 执行实例（Run）：run_id、job_id、计划触发时间（scheduled_at）、状态（SCHEDULED、QUEUED、RUNNING、SUCCEEDED、FAILED、DEAD）、尝试序号（attempt）、租约持有者与到期时间、开始与结束时间、结果摘要。
  - Worker：worker_id、能力标签、容量、最后心跳。
- 接口：
  - `POST /jobs`（带幂等键，返回 job_id），`PUT /jobs/{id}`，`DELETE /jobs/{id}`。
  - `POST /jobs/{id}/runs` 立即执行一次，返回 run_id。
  - `GET /jobs/{id}`、`GET /jobs/{id}/runs?from=&to=&status=&cursor=`、`GET /runs/{run_id}`、`POST /runs/{run_id}/cancel`。
  - worker 内部协议：`lease`（拉取并领取租约）、`heartbeat`、`complete`、`fail`，每次都带 run_id 与 attempt，作为围栏令牌（fencing token）。

图中从上到下：API 层写入任务定义和第一个待定 Run；调度器分片每分钟按索引范围扫描"未来几分钟内到期"的 Run，装进内存里的时间堆；到点后用比较并交换（Compare And Swap，CAS）把状态从 SCHEDULED 改为 QUEUED 并投进工作队列；worker 拉取、领租约、执行、心跳；终态写回并同步到历史库。

1. 写入路径。API 层校验 cron 表达式，计算出第一个触发时间，同事务写入 Job 与一条 SCHEDULED 状态的 Run。cron 任务永远只物化"下一次"这一条 Run：它被分发的同一个事务里再算出再下一次并插入。这样 5 百万个 cron 任务也只占 5 百万行，而不是把未来一年的触发点全部展开。
2. 发现到期任务。Run 表按 job_id 哈希分成多个分片（例如 32 个），每个分片有一个索引 `(shard, scheduled_at)`。分片的"属主调度器"每 30 秒左右执行一次范围扫描，取出未来 60 秒内到期、状态为 SCHEDULED 的行，放进本地的最小堆。粗粒度走数据库，精粒度走内存堆，数据库查询频率因此是每分片每半分钟一次，与任务总量无关。
3. 触发。堆顶到点后，调度器执行 `UPDATE run SET state='QUEUED', version=version+1 WHERE run_id=? AND state='SCHEDULED'`，影响行数为 1 才把消息投进队列。哪怕分片属主切换期间出现两个调度器同时处理同一行，也只有一个 CAS 成功，这是"不重复分发"的真正防线，选主只是为了减少无谓的竞争。
4. 分发与执行。工作队列按优先级分多个层级（高、中、低，必要时再按租户或资源类别拆分）。worker 是拉取模式：按自己的剩余容量拉取，拿到后把 Run 改为 RUNNING，写入租约到期时间和 attempt，执行期间每隔三分之一租约时长续约一次。拉取模式自带背压，并且 worker 之间性能不同也不会被推爆。
5. 失败处理。执行报错或租约过期都视为一次失败：attempt 加一，按指数退避加抖动算出新的触发时间，把 Run 改回 SCHEDULED。重试因此被统一成"一次更晚的到期"，复用同一套发现与触发机制，不需要第二条路径。超过最大次数则置 DEAD 并写入 DLQ，同时告警。
6. 历史归档。Run 到达终态后通过变更流（事件总线）写入历史库并删除热表中的行，热表因此只含待定与运行中的 Run，规模稳定在 GB 级。历史库用宽列存储（Cassandra 一类）或按月分区的列存，主键为 `(job_id, 月份)` 加时间倒序，查询某任务的最近执行是单分区顺序读；超过一年的分区整体丢弃（TTL），不做逐行删除。

**深入。**
1. 【必讲】怎样在亿级待定任务里亚秒级找到到期任务。
   - 方案一：每秒全表 `WHERE scheduled_at <= now()`。有索引时单次扫描本身不贵，真正的成本是每秒一次的高频查询、多个调度器抢同一批行造成的锁竞争，以及整点时一次取出几十万行；调度器一多反而更慢，扩不动。
   - 方案二：时间分桶。把 Run 按分钟写进桶，每个桶一个队列或分区，调度器只处理"当前桶"。查询极简单，但桶内秒级精度要另做，且 cron 的整点扎堆会让某几个桶特别大。
   - 方案三（选用）：数据库做粗筛，内存堆做精筛，再加分片属主。粗筛的频率与任务总量无关，精筛是 O(log n)，分片让每个调度器只管自己那一份，扎堆时可以拆分片或加抖动。代价是调度器重启会丢堆，所以堆只是缓存，数据库永远是事实来源，重启后重新扫描即可。
2. 【必讲】至少一次与"不会同时执行两次"。
   - 租约（lease）：worker 领取时写 `lease_until`，续约时检查 attempt 未变；到期没续约，扫描器把 Run 判为失败并重试。这给出至少一次。
   - 围栏令牌：旧 worker 可能只是网络卡住并没有死，等它醒来时新的 attempt 已经在跑。所以所有对状态的写入（完成、失败、续约）都带 attempt，数据库用 `WHERE attempt = ?` 拒绝过期写入。对外部系统的副作用则要求把 run_id 作为幂等键传给下游。
   - 需要说清楚的边界：任务本身的副作用只能靠任务幂等来吸收。如果任务内容是用户自定义、无法检查幂等（长时间运行又可编辑的变体），提供一个"至多一次"开关：租约丢失时不自动重试，状态置 UNKNOWN 交给人工或回调决定。
3. 【必讲】一年历史的存储与查询。
   - 数字：平均每秒约 3300 次，每年约 1.05×10^11 条，每条约 150 字节，合计约 16 TB。
   - 热表与历史库分开：热表需要频繁更新与按到期时间索引，历史库只追加、按任务查询。同表存放会让一年数据拖累热路径的索引。
   - 过期：按月分区，整分区删除，避免 1 亿行级别的逐行 DELETE。需要报表时，再把历史导出到列存仓库做聚合，查询接口只做按任务的明细。
4. 【追问再讲】cron 的语义细节（高频追问，也是区分度）。
   - 时区与夏令时：存储表达式与 IANA 时区，每次用该时区算下一次；春季跳时的不存在时刻默认顺延，秋季重复的时刻只触发一次，并把这个选择写进文档。
   - 错过的触发：调度器停了十分钟，恢复后怎么办。可配置三种策略：全部补跑、只补最近一次、全部跳过；默认只补最近一次，防止恢复瞬间雪崩。
   - 重叠：上一次还没跑完下一次又到点，可配置允许并发、跳过、或取消旧的；默认跳过并记录一条"被跳过"的历史。
   - 整点扎堆：大量任务写成 `0 * * * *`。对没有精确要求的任务加 0 到 N 秒的稳定抖动（按 job_id 哈希，保证每次一致），把一个尖峰摊平。
5. 【追问再讲】长时间运行、多阶段、资源匹配。
   - 数秒到数周的任务：不能靠一次租约覆盖。租约只覆盖"worker 还活着"，续约带进度检查点；worker 失联后新 worker 从最近检查点继续。
   - 多阶段且不能丢进度：把每个阶段拆成独立 Run，上游完成后才把下游置 SCHEDULED（有向无环图，DAG），阶段输出落外部存储。这就是持久化执行（durable execution）的思路，规模再大或逻辑复杂时直接引入 Temporal 一类引擎，调度器只负责"何时启动工作流"。
   - 资源匹配（任务声明 CPU/内存）：worker 注册自己的容量，队列按资源类别拆分；或者让调度器做过滤加打分的装箱（bin packing），本质上变成集群调度器（Borg、Kubernetes 调度器）。先按资源类别分队列是最小可行的版本。

**取舍与追问。** 按被问到的可能性排，通常口述就够：
- 追问"为什么不直接用 SQS 加 DynamoDB"：托管队列的延迟投递有上限（SQS 为 15 分钟），长周期任务仍需要自己的存储来放远期任务；并且让 worker 靠队列去重实现无状态调度，其实把正确性推给了 worker。若面试官要求不用托管服务，就用分片关系库当队列：`SELECT ... FOR UPDATE SKIP LOCKED` 领取，行锁代替可见性超时。
- 追问"调度器本身怎么做高可用"：分片属主靠租约或协调服务（etcd、ZooKeeper）选出，宕机后另一个节点在租约过期后接管；因为 CAS 保护，选主短暂重叠也不会双发。
- 追问"调度延迟太大怎么排查"：监控 `dispatch_time - scheduled_at` 的分位数、各分片堆长度、队列积压、worker 空闲率，积压在哪一层就扩哪一层。
- 追问"某租户一次提交 100 万个任务"：入口限流加每租户配额，队列层按租户做加权公平调度，防止一家挤占全体。
- 追问"优先级会不会饿死低优先级"：为低优先级任务按等待时间逐步提升有效优先级（老化，aging）。
- 追问"每秒 1 万是峰值还是平均，写放大多少"：一次执行至少 4 次状态写（创建、入队、运行、终态），峰值约 4 万写每秒，分 16 个分片则每片约 2500 写每秒，单机可承受。

**级别期望。**
- 中级：画出任务表、定时扫描、队列、worker、重试与 DLQ，能解释为什么不能每秒全表扫描。
- 高级：说清粗筛加精筛、租约与围栏令牌、cron 只物化下一次、热表与历史库分离，并能算出分片数和存储量。
- 资深（staff）：主动讲调度器属主切换时的正确性、错过触发与重叠策略、持久化执行与长任务、多租户公平与调度延迟的可观测性，并能在"自建与托管"之间给出判断依据。
