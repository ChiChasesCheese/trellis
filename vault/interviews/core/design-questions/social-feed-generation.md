## Q
**社交信息流生成系统（News Feed）**｜系统设计

设计一个类似 Twitter、Instagram、Facebook 的个性化信息流：用户发帖，关注他们的人在首页看到按排序打分的信息流；信息流里除了好友的帖子，还可能混入广告（sponsored）、新闻文章和图片等推荐内容。面试官有时只要求设计接口（发帖、取信息流、分页），有时深入到"推还是拉"、名人账号怎么处理、排序放在哪一层。

给出完整解答：需求、核心实体与接口、整体设计、深入问题、取舍、不同级别的期望。

## A
**一句话。** 信息流的难点是读写不对称加上"关注数极不均匀"：普通用户适合发帖时把帖子推进粉丝的收件箱（写扩散），名人适合读取时再拉取（读扩散），排序和广告插入放在读取时的少量候选上做，而不是对全部帖子预先排序。

**60 分钟路线。**

| 时间 | 做什么 |
|---|---|
| 0–5 分 | 要求和数字：读写不对称，粉丝数极不均匀 |
| 5–10 分 | 实体、接口、游标分页 |
| 10–25 分 | 整体设计：发帖、扇出、读取、排序 |
| 25–50 分 | 深入：推拉混合、排序放读时、广告与推荐 |
| 50–60 分 | 追问：已读去重、名人热点、一致性、只存 ID |

**需求。**
- 功能：
  1. 发布帖子（文字、图片），关注与取消关注。
  2. 获取首页信息流：好友帖子为主，按相关性排序，支持无限下拉分页。
  3. 信息流中混入广告和推荐内容（新闻、图片）。
  4. 查看某个用户的个人主页帖子列表。
- 非功能：
  - 规模假设：3 亿日活，每人每天打开信息流约 10 次，约 3.5 万次读取每秒；每天 1 亿条新帖，约 1160 条每秒；平均粉丝数 200，名人粉丝上千万。
  - 延迟：信息流 P99 小于 500 毫秒；发帖到粉丝可见（新鲜度）在数秒到十几秒内。
  - 可用性优先于一致性：信息流稍旧可以接受，不能打不开。
  - 存储：每个用户保留最近约 800 条帖子 ID 的收件箱，3 亿 × 800 × 8 字节 ≈ 1.9 TB，放内存集群可行。

**核心实体与接口。**
- 实体：用户（User）、帖子（Post：post_id、作者、正文、媒体引用、创建时间）、关注关系（Follow：follower_id、followee_id）、信息流收件箱（用户到帖子 ID 列表）、广告（Ad）、推荐内容（Content）。
- 接口：
  - `POST /posts {text, mediaIds}` 返回 post_id；媒体先通过预签名地址直传对象存储，再引用。
  - `GET /feed?cursor=&limit=20` 返回帖子列表和 `nextCursor`。游标是不透明令牌，内含上一页最后一条的排序位置和已见集合版本；不用页码偏移，因为信息流在翻页过程中会不断插入新内容，偏移会导致重复或漏掉。
  - `GET /users/{id}/posts?cursor=`、`POST /follow/{userId}`、`DELETE /follow/{userId}`。
  - 用户身份来自登录态，不放在请求参数里。

1. 发帖：帖子服务把帖子写入帖子库（按 post_id 分片的 KV 或宽列库），媒体在对象存储；随后向 Kafka 发布 `PostCreated` 事件。
2. 扇出（fan-out）服务消费事件：查作者的粉丝列表，对粉丝数不超过阈值（例如 10 万）的作者，把 post_id 追加到每个粉丝的收件箱（Redis 有序列表，按时间排序，超过 800 条裁掉旧的）。粉丝数超过阈值的名人，不做扩散写入，只写入作者自己的"近期帖子"列表。
3. 读取信息流：信息流服务取用户的收件箱（候选一）；对用户关注的名人，实时拉取其近期帖子列表（候选二）；再从推荐服务取非关注内容（候选三）；合并去重后进入排序。
4. 排序：先用轻量模型粗排到几百条，再用完整模型精排取前 50 条左右；做多样性规则（同一作者不连续出现）；广告服务根据用户和上下文每隔若干条插入一个广告位；最后批量取帖子详情、作者信息、点赞数，返回一页。
5. 缓存：帖子对象和作者信息放缓存；计算好的一页结果可以短时间缓存（几十秒），用户来回切换页面时不重复排序。

**深入。**
1. 【必讲】推还是拉：扩散策略。
   - 读时拉取（fan-out on read）：发帖只写一次；读取时查所有关注者的最近帖子并归并。写便宜，读贵，关注 500 人时每次读取要查 500 个列表，延迟高。
   - 写时推送（fan-out on write）：发帖时写入每个粉丝的收件箱；读取就是读一个列表，很快。写放大：平均 200 粉丝时 1160 条每秒帖子产生约 23 万次收件箱写入每秒，可承受；名人一条帖子 1000 万次写入，延迟可达分钟级，并浪费在不活跃粉丝上。
   - 混合（选用）：普通作者推，名人拉。读取时把推送的收件箱与拉取到的名人帖子合并，成本是每个用户关注的名人数（通常很少）。再对不活跃用户（几十天未登录）跳过推送，他们回来时再现算收件箱，省掉大量无效写入。
2. 【必讲】排序放在哪里。
   - 纯时间序：实现最简单，推的收件箱本身就是时间序。
   - 读时排序（选用）：收件箱只存 post_id 与基础时间，排序在读取时对几百个候选执行，使用的特征包括与作者的亲密度、帖子互动速度、内容类型、用户偏好。排序模型更新时无需重写任何收件箱。
   - 预排序写入收件箱：看上去读快，但每次模型变化或互动数变化就得重写，代价高，不采用。
   - 降级：排序服务超时或故障时，退回到收件箱的时间序，保证信息流能打开。
3. 【必讲】广告与推荐内容。
   - 广告由独立的广告系统决定：信息流服务在排序结果中预留广告位（例如第 4 位之后每隔 5 条），向广告服务请求，传入用户画像与上下文，对返回的广告做频次控制；广告点击和曝光走独立的事件管道，不进入信息流的帖子库。
   - 新闻、图片等推荐内容来自推荐服务的候选，与好友帖子一起参与排序，比例可由产品配置。
4. 【追问再讲】已读去重与分页稳定性。
   - 记录用户最近看过的帖子（布隆过滤器或最近 N 条列表），避免刷新后重复出现。
   - 游标内记录排序快照的版本，同一次下拉会话内保持相对稳定的顺序；新内容通过"有新帖子"提示让用户主动刷新，而不是在翻页中插入。
5. 【追问再讲】关注关系与热点。
   - 社交图单独存储：`follower → followees` 与 `followee → followers` 两个方向，按用户 ID 分片，粉丝列表分页读取，避免一次取千万条。
   - 名人的帖子被千万人拉取是读热点：名人近期帖子列表在缓存中复制多份（缓存分片加本地副本）。
6. 【追问再讲】数据一致性。
   - 发帖成功但扇出稍后才到是可接受的最终一致；作者自己看自己的帖子要立即可见（读自己时合并最近发布，或写后读自己的分片）。
   - 删除帖子：帖子对象标记删除，读取时过滤，收件箱里的 ID 不主动清理，到期自然被裁掉。

**取舍与追问。** 按被问到的可能性排，通常口述就够：
- 为什么不把完整帖子复制进每个粉丝收件箱：存储放大数百倍且编辑删除要全局更新；只存 ID，读取时批量取详情并走缓存。
- 新用户没有关注任何人怎么办：冷启动用热门内容和兴趣推荐填充候选。
- 信息流 API 的设计要点：游标分页、返回结构里带每条内容的类型（帖子、广告、推荐）和曝光追踪标记、幂等的点赞与关注、服务端生成时间。
- 实时性要到什么程度：对关系紧密的好友，可以通过推送通知或长连接提示新帖；信息流本身按拉取刷新即可。
- 多区域：帖子库与社交图跨区域复制，收件箱在用户所在区域本地维护。

**级别期望。**
- 中级：发帖、关注、读取好友最近帖子的接口与基础表设计，说出推与拉两种思路。
- 高级：混合扩散、收件箱结构与容量估算、读时排序与降级、游标分页。
- 资深（staff）：广告与推荐的合并机制、不活跃用户的懒物化、热点（名人）的缓存复制、排序服务的故障隔离与延迟预算，以及多区域一致性取舍。
