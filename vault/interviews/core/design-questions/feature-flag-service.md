## Q
**功能开关服务（Feature Flag Service）**｜系统设计

设计一个功能开关服务：团队不用发布代码就能动态打开或关闭某个功能，支持按用户群（地区、套餐、百分比）做定向灰度，能快速回滚，能做 A/B 实验。峰值每秒 100 万次开关取值（flag evaluation），延迟要尽可能小。常见追问有：灰度百分比到底怎么分配（具体算法）；规则求值的数据结构；数据建模；客户端（浏览器、手机）怎么存开关数据、延迟和失败怎么处理；控制面故障时业务怎么办。

给出完整解答：需求、核心实体与接口、整体设计、深入问题、取舍、不同级别的期望。

## A
**一句话。** 100 万次取值每秒只可能在业务进程内本地完成，所以设计的重心不是"一个高并发的取值服务"，而是"把规则集可靠、快速、可回滚地分发到每个 SDK，并保证同一个用户在同一个开关上的结果稳定、可复现"。

**60 分钟路线。**

| 时间 | 做什么 |
|---|---|
| 0–5 分 | 需求和数字：每秒 100 万次取值，只能本地求值，规则集 2 到 20 MB |
| 5–10 分 | 实体和接口：开关、环境配置、规则；控制面和数据面分开 |
| 10–25 分 | 画分发链路：控制面 → 快照加 CDN → SDK 内存，客户端 SDK 走边缘取值 |
| 25–50 分 | 深入：百分比灰度的稳定哈希、变更传播、控制面故障时的行为 |
| 50–60 分 | 追问：规则求值顺序、A/B 实验、数据建模 |

**需求。**
- 功能：
  1. 创建和修改开关：布尔或多变体（variant），按环境（开发、预发、生产）分别配置。
  2. 定向规则：按用户属性（地区、套餐、版本）、用户名单、人群（segment）和百分比灰度。
  3. 取值：给定开关 key 和用户上下文，返回变体；没有数据时返回代码里的默认值。
  4. 快速回滚：一键关闭，或回到上一个版本。
  5. 审计日志与权限；A/B 实验的曝光记录。
- 非功能：
  - 取值：100 万次每秒，P99 低于 1 毫秒，纯本地内存计算，不依赖网络。
  - 传播：变更在 5 到 10 秒内到达绝大多数 SDK；控制面完全不可用时业务照常运行。
  - 一致性：同一用户同一开关结果稳定；灰度比例上调时已命中的用户不会掉出。
  - 规模：规则集规模为数千到上万个开关，每环境约 2 到 20 MB；SDK 实例数万到十万。

**核心实体与接口。**
- 实体：
  - 开关（Flag）：key、类型、变体列表、默认变体、负责人、过期时间。
  - 环境配置（FlagConfig）：开关在某环境的有序规则列表、是否启用、`version`（单调递增）。
  - 规则（Rule）：条件列表（属性、操作符、值）、命中后的动作（固定变体，或带权重的百分比分布）。
  - 人群（Segment）：条件或成员名单，可被多个开关引用。
  - 审计事件（AuditEvent）：谁在什么时候把哪个版本改成了什么。
- 接口：
  - 控制面：`POST/PUT /flags/{key}/environments/{env}`（带期望版本号做乐观并发控制）、`POST .../rollback?to=version`、`GET /flags`。
  - 数据面：`GET /sdk/config?env=` 返回整份规则集快照（带 ETag）；`GET /sdk/stream?env=` 服务端推送（SSE）变更；客户端用的 `POST /eval` 提交用户上下文，返回该用户的全部开关取值。

1. 控制面：管理 API 写入关系库（PostgreSQL），每次修改生成新的不可变版本；校验规则语法与引用关系，生产环境可要求审批；写库成功后发布"新快照"事件。
2. 发布：快照生成服务把环境的完整规则集序列化为一个文件（JSON 或 protobuf，压缩），带版本号写入对象存储，经 CDN 分发；同时通过流服务推送"版本号变了"的通知。
3. 服务端 SDK：启动时拉一次快照放入内存，建立到流服务的长连接，收到通知后拉取新快照（或增量差异）并原子替换；连接断开时退回到每 30 秒轮询。取值就是对内存里的规则集求值，不发网络请求。
4. 客户端 SDK（浏览器、手机）：不下发规则，因为规则里有其他用户的名单和商业信息；改为调用边缘的取值服务，用用户上下文换取该用户的开关取值，结果缓存在本地存储，带过期时间；启动先用缓存值，后台刷新。
5. 遥测：SDK 本地对（开关, 变体）计数，每分钟批量上报一次，不是每次取值一条；实验需要的曝光事件在每个用户每个开关首次命中时才记录。

**深入。**
1. 【必讲】百分比灰度怎么分配（最常被追问的算法）。
   - 随机数：每次取值随机，同一用户时而开时而关，体验错乱，不可用。
   - 存储每个用户的结果：10 亿用户的表，维护成本高，且规则一改就要迁移。
   - 稳定哈希（选用）：把 `开关key + 盐 + 用户ID` 做哈希（如 MurmurHash3 或 SHA-1 取前 4 字节），对 10000 取模得到 0 到 9999 的桶号；桶号小于 `百分比 × 100` 就命中。无状态、可复现、各 SDK 结果一致。把开关 key 放进哈希，使不同开关的分桶相互独立，否则总是同一批用户做小白鼠。
   - 单调性：5% 调到 20% 时，已在前 5% 的用户仍在命中范围内，不会闪回；回滚到 5% 时同一批用户保留。
   - 多变体：把 0 到 9999 切成按权重的连续区间，例如 A 50%、B 30%、C 20%，用同一个桶号落区间。

```python
import hashlib

def bucket(flag_key: str, salt: str, user_id: str) -> int:
    # 开关 key 与盐参与哈希：不同开关互相独立，改盐即可重新洗牌
    h = hashlib.sha1(f"{flag_key}.{salt}.{user_id}".encode()).digest()
    return int.from_bytes(h[:4], "big") % 10000   # 0..9999，结果与 SDK 语言无关

def pick_variant(buckets: list[tuple[str, int]], b: int) -> str:
    # buckets 例如 [("A", 5000), ("B", 3000), ("C", 2000)]，按权重累计成区间
    acc = 0
    for variant, weight in buckets:
        acc += weight
        if b < acc:
            return variant
    return buckets[-1][0]
```
2. 【必讲】变更怎么快速、安全地传播。
   - 推与拉：纯轮询要么慢要么对服务端压力大；十万个 SDK 每 30 秒拉一次也只有约 3300 次每秒，由 CDN 吸收完全没问题。推送只用来缩短延迟，且不承载数据，只通知版本号，丢了也不要紧。
   - 大规则集：2 到 20 MB 的快照每次全量下发代价高，用 ETag 避免无变化的下载，并支持"从版本 N 到 N+k 的增量差异"。
   - 原子性：SDK 用新快照整体替换，不能出现一半新规则一半旧规则；同一次请求内多次取值使用同一份快照，避免请求中途结果变化。
3. 【必讲】失败时的行为（重点追问）。
   - 控制面宕机：SDK 继续使用内存里最后一份已知可用的快照（fail static）；新启动的实例从 CDN 或本地磁盘缓存取快照。
   - 从未成功加载过：使用代码里写死的默认值，因此每个开关调用点都必须带默认值，并且默认值应该是"安全的旧行为"。
   - 错误配置的爆炸半径：开关配置本身也像代码一样要灰度：先对一小部分 SDK 推新版本、监控错误率，再全量；保留上一个版本，回滚就是把"当前版本"指回旧版本，不需要重新计算。
   - 客户端存储：手机端缓存带过期时间；离线时用缓存；缓存过期且取不到时用默认值。
4. 【追问再讲】规则求值的顺序与数据结构。
   - 顺序：开关未启用则返回关闭值；其次是个人覆盖名单；然后按优先级依次匹配规则，第一条命中的规则决定结果；都不命中走默认规则（兜底的百分比或固定值）。有前置条件的开关（依赖另一个开关已开）放在最前面检查，并检测依赖环。
   - 结构：规则编译成不可变的内存对象，条件预解析为比较函数，人群名单用哈希集合；取值时无分配、无锁，整份规则集替换时只换一个引用。
   - 属性缺失：用户上下文没带某属性时，条件视为不命中而不是报错，并且各 SDK 语义必须一致，要有一套跨语言的一致性测试用例。
5. 【追问再讲】A/B 实验与遥测。
   - 实验是带两个以上变体的开关，加上指标定义；分桶复用同样的稳定哈希，使用独立的盐，让不同实验互相独立；互斥实验放入同一"层"，在层内再分桶。
   - 曝光日志只记首次命中，并写入事件流供分析平台使用；校验样本比例失衡（实际分配比例偏离设计比例）以发现 SDK 或上下文丢失的问题。
   - 不要为每次取值记日志：100 万次每秒的日志本身就是一个更大的系统。
6. 【加分】数据建模。
   - 开关定义和环境配置分表，环境配置存规则列表（JSON 列）与版本；版本表只追加；审计表按时间追加。
   - 为什么用关系库：控制面写入量很低（每天几千次修改），要事务、约束和审计；高并发读走的是快照，不走数据库。

**取舍与追问。** 按被问到的可能性排，通常口述就够：
- 追问"为什么不做一个取值微服务"：每次取值一次网络往返，100 万每秒需要成百上千台机器，并把开关服务变成所有业务的关键依赖和单点；本地求值把可用性依赖降为零。
- 追问"实时性要求更高（秒级内）怎么办"：保持流推送加快速拉取；更高要求下，SDK 与边缘节点之间保持长连接并由边缘做增量推送。
- 追问"同一用户在多个服务看到不一致怎么办"：在入口服务求值一次，把结果放进请求头或上下文向下游传递；或要求所有服务使用同一版本的快照并在日志中记录版本号。
- 追问"开关越积越多"：每个开关带负责人和预期删除日期，长期无变化的开关报警；代码中通过静态检查找出已完全开启的开关并提示清理。
- 追问"隐私与合规"：用户属性只在 SDK 本地用于求值，不上传；客户端 SDK 用的取值服务不记录原始属性，只记录聚合计数。
- 追问"数据面怎么多区域"：快照通过 CDN 全球分发，控制面单主多读，写入只在主区域，快照生成后全球可读。

**级别期望。**
- 中级：开关表、规则表、管理 API、SDK 轮询取规则，能解释为什么本地求值。
- 高级：稳定哈希的灰度算法与单调性、推加拉分发、失败时的 fail static、遥测聚合，能算出 SDK 拉取量。
- 资深（staff）：配置变更自身的灰度与回滚、规则集的版本化与增量传播、客户端 SDK 的隐私设计、实验平台与曝光日志的设计、跨服务一致性，以及怎么治理开关债务。
