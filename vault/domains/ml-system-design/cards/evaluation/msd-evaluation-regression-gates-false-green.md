## Q
回归门全绿，新版本上线后用户却明显感到回答变差了。"假绿"通常是什么原因？各自怎么防？

## A
- **测的不是上线的那个东西**：评测用的模型文件、量化方式、引擎参数（最大批大小、是否开前缀缓存）和线上部署配置不一致。
  - 防：评测直接调用和线上同一个镜像、同一份配置；上线前核对模型文件的校验和（checksum）。
- **评测集不代表线上流量**：评测集是半年前抽的，线上已经多了大量长对话、新语言、新功能（例如工具调用）。
  - 防：每月对比评测集和线上请求的分布（长度、语言、意图），差距大的类别补题。
- **只测短输入**：评测平均输入 500 个 token（模型处理文字的最小单位），线上大量 8,000 以上；长上下文的问题测不到。
  - 防：按输入长度分档设评测切片。
- **只测单请求**：评测一次只发一个请求，线上大并发凑批（多个请求合在一起算）。高并发下才出现的数值问题、缓存串用、调度 bug 都漏掉了。
  - 防：评测也在真实并发下跑一遍，比较高并发和单请求的结果是否一致。
- **平均值掩盖了切片**：总分持平，但某一类问题大幅下降、另一类上升。
  - 防：关键切片单独设阈值，对比结果中列出变化最大的切片。
- **评委或答案提取跟着一起坏了**：评委模型被升级、评分提示被改，或提取规则过于宽松，把错答判成对。
  - 防：评委和提取脚本版本锁定；定期用人工复核一批评委判定。
- **缓存的结果**：评测框架复用了上一次的结果文件，实际没有重跑。
  - 防：结果里记录模型版本和运行时间，版本对不上就判为无效。
- **线上问题不在质量指标上**：延迟变长导致超时、流式输出断开，用户感觉"变差"。
  - 防：性能和稳定性也是门的一部分，并在金丝雀阶段监控用户反馈信号（重新生成率、点踩率）。

**总结**：门全绿只说明"在门测到的范围内没退化"。每次线上事故都要补一条能抓住它的评测。
