## Q
什么是 ML 系统的"隐藏技术债"（hidden technical debt）？举几个具体例子，说明它为什么比普通代码的技术债更难还。

## A
**核心观察**：在一个真实的 ML 系统里，训练模型的代码只占很小一块；周围的数据收集、特征提取、数据校验、流水线、服务、监控才是大头。技术债主要藏在这些"胶水"里。

**几种典型的债：**
- **牵一发动全身**（Changing Anything Changes Everything）：模型把所有输入混在一起用。改一个特征的计算方式、加一个特征，所有其他特征的作用都会变，无法像改一个函数那样局部验证。
- **数据依赖不可见**：代码依赖有编译器和包管理检查；数据依赖没有。上游团队把某个字段的单位从秒改成毫秒，下游模型照常运行，只是悄悄变差。
- **未声明的消费者**：别的团队直接读你模型的输出当特征。你一改模型，他们的系统就坏了，而你根本不知道他们存在。
- **流水线丛林**（pipeline jungle）：特征是一层层临时脚本拼出来的，没人敢删任何一步。
- **死掉的实验分支**：配置里留着几十个开关，组合出的路径大多从未测试过。
- **反馈闭环**：模型影响用户行为，用户行为又成为下一版模型的训练数据，问题很难在一个版本里看出来。

**为什么更难还**：普通技术债至少会让代码难读、编译失败或测试变红；ML 的债往往只体现为"指标慢慢下降 0.5%"，没有报错，没有明确的责任方。

**还债手段**：数据像代码一样有模式（schema）和版本；对输入做自动校验；模型输出只通过注册过的接口提供；定期删除没用的特征和实验开关；训练和服务共用同一份特征代码。
