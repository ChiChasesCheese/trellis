## Q
两个组件各自有 95% 的单元测试覆盖率，合在一起却出了 bug。单元测试为什么抓不到？一个好的集成测试应该瞄准什么，又怎么让它既真实又不太慢？

## A
**单元测试里的替身（mock）是测试作者对另一个组件的「想象」。两边各自对着自己的想象通过了，但想象和真实不一致的地方，只有让真组件碰面才会暴露。**

- **集成测试该瞄准的接缝（seam）：**
  - **接口约定：** 字段名、必填项、单位（毫秒还是秒）、枚举值、错误码。
  - **序列化：** JSON 里的大整数、时间格式、编码、空值和缺字段。
  - **配置与版本：** 默认值不同、依赖版本不匹配、功能开关。
  - **时间与失败：** 超时、重试、连接中断、对端慢。
- **真实又快的做法：**
  - **用真依赖，但在本机起：** Testcontainers 或 `docker compose` 起一个真 PostgreSQL，比内存里的假数据库多抓一类 SQL 方言和事务的 bug，启动只要几秒。
  - **只测接缝，不走全链路：** 一个集成测试只连两三个组件，其余的仍用替身。
  - **契约测试（contract test）：** 消费方把「我会怎么调用、期望什么回应」写成契约文件，提供方在自己的 CI 里对着契约验证。不用把双方同时部署起来，就能抓住字段改名这类问题。
  - **共享昂贵资源：** 数据库容器用 session 级 fixture 启一次，每个测试用事务回滚或独立 schema 隔离。
- **反面教材：** 集成测试里又把对端整个 mock 掉，它就退化成了一个更慢的单元测试，什么接缝都没测到。
