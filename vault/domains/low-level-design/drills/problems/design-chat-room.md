# Drill：聊天室（Chat Room）

一个**进程内**的简化聊天室：用户可以建群、私聊、发消息，能看到历史和未读数，也能看到谁在线、
谁正在输入。规模是几十个用户、几十个房间，全部状态留在内存里，不是分布式系统，也不落盘。照
真实机考的节奏分关来做，做完一关再看下一关。时间一律来自注入的时钟，代码里不许出现
`datetime.now()` 在业务逻辑里直接调用。

**分关要求**（每关做完再看下一关，像真实的机器编码轮）
- 第 1 关（约 15 分钟）：用户、房间、加入与离开、发消息、读历史。历史必须有一个**稳定的
  顺序**，写一个测试证明这个顺序是服务端收到消息的先后，而不是任何客户端能提供的时间信息——
  提示：你的 `send_message` 签名里根本不应该有一个可以传时间戳的参数。不是房间成员的人发消息
  或读历史要被拒绝。
- 第 2 关（约 12 分钟）：私聊要用**同一套**房间、消息、历史机制实现，不要为它单独建一个类或
  一套接口；反复对同一对用户调用建私聊的方法要返回同一个房间。每个用户在每个房间有一个已读
  游标；未读数从游标现算，不要单独维护一个计数字段——写一个测试证明自己发的消息不计入自己的
  未读数。
- 第 3 关（约 15 分钟）：定义一个"连接"的抽象，只需要一个方法（把一条消息交给这个在线的人），
  测试里用一个把收到的消息记进列表的假实现代替真实连接。发消息时只投递给当前在线的房间成员；
  离线成员重新上线后要能补上错过的消息——说清楚并测试这一步不需要任何新代码，只是把第 2 关的
  已读游标和历史接口组合起来用。在线状态和"正在输入"是临时状态，写一个测试证明它们从不出现在
  任何持久化的历史里。
- 第 4 关（选做）：给消息加编辑或删除，历史必须反映最新内容（删除后位置保留、内容清空）。判分
  点只有一个：这件事要不要碰第 3 关写的投递代码——写一个用例证明编辑或删除一条消息不会给在线
  成员产生新的投递。收尾：一个用户断开连接时，"正在输入"这个容器必须真的缩小——写一个用例证明
  断开连接之后，这个用户此前标记过"正在输入"的每一个房间都不再显示他。

**怎么练**：把 `vault/domains/low-level-design/problems/chat-room/starter.py` 的方法体补全，
然后在仓库根目录运行
`IMPL=starter uv run --with pytest python -m pytest vault/domains/low-level-design/problems/chat-room -q`。

**评分点**
- 消息顺序是服务端到达顺序，说得出为什么客户端时间戳不可靠、接口签名上就不给它可传（[[problems-chat-room-server-arrival-order]]）。
- 私聊是同一个 `Room` 类型上的一个字段而不是子类或独立接口，说得出继承在这里买不到任何多态好处（[[problems-chat-room-direct-room-is-a-flag-not-subclass]]）。
- 断线重连靠组合已读游标和历史查询，主动拒绝单独建一条"待推送"队列（[[problems-chat-room-reconnect-reuses-cursor]]）。
- 未读数是从游标现算的查询，不是一个可能和历史漂移的独立计数器（[[problems-chat-room-unread-derived-from-cursor]]）。
- 断开连接会清理这个人在所有房间的"正在输入"状态，用了一个反向索引而不是遍历全部房间（[[problems-chat-room-typing-shrinks-on-disconnect]]）。
- 连接抽象是一个只有一个方法的 `Protocol`，说得出为什么这里选结构化子类型而不是 `abc.ABC`（[[problems-chat-room-connection-protocol]]）。
- 编辑消息用 `dataclasses.replace` 生成新快照整体替换，`seq` 和位置不受影响（[[problems-chat-room-edit-preserves-position]]）。
- 私聊去重用 `frozenset` 做无序对的键，反复调用建私聊的方法保持幂等（[[problems-chat-room-dm-idempotent-index]]）。
- 三个核心类（消息、房间关系、在线状态）互不持有对方引用，协作时把依赖当参数传入。
- 回调/投递时不持有会阻塞其他成员的锁，一个成员的连接出问题不该拖垮其他成员的投递（[[patterns-observer-notify-lock]]）。
