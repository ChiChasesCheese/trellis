# Drill：活动推荐规则修复（Event Campaigns）

一个票务市场给客户发推荐活动：「离你近」「这个周末」「五十美元以下」。活动是一张分级列表，每一级是一条由小规则拼成的规则，运营改配置就能新建活动。规则重写后线上出了五个现象：分享了精确位置却按家推荐、周日的演出从不出现、售罄的便宜票被推荐、后发的客户拿到先发客户的演出、有些客户一场都收不到。
规模是五个规则类、两个组合子和一个推荐器；难点不在代码量，而在把现象对到缺陷、边界（含不含、差一微秒）和"同一个规则对象被所有客户共用"。

**分关要求**（每关做完再看下一关，像真实的机器编码轮）
- 第 1 关（约 15 分钟）：分诊。读 `starter.py`，把五个现象各对到一处缺陷，写成一张表；为每个现象先写一个会失败的测试（周日 19:00 的演出、便宜但售罄的票、两位客户共用一个规则、最早几场都在远处），确认它们在 `starter.py` 上失败。
- 第 2 关（约 15 分钟）：规则逐条符合定义。出发点优先级与缺失即不匹配，都市圈（含家城市、双向、不传递），`within_days` 两端含，周末窗口 `[周六 00:00, 下周一 00:00)`，价格严格小于且有货，`all_of` 与 `any_of` 的空集语义。每条规则写出"恰好等于"与"差一微秒"两个断言。
- 第 3 关（约 10 分钟）：推荐器。可推荐集合与排序、先匹配后截断、第一个命中的级别、对每位客户一样的兜底。用同一个活动先发给住西雅图的客户、再发给人在斯波坎的客户，交换顺序结果不变。
- 第 4 关（选做，约 5 分钟）：复用与书面回答。把一条别处写的规则放进组合子；八个线程用屏障共用一个推荐器；再回答三个问题：不改推荐器怎么加新规则、什么让规则可以安全复用、怎么试验未验证的信号、兜底怎么保证又怎么看得见。

**怎么练**：把 `vault/domains/low-level-design/problems/lcp-event-campaigns/starter.py` 里有缺陷的实现修好，然后在仓库根目录运行
`IMPL=starter uv run --with pytest python -m pytest vault/domains/low-level-design/problems/lcp-event-campaigns -q`。

**和编程智能体一起练**：用编程智能体（Claude Code 或工作区自带的智能体）打开 `starter.py`。第一条指令给十一条规则和你整理的"现象到缺陷"表，要求它先复述最容易漏的几条（周日、缺位置不是距离 0、先匹配后截断），不要让它直接动手；
然后一次只给它一个失败的测试，改完立刻运行全部测试。规则无状态、缺失即不匹配、周末窗口怎么算、先匹配后截断，这几个设计决定自己留着；要它解释每处改动对应哪个现象。不接受"把测试改成通过"，也不接受只靠题目给的那个例子验收，因为它在修复前的代码上也通过。

**评分点**
- 写得出开工前的合同：出发点与缺失、两个时间窗口的边界、价格同一张票、空组合子、先匹配后截断、人人一样的兜底（[[lcp-event-campaigns-contract-rules]]）。
- 说得清规则里该存什么、为什么冻结、为什么共用一个规则对象会串数据，以及缓存该放在哪（[[lcp-event-campaigns-state-and-invariant]]）。
- 知道不改推荐器怎么上线一条新规则，怎么用影子模式和随机小流量对照验证它，看哪些指标（[[lcp-event-campaigns-reflection-new-rule-and-trial]]）。
- 知道兜底的保证来自结构而不是某一级规则，怎么让它相关，怎么在分析里看见兜底率（[[lcp-event-campaigns-reflection-fallback-visible]]）。
- 写得出能抓住缺陷的测试：周日边界、恰好等于与差一微秒、换顺序复用同一个规则、最早几场都不相关（[[lcp-event-campaigns-contract-rules]]、[[lcp-event-campaigns-state-and-invariant]]）。
