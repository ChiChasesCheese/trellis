## Q
**功能开关服务（Feature Flag Service）**｜系统设计｜被报告 39 次 · Stripe · 最近 2026-10 · 先修见：新闻聚合信息流、图书比价代购平台、聊天与即时通讯系统、分布式限流器 · 模式：版本化规则与配置分发

设计一个功能开关服务：团队不用发布代码就能动态打开或关闭某个功能，支持按用户群（地区、套餐、百分比）做定向灰度，能快速回滚，能做 A/B 实验。峰值每秒 100 万次开关取值（flag evaluation），延迟要尽可能小。常见追问有：灰度百分比到底怎么分配（具体算法）；规则求值的数据结构；数据建模；客户端（浏览器、手机）怎么存开关数据、延迟和失败怎么处理；控制面故障时业务怎么办。

讲出：难点一句话、必讲的决策、取舍、级别期望。


## A
**一句话。** 100 万次/秒取值只能在业务进程内本地完成，重心不是高并发取值服务，而是把规则集可靠、快速、可回滚地分发到每个 SDK，并保证同一用户在同一开关上的结果稳定可复现。

**必讲。**
- **百分比灰度：** 随机数让同一用户时开时关，存每用户结果要 10 亿行表且改规则要迁移 → 稳定哈希：`开关key + 盐 + 用户ID` 哈希（MurmurHash3），对 10000 取模得桶号，小于 `百分比 × 100` 命中；无状态，各 SDK 一致；开关 key 进哈希使不同开关分桶独立，否则总是同一批用户当小白鼠。单调：5% 调到 20% 原命中用户不闪回，回滚到 5% 还是同一批；多变体把 0–9999 按权重切连续区间。
- **变更传播：** 十万 SDK 每 30 秒拉一次只有约 3,300 次/秒，CDN 吸收；推送只通知版本号，丢了无妨；2–20 MB 快照用 ETag 避免无变化下载并支持增量 → SDK 用新快照整体替换，同一请求内多次取值用同一份快照。
- **失败行为：** 控制面宕机 SDK 继续用内存里最后一份可用快照（fail static），新实例从 CDN 或本地磁盘取；从未加载成功用代码里写死的安全旧行为默认值，所以每个调用点必须带默认值 → 配置变更也要灰度：先推一小部分 SDK 监控错误率，回滚就是把当前版本指回旧版本。

**取舍。**
- 求值顺序：开关未启用 → 个人覆盖名单 → 按优先级首条命中规则 → 默认规则；前置依赖开关最先查并检测环；属性缺失视为不命中，各 SDK 语义要有跨语言一致性测试。
- 规则预编译成不可变内存对象，整份替换只换一个引用，取值无分配无锁。
- A/B 实验用独立盐的同一稳定哈希，互斥实验放同一层再分桶；曝光日志只记首次命中，不为每次取值记日志（100 万/秒的日志是更大的系统）。
- 不做取值微服务：每次一次网络往返要成百上千台机器，且成为所有业务的单点。
- 跨服务一致：入口求值一次把结果放请求头向下传，或日志里记快照版本。
- 控制面写入每天几千次，关系库加审计表足够，读走快照。
- 用户属性只在 SDK 本地求值不上传；开关带负责人和预期删除日期，防开关债务。

**级别。** 高级：稳定哈希与单调性、推加拉分发、fail static、算出 SDK 拉取量。资深：配置变更自身灰度回滚、版本化与增量、客户端隐私、实验平台与曝光日志、跨服务一致性、开关债务治理。
