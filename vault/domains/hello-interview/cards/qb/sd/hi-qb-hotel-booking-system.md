## Q
**酒店预订系统（Expedia 型聚合与自营）**｜系统设计｜被报告 45 次 · Amazon、Carta、Expedia、JPMorgan Chase、Meta 等 · 最近 2026-10 · 先修见：聊天与即时通讯系统、新闻聚合信息流 · 模式：先预留再确认与补偿、实体状态机与合法迁移、事务外盒与可靠发布事件、热点键与竞争、原子条件更新与防超卖

设计一个酒店预订系统：用户按城市、日期、人数搜索酒店，查看各房型每晚价格，下单预订，管理和取消订单。面试官通常把重点压在数据建模和 SQL 上：房态（availability）、按日定价、预订三张表怎么设计，怎样一条查询找出某日期范围内有房的酒店，怎样避免超卖。典型规模：1 亿日活用户，10 万家酒店，每家约 1000 间房，每天约 100 万笔预订。常见变体：房源和支付是外部服务，预订与支付可能不可用，要允许异步重试；酒店房态由外部系统每 30 分钟导出一次数据转储，或通过 webhook 与 API 推送，数据变更要在 15 分钟内反映，所以搜索可能看到过期房源；酒店需要审批预订并通过回调通知；预订保留（TTL）；高峰突发；预订过程中某个组件宕机怎么恢复；会议室预订的缩小版。

讲出：难点一句话、必讲的决策、取舍、级别期望。

## A
**一句话。** 读极多、写极少、写绝对不能超卖：搜索走可略微过期的预聚合索引，下单才对“房型 × 每晚”的库存行原子扣减；房态按房型和日期聚合存，不是一间房一行，否则 1000 间 × 365 天 × 10 万酒店是 365 亿行。

**必讲。**
- **库存建模：** 只存预订表用区间重叠算占用则每次搜索扫表；房型 × 日期计数行约 7.3 亿行可分片，下单是对 N 晚各加一 → 代价是没有具体房号，入住前再分配，少量场景用 PostgreSQL 区间排他约束 `EXCLUDE USING gist (room_id WITH =, daterange WITH &&)`。
- **防超卖：** 靠数据库而不是先查后写。悲观：按日期升序 `SELECT … FOR UPDATE` 避免死锁；乐观：单条 `UPDATE … SET reserved = reserved + 1 WHERE reserved < total`，影响行数必须等于晚数，否则回滚。按 `hotel_id` 分片，事务不跨片。
- **保留与支付：** 先保留库存，状态 HELD 带 10 分钟到期，扫描任务每 30 秒把过期的置 EXPIRED 并释放库存；支付用预授权加确认后扣款，回调迟到则重新尝试扣减，失败退款。
- **搜索路径：** Elasticsearch 出几百个候选，再查预聚合 `availability_summary(hotel_id, date, min_price, rooms_left)`，由库存变更事件异步刷新，允许几十秒过期；点进详情和下单时再向实时库存核验价格。

**取舍。**
- 热点酒店：事务缩短（支付放事务外）；单行每秒数百次更新是上限，更高就入口排队（虚拟等候室），或把库存拆成多个计数器子行，扣减随机挑有余量的，读时求和。
- 外部供应商用状态机 HELD → PAID → PENDING_SUPPLIER → CONFIRMED 加发件箱，不用两阶段提交；用预订 ID 作幂等键，超时进重试队列，用户看到“确认中”；对账任务修复不一致。
- 供应商同步：先进 Kafka，“来源时间戳更晚才覆盖”防乱序；30 分钟转储用差异导入。
- 超额预订：`reserved < total × (1 + ratio)`，是配置不是事务逻辑变化。
- 重复点击下单：唯一约束 `(user_id, 幂等键)`。

**级别。** 高级：房型 × 日期建模、预聚合搜索、乐观或悲观扣减、保留与支付两阶段、按酒店分片。资深：供应商同步与过期数据、状态机加发件箱恢复、热点排队、对账与供应商延迟监控。
