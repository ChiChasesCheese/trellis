## Q
**对话式 AI 聊天服务（简化版 ChatGPT）**｜系统设计｜被报告 9 次 · Plaid · 最近 2026-10 · 先修见：图书比价代购平台、聊天与即时通讯系统 · 模式：下游保护：熔断、隔离与扇出预算、限流算法与原子计数、实时推送与有状态连接、准入控制、排队与削峰、字节与元数据分离

设计一个类似 ChatGPT 的对话式 AI 系统：用户和模型进行自然语言多轮对话并收到逐字流出的回复。面试官明确要求"先做一个简单版本，支撑有限数量的用户"，所以重点是一条清晰、能跑通的主链路，再按追问扩展：上下文怎么保存与截断、流式输出怎么做、推理资源紧张时怎么排队、怎样限流和控制成本。

讲出：难点一句话、必讲的决策、取舍、级别期望。


## A
**一句话。** 聊天服务本身很薄（存消息、拼提示词、转发流），难点在昂贵且慢的大模型推理：回复要流式返回，一次生成占 GPU 几秒到几十秒，容量有限，所以要管理上下文长度、排队与限流，并能在流中途取消或失败后恢复。

**60 分钟路线。**

| 时间 | 做什么 |
|---|---|
| 0–5 分 | 容量：约 60 条/秒峰值、约 600 路并发流 |
| 5–10 分 | 对话、消息实体，一个 SSE 发送接口 |
| 10–25 分 | 网关 → 聊天服务 → 调度队列 → 模型副本，讲为什么用 SSE |
| 25–50 分 | 流式与取消、上下文截断、推理排队与并发上限 |
| 50–60 分 | 追问：按词元限流、故障恢复、自托管还是 API |

**必讲。**
- **流式与取消：** 一次生成几十秒，用户可能点停止或关页面 → 服务端检测 SSE 连接关闭后取消上游请求、释放 GPU，已生成部分以被中断状态存下 → 每路流设发送缓冲上限，客户端读得慢超限就断开（背压）。
- **上下文管理：** 每次请求都带历史，长度决定成本延迟 → 简单版用滑动窗口：每条消息存 `tokenCount`，从最新向前累加到预算（窗口上限减去输出预留）；摘要要多一次推理且有损，检索式记忆适合超长对话但最复杂。
- **推理容量与排队：** 连续批处理让一个副本同时处理几十路，但并发过高每路变慢、KV cache 耗尽 → 每副本并发上限 30–60 路，调度队列做准入，等待超过约 10 秒返回 `429`/`503` 与重试提示 → 600 路约需十几到几十个副本并留余量。

**取舍。**
- 按词元而不是请求数计量限流：每用户并发流 1–2 路、每分钟请求数、每日词元预算；输入输出内容审核放调度前后，每次生成的词元写计量表。
- 副本在生成中失败：已开始的流中断，让用户重试或自动重试一次，未开始的重新分配；标题用小模型、主对话用大模型。
- 前缀缓存：保持提示词前缀稳定、只往后追加，复用 KV cache 降低首词元延迟。
- 断线续传：生成内容先写 Redis 缓冲，重连带 `lastEventId` 补发；简单版只口述。
- API 上手快但成本限速由供应商定，自托管成本可控但要 GPU 运维；简单版先接 API。
- 重新生成加 `parentId` 形成分支树，简单版覆盖最后一条。

**级别。** 高级：SSE、上下文截断与词元预算、取消背压、推理容量估算、词元限流。资深：连续批处理与前缀缓存对容量的影响、摘要与检索取舍、模型路由与成本、断线续传、审核安全、多区域。
