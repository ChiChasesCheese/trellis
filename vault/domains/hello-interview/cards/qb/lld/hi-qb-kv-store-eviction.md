## Q
**设计可配置淘汰策略的内存键值存储（Redis-lite）**｜低层设计｜被报告 8 次 · Microsoft · 最近 2026-09 · 先修见：新闻聚合信息流 · 模式：策略模式：把变化点做成可替换部件、类设计中的并发：锁粒度与线程模型、数据结构选型：哈希表加链表、堆与有序结构

设计并实现一个内存键值存储：除了最基本的字符串，还要支持多种数据结构（列表、有序集合等）；容量满了以后能按不同的淘汰策略（LRU 最近最少使用、LFU 最不经常使用、按 TTL 过期时间）清出空间，而且策略要能在配置里切换；键可以设置过期时间。进阶版本要求支持事务。面试官看重的是：存储层、数据结构层、淘汰策略三者是否解耦（接口与策略模式），以及你能不能把 LRU/LFU 做到 O(1)。

讲出：难点一句话、必讲的决策、取舍、级别期望。


## A
**一句话。** 把数据放哪里、每种数据结构怎么操作、满了赶走谁拆成三个互不知道内部的部件，用接口粘起来；淘汰策略只回答一个问题：谁是下一个受害者。

**60 分钟路线。**

| 时间 | 做什么 |
|---|---|
| 15–45 分 | 写策略接口、LRU、`KVStore` 的惰性过期和淘汰 |
| 50–60 分 | 追问：O(1) 的 LFU、TTL 策略、数据结构层、事务 |

**必讲。**
- **O(1) 的 LRU/LFU：** LRU 用 `OrderedDict`（哈希表加双向链表），`move_to_end` 和取第一个都是 O(1)；LFU 天真地找最小频次要 O(n) 或 O(log n) → 用「频次 → 该频次 key 有序集合」加记住最小频次，访问时把 key 从 f 桶挪到 f+1 桶，原桶空且是最小频次则最小频次加一；同频次淘汰最老的 → 两者共用接口，`KVStore` 不关心是哪种。
- **淘汰与过期是两回事：** 过期是到点就该消失，淘汰是内存不够主动牺牲 → 惰性（访问时检查）加主动（后台每次抽样约 20 个，过期比例高就再抽，Redis 做法）并用：只惰性会泄漏内存，只主动则读到过期数据的窗口无法避免。
- **并发：** 一把全局锁，实现简单、事务天然隔离，像 Redis 单线程模型；`get` 也要写锁，因为读会改 LRU 顺序和 LFU 频次 → 分段锁并发度高，但淘汰变成段内近似，跨段事务要固定加锁顺序。

**取舍。**
- TTL 策略用小根堆，旧记录留在堆里，堆顶与真实过期时间不符就丢弃（惰性删除）。
- LRU 被一次性大扫描冲刷热数据；LFU 抗扫描但新数据易被立刻淘汰、旧高频不衰减，实用版加衰减或 TinyLFU 准入。
- 精确 LRU 的链表在高并发下是热点，Redis 随机抽样 N 个淘汰最久未用的。
- 容量按键数最简单，但一个有序集合可能有百万成员，真实做法是每个值 `size_of()` 并循环淘汰到上限以下。
- 事务：提交前只缓冲，提交时同一把锁内执行；首次触碰 key 存快照，出错按快照还原；事务里插入触发的淘汰不回滚，要写明；乐观事务用版本号（WATCH）。
- 有序集合用字典加有序列表 `zadd` O(n)，生产用跳表 O(log n)；淘汰粒度是 key，不是元素。

**级别。** 高级：策略接口解耦、O(1) LFU、惰性加主动过期、时钟注入、线程安全。资深：事务快照回滚与淘汰交互、按字节计容量、分段锁与近似 LRU、抗扫描 LFU、开闭原则。
