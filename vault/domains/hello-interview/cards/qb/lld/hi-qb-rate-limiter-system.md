## Q
**限流器（单机类设计）**｜低层设计｜被报告 2 次 · Amazon · 最近 2026-10 · 先修见：可配置淘汰策略的内存键值存储 · 模式：限流算法与原子计数、策略模式：把变化点做成可替换部件、类设计中的并发：锁粒度与线程模型、时间注入与可测试性

设计一个限流器：在 T 秒内最多允许某个调用方发起 N 个请求，超出的请求被拒绝。要求支持多种限流算法（固定窗口、滑动窗口、令牌桶等），可以按用户或 API Key 分别限流，线程安全，算法可以替换而不改调用方。这是类与接口层面的设计题，和"分布式限流器"那道系统设计题不同——这里关心的是类怎么划分、状态怎么放、并发怎么处理、怎样写出能测试的代码。

讲出：难点一句话、必讲的决策、取舍、级别期望。


## A
**一句话。** 策略模式的典型题：把算法做成可替换的、只管单个 key 的状态机，把按 key 管理和并发放在外层，并让时间可以注入，代码才好测。

**60 分钟路线。**

| 时间 | 做什么 |
|---|---|
| 0–8 分 | 问清算法种类、按什么 key、要不要剩余额度，定 `Decision` 和 `allow(key)` |
| 8–13 分 | `Limiter` 策略、`RateLimiter` 入口、per-key 锁 |
| 13–43 分 | 写三种算法和 `RateLimiter` |
| 48–60 分 | 追问：内存回收、多规则、权重、分布式 |

**必讲。**
- **并发正确性：** 先读计数再写回，多线程各读到旧值双双放行 → per-key 锁，让读状态、判定、写状态成一个临界区 → 全局锁所有 key 串行，CAS 对多字段状态要打包成不可变对象再整体 CAS，复杂；选 per-key 锁，且从不同时持全局锁和 key 锁，避免死锁。
- **算法取舍：** 固定窗口最便宜但有边界突发；滑动窗口日志最准但内存随 N 线性增长；滑动窗口计数（当前与上一窗口两个计数按重叠加权）内存 O(1)、误差小；令牌桶允许突发，是 API 限流默认选择 → 严格每 T 秒不超 N 用日志，平均速率受限允许突发用令牌桶；先实现一种，说出其他差别。
- **时间源：** 用单调时钟 `time.monotonic`，墙钟被 NTP 调整会回退，令牌变负 → 时钟作为构造参数注入，测试用可拨动的假时钟，不用 `sleep`。

**取舍。**
- 内存：`_entries` 对每个出现过的 key 留一份，用户输入的 key 会无限增长；记录最后访问时间惰性清理或用带上限的 LRU 字典，不活跃后状态等价于初始，删除不影响正确性。
- 多规则（每秒 10 次且每分钟 100 次）：`CompositeLimiter` 全部通过才放行，先检查后统一扣，避免一个拒绝时已通过的被扣减。
- 带权重：`try_acquire(now, cost=1)`，令牌桶直接扣 `cost`。
- 多实例要共享状态，Redis 加 Lua 保证原子，`Limiter` 接口不变。
- 想等到有配额再执行，在 `retry_after` 之上封装睡眠加重试。
- 并发测试多线程对同一 key 调 N+M 次，放行数恰好 N。

**级别。** 高级：策略模式、per-key 锁、单调时钟与注入、算法取舍。资深：内存回收、权重与多规则、单机到分布式接口不变、并发测试、性能分析。
