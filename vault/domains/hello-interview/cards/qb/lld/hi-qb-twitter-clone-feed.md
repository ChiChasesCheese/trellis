## Q
**微博客与个性化信息流（Twitter）**｜系统设计｜被报告 1 次 · Headout · 最近 2026-06 · 先修见：新闻聚合信息流、聊天与即时通讯系统、分布式任务调度器（含 cron 与一年执行历史） · 模式：写扩散与读聚合、缓存、失效与一致性窗口、排序、排行榜与 Top-K

设计一个类似 Twitter 的社交平台：用户可以关注和取消关注其他用户、发布推文（tweet），并查看由所关注的人的推文组成的个性化主页时间线（home timeline）。需要给出关注关系、发推、读时间线三条主链路的设计，并回答明星用户（粉丝上千万）发推时怎么办、时间线怎么分页、读写负载怎么扩展。

讲出：难点一句话、必讲的决策、取舍、级别期望。


## A
**一句话。** 读远多于写，且存在一个人对应千万读者的扇出问题：难点是选写时扇出还是读时聚合，并为粉丝极多的账号单独处理，让发推延迟、读延迟和存储成本都可控。

**60 分钟路线。**

| 时间 | 做什么 |
|---|---|
| 0–5 分 | 数字：峰值读约 23 万次/秒，写时扇出约 200 亿条/天，读写比约 40 比 1 |
| 5–10 分 | 推文、关注、时间线接口；游标用推文 ID 不用页码 |
| 10–25 分 | 发推 → Kafka → 扇出 Worker → 时间线缓存；读时间线；关注存两份 |
| 25–50 分 | 写时扇出、读时聚合与明星用户混合；缓存、游标、重建 |
| 50–60 分 | 追问：分片、扇出可靠性、缓存存什么、排序、降级 |

**必讲。**
- **扇出策略：** 读时聚合关注 500 人就是 500 次查询，读是主要负载；写时扇出写放大平均 200 倍，3000 万粉丝一条推文就是 3000 万次写、几十分钟才推完 → 混合：普通用户写时扇出，粉丝超阈值（如 10 万）的大 V 不扇出，读时拉取我关注的大 V 最新推文并合并 → 大 V 通常只有几个到几十个，且推文是被所有粉丝共享的热数据；只给近 30 天活跃用户写缓存进一步压写放大。
- **时间线存储与分页：** Redis 有序集合按推文 ID 排序，限 800 条 → 客户端带上一页最后的 ID，返回小于它的前 20 条，合并大 V 推文也用同一游标归并 → 缓存丢失（新用户、淘汰、节点故障）用读时聚合重建并回填，是正确性兜底。

**取舍。**
- 分片：推文库按推文 ID 分片；关注正向表按 `followerId`、反向表按 `followeeId`；媒体走对象存储加 CDN。
- 扇出 Worker 水平扩展，Kafka 按作者 ID 分区，每批几千粉丝，失败重试，有序集合里同一 ID 只一份所以幂等；活跃粉丝优先。
- 删除：推文库标记，读时过滤，不清每个粉丝的缓存。
- 缓存只存 ID 省空间且删改只改一处，再加热推文内容缓存。
- 排序加推荐时先取几百候选再模型打分；关注后立刻可见靠回填或读时合并。
- Redis 节点挂掉，该分片用读时聚合降级，延迟升高功能不丢。

**级别。** 高级：混合扇出与阈值理由、缓存只存 ID 并裁剪、游标分页、容量估算。资深：写放大量化、活跃优先、缓存重建、排序漏斗、分片、删除与受保护账号、降级。
