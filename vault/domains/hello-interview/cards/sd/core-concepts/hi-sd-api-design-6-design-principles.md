## Q
**API 设计的九条原则**｜系统设计 · 核心概念

面试官评价一个 API“干净”，是在对照哪些原则？请说出这些原则，并说明重试、分页、版本演进、错误响应各应怎么处理。

## A
**九条原则。**
1. 围绕资源而非动作设计
2. 处处一致：命名、参数名、响应结构（别一处 `status` 一处 `state`）
3. 最小惊讶：GET 不改数据，200 就是成功，不要在 200 里包着“失败”
4. 无状态：每个请求自带认证令牌、参数、载荷，任何服务器都能处理，水平扩展就只是负载均衡的事（JWT 流行的原因之一）
5. 重试安全：POST 创建重要资源时用幂等键
6. 凡会增长的集合都分页，并限制单页上限，防止 `?limit=100000`
7. 默认安全：每个端点默认需要有效令牌，授权要确认调用者能操作这个具体资源，再配限流
8. 演进时不破坏客户端：加字段安全，改名、删除、改语义是破坏性变更，需要版本策略
9. 错误可操作：4xx 与 5xx 分清，再加机器可读的错误码和人可读的信息

**取舍。** 版本化通常用 URL（`/v1/events`），明确、好解释；请求头版本更干净但不直观。错误体用统一信封，如 `{"error": {"code": "SEAT_UNAVAILABLE", "message": "..."}}`，客户端按 code 分支。

**易错。** 不要罗列原则，要在具体决定里说出来，例如“这里用幂等键，重试就不会重复订座”。
