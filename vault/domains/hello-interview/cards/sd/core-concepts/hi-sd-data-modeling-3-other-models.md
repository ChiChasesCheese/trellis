## Q
**四种非关系型模型：何时才选**｜系统设计 · 核心概念

文档、键值、宽列、图数据库各适合什么场景，对数据建模有什么影响？面试里哪个最该避免？

## A
**要点。**
- 文档型（MongoDB、Firestore）：模式灵活，把相关数据嵌套在文档内，减少 join，要更激进地反范式化。适合模式经常变、嵌套深、记录结构差异大。但面试的需求固定，几乎没有演进的模式，只有面试官明确说结构常变时才考虑。
- 键值（Redis、DynamoDB）：只按精确键查找，极快但查询能力弱。适合缓存、会话、功能开关，或高写入且只按单一标识查找。模式很扁平，要为不同访问模式在多个键下重复存数据，读好但更新时一致性差。实际常与 SQL 搭配：SQL 作为事实来源，前面放键值缓存。
- 宽列（Cassandra、HBase）：行键是（分区键，时间戳），同分区的行存在一起，写入就是追加，读是扫描连续范围。适合巨量写入、时序、遥测、日志、IoT，设计围绕查询模式，时间是一等公民。
- 图（Neo4j、Neptune）：节点与边，擅长遍历关系。

**易错。** 图数据库是面试中的常见错误，听着高级却增加不必要的复杂度。Facebook 的社交关系存储（TAO）和 Twitter 的关注关系都建在 MySQL 上。
