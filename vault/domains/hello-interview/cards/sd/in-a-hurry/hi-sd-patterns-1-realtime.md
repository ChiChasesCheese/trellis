## Q
**模式：推送实时更新**｜系统设计 · 速成

聊天、通知、实时看板需要把更新推给用户。协议和服务端各怎么选？默认从什么开始？

## A
**要点。** 协议选项：HTTP 轮询（最简单，但效率低）、SSE 和 WebSocket（专为实时设计，但基础设施不好搞）。建议从 HTTP 轮询开始，直到它不够用再考虑 SSE 或 WebSocket。

服务端有两类：发布订阅（Pub/Sub）服务把发布者和订阅者解耦（聊天类题目常用）；一致性哈希环等有状态服务器，适合处理较重的场景（协作文档类题目）。

**为什么。** 同步 API 在请求完成时返回结果即可；只有聊天、通知、实时看板这类需要在事件发生时主动推送。

**取舍。** SSE 单向，足够覆盖服务端下推；WebSocket 双向，但长连接的基础设施成本高。

**使用时机。** 题目出现「用户要立即看到变化」时才引入，否则从轮询起步。
