## Q
**预留放 Redis、库存放 MySQL 的缺口**｜系统设计 · 真实案例

电商结账要做防超卖（oversell protection）：付款时先预留库存几分钟，付款成功再永久扣减。预留计数放 Redis、商家真实库存放 MySQL，会出什么问题？两阶段提交或发件箱为什么也补不上？

## A
**要点。** 付款成功要做两件事：在 MySQL 扣库存，在 Redis 清除预留。两个库不能一起提交。
- 先改 MySQL 再崩溃：购买已完成，Redis 仍认为这些单位被预留，把其实可用的库存藏起来。
- 先清 Redis 再崩溃：预留被释放、单位重新可卖，但 MySQL 还没扣，已经卖掉的库存被再卖一次。
调换顺序只是改变会出哪种错，两次写入之间的窗口还在。

**为什么。** 两阶段提交（2PC）需要两个库参与同一个协调协议，Redis 做不到。发件箱（outbox）或对账任务最终能发现并修复不一致，但在修复之前库存是错的；闪购中短暂的错误就可能把同一个单位卖两次。

**数字。** 这个系统处理美国电商的 14% 以上订单，罕见的错误在这个规模下也会变成常态。

**易错。** Redis 作为并发机制没毛病（单线程保证两个买家抢不到同一最后一件）；它被淘汰是因为无法加入账本的事务。
