## Q
**类设计中的并发：锁粒度与线程模型 (Locking / Thread-safety)**｜跨题模式 · 对比

八道题都要回答并发，但共享状态不同，选的锁粒度或模型也不同。请逐题说明。

## A
| 题 | 在这里怎么用 | 为什么和别的题不同 |
|---|---|---|
| [[tt-per-merchant-rate-limit\|按商户限流]] | 按商户名哈希分段加锁，令牌桶惰性补充，LRU 的访问也在锁内 | 几十万商户下，分段锁的粒度与 LRU 的内存上限要一起考虑；不同商户尽量不互相阻塞 |
| [[rate-limiter-system\|限流器（单机类设计）]] | 单个 key 的状态用 per-key 锁保护，外层 key 管理另有一把短锁 | 两层锁的顺序是死锁来源，所以先释放外层锁再取内层锁，明确层次 |
| [[kv-store-eviction\|可配置淘汰策略的内存键值存储]] | 一把全局锁，淘汰与数据结构操作在同一临界区，事务在同一把锁内顺序执行 | `get` 也会改变淘汰顺序，所以也要拿写锁，读写锁对 LRU 收益有限；分段锁是下一步，跨段事务要固定加锁顺序 |
| [[recently-viewed-items\|"最近浏览"记录]] | 每客户一个 LRU，客户锁用分段锁，外层字典的结构变化另用一把极短的锁 | 锁保护的是单客户的小结构，竞争很低；客户被淘汰时的竞态对尽力而为的数据可接受 |
| [[api-circuit-breaker\|熔断器]] | 状态迁移在锁内，调用下游不持锁，迟到的旧结果靠状态代号丢弃 | 关键陷阱是不持锁调用下游，以及半开期的惊群（只放少量探测） |
| [[event-ticket-booking\|活动票务预订后端]] | 悲观锁、乐观版本号、带条件的原子更新三选一，慢的付款调用放在事务之外 | 并发控制落在数据库，而不是进程内锁；内存版的 `TicketType` 只用一把锁保护检查加占位 |
| [[elevator-design\|电梯系统]] | 所有状态变化收在一个调度线程里，外部线程只往线程安全的队列放请求对象 | 用线程封闭代替锁（单写者原则），是并发的另一种答案 |
| [[multithreaded-logging-framework\|多线程日志框架]] | 单个写线程代替多线程写同一文件加锁，三级有界队列，保证顺序和批量刷盘 | 并发模型本身就是设计：专职线程加有界队列，而不是给共享文件加锁 |

**共同点：** 先找唯一的共享状态，再选最小的保护。**差异来自状态的形状：** 海量独立 key 用分段，读也改状态的结构用写锁，要调慢下游就不持锁，顺序事件流用线程封闭，跨进程用数据库。
