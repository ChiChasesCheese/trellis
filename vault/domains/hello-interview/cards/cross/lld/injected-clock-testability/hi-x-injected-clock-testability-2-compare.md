## Q
**时间注入与可测试性**｜跨题模式 · 对比

限流器、按商户限流、任务调度器、熔断器、日期时间库、股价提醒这几道设计题都依赖时间，各自怎样注入和使用时钟，测试的重点有什么不同？

## A
| 题 | 在这里怎么用 | 为什么和别的题不同 |
|---|---|---|
| [[rate-limiter-system\|限流器（单机类设计）]] | 单调时钟作为构造参数注入，入口每次判定读一次时间传给具体算法 | 令牌补充与窗口滑动全部依赖时间，所以是最典型的场景；测窗口边界、突发后的恢复、不同 key 隔离 |
| [[tt-per-merchant-rate-limit\|按商户限流]] | 惰性补充只在 allow 时读时间，补充量取 max(0, 现在 − 上次)，时钟回拨补 0 | 没有定时器和后台线程，只要注入时钟就能确定性地测试；还要测回拨不产生负令牌 |
| [[scheduler-system-design\|设计任务调度器（定时、周期、带优先级）]] | 计时堆依赖当前时间，另提供 run_pending(now) 同步推进，测试里拨假时钟 | 触发时间是绝对时刻，默认读墙钟；还要覆盖时区与夏令时，是日期库的消费者 |
| [[api-circuit-breaker\|熔断器（Circuit Breaker）]] | 打开后的冷却时间和半开期探测都依赖时间，用假时钟拨过去 | 测试重点是并发下的状态迁移（半开只放一个探测），不仅是时间 |
| [[date-time-management\|设计日期时间库（Date and Time Library）]] | 把时间点、墙上读数和时区规则分开，当前时间由可注入的 Clock 提供 | 它是提供时间抽象的库本身，夏令时的间隙与重叠要有正确性验证 |
| [[stock-price-alerts\|股票价格提醒系统]] | 用历史报价回放测试滞回与冷却，断言每个上穿事件最多触发一次通知 | 时序行为是产品行为的一部分，冷却期和滞回要精确验证 |
