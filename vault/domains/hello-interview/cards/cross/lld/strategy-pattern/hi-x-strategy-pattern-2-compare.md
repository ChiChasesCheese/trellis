## Q
**策略模式：把变化点做成可替换部件**｜跨题模式 · 对比

停车场、限流器、键值存储淘汰、电梯、计费引擎、任务调度器、职位搜索这七道低层设计题都用到策略。每道题里策略回答的问题是什么，形态有什么不同？

## A
| 题 | 在这里怎么用 | 为什么和别的题不同 |
|---|---|---|
| [[parking-lot-system\|停车场管理系统]] | 车位分配（最近优先，每种车位类型一个按距离排序的堆）和计费规则（阶梯）是两个可替换的策略；车型到车位的兼容关系用表，不用继承 | 两个变化点各自独立，策略只回答选哪个车位、收多少钱；车位的占用释放由门面在锁内保护 |
| [[rate-limiter-system\|限流器（单机类设计）]] | 固定窗口、滑动窗口日志、令牌桶是可替换的状态机，只管单个 key；外层管按 key 的锁和映射 | 策略有状态，所以并发（per-key 锁）和时间源（注入单调时钟）必须在策略边界上定义清楚 |
| [[kv-store-eviction\|设计可配置淘汰策略的内存键值存储（Redis-lite）]] | 数据存储、数据结构操作、淘汰策略三个部件互不知道对方内部，淘汰策略只回答谁是下一个受害者 | 淘汰策略要能在运行时切换（用现有键重建新策略），还要区分淘汰与过期是两回事 |
| [[elevator-design\|设计电梯系统（面向对象，可运行的代码）]] | 单部电梯用 LOOK 扫描决定路线，多部电梯由可替换的调度器用代价函数挑一部 | 策略分两层：单梯的路线策略和多梯的分配策略；分配一旦做出就不再改派 |
| [[tt-billing-tax-engine\|计费 / 计税引擎]] | 规则是可调用对象排成链，加一种费用或税不改引擎，封顶和保底用装饰器包装 | 规则按顺序组合（税在费用后面），并且规则集带生效时间的版本 |
| [[scheduler-system-design\|设计任务调度器（定时、周期、带优先级）]] | 「下一次什么时候触发」抽象为触发规则（一次、固定频率、cron），统一周期任务 | 策略产出的是一个时间，不是一个选择，要和定时堆配合 |
| [[job-board-platform\|招聘信息平台（Job Board）]] | 搜索条件用规格模式（Specification）组合，新增筛选项不改搜索主流程 | 策略是可用与、或组合的布尔条件，不是互斥的单选 |
