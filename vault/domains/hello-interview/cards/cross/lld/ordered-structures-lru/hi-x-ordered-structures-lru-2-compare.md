## Q
**数据结构选型：哈希表加链表、堆与有序结构**｜跨题模式 · 对比

键值存储淘汰、最近浏览、按商户限流、任务调度器、电梯、Top-K 榜这六道设计题都在选「按顺序取最小或最旧」的结构。每题用哪种结构、为什么不同？

## A
| 题 | 在这里怎么用 | 为什么和别的题不同 |
|---|---|---|
| [[kv-store-eviction\|设计可配置淘汰策略的内存键值存储（Redis-lite）]] | LRU（有序字典）、LFU（频次桶加最小频次）、TTL（小根堆加惰性删除）三种策略，都做到 O(1) 或 O(log n) | LFU 需要频次桶，Redis 的近似做法是随机采样；淘汰与过期是两回事，二者要并用 |
| [[recently-viewed-items\|设计"最近浏览"记录（类似 LRU 缓存，上限在构造时给定）]] | 每个客户一个定长 LRU：重复浏览是摘下来放队尾，超限丢队头；「第一个唯一值」用同样的思路 | 客户数量巨大时内存是追问（外层再套一层 LRU）；真实系统用 Redis 有序集合，上限可在运行时调整 |
| [[tt-per-merchant-rate-limit\|按商户限流]] | 按访问顺序排序的哈希表（LRU）限制几十万个令牌桶的内存上限 | 被淘汰的是不活跃商户的桶，丢了可以重建成满桶；若淘汰时桶没补满，会多得一次突发 |
| [[scheduler-system-design\|设计任务调度器（定时、周期、带优先级）]] | 按触发时间排序的最小堆，取消用惰性删除，就绪队列按优先级排序 | 惰性删除会在堆里积累垃圾，已取消条目超过一半就重建堆；时间堆与优先级队列分成两级 |
| [[elevator-design\|设计电梯系统（面向对象，可运行的代码）]] | 每部电梯分方向维护待停楼层的集合，沿方向走到最远的请求再掉头 | 结构服务于扫描策略，每个时间片扫描集合找前方请求，成本由待停靠站数决定 |
| [[top-k-counts\|Top-K 热门榜（视频播放、歌曲、话题标签）]] | 各分片用有序集合或堆维护前 K，再归并；对象按 ID 分区，所以全局前 K 必在各分片前 K 的并集里 | 规模大到要用近似结构（计数最小草图加大小为 1000 的候选堆），不再用精确的有序结构 |
