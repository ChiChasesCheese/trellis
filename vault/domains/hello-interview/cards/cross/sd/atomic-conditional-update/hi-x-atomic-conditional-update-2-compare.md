## Q
**原子条件更新与防超卖**｜跨题模式 · 对比

活动票务、酒店预订、秒杀抢票、众筹购股、钱包扣款、股票下单、停车场、生鲜订阅这几道设计题都用到“检查加占住不可分”，各自的资源是什么，原子手段和需要额外处理的点有什么不同？

## A
| 题 | 在这里怎么用 | 为什么和别的题不同 |
|---|---|---|
| [[event-ticket-booking\|活动票务预订后端（防超卖的 REST 服务）]] | 比较悲观锁、乐观版本号、条件更新三种，选一条条件更新同时检查和占住库存 | 库存计数不放 Redis，真相在数据库；释放需要幂等保护 |
| [[hotel-booking-system\|酒店预订系统（Expedia 型聚合与自营）]] | 对“房型 × 每个晚上”的库存行原子扣减，多晚要在同一事务里全部成功 | 数据模型是按房型和日期聚合的行，一间房一行会有 365 亿行 |
| [[tt-flash-sale-ticketing\|秒杀抢票（排队、限流、防超卖）]] | 先准入，再用 Redis 脚本做闸门，数据库条件更新做最终真相 | 库存很小（如 10 件）时准入缩到约 20 人，数据库条件更新甚至行锁就够 |
| [[crowdfunding-share-purchase\|设计限时众筹购股系统（用账户余额抢固定数量的公司股份）]] | 全局有限股份用 Redis 脚本原子扣减，数据库为真相，Redis 崩溃后按公式重算 | 库存争用还要和单人限购、外部余额服务的恰好一次扣款一起设计 |
| [[tt-wallet-ledger-service\|钱包与复式账本服务（余额、冻结、转账、多币种）]] | 同一用户同时两笔消费、余额只够一笔，条件更新一个成功另一个影响行数为 0 | 只有退款路径能把余额打成负，消费路径永不允许透支 |
| [[stock-trading-platform\|设计简化版股票交易平台（券商端，限价单）]] | 下单时用条件更新冻结资金或持仓，防止同一笔钱被占用两次 | 市价单冻结金额要用保守估价，成交后才结转 |
| [[parking-lot-system\|停车场管理系统]] | 车位的分配与释放在同一把锁内完成，离场先缴费成功才释放 | 内存里的类设计，原子性靠锁或 CAS 而不是数据库；重复离场不能二次释放 |
| [[grocery-subscription-orders\|生鲜订阅转订单服务]] | 库存与余额用条件更新，每个用户一把锁让检查与扣减在同一临界区 | 同一用户的多个订阅同时转订单是它特有的竞争场景 |
