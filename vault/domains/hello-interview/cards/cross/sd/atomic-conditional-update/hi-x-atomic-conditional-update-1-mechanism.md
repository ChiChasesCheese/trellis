## Q
**原子条件更新与防超卖**｜跨题模式 · 共性

库存、余额、车位这类有限资源，并发抢占时为什么不能“先查够不够，再扣减”？原子条件更新（conditional update）是怎么同时完成检查和占住的？

## A
**问题。** 先读后写有时间窗口：两个请求同时读到“还剩 1 件”，各自扣减，结果超卖或余额变负。加长锁能解决，但热点计数器上所有请求排队，付款这类慢的外部调用更不能放在锁里。

**机制。** 把“检查够不够”和“占住”合成一个不可分的动作：

- 数据库：`UPDATE ... SET stock = stock - n WHERE stock >= n`，看影响行数，为 0 就是不够，失败是一个明确结果而不是异常；
- 乐观版本号：`WHERE version = ?`，冲突就重试；
- Redis 脚本或内存里的锁、CAS：同样让检查与扣减不可被打断。

**共同的不变量。** 任何时刻 已占用 + 已保留 ≤ 总量，余额不会为负；检查与占住不可分；真相落在持久层；慢的外部调用放在这个原子动作之外，用状态和幂等键衔接。

**不用它会怎样。** 开售瞬间数万人同时请求，同一份库存被卖给多个人，或同一笔钱被占用两次。
