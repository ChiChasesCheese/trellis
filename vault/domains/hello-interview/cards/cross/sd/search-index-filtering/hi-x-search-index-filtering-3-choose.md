## Q
**检索：倒排索引、预聚合搜索与过滤**｜跨题模式 · 怎么选

面对新的搜索设计题，怎样决定索引放哪里、多新鲜、什么时候回到真相？列出判断信号，每个分支给一个例子。

## A
| 信号 | 选择 | 例子 |
|---|---|---|
| 数据量小（几千到几万条），筛选条件会不断新增 | 内存倒排索引加规格模式；规模上去后翻译成搜索引擎的过滤器，接口不变 | [[job-board-platform\|招聘信息平台（Job Board）]] |
| 库存、价格不能错，但搜索量远大于下单量 | 预聚合摘要，下单与进详情时核验，一致性只放写路径 | [[hotel-booking-system\|酒店预订系统（Expedia 型聚合与自营）]] |
| 搜索结果来自按调用计费的外部系统 | 缓存、合并请求、预热热门航线，最终价格推迟到点击时 | [[flight-search-system\|设计机票搜索系统（多供应商聚合，按调用计费）]] |
| 内容由商家持续更新，要近实时可见 | 事件流写索引，版本保序，易变字段从缓存覆盖 | [[merchant-product-listings\|商家商品上架与更新系统]] |
| 历史很长，或内容受加密约束 | 单独的搜索索引，只索引近期或自己相关的部分；端到端加密则无法服务端搜索 | [[messenger-chat-system\|设计聊天/即时通讯系统（WhatsApp / Messenger）]] |
| 同一事件有多个来源 | 摄取阶段聚类去重，查询阶段只展示代表项 | [[news-aggregator-feed\|设计新闻聚合系统（Google News）]] |

过滤条件走过滤器（不计分），关键词走相关性评分；先问「搜索结果过期一分钟的代价是什么」，再决定下单处要核验多少。
