## Q
**检索：倒排索引、预聚合搜索与过滤**｜跨题模式 · 对比

酒店预订、机票搜索、商品上架、职位平台、聊天历史搜索、新闻聚合这六道设计题都有「搜索」一环。它们的索引由什么驱动、瓶颈在哪里、有什么特有的取舍？

## A
| 题 | 在这里怎么用 | 为什么和别的题不同 |
|---|---|---|
| [[hotel-booking-system\|酒店预订系统（Expedia 型聚合与自营）]] | 搜索走预聚合的酒店摘要，准确库存到下单时才对「房型 × 日期」行做条件扣减 | 明确接受搜索结果过期，并要能回答「为什么搜索不直接查库存表」 |
| [[flight-search-system\|设计机票搜索系统（多供应商聚合，按调用计费）]] | 多供应商聚合的结果经缓存和请求合并返回，弹性日期与日历视图靠缓存和预计算 | 瓶颈是按调用计费的供应商，不是索引本身；价格确认推迟到点击行程 |
| [[merchant-product-listings\|商家商品上架与更新系统]] | 商品更新经 CDC 和事件流写进搜索索引，关注索引多快跟上 | 搜索只是众多派生视图之一，更新顺序（版本）决定最终正确性；价格库存从缓存覆盖，不为改价重建文档 |
| [[job-board-platform\|招聘信息平台（Job Board）]] | 用规格模式（Specification）组合搜索条件，内存倒排索引足够，规模大时换专用搜索引擎 | 这是类设计：重点是新增筛选项不改搜索主流程，以及过期用 expires_at 判断而不依赖定时任务 |
| [[messenger-chat-system\|设计聊天/即时通讯系统（WhatsApp / Messenger）]] | 长期历史的搜索（5 年、可搜索）是变体：近期留消息库，老数据归档，全文搜索单独建索引 | 端到端加密后服务端只存密文，无法做服务端搜索，是特有的权衡 |
| [[news-aggregator-feed\|设计新闻聚合系统（Google News）]] | 新闻按分类存取，同一事件的多家报道用 simhash 聚类，只展示簇的代表文章 | 聚类决定展示什么，是摄取阶段的任务，不是查询阶段；只和同分类近 48 小时的簇比较 |
