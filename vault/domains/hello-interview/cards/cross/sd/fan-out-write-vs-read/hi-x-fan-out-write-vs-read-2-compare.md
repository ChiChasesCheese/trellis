## Q
**写扩散与读聚合**｜跨题模式 · 对比

微博时间线、社交信息流、新闻聚合、聊天群消息、通知群发、股价提醒、拍卖价格推送，这七道题都要「一对多」地送达内容。它们各自选了写扩散还是读聚合，扇出的对象是什么，为什么不同？

## A
| 题 | 在这里怎么用 | 为什么和别的题不同 |
|---|---|---|
| [[twitter-clone-feed\|微博客与个性化信息流（Twitter）]] | 普通用户写时扇出到粉丝的 Redis 时间线，明星用户读时再拉后合并 | 时间线存 ID 的有序集合并限长；核心是粉丝数极不均匀下的发推延迟和存储成本 |
| [[social-feed-generation\|社交信息流生成系统（News Feed）]] | 普通作者推进收件箱，名人读时拉，排序与广告放在读取时对几百个候选做 | 更强调排序放哪里、已读去重、分页稳定；排序放读时，换模型不用重写收件箱 |
| [[news-aggregator-feed\|设计新闻聚合系统（Google News）]] | 同一分类全员共享，读时对几个分类的有序集合归并，几乎全靠缓存 | 读者共享同一份内容，反而选读聚合：写扩散会让每篇文章要写很多份 |
| [[messenger-chat-system\|设计聊天/即时通讯系统（WhatsApp / Messenger）]] | 群消息给每个成员写一条收件箱指针，在线成员经各自网关推送 | 要路由到「收件人此刻连在哪台网关」；群有成员上限（约 100 人），万人级大群改读扩散；可靠靠收件箱游标 |
| [[notification-system-scale\|通知系统（支持单发与群发，百万级每秒）]] | 群发在系统内部懒扇出：活动存一条记录加游标，分页展开，发送前检查过期 | 扇出的对象是外部通道，不是自己的存储；重点是促销洪峰不能压住关键通知 |
| [[stock-price-alerts\|股票价格提醒系统]] | 触发判断按股票分区在内存里做，触发后订阅者按块并行发送 | 先判断、后扇出：扇出只发生在触发之后，还要防抖，避免重复提醒 |
| [[tt-realtime-auction-bidding\|实时竞价拍卖]] | 最新价按拍卖分区广播，每个网关只订阅有观众的拍卖，几百毫秒内合并成最新快照 | 扇出的是一个数值，丢一次没关系，下一次会覆盖，不需要持久收件箱 |
