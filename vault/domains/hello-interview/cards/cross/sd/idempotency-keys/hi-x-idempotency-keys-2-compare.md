## Q
**幂等键与只生效一次**｜跨题模式 · 对比

幂等转账、限时捐款、支付授权与批量结算、众筹购股、直播礼物扣币、拍卖出价、图书比价代购、分布式任务调度、聊天消息，这九类设计都要防止重复请求重复生效。它们的键怎么用、保存什么、还要配合什么机制，各有什么不同？

## A
| 题 | 在这里怎么用 | 为什么和别的题不同 |
|---|---|---|
| [[tt-idempotent-transfer\|幂等转账服务]] | 客户端键先用唯一约束占位，转账和保存结果同事务，重复请求读出第一次的响应 | 幂等本身：「进行中」合并并发、同键异请求拒绝（422）、余额不足这种业务拒绝也要被记住 |
| [[donations-website-charities\|设计限时捐款网站]] | 页面加载时生成 UUID 作键，双击、PSP 超时重发都落在同一条捐款记录上 | 键必须由前端生成；同一个键还要交给 PSP 当它的幂等键，我方、对方各挡一层 |
| [[payment-batch-processing\|设计支付处理系统（授权冻结 + 每日批量结算）]] | 商户到我们用 (商户, 键) 唯一约束；我们到网络用 holdId 做引用号；批次提交用批次号加文件校验和 | 键延伸到卡组织调用和每日批量，超时后「钱冻没冻」未知，要靠查询或冲正 |
| [[crowdfunding-share-purchase\|设计限时众筹购股系统（用账户余额抢固定数量的公司股份）]] | purchaseId 作主键插入，扣款用同一个 purchaseId 调余额服务，超时可安全重发 | 余额服务不归我们管，必须约定它支持幂等；不支持时只能保证每笔购买最多发起一次并留记录，靠对方流水确认 |
| [[tt-live-gift-coin-settlement\|直播虚拟礼物：金币记账与主播结算]] | gift_id 作主键，冲突即已处理；充值用 (平台, 交易号) 作主键 | 下游聚合器也要按 gift_id 去重，吸收发件箱的至少一次投递，两处幂等各管一段 |
| [[tt-realtime-auction-bidding\|实时竞价拍卖]] | 出价 ID 在同一事务里判重并更新最高价 | 幂等叠加「价格不倒退」：要单一拥有者加世代号给出价排序；重试要先按键查，否则已领先的出价会被判「太低」 |
| [[book-seller-platform\|图书比价代购平台（Book Seller Platform）]] | 稳定的 orderRef（订单号加尝试序号），要求书商按它幂等 | 对方是不可靠的第三方：超时进 UNKNOWN，先用 status 查询，查不到才重发同一个 orderRef |
| [[job-scheduler-cron-history\|分布式任务调度器（含 cron 与一年执行历史）]] | 没有请求键：用比较并交换（CAS）把状态从 SCHEDULED 改为 QUEUED 防双发，attempt 作围栏令牌，run_id 传给下游当幂等键 | 保证的是「至少一次且不同时跑两次」，靠租约、围栏令牌和任务自身幂等，不是一张键表 |
| [[messenger-chat-system\|设计聊天/即时通讯系统（WhatsApp / Messenger）]] | (chatId, clientMsgId) 去重，重复请求返回上次结果 | 去重对象是消息而不是资金，再配会话内序号和游标，用来保序和补收 |
