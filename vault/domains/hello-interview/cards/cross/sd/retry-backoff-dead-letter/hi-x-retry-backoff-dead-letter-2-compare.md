## Q
**至少一次、重试退避与死信**｜跨题模式 · 对比

商户 Webhook、通知系统、分布式任务调度器、调度器类设计、视频审核、网络爬虫、聊天、支付批处理这八道设计题都在「失败后重试」，重试的对象、等待放在哪里、还要保证什么，各有什么不同？

## A
| 题 | 在这里怎么用 | 为什么和别的题不同 |
|---|---|---|
| [[tt-merchant-webhook-delivery\|商户回调（Webhook）投递系统（至少一次、重试、顺序、签名）]] | 商户端点失败后指数退避加抖动，超限进死信并可手动重发，商户按事件号去重 | 明说对外部服务器没有恰好一次；重点是平台的重试不能变成对商户的攻击：每端点并发额度、熔断、探测、慢启动 |
| [[notification-system-scale\|通知系统（支持单发与群发，百万级每秒）]] | 对推送、短信、邮件通道按通道限速、失败重试，主服务商故障切备用 | 关键通知与群发促销物理隔离；每条消息带过期时间，出队和发送前各检查一次 |
| [[job-scheduler-cron-history\|分布式任务调度器（含 cron 与一年执行历史）]] | worker 随时会死，靠租约和心跳发现，失败就把任务改回「更晚到期」，复用同一套触发机制 | 要同时保证不会同时执行两次，所以重试之外还要围栏令牌（attempt） |
| [[scheduler-system-design\|设计任务调度器（定时、周期、带优先级）]] | 失败后按重试策略重新入定时堆，超次数写死信记录，优先级队列用老化防饥饿 | 类设计层面：重点是下一次触发时间怎么算，且要求任务幂等，因为「执行一半失败」和「没执行」无法区分 |
| [[video-moderation-system\|视频内容审核系统]] | 处置至少一次执行：下架这类副作用用稳定幂等键，指数退避，多次失败进死信并报警 | 重试的是模型推理和处置动作，处置结果全程要可审计，域服务前加熔断 |
| [[web-crawler-design\|网络爬虫（Web Crawler）]] | 下载失败入队退避，5 次后判站点不可达进死信；写入对象存储前不确认消息 | 重试还要守礼貌约束：同一主机限速，等待时间加抖动，避免多节点同时重试同一主机 |
| [[messenger-chat-system\|设计聊天/即时通讯系统（WhatsApp / Messenger）]] | 经收件箱兜底，网关宕机或发布订阅丢消息时客户端带游标补收；断线重连用退避加抖动 | 有序与幂等同时要求：补发不能改变会话内顺序，也不能重复显示 |
| [[payment-batch-processing\|设计支付处理系统（授权冻结 + 每日批量结算）]] | 被拒绝的批次进入重试批次，多次失败转人工或向商户追索 | 重试对象是金额级的批量，必须幂等且可对账 |
