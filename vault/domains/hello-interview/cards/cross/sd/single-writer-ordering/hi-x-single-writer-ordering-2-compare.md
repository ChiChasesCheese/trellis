## Q
**单写者、序号与版本排序**｜跨题模式 · 对比

象棋对局、拍卖出价、聊天会话、商品更新、Webhook 投递、云盘同步、多线程日志、协作绘图这八道设计题都要给同一实体的事件排出先后。它们由谁排序、顺序强到什么程度、冲突怎么处理，各有什么不同？

## A
| 题 | 在这里怎么用 | 为什么和别的题不同 |
|---|---|---|
| [[online-chess-platform\|在线国际象棋平台]] | 一局棋由 hash(gameId) 固定的所有者节点单线程串行处理，走子带 moveNo，宕机后从外部日志重放 | 难点是写者归属本身：怎么保证任何时刻只有一个所有者，以及玩家换设备后怎么路由 |
| [[tt-realtime-auction-bidding\|实时竞价拍卖]] | 出价按 auction_id 路由到唯一拥有者，数据库条件写入，租约加世代号防双主，价格不倒退 | 世代号拒绝旧拥有者的迟到写入，是最强的追问点；幂等和排序叠加 |
| [[messenger-chat-system\|设计聊天/即时通讯系统（WhatsApp / Messenger）]] | 每个会话一个递增序号，由会话所在分片分配，客户端按序号显示并发现空洞 | 只要会话内有序，不要全局有序，序号在会话分区内分配即可 |
| [[merchant-product-listings\|商家商品上架与更新系统]] | 同商品进同一分区，更新带版本，条件更新丢弃旧版本，缓存和索引也只接受更高版本 | 乱序来自批量重试和并行 worker；还要让批量不挤占单条更新 |
| [[tt-merchant-webhook-delivery\|商户回调（Webhook）投递系统（至少一次、重试、顺序、签名）]] | 默认不保证顺序，事件带 resource_version，商户自己忽略旧版本；要求顺序时按资源串行 | 顺序是尽力的：重试会让后一个事件先到，所以把排序责任交给接收方 |
| [[file-sync-system\|设计云盘与文件同步系统（Dropbox / Google Drive）]] | 元数据提交是单分片事务加 baseVersion 比较，客户端带游标追变更日志 | 冲突由版本比较发现，之后保留两份冲突副本，不自动合并 |
| [[multithreaded-logging-framework\|多线程日志框架]] | 单个接入线程分配序号，单个写入线程落盘，天然 FIFO | 这是进程内版本：用专职线程代替加锁，所以是三个专职线程而不是线程池 |
| [[figma-draw-api\|矢量图形编辑器的绘图 API（类 Figma）]] | 只有提交的操作进入同步，服务端排序并按（对象, 属性）后写者胜 | 多个写者同时编辑同一对象，不去掉并发，而是用属性级合并收敛；瞬时预览只在本地和 presence 通道 |
