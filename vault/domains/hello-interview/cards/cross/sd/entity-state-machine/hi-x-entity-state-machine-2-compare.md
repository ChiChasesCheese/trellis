## Q
**实体状态机与合法迁移**｜跨题模式 · 对比

同样是状态机，活动票务、酒店预订、在线象棋、股票交易、招聘申请、饮品售卖、电梯、熔断器这几道设计题，各自的状态由谁推进，保护迁移正确性的手段有什么不同？

## A
| 题 | 在这里怎么用 | 为什么和别的题不同 |
|---|---|---|
| [[event-ticket-booking\|活动票务预订后端（防超卖的 REST 服务）]] | 保留、确认、过期三态，每次迁移是带条件的原子更新 | 释放动作必须幂等，状态机防止同一份库存被释放两次 |
| [[hotel-booking-system\|酒店预订系统（Expedia 型聚合与自营）]] | HELD、PAID、PENDING_SUPPLIER、CONFIRMED，每步在本地事务内改状态，崩溃后由状态驱动恢复 | 用状态机代替分布式事务，状态里显式表示“在等外部供应商” |
| [[online-chess-platform\|在线国际象棋平台]] | 一局棋是小而强一致的状态机，走子、悔棋、超时、认输由唯一写者串行处理 | 事件来自两位玩家和计时器，重点是单写者归属与宕机后从日志重放，而不是吞吐 |
| [[stock-trading-platform\|设计简化版股票交易平台（券商端，限价单）]] | 订单从已发送、部分成交到已成交或已取消，取消与成交会竞争 | 状态由外部交易所的执行报告推进，要按 execId 去重，等最终回执才释放冻结资金 |
| [[job-board-platform\|招聘信息平台（Job Board）]] | 申请有合法迁移表，同一求职者对同一职位只能有一个有效申请 | 触发方分角色，迁移带权限：雇主推进、求职者撤回 |
| [[beverage-vending-system\|多地点饮品自助售卖系统]] | 订单和机器各自是状态机，机器离线时订单据此失败或改派 | 两个状态机互相影响，库存预留跨在它们之间 |
| [[elevator-design\|设计电梯系统（面向对象，可运行的代码）]] | 单部电梯是小状态机，所有状态变化收在一个线程里 | 状态机与可替换的调度策略分离，并发靠单线程而不是加锁 |
| [[api-circuit-breaker\|熔断器（Circuit Breaker）]] | 闭合、打开、半开三态，失败多了快速失败，再用探测恢复 | 难点是并发下迁移的正确性：半开只放少量探测，迟到的旧结果不能污染新状态 |
