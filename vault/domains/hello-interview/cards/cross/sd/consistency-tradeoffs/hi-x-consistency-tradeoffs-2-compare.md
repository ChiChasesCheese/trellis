## Q
**强一致与最终一致的取舍**｜跨题模式 · 对比

钱包账本、点赞、菜品评价、文件同步、酒店预订、直播礼物、短链接、缓存一致性热点这几道设计题，各自把强一致放在哪里、把最终一致放在哪里，边界有什么不同？

## A
| 题 | 在这里怎么用 | 为什么和别的题不同 |
|---|---|---|
| [[tt-wallet-ledger-service\|钱包与复式账本服务（余额、冻结、转账、多币种）]] | 余额扣减强一致（条件更新加账本），汇总和审计异步 | 同一服务里同步路径只做最少的事，强弱一致共存 |
| [[like-unlike-system\|点赞与取消点赞（收藏）系统]] | 自己的点赞状态立即可见（条件写、写穿），总数允许最终一致且可近似 | “实时只对自己的那一票有意义”的典型 |
| [[food-item-reviews\|设计带打赏的菜品评价系统（点评 + 投票 + 达标付款）]] | 展示的票数晚几秒无所谓，一人一票和里程碑付款靠主键强约束 | 同一系统内高频低价值的数据放松，低频高价值的数据收紧 |
| [[file-sync-system\|设计云盘与文件同步系统（Dropbox / Google Drive）]] | 元数据提交强一致（单分片事务加版本比较），设备之间的视图最终一致 | 强一致只放在单分片的提交点上，其余靠追游标收敛 |
| [[hotel-booking-system\|酒店预订系统（Expedia 型聚合与自营）]] | 搜索摘要允许几十秒过期，下单时库存强一致，并在详情和下单时再核验 | 把一致性边界收窄到写路径的最后一步 |
| [[tt-live-gift-coin-settlement\|直播虚拟礼物：金币记账与主播结算]] | 观众钱包强一致，主播收益展示是预估，结算再重算 | 不用 Redis 记余额：异步复制故障转移会丢扣减 |
| [[url-shortener-design\|短链接服务（URL Shortener / TinyURL）]] | 创建时靠唯一约束保证短码唯一，读缓存短暂旧数据可容忍，创建者要读到自己的写 | 读写比约 1000 比 1，一致性只在创建这一小步收紧 |
| [[tt-cache-consistency-hot-keys\|缓存一致性与热点 Key]] | 缓存与数据库两份副本的不一致窗口只能压小，先更库再删缓存，加变更日志兜底和 TTL | 把“强一致怎么办”作为追问，答案是下单校验读主库或版本化缓存 |
