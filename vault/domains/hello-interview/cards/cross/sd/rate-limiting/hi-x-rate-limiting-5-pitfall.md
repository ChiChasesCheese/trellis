## Q
**限流算法与原子计数 (Rate Limiting)**｜跨题模式 · 易错

实现或设计限流时，候选人常犯哪些错？每个错的具体后果是什么？

## A
1. **先读计数再写回，不是原子。** 两个网关或线程各读到旧值，双双放行。解法：单机 per-key 锁，多机 Redis Lua。（[[distributed-rate-limiter|分布式限流器]]、[[rate-limiter-system|限流器（单机类设计）]]）
2. **用墙钟计时。** NTP 校时或手工改时间会让时钟回退，令牌变负或窗口错乱；解法是单调时钟，补充量取 `max(0, …)`，并注入假时钟代替 `sleep` 测试。
3. **用固定窗口还说"严格每秒 N 次"。** 窗口交界处会放过两倍额度；要严格就用滑动窗口。
4. **两层锁的顺序。** 同时持有全局锁和 key 锁容易死锁；做法是先释放全局锁再取 key 锁。（[[rate-limiter-system|限流器（单机类设计）]]）
5. **key 无限增长。** 状态按用户输入产生，不清理就撑爆内存；解法是 LRU 上限或惰性清理。不活跃一个窗口后状态等价于初始状态，所以淘汰近乎无损。（[[tt-per-merchant-rate-limit|按商户限流]]）
6. **把出向限速分散到多个节点。** 同一主机的请求被多个节点各自发出，礼貌上限无法统一控制，对方被打爆。（[[web-crawler-design|网络爬虫]]）
7. **不回答限流器挂了怎么办。** 全部拒绝会把整个 API 一起关掉并引发重试风暴，全部放行会在高峰时把流量压向后端；要说出取向并配告警。
