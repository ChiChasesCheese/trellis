## Q
**限流算法与原子计数 (Rate Limiting)**｜跨题模式 · 对比

七道题都有限流，但限的对象和方向不同。请说明每道题限的是谁、状态放哪、为什么与别的题不同。

## A
| 题 | 在这里怎么用 | 为什么和别的题不同 |
|---|---|---|
| [[distributed-rate-limiter\|分布式限流器]] | 比较四种算法，Redis Lua 脚本做原子读改写，按客户端标识分片扛百万次每秒 | 关注规模：状态分片、为什么允许最终一致、多规则组合、限流器故障时放行还是拒绝 |
| [[rate-limiter-system\|限流器（单机类设计）]] | 算法做成可替换的策略，只管单个 key 的状态，外层按 key 管理并发 | 是类设计：重点是策略模式、两层锁的顺序（死锁风险）、单调时钟和注入假时钟 |
| [[tt-per-merchant-rate-limit\|按商户限流]] | 令牌桶惰性补充，每次判定 O(1) 且无定时器；LRU 限制几十万商户的内存；分段加锁 | 多实例时把桶放进 Redis 用 Lua 原子完成；故障取向按场景定，支付倾向拒绝 |
| [[tt-flash-sale-ticketing\|秒杀抢票]] | 限流是"逐层便宜地拒绝"中的一层，准入之后才让极少数请求碰到库存 | 目的不是公平计费，而是保护库存和数据库：99.6% 的请求注定失败，必须在最外层拒绝 |
| [[web-crawler-design\|网络爬虫]] | 对每个站点限速，保持礼貌，遵守 robots.txt | 限的是出向请求，按主机限速而不是按调用方限速，同一主机必须归同一节点 |
| [[notification-system-scale\|通知系统]] | 对第三方推送和邮件通道设置限速，群发时懒扇出 | 限流是出向的、按通道的，而且关键通知不能被群发挤占 |
| [[chatbot-design\|对话式 AI 聊天服务]] | 按用户和全局对推理请求限流，再加排队保护 GPU | 限的是昂贵的推理资源，常按词元（token）数而不是请求数计量 |

**共同点：** 每个主体一份小状态加原子判定。**差异来自"限谁"：** 入向按调用方，出向按被调用方，保护库存按层级，保护推理按成本。
