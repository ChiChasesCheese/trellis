## Q
**事实与派生视图**｜跨题模式 · 对比

点赞、商品上架、酒店预订、支付对账、照片存储、指标监控、Top-K 榜单、直播礼物结算这几道设计题，各自的“事实”和“派生视图”分别是什么，派生的目的有什么不同？

## A
| 题 | 在这里怎么用 | 为什么和别的题不同 |
|---|---|---|
| [[like-unlike-system\|点赞与取消点赞（收藏）系统]] | 事实表存 (用户, 内容) 的点赞关系，总数是派生统计，经事件流聚合后异步更新 | 必须保留事实表才能点查、列出我的点赞、去重，不能只存计数 |
| [[merchant-product-listings\|商家商品上架与更新系统]] | 写侧是可校验可重放的批量摄入，读侧缓存和搜索索引是派生视图，用 CDC 事件连接 | 难点是更新顺序、批量对单条的挤压，以及缓存与索引多快跟上 |
| [[hotel-booking-system\|酒店预订系统（Expedia 型聚合与自营）]] | 搜索读预聚合摘要，库存行是真相，两者通过过期容忍和下单时的核验衔接 | 读极多写极少，视图可以偏旧，只有写路径需要精确 |
| [[tt-payment-reconciliation\|支付对账系统（内部账本、PSP 结算文件、银行流水三方对账）]] | 对账匹配结果是派生数据，可由账本、PSP 文件和银行流水重算 | 派生是为了出错时能重跑，不修改历史输入；人工匹配单独存储并优先 |
| [[photo-storage-sharing\|照片存储与分享系统（Google Photos）]] | 分析查询不放线上库，经 CDC 流入数据仓库或列存 | 派生是为了保护线上元数据库，不是为了加速读 |
| [[metrics-monitoring-alerts\|指标监控与告警平台]] | 原始点追加写入，按时间降采样为 5 分钟和 1 小时序列 | 视图的粒度随时间变粗，用精度换扫描量，且要保留最小、最大、平均、计数 |
| [[top-k-counts\|Top-K 热门榜（视频播放、歌曲、话题标签）]] | 把 Top-K 的计算挪到写入之后的预计算，查询只读缓存 | 视图是窗口化的聚合，精确还是近似、滑动还是对齐窗口决定整套架构 |
| [[tt-live-gift-coin-settlement\|直播虚拟礼物：金币记账与主播结算]] | 主播实时收益是事件的汇总视图，周结算由事件重算覆盖 | 视图明确标“预估”，真相是事件而不是汇总值 |
