## Q
**实时推送与有状态连接**｜跨题模式 · 对比

聊天、在线象棋、实时竞价、文件同步、股票交易、聊天机器人、编程竞赛这几道设计题都涉及“把结果推给客户端”，各自的连接怎么用，推送丢了怎么兜底，有什么不同？

## A
| 题 | 在这里怎么用 | 为什么和别的题不同 |
|---|---|---|
| [[messenger-chat-system\|设计聊天/即时通讯系统（WhatsApp / Messenger）]] | 会话目录记录用户连在哪台网关，消息按目录发到对应网关的频道，路由通道丢了由收件箱兜底 | 同时要有序、幂等和离线补收，三者在每天上百亿条的规模下同时成立 |
| [[online-chess-platform\|在线国际象棋平台]] | 两位玩家与观战者连到同一局的唯一写者，走子和计时事件实时下发 | 规模不大但强一致，重点是宕机后重连到新写者，以及用 moveNo 幂等拒绝重复和乱序 |
| [[tt-realtime-auction-bidding\|实时竞价拍卖]] | 最新价格几百毫秒内推给几万个连接，每条推送带版本号，状态页以快照为准 | 推送允许丢也允许合并，因为只关心最新价；出价本身走单独的强一致 HTTP 路径 |
| [[file-sync-system\|设计云盘与文件同步系统（Dropbox / Google Drive）]] | 每个客户端一条连接，里面复用多个命名空间的通知，通知只说“有新游标” | 推送有损，所以仍然要定时用游标拉取：游标是幂等的追赶机制，推送只是加速 |
| [[stock-trading-platform\|设计简化版股票交易平台（券商端，限价单）]] | 行情按代码发布订阅，服务端对同一代码聚合后广播，每秒一两次 | 行情只是读数据，可以合并降频；订单状态在数据库里，推送只是告知 |
| [[chatbot-design\|对话式 AI 聊天服务（简化版 ChatGPT）]] | 回复用 SSE 单向流式输出，客户端断开就取消上游并释放 GPU | 一路流占用 GPU 几秒到几十秒，重点是取消及时回收资源，续传要先写缓冲 |
| [[coding-contest-platform\|在线判题与编程竞赛平台（LeetCode）]] | 默认异步判题加每秒轮询，是否改用 WebSocket 推送是追问 | 结果是一次性的，轮询是轻量读；十万级长连接的复杂度换不来不到一秒的延迟 |
