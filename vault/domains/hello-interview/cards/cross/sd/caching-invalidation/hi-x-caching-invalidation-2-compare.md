## Q
**缓存、失效与一致性窗口**｜跨题模式 · 对比

缓存专题、短链接、新闻聚合、机票搜索、微博时间线、商品更新、酒店预订、最近浏览这八道设计题都用到缓存或缓存式的派生视图。它们缓存什么、一致性窗口由什么决定、关注点有什么不同？

## A
| 题 | 在这里怎么用 | 为什么和别的题不同 |
|---|---|---|
| [[tt-cache-consistency-hot-keys\|缓存一致性与热点 Key]] | 旁路缓存，先更新库再删缓存，删除失败靠 CDC 或重试兜底，防击穿、穿透、雪崩 | 缓存本身的专题：各种读写顺序下的竞态窗口，以及为什么选删除而不是更新 |
| [[url-shortener-design\|短链接服务（URL Shortener / TinyURL）]] | 跳转读路径靠数据库索引、Redis、CDN 逐层加速，读写比约 1000 比 1 | 映射几乎不变，几乎没有一致性问题，主要是命中率与容量；用 302 而不是 301，才能保留统计、过期和改指向 |
| [[news-aggregator-feed\|设计新闻聚合系统（Google News）]] | 同一分类全员共享，分类最新一页在 CDN 或 API 层缓存 15 到 30 秒，读端几乎全靠缓存 | 缓存的是共享内容，新鲜度由摄取节奏决定；Redis 分类索引丢了可从文章库重建 |
| [[flight-search-system\|设计机票搜索系统（多供应商聚合，按调用计费）]] | 按供应商分开缓存价格，合并重复请求，热门航线预热，价格确认推迟到点击行程时 | 缓存新鲜度直接换成供应商账单；TTL 按距起飞的远近分档，值不值得缓存要靠实验验证 |
| [[twitter-clone-feed\|微博客与个性化信息流（Twitter）]] | 时间线用 Redis 有序集合只存推文 ID，内容另取，热点读走缓存 | 缓存只存 ID 还是存完整内容是追问点：存 ID 时删除和编辑只改一处 |
| [[merchant-product-listings\|商家商品上架与更新系统]] | 商品更新后，缓存和搜索索引通过变更事件跟上，只接受更高版本 | 读侧缓存与索引是派生视图，靠事件和版本而不是请求时失效；商家后台要读自己的写 |
| [[hotel-booking-system\|酒店预订系统（Expedia 型聚合与自营）]] | 搜索走可略微过期的预聚合摘要，下单才对库存行做条件扣减 | 接受搜索结果过期，把一致性只放在写路径，点进详情和下单时再核验 |
| [[recently-viewed-items\|设计"最近浏览"记录（类似 LRU 缓存，上限在构造时给定）]] | 每个客户一个定长 LRU，真实系统放在 Redis 之类的缓存里 | 这是类设计：重点是 O(1) 摘除与重新插入，不是分布式缓存一致性 |
