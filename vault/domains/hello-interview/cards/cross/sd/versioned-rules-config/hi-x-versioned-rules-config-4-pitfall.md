## Q
**版本化规则与配置分发 (Versioned Rules / Control Plane vs Data Plane)**｜跨题模式 · 易错

设计版本化规则时，候选人常犯哪些错？每个错的具体后果是什么？

## A
1. **只保存当前配置。** 重算上个月的交易会用今天的规则，账对不上；退款手续费会套错价格计划。要把"计算依据的时间"作为显式参数。（[[tt-billing-tax-engine|计费 / 计税引擎]]）
2. **更正历史时修改旧行或旧版本。** 审计链断了。应发布新版本，并对受影响的交易追加差额调整行。生效时间必须严格递增，否则二分查找不成立。
3. **每次请求远程判定。** 热路径依赖网络，控制面一挂业务一起挂。应本地判定，控制面宕机时继续用内存里最后一份快照。（[[feature-flag-service|功能开关服务]]）
4. **所有开关用同一个哈希输入。** 每个开关都是"用户 ID 排名前 X%"，同一批用户永远是所有实验的小白鼠。哈希里要加开关键和盐；调大百分比时已命中的用户不能掉出。（[[feature-flags-service|功能开关服务（SDK 本地判定）]]）
5. **迟到的旧快照覆盖新快照，或一次请求里读到两份规则。** SDK 只接受更高版本，一个请求内取一次快照引用。
6. **规则缺一个输入就当 0 放行。** 模型服务超时，故障变成漏审。规则对缺失值要有明确语义（`unknown`），高风险组合转人工复审。（[[video-moderation-system|视频内容审核系统]]）
7. **配置本身不灰度。** 一次错误配置一次推到全部实例，爆炸半径是整站。配置也要像代码一样先推一小部分、看错误率、再全量，并保留上一版本。
