## Q
**版本化规则与配置分发 (Versioned Rules / Control Plane vs Data Plane)**｜跨题模式 · 怎么选

面对一道"规则会变"的新题，怎么决定版本化到什么程度、怎么分发？请按判断信号分支，各举一题。

## A
1. **过去某一时刻的结果必须能重现吗？**（对账、退款、审计）必须：每个版本带生效时间，按事件发生时间二分查找，版本只追加，更正写调整行。例：[[tt-billing-tax-engine|计费 / 计税引擎]]。
2. **改规则有风险，需要先验证吗？**（误判代价高）是：规则数据化，保存足够的输入（历史分数），新规则先回放对比差异，再影子、灰度、生效。例：[[video-moderation-system|视频内容审核系统]]。
3. **只关心当前版本，但要求传播快、结果稳定吗？**（开关）是：整份快照加版本号，ETag 轮询加推送缩短延迟，回滚即指回旧版本，SDK 只接受更高版本。例：[[feature-flag-service|功能开关服务]]。
4. **需要给用户稳定地分组吗？**（百分比放量）用确定性哈希（开关键加盐加用户 ID），不用存储；只有"一旦分配永不改变"的正式实验才写分配表。例：[[feature-flags-service|功能开关服务（SDK 本地判定）]]。
5. **只是几个参数吗？**（限速）热更新即可，下一次判定读新值，不保留历史。例：[[tt-per-merchant-rate-limit|按商户限流]]、[[distributed-rate-limiter|分布式限流器]]。

**传播方式：** 默认轮询加缓存，简单可靠；安全应急要求高时叠加推送，推送只通知版本号，丢了不要紧。
