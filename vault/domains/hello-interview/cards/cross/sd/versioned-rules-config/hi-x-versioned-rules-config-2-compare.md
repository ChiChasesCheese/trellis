## Q
**版本化规则与配置分发 (Versioned Rules / Control Plane vs Data Plane)**｜跨题模式 · 对比

六道题都用了版本化规则，但"版本"的用途不同：有的只关心当前版本，有的要查过去某一时刻的版本。请逐题说明。

## A
| 题 | 在这里怎么用 | 为什么和别的题不同 |
|---|---|---|
| [[feature-flag-service\|功能开关服务（系统设计）]] | 整份规则集快照可靠、快速、可回滚地分发到每个 SDK，百万次每秒的取值只在进程内完成 | 重点是变更传播、控制面宕机时的默认行为（fail static）和同一用户在同一开关上的结果稳定 |
| [[feature-flags-service\|功能开关服务（SDK 本地判定）]] | 配置集中管理，判定在客户端 SDK 用确定性哈希完成，粘性靠哈希而不是存储 | 百分比放量的单调性；不同开关的哈希输入不同（加 salt），避免同一批用户总被选中 |
| [[tt-billing-tax-engine\|计费 / 计税引擎]] | 每个商户的规则版本按生效时间排序，`bisect` 二分查找，费用按事件发生时的规则算 | 发错规则不改旧行，而是追加调整行；退款按原交易所属的规则版本计算；没有生效版本就报错 |
| [[video-moderation-system\|视频内容审核系统]] | 规则存成数据（表达式树），草稿、影子、灰度、生效逐级推进；用保存的历史分数回放验证新规则 | 规则改动要能先回放评估再上线，每条审核记录写入命中的规则版本和模型版本 |
| [[tt-per-merchant-rate-limit\|按商户限流]] | 配置实时修改，下一次 `allow` 读到新配置 | 配置只是限速参数，不涉及历史版本和回放 |
| [[distributed-rate-limiter\|分布式限流器]] | 限流规则可配置（如每用户每分钟 100 次），网关本地缓存，轮询或推送更新，多条规则同时生效 | 规则要在多台服务器间一致生效，允许短暂的最终一致；多规则各自独立计数 |

**共同点：** 配置是数据，判定在本地，改动不需要发版。**差异来自"过去的结果要不要能重现"：** 钱和审核要，开关和限速只要当前版本。
