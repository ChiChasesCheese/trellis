## Q
**异步流水线、背压与批量 (Async Pipeline / Backpressure / Batching)**｜跨题模式 · 对比

八道题都有异步流水线，但背压的单位、瓶颈和丢弃策略不同。请逐题说明。

## A
| 题 | 在这里怎么用 | 为什么和别的题不同 |
|---|---|---|
| [[multithreaded-logging-framework\|多线程日志框架]] | 接入、写入、确认三个专职线程加有界队列，批量刷盘，写成功后才确认，关闭时毒丸排空 | 单进程的生产者-消费者；背压要选：阻塞调用方（默认，不丢）、丢弃或按级别丢 |
| [[video-moderation-system\|视频内容审核系统]] | 事件驱动多阶段：并行模型推理，规则判定，幂等处置，审计 | 每个阶段成本和优先级不同；模型缺失分数不能当 0，要转人工或重试；打分结果能被规则回放 |
| [[merchant-product-listings\|商家商品上架与更新系统]] | 批量摄入经校验后进事件流，消费者更新缓存与索引，按 `productId` 分区保序 | 批量会挤压单条更新：分队列、按商家令牌桶限速；队列堆积时批量接口返回"排队中" |
| [[metrics-monitoring-alerts\|指标监控与告警平台]] | 每秒百万点先进 Kafka 再写时序库，存储与告警各自消费 | 追加写、几乎不读；允许缓冲区满时丢最老的点并计数；告警链路必须比被监控系统更可靠 |
| [[web-crawler-design\|网络爬虫]] | 按主机分前沿队列，下载、解析分阶段，写入对象存储后才确认消息，进度持久化 | 瓶颈是礼貌而不是算力；队列里只放 URL 指纹，不放 HTML；解析逻辑改了可对已存页面重跑 |
| [[chatbot-design\|对话式 AI 聊天服务]] | 推理请求排队，流式输出，中途取消时回收资源 | 单个请求占用很久，背压体现为排队时长和拒绝（等待超过阈值就快速失败） |
| [[notification-system-scale\|通知系统]] | 按优先级分离多条管道，每个渠道独立队列，发送前检查过期 | 背压要保证关键通知不被群发压住，而不仅是平滑 |
| [[figma-draw-api\|矢量图形编辑器的绘图 API]] | 高频指针事件每帧最多处理一次，只有提交的操作才进入撤销栈、持久化和同步，批量发送 | 批处理的对象是前端手势事件，目标是控制渲染和网络的频率，而不是后端队列的深度 |

**共同点：** 有界缓冲加批量加写后确认。**差异来自"满了怎么办"：** 日志默认阻塞，指标丢点，聊天拒绝，通知分级，批量商品让路给单条。
