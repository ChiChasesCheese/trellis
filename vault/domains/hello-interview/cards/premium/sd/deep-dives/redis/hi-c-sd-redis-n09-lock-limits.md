## Q
**Redis · 分布式锁的边界：Redlock、围栏令牌、何时不用**｜摘要 · 必会

Redis 锁在什么情况下会失效？Redlock 解决了什么，又有什么争议？什么时候应该放弃它？

## A
- **失效模式：** 复制是异步的，主节点刚授予锁就挂了，被提升的副本可能根本不知道有这把锁，会把同一把锁授予别人。
- **Redlock：** 在多个独立 Redis 节点中的多数上加锁，以扛住这种故障。有争议：暂停或变慢的客户端在锁过期后仍可能继续动作（进程暂停、网络延迟、时钟跳变都可能造成）。
- **标准防御是围栏令牌（fencing token）：** 每次授予锁都附带一个递增的数字，存储层拒绝带着旧数字的写入。Redis 本身不提供。
- **结论：** 把 Redis 锁当成偶尔会失灵的效率工具，不是正确性保证。如果过期的持有者会损坏数据，就在数据所在处保证不变式，或用 ZooKeeper、etcd 这类共识系统。
- **常常不需要分布式锁：** 数据库的 `SELECT ... FOR UPDATE` 行锁，或条件更新 `UPDATE ... WHERE version = X`，往往完全替代它。
