## Q
**PostgreSQL · MVCC 的代价：死元组、VACUUM 与长事务**｜拓展 · 加分

为什么 PostgreSQL 的更新密集表会膨胀？长时间不提交的事务有什么危害？

## A
- **MVCC 的做法：** 更新一行不是原地改，而是写一个新版本，旧版本留着给还在用旧快照的事务读。这就是为什么读不阻塞写、写不阻塞读。
- **后果：** 旧版本成为死元组（dead tuple），需要 VACUUM 回收空间；回收不及时，表和索引膨胀（bloat），扫描变慢、缓存命中变差。`autovacuum` 会自动做，高更新率的表可能要调得更积极。
- **长事务的危害：** 只要有一个老事务还没结束，它可能还要看旧版本，清理就不能越过它，死元组越攒越多；在副本上跑长查询也可能阻止主节点清理或与复制冲突。
- **2026 亮点：** PostgreSQL 17 新增 `transaction_timeout`：整个事务（含隐式单语句事务）超过时长就终止会话，补上只管空闲的 `idle_in_transaction_session_timeout` 与只管单条语句的 `statement_timeout` 之间的缺口。默认 0 即关闭，不建议写进全局配置，应按角色或数据库为业务连接设置并配合 `lock_timeout`；超时后事务回滚，调用方必须幂等可重试。
- **事务 ID 回卷：** 事务 ID 是 32 位，需要定期冻结（freeze）旧行，否则数据库会为了防止回卷而强制停写，是需要监控的运维风险。
- **设计含义：** 频繁更新同一批行（如计数器）会放大这个问题，计数更适合缓冲聚合后再写，或放到专用存储。
