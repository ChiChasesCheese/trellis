## Q
**大数据结构 · 缓存前置过滤器的失效**｜考点 · 必会

团队在 Redis 缓存前放了一个布隆过滤器，记录哪些键写进了缓存，想让未命中的请求直接走数据库。运行三天后命中率下降、过滤器说「可能在」的比例越来越高。为什么？怎么修？

## A
- **原因：** 缓存键有 TTL，会过期和被淘汰，但标准布隆过滤器不能删除，位只增不减，越来越饱和，假阳性越来越多，几乎都说「可能在」，前置过滤失去作用，每次还多一次判断。
- **还有一个漏洞：** 若有多个写入方，别的客户端写进缓存的键，这个过滤器没记录，会被判为「不在」，白白错过缓存命中。
- **修法：**
  - 按固定周期重建过滤器，或分代轮换（旧的和新的同时查，旧的过期后丢弃）；
  - 改用支持删除的变体（计数型布隆过滤器、布谷鸟过滤器）；
  - 让所有写入方共用同一个过滤器。
- **先问值不值：** 缓存查询本身只要 1–2ms 时，过滤器能省下的只是未命中时白付的那次缓存查询，可能根本不值得引入。
