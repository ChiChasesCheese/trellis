## Q
**Temporal · 信号的边界：发给没启动或已结束的 Workflow、重复信号、数量上限**｜拓展 · 追问

支付回调要给订单 Workflow 发"已付款"信号。如果 Workflow 还没启动、已经结束，或者回调重试发了三次，各会怎样？一个 Workflow 能收多少信号？什么时候该用 Update 而不是信号？

## A
**一句话。** 信号一旦被服务端接受，就写进事件历史，不会丢；但它只能发给正在运行的执行。还没启动用 Signal-With-Start，已结束会返回错误；重复要靠业务事件 ID 自己去重；单个执行最多 1 万个信号，长期接收信号的 Workflow 要定期 Continue-As-New。

**情况逐个看。**
- **Workflow 正在运行：** `SignalWorkflowExecution` 返回成功，就表示 `WorkflowExecutionSignaled` 已进历史。之后 Worker 宕机、服务端重启都不影响，它会在下一个 Workflow 任务里被处理。
- **还没启动：** 用 Signal-With-Start：有同 ID 的运行中执行就发信号，没有就启动一个新执行并立即投递这个信号，这一步是原子的。适合"第一个事件来了才建流程"的场景。
- **已经结束：** 信号发不进去，客户端收到"执行不存在或已完成"的错误。回调方要能处理这个错误，例如记日志或走补偿，而不是无限重试。
- **重复信号：** 请求里的 `request_id` 只为 SDK 自己重发同一次调用去重；回调方的三次独立重试是三个信号。信号里带支付事件 ID，Workflow 用一个集合记住处理过的 ID。
- **顺序：** 信号按写进历史的顺序被处理；不同发送方之间没有业务意义上的先后，代码不要假设"已付款"一定在"已发货确认"之前。

**数字。**
- **每个执行最多 1 万个信号：** 到上限后不再处理新的信号。持续流量建议每个执行每秒不超过约 5 个，多了就把事件攒批再发，或分散到多个执行。
- **事件历史上限：** 51,200 个事件或 50 MB，1 万个事件或 10 MB 时开始告警。长期接收信号的 Workflow 要定期 Continue-As-New，把状态带到新执行里。
- **未完成项：** 一个执行同时挂着的未完成 Activity、子 Workflow、外部信号和取消请求合计最多 2000 个。

**信号还是 Update。**
- **信号：** 异步，发送方拿不到结果也拿不到异常，Worker 不在线也能发。适合"通知一下"：已付款、已签收。
- **Update：** 同步，调用方等到处理函数返回结果或拒绝，可以先校验再接受。适合"要知道成没成"：修改出价、改收货地址。代价是要等 Worker 在线处理。

**面试里这样说。** 「回调用 Signal-With-Start 发信号，带支付事件 ID，Workflow 里去重；已结束的执行会报错，回调方转补偿。信号多的长期流程定期 Continue-As-New。」
