## Q
**写扩展 · 用逻辑分片避免重新哈希**｜拓展 · 加分

为什么"哈希后对机器数取模"一扩容就要大搬家？生产里怎么避免？

## A
- **取模的问题：** `hash(key) % N` 在 N 从 8 变 16 时，大约一半的键要换位置；搬家期间读写路径也会混乱。
- **预先划分许多逻辑分片：** 一开始就切成几千个逻辑分片（槽或虚拟分片），再把它们映射到物理节点。Redis Cluster 就用固定的 16384 个槽。
- **扩容时：** 只需把部分槽整体搬到新节点，键到槽的映射永远不变，不用重新哈希。每个槽的迁移可以单独做双写和切换。
- **一致性哈希 + 虚拟节点：** 效果类似，新节点只接管环上相邻的一小段。
- **选择：** 逻辑分片数要一开始就留足余量，因为日后改它又是一次大迁移。
