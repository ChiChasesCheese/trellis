## Q
**实时更新 · WebSocket：全双工**｜摘要 · 必会

WebSocket 怎么建立？适合什么场景？为什么面试里不要太早选它？

## A
- **机制：** 先发一次 HTTP 请求并"升级"（upgrade），同一条 TCP 连接换成 WebSocket 协议，所以可以复用 Cookie、头部等已有的会话信息。之后两端都能随时发消息，消息是不透明的字节，可以是字符串、JSON、Protobuf，相当于带便利的 TCP 连接。
- **适合：** 高频的双向通信，如聊天、协作编辑、游戏。
- **优点：** 全双工、没有每次请求的头部开销所以延迟低、频繁消息高效、浏览器支持广泛。
- **缺点：** 实现复杂；需要整条链路都支持；有状态连接让负载均衡和扩展变难；需要处理重连。
- **基础设施挑战：** ①客户端能升级不代表中间设备支持；②发布部署时要么断开所有旧连接让它们重连，要么新服务器接管（通常选前者，更简单，但"持久"的程度要打折，客户端必须能补上断线期间错过的更新）；③长连接必须"粘住"最初的分配，均衡器不能随意改派。
- **常见架构：** 尽早把 WebSocket 终止在一个专门的 WebSocket 服务里，由它管理连接和扩展，后面的系统保持无状态；这个服务改动少，部署少，连接抖动也少。
- **不要过早采用：** 写入完全可以走普通 HTTP POST，常见做法是"SSE 订阅更新 + HTTP 写入"。除非有高频双向需求，否则优先 SSE。
- **要谈的事：** 连接管理、重连、部署策略、状态怎么收敛；负载可能不均匀，用"最少连接"策略，并让 WebSocket 服务做的事尽量少，重活交给可独立扩展的后端。
