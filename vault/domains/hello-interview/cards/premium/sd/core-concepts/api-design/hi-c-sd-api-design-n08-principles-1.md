## Q
**API 设计 · 设计原则（上）**｜摘要 · 必会
面试官评价一个 API "干净"，实际在拿哪几条原则衡量？前五条分别是什么、违反时长什么样？

## A
- **用法：** 很少被直接问原则，它们是评分标准；在做决定时说出理由（"用幂等键，重试就不会重复订座"）比背诵更得分。
- **1 围绕资源而非动作：** 看到 `/getUserBookings`、`/processPayment` 就停，改成 `GET /users/{id}/bookings`、`POST /payments`。
- **2 处处一致：** 命名、参数名、响应形状一致。一个端点用 `status=paid`、另一个用 `state=paid`，使用者就只能死记。
- **3 最小惊讶：** 照 HTTP 通行语义用：GET 不改数据、DELETE 删除、200 就是成功，不要 200 里塞 `"success": false`。每处偏离都让每个调用方永远多付一点成本。
- **4 无状态：** 每个请求自带服务器处理所需的一切（令牌、参数、载荷），任何实例都能处理任何请求，水平扩展就只是负载均衡的事。这是 JWT 流行的原因之一。
- **5 重试安全：** 网络会在请求中途断掉，客户端不知道服务器做没做，只能重试，所以接口必须让重试无害：GET/PUT/DELETE 天然幂等，创建订单、付款用幂等键。
