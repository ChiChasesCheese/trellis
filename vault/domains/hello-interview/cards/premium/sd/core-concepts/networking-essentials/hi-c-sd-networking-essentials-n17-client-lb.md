## Q
**网络基础 · 客户端负载均衡**｜摘要 · 必会

客户端负载均衡怎么工作，有哪些例子，适合什么场景？

## A
- **机制：** 客户端自己决定去哪台服务器，通常先向服务注册表（service registry）获取可用服务器列表，再直接请求其中一台；服务器变化时靠定期轮询或推送更新列表。
- **优点：** 快且高效：客户端自己决策，可以选最快的服务器，每个请求不需要多一跳网络转发，只需（周期性）同步服务器列表。
- **例子，Redis Cluster：** 节点之间用 gossip 协议共享集群信息，每个节点都知道所有其他节点。客户端连任一节点，询问集群里有哪些节点及各自负责的分片；读写时对键哈希得到分片，再用本地节点信息选节点。发错节点会收到 `MOVED` 响应。
- **例子，DNS：** 解析 `example.com` 时返回轮转的 IP 列表，每次请求顺序不同甚至集合不同，不同客户端自然访问不同服务器。同样的思路也能避免负载均衡器自己的单点故障：部署两台均衡器（最好在不同数据中心或区域），用 DNS 轮转，一台挂了，部分客户端会自动尝试另一台（不保证，也可能等很久）。
- **适用：** (1) 客户端数量少且受你控制（Redis Cluster 客户端、gRPC 内部服务的客户端均衡），更新很容易通知；(2) 客户端数量大但能容忍更新慢（DNS）。通知时间随客户端数量增加，DNS 有 TTL（条目有效时间），远端 DNS 服务器可以缓存，所以更新速度不可能快于 TTL。
- **面试里：** 对内部微服务效果很好（gRPC 内置），被问到服务之间的连线细节时一定要提。其他情况需要专用负载均衡器。
