## Q
**在线拍卖 · 中解：Redis 缓存最高价**｜摘要 · 必会

把最高价放进 Redis 解决了什么，又带来什么新问题？

## A
- **流程：** 读 Redis 里这场拍卖的最高价 → 更高就更新缓存 → 把出价写库，状态是接受或拒绝。它避免了每次查 bids 表算最大值、锁一大堆行。
- **原子性：** 读和写必须是一个原子操作。Redis 单线程并支持原子操作，用 Lua 脚本做比较并设置（compare-and-set）：当前最高价取出，新价更大就 SET 并返回真，否则返回假。MULTI/EXEC 本身不行，因为事务里读出的值不能用来决定同一事务里的写。
- **新问题：** 把数据库内部的一致性问题换成了缓存与数据库之间的一致性。缓存说最高价是某个值，但那条出价可能因为失败而没进库。
- **三种处理：**
  - 拍卖期间把 Redis 当作事实来源，异步写库：性能好，牺牲一致性，务实；
  - 先原子更新缓存，再写库，库写失败回滚缓存（乐观并发加重试）；
  - 先写库，再更新缓存，缓存失败就失效，下次读时重建。
- **根本局限：** Redis 与关系库之间没有干净的事务（没有两阶段提交）。需要跨系统原子性时，先想能不能改成都放在一个系统里。
