## Q
**Tinder · 完整解答**｜摘要 · 必会

设计一个类似 Tinder 的约会应用：用户设置偏好，看到附近的候选人叠（stack），左右滑动表达 no / yes，互相右滑就收到匹配通知。给出需求、实体与接口、整体设计、深入问题、各级别期望。

## A
**一句话。** 「推荐流 + 海量滑动写入 + 互相右滑的瞬时判定」：三个难点是互相滑动不能漏匹配、一打开就有候选人、不重复展示滑过的人。

**60 分钟路线。**

| 时间 | 做什么 |
|---|---|
| 0–5 分 | 需求与数字：2000 万日活 × 100 次滑动 = 20 亿次/天，平均约 2.3 万次/秒；每条约 100B，约 200GB/天、一年 73TB，必须分区，适合写优化的存储；滑动强一致，候选叠 < 300ms |
| 5–20 分 | 实体 User / Swipe / Match；`POST /profile`、`GET /feed?lat&long&distance`（位置由客户端传）、`POST /swipe/{userId}`（身份取自 JWT，路径里是被滑的人）；资料服务与独立的滑动服务和库（Cassandra 按 swiping_user_id 分区，写入远多于资料写入，要独立扩缩）；滑动时写入并查反向滑动，有就立刻给后滑的人返回匹配，先滑的人可能已离线，靠 APNS / FCM 推送 |
| 20–50 分 | 必讲：匹配原子性、候选叠低延迟、不重复展示 |
| 50–60 分 | 追问：缓存过期、布隆过滤器、Redis 故障、用户对分区长大 |

**必讲。**
- **匹配原子性：** 竞态：两人同时先检查都没看到对方、再各自写入，匹配永远丢失。轮询数据库有延迟且加负载；Cassandra 轻量级事务只在单分区内成立，20 亿次/天必然跨分区。解法一：分区键用排好序的用户对，互相的滑动落进同一分区；解法二：Redis 以用户对为键，Lua 里先写后读原子完成，Cassandra 留作持久层。也可放弃强一致、定期对账补发，但面试官多半让你回到强一致。
- **候选叠低延迟：** 按经纬度和年龄直接查库太慢；用带地理索引的 Elasticsearch（经 CDC 同步），再加预计算缓存，快刷完时后台续算。缓存会过期（别人搬家改资料、自己改条件）：TTL 小于 1 小时、只为活跃用户预热、条件变化触发刷新。
- **不重复展示：** 只查滑动库做 contains 会因最终一致漏掉新滑动、历史长了越来越慢；客户端缓存最近 K 次滑动补空窗；历史极长的用户再用布隆过滤器。

**追问再讲。** Redis 丢数据要回退查 Cassandra；用户对分区会随时间长大，需归档。

**级别期望。** 中级跑通三条流程并解决去重；高级主动比较 feed 取舍并知道缓存何时过期；Staff 把匹配一致性和 feed 讲出实战细节。
