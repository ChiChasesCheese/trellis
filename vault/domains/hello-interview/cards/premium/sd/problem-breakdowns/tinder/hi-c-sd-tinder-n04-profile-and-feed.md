## Q
**Tinder · 高层设计：建资料与朴素候选叠**｜摘要 · 必会

先用最简单的设计满足"建资料"和"看候选叠"两个功能，朴素的查询长什么样，为什么必须优化？

## A
- **建资料：** 客户端 → API 网关 → 资料服务 → 用户库，保存偏好。网关负责把请求路由到对应服务。
- **候选叠（朴素版）：** 资料服务直接对用户表做范围查询：年龄在区间内、感兴趣的性别一致、纬度和经度都落在当前位置加减最大距离的方框里，把结果返回。
- **为什么慢：**
  - 经纬度是两个维度的范围条件，普通 B 树索引只能高效用上一个维度，另一个维度要大量扫描；
  - 方框比真实圆形大（面积比 4/π ≈ 1.27），还要再做一次精确距离过滤；
  - 每次打开应用都实时查一遍，规模下根本达不到 300ms。
- **口述方式：** 先把这个"能用但慢"的版本画出来满足功能，明说"位置查询是难点，深入时用地理索引和预计算解决"，不要一开始就陷进优化。
