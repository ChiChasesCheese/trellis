## Q
**Strava 运动记录 · 完整解答**｜摘要 · 必会

设计一个类似 Strava 的跑步/骑行记录应用：用户开始、暂停、结束并保存活动，运动中实时看到路线、距离和时间，事后查看自己和好友的活动。要支持同时进行的一千万个活动，在没有信号的野外也能用。给出需求、实体与接口、整体设计、深入问题、取舍。

## A
**一句话。** 这题的关键是看穿"客户端是主角"：运动数据完全可以先记在手机本地，结束或联网时一次性上传。一旦想通，离线、准确的本地统计、后端写入量下降两个数量级这三件事同时解决，后端就只剩一个很普通的服务加一个库。

**60 分钟路线。**

| 时间 | 做什么 |
|---|---|
| 0–5 分 | 需求：开始/暂停/结束保存；运动中看数据；看自己与好友的活动；可用性优先、离线可用、1000 万并发 |
| 5–10 分 | 实体 User / Activity / Route / Friend；PATCH 改状态、POST 上传路线 |
| 10–20 分 | 先画最简版：客户端每隔几秒把 GPS 点传给服务端；用状态日志算用时 |
| 20–40 分 | 必讲：本地先记（内存缓冲 + 每约 10 秒落盘）；规模估算（每年约 500TB）与分片/分层 |
| 40–60 分 | 追问：好友实时观看（轮询优于 WebSocket）；排行榜（Redis 有序集合） |

- **需求**
  - 功能：开始/暂停/结束/保存跑步或骑行；运动中看路线、距离、时间；查看自己和好友已完成的活动。好友管理、认证、点赞评论不做
  - 非功能：可用性远高于一致性；无网络的野外也能用；运动中本地统计准确及时；扩展到 1000 万并发活动
- **实体与接口**：User、Activity（类型、起止时间、距离、时长）、Route（GPS 点集合，可作为 Activity 字段）、Friend；`POST /activities`、`PATCH /activities/:id`（状态 STARTED / PAUSED / COMPLETE）、`POST /activities/:id/routes`、`GET /activities?mode=USER|FRIENDS`、`GET /activities/:id`
- **整体设计**：一个活动服务加一个库。用时不是"结束时间 − 开始时间"（暂停会被算进去），而是存状态变更日志，累加每段运行中的时长；GPS 点用 Haversine 公式算距离；好友列表是 SQL 的 `IN (子查询)`
- **深入一，离线（必讲）**
  - 客户端内存缓冲 GPS 点，每约 10 秒落盘一次，最多丢 10 秒；结束或联网后一次上传，长活动分块
  - 一举解决离线、省电省流量、本地统计即时准确三件事，服务端请求量降约两个数量级
- **深入二，规模**：1 亿日活每天 1 亿活动，每年约 365 亿条；每条路线约 600 个点 × 24 字节 ≈ 14.4KB，年增约 530TB。按完成时间分片、按冷热分层、需要再加缓存；数据库选谁并不关键
- **深入三，好友实时观看**：恢复每 2–5 秒上传，好友轮询而不是 WebSocket，因为更新间隔可预测且几秒延迟可接受；客户端故意滞后一两个周期来平滑动画
- **深入四，排行榜**：全表聚合太慢 → 定期聚合有延迟 → Redis 有序集合 ZINCRBY 实时累加，按国家分多个集合；时间范围过滤要另想办法
- **取舍**：简单一体化服务而非微服务，因为读写没有明显倾斜；难点是 Redis 与主库的一致性、内存占用
