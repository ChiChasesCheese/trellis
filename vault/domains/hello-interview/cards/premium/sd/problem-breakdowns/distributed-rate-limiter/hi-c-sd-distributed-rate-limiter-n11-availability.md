## Q
**分布式限流器 · 深入二：高可用与失败模式**｜摘要 · 必会

分片挂掉时，放行（fail-open）和拒绝（fail-closed）各有什么风险？这个系统选哪个，怎样降低故障概率？

## A
- **问题：** 分片一挂，归属该分片的所有客户端都失去限流，还可能引起级联故障（用户激进重试）。
- **fail-closed（拒绝）：** 连不上 Redis 就返回 503 或 429，没验证过的一律不放。风险：相当于让 API 下线，后端明明健康；用户收到错误会更激进地重试。适合支付、高安全这类"没有保护宁可不服务"的场景。
- **fail-open（放行）：** 当作没有限流直接转发。风险：失去保护；若 Redis 是因为负载高而挂，所有流量涌向后端，可能引发整个系统崩溃，社交平台遇到热点事件时尤其危险。
- **这个系统的选择：** 两者都算合理，取决于需求。该社交平台选 fail-closed：限流故障常与流量高峰同时发生，恰好最需要保护，短暂拒绝好过整个平台崩溃。
- **更根本的是预防：** 每个分片配一个或多个副本做主从复制，主挂了自动提升一个副本；Redis Cluster 自带故障检测和提升。代价是成本和复制延迟（通常很小）。
- **监控告警：** 看 Redis 的 CPU、内存、网络，以及限流成功率、延迟，并对"进入放行状态"告警。
