## Q
**分布式限流器 · 失败时不只是二选一：降级到本地近似限流**｜拓展 · 加分

Redis 不可用时，除了全部放行或全部拒绝，还有第三种做法吗？限流调用本身的超时应该怎么设？

## A
- **第三种：降级模式。** 网关内存里保留一个粗糙的本地限流器：把全局限额除以网关数当作每台的限额（100 次/分钟、5 个网关就每台约 20 次），Redis 恢复前用它顶着。精度差，但挡得住大流量冲击，也不会让 API 下线。这和"进程内限流"的缺点相同，但只是应急，差一点可以接受。
- **配合熔断：** 对 Redis 的调用要设很短的超时（预算是总延迟 10ms 的一小部分，比如几毫秒），连续失败达到阈值就熔断，直接走降级，隔一会儿放少量探测请求看 Redis 是否恢复，避免每个请求都傻等超时。
- **为什么超时必须短：** 限流在每个请求的关键路径上，如果 Redis 变慢但没挂，等 100ms 比拒绝更伤——整个 API 的尾延迟都被拖垮，请求堆积后反而压垮网关。
- **取舍：** 降级比二选一更复杂，但按客户端类型区分更好：对高风险端点（登录、支付）选 fail-closed，对读多的端点选降级放行。
- **模式。** 优雅降级：核心依赖挂掉时，退到精度更低但自给自足的备份路径。
