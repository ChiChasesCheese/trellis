## Q
**分布式限流器 · 完整解答**｜摘要 · 必会

设计一个分布式限流器（rate limiter）：对一个社交平台的 API 请求，按用户、IP 或 API key 套用可配置的规则，超限时返回 HTTP 429。目标是每秒 100 万请求、1 亿日活。给出需求、接口、整体设计、深入问题、各级别期望。

## A
**一句话。** 这是"每个请求都要做一次原子读改写"的题：难点不在算法本身，而在 100 万次/秒的共享计数怎么分片、怎么原子、挂了怎么办、延迟怎么压到 10ms 内。

**60 分钟路线。**

| 时间 | 做什么 |
|---|---|
| 0–5 分 | 先问规模；需求：识别客户端、按规则限流、超限返回 429；延迟小于 10ms、高可用、最终一致可接受 |
| 5–10 分 | 实体 Rules / Clients / Requests 与一个接口 `isRequestAllowed` |
| 10–25 分 | 放哪里（网关）、怎么识别客户端、选算法（令牌桶）、状态放 Redis |
| 25–50 分 | 必讲：Lua 脚本原子化；分片到 10 个以上 Redis；失败时放行还是拒绝；压延迟 |
| 50–60 分 | 追问：热点键、动态规则、多区域、监控 |

- **需求**
  - 功能：按用户 ID、IP 或 API key 识别客户端；按可配置规则限制请求（如每用户每分钟 100 次）；超限返回 429 并带剩余次数、重置时间等响应头
  - 非功能：每次检查增加小于 10ms；高可用，最终一致可接受（各节点执行限额晚一点没关系）；100 万次/秒，1 亿日活，约每人每天 864 次
  - 必须在服务端限流：客户端不可信；客户端限流只是补充
- **实体与接口**：Rules（规则）、Clients（被限流的对象）、Requests；`isRequestAllowed(clientId, ruleId) → {passes, remaining, resetTime}`
- **整体设计**
  - 放网关：请求先过限流再到应用，被拦的请求应用服务器看不到；进程内每台只看到自己的流量，独立服务多一跳且多一个故障点
  - 客户端识别：登录用户看 JWT，匿名看 IP（`X-Forwarded-For`），开发者看 `X-API-Key`；多条规则叠加，取最严格的
  - 算法选令牌桶：每客户端只存（令牌数，上次补充时间），既限制长期速率又容纳突发；固定窗口有边界突发、滑动日志耗内存、滑动窗口计数器是近似
  - 状态放 Redis 让所有网关共用；读、算、写必须放进一个 Lua 脚本才不会有竞态（MULTI/EXEC 不够，读在事务外）
  - 超限立刻 429，不排队；头里给 Limit、Remaining、Reset、Retry-After
- **深入一，扩到 100 万次/秒（必讲）**：单个 Redis 约 10–20 万次操作/秒；按客户端标识哈希分片，同一客户端永远落同一分片；生产用 Redis Cluster 的 16384 个哈希槽
- **深入二，高可用（必讲）**：分片挂了放行（fail-open）会把流量全压向后端，拒绝（fail-closed）等于下线 API；每个分片配主从自动故障转移；监控进入放行状态的告警
- **深入三，延迟（必讲）**：连接池、就近部署；本地缓存状态有风险
- **追问再讲**：热点键（合法大客户与滥用分别处理）；动态规则（拉取 30 秒 vs 推送）
- **级别**：中级讲清一种算法、网关、Redis 与分片；高级讲清取舍、原子性、故障模式；Staff 讲运维、多区域与灰度
