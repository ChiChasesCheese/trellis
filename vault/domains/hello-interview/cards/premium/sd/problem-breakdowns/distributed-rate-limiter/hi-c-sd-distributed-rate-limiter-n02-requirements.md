## Q
**分布式限流器 · 需求与规模**｜摘要 · 必会

设计分布式限流器，开场要确认什么？功能和非功能需求是什么，为什么坚持服务端限流？

## A
- **先问规模：** 是每天几千次请求的小 API，还是每秒百万次的大平台？规模会彻底改变设计。这里取每秒 100 万请求、1 亿日活，换算每人每天约 864 次（100 万 × 86,400 ÷ 1 亿）。
- **范围：** 社交平台的 API，限制的是单个 HTTP 请求（发帖、拉时间线、上传图片），而不是更高层的业务动作。
- **功能：**
  - 用用户 ID、IP 或 API key 识别客户端，套用合适的限额；
  - 按可配置规则限流，如每用户每分钟 100 次；
  - 超限返回 429，并带剩余次数、重置时间等响应头。
- **范围外：** 对限流数据的复杂查询或分析、限流数据的长期持久化。
- **非功能：**
  - 每次检查引入的延迟小于 10ms，因为它在每个请求的关键路径上；
  - 高可用，允许最终一致：各节点之间执行限额晚一点是可以接受的；
  - 处理 1M 请求/秒。
- **为什么服务端：** 客户端不可信，不会自觉限速，安全和保护系统必须靠服务端；客户端限流（SDK 里自带）只是补充，能减少无谓流量。
