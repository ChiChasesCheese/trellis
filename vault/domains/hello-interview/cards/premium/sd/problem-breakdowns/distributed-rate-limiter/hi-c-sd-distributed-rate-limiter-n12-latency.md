## Q
**分布式限流器 · 深入三：压低每次检查的延迟**｜摘要 · 必会

每个请求多一次到 Redis 的往返，怎么把延迟压住？哪些优化是首选，哪些要谨慎？

## A
- **根因：** Redis 操作本身是亚毫秒，但网络往返会增加几毫秒，100 万次/秒下就明显。
- **首选一，连接池：** 网关维持一组持久连接，避免每次检查都建新 TCP 连接，省掉握手开销（根据网络距离可达 20–50ms）。多数 Redis 客户端自带池，要按请求量和 Redis 响应时间调池大小。
- **首选二，就近部署：** API 网关和 Redis 集群部署到多个区域，东京的用户别去访问弗吉尼亚的 Redis。代价是跨区域数据一致，但限流可以接受区域间最终一致，换更低的延迟。
- **谨慎使用：**
  - 在网关本地缓存限流状态：可行，但缓存过时会导致判断错误；
  - 用 Redis 流水线（pipelining）或 Lua 脚本合并命令，减少往返；
  - 请求批处理：同一用户的多个请求合并检查。
  - 这些增加复杂度，连接池和就近部署做好后通常不必要，面试里除非被问到，可以不展开。
