## Q
**在线象棋 · 深入二：状态放共享库，用 Redis pub/sub 送走法**｜摘要 · 必会

如果不要求同一局的两人连同一台服务器，要怎样保证正确？为什么还是倾向把状态留在一台机器上？

## A
- **做法：** 棋盘与棋钟放共享存储，任何服务器都能处理走子。风险是并发：Alice 开两个标签页发两步不同的合法走法，只能接受一步。
- **版本号：** 读局面与版本，校验后**仅当版本未变才提交**；Postgres 事务里同时检查当前步序号，重复或过期的请求只拿回当前状态。若用 Redis 缓存棋盘也要存版本，写缓存同样条件更新，否则延迟的旧写会盖掉新棋盘。不同服务器接力处理，棋钟也需要共享的时间源，不能各用自己进程的计时器。
- **送给对手：** 存好后发布到该局的 Redis pub/sub 频道，对手那台订阅后经 WebSocket 转发。pub/sub 不保留断线订阅者的消息，所以客户端靠步序号发现缺口，重连时拉最新状态，还要定期核对版本（缺口之后可能没有新消息来暴露它）。
- **代价与倾向：** 每步多了取共享状态、版本检查、发布这几次往返。**单机持有对局**时逐步处理，没有多服务器抢同一棋盘，不需要版本检查和缓存协调，走子直接走已有的 WebSocket。复杂度推到连接或服务器变化时（路由、恢复）处理，两种答案都可接受，要说清所选的代价。
