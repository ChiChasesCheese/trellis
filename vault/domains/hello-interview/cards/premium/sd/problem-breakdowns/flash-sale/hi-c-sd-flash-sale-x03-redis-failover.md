## Q
**限时抢购 · 故障：Redis 主节点宕机，从节点落后了一些扣减**｜考点 · 必会

选用了 Redis 计数器方案。主节点在大促中崩溃，从节点晋升，但它落后主节点 N 次扣减（异步复制）。会出什么事？怎么兜底？

## A
- **后果：** 晋升后的计数器比真实值多 N，也丢了这 N 个预留记录（如果也存在 Redis）。后续多发出 N 个预留，**超卖约 N 件**；已经收到预留的用户可能发现预留凭据在新主上不存在。
- **原因：** Redis 默认异步复制，主节点确认写入后才同步给从节点，故障时最近的写入可能没到；这就是"Redis 变成真相来源"的代价。
- **兜底一：** 在抢购期间让关键写入落一份到持久的库（如预留记录入库，库存以库为准），Redis 只做快速闸门；购买时以库为最终裁判，核对"已确认的预留数 ≤ 库存"。
- **兜底二：** 晋升后用数据库重建计数器：库存总数减去库里有效预留数，再放开流量。
- **兜底三：** 用 `WAIT` 要求同步写副本，能减小窗口但不能消除，还会拖慢关键路径。
- **对比：** 每件库存一行、用 `SKIP LOCKED` 领取的方案（ReservationUnit）没有这个问题，因为库存和预留在同一事务里提交，崩溃不会丢失其中一半。
