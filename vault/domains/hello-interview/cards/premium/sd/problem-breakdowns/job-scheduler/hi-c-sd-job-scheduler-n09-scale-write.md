## Q
**分布式任务调度器 · 深入二：创建路径与数据库的扩展**｜摘要 · 必会

从左到右检查瓶颈：作业创建服务和作业数据库怎么扩？热分区怎么避免？

## A
- **方法：** 从左到右逐个组件找瓶颈并逐个解决。
- **作业创建：** 上界是每秒 1 万次创建（实际更低，因为有周期作业）。该问面试官一次性与周期作业的比例；一次性多，创建服务才可能成为瓶颈。
  - 可以在 API 和创建服务之间加 Kafka/RabbitMQ 做缓冲和削峰；
  - 但这很可能过度设计：数据库本来就能承受写入，前面总要有可水平扩展的服务；除非创建里有昂贵逻辑要隔离，否则直接扩服务更简单。队列是可选的。
- **Jobs 表：** 分区键 job_id，每个作业 ID 唯一，写入自然均匀。
- **Executions 表：** 分区键是小时桶，当前这个小时的所有写落在同一分区（DynamoDB 单分区上限约 1000 WCU）。解决：写分片，在分区键后加随机后缀（`time_bucket#shard_3`），把写分摊到多个分区；worker 并行查询该时间桶的全部分片。
- **冷数据：** 执行完的记录要保留供用户查询，过了合理时间（如 1 年）搬到更便宜的存储，如 S3。
- **模式。** 写分片：用随机后缀把一个热键打散成多个，代价是读要汇总。
