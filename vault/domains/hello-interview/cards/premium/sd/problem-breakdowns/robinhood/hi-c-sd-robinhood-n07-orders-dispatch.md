## Q
**股票交易平台 · 下单路径：直发、经队列与订单网关**｜摘要 · 必会

订单怎么送到交易所？直发交易所、经队列、订单服务加网关三种方案各有什么问题和优势？

## A
| 方案 | 做法 | 问题 |
|---|---|---|
| 客户端直发交易所（差） | 手机直接调交易所 | 交易所客户端和并发请求暴增，成本极高；客户端没法查订单状态，只能轮询交易所或直听成交流，两者都不可行；订单只记在客户端，卸载应用或手机坏了就丢 |
| 经队列交给派发服务（好） | 订单服务入队，派发服务代理交易所，队列长度驱动弹性扩容 | 流量突发、扩容未完成时订单排队，延迟可能超过 200ms；用户想快速下单或撤单却在等扩容，交易敏感时段不可接受 |
| 订单网关（最好） | 订单服务直接向交易所发起调用，出口经 NAT 网关（如 AWS NAT Gateway 加弹性 IP），交易所看到的只是少数几个 IP | 订单服务要同时兼顾客户端交互和交易所交互效率（例如把订单批在一起）；因为它直接承担流量，扩容阈值要敏感，如平均 CPU 50% 就扩，或者多预留容量吸收尖峰 |

- **关键点：** 客户端不能可靠地保存订单；订单必须有我们自己的记录；低延迟下单不能依赖等待扩容。
- **订单服务的责任：** 运行订单业务逻辑，同步拿到交易所返回的外部订单号。
