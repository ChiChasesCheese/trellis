## Q
**股票交易平台 · 完整解答**｜摘要 · 必会

设计一个股票交易平台（类似 Robinhood）：用户实时看股价，下限价单或市价单并能撤单。给出需求、实体与接口、整体设计、深入问题、各级别期望。

## A
**一句话。** 我们是券商不是交易所：把用户请求代理给外部交易所。难点只有两个：把一路行情推给几百万在线用户，以及订单在"我们的库"和"交易所"之间崩溃了也不能对不上。

**60 分钟路线。**

| 时间 | 做什么 |
|---|---|
| 0–5 分 | 澄清交易所接口（同步下单撤单、推送成交流），收需求并报数 |
| 5–10 分 | 实体（用户、股票、订单）与四个接口 |
| 10–25 分 | 高层设计：行情走缓存加 SSE；订单走订单服务直连交易所，订单库按用户分片 |
| 25–55 分 | 必讲深入：行情路由；订单状态怎么跟踪；下单撤单的一致性 |
| 55–60 分 | 追问：过量行情、批量下单、实时订单状态、历史数据 |

- **需求**
  - 功能：看实时股价；创建（市价、限价）、撤销、列出订单。盘外交易、期权加密货币、盘口深度放在范围外
  - 非功能：订单强一致；2000 万日活每人日均 5 笔，约 1 亿笔每天（平均约 1157 笔/秒）；行情和下单延迟小于 200ms；尽量少的交易所连接，因为很贵
- **实体与接口**
  - 用户、Symbol、Order；价格用整数 `priceInCents` 避免浮点误差
  - `GET /symbol/:name`、`POST /order`、`DELETE /order/:id`、`GET /orders`；身份来自 JWT，不信请求里的 userId
- **行情**
  - 直接轮询交易所不可行（重复调用、更新慢）；轮询内部缓存仍有延迟；最好是 SSE 单向推送，缓存给初始快照，处理器监听交易所推成交价
- **订单**
  - 直发交易所连接数暴涨且客户端不可靠；经队列在洪峰时延迟不可控；最好是订单服务直接调交易所，出口走 NAT 网关收敛 IP
  - 订单库为关系型，按 userId 分片，含 `externalOrderId`；成交流由交易流处理器消费
- **深入一，行情路由（必讲）**：每台符号服务维护"符号到用户集合"，向 Redis 发布订阅按符号订阅，没人订就退订
- **深入二，订单更新（必讲）**：库按 userId 分片，查不到外部订单号；加键值库（RocksDB）存 `externalOrderId` 到 `(orderId, userId)` 的映射
- **深入三，一致性（必讲）**：先落 pending 再提交；提交后写库失败靠清理任务，用 `clientOrderId` 向交易所对账；撤单先标 pending_cancel
- **级别**
  - 中级：功能设计加知道代理交易所；高级：快速过设计，深讲行情传播和订单容错；Staff：技术选型有实战依据，主动选方向
