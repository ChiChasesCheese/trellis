## Q
**ChatGPT · 故障：工作者生成到第 300 个 token 时崩溃**｜考点 · 追问

工作者在 Run 已向 Stream 写了 300 个 token 后崩溃。如果队列把这个 Run 重新派给另一个工作者，从头生成并继续 `XADD` 到同一个 Stream，客户端会看到什么？怎么设计才正确？

## A
- **问题：** 模型采样有随机性，第二次生成的开头和第一次通常不同。新工作者的第 1 个 token 被追加在已有的 300 个之后，客户端读到的是两次生成的拼接，文字乱掉。
- **做法一：每次尝试一个新 Stream 或新条目前缀：** key 带 attempt 编号，新尝试开始时先写一个"重置（reset）"事件，客户端清掉已显示的内容再接新的；也可以让聊天服务把 Run 标成 failed 并让用户手动重试。
- **做法二：** 只在**尚未输出任何 token 时**自动重试（排队阶段或预填充阶段失败），已开始输出就走 failed 或重置。
- **做法三，接着写：** 新工作者读出流里已有的 300 个 token，把提示加这 300 个 token 重新预填充，从第 301 个继续；已发出的文字是事实，不会改变，客户端看到的是连续回答，代价是多一次预填充。
- **计量：** 失败的尝试也消耗了 GPU，配额按实际消耗还是只按成功结果收，是产品决策；至少要记录 token 数。
- **要点：** 重试必须幂等：同一个 runId 同时只允许一个活动尝试，派发时用条件更新抢占（`WHERE status='queued'`），防止两个工作者同时跑。
