## Q
**ChatGPT · 完整解答**｜摘要 · 必会

设计 ChatGPT：用户发送提示词，大语言模型把回答逐字流式返回，对话被保存，用户能回到旧对话继续聊。把模型当黑盒，设计它外围的服务系统。给出路线、需求、接口、整体设计、深入问题和各级别期望。

## A
**一句话。** 业务逻辑很薄，难点全在「服务一个昂贵、稀缺的 GPU 池」：首个 token 要快、流要能断线续传、GPU 要排队调度并公平分配、对话越长成本越高要压住。

**60 分钟路线。**

| 时间 | 做什么 |
|---|---|
| 0–5 分 | 需求与规模：首 token < 500 ms；2 亿日活，峰值约 2 万提示词/秒，一次回答约 6 秒，按 Little 定律约 12 万路并发流；可用性优先 |
| 5–20 分 | 实体 User / Chat / Message，接口；朴素同步设计（聊天服务无状态，推理服务是 GPU 池），点出两个缺口：最长 30 秒空白屏，没有准入控制 |
| 20–55 分 | 必讲：SSE 流式 + Run、续传、队列与连续批处理、按 token 计费的公平、上下文成本 |
| 55–60 分 | 追问：取消、推测解码、审核 |

**必讲。**
- **流式：** 轮询让首 token 受间隔拖累（12 万路每 300 ms 一次 = 40 万请求/秒）；WebSocket 太重；SSE 单向、纯 HTTP、可自动重连。`POST` 立刻返回 `runId`（Run 是一次生成尝试，有排队、流式、完成、取消、失败的生命周期），客户端 `GET /runs/{id}/stream`；工作者到聊天服务走 gRPC 服务端流。
- **续传：** pub/sub 发射即忘，换实例的空窗期会丢 token；改用 Redis Stream（`XADD` 增量，`XREAD` 从最后见到的 ID 续读，`MAXLEN` 和 TTL 控内存）；最终消息写 Postgres 才是真相。
- **GPU 调度：** 请求入队、工作者拉取；连续批处理让一块 GPU 同时推进几十条序列；队列限深，超限拒绝（背压）。
- **公平：** 全局限流让一个人拖垮所有人，每用户限流只数请求不数成本；用按 token 的桶，入场先扣输入加预留最大输出，结束后退还；付费层优先但给免费层留保底。
- **上下文成本：** 50 轮 × 500 token，最后一轮要发约 2.5 万输入 token，越聊越贵还会超窗口；截断便宜但突然失忆；前缀缓存（复用稳定前缀的 KV cache）同时降成本和首 token 延迟；滚动摘要保住窗口，代价多一次便宜模型调用，别每轮重写否则缓存失效。

**追问再讲。** 取消用显式 `POST /runs/{id}/cancel`，关标签页不等于取消。

**级别期望。** 中级同步设计加想到 SSE 和队列；高级讲清 SSE 对 WebSocket、队列加连续批处理，并提摘要或截断；Staff 自带 GPU 经济账、前缀缓存，区分「用户间公平」与「层级优先」。
