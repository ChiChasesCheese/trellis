## Q
**ChatGPT · 深入五：对话变长时怎样控制成本又不失忆**｜摘要 · 必会

对话越长每轮越贵，还会超窗口。截断、前缀缓存、滚动摘要各是什么，怎么组合？

## A
- **问题：** 50 轮、每轮约 500 token，下一轮要发约 2.5 万输入 token，每次调用都计费；超出上下文窗口则根本放不下。
- **截断（好但失忆）：** 只留最近 N 轮，一次有界的 `ORDER BY createdAt DESC LIMIT N`，再翻回时间顺序。成本有界，但助手在第 N+1 轮突然什么都不记得。
- **前缀缓存（prefix caching）：** 同一对话相邻两轮，系统提示和已说的话几乎完全相同；推理服务可缓存稳定前缀的中间状态（KV cache）并复用，只处理最新消息。既降成本也降延迟（直接帮助首 token），配合对话感知路由，把同一对话发到前缀仍热的工作者。要管理：显存有限，前缀按 LRU 淘汰，沉默很久再回来的对话要整段重算。
- **2026 亮点：** 自建推理时前缀缓存已是默认能力：vLLM 用块哈希链自动复用共享前缀，几乎没有额外开销。多副本时普通轮询会把同一对话打散、命中率暴跌，所以网关层要做缓存感知路由（K8s Inference Gateway 的 endpoint picker、llm-d），同会话尽量粘到同一副本，同时防止热点副本被打满；多租户用 cache_salt 隔离，避免通过命中时延探测别人的前缀。
- **滚动摘要：** 最近几轮逐字保留，更早的压缩成运行中的摘要：系统提示 → 摘要 → 最近几轮 → 新消息。后台更新。它让提示保持在窗口内；前缀缓存让稳定部分便宜。
- **代价：** 摘要要额外调一次（更便宜的）模型，且会丢细节；每轮重写摘要会让前缀缓存失效，所以更新要放慢。原则：把质量损失花在旧的低价值上下文，不花在最近的。
