## Q
**协同文档编辑 · 完整解答**｜摘要 · 必会

设计一个多人协同的在线文档编辑器（类似 Google Docs）：多人同时编辑同一篇文档，实时看到彼此的修改和光标。给出需求、实体与接口、整体设计、深入问题、各级别期望。

## A
**一句话。** 核心是"并发编辑怎么收敛成同一份文档"：把每次修改当作操作（operation）发给一台固定的服务器，由它用操作转换（OT）排定顺序并持久化；后面的难点是百万级 WebSocket 连接怎么摊开、操作日志怎么压缩。

**60 分钟路线。**

| 时间 | 做什么 |
|---|---|
| 0–5 分 | 收需求：每篇文档最多 100 个并发编辑者，延迟小于 100ms，最终一致 |
| 5–10 分 | 实体（编辑者、文档、编辑、光标）与 REST 加 WebSocket 消息 |
| 10–30 分 | 高层设计：建文档；编辑为什么不能发快照；OT 对 CRDT；读路径；光标 |
| 30–55 分 | 必讲深入：一致性哈希加 ZooKeeper 摊开连接；快照压缩 |
| 55–60 分 | 追问：只读模式、版本历史、内存、离线 |

- **需求**
  - 功能：建文档；多人并发编辑；实时看到修改；看到他人光标和在线状态。权限、富文本、历史版本放在范围外
  - 非功能：最终一致；更新延迟小于 100ms；百万并发用户、数十亿文档；单文档并发编辑者不超过 100；服务重启后文档仍在
- **实体与接口**
  - 编辑者、文档、编辑（Edit）、光标；`POST /docs` 建文档；`WS /docs/{docId}` 上发 insert、delete、updateCursor，下收 update
- **编辑的一致性**
  - 每次发整篇快照：流量巨大，且后到的覆盖先到的，丢修改
  - 只发位置编辑：编辑依赖产生时的文档状态，乱序后会删错字符
  - OT：服务器把后到的编辑按前面已落地的编辑平移位置；省内存、适合文本，但要中心服务器排序、实现易错
  - CRDT：位置用可无限细分的唯一标识，删除留墓碑，任意顺序都收敛；无需中心但内存只增不减。这里选 OT
  - 写路径：服务器转换后追加写入 Cassandra（按文档分区、按时间排序），落盘再确认，满足持久性
- **读路径与光标**
  - 连接建立时回放历史操作；之后每个新操作落盘后广播给同服务器上同文档的所有连接；客户端也要做 OT
  - 光标和在线状态是瞬时的：只放内存，经同一 WebSocket 广播，断线即移除
- **深入一，连接（必讲）**：一致性哈希环加 ZooKeeper，每篇文档固定落在一台服务器，错了就重定向后升级为 WebSocket；伸缩时需要搬状态
- **深入二，存储（必讲）**：50KB × 10 亿篇 = 50TB，且大文档的几百万条操作每个新连接都要重放；周期性压缩成一条。离线压缩要版本号翻转加协调；在线压缩由持有文档的服务器在最后一人离开时做，更好
- **级别**
  - 中级：通常不问；高级：看出一致性与持久性难点，会讲数据库取舍；Staff：精通套接字服务伸缩、一致性、事务、序列化问题
