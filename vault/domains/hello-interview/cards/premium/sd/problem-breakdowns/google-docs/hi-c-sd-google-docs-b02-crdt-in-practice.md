## Q
**协同文档编辑 · 拓展：CRDT 工程上怎么控制元数据膨胀**｜拓展 · 加分

纯理论的文本 CRDT 每个字符一个条目，实际库（如 Yjs）怎么让它可用？还有什么坑？

## A
- **合并相邻字符：** 同一个作者连续输入的字符，在逻辑上可以合并为一个条目（一段文本），元数据按"段"计，而不是按"字符"计，大幅降低内存。
- **垃圾回收墓碑：** 当所有副本都已见过某个删除，就可以安全回收墓碑；这需要知道各副本的进度，在点对点环境里难以确定。
- **交错问题（interleaving）：** 两人同时在同一位置输入一个词，朴素算法可能把两个词的字母交错在一起（如 `Hello t,here!` 这类结果）。较新的序列 CRDT 算法专门设计来避免这种交错，让每个人连续输入的内容保持连在一起。
- **状态同步：** 新节点加入时，传输整个状态向量或增量，而不是重放全部历史。
- **选型含义：** 即使选了 CRDT，仍然需要持久化、压缩和版本管理，这些并不会自动消失。
- **一般原则：** 理论上的"无需中心"在工程上通常被"有一个中心服务器做持久化和中继"补强，但冲突解决仍然是去中心的。
