## Q
**协同文档编辑 · 预测：负责某文档的服务器突然崩溃**｜考点 · 必会

一台文档服务崩溃，它承载 3 万个连接、2 千篇活跃文档。哪些数据会丢，哪些不会？客户端发出去但尚未确认的编辑怎么办？

## A
- **不丢：** 已确认的操作已落进 Cassandra，那是持久的；文档元数据在 Postgres。
- **丢失：** 内存中的状态：连接、光标和在线状态（本来就是瞬时的）、以及尚未落盘的操作。这些操作用户没收到确认。
- **恢复：** 哈希环更新后，这些文档由新的服务器接手。客户端检测到断开后重连，被重定向到新的负责服务器；新服务器从操作库加载这篇文档的全部操作。
- **未确认的编辑：** 客户端保留本地待确认队列，重连后把这些编辑重发。因为服务器可能在落盘后、确认前崩溃，同一编辑可能已存在，需要给每个操作一个唯一 ID，服务器按 ID 去重，保证重发幂等。
- **光标：** 重连后各客户端重新上报光标，在线状态自动恢复。
- **风险：** 3 万个客户端同时重连是惊群，需要重连退避加随机抖动，避免压垮接手的服务器。
- **模式。** 日志是事实，内存是缓存：服务器可任意重启，持久性靠追加日志。
