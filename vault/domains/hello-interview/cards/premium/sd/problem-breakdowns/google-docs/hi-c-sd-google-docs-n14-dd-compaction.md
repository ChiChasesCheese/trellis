## Q
**协同文档编辑 · 深入二：离线压缩与在线压缩**｜摘要 · 必会

离线压缩服务和文档服务在线压缩各怎么做，正确性靠什么保证，各有什么代价？

## A
| 方案 | 做法 | 代价 |
|---|---|---|
| 离线压缩服务（好） | 压缩服务定期读出操作，折叠后写回；挑选大、久未压缩、近期没写入的文档 | 压缩会改动后续操作，必须不影响正在编辑的文档；Cassandra 只有行级事务，所以引入元数据库里的 `documentVersionId`：加载文档前先取版本号，新操作写入新版本，再翻转版本号；翻转都经过文档服务；文档已加载则丢弃翻转命令，推迟压缩。编排里容易藏 bug，且压缩服务本身是大量读写，要限流 |
| 在线压缩（最好） | 文档服务拥有文档的独占权，所以压缩无需协调；最自然的时机是文档空闲、无连接时。最后一个客户端断开时，把已在内存里的全部操作交给一个低优先级（nice）的独立进程压缩，用新的 `documentVersionId` 写回库，再翻转元数据库里的版本号 | 压缩进程占 CPU，可能抬高操作的尾部延迟（p99），所以放进独立低优先级进程 |

- **要点：** 压缩的难点不是折叠算法，而是"不能和实时写入冲突"；让唯一的写入者（文档服务）自己做，就不需要分布式事务。
- **独占前提：** 这条论证只在集群没有扩缩容的时候成立，扩缩容期间文档可能换主，要注意。
