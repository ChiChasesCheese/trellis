## Q
**协同文档编辑 · 深入二：存储为什么需要控制**｜摘要 · 必会

文档操作日志为什么会成为存储和内存问题？压缩（snapshot/compact）的思路是什么？

## A
- **规模：** 数十亿篇文档，若每篇 50KB，就是 50TB。OT 比 CRDT 已经省了一个系数，但仍然大。
- **更糟的是长日志：** 一篇有几百万条操作的文档，每个新连入的客户端都要传输并应用这几百万条。
- **内存：** 所有活跃文档都要装进文档服务的内存，空间必须小，否则内存成为瓶颈。
- **思路：** 周期性对操作做快照或压缩（compact），把许多操作折叠成一条，同时节省处理和空间。除非需要版本历史，否则不必保留原始的全部操作。
- **有多种实现：** 离线压缩服务和文档服务在线压缩两种，核心区别是由谁负责避免压缩与实时写入冲突。
