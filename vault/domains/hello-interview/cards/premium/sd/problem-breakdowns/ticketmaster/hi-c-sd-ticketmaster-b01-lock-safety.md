## Q
**票务系统 · 拓展：Redis 锁怎么释放才安全**｜拓展 · 加分

用 `SET NX EX` 做占座锁，释放锁时直接 `DEL` 有什么隐患？Redlock 和围栏令牌（fencing token）又是怎么回事？

## A
- **直接 DEL 的隐患：** A 的锁已过期，B 拿到了同一个键；A 此时执行 `DEL`，把 B 的锁删了，C 又能进来。
- **正确做法：** 值存随机的持有者标识（或用户 ID 加请求 ID）；释放用 Lua 脚本，先比较值再删除，保证「比较并删除」原子。
- **更根本的问题：** 锁是靠时间限制的租约，持有者可能因 GC 停顿或网络延迟，在锁过期后仍以为自己持锁。Redis 单点或异步复制主从故障转移时，锁也可能丢。
- **围栏令牌：** 每次获取锁得到一个递增的号，写数据库时带上号，存储端拒绝比已见过的更小的号。
- **对票务的意义：** 数据库事务里的 OCC（只有票仍是预期状态时才更新）就起到围栏的作用，所以 Redis 锁只是优化体验，正确性不依赖它。
- **Redlock：** 多个独立 Redis 节点多数派加锁的算法，对时钟和暂停的假设有争议；票务这类有数据库兜底的场景不必引入。
