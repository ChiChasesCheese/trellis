## Q
**通知系统 · 高层设计一：直发与定时发送**｜摘要 · 必会

同步版的单条通知怎么发？推送与邮件、短信有什么不同？定时发送最小做法是什么？候选人最常犯的概念错误是什么？

## A
- **组件：** API 网关（验 API Key、限流，防止某个失控服务拖垮验证码）→ 通知服务（查联系方式、持久化、调用服务商）→ 数据库（通知行加同步来的部分用户数据，Postgres 即可，没有特殊要求）→ 邮件服务商。
- **流程：** 调用方 POST → 网关认证转发 → 服务查邮箱 → 写一行 `PENDING` 再调服务商 → 按响应更新为 `SENT` 或 `FAILED` → 返回 200 和状态。短信几乎相同，只是查电话号码。
- **推送：** 要把设备令牌交给 APNs（苹果）或 FCM（谷歌）。令牌会轮换，用户服务没有稳定数据可同步，所以移动端在登录和令牌变化时直接上报，保存在我们这边，之后发送与邮件同形，只是查令牌。
- **定时：** 写成 `SCHEDULED` 就停，不调服务商；新增一个每分钟扫描通知表的 cron，把到点的行送进同一条发送路径。分钟级粒度够用，秒级要求的验证码走同步请求，根本不碰 cron。
- **最常见的错误：** 把通知平台和投递服务商混为一谈。平台是路由器加记账员：决定发什么到哪，记录发生了什么；运营商关系和设备长连接归 APNs、Twilio、邮件服务商。去设计手机长连接是在解另一个更难的问题，除非需求就是要它，所以需求阶段要说清。
