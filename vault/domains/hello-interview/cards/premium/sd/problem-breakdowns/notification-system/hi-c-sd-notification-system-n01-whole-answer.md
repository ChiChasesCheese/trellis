## Q
**通知系统 · 完整解答**｜摘要 · 必会

设计一个通知系统：公司内部其他团队通过它给用户发推送、邮件、短信，可以立刻发或定时发，也可以对一个人群发活动（campaign）。给出需求、实体与接口、整体设计、深入问题、各级别期望。

## A
**一句话。** 这是内部平台题，系统自己只是"路由器加记账员"，最后一公里归服务商；真正的难点有三个：接受了的通知绝不能丢，验证码要在大促洪峰里 5 秒送到，至少一次投递之上还要尽量不重复。

**60 分钟路线。**

| 时间 | 做什么 |
|---|---|
| 0–5 分 | 收需求，报数：日 1000 万条，洪峰每秒 5000 条（约 50 倍） |
| 5–10 分 | 实体（通知、活动、人群、用户）与三个接口 |
| 10–20 分 | 先搭同步版：直发、定时 cron、活动扇出、偏好检查 |
| 20–50 分 | 必讲深入：不丢、优先级隔离、去重 |
| 50–60 分 | 追问：发送时间优化、频率上限、取消活动、按时区发 |

- **需求**
  - 功能：向单个用户发推送、邮件、短信，立即或定时；向人群发活动；用户设渠道退订与免打扰时段。模板、数据看板、站内信、频率上限放在范围外
  - 非功能：至少一次投递加尽力去重（宁可重复，不可丢失）；洪峰每秒 5000 条；高优先级（验证码、安全提醒）接受后 5 秒内送出，大促期间也是
- **实体与接口**
  - 通知（一人一渠道一条）、活动（定义）、人群、用户；活动与通知是"定义和实例"的关系
  - `POST /notifications`（用户、渠道、优先级、内容、可选定时）；`POST /campaigns` 立即返回 202；`PUT /users/{id}/preferences`
- **同步版设计**
  - 网关验 API Key 并限流；通知服务查联系方式、写库、调服务商；定时发送写成 SCHEDULED，由每分钟的 cron 捞出；活动由 cron 读人群快照后逐个走同一发送路径；偏好在调用服务商前检查，被拦截的记为 SUPPRESSED 并写原因
  - 三个毛病：服务商调用在请求里；大活动挤占验证码；一台机器循环发上百万次
- **深入一，不丢（必讲）**
  - 请求内重试差（内存里的重试，崩溃即丢）；数据库当队列好但笨（要 `SKIP LOCKED`、自建重试、轮询延迟）；先写持久队列最好，队列确认后返回 202，靠可见性超时、指数退避、死信队列兜底
- **深入二，优先级（必讲）**
  - 加机器不行，瓶颈是服务商限速；按优先级分队列只解决排队；最好是独立工作池加按层令牌桶，高优先级独占一份保留额度（如 1000 里留 100），再加熔断、舱壁、备用服务商
- **深入三，去重（必讲）**
  - 先用 SET NX 占坑再发送，崩溃后重投会被误判已处理，变成最多一次；正确做法是发送前查"已发送"，服务商接受后再记；Redis 在前、库在后，两者都挂就照发
- **级别**
  - 中级：画出接口与同步设计，提示后做到持久化；高级：自己推进持久投递和优先级隔离；Staff：用数字找瓶颈，讲清失败语义和运维约束
