## Q
**Instagram 图片分享 · 完整解答**｜摘要 · 必会

设计一个类似 Instagram 的图片/视频分享应用：用户发带说明文字的图片或视频、关注别人、按时间顺序看关注者的动态流（feed）。规模 5 亿日活（DAU）、每天 1 亿条帖子。给出需求、实体与接口、整体设计、深入问题、各级别期望。

## A
**一句话。** 这是一个极端"读多写少"的系统：每人每天刷几十上百条，却只偶尔发一条。所以设计的核心是把计算从读时挪到写时（预计算动态流），再用 CDN 把大文件挪到离用户最近的地方。

**60 分钟路线。**

| 时间 | 做什么 |
|---|---|
| 0–5 分 | 需求与规模：5 亿 DAU、1 亿帖/天、动态流 500ms 内、最终一致可到 2 分钟 |
| 5–10 分 | 实体 User / Post / Media / Follow；三个接口 |
| 10–20 分 | 先画简单版：发帖、关注、读时扇出（fan-out on read）的动态流 |
| 20–45 分 | 必讲：读时扇出为什么撑不住 → 写时扇出 → 名人问题与混合方案；大文件分片直传 + CDN |
| 45–60 分 | 追问：Redis 持久化、存储与吞吐估算、各级别展开 |

- **需求**
  - 功能：发帖（图/视频 + 说明）；关注他人（单向）；看按时间倒序的动态流。点赞评论、搜索、快拍（Stories）、直播不做
  - 非功能：可用性优先于一致性（动态流晚到 2 分钟可接受）；动态流 < 500ms；媒体秒开；撑住 5 亿 DAU
- **实体与接口**
  - 实体：User、Post（图/视频共用一个实体）、Media（字节放对象存储）、Follow（follower → followed）
  - 接口：`POST /posts`、`POST /follows`（关注者 ID 取自登录令牌，不信请求体）、`GET /feed?cursor=&limit=`
- **整体设计**：网关 + 发帖服务 + 关注服务 + 动态流服务；元数据放 DynamoDB（Posts 以 userId 为分区键、createdAt+postId 为排序键；Follow 以 followerId 为分区键），字节放 S3
- **深入一，动态流（必讲）**
  - 读时扇出：每次刷新要查上千个被关注者，约 10 万+/秒的请求压垮数据库
  - 加缓存只是治标；写时扇出：发帖时把 postId 推进每个粉丝的 Redis 有序集合（ZSET），读一次就够
  - 缺点是名人发帖要写几百万次。混合方案：粉丝少于约 10 万的推（写时扇出），名人的帖子读时再拉并合并
  - 读取时 postId 要回填元数据：Redis 里放短 TTL 的元数据哈希，缺的用 BatchGetItem 补
- **深入二，大媒体**：照片 8MB、视频 4GB；发帖拿预签名 URL，客户端分片（multipart）直传 S3；完成后由 S3 事件通知服务端把状态改为 complete；读取走 CDN，并为不同设备生成多种分辨率/格式
- **深入三，规模**：每天 1 亿 × 2MB = 200TB 媒体，元数据 1 亿 × 1KB = 100GB；冷数据逐级下沉到更便宜的存储
- **追问再讲**：Redis 用 Sentinel + AOF/RDB 保持可用与持久；共享数据库还是每服务一库的取舍
- **级别**：中级跑通上传/关注/动态流并在提示后想到写时扇出；高级讲清三种扇出的取舍与大文件上传；Staff 讲系统演进（100 万 → 5 亿用户）、故障模式与运维
