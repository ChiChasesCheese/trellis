## Q
**支付系统 · 完整解答**｜摘要 · 必会

设计一个支付系统（类似 Stripe）：商户发起收款，顾客用信用卡或借记卡付款，商户能查询状态。给出需求、实体与接口、整体设计、深入问题、各级别期望。

## A
**一句话。** 支付系统的核心是在"外部支付网络既慢又不可信"的条件下，做到不丢记录、不重复扣款、卡数据不泄露：超时不等于失败，所有状态变化都写进不可变的事件流，再由对账服务与网络核对。

**60 分钟路线。**

| 时间 | 做什么 |
|---|---|
| 0–5 分 | 收需求并报数：峰值约 10,000 笔/秒，安全与持久是硬要求 |
| 5–10 分 | 实体（商户、PaymentIntent、Transaction）与三个接口 |
| 10–20 分 | 高层设计：建意图；交易服务对接支付网络；轮询状态 |
| 20–55 分 | 必讲深入：安全；审计与持久；超时与对账；规模 |
| 55–60 分 | 追问：Webhook、级别差异 |

- **需求**
  - 功能：商户创建收款请求；顾客用卡支付；商户查状态。保存卡、退款、报表、其他支付方式、订阅、打款放在范围外
  - 非功能：高安全；永不丢交易数据且可审计；异步的外部网络下保证交易安全与资金一致；10,000+ 笔/秒且能应对突发
- **实体与接口**
  - 商户；PaymentIntent（收款意图，拥有 created → authorized → captured 的状态机并保证幂等）；Transaction（一次资金动作，一个意图可有多个）
  - `POST /payment-intents`、`POST /payment-intents/{id}/transactions`、`GET /payment-intents/{id}`；金额用整数分
- **高层设计**
  - 网关负责认证限流；意图服务建 `created` 的意图；交易服务收卡信息、写 `pending` 的交易、连接支付网络并监听回调；状态由意图服务读库返回
- **深入一，安全（必讲）**
  - 商户认证：公钥加私钥，请求用 HMAC 签名并带时间戳和随机数，防篡改防重放
  - 卡数据：商户服务器绝不接触；用 iframe 隔离，再加公钥加密，私钥在 HSM 里
- **深入二，持久与审计（必讲）**
  - 只存当前状态会丢历史；审计表依赖应用记得写；最好是运营库加 CDC 加 Kafka 不可变事件流，并归档对象存储
- **深入三，异步网络（必讲）**
  - 超时当失败会重复扣款；手工对账撑不住；最好是调用前先记录尝试，超时事件触发对账服务按引用号查询并处理网络的结算文件，加幂等键
- **深入四，规模（追问）**
  - 服务无状态；Kafka 按 `payment_intent_id` 分区、副本 3；数据库按商户分片，每行 500 B，约 432 GB/天，冷数据归档
- **加分**：Webhook（服务端对服务端），签名、指数退避重试、商户按事件 ID 去重
- **级别**
  - 中级：跑通流程，知道卡数据不碰商户服务器；高级：看出超时不等于失败，幂等与竞态；Staff：事件溯源加对账，多层安全，网络宕机的降级路径
