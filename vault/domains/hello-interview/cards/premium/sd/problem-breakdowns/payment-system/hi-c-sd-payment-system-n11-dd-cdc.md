## Q
**支付系统 · 深入二：数据库加 CDC 加不可变事件流**｜摘要 · 必会

Stripe 式的持久与审计架构是什么？CDC 本身是单点故障，怎么应对？

## A
- **架构：** 运营库只做当前状态，服务商户 API（不需要审计表）；变更数据捕获（CDC）读数据库的预写日志（WAL）把每个已提交的变更捕获成事件；事件发布到 Kafka，形成每次状态转换的追加日志，按 `payment_intent_id` 分键，含变更前后的完整状态；不同的消费者各取所需。
- **消费者：** 审计服务（合规查询用的完整历史）；分析（商业智能的反规范化视图）；对账（把我们的事件与外部网络事件对照）；Webhook 投递（记录哪些状态变化要通知商户）。
- **为什么好：** CDC 在数据库层工作而不是应用层，只要变更提交，就一定出现在事件流里，不依赖代码记得写；商户 API 保持毫秒级响应；运营库和审计各自独立扩展，互不抢资源。
- **持久性：** Kafka 通常三副本、跨可用区，事件保留 7–30 天，所有事件落到 S3 等对象存储做长期保存，可以在多年后重建任何一笔支付的完整历史。
- **CDC 是单点：** 它停了，数据库写入继续但事件不再流出。应对：同一个库上跑多个独立的 CDC 实例，写入不同 Kafka 集群；监控 CDC 延迟，秒级告警；保留从数据库日志重放丢失事件的恢复流程；关键事件可以由应用层兜底，在 CDC 超时未确认时直接写 Kafka。
