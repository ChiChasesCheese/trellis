## Q
**新闻聚合 · 完整解答**｜摘要 · 必会

设计一个类似 Google News 的新闻聚合服务：从全球成千上万家出版商收集文章，用户看到按地区聚合的动态流，可以"无限"滚动，点击文章跳转到出版商网站阅读全文。规模 1 亿日活、峰值 5 亿，动态流加载 < 200ms。给出需求、实体与接口、整体设计、深入问题。

## A
**一句话。** 这是一个"写很少、读极多"的系统：后台定时收集文章，前台绝大多数请求读的是同一份"某地区最近的文章"。所以答案是把每个地区的动态流预先算好放进内存缓存，用游标分页保证滚动不重不漏，再用变化数据捕获（CDC）让新文章秒级进入缓存。

**60 分钟路线。**

| 时间 | 做什么 |
|---|---|
| 0–5 分 | 需求与规模：1 亿日活、峰值 5 亿、< 200ms，可用性优先 |
| 5–10 分 | 实体 Article / Publisher / User；一个 `GET /feed` 接口（点击跳转不需要接口） |
| 10–20 分 | 基础设计：数据收集服务（拉 RSS）→ 数据库 + 对象存储；分开的动态流服务 |
| 20–45 分 | 必讲：游标分页；Redis 地区动态流 + CDC；新鲜度（轮询分级、爬取、Webhook）；缩略图用 CDN |
| 45–60 分 | 追问：突发流量（地区部署、读副本）；分类；个性化 |

- **需求**
  - 功能：看聚合动态流；无限滚动；点击跳转出版商网站。按兴趣定制、收藏、分享不做
  - 非功能：可用性优先于一致性（宁可旧一点也别空白）；1 亿日活、峰值到 5 亿；动态流 < 200ms
- **实体与接口**：Article、Publisher（含 RSS 地址与地区）、User（地区）；`GET /feed?region=&limit=` 起步用页码，后面改成游标
- **整体设计**
  - 数据收集服务每隔几小时轮询出版商的 RSS 或接口，解析后缩略图存对象存储、元数据存库；动态流服务另设，因为一个写多、批处理，另一个读多、用户可见，扩缩需求完全不同
  - 无限滚动：页码（OFFSET）在新文章不断插入时会重复或漏
- **深入一，分页**：时间戳游标遇到同一时间戳的多篇文章会漏；用 (时间, 文章 ID) 复合游标，或让 ID 本身单调递增（ULID），游标就只是一个 ID
- **深入二，< 200ms**：直接查库不行；Redis 缓存带 TTL（有惊群、新文章最多晚一个 TTL）；最好是 CDC 触发 worker 更新 Redis 有序集合，只保留最近 1000–2000 篇
- **深入三，30 分钟内可见**：提高 RSS 轮询频率并分级（大站 5–10 分钟），对无 RSS 的站点爬取，最优是出版商 Webhook 推送，其余保底轮询
- **深入四，缩略图**：库里存二进制最差；S3 直连延迟高；S3 + CDN 且多种尺寸（srcset）最好
- **深入五，突发流量**：新闻是区域性的，按地区部署；服务无状态水平扩展；Redis 主节点加读副本（吞吐瓶颈而非容量）
- **加分深入**：分类——把分类字段放进缓存的地区流里内存过滤，比为每个分类单独建缓存更简单；个性化——存用户偏好向量，按比例混合预计算的分类流
