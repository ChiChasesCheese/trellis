## Q
**分布式缓存 · 完整解答**｜摘要 · 必会

设计一个类似 Redis 的分布式缓存：支持 set / get / delete，支持过期时间（TTL），按 LRU 淘汰。规模 1TB 数据、峰值 10 万请求/秒、读写延迟 < 10ms。给出需求、数据结构、整体设计、深入问题、各级别期望。

## A
**一句话。** 前半是低层设计：哈希表加双向链表，让读写和淘汰都是 O(1)；后半才是系统设计：怎样把一台机器的缓存变成多机集群，要回答复制、分片、热键、网络开销这几件事。

**60 分钟路线。**

| 时间 | 做什么 |
|---|---|
| 0–5 分 | 需求与规模：1TB、10 万 QPS、< 10ms，可用性优先、最终一致 |
| 5–10 分 | 实体只有键和值；三个接口 set / get / delete，几句话带过 |
| 10–20 分 | 单机：哈希表；加 TTL（惰性过期 + 后台清理）；哈希表 + 双向链表做 LRU |
| 20–50 分 | 必讲：复制（同步/异步/对等）、节点数估算、一致性哈希分片、热键读写 |
| 50–60 分 | 追问：性能（批处理、连接池）、故障转移细节 |

- **需求**
  - 功能：set / get / delete；可配置 TTL；LRU 淘汰。可配置缓存大小不做；先问清是不是 LRU，别的策略有 LFU、FIFO
  - 非功能：高可用，最终一致可接受；延迟 < 10ms；1TB、10 万 QPS。持久化、强一致、复杂查询、事务不做，但要和面试官确认
- **实体与接口**：只有键和值，接口是 `POST /:key`、`GET /:key`、`DELETE /:key`，别花时间
- **单机设计**
  - 哈希表 O(1) 查找，但不知道使用顺序；链表知道顺序但查找慢，所以两者合用：哈希表的值指向链表节点，访问就移到表头，淘汰就删表尾
  - TTL：节点存到期时间；读时发现过期就删（惰性）；后台清理线程定期扫，防止没人读的过期键占内存
- **深入一，复制**：同步复制要等所有副本，延迟和可用性随副本数变差，不适合；异步复制（主节点确认即返回）合适，Redis 默认就是；对等复制（gossip）最可扩展但要处理冲突
- **深入二，规模**：吞吐（假设压测单机 2 万 QPS）10 万 ÷ 2 万 = 5 台（留余量约 8 台）；存储 1024GB ÷ 24GB ≈ 43 台（留余量约 50 台）；取大者，50 台
- **深入三，分片**：取模换节点会让几乎所有键重映射；一致性哈希只动相邻区间
- **深入四，热读**：单纯整体升配最差；独立热键层、读副本可用；最好是给热键加后缀复制多份，读时随机选一份
- **深入五，热写**：写批处理（客户端攒 50–100ms 合并成一次）；或后缀分片计数器，读时求和
- **深入六，性能**：批处理、一致性哈希（客户端自己算，省一次路由往返）、连接池
- **级别**：中级把时间放在单机数据结构和基础复制；高级讲取舍，把热键和一致性哈希当第二天性；Staff 一般不问这题
