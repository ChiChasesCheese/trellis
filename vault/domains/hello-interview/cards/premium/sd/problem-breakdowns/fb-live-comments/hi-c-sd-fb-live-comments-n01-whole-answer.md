## Q
**Facebook 直播评论 · 完整解答**｜摘要 · 必会

设计 Facebook 直播评论系统：观众给直播视频发评论，正在看的人几乎实时地看到新评论，后加入的人能往回翻看之前的评论。要支持数百万个并发直播、单个直播每秒数千条评论。给出需求、实体与接口、整体设计、深入问题、各级别期望。

## A
**一句话。** 读写极度失衡的广播问题：发评论的人很少，看的人极多。难点是把一条评论推给分散在许多服务器上的几十万观众，以及某个直播爆红时需求本身要怎样变。

**60 分钟路线。**

| 时间 | 做什么 |
|---|---|
| 0–5 分 | 需求：发评论、实时看新评论（延迟 < 200ms，低于它人就觉得是实时）、看历史；数百万并发直播、单直播每秒数千条；可用性优先，最终一致 |
| 5–20 分 | 实体 User / Live Video / Comment；POST 与游标分页 GET；评论服务加 DynamoDB（简单键值，不要事务）；先用轮询 |
| 20–50 分 | 必讲：推送（SSE）、多服务器协调、爆红直播采样或 CDN 快照 |
| 50–60 分 | 追问：断线补发、调度服务、Redis 与 Kafka 取舍 |

**必讲。**
- **轮询为什么不行：** 要准实时得每 100 ms 轮询一次，每个观众每秒约 10 次请求，且几乎全是空请求。历史用游标分页（「小于游标的评论 ID 倒序取 N 条」），比偏移分页稳定高效。
- **推送用 SSE：** WebSocket 双向、开销高；评论读远多于写，SSE 单向、建立在普通 HTTP 上，发评论仍用 POST。
- **多服务器：** 单机连接数受 CPU、内存、文件描述符限制，同一直播的观众可能在不同服务器。朴素 Pub/Sub 让所有服务器收到所有评论，浪费；改成按 `hash(liveVideoId) % N` 分频道，L7 负载均衡按 liveVideoId 一致性哈希让同一直播的观众落在同一台。备选：调度服务（Dispatcher）直接把评论发给有观众的服务器。
- **爆红直播：** 每秒 5000 条没人读得完；先采样（评论越快采样率越低），再用 CDN 每秒发一次快照，客户端轮询并平滑播放，延迟 1–2 秒可接受。
- **断线：** SSE 的 Last-Event-ID 重连时回放错过的评论，限定范围（如最近 5 分钟），多台服务器共享 Redis 缓存历史，客户端按评论 ID 去重。

**级别期望。** 中级识别轮询的局限并想到推送；高级主导扩展并看出取舍；Staff 点出 Pub/Sub 的可靠性与扩展局限并给出选型。
