## Q
**WhatsApp 即时通讯 · 完整解答**｜摘要 · 必会

设计一个类似 WhatsApp 的即时通讯系统：用户建群（最多 100 人）、发收消息、离线 30 天内补收消息、发图片文件。给出需求、实体与接口、整体设计、深入问题、各级别期望。

## A
**一句话。** 「持久化保证送达 + 长连接实时推送」：先把消息写进库（不丢），再尽力推给在线的人（快）；难点是几亿条长连接分散在许多服务器上，消息怎么找到收件人所在的那台。

**60 分钟路线。**

| 时间 | 做什么 |
|---|---|
| 0–5 分 | 需求与数字：10 亿用户、约 2 亿同时在线、人均每天 20 条约 4–5 万条/秒；在线延迟 < 500ms，保证送达，群上限 100 人，离线 30 天补收；先问 1:1 还是大群为主（1:1 只是 2 人的群） |
| 5–20 分 | 实体 User / Chat / Message / Client（一人多设备）；WebSocket 命令式接口（`createChat`、`sendMessage`、`createAttachment`，服务端推 `newMessage`），客户端必须 ack；单台聊天服务：DynamoDB 的 Chat、ChatParticipant（chatId 分区键，加 participantId 为分区键的 GSI）、Message、Inbox；发送先写 Message 与每个收件人的 Inbox，再推在线的人，收到 ack 才删 Inbox，两张表设 TTL；附件用预签名 URL 直传对象存储 |
| 20–50 分 | 必讲：多服务器路由、多设备、连接悄悄断了 |
| 50–60 分 | 追问：乱序、「最后在线」、频道按用户还是按聊天、分区与容错 |

**必讲。**
- **多服务器路由：** 加负载均衡发不到对方连接；每用户一个 Kafka 主题撑不住（每个约 50KB，10 亿用户 50TB+）；一致性哈希可行但服务器要两两互联、扩缩易惊群。选 Redis Pub/Sub：服务器为连上来的用户订阅 userId 频道，发消息往该频道发布；它至多一次，所以先写库再发布，丢了靠 Inbox 补。频道按用户分（1:1 为主），大群超阈值再按群订阅。
- **多设备：** 加 Clients 表，Inbox 改为按客户端并限制设备数；Pub/Sub 仍按 userId。
- **连接断了：** TCP 超时太慢；ack 超时重试；应用层心跳（10–30 秒 ping，5 秒内要 pong）；把每用户递增序号搭在心跳上发现漏消息，低频轮询兜底。

**追问再讲。** 乱序用服务端接收时间戳排序，接受偶尔插队；「最后在线」只在断开时写一次，在线状态走 Pub/Sub 询问。

**级别期望。** 中级跑通单机并看出不能扩；高级主讲路由与分区；Staff 讲故障模式、数据库优化、分区域与 cell 架构。
