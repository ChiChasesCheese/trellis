## Q
**网络爬虫 · 完整解答**｜摘要 · 必会

设计一个为大模型训练收集文本的网络爬虫（web crawler）：从种子 URL 出发爬取网页，提取文本存起来。给出路线、需求、数据流、整体设计、深入问题和各级别期望。

## A
**一句话。** 这是没有用户界面的数据处理系统：核心是"待爬队列加流水线加礼貌控制"。难点是失败不丢进度、对每个站点保持礼貌、在 5 天内爬完 100 亿页。答案是拆成可重试的阶段、用 SQS 做队列与退避、按域名限速、横向扩展爬虫。

**60 分钟路线。**

| 时间 | 做什么 |
|---|---|
| 0–5 分 | 定范围：只抓文本；问清规模：100 亿页、每页约 2 MB、5 天 |
| 5–10 分 | 系统接口（种子 URL 进，文本出）和数据流 |
| 10–20 分 | 简单版：待爬队列、爬虫、DNS、网页、S3 |
| 20–50 分 | 必讲：拆流水线与重试；robots.txt 与限速；扩展与去重 |
| 50–60 分 | 追问：爬虫陷阱、动态内容、持续更新、优先级 |

- **需求**
  - 功能：从种子 URL 爬取并提取文本。训练、非文本、动态渲染、登录网页都在范围外；只能覆盖绝大多数网页，不是全部
  - 非功能：容错、礼貌（遵守 robots.txt）、效率（5 天内）、扩展到 100 亿页
- **接口与数据流**
  - 输入种子 URL，输出文本。流程：取 URL → DNS → 拉 HTML → 提取文本和链接 → 存文本 → 新链接入队
- **整体设计**
  - 待爬队列（Kafka、Redis 或 SQS）、爬虫、DNS、外部网页、S3
- **深入一，容错（必讲）**
  - 把爬虫拆成"拉取 HTML 入 blob"与"提取文本和链接"两级，元数据库存状态与位置，队列只放 ID，不放 HTML
  - 重试：内存计时器不行；Kafka 手写退避可行但繁琐；SQS 用可见性超时加 ChangeMessageVisibility 最好，5 次后进死信队列
  - 崩溃：成功入库后才确认，没确认的消息会重新可见（Kafka 靠不提交偏移量，SQS 靠可见性超时）。解析 worker 同理
- **深入二，礼貌（必讲）**
  - 把 robots.txt 的规则存在元数据库（Crawl-delay 不是官方标准，但遵守是礼节）；被禁止的直接确认丢弃；Crawl-delay 靠域名表里的上次时间加原子域名锁（Redis `SET NX` 加 TTL）
  - 每域名每秒 1 个请求，集中用 Redis 做滑动窗口，加抖动避免同步重试
- **深入三，规模与效率（必讲）**
  - 单机网络约 200 Gbps，折合 12500 页/秒，按 30% 利用约 3750 页/秒；单机 30.9 天，8 台约 3.9 天。每域名每秒 1 个请求并不拖累总吞吐，因为爬虫同时面对数百万个域名
  - 解析 worker 按队列积压自动伸缩；DNS 用缓存加多家服务商；去重：先 URL 后内容，哈希加索引比布隆过滤器更实用
- **追问再讲**
  - 爬虫陷阱用最大深度（15 到 20 跳，深度指链接跳数而非路径层数）；动态内容用无头浏览器；大文件先发 HEAD 看 Content-Length，超过 10 MB 就跳过；持续更新加 URL 调度器，按上次爬取时间和热度入队；优先级用多个队列
- **级别**
  - 中级：说清数据流、搭出简单版；高级：深入礼貌与 robots.txt，会谈扩展和 5 天的算账；Staff：至少三个方向有深入见解，让面试官有收获
