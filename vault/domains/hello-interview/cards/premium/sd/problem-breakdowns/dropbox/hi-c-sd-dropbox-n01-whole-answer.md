## Q
**云文件存储 · 完整解答**｜摘要 · 必会

设计一个像 Dropbox 的云文件存储服务：用户能从任意设备上传、下载、分享文件，并在多设备间自动同步，单个文件最大 50GB。给出需求、实体与接口、整体设计、深入问题、各级别期望。

## A
**一句话。** 文件字节和元数据分开：字节走对象存储，元数据走数据库；应用服务器只做控制（发预签名链接、记状态），不碰大文件。难点是 50GB 大文件的分块可续传，以及多设备同步。

**60 分钟路线。**

| 时间 | 做什么 |
|---|---|
| 0–5 分 | 需求：上传、下载、分享、同步；50GB；可用性优先于一致性（别人几秒后才看到新文件可接受） |
| 5–25 分 | 实体（File、FileMetadata、User）与接口；按四个功能推进：直传对象存储、CDN、分享表、同步 |
| 25–50 分 | 必讲：大文件分块与续传（花最多时间）、加速、安全 |
| 50–60 分 | 追问：增量同步、冲突、压缩、签名链接泄露 |

**必讲。**
- **直传：** 元数据放 DynamoDB 或 Postgres，字节放 S3。服务器发预签名 URL 并写元数据（uploading），客户端直传 S3，S3 通知后改 uploaded，不经应用服务器。下载同样用预签名 URL，远距离慢再加 CDN 签名链接。
- **大文件：** 单次 POST 50GB 在 100Mbps 下约 1.1 小时无响应、网关有 10MB 一类上限、断网重来、无进度。客户端切 5–10MB 块并行传，用 S3 Multipart Upload，每块一个预签名 URL，元数据记 chunks 状态以便续传；只信客户端 PATCH 不安全，用每块 ETag 加 `ListParts` 在服务端校验，完成后 `CompleteMultipartUpload` 合并再标 uploaded。用内容 SHA-256 指纹而非文件名判断是否传过；下载合并后是普通对象，可用 Range 续传。
- **分享：** 元数据里放 sharelist 查「分享给我的」要全扫；单独的 SharedFiles 表（userId 分区键、fileId 排序键）可直接查，且无同步问题。
- **同步：** 本地用文件系统事件发现变化再上传，冲突先用最后写入者胜出；远端到本地每设备一条 WebSocket 推送，客户端再定期 `changes?since=` 轮询兜底。
- **加速：** 并行块和自适应块大小，只同步变化的块；固定分块在开头插一字节会让所有块变化，用内容定义分块（滚动哈希）；文本值得压缩，图片视频不值得，先压缩再加密。
- **安全：** HTTPS 传输、S3 静态加密；ACL 即分享表；签名 URL 短时效（如 5 分钟），但它是持有者令牌，谁拿到谁能用，高安全场景可绑 IP 或要求 cookie。

**级别期望。** 中级跑通四个功能；高级详细讲大文件上传；Staff 深入多个主题并主导方向。
