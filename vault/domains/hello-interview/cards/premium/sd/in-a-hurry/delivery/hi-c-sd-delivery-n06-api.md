## Q
**交付框架 · API 或系统接口**｜摘要 · 必会
这一步怎么选协议、命名资源？用户身份该从哪里取，为什么？

## A
- **作用：** 约 5 分钟，定义系统与用户之间的契约，用来指导高层设计，通常直接对应功能需求（但不总是）。
- **协议：** REST（HTTP 动词对资源做增删改查）是默认；GraphQL 适合客户端多样、数据需求各异，避免多取少取；RPC（如 gRPC）适合对性能敏感的内部服务调用。别纠结，没有特别理由就用 REST。实时功能再补 WebSocket 或 SSE，但先设计核心 API。
- **资源命名：** 用复数名词表示系统里的事物（`/v1/links`，不是 `/v1/link`），围绕核心实体设计端点。
- **用户身份：** 当前用户从请求头里的认证令牌推出，不要从请求体或路径参数里取。信任用户传来的用户 ID，别人就能冒充，要始终认证请求。
