## Q
**关键技术 · 带过期的分布式锁为什么还不够安全**｜拓展 · 加分

进程 A 拿到带 10 分钟过期的 Redis 锁，随后一次长时间停顿（如垃圾回收、网络卡顿）超过了过期时间，进程 B 拿到锁，A 醒来继续写。怎么防？

## A
- **问题：** 过期解决了"持有者崩溃"，却制造了"持有者以为自己还有锁"。A 醒来时锁已易主，两个进程同时写同一资源。
- **围栏令牌（fencing token）：** 每次拿锁，锁服务返回一个单调递增的数字；写资源时带上它，存储层只接受不小于已见最大值的令牌，旧持有者的写会被拒绝。
- **含义：** 真正保证互斥的是被保护资源上的检查，而不是锁本身。用 ZooKeeper 或 etcd 这类提供一致性保证的系统更容易拿到递增版本号；对正确性要求高时，不要只靠单个 Redis 键或 Redlock。
- **何时够用：** 锁只是为了"尽量别重复干活"（效率型，如定时任务去重）时，偶尔重复无害，简单锁即可。
