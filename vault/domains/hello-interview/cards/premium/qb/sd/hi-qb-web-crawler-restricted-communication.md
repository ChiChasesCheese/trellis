## Q
**设计无中心协调的分布式网络爬虫（节点间通信受限）**｜系统设计｜被报告 56 次 · Meta · 最近 2026-04 · 先修见：在线国际象棋平台、聊天与即时通讯系统

你控制 10,000 台机器，单机带宽和 CPU 充足，但机器之间通信很受限；不能用主控节点、数据库、消息队列或任何云服务。目标站点有 10 亿个互相链接的 URL，从根页面递归跟链接能爬到全部。要求：下载全部页面；同一个 URL 绝不下载两次；任何单个节点的流量尽量小。面试官常追问：谁来去重、怎样保证所有机器都不闲着、节点宕机怎么办、没有主控怎么知道爬完了。

讲出：难点一句话、必讲的决策、取舍、级别期望。


## A
**一句话。** 用确定性的所有权代替中心：对规范化 URL 哈希，每个 URL 有且只有一个主人节点，主人负责去重和下载，发现新链接的节点批量转给主人。去重的检查并插入从全局锁变成单一写者，通信量只和不同 URL 的数量成正比。

**60 分钟路线。**

| 时间 | 做什么 |
|---|---|
| 0–6 分 | 澄清节点流量的含义和故障假设；估算每节点 10 万个 URL |
| 6–12 分 | 成员表、待爬队列、已见集合和消息 |
| 12–25 分 | 规范化、哈希定主人、批量转发、本地爬取循环 |
| 25–50 分 | 所有权与去重；通信量；让所有机器有活干 |
| 50–60 分 | 追问：宕机与成员、终止检测、礼貌与陷阱 |

**必讲。**
- **所有权去重：** 广播已爬 URL 通信放大 10,000 倍，共享布隆过滤器误判会漏爬而下载全部是硬要求，按主机名哈希会全压到一个节点（只有一个主机）→ 按完整规范化 URL 哈希，成员表固定，大家对谁是主人答案一致 → 检查并插入只在主人一处，不要锁也不要共识。
- **通信量：** 99.99% 的链接指向别的节点，没有局部性可挖 → 发送端用 `sent` 去重并批量，每节点发送从 400 MB 降到 80 MB，每批 1,000 条约 80 KB，整个爬取约 1,000 个包 → 只传 URL，`sent` 丢了顶多多发，主人 `seen` 仍会拦。
- **不闲着：** 每页 50 个链接，约三层（50³ = 125,000 > 10,000）全员有活；稳态页面大小不均，空闲节点向邻居发 `Steal` 取尚未开始的 URL → 去重权仍在主人，只把下载委托出去。

**取舍。**
- 宕机：gossip（SWIM）探测，后继接管槽位，未确认的转发重发；主人的 `seen`（800 KB）和待爬日志异步复制给后继 2 个节点，页面按指纹命名覆盖写，最多多下载一次。
- 终止检测：沿 gossip 求和每节点 `Forward` 收发计数和空闲状态，全空闲且发送等于接收、连续两轮不变才算完成；光看空闲不够，在途消息会让别人重新有活。
- 礼貌：总速率按活跃节点数均分令牌桶；陷阱靠 URL 深度长度上限和内容指纹。
- 每节点 800 KB 精确集合优于布隆过滤器，URL 多 1,000 倍再换。
- 允许一个协调者时它只存成员表，不放在 URL 路径上。

**级别。** 高级：所有权代替中心、批量转发、规范化、启动扩散与空闲处理、宕机接管。资深：通信量和集合大小数字、去重权与执行权分离、状态复制与崩溃语义、计数终止检测、总速率约束。
