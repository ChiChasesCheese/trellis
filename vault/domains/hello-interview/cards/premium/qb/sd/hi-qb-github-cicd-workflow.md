## Q
**设计 CI/CD 平台（类 GitHub Actions）**｜系统设计｜被报告 63 次 · OpenAI · 最近 2026-03 · 先修见：分布式任务调度器（含 cron 与一年执行历史）

设计一个多租户（multi-tenant）的 CI/CD 平台：用户把代码推送（push）到仓库后，系统读取仓库里的工作流文件，自动在隔离的机器上执行其中的任务，并让用户实时观察执行过程。规模约 1,000 万个仓库，平均每秒 10 次推送，有突发。面试官常追问：突发怎么吸收、任务怎么分给执行机、执行机崩了怎么办、日志怎么实时看、多租户怎么公平和隔离、怎么取消和重试。

讲出：难点一句话、必讲的决策、取舍、级别期望。


## A
**一句话。** 这是事件驱动的推送 → 运行 → 任务依赖图 → 执行机流水线：事件靠持久队列和幂等键恰好一次变成运行，任务进按租户公平排队的队列、由执行机带租约拉取，日志走独立的分块追加通道。难点不在吞吐，在公平、失联恢复和不可信代码的隔离。

**60 分钟路线。**

| 时间 | 做什么 |
|---|---|
| 5–10 分 | 运行、任务、执行机、日志块实体与状态 |
| 10–25 分 | 事件队列 → 触发服务 → 调度队列 → 执行机 → 日志通道 |
| 25–50 分 | 事件到运行的幂等；公平队列加租约；日志与实时观察 |
| 50–60 分 | 追问：突发扩容、隔离、取消重跑、缓存 |

**必讲。**
- **事件到运行：** Kafka 至少一次投递 → Run 带唯一键 `(repoId, sha, workflow, eventId)`，重复插入即跳过 → 恰好一次；按 `sha` 读文件而非分支最新，免得执行别人的代码；语法错误也建一个失败运行展示给用户。
- **任务分发：** 执行机在内网只能主动连出 → 拉取式，背压天然；每租户一个子队列做赤字轮转加并发上限（假设免费 20、企业 500）；领任务得 60 秒租约、每 20 秒心跳，过期就重置 `READY`、`attempt + 1`，旧执行机的结果带旧 `attempt` 被围栏拒绝。步骤可能有副作用，默认失联即失败。
- **日志：** 36,000 个并发任务是 18,000 块/秒的小写入 → 执行机每 2 秒上传 `(jobId, seq, bytes)` 块，先进 Kafka 再批量落对象存储，同时推 Redis 发布订阅 → 浏览器用 SSE 带 `from=seq` 续传，先读已落盘段再接实时尾部；密钥脱敏在执行机端做。

**取舍。**
- 突发要靠扩容不是余量：按最老任务等待时间伸缩，暖池冷启动约 30 秒；排队时间是头号指标。
- 隔离：每任务新 microVM，用完销毁；fork 的拉取请求不给密钥；短期令牌运行时注入。
- 取消：条件更新为 `CANCELLING`，执行机在心跳响应里收到；同分支新推送自动取消旧运行。
- 单机线程池崩了整个进程一起崩，这里执行机会无声消失，所以锁变租约加围栏号。
- Temporal 能省重试和依赖，但租约和日志仍要自建，规模小或流程复杂再选。

**级别。** 高级：队列吸收突发加幂等创建、拉取与租约、依赖图、日志续传、租户公平。资深：数字说明靠扩容、围栏、公平算法、隔离与密钥下发、与工作流引擎取舍。
