## Q
**设计图像变换流水线（并发与分布式扩展）**｜低层设计｜被报告 27 次 · Anthropic · 最近 2026-10 · 先修见：可配置淘汰策略的内存键值存储

一个图片目录里有上万张图（分大图、小图两个子目录），另有一个目录存放变换定义：每个 JSON 文件是一个变换列表，形如 `[{"transform": "mirror", "arg": []}, ...]`，每个文件有若干步。要求对每张图应用每个变换文件，保存结果。分三步给：先写串行版本；再用线程、进程等并发提速；最后讨论百万张图、图片和输出分散在不同位置时怎么分布式处理（队列、多个工作进程）。面试官看重的是：图像和变换怎么建模、能不能提前发现非法变换、并发为什么用进程不用线程、重复劳动怎么省，以及分布式的任务切分和幂等。

讲出：难点一句话、必讲的决策、取舍、级别期望。


## A
**一句话。** 图像和变换都是不可变值对象，变换按名字注册、从 JSON 构造成流水线；串行版先写对，再以「一张图 × 全部流水线」为任务单位用进程池并行；规模放大后把图片清单切批入队，输出位置由内容哈希决定，重复投递也安全。

**60 分钟路线。**

| 时间 | 做什么 |
|---|---|
| 12–38 分 | 写值对象、几种变换、流水线、JSON 构造 |
| 42–60 分 | 追问：为什么进程、提前校验、前缀缓存、分布式 |

**必讲。**
- **并发为什么是进程：** 工作是 CPU 密集的纯计算，线程抢 GIL → 实测 8 线程 3.36 秒、串行 3.33 秒、进程 0.93 秒 → 用进程池；若像素运算在 C 里释放 GIL（Pillow、numpy）线程也行。任务粒度取一张图 × 全部流水线：更细每个任务都要传图，更粗没法均衡负载；单张图出错只返回错误，不拖垮整批。
- **值对象加统一接口：** `frozen` 数据类自带按值比较和哈希，可做缓存键、可跨进程传；步骤接口用 `Protocol`，不必继承；参数合法在构造时查，形状合法在应用时查，包成带 `index` 的 `StepError`。
- **分布式切分：** 每批 50 张，一个任务约 200 秒（50 × 200 个输出 × 20 ms），够长摊薄队列开销、够短便于重做；百万张是 20,000 个任务。队列至少一次投递加可见性超时，所以必须幂等：输出路径由 `(图, 变换内容)` 的哈希决定，重复执行只是覆盖；总失败的毒丸重试几次后进死信队列。

**取舍。**
- 提前校验只算形状（`output_size`），不要先跑一遍，大图太贵还会让半截结果污染缓存。
- 前缀缓存的键用图像内容不用 `id()`，`id` 回收后会被复用造成错误命中；每项是整张中间图，要按字节限量。
- 流水线内每步依赖上一步，不能并行，在图与图之间并行更划算。
- 队列选竞争消费的工作队列；用 Kafka 并行度受分区数限制。
- 换成彩色图、numpy 或 GPU 时，只改 `Image` 和步骤，流水线、缓存、队列不变。

**级别。** 高级：不可变值对象、注册表、任务粒度与失败隔离、前缀缓存。资深：任务切分与幂等输出、死信、用数字推导规模、队列与分区取舍。
