## Q
**什么时候不该上 Kubernetes**｜补充 · 平台基础设施：容器、服务网格、发布 · 追问

面试官：「什么情况下 Kubernetes 是过度设计？不用它你会用什么？」

## A
**结论。** Kubernetes 收的是平台税：集群升级、网络与入口、可观测性、堆积的 YAML，实际还要一个平台团队来负责。只有几个普通 HTTP 服务、团队小、没有特殊调度需求时，这笔税不值得。

**要点。**
- **替代方案：** 托管容器平台（Cloud Run、Fargate、ECS）按容器部署和自动伸缩，不用运维集群；放在 PaaS 上的单体能撑的时间比多数团队以为的长。
- **什么时候该上：** 你本来就在自己造它的功能：自定义调度、服务发现、批处理或 GPU 编排；或者很多团队要共享它的生态（operator）。
- **判断标准：** 看团队有没有人专门负责集群；没有人，宁可用托管平台。

**面试里这样说。** 「服务不多、团队也小，我会用 Cloud Run 或 Fargate，不自己养集群。等到需要自定义调度、GPU 或几十个团队共享一套平台时，再上 Kubernetes。」

**易错。**
- **默认就上 Kubernetes：** 在三个服务的规模上，平台运维比业务开发还重。
- **把托管平台看成「不专业」：** 少运维一层，故障面也更小。
