## Q
**JSON 当数据契约有哪些坑**｜补充 · 编码与模式演进（Encoding & Evolution） · 追问

面试官：「服务之间默认都用 JSON。把它当数据契约，具体有哪些弱点？团队通常怎么补？」

## A
**结论。** 数字类型模糊、没有二进制类型、没有强制的模式，每条记录还重复字段名。补救是 JSON Schema 或 OpenAPI 校验、契约测试，需要机器检查演进时改用带注册表的 Protobuf 或 Avro。

**要点。**
- **数字：** 不区分整数和浮点，JavaScript 一类解析器把数字存成 64 位浮点，超过 2⁵³−1 = 9,007,199,254,740,991 的整数会悄悄丢精度。所以 64 位的雪花 ID 要用字符串传。
- **没有二进制类型：** 二进制要转 Base64，体积大约变成 4/3，多 33%。
- **没有强制模式：** 兼容性只靠约定，生产者改字段名，消费者在运行时才发现。
- **冗长：** 每条记录重复字段名，压缩能减小体积，解析成本不变。
- **补救：** 在 CI 里用 JSON Schema 或 OpenAPI 校验，生产者和消费者之间做契约测试；演进保证要机器检查的场景换成 Protobuf 或 Avro 加注册表。

**面试里这样说。** 「JSON 的数字没有整数类型，超过 2 的 53 次方就丢精度，所以大整数 ID 我用字符串；二进制要 Base64，多 33%。它也没有强制的模式，我会用 JSON Schema 和契约测试兜住，演进要求严的内部流量换 Protobuf 或 Avro。」

**易错。**
- **把 64 位 ID 直接放进 JSON 数字：** 前端解析后末几位变了，两个不同的 ID 变成同一个。
- **以为压缩能解决性能：** 压缩只减传输量，解析和对象创建成本还在。
