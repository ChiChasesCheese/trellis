## Q
**DNS 到底是不是爬虫的瓶颈**｜补充 · 网络爬虫 · 追问

面试官：「100 亿页、5 天爬完，爬取速率约 2.3 万页/秒。每次爬取都要解析域名，DNS 会成为瓶颈吗？你要不要为它建一个同样规模的解析系统？」

## A
**结论。** DNS 的查询量不大，但冷查询的延迟会卡住爬取线程。查询量取决于不同主机的数量，不是 URL 数量：解析结果缓存之后，新查询数不超过不同主机数。假设平均每个主机约 100 页，查询量约是爬取速率的 1/100，约 230 次/秒，不需要建一个同规模的 DNS 系统。真正要处理的是冷查询慢：用本地缓存、异步解析和过期后失败刷新。

**要点。**
- **算数：** 1×10¹⁰ ÷ (5 × 86400) ≈ 23,148 页/秒；每主机约 100 页，查询约 231 次/秒（这个比例是假设）。
- **按主机缓存：** 同一主机的所有 URL 复用一次解析结果，缓存 TTL 对齐一轮爬取周期。
- **冷查询的代价：** 一个新主机的首次解析要经过多层 DNS 的往返，同步调用会让爬取线程空等，早期爬虫曾有线程大部分时间花在解析上。
- **缓解：** 异步解析，在 URL 进入待爬队列时就预热解析结果，必要时多家解析服务商轮询，避开限额。
- **过期处理：** 主机换了 IP 后缓存会过期；爬取失败时刷新解析，而不是缩短所有缓存。

**为什么。** 要把量和延迟分开看。量由不同主机数决定，缓存后很小；延迟是每个新主机的首次解析成本，靠异步化和预热消化。

**面试里这样说。** 「DNS 查询量按不同主机算，不按 URL 算，缓存后大约只有爬取速率的百分之一，我不会为它建大系统。要防的是冷查询卡住爬取线程，所以我用异步解析、在 URL 入队时预热缓存，爬取失败时再刷新。」

**易错。**
- **把 DNS 当成和爬取同量级的负载：** 按 URL 算量，会过度设计。
- **只看总量就忽略冷查询延迟：** 同步解析会让线程空等，吞吐上不去。
