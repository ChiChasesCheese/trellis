## Q
**图的边怎么存：按（类型, 源点）建索引**｜补充 · 社交图谱与好友搜索 · 必会

面试官：「好友、关注、拉黑几种关系放在同一个存储里。你按什么键存？为什么不只按用户 ID 建索引，查出来再按类型过滤？」

## A
**结论。** 主键用（边类型, 源用户），值是目标用户的有序列表，类似倒排索引里「词 → 文档列表」。好友是双向关系，存两行有向边（A→B 和 B→A），整个存储按源用户哈希分片。

**要点。**
- **只按用户建索引的问题：** 取出该用户所有类型的边，应用层再丢掉不要的，类型分布不均时读了大量无用行。
- **复合键直接定位：** （friend, A）只读好友的那一份，不读 follow 和 blocked。
- **像倒排索引：** 「边类型 + 源点」相当于词项，目标 ID 列表相当于倒排列表。
- **好友存两行：** A→B 和 B→A 各在自己源点的分片上，两个方向的查询都是单分片读取。
- **列表的顺序：** 按目标 ID 排序便于两个列表做有序归并求交；按时间取最近的另建索引。

**为什么。** 绝大多数查询是「某个用户的某类关系」，让索引顺序和查询形状一致，就不用在读出之后再过滤。

**面试里这样说。** 「边我用（边类型, 源用户）做键，值是按目标 ID 排序的列表，像倒排索引；好友存 A→B 和 B→A 两行，各落在自己源点的分片上，所以正反两个方向的一跳查询都是单分片读取。」

**易错。**
- **只按 srcId 索引再过滤类型：** 读了没用的行，类型越多越浪费。
- **好友只存一行：** 查「谁是我的好友」要查两个方向，或者跨分片。
- **列表不排序：** 后面的共同好友求交只能用哈希集合，大列表更慢。
