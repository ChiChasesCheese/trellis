## Q
**自动故障转移：丢写的下游后果与超时**｜补充 · 复制 · 追问

面试官：「MySQL 主库挂了，自动切换把一个落后的从库提升为主。为什么很多团队对核心库仍保留手动切换？除了脑裂，自动切换还有哪两个容易被忽略的坑？」

## A
**结论。** 异步复制下新主缺少旧主已确认的最后一批写入，丢掉它们会让依赖它们的下游悄悄出错；超时设短了，系统一慢就误触发切换，把故障放大。所以核心库常保留人工确认。

**要点。**
- **丢写的下游后果：** 新主的自增计数落后，会把已经发出去的主键再发一遍。GitHub 的一次事故里，重复的主键又被 Redis 用作缓存键，部分私有数据被返回给了别的用户。
- **超时太短：** 负载高、响应变慢时恰好触发不必要的切换，新主还要接住全部流量，雪上加霜。
- **超时太长：** 真宕机时停机更久。超时要按实测的延迟分布取，不是固定常数。
- **脑裂：** 旧主恢复后仍自认是主，要靠围栏（fencing）让它不能再写。

**面试里这样说。** 「自动切换我会提升日志最新的从库，并要求旧主恢复后自动降级。丢掉的写入不只是丢几行：新主的自增 ID 会复用，缓存里按 ID 存的数据会串到别人身上。所以账务这类核心库，我让切换需要人工确认。」

**易错。**
- **只讲脑裂：** 漏了丢写后主键复用对下游缓存和消息的污染。
- **超时越短越好：** 抖动和 GC 会让误切换成为常态。
