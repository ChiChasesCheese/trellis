## Q
**RED 与 USE：服务看哪个，机器看哪个**｜补充 · 可观测性 · 必会

面试官：「RED 方法和 USE 方法分别度量什么？支付服务和数据库主机各该用哪一个？为什么说饱和度比利用率更能预警？」

## A
**结论。** RED 面向请求型服务：请求率、错误率、耗时分布，是用户视角，也是 SLI 的数据基础。USE 面向资源：利用率、饱和度、错误，是容量视角。支付服务看 RED，数据库主机看 USE；先用 RED 发现影响，再用 USE 解释原因。

**要点。**
- **RED：** Rate 每秒请求、Errors 每秒失败、Duration 延迟分布，每个请求型服务都要有。
- **2026 亮点：** 存量服务没有埋点时，可以用 eBPF 零代码插桩（OpenTelemetry eBPF Instrumentation，OBI，前身 Grafana Beyla）在内核层抓 HTTP、gRPC 和数据库调用，不改代码、不重启就出各服务的 RED 指标、服务拓扑和 trace，再经 OTLP 送进现有后端，适合多语言存量栈兜底。取舍：看不到业务属性和自定义 span，关键链路仍要 SDK 手工插桩；需要 Linux 5.8 以上和 root 或特定 capability。
- **USE：** Utilization 忙碌比例、Saturation 排队深度或等待、Errors，对 CPU、内存、磁盘、连接池、GPU 等每种资源。
- **支付服务：** 看 RED，因为用户感受的是请求成功和快慢。
- **数据库主机：** 看 USE，因为要回答资源是否到瓶颈。
- **饱和度更靠前：** 利用率 70% 但队列在增长，就已经在恶化；只看利用率会漏掉。

**为什么。** 两种方法回答不同问题：RED 说用户是否受影响，USE 说资源哪里紧。一个负责发现，一个负责归因。

**面试里这样说。** 「请求型服务我做 RED 面板，错误率和延迟直接作为 SLI；机器和连接池等资源做 USE，重点看饱和度，比如队列深度，因为它比利用率更早预警。」

**易错。**
- **只看 CPU 利用率：** 队列已经在涨还显示正常。
- **给资源设 RED 告警：** 资源没有用户视角的成功率。
- **只看平均耗时：** 尾部延迟被淹没，要看分布。
