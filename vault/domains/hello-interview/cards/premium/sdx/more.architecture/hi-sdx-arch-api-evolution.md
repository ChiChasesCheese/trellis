## Q
**API 演进：先加字段再谈版本**｜补充 · 服务架构：微服务、服务发现、Serverless · 追问

面试官：「对外 API 要演进：用 URI 版本（/v2/）、请求头或日期版本，还是不开新版本只做增量？各在什么时候用？」

## A
**结论。** 默认只做兼容的增量变更：加可选字段，客户端忽略不认识的字段，线上只运营一个版本。只有真正破坏性的重设计、又有外部调用方时才开 `/v2/`；日期版本只在「小改动很多、又要保持对外稳定」时才值得。

**要点。**
- **增量优先：** 只加不改不删；非改不可时用并行变更（先并存，再迁移，最后删旧）过渡。
- **URI 版本：** 显式、可缓存、易于按版本路由和下线；代价是要同时养 N 个版本，内部模型也会分叉。
- **日期或请求头版本：** 每个客户端钉在一个日期版本上，服务端用一串翻译层把旧版请求和响应转换到唯一的内部模型（Stripe 的做法）；开发者体验好，翻译链很贵。
- **内部服务：** 调用方都是自己人，用增量加契约测试，不必版本化。

**为什么。** 每多一个线上版本，就多一份运维、测试和安全补丁。版本号是最后手段，不是默认动作。

**面试里这样说。** 「我先要求所有改动都向后兼容，只加可选字段；只有遇到外部客户无法迁移的破坏性变更，才开 /v2/，并给旧版定下线日期。」

**易错。**
- **一有改动就开 /v2/：** 能增量做的改动也升版本，等于永久多养一个版本。
- **版本号一路复制到内部模型：** 内部也出现 N 套实现，修一个 bug 要改 N 处。
