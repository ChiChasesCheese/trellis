## Q
**共享数据库与分布式单体**｜补充 · 服务架构：微服务、服务发现、Serverless · 必会

面试官：「订单服务和库存服务直接读写同一个数据库，发布也得一起上线。这算微服务吗？你怎么检验服务边界划对了没有？」

## A
**结论。** 不算，这是分布式单体（distributed monolith）：进程拆开了，耦合还在。我用一个问题检验：「这个团队现在能不能不问任何人，单独发布自己的服务？」答不是，就没拆开。

**要点。**
- **数据独占：** 服务独占自己的数据，别人只能走它的 API 或订阅它发布的事件；边界画在业务能力（限界上下文）周围。
- **共享库的坏处：** 任何表结构改动都可能弄坏不知名的读者，却没有单体里的编译器、测试和原子发布兜底；两个写者之间，不变量由谁负责也说不清。
- **其他症状：** 必须同时或按固定顺序发布；一个需求改 N 个仓库；共享的内部库逼所有人同时升级；细碎的同步调用。
- **代价要说出口：** 拆开后没有跨服务 join 和事务，改用 API 组合、事件复制数据，接受最终一致。

**为什么。** 拆服务买的是独立演进。共享数据库把耦合挪到数据层：既没有独立演进，又多了网络故障和运维成本，比单体和干净的微服务都差。两个「服务」总要碰对方的表，说明它们本来就是一个服务，应该合并。

**面试里这样说。** 「我检验边界只问一句：这个团队能不能单独发布？数据我让服务独占，别人只能调它的 API 或订阅它的事件；两个服务老要碰对方的表，我宁可合并也不共享库。」

**易错。**
- **只拆代码、不拆数据：** 看上去有一堆服务，改一张表仍要全员协调。
- **共享库当「过渡」长期保留：** 过渡期一过，没人再敢动表结构。
