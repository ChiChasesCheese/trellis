## Q
**限流器 · 完整解答（一张卡）**｜摘要 · 必会

为 API 网关设计一个单进程、内存中的限流器：配置在启动时给出，每个端点有自己的算法和参数（例如令牌桶 `capacity`、`refillRatePerSecond`）；请求带客户端 ID 和端点；返回是否放行、剩余额度和被拒时多久后可重试；没有配置的端点用默认限流。给出需求、实体与接口、整体设计、关键实现、深入问题和各级别的期望。

## A
**一句话。** `RateLimiter` 只做路由：按端点找到对应的 `Limiter`，把客户端 ID 交给它；每种算法（令牌桶、滑动窗口日志）自己管每个客户端的状态；配置是原始 JSON，由工厂按 `algorithm` 字段造出限流器。

**60 分钟路线。**

| 时间 | 做什么 |
|---|---|
| 0–5 分 | 澄清：配置形态、输入输出、没配置怎么办、并发是否现在做 |
| 5–20 分 | 实体与类设计：`RateLimiter`、`Limiter`、`RateLimitResult`，请求和客户端不建类；`Limiter` 为什么是接口；工厂 |
| 20–45 分 | 实现一种算法（令牌桶为主）和 `allow` |
| 45–60 分 | 带数字验证突发、补充、被拒后重试时间；追问加算法、动态配置、线程安全、内存增长 |

**必讲。**
- **Limiter 为何是接口：** 每种算法每个键的状态完全不同（桶是两个数，日志是队列，固定窗口是计数加起点），没有可抽出的共同字段，抽象基类没意义。
- **令牌桶算术：** 补充量 = 间隔 × 速率 ÷ 1000，封顶到容量，请求到来时一次性结算，不开后台线程；被拒时重试时间 = 向上取整((1 − 当前令牌) × 1000 ÷ 速率)。滑动窗口日志：每客户端一个时间戳队列，先清窗口外的再数。
- **路由与默认：** 构造时遍历配置造好各端点的限流器，存进字典，另预建默认限流器；`allow` 查不到端点就用默认。
- **工厂：** 按判别字段分发，未知算法立刻失败；以后可演进为注册表。

**追问再讲。** 线程安全：同一客户端的读-改-写要原子，按键加锁，不同客户端并行；建键本身是 check-then-act。加新算法：一个新类加工厂一行。动态配置（整体替换 vs 原地更新保留状态）、内存增长（按空闲时间淘汰）、时钟用单调时钟。

**级别期望。** 中级边界清晰，配置以原始数据流经工厂，能解释为什么要工厂、状态为什么在各限流器里；高级自己发现边界（长期没请求的客户端、时间戳溢出），先讲简单方案再讲何时上模式，能谈分布式和内存治理。
