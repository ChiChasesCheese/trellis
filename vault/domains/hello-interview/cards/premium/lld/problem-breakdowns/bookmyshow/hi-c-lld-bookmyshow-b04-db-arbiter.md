## Q
**电影票预订 · 多台服务器时，内存里的锁还够吗**｜拓展 · 追问

服务部署成多个实例，每个实例有自己的场次锁。"恰好一个成功"还成立吗？生产里谁来仲裁？

## A
- **不成立：** 进程内的锁只保护本进程；两台服务器上的两个请求各自拿到自己的锁，都检查通过，都保存，同一座位被订两次。
- **仲裁者放在共享存储里：** 数据库对"场次 id 加座位 id"建唯一约束，插入订单行时由数据库保证只有一个成功，失败的得到约束冲突。多座位订单放在一个事务里，全有或全无。
- **悲观与乐观：** 悲观锁先锁住要订的座位行（`SELECT ... FOR UPDATE`），按固定顺序加锁防死锁；乐观做法直接插入，靠唯一约束或版本号发现冲突后重试。
- **临时占座：** 常用带过期时间的键值存储，原子的"不存在才设置，并带过期"操作（Redis 的 `SET key value NX EX seconds`）；过期由存储负责，不需要自己跑清理任务。
- **内存版的位置：** 面试里的内存版回答的是单进程内的正确性；说出"多实例时仲裁交给数据库的唯一约束"是资深加分点。
- **相关：** 异步环境里即使单线程，`await` 处也会交错，同样需要事务或分布式锁。
