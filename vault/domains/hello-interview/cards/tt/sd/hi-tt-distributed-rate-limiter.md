## Q
**分布式限流器（Rate Limiter）**｜系统设计｜TikTok 报告 · 先修见：聊天与即时通讯系统、在线国际象棋平台、分布式限流器 · 模式：限流算法与原子计数、版本化规则与配置分发

设计一个限流系统，控制 API 请求的速率以防止过载并保证公平：按用户 ID、IP 或 API Key 识别客户端，按可配置规则（如每用户每分钟 100 次）限制请求，超限时返回 HTTP 429 并带上剩余额度和重置时间的响应头。要能在多台服务器间共同计数。规模按每秒 100 万请求、1 亿日活设计，单次检查额外延迟 < 10ms。常见变体：给公司内部服务之间做限流；"每 T 秒最多 N 个请求"的基础版；要求支持固定窗口、滑动窗口、令牌桶等多种算法；以及"1 亿日活怎么保证系统不被打垮"的开放版。

讲出：难点一句话、必讲的决策、取舍、级别期望。

## A
**一句话。** 对海量计数器做低延迟的原子读改写：难点是算法选择（突发与精度）、状态放哪与怎么分片，以及限流组件自己故障时放行还是拒绝。

**必讲。**
- **算法与原子性：** 固定窗口（`INCR` 加 `EXPIRE`）最便宜，但窗口交界 1 秒内能打出两倍额度；滑动窗口日志最准但内存随请求数线性涨；滑动窗口计数 `上一窗口计数 × 重叠比例 + 当前计数` 内存小、误差小；令牌桶状态只有剩余令牌加上次补充时间，允许可控突发，是默认选择，漏桶用于只能匀速的下游 → 读、算、写回必须一步，否则两个网关各读旧值双双放行 → 用 Redis Lua 脚本一次执行、一次往返；时间用 Redis `TIME` 避免网关时钟偏差，`PEXPIRE` 让不活跃桶消失。
- **扛 100 万次/秒：** 单 Redis 约 10 万次/秒，撑不住 → 按客户端标识分片（Redis Cluster 16384 槽），同一客户端永远同一分片；每片按 5–7 成负载约 7 万次/秒算需约 15 个主分片，主从复制。
- **限流器挂了：** fail-closed 等于关掉整个 API 还引发重试风暴，只适合支付这类场景；fail-open 保持可用但失去保护，且故障常与高峰同时 → 折中：放行但退化为每网关本地令牌桶（限额按网关数均分）并告警，必须说出选择和理由。

**取舍。**
- 降延迟：先做长连接池和就近部署，跨区域各自限流接受最终一致；进阶是网关批领令牌本地发放，Redis 压力降一个数量级，代价是多放行最多一批、重启丢未用令牌。
- 热点客户端：合法大客户给更高限额或专用分片；恶意流量连续超限进封禁列表，网关本地缓存几秒，更上游交 CDN 和 DDoS 防护；共享出口 IP 的限额放宽，靠认证后的用户限额。
- 多规则要多个键同分片（hash tag `{clientId}`），脚本里一起检查，全部通过才扣减。
- 动态规则网关每 30 秒左右轮询，紧急调低再叠加 etcd watch 推送，轮询兜底。
- 超限返回 429 加 `Retry-After`；内部服务限流要与舱壁、熔断配合，不是替代。

**级别。** 高级：四种算法对比、Lua 原子性、分片与容量估算、fail-open 与 fail-closed。资深：批领令牌的误差分析、热点与封禁、多区域最终一致、动态规则兜底、自身可观测与降级。
