## Q
**缓存一致性与热点 Key**｜系统设计｜TikTok 设计轮常见追问 · 先修见：新闻聚合信息流、聊天与即时通讯系统、在线国际象棋平台 · 模式：热点键与竞争、缓存、失效与一致性窗口、强一致与最终一致的取舍

在系统设计面试里，给你一个读多写少的服务（商品详情、用户资料、视频元数据），要求设计它的缓存层：读峰值每秒 100 万次，数据库只能稳定承受每秒 2 万次读；数据会被修改，缓存和数据库之间的不一致必须被控制在可说明的范围内；还要扛住热点（一个爆款商品或一个明星账号占掉整个流量的很大一部分）。面试官会连续追问：先更新库还是先删缓存、删除失败怎么办、缓存击穿 / 穿透 / 雪崩各怎么防、分布式锁怎么用才对、热 key 怎么发现和处理。

讲出：难点一句话、必讲的决策、取舍、级别期望。

## A
**一句话。** 缓存把“一个正确的数据库”变成“两份会分叉的副本”：核心是把不一致窗口压到最小且有兜底，缓存失效时不压垮数据库，单个热 key 的流量不落到某一个节点。

**必讲。**
- **旁路缓存一致性：** 写时更新库后删缓存，不更新缓存（并发写时缓存上的顺序可能和库不同，留下旧值）。先删缓存再更库：A 删缓存，B 此时未命中读到旧值回填，缓存留旧值到 TTL，窗口是整个库更新耗时；先更库再删缓存要 B 读库加回填比写库加删除还慢才出错，概率低得多，所以选它，但不是强一致。删除失败：应用重试几次，再丢消息队列重试（删除天然幂等），binlog 订阅链路独立再删一次，最后 TTL 兜底。回填读从库而从库落后会回填旧值 → 对刚失效的 key 回填读主库，或延迟消息做延迟双删（不用线程睡眠），或值带版本号用 Lua 比较，旧版本不覆盖新版本。
- **击穿：** 热 key 过期瞬间成千上万请求一起回源 → 进程内合并（singleflight、Caffeine `get(key, loader)`）；跨进程 `SET lock:key token NX PX 3000` 抢重建权，抢到后再查一次缓存；逻辑过期则不设物理 TTL，读到过期值立即返回旧值，由抢到锁的一个线程异步重建，无人阻塞，代价是短暂旧数据。
- **热 key：** 100 万 QPS 里爆款占 20% 即 20 万 QPS，哈希分片后永远落同一节点，加机器没用 → 应用实例本地缓存约 1 秒（1000 实例最多每秒 1000 次回 Redis）；不够再把 key 复制成 `item:123#0…#N-1` 随机读，写要删全部副本，只适合读极多写极少；热点写用分片计数。发现热 key：SDK 或代理层 count-min sketch 加小顶堆维护 Top-K，超阈值（如单实例每秒 1000 次）上报。

**取舍。**
- 穿透（数据库根本不存在）：缓存空结果 30–60 秒，或布隆过滤器（1 亿 ID、1% 误判约 120 MB），新增数据必须同步加入否则被误拒。雪崩：TTL 加 0–20% 随机抖动，多级缓存，Redis 高可用，最后对数据库限流降级，宁可部分失败。
- 分布式锁：单实例 `SET NX PX` 加唯一 token，释放用脚本比对 token；风险是锁过期持有者还在跑（GC 暂停）和主从切换丢锁 → 资源方用围栏令牌（单调递增号，拒绝更小的写），需要时用 ZooKeeper 或 etcd。缓存重建这种重复执行无害的场景锁只是优化；库存扣减、转账靠数据库唯一约束、条件更新或版本号仲裁。

**级别。** 高级：先更库再删缓存的原因和仍会出的错、binlog 兜底、击穿穿透雪崩方案、本地缓存处理热 key、Redis 锁基本用法。资深：从库延迟与版本号保护、热 key 发现与副本、围栏令牌与锁的适用边界、按命中率推算数据库容量、故障演练与一致性度量。
