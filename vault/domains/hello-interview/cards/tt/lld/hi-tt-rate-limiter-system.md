## Q
**限流器（单机类设计）**｜低层设计｜通用 · 先修见：可配置淘汰策略的内存键值存储 · 模式：限流算法与原子计数、策略模式：把变化点做成可替换部件、类设计中的并发：锁粒度与线程模型、时间注入与可测试性

设计一个限流器：在 T 秒内最多允许某个调用方发起 N 个请求，超出的请求被拒绝。要求支持多种限流算法（固定窗口、滑动窗口、令牌桶等），可以按用户或 API Key 分别限流，线程安全，算法可以替换而不改调用方。这是类与接口层面的设计题，和"分布式限流器"那道系统设计题不同——这里关心的是类怎么划分、状态怎么放、并发怎么处理、怎样写出能测试的代码。

讲出：难点一句话、必讲的决策、取舍、级别期望。

## A
**一句话。** 策略模式的典型题：算法做成可替换、只管单个 key 的状态机，按 key 管理与并发放外层，时间可注入，代码才好测。

**必讲。**
- **并发正确性：** 先读计数再写回，多线程各读到旧值双双放行 → per-key 锁让“读状态、判定、写状态”成为一个临界区；全局一把锁所有 key 串行，无锁 CAS 在状态含多字段（令牌数加时间）时要打包成不可变对象整体 CAS，复杂。代码里从不同时持有全局锁和 key 锁（先放全局锁再取 key 锁），避免锁顺序死锁。测试：额度 100 的 key 被 130 个线程同时调用，恰好放行 100 个。
- **算法取舍：** 固定窗口最便宜但有边界突发（`FixedWindow(3,10)` 下 8、8.1、8.2 与 10、10.1、10.2 秒 6 个请求全放行，滑动窗口日志后三个被拒）；滑动窗口日志最准但内存随额度线性涨；滑动窗口计数（当前与上一窗口两个计数按重叠比例加权）内存 O(1)、误差小；令牌桶允许突发，是 API 限流默认选择。要“严格每 T 秒不超过 N”选日志，“平均速率受限但允许突发”选令牌桶；先实现一种，说出差别，再按要求补。
- **时间源：** 用单调时钟（`time.monotonic`），墙钟被 NTP 校时或手改会回退，令牌为负或窗口错乱；时钟作为构造参数注入，测试用可拨动的假时钟，不 `sleep`。

**取舍。**
- 内存增长：`_entries` 对每个出现过的 key 留状态，key 来自用户输入会无限涨 → 惰性清理久未访问的 key 或带容量上限的 LRU；滑动窗口过一个窗口、令牌桶补满后状态都等价于初始，删除不影响正确性，所以允许“删除后重建”。
- 单机变分布式：状态放 Redis 加 Lua 保证原子，`Limiter` 接口只依赖 `try_acquire`，基本不变。
- 多规则（每秒 10 次且每分钟 100 次）：`CompositeLimiter` 全部通过才放行，其一拒绝时之前通过的不应被扣减，先检查后统一扣或回滚。
- 带权重请求：`try_acquire(now, cost=1)`，令牌桶直接扣 `cost`，窗口类按 `cost` 累加。
- 默认非阻塞立即判定；要“等到有配额再执行”就在 `retry_after` 上封装睡眠重试或条件变量。

**级别。** 高级：策略模式支持多算法、per-key 锁、单调时钟与时钟注入、各算法取舍。资深：内存回收、权重与多规则组合、单机到分布式时接口不变、并发测试方案、性能分析。
