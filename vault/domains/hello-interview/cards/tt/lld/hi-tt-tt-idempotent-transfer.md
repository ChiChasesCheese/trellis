## Q
**幂等转账服务**｜低层设计｜支付类设计练习 · 先修见：可配置淘汰策略的内存键值存储、聊天与即时通讯系统 · 模式：幂等键与只生效一次

实现 `transfer(client, key, src, dst, amount, currency)`，把钱从一个钱包转到另一个钱包。客户端会因为超时而重试，同一个 `key` 可能先后到达多次，也可能同时到达多次。要求：同一个键只转一次，重试拿到和第一次完全相同的结果；同一个键配了不同的请求要拒绝；余额不足时拒绝，并且这个拒绝结果也要被记住；并发到达的重复请求不会各执行一遍。面试官接着会问：处理到一半进程崩溃怎么办、第二步要调外部支付渠道怎么办、键存多久、多实例部署怎么办、同一个账户被高并发转出怎么办。

讲出：难点一句话、必讲的决策、取舍、级别期望。

## A
**一句话。** 幂等不是“检查一下是否做过”，而是先用唯一约束原子地占住键，再把业务动作和结果保存放进同一个事务，并让并发的重复请求合并到第一个请求上，而不是各自再执行。

**必讲。**
- **进行中状态与合并：** 只在完成后记录键有个窗口，两个相同请求同时到达都查不到、都执行，转账两次；全局锁让所有转账串行，每键锁要管生命周期 → 占位记录加事件：第一个请求持占位，其余等待并拿到第一次的结果，不是“冲突”错误；`done.wait` 带超时，避免第一个卡住拖垮所有重试者。
- **业务拒绝也要记住：** 余额不足是确定的业务结果，不记住的话同一个键第二次到达时恰好有人充值就成功了，同键两次结果不同；拒绝与成功一样保存，充值后要重试必须用新键（新的业务意图）。网络错误、超时、库暂不可用是“结果未知或可重试”，不当结论保存：记账前失败就释放键，记账后失败靠分录 ID 幂等兜底，重放不会记两次。
- **检查与扣款原子：** 先读余额再写账本，中间别的转账可能把钱转走 → 同事务里 `UPDATE wallet SET balance = balance - x WHERE id = ? AND balance >= x`，影响行数 0 即不足；涉及多账户按账户 ID 排序 `SELECT … FOR UPDATE`。
- **崩溃恢复：** 占键后执行完成前崩溃，键永远停在“进行中” → 键记录带开始时间，恢复任务扫描超阈值的记录用同一个键重放第二步；分录 ID 由键派生，重放要么发现已记账补写结果，要么记账。

**取舍。**
- 同键不同请求拒绝（`KeyReuse`，422）：几乎总是客户端 bug，悄悄执行第二个会转出错误金额，悄悄返回第一个结果会让调用方以为第二个成功。
- 重放返回同码同内容（新建 201），`StillRunning` 用 409 加 `Retry-After`。
- 键保留至少覆盖客户端最长重试窗口（24 小时到几天），过期后按时间分区批量清理，过短会让迟到的重试变第二次转账。
- 外部支付渠道不能放进数据库事务：事务里写业务数据和“待发出的渠道请求”（outbox），后台用同一个幂等键调用，超时视为结果未知，用同键查询或重试，绝不当失败重新下单；三层幂等（客户端到平台、平台到渠道、崩溃窗口先记意图再重放）缺一层就会重复扣款。
- 多实例：键表与账本同库，才能同事务提交。

**级别。** 高级：占位记录合并并发重复、指纹检测同键异请求、检查与扣款原子、拒绝结果也记住。资深：崩溃恢复与重放、outbox 与外部渠道结果未知、三层幂等、唯一约束与条件更新、键保留期与清理、热点账户串行化。
