## Q
语言选型最常见的失败是什么？基于微基准的决定、热身被忽略、“重写能解决一切”的想法，在真实数字上怎样出错？

## A
**失败一：被微基准误导**。同一个三亿次的整数循环，本机测量 Java 约 92 ms、Rust 约 135 ms、Go 约 161 ms，三者差距小于两倍，且 Java “赢”。如果据此得出“Java 比 Rust 快”，就被 JIT 针对这个简单循环的优化误导了；换成有大量内存访问、分配或锁的真实负载，排序完全不同。微基准衡量的是编译器处理那一小段代码的能力。

**失败二：忽略热身**。同一段 Java 循环，第 1 轮约 3.5 ms，稳态约 1.9 ms，关闭 JIT 约 17 ms。用只跑一次的测试比较 Java 与 Go，会得出错误结论；反过来，用稳态数字评估一个冷启动的函数计算场景，又会高估 Java。基准要匹配生产形态：长跑服务测稳态，函数计算测冷启动。

**失败三：只比平均，不比尾部**。GC 暂停、JIT 去优化、事件循环阻塞都体现在 p99 上。一个 Python 协程里的阻塞调用，使三个任务从 1.0 秒变成 3.4 秒，平均值可能还可以接受，尾部已崩溃。

**失败四：为性能重写，结果没有收益**。典型过程：服务慢 → 怀疑语言 → 重写 → 发现慢的原因是数据库查询或序列化，新语言并没有改善；同时丢掉了旧系统多年累积的边界情况处理。正确的顺序是：性能分析 → 找到瓶颈 → 局部修复（算法、缓存、批量化、原生扩展）→ 仍不够才考虑换语言。

**失败五：低估学习成本**。Rust 的所有权在小项目上是投资，在三个月交付的项目上可能是风险。把“语言能做到”与“我的团队在预算内能做到”混为一谈。

**失败六：技术栈碎片化**。每个团队选自己喜欢的语言，三年后组织里有七种语言，没有一种有足够的人才深度，跨团队支持变得不可能。

**防线**：
1. 基准用接近生产的数据量和形态，包含热身、尾部延迟和资源占用。
2. 重写之前先用性能分析器证明瓶颈在语言上。
3. 在组织层面限制“官方支持”的语言数量，新增需要评审。
4. 用原型验证，而不是论文式比较。
