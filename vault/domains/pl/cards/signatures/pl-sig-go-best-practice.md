## Q
写地道的 Go 有哪些核心实践？资深工程师在项目结构、接口、错误和并发上遵守什么规则？

## A
**规则与理由**：
1. **接受接口，返回具体类型**（accept interfaces, return structs）：函数参数用小接口，使调用方灵活；返回值用具体类型，调用方能访问全部能力，接口由使用方定义。
2. **接口小而专一**：一到两个方法最佳；大接口是设计问题。
3. **错误是值，立即处理或加上下文向上传**：用 `fmt.Errorf("读取配置: %w", err)` 包装，调用方用 `errors.Is`/`errors.As` 判断；不要忽略错误，不要既记录又返回（重复）。
4. **每个 goroutine 有明确的退出条件**：用 `context.Context` 传递取消和超时，发送方负责关闭通道；不要“发射后不管”。
5. **共享内存时加锁，传所有权时用通道**：两者都是工具，别教条；热路径上互斥锁往往比通道简单也快。
6. **用 `go test -race` 和 `go vet` 作为常规检查**。
7. **项目结构扁平**：先把代码放在一个包里，真有需要再拆；包名短、小写、无下划线；`internal/` 封装内部实现；不照搬 Java 的深层目录。
8. **零值可用**：设计类型时让零值就是合理的初始状态（`sync.Mutex`、`bytes.Buffer`），减少构造函数。
9. **表驱动测试**：把输入与期望放进切片循环执行，新增用例只加一行。

**何时破例**：性能热点可以用 `sync.Pool`、手工内存复用；确实需要通用容器时用泛型，但不要为了“看起来现代”把业务代码泛型化；与 C 互操作时不得不使用 `unsafe` 与 cgo，封装在小模块里。

**一个判断标准**：一位没读过你代码的 Go 程序员，能不能在不翻文档的情况下读懂并正确修改它？如果能，就是地道的 Go。
