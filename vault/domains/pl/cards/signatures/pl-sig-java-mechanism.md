## Q
JIT 内部做了哪些优化使“动态”的 Java 能追上静态编译？推测优化（speculative optimization）与去优化（deoptimization）是什么？

## A
**JIT 的优势来自运行时信息**。典型优化：
1. **内联**：把小方法的函数体直接嵌入调用点，省掉调用开销，并打开后续优化。
2. **逃逸分析**：对象不逃出方法，就把它拆成局部变量（标量替换）甚至不分配。
3. **循环优化**：展开、向量化、去掉边界检查。
4. **锁消除/粗化**：证明锁不会被竞争，直接去掉。

**推测优化**：这是静态编译器做不到的部分。JIT 观察实际执行，并**押注**：
- 这个接口调用在运行中**只见到一种实现**，于是直接内联这个实现（单态内联），加一个“类型检查守卫”。
- 这个 `if` 分支从未执行，就不为它生成代码。
- 这个值始终非空，去掉空检查。

**去优化**：押注失败时（出现了第二种实现、走到了从未执行的分支），守卫触发，JVM 把这段代码**撤回到解释器**继续执行，之后重新收集数据再编译。正确性始终保证，代价是一次性能下降。

**后果**：
1. **性能曲线不是平的**：程序运行中加载了新的实现类，可能触发去优化，延迟出现尖刺。
2. **微基准很难写对**：JIT 会把不使用结果的代码整个删掉（死代码消除），要使用 JMH 框架。
3. **同一份代码，在不同负载下表现不同**：因为 JIT 押注的对象是真实流量。

**数字**：一次本机测量，关闭 JIT 约 17 ms 每轮，开启后稳态约 1.9 ms 每轮，差约 9 倍。

**对比**：Go 和 Rust 在构建期完成全部优化，行为可预测，没有预热，也没有去优化；它们看不到运行时信息（只能用 PGO，按训练数据编译）。Java 的路线是：把优化推迟到最知道情况的时刻，用复杂的运行时换取峰值性能。

**要记住的一点**：理解 JIT，就理解了为什么 Java 服务要预热、要压测稳态、要谨慎对待“看起来没用”的代码。
