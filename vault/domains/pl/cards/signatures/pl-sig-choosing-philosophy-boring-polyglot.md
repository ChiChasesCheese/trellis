## Q
“选无聊的技术”与“合适的工具做合适的事”（多语言分工）看似矛盾，资深工程师怎样调和它们？

## A
**两个都是真的经验**：
- **选无聊的技术**（Dan McKinley 提出）：每个组织有有限的“创新代币”。新数据库、新语言、新框架都要消耗代币，因为你不知道它在生产中的失败方式。把代币花在真正能带来业务差异的地方，其余用成熟、已知失败方式的技术。
- **合适的工具做合适的事**：Python 做机器学习，Go 做服务，Rust 做热点组件，Java 做企业系统。强行统一在一门语言上，会让某些问题难做。

**调和的方式：区分“新”与“多”**：
1. **“无聊”指的是成熟度，不是新旧**。Go 与 Rust 在各自领域已经成熟；一个新的小众语言不是。
2. **多语言的单位是“服务”或“组件”，边界在协议**。每个组件内部保持单一语言和技术栈，组件之间通过稳定的接口（HTTP、gRPC、消息）通信，替换一个组件的语言不影响其他。
3. **每增加一门语言，要有明确的、可度量的理由**：性能需求不满足、生态缺失、安全要求，而不是“团队想学”。
4. **投入要与收益匹配**：引入一门新语言意味着要建立构建、部署、监控、代码规范、招聘与培训的全套，只在有一个明显的、持续的收益时才值得。

**反例**：
- 为了简历好看引入新语言（简历驱动开发）。
- 一个十人团队同时使用五门语言，每门都没有深度。
- 因为一次性的基准测试结果就重写系统。

**正例**：
- 大型系统在 Python/Java 为主的基础上，只对一个确认的热点用 Rust 重写。
- 用 Go 写所有基础设施工具，一种语言，统一的构建和部署。

**揭示的价值观**：技术选择的目标是**降低整个组织的长期成本**，不是追求局部最优。最优的语言选择往往是“**足够好、团队熟悉、边界清晰、可替换**”。
