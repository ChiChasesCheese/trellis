## Q
Rust 社区常说“让编译器成为你的搭档”（lean on the compiler）。这种“编译期付费”的哲学与 Go 的“运行时付费”有什么根本区别？

## A
**Rust 的价值观：正确性优先，成本前置**。设计原则可以概括为：
1. **让非法状态不可表示**：用枚举、所有权、类型状态（typestate）让错误的程序无法编译。
2. **显式胜于隐式**：没有隐式类型转换，没有隐藏的分配，错误通过 `Result` 显式传播，可变性必须声明（`mut`）。
3. **安全默认，危险显式**：所有不安全操作都要写 `unsafe`，可搜索可审计。
4. **编译错误是服务**：错误信息详细、给出修复建议（如“移除这个分号”），编译器是第一位审阅者。
5. **重构有信心**：改一个类型的签名，编译器带你找出所有要改的地方。

**与 Go 的对比**：
- **Go**：编译快、规则少，把剩下的问题留到测试、`go vet`、竞争检测器和线上；信任开发者与评审。成本后置，简单优先。
- **Rust**：编译慢、规则多，把尽可能多的问题挡在编译期；开发者先为说服编译器付出时间，之后线上更安静。成本前置，保证优先。

**体验上的差异**：写 Rust 的早期是“与编译器战斗”，之后是“编译通过就大概率正确”；写 Go 是“很快跑起来”，之后是“靠测试和观察发现问题”。两种体验都是真实的，不是谁好谁坏，而是**你愿意在哪个阶段付出**。

**代价**：
- 学习曲线陡峭，团队培训成本高。
- 迭代原型较慢，设计要先想清楚所有权。
- 有些“合理的程序”要绕着借用检查器重构。
- 编译时间与二进制大小。

**揭示的价值观**：Rust 相信**大型、长期、多人维护的关键软件**，错误的成本远高于编写的成本；所以把“让机器检查”做到极致。这个赌注在安全和基础设施领域已被验证，在一般业务领域仍有争议。
