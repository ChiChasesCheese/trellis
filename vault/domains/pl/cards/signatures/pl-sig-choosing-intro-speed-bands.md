## Q
同一个计算密集的循环，在 Go、Rust、Java、Python 里大约差多少？“速度档位”应该怎样理解和使用？

## A
**本机一次测量**：三亿次循环，每次计算 `s += (i % 7) * (i ^ 3)`（整数运算，无内存访问）：

| 语言 | 耗时 |
|---|---|
| Java（JIT 热身后） | 约 92 ms |
| Rust（`-O`） | 约 135 ms |
| Go | 约 161 ms |
| Python（3000 万次实测 1165 ms，外推三亿次） | 约 11.7 s |

**读法**：
1. **编译型语言在同一档**：Rust、Go、Java 的差距在两倍以内，而且谁快谁慢取决于具体代码（编译器如何向量化、JIT 如何优化）。这里 Java 略快是因为 JIT 把该循环优化得很好，不代表 Java 总是比 Rust 快。
2. **Python 在另一档**：大约慢 70 到 130 倍。这是纯 Python 循环的结果；如果把循环放进 NumPy，差距会缩小到同一量级。
3. **真实程序的差距通常更小**：多数服务的时间花在 I/O、序列化、数据库、锁和内存分配上，语言本身的计算速度是其中一小部分。

**档位的实用划分**：
- **第一档（原生，可预测）**：C、C++、Rust。
- **第二档（原生或 JIT，接近第一档）**：Go、Java、C#。
- **第三档（解释型，慢一到两个数量级）**：Python、Ruby、纯 JavaScript 解释执行（V8 的 JIT 让现代 JavaScript 属于第二档偏下）。

**使用档位时的规则**：
1. 差一档才有决定意义；同档之间的差异让位于团队、生态和部署。
2. 先找到真正的瓶颈：用性能分析器看时间花在哪里，再决定是否需要换语言或把热点下沉到原生库。
3. 延迟分布比平均值重要：GC 暂停、JIT 预热、冷启动影响的是尾部延迟。

**要记住的一点**：速度档位是选语言时的**过滤器**，不是**排序器**：它帮你排除明显不合适的，剩下的靠其他维度决定。
