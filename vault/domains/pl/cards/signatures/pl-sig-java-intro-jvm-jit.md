## Q
JVM、字节码和 JIT 编译（just-in-time compilation）是什么？为什么 Java 程序“越跑越快”，一个实测怎样体现预热？

## A
**JVM 与字节码**：`javac` 把 `.java` 编译成 `.class` 文件，里面是一种与具体 CPU 无关的指令集——字节码。JVM 加载并执行字节码。最初靠解释器逐条执行，较慢。

**JIT**：JVM 在运行时统计哪些方法和循环被频繁执行（热点），把它们编译成当前机器的原生代码。更重要的是，JIT 可以利用**运行时才知道的信息**做优化：哪些分支实际从不走、一个虚方法调用实际只有一种实现（于是直接内联），同时保留“假设失效时退回解释”的能力。静态编译器看不到这些，所以长期运行的 Java 程序在某些场景下比提前编译的代码更快。

**分层编译**：先用快速但优化较弱的编译器 C1，热点再用优化强的 C2（也有 Graal 等选择）。

**实测（本机，同一个循环重复 20 次，每轮计时）**：

| 模式 | 每轮耗时 |
|---|---|
| 关闭 JIT（`-Xint`，纯解释） | 约 17 ms，每轮都一样 |
| 默认（开启 JIT）第 1 轮 | 约 3.5 ms |
| 默认第 2 轮起 | 约 1.9 ms，稳定 |

热身后比纯解释快约 9 倍；第一轮比稳态慢近一倍，因为编译尚未完成。

**后果**：
1. **预热**：服务刚启动时较慢，需要流量（或预热请求）后才达到稳态。
2. **长期运行占优**，短命进程（命令行、函数计算）不占优。
3. **性能测试必须预热**，否则测的是解释器。
4. **启动优化方案**：类数据共享（CDS）、GraalVM 原生镜像、OpenJDK 的 Leyden 项目，都是把一部分工作提前到构建期。

**要记住的一点**：Java 的性能是“动态”的，取决于运行时间、负载形状和 JIT 的决策，这既是它的力量，也是它不如静态编译语言可预测的地方。
