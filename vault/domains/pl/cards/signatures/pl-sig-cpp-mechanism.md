## Q
C++ 程序为什么又快又可预测？从源码到机器码这条链上，哪些环节造就了这点，又损失了什么？

## A
**快的来源（编译期做了大部分工作）**：
1. **提前编译（AOT）到机器码**：没有解释器，没有虚拟机，没有预热；程序一启动就是满速。
2. **静态分派加内联**：普通函数、模板、`constexpr` 在编译期绑定，编译器能把调用展开，再做向量化、常量折叠、死代码消除。`std::sort` 比 `qsort` 快约 4 倍（比较器被内联）。
3. **值语义与连续内存**：`vector<int>` 存的就是 `int`；遍历是顺序读取，缓存友好；本机 200 万个 `int` 求和，`vector` 比 `list` 快约 20 倍。
4. **无强制运行时**：没有 GC、没有调度器、没有后台线程；不用的功能（异常、RTTI）可以关掉。
5. **优化器利用未定义行为**：有符号溢出、空指针等"不会发生"的假设让编译器大胆变换。
6. **链接时优化（LTO）与 profile 引导优化（PGO）**：让编译器看到整个程序，并按真实负载决定内联与布局。

**可预测的来源**：
- **没有 GC 暂停**：释放在析构函数里，时间点和成本可见；
- **没有 JIT 编译的预热和去优化**；
- **分配是显式的**：热路径上可以预先分配，避免运行时的 `malloc`；
- **延迟的来源都是你能看到的**：缓存未命中、系统调用、锁争用、分支预测。

**损失了什么**：
1. **没有运行时自适应**：JVM 的 JIT 可以根据实际运行数据做推测优化、去虚化、逃逸分析；C++ 的 AOT 只能靠编译期信息和 PGO；
2. **没有可移植的二进制**：为 x86 编译的程序不能在 ARM 上跑，不同编译器、标准库之间 ABI 也不通用；
3. **编译慢**：模板与头文件让构建时间成为开发瓶颈；
4. **调试与诊断需要工具**：崩溃通常是段错误，不是带栈追踪的异常；需要调试器、sanitizer、核心转储；
5. **安全由你负责**。

**典型的性能工程流程**：写正确的代码 → 用 `perf`/Instruments/VTune 找热点 → 看汇编确认编译器做了什么 → 调整数据布局、避免分配、消除分支 → 用基准测试（Google Benchmark）验证。

**对比**：Java 在稳态下可以接近 C++，但启动慢、延迟有 GC 抖动；Go 的 GC 暂停很短但仍存在，编译器优化弱于 LLVM；Rust 与 C++ 的机器码质量同级（都用 LLVM），区别在安全；Python 慢两个数量级，靠 C 扩展。

**要记住的一点**：C++ 的速度不是因为"某个魔法"，而是因为"运行时什么都不做"，所有的决定提前到编译期，剩下的由你控制。
