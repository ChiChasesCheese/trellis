## Q
CPython 的执行模型决定了它慢在哪里？一个简单循环里每次迭代发生了什么，近年的优化（自适应解释器、JIT）改变了什么？

## A
**执行流程**：源码先被编译成字节码（`.pyc` 缓存），然后由一个巨大的 `switch`/`goto` 循环——字节码解释器——逐条执行。每条字节码操作的是 Python 对象。

**一次 `s += i * 2` 里发生的事**：
1. 从局部变量表取出 `i`、`s`，它们是指向堆上整数对象的指针，增加引用计数。
2. 调用 `i * 2`：检查两个对象的类型（是否整数）、分派到整数乘法实现、**分配**一个新的整数对象存放结果。
3. 调用 `s + 结果`：同样的类型检查与分配。
4. 把新对象存回 `s`，旧对象引用计数减一，可能被释放。

每次迭代有多次类型分派、对象分配和引用计数操作。本机实测，纯 Python 循环五百万次约 145 ms，平均每次迭代约 29 ns，相当于几十到上百条机器指令；C 里同样的循环是约 1 ns 以内。

**对比其他语言**：Java 与 Go 在编译期（或 JIT）知道 `i` 和 `s` 是整数，直接生成加法指令；Python 的变量没有类型，每次都要在运行时发现。

**近年的改进**：
- **自适应解释器（Python 3.11，PEP 659）**：观察到某条字节码总是处理同类型的数据，就把它改写成专门化版本（例如“整数加法”），去掉类型分派，常见代码快 10% 到 60%。
- **实验性 JIT（3.13 起，PEP 744）**：基于“拷贝并修补”的轻量 JIT，目前收益有限，是长期方向。
- **自由线程**（见 GIL）。
- **更快的启动与更便宜的帧**。

**为什么还是慢**：对象模型（一切皆对象、动态属性）限制了优化空间，去掉这些需要改变语言语义。

**实践推论**：
1. 热循环放进原生库（NumPy）或用 Cython/Numba/Rust 扩展。
2. 减少 Python 层的“逐元素”操作，改用向量化与内置函数（`sum`、`map`、推导式比显式循环快）。
3. 在 Python 里做性能优化的第一步是用 `cProfile` 找到热点，而不是微调语法。

**要记住的一点**：Python 的慢是由“每一步都要动态确认”的成本累积而成的；让它快的唯一彻底办法，是不让大量的步骤发生在 Python 里。
