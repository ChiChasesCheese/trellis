## Q
部署形态（二进制、虚拟机、解释器）怎样影响语言选择？一个“hello world”在五门语言里的体积、内存和启动时间差多少？

## A
**三种部署形态**：
1. **自包含的原生二进制**（Go、Rust、C++）：编译成可执行文件，拷贝即可运行，不依赖目标机器的运行时。C++ 默认动态链接系统的 C++ 运行库，所以目标机器要有匹配版本的库，除非静态链接。
2. **虚拟机加字节码**（Java）：需要 JVM，应用以 JAR 形式分发（或用 `jlink`、GraalVM 原生镜像打包）。
3. **解释器加源码/依赖**（Python）：需要匹配版本的解释器、虚拟环境和依赖包，原生扩展还要匹配平台。

**本机一次测量（打印 `hi` 的最小程序，量级参考）**：

| 语言 | 产物 | 启动时间 | 常驻内存 |
|---|---|---|---|
| C++（Clang `-O2`，动态链接系统的 libc++） | 约 33 KB 的可执行文件 | 与 Rust 相当（并排实测，差别在零点几毫秒内） | 约 1.6 MB |
| Rust（`rustc -O`） | 约 470 KB 的可执行文件 | 约 9 ms | 约 2 MB |
| Go | 约 2.4 MB 的静态可执行文件 | 约 10 ms | 约 4 MB |
| Python | 源文件加解释器 | 约 9 ms | 约 17 MB |
| Java | 类文件，需要 JVM | 约 14 到 25 ms | 约 42 MB |

**解读**：
1. 对长期运行的服务，这些差别（几十 MB、十几毫秒）微不足道，被业务数据和缓存淹没。
2. 对**大量小实例**（每个请求一个函数、边车容器、命令行工具、边缘设备），内存和启动成为成本：一千个 Java 实例比一千个 Go 实例多占几十 GB。
3. **镜像体积与分发**：Go 与 Rust 可以放进 `FROM scratch` 镜像，几 MB；Java 需要带 JRE 的镜像（百 MB 量级）；Python 需要解释器和依赖（几十到几百 MB）。
4. **交叉编译与目标平台**：Go 一条命令生成 Linux 静态二进制（本机约 0.5 秒）；Rust 需要目标工具链；Java 的字节码天然跨平台；Python 的纯 Python 部分跨平台，原生扩展不行。
5. Java 的稳态内存还要加堆：JVM 会按堆设置占用远多于 hello world 的内存。

**要记住的一点**：部署形态决定“把代码变成线上进程”这一步的复杂度，它在小规模时不重要，在函数计算、边缘、嵌入式和超大规模下变成首要因素。
