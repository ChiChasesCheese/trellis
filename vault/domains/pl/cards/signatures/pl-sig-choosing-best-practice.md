## Q
资深工程师怎样走完一次语言选型的流程？通用步骤是什么，需要避开哪些常见的错误推理？

## A
**流程（按顺序）**：
1. **写下约束，而不是偏好**：延迟与吞吐目标、数据规模、部署环境、合规要求、团队规模和技能、项目寿命、预算与交付时间。
2. **列出候选（两到三个）**：包括团队已熟悉的语言作为基线。
3. **用约束给候选打分**：每个维度问“这个语言会让我们付出什么代价”，而不是“它有什么优点”。
4. **找出否决项**：一个硬约束不满足就淘汰（例如 JVM 无法满足冷启动要求，Python 无法满足微秒级延迟，团队没人会 Rust 而三个月要上线）。
5. **做一个小的可验证原型**：用候选语言做项目里最难的一小块（性能热点、并发模型、关键集成），一到两周，度量真实数据。
6. **评估可逆性**：如果选错，退出成本多大？边界是否在协议上？
7. **记录决策与理由**（ADR 架构决策记录），写明被否决的选项及其原因，以及何时重新评估。

**需避开的错误推理**：
- **微基准决定一切**：hello world、斐波那契的结果几乎不预测真实服务。
- **只看峰值，不看开发成本**：最快的语言如果让交付晚半年，可能总成本更高。
- **忽视运维**：构建、发布、监控、排障的难度，往往比语言特性更影响长期成本。
- **以为重写会解决问题**：重写常常是在丢掉多年积累的行为细节与修复。
- **从流行度直接得出适配度**：流行说明生态，不说明适合你的问题。

**按语言快速核对**：
- 选 Go 前问：是否需要丰富的类型建模或大量科学计算？是则慎重。
- 选 Java 前问：冷启动与内存足迹是否硬约束？是则评估原生镜像或换语言。
- 选 Rust 前问：团队是否有时间学习，错误的代价是否足够高？
- 选 Python 前问：热点能否下沉到原生库？是否需要严格的静态保证？
- 选 C++ 前问：是否有存量代码或必需的 C++ 库？团队能否在 CI 里坚持 sanitizer、模糊测试和代码评审？没有存量时，要把内存安全的成本与 Rust 比较。

**何时破例**：个人项目与学习项目，可以选择想学的语言；这与生产选型不同。
