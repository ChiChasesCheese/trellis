## Q
把五门语言的经典陷阱与它们背后的设计选择对应起来，会看到什么规律？

## A
| 语言 | 代表陷阱 | 背后的设计选择 | 失败方式 |
|---|---|---|---|
| Go | nil 接口不等于 nil；切片别名 | 接口是（类型，值）对；切片是视图加共享数组 | 静默错误结果 |
| Java | `Integer ==` 在 128 起不相等；`remove(int)` 与 `remove(Object)` | 基本类型与装箱类型并存；重载解析 | 静默错误结果 |
| Rust | 与借用检查器拉锯；发布模式溢出回绕；`Rc` 环泄漏 | 保守的编译期证明；为性能不检查溢出 | 编译错误；静默回绕；泄漏 |
| Python | 可变默认参数；晚绑定闭包；遍历时修改 | 默认值定义时求值；闭包捕获变量；迭代器基于索引 | 静默错误结果 |
| C++ | 悬空引用与迭代器失效；读未初始化变量；有符号整数溢出；`map[k]` 读取会插入 | 零开销加手动内存加 C 兼容：不检查，违反规则即未定义行为（UB） | 崩溃、静默错值，或被优化器“合理”地改写 |

**规律一：每个陷阱都是某个收益的另一面**。
- Go 的“零值可用”与“接口轻量”换来简单，代价是 `nil` 的多重含义。
- Java 的基本类型换来性能，代价是装箱类型的语义差异。
- Rust 的编译期证明换来零成本，代价是学习与拉锯。
- Python 的动态换来灵活，代价是行为发生在运行时、顺序可能出乎意料。
- C++ 的零开销与控制权换来性能，代价是违规即未定义行为：编译器可以假设它不发生。最短的例子（`-Wall -Wextra` 无警告）：

```cpp
bool f(int x) { return x + 1 > x; }   // signed overflow is UB
// f(INT_MAX): -O0 prints 0, -O2 prints 1
```

同一份源码，`-O0` 输出 `0`，`-O2` 输出 `1`，因为优化器按“有符号溢出不会发生”把比较折叠成恒真。`-fsanitize=undefined` 运行时报 `signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'`。

**规律二：静态程度越高，陷阱越早暴露**。Rust 的陷阱大多是编译错误；Go 与 Java 居中，需要 vet、linter 和测试；Python 几乎全在运行时，需要类型检查器和测试覆盖。C++ 是例外：它是静态类型，陷阱却不被类型系统拦截，只能靠警告、sanitizer 和测试。静态类型不等于早暴露，要看类型系统检查的是什么。

**规律三：语言越“信任”开发者，陷阱越隐蔽**。Python、Go 信任你理解语义；C++ 信任得最彻底，连“程序没有 UB”都当作前提；Rust 不信任，所以拦在编译期。

**规律四：陷阱随语言演进被逐步修补**。Go 1.22 修复了循环变量，Java 的 `record`、`switch` 表达式减少了样板错误，Python 的 `dataclass` 避免了手写 `__init__`，Rust 的 NLL 减少了不必要的借用报错。修补的方式是：**新增更安全的路径，不删除旧的**。C++ 是这条规律最极端的例子：`unique_ptr`、`std::span`、`std::array` 逐版出现，裸指针和 C 数组一个也没有删，陷阱的入口永远开着。

**使用方法**：学一门新语言时，找到它的陷阱表，等于拿到了它的设计取舍的索引。
