## Q
写地道的 Rust 有哪些核心实践？资深工程师怎样设计所有权、错误处理、API 和依赖？

## A
**规则与理由**：
1. **先按所有权设计数据**：每个值谁拥有、谁借用、谁需要共享。设计对了，借用检查器几乎不妨碍你；设计错了，会处处冲突。
2. **函数参数优先借用**：读用 `&T`/`&str`/`&[T]`，修改用 `&mut T`，只有真正需要拥有才取值；返回拥有的值，不返回指向局部的引用。
3. **用 `Result` 和 `?` 传播错误**：库用 `thiserror` 定义具体错误类型，应用用 `anyhow` 汇总并加上下文；`unwrap`/`expect` 只用于“真不可能失败”的地方或测试。
4. **用枚举建模状态**，`match` 不写通配分支，新增变体时编译器带你找全。
5. **遇到借用冲突，不要立刻 `clone()` 或 `Rc<RefCell<>>`**：先问能否重新组织数据（拆结构体、用索引代替引用、缩小借用范围）。`clone` 在冷路径上没问题，别在热路径上滥用。
6. **迭代器优于下标循环**：表达意图，编译器可优化，边界检查自然消除。
7. **`unsafe` 越少越好**：封装在小模块，写明不变量，用 Miri 检查；应用 crate 可 `#![forbid(unsafe_code)]`。
8. **公共 API 小而稳定**：默认私有，`pub(crate)` 内部共享，使用 `semver` 并用 `cargo-semver-checks` 检查。
9. **CI 常规检查**：`cargo fmt --check`、`cargo clippy -- -D warnings`、`cargo test`、`cargo audit`/`cargo deny`。
10. **依赖要节制**：每个依赖都增加编译时间与供应链风险；关键依赖审阅 `unsafe` 的使用。

**何时破例**：原型阶段可以大量 `clone` 和 `unwrap` 求快，再迭代；与 C 互操作时 `unsafe` 不可避免，集中处理；异步代码里 `Arc<Mutex<>>` 往往是务实选择。

**一个判断标准**：编译器的报错是在指出设计问题，还是只是你不熟悉规则？前者要改设计，后者要多读文档。
