## Q
全局解释器锁（GIL，Global Interpreter Lock）是什么？它对多线程 CPU 密集代码有什么影响，自由线程（free-threaded）构建又改变了什么？

## A
**是什么**：CPython（标准的 Python 解释器）里有一个全局锁，**任何时刻只有一个线程在执行 Python 字节码**。线程仍然存在，但执行 Python 代码时要轮流持有这把锁。

**为什么有它**：CPython 用引用计数管理内存，每个对象有一个计数器。如果多个线程同时修改计数器，就需要给每个对象加锁（慢且易死锁）。一把全局锁让解释器内部实现简单，对单线程程序也更快，并让 C 扩展容易编写。

**影响**：
- **I/O 密集**：线程在等待网络或磁盘时会释放 GIL，所以多线程仍然能并发，只是不并行执行 Python 代码。
- **CPU 密集**：多个线程无法同时利用多核。

**实测（本机，每个线程做一千万次整数累加）**：

| 构建 | 1 个线程 | 4 个线程（各做同样的活） |
|---|---|---|
| 标准 CPython 3.14（有 GIL） | 0.12 s | 0.47 s |
| 自由线程构建 3.14t（无 GIL） | 0.12 s | 0.14 s |

有 GIL 时，4 个线程的总时间约是 1 个线程的 4 倍：它们实际上被**串行化**了，多线程没有加速，反而有切换开销。无 GIL 的构建下，4 个线程并行，总时间几乎等于 1 个。

**绕开 GIL 的办法（至今主流）**：
1. `multiprocessing` / `ProcessPoolExecutor`：多进程，每个进程有自己的解释器和 GIL，代价是进程间通信与内存。
2. 把计算放到释放 GIL 的原生库里（NumPy、PyTorch 内部会释放 GIL）。
3. `asyncio`：单线程并发 I/O。

**自由线程构建**（PEP 703，Python 3.13 起作为可选的实验构建，3.14 继续推进）：去掉 GIL，改用更细粒度的机制保证安全。代价是单线程略慢，并且依赖 C 扩展必须适配。

**要记住的一点**：GIL 不是缺陷，而是一个已经被取舍的设计，现在正在被逐步改变。
