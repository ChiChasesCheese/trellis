## Q
Go 的单一静态二进制、快速编译和一体化工具链具体是什么样？交叉编译和部署为什么这么简单？

## A
**静态链接的单一可执行文件**：`go build` 把你的代码、所有依赖和 Go 运行时（调度器、垃圾回收器）链接成一个文件，不需要目标机器上有 Go、JVM 或任何共享库（Linux 下纯 Go 程序甚至不依赖 libc）。部署就是拷贝一个文件。

**本机实测**：
- 一个只打印 `hi` 的 Go 程序，二进制约 2.4 MB；同样功能的 Rust 程序约 470 KB。
- 运行时启动约 10 ms，常驻内存约 4 MB。
- **交叉编译**：`GOOS=linux GOARCH=amd64 go build` 在 Mac 上直接产出 Linux x86-64 的静态可执行文件，耗时约 0.5 秒，`file` 显示 `ELF 64-bit LSB executable, x86-64, statically linked`。不需要交叉编译器、不需要容器。

**快速编译为什么可能**：包依赖图是无环的，可以并行编译；编译后的导出信息很小；语言没有头文件、没有模板实例化爆炸；未使用的导入是错误，依赖图保持精简。把标准库的 `net/http` 连同其依赖全部重新编译（`go build -a`）也只要约 2.3 秒（多核）。

**一体化工具链**：`go build/run/test/vet/fmt/mod/doc` 都在一个命令里，没有 Makefile、没有构建配置文件，规则由目录结构和 `go.mod` 决定。

**部署后果**：容器镜像可以是 `FROM scratch` 加一个二进制，镜像只有几 MB；冷启动在毫秒级，适合 serverless 和命令行工具；没有“目标机器的运行时版本不对”这一类问题。

**代价**：二进制比 C/Rust 大（包含运行时和 GC）；使用 cgo 调用 C 库时就失去静态和跨平台编译的优势；运行时的垃圾回收仍有内存与延迟特性。

**要记住的一点**：Go 把“从代码到线上进程”这一整条路径做得非常短，这是它在云基础设施领域取得成功的重要原因，不亚于语言特性本身。
