## Q
写可维护的 Python 有哪些核心实践？资深工程师在类型、依赖、性能、并发和项目结构上遵守什么规则？

## A
**规则与理由**：
1. **公共接口写类型注解，并在 CI 里运行类型检查器**（`mypy` 或 `pyright`）：把动态语言的主要风险压下去，同时保留灵活性。
2. **用 `dataclass(frozen=True, slots=True)` 或 `pydantic` 表达数据**：比字典清晰，边界处用 `pydantic` 校验外部输入。
3. **用 `pyproject.toml`、虚拟环境和锁文件**（`uv`）：每个项目独立环境，依赖可复现。
4. **用 `ruff` 做格式化与检查，用 `pytest` 做测试**：统一风格，提早发现问题。
5. **性能：先测量**。用 `cProfile`/`py-spy` 找热点；热点用向量化（NumPy）、内置函数、标准库，或者原生扩展（Cython、Numba、Rust 的 PyO3）；不要微调语法。
6. **并发选对工具**：I/O 密集用 `asyncio` 加 `TaskGroup`，或线程池；CPU 密集用 `multiprocessing`，或使用释放 GIL 的原生库；评估自由线程构建但先验证依赖是否兼容。
7. **异常要具体**：捕获具体的异常类型，不写裸 `except:`；错误不要悄悄吞掉。
8. **避免可变默认参数与全局状态**；函数小而纯，资源用 `with`。
9. **项目结构**：`src/` 布局，包名不与标准库冲突，入口脚本用 `python -m`。
10. **渐进采用现代特性**：`match`、`|` 联合类型、`pathlib`、`f-string`；与团队的最低 Python 版本对齐。

**何时破例**：一次性脚本、数据探索笔记本可以不加类型不写测试；但一旦要共享或长期使用，就应补上。性能敏感的循环为了速度可能牺牲一部分“Pythonic”。

**一个判断标准**：新同事能否通过类型注解和测试，在不运行代码的前提下理解每个函数的输入输出？如果能，这个 Python 项目就具备了规模化的基础。
