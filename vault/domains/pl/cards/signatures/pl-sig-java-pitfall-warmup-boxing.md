## Q
Java 在生产里最常见的“平台性”陷阱是什么？预热与基准测试错误、短命进程的启动成本、线程耗尽分别是什么表现？

## A
**1. 预热被忽略**：同一段循环，默认运行时第 1 轮约 3.5 ms，稳态约 1.9 ms；关闭 JIT 则每轮约 17 ms（真实输出）。如果性能测试只跑一次，测到的是解释器加编译的混合状态，数字没有意义；如果发布时直接把全部流量切给刚启动的实例，前几十秒的延迟会明显高于稳态，触发超时和重试风暴。

**防线**：
- 用 JMH 做微基准，自动处理预热与死代码消除。
- 上线用渐进放量（金丝雀），先给少量流量。
- 对冷启动敏感的场景使用 CDS、GraalVM 原生镜像，或保持实例常驻。

**2. 微基准里的死代码**：循环里算了结果却从不使用的“基准”，常被 JIT 整个删掉，得到“0 ms”的美好数字，因为结果没被使用。必须把结果交给黑洞（JMH 的 `Blackhole`）或返回。

**3. 平台线程耗尽**：每请求一线程的服务，下游变慢，线程全部阻塞，池满后新请求排队或被拒绝。本机复现：5000 个各睡 1 秒的任务提交给缓存线程池，得到 `OutOfMemoryError: unable to create native thread`。Java 21 起的虚拟线程可以缓解，但要同时限制对下游的并发。

**4. GC 压力来自对象数量**：`List<Integer>`、`Map<String, Long>` 的每个元素都是堆对象，热路径上大量短命对象让年轻代频繁收集。一次本机测量，一千万个对象的数组乱序访问，约是 `int[]` 的 4 倍时间。

**5. 容器里的内存认知**：旧版本 JVM 看不到容器限制，堆设置过大被 OOM 杀；新版本默认感知容器，但仍要注意堆外内存（线程栈、直接缓冲区、元空间）也计入容器内存。

**共同教训**：Java 的性能与资源行为是运行时决定的，必须在**接近生产**的条件下测量，并为预热、堆外内存和下游变慢留出余量。
