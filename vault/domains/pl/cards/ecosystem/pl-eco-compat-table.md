## Q
比较 Go、Java、Rust、Python 的兼容与演进策略：各选了哪种策略，买到什么，付出什么？

## A
| 语言 | 策略 | 买到 | 付出 |
|---|---|---|---|
| Go | Go 1 兼容承诺；语义变化按模块选择加入（`go` 行、`GODEBUG`） | 十几年前的代码仍能构建；升级几乎无痛 | 语言演进谨慎缓慢；早期设计难以修正（只能新增） |
| Java | 二进制与源码高度兼容；先弃用后阻断（`forRemoval`）；实质性破坏很少且给迁移通道 | 企业系统几十年可持续运行 | 历史包袱重（装箱类型、旧 API）；新特性要绕着旧设计做 |
| Rust | 稳定版不破坏；语法层面的变化用 edition 按 crate 选择 | 能做语法层面的改进，同时生态互通 | edition 迁移虽可自动，仍有工作量；编译器要同时支持所有 edition |
| Python | 曾经大断裂（2→3）；现在按固定节奏弃用并删除 | 语言得以清理，标准库保持相对现代 | 次版本升级就可能破坏；生态要持续追赶 |

**逻辑**：兼容策略反映每门语言的用户是谁。Java 与 Go 的用户是长期运行服务的企业，运行的代码寿命以十年计，所以兼容放在首位；Java 的“几乎不删”和 Go 的“承诺”是同一价值观的两种表达。Rust 的目标是长期稳定的同时保持演进，edition 是为此发明的专门机制。Python 的用户是研究者和脚本作者，代码寿命相对短，愿意用较频繁的小破坏换取清洁，但 2→3 的教训让它放弃了大爆炸。

**一个通用观察**：无论哪种策略，设计者最终都发现：**只增不删**是最容易承诺的；**必须修正的错误**需要“选择加入”的机制，让破坏有范围；**大断裂**的成本通常比预期高一个数量级。
