## Q
Go 的 `go.mod` 与最小版本选择（MVS，Minimal Version Selection）是什么？为什么它不需要求解器，也不需要锁文件就能复现？

## A
**`go.mod`**：声明模块路径和依赖，每个依赖写成「至少需要这个版本」：

```
require (
    example.com/b v1.2.0
    example.com/d v1.4.0
)
```

**最小版本选择（MVS）规则**：构建时，对每个模块取整个依赖图里**被要求的最高版本**，就用它。它选的是「满足所有下限的最低版本」，而不是「仓库里最新的版本」。

**场景**：`b` 声明需要 `d v1.2`，`c` 声明需要 `d v1.4`，应用依赖 `b` 和 `c`。MVS 取所有要求里的最大值 v1.4，因此 `d` 用 v1.4，b 和 c 都用同一份。真实验证（用本地目录替换模拟三个版本）：`go list -m all` 显示 `example.com/d v1.4.0`，两个模块输出的都是 `d v1.4`。即使仓库里已有 v1.9，只要没有人要求，就不会用到。

**为什么不需要求解器**：规则只是「取最大值」，是线性的，不会回溯，也不可能无解。因为只会选择图里某个 `go.mod` 明确写过的版本，**结果只取决于 go.mod 的内容，不取决于今天仓库里有什么**。所以不需要额外的锁文件就能复现；`go.sum` 只是记录每个版本内容的哈希，防篡改。

**升级是显式的**：`go get example.com/d@latest` 会把 `go.mod` 里的下限改成最新。新发布的版本不会悄悄进入你的构建。

**主版本规则**：v2 及以上的模块导入路径要带 `/v2`（`example.com/d/v2`），所以 v1 和 v2 被视为两个不同的模块，可以同时存在。这样才让「取最大值」总是安全的：同一主版本内承诺兼容。

**要记住的一点**：MVS 用「保守、可预测」换掉「总是最新」。
