## Q
为什么语言需要模块与命名空间系统？它要同时承担哪几个职责，设计空间沿什么轴取舍？

## A
**问题**：代码量一大，必须分成多个文件、多个团队、多个第三方库，于是出现四个相互独立的问题：
1. **命名**：两个库都有叫 `Parser` 的东西怎么办？需要命名空间。
2. **可见性**：哪些名字是对外的承诺，哪些是随时可以改的内部实现？
3. **编译单位**：一次编译处理多少代码？改一个文件要重编多少？
4. **发布单位**：一份可被别人依赖和版本化的东西叫什么？

四门语言用不同的概念组合回答这四个问题：

| 问题 | Go | Java | Rust | Python |
|---|---|---|---|---|
| 命名空间 | package | package | module（mod） | module / package |
| 编译单位 | package | 类（文件） | crate | 无（运行时导入） |
| 发布单位 | module | JAR / JPMS 模块 | crate | distribution（wheel） |

**取舍轴**：
- **边界的强度**：可见性是靠编译器强制，还是靠命名约定？
- **粒度**：命名空间、编译单位、发布单位是三个概念，还是合并成一个？合并简单，分开灵活。
- **依赖图的形状**：是否允许循环依赖？禁止循环强迫分层，允许则更灵活但容易形成大泥球。

模块系统是大型代码库架构的物质基础：边界画在哪里、画得多硬，决定了系统能否被几十人同时修改而不互相破坏。
