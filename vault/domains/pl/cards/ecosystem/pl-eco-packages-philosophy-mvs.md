## Q
Go 选择最小版本选择（MVS），而 Cargo 和 uv 选择「最新兼容版本加锁文件」。这反映了对「新版本」怎样相反的态度？

## A
**共识的起点**：新发布的版本是**好**还是**风险**？

**Cargo / Python / npm 的态度：新版本大概率更好**。默认取最新兼容版本，自动拿到补丁、安全修复和性能改进。但也意味着：同一个 `Cargo.toml` 在不同日期解析出不同结果，所以需要锁文件来冻结。默认状态是「漂移」，锁文件是你施加的稳定。

**Go MVS 的态度：新版本是未经验证的风险，除非你主动选择**。你的 `go.mod` 里写的下限，是你（或你依赖的作者）**实际测试过的**那个版本。仓库里出现 v1.9 不会改变你的构建，直到有人明确要求它。默认状态是「稳定」，升级是你施加的行动。Russ Cox 设计 MVS 时的核心论点：**高保真构建**（high-fidelity build）：你构建的就是作者测试过的组合，不是“碰巧今天满足约束的组合”。

**各自的代价**：
- Go：安全补丁不会自动进来，需要工具（`govulncheck`、dependabot）提示你主动升级。
- Cargo/Python：构建在更新锁之前是稳定的，但每次更新锁，你面对的是一次“批量升级”，其中任何一个依赖都可能有破坏。

**更深一层**：这是**确定性**与**新鲜度**的取舍，类似「长期稳定版」与「滚动发布」两种发行版哲学。Go 更接近前者，认为生产构建应当是确定的、可审计的；Cargo/pip 更接近后者，再用锁文件把它冻结成确定。

**对实践的含义**：无论哪种，团队都需要**定期升级的流程**；差别只在于升级的触发是“你主动”还是“工具默认”。
