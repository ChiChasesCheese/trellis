## Q
Go 为什么由编译器直接禁止包之间的循环依赖，Python 与 Java 却允许？这个规则怎样体现各自的架构哲学？

## A
**Go：把架构原则写进编译器**。`import cycle not allowed` 不是警告而是错误。理由有两层：
1. **工程上**：无环图才能自底向上并行编译、增量缓存，这是 Go 编译速度的基础。
2. **架构上**：循环依赖意味着两个包其实是一个概念被拆错了。强迫你要么合并，要么抽出第三个包放共享的东西，要么用接口反转依赖。结果是整个代码库自然形成分层结构。

有人觉得这很烦：拆包时经常撞上循环，得重新设计。Go 的态度是：这种烦恼是在提早暴露设计问题，比让它长成泥球后再重构便宜。

**Python：允许，把责任交给开发者**。循环导入只在恰好执行顺序不利的时候才出错，所以经常「偶尔能跑」。社区的惯用对策是在函数内部延迟导入、或把共享的东西抽到第三个模块。Python 的立场是：别替我做决定，我知道怎么处理。后果是大型 Python 代码库往往靠外部工具（`import-linter`）和约定维持分层。

**Java：包之间允许循环，模块之间禁止**。JPMS 的 `requires` 图不能有环，但绝大部分 Java 代码并未使用 JPMS，包内与包间的环在大型项目里非常常见，需要 ArchUnit 这类测试库来强制分层。

**Rust：crate 之间禁止，crate 内部的 mod 允许**，因为同一 crate 整体编译，互相引用没有成本。

**C++：编译器不管**。头文件可以互相 `#include`（靠 include guard 防止无限展开，靠前置声明打断依赖），库与库之间的循环依赖到链接期也不报错，只有静态库的链接顺序有时会暴露出来。分层靠 CMake 的目标依赖、Bazel 的可见性规则或外部工具来执行。立场与 Python 相近，却更彻底：语言连“依赖”这件事都没有一个概念。

**揭示的价值观**：Go 与 Rust 愿意用规则的刚性，换取可预期的结构；Python 与 Java 愿意用灵活，换取低门槛，然后在后期用工具补偿。选语言时，也是在选「架构纪律由谁来执行」：编译器，还是你的团队。
