## Q
格式化器、静态检查器和测试框架各解决什么问题？「官方工具链」与「社区各家工具」是两种什么样的设计选择，沿什么轴取舍？

## A
**四类工具各管一件事**：
1. **格式化器**（formatter）：统一代码排版（缩进、换行、空格），消灭代码评审里的风格争论。
2. **静态检查器**（linter / static analyzer）：不运行代码，发现可疑写法与潜在 bug，如未使用的变量、格式串与参数不匹配、可疑的比较。
3. **类型检查器**：验证类型声明是否自洽。静态语言内置于编译器，Python 需要额外工具。
4. **测试框架**：运行测试、报告结果、测量覆盖率。

**设计空间（谁提供、提供多统一）**：
- **官方、内置、唯一**：语言团队随工具链提供一个，且几乎不可配置（Go 的 `gofmt`）。
- **官方、内置、可配置**：官方提供，但有配置文件（Rust 的 `rustfmt`、`clippy`）。
- **社区生态、多家并存**：由市场选择（Java 的格式化与检查工具、Python 的 black / ruff / flake8 / pylint）。

**取舍轴**：统一与自由。统一的工具让所有项目长得一样，新人不用重新学习，也省去配置与选择；自由则让团队按需定制，工具可以独立于语言版本快速演进，但项目之间风格各异，选型与配置本身成了负担。

**为什么这是语言设计的一部分**：工具链决定了每天的开发体验。一门语言如果不随附格式化器、测试运行器和依赖管理，每个团队都要自己拼一套；随附了，就把“如何开发”变成了语言约定的一部分。Go 与 Rust 都选了后者；Java 与 Python 历史上选了前者，近年 Python 以 `uv`/`ruff` 为代表向统一靠拢。
