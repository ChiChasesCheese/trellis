## Q
Java、Go、Rust、Python、C++ 各用什么技术机制来保存兼容性？“版本号”记录在哪里，由谁在什么时候读它？

## A
兼容性策略要落到可检查的机制上。五门语言把“这段代码属于哪一版规则”记录在不同位置。

| 语言 | 版本记录在哪里 | 谁读它 | 效果 |
|---|---|---|---|
| Java | 每个 `.class` 文件头里的主版本号（Java 8 是 52，Java 25 是 69） | JVM 加载时检查 | 新 JVM 接受所有旧版本的类；旧 JVM 拒绝更新的类 |
| Go | 每个模块 `go.mod` 的 `go` 行 | 编译器的语言版本开关，按模块（甚至按文件）启用 | 同一个编译器，按模块切换语义，如循环变量 |
| Rust | 每个 crate 的 `edition` | `rustc --edition`，前端解析器 | 同一个编译器，按 crate 切换语法方言 |
| Python | 无文件级版本；用 `from __future__ import xxx` 提前启用 | 解释器编译这个文件时 | 一个文件可提前选择将来的语义 |
| C++ | 编译命令里的 `-std=c++XX`（由构建系统按目标设置） | 编译器前端，按编译单元读取 | 同一个编译器按编译单元切换语言和库的版本；但标准版本不记录在目标文件里，混用不同 `-std` 的库要自己保证兼容 |

**细节**：
- **Java**：真实检查，用 `--release 8` 编译的类，`javap -v` 显示 `major version: 52`，在 Java 25 上直接运行；`--release` 还用一份“API 签名表”确保你没用到目标版本没有的 API。
- **Go**：Go 1.21 起，`go` 行是**下限**要求，编译器遇到比自己新的 `go` 行会拒绝或自动换工具链；语言语义的变化（如循环变量）由 `-lang` 版本控制。
- **Rust**：edition 的区别是在**编译器前端**处理的：解析、名字解析、宏展开；到了中间表示就没有 edition 概念，所以不同 edition 的 crate 才能互相链接。宏展开出的代码甚至带着“定义它的 crate 的 edition”，保证旧宏在新 crate 里行为不变。
- **Python**：`from __future__ import annotations` 这类语句是对单个文件的选择加入，让它提前使用将来才默认的语义（类型注解变成字符串、延迟求值）。没有这个机制的变化，只能靠弃用警告加删除。

**规律**：能把版本记录在“最小的可检查单位”（类文件、模块、crate、文件）上，就能让新旧代码在一个系统里共存；做不到的，破坏就只能是全局的。
