## Q
比较 Go、Java、Rust、Python、C++ 的模块系统：边界强度、粒度和对循环依赖的态度各是什么，买到什么，付出什么？

## A
| 语言 | 边界与粒度 | 循环依赖 | 买到 | 付出 |
|---|---|---|---|---|
| Go | 目录即包；大小写决定可见性；`internal` 限制范围；go.mod 为版本边界 | package 间禁止 | 规则极少，编译快，强迫分层 | 可见性只有两档；拆包时常要为避免循环重构 |
| Java | package 加 JPMS 模块；`public` 对所有人 | package 之间允许；JPMS 模块间禁止 | 精细（`exports ... to`），可裁剪运行时 | 概念多；JPMS 采用率低，多数项目仍在类路径上 |
| Rust | crate 为编译与发布单位；`mod` 树；多档 `pub` | crate 间禁止；crate 内的 mod 允许 | 默认私有、逐级公开，API 面小而可控 | 要理解 mod 与文件布局；大 crate 编译慢 |
| Python | 文件即模块；目录即包；无访问控制 | 允许，但会在运行时出错 | 零仪式，几秒就能拆文件 | 没有强边界，路径遮蔽与循环导入靠自觉 |
| C++ | 翻译单元（一个 `.cpp` 加它 `#include` 的全部头文本）为编译单位；`namespace` 只管命名；可见性靠类内的 `public/private`、匿名命名空间和链接可见性；C++20 起有模块 `import` | 头文件之间可以循环（靠前置声明和 include guard，头文件保护）；链接期不检查包依赖 | 向后兼容 C；灵活，几乎没有仪式 | 头文件被每个翻译单元重复解析，宏会泄漏进别人的代码，同名不同定义（ODR 违规，一个定义规则被破坏）不被编译器发现；模块采用率仍低 |

**逻辑**：边界的强度与语言「信任谁」成正比。Go 的设计目标是几百人的代码库不被复杂规则拖累，所以用极少数强制规则取代配置。Java 起源于企业环境，多年间默认「信任同一个 JVM 里的所有代码」，等到类路径成了灾难才补上 JPMS，所以它是后加的、选配的。Rust 面向系统级库，API 稳定性是核心价值，所以默认私有。Python 面向个人与小团队的快速开发，边界要靠约定，这在大型代码库里需要用 lint 工具（如 import-linter）补偿。C++ 的边界最弱也最老：`#include` 是文本复制，不是依赖声明；这是 C 兼容的遗产，也让零开销原则落到编译期（头文件里的模板和内联函数才能被内联）。C++20 的模块想补上真正的边界，但要和已有的头文件世界共存，迁移很慢。
