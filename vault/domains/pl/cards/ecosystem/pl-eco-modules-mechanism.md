## Q
模块边界在编译与运行时分别如何影响构建速度和启动行为？Go、Java、Rust、Python 各在什么时刻处理依赖？

## A
**依赖在哪个时刻被处理，决定了错误何时暴露**：

| 语言 | 依赖解析时刻 | 缺失或冲突时的表现 |
|---|---|---|
| Go | 编译期，按 package DAG 顺序编译 | 编译失败；循环直接被拒绝 |
| Java | 编译期检查签名，运行期按需加载类 | 类路径上缺类：运行时 `NoClassDefFoundError`；用 JPMS 则启动时检查 |
| Rust | 编译期，整个 crate 一次编译 | 编译失败；crate 间依赖在 Cargo 解析时确定 |
| Python | 运行期，执行到 `import` 语句时 | 到那一行才失败，可能是深处的某个分支 |

**为什么 Go 编译快**：package 依赖图无环，可以自底向上、并行编译；每个 package 编译后的导出信息很小，下游只读这份摘要，不必重新解析上游源码。禁止循环、禁止未使用的导入，是为了让这个模型成立。

**Rust 的粒度**：整个 crate 是一个编译单位，所以单个 crate 越大，改一行重新编译越慢；大项目被拆成许多 crate，既缩短增量编译，也强迫声明 API 边界。

**Java 的延迟加载**：JVM 在第一次使用某个类时才加载并链接它，所以启动快、但依赖错误可能在运行了一小时后才出现。

**Python 的启动成本**：每个 `import` 都要查找、读文件、执行顶层代码。大型应用启动时导入几百个模块，启动可达数百毫秒；`python -X importtime` 可以按模块列出耗时，常见优化是把重模块的导入推迟到函数内部。

**结论**：边界越静态、越在编译期，错误暴露越早，工具越容易并行与缓存；边界越动态，越灵活，也越需要测试覆盖所有导入路径。
