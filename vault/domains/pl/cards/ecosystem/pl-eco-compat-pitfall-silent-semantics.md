## Q
语言版本升级时最危险的变化是什么？循环变量语义变化与移除标准库模块，在升级时分别怎样出事？

## A
**最危险的是编译通过、行为不同的变化**。报错的升级最容易处理（编译器告诉你哪里坏了）；静默改变语义的升级则需要测试才能发现。

**Go 的循环变量**：同一份代码，因为 `go.mod` 的 `go` 行不同而行为不同：

```go
for i := 0; i < 3; i++ { fs = append(fs, func() { fmt.Print(i, " ") }) }
```

`go 1.21`：输出 `3 3 3`；`go 1.22`：输出 `0 1 2`。升级那一行 `go.mod` 的版本号，语义就变了。依赖旧行为的代码（极少，但存在：例如有意让所有闭包共享一个计数器）会悄悄出错，且编译器不报。Go 团队为此提供了工具（`go vet` 的 `loopclosure` 检查、基于数据的分析），并只对声明新版本的模块生效。

**Python 的模块移除**：升级到 3.12 后，依赖 `distutils` 或 `imp` 的老 `setup.py` 脚本、老工具链，直接 `ModuleNotFoundError`。这种错误至少很响，但它出现在 CI 的构建阶段，常常是一整批老包同时崩溃，因为它们是传递依赖的一部分，你自己没写过 `import imp`。

**Java 的“行为替换”**：`Thread.stop()` 仍可编译，升级到新 JDK 后在运行时抛 `UnsupportedOperationException`。编译时只有一个 `removal` 警告，没人读就会被带到生产。

**Rust 的 edition**：迁移时 `array.into_iter()` 在 2018 下按引用迭代，在 2021 下按值迭代，类型变了，大多数时候编译器会报错，少数时候代码依然编译通过但含义变了，因此升级 edition 的建议流程是 `cargo fix --edition` 加完整测试。

**防线**：
1. 升级前先让现有测试在**旧版本**上全绿，再只改版本号，对比结果。
2. 升级期间打开所有弃用与迁移 lint。
3. 把升级拆成“工具链升级”和“语言版本升级”两步，分开发布，便于二分定位。
4. 灰度发布，监控行为指标，而不只是错误率。
