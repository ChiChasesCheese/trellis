## Q
Zig 的核心想法是什么：没有隐藏的行为、显式分配器和 `comptime`？它是对 C 和 C++ 的怎样一种回应？

## A
**定位**：Zig（Andrew Kelley，2016 起）是一门系统编程语言，目标是“更好的 C”：同样的底层控制，但去掉 C 的陷阱，并让编译期能力强大而统一。它还没有 1.0，但已被用于 Bun（JavaScript 运行时）和 TigerBeetle（数据库）等项目。

**三个核心想法**：
1. **没有隐藏的控制流和隐藏的分配**：读代码就能看到一切。没有运算符重载、没有析构函数自动运行、没有异常、没有隐藏的内存分配。想释放就显式写 `defer`。这与 C++ 的 RAII 形成对照：C++ 靠“自动发生”，Zig 靠“必须写出来”。
2. **显式分配器**：任何需要分配内存的函数都要**把分配器作为参数传进来**。标准库不偷偷调用全局的 `malloc`。好处是：你可以为测试换成检测泄漏的分配器，为某个子系统换成区域（arena）分配器，在嵌入式里换成固定内存池，而调用方一眼就能看出哪些函数会分配。
3. **`comptime`**：在编译期运行普通的 Zig 代码。泛型就是“接受类型作为 `comptime` 参数的函数”，不需要模板或宏这类单独的语言；条件编译也是同一套机制。

**对比**：
- **C**：Zig 保留指针算术和手动内存管理，但有更好的错误处理（错误联合类型）、可选类型和更安全的默认行为（越界检查在调试模式下开启）。
- **C++**：Zig 不要模板元编程和 RAII，认为那些“聪明”的特性让程序难以推理。
- **Rust**：Rust 用类型系统证明内存安全；Zig 不做这个，选择简单的语言加好的工具，让程序员自己负责安全，同时提供检测工具。

**流向与意义**：Zig 的 `comptime` 是“编译期执行统一取代宏和模板”这一趋势的代表，显式分配器影响了其他系统语言关于分配器 API 的设计（Rust 的 `Allocator` 提案、Odin 等）。

**要记住的一点**：Zig 的哲学是“把成本和行为写在代码里让人看见”，与 Go 的“少即是多”有相近精神，但目标域是系统编程。
