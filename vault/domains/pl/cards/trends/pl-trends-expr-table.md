## Q
比较 Go、Java、Rust、Python、C++ 的表达式化程度：控制流结构哪些能产生值，各自买到什么，付出什么？

## A
| 语言 | 立场 | 哪些结构产生值 | 买到 | 付出 |
|---|---|---|---|---|
| Rust | 一切皆表达式 | `if`、`match`、块、`loop`（`break 值`） | 不可变绑定、穷尽性、可组合 | 分号的细微语义，学习曲线 |
| Java | 逐步补上 | `switch` 表达式（14）、三元 `?:`、模式匹配 | 兼容旧代码，修复最易错的 `switch` | `if`、`try` 仍是语句；新旧并存 |
| Python | 语句为主，补专用表达式 | 条件表达式、推导式、`lambda`、`:=` | 日常够用，可读性好 | 表达式能力不一致，`lambda` 受限，优先级陷阱 |
| Go | 故意语句导向 | 几乎没有（函数调用与运算符） | 代码形状统一，规范简单 | 要多写几行，需要中间变量 |
| C++ | 语句为主，补专用表达式 | 三元 `?:`、lambda（可立即调用来初始化 `const` 变量）、折叠表达式；`if`、`switch` 仍是语句 | 兼容 C，lambda 立即调用能一步初始化不可变变量 | 没有语言级模式匹配（`std::visit` 是库版本）；三元两侧类型必须兼容；写法零散 |

**逻辑**：这张表对应每门语言对“组合”的态度。Rust 来自 ML 传统，认为程序是表达式的组合，副作用是例外。Java 是命令式语言，选择只改造最痛的地方，避免全局破坏。Python 讲“可读性”，用专用形式补足最常见的表达式需求，其余留给函数。Go 讲“显式与统一”，宁愿让读者看到每一步赋值。C++ 继承了 C 的语句导向，又不愿打破兼容，于是用“立即调用的 lambda”这种绕道补上缺口，如 `const int n = [&] { if (c) return 1; return 2; }();`：一个可以包含语句的表达式，换来不可变的初始化。这是兼容性压力下“在旁边补一个机制”的典型做法。

**一个重要后果**：表达式化程度高的语言，倾向把函数写成小而纯的组合，错误处理也走向表达式（Rust 的 `Result` 与 `?`、Java 的 `Optional` 链）；语句导向的语言倾向于逐步命令式的写法，错误处理走向 `if err != nil`。两种风格各有一致的美学，混用则不协调。
