## Q
Java 选择虚拟线程，Rust/Python/JavaScript 选择 async/await。“保持编程模型、替换实现”与“引入新的编程模型”这两条路，反映了怎样的哲学分歧？

## A
**两种回应同一个问题**：线程太贵，如何支持海量并发？

**async/await：改变编程模型**。让函数显式标记“可能暂停”，编译器把它转成状态机。哲学：**暂停点应该是可见的**。读代码的人看到 `await` 就知道这里会让出控制权，其他任务可能在此时运行；共享状态的修改在两个 `await` 之间是原子的（单线程事件循环）。这对推理并发正确性是真实的好处，也是 Rust 选择它的原因：没有运行时，也没有隐藏的栈切换，所有成本可预测。代价是**染色**：整个生态分裂为同步和异步两个世界，每个库要写两套。

**虚拟线程：保持编程模型，改变实现**。Java 的判断是：几十年积累的库、框架、调试工具都建立在“线程调用阻塞方法”的模型上。与其让所有人改写代码，不如让线程本身变便宜。哲学：**不要让开发者为了运行时的限制而改变编程方式**。Brian Goetz 和 Ron Pressler 的论证是：同步的、阻塞的风格本来就是更好的编程模型，只是线程的实现拖累了它。代价是暂停点不再可见：任何方法调用都可能切换线程，同步块里持锁时还可能钉住系统线程。

**Go 与 Java 同路，但更早、更彻底**：Go 从第一天就是 goroutine，没有历史包袱。

**Python 与 JavaScript 的情形不同**：它们的运行时本来就是单线程的事件循环（JavaScript）或受 GIL 限制（Python），没有“廉价的栈”，async/await 是唯一现实的路径。

**揭示的价值观**：
- Rust：**可预测与显式**优先，愿意接受染色。
- Java/Go：**简单与兼容**优先，愿意让运行时更复杂。

**对实践的含义**：选择模型时问两件事：你有多少现有的阻塞代码？你需要看见每个暂停点吗？前者多，倾向轻量线程；后者重要（例如要论证状态在两处之间不变），倾向 async。
