## Q
Go、Java、Rust、Python、C++ 分别把哪些效应写进了类型或语法，哪些藏在约定里？

## A
| 语言 | 失败 | 异步 / 挂起 | 修改 / 不安全 | I/O |
|---|---|---|---|---|
| Go | `error` 返回值（约定），`panic` 不记录 | 不记录：goroutine 里任何函数都能阻塞 | 无标记；指针可修改，`unsafe` 包可识别 | 不记录 |
| Java | 受检异常记录在 `throws`，非受检不记录 | 不记录（虚拟线程）；`CompletableFuture` 是值 | 无标记；`final` 限制变量 | 不记录 |
| Rust | `Result`/`Option` 在返回类型里；`panic` 不记录 | `async fn` 标记，`Future` 是值 | `&mut`、`unsafe fn`、`const fn` 都在签名里 | 不记录 |
| Python | 不记录（任何函数都可抛） | `async def` 标记 | 无标记 | 不记录 |
| C++ | 异常不进签名（`noexcept` 只标“不抛”）；`std::expected`、返回码是显式值 | 协程由返回类型加 `co_await` 体现，调用方看不出 | `const` 成员函数、`constexpr`/`consteval`、`noexcept` 在签名里；不安全无标记（整门语言） | 不记录 |

共同点：**没有一门语言把 I/O 记在类型里**（Haskell 才这样做）。五门语言里 Rust 记录的效应种类最多：可失败、可挂起、可修改、不安全、编译期可求值。

规律：**一种效应被写进类型，通常是因为忽略它的代价高到值得让编译器介入。**

- Rust 把失败、不安全、可变性写进类型，因为这三个正是内存安全和并发安全的来源，不显式写出就无法检查。
- Java 一度把失败写进类型（受检异常），后来在组合性压力下放弃了对新 API 的使用；Java 对 I/O 与阻塞不做类型标记，因为虚拟线程让它们不再需要。
- Go 选择最少的标记：错误是值，但不是类型层面的效应；一切并发和阻塞都靠运行时。
- Python 只在 `async` 上做标记，因为那是协程实现所需要的最低限度。
- C++ 标记的是编译器能据此优化的东西：`const`、`constexpr`、`noexcept`。动态异常规范（`throw(X)`，列出可能抛哪些异常）因运行期检查成本高、收益小，在 C++11 弃用、C++17 移除，只留下 `noexcept`。这是零开销原则的取向：只记录能换来运行时收益的效应，不记录只为人服务的约束。

这些选择的另一面是**有多少信息需要读者自己记住**。看 Rust 函数签名，你能读出「会不会失败、会不会改参数、能不能在 const 里用」；看 Go 签名，你只能读出「返回一个 `error`」，其余靠命名与文档。

趋势：各语言都在向「把更多效应显式化，同时让显式化的成本尽量低」靠拢——Rust 用 `?` 把 `Result` 的传播成本降到一个字符，Swift 用 `try` 和 `await` 标注调用点，Kotlin 的挂起函数用 `suspend`；另一路是 OCaml 5 式的效应处理器，把效应的**实现**与**使用**分开。
