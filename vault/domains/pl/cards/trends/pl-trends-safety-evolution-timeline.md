## Q
内存安全运动是怎样一步步发展起来的？Rust 进入 Linux 内核和 Android 说明了什么，未来的方向是什么？

## A
**时间线（概要）**：
1. **长期背景**：1990 年代 Java 用 GC 和边界检查证明“主流语言可以内存安全”；系统领域长期仍是 C/C++，因为没有同时无 GC、有安全保证的选项。
2. **2015 年**：Rust 1.0 发布，首次给出“无 GC、编译期保证内存安全”的实用方案。
3. **2019 年前后**：Microsoft、Google 公布漏洞统计，内存安全问题约占严重漏洞的七成，工业界开始系统地讨论。
4. **2022 年**：美国国家安全局发布关于内存安全语言的指南；Linux 内核 6.1 版合并 Rust 支持的基础设施，允许用 Rust 写内核模块和驱动。
5. **2024 年**：白宫国家网络总监办公室发布报告，呼吁转向内存安全语言；Google 公布 Android 新代码改用 Rust 等语言后，内存安全漏洞占比大幅下降。
6. **之后**：CISA 推动软件厂商制定并发布内存安全路线图；Rust 在内核和 Android 中的使用持续扩大；C++ 社区推进加固与 profiles。

**这说明什么**：
- **“新代码用安全语言”足以明显改变漏洞结构**。漏洞多出现在新写的和近期修改的代码里，旧代码经过多年审计和使用，缺陷密度本来就低。所以不重写旧代码，只让新增代码改用安全语言，漏洞占比也会随时间下降。
- **工业界认可 Rust 能进入最保守的领域**：操作系统内核。这些领域曾被认为“只能是 C”。

**方向**：
1. **互操作成为关键**：C/C++ 与 Rust 之间的安全 FFI 工具（bindgen、cxx）。
2. **更多语言加入安全承诺**：Swift、Go、Kotlin 的系统级用法；新的实验语言。
3. **硬件辅助**：指针认证、内存标记（如 ARM MTE）从硬件层降低漏洞的可利用性，与语言层面的安全互补。
4. **形式化与可验证**：对关键组件用形式化验证（如 Rust 生态里的 Kani、Verus）。

**一句话**：语言安全从个人偏好变成供应链要求，决策者不再只问“能不能更快”，也问“出了漏洞的代价由谁承担”。
