## Q
当前并发模型的行业共识是什么？还有哪些尚未解决的问题，未来的走向如何？

## A
**已经形成的共识**：
1. **I/O 并发不应该占用一个重量级线程**。Go（goroutine）、Java（虚拟线程）、Python/Rust/JavaScript（async）、Kotlin（协程）、Erlang（进程）各用自己的办法，目标一致。
2. **并发单位的生命周期应当嵌套**。结构化并发从 2016 年前后被提出，经 Kotlin、Swift、Python 3.11、Java 预览、Go 社区约定，已成为设计新 API 的默认思路。
3. **取消与超时是一等公民**：Go 的 `context`，Java 的中断与作用域，Python 的 `asyncio.timeout`，都在把它标准化。
4. **数据竞争不应靠自觉**：Rust 的 `Send`/`Sync`，Go 的竞争检测器，Java 的内存模型，各自用不同强度来管。

**尚未解决的问题**：
- **染色的最终解法**：有些语言（例如 Rust 社区关于效果系统与关键字泛型的讨论）在探索让同一份代码既能同步也能异步运行。
- **虚拟线程的钉住与调度公平**：本地代码和锁与运行时的交互还在改进。
- **结构化并发的标准化**：Java 仍在预览，Go 没有语言级支持。
- **CPU 并行**：Python 的 GIL 在 3.13 起有可选的自由线程构建，是否成为默认、生态何时兼容，仍在进行；Java 的 Fork/Join 与 Rust 的 rayon 已经成熟。
- **分布式的类比**：本地的结构化并发思想正被推广到分布式工作流（持久化执行，如 Temporal），任务的生命周期跨越进程崩溃。

**方向**：并发抽象将越来越上层：开发者描述“要并行做哪些事、失败与超时如何处理”，运行时决定用线程、协程还是进程。就像垃圾回收让大多数人不再手动管理内存，**并发调度也在成为运行时的责任**。

**给学习者的建议**：把精力放在不随模型改变的原则上：所有权、取消、背压、超时、可观测性。具体语法会换，这些问题不会。
