## Q
Go 等了十几年才加泛型，而且加的是克制的版本。这个“慢”反映了怎样的设计哲学，它与 Java 的节奏有什么对比？

## A
**事实**：Go 1.0 发布于 2012 年，泛型在 1.18（2022 年）才加入。社区十年里反复要求，团队的回答是“我们还没找到合适的设计”。

**哲学：特性是债务**。Go 的设计者认为，每增加一个特性，所有读代码的人、所有写工具的人、所有学语言的人都要付出代价；而且特性一旦加入，永远不能移除（兼容承诺）。所以门槛不是“它有没有用”，而是“它是否值得整个语言永远承担”。这与 Go 的兼容承诺是同一个逻辑：承诺越强，加东西越要谨慎。

**这个慢的好处**：
1. **设计更合适**：团队看了其他语言（C++ 模板、Java 擦除、Haskell 类型类）的教训，选了接口作为约束，避免了模板元编程的复杂度。
2. **生态避免分裂**：没有泛型的十年里，社区没有演化出两三套互相冲突的“泛型库风格”。
3. **标准库先行**：加入泛型后，标准库逐步引入 `slices`、`maps`，而不是让社区库各自为政。

**这个慢的代价**：十年里的重复代码、`interface{}` 的类型不安全、代码生成工具泛滥；有些库的设计（比如在泛型之前写好的 API）此后只能并存新旧两套。

**对比 Java**：Java 5（2004）较早加入泛型，但为了兼容旧字节码使用了擦除，留下了不能 `new T()`、不能对基本类型泛型等限制，到今天（Valhalla 项目）还在补救。**早加入且带历史包袱**与**晚加入但设计干净**，是同一问题的两种成本。

**揭示的价值观**：Go 把“语言的稳定与简单”置于“功能的及时性”之上；Java 把“及时回应开发者需求”与“兼容”同时保住，结果是更拧巴的设计。
