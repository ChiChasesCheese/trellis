## Q
资深工程师在内存安全的趋势下怎样做技术决策？通用规则是什么，Go、Java、Rust、Python、C/C++ 的代码库各自怎么办？

## A
**通用规则**：
1. **新代码默认用内存安全语言**，尤其是解析不可信输入的部分（文件格式、网络协议、媒体解码）。
2. **旧代码不必整体重写**：先加固，再按风险排序替换最危险的模块，边界用清晰的 FFI。
3. **缩小逃生舱面积**：封装成小模块，写文档，写测试，在 CI 里用工具检查。
4. **开启一切免费的防护**：编译器加固选项、ASan/UBSan 在 CI 里跑、模糊测试。
5. **把依赖也算进攻击面**：C 扩展与原生依赖里的漏洞同样会进入你的产品。

按语言：
- **C/C++ 存量**：开启加固模式和 `-fstack-protector` 一类编译选项；解析器放进沙箱；新增功能用 Rust 或托管语言。
- **Rust**：应用 crate 里 `#![forbid(unsafe_code)]`；必须用 `unsafe` 时封装在小模块，注释写明不变量，用 Miri 和 `cargo geiger` 检查；FFI 边界处做输入校验。
- **Go**：并发代码跑 `go test -race`；避免 `unsafe`；`cgo` 的调用边界做输入校验；序列化库的 `unsafe` 用法留意版本。
- **Java**：避免 `sun.misc.Unsafe` 与自写 JNI；升级到较新 JDK 以使用 FFM API 取代 JNI；依赖的原生库保持更新。
- **Python**：C 扩展与 `ctypes` 是风险点；热点用 Rust（PyO3）替换 C 扩展；不要对不可信输入调用原生解析库的旧版本。

**何时破例**：嵌入式、遗留硬件接口、极端性能路径，可能必须用 C；这种场景把“安全”的负担转移到流程上：评审、模糊测试、静态分析、最小权限。
