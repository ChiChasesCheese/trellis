## Q
比较 Go、Java、Rust、Python、C++ 对“吸收新特性”的态度：各自的节奏和方式是什么，买到什么，付出什么？

## A
| 语言 | 吸收方式 | 买到 | 付出 |
|---|---|---|---|
| Go | 极度审慎：等共识、等相容设计，十年才加泛型 | 语言小，旧代码风格一致，学习成本低 | 长期缺口让用户用丑陋的变通；有些设计后来被迫补救 |
| Java | 固定半年节奏，预览特性试验，兼容为先 | 持续现代化，企业能平滑跟进 | 新旧特性并存，同一问题有多种写法；受兼容约束，设计常较拧巴 |
| Rust | 先发者；用 RFC 流程公开讨论，edition 吸收语法层变化 | 一开始就内聚；新特性有严格流程 | 特性数量在增长，学习曲线陡 |
| Python | 较快吸收，PEP 流程；语法进入语言，检查交给工具 | 能快速追上潮流，生态活力大 | 语言越来越大；类型注解、`match` 的保证较弱 |
| C++ | ISO 委员会每三年一版；提案先在 Boost 等库里验证，多年的论文评审后才进标准；只加不删 | 持续吸收（lambda、concepts、ranges、协程、模块、`expected`），且必须过零开销与兼容的审查 | 设计周期以年计（模块从提出到进标准近十年）；新旧写法并存，语言体积最大，特性数量和学习成本持续上升 |

**逻辑**：每门语言的吸收节奏，是它对“谁是用户”的回答。Go 的用户是大型团队里轮换的维护者，所以复杂度是头号敌人，宁可慢。Java 的用户是企业，要同时满足“现代”与“十年后仍能运行”，所以采用固定节奏加预览机制，让社区先试再定。Rust 的用户愿意为正确性付学习成本，所以内聚的设计和公开的 RFC 比速度更重要。Python 的用户横跨科学计算到脚本，生态拉着语言走，吸收速度快，但每个新特性都要和既有动态语义妥协。C++ 的用户是需要性能和控制的系统工程师加海量存量代码，所以走委员会路线：吸收的东西最多，因为谁都想把自己领域的需求塞进去，但每一项都要过“不用的不付费”和“不破坏旧代码”两道关，代价是做得慢、做得重，也永远删不掉旧的。这是“吸收太快会成特性堆砌”的批评最常落在它身上的原因。

**一个共同的警示**：每个新特性都有成本，包括学习成本、工具支持成本、以及“同一件事有多种写法”的风格分裂。收敛的好处常被高估，成本常被低估。
