## Q
内存安全的运行时代价有多大？边界检查、垃圾回收与 Rust 的编译期证明，各自把成本放在哪里？

## A
**边界检查的成本很小**。本机一次测量（Rust，一亿个元素的数组，按乱序下标求和，每个元素 8 字节）：带边界检查的版本约 229 ms，用 `get_unchecked` 去掉检查的版本约 223 ms，差距约 3%。第一轮冷启动时差距更大（387 ms 对 221 ms），受缓存和预热影响。

**原因**：边界检查是一次比较加一次几乎总是不跳转的分支，现代 CPU 的分支预测几乎免费，并且指令可以与内存加载并行执行。真正的瓶颈是乱序访问造成的缓存缺失，检查被隐藏在内存延迟之下。对顺序遍历，编译器还能证明下标合法，直接消除检查。

**成本分布**：

| 机制 | 成本放在哪里 | 量级 |
|---|---|---|
| 边界检查（所有安全语言） | 每次下标访问一次比较 | 通常几个百分点，内存受限的代码中几乎不可见 |
| 垃圾回收（Java、Go、Python） | 内存开销（额外堆空间）、暂停或后台 CPU、写屏障 | 吞吐损失常见在几个百分点到两位数；内存常需要 1.5 到 2 倍余量 |
| Python 的整体解释执行 | 每个操作的解释器开销 | 数量级的差异，但与内存安全无关 |
| Rust 的所有权 | 编译期：编译时间和学习成本；运行时几乎为零 | 运行时接近 C |

**两点澄清**：
1. 内存安全的“代价”主要不是速度，而是**确定性**（GC 暂停）、**内存占用**和**开发者的学习曲线**。
2. 对大多数服务，GC 与边界检查的成本远小于网络和数据库延迟，不是迁移的障碍；真正的障碍是**存量代码和互操作**。

**结论**：安全语言的速度劣势被普遍夸大了；真正的取舍是 GC 的延迟特性与 Rust 的人力成本。
