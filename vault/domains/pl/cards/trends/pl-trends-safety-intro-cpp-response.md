## Q
C++ 面对内存安全运动做了什么回应？加固（hardening）、安全子集与 profiles 各是什么思路，为什么它们是困难的？

## A
C++ 有数十亿行存量代码，无法像新语言那样从头保证安全，所以回应是“在兼容的前提下尽量改善”。

**三条路线**：
1. **加固标准库与编译选项**（hardening）：标准库的容器在开启加固模式时，对 `operator[]` 做边界检查，违规则终止程序，而不是产生未定义行为。LLVM 的 libc++ 提供加固模式，libstdc++ 提供类似的断言选项。编译器也提供选项，对指针和数组边界做额外检查。代价是一点运行时开销，收益是不改源码就收紧一大类漏洞。
2. **安全子集 / 配置文件（profiles）**：C++ 标准委员会讨论的方向。思路：定义若干“profile”（例如类型安全、边界安全、生命周期安全），代码声明启用某个 profile 后，编译器拒绝违反规则的写法。优点是渐进采用，不需要新语言；难点是 C++ 的别名与生命周期规则太复杂，完整的静态证明很难，保证会弱于 Rust。
3. **“另起炉灶”的方案**：给 C++ 增加类似借用检查的新语法（学术和实验性提案），或者新语言（如 Google 的 Carbon 项目，定位为 C++ 的互操作后继）。这类方案能给出更强保证，但意味着更大的语言变动。

**为什么困难**：内存安全是“证明性质”，需要程序里每一处指针的来源和生命周期都可知。C++ 允许任意的指针算术、`reinterpret_cast`、未约束的别名，语言的基础设计就不是为证明而做的。加固能消灭“越界”这类容易检查的错误，但“释放后使用”需要生命周期信息，难以在不改语法的情况下补上。

**这条路的现实意义**：很多机构选择的是组合策略：旧代码加固加模糊测试，新模块用 Rust 或其他内存安全语言，边界上用 FFI（外部函数接口）连接。
