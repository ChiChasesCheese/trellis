## Q
从其他语言“借想法”时最常见的误区是什么？为什么特性被借走之后，保证常常变弱，会在生产里出事？

## A
**误区一：只借表面，不借保证**。TypeScript 的类型在运行时被擦除，真实验证：文件里 `let n: number = "oops"`，`tsc` 报类型错误，但用 Node 直接运行（只剥掉类型）照常输出，没有任何运行时拦截。类似地，Python 的类型注解不被解释器检查，Java 的 `Optional` 不阻止你返回 `null`。把它们当成“有保证”的特性，就会在边界上栽跟头：外部 JSON 声称是 `number`，实际是字符串，类型系统毫不知情。

**防线**：在系统边界处做运行时校验（Python 的 pydantic、TypeScript 的 zod、Java 的 Bean Validation），内部再依赖类型。

**误区二：把一门语言的惯用法硬搬到另一门**。
- 在 Go 里模仿 Java 的深层继承和工厂：Go 没有继承，只能用嵌入，结果别扭。
- 在 Python 里写满 `getter`/`setter` 和大量工厂类：Python 用属性和简单函数。
- 在 Rust 里到处 `clone()` 或用 `Rc<RefCell<>>` 模仿 Java 的共享可变对象：回避了借用检查，却失去 Rust 的优势。
- 在 Java 里模仿 Haskell 的深度函数式：没有柯里化、尾调用优化，栈和堆开销都会反噬。

**误区三：为新鲜感引入新范式**。团队里只有一个人熟悉某种风格，别人读不懂，这个人离开后代码成为负担。

**误区四：忽视被借走的特性在原语言里依赖什么**。例如，Kotlin 的空安全依赖整个标准库按照它的约定设计；单独在 Java 里加注解，遇到没标注的库代码就失效。Rust 的 `async` 依赖所有权模型保证安全，搬到没有所有权的语言就没有同样的保证。

**教训**：评估一个“借来的特性”，要问三件事：它的**保证是什么**？这个保证依赖**哪些前提**？在我的语言里这些前提**是否仍成立**？三个答案都清楚，才算真正理解了它。
