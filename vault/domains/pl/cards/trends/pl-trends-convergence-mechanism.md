## Q
把几个收敛的特性按语言和时间摆在一起，能看出什么规律？同一个特性在不同语言里的“落地形式”有什么区别？

## A
**时间线（版本是各语言的正式发布）**：

| 特性 | Rust | Java | Go | Python |
|---|---|---|---|---|
| 枚举加模式匹配 | 1.0（2015） | `switch` 模式 21（2023） | 无（仍用接口加类型 switch） | `match` 3.10（2021） |
| 泛型 | 1.0 | 5（2004，擦除） | 1.18（2022） | 类型注解 3.5（2015，仅标注） |
| 简洁的数据类 | `struct` 加 `derive` | `record` 16 | `struct`（一直有） | `dataclass` 3.7 |
| 局部类型推断 | 一直有 | `var` 10 | `:=` 一直有 | 动态，无需 |
| 迭代器抽象 | 1.0 | `Stream` 8 | `iter.Seq` 1.23 | 生成器一直有 |

**规律一**：Rust 把这些作为第一天的设计，其他语言在 5 到 15 年后补上。可以把 Rust 看作一次对“如果现在重新设计会怎样”的试验。

**规律二：落地形式取决于语言的核心约束。**
- **Java**：必须兼容 JVM 和现有字节码，所以泛型用擦除实现（运行时没有类型参数），模式匹配以 `sealed` 加 `record` 的组合出现，而不是新的和类型关键字。
- **Go**：必须保持小而快的编译，所以泛型选择了接口约束和有限的实例化方式；不加枚举，因为已有接口。
- **Python**：必须保持动态语义，所以类型注解不影响运行时，`match` 不做穷尽性检查。
- **Rust**：编译期全部展开（单态化），泛型零开销。

**规律三：收敛的是“思想”，而非“实现”**。穷尽性检查在 Java 是编译器强制，在 Python 是类型检查器可选，在 Go 靠 linter。你以为学会了“模式匹配”，在每门语言里的保证强度却不同。

**对学习的含义**：迁移时不要只问“有没有这个特性”，要问“它的保证强度是什么、由谁检查、成本是什么”。
