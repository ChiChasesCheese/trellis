## Q
为什么在类型系统之外还需要动态检查器（dynamic checker / sanitizer）？它们大体有哪几种做法，共同的取舍是什么？

## A
**问题**：类型系统和编译器对所有可能的输入做证明，所以必须保守，只能保证它能证明的那一部分。有四类问题它证明不了：
- `unsafe` 代码和对 C 库的调用（编译器放弃检查，由程序员担保）；
- C、C++ 的内存错误：越界读写、释放后使用；
- Go、Java 这类语言里的数据竞争，类型系统不管线程之间的同步；
- 与硬件内存模型相关的重排序可见性问题。

**动态检查器**换了一条路：不证明，只观察。在程序真实运行时检查每一次内存访问或同步操作，一旦发现违规立刻报告出错位置。

**三种做法**：
1. **编译器插桩加影子状态**：编译时在每次内存访问处插入检查，运行时库为每块内存维护「影子」元数据。AddressSanitizer（ASan）查内存错误，ThreadSanitizer（TSan）查数据竞争，UndefinedBehaviorSanitizer（UBSan）查未定义行为。
2. **解释器**：在一个能检查一切的解释器里运行程序，如 Rust 的 Miri。极慢，但检查最彻底。
3. **压力测试加结果统计**：把一小段并发代码在各种线程调度下重复运行数十亿次，统计出现了哪些结果，如 Java 的 jcstress。

**共同的取舍**：报告的问题几乎都是真问题（误报少），但只覆盖**实际执行过的路径和调度**，一次干净的运行不等于没有 bug；代价是运行变慢、内存变多，所以用在测试和 CI，不在生产常开。
