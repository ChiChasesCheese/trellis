## Q
Go、Java、Rust、Python 在「编译器、linter、类型检查器」之间怎样分工？换来什么，代价是什么？

## A
| 语言 | 分工 | 换来 | 代价 |
|---|---|---|---|
| Go | 编译器管类型，并把未使用的变量和导入变成**错误**；`go vet` 只做把握很大的检查；staticcheck 与 golangci-lint 是第三方补充 | 规则少而硬，工具统一，几乎没有「警告噪声」 | 语言表达力有限，官方不做深度分析，空指针等需要靠测试和 review |
| Java | 编译器管类型；`-Xlint` 管警告；Error Prone、SpotBugs、NullAway 是外挂 | 生态最丰富，可按项目选择严格程度 | 工具要自己选、自己配；分析器之间规则重叠，配置成本高 |
| Rust | 编译器吸收了借用、生命周期、穷尽匹配等检查；clippy 管风格与隐患 | 同类问题最少漏到运行时，linter 压力小 | 编译器的要求严格，学习曲线陡；clippy 的建议有时过于「地道」 |
| Python | 解释器几乎不检查；mypy、pyright 查类型；ruff、pylint 查模式 | 完全可选，可渐进采用 | 保证强度取决于团队纪律；注解不完整的地方没有保证 |

**规律**：检查被放在哪一层，是语言哲学的直接体现。Go 把规则做小，主张「少即是多」，所以连警告都不要，直接让未使用的变量报错；Rust 追求「能在编译期证明的都证明」，把本来属于 linter 的职责交给编译器；Java 面向大型企业项目，让工具生态承担多样性；Python 的动态性是核心卖点，因此静态约束只能是可选的外挂。

对工程实践的含义：越往 Python 方向，越需要把 linter 与类型检查器写进 CI 当作硬门槛；越往 Rust 方向，CI 里的静态检查就越是编译器本身。
