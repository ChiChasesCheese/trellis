## Q
资深工程师写测试遵循哪些做法？为什么这样做，什么时候可以破例？

## A
1. **测行为，不测实现**：断言公开 API 的输入输出和可观察的副作用。重构内部时测试不该坏；一重构就坏的测试是负担。
2. **测试要快且确定**：把时间、随机数、网络隔离掉。不稳定的测试（flaky test）按缺陷处理：定位根因，而不是加重试。重试只会掩盖问题，并逐渐让团队不再相信红灯。
3. **依赖外部系统时用真实实例**：数据库、消息队列用 Testcontainers（Java、Go、Python、Rust 都有）起一个容器，通常比 mock 数据库更可靠，mock 的行为和真实系统总有差异。
4. **每个 bug 配一条回归测试**：先写出会失败的测试，再修复。
5. **选对形态**：解析器、编解码、序列化、数学函数加属性测试；大而结构化的输出用快照；业务规则用表驱动或参数化的示例测试。
6. **覆盖率是探针，不是目标**：它告诉你哪里没测过，不告诉你测得好不好。100% 的行覆盖也可能没有一条有效断言。衡量断言质量要用变异测试（Java 的 PIT、Rust 的 `cargo-mutants`、Python 的 `mutmut`）：自动改动代码，看测试能不能发现。

**各语言的具体做法**：Go 用表驱动加 `t.Parallel()`，CI 里始终带 `-race`；Java 用 JUnit 5 加 AssertJ，克制使用整个应用上下文的测试（如 `@SpringBootTest`），因为慢；Rust 单元测试与实现同文件，公开 API 用 `tests/`；Python 用 pytest，fixture 保持最小作用域，测试里不要写逻辑。

**何时破例**：探索性的原型和一次性脚本不值得补测试；遗留代码没有任何测试时，先写覆盖当前行为的特征测试（characterization test，用快照最方便），再重构。
