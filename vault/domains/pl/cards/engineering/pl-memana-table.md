## Q
Go、Java、Rust、Python 分别靠什么手段分析内存？各自能看到什么，不能看到什么？

## A
| 语言 | 主要手段 | 能看到 | 看不到或代价 |
|---|---|---|---|
| Go | heap profile（采样分配点）、goroutine profile | 谁在分配、仍存活多少，开销低可常开 | 没有对象引用图，找持有者要靠读代码 |
| Java | 堆转储加 MAT，类直方图，JFR 分配与老对象事件 | 最完整：对象、引用、支配树、到 GC 根的路径 | 转储要暂停应用，文件和堆一样大 |
| Rust | `dhat`、`heaptrack`、Valgrind 类工具（分配器层） | 每个分配点、结束时仍存活的块 | 没有运行时对象图；要自己判断谁该释放 |
| Python | `tracemalloc`，`gc` 模块与 `objgraph` | 行级分配点，两次快照差分 | 开销大；C 扩展里的 `malloc` 看不到 |

**规律**：分析工具能做到多深，取决于运行时知道多少。JVM 为了精确回收，本来就维护着完整的对象元数据并能遍历整个堆，所以堆转储可以给出引用关系；Go 为了低延迟、少开销，运行时只留下分配点的采样，没有给每个对象建立可查询的引用图；Rust 没有运行时，只能在分配器这一层插桩；Python 的分配钩子容易挂，所以 `tracemalloc` 能做到行级，但对象图要靠 `gc` 另行遍历。

对应的排查思路也不同：Java 习惯先转储再离线分析持有者；Go 习惯持续抓采样的 profile 做差分；Rust 习惯从所有权结构（谁该释放）推理，再用分配器级工具验证。
