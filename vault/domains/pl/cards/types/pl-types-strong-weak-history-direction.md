## Q
隐式转换的态度在语言设计史上是怎么变的？为什么新语言越来越少用隐式转换？

## A
C（1972）为了接近汇编、便于写系统代码，允许整数、指针、字符之间大量互转，类型系统更像是对寄存器宽度的提示。Pascal 等教学语言则强调严格的类型，认为隐式转换是 bug 的来源。

1995 年的 JavaScript 为了让网页脚本「尽量不报错」，设计了很宽松的强制转换；后来人们为这些规则写了无数「JavaScript 怪癖」的列表，TypeScript 和严格相等运算符 `===` 都是对它的修补。

之后设计的语言明显收紧：Go（2009）、Rust（2015）、Kotlin、Swift 都不允许整数类型之间隐式转换，哪怕是加宽。Java（1995）和 C# 保留了数值的隐式加宽，是 C 的遗产。C++ 因为必须兼容 C 而一条都没删，只能用补丁收紧：C++98 的 `explicit` 关键字让构造函数不参与隐式转换，C++11 的花括号初始化在缩窄时报错，编译器警告（`-Wconversion`、`-Wsign-compare`）则要手动打开。

收紧的原因有三条：

1. 代码审查成本：隐式转换藏在读代码时看不见的地方，bug 难发现。
2. 精度和溢出风险：加宽可能丢精度，缩窄可能截断，隐式发生时没有人注意。
3. 类型推断冲突：类型推断需要每个表达式有唯一的类型，隐式转换让「这个表达式是什么类型」变得含糊。

趋势是：便利交给显式的转换函数（`From`、`into()`、`float64()`），而不是交给编译器自动猜。
