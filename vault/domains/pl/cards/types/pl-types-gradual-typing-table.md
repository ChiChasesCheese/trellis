## Q
Go、Java、Rust、Python 在「类型检查的强制程度与逃生口」上各自怎么选？换来什么，付出什么？

## A
| 语言 | 选择 | 换来 | 代价 |
|---|---|---|---|
| Go | 整体静态，强制标注；逃生口是 `any`（空接口）和反射 | 编译即保证；逃生口很少用 | 想要动态行为时要手写类型断言 |
| Java | 整体静态；逃生口是 `Object`、原始类型（raw type）、反射、未经检查的转换 | 兼容老代码，泛型可以逐步引入 | 逃生口会把 `ClassCastException` 推到运行期；泛型的类型参数编译后不保留 |
| Rust | 整体静态；逃生口是 `dyn Any`（可装任何类型）和 `unsafe`（放松检查的代码块） | 逃生口显式且受限 | 动态场景（插件、序列化）需要更多设计 |
| Python | 标注可选，运行时擦除，由外部检查器按需检查；逃生口是 `Any` | 可以逐文件、逐函数引入；零运行时开销；不改动老代码 | 没有保证；漏标或 `Any` 会让检查悄悄失效 |

背后的逻辑：静态语言从一开始就要求类型，所以逃生口是例外；Python 从一开始没有类型，所以类型是后加的层，保证必须是可选的，否则无法兼容二十年积累的代码。也因此 Python 的类型系统是「工具」而不是「语言语义」：同一份代码在 `mypy` 下通过，在 `pyright` 下可能报错，因为两者对推导和相容的细节判定不同。选渐进类型，等于接受「越多标注越安全，但永远没有 100% 保证」。
