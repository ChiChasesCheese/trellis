## Q
C++、Go、Java、Rust、Python 判定「类型满足接口」的方式各是什么？换来什么，付出什么？

## A
| 语言 | 选择 | 换来 | 代价 |
|---|---|---|---|
| Go | 结构：方法集吻合即满足，接口由使用方定义 | 解耦最彻底，标准库的类型自动满足你新定义的接口 | 满足关系不显眼，可能碰巧满足，需要手写编译期断言来固定意图 |
| C++ | 两套并存：运行期多态用名义（继承抽象基类加 `virtual`）；模板用编译期结构（类型只要支持用到的表达式就行），C++20 的 concepts（concept：把「类型须支持哪些操作」写成可检查的约束）让这种要求显式 | 模板的结构匹配零开销，不需要继承；继承的名义关系用于真正需要运行期多态的地方 | 没有 concepts 时，约束不满足的报错出现在模板深处，动辄上百行；继承版本无法让第三方类型事后加入 |
| Java | 名义：必须 `implements` | 意图明确，IDE 能列出全部实现者 | 无法事后让第三方类型满足接口，只能写适配器包一层 |
| Rust | 名义：`impl Trait for Type`，但 `impl` 块独立于类型定义 | 显式，又能给外部类型补实现，静态分派零开销 | 孤儿规则：trait 和类型至少一个属于本 crate，否则不能实现 |
| Python | 鸭子类型，`Protocol` 提供可选的结构检查，ABC 提供可选的名义检查 | 最灵活，三种方式随用随选 | 默认到运行期才失败 |

背后的逻辑：关键的问题是「满足关系由谁来建立」。名义类型让类型的作者建立（Java），清晰但僵硬；Rust 的折中是让任何有权的人建立，但要显式写出来，并用孤儿规则避免两个库对同一类型给出冲突的实现；结构类型让使用方建立（Go），耦合最低，但代价是关系变得隐式。Go 的小接口文化、Rust 的 trait 一致性规则、Java 的适配器模式，都是同一个权衡的不同落点。C++ 把这个权衡拆成两半，让程序员按成本选：要运行期替换实现就付虚调用的钱，用名义的继承；只在编译期需要多态就用模板，结构匹配，不付任何运行期代价。
