## Q
为什么 TypeScript 和 Python 的类型工具有意放弃可靠性？这种「务实的不可靠」比 Rust 的严格可靠差在哪里、强在哪里？

## A
可靠的类型系统不是免费的。要保证「检查通过就安全」，检查器就必须拒绝它无法证明的代码，而现实里大量**正确**的代码正好落在无法证明的范围内。

TypeScript 和 Python 的类型工具面对的是**已经存在的、没有类型的海量代码**。要让它们愿意加类型，工具必须：

1. **接受遗留写法**：JS 里数组随便放对象、回调参数类型随意，严格规则会让大多数现有库无法标注。
2. **渐进采用**：可以只给一部分代码加类型，其余是 `any` 或未注解，不影响运行。
3. **不改变运行行为**：类型擦除，没有运行时成本，也不会因为类型检查而改变程序语义。

这三个目标和「可靠」天然冲突，所以它们选了**有用但不完整的保证**：能抓住大量常见错误（拼错属性名、传错参数个数、忘记处理 `null`），不去承诺抓住全部。

Rust 的选择相反：从零设计，不背遗留代码，所有权规则在语言诞生时就存在，库生态从第一天就按这套规则写，所以能做到严格。代价是**学习成本**和**拒绝合法程序**（借用检查器的误报），逼着你改设计。

哪种更好取决于要防的事故：

- 如果错误的后果是**安全漏洞或数据损坏**（操作系统、浏览器内核、网络服务的核心），可靠性值得付出表达力的代价，这是 Rust 在系统软件里扩张的原因。
- 如果错误的后果是**业务 bug**（页面显示错、接口返回错字段），而修复便宜，渐进的、尽力而为的检查加快速迭代更划算。

务实的不可靠有一个常被忽略的风险：类型给人**虚假的安全感**。声明了 `retries: number`，读代码的人会假定它一定是数字；一旦数据来自不受检的边界，这个假定就是错的，而且没有人再去校验。

所以使用不可靠类型系统的纪律是：**把类型当作文档和提示，把运行时校验放在数据进入程序的边界上。**
