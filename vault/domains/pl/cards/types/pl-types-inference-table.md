## Q
C++、Go、Java、Rust、Python 在类型推断上各选了多强？换来什么，付出什么？

## A
| 语言 | 选择 | 换来 | 代价 |
|---|---|---|---|
| Go | 弱：只看右侧，函数签名必须写；泛型调用的类型实参可以推导 | 规则简单，局部可读，编译快，报错位置准 | 稍显啰嗦；字面量按默认类型（`1/2` 是整数 0） |
| C++ | 中：`auto`（C++11，按初始值推导类型）、模板实参推导、C++17 的类模板实参推导（CTAD，`std::vector v{1, 2}` 推出元素类型），以及返回类型推导 | 在几乎零成本的前提下省掉冗长的迭代器和模板类型；泛型代码里的类型根本写不出来 | `auto` 默认丢掉引用和 `const`，静默复制；推导失败的报错可长达上百行 |
| Java | 中：`var` 限局部变量，钻石运算符和 lambda 参数用目标类型 | 在不改变兼容性的前提下逐步减少样板 | 只能增量加入（Java 10 才有 `var`）；`var` 加钻石会退化成 `Object` |
| Rust | 强：函数体内几乎不用标注，约束求解，返回类型也参与推导 | 代码短，`collect()`、`parse()` 这类按目标类型选实现的 API 成为可能 | 约束不足时报 `type annotations needed`，读者要在脑中模拟编译器 |
| Python | 解释器不推导；`mypy` 等外部检查器会推导；未标注函数的返回值视为 `Any` | 语言无需为此付复杂度 | 推导结果不影响运行，未标注的部分检查器看不见 |

背后的逻辑：推导强度和语言的整体复杂度直接相关。Go 要让任何人几分钟读懂任何一行，所以限制推导在最简单的一档；Java 受向后兼容约束，只能在旧语法旁边追加推导；C++ 同样是在兼容 C 和旧标准的约束下追加，每个标准多放宽一点，从 C++11 的 `auto` 一路到 C++17 的类模板实参推导，因为模板元编程里的类型常常无法手写，推导是必需品而不是便利；Rust 的类型系统本来就是为表达不变量设计的，推导是让它不至于写到崩溃的必要补偿；Python 把推导整个外包给工具。
