## Q
Go、Java、Rust、Python 的类型系统各处在可靠性光谱的哪个位置？已知的漏洞和各自的兜底机制是什么？

## A
| 语言 | 可靠性定位 | 主要漏洞 | 兜底 |
|---|---|---|---|
| Rust | 安全子集静态可靠 | `unsafe` 块、编译器自身缺陷 | `unsafe` 要显式标记，审计范围小 |
| Java | 静态加运行时检查 | 数组协变、原始类型、不受检转换、`null` | JVM 在转换、数组存入、泛型出口处动态检查，保内存安全 |
| Go | 单 goroutine 内基本可靠 | 数据竞争导致多字值撕裂，`unsafe` 包，`nil` | 竞态检测器，通道，约定 |
| Python | 运行时强类型；静态注解不保证 | 注解不执行，`Any`，`cast` | 外部检查器 mypy/pyright，运行时校验库 |

作为对照，TypeScript 有意不可靠（数组协变、方法参数双变、`as`），C 不做承诺。

规律：**可靠性的强度与「错误被谁发现」成反比关系**：

- Rust 把错误推到编译期，你在写代码时被拒绝；
- Java 把漏洞的后果推到运行期的明确异常，进程不会被攻破，但可能在生产环境才发现；
- Go 在无竞争的前提下可靠，把并发正确性交给工具和约定；
- Python 把类型检查整体外包给工具。

各自的逻辑与语言目标一致。Rust 要在没有垃圾回收的前提下仍保证内存安全，所以必须在编译期证明，并为此接受类型系统的复杂度。Java 诞生于要运行不可信的网络代码（applet），虚拟机必须保证无论字节码怎样都不会破坏内存，于是把检查放在运行时，对静态漏洞的包容度反而更高。Go 追求简单，不引入复杂的所有权规则，把并发的正确性留给运行时工具。Python 以开发效率为先，类型是后加的选配。

由此得出一条选型原则：**要靠类型系统挡掉整类缺陷，选 Rust 一类的静态可靠语言；要靠测试和运行时检查补，选 Java、Go；要靠约定与工具，选 Python。**
