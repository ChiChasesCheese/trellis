## Q
Go 的类型系统大体可靠，为什么数据竞争（data race）能让它的类型安全和内存安全同时失效？

## A
Go 的静态类型相当严格：没有隐式转换、没有指针运算、数组切片有边界检查、`nil` 解引用是 panic 而不是读脏内存。在**单个 goroutine** 里，类型系统对内存安全的承诺基本成立。漏洞出在并发。

问题来自 Go 里几个**多字**的值：

- 接口值（interface）= 两个字：类型指针 + 数据指针。
- 切片 = 三个字：指针、长度、容量。
- 字符串 = 两个字：指针、长度。
- map 在运行时内部是更复杂的结构。

CPU 只保证单个机器字的读写是原子的。如果一个 goroutine 正在写一个接口变量，另一个同时读，读的一方可能看到**半新半旧的值**：新的类型指针配旧的数据指针。接口值说自己是类型 A，数据却是类型 B 的指针；这时调用方法，就是拿 B 的内存当 A 的布局来读，**类型混淆**（type confusion），直接读写任意内存。切片同理：新长度配旧指针，越界访问绕过了边界检查。

Go 的内存模型对此直言不讳：多字值上的数据竞争，读到的可能是并非任何一次写入的组合；依赖内部（指针, 长度）或（指针, 类型）一致性的值，包括接口、map、切片和字符串，这样的竞争会导致任意的内存破坏。

所以 Go 的安全承诺是**有条件的**：程序**没有数据竞争**时，类型和内存安全成立；一旦有数据竞争，语言不再保证任何事。这与 Java 形成对比：Java 的内存模型规定，即使有数据竞争，读到的也是某次真实写入的值（对引用来说至少是有效引用），不会出现类型混淆。

Go 的应对不是语言机制，而是工具：`go run -race`、`go test -race` 的竞态检测器，以及「用通道传递所有权，别共享内存」的惯用法。

要记住的事实：「内存安全的语言」要看它在并发下是否仍然安全；Go 在这点上依赖程序员，Rust 用类型系统（`Send`/`Sync`）在编译期排除，Java 用内存模型限定后果。
