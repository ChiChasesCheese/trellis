## Q
Go、Java、Rust、Python 在类型检查上各自做了什么选择？换来什么，付出什么？

## A
| 语言 | 选择 | 换来 | 代价 |
|---|---|---|---|
| Go | 静态，编译期检查，类型系统刻意简单 | 构建就挡住类型错误，重构有保障，工具可靠 | 要写类型；表达力有限，泛型直到 1.18 才加入 |
| Java | 静态，加运行期的向下转型检查，泛型被擦除 | 大型代码库可安全重构，IDE 支持最强 | 啰嗦；反射、转型和擦除把部分检查推回运行期 |
| Rust | 静态，类型承担最多的不变量（空值、错误、线程安全） | 一大类 bug 在编译期就不可能出现 | 学习成本和编译期推导的复杂度最高 |
| Python | 动态，值带类型，类型提示可选且不强制 | 写得最快，运行时可以任意改造（猴子补丁、元编程） | 错误晚暴露；大型代码库要靠测试和外部检查器补上 |

背后的逻辑：静态类型把「验证」前移，成本是前期的标注和类型系统的复杂度；动态类型把验证后移到测试和线上，成本是后期的调试与不确定性。语言的目标人群决定选择：Go 和 Java 服务于大团队的长期协作，要的是可预测；Rust 服务于「不允许出错」的系统代码，愿意付最高的前期成本；Python 服务于探索和原型，一个人写完整个脚本比任何检查都重要。项目越大、人越多、寿命越长，静态类型的收益越大。
