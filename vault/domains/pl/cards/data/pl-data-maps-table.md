## Q
比较 Go、Java、Rust、Python、C++ 的映射与集合库：各提供什么，迭代顺序怎么定，买到什么，付出什么？

## A
| 语言 | 库的形状 | 迭代顺序 | 买到 | 付出 |
|---|---|---|---|---|
| Go | 内建一种 `map`，集合靠 `map[T]struct{}` | 故意随机 | 极小的语言面，没人依赖顺序 | 没有有序映射、集合类型，要自己拼 |
| Java | `Map` 接口加多种实现（Hash、Linked、Tree、Concurrent、Enum） | 随实现：无序、插入序、排序 | 按需精确选择，接口统一 | 选择太多，装箱开销，容易选错 |
| Rust | `HashMap`/`BTreeMap` 与对应集合，`entry` API | 哈希随机，树有序 | 抗攻击默认值，选哈希还是树是显式决定 | 默认哈希较慢，键需要实现 trait |
| Python | `dict`/`set` 内置，`collections` 补充 | `dict` 保证插入序，`set` 无序 | 日常几乎只用这两个，行为直观 | 没有树，可变键不能用，顺序保证成了 API 契约 |
| C++ | `std::unordered_map`/`set`（哈希）、`std::map`/`set`（红黑树）；C++23 加 `flat_map`（有序数组） | 哈希：顺序未规定；树：按键有序 | 哈希和树都在标准库，按需选择；键与哈希是模板参数，无装箱 | 标准要求元素引用稳定，哈希只能做成节点式桶链，比 Go/Rust 的开放寻址慢；默认哈希不抗攻击 |

**逻辑**：五门语言对「顺序」给出了五个答案，恰好对应各自的价值观。C++ 说「未规定，要有序请换容器」：`unordered_map` 不承诺顺序，`map` 承诺有序，类型名里写明了，和 Java 一样；不同的是它的承诺被标准里的另一条要求绑住了，即插入、扩容后元素的引用和指针必须保持有效，这让标准库的哈希表无法改用更快的开放寻址布局，Abseil 的 `flat_hash_map` 等第三方库才提供。零开销原则承诺的是“手写不会更快”，而这里的接口承诺让标准实现比手写的更慢，是 C++ 为早期标准付出的历史代价。Go 说「别依赖顺序」，所以故意打乱，避免未来无法修改实现。Python 说「顺序对人有用」，所以把它升级为保证，让 JSON、关键字参数、类定义都能依赖它。Java 说「由你选」，把顺序暴露在类型名里。Rust 说「默认安全，需要的话显式选择」。

**共同的结构**：每门语言的库都在回答同一组问题：要不要有序？要不要抗攻击？要不要并发？答案分散在类型选择（Java、Rust）、约定（Go）或统一容器加少量变体（Python）里。
