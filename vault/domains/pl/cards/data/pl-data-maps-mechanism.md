## Q
Go、Java、Rust、Python 的哈希表在一百万个整数键上大约有多快？为什么实现差异（链表 vs 开放寻址）影响这么大？

## A
**本机一次测量**（一百万个整数键，每个操作的平均耗时，仅为量级参考）：

| 语言 | 插入 | 查找 | 备注 |
|---|---|---|---|
| Go `map[int]int` | 约 51 ns | 约 12 ns | Swiss Table，开放寻址 |
| Rust `HashMap` | 约 51 ns | 约 17 ns | SipHash，Swiss Table |
| Java `HashMap<Integer,Integer>` | 约 20 到 30 ns | 约 2 到 8 ns（预热后） | 链表法，键值装箱 |
| Python `dict` | 约 26 ns | 约 34 ns | 循环本身占大头 |

**怎样解读**：
1. 数字都在几十纳秒以内，大小差异不大，**差异主要来自布局和哈希函数，而不是语言快慢**。
2. 开放寻址（Go、Rust、Python）把键值放在连续内存里，一次缓存行读入能探测多个槽位；Swiss Table 更进一步，用一个字节的元数据，借助 SIMD 指令一次比较一组槽位。链表法每次跳转都是一次指针追逐，缓存不友好，这个测试里 Java 反而很快，因为键是顺序创建的，装箱对象在堆上恰好相邻，缓存表现被高估；真实应用里键的内存分布散乱得多。
3. Rust 默认的 SipHash 比 Go 的硬件加速哈希慢，换成 FxHash 会更快，换来的是失去抗攻击能力。
4. Python 的查找一栏比插入慢，是因为测量代码里 `s += big[i]` 还包含了循环和整数加法，不能全算在字典头上。

**负载与内存**：Java 每个条目是一个 `Node` 对象（约 32 字节加上装箱的键值），内存开销比开放寻址高出一倍以上。Python 紧凑字典每个条目存（哈希，键指针，值指针）约 24 字节，再加一个小的索引数组，整体比链表法紧凑。

**结论**：不要凭「哪门语言的 map 快」来选语言。真正要问的是：键的布局是否连续、哈希是否昂贵、是否发生装箱。
