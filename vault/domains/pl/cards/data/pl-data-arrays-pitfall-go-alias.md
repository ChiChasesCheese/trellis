## Q
Go 的切片 `append` 为什么会「有时改到原数据、有时不改」？这个别名陷阱在线上的表现是什么，怎样修？

## A
陷阱来自一个事实：`append` 是否复制取决于**容量是否够**，而调用者通常看不到容量。

```go
a := []int{1, 2, 3, 4}
b := a[:2]
b = append(b, 99)      // cap 4 enough: writes into a's memory
fmt.Println(a, b)      // [1 2 99 4] [1 2 99]
b = append(b, 100, 101) // exceeds cap: reallocates
b[0] = -1
fmt.Println(a, b)      // [1 2 99 4] [-1 2 99 100 101]
```

真实输出如注释。第一次 `append` 悄悄改掉了 `a[2]`（原来是 3，现在是 99）；第二次超出容量，复制到新数组，之后对 `b` 的修改不再影响 `a`。同一段代码，行为随长度突然改变。

**线上表现**：
- 从一个大切片里取出一个子切片，交给另一个 goroutine 追加，悄悄覆盖了后面的数据，偶发数据损坏，很难复现。
- 缓冲区池里复用的切片被多个请求共享，数据串到别的请求里。
- 保存了一个大切片的小子切片（比如从 10 MB 的响应里取 10 个字节），整个 10 MB 数组都不能被 GC 回收，内存「泄漏」。

**修复**：
1. 需要独立副本就显式复制：`slices.Clone(s)` 或 `append([]T(nil), s...)`。
2. 返回子切片时限制容量：`s[a:b:b]`，之后 `append` 必然复制。
3. 对外 API 约定：切片参数不会被修改、也不会被持有，写在文档里。
4. 小子切片长期持有时，复制出来，让大数组可以回收。

作为对比，Python 里切片总是复制（安全但慢），Rust 里这段代码根本编译不过。
