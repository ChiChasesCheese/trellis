## Q
Go 的一个 `[]T` 与 Rust 的 `Vec<T>`/`&[T]` 拆分，反映了两门语言对「所有权信息该不该出现在类型里」怎样的立场？

## A
同一个操作「取子区间并追加」，两门语言的结果差别很大。

**Go：类型不说所有权**。`[]int` 既可能独占一块内存，也可能是别人数组的一部分。读到一个 `[]int` 参数，你无法从类型判断：我可以修改它吗？修改会影响谁？`append` 之后原切片还有效吗？答案取决于代码的上下文和容量。这是 Go「少即是多」的立场：减少概念，信任程序员遵守约定，复杂情形靠文档与 code review。它也带来一类典型 bug：两个 goroutine 各持有同一数组的不同切片，一个 `append` 悄悄写进了另一个的区域。

**Rust：类型就是所有权声明**。`Vec<T>` 说「我拥有」，`&[T]` 说「我只读借用」，`&mut [T]` 说「我独占借用」。函数签名里就能看到它会不会修改、会不会保存数据。编译器检查所有这些主张，所以同类 bug 在编译期消失。立场是：**正确性信息应该由编译器检查，而不是靠约定和记忆**。

**揭示的价值观**：Go 为「可读性与上手速度」优化，把一部分责任留给程序员；Rust 为「大型代码库长期正确」优化，把责任交给类型系统。

**C++：类型说了，但没人检查**。`vector` 拥有、`span` 借用，签名里能读出所有权；可是 `span` 悬空、`vector` 扩容后旧引用失效，都不是编译错误。它和 Rust 的分歧不在类型怎么拆，而在谁来保证声明为真：C++ 交给程序员和 sanitizer（运行期检测工具），这是零开销与手动控制的一贯选择。

**Java 与 Python 的第三种态度**：不暴露内存共享。列表就是对象引用，要共享就是共享同一个对象；要隔离就复制。性能让位于心智模型的简单。

**判断方法**：团队里新人多、代码评审强，Go 的做法效率更高；并发多、不能容忍静默别名的核心库，Rust 的做法更稳。
