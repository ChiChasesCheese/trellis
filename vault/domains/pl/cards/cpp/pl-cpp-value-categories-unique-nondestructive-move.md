## Q
C++ 的移动为什么是“非破坏性”的？这个选择对类型设计、对 Rust 的对比意味着什么？

## A
**事实**：C++ 的移动只是调用另一个构造函数。源对象的生命周期不受影响：它仍在作用域里，到了作用域结尾，析构函数照常运行。

**为什么这样设计**：
1. **向后兼容**：C++98 的对象模型里，每个对象在作用域结束时恰好析构一次。要引入“被移动的变量不析构”，编译器就得在每个出口追踪变量是否被移走，改变整个对象模型。
2. **移动有时是有条件的**：`if (cond) sink(std::move(x));`——编译器在编译期无法知道 `x` 是否被移走。Rust 为此引入了运行时的“drop flag”和严格的移动检查；C++ 选择了更简单的路：什么都照常析构。

**代价与后果**：
1. **每个可移动的类型必须有“空”状态**：这就是为什么 `unique_ptr` 不能做成“永远非空”，`std::string` 移动后是空串。想要“不可为空”的类型，同时又要可移动，是矛盾的需求。
2. **使用被移动对象是合法的**：编译通过，行为是“有效但未指定”。真实输出：

```cpp
q.push_back(std::move(s));
println("size after move = {}", s.size());   // size after move = 0
```

输出 `size after move = 0`，但这个 0 只是 libc++ 恰好如此，换标准库可能不同。
3. **移动后析构的成本**：被移空的对象析构仍要执行一次（检查指针是否为空），通常可忽略，但在极热的路径上算一笔。

**对比 Rust**：
```rust
let t = s;
println!("{}", s);  // error[E0382]: borrow of moved value: `s`
```
Rust 把“被移动”做成编译错误，同时省去了空状态与多余的析构。

**要记住的一点**：C++ 的移动是“约定”而不是“保证”：没有工具会替你拦住对被移动对象的使用，需要靠静态分析（`clang-tidy` 的 `bugprone-use-after-move`）和约定。
