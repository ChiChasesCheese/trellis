## Q
C++、Rust、Go、Java、Python 在内存安全上各自提供什么保证？机制、成本和逃生口分别是什么？

## A
| 语言 | 越界/释放后使用 | 保证来自 | 成本 | 逃生口 |
|---|---|---|---|---|
| C++ | 默认都是 UB | 无；靠加固、分析、纪律 | 加固有少量运行时开销 | 全语言都是（无边界） |
| Rust | safe 代码内不会发生 | 编译期所有权与借用，加上边界检查 | 学习与设计成本；边界检查 | `unsafe` 块 |
| Go | 越界 panic；无释放后使用（GC） | GC 与运行时检查 | GC 与检查开销 | `unsafe` 包、数据竞争仍可能破坏 |
| Java | 越界抛异常；无释放后使用 | GC 与运行时检查，JVM 验证字节码 | 同上 | `Unsafe`、JNI |
| Python | 都是异常；无释放后使用 | 解释器 | 解释开销 | C 扩展、`ctypes` |

**逻辑**：这几行沿"**谁来保证、保证在哪里生效**"排列。
- Rust 在**编译期**证明（所有权），加上必要的运行时检查（边界），保证覆盖 safe 子集，逃生口 `unsafe` 的**位置明确**，可以审查；
- Go、Java、Python 靠**运行时**（GC + 检查），保证覆盖整个语言，逃生口在语言边缘（JNI、`unsafe` 包、C 扩展）；
- C++ **没有语言级保证**，保证来自外部：编译器选项、加固的库、静态分析、测试、编码规范。

**两个常被忽略的点**：
1. **Rust 和 Java/Go 的"安全"定义不同**：Go 的数据竞争可以破坏内存安全（竞争写切片头），Rust 的 safe 代码保证无数据竞争；Java 的竞争不破坏内存安全但会产生不确定值；
2. **C++ 的"逃生口"是整个语言**：无法 grep 出风险点，Rust 可以 grep `unsafe`。审计一个 C++ 代码库的内存安全，意味着审计所有指针和引用的使用。

**现实中的 C++ 工程**：不是"有没有保证"二选一，而是**多层防御**：加固的库挡越界，智能指针挡泄漏和重复释放，ASan/TSan/UBSan 在 CI 里挡剩余，模糊测试给输入，静态分析抓模式。每一层都不完整，叠加起来把剩余风险压到可接受。

**实用结论**：评估一个系统用不用 C++ 时，把"内存安全"当作一项要用**流程**（CI、加固、审计）购买的属性，而不是语言附赠的属性，并把这笔流程成本算进总成本。
