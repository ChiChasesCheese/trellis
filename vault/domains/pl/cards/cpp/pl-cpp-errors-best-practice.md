## Q
资深 C++ 工程师在错误处理上遵循哪些规则？一个项目起步时应当怎样划分"异常、`expected`、断言"的分工？

## A
**分工原则**（参照 C++ Core Guidelines 的 E 章与常见的工业实践）：

| 失败的性质 | 用什么 |
|---|---|
| 违反前置条件、程序员错误、"不应该发生" | `assert` / 契约 / 终止；不要当作可恢复的错误 |
| 预期会发生的失败：输入非法、文件不存在、网络超时 | `std::expected<T, E>` 或 `std::optional` |
| 罕见的、无法在本层处理的失败：内存耗尽、构造失败、第三方库抛出 | 异常 |
| 禁用异常的子系统的所有失败 | `expected`；构造失败用工厂函数 |

**写法规则**：
1. **异常按 `const&` 捕获**，派生类放在基类之前；
2. **抛出的类型继承 `std::exception`**，消息包含上下文（哪个文件、哪个操作）；
3. **析构函数、`swap`、移动操作不抛出**，并标 `noexcept`；
4. **资源全靠 RAII**；不要在业务代码里写 `try { ... } catch (...) { 清理; throw; }`，应该把清理封装进析构函数；
5. **在边界处捕获**：线程入口、`main`、C 回调的外层，不让异常跨越；
6. **返回错误的函数加 `[[nodiscard]]`**，这样忽略返回值会得到警告；
7. **错误类型要有结构**：`std::error_code` 加类别，或带上下文的枚举，不要只返回字符串；
8. **构造函数失败用异常**，或用静态工厂返回 `expected<T, E>` 并把构造函数设为私有。

**异常安全检查表**：每个修改状态的函数问三个问题——失败在第几行？此时对象不变量成立吗？是否需要强保证？

**工具**：`clang-tidy` 的 `bugprone-exception-escape`（检测 `noexcept` 里可能逃出异常）、`misc-throw-by-value-catch-by-reference`、`cert-err*` 系列。

**什么时候打破**：热路径上预期失败率高的接口，不用异常；一次性脚本式的工具程序，让异常直接终止进程也可以。

**为什么这样**：这套分工的逻辑是"**失败越是预期的，越要显式表达在类型里；越是意外的，越适合隐式传播**"。

**要记住的一点**：先定约定，再写代码；约定写进规范并用工具检查，比争论哪种机制更好重要得多。
