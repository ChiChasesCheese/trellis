## Q
在“如何对待抽象的成本与程序员的责任”上，C++、Go、Java、Rust、Python 各做了什么选择？换来什么，代价是什么？

## A
| 语言 | 选择 | 换来 | 代价 |
|---|---|---|---|
| C++ | 抽象编译后消失，安全默认交给程序员 | 性能与控制最大，可贴近硬件 | 未定义行为（UB）、复杂度高、编译慢 |
| Rust | 抽象编译后消失，安全由编译器证明 | 同等性能，且无内存错误 | 借用检查器带来学习与设计成本 |
| Go | 小语言加运行时（GC、调度器） | 简单、编译快、并发易用 | 少一层控制，GC 与运行时的开销 |
| Java | 虚拟机加 JIT 加 GC | 生态、可移植、长期稳定 | 启动与内存足迹，GC 暂停 |
| Python | 解释执行，一切皆对象 | 开发速度最快 | 速度慢约两个数量级 |

**逻辑**：这五个答案沿着同一条轴排列——“**谁来承担复杂度**”。Python、Java、Go 让运行时和语言设计者承担，换来程序员的轻松；C++ 与 Rust 让程序员（或编译器）承担，换来运行时的零成本。C++ 与 Rust 的分歧只在最后一步：**C++ 相信程序员会遵守规则，Rust 要求编译器证明规则被遵守**。

这个分歧有历史原因：C++ 诞生时（1980 年代）没有现成的静态分析手段，也必须兼容数以亿行计的 C 代码，所以选择了“信任”；Rust 出现在 2010 年代，借助线性类型与区域推理的研究成果，才有可能把同样的规则变成编译器检查。

**最适合的组合**：C++ 适合已经有大量 C/C++ 资产、需要极致性能的系统（游戏引擎、交易系统、数据库、浏览器）；其余场景要看团队能否承担它的复杂度。
