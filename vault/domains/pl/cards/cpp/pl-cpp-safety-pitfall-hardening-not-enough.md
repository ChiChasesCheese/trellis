## Q
开了标准库加固和 `-Wall` 之后，哪些 C++ 内存安全 bug 仍然会漏进生产？为什么"我们开了加固"不等于"安全"？

## A
**加固只检查它能看见的前置条件**：容器和视图成员函数的下标、空容器。以下情形它都看不见：

**1. 生命周期错误**。本机实测：一个按引用捕获局部变量并逃出函数的 lambda，`-Wall -Wextra` 零警告；开启 `_LIBCPP_HARDENING_MODE_EXTENSIVE` 并 `-O2` 编译，运行输出 `2`（读到垃圾），退出码 0，**没有崩溃，没有报错**。只有 ASan 加 `detect_stack_use_after_return=1` 才会报告。

**2. 指针算术和 C 数组**：`p[i]`、`*(p + n)`、`memcpy` 越界。加固的库只改 `std::vector` 这类类型的成员函数，裸指针没有被包住。

**3. 释放后使用**：`std::string_view` 指向已销毁的临时 `std::string`（clang 能警告其中简单的形态：`-Wdangling-gsl`），迭代器在容器扩容后继续用。

**4. 数据竞争**：加固与此无关。

**5. 整数溢出导致的尺寸错误**：`size_t` 计算溢出后分配了小缓冲区，之后在合法范围内的检查全部通过，但访问越过了真实缓冲区。

**6. 第三方 C 库和插件**：它们不走你的加固库。

**7. 类型混淆**：`reinterpret_cast`、`union` 误用。

**为什么"开了加固"会给人虚假的安心**：加固把一类常见的、容易发现的 bug 变成崩溃，大幅降低了整体风险，但没有改变剩下的 bug 仍是未定义行为这一事实。更糟的是，安全评估中"加固已开启"这一条会让评审者放松对生命周期的审查。

**识别一个系统还剩多少风险**：
1. 统计裸指针和引用成员的数量、`reinterpret_cast`、`memcpy` 的数量；
2. 看生命周期复杂的组件：异步回调、跨线程共享、lambda 逃逸、视图作为成员；
3. 在 ASan 加模糊测试下的覆盖率；
4. 历史 CVE 的分类是否集中在某一类。

**对策**：
- 缩小"借用"的跨度：视图和引用只在局部使用，不跨函数边界长期保存；
- 异步代码里捕获按值，共享状态用 `shared_ptr` 或明确的所有者；
- 把 sanitizer 和模糊测试覆盖到所有解析不可信输入的路径；
- 对生命周期复杂的核心组件，考虑用 Rust 之类有静态保证的语言重写。

**要记住的一点**：加固解决了空间安全的大头，时间安全仍然需要工具、设计和纪律；两者要分开说，不要用一个"已加固"概括。
