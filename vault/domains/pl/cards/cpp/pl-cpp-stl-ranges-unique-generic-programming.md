## Q
STL 体现的"泛型编程"（generic programming）哲学是什么？它与面向对象的容器库设计有什么根本不同？

## A
**泛型编程的核心**（Stepanov）：从具体算法出发，找出它对数据**最少的要求**，把算法写成适用于所有满足这些要求的类型。`std::find` 只要求"能前进、能读取、能比较"；不要求"继承自某个基类"。

**与面向对象的容器库对比**：

| | OO 式（Java Collections） | STL |
|---|---|---|
| 抽象方式 | 接口与继承：`List`、`Collection` | 概念：迭代器类别，按能力分层 |
| 算法位置 | 容器的方法或静态工具类 | 独立的函数模板 |
| 绑定时机 | 运行时（虚调用） | 编译期（模板实例化） |
| 基本类型 | 要装箱成对象 | 直接存放 |
| 扩展 | 新类要继承或实现接口 | 满足概念即可，包括内置类型和指针 |

**一个微妙的结果**：指针是合法的迭代器，所以 `std::sort(arr, arr + n)` 对 C 数组也能用；STL 没有为 C 数组特别设计，只是它们恰好满足要求。这是"按概念而不是按类型"的威力。

**复杂度也是契约的一部分**：标准规定了每个操作的最坏或均摊复杂度，这是 STL 区别于很多库的地方。`std::map::find` 是 O(log n)，`std::unordered_map::find` 平均 O(1)，`std::list::size()` 自 C++11 起是 O(1)。选择算法和容器变成了可以推理的工程决策。

**这种哲学的成本**：
1. **接口是隐式的**：算法需要迭代器有什么能力，不看文档就不知道，ranges 与 concepts 把它显式化；
2. **错误信息**：模板深处报错；
3. **迭代器失效等语义靠文档**：对象与对象之间没有类型层面的所有权关系，容器和迭代器的关系，类型系统不管。

**与 Rust 的对照**：Rust 的 `Iterator` trait 是同一种思想的现代版本：算法写在 trait 上，通过 trait 约束表达要求，借用检查器管理容器与迭代器的关系。可以说 Rust 把 STL 的语义契约（包括失效规则）变成了类型系统的一部分。

**要记住的一点**：理解 STL，就是理解"**算法依赖概念，概念由类型的能力满足**"；这套思路后来被 Rust、Swift 的协议、C++ 的 concepts 继承。
