## Q
C++、Rust、Go、Java、Python 各用什么机制决定"谁释放资源"？换来什么，代价是什么？

## A
| 语言 | 机制 | 换来 | 代价 |
|---|---|---|---|
| C++ | 析构函数 RAII；`unique_ptr` / `shared_ptr` 表达所有权 | 确定性释放，覆盖内存与所有资源，零运行时 | 所有权是约定，编译器不拦错误使用 |
| Rust | `Drop` 加所有权与借用检查 | 同样的确定性，且编译期证明无悬垂、无重复释放 | 学习曲线、设计受约束 |
| Go | 追踪式 GC；其他资源 `defer` | 内存无需操心 | GC 开销；文件、锁要每处写 `defer` |
| Java | 追踪式 GC；`try-with-resources` | 同上，生态成熟 | 同上，加上暂停与内存占用 |
| Python | 引用计数加循环收集；`with` | 多数对象用完即释放 | 每次赋值都改计数；环要靠 GC |

**逻辑**：这五行是同一条轴上的五个点——**释放的责任放在哪里**。
- 放在**运行时**（Go、Java、Python）：程序员省心，但要付 GC 或计数的运行时成本，并且只对内存有效；
- 放在**类型**里（C++、Rust）：成本在编译期付清，释放对所有资源通用。

C++ 与 Rust 的唯一差别在**谁来检查所有权被正确使用**：Rust 的编译器检查，C++ 靠程序员、代码评审、静态分析和 sanitizer。这就是 C++ 的同一批问题（悬垂指针、double free、use-after-free）在 Rust 里变成编译错误的原因。

C++ 的优势在于它出现得早：它在没有这些检查手段的 1980 年代，用最小的语言扩展（析构函数）给出了今天仍在使用的资源管理模型，Rust 的 `Drop` 是直接继承。代价是留下大量"可以写错"的空间：混用裸指针、重复管理同一指针、忘记 `virtual` 析构函数等。

**实用结论**：在 C++ 里，**所有权类型就是你的"编译器检查"**。接口里尽可能用 `unique_ptr`、引用、`span` 这类带语义的类型，不要用裸指针；这是把约定变成类型的唯一办法。
