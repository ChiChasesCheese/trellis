## Q
C++、Rust、Java、Go、Python 的"一份代码服务多种类型"各用什么实现？约束在什么时候检查，换来什么，代价是什么？

## A
| 语言 | 实现方式 | 约束检查 | 换来 | 代价 |
|---|---|---|---|---|
| C++ | 单态化（每个类型一份代码） | 实例化时按用法检查；concepts 检查调用点 | 极致运行速度，可内联；能写任何图灵完备的元编程 | 编译慢、体积大，模板体靠鸭子类型 |
| Rust | 单态化 | 定义时按 trait 约束检查 | 同样快，且泛型体的错误在定义处报 | 表达力受 trait 限制，编译同样慢 |
| Java | 类型擦除（一份代码，基本类型装箱） | 编译时检查，运行时擦除 | 体积小，兼容旧字节码 | 无法 `new T()`，基本类型要装箱 |
| Go | GC 形状模板（形状相同共用一份加字典） | 定义时按约束检查 | 编译快，体积适中 | 部分调用有间接成本，不如完全单态化 |
| Python | 无泛型（动态类型），类型注解只是提示 | 不检查（工具可选检查） | 最灵活 | 全是运行时查找 |

**逻辑**：这是沿着"**用多少编译期成本换运行期速度**"一条轴排列的。C++ 与 Rust 在最前端：把全部代价放到编译期；Java 与 Go 居中：共享代码，换来小体积和快编译；Python 在另一端：什么都不付，也什么都不保证。

**C++ 与 Rust 的关键差别**不在速度，而在**谁约束模板**：
- Rust 要求泛型函数体**只能使用 trait 声明的操作**，实现者和使用者的契约是明确的；
- C++ 允许模板体使用类型实参上的任何操作，只在实例化时才检查，concepts（C++20）补上了调用点的约束。

这个差别是历史造成的：C++ 的模板在 1990 年代设计，目标是 STL（Stepanov 的泛型编程），要求"**不加任何运行时成本**"；类型约束的语言机制被留到二十多年后，也就是 concepts。Rust 吸取了这一教训，一开始就把 trait 约束设计进去。

**实用结论**：在 C++ 里写公共模板，要**主动**补上 Rust 默认给你的东西：用 concepts 写出约束，再为每个约束写测试，确认模板体没有使用约束以外的操作。
