## Q
C++、Rust、Zig、Go、Java、Python 各自能在编译期做什么计算？换来什么，代价是什么？

## A
| 语言 | 编译期能力 | 换来 | 代价 |
|---|---|---|---|
| C++ | `constexpr`/`consteval` 函数、模板、`if constexpr`，C++26 反射 | 几乎任何普通代码都能在编译期运行，类型也能算 | 编译慢，求值器是解释器 |
| Rust | `const fn`、const 泛型、宏（`macro_rules!` 与过程宏） | 常量计算加强大的代码生成宏 | `const fn` 限制比 C++ 多；过程宏编译重 |
| Zig | `comptime`：类型是编译期值，任何函数可在编译期运行 | 泛型与元编程统一成一套普通代码 | 语言小众，生态弱 |
| Go | 常量表达式（只有字面量算术），无编译期函数 | 简单、编译快 | 想生成表要用 `go generate` 外挂脚本 |
| Java | 常量折叠（字面量）；注解处理器做代码生成 | 简单 | 能力弱，生成要靠外部工具 |

**逻辑**：这是沿着"**编译期与运行期的界线画在哪里**"一条轴的选择。
- Go 和 Java 把界线画得很早：编译期只做最少的事，保持编译快和语言简单；
- C++、Rust、Zig 把界线推后：让编译期成为可以跑程序的地方。

**三者的路径不同**：
- C++ 是**渐进式**的：从宏到模板到 `constexpr`，每一版放宽一点，新旧方式并存；
- Rust 把编译期计算分成两层：`const fn` 做值，**宏**做代码生成（宏在语法树上展开，不是函数调用）；
- Zig 一开始就统一：`comptime` 让类型也是值，没有"模板"这个单独的概念，泛型是普通函数带 `comptime` 参数。

**C++ 的最大特点**：编译期求值器与运行期共享**同一份语言**，同一个函数两边都能用。这让测试、复用变得容易，代价是语言规范必须同时描述两种执行环境，复杂度很高。

**实用结论**：选 C++ 做需要编译期生成表、做静态校验、做零开销配置的系统（嵌入式、交易系统、游戏）时，`constexpr` 是核心工具；不需要这些的场景里，C++ 的这套机制就是纯复杂度。
