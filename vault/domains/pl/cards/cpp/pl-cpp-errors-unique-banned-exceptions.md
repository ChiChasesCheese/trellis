## Q
为什么很多低延迟、游戏和大型工程的 C++ 代码禁用异常？这个现象说明了 C++ 怎样的特殊性？

## A
**事实**：Google 的 C++ 风格指南长期禁用异常；游戏引擎、交易系统、嵌入式固件、浏览器的大部分代码都用 `-fno-exceptions` 编译。这不是对异常的偏见，而是几条工程理由：

1. **最坏延迟不可控**：一次抛出约 2.6 μs，更关键的是展开表可能在冷内存里，第一次触发会缺页，延迟抖动大。低延迟系统关心的是 99.99 百分位，不是平均值。
2. **控制流不可见**：任何函数调用都可能"提前出口"，审查代码时看不到。资源管理必须全靠 RAII，否则泄漏。对大型老代码库，要保证所有代码都异常安全几乎不可能。
3. **二进制体积与优化**：展开表占空间；可能抛出的调用点限制优化。嵌入式环境很在意。
4. **接口兼容**：异常无法安全地跨越 C 接口或不同编译器的二进制边界；和 C 库、插件系统打交道时必须转换。
5. **历史包袱**：很多代码库在异常安全尚未被广泛理解的年代写成，加入异常等于要重新审计所有代码。

**代价**：关闭异常后，`new` 失败不抛 `bad_alloc`（程序直接终止）；构造函数无法报告失败，必须采用两段式初始化（先构造，再 `init()` 返回状态）或工厂函数返回 `expected`；标准库中依赖异常的接口（`vector::at`、`stoi`）不能用，生态会分裂成"有异常"与"无异常"两派，库很难同时服务两边。

**这反映了 C++ 的什么**：
- **没有统一的错误模型**：不同于 Go 和 Rust 一开始就定死，C++ 把选择权交给项目，`-fno-exceptions` 是一个**合法的、被主流编译器支持的子集**。
- **"你不用就不付"原则的延伸**：不想为异常付体积和延迟，就整个关掉。
- **代价是分裂**：C++ 不是一门语言，而是一族方言，团队需要明确自己属于哪个方言。

**对比**：Rust 的 `panic` 在嵌入式场景也可以改成直接终止（`panic = "abort"`），但库的主要接口是 `Result`，不受影响；Java 和 Python 没法关闭异常。

**要记住的一点**：在 C++ 里"是否使用异常"是项目级的架构决策，而且要尽早决定，因为之后改的成本极高。
