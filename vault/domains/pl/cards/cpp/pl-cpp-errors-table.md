## Q
C++、Go、Java、Rust、Python 的错误处理主流机制各是什么？成本模型与可见性怎样？

## A
| 语言 | 主流机制 | 正常路径 | 失败路径 | 错误是否可见于签名 |
|---|---|---|---|---|
| C++ | 异常 + `expected`/错误码并存 | 异常：零；`expected`：一次判断 | 异常约 2.6 μs；`expected` 极便宜 | 异常否（`noexcept` 仅表示不抛）；`expected` 是 |
| Go | 多返回值 `error`，`panic` 仅用于严重错误 | 每次调用后判断 | 普通返回，便宜 | 是 |
| Java | 异常（受检 + 非受检） | 几乎零 | 创建栈追踪，较贵 | 受检异常是，其余否 |
| Rust | `Result<T, E>` + `?`，`panic!` 仅限程序错误 | 一次判断 | 普通返回，便宜 | 是 |
| Python | 异常，`EAFP` 风格 | 3.11 起 `try` 零成本 | 较贵（对象 + 栈追踪） | 否 |

**逻辑**：这张表的横轴是"**错误是不是类型的一部分**"。Go、Rust 把错误做成返回值，调用者必须面对；Java 用受检异常想做到这点但被广泛视为失败（样板多、被滥用 `throws Exception`）；Python 完全隐式；C++ 两头都占。

**C++ 为什么两者并存**：历史上先有异常（1990 年代，用来解决构造函数无返回值问题），后来发现在低延迟与嵌入式领域异常的最坏延迟不可接受，又出现了 `std::error_code` 和 `expected`。标准库本身混用两种：`std::vector::at` 抛 `out_of_range`，`std::from_chars` 返回错误码，`std::filesystem` 的大多数函数同时提供抛异常和返回 `error_code` 的两个重载。

**C++ 的现实**：你的项目要自己定一个"**哪一类错误用哪种机制**"的约定。没有约定时最糟糕：一半函数抛异常，一半返回错误码，调用者不知道该检查还是该捕获。

**对比 Rust 的启示**：Rust 的做法是语言一次定死——可恢复错误用 `Result`，不可恢复用 `panic`。C++ 的好处是适合各种场景，坏处是每个项目都要重新做决定，而且第三方库的选择会渗入你的代码。

**实用结论**：新代码里，预期失败用 `std::expected`，罕见失败和构造失败用异常，违反前置条件用断言，并把约定写进编码规范。
