## Q
从 `.cpp` 到可执行文件，经历哪几个阶段？名字改编（name mangling）是什么，为什么 C++ 链接比 C 更容易出莫名其妙的错？

## A
**四个阶段**：
1. **预处理**：展开 `#include`、宏、条件编译，得到一个翻译单元的完整文本；
2. **编译**：把这个翻译单元编译成机器码，产出**目标文件**（`.o`），里面有这个单元定义的符号和它引用但未定义的符号；
3. **链接**：链接器把所有目标文件和库合在一起，把每个"引用了某名字"的地方连到"定义了该名字"的位置，产出可执行文件；
4. **加载**：运行时由操作系统加载，动态库在此时解析。

**符号用名字匹配**。C 里函数 `answer` 的符号就是 `answer`（macOS 前面多一个下划线）。C++ 允许**重载**（同名不同参数）、命名空间、模板，同一个名字可以对应许多函数，所以编译器给每个函数生成一个包含完整信息的**改编名**（mangled name）：

```
bool will_overflow(int)
  -> __Z13will_overflowi
```

读法：`13will_overflow` 是长度加名字（13 个字符），结尾的 `i` 表示参数类型 `int`；macOS 上再多一个下划线前缀。

模板实例带上类型实参，名字会很长，如 `std::vector<int, std::allocator<int>>` 参与的函数名有上百字符。命令行工具 `c++filt` 或 `nm -C` 把它还原成可读形式。

**这带来的实际后果**：
1. **链接错误难读**：未定义符号报的是改编名，如 `Undefined symbols: "from_a()"`，需要还原和判断是漏链接库、还是声明与定义签名不一致；
2. **没有统一的 ABI**（应用二进制接口：函数怎样传参、改编规则、类布局）。改编规则由编译器厂商定义（Itanium ABI 用于 GCC/Clang，MSVC 另一套），不同编译器、甚至同一编译器的不同版本和标准库实现编译出的二进制，可能不能混用；
3. **C 是通用语**：跨语言、跨编译器的接口通常用 `extern "C"` 声明，关掉改编，退回 C 的规则；
4. **模板和 `inline` 在多个目标文件里各有一份**，链接器按名字合并，只保留一份（这正是 ODR 违反不报错的原因）。

**时间花在哪里**：大项目里编译（含解析头文件）通常占主要时间，链接则在最后一步，对大型可执行文件也可能要几十秒；LTO（链接时优化）让优化器看到所有翻译单元，生成更好的代码，但链接变慢。

**对比**：Rust 没有稳定 ABI（只保证在同一编译器版本内），它的库以 `rlib` 形式随源码元数据一起分发，由编译器统一处理；Java 的 `.class` 格式稳定，JVM 负责链接；Go 静态链接成单个二进制。C++ 的二进制兼容全靠约定。

**要记住的一点**：C++ 的链接发生在"名字"的层面，编译器负责把类型信息编码进名字，这个做法让重载可行，但也让跨编译器协作变得脆弱。
