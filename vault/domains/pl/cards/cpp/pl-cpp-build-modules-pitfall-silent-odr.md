## Q
头文件与 ODR 在生产里最常见的坑是什么？为什么 ODR 违反能"构建成功、测试通过、上线出事"？

## A
**典型事故：同名的 `inline` 函数或类在不同文件里内容不同。**

```cpp
// a.cpp
inline int answer() { return 1; }  int from_a() { return answer(); }
// b.cpp
inline int answer() { return 2; }  int from_b() { return answer(); }
```

本机实测，同一份代码：
- `-O0`：`from_a=1 from_b=1`（链接器合并了两个 `answer`，只留一份，`from_b` 得到错误的值）；
- `-O2`：`from_a=1 from_b=2`（内联后各用各的）。

**没有任何编译错误，没有链接警告**。测试在 Debug 构建下结果错，在 Release 构建下结果对；或者反过来。

**真实项目里常见的形态**：
1. **两个库各自定义了同名的辅助类/函数**（如 `Config`、`Logger`、`to_string`），链接进同一个程序，链接器悄悄只留一个；
2. **同一个头文件在不同翻译单元里因宏不同而展开成不同的类定义**：一个文件 `#define FEATURE_X` 在包含头文件之前，另一个没有，类的成员变量布局不同。一个文件创建对象，另一个文件访问成员，偏移错位，读到垃圾；
3. **静态库和动态库里各带一份同名类**，加载顺序决定谁生效；
4. **编译选项不一致**（`-std=`、`_GLIBCXX_DEBUG`、`NDEBUG`、对齐/打包选项）：标准库的类布局随选项变化，库与应用混用时崩溃；
5. **全局对象的初始化依赖顺序**：跨翻译单元的静态初始化顺序没有规定，改一下链接顺序行为就变。

**为什么构建成功**：编译器一次只看一个翻译单元；链接器只比较**名字**，不比较定义的内容；标准明确说"违反 ODR 不需要诊断"（no diagnostic required），所以实现可以不检查。

**排查**：
- **缩小范围**：用 `nm -C` 找出被多个目标文件定义的弱符号，检查它们的内容是否一致；
- **LTO 加警告**：GCC 的 `-flto -Wodr` 能发现类型定义不一致；
- **统一编译选项**：检查所有库是否用相同的编译器版本、标准、关键宏；
- **ASan 的 `ASAN_OPTIONS=detect_odr_violation=2`**：对全局变量冲突有帮助，不能保证抓到函数体差异；
- **看是否只在某个优化级别出错**：这是 ODR 或 UB 的典型信号。

**预防**：
1. 文件内私有的东西放匿名命名空间；
2. 不同库的符号放进各自命名空间；
3. 在构建系统里统一编译选项，对第三方库也一样；
4. 限制符号可见性（`-fvisibility=hidden`），只导出需要的接口；
5. 头文件不依赖包含顺序的宏。

**要记住的一点**：如果一个 bug 在换优化级别、换链接顺序、换编译器时才出现，先怀疑 ODR 违反或 UB，而不是业务逻辑。
