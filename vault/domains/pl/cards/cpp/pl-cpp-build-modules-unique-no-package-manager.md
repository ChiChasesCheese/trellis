## Q
"C++ 没有统一的包管理器"这件事揭示了 C++ 的什么性格？标准委员会与生态各自承担什么，为什么最终是生态来填补？

## A
**表面**：没有官方的包管理器和构建工具。

**深层原因：C++ 是"标准加实现"的语言**。ISO C++ 是一份规格，编译器是多家厂商实现的，没有"官方实现"。凡是规格没有定义的东西，各实现、各平台、各公司按自己的需要处理。

**这与 Rust、Go 的根本区别**：
- Rust 和 Go 是由一个团队主导的语言，它们的编译器、包管理器、格式化工具都是同一套**官方工具链**，同时发布；
- C++ 的"工具链"其实是多个独立项目拼成：GCC、Clang、MSVC 是编译器，CMake、Bazel 是构建，vcpkg、Conan 是包管理，clang-format、clang-tidy 是工具。

**好处**：
1. **多个实现竞争**：编译器进步快，诊断、优化、sanitizer 互相促进；
2. **适配极端环境**：嵌入式、操作系统内核、GPU、专用芯片都能有自己的工具链；
3. **没有锁定**：大公司可以用 Bazel 自己的体系，不被迫接受某个工具。

**代价**：
1. **碎片化**：每个团队的构建都是定制的；
2. **难以统一做的事做不成**：全生态统一的包元数据、统一的 ABI、统一的代码格式；
3. **新人门槛高**。

**与"零开销、信任程序员"的一致性**：C++ 的语言设计里不给你一个默认的路，需要你自己做选择并承担选择的后果；构建与依赖层面同样如此。这既是它灵活的来源，也是它复杂的来源。

**趋势**：生态在自发收敛。CMake 成为通用语，`compile_commands.json` 成为工具之间的接口，vcpkg 和 Conan 提供清单文件，Google 的 Abseil、Meta 的 Folly 等公司库以"可被 CMake 引入"的方式发布。不是被设计出来的统一，而是被事实形成的统一。

**要记住的一点**：C++ 的"生态层"和"语言层"是分开的；评估 C++ 的成熟度，要同时看两层，不能只看标准版本。
