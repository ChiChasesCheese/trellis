## Q
"C++ 提供机制而不提供策略"在并发上具体指什么？它与 Go 的运行时调度、Rust 的 `Send`/`Sync` 相比，揭示了怎样的哲学？

## A
**机制与策略**：机制是"能做什么"（线程、锁、原子、协程），策略是"该怎么用"（谁调度、任务怎么分发、错误怎么传播）。C++ 标准基本只提供机制：

- 有线程，**没有线程池**（`std::async` 的默认启动策略允许延迟执行，不保证异步，不能当线程池用）；
- 有协程语言特性，**没有协程运行时**；
- 有原子和内存序，**没有无锁数据结构**；
- 有互斥量，**没有读写锁的优先级策略**（`shared_mutex` 的策略由实现决定）。

**一个暴露这种哲学的陷阱：`std::async` 的返回值被忽略**。本机实测：

```cpp
std::async(std::launch::async, slow, 1);   // 返回的 future 是临时对象
std::async(std::launch::async, slow, 2);
```

临时 `future` 在语句结束时**析构，而它的析构函数会阻塞等待任务完成**。结果是两个"异步"任务变成串行：约 490 到 680 ms（每个任务睡眠 200 ms，本机睡眠有额外开销），而保留 `future` 的版本并行完成，约 330 到 350 ms。编译器警告：`ignoring return value of function declared with 'nodiscard' attribute`。

**三种哲学的对比**：
1. **C++：我给原语，你搭系统**。好处是可以搭出针对你场景优化的调度器（交易系统用的绑核无锁队列，游戏引擎用的任务图）；代价是每个项目、每个库各有各的线程池和协程类型，互不兼容，生态碎片化。
2. **Go：语言内置策略**。goroutine、channel、调度器、`select` 都是语言的一部分，所有 Go 代码用同一套。写起来简单一致，但不能换成自己的调度策略。
3. **Rust：标准库提供原语，类型系统提供策略**。`Send`/`Sync` 规定什么能跨线程；运行时（tokio）由生态提供，也有碎片化，但"能不能跨线程共享"的规则是统一且强制的。

**为什么 C++ 这样**：与"零开销"和"不强加不用的东西"一致——不想为不需要的调度器付运行时成本；标准委员会也很难就"策略"达成一致。C++26 的 `std::execution`（sender/receiver 模型）试图补上统一的异步抽象，但仍然是一个让你组合调度器的框架，不是一个现成的运行时。

**要记住的一点**：用 C++ 做并发，要先选一个库作为"策略层"（Boost.Asio、folly、TBB、自写），不要指望标准库替你定好。
