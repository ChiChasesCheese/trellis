## Q
C++20 的模块（module）是什么？它解决头文件模型的哪些问题，现在的工具链支持到什么程度？

## A
**模块**：一个源文件声明自己是模块（`export module greet;`），用 `export` 标出对外可见的接口；使用者写 `import greet;` 而不是 `#include`。编译器把模块**编译一次**成内部表示（二进制接口文件），使用者读取这个表示，不再重新解析源码文本。

**解决的问题**：
1. **编译速度**：模块只编译一次，被导入时直接读取，不像头文件被粘贴进每个翻译单元；
2. **隔离**：模块里的宏不会泄漏给导入者，导入顺序不影响含义；
3. **接口明确**：只有 `export` 的东西可见，没有"声明在头文件、实现细节也在头文件"的问题；
4. **减少 ODR 类问题**：模块有明确的所有权，同名实体属于各自的模块；
5. **标准库模块**（C++23）：`import std;` 一行导入整个标准库，不用逐个包含头文件。

**现状（谨慎看待）**：
- 编译器：GCC、Clang、MSVC 在较新版本中都支持，完整度和稳定性不同；MSVC 最成熟；
- 构建系统：需要构建系统先扫描依赖、再按顺序编译模块接口。CMake 3.28 起正式支持（配合 Ninja）；其他系统支持有限；
- 库：大量现有库仍是头文件，很多项目用 `#include` 与 `import` 混合；
- **本机的 Apple clang 不接受模块写法**：

```
m.cppm:1:8: error: expected template        // export module greet;
use2.cpp:1:1: error: unknown type name 'import'   // import std;
```

这说明模块的**推广受制于整条工具链**：编译器、构建系统、IDE、静态分析器和包管理器要同时跟上，缺任何一环项目就用不了。

**与其他语言**：Java 9 的模块系统（JPMS）、Rust 的 crate 与 `mod`、Go 的包，本来就是编译器理解的单位，没有历史包袱；C++ 要在保持与数以亿行计的旧头文件兼容的前提下引入，所以过渡极长。

**实用建议**：
- 新的、自成体系的内部库可以尝试模块，但要确认全部目标平台的工具链；
- 面向外部发布的库，目前仍以头文件为主，接口稳定；
- 在模块普及之前，用预编译头、`ccache`、少包含、前置声明控制编译时间。

**要记住的一点**：模块是对头文件模型的正式修正，但落地速度取决于工具链，不是语言规格；评估时先在你的编译器和构建系统上跑通。
