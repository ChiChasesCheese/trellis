## Q
C++、Rust、Go、Java、Python 在“把一个对象的内容交给另一个变量”时，分别选了什么语义？换来什么，代价是什么？

## A
| 语言 | 默认语义 | 换来 | 代价 |
|---|---|---|---|
| C++ | 值拷贝；移动要用 `std::move` 声明；非破坏性 | 值语义和移动都可控，向后兼容 | 规则多，被移动对象仍存在，易误用 |
| Rust | 赋值即移动；编译器禁止再用源变量 | 零成本，且无“被移动对象”这一状态 | 需学所有权，设计受约束 |
| Go | 值拷贝；slice、map、指针共享底层 | 简单，拷贝是浅的 | 别名要靠约定，没有移动概念 |
| Java | 对象都是引用，赋值只复制引用 | 无拷贝成本，无所有权问题 | 每个对象在堆上，需要 GC |
| Python | 同上，一切皆引用 | 同上 | 引用计数或 GC 开销 |

**逻辑**：这几个答案是同一个问题的不同折中。Java/Python/Go 通过“共享引用”**避开**了移动问题——代价是对象身份与所有权混在一起，靠 GC 兜底。Rust 与 C++ 都要求零成本，所以都需要“转移所有权”：Rust 让编译器强制，**源变量作废**；C++ 为兼容旧代码让程序员显式声明，**源对象留下一个空壳**。

最重要的区别在“空壳”：C++ 的移动是**非破坏性**的，源对象的析构函数照常运行，所以每个可移动的类型都必须有一个“已被移走”的合法状态（`unique_ptr` 的空指针、`string` 的空串），这个状态在类型设计中必须被考虑。Rust 的移动是**破坏性**的，编译器知道源变量已无效，不需要这个状态，也不会执行它的析构。

对比 Rust，C++ 少了编译器检查：移动后继续使用 `s` 在 C++ 里能通过编译，在 Rust 里报错 `borrow of moved value: 's'`。
