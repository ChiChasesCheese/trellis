## Q
C++、Rust、Go、Java、Python 的标准容器与迭代/惰性管道设计，各做了什么选择？在"迭代时修改容器"上谁负责拦截？

## A
| 语言 | 容器的元素存储 | 迭代/管道 | 迭代时修改容器 |
|---|---|---|---|
| C++ | 值直接存放，`vector` 连续 | 迭代器对；ranges 视图（惰性，编译期展开） | 不检查，UB |
| Rust | `Vec<T>` 同样连续值存放 | `Iterator` 适配器（惰性，零成本） | 借用检查器编译期拒绝 |
| Go | 切片、map；值存放，map 无序 | `for range`；无标准惰性管道 | 切片追加后别名可能错乱；map 遍历中修改有定义 |
| Java | 集合存对象引用；基本类型要装箱 | `Iterator`、`Stream`（惰性，单次使用，有运行时开销） | 运行时抛 `ConcurrentModificationException` |
| Python | 列表存引用 | 迭代器协议、生成器（惰性） | 字典遍历中改大小抛 `RuntimeError` |

**逻辑**：这是一条"**谁保证迭代期间容器没被破坏**"的轴。
- Rust 靠**所有权规则**：迭代器借用容器，借用期间不能修改，没有运行时成本；
- Java、Python 靠**运行时标记**（修改计数器）在检测到修改时报错，简单但有开销；
- C++ **什么也不做**，因为任何检查都违反"不用不付费"，文档规定了规则，遵守是你的事。

**C++ 容器模型的独特点**：
1. **值语义**：`vector<int>` 存的就是 `int`，没有对象头和间接引用，遍历是顺序内存读取，这是 C++ 性能的基础；
2. **接口即复杂度契约**：标准规定每个操作的复杂度，使"按需选择容器"成为可推理的设计；
3. **算法与容器解耦**：同一个 `std::ranges::sort` 适用于所有满足 concepts 的范围；
4. **零成本惰性管道**：ranges 视图在 `-O2` 下通常能优化到接近手写循环。

**C++ 的短板**：
- 标准库缺少一些现代语言默认有的东西，如标准的并发容器、不可变容器、完善的 `enumerate`（C++23 的 `views::enumerate` 本机的 libc++ 尚未实现）；
- 迭代器失效和视图悬垂只能靠约定与工具防御。

**实用结论**：把 Rust 的借用检查器想象成"自动执行了 C++ 文档里的失效规则"；在 C++ 里你要自己扮演这个检查器，并用 ASan 在测试里兜底。
