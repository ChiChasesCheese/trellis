## Q
"UB 是一份契约"这个看法对工程实践意味着什么？它与 Java 的"一切有定义"、Rust 的 `unsafe` 各有什么不同？

## A
**把 UB 看成契约**：函数的前置条件（precondition）如果被调用者违反，函数的行为不再有任何规定。`std::vector::operator[]` 的前置条件是 `i < size()`；违反它不是"返回垃圾"，而是整个程序进入未定义状态。这与 Java 的 `ArrayIndexOutOfBoundsException` 完全不同：Java 把违约变成**一个可处理的事件**，C++ 把违约变成**无法保证的状态**。

**两条推论**：
1. **没有"安全地失败"**：UB 之后，程序的任何部分都不再可信，包括日志、错误处理、断言。所以不能写 `try { v[i] } catch(...)` 来保护。保护只能是**事前检查**。
2. **测试通过证明不了没有 UB**：编译器不报错，运行不崩溃，也可能含有 UB，只是这次碰巧正常。

**对比**：
- **Java**：JLS（语言规范）几乎对每一种情况都规定了结果，包括数据竞争（内存模型规定了竞争程序仍有受限的合法结果）。目标是"同一份字节码在任何 JVM 上行为一致"。
- **Rust**：安全代码里**没有 UB**；`unsafe` 块是程序员向编译器承诺"这里我替你检查"。UB 被圈在 `unsafe` 里，并且有明确的 `unsafe` 标记便于审查。内部使用的规则（别名、有效值）与 C++ 的 UB 概念同源。
- **C++**：UB 遍布整个语言，没有范围标记。每一行都可能是契约的一方。

**哲学上的区别**：Java 和 Rust 把"安全"当作语言的保证；C++ 把"性能"当作语言的保证，安全是程序员加护栏之后的结果。

**实践含义**：在 C++ 项目里，必须把"**可信边界**"设计出来：所有来自外部的输入（网络、文件、用户）在边界处完整校验，内部代码才能依赖前置条件；内部用断言和 sanitizer 保护契约，边界之内才可以放心地不做检查。

**要记住的一点**：在 C++ 里"校验输入"和"防止 UB"是同一件事；安全问题往往出在某个没做校验就假设前置条件成立的地方。
