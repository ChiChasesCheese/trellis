## Q
C++、Rust、Go、Java、Python 的并发模型各是什么？怎样防数据竞争，换来什么，代价是什么？

## A
| 语言 | 并行单元与共享方式 | 防数据竞争的办法 | 换来 | 代价 |
|---|---|---|---|---|
| C++ | OS 线程；共享内存 + 锁/原子；协程只有机制 | 无（UB），靠纪律 + TSan | 最低层控制，最快 | 竞争是未定义行为 |
| Rust | OS 线程 + async；共享内存 + 所有权 | `Send`/`Sync` 编译期检查 | 无畏并发，同样快 | 借用规则带来的设计约束 |
| Go | goroutine（M:N 调度）；channel 优先 | 约定 + `-race` 检测 | 并发极易用，创建便宜 | 共享内存仍可能竞争，运行时调度开销 |
| Java | 平台线程 / 虚拟线程；共享内存 + 锁 | 内存模型规定竞争程序仍有受限行为 | 工具与库成熟 | 竞争仍会产生逻辑错误 |
| Python | 线程受 GIL 限制；asyncio 协程；多进程 | GIL 保证解释器内部安全 | 简单，I/O 并发好用 | CPU 密集型无法多线程并行（3.13 起有自由线程构建） |

**逻辑**：这是"**谁来保证正确**"的轴。
- Rust 靠编译器；
- Go 靠约定和运行时的检测工具（鼓励用 channel 减少共享）；
- Java 靠成熟的内存模型和库，竞争的后果可预期但不是好事；
- Python 靠全局解释器锁牺牲并行；
- C++ 什么都不保证，**回报是没有任何中间层**：线程是内核线程，原子操作是硬件指令，没有调度器开销。

**C++ 的特殊处**：它是**第一个**为多线程正式定义**内存模型**的主流系统语言之一（2011 年，借鉴了 Java 2004 年的内存模型工作），并把"数据竞争是 UB"写进标准。这是一个深思熟虑的选择：允许编译器在假设"无竞争"的前提下做重排和优化。

**实用结论**：C++ 的并发安全是"**设计出来的**"——用线程池、任务队列和不可变数据减少共享；必须共享时用封装好的类，把锁和数据放一起；CI 里持续跑 TSan。需要编译器替你保证时，换 Rust。
