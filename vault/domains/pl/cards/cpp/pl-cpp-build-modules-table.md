## Q
C++、Rust、Go、Java、Python 的代码组织单位、依赖管理和构建工具各是什么？C++ 缺的是哪一块？

## A
| 语言 | 编译/组织单位 | 依赖与构建 | 重复定义的检查 |
|---|---|---|---|
| C++ | 翻译单元 + 头文件；C++20 模块 | 语言之外：CMake、Bazel、vcpkg、Conan 各选 | 链接器按名字，ODR 违反常无声 |
| Rust | crate（含模块树） | `cargo` + crates.io，一体 | 编译器看整个 crate，重复是错误 |
| Go | package | `go mod` + `go build`，一体 | 包内重复定义是编译错误 |
| Java | class 与 package，JAR | Maven/Gradle + Maven Central | 类加载器按全名，冲突在加载时 |
| Python | module / package | `pip`、`uv` + PyPI | 后导入覆盖先导入，无检查 |

**逻辑**：这张表的轴是"**语言是否把构建当作自己的一部分**"。Rust、Go 都把构建与包管理做进语言的官方工具链，因此体验统一；Java 靠社区形成了事实标准；Python 靠 PyPI；C++ 什么官方的都没有。

**为什么 C++ 缺这一块**，不是疏忽，而是历史必然：
1. **起源早于包管理时代**：C++ 的模型来自 1970 年代的 C，当时没有"下载一个依赖"这回事；
2. **平台和编译器多样**：Linux、Windows、macOS、嵌入式，GCC、Clang、MSVC、各种交叉编译器，没有哪个构建方式能覆盖所有；
3. **ABI 不统一**：预编译好的二进制库不能随便分发，必须按编译器、版本、标准库、选项组合分别编译，所以包管理器多半要**从源码构建**，慢，且组合爆炸；
4. **委员会的职权**：WG21 只管语言和标准库，构建工具超出范围。

**后果**：
- 新人跑起一个依赖五个库的项目，可能要先花一两天配环境；
- 公司之间的做法各不相同，人员在项目间迁移要重新学；
- 供应链安全、版本锁定要自己做；
- 小的头文件库（单文件库，如 `nlohmann/json`、`doctest`）因为"拷一个文件就能用"而特别流行。

**正在改善的方向**：vcpkg 与 Conan 成熟、CMake 成为公约数、C++20 模块与"包描述"的标准化讨论（工具链与 ABI 的互通由 SG15 小组工作）；但没有一个能达到 `cargo` 的一体化。

**实用结论**：评估一个 C++ 项目的维护成本时，除了代码，还要看它的**构建与依赖基础设施**成熟度；这是 C++ 工程相比其他语言额外要付的成本。
