## Q
在 Java 和 Go 的生产系统里，调 GC 的最佳实践是什么？为什么「减少分配」通常比「调参数」更有效？

## A
GC 的成本大致等于「存活数据量」乘「回收频率」，而回收频率由「分配速率」决定。所以降低分配速率是杠杆最大的手段，调参只是在已有负载下重新分配成本。

**Java**
1. 先用默认的 G1，并打开 GC 日志（`-Xlog:gc`）。先有数据再选择：关心尾延迟（p99 暂停）就试 ZGC，关心离线吞吐就用 Parallel。
2. 服务端把 `-Xms` 与 `-Xmx` 设成相同，避免堆动态伸缩造成的额外回收；容器里留出堆外内存（线程栈、元空间、直接内存）的余量。
3. 看三个指标：分配速率、暂停时间分布、回收后的存活集大小。存活集持续上升不是调参问题，是泄漏。
4. 不要在代码里调用 `System.gc()`。

**Go**
1. 先降低分配：基准里看 `allocs/op`，用 pprof 找出分配热点，复用缓冲区，预分配容量。
2. 容器里设置 `GOMEMLIMIT`（软上限，略低于容器内存），让 GC 在接近上限时更积极，避免被 OOM kill；`GOGC` 只在明确想用内存换 CPU 时调大。
3. 不要在业务代码里调 `runtime.GC()`。

**Python**：不要随便 `gc.disable()`；要关就要保证没有循环引用，并有监控。

为什么：GC 日志与指标告诉你问题在分配、存活集还是回收器本身；在没有数据时换回收器、堆大小，只是随机试错。

什么时候违反：硬实时、超低延迟系统（交易撮合）会直接避免在热路径上分配，把 GC 排除在关键路径之外。
