## Q
编译器怎样在编译期检查「移动后不可用」？当值只在某条分支里被移走时，运行时怎么知道要不要销毁，什么是 drop flag？

## A
**检查在编译期完成。**借用检查器在函数的控制流图上对每个变量跟踪一个状态：已初始化、已移动、部分移动。每次使用一个变量，都检查在所有可能到达这里的路径上它是不是还处于「已初始化」。任何一条路径上它可能已被移走，就报错 `E0382: use of moved value`。这是一种静态数据流分析，没有运行时成本。

**销毁的时机也由此推导。**变量离开作用域时，如果它在所有路径上都还没被移走，编译器就在那里插入一次 `drop`；如果在所有路径上都已被移走，就不插入。

难点是**条件移动**：只有一部分路径移走了值。

```rust
let t = T("x");       // T's Drop prints "drop <name>"
if std::env::args().count() > 5 { drop(t); }   // moved on one path only
println!("end");
```

无参数运行：条件为假，输出 `end`、`drop x`（作用域结束时销毁）。带 5 个以上的参数运行：条件为真，`drop(t)` 先执行，输出 `drop x`、`end`，函数结束时**不会**再次销毁。

编译器在这里插入了一个运行时标志：**drop flag**，是存在栈帧里的一个布尔位，记录「`t` 还拥有值吗」。变量初始化时置位，被移走时清零，离开作用域时检查：置位才调用析构。只有在静态分析无法确定的变量上才需要它；多数变量的移动路径是确定的，编译器会省掉这个标志。

这展示了仿射类型的实现代价：

1. **静态检查零成本**：路径确定时，不需要任何运行时记录。
2. **条件移动需要 1 位的运行时状态**：每个这样的变量多占一点栈空间，销毁时多一次判断，远比垃圾回收轻。
3. **与 C++ 的差别**：C++ 的被移走对象仍会运行析构（要靠移动构造函数把对象置成可安全析构的空状态），Rust 的被移走变量根本不会再被析构。

结论：所有权的「用一次」规则，是一个控制流敏感的静态分析，加上少量运行时标志来处理分支。
