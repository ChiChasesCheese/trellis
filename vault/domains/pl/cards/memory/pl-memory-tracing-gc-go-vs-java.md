## Q
Go 的回收器为什么选择「非分代、非移动」，Java 为什么选择分代和移动？这两种取舍各换来什么？

## A
两者在不同约束下做了不同选择。

**Go：并发三色标记-清除，非分代，非移动**
- 对象一旦分配地址就不变。好处：指针可以直接传给 C 代码；内部指针（指向结构体字段的指针）不需要更新；不需要读屏障，只需要写屏障，程序线程的开销小。
- 因为不移动，内存碎片要靠分配器解决：Go 的分配器按大小分级（size class），同一大小的对象放在同一块内存页里，释放后槽位直接复用，几乎没有外部碎片。
- 不分代是因为分代需要移动（把存活对象晋升到老年代）或更复杂的记录结构（要跟踪老年代指向年轻代的引用）。Go 把降低垃圾产生量交给逃逸分析和值类型：很多 Java 里的短命堆对象，在 Go 里是栈上值。
- 调优面窄：`GOGC` 和 `GOMEMLIMIT`。
- 较新的 Go（本机 1.27）默认启用 Green Tea 回收器：按内存页成批扫描对象，改善缓存局部性、降低标记开销，但仍是非分代、非移动。

**Java：分代、复制与整理，可选多种回收器**
- 对象会被移动，所以内存紧凑，分配只需移动指针（每个线程有自己的小块分配缓冲，几条指令）。短命对象的年轻代回收极便宜。
- 代价是需要更复杂的屏障（G1 有写屏障，ZGC 还有读屏障（程序线程每次读引用时检查对象是否已被搬走）），运行时更大，参数多。
- 对象几乎都在堆上，垃圾产生量大，所以 GC 效率是 Java 性能的关键，也就催生了 G1、ZGC 等多种回收器供不同负载选用。

一句话：Go 减少垃圾并保持回收器简单，Java 接受更多垃圾并用更强的回收器消化。
