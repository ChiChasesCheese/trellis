## Q
在 C++、Go、Java、Rust、Python 里，处理栈与堆的最佳实践分别是什么？为什么？

## A
通用原则：不要凭直觉预判分配，先测量，再把分配挪出热路径。栈分配几乎免费，堆分配的真正代价在于之后的回收和缓存未命中，所以瓶颈要由 profile 指出，而不是由习惯指出。

- **Go**：小结构体传值，大结构体或需要修改时才传指针；热路径上用 `go test -bench . -benchmem` 跑基准，输出里的 `allocs/op` 是每次操作的堆分配次数；已知元素数量时用 `make([]T, 0, n)` 预分配容量，避免 `append` 反复扩容搬家。不要为了「省一次复制」到处用指针，那常常会让变量逃逸到堆。
- **Java**：不要手工池化小对象。对象的分配（指针碰撞）和短命对象的回收都极便宜，池化反而制造老年代对象和同步开销。需要紧凑数据时用基本类型数组。递归深度由输入决定时，改成显式栈（`ArrayDeque`），而不是调大 `-Xss`。
- **Rust**：默认放栈，是正确的起点。大数组（几百 KB 以上）用 `Vec` 或 `Box<[T]>`；递归深度无界的算法改写成循环加显式 `Vec` 栈。
- **C++**：默认值语义、放栈；大数组和不定长数据用 `std::vector`、`std::array`（定长且小）；需要堆上单个对象才用 `make_unique`，不写裸 `new`；热路径上预留容量（`reserve`）避免反复扩容，必要时用 `std::pmr`（多态分配器，让容器从预先分好的内存池里取内存）。递归深度由输入决定时改成显式栈。
- **Python**：递归遇到 `RecursionError` 时改成迭代，而不是调高 `sys.setrecursionlimit`（那只是把崩溃从 Python 异常换成进程段错误）。大量数值用 `array` 或 NumPy。

什么时候违反：对象确实要跨函数、跨线程长期存在时，放堆是对的；延迟敏感的路径（交易、实时音视频）则值得把分配彻底挪到启动阶段预先完成。
