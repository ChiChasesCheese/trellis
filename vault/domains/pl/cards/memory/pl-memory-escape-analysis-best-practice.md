## Q
依赖逃逸分析的语言（Go、Java）里，写热点代码的最佳实践是什么？为什么「验证」比「相信」更重要？

## A
逃逸分析是编译器的优化，不是你的契约，除非你亲手验证过。

**Go**
1. 先写清晰的代码，小结构体传值。只对基准和 pprof 指出的热点优化。
2. 用 `go test -bench . -benchmem` 看 `allocs/op`；对 0 分配有要求的函数，写测试用 `testing.AllocsPerRun` 断言，防止以后改动悄悄引入逃逸。
3. 用 `-gcflags=-m` 找出逃逸原因，常见元凶：把值传给 `any` 参数（`fmt.Println`、日志）、闭包捕获并返回、存入全局或逃逸的容器、容量未知的大切片。
4. 热路径上避免接口和装箱，用泛型或具体类型；复用缓冲区；预分配容量。`sync.Pool` 有效但引入复杂度，要测量后再用。

**Java**
1. 写正常的小对象、不可变值对象代码，JIT 通常会处理好，不要为了迎合逃逸分析而扭曲代码或手工池化。
2. 但不要凭信念：用 JMH（Java 的微基准测试框架）做基准，配合 `-Xlog:gc` 或 JFR 的分配事件，确认优化真的发生。
3. 保持热点方法小而可内联，这是标量替换生效的前提。
4. 考虑 JIT 预热：基准与压测都要先热身。

**C++**（不依赖逃逸分析）
1. 默认写值：局部对象和容器里的元素本来就在栈上或内联，不要为了「像 Java」而到处 `new`、`make_unique`（在堆上创建对象并返回自动释放的智能指针）。
2. 只有需要多态、需要比作用域更长的生命周期或对象很大时才放堆；返回对象直接按值返回（C++17 起强制省略拷贝，不付复制成本）。
为什么：同样一行 `new Point()`，在不同上下文里可能是零分配，也可能是一次真实的堆分配；差别由周围的代码决定。没有测量，性能模型就是猜测。

什么时候违反：不是热点的代码，直接按可读性写，分配的成本不值得花时间。
