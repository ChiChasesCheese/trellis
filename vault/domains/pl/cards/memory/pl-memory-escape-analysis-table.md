## Q
Go、Java、Rust、Python 对「对象放栈还是放堆」的自动优化各做到什么程度？换来什么，代价是什么？

## A
| 语言 | 选择 | 换来 | 代价 |
|---|---|---|---|
| Go | 编译期逃逸分析是语言实现的核心 | 结果确定、可用 `-gcflags=-m` 和 `allocs/op` 验证 | 保守，函数边界上的接口、闭包常导致逃逸 |
| Java | C2 的 JIT 逃逸分析加标量替换 | 热点代码里小对象可完全消失 | 要预热、依赖内联，无保证，不同版本结果可能不同 |
| Rust | 不需要：程序员显式决定栈或堆 | 没有隐式行为 | 由人负责；LLVM 偶尔额外消除堆分配 |
| Python | 无 | 实现简单 | 所有对象都分配 |

逻辑：语言越是把「栈与堆」藏起来，越需要这类优化来补回性能。Go 把它做成稳定的编译期行为，所以它变成了可以讨论、可以测试的性能契约；Java 把它做成机会性的 JIT 优化，只能当作红利，不能当作保证。对性能敏感的代码，应当依赖可验证的行为：Go 里用基准确认零分配，Java 里用 JMH 加 GC 日志验证，而不是凭「JIT 应该会优化掉」。
