## Q
C++、Go、Java、Rust、Python 在回收内存的方式上各选了什么？换来什么，代价是什么？

## A
| 语言 | 选择 | 换来 | 代价 |
|---|---|---|---|
| Go | 并发三色标记-清除，不分代、不移动 | 暂停极短，实现简单，对象地址稳定 | 无法靠分代降低成本，要靠少分配；调优旋钮只有 `GOGC`、`GOMEMLIMIT` |
| Java | 多种可替换回收器：G1（默认）、ZGC 等，分代、移动 | 吞吐与延迟都能做到极致，ZGC 暂停亚毫秒级 | 运行时复杂，屏障有开销，参数多、需要选型 |
| C++ | 标准没有 GC；释放点由 RAII 和智能指针在编译期决定（可选的第三方保守 GC 如 Boehm 极少使用） | 无暂停、无运行时、内存紧凑，释放时机确定 | 所有权靠约定，泄漏和悬空指针编译器不拦 |
| Rust | 无 GC，所有权在编译期决定释放点 | 无暂停、无运行时、内存紧凑 | 数据结构受所有权约束，共享要显式处理 |
| Python | 引用计数为主，循环垃圾检测器兜底 | 对象立即回收，销毁时机可预期 | 每次赋值都改计数；循环检测有停顿；多线程要 GIL 配合 |

规律：每种选择都是在「暂停时间、吞吐、内存开销、实现复杂度」四者里取舍。Go 的设计者把简单与低延迟放在首位，宁可牺牲吞吐的上限，并通过逃逸分析与值类型减少垃圾总量；Java 面对各种负载，干脆让用户选回收器，哲学是「没有万能的 GC」；Python 早年追求实现简单和与 C 扩展的兼容，引用计数恰好满足；C++ 与 Rust 拒绝运行时回收，把成本转移到编译期和程序员身上：C++ 靠 RAII，是零开销原则的直接结果（C++11 曾为可选 GC 预留过接口，后来在 C++23 被删掉，说明社区并不需要）；Rust 在此之上加了借用检查。

没有赢家：低延迟和高吞吐、小内存占用三者不可兼得，换一个目标，最优答案就不同。
