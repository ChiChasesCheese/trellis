## Q
Go、Java、Rust、Python 靠什么保证内存安全？各自留下了什么缺口，代价是什么？

## A
| 语言 | 选择 | 换来 | 缺口与代价 |
|---|---|---|---|
| Go | GC 加运行期边界检查 | 越界与释放后使用不可能 | 数据竞争不受保护，slice、接口值竞争写可能撕裂；`unsafe`、cgo |
| Java | GC 加运行期检查，内存模型保证竞争不损坏 JVM | 最强的「出错也不会破坏运行时」 | 竞争仍会导致逻辑错误；`Unsafe`、JNI、FFM |
| Rust | 所有权、借用、生命周期加运行期边界检查 | 安全代码里连数据竞争都排除 | 学习曲线；`unsafe` 块里自己负责 |
| Python | 引用计数加边界检查，GIL 保护解释器内部 | 纯 Python 代码不会内存破坏 | `ctypes` 与 C 扩展可以随意破坏；GIL 不保护业务逻辑 |

逻辑：越界检查几乎所有语言都做，区分度在两个问题上：（1）不靠 GC 能否保证安全；（2）并发下能否保证安全。只有 Rust 对两者都给出了编译期的回答，代价是把复杂度推给了程序员；GC 语言用运行时机制解决（1），对（2）各给出不同强度的承诺：Java 给出内存模型保证，Go 只给工具，Python 靠 GIL 的副作用。

对选型的含义：内存安全是一个光谱而不是一个开关。评估一个系统时要问清楚：不安全的部分（`unsafe`、FFI、C 扩展）有多大，是否被封装在小范围内，是否被审计。
