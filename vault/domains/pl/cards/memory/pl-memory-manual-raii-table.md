## Q
Go、Java、Rust、Python 对「谁在何时释放资源」各选了什么机制？换来什么，代价是什么？

## A
| 语言 | 选择 | 换来 | 代价 |
|---|---|---|---|
| Go | 内存交给 GC；其他资源靠 `defer` | 内存无需操心 | 没有析构，释放文件、锁要靠调用者记得写 `defer` |
| Java | 内存交给 GC；其他资源靠 try-with-resources | 同上 | `finalize` 已弃用，资源释放全靠调用者用对语法 |
| Rust | 内存与其他资源统一用 `Drop`（RAII） | 释放时机确定，类型自带清理，不会忘 | 生命周期必须是词法嵌套的，共享要显式 `Rc`（引用计数的共享指针） |
| Python | CPython 引用计数归零即销毁；资源靠 `with` | 多数情况下对象用完立刻释放 | `__del__` 的时机不是语言保证的，其他实现可能不同 |

规律：RAII 把「释放」和「作用域」绑定，所以内存与文件、锁能用同一个机制；GC 把内存的释放从作用域里剥离出来，换来共享引用的自由，却让其他资源失去了免费的自动化，只好另外补一套作用域语法。这是一个干净的取舍：共享的灵活性对确定性的释放。

所以 GC 语言里「资源要在作用域里获取并释放」不是风格偏好，而是用语法弥补语言机制的缺口；Rust 里则是类型系统的一部分，忘记释放几乎不可能发生。
