## Q
引用计数在 C++、Go、Java、Rust、Python 里分别处于什么位置？为什么各自这样选？

## A
| 语言 | 选择 | 换来 | 代价 |
|---|---|---|---|
| C++ | 可选库类型：`shared_ptr`（计数更新线程安全，实际是原子操作）加 `weak_ptr`；默认用 `unique_ptr`（单一所有权，无计数） | 只在需要共享所有权时付费，`make_shared` 把对象与计数放进同一次分配 | 没有非原子版本，单线程里也付原子操作的钱；循环引用会泄漏，要自己用 `weak_ptr` 破环 |
| Go | 不用，纯追踪式 GC | 赋值不改计数，没有循环问题 | 释放时机不确定 |
| Java | 不用，纯追踪式 GC | 同上，且可以做分代与移动 | 同上 |
| Rust | 可选库类型：`Rc`（非原子）、`Arc`（原子）、`Weak` | 只在确实需要共享所有权时付费，线程安全由类型决定 | 循环会泄漏，要自己用 `Weak` 破环 |
| Python | 每个对象都有计数，加循环检测器 | 销毁即时，资源与 C 扩展管理简单 | 每次引用变化都是一次内存写；多线程需要 GIL 或更复杂的计数 |

逻辑：引用计数的成本与「引用操作的频率」成正比，追踪式 GC 的成本与「存活对象的数量」成正比。Go、Java 的程序里引用被大量复制、传递，每次都改计数代价太高，所以选了追踪式；Rust 和 C++ 的默认是单一所有权（`Box`、`unique_ptr`），引用操作本来就少，在少数需要共享的地方用计数很划算（C++ 的 `shared_ptr` 与 Rust 的 `Arc` 同构，区别是 C++ 没有 `Rc` 这样的单线程便宜版本，也没有编译器替你挡住误用）；Python 的解释器本身就在频繁地创建、销毁引用，加一次计数相对不显眼，换来的却是确定的销毁和对 C 扩展友好的内存模型。

另一个角度是并发：计数更新在多线程下要原子化，这是引用计数的暗成本。Rust 让你为此单独付费（`Rc` 对 `Arc`），Python 的 GIL 在很长时间里替所有对象包办了这件事。
