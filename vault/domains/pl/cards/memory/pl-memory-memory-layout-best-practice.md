## Q
为性能敏感的代码设计数据布局时，各语言的最佳实践是什么？

## A
通用思路：**让热数据连续、紧凑、按访问顺序排列**。CPU 的瓶颈经常是内存而不是算力，每次缓存未命中都是几十到上百 ns。

- **Go / Rust**：热路径优先 `[]T` / `Vec<T>`，避免 `[]*T` 和 `Vec<Box<T>>`，除非元素必须共享或很大。字段按从大到小排列，减少填充（Go 按声明顺序布局；Rust 默认会重排，但 `repr(C)` 不会）。需要时用 `unsafe.Sizeof`、`size_of` 检查大小。
- **结构数组（SoA）对数组结构（AoS）**：只用到少数字段的批量扫描（粒子系统、列式分析），把各字段分别存成数组，读取时每条缓存行都是有用数据。
- **伪共享**（false sharing）：两个线程写同一条缓存行的不同变量会互相拖慢，计数器之类用 64 字节对齐（Rust 的 `#[repr(align(64))]`，Java 的 JDK 内部注解 `@Contended`，需开启选项）隔开。
- **Java**：大量数值用基本类型数组，或第三方的原始类型集合；避免 `List<Integer>`、`Map<Long, ...>` 装箱；热点对象保持字段少。需要时升级 JDK 以获得紧凑对象头。
- **Python**：数值数据用 `array`、NumPy，把循环放进 C；类里用 `__slots__` 省去每实例字典。

为什么：布局决定缓存命中，算法复杂度相同的两段代码，常数可以差一个数量级。

什么时候违反：不是热点的代码。小数据量时布局差异被其他开销淹没，按可读性写即可；过早做 SoA 之类的转换会让代码难维护。先 profile，确认是内存受限，再动布局。
