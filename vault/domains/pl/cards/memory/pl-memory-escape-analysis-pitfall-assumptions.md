## Q
关于逃逸分析，哪些常见假设是错的？为什么「用指针更省」在 Go 里经常适得其反？

## A
**误区一：`&T{}` 一定在堆上，`T{}` 一定在栈上。** 都不对。Go 里哪里分配由是否逃逸决定，与写没写 `&` 无关。一个 `&T{}` 只在局部使用，仍然在栈上；一个值类型的 `T{}` 放进接口后，装箱的副本可能在堆上。

**误区二：传指针比传值快。** 对小结构体（几个字，比如 16 到 64 字节），传值复制几个寄存器，非常便宜；传指针则可能让原变量逃逸到堆，多了一次分配、多了 GC 扫描的工作，还多了间接寻址。

```go
func use(p *P) { global = p }   // stores the pointer: caller's p escapes
```

只要函数把参数指针存进了全局变量或返回，调用者的那个变量就必须搬到堆。

**误区三：看起来无害的写法不会逃逸。** 下面这些都会：
- 传给 `fmt.Println`、`log` 这类参数是 `any` 的函数（装箱）。
- 闭包捕获并被返回，或被 `go` 语句使用。
- `append` 到全局或逃逸的 slice。

**Java 一侧的误区**：以为所有小对象都被「优化掉」了。逃逸分析依赖内联，一旦对象被存进字段、放入 `List`、或传入没有被内联的方法，它就是真的堆对象，且仍然带 12 字节左右的对象头。

验证习惯：不要凭直觉，Go 用 `-gcflags=-m` 和基准里的 `allocs/op`；Java 用 JMH 加 `-Xlog:gc` 或 JFR 的分配事件。
