## Q
「遍历时修改集合」这类别名加修改的问题，Go、Java、Rust、Python 各选了什么处理点？换来什么，代价是什么？

## A
| 语言 | 选择 | 换来 | 代价 |
|---|---|---|---|
| Go | 不管，并发写 map 才会运行期 fatal，竞争靠 `-race` 工具 | 语言最简单，没有额外规则 | 这类 bug 只有运行时、有时甚至上线后才暴露 |
| Java | 集合记 `modCount`，迭代器检查，抛 `ConcurrentModificationException` | 常见错误能快速失败（fail-fast） | 尽力而为，不保证；并发场景要自己加锁或用并发集合 |
| Rust | 借用检查：`&` 与 `&mut` 不能共存，编译期拒绝 | 迭代器失效、悬空引用、数据竞争一并消除，零运行时成本 | 学习曲线陡，保守检查会拒绝一些其实安全的写法 |
| Python | 字典、集合检查大小变化，抛 `RuntimeError` | 常见错误有提示 | 列表等不报错；线程安全靠约定 |

逻辑：这是一个「何时发现错误」的光谱：不发现（Go）、运行时尽力发现（Java、Python）、编译期保证（Rust）。越往后越早，也越贵。Rust 的哲学是 bug 的成本随发现得越晚而上升，因此愿意让程序员在写代码时多花力气，换取上线后不再出现这一整类问题；Java、Python、Go 的哲学是让程序先跑起来，用测试、工具和约定兜底。

选择的依据是系统的容错成本：长期运行的基础设施、并发密集的代码，早发现的价值很高；快速迭代的业务脚本，则未必值得。
