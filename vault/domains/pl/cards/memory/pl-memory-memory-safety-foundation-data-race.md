## Q
数据竞争（data race）是什么？GIL 和 Go 的 `-race` 工具在这里各起什么作用？

## A
**数据竞争**：两个线程同时访问同一块内存，其中至少一个在写，并且没有同步（锁、原子操作等）。典型例子是两个线程各执行一千次 `n++`：`n++` 实际是“读、加、写”三步，两个线程的步骤交错时会丢失更新，结果小于 2000。更糟的是对多个字组成的值（slice 的指针与长度、接口值）并发写入，读者可能读到“一半旧一半新”的撕裂值，指针和长度对不上，造成真正的内存破坏。

各语言的处境：
- **Java**：内存模型保证有竞争时读到的也是某次真实写入的值，不会损坏 JVM，但程序逻辑仍然会错。
- **Go**：没有编译期保护。`go run -race` 或 `go test -race` 启用**竞争检测器**，运行时记录每次内存访问，发现无同步关系的并发读写就报 `WARNING: DATA RACE` 并给出两处调用栈；有 2 到 20 倍的运行开销，只发现实际执行到的路径，用在测试与 CI。
- **Python（CPython）**：默认构建里有 **GIL**（全局解释器锁，global interpreter lock）：同一时刻只有一个线程在执行 Python 字节码，所以解释器自身的数据结构不会被并发破坏；但 `n += 1` 仍可能在字节码之间被切换，业务逻辑上的竞争照样存在。
- **C++**：数据竞争是未定义行为（不是读到旧值那么温和，编译器可以假设它不存在），没有编译期或运行期的默认保护；用 `std::mutex`、`std::atomic` 同步，用 ThreadSanitizer（`-fsanitize=thread`，运行时竞争检测器）在测试里找。
- **Rust**：借用规则加 `Send`/`Sync` 标记，在编译期直接拒绝。

要记住的一个事实：GC 解决了“释放后使用”，但没有解决并发读写；多线程共享可变数据是需要另外回答的安全问题。
