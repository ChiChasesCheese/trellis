## Q
悬空引用（dangling reference）是什么问题？生命周期（lifetime）是为了解决它而设计的什么概念？

## A
引用只是一个地址。如果它指向的值已经被销毁，这个地址就成了悬空引用，读它得到垃圾，写它破坏别人的内存。最典型的写法是返回局部变量的地址：函数返回时栈帧被回收，地址还在，但里面的东西已经没了。

语言有四种应对：
1. **不管**（C）：靠程序员小心，错了是未定义行为。
2. **让值活到最后一个引用消失**（Java、Go、Python）：值放在堆上，由 GC 或引用计数保活，只要还有引用，值就不会被回收。引用永远不会悬空，代价是所有值都进入托管堆（或者靠逃逸分析自动提升）。
3. **只允许值语义，不给引用**：到处复制，安全但慢。
4. **编译期证明引用不会比值活得更久**（Rust）：不需要 GC，也不放弃引用。

生命周期就是第四种做法的核心概念：一个引用有效的程序区间。编译器要求每个引用的生命周期被其指向值的生命周期完全包住：值必须比引用「活得更长」。

对比第二种做法可以看出本质：GC 语言在运行时延长值的寿命来保证引用有效，Rust 在编译期检查寿命的包含关系，不满足就拒绝编译。多数时候这些生命周期是编译器自己推出来的，只有函数签名里出现多个引用、返回值借用其中之一时，才需要程序员写出标注。
