## Q
Go、Java、Rust、Python 在「值放栈还是放堆」上各自做了什么选择？换来什么，又付出什么代价？

## A
| 语言 | 选择 | 换来 | 代价 |
|---|---|---|---|
| Go | 语法不区分，编译器用逃逸分析（escape analysis）决定 | 写法简单，小对象多数在栈上 | 去向要靠 `-gcflags=-m` 才看得见，一个改动可能让变量悄悄进堆 |
| Java | 语言规定：对象在堆，局部变量与引用在栈 | 心智模型最简单，GC 统一管理 | 小对象也要分配、带对象头；靠 JIT 优化补救，无保证 |
| Rust | 默认栈，要堆就显式写 `Box`、`Vec` | 成本在代码里可见，无运行时开销 | 程序员要自己决定，大数组放栈会溢出 |
| Python | 所有对象都在堆（CPython） | 语义统一，动态特性容易实现 | 每个整数都是约 28 字节的对象，没有补救 |

背后的逻辑是各语言对「谁来为性能负责」的回答不同。Rust 的哲学是成本透明，把决定权给程序员；Java 和 Python 的哲学是让程序员别操心，把成本转给运行时和 GC；Go 取中间：既不想让程序员写栈堆标注，又不想把一切放堆，于是让编译器做一次保守的分析，代价是性能模型变得「隐式」，需要工具才能看清。

可以用一个判断标准概括：栈分配的成本接近零，所以所有语言的优化方向都是「让更多值留在栈上」。区别只是由谁来争取：Rust 靠人，Go 靠编译器，Java 靠 JIT，Python 基本放弃。
