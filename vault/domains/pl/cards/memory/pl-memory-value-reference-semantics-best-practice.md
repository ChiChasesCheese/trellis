## Q
面对别名（多个名字指向同一个可变对象）的风险，C++、Go、Java、Rust、Python 里有经验的工程师分别怎么做？

## A
共同思想：**可变性与共享不要同时出现**。对象要么不可变，要么只有一个明确的所有者。

- **Java**：能用不可变就用不可变（`record`、`String`、`List.of`），不可变对象可以随意共享，无需防御性拷贝。必须暴露内部集合时，返回只读视图（`Collections.unmodifiableList`）或拷贝，而不是原集合。类里不要把传入的可变参数直接存起来，先拷贝。
- **Go**：同一个类型的方法接收者保持一致，要么全用值，要么全用指针。需要修改或结构体较大才用指针。`slice` 要把底层数组所有权想清楚：返回内部切片前 `copy`，或用三下标切片限制容量，防止调用方的 `append` 覆盖你的数据。
- **C++**：默认值语义，不需要共享时不要用指针和引用成员；需要修改传入对象才传 `T&`，只读大对象传 `const T&`；长寿命对象里不要存引用成员或裸指针（对象销毁后悬空）；类内部有 `const` 方法就保证不修改，让编译器替你检查。
- **Rust**：能借用就借用，不要为了绕过借用检查器而习惯性 `.clone()`；`clone` 应当是有意为之的「我愿意为此付复制的成本」。
- **Python**：不用可变对象做默认参数；不可变数据用 `tuple`、`frozenset`、`@dataclass(frozen=True)`；嵌套结构的拷贝要想清楚是浅拷贝还是 `deepcopy`。

为什么：别名的 bug 最难排查，因为修改与症状在代码上相隔很远。不可变性把这类问题从「运行时行为」变成「结构保证」，是成本最低的防线。

什么时候违反：热路径上，复制成本大于风险（大缓冲区）；这时靠清晰的所有权约定和文档替代类型保证。
