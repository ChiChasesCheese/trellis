## Q
边界检查和「安全代码与 unsafe 代码的分界」在底层是怎么实现内存安全的？

## A
**边界检查**：数组或 slice 在运行时带着长度。每次 `v[i]` 编译成「比较 `i` 与长度；若 `i >= len` 就跳到 panic/异常路径；否则按地址读取」。只多一次比较和一个几乎总是预测正确的分支，现代 CPU 上成本很小。编译器常常能证明下标一定在范围内（例如 `for i in 0..v.len()`），把检查直接删掉。越界时转到的是语言定义好的错误（panic、异常），而不是读到旁边的内存。

**安全与 unsafe 的分界**：安全语言在语言层面禁止直接操作原始地址，所以越界、悬空只能通过「检查」或「类型规则」挡住。但总要有人去做实际的内存操作，比如标准库里 `Vec` 的底层缓冲区管理、调用操作系统、与 C 交互。这些底层部分必须能做不安全的事，于是语言提供受控的逃生口：
- Rust：`unsafe` 块，里面可以解引用裸指针、调用 `unsafe` 函数，等等。
- Go：`unsafe` 包，提供 `unsafe.Pointer`，可绕过类型系统。
- Java：`sun.misc.Unsafe`、JNI（Java 本地接口）、FFM API。
- Python：`ctypes`、C 扩展。

设计原则是**缩小信任的范围**：不是整个程序都要审查，只需要审查那几处 `unsafe`，并保证它们对外暴露的接口是安全的（safe abstraction）。例如 `Vec::push` 内部有 `unsafe`，但对外只暴露安全函数，调用者无法用它触发未定义行为。

所以，「内存安全语言」的准确含义是：只用语言的安全部分写的代码，保证不出现内存安全错误；不安全的代码要自己负责。
