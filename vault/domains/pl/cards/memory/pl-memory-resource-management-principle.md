## Q
文件、锁、数据库连接这类非内存资源（non-memory resource）为什么不能像内存一样交给垃圾回收？语言有哪几种解法？

## A
内存和这类资源在三点上不同：
1. **稀缺且有硬上限**：进程的文件描述符常常只有几千个，连接池只有几十个。内存多一点无所谓，句柄漏光服务就停了。
2. **释放有语义**：关闭文件会把缓冲区刷盘，释放锁会唤醒别的线程，提交事务会让数据可见。晚释放不是「浪费」，而是行为错误。
3. **释放可能失败**：`close` 可能报 I/O 错误，而内存的释放不会。

GC 恰好在这三点上都帮不上忙：它只在内存紧张时才运行，时机不确定，甚至可能一直不运行；一个文件对象占几十字节，堆里很空闲，GC 没有动力去回收它，而文件描述符早就耗尽了。

所以资源管理需要确定的释放时机，设计空间有四种：
1. **手动成对调用**（`open`/`close`，配 `try/finally`）：灵活，最容易漏。
2. **作用域语法**（Java 的 try-with-resources、Python 的 `with`、Go 的 `defer`、C# 的 `using`）：语言保证离开作用域时执行清理，但调用者必须记得使用。
3. **析构绑定到对象生命周期**（C++ 与 Rust 的 RAII）：类型自带清理，调用者无法忘记。
4. **终结器（finalizer）**：对象被 GC 回收时回调。时机不确定，只能当作最后的保险，不能当作机制。

轴线是「谁来保证不忘记」：程序员（1）、调用者的纪律（2）、类型系统（3）。
