## Q
Go 和 Java 的逃逸分析在设计哲学上有什么对比？为什么 Go 里「减少逃逸」成了常规调优手段？

## A
两者的差别是：Go 把逃逸分析当成语言实现的一部分，结果稳定可查；Java 当成可有可无的 JIT 优化。

**Go**
- 分析发生在编译期，同一份代码、同一版编译器，结果总是一样，可以写测试断言 `allocs/op == 0`。
- Go 编程里大量使用结构体值而不是指针，天然更容易不逃逸。
- 因为 Go 的 GC 不分代、不移动，堆分配的相对代价更高（每个对象都要被标记扫描），所以少分配几乎是最有效的性能手段。
- 工作流：跑基准看 `allocs/op`，用 `-gcflags=-m` 找出是哪一行导致逃逸，改写。

**Java**
- JIT 在运行时才分析，要先热身；方法内联深度、字节码大小都会影响结果。
- 因为 JVM 的年轻代分配极便宜（指针碰撞），年轻代回收也便宜，所以即使逃逸分析失败，代价也相对可控；调优的重点通常转向选择 GC，而不是逐行消除分配。
- 没有稳定的方式向开发者保证「这个对象不会分配」。

一个 Go 里典型的「减少逃逸」例子是闭包：

```go
func counter() func() int {
	n := 0
	return func() int { n++; return n }
}
```

编译器输出 `moved to heap: n`。`n` 被返回的闭包捕获，必须活得比 `counter` 更久，所以搬到堆上。一旦知道原因，就能决定这个分配是不是值得保留。
