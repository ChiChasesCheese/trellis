## Q
与借用检查器合作的最佳实践是什么？其他语言的工程师能从所有权思想里借用什么？

## A
**Rust 里**
1. **参数借用，返回拥有**：函数参数优先 `&T` / `&mut T`，调用者保留所有权；返回值通常返回拥有的类型，把生命周期复杂度挡在 API 之外。
2. **遇到借用冲突，先改数据流，不要先 `clone`**。常见出路：缩短借用范围；把需要的小值复制出来；用索引代替引用；把一个大结构体拆成互不重叠的字段，分开借用；用 `split_at_mut` 这类已验证的 API。
3. **`Rc<RefCell<T>>` 和 `unsafe` 是最后手段**：它们把检查推迟到运行期或交给你自己。
4. **小而专一的所有者**：每块数据有一个明确的拥有者类型，其他部分只借用。这和好的架构设计是一回事。
5. 把「谁拥有它」写进类型：`Vec<T>` 拥有，`&[T]` 借用，`Arc<T>` 共享。

**在 Java、Go、Python 里借用这套思想**
- 每个可变对象指定一个所有者，其他代码只拿只读视图或拷贝。
- 并发代码里，用「所有权转移」代替「共享加锁」：Go 的口号「通过通信共享内存，而不是通过共享内存通信」正是此意，把数据通过 channel 交给下一个所有者。
- 构造后不再改变的对象，在 Java 里写成 `record`，在 Python 里用 frozen dataclass。

为什么：别名加修改是几乎所有内存与并发 bug 的共同根源，规则是语言强制还是团队约定，思路一致。

什么时候违反：性能关键处的内部可变性（缓存、引用计数的内部计数器）、与 C 交互的边界。
