## Q
注解（annotation）和装饰器（decorator）要解决什么问题？有哪几种设计，区别在「描述」还是「执行」？

## A
**问题**：很多需求是横切的（cross-cutting）：这个方法要加事务、要缓存、要鉴权、要计时；这个字段在 JSON 里叫另一个名字。如果每处都手写样板，业务代码被淹没；如果完全交给外部配置文件，配置和代码对不上又很难发现。需要一种办法在代码旁边贴一个标记，让别的程序按标记行动。

**设计空间**：
1. **声明式元数据**：只是贴标签，标签本身不做事，由另一个程序（框架、编译器插件、序列化库）读取后行动。Java 注解、Go 的 struct tag、Rust 的属性（attribute）。
2. **包装式装饰器**：`@d` 是一次真正的函数调用，把原函数交给 `d`，用返回值替换它。Python 装饰器。
3. **不用标记，显式组合**：自己用函数把行为包起来，比如 Go 的 HTTP 中间件 `handler = auth(log(h))`。

**取舍轴**：声明式简洁，但「谁来读这个标签、在什么时候」是隐式的，行为发生在别处；包装式让行为在定义点可见，但需要语言支持把函数当值。越声明式，越依赖框架约定和工具；越显式，越啰嗦但越好追踪。
