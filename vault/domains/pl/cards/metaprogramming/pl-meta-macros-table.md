## Q
比较 Go、Java、Rust、Python、C++ 对宏的态度：各自用什么替代，买到什么，付出什么？

## A
| 语言 | 选择 | 买到 | 付出 |
|---|---|---|---|
| Go | 没有宏；靠泛型（Go 1.18）、接口和 `go generate` | 所有人写出的代码形状相同，工具容易解析 | 样板代码多，要靠外部生成器 |
| Java | 没有宏；靠注解加注解处理器，Lombok 之类靠内部 API 改写语法树 | 语法由语言团队统一把关 | 样板靠框架黑魔法消除，升级 JDK 时常出兼容问题 |
| Rust | `macro_rules!` 加过程宏，`derive` 是日常 | 库作者能发明 DSL，消除样板且零运行时开销 | 编译慢，展开后的错误难读，IDE 理解困难 |
| Python | 没有宏；靠装饰器、元类、运行时 `ast` 和 `exec` | 想改行为在运行时随时可以 | 灵活性发生在运行期，不是语法层面 |
| C++ | 继承 C 的预处理器（文本宏），再加模板、`constexpr` 与概念（concept，对模板参数的约束） | 宏能做条件编译和跨平台；模板与 `constexpr` 在编译期运行真正的 C++ 代码，类型安全、零运行时代价 | 文本宏不懂语法，有优先级和重复求值的坑；模板元编程的错误信息难读，编译慢 |

**逻辑**：Go 和 Java 都把「语法归语言团队所有」当作可维护性的基石，十年后读别人的代码仍然是同一门语言。Python 不需要宏，因为函数和类本身在运行时就是可改写的对象，宏要解决的大部分问题已被运行时动态性解决。Rust 是唯一有语法树级宏的一方，原因是它既要零成本抽象（不能用运行时反射），又要有表达力（serde、async 运行时的入口宏），宏就成了同时满足两者的出口。

C++ 同样要零成本抽象，走的是更早的两条路：沿用 C 的文本宏，再用模板和 `constexpr` 在语言内部做编译期计算。它的现代做法是把宏退守到条件编译和 `#include`，其余都交给模板、`constexpr` 函数和概念：C 兼容让它丢不掉预处理器，零开销原则让它不愿用运行时机制替代宏。Rust 的宏可以看作对这两样东西的重做：有语法意识、有卫生、不依赖模板的图灵完备性。
