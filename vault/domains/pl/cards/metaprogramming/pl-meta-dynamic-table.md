## Q
Go、Java、Rust、C++ 为什么给不出 Python 这样的运行时动态能力？各自能做到什么程度的「运行时改写行为」？

## A
| 语言 | 运行时能改什么 | 机制 | 限制 |
|---|---|---|---|
| Go | 几乎不能；只能经 `reflect` 读写值 | 接口值、`plugin` 包（很少用） | 类型和方法集在编译期固定 |
| Java | 能生成新类、替换类、包装对象 | 动态代理、类加载器、`java.lang.instrument` 代理 | 要通过字节码层面；JDK 内部受强封装保护 |
| Rust | 不能；只有 `dyn Trait` 的动态分派 | trait 对象 | 所有类型在编译期确定，没有运行时改写 |
| Python | 几乎一切：属性、方法、类、模块都可替换 | 数据模型协议、`__dict__`、`exec` | 全靠约定，无强制边界 |
| C++ | 几乎不能；只有虚函数分派、`dynamic_cast`（运行期向下转换）、`dlopen` 加载共享库 | 虚表、RTTI（运行期类型信息，只回答“这是什么类型”）、动态链接器 | 类型和对象布局编译期固定，不能增删成员，没有标准的运行期反射 |

**逻辑**：这是语言「编译期还是运行期决定对象形状」的直接后果。Python 的对象是字典，改字典就是改对象，不需要额外设计。Java 的对象有固定布局，但 JVM 本身设计成字节码解释器，类可以在运行时加载和转换，所以动态能力存在，只是在字节码一层：Spring 用 CGLIB 动态生成子类、Mockito 在运行时生成假对象。Go 与 Rust 把类型布局固定在编译产物里，要动态就必须显式用接口（Go）、`dyn Trait`（Rust）或虚函数（C++），表达的是「这里有一个我允许变化的点」，而不是「一切皆可变」。

**对应的工程后果**：Python 做原型和胶水快，大型代码库需要靠类型注解和测试补上约束；Go 与 Rust 灵活性受限，但读代码时形状可信。
