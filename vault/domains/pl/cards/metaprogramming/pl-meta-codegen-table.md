## Q
比较 Go、Java、Rust、Python、C++ 的代码生成路线：各选了设计空间的哪一点，买到什么，付出什么？

## A
| 语言 | 选择 | 买到 | 付出 |
|---|---|---|---|
| Go | 显式外部生成器，产物提交入库 | 产物可读可 diff，无构建魔法，IDE 完全理解 | 要手动运行，容易过期，样板进仓库 |
| Java | 注解处理器自动运行，产物在构建目录；运行时另有字节码库 | 对开发者透明，Dagger 之类零运行时反射 | 只能新增不能改已有类；增量编译和 IDE 配置易出问题 |
| Rust | `build.rs` 加过程宏，全在构建期 | 零运行时代价，类型检查覆盖生成物 | 编译变慢，宏难调试，生成物不可见 |
| Python | 运行时生成（`dataclass`、元类） | 无需外部步骤，改一行即生效 | 导入变慢，调试时看到 `<string>`，静态工具看不懂 |
| C++ | 语言内：模板实例化与 `constexpr` 在编译期生成代码和数据；语言外：`protoc`（protobuf 编译器）、Qt 的 `moc`（元对象编译器）等外部生成器，由 CMake 等构建系统驱动 | 模板生成的代码零运行时代价，类型检查覆盖生成物；外部生成器的产物可读 | 模板错误信息难读，编译慢；外部生成器要接进构建系统，产物过期的风险与 Go 相同 |

**逻辑**：Go 的语言哲学是「程序的全部行为应该能在源码里读到」，生成物提交入库正是这个信条：魔法也必须落成可读文件。Java 的哲学是工具与框架承担复杂度，处理器和字节码库放在后台工作，开发者只写注解。Rust 的哲学是编译期做完一切，所以生成既自动又在构建内。Python 的哲学是动态，生成发生在运行时顺理成章。C++ 的哲学是“让语言本身够强，少用外部工具”：模板和 `constexpr` 就是语言内部的代码生成器，不需要第二套工具，代价是生成物（实例化后的代码）不可见，只能看汇编或编译器的展开输出。零开销原则要求这些生成全部在编译期完成；C 兼容则保留了预处理器和外部生成器这条老路。五条路线其实是同一个问题（谁看得见生成物）的五种答案。
