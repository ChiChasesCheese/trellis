## Q
比较 Go、Java、Rust、Python、C++ 的「给代码贴标记」机制：各选了什么点，买到什么，付出什么？

## A
| 语言 | 选择 | 买到 | 付出 |
|---|---|---|---|
| Go | struct tag：一个无类型字符串，运行时反射解析 | 极简，标准库 `json`/`db` 都用同一个约定 | 写错不报错，只在运行时悄悄失效 |
| Java | 有类型的注解，可在编译期或运行期处理 | 类型检查标签参数；框架生态（Spring、JPA、JUnit）围绕它建立 | 行为藏在框架里，调用链难追，代理有边界情况 |
| Rust | 属性加过程宏，编译期展开 | 零运行时代价，错误是编译错误 | 宏的编译时间与可读性成本 |
| Python | 装饰器就是普通函数调用 | 行为在定义处可见，可调试，可组合 | 会丢函数元数据；叠加顺序容易搞反 |
| C++ | 属性（attribute）`[[nodiscard]]`、`[[deprecated]]` 等，标准规定的一小组，由编译器解释；不能自定义标签 | 零运行时代价；返回值被忽略等错误成为编译警告；拼错的属性会被报警 | 没有框架生态：不存在“贴标签、让容器按标签行动”这套做法，只能靠模板、宏或外部生成器 |

**逻辑**：Java 的 EE 传统是「应用只写业务，容器负责横切逻辑」，所以注解必须是纯声明，由容器按标签行动。Go 想要最小机制，一个字符串加一个约定够用，不值得引入新语法。Rust 想让标签的处理保持零成本，只能放在编译期。Python 的函数是一等对象，装饰器根本不需要新机制，只是一个语法糖。C++ 的属性是另一个极端：标记只用来给编译器提示，不是给框架读的元数据。零开销原则让它没有运行时元数据可读，所以 Spring 式的“容器按标签装配”在 C++ 里不存在，依赖注入和序列化只能走模板、宏或编译期生成（C++26 的静态反射会改变这一点）。
