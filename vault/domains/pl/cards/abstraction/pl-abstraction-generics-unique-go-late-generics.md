## Q
Go 为什么拖了十多年才加泛型？Go 泛型的最小设计和 1.27 加入的泛型方法反映了什么价值观？

## A
Go 1.0 在 2012 年发布，泛型到 1.18（2022）才有。设计者的立场是：泛型有三种已知代价——**编译慢**（C++ 模板）、**运行慢**（Java 的装箱）、**复杂**（类型系统变难学）；在没有找到一个让三者都可接受的方案前，宁可不加。社区用 `interface{}` 加类型断言、代码生成来凑合十年，换来的是语言简单和快速编译。

最后的方案体现取舍：

- **约束就是接口**：不新增概念，复用已有的接口机制。
- **只在函数与类型上有类型参数**：保守起步。1.27 才允许**泛型方法**（方法自己带类型参数，如 `func (b Box[T]) Map[U any](f func(T) U) Box[U]`）。这也有限制：接口里的方法**不能**声明类型参数，所以带泛型方法的类型无法满足一个同名的非泛型接口方法，编译报 `wrong type for method Map`。
- **实现用折中办法**：既不完全单态化，也不完全擦除（详见泛型实现一节），为了保持编译速度。

Rust 的立场是相反的：泛型是核心，复杂性可以接受，因为换来的是零成本抽象；Java 的立场是向后兼容优先。Go 的立场则是「先观察真实需求再扩展」，晚加、少加、逐步放宽。这种保守让 Go 的代码库风格极其一致，也让一部分抽象写起来不如 Rust 或 Java 优雅。
