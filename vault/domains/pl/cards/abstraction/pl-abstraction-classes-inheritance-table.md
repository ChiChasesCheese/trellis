## Q
C++、Go、Java、Rust、Python 对「实现继承」各做了什么选择？各自换来什么、失去什么？

## A
| 语言 | 选择 | 买到 | 付出 |
|---|---|---|---|
| C++ | 多继承；成员函数默认非虚，要多态必须写 `virtual`；菱形要显式用虚继承 | 零开销（不用虚函数就没有虚表）；按需选择多继承 | 忘写 `virtual` 就静态绑定，基类析构函数非虚时通过基类指针 `delete` 是未定义行为；按值传基类参数会「切片」（丢掉派生部分）；虚继承的内存布局复杂 |
| Go | 没有继承，用结构体嵌入 | 依赖显式，没有脆弱基类 | 想要「重写父类钩子」的模板方法很别扭 |
| Java | 单继承 + 多接口 | 层级简单，虚表简单，无菱形 | 层级易被滥用，接口里带实现的 `default` 方法又把多继承带回一部分 |
| Rust | 没有继承，trait 的默认方法 | 行为复用与类型层级彻底分离 | 要共享数据字段必须自己组合 |
| Python | 多继承 + C3 MRO | 最大灵活度，混入写起来最轻 | 调用顺序隐式，`super()` 的含义依赖实例的类 |

规律：越晚设计的语言越不愿意提供实现继承。原因是实践中得到的教训越来越一致：继承的两个收益（复用、可替换）各有更便宜的替代品（组合、接口），而它的代价（父类内部细节泄漏给子类、层级不可逆）无法被替代。

C++ 是这条线的起点：继承来自 Simula，C++ 保留了全部能力（包括多继承），但按零开销原则（不用的功能不付钱）把一切代价都变成「你写了才付」，所以继承在 C++ 里默认不多态、不虚。它把 Java 里被语言禁止的选项变成了程序员要自己负责的选项。Go 和 Rust 是在 Java 之后设计的，它们选择把两件事分开，不让两者再绑定；Python 起步于 1990 年代初，沿用了当时通行的「类就是一切」的思路，并用 MRO 把多继承的混乱控制住；Java 则出于对 C++ 多继承的反思，只留单继承，用接口补足。
