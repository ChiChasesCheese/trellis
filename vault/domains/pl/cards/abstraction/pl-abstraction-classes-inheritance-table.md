## Q
Go、Java、Rust、Python 对「实现继承」各做了什么选择？各自换来什么、失去什么？

## A
| 语言 | 选择 | 买到 | 付出 |
|---|---|---|---|
| Go | 没有继承，用结构体嵌入 | 依赖显式，没有脆弱基类 | 想要「重写父类钩子」的模板方法很别扭 |
| Java | 单继承 + 多接口 | 层级简单，虚表简单，无菱形 | 层级易被滥用，接口里带实现的 `default` 方法又把多继承带回一部分 |
| Rust | 没有继承，trait 的默认方法 | 行为复用与类型层级彻底分离 | 要共享数据字段必须自己组合 |
| Python | 多继承 + C3 MRO | 最大灵活度，混入写起来最轻 | 调用顺序隐式，`super()` 的含义依赖实例的类 |

规律：越晚设计的语言越不愿意提供实现继承。原因是实践中得到的教训越来越一致：继承的两个收益（复用、可替换）各有更便宜的替代品（组合、接口），而它的代价（父类内部细节泄漏给子类、层级不可逆）无法被替代。

Go 和 Rust 是在 Java 之后设计的，它们选择把两件事分开，不让两者再绑定；Python 起步于 1990 年代初，沿用了当时通行的「类就是一切」的思路，并用 MRO 把多继承的混乱控制住；Java 则出于对 C++ 多继承的反思，只留单继承，用接口补足。
