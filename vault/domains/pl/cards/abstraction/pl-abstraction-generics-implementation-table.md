## Q
C++、Go、Java、Rust、Python 的泛型实现策略各是什么？分别在体积、速度、运行期信息上付出什么？

## A
| 语言 | 实现 | 速度 | 体积与编译 | 运行期类型信息 |
|---|---|---|---|---|
| C++ | 模板实例化（单态化），每个类型参数组合生成一份 | 最快，可内联，值类型无装箱 | 最大，编译最慢（头文件里反复实例化） | 无，类型在编译后消失 |
| Go | GC shape 分组 + 字典 | 值类型专用，指针类型间接 | 中等 | 有字典，但不暴露类型实参 |
| Java | 擦除 | 基本类型要装箱 | 最小 | 无，`List<String>` 就是 `List` |
| Rust | 单态化 | 最快，可内联 | 最大，编译慢 | 无，也不需要 |
| Python | 无（动态类型） | 无泛型成本 | 无 | 仅检查器可见 |

规律：**越晚决定、越保守的语言越倾向共享代码**。Java 为兼容旧库选择擦除；Go 为编译速度和体积折中；Rust 把性能放第一，用编译时间和体积买单；Python 根本没有这个问题，因为动态类型的值本来就都是对象引用。

C++ 和 Rust 在这一栏是同一个答案，C++ 是原版：它的零开销原则（用到的抽象，手写也不会更快）正是靠为每个实例生成专用代码做到的，代价记在编译时间和二进制体积上，且默认没有缓解：实例化发生在每个用到它的源文件里（链接器再去重），要减少重复得自己做显式实例化。背后的哲学：Rust 说「抽象不应该有运行期代价」，所以愿意让编译器多干活；Java 说「一个二进制要能跑二十年」，所以保持一份代码、一份类型信息；Go 说「编译要快、二进制要小、代码要可预测」，所以在两者之间画了一条务实的线。三种选择都不是技术上的唯一答案，而是各自目标函数的最优解。
