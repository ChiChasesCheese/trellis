## Q
为什么说 Go 的嵌入「故意」放弃了虚方法回调？这个设计反映了 Go 的什么价值观？

## A
Go 的设计者在语言诞生时就面对着 C++ 与 Java 的经验：深层继承和虚方法回调带来了难以推理的行为。一个方法被覆写，会影响所有在父类里调用它的路径，阅读 `Base.Greet` 的人无法知道它会调到哪里。

Go 的回答是让被嵌入类型的方法**永远只看到自己**。这有三个后果，都符合 Go 的价值观：

- **局部可推理**：读 `Base.Greet` 的代码，就能确定它调用的 `Name()` 是 `Base.Name`。任何位置的覆盖都不会改变它。
- **数据与行为不混层级**：想要多态就显式用接口，想要复用就显式嵌入，不能同时靠一个机制办到。
- **鼓励小而明确的构件**：想让父级流程中的某一步可替换，必须把那一步作为函数值或接口参数传入，调用关系可以在签名里看见。

代价同样明确：不能写框架式的模板方法；嵌入把内层所有公开方法暴露给外层的使用者，造成接口过宽；多层嵌入时「这个方法到底来自哪一层」要靠阅读才能确认。Go 接受这些代价，因为它优化的是**数百人团队长期阅读和维护代码**，而不是写代码时的便利。

对比 C++：它也有同样的二选一，非虚函数不回调，`virtual` 函数回调，但默认值与 Java 相反（默认不回调），由程序员逐个函数决定；Go 则把整个选项拿掉了。对比 Java：同一个需求在 Java 里是语言内置的能力（覆写），在 Go 里要用接口或函数参数写成显式的。能力少一点，但每一步是看得见的。
