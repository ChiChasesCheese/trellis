## Q
Go、Java、Rust、Python 的封装边界各画在哪里？这反映了什么样的信任模型？

## A
| 语言 | 边界单位 | 默认可见性 | 信任模型 |
|---|---|---|---|
| Go | 包；大小写决定导出 | 小写（包内） | 包内互相信任，包外靠 API |
| Java | 类；包；模块 | 包私有 | 逐层收紧，类内最严 |
| Rust | 模块；`pub(crate)` 等 | 私有（含子模块） | 精细授权，谁能看都要写明 |
| Python | 无强制 | 全部公开 | 信任开发者，约定为主 |

规律：边界单位越大（Go 的包），规则越少，写起来越轻；边界单位越小（Java 的类），保护越细，但需要更多修饰符。

Go 的包级信任来自「小团队、清楚的包边界」这一假设：一个包就是一个人或一个小组维护的整体。Java 来自「大团队、多个来源的代码、框架深度介入」的企业环境，需要多级访问权限，模块系统则回应了 JDK 与第三方库共存的问题。Rust 是系统编程语言，出于安全和接口稳定的考虑，要求每个可见性都有明确意图，默认关闭。Python 为小规模、快速迭代、探索性的使用场景设计，强制反而成为阻碍。

没有一种比另一种更「正确」；是语言预设的工程规模和协作方式决定了它们的封装哲学。
