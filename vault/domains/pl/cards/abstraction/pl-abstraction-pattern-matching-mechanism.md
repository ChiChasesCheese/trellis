## Q
模式匹配在编译器里是怎么实现的？穷尽检查为什么需要「封闭的类型集合」？

## A
**实现**：编译器把一组模式编译成**决策树**（decision tree）或一串优化过的跳转。例如先读 enum 的标签字节，用跳转表直接跳到对应的分支；嵌套模式再对子字段继续判断。这比手写的 `if/else` 链少做重复测试，也不会因为写错顺序而重复判断。Rust 的枚举有显式标签，`match` 编译后就是一次标签比较加解构，几乎没有额外开销。

Java 的 `switch` 模式用 `invokedynamic` 在首次执行时生成匹配逻辑（`typeSwitch` 引导方法），分支多时按需优化。Python 则是逐个 `case` 顺序尝试，每个 `case` 是若干类型检查和属性读取，没有决策树优化。

**穷尽检查**是一个集合运算：全部可能的值减去各分支覆盖的值，结果为空才通过。它需要两个前提：

1. **值的集合是有限且已知的**。`enum`、`sealed` 满足；普通接口和开放的类不满足。
2. **模式可以被代数化**：编译器知道一个模式覆盖哪些值。守卫 `if x < 0` 里的任意表达式编译器无法推理，所以带守卫的分支被当作「可能不匹配」，不计入覆盖。

穷尽检查给出的真正价值在**演化期**：当你给 `enum` 增加一个变体，所有不带通配符的 `match` 都会编译失败，编译器列出每一个需要处理的位置。这比靠测试或代码审查可靠得多。这也是下一节最佳实践里「不要滥用通配符」的原因：通配符会让这条保险失效。
