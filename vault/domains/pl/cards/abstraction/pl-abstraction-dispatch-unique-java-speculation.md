## Q
HotSpot 的「推测性优化加去优化」和 Rust 的「编译期显式选择」是两种相反的哲学，各自怎样看待动态分派？

## A
**Rust 的立场：不要有意外**。泛型与 `dyn` 在源代码里就写明，性能特征由代码本身决定：看到 `dyn` 就知道这里有一次间接调用、不可内联；看到泛型就知道这里会生成专用代码。程序员为此付出的是表达上的负担（要选，要处理 `Box<dyn ...>` 的所有权，泛型会向外传染）。收益是**可预测**，且不依赖预热。

**HotSpot 的立场：写自然的代码，让运行时去赌**。JIT 观察到某调用点只有一个实现，就内联并加一个检查；赌输（出现了新类型）就丢掉编译结果，退回解释器重来，这叫去优化（deoptimization）。因为 JIT 有运行期真实数据，它能做静态编译器做不到的事，比如在从未出现第二个实现的接口上做激进内联。代价是**不可预测**：代码行为没变，仅因为输入里出现了新类型，同一行代码的耗时就可能跳变；启动期也慢。

两种立场对应两种世界：Rust 针对「开发者知道所有类型」的系统编程，Java 针对「类型分布随输入和时间变化」的长期运行服务。

对 Go 来说这个维度位于中间偏 Rust：没有运行期推测，编译期决定一切，但为了简单不让程序员选，接口调用就是动态的，只在编译器能证明目标时才去虚化。
