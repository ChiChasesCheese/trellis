## Q
资深工程师在各语言里什么时候写泛型，什么时候不写？

## A
通用判断：**当你发现同一段逻辑需要对多种类型重复，且逻辑不依赖类型的具体行为时，才写泛型**；不要为了「可能复用」而预先泛化。泛型会向外传染（调用方、测试、文档都要带上类型参数）。

- **Go**：Go 社区的经验法则是「先写具体类型，出现第二个使用者再抽象」。适合泛型的场景是容器（集合、缓存）、纯数据变换（`Map`/`Filter`/`Keys`）、对多种数字类型的同一算法；行为随类型变化的场景仍然用接口。
- **Java**：避免原始类型；API 参数用通配符提高灵活性（详见约束与型变一节）；不要把泛型类型暴露成数组（`T[]` 会出问题）。对性能敏感的数值代码，注意泛型意味着装箱。
- **C++**：模板参数一律用 concepts 约束（标准库已有 `std::integral`、`std::ranges::range` 等），让错误出现在调用处；模板实现放头文件，函数体越大越要考虑代码膨胀，把与类型无关的部分抽成普通函数；不要用模板元编程技巧解决一次性问题。
- **Rust**：函数参数用泛型约束，约束只写必需的 trait，写 `T: Display` 而不是 `T: Debug + Display + Clone` 的一大串；多个约束放 `where`。需要异构集合再转 `dyn`。
- **Python**：公共库的 API 用 `TypeVar` / `Protocol` 标注，让下游的检查器受益；应用代码不必处处泛型化，用具体类型。CI 里必须跑 `mypy` 或 `pyright`，否则注解只是装饰。

何时打破：写通用基础设施（缓存、连接池、序列化库）时，泛型的收益远大于传染成本；业务代码里通常不值得。
