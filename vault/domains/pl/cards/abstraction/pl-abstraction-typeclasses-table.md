## Q
Go、Java、Rust、Python 分别用什么机制表达「为类型追加能力」？它们在能否事后追加、谁来选实现、有无一致性保证上有什么不同？

## A
| 语言 | 机制 | 能给已有类型事后追加吗 | 实现怎么选 |
|---|---|---|---|
| Rust | trait 加独立的 `impl`，带孤儿规则 | 能（自己的 trait 给任何类型；别人的 trait 给自己的类型） | 编译期按类型，或 `dyn` 虚表 |
| Java | 接口，类声明时实现 | 不能；要靠适配器或传 `Comparator` | 运行时按对象的类 |
| Go | 结构化接口 | 间接：接口可由别人的类型满足，但不能给别人的类型加方法 | 运行时按动态类型的方法表 |
| Python | 鸭子类型、`Protocol`、`singledispatch`、`ABC.register` | 能，且发生在运行时 | 运行时按对象的类型 |

规律：**能力放在类型之外的语言，可以事后追加；代价是需要一致性规则。**

逻辑：

- **Rust** 要在没有运行时的前提下做零成本抽象，同时让库生态可以组合：不同库之间互不认识，却要能为彼此的类型建立关系。所以 trait 实例独立存在，用孤儿规则保证全局唯一，编译期选择实现。
- **Java** 的接口诞生于「类就是一切」的年代，能力属于类的定义。事后追加不被支持；Java 的补救是 `Comparator` 这类显式传递的策略对象，以及语言层面一再增加的默认方法。
- **Go** 的接口由消费方定义，减少了对事后追加的需求：定义接口的一方描述自己需要什么，任何碰巧有这些方法的类型都满足。真正缺失的是为标准类型加方法。
- **Python** 不需要静态一致性：一切在运行时解析，所以连 `int` 也能被事后注册到你的抽象基类里，代价是没有任何全局唯一性保证，两个库可以互相覆盖。

趋势：Go 1.18 的泛型约束（类型集合）、Python 的 `Protocol`、Java 接口的默认方法，都在向「按能力而不是按血缘描述类型」靠拢，这是类型类思想对主流语言的渗透。
