## Q
模式匹配（pattern matching）要解决什么问题？处理「几种形态之一」的数据时有哪几种办法，各自在什么轴上取舍？

## A
场景：一个值可能是几种形态之一（表达式树的节点是数字、加法或取负；命令是移动、说话或退出），代码要对每种形态做不同的事，并且取出其中的数据。

没有模式匹配时的办法：

1. **if/else + 类型判断 + 强转**：`if (e instanceof Add) { Add a = (Add) e; ... }`。冗长，且编译器不知道你是否漏了某个形态。
2. **多态方法**：把每种形态的行为写成子类的方法。加新形态容易，加新操作要改所有子类。
3. **访问者模式**（visitor）：把操作移到外面，加新操作容易，加新形态要改访问者。样板很多。
4. **模式匹配**：一个构造同时完成**判断形态、取出字段、绑定变量**，并且让编译器检查是否覆盖了所有形态（**穷尽检查**）。

模式匹配是「构造」的对偶：构造是把字段组装成值（`Add(a, b)`），模式是反过来把值拆回字段（`case Add(a, b)`）。

轴是**扩展方向**，即表达式问题（expression problem）：面向对象方便加新形态（新子类），不方便加新操作；模式匹配方便加新操作（新 `match` 函数），加新形态时需要改每一个 `match`——但穷尽检查把「要改的地方」全部指出来，使得这个缺点可控。它和代数数据类型（和类型）是天然一对：和类型提供「有限的几种形态」，模式匹配提供「按形态拆开」。
