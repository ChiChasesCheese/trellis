## Q
在支持运算符重载的语言里，资深工程师怎样判断一个运算符该不该重载？

## A
判断标准：**重载后的行为是否与读者对该符号的数学期望一致**。向量 `+`、矩阵 `@`、金额 `+`、时间差 `-` 都是读者期望的；`+` 用于「把元素追加进容器」、`<<` 用于写日志，就是在制造意外。

- **满足代数定律**：`a + b == b + a`，`(a + b) + c == a + (b + c)` 在领域上成立才重载 `+`；否则用方法名表达。字符串拼接是一个已有的例外，也因此常被批评。
- **成本与符号一致**：O(1) 的符号不要藏 O(n) 的复制。Rust 里为 `&T` 单独实现，就是让借用与移动的区别可见。
- **一致性规则**：重载 `==` 就要同时处理 `hash`（Python 里定义了 `__eq__` 而不定义 `__hash__`，类会变成不可哈希，见相等与哈希一节）；Rust 里 `PartialEq`、`Eq`、`Hash`、`Ord` 要互相一致。
- **不改变左操作数**：`a + b` 返回新值，不修改 `a`；需要原地修改用 `+=`（Python 的 `__iadd__`、Rust 的 `AddAssign`）。

C++ 的具体建议：只重载读者有数学期望的运算符；先写 `+=`（成员函数，原地修改），再用它实现 `+`（自由函数，按值取左操作数）；永远不要重载 `&&`、`||`、`,`（重载后它们变成普通函数，两边都先求值，短路和顺序保证都没了）；C++20 起用 `= default` 的 `operator==` 与 `operator<=>` 让编译器生成比较。
各语言的具体建议：Python 里遇到不认识的类型返回 `NotImplemented`，不要抛异常，让反射方法有机会接手；Rust 优先用 `derive_more` 之类的宏生成样板；Java 里需要领域数学时，写一个小的值类并提供有语义的方法名（`plus`、`times`）；Go 同理，必要时用具名方法和小型表达式构造器。何时打破：几乎不应该——重载在领域外的创意用法是最常见的悔恨来源。
