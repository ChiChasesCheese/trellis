## Q
Go、Java、Rust、Python 在接口 / trait 的「谁来声明满足」上各选了什么？各自的收益和代价是什么？

## A
| 语言 | 谁声明满足 | 买到 | 付出 |
|---|---|---|---|
| Go | 方法齐全即自动满足，接口常定义在使用方 | 零耦合，库之间无需互相依赖 | 满足可能是巧合；改签名会无声地让类型不再满足 |
| Java | 类作者用 `implements` 声明 | 一眼可查，工具支持强 | 不能给别人的类补接口，要写适配器 |
| Rust | `impl Trait for Type`，受孤儿规则约束 | 事后补实现，全局一致 | 孤儿规则迫使你包一层 newtype |
| Python | ABC 显式继承，或 Protocol 按形状 | 两种风格都可用，运行期最灵活 | 运行期才发现缺方法，除非用类型检查器 |

规律：绑定发生得越晚、越不依赖类型作者，库之间就越松耦合，但「这个类型到底实现了什么」就越难从定义处看出来。

Go 的哲学是接口越小越好、由使用方描述它需要的最小能力，所以选择隐式满足；Java 的哲学是大型团队需要明确的、可检索的类型关系，所以选择显式声明；Rust 要在两者之间取得「能补实现」又「全局一致」，才有了孤儿规则这个折中；Python 想让简单脚本无需任何声明就能跑，又在大型项目里提供 ABC 和 Protocol 来补上约束。
