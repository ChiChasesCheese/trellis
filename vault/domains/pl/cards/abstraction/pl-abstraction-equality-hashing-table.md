## Q
C++、Go、Java、Rust、Python 在「默认相等」「谁定义」「哈希」上的选择有什么区别？

## A
| 语言 | `==` 的默认含义 | 自定义相等 | 防护 |
|---|---|---|---|
| Go | 逐字段比较；切片 / map / 函数不可比较 | 不能重载 `==` | 键类型编译期检查，接口里运行期 panic |
| C++ | 类没有默认 `==`（C++20 起可写 `operator==(...) const = default;` 逐成员比较）；指针比较地址 | 自己写 `operator==`，哈希要特化 `std::hash`（标准库的哈希定制点） | 无哈希的类型放进 `unordered_set` 直接编译失败；容器里的键是 `const`，不能就地修改；`NaN` 无人管 |
| Java | 引用同一性；`equals` 才是值 | 重写 `equals` + `hashCode` | 无，靠约定；`record` 自动生成 |
| Rust | 无默认，需要 `PartialEq` | `derive` 或手写 trait | `f64` 不是 `Eq`，不能做键 |
| Python | `is` 同一性；`==` 默认等同 `is` | `__eq__`，要配 `__hash__` | 定义 `__eq__` 后自动不可哈希 |

规律：越是**类型系统强**的语言越把相等的各个性质（部分、完全、可哈希）显式写进类型；越是**动态**的语言越靠运行期规则兜底。

Rust 的分层最细，因为它想让编译器能检查「这个类型能不能做键、能不能排序」；Go 追求简单可预测，把相等做成内置规则，不让用户改；Java 为了灵活选择了「方法可重写」，代价是约定多、错误多，`Effective Java` 用专门一章讲 `equals` 的契约；Python 对哈希的自动关闭是一个务实的保护，防止人们在没想清楚时就把对象放进字典。

C++ 的位置与 Rust 相近：没有隐含的相等，所有东西都要显式写出来，而且 C++20 的 `= default` 把最常见的逐成员比较降到一行；但它不区分「部分相等」与「完全相等」，也不在类型里挡住 `double` 做键，那是零开销原则（不用的功能不付钱）下「相信你知道自己在做什么」的又一例。
五门语言都没解决的问题是 `NaN`：浮点相等的数学规则（IEEE 754）与「等价关系」的要求冲突，各语言各自选了不同的折中（见下一张）。
