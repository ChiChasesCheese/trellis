## Q
C++、Go、Java、Rust、Python 各自支持哪几种多态？每门语言的取法买到了什么、付出了什么？

## A
| 语言 | 子类型 | 参数 | 特设 | 取舍 |
|---|---|---|---|---|
| C++ | 继承加 `virtual`（要显式声明才动态调用） | 模板（C++98 起，编译期按类型参数生成代码），C++20 加 concepts（显式约束） | 函数与运算符重载，模板特化 | 三种都有且互相独立，每一种都是「选了才付钱」；代价是三套规则并存，重载、特化、虚函数的交互是公认的难点 |
| Go | 接口，隐式满足 | 1.18 起泛型 | 无重载 | 机制最少，代价是表达力受限，同名函数要靠改名 |
| Java | 类继承 + 接口 | 泛型（擦除） | 方法重载 | 三种都有，代价是重载与泛型擦除叠加后规则繁杂 |
| Rust | `dyn Trait` | 泛型 + trait 约束 | `impl Trait for T` | 一个 trait 机制覆盖三种，代价是学习曲线 |
| Python | 鸭子类型，无需声明 | 仅类型检查层 | 无重载，`singledispatch` | 运行期最灵活，代价是类型错误晚发现 |

C++ 是三种多态最早、最完整的提供者（虚函数来自 Simula，模板和重载是它自己加的），而且比 Java 更彻底地让程序员选择：不写 `virtual` 就没有子类型多态的成本。背后的逻辑是各自的哲学：Go 把「少即是多」放在第一位，所以先只给接口，十年后才补泛型，始终不加重载（官方 FAQ 的理由是：只按名字查找函数，分派就简单，类型系统也简单）。Java 追求面向对象的完整性和向后兼容，每一版都往已有机制上叠加。Rust 想让「零成本抽象」成立，所以用 trait 一个机制统一三种多态，由使用者选静态还是动态。Python 不做编译期选择，所有选择都推迟到运行期，类型注解只服务工具。
