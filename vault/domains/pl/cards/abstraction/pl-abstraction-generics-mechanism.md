## Q
泛型函数是在定义处检查还是在使用处检查？这两种做法对错误信息和代码设计有什么影响？

## A
两种检查时机：

1. **定义处检查**（Java、Rust、Go）：编译器只对照类型参数的约束检查泛型函数体一次。约束里没有的操作一律拒绝，所以只要泛型函数通过编译，任何满足约束的类型都保证能用。
2. **实例化处检查**（C++ 模板）：函数体被当成「待填的模板」，每次用具体类型代入后才检查，代入失败才报错。

两者对比，用同一个想法「需要比较」：

```rust
fn bigger<T>(a: T, b: T) -> bool { a > b }
// Rust：定义处立即报错，并建议加 PartialOrd 约束
```

C++ 的 `template <class T> bool bigger(T a, T b) { return a > b; }` 在定义处不报错；用 `bigger(x, y)` 时若 `x` 的类型没有 `>`，错误才出现，并且是一屏模板展开的堆栈。

C++20 的 concepts 给实例化检查加了一层前置约束：`template <std::totally_ordered T> bool bigger(T a, T b)`，传入不满足的类型时，错误出现在调用处并指出哪条约束不满足，而不是展开一屏模板栈。但函数体依然只在实例化时检查：如果函数体用了 concept 没列出的操作，错误仍在实例化时才出现。所以 C++ 的约束是对调用者的前置检查，不是 Rust 那样同时约束函数体的契约。
定义处检查的好处：**泛型是契约**，错误精确，库作者可以在不知道用户类型的情况下保证正确；约束成为文档。代价：表达力受限于约束语言的能力，约束写不出来的东西就不能做（例如 Go 的约束里没法直接写「支持 `<`」，只能列出所有有序类型的并集）。

Python 在这里是第三条路：没有任何检查，类型注解交给外部工具，所以「泛型契约」只存在于工具里。

这一点之所以重要，是因为它决定了泛型对库设计的意义：定义处检查的语言里，`T: Bound` 就是函数签名的一部分，改它就是破坏性变更。
