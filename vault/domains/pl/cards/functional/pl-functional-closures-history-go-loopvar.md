## Q
Go 1.22 为什么愿意改变 `for` 循环变量的语义？这对「语言演进」说明了什么？

## A
Go 有强烈的向后兼容承诺（Go 1），改变已有程序行为被视为大事。但循环变量问题长期是 Go 里最常见的 bug 来源之一：几乎每个 Go 程序员都踩过「所有 goroutine 看到同一个 `i`」。团队分析了大量真实代码后发现，旧语义**很少是有意为之**，而新语义能修复大量潜在 bug。他们还用工具验证过：把大型代码库切到新语义，真正依赖旧行为的只有极少数。

Go 1.22（2024 年初）的做法是：

- 每次迭代为循环变量创建新的副本（包括三段式 `for` 的 `i`）。
- 由 `go.mod` 里的 `go` 指令控制：声明 `go 1.22` 或更高的模块得到新语义，旧模块保持旧语义，同一个构建里可以混用。
- 提供 `GOEXPERIMENT=loopvar` 等工具先行试验，并在迁移期用 `go vet` 的检查提示。

这套机制说明了语言演进的一个原则：**可以改变语义，但要有逐模块的开关、有迁移工具、有数据证明**。Go 的版本化语义让它能修复早期的设计错误，而无需 Python 2 到 3 那样的大断裂。

同类的设计选择：Rust 用 edition 机制按 crate 切换语法 / 语义；Java 依赖编译器 `--release` 版本与极度保守的兼容；Python 3 选择了断裂式升级。三种路径反映三种对兼容与修复的取舍。
