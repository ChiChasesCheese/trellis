## Q
Go 把栈大小藏进运行时，Rust 与 Java 把它暴露给程序员，这反映了怎样不同的哲学？

## A
**Go 的立场：并发是常态，栈是运行时的事**。Go 鼓励开大量 goroutine，如果每个都要预先分配固定大小的栈（比如 1 MB），十万个 goroutine 就是 100 GB，不可行。因此运行时让栈从 2 KB 起步、按需增长，程序员既不用估算栈大小，也不用担心线程栈不够。代价：栈增长时的复制、与 C 互操作的复杂度、运行时更重。哲学是**把复杂性收进运行时，让写代码的人少操心**。

**Rust 的立场：没有隐藏的运行时开销**。栈就是操作系统线程栈，大小固定、行为透明，不引入复制或额外的检查。栈溢出了就中止，因为没有安全的方法恢复。程序员需要自己判断深度，需要时开大栈线程。哲学是**零成本、可预测，一切资源由程序员掌控**。C++ 的立场相同，并且是它的出处：零开销原则下栈就是 C 的栈，溢出是未定义行为，连“中止”都不保证。

**Java 的立场：折中，历史包袱**。线程栈由 JVM 管理，大小可配置，溢出抛可捕获的 `Error`。虚拟线程的栈放在堆上，可以增长，是向 Go 的做法靠拢的一步。

**Python 的立场：安全优先**。解释器在崩溃前设一道人为的限制，让错误成为可恢复的异常。

观察：**栈增长的收益在并发场景最大**，而对只有少数线程的程序，固定栈足够。所以Go 与 Java 虚拟线程的做法，是随"海量轻量并发"这个需求一起出现的；对只需少数线程的系统编程语言，固定栈的简单与可预测更有价值。
