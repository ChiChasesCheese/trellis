## Q
Go、Java、Rust、Python、C++ 的迭代器 / 惰性机制在驱动方式和性能上有什么区别？

## A
| 语言 | 驱动方式 | 惰性的边界 | 性能特征 |
|---|---|---|---|
| Go（1.23） | 推送：`range` 一个函数 | 只有序列函数本身，无标准适配器 | 简单时内联，复杂时是闭包调用 |
| Java | `Stream` 流水线（推送），终端操作触发 | 中间操作惰性，一次性 | 依赖 JIT，数值要用基本类型流 |
| Rust | 拉取：`Iterator::next` | 适配器惰性，`must_use` | 内联为单个循环，零成本 |
| Python | 拉取：`__next__`，生成器 | 生成器和 `map`/`filter` 惰性，推导式立即 | 每元素每阶段一次解释器调用 |
| C++ | 拉取：迭代器（`begin`/`end` 一对）；C++20 ranges 视图用管道运算符串成流水线 | 视图惰性，且不拥有数据；要物化须显式 `std::ranges::to`（C++23） | 模板展开可内联，但不保证等于手写循环：本机实测 filter + transform 求和慢约 2.7 倍；视图可悬空 |

规律：**静态类型 + 单态化的语言能把惰性的成本抹掉**（Rust、C++），动态或运行期优化的语言把成本留在运行期。

Rust 的做法是通过类型系统把「流水线结构」编码进类型，所以能编译成最优循环；Java 当年在没有改变泛型与基本类型的前提下加了 Stream，因此有了装箱与预热的包袱；Python 用生成器把惰性做成语言特性，用最简单的协议获得最大的通用性；Go 起步最保守，等到有泛型和足够的需求后才加入最小形式。

C++ 是这条路的开创者：STL（1990 年代）把「迭代器 + 算法」做成泛型，让算法与容器解耦且可内联，这是零开销原则的原型。代价是历史包袱：迭代器对的接口易错，C++20 的 ranges 才补上可组合的惰性流水线，而它的「零成本」要靠实测确认：同样的 filter + map + 求和，Rust 的流水线与手写循环一样被向量化，C++ 的视图版本却没有。

选择与哲学：Rust 说「抽象不应该有代价」；Java 说「在不改变语言的前提下用类库提供」；Python 说「简单协议，处处可用」；Go 说「语言只加一点，其余留给用户」。
