## Q
Go、Java、Rust、Python、C++ 在「默认并发单位」上各选了设计空间里的哪一点？各自换来什么、付出什么？

## A
| 语言 | 默认选择 | 换来 | 代价 |
|---|---|---|---|
| Go | 运行时调度的 goroutine，自动铺满所有核 | I/O 密集和 CPU 密集用同一个工具，几十万并发 | 运行时较重，调度对程序员不透明 |
| Java | OS 线程（平台线程），21 起可选虚拟线程 | 与操作系统、原生库、调试器无缝对接；老代码不用改 | 线程重，需要自己选线程池或虚拟线程 |
| Rust | OS 线程；async 由外部运行时提供 | 没有语言级运行时，开销可控，可用于嵌入式和内核 | 生态分裂（同步 / 异步两套），要自己选运行时 |
| Python | OS 线程，受 GIL 限制；asyncio；多进程 | 解释器实现简单、单线程快，C 扩展易写 | 线程不能并行算 CPU 密集任务 |
| C++ | OS 线程（`std::thread`，C++11）；C++20 起有无栈协程，但没有线程池和调度器 | 与操作系统、C 库一一对应，没有运行时开销 | 池、事件循环、调度全靠自己或第三方库；数据竞争是未定义行为 |

背后的逻辑：
- 各语言的取舍是被**诞生时的目标**推出来的。Go 为服务端并发而生，所以把调度器做进语言；Rust 不愿为抽象付运行时的钱，所以把运行时留给库；Java 要兼容二十年的线程代码，所以最后才在线程模型下面换发动机（虚拟线程）；Python 的 GIL 是早期为简化引用计数换来的，之后成了兼容性包袱。
- 同一个问题的两种需求被分开对待：I/O 密集追求「等待重叠」（便宜的并发单位），CPU 密集追求「核数」（真正的并行）。语言默认给的单位，决定了你在哪一类上省力、哪一类上要绕路。
- C++ 与 Rust 同属「只给机制」一派：线程是对操作系统线程的薄封装，其余交给库。零开销原则（不用的不付费）和 C 兼容让语言不愿内置运行时，换来最大的控制权，也让每个项目自己选并发框架。
