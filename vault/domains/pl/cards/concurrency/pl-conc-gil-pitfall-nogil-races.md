## Q
一段在默认 Python 里一直「正确」的多线程代码，换成自由线程构建后会出什么问题？请用 `n += 1` 说明。

## A
代码：4 个线程各对全局变量做 100 万次 `n += 1`，不加锁。
```python
def bump():
    global n
    for _ in range(1_000_000): n += 1
# 4 threads run bump(); print(sys._is_gil_enabled(), n)
```
输出（同一份代码，一次测量）：
- 默认构建：`GIL enabled: True | n = 4000000`，每次都对。
- 自由线程构建：`GIL enabled: False | n = 1076857`（再跑一次是 `1048867`），丢了约四分之三的更新。

原因：`n += 1` 是读、加、写三步。默认构建里，GIL 只在特定检查点切换线程，这三步之间恰好没有检查点，所以“碰巧”原子，代码多年没出问题。自由线程构建里线程真的并行，两个线程同时读到同一个值，更新就丢了。

这类隐性依赖 GIL 的代码很常见：
- 全局计数器、缓存字典的“先检查后写入”；
- 懒初始化的单例（两个线程都发现未初始化）；
- 遍历列表时另一个线程在修改；
- 以为 `dict` 和 `list` 的单次操作线程安全，于是组合多步操作也不加锁。

自由线程构建会保证**解释器内部**不崩溃（容器的单次操作内部有锁），但**不会**保护你的业务不变量。这与 Java、Go 的世界一致：使用共享可变数据的 Python 代码，现在需要像它们一样显式加锁、使用 `queue.Queue` 或避免共享。迁移时应当把这类代码当作 bug 修复，而不是 GIL 的“副作用”。
