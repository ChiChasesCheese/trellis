## Q
Go 的 goroutine、Java 的虚拟线程、Rust 与 Python 对「便宜的用户态线程」做了什么选择？为什么会不一样？

## A
| 语言 | 选择 | 换来 | 代价 |
|---|---|---|---|
| Go | 从 1.0 起 goroutine 就是唯一的并发原语，运行时可抢占 | 顺序写法就能支撑几十万并发；标准库阻塞调用都已改造 | 必须带一个较重的运行时；与 C 互操作（cgo）贵 |
| Java | 21 正式的虚拟线程，保持 `Thread` API 不变 | 存量的阻塞式代码几乎不改就能放大并发 | 协作式，不抢占 CPU 密集任务；要等十几年才补上 |
| Rust | 1.0 之前有过，随后删除，改用 async 状态机 | 不要求运行时，FFI 零成本，嵌入式可用 | 函数着色，生态分裂 |
| Python | 标准库没有；asyncio 事件循环；第三方 greenlet | 与 GIL 现实兼容，单线程模型简单 | 同步库不能直接用 |

背后的逻辑：
- 这是「运行时的重量」与「编程模型的简单」之间的权衡。有栈的用户态线程让代码保持顺序风格，但需要运行时管栈、调度、改造阻塞调用；无栈的 async 不需要运行时，但把复杂度转嫁给了程序员。
- Go 的设计目标是服务端网络程序，运行时不是问题，所以一次做到位。Rust 的设计目标包含「不为不用的东西付费」和「能写操作系统」，所以不可能内置运行时，早期的绿色线程因此被删。
- Java 的先发优势成了负担：数以亿计的行代码用 `Thread`，所以只能在 JVM 里改底层，让旧 API 悄悄变便宜，而不是引入新模型。

量级参考（一次测量）：100 万个阻塞 goroutine 约占 2.8 GB 系统内存（每个约 2.7 KB）；100 万个 Java 虚拟线程堆占用约 0.8 GB。
