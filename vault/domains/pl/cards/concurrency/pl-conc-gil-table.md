## Q
要在多核上跑 CPU 密集的 Python 代码，有哪几条路？它们和 Go、Java、Rust「没有全局锁」的做法比，各自换来什么、付出什么？

## A
| 做法 | 并行方式 | 换来 | 代价 |
|---|---|---|---|
| Python 默认线程（有 GIL） | 无，轮流执行 | 单线程最快、C 扩展简单 | CPU 密集无加速 |
| Python 多进程 | 每进程一份解释器和 GIL | 真并行，完全隔离 | 进程启动重，数据要序列化（pickle）传递 |
| Python 自由线程构建 | 线程真并行，共享对象 | 保持线程模型，可共享内存 | 单线程约慢几个百分点；扩展库要适配；业务锁必须自己加 |
| Python 子解释器（每解释器一个 GIL，3.12 起） | 同进程内多个独立解释器 | 比进程轻，隔离 | 对象不能直接共享，需通道传递；生态仍在适配 |
| Go / Java / Rust | 线程或 goroutine 真并行，无全局解释器锁 | 并行与共享内存都是默认能力 | 数据竞争由程序员（或 Rust 编译器）负责 |

背后的逻辑：
- GIL 把「并行安全」做成**解释器的责任**，换来了使用者的省心；其他三门语言把它交给**程序员**（Rust 交给编译器）。这是“谁来为线程安全负责”的分歧。
- 所有 Python 的出路都在用别的方式付这笔账：多进程用序列化付，子解释器用隔离付，自由线程用单线程性能和生态适配付。没有一条是免费的。
- 所以 Python 社区的现实做法是：计算热点下沉到 C/Rust 扩展（NumPy、PyTorch），让它们释放 GIL 或自己管理线程，Python 只做胶水。
