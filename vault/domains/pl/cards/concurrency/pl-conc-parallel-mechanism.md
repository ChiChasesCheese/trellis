## Q
Java 的并行流和 Rust 的 rayon 在底层是怎样工作的？一次并行求和 1 亿个元素大约能加速多少？

## A
两者都基于**工作窃取的 fork/join 线程池**：
1. 启动固定数量的工作线程，默认等于核数（Java 公共池 `commonPool` 是核数减 1，因为调用线程也参与；本机为 11）。
2. 每个线程有自己的双端队列（deque）。一个任务被**拆分**：递归地把区间一分为二，一半放进自己队列（fork），另一半继续做；小到阈值就直接计算。
3. 自己的队列做完后，线程从**别的线程队列的另一端偷**一个较大的任务，保证负载自动均衡，同时偷的是最早入队的大块，减少冲突。
4. 子结果返回时 join，逐层合并。

实测（12 核 Mac，对 1 亿个元素求 `sqrt(i) * sin(i)` 之和，一次测量，加速比而非绝对值才有可比性）：
- Java `LongStream.range(0, N).parallel()`：顺序 2553 毫秒 → 并行 343 毫秒，约 7.4 倍。
- Rust rayon `into_par_iter()`：顺序 275 毫秒 → 并行 45 毫秒，约 6.1 倍。
- Go 手工分成 12 片、每片一个 goroutine：顺序 265 毫秒 → 并行 40 毫秒，约 6.6 倍。

加速比达不到 12，原因：Apple Silicon 有性能核和能效核，速度不同；内存带宽、合并开销、最慢的一块拖后腿。

对比：Python 的 NumPy 单线程 1.71 秒，8 个线程（GIL 在 C 内核里被释放）1.04 秒，约 1.6 倍，因为数组运算是内存带宽受限的，核数再多也有上限。

数字之外要记住的一条：并行的成本是固定开销（拆分、调度、合并），收益与每块工作量成正比。
