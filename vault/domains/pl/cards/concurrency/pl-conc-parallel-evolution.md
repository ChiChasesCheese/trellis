## Q
数据并行的工具是怎么演化的？从 fork/join 到并行流、rayon，再到 GPU 与 Python 的向量化生态，趋势是什么？

## A
**背景**：2005 年前后主频不再增长，CPU 厂商转向多核（“免费的午餐结束了”）。语言必须帮程序员用上多核。

**演化**：
1. **工作窃取调度**：来自 MIT 的 Cilk 项目（1990 年代），证明了工作窃取在理论和实践上都能高效平衡负载。
2. **Java**：Java 7（2011）加入 `ForkJoinPool`；Java 8（2014）加入 `Stream`，用 `.parallel()` 把调度包装成一个开关。便利带来了滥用：公共池、副作用、小数据变慢。
3. **Rust**：rayon（约 2015 年）用 trait 与所有权把“并行迭代器”变成安全抽象，让“把 `iter` 改成 `par_iter`”既简单又不会引入数据竞争。
4. **Go**：保持显式，没有标准库的并行迭代器；靠 goroutine 和 `errgroup` 手工分片。
5. **Python**：语言自身不并行，生态把计算下沉到 C/Rust 内核（NumPy、Polars、PyTorch），并通过自由线程、子解释器逐步补上语言层面的并行。

**趋势**：
- **从多核到异构**：真正大规模的数据并行在 GPU 和 SIMD 上。工作越来越多地用“数组/张量/数据框”的声明式写法，运行时决定怎么拆、放到哪个核或设备上（NumPy、JAX、Polars 的惰性执行）。
- **并行安全被前移**：Rust 的 rayon 展示了“类型系统保证并行安全”的可行性，其他语言通过静态分析和约定在追赶。
- **并行度由运行时管理**：容器时代，运行时需要感知 cgroup 的 CPU 配额（Go 和较新的 JVM 都在加这类支持），避免“以为有 64 个核，实际只配了 2 个”。
- **并发与并行分工明确**：I/O 用轻量并发（虚拟线程、协程），CPU 用有界并行池，是当前的共识做法。
