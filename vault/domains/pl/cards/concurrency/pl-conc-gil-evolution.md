## Q
去掉 GIL 为什么拖了二十多年？PEP 703 的方案与早期尝试有何不同，现在进展到哪一步？

## A
**早期尝试失败**：1999 年有人给 Python 1.5 做过“去 GIL”补丁：给每个对象和结构加细粒度锁。结果单线程变慢约一倍，多线程在当时的双核机器上也只有有限收益，社区拒绝了。之后的 Gilectomy（2016 年前后）同样因为单线程性能下降和引用计数的竞争没有走通。核心矛盾是：**引用计数 + C 扩展接口**让任何细粒度方案都要在所有对象上付出代价，并破坏大量 C 扩展。

**PEP 703（2023 年被接受）的新办法**：不是简单地加锁，而是重新设计引用计数与对象访问：
- 不朽对象，让常量不再改计数；
- 偏向引用计数，创建线程用廉价的非原子计数；
- 延迟引用计数与线程安全的内存分配器；
- 容器内置临界区锁。
目标是单线程性能下降控制在个位数百分比，以换取多线程的真并行。

**落地节奏**（保守且可回退）：
- 3.12：每个子解释器拥有独立 GIL（PEP 684）；
- 3.13：自由线程构建作为实验性选项出现，另外提供实验性 JIT；
- 3.14：自由线程构建进入官方支持阶段，标准库出现 `concurrent.interpreters` 子解释器接口；
- 未来：看生态适配程度，再决定是否成为默认。

**趋势**：Python 在向“可选的并行”演进，而不是推翻重来；要紧的是 C 扩展生态的迁移。同时，Java、Go、Rust 这一侧的启示是：内存管理方式（追踪式 GC 还是引用计数）早早地决定了语言能否便宜地支持多线程，设计初期的选择会影响几十年。
