## Q
GIL 具体什么时候被释放？为什么 I/O 和 NumPy 里的线程能并行，而纯 Python 计算不能？

## A
GIL 是一个互斥量，线程要执行 Python 字节码必须持有它。释放的时机有三类：
1. **时间片到期**：每个线程默认最多连续跑约 5 毫秒（`sys.getswitchinterval()` 为 0.005）。等待 GIL 的线程会请求，持有者在字节码的特定检查点（循环回跳、函数调用）放下它。
2. **阻塞的系统调用**：读写文件、网络、`time.sleep`、等待锁，C 代码在进入系统调用前主动释放 GIL，返回后重新获取。
3. **C 扩展主动释放**：长时间的 C 计算在不碰 Python 对象时可以暂时放下 GIL，如 NumPy 的大数组运算、`hashlib`、`zlib`、`re` 的部分操作。

所以：
- **I/O 密集**：线程大部分时间在等，GIL 在别人手里没关系。
- **纯 Python 计算**：始终要拿着 GIL，线程轮流用，没有并行，还多了切换。
- **C 扩展里的计算**：释放了 GIL，可以真并行。实测（一次测量）：对 200 MB 数据做 4 次 SHA-256，顺序 0.22 秒，4 个线程 0.06 秒。

**自由线程构建（free-threaded build，3.13 起提供，3.14 起受官方支持）**去掉了 GIL，靠这些机制保证安全：
- 不朽对象（immortal objects）：常量、小整数等不再改引用计数；
- 偏向引用计数（biased reference counting）：对象的创建线程用快速的非原子计数，其他线程用共享计数；
- 容器等对象内置细粒度锁（每个对象一个临界区）；
- 线程安全的内存分配器。

实测（4 线程数素数，一次测量）：默认构建 1 线程 0.32 秒、4 线程 0.32 秒；自由线程构建 1 线程 0.34 秒、4 线程 0.13 秒，单线程慢了约 6%。
