## Q
在同一台机器、同样的“5000 个空闲连接”下，Go、Java 虚拟线程、Rust tokio、Python asyncio 各用多少线程和内存？这反映了哪些设计差异？

## A
一次测量（macOS ARM64，12 核，每种语言一个 echo 服务器，5000 个连接建立后空闲）：

| 运行时 | 任务表示 | OS 线程数（空闲 → 5000 连接） | 内存 RSS（空闲 → 5000 连接） | 每连接约 |
|---|---|---|---|---|
| Go | goroutine（独立栈，约 2 KB 起） | 5 → 14 | 4 → 27 MB | 4.7 KB |
| Java 虚拟线程 | 栈存堆上的虚拟线程 | 21 → 35 | 43 → 73 MB | 6 KB |
| Rust tokio | 编译器生成的状态机 | 13 → 13 | 2 → 10 MB | 1.6 KB |
| Python asyncio | 协程帧加传输/流对象 | 1 → 1 | 25 → 56 MB | 6.2 KB |

（这是用来比较量级的单次测量，不是基准；JVM 的基线内存本身就高。）

**读法**：
1. 四种方案都把 5000 条连接压在几十个以内的 OS 线程上，对比线程模型里每个线程约 70 KB 且受内核线程数限制，成本降了一个数量级。
2. **最轻的是 Rust 的状态机**：没有独立栈，只保存跨 `await` 仍需要的变量；代价是编译器要重写函数、语言要有 `async` 染色。
3. **Go 和 Java 的任务带着栈**，每个多出几 KB，但保持了“同步写法、不分颜色”。Java 比 Go 多的部分来自载体线程池、线程与 JVM 基础开销。
4. **Python 单线程**：线程数最少，但每个连接的 Python 对象很重，并且不能并行；它的限制在 CPU，不在连接数。

逻辑：这是同一个交换的不同刻度。把“等待状态”存放在哪里：栈（Go、Java）还是状态机（Rust）还是对象（Python）？越靠近编译器生成的结构越小，越靠近运行时通用机制越方便。语言选择的是自己的设计目标：Go 要简单，Rust 要零成本，Python 要生态与开发速度，Java 要兼容旧代码并升级现有线程模型。
