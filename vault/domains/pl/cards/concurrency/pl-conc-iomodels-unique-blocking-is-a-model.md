## Q
为什么说 Go 的 goroutine 和 Java 的虚拟线程“把线程模型救了回来”？同步的阻塞写法和异步回调在表达力上有什么根本差别？

## A
一连接一线程在 C10K 时代被判了死刑，原因是**线程贵**（栈、内核结构、调度），而不是“阻塞写法”本身有错。事件驱动的写法要付出另一种代价：一个请求的逻辑被拆成多个回调或状态机状态，局部变量、异常、循环、调用栈都要手工维护。

对比一个“读请求、查数据库、调下游、写响应”的处理：
- **阻塞写法**：四行顺序代码，局部变量自然保存状态，`try/catch` 或 `if err != nil` 自然处理错误，栈追踪直接指出哪个调用失败；
- **回调写法**：四个回调函数，状态放在对象里传来传去，错误要在每一层传播，栈追踪只显示事件循环。

**用户态线程的洞察**：阻塞写法的好处在**程序模型**，线程昂贵是**实现问题**。如果运行时能把“线程”做得足够便宜（Go 的 goroutine 初始栈约 2 KB，Java 虚拟线程的栈放在堆里按需增长），并在阻塞点把线程挂起而不占 OS 线程，就可以保留顺序写法而得到事件循环的规模。底层依旧是 epoll 加就绪队列，但用户看不见。

**所以两条路线的区别**是“把成本放在哪里”：
| | async/await（Rust、Python、JS） | 用户态线程（Go、Java 虚拟线程） |
|---|---|---|
| 谁知道要切换 | 程序员，在 `await` 处显式标出 | 运行时，在阻塞点自动切换 |
| 代码形态 | 函数分同步/异步两种“颜色” | 所有函数一样，不分颜色 |
| 额外要求 | 库要有异步版本 | 标准库的每个阻塞点都要改造过 |

Rust 选了前者，因为它不愿意引入带栈切换的运行时；Go 和 Java 选了后者，因为它们本来就带运行时，且重视“同一份代码不分颜色”。这是语言哲学的直接结果：Rust 把成本交给程序员显式管理，Go/Java 把成本交给运行时隐藏。
