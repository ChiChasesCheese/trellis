## Q
什么时候值得把一个计算改成数据并行？资深工程师在 Java、Rust、Go、Python 里的做法是什么？

## A
**先问四个问题，再动手**：
1. **瓶颈真的是 CPU 吗？** 先剖析（profile）。如果在等 I/O 或锁，并行只会让它等得更热闹。
2. **有没有更便宜的优化？** 更好的算法、减少分配、向量化，常常比多核收益大一个数量级。
3. **每个元素的工作量够大吗？** 经验上，一块工作至少应该是几十微秒以上。实测：Java 并行流处理只有 1000 个元素的小列表，重复 2000 次，顺序 12 毫秒，并行反而 36 毫秒（约慢 3 倍）。
4. **元素之间独立吗？** 有共享可变状态或顺序依赖的，先重构，再并行。

**做法**：
- **用 `map` + `reduce` / `collect` 产出新值**，不在并行体里改外部变量；归并操作要满足结合律。
- **用有界、专用的池**。Java 并行流默认用全进程共享的 `commonPool`，一个流里的阻塞调用会拖慢所有使用它的代码；可以放进自定义的 `ForkJoinPool` 中提交，或对阻塞型任务改用虚拟线程 / 普通线程池。
- **CPU 密集的并行度取核数**，留一两个核给其他事情；容器里要注意核数是否被 cgroup 限制（Java 与 Go 对此的识别程度因版本而异，Go 1.25 起会感知 cgroup 的 CPU 限额）。
- **Go**：按核数分片，每片一个 goroutine，每个 goroutine 写自己的输出槽位（不同的切片下标），最后合并，避免锁。
- **Python**：不要在纯 Python 里并行数值循环；用 NumPy/Polars 等库的向量化，必要时 `ProcessPoolExecutor` 处理粗粒度任务。
- **度量并行度收益**：对比顺序版本，看加速比是否接近核数；差得远就找最慢的分片、内存带宽或合并开销。

什么时候不并行：延迟敏感的请求路径上的小任务、已经被外层并发占满核的批处理（在每个请求里再开并行，会互相争抢）。
