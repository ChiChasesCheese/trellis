## Q
阻塞 I/O 和非阻塞 I/O 在系统调用层面有什么区别？如果只用非阻塞调用而不借助通知机制，会发生什么？

## A
网络连接在程序里是一个**文件描述符**（file descriptor，fd，一个小整数）；`read(fd)` 要从内核的接收缓冲区取数据。

- **阻塞模式**（默认）：缓冲区是空的，`read` 就不返回；内核把调用线程标记为“睡眠”，放进这个连接的等待队列，数据到达时再唤醒。睡眠期间线程不占 CPU，但它的栈和内核结构一直被占着。
- **非阻塞模式**：缓冲区是空的，`read` 立刻返回错误 `EAGAIN`（“资源暂时不可用，稍后再试”）。线程不会睡，但你得到的是一个“没有”。

Python 里直接看到（macOS）：
```python
a.setblocking(False)
a.recv(10)   # BlockingIOError: [Errno 35] Resource temporarily unavailable
```

**只用非阻塞、不用通知会怎样**：你不知道什么时候有数据，只能反复调用试试，叫**忙轮询**（busy polling）。实测：等 0.2 秒来一个字节，忙轮询的线程调用了约 88 万次 `recv`，全部失败，占满一个核心（CPU 时间 315 毫秒）；同样的等待用阻塞 `recv`，CPU 时间只有 0.2 毫秒。

所以非阻塞本身不是目的，它只是前提：它让一个线程可以**同时管理很多个连接**而不会被其中任何一个卡住，但还需要一个机制告诉你“哪个连接现在有事”，这就是就绪通知。

两种模式对比：
| | 阻塞 | 非阻塞（单用） |
|---|---|---|
| 没数据时线程 | 睡眠，不耗 CPU | 继续跑，空转 |
| 一线程管几个连接 | 一个 | 多个，但要自己轮询 |
| 代码形态 | 顺序、直观 | 要处理“还没好” |
