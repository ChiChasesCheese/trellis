## Q
什么时候该用通道，什么时候该用锁？通道的容量、关闭和背压怎么设计？

## A
**通道还是锁**（Go 社区的经验法则）：
- **传递数据所有权、串联流水线、扇入扇出、事件通知** → 通道。数据流动的方向清晰，同一时刻只有一个所有者。
- **保护一份被多处读写的状态**（缓存、计数器、配置） → 互斥锁。用通道去“保护状态”会把简单问题变成一个管家 goroutine 加请求响应协议，更慢也更难读。
- 口号「通过通信来共享内存」是一个倾向，不是教条。

**容量**：
- 容量不是调参旋钮，而是语义选择：0 表示严格同步；N 表示允许生产者领先 N 个。实测：同一个生产者在消费者尚未开始时，容量 0 能完成 0 次发送，容量 2 能完成 2 次。
- 有界永远优于无界。有界通道在下游变慢时让上游阻塞，这就是背压（backpressure）；无界通道把问题藏进内存，直到进程被杀。
- 性能上：Go 无缓冲约 70 纳秒 / 条，容量 1024 约 16 纳秒 / 条（一次测量）；批量化比调大容量更有效。

**关闭**：
- 只让**发送方**关闭，接收方不关；多个发送方时用 `WaitGroup` 等所有发送方结束后由一个协调者关闭。
- Rust 里所有 `Sender` 被丢弃，接收端迭代就结束，所以要记得 `drop` 掉主线程手里多余的 `tx`。
- Java / Python 的队列没有关闭，用毒丸，每个消费者一个。

**取消**：每个阻塞点配一个退出分支（`select` 里加 `ctx.Done()`），没有它，上游一失败，下游就永远等着。

不用通道的场景：简单的并行计算，用 `WaitGroup` 或结构化并发加结果切片更直接。
