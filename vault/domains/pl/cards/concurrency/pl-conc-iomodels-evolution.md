## Q
从 C10K 到 io_uring，服务器 I/O 模型在这二十多年里怎样演进？推动它的是什么力量，现在走向哪里？

## A
**时间线**（年份为大致发布时间）：
- 1999：Dan Kegel 提出 C10K 问题：一台机器能否同时服务一万个连接。当时主流做法是一连接一个进程或线程，调度和内存开销撑不住。
- 2000 到 2002：FreeBSD 加入 `kqueue`，Linux 2.5.44 加入 `epoll`。此前的 `select`/`poll` 每次调用都线性扫描全部连接，这两个新接口让成本只和就绪数有关。
- 2004 起：nginx 等基于事件循环的服务器证明单线程事件驱动能比线程模型的 Apache 更省资源；Node.js（2009）把这一模型推到应用开发者面前，也把“回调地狱”带给了更多人。
- 2010 年代：语言层面的反应：回调 → Promise/Future → `async/await`（C#、Python、JavaScript、Rust），以及 Go 的 goroutine，把顺序写法还给程序员。
- 2019：Linux 5.1 引入 `io_uring`，把完成模型和批量提交带进 Linux；文件 I/O 也有了真正的异步。
- 2023：Java 21 虚拟线程正式发布，传统阻塞 API 也能扛百万级并发。

**推动力是同一个矛盾**：连接数增长得比线程便宜得多的速度更快。每一步都是把成本从“每连接”挪到“每活跃事件”：进程 → 线程 → 就绪通知 → 轻量用户态线程 → 批量完成通知。

**趋势**：
1. **编程模型和执行模型分离**：写顺序代码（goroutine、虚拟线程、`async`），底层统一是事件循环。
2. **减少系统调用**：`io_uring` 的批量提交与共享内存队列，网络栈绕过内核（DPDK、`AF_XDP`）用于极端场景，如高频交易和 CDN。
3. **异步文件 I/O 成为一等公民**，不再靠线程池模拟。
4. **结构化并发与取消**成为必需：连接多了，“谁来取消没人要的请求”变成语言层要回答的问题。
