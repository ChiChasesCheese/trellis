## Q
Java 为什么同时保留了 `java.io`、NIO `Selector`、NIO.2 异步通道和虚拟线程这几代 I/O API？这反映了它怎样的演化哲学？

## A
Java 的 I/O 有四代，至今都在被使用：
1. **`java.io`**（1.0）：流式、阻塞，一连接一线程。
2. **NIO**（1.4，2002）：`Channel` + `Buffer` + `Selector`，事件驱动，为了在少量线程上服务大量连接。Netty、Vert.x 等框架建立在它之上。
3. **NIO.2**（7，2011）：`AsynchronousSocketChannel`，用回调或 `Future` 获取完成通知，Windows 上基于 IOCP，Linux 上基于 epoll 加内部线程池；实际使用不多。
4. **虚拟线程**（21，2023）：保持 `java.io` 的阻塞 API，由 JDK 内部自动挂起与恢复。

Go 在 2009 年第一天就是“goroutine + 阻塞 API”，Java 经历了二十年才走回类似的位置。这不是 Java 慢，而是它的**价值观**决定的：
- **向后兼容几乎是绝对的**：1996 年写的 `java.io` 代码今天仍然能跑。新方案只能“加”，不能“换”；每一代 API 的存在都意味着有人在生产里依赖它。
- **用库解决，再用语言/VM 吸收**：NIO 先让 Netty 这样的第三方框架证明模型，等到痛点（回调的可读性、调试困难）足够清晰，再由 JVM 层面提供根本方案。
- **让旧代码受益**：虚拟线程最重要的设计选择是不引入新 API 和“颜色”，已有的阻塞式代码、库、调试器、剖析器几乎原样受益。对比 Rust 和 Python 的 `async`，生态要分裂成同步和异步两套。

代价是**选择变多**：新项目面对四套 API，教程与框架混杂；虚拟线程之后，Netty 式事件驱动是否仍有必要成为实际的争论（在要极致吞吐、或要复用已有 Netty 协议栈时仍有价值）。

可以看到的规律：**成熟的平台在大规模变化时，选择“不破坏现有代码”优先于“最优雅的设计”**。这与 Go 的“少且一致”、Rust 的“让用户显式”形成了三种不同的演进风格。
