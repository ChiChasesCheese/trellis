## Q
编译期证明（Rust）和运行期检测（Go 的 `-race`）在原理上差在哪里？竞争检测器怎样判断“两次访问之间没有同步”？

## A
**编译期：对所有可能的执行证明“不会”。** Rust 的规则是：
1. 同一时刻，一个值要么有任意多个只读引用，要么只有一个可变引用（借用规则）；
2. 跨线程的值必须满足 `Send`（可移动）或 `Sync`（可共享引用）；
3. 要在线程间修改共享数据，必须通过 `Mutex`、原子类型等同步类型，它们的 `Sync` 实现保证了所有访问都是受控的。
三条合起来，**数据竞争的三个条件**（同一位置、至少一个写、无同步）在安全代码里不可能同时满足。证明是静态的，不需要运行程序，代价是一些合理的程序被拒绝。

**运行期：对这一次执行检查“有没有”。** 基于 ThreadSanitizer 的 happens-before 检测：
1. 编译时给每次内存读写插入检测调用；
2. 运行时为每个线程维护一个**向量时钟**（vector clock，记录“我已经看到其他每个线程的第几步”）；锁的加解锁、通道收发、`WaitGroup`、原子操作等同步事件会在线程之间传递时钟，建立 happens-before；
3. 每个内存位置在**影子内存**里记录最近几次访问的线程和时钟；
4. 新的访问发生时，若与影子记录里的某次访问“互相不 happens-before”，且至少一个是写，就报告数据竞争。

因为判断依据是同步关系而不是“碰巧同时发生”，即使两次访问在时间上隔得很远，只要没有同步链把它们连起来，也会被检测出来。这使检测器比“跑很多次看会不会出错”强得多。

两者的互补关系：
- Rust 的证明**覆盖所有路径**，但只适用于安全 Rust；`unsafe` 代码和 FFI 仍可能有竞争，所以 Rust 项目也会跑 ThreadSanitizer / Miri / loom；
- `-race` 不限制你怎么写，但只能发现**被测试执行到**的竞争，所以要靠测试覆盖和并发压测；
- 都不能发现竞态条件（逻辑上的交错错误，如检查-再-操作）和死锁。
