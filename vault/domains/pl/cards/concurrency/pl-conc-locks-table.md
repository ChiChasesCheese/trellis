## Q
Go、Java、Rust、Python、C++ 在「锁与数据的关系」「是否可重入」「怎么保证释放」上的选择，各自体现什么取舍？

## A
| 语言 | 锁与数据 | 可重入 | 保证释放的机制 | 取舍 |
|---|---|---|---|---|
| Go | 分离；约定俗成把锁放在结构体字段里 | 否 | `defer mu.Unlock()` | 极简，依赖纪律；故意不可重入，让设计问题暴露 |
| Java | 分离；`synchronized` 把对象本身当锁 | 是 | `synchronized` 块自动释放；`Lock` 用 `finally` | 功能最全（读写锁、条件、`StampedLock`），可重入掩盖设计问题 |
| Rust | 锁**包着**数据：`Mutex<T>` | 否 | 守卫离开作用域自动释放（RAII） | 用类型表达「锁保护谁」，代价是锁中毒、借用规则 |
| Python | 分离 | `Lock` 否，`RLock` 是 | `with lock:` | 标准库精简；GIL 让很多场景「看起来」不需要 |
| C++ | 分离：`std::mutex` 是独立对象（Clang 的 `GUARDED_BY` 标注可静态检查） | 否；`std::recursive_mutex` 另有 | `std::lock_guard` / `std::scoped_lock`：析构时释放（RAII，构造获取、析构释放） | RAII 的发源地，`scoped_lock` 一次锁多把防死锁；但不保护「忘了加锁」 |

背后的逻辑：
- **谁来记住「这把锁保护什么」** 是核心分歧。Java、Go、Python、C++ 把它留给文档和程序员，Rust 把它放进类型，使「忘记加锁」变成编译错误。代价是写法更严格，比如不能随意在持锁时调用会回调到自身的方法。
- **可重入**是便利与清晰的权衡。可重入锁让「持锁的公开方法调用另一个持锁的公开方法」直接可用，却让锁的持有范围不再清晰；Go 和 Rust 的不可重入逼你拆成「加锁的外层方法」和「假设已持锁的内层方法」，设计更诚实。
- **释放的保证**越靠近语言机制越可靠：块结构、`defer`、`with`、RAII 都是把「成对出现」交给语言，而不是交给人。C++ 的 `lock_guard` 是这一思路的原型：析构函数在离开作用域（含异常）时必然运行，所以 Rust 的守卫和 Java 的 try-with-resources 都是它的后裔。
- C++ 不把锁塞进数据，也没有「每个对象自带一把锁」（Java 在每个对象头付这笔成本）：零开销原则下，不用锁的对象不该承担锁的空间。代价是锁与数据的绑定只能靠注释、封装或静态标注。
