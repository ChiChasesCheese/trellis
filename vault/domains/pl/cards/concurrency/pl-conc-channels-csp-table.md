## Q
Go、Rust、Java、Python、C++ 把「消息传递」放在语言还是库里？各自的默认容量、结束信号和多路等待说明了什么取舍？

## A
| 语言 | 形态 | 默认容量与结束 | 多路等待 | 取舍 |
|---|---|---|---|---|
| Go | 语法级 `chan`、`select` | 零容量（同步碰头）；`close` 是结束信号 | `select` 内置 | 把 CSP 当作程序结构的骨架，代价是运行时和语法更重 |
| Rust | 标准库 `mpsc`（多发单收） | `channel()` 无界；所有发送端丢弃即结束 | 标准库没有，用 crossbeam / `tokio::select!` | 库级；所有权随消息移动，代价是默认无界、功能最小 |
| Java | `BlockingQueue` 系列 | 容量由实现决定；无关闭语义，要毒丸 | 无 | 队列是线程安全的数据结构，不是通信哲学 |
| Python | `queue.Queue` | `maxsize=0` 即无界；无关闭，要哨兵值 | 无；asyncio 里用 `wait` | 同上，简单够用 |
| C++ | 标准库没有通道；用 `std::queue` 加 `std::mutex` 和条件变量自己搭，或用 Asio、folly 等库的队列 | 容量、关闭都自己定义（标志位或哨兵） | 无 | 只给底层原语，不规定通信风格；`std::move` 搬走的对象仍可被误用 |

背后的逻辑：
- Go 的默认零容量是一个**设计声明**：通信同时也是同步，发送方知道对方已经收到。Java 和 Python 的队列默认就是缓冲区，目的是削峰，不是同步。
- 默认值决定了典型的故障：Go 的零容量，常见故障是死锁和泄漏；Rust、Python 的无界默认，常见故障是内存无限增长而无人察觉。
- 结束信号放在通道里（`close`、全部发送端丢弃）还是放在数据里（毒丸），决定了多生产者场景下谁来负责收尾。Go 把责任交给「唯一的发送方」，Rust 用引用计数式的发送端自动判断。
- 只有 Go 把「同时等待多个事件」做进语法，所以超时、取消、多路汇聚在 Go 里是一等公民，在其他语言里要借助额外的库。
- C++ 连队列都不是并发原语：标准库只提供线程、锁、条件变量，通信风格由项目自己选。这是零开销原则和手动控制的结果（语言不替你决定容量、关闭和公平性），代价是每个项目重写一遍带关闭语义的队列。
