## Q
Rust、Go、Java、Python 在「何时、如何阻止数据竞争」上选了不同的位置，各自的保证和代价是什么？

## A
| 语言 | 策略 | 保证 | 代价 |
|---|---|---|---|
| Rust | 编译期：`Send`/`Sync` + 借用检查 | 安全代码里不可能有数据竞争 | 学习曲线；有时合理的代码被拒绝；要显式选 `Arc<Mutex<T>>` |
| Go | 运行期工具：`-race`；map 并发写直接崩溃 | 只发现被执行到的竞争 | 零语言成本，但靠测试覆盖 |
| Java | JMM 限制后果 + 线程安全库 + 约定 | 竞争不会让 JVM 崩溃，但不保证你的逻辑 | 靠审查、纪律和压测 |
| Python | GIL 保护解释器内部 | 容器结构不会被破坏 | 业务不变量不保证，给人错觉 |

背后的逻辑：
- 这是「**越早发现越贵**」的权衡。编译期证明最安全，但语言要提前定义“什么叫共享、什么叫独占”，所以只有带所有权的 Rust 做得到；GC 语言里到处都是别名，类型系统没有办法分辨哪些引用会被多线程同时使用。
- Go 选择工具而不是语法，符合它「语言简单，工具补位」的哲学；`-race` 因此成为生产代码默认的 CI 步骤。
- Java 选择限制后果（不能凭空出现数值、不会让虚拟机崩溃），保证了平台的安全性，把正确性留给应用。
- Python 的 GIL 提供的是实现层面的保护，不是语言层面的承诺，所以最容易被误解。
- 只有 Rust 能阻止数据竞争；四门语言都不能阻止竞态条件和死锁。
