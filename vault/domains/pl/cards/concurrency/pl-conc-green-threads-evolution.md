## Q
绿色线程（green threads）为什么在 Java 和 Rust 里先被抛弃，后来又在 Go 和 Java 21 里成功？

## A
**第一次失败**：早期 Java（1.1 时代，在一些平台上）和 Rust（1.0 之前）都用过用户态线程，后来都删掉了。原因是当时的实现有硬伤：
- 只在一个 OS 线程上复用（N:1），无法利用多核；
- 阻塞的系统调用会卡住所有绿色线程；
- 与原生代码、调试器、性能分析工具互相不认识。
Java 回到 1:1 的 OS 线程，Rust 为了「无运行时、FFI 零成本」的目标，在 1.0 之前删除了绿色线程。

**为什么后来成功**：
1. **M:N + 多核调度**：Go 的调度器用多个 OS 线程跑，做了工作窃取，阻塞时交出 P；
2. **运行时和库一起改造**：网络 I/O 走非阻塞加轮询器，阻塞调用在用户态被拦截成挂起；
3. **栈可增长**：从约 2 KB 起步，按需复制扩容，让「一个任务一个线程」在内存上可行；
4. **需求变了**：云服务把大量 I/O 并发变成主流负载，线程数成为瓶颈。

**Java 的第二次尝试（Project Loom）**：2023 年随 Java 21 正式发布虚拟线程，保持 `Thread` API 不变，在 JDK 里把阻塞的 I/O 和锁改成可挂起，栈存成堆上的对象。JDK 24 起 `synchronized` 内阻塞也不再钉住载体线程。

**趋势**：两条路线并存。对服务端，「便宜线程 + 同步写法」成为主流方向（Go、Java、Kotlin 协程、Erlang）；对系统与嵌入式，无栈 async 仍然更合适。共同点是：让程序员写顺序代码，把调度藏进运行时。
