## Q
同一段 CPU 密集的 Python 代码，在默认线程、多进程、自由线程三种方式下实际快多少？这反映了 Python 怎样的取舍？

## A
任务：数 0 到 40 万之间的素数，把区间切成 4 份（一次测量，12 核 Mac，Python 3.14）：

| 方式 | 耗时 |
|---|---|
| 1 个线程（默认构建） | 0.32 秒 |
| 4 个线程（默认构建，有 GIL） | 0.32 秒 |
| 4 个进程（`multiprocessing.Pool`） | 0.18 秒 |
| 4 个线程（自由线程构建 `3.14t`） | 0.13 秒（1 线程 0.34 秒） |

检查构建用 `sys._is_gil_enabled()`：默认返回 `True`，自由线程构建返回 `False`。

读法：
- 默认线程没有任何加速，因为同一时刻只有一个线程执行字节码，多线程还多一点调度开销。
- 多进程有加速，但只有约 1.8 倍：进程启动、把参数和结果序列化传回主进程要花时间，任务越小越吃亏；4 份工作量也不均匀。
- 自由线程最快，约 2.6 倍，代价是单线程慢了几个百分点。

这反映了 Python 的价值排序：**可用性和生态兼容 > 极致并行**。语言没有强行变成并行语言，而是留出多种出路（进程、扩展、自由线程），并用二十年时间保证绝大多数现有 C 扩展不被破坏。这也是为什么自由线程构建是一个单独的、可选的构建，而不是直接替换默认版本。
