## Q
Java、Go、Rust、Python、C++ 在内存模型的「可选顺序档位」上做了不同选择，这体现了怎样的取舍？

## A
| 语言 | 模型与档位 | 换来 | 代价 |
|---|---|---|---|
| Java | JMM（Java 5 定型）；`volatile`、`Atomic*` 默认顺序一致；`VarHandle` 开放更弱模式 | 绝大多数人只需知道 happens-before | 弱序控制只给专家，普通 API 不够细 |
| Go | 2022 年随 Go 1.19 重写；`sync/atomic` 只有顺序一致一档 | 极简，几乎不可能用错档位 | 在弱序硬件上放弃部分性能 |
| Rust | 沿用 C++20 的五档 `Ordering` | 在 ARM 上能榨出最低开销，可写无锁结构 | 程序员要自己论证正确性 |
| Python | 无成文模型，靠 GIL 的实现行为 | 对使用者无负担 | 自由线程构建下需要重新面对 |
| C++ | C++11 起有成文模型；`std::atomic` 的 `memory_order` 六档，默认顺序一致；数据竞争是未定义行为（UB） | 与 Java 一起奠定 DRF-SC 框架，是 Rust 档位的来源；弱序硬件上可榨出最低开销 | 全靠程序员论证；`consume` 档实际被编译器当 `acquire` 处理；错档位只在特定 CPU 上出错 |

背后的逻辑：
- Java、Go、Rust、C++ 的共同承诺是「**无数据竞争的程序按顺序一致执行**」（DRF-SC）。只要把共享数据用锁、通道或原子变量保护起来，就不必理解重排。
- 分歧在于：要不要让普通程序员接触更弱的顺序。Go 说不要（简单优先），Rust 和 C++ 说要（性能与控制优先），Java 折中（默认强，专家有后门）。
- C++ 是开得最大的那扇门：零开销原则要求原子操作能退化成最便宜的硬件指令，所以把全部档位交给程序员，并且不加安全网（同步不足而产生的数据竞争即 UB）。Rust 的档位是它的子集（少了 `consume`），多出来的是类型系统的保护。
- 这和它们的定位一致：Go 面向大规模工程里的普通团队，Rust 面向写运行时和基础库的人，Java 面向既有大量应用代码、又要支撑 JDK 自身并发库的平台。
- 弱序硬件的现实（Apple Silicon、服务器 ARM）让「不会出问题」不再等于「x86 上没出问题」。
