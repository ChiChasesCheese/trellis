## Q
完成通知（completion notification）模型，比如 Linux 的 `io_uring` 和 Windows 的 IOCP，和就绪通知有什么本质区别？它省掉了什么？

## A
就绪通知回答的是“**现在能不能读/写**”，之后的 `read`/`write` 仍是你发起的一次系统调用，数据在这次调用里从内核拷到你的缓冲区。完成通知回答的是“**我要求的那次读/写做完了**”：你先提交一个请求（“从这个 fd 读，放进这块缓冲区”），内核（或 IO 线程池）去完成，完成后在一个完成队列里放一条记录。

`io_uring`（Linux 5.1，2019）的结构：用户态和内核共享两个环形队列。
- **提交队列**（submission queue）：你把请求写进去；
- **完成队列**（completion queue）：内核把结果写进去，你读取。
两个队列都在共享内存里，可以一次性提交一批请求，甚至在轮询模式下完全不需要系统调用。IOCP 则是 Windows 的原生模型：请求交给系统，完成时通过完成端口取出。

**对比**：
| | 就绪（epoll/kqueue） | 完成（io_uring/IOCP） |
|---|---|---|
| 内核告诉你 | 可以做了 | 已经做完了 |
| 每个操作的系统调用 | 等待 + `read` 至少两次 | 可批量提交，可降到接近零 |
| 缓冲区 | 就绪时才需要 | 提交时就要备好，完成前不能动 |
| 适用的 I/O | 网络套接字等可轮询的 | 普通文件、磁盘也能异步 |

最后一行很关键：**普通文件对就绪模型无意义**（它们永远“就绪”），所以 epoll 模型下磁盘 I/O 只能扔给线程池；完成模型下磁盘读写也是异步的。

**代价**：缓冲区的所有权要交给内核直到完成，这对 Rust 这样要求借用安全的语言尤其麻烦（取消一个请求时，内核可能仍在写那块内存），tokio 为此专门保持了基于 epoll 的主路径，而用独立的 `tokio-uring` 等实验性运行时做完成模型。Go、Java、Python 的标准运行时在 Linux 上仍以 epoll 为主。
