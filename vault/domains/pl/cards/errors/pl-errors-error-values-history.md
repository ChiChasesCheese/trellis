## Q
Go 的错误处理从 1.0 到今天有哪些演进，为什么语法一直没变？

## A
1. **Go 1.0（2012）**：`error` 接口，`errors.New` 与 `fmt.Errorf`。判断错误只能比较哨兵值或做类型断言。
2. **社区方案**：`pkg/errors` 等库提供包装与栈追踪，成为事实上的标准。
3. **Go 1.13（2019）**：标准库吸收了这些经验：`%w` 动词、`errors.Is`、`errors.As`、`Unwrap` 约定，从此包装和判断有了统一的做法。
4. **Go 1.20（2023）**：`errors.Join` 和多个 `%w`，处理多个错误并存的情形。
5. **语法改进提案**：2018 到 2019 年的 `check/handle` 和 `try` 提案因社区强烈反对被撤回。之后又有多个提案（`?` 风格等）。Go 团队后来表示，在没有出现既简洁又不牺牲显式性的方案之前，不再为错误处理语法接受新提案。
6. **工具化**：`errcheck`、`staticcheck`、`golangci-lint` 在 CI 里补充了编译器没做的强制检查。

为什么语法不变：Go 的价值观是稳定与可读性。`if err != nil` 的冗长是已知的代价，换取的是：任何 Go 程序员都能读懂任何 Go 项目的错误处理，没有各式各样的小方言。

趋势：错误本身的**表达能力**持续丰富（包装、联合、更好的信息），而**控制流的写法**保持不变。与之对比，Rust 和 Swift 选择在语法层面压缩样板。
