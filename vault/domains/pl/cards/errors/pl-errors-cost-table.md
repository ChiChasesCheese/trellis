## Q
C++、Go、Java、Rust、Python 的错误处理在正常路径和失败路径上各花多少？

## A
下表是本机一次测量的量级，用来比较形状，不是基准结论：

| 语言 | 选择 | 正常路径 | 失败路径 |
|---|---|---|---|
| C++ | 异常（表驱动）；或错误码、`std::expected`（C++23，值型返回） | 异常：约 0，`try` 不执行指令；`expected`：约 0.4 ns 的判断 | 异常在 macOS 上栈深 5、20、200 时平均每次调用（一半抛出）约 2.4、5.2、40 µs，即每次抛出约 5、10、80 µs，随栈深线性增长，没有栈追踪也如此（展开本身贵）；`expected` 的失败路径与成功一样便宜 |
| Go | 错误值 | 约 0.5 ns 的判断 | 返回哨兵约 0；`fmt.Errorf("%w")` 包装约 37 ns（含分配） |
| Java | 异常 | 约 0，`try` 不执行指令 | 栈深 20 时约 0.8 µs 每次抛出；无栈追踪时可降到约 ns |
| Rust | `Result` | 约 0.5 ns 的判断 | 同样一次返回，不分配 |
| Python | 异常（3.11+ 零成本 `try`） | 与无 `try` 相同，约 11 ns 每次迭代 | `raise` 加 `except` 约 79 ns，相比返回 `None` 的约 15 ns 贵约 5 倍 |

逻辑：异常语言（C++、Java、Python）的账本是「正常路径免费，失败路径贵」，C++ 的失败路径比 Java 还贵：它没有栈追踪可省，所有时间都花在展开器逐帧查表、匹配、运行析构上（这里是 macOS 上的一次测量，具体数值随平台和展开器实现变化，量级结论不变）；错误值语言（Go、Rust）是「两条路径都便宜」。Java 的失败路径贵，主要因为栈追踪随深度线性增长，Python 的相对代价小，因为本来每次调用就慢。

C++ 同时把两种账本都放进了标准库：异常给罕见失败，C++23 的 `expected` 和错误码给常见失败，由程序员按失败频率选。这就是为什么两种文化对「用错误做控制流」的态度相反：Python 把 `try/except` 当作常规工具（EAFP），因为不抛的时候免费，且 Python 里一次异常也就几十 ns；Java 社区强调不要用异常做控制流，因为在深栈下每次要付出亚微秒到微秒量级，并产生大量垃圾对象。

结论：判断成本不能脱离失败的频率。公式很简单：总成本约等于「调用次数 × 正常路径成本 + 失败次数 × 失败路径成本」。
