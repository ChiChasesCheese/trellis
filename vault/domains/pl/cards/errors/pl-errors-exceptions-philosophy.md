## Q
Java 为什么设计受检异常，后来为什么被广泛认为是失败的？Python 的 EAFP 又基于什么理由？

## A
**Java 的受检异常**基于一个合理的直觉：外部世界不可靠，I/O、网络失败是调用者必须面对的，函数签名应当诚实地说出它可能失败。把它放进类型系统，编译器就能确保没人漏掉。

问题出在实践：
1. **耦合与泄漏**：底层的 `SQLException` 要么一路 `throws` 到顶层，污染所有中间层的签名，要么被包装。每次新增一种异常，调用链上所有的签名都要改。
2. **与函数式不兼容**：`Stream.map(x -> readFile(x))` 里的 lambda 不允许抛受检异常，需要大量包装。
3. **鼓励吞异常**：为了让编译通过，程序员写空的 `catch (Exception e) {}`，结果比不强制更糟。
4. **很多异常其实无法就地恢复**：强制每层处理，不过是强制每层转发。

结论：受检异常的初衷（让失败可见）是对的，但把它做成语言的强制特性，成本大于收益。多数后来的语言（C#、Kotlin、Scala）放弃了它；Java 社区的现代风格是主要使用非受检异常，只在少数真正需要调用者处理的场合保留受检异常。

**Python 的 EAFP** 基于另一套理由：
- 检查再执行（LBYL，Look Before You Leap）有竞态（检查与使用之间文件可能被删），并且常常重复了被调用方本来就要做的检查。
- Python 的异常便宜且常见，`StopIteration` 就是用异常实现的循环终止信号。
- 鸭子类型不预设类型，试一下比查询能力更直接。

**C++ 的异常**基于第三套理由：零开销原则（不用的功能不付钱）。它不替你检查签名，也不要求每层处理，目标只有一个：不抛的时候不付钱。受检异常的前身（运行时检查的 `throw(X)` 规约）被它自己废弃，说明「强制声明」这条路在 C++ 里同样走不通。
所以：Java 是「契约式」的悲观主义，要求在签名里承诺；Python 是「信任式」的乐观主义，出了问题再处理。
