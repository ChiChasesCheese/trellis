## Q
Go 里处理错误的最佳实践是什么？包装、哨兵、自定义类型各在什么时候用？

## A
1. **每一层都加上下文，用 `%w` 包装**：`fmt.Errorf("load user %d: %w", id, err)`。上下文写「在做什么」，不重复底层已经说过的信息。最终的错误信息读起来像一条调用路径：`handle request: load user 7: query: connection refused`。
2. **要么处理，要么返回，不要两者都做**。「记录日志后返回」会让同一个错误被打印多次。
3. **用 `errors.Is` 和 `errors.As` 判断，不要比较 `==` 或字符串**。包装之后 `==` 失效，字符串匹配会随消息改动而坏掉。
4. **哨兵错误**（`var ErrNotFound = errors.New(...)`）用于调用者需要判断的少数状态。**自定义错误类型**用于需要携带数据（字段名、状态码）的场合。二者都是 API，导出前要想清楚。
5. **控制是否暴露底层错误**：`%w` 让调用者可以 `Is` 到底层错误，从而依赖它；如果不想把底层实现泄漏出去（比如数据库驱动的具体错误），用 `%v` 只保留文本。
6. **不要用 `_` 丢弃错误**，除非能写出理由。对 `Close()` 之类的写入型操作，要检查返回值。
7. **错误信息约定**：小写开头、不加句号，因为它们会被拼接到更长的消息里。
8. **库代码不 panic**，不要因为调用者的输入错误而崩溃进程。
9. **在 CI 里启用 `errcheck`/`golangci-lint`**，把忽略错误变成可检测的问题。
10. **多个错误并存时用 `errors.Join`**，例如并行任务各自失败。

什么时候违反：脚本式的小工具里，`log.Fatal(err)` 直接退出就足够，不必构造复杂的错误链。
