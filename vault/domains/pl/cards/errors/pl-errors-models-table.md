## Q
C++、Go、Java、Rust、Python 在错误处理上各选了哪种模型？换来什么，代价是什么？

## A
| 语言 | 选择 | 换来 | 代价 |
|---|---|---|---|
| C++ | 全都有：异常（非受检）、错误码（`errno`、`std::error_code`：数值加所属类别）、C++23 的 `std::expected<T, E>`（装着值或错误的结果类型）、`std::optional`（可能没有值），bug 用 `assert` 与 `std::terminate`（终止进程） | 零成本异常，常见失败可走值型返回；按场景选 | 没有统一约定，库之间风格不同；编译器几乎不强制处理（只有给函数标上 `[[nodiscard]]` 之后，丢弃返回值才会警告） |
| Go | 错误值：多返回值 `(T, error)`，加 `panic` 处理 bug | 控制流显式，每个失败点可见，无隐藏跳转 | 样板多（`if err != nil`），编译器不强制检查 |
| Java | 异常：受检与非受检并存 | 正常路径代码干净，栈追踪自带 | 受检异常（编译器强制调用者处理或在签名里声明）污染签名，且与 lambda（匿名函数）难配合；非受检异常不可见 |
| Rust | `Result` / `Option` 加 `?` 运算符，加 `panic!` | 失败在类型里，编译器强制处理，样板由 `?` 压缩 | 要设计错误类型，转换与组合需要学习 |
| Python | 异常，全部非受检 | 写起来最快，“先做、出错再处理”的风格自然 | 任何调用都可能抛，签名不说明，漏处理要到运行时 |

逻辑：每种选择反映「失败应该有多显眼」。Go 认为失败是程序逻辑的正常一部分，应该和其他值一样被读到、被处理；Java 的设计者想让编译器强制处理失败，但受检异常的实践效果不佳；Rust 保留了强制性，又通过 `?` 和类型把成本降下来；Python 信任程序员，优先写起来快。

C++ 的位置最特殊：它不选一个模型，而是把全部四种都放进语言和标准库，让程序员按失败的频率和代码的约束（比如实时代码关闭异常）自己选，这是零开销原则（不用的功能不付钱）的另一种表现，也是它的代价：一个代码库里经常异常、错误码和 `expected` 混用。五个选择的本质区别，是「谁来确保错误被处理」：Go 和 C++ 靠程序员的纪律和评审（C++ 加上 `[[nodiscard]]` 警告），Java 靠编译器（但只管受检的那部分），Rust 靠类型系统，Python 靠测试和运行时。
