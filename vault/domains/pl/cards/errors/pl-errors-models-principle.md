## Q
一个函数可能失败时，语言要解决什么问题？错误处理有哪几种基本模型，它们沿着哪些轴取舍？

## A
任何会和外部世界或不可信输入打交道的函数都可能失败：文件不存在、网络超时、输入不合法。语言必须回答三个问题：调用者怎么知道失败了？谁有义务处理？不处理会怎样？

设计空间有四种基本模型：
1. **错误码或错误值**（C 的返回 -1 加 `errno`、Go 的 `error`）：失败就是一个普通的返回值，控制流不跳转。
2. **异常**（Java、Python、C++）：失败时抛出，运行时沿调用栈向上寻找处理者，中间的函数不用写任何代码。
3. **代数类型**（Rust 的 `Result<T, E>` 与 `Option<T>`、Haskell 的 `Either`）：返回类型本身说明「成功得到 T，或失败得到 E」，编译器强制处理。
4. **不可恢复错误**（Go 的 `panic`、Rust 的 `panic!`、断言）：表示程序 bug 或状态已损坏，目标是尽快终止，而不是被调用者处理。

它们沿着四条轴取舍：
- **可见性**：失败是否体现在函数签名上？异常（非受检）和 Python 看不到，Go、Rust 看得到。
- **强制性**：忽略错误会怎样？Go 编译器不管；Rust 有警告；Java 受检异常是编译错误。
- **控制流**：失败是正常的返回，还是隐式的非本地跳转？后者让代码短，但阅读时不知道哪里会跳走。
- **成本**：正常路径与失败路径各付出多少。

理解四种模型的关键不是语法，而是：每个选择，都是把「错误处理的负担」放在了不同的人身上：写函数的人、调用的人、或者编译器。
