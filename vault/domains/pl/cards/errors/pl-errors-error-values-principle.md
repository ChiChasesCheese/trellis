## Q
Go 为什么选择把错误做成普通的返回值，而不是异常？这一设计的核心主张是什么？

## A
Go 的设计者对异常的批评集中在一点：**隐藏的控制流**。在带异常的语言里，任何一次函数调用都可能让当前函数在中途跳走，你无法从代码的形状判断哪一行会失败、失败后哪些清理没有执行。随着代码增长，这类不确定性使得推理变难；异常还容易被滥用于常规流程（把「文件不存在」这种预期情况也当成异常）。

Go 的主张叫「错误是值」（errors are values）：
1. `error` 是一个只有一个方法 `Error() string` 的接口，任何类型都可以实现它。
2. 可能失败的函数把 `error` 作为最后一个返回值。调用者**在调用点**检查它。
3. 因为错误只是值，可以用语言已有的所有工具处理它：存进结构体、放进 channel、在循环里累积、比较、包装。
4. 真正的 bug（空指针、越界）才用 `panic`，且约定不跨包边界使用。

好处：
- 控制流显式：函数里每个可能失败的点都在眼前。
- 错误处理逻辑和业务逻辑用同一种语言写，不需要学习独立的机制。
- 成本可预测：一次返回加一个分支。

代价：
- 冗长：`if err != nil { return err }` 在函数里重复出现，是 Go 最常被批评的地方。
- 编译器不强制检查，错误可以被轻易忽略。
- 栈追踪不自带，需要自己在包装时加上下文。

这是一个有意的取舍：Go 宁可让代码啰嗦而清楚，也不要简短而隐晦。
