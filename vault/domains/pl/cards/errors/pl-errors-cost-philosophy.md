## Q
C++ 常说「不要为不用的东西付费」，这条原则怎样塑造了零成本异常？Rust 和 Go 的选择为什么不同？

## A
**零开销原则（zero-overhead principle）**：C++ 的设计信条是，不使用的特性不应该给程序增加任何成本；用到的特性，手写也不会更快。异常模型就是它的产物：正常路径不付费，失败路径随便昂贵，因为失败「应当罕见」。这把成本从最常见的情形转移到了最罕见的情形，在性能上看是最优配置。

代价是**可预测性**：抛出一次要花多久，取决于栈深、展开途中有多少要析构的对象、运行时是否要加载异常表的页。实时系统、游戏引擎、嵌入式因此常常禁用 C++ 异常（`-fno-exceptions`）。

**Rust 与 Go 选择了另一个原则：可预测，成本在代码里可见。** 每次可能失败的调用后面都有一个分支，大家都看得见；失败路径与正常路径一样便宜，没有「偶尔有一次尖峰」的行为。对服务端、实时系统，延迟的分布比平均值更重要，尖峰比慢一点更难接受。Rust 的 `Result` 还享受空位优化，几乎没有额外内存。

**Java 与 Python 把便利放在第一位**：异常让代码短、错误路径不干扰阅读，成本由运行时（JIT、表驱动）尽量吸收。

C++ 社区近年的讨论说明了这条路线的内在张力：Herb Sutter 提出的「确定性异常」（P0709）想让抛出像返回值一样便宜且可预测，等于承认「失败路径昂贵」的契约在大规模工程中是个负担。

总结：错误处理的成本模型反映语言对「平均性能还是尾部延迟」「写代码的人还是读代码的人」的偏好。
