## Q
「区分错误种类，并保留上下文」这件事，Go、Java、Rust、Python 各用什么手段？换来什么，代价是什么？

## A
| 语言 | 选择 | 换来 | 代价 |
|---|---|---|---|
| Go | 错误链加 `errors.Is` / `errors.As`，哨兵值或自定义类型 | 灵活，无新语言机制；可在包装时逐层加上下文 | 靠约定，调用者不知道会收到哪些种类；无自带栈追踪 |
| Java | 异常类层次加 `catch` 按类型匹配，`cause` 链 | 类型层次天然表达种类，栈追踪自带 | 种类过多时层次臃肿；受检异常使签名膨胀 |
| Rust | 枚举：每种错误种类是一个变体，用 `match` 区分 | 种类是封闭集合，编译器检查是否覆盖全部变体 | 要自己定义枚举和类型之间的转换 |
| Python | 异常类层次加 `except` 匹配，`__cause__` 链 | 简洁，栈追踪自带 | 同 Java，签名不声明 |

逻辑：错误种类是否是「封闭集合」决定了合适的表示。Rust 的枚举把集合封死，调用者的 `match` 若漏掉某个变体，编译器会报错，这对库的使用者最友好；Go 的接口加哨兵是**开放**的，库的维护者新增错误种类不破坏兼容，调用者通常只关心少数几个，并用 `errors.Is` 检查；Java 与 Python 的类层次也是开放的，同时多了栈追踪。

Go 的核心取舍是：不为错误设计新机制，只是复用接口、值和函数，所以简单、正交、容易理解，代价是调用者对可能的错误只能靠文档了解。

对 API 设计者的含义：被导出的哨兵值和错误类型，一旦发布就成为 API 的一部分，调用者会依赖它们，不能随意更改或删除。
