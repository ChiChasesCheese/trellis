## Q
资深工程师怎样选择绑定时机？什么时候该「提前绑定」，什么时候该留出可替换的缝隙？

## A
原则：**默认早绑定，只在有明确需求的地方留晚绑定的缝。**早绑定让工具帮你检查和优化，晚绑定让别人（测试、插件、未来的你）能替换实现；缝留得越多，读代码时需要追踪的可能性就越多。

**该留缝的地方：**
- 跨越进程或系统边界的依赖（数据库、网络、时钟、文件系统）：这些在测试里一定要换。在 Go 里定义小接口（消费方定义），在 Java 里用接口加构造器注入，在 Rust 里用泛型参数或 `dyn Trait`，在 C++ 里用抽象基类加 `virtual`，或把依赖做成模板参数（编译期替换的类型），在 Python 里传参数或用依赖注入，而不是依赖猴子补丁。
- 需要运行时选择的策略（压缩算法、序列化格式）：用枚举或接口，不要用字符串反射。

**该早绑定的地方：**
- 热路径上的小函数：Rust 用泛型而不是 `dyn Trait`，Go 在热点处用具体类型而不是接口，Java 把热点类标成 `final` 或让层次保持单态，C++ 用模板，或在 `virtual` 类上标 `final` 让编译器把虚调用改成直接调用（去虚拟化）。
- 常量与配置：能在编译期确定的就写成常量，不要读环境变量后到处传。

**各语言的具体做法：**
- Python：把猴子补丁限制在测试里（`unittest.mock.patch` 作用域内自动还原），产品代码里不要改别人的类；用类型注解和 mypy 把一部分名字错误提前到检查阶段。
- Java：避免在热点处使用反射和动态代理，它们让 JIT 看不到真实调用目标；类层次保持浅。
- Go：不用 `plugin` 包做主要扩展方式，用进程边界（RPC、子进程）。
- Rust：二进制体积敏感时，对冷路径用 `dyn Trait` 换取更少的代码副本。
- C++：对外发布的动态库接口保持窄而稳定（`virtual` 函数的顺序和类的布局都是 ABI，二进制接口约定），内部实现用模板和静态链接。

什么时候违反：做原型、脚本和一次性工具时，晚绑定的开发速度比运行速度重要，没必要提前设计缝隙。
