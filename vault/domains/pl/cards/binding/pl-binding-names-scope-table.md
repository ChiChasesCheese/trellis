## Q
C++、Go、Java、Rust、Python 在作用域粒度、遮蔽规则和闭包捕获方式上各选了什么，这些选择的逻辑是什么？

## A
| 语言 | 作用域粒度 | 局部遮蔽局部 | 闭包捕获 |
|---|---|---|---|
| C++ | 块；`if`、`for` 的头部可以声明只在该语句内有效的变量 | 内层块可以遮蔽外层（编译器选项 `-Wshadow` 才警告）；同一块内重复声明是错误 | 显式捕获列表：`[i]` 复制值，`[&i]` 借用变量；借用的变量先销毁则悬空 |
| Go | 块；`:=` 在当前块新建 | 允许（常见坑） | 捕获变量，必要时升到堆；1.22 起循环变量每次迭代一份 |
| Java | 块 | 禁止 | 捕获值，须 effectively final |
| Rust | 块（块是表达式） | 允许且鼓励 | 按需借用或 `move`，借用检查器验证 |
| Python | 函数（无块作用域） | 不适用（同一函数里同名就是同一变量） | 捕获变量（cell），`nonlocal` 才能改 |

背后的逻辑是各语言对「谁来防止名字相关的错误」的回答不同。

**Java 靠编译器禁止**：不让两个同名局部变量共存，也不让 lambda 看到会变的变量，错误在编译期消失，代价是写法受限。

**Go 靠简短和工具**：允许遮蔽，把检查交给 `go vet` 一类外部工具，换来 `:=` 的简洁。

**Rust 靠类型和所有权**：遮蔽是合法的数据流写法，真正危险的东西（悬空引用、数据竞争）由借用检查器拦截，名字层面不再设限。

**C++ 靠程序员和警告**：遮蔽合法，`-Wshadow` 只是可选的警告；闭包的捕获方式必须自己写在捕获列表里，值或引用二选一，选错引用时编译器不拦，变量销毁后再调用就是未定义行为（标准不规定后果）。显式比 Go 的隐式更清楚，但安全仍靠自觉。
**Python 靠约定**：函数级作用域和动态类型让规则尽量少，代价是循环变量泄漏、闭包晚绑定这类意外只能由程序员记住。

规律：语言越不信任程序员（Java），越多规则写进编译器；越相信类型系统能兜底（Rust），越放开名字的使用。
