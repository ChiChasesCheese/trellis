## Q
Go、Java、Rust、Python 在方法调用、类型、链接和扩展方式上分别选了哪个绑定时机，各自换来什么、失去什么？

## A
| 语言 | 默认绑定时机 | 换来 | 失去 |
|---|---|---|---|
| Rust | 编译时：单态化、静态链接；`dyn` 才是运行时 | 零成本抽象、可内联、错误早发现 | 编译慢、代码膨胀、运行时不能替换实现 |
| Go | 编译时 + 链接时；接口调用走函数表 | 单个二进制、构建快、行为可预测 | 无运行时扩展（没有猴子补丁、插件很受限） |
| Java | 类在首次使用时加载；方法调用晚绑定，JIT 推测式早绑定 | 动态加载、热点性能接近静态语言 | 预热时间、去优化抖动、启动慢 |
| Python | 运行时：名字、属性、导入全是执行时才解析 | 极强的灵活性，测试与插件极方便 | 慢；拼错名字要执行到才暴露 |

规律：**绑定得越早，工具链能做的事越多（检查、优化、单文件部署），运行时能做的事越少。**

各语言的位置由设计目标决定。Rust 要在没有垃圾回收和运行时的前提下做到「抽象不付费」，只能把能决定的都在编译期决定。Go 追求的是简单可预测的构建与部署，所以选择静态链接加最少的运行时魔法。Java 诞生时的目标是「一次编写，到处运行」和可以在运行中加载来自网络的类，晚绑定是前提；等硬件与 JIT 技术成熟，才用推测把性能补回来。Python 把「写起来最快」放在第一位，让一切都可改，性能留给扩展模块（C、NumPy）去弥补。

趋势：晚绑定的语言在引入类型注解（Python）、AOT 编译（Java 的 GraalVM Native Image）；早绑定的语言在补运行时扩展（Rust 的 `dyn`、Go 的 `plugin` 包）。
