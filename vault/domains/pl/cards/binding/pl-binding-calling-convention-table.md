## Q
Go、Java、Rust、Python 在调用约定、栈的管理和栈空间上限上各选了什么，背后的逻辑是什么？

## A
| 语言 | 参数与帧 | 栈的管理 | 深度上限 |
|---|---|---|---|
| Go | 自有 ABI，寄存器传参（1.17 起），无被调用者保存寄存器 | 协程栈从几 KB 起，入口检查，复制扩容 | 默认 1 GB，近乎不会触顶 |
| Java | 字节码帧（局部变量表 + 操作数栈）；JIT 后用原生帧，可内联 | 线程栈大小固定（`-Xss`） | 几万层，超出抛 `StackOverflowError` |
| Rust | 默认 ABI 不稳定，`extern "C"` 用平台 ABI | 线程栈固定；溢出时进程直接中止 | 主线程通常 8 MB，新线程默认 2 MiB |
| Python | 帧对象在解释器数据栈（3.11 起） | 解释器管理 | 人为限制 `sys.getrecursionlimit()`，默认 1000 |

规律：**栈的灵活性与语言的运行时厚度成正比。**

Rust 追求没有运行时，所以栈就是操作系统分的一块固定内存，大小在创建线程时决定，溢出就是进程被终止，由程序员负责不越界。Go 自带运行时和调度器，因此能把栈做成可增长的，换来「廉价的协程」这一核心卖点。Java 的线程直接对应操作系统线程，栈大小固定，所以深递归在 Java 里是真实的风险。Python 在解释器层面主动设了一个上限，宁可早点报一个干净的异常，也不让 C 栈被写穿。

调用约定对程序员是不可见的，但它决定了三件看得见的事：递归能走多深，创建一个线程或协程占多少内存，以及调用一个函数的真实代价。

趋势：各语言在往同一个方向走——用运行时换栈的灵活性（Go 的协程栈、Java 21 的虚拟线程把栈拷到堆上、Rust 的异步状态机把「栈」编译成一个结构体），目标都是让并发任务的栈成本接近于零。
