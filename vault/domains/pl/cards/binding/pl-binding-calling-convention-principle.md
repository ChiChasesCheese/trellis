## Q
一次函数调用在机器层面必须解决哪些问题？调用约定（calling convention）规定了什么，为什么需要它？

## A
CPU 只会顺序执行指令，没有「函数」这个概念。一次调用要让机器完成四件事：

1. **跳过去，再跳回来**：被调用者执行完必须回到调用点的下一条指令，所以要有地方存**返回地址**。
2. **传参数**：调用者把值交给被调用者。
3. **传返回值**：被调用者把结果交给调用者。
4. **不破坏对方的状态**：被调用者要用的寄存器，调用者可能正在用；总得有人负责保存和恢复。

**调用约定**（calling convention）是一份调用者和被调用者共同遵守的契约，规定：参数放在哪些寄存器或栈位置、返回值放哪里、返回地址放哪里、哪些寄存器被调用者必须还原、栈怎样对齐、谁来清理栈。把它放到**二进制层面**的规范叫 ABI（Application Binary Interface，应用二进制接口）。

契约存在的原因：编译器是逐个函数独立编译的，编译 `caller` 时看不到 `add3` 的内部。只要双方按同一份约定生成代码，不同文件、不同库、甚至不同语言编译出的函数就能互相调用。没有约定，每个函数都得知道所有别的函数怎么用寄存器。

设计空间里的关键选择：

- **参数放栈上还是寄存器里**：栈上简单，但每个参数都要写内存再读内存；寄存器快，但数量有限（x86-64 常用 6 个整数寄存器，ARM64 有 8 个），放不下的再溢出到栈。现代 ABI 基本都优先用寄存器。
- **保存寄存器的责任归谁**：调用者保存还是被调用者保存，这是一个平衡调用者和被调用者负担的选择。
- **栈由谁增长**：固定大小的栈还是可增长的栈（Go 的协程栈）。

每个平台一套标准（x86-64 Linux/macOS 的 System V ABI、ARM64 的 AAPCS64、Windows 自己的约定）。Rust 的默认调用约定刻意不做稳定承诺，标 `extern "C"` 的函数才遵守平台 C ABI；Java 和 Python 的虚拟机另有自己的帧布局。
