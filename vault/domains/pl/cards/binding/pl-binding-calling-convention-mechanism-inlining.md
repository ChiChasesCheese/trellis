## Q
函数调用本身有多贵？内联（inlining）怎样把调用约定的开销整个消掉，为什么它的真正价值不止于此？

## A
一次调用的固定开销来自：保存返回地址和需要保存的寄存器、跳转、进入时检查栈、返回时恢复。在现代 CPU 上这只是几条指令。对 Go 做一次基准测试，循环里调用一个只做加法的函数：

```go
//go:noinline
func addNo(a, b int) int { return a + b }
func addIn(a, b int) int { return a + b }   // inlined by the compiler
// BenchmarkNoInline 0.43 ns/op     BenchmarkInline 0.21 ns/op   (one measurement)
```

不内联约 0.43 纳秒，内联约 0.21 纳秒，差别不到 0.3 纳秒，大约一两个 CPU 周期。所以单次调用本身很便宜，不需要为了「省调用」把函数写大。

**内联**是编译器把被调用函数的函数体直接复制到调用点，调用约定完全不再发生：不用 `call`、不用搬运参数、不用栈帧。Go 编译器用 `-gcflags=-m` 报告决定：

```text
./g.go:8:6: can inline sq
./g.go:11:31: inlining call to sq
```

内联的真正价值是**打破函数边界，让后续优化看到全貌**：

1. **常量折叠**：`sq(4)` 内联后变成 `4*4`，直接算成 `16`。
2. **消除分配**：被调用者里创建的对象，如果内联后发现不会逃出调用者，就可以分配在栈上甚至拆成寄存器（逃逸分析与标量替换，需要看到完整的使用）。
3. **删除死代码**：参数是常量时，函数里的分支可以整段删除。

内联不是总有好处。副作用是**代码变大**，指令缓存压力上升；所以编译器用预算控制：Go 按函数体的复杂度打分（预算很小，函数一大就放弃），Java 的 HotSpot 按字节码大小和调用热度决定（小于约 35 字节的方法或热点方法才内联），Rust 的 LLVM 按成本模型，`#[inline]` 只是提示；C++ 的 GCC、Clang 同样按成本模型，`inline` 关键字也只是提示（它真正的作用是允许同一函数在多个文件里定义）。

决定能否内联的还有**绑定时机**：只有调用目标在编译期已知，才能内联。这就是为什么虚方法、接口方法、Python 的任意方法都难以内联，也是为什么 JIT 要先推测调用目标。

结论：调用约定的开销很小，真正的代价是它把优化器的视野切成了一个个函数；内联就是把这些切口缝上。
