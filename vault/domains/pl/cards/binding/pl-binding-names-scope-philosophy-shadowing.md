## Q
同样是「允许遮蔽」，为什么 Go 的遮蔽被当作坑，Rust 的遮蔽却被当作惯用写法，而 Java 干脆禁止？

## A
遮蔽本身只是同一个现象：内层名字盖住外层名字。是否危险取决于**盖住之后，错误能不能被别的机制发现**。

**Go：遮蔽 + 可忽略的返回值 = 静默错误。** `err` 是普通变量，类型是接口，被遮蔽后外层的 `err` 仍是合法的 `nil`，编译器没有理由报错。错误处理依赖「程序员记得检查」，一旦遮蔽，检查对象就换成了另一个变量。

**Rust：遮蔽的是不可变绑定，且类型往往变了。** `let s = s.trim();`、`let n: u32 = s.parse()?;` 这类写法把旧值转换成新值，旧值的类型已不对，误用会被类型检查拦截。不可变默认也消除了「想改外层变量却新建了一个」的歧义：想改必须写 `mut`。

**Java：禁止。** 它不信任「读者能一眼看出是哪个变量」。代价是你要多想一个名字，收益是读任何方法时，一个局部名字在方法内永远只指一个东西。

三种做法的排序可以看成语言对**程序员注意力**的估价：

1. Java 把注意力成本压到最低，规则最多；
2. Rust 用类型系统替程序员记忆，让遮蔽变成零成本的便利；
3. Go 假定程序员会读代码、会用工具，规则最少。

最清晰的对照是 Go 的 `n, err := f()` 与 Rust 的 `let n = f()?;`：前者在块内重新声明会吞错，后者的 `?` 把错误传播做成了语法，名字再怎么遮蔽也丢不掉错误。

C++ 的位置和 Go 接近：内层块遮蔽外层是合法的，靠 `-Wshadow`（编译器的变量遮蔽警告，默认关闭）这个可选警告兜底，而不是语言规则或类型系统。
要记住的一点：评价一个特性不能只看它「允许什么」，要看它周围还有哪些机制承担了安全责任。
