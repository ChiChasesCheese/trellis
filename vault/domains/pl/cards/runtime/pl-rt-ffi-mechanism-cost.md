## Q
一次跨语言调用到底比普通调用贵多少？各语言的代价分别来自哪里？
这对“在循环里每个元素调用一次 C”意味着什么？

## A
实测（Apple Silicon，调用一个 C 动态库里的 `c_add(a, b)`，与同语言里一个简单函数的调用对比；一次测量）：

| 语言 | 普通调用 | 调 C | 代价主要来自 |
|---|---|---|---|
| Rust（`extern "C"`） | 约 0.5 纳秒 | 约 1.0 纳秒 | 只多了经动态库跳转，没有运行时参与 |
| Java（FFM downcall） | 约 0.2 纳秒（可内联） | 约 3.0 纳秒 | 线程状态切换（进入原生/回到 Java）、检查点、不可内联 |
| Go（cgo） | 约 0.5 纳秒 | 约 13 纳秒 | 切到系统线程栈、通知调度器、返回后恢复 |
| Python（ctypes） | 约 28 纳秒 | 约 147 纳秒 | 参数类型转换、构造 C 参数、打包返回值 |

（Python 的 C 内置函数 `math.sqrt` 约 24 纳秒，C 扩展的调用本身比 ctypes 便宜得多，因为没有运行时类型转换。）

结论一：**边界调用比函数调用贵约 3 到 26 倍**，但绝对值是十几到上百纳秒。单次调用的开销可忽略，**在热循环里每个元素调用一次**才是问题：对 1 亿个元素逐个 `cgo` 调用就是 1.3 秒的纯边界开销。

结论二：解决办法是**批量化**——一次调用传一整个数组、返回一整个结果，让边界成本被摊薄。NumPy 的设计原则就是：Python 层一次调用，C 层处理一整块连续内存。

代价的来源（对应各语言的运行时模型）：
- **Rust**：没有运行时，可以按 C ABI 布局，调用等同于普通调用；
- **Java**：JVM 必须知道线程正在原生代码里（GC 需要在安全点停住所有 Java 线程，原生线程不能被卡住），所以进入、返回都要改线程状态；
- **Go**：goroutine 的栈小且可增长，C 需要真正的系统栈，必须切换；调度器还要决定是否让出这个 P；
- **Python**：解释器要把 Python 对象转成 C 类型（`ctypes` 在运行时做，C 扩展编译期做），还要管引用计数。
