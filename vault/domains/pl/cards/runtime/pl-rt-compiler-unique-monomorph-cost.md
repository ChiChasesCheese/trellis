## Q
Rust 的“零成本抽象”到底把成本转移到了哪里？泛型单态化让编译时间和体积付出了多少？
同样的功能用 `dyn Trait` 会怎样？

## A
“零成本”指**运行时**成本为零：泛型函数对每个具体类型各生成一份专用的机器码（单态化，monomorphization），调用可内联，没有虚表查找。作为对比，`dyn Trait`（特征对象）只生成一份代码，调用时通过虚表（函数指针表）在运行时找到具体实现。这笔成本没消失，而是转移到了**编译期**和**二进制体积**。

实验（一次测量）：定义 200 个实现同一个 `Shape` trait 的结构体，每个类型各调用一次下面的函数，对比泛型版本与 `&dyn Shape` 版本（`-O`，两者的输出相同）：
```rust
#[inline(never)] fn total<T: Shape>(xs: &[T]) -> f64 { /* 3 loops calling x.area() */ }
#[inline(never)] fn total(xs: &[&dyn Shape]) -> f64 { /* same body */ }
```
| 版本 | 编译时间 | 二进制 |
|---|---|---|
| 泛型（200 份实例） | 3.75 秒 | 561 KB |
| `dyn Trait`（1 份代码） | 1.78 秒 | 464 KB |

泛型版本编译慢约 2 倍，体积多约 100 KB，也就是每个实例约 0.5 KB。

这背后是一个哲学选择：Rust 选择让**编译器多做功**，使抽象在运行时消失。对比：
- Java 擦除泛型，只生成一份代码，运行时靠 JIT 去优化；
- Go 的泛型用“GC shape 模板 + 字典”折中：同形状的类型共用一份代码，减少体积；
- C++ 模板与 Rust 同路线，同样有编译慢、体积膨胀的问题。

实践上的含义：热路径用泛型（内联收益大），冷路径或接口边界用 `dyn Trait`，在编译时间和体积上省钱；二进制体积敏感时（嵌入式、WASM）要特别留意泛型膨胀。
