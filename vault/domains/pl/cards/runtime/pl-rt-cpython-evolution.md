## Q
CPython 的性能工作近年走了怎样的路线？为什么是“渐进改进”而不是重写？

## A
**约束**：CPython 必须同时保持语言兼容和 C API 兼容（见数据科学生态）。任何激进的改变（换对象模型、换内存管理）都会让数以万计的扩展失效。所以性能工作的策略是：**在不改变外部契约的前提下，一层一层削掉解释器的开销**。

**时间线**（Faster CPython 项目，2021 年起）：
- **3.11**：自适应特化解释器、更便宜的栈帧（调用不再分配 C 栈）、零成本异常（try 块不花钱），平均提速约 25%。
- **3.12**：不朽对象（immortal objects）为之后的去 GIL 铺路；每个子解释器一把 GIL。
- **3.13**：自由线程构建（实验性）与 copy-and-patch JIT（实验性，默认关闭）。
- **3.14**：自由线程构建进入官方支持阶段；新的“尾调用”解释器在支持的编译器（如较新的 Clang）上再快个位数百分比（最初公布的约 10% 有一部分来自对比基线的编译器回归）；实验性 JIT 仍默认关闭，本机测试里它在简单循环上反而比解释器慢。

**反例的另一条路**：PyPy 完全重写了执行引擎（追踪 JIT），纯 Python 代码快一个数量级，但扩展兼容性成了瓶颈，生态没有迁移。教训是：生态的惯性往往大于技术优势。

**趋势**：
1. 解释器内部持续特化与内联缓存，逐步缩小与 JIT 的差距，同时保留可调试性。
2. 并行化通过多条路线推进：子解释器、自由线程，而不是一刀切。
3. 性能关键路径在生态层面下沉到 Rust/C++（Polars、Ruff、pydantic-core），Python 保持“控制层”的定位。
4. 类型注解为未来的优化提供信息，但目前运行时不使用它们。
