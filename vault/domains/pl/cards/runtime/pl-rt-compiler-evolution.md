## Q
编译器的架构这些年有什么变化？LLVM、Go 自研工具链、增量编译各反映了什么趋势？

## A
**共享后端成为基础设施**：LLVM（2000 年代由伊利诺伊大学启动，苹果推动成熟）把“优化器 + 多目标后端”做成可复用的库。Clang、Swift、Rust（以及 Julia、Zig 的早期版本）都用它。新语言不必自己写优化器，直接得到世界一流的代码质量，这是 Rust 能在十年内追平 C++ 性能的重要原因。代价是依赖庞大的 C++ 代码库，编译慢，后端出 bug 时难以修。

**自研后端的反例**：Go 早期用 C 写编译器（来自 Plan 9 工具链），1.5 版（2015）用 Go 重写，并把后端换成 SSA。它选择不用 LLVM，换来可控的编译速度、简单的交叉编译和独立的工具链；放弃的是最前沿的向量化与激进优化。Zig 近年也在做摆脱 LLVM 的自研后端；Rust 社区则有 Cranelift 后端，用于更快的 debug 构建。

**增量化 / 查询化**：现代编译器（rustc 的查询系统、Roslyn、TypeScript 的语言服务）把编译看作缓存的函数调用图：改了一处，只重算依赖它的部分。这是为了 IDE 实时响应，同时也加速了构建。

**并行前端**：rustc 逐步让前端并行；各大编译器都在把“单线程处理一个文件”改成多线程。

**趋势**：
1. 前后端解耦：中间表示标准化（LLVM IR、WebAssembly、MLIR），新语言“借”优化。
2. 编译器与 IDE 一体：编译器同时服务命令行构建和编辑器，需要增量、容错的解析。
3. 运行时优化与提前编译混用：JVM 加 AOT/CDS（类数据共享），.NET 加 ReadyToRun，PGO（按运行 profile 反馈编译）让 AOT 获得 JIT 才有的信息。
4. 构建速度重新被看作产品指标：Go 早就这样做，Rust、Zig、TypeScript（原生移植）都在跟进。
