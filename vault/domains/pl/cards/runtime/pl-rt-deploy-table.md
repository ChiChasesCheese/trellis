## Q
Go、Rust、Java、Python 的典型部署形态各有什么优缺点？
选择它们时，部署方面的收益和代价是什么？

## A
| 语言 | 典型产物 | 优点 | 代价 |
|---|---|---|---|
| Go | 单个静态二进制（可放进 `scratch` 镜像，约 2 MB） | 复制即运行；交叉编译只需两个环境变量；镜像极小 | cgo 会破坏单文件和交叉编译；更新依赖要重新构建 |
| Rust | 原生二进制（可选 musl 静态） | 体积小、无运行时依赖 | 交叉编译和 C 依赖需要工具链配置；构建慢 |
| Java | JAR（可内嵌依赖）+ JVM；或 jlink 运行时；或原生镜像 | 字节码跨平台；生态成熟（构建、监控） | 需要匹配的 JVM；镜像体积大；启动与预热 |
| Python | 源码 + 解释器 + 依赖（wheel） | 零编译、开发快 | 依赖平台相关的二进制；环境要重建；镜像较大；类型与语法错误到运行时才暴露 |

背后的逻辑：
- 部署形态是**语言执行模型的直接后果**：AOT 编译的语言能把一切收进一个文件；虚拟机语言必须带上虚拟机；解释型语言必须带上解释器和源码。
- Go 的设计者有意识地把“部署是一个文件”当作产品特性，所以连 `net` 包都有纯 Go 实现，标准库尽量避开 cgo。
- Java 靠“平台”换取跨平台与动态能力，代价由容器时代的镜像体积和冷启动承担，所以原生镜像、`jlink` 都是在缩小这个代价。
- Python 的难点不在自己的代码，而在**带 C 扩展的依赖**：wheel 与平台、Python 版本、ABI 绑定，换一台机器就可能装不上或行为不同。
- 容器把四者的差别压缩到镜像大小与构建流程，但没有抹平“能否静态链接、能否交叉编译”这些语言层面的差异。
