## Q
Go 和 Rust 的“静态二进制”为什么启动只要几毫秒？GraalVM 原生镜像（Native Image）想把同样的做法用到 Java 上，它是怎样做到的，又放弃了什么？

## A
**静态二进制**：Go 和 Rust 的编译产物是一个已经链接好的机器码可执行文件，里面包含你的代码、依赖库和（Go 的）运行时。启动流程只剩：操作系统映射文件 → 运行时初始化（Go 建堆、启动调度器和 GC 后台线程；Rust 几乎没有运行时，只有 `main` 之前的少量初始化）→ 直接进入 `main`。没有类加载、没有解析、没有预热，因为机器码在构建时就编好了。

实测（Apple Silicon，Hello World，20 次取中位数，一次测量）：
| 语言 | 启动 | 最大常驻内存 | 文件大小 |
|---|---|---|---|
| Rust（`-O`） | 约 2.1 毫秒 | 约 1.8 MB | 约 460 KB（去符号后约 335 KB） |
| Go | 约 2.7 毫秒 | 约 4.2 MB | 约 2.3 MB（去符号后约 1.5 MB） |
| Python | 约 7.6 毫秒 | 约 16 MB | 另需解释器 |
| Java | 约 24 毫秒 | 约 40 MB | 另需 JVM |

**GraalVM 原生镜像**：在构建时对整个应用做**封闭世界分析**（closed-world analysis）——从 `main` 出发，找出所有可达的类和方法，只编译这些，连同一个精简的运行时（GC、线程）打包成一个原生可执行文件。启动时不再加载类、不再解释、不再预热，因此启动可降到十毫秒量级、内存占用大幅下降。（本机没有安装 GraalVM，此处不给出数字。）

**放弃的东西**：
1. **动态性**：反射、动态代理、`ClassLoader` 加载、序列化，在构建时必须提前声明（配置文件或框架辅助），否则运行时找不到。
2. **JIT 的稳态优化**：没有运行时 profile，峰值吞吐通常低于 HotSpot，可用 PGO 弥补。
3. **构建代价**：构建慢（分钟级）、占内存大，调试与观测手段不同于普通 JVM。

这是同一个权衡的两端：**越早确定（构建时），启动越快、越小；越晚确定（运行时），越灵活、稳态越强。**
