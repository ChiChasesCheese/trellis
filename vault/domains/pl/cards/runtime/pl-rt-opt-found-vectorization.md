## Q
自动向量化（auto-vectorization）是什么？为什么在 Rust 里对 1000 万个元素求和，整数版本比 `f32` 版本快约 10 倍？

## A
现代 CPU 有 SIMD 指令（single instruction, multiple data）：一条指令同时处理 4 个 32 位数（ARM 的 NEON 是 128 位寄存器，x86 的 AVX2 是 256 位）。**自动向量化**是编译器把标量循环改写成 SIMD 版本，源码一个字都不用改。

Rust（`-O`）求和的汇编，整数版本：
```
ldp   q4, q5, [x8, #-32]     ; 一次载入 8 个 i32
add.4s v0, v4, v0            ; 一条指令加 4 个 i32，共 4 个累加器
```
`f32` 版本却是逐个顺序累加：`fadd s0, s0, s1; fadd s0, s0, s5; ...`。

**原因**：整数加法满足结合律，编译器可以把 `a+b+c+d+...` 重排成多个累加器并行相加，最后合并，结果不变。浮点加法**不**满足结合律（舍入误差随顺序而变），重排会改变结果，违反“可观察行为不变”，所以编译器不敢做；除非你开 `-ffast-math` 之类放宽语义的选项，或手写多累加器版本。

一次测量（1000 万元素求和，每次遍历的耗时）：
| 实现 | 整数 | `f32` |
|---|---|---|
| Rust `-O`（LLVM 向量化） | 约 0.46 ms | 约 4.5 ms |
| Go（`gc` 不自动向量化） | 约 2.2 ms | 约 5.3 ms |
| Java（HotSpot C2） | 约 2.1 ms | 约 4.6 ms |

另外，Python 的内置 `sum(list)` 约 14.7 ms，因为每个元素是堆上的对象，没有连续内存可供 SIMD；Python 的做法是把循环交给 NumPy 这样的 C 库，由库内部使用 SIMD。

结论：**向量化是 LLVM 这类重型优化器的专长**；Go 的编译器为了编译速度不做它。写数值热点时，要把数据放在连续数组里、避免循环间依赖，浮点归约想要快就手工分块。
