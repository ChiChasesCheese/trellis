## Q
Go 的编译器为什么刻意只做“适度”的优化？这一选择反映了 Go 怎样的价值观，换来什么、损失什么？

## A
对照数据：
- 在构建速度上，同样的 3000 个小函数，`go` 约 0.25 秒，`rustc -O` 约 3 秒（一次测量）。
- 在运行速度上，1000 万个 `int32` 求和，Go 约 2.2 ms 一遍，Rust 约 0.46 ms，慢约 5 倍，原因是 Go 不做自动向量化。
- 内联预算只有 80 的成本，稍复杂的函数就不内联。

这不是“没做到”，而是**选择**。Go 把几件事放在极致性能之上：
1. **编译速度是产品特性**：Go 诞生于等 C++ 构建的痛苦。优化 pass 越多越慢，所以每加一个都要问值不值得。
2. **性能可预测**：简单的优化器行为容易推理；`-m` 输出能直接告诉你哪个函数没被内联，因为规则只是一个成本阈值，而不是几十个相互作用的 pass。
3. **编译器自己要简单**：自研后端（SSA）代码量小，容易维护、交叉编译、跟随语言演进；不依赖外部 LLVM。

代价是一类热点代码（数值计算、紧凑循环、SIMD）达不到 C/Rust 水平。Go 的补救方式很有一贯性：不去让编译器更聪明，而是**把信息喂给它**——1.21 起的 PGO 让生产 profile 指导内联与去虚化；真正需要 SIMD 就写汇编或调用库。

价值观的对照：Rust 相信“编译器可以为我做得更多，慢一点没关系”；Go 相信“编译器只做它能快速做、且我能预测的事”；Java 相信“运行时最了解程序”。这三种信念是它们各自生态里工具、基准和性能文化的来源。
