## Q
Go、Java、Rust、Python 的代码默认怎样被“接起来”？各自的 ABI 稳定性策略是什么，换来什么、付出什么？

## A
| 语言 | 默认链接/加载方式 | 稳定的“边界” | 换来 | 代价 |
|---|---|---|---|---|
| Go | 静态，自带链接器，纯 Go 程序单文件 | 源码兼容；对外边界是 C ABI（cgo） | 部署最简单，交叉编译只要换两个环境变量 | 用 cgo 即失去纯静态和快速构建；官方 `plugin` 包限制多（版本、构建参数必须完全一致），实际很少用 |
| Java | 类在**首次使用时**由类加载器加载并解析、链接 | 类文件格式与 Java 语言规范里的二进制兼容性规则 | 库可以独立升级，同一个 jar 在任何平台上运行；增量发布方便 | 链接错误推迟到运行时（`NoSuchMethodError`），要靠测试发现 |
| Rust | Rust 依赖静态链接；对系统库动态 | 不稳定，只有 `extern "C"` + `#[repr(C)]` 是稳定的 | 编译器可自由改布局，优化空间大 | 无法发布 Rust 共享库插件体系；跨版本要重新编译全部依赖 |
| Python | 运行时 `import`，C 扩展是 `.so`/`.pyd` | 完整 C API 随版本变化；`abi3` 受限 API 跨小版本稳定 | 灵活，动态；`abi3` 轮子可跨 Python 版本 | 每个 Python 小版本要发一批二进制轮子，或者放弃部分 C API |

逻辑：
- **Go 和 Rust 的哲学一致**：把依赖在构建时全部确定，运行时没有意外。区别是 Go 把“链接器、运行时、构建”整合成一个工具，Rust 把“可以随意优化”放在“稳定接口”之上。
- **Java 把链接推迟到运行时，是为了让库独立演化**。这也是它能支撑大型企业生态（几百个 jar 各自版本）的原因，同时让二进制兼容性成为库作者需要严格遵守的规则。
- **Python 的 C 扩展生态**依赖解释器内部结构，每次解释器升级都要重新适配；`abi3` 是为了缓解它而出现的折中。
