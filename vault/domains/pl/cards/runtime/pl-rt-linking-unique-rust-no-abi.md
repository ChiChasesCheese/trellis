## Q
Rust 为什么宁愿没有稳定 ABI？这一选择换来了什么，和 Swift 的“稳定 ABI”相比，各自付出什么代价？

## A
稳定 ABI 的实质是**承诺不再改布局**：结构体字段顺序、枚举编码、调用约定一旦发布就永远不变，这样不同时间、不同编译器编译的代码才能链接在一起。Rust 选择不做这个承诺，把这份自由用在优化上。

**换来的优化（实测）**：
1. **字段重排**：`struct { a: u8, b: u32, c: u8 }` 默认 8 字节，按 C 布局则 12 字节。
2. **利用空值做“空槽”优化**（niche optimization）：`Box<u64>` 永远非空，所以 `Option<Box<u64>>` 用空指针表示 `None`，大小仍是 8 字节；而 `Option<u64>` 没有哪个值可以空出来，需要额外的标记，所以是 16 字节。实测输出：`Box<u64>=8 Option<Box<u64>>=8 u64=8 Option<u64>=16`。
3. 泛型单态化后，每个具体类型都可以选最合适的布局和调用方式，不受固定约定限制。

**代价**：不能把 Rust 编译的库作为稳定的共享库发布让其他版本的 Rust 代码动态加载；插件系统要走 C ABI（`#[repr(C)]` + `extern "C"`），或者用 `abi_stable` 这样的库；所有依赖每次都随工具链重新编译，这也是 Rust 构建慢的原因之一。

**Swift 的相反选择**：Swift 5.0（2019）在 Apple 平台冻结 ABI，因为苹果需要把 Swift 标准库放进操作系统、让所有 App 共享。为了在库升级后仍能兼容，Swift 引入了“库演进”（resilience）机制：跨库边界的类型字段访问要走间接调用，禁止了许多内联与布局优化，性能和灵活性要为兼容性让路。

**价值观**：Rust 的选择是“让工具链和所有依赖作为一个整体编译，换取最优结果”，适合服务器和嵌入式；Swift 的选择是“让操作系统与应用能独立升级”，适合平台型生态。二者的 ABI 策略，反映的是**谁拥有整套软件的升级节奏**。
