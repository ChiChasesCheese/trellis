## Q
为什么近年各语言的性能工作都在向“内存布局”和“批量化”靠拢？
这个趋势背后的硬件事实是什么？

## A
**硬件事实**：CPU 的计算速度在过去三十年增长远快于内存访问速度，这个差距叫“内存墙”（memory wall）。今天一次缓存未命中相当于几百条指令的时间，现代处理器靠大缓存、预取和向量指令（SIMD）掩盖，但前提是数据**连续、可预测**。

**因此性能问题的重心从“指令数”转到“内存访问模式”**，这影响了语言的演进：
1. **Java**：Project Valhalla 引入值类（value class）和原始类型泛型，目标是让 `List<Point>` 像 `Point[]` 一样连续、无对象头；同时改进对象头压缩（紧凑对象头）和 GC（ZGC、Shenandoah 低暂停）。
2. **Python**：向量化生态（NumPy、Arrow、Polars）把“按列连续存储”做成主流；解释器本身通过自适应特化与内联缓存削减开销，JIT 在实验中。
3. **Go**：保持值语义结构体、切片；GC 持续降低暂停并加入内存限制；编译器改进内联与逃逸分析，PGO 帮助去虚化。
4. **Rust**：数据导向设计成为社区惯用法（ECS 游戏引擎、`Vec` 优先）；SIMD 库、`std::simd` 在稳定化。
5. **面向数据的设计**（data-oriented design）：从游戏行业扩散到数据库与服务端，按访问模式而不是按“现实世界的对象”组织数据。

**批量化的趋势**：边界（FFI、系统调用、网络往返、GPU 调用）的固定成本不下降，所以接口越来越倾向批量：批量 API、列式格式、向量化执行引擎、`io_uring`。

**异构计算**：真正大规模的数据并行在 GPU 和专用加速器上，语言通过“把计算描述交给编译器/运行时”（JAX、PyTorch 的编译模式、Mojo）而不是自己执行。

**给工程师的结论**：
- 评估一个设计时，先画出它的**内存访问路径**；
- 把“每个元素一个对象”的设计，换成“连续数组加索引”，往往是最大的杠杆；
- 语言在慢慢缩小这些差异，但在 Valhalla 这样的特性落地并普及之前，Java 和 Python 的使用者仍然需要自己管理数据布局。
