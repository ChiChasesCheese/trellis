## Q
同样是 `s += i` 这样的热循环，Python、Java、Go、Rust 的执行方式差在哪里？为什么差距是几十倍？

## A
| 语言 | 怎么执行 | 每次迭代的主要成本 | 量级 |
|---|---|---|---|
| Python（CPython） | 字节码解释，整数是堆对象 | 分派 + 类型检查 + 可能的对象分配 + 引用计数 | 约 12 纳秒 |
| Java | 先解释，热点被 JIT 成机器码 | 稳态时寄存器加法，向量化展开 | 约 0.23 纳秒（稳态） |
| Go | 提前编译成机器码 | 寄存器加法，循环计数器自增 | 约 0.2 纳秒 |
| Rust | 提前编译，LLVM 可能向量化 | 同上；LLVM 常把整个循环折叠成公式，强制保留循环（`black_box`）后约 0.9 纳秒 | 约 1 纳秒以下 |

（四个数字都是本机对 20 亿或 2000 万次迭代的一次测量；标量循环极简，编译器的展开与向量化决定了小数点后的差别，重点是和 Python 的数量级差距。）

背后的逻辑：
- 差距的来源是三件事的叠加，而不是某一件事：**解释**（每条指令一次分派）× **装箱**（整数是对象）× **动态类型**（每次操作要查类型）。静态类型的编译型语言一次消除这三项：类型在编译期已知，整数放寄存器，指令直接执行。
- 所以 Python 慢，**在循环体里做很少事情的代码上最明显**；如果每次迭代本来就要调用一个大的 C 函数（排序、正则、矩阵乘法），解释开销被摊薄到可以忽略。
- 这就是 Python 的分工：用 Python 描述“做什么”，把“怎么高速地做”交给 C/Rust 实现的内核。
- Java 在稳态下能追上 AOT，但要付出预热；Python 的自适应解释器和实验性 JIT 想缩小差距，而非消除。
