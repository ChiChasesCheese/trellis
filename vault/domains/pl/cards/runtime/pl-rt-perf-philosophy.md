## Q
各语言对“性能”这件事持什么态度？为什么 Python 社区说“先写对，再决定要不要快”，而 Rust 社区说“性能是特性”？

## A
**Rust：性能是语言契约的一部分。** 设计目标是“不比手写 C 慢，且更安全”，所以抽象必须零成本，没有运行时，布局可预测。性能不是靠优化器碰运气，而是由语言规则**保证**的：没有隐藏的分配、没有隐式拷贝、没有 GC 暂停。代价是你要把性能相关的决定（谁拥有、谁借用、是否分配）写在代码里。

**C++：性能是第一原则，安全让位。** 零开销原则（不用的不付费，用到的手写也不会更快）是语言的设计纲领，内存布局、分配、内联都由程序员控制。价值观是“信任程序员”：语言不替你检查边界、不替你管内存，换来最大的控制权。代价是错误无声（未定义行为）和对程序员水平的依赖。

**Go：性能够用、可预测、可诊断。** 不追求榨干最后 10%，而追求没有意外：GC 暂停短，调度器公平，编译器简单，工具（pprof、trace、`-race`）内置。态度是：先把正确、清晰的版本写出来，用 profiler 找瓶颈，不靠猜。

**Java：性能来自平台。** 程序员写面向对象的清晰代码，JIT、GC、逃逸分析在运行时优化。“热点自己会变快”，代价是预热、不确定性和内存。态度是：**运行时比你更了解程序**，所以不要手工优化 JVM 能做的事，用 JMH 验证。

**Python：开发者的时间比 CPU 的时间贵。** 性能不是语言的目标，生态的做法是把热点交给 C/Rust。态度是：先写正确，量出瓶颈，再把那一小块换成向量化或原生扩展。

这些态度的共同教训，也是资深工程师的准则：
1. **“过早优化是万恶之源”不是不要优化，而是要在剖析之后优化**，对象是量出来的热点。
2. **性能的主要杠杆按顺序是**：算法与数据结构 → I/O 与并发结构 → 内存布局与分配 → 语言与运行时的常数因子。把第四项当成第一项，是最常见的错误。
3. **选语言要看目标负载的瓶颈在五类成本的哪一类**，而不是看一个笼统的“快慢”排名。
