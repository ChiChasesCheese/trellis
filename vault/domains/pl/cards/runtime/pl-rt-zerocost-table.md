## Q
Rust、Java、Go、Python、C++ 里“抽象的代价”分别出现在哪里？各自用什么方式（编译器、JIT、不管）处理？

## A
实测对象：50M 元素（Python 为 10M）里挑偶数求平方和，分别用手写循环与更高层的写法（一次测量）。

| 语言 | 抽象的代价在哪 | 消除办法 | 实测 |
|---|---|---|---|
| Rust | 编译时间、二进制体积；`dyn` 与 FFI 边界 | 单态化 + 内联 | 迭代器链 6.6 ms = 手写 6.7 ms；`dyn Fn` 17.5 ms |
| Java | 装箱、对象分配、虚调用；预热期 | JIT 内联、逃逸分析 | 手写 `int[]` 循环 16.7 ms；`IntStream` 11.2 ms；`Stream<Integer>` 19.1 ms |
| Go | 接口调用与闭包通常不内联；泛型用字典 | 编译器内联小函数，PGO 可去虚化 | 手写 22–26 ms；函数值 16–18 ms；泛型 21 ms |
| Python | 每层抽象都是真实的调用与对象 | 不消除，交给 C 内核 | 循环 151 ms；生成器表达式 146 ms（10M） |
| C++ | 编译时间、体积（模板膨胀）；虚函数、`std::function` 的间接调用 | 模板单态化 + 内联（`-O2`） | 手写 6.7 ms；`std::accumulate` 6.6 ms；ranges 视图 15.8 ms；`std::function` 32 ms |

背后的逻辑：
- **Rust** 把“消除抽象”放在编译期且是**确定性的**：写法对了就一定得到手写级别的代码；代价是编译慢、体积大，以及 `dyn` 之外的抽象要求编译器看见具体类型。
- **C++** 是这条路线的发明者，规则与 Rust 相同，但“写法对了就一定得到手写级别”并不总成立：本机 50M 元素同一任务，STL 算法 `std::accumulate` 与手写循环同速（都被向量化），而 C++20 的 ranges 视图版本慢约 2.4 倍，`std::function` 版本慢约 5 倍（一次测量）。零开销原则承诺的是“不用的不付费”和“手写不会更好”，而不是“任何高层写法都等于手写”，所以要靠基准确认。
- **Java** 把它放在运行时且是**概率性的**：热点稳定时 JIT 能把流水线编译得和循环一样好（本机 `IntStream` 甚至更快，因为 JIT 做了向量化），但依赖预热，且装箱类型（`Stream<Integer>`）有额外对象成本。
- **Go** 选择**可预测、简单的编译器**：不做 Rust 那样激进的跨层融合，因此高层写法不一定与手写一样快，但差距小、性能容易预估（上述 Go 数字在噪声范围内）。
- **Python** 不尝试：抽象的每一层都有开销，但因为循环本来就慢，抽象的相对开销反而看不出来。
