## Q
链接器还做哪些事影响二进制大小和构建速度？“死代码剥离”、LTO 和 `-s -w` 各改变了什么？

## A
链接器除了匹配符号，还负责**裁剪**。按函数或数据分段编译（C 的 `-ffunction-sections`，Go 和 Rust 默认如此）时，链接器从入口出发标记所有可达的符号，**没被引用的整段丢弃**。这就是 Go 里 `import "fmt"` 不会把整个标准库带进来的原因：Go 的链接器会剥离不可达函数。

**符号表和调试信息占体积**。同一个 hello world（一次测量，macOS ARM64）：
| 构建 | 大小 |
|---|---|
| Go `go build` | 约 2.43 MB |
| Go `-ldflags="-s -w"`（去符号表和 DWARF 调试信息） | 约 1.59 MB |
| Rust `rustc -O` | 约 470 KB |
| Rust `-C strip=symbols -C lto` | 约 303 KB |

Go 去掉符号后小了约三分之一；代价是崩溃堆栈里仍有函数名（Go 运行时自带一份），但 `pprof`、调试器会少信息，所以通常把带符号的版本留档，发布去符号的版本。

**LTO**（Link-Time Optimization，链接期优化）：普通编译优化只在一个编译单元内进行，跨单元的调用被迫保持原样。LTO 把各单元的 IR 留到链接时再一起优化，于是跨 crate 的函数也能内联、整个程序中没用的函数可以删除，代价是链接变得慢得多、内存占用大。Rust 里是 `lto = "thin"` 或 `"fat"`；Go 的链接器不做这件事，编译时整包优化。

**链接速度**本身也是大型项目的瓶颈：Rust 增量构建的大头往往是链接，所以社区换用 `lld` 或 `mold`，链接比系统默认的快数倍；Go 因为自带链接器并只带必要的代码，链接通常是亚秒到几秒。

要点：二进制大小不只是代码量，更是**“默认带着多少运行时”加上“链接器丢掉多少”**。嵌入式、WASM、Lambda 冷启动这类体积敏感场景，要主动开启裁剪和去符号。
