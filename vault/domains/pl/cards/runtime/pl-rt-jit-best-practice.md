## Q
在有 JIT 的平台上，资深工程师怎样处理预热、基准测试和代码结构，才能让 JIT 发挥作用？

## A
**服务端长期运行（Java）**：
1. **预热是成本，要被纳入设计**。滚动发布后新实例前几分钟的延迟更高：用预热请求或流量渐进放量（慢启动），而不是一上线就吃满流量。需要缩短预热时，看 CDS / AppCDS（类数据共享）与 JDK 新的 AOT 缓存特性（Leyden 项目），以及 GraalVM 原生镜像。
2. **别在热路径上破坏 JIT 的假设**：
   - 保持调用点的类型单态或双态，避免在紧循环里用多种实现的接口；
   - 让热方法保持小（HotSpot 对字节码大小有内联阈值，约几十到几百字节）；
   - 避免在热路径用反射、异常做流程控制、过度装箱。
3. **不要乱调 JVM 参数**。默认的分层编译已经很好；`-XX:TieredStopAtLevel=1`（只用 C1）适合短命的工具进程，换取更快启动，放弃峰值性能。
4. **用 JMH 做基准**：它处理预热、多次 fork、防止死代码消除和常量折叠。手写 `System.nanoTime()` 的循环常常测量到的是编译器的行为，而不是你的代码。
5. 生产里看 JIT 日志与指标（`-XX:+PrintCompilation`、JFR 的编译事件、代码缓存使用率），代码缓存满会让 JIT 停止，性能突降。

**Python**：
- 追求性能：优先换算法和向量化库；纯 Python 的热循环确实能用 PyPy 提速，前提是依赖都兼容。
- CPython 自带的 JIT 当前是实验性的，除非有实测收益不要开。

**Go / Rust**：没有 JIT，不存在预热；若要“根据运行时数据优化”，用 PGO（Go 的 profile-guided optimization、Rust 的 `-C profile-use`），用生产 profile 喂给编译器。

什么时候打破：延迟极其敏感的系统可以主动预热并固定编译，或选 AOT 语言来避开抖动。
