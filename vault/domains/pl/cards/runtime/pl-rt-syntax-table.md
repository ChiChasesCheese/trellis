## Q
Go、Java、Rust、Python、C++ 的语法设计和解析器实现各站在“人好写”与“机器好解析”轴上的哪一点？

## A
| 语言 | 解析器 | 语法上的关键选择 | 换来 | 代价 |
|---|---|---|---|---|
| Go | 手写递归下降 | 词法层自动补分号、5 级优先级、泛型用 `[]` | 解析极快（单个记号前瞻），`gofmt` 能把格式固定成一种 | `{` 不能另起一行，换行位置影响语义 |
| Java | 手写递归下降（`javac`） | 沿用 C 系语法，`<>` 靠位置消歧，`>>` 要拆分 | 对 C/C++ 程序员零学习成本 | 为兼容旧语法积累了许多特例，泛型位置规则繁琐 |
| Rust | 手写递归下降 | 类型位置 `<>`、表达式位置 `::<>`，比较不可链式，表达式基于块 | 不需要符号表就能解析，报错可以带修复建议 | turbofish 看起来奇怪，语法面大（宏、模式、生命周期） |
| Python | PEG 生成（3.9 起） | 缩进即块，比较链，软关键字 `match` | 书写最短，视觉与结构一致 | 缩进即语义，Tab/空格敏感，语法随版本增长 |
| C++ | 手写递归下降（Clang、GCC），但必须带着符号表解析 | 沿用 C 的文法，`<>` 既是比较又是模板括号，`T * x;` 是乘法还是声明取决于 `T` 是不是类型 | 与 C 源码和库完全兼容 | 文法上下文相关，解析必须先知道名字的含义；难写工具、报错难读、最令人困惑的解析（most vexing parse）等 |

背后的逻辑：**每门语言的语法都是它的优先级的第一个落点**。Go 要在巨型代码库里快速构建，所以先保证语法无需回溯，格式也由语言收口；Java 要吸引 C++ 程序员，沿用熟悉的形状，并把兼容性债务留给解析器；Rust 要在表达力很强（泛型、模式、宏）的同时保持可解析，所以宁可让用户多写 `::<>`；Python 把“读起来像伪代码”放在第一位，并且在 3.9 换成能回溯的 PEG 解析器，才让 `match` 和括号里写多个 `with` 这类原来无法用 LL(1) 描述的语法成为可能。C++ 是“兼容优先”的极端：它要把四十年的 C 代码原样编译，文法因此是上下文相关的，一个声明和一个表达式可能写得一模一样，只有查过符号表才能分辨；这是 Go 的“工具友好”约束要避开的东西，也是 C++ 工具链至今难写的原因，编译器不得不把解析和语义分析交织在一起。
