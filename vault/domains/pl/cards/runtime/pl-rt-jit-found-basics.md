## Q
解释器、编译器和 JIT 编译器分别是什么？它们执行同一个循环的成本模型有什么区别？

## A
**解释器**（interpreter）：读一条指令（源码、AST 或字节码），立刻用自己的代码执行它，再读下一条。每执行一次循环，都要重新“取指令、识别是什么指令、跳到对应的处理代码”。没有准备阶段，启动快；执行慢。

**编译器**（AOT，Ahead-Of-Time，提前编译）：运行前就把整个程序翻译成目标 CPU 的机器码，运行时 CPU 直接执行，没有“识别指令”的开销，还能在翻译时做全局优化。启动即全速；但翻译时不知道程序运行时的真实情况。

**JIT**（Just-In-Time，即时编译）：程序一开始用解释器跑，同时**统计哪些代码被执行得最频繁**，把这些“热点”在运行中编译成机器码，之后直接执行机器码。

一个循环的成本模型（计数 0 到 40 万的素数，本机一次测量）：
- 纯解释（`java -Xint`）约 93 毫秒；
- JIT 后的稳态约 12 到 15 毫秒；
差约 6 到 7 倍。解释执行时每次迭代要付“分派开销”；JIT 把循环体变成了一段连续的机器码。

时间线上的取舍：
| | 启动 | 稳态速度 | 优化依据 |
|---|---|---|---|
| 解释器 | 最快 | 最慢 | 无 |
| AOT 编译 | 快 | 快 | 只有源码信息 |
| JIT | 慢（要预热） | 快，可能超过 AOT | 源码 + 运行时观测 |

JIT 的两个特点：
1. **预热**（warm-up）：程序刚启动时，热点还没被发现、没编译完，速度是慢的；
2. **编译本身占资源**：JIT 编译在后台线程里消耗 CPU 和内存。

Java 的 HotSpot 虚拟机、JavaScript 的 V8、.NET 的运行时都是这个模式；Go 和 Rust 是纯 AOT；CPython 以解释为主，近年在试验 JIT。
