## Q
同一个“依赖的闭包”在五门语言里分别在什么时候、由谁解析并固定下来？这对产物体积和可复现性意味着什么？

## A
部署时真正重要的问题是：**程序运行所需的全部东西，是在构建时就固定、还是运行时才去找？**

| 语言 | 依赖在何时固定 | 运行时还要找的东西 |
|---|---|---|
| Go | 构建时：模块版本由 `go.mod`/`go.sum` 锁定，源码编译链接进二进制 | 几乎没有（纯 Go） |
| Rust | 构建时：`Cargo.lock` 锁定，静态链接 Rust 依赖 | 系统 C 库（glibc 等）、动态链接的本地库 |
| C++ | 构建时编译并链接自己的代码；第三方库由包管理器或系统决定（没有统一标准），共享库在启动时由动态链接器**按名字和版本**查找 | 系统的 C/C++ 运行库、动态链接的共享库（版本必须匹配） |
| Java | 构建时选版本（Maven/Gradle），运行时靠类路径（classpath）**按名字**加载类 | 一个兼容的 JVM、类路径上的每个 JAR |
| Python | 安装时解析并装进 `site-packages`，运行时 `import` **按名字**搜索 `sys.path` | 解释器、所有包、平台匹配的二进制轮子 |

机制要点：
- **构建时固定**（Go、Rust）：产物包含一切，复现性强，产物大。依赖更新要重新构建；漏洞库升级要重新发版。
- **运行时按名字查找**（Java、Python）：类路径或 `sys.path` 上第一个匹配的名字生效。两个版本的同名类都在路径上时，哪个先生效取决于顺序，这类“依赖冲突”在 Java 叫 classpath hell，在 Python 叫版本冲突。产物小，但运行结果取决于环境。
- C++ 介于两者之间：自己的代码在构建时固定，共享库在运行时按名字查找；缺哪个版本，就在启动时报 `GLIBCXX_x.y.z not found` 这类错误。静态链接可以把它变成 Go/Rust 的形态。
- Java 9 的模块系统（JPMS）和 `jlink` 让这个依赖闭包能在构建时显式固定；Python 用 `uv.lock`/`pip-tools` + 哈希锁定安装结果，用虚拟环境隔离。

实测的体积量级（一次测量）：Go 静态二进制 1.5 MB（含运行时，去符号后）；Java 完整 JDK 约 294 MB，`jlink` 的 `java.base` 最小运行时约 45 MB；Python 基础安装约 76 MB，一个 numpy 的环境约 22 到 56 MB（因平台而异）。

结论：自包含产物的“体积”是为“可复现、少依赖目标环境”付的价。
