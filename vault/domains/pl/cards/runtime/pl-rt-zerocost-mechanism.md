## Q
Rust 的迭代器链 `filter().map().sum()` 为什么能和手写的 `for` 循环一样快？一旦把闭包放进 `dyn Fn`，会发生什么？

## A
机制是**单态化 + 内联 + 优化器融合**：
1. 每个闭包在 Rust 里是一个独有的匿名类型。`iter().filter(f).map(g).sum()` 的每一层适配器是一个泛型结构体，被单态化成包含具体闭包类型的专用代码。
2. 所有调用目标在编译期已知，LLVM 把 `next()`、闭包体全部内联到同一个函数里。
3. 内联之后，优化器看到的是一个简单循环，可以做循环融合、消除中间对象，甚至向量化。迭代器适配器本身没有堆分配，只是栈上的小结构，最终被拆成寄存器。

实测（50M 个 `u64`，求偶数的平方和，`-O`，两轮稳态取值，一次测量）：

| 写法 | 耗时 |
|---|---|
| 手写下标循环 | 6.7 ms |
| 迭代器链（filter + map + sum） | 6.6 ms |
| 每个元素调用 `&dyn Fn(u64) -> u64` | 17.5 ms |

迭代器链与手写循环几乎完全一样。

`dyn Fn` 不同：调用目标要在运行时通过虚表查找，编译器看不到闭包体，**无法内联**，也就无法融合、向量化，每个元素多一次间接调用，慢约 2.6 倍。

教训：零成本依赖于**编译器能看见全部代码**。抽象一旦跨越“编译器看不见”的边界（动态分派、FFI、跨 crate 但未标注内联的泛型之外的函数），优势就消失。

对比：Go 的泛型和函数值通常不会像 Rust 那样被彻底内联（接口调用要经过 itab，函数值是间接调用，只有编译器能证明目标时才会内联）；Java 依赖 JIT 在运行时做同样的事；Python 解释器完全没有这一层。
