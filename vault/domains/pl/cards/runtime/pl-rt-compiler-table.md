## Q
Go、Rust、Java、Python、C++ 的编译器分别站在「编译速度 vs 代码质量」轴上的哪一点？实测编译速度差多少？

## A
实测（一次测量，12 核 Mac）：用脚本生成 3000 个各含一个小循环的函数，各自编译：

| 语言 | 工具链 | 耗时 | 选择 |
|---|---|---|---|
| Go | 自研编译器与后端 | 约 0.25 秒 | 编译速度是设计约束：语法简单、依赖无环、不做太激进的优化 |
| Rust | rustc + LLVM，`-O` | 约 3.0 秒 | 要最强的优化器和零成本抽象，编译慢是代价；`opt-level=0` 约 0.54 秒 |
| Java | javac → 字节码，不优化 | 约 0.42 秒 | 编译只做类型检查和降级；优化留给运行时 JIT |
| Python | 编译成字节码，不做类型检查 | 毫秒级，隐式发生在导入时 | 没有静态阶段，错误在运行时才出现 |
| C++ | Clang（借 LLVM）或 GCC，`-O2` | 约 0.8 秒；`-O0` 约 0.13 秒 | 要最强的优化和零开销抽象；这个测试里没有头文件和模板，真实项目的慢主要来自它们 |

背后的逻辑：
- **Go** 的诞生动机之一就是 Google 内部巨型 C++ 代码库的构建慢。所以编译速度是一等设计目标：语言刻意简化（没有头文件、导入未使用即报错、禁止循环依赖），编译器自研以掌控速度，不追求最强优化。
- **Rust** 承诺“零成本抽象”和“无运行时”，这些都要靠编译期完成：泛型单态化、内联、借用检查，再交给 LLVM 做深度优化。编译时间是它最常被抱怨的代价。
- **C++** 和 Rust 同属“编译期付费”：优化器同样是 LLVM（Clang）或 GCC，运行时的零开销原则靠编译期做到。上表 3000 个小函数里，C++ 的 `-O2` 比 Rust 的 `-O` 快，因为没有借用检查和单态化；C++ 真正的编译成本是 `#include`（预处理器把头文件文本复制进每个编译单元，同一份头被反复解析）和模板实例化，所以大型 C++ 项目的构建同样让人头疼。这是 C 兼容的遗产：沿用文本包含模型，C++20 才有模块。
- **Java** 把工作拆成两半：`javac` 快而浅，JIT 在运行时用真实的 profile 做优化，所以 Java 的“慢”出现在启动和预热，而不是编译。
- **Python** 把检查全部推迟到运行时，换来了最快的“改完就跑”循环，付出的是运行速度与错误发现的时机。
