## Q
Go、Java、Rust、Python、C++ 的优化器各做哪些优化、做不到哪些？AOT 与 JIT 的上限分别在哪里？

## A
| 语言 | 优化发生在 | 擅长 | 做不到或不做 |
|---|---|---|---|
| Go | 构建时，自研 SSA 后端 | 内联（预算 80）、逃逸分析、边界检查消除、静态去虚化；1.21 起支持 PGO | 不自动向量化，激进循环变换少；接口调用常保留间接 |
| Java | 运行时，C1/C2 分层 JIT | 基于 profile 的推测内联、去虚化、逃逸分析与标量替换、去优化回退 | 要预热；静态不可知的事实才能下注；堆上对象布局不可控 |
| Rust | 构建时，LLVM 全套 | 深度内联、循环向量化、标量演化、`noalias` 带来的别名优化、跨 crate 的 LTO | 编译慢；无法使用运行时信息（除非 PGO）；`dyn` 调用不一定能去虚化 |
| Python | 编译字节码时少量折叠；3.13 起有实验性 JIT（默认关闭） | 常量折叠，窥孔优化 | 无内联、无类型特化的通用优化；速度靠把循环交给 C 库 |
| C++ | 构建时，Clang（LLVM）或 GCC 全套 | 模板展开后深度内联、向量化、LTO（链接期优化）和 PGO；利用未定义行为（UB）作假设 | 别名分析弱于 Rust：没有 `noalias`，`const&` 也可能与别的引用指向同一块内存；程序一旦含 UB，优化后的行为不可预测 |

逻辑：
- **Rust 和 Go 是 AOT**，所以每个优化都必须是“可证明正确”的。Rust 选择把预算花在优化器上（承诺零成本抽象），Go 选择把预算花在构建速度上（承诺几秒内完成构建）。两者在简单函数上产出相同的机器码，差距在复杂循环和跨函数分析上。
- **Java 是 JIT**，上限更高也更怪：它可以基于真实运行状况押注，因此对虚方法密集的面向对象代码常常比保守的 AOT 更快，代价是启动慢、预热、峰值之前性能不稳定。
- **Python 的解释器**把每条操作都留给运行时，优化的空间主要留在 C 库一侧（NumPy 等）。
- **Rust 的 `noalias`**（`&mut` 引用不会与其他引用指向同一块内存）是个特别的优势：类型系统提供了别名事实，让编译器能做 C 编译器不敢做的重排。C++ 就在“C 编译器”这一侧：引用和指针默认都可能别名，只有靠严格别名规则（不同类型的指针不指向同一对象）和非标准的 `__restrict` 才能让编译器放手。
- **C++** 与 Rust 共用 LLVM，在简单代码上产出相同的机器码。区别是它把“程序没有 UB”当作公理（比如有符号整数溢出不会发生），编译器据此删除检查、推理范围。这是更多的优化空间，也是错误无声的来源。
