## Q
“构建产物”和“部署”要解决什么问题？一个程序要在另一台机器上跑起来，需要带上什么，设计上有哪几种做法？

## A
**问题**：你在开发机上能跑的程序，要在生产机器上同样能跑。能不能跑取决于它所依赖的一切都在目标机器上：
1. **你的代码**（机器码、字节码或源码）；
2. **第三方依赖**（库）；
3. **语言运行时**（JVM、Python 解释器、Go 的运行时）；
4. **系统库**（libc、OpenSSL、动态链接的 `.so`）；
5. **操作系统与 CPU 架构**（Linux/macOS，x86-64/ARM64）。

“在我机器上能跑”类故障，几乎都是这五层里的某一层与开发机不一致。

**设计空间**——谁来保证这五层齐全：
- **把一切打进一个文件**（静态链接的单文件二进制）：目标机器只需要正确的操作系统和 CPU，别的都不用装。
- **打包应用 + 要求目标机器有运行时**（JAR + JVM，源码 + Python 解释器）：产物小、跨平台，但依赖目标机器的运行时版本。
- **把整个环境一起交付**（容器镜像）：应用、依赖、运行时、系统库全部打包，运行在共享的内核上。语言本身的产物形态变得没那么重要。
- **平台托管**（PaaS、Serverless）：你只提交代码，平台提供运行时。

核心权衡：**产物越自包含，部署越简单、越可复现，但体积越大、更新依赖要重新构建；产物越依赖目标环境，体积越小、越灵活，但越容易出现环境差异。**

交叉编译（cross-compilation）也属于这个问题：在一种平台上构建出另一种平台的产物（在 Mac 上构建 Linux 服务器的二进制），是否容易，取决于工具链和对 C 库的依赖。
