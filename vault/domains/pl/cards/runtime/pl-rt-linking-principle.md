## Q
链接（linking）、加载（loading）和 ABI 各解决什么问题？一个程序的各个部分可以在什么时候被“接起来”，不同时机在换什么？

## A
**问题**：程序不是一个文件。你的代码调用别的编译单元里的函数，调用标准库，调用操作系统。编译每个单元时，调用方只知道“我要调用一个叫 `helper` 的东西”，不知道它的地址。把名字变成地址的过程就是**链接**；把可执行文件和库放进内存并让它跑起来的过程是**加载**。

**ABI**（Application Binary Interface，应用二进制接口）是链接能成立的契约：参数放在哪个寄存器、返回值怎么传、结构体里每个字段的偏移、符号叫什么名字。API 是源码层的约定，ABI 是机器码层的约定。两边的 ABI 不一致，编译都通过了，运行时也会读到错位的数据。

**设计空间：什么时候接起来**：
1. **构建时，静态链接**：链接器把所有库的代码拷进一个可执行文件。部署就是拷一个文件；代价是体积大、库有安全补丁时必须重新构建并发布每个程序。
2. **启动时，动态链接**：可执行文件只记着“需要 libfoo 的符号 bar”，操作系统的动态加载器在启动时找到共享库并填好地址。多个进程共享同一份库代码，库可以独立升级；代价是“在我机器上能跑”问题，要求库的 ABI 向后兼容。
3. **运行时，显式加载**：`dlopen`、Java 的类加载器、Python 的 `import`。插件和延迟加载靠它，一切推迟到用到那一刻，失败也推迟到那一刻。

**权衡轴**：**部署的确定性、隔离** vs **共享、独立升级、体积**。静态偏向前者，动态偏向后者；越晚绑定越灵活，也越晚才发现不兼容。

四门语言的默认选择差异很大（Go 与 Rust 默认静态，Java 与 Python 默认运行时加载），这是后面所有部署、互操作与升级问题的根源。
