## Q
资深工程师在这四门语言里，怎样“与优化器合作”而不是去和它对抗？

## A
**总原则**：先写清楚、写简单的代码，让优化器认得出模式；先测量，再动手；只在有数据证明的热点上让步。

**通用**：
1. 手工“优化”（循环展开、位运算代替除法、缓存长度）几乎都是在重复编译器已经做的事，还会让代码更难认。
2. 数据布局比指令级技巧重要：连续数组、小结构体、少指针追逐，这是优化器无法替你做的。
3. 用优化后的构建测量，测量要有重复和预热，且检查测量的结果没被消除（见基准陷阱）。

**Go**：用 `go build -gcflags=-m` 看热点函数有没有被内联、哪些变量逃逸到堆上；热点函数保持小，把冷路径（错误处理）拆出去，让热路径落在内联预算内；热路径上避免经常传入接口值，除非必要；有稳定的生产负载时，采集 CPU profile 放进 `default.pgo` 开启 PGO。

**Java**：不要手写“让 JIT 更容易”的怪代码，JIT 在变；用 JMH 做基准；保持方法小、调用点类型稳定（单态），热点避免大量装箱；用 `-XX:+PrintInlining` 排查热点方法没被内联的原因。

**Rust**：发布构建用 `--release`；依赖迭代器链和泛型，信任 LLVM；热点里用 `get_unchecked` 之前先用迭代器或断言长度的写法消除检查；跨 crate 的小函数加 `#[inline]`，或在发布 profile 开 LTO 与 `codegen-units = 1`；确有收益且有数据时才用 PGO。

**Python**：优化的单位是“调用次数”而不是指令：把循环推进 C 库（NumPy、内置的 `sum`/`sorted`、生成器表达式交给 `str.join`），再不行才考虑 Cython、PyPy 或 Rust 扩展。

**何时打破**：已有数据证明某函数是瓶颈，且编译器报告显示没有被内联/向量化，才值得为它改写法，并在旁边写注释说明“为什么这样写、对应哪个编译器报告”。
