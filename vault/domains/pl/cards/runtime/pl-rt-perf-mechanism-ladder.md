## Q
把各类成本换成具体数字：一次循环迭代、一次间接访问、一次分配、一次越界检查、一次动态分派、一次跨语言调用，在这几门语言里大约分别是多少？

## A
下表是本机（Apple Silicon，12 核）的一次测量，目的是建立**量级感**，不是排名。

| 成本类别 | 实测 |
|---|---|
| 解释开销：循环 `s += i` 每次迭代 | Python 约 12 ns；Go、Java 约 0.2 ns；差约 55 倍 |
| 间接 + 缓存未命中：1000 万个整数求和 | Java `int[]` 约 2.1 ms；洗牌后的 `ArrayList<Integer>` 约 31 ms；差约 15 倍 |
| 堆分配（逃逸） | Go 约 4.5 ns，Java 约 3.4 ns，Rust `Box` 约 5.6 ns，Python 约 50 ns |
| 分配被消除（不逃逸） | Go、Java 约 0.23 ns |
| 数组边界检查（Rust，5000 万次随机读取） | 带检查约 33–35 ms，不检查约 33 ms，差在噪声内 |
| 动态分派 | Rust `dyn Fn` 比内联慢约 2.6 倍；Java 调用点 4 种类型比 1 种慢约 2.3 倍 |
| 跨语言调用 | Rust 约 1 ns，Java FFM 约 3 ns，Go cgo 约 13 ns，Python ctypes 约 147 ns |

读法：
1. **最大的差距来自解释和布局（几十倍）**，而不是安全检查。边界检查几乎免费，因为分支预测对从不触发的检查非常准，而且编译器常能证明下标合法。
2. **间接访问的代价取决于缓存**：数据在缓存里时，间接只多几纳秒；数据散落并超出缓存时，每次近百纳秒。上表“15 倍”的差距在更大的数据量上会继续拉大。
3. **分配本身只有几纳秒**，但因为它触发 GC，真实代价体现在 CPU 总量和延迟抖动上。逃逸分析把它降到零，是 JIT/AOT 最值钱的优化之一。
4. **边界成本像税**：每次几到几百纳秒，单次可忽略，放进每元素的热循环才致命。

记住这张表，评估设计时就能快速估算：一亿次的 12 ns 是 1.2 秒；一亿次的 0.2 ns 是 20 毫秒。
