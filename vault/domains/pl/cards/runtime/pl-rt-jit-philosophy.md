## Q
Java 相信运行时，Go 和 Rust 相信编译期，Python 谨慎试探：这三种对 JIT 的态度各反映什么价值观？

## A
**Java：相信运行时比编译器更了解程序。** HotSpot 的设计前提是程序行为只有运行起来才知道：哪些方法热、哪个调用点只见过一种类型、哪个分支几乎不走。所以字节码本身不做优化，把优化推迟到有真实数据之后。价值观：**让开发者写清晰的、面向对象的代码，把性能交给平台**。代价是预热、内存、不确定的延迟，以及“性能不透明”（你很难一眼看出某段代码最终会怎样）。

**Go 与 Rust：相信编译期，要求结果可预测。** 它们的目标场景（低延迟服务、系统软件、命令行工具、嵌入式）看重：启动即全速、没有预热抖动、没有后台编译线程抢 CPU、内存占用小。所以选择纯 AOT，所有优化在构建时完成。价值观：**可预测性比极限峰值更重要**。代价是不能利用运行时信息（用 PGO 间接弥补），也无法对运行中才加载的代码做优化。

**Python：保守和兼容。** CPython 的第一优先级是简单、可维护、兼容庞大的 C 扩展生态。所以先做对解释器友好的优化（自适应特化），JIT 只作为小步试验：copy-and-patch，默认关闭，收益不确定时不强推。PyPy 激进地走了另一条路，但生态没有跟上。价值观：**兼容与可维护性优先于峰值性能**。

三者的共同规律：**JIT 需要两样东西——足够多的运行时间来摊销编译成本，和足够稳定的行为来让推测成立**。
- 长期运行、热点集中的服务 → JIT 值得；
- 短命进程、行为分散、对延迟抖动敏感 → AOT 更合适；
- 这种差异也解释了为什么云原生场景下，Java 反过来在做 AOT（原生镜像、AOT 缓存），而 Go/Rust 在引入 PGO：**各取对方的一部分**。

选型时应问：负载是长期稳态还是频繁冷启动？延迟的尾部抖动能否接受？团队能否做预热和运维 JIT？
