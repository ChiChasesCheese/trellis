## Q
Go 的“二进制就是程序”和 Java 的“程序运行在平台上”反映了怎样不同的价值观？为什么这会影响启动与内存？

## A
**Java：平台哲学（Write Once, Run Anywhere）。** 程序是平台无关的字节码，JVM 是在每个机器上提供一致语义的平台：类加载、GC、JIT、安全模型、监控（JMX、JFR）、热部署。价值观是：**把复杂性放进平台，让应用代码可移植、可观测、可动态调整**。为此付出的是平台本身的体量：启动要引导 JVM，内存要装下 JIT 和元数据，进程是“一个小操作系统”。1990 年代的目标是跨异构的服务器和桌面，这个取舍很合理。

**Go：产物哲学。** 构建的结果是一个**完全自包含**的原生文件，不依赖运行时安装，不依赖共享库（纯 Go 时）。部署就是复制文件。价值观是：**简单的部署和可预测的运行**。为此放弃了：运行时的动态加载、JIT 的稳态优化、插件式生态。Go 诞生于 Google，目标是大量部署在集群里的网络服务和工具，部署简单和启动快是真实需求。

**Rust：零开销。** 连运行时都不带，目标是能进内核和嵌入式。**C++** 是这一哲学的前辈，同样没有强制运行时。**Python：开发者的时间最贵。** 解释执行、导入即执行，让“改了就跑”的反馈循环最快。

这些价值观今天正在相互渗透：云原生（容器、Serverless、边缘）让“启动快、占内存少”变成主流需求，推动 Java 走向 AOT（原生镜像、AOT 缓存），推动 Python 做延迟导入和更快的解释器；同时 Go 的运行时随着功能增加也越来越重。

选型时可以问：这个程序的生命周期是几毫秒、几分钟，还是几周？实例有几个？运行的环境你控制多少？答案会指向平台、产物，或解释器。
