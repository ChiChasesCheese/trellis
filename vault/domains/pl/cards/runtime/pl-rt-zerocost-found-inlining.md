## Q
内联（inlining）是什么？为什么它被称为“最重要的优化”，什么情况下编译器不能内联？

## A
**内联**：编译器把函数调用处直接替换成函数体，不再产生真正的“调用”。
```
// before
fn square(x: i32) -> i32 { x * x }
fn f(a: i32) -> i32 { square(a) + 1 }
// after inlining
fn f(a: i32) -> i32 { a * a + 1 }
```
真正调用一个函数要做：把参数放到约定的寄存器或栈、保存返回地址、跳转、在函数里保存/恢复寄存器、返回。即使很快（约 1 纳秒量级），对一个只有一两条指令的小函数来说，调用开销比函数体本身还大。

**更重要的是内联打开了别的优化**。内联之前，编译器只能一个函数一个函数地看；内联之后，调用方和被调用方连成一体，优化器可以：
- 常量传播：参数是常量，计算在编译期完成；
- 消除重复计算和死代码；
- 消除中间对象（逃逸分析），把小结构体拆进寄存器；
- 循环融合与向量化（迭代器链在内联后变成一个循环）。

因此“零成本抽象”的前提几乎总是：抽象层（小函数、闭包、迭代器适配器）能被**内联穿透**。

**什么时候不能内联**：
1. **目标在编译期未知**：虚函数、接口调用、函数指针、`dyn Trait`，调用目标要到运行时才知道（JIT 可以基于观察推测并内联，AOT 一般不能）；
2. **函数太大**：内联会让代码体积膨胀，编译器有大小阈值；
3. **递归**；
4. **跨编译单元且没有源码或内联提示**：C 的跨 `.c` 文件、Rust 的跨 crate 非泛型函数（除非标注 `#[inline]` 或开启 LTO）；
5. **跨语言边界**（FFI）。

各语言：Rust/LLVM 与 Go 编译器都做内联（Go 的内联预算较小，更保守）；Java 的 JIT 在运行时内联，包括基于类型剖析推测内联虚调用；CPython 解释器没有内联。
