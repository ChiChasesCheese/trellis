## Q
容器镜像（container image）是什么？它为什么几乎抹平了语言之间的部署差异？多阶段构建和 `scratch` 镜像又是什么？

## A
**容器**是用操作系统内核的隔离能力（命名空间、cgroup）把一个进程和它需要的整套文件系统关在一起运行的技术。**镜像**是这套文件系统的只读分层快照：基础层（如 Debian 的最小文件系统）+ 运行时层 + 你的应用层。镜像在任何装了容器引擎的 Linux 内核上行为一致，这解决了“环境差异”：库的版本、解释器、系统工具全部随镜像走。

因此对运维而言，交付物统一成“一个镜像”，无论里面是 Go 二进制还是 Java 加 JVM 还是 Python 加依赖。差异转移到了**镜像大小、构建时间、启动时间、安全面**上。

**多阶段构建**（multi-stage build）：Dockerfile 里写多个 `FROM`，第一个阶段包含完整的编译工具链（Go 编译器、JDK、构建依赖）来构建；最后一个阶段从一个很小的基础镜像开始，只 `COPY` 构建产物进来。工具链不进最终镜像，体积和攻击面都小得多。

**`scratch`**：一个完全空的基础镜像，什么文件都没有，连 shell 和 libc 都没有。只有**完全静态链接**的程序才能在里面运行，Go 的静态二进制恰好满足。

实测（一次测量）：把约 1.5 MB 的 Go 静态二进制放进 `FROM scratch` 的镜像，`docker images` 显示 **2.22 MB**，`docker run` 正常输出 `hello`。对照：Python 的官方精简镜像、带 JRE 的 Java 镜像，常见量级分别是一百多 MB 与两百多 MB（取决于基础镜像与版本）。

**其他常见的小基础镜像**：`distroless`（只含运行时必需的库，没有 shell）、`alpine`（用 musl libc，体积小，但与 glibc 的差异偶尔引发兼容问题）。

要点：容器让“带一整个环境”变得廉价，**弱化**了静态单文件的部署优势，但并没有消除体积、安全面和冷启动速度的差异。
