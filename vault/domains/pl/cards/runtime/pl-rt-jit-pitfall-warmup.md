## Q
在 JIT 平台上，哪些常见现象会让性能测量和线上表现与预期不一致？请用 Java 与 CPython 的实测说明。

## A
**1. 预热期的性能不是稳态。** Java 对 2 万个数做素数判断，每批 2 万个，连续 12 批（一次测量）：第 0 批约 1806 微秒，第 1 批起约 1000 微秒，之后稳定在约 955 微秒。如果只跑一次就下结论，会高估近一倍的耗时；短命的进程（命令行工具、Serverless 函数）永远处在预热期，JIT 甚至还没来得及起作用。

**2. 解释执行与 JIT 差一个数量级。** 同一个素数计数循环：`java -Xint` 约 93 毫秒，默认约 12–15 毫秒。JIT 编译线程还没赶上时，请求跑在慢速路径上，表现为上线初期的延迟尖峰。

**3. 去优化带来的抖动。** 一个长期单态的调用点突然见到新类型（比如只在月末才触发的代码路径加载了新实现），原来内联的机器码被作废，退回解释器并重新编译，出现偶发的延迟毛刺。日志里能看到 `made not entrant`。

**4. 微基准会被编译器“聪明地”改写。** 常量折叠、死代码消除、循环外提都可能让测的东西根本没有执行。结论：不用 JMH，就别信 Java 的微基准。

**5. JIT 不一定更快。** CPython 3.14 的实验性 JIT（`PYTHON_JIT=1`）在同一个纯 Python 素数循环上：默认 0.33 秒，开 JIT 0.51 秒，反而更慢；PyPy 同样代码 0.02 秒。原因是 copy-and-patch 只是省掉了解释器的分派，没有做类型特化与内联，编译和代码缓存的开销抵消了收益。结论：JIT 是否有效是一个要测的问题，不是默认答案。

**6. 容器环境放大预热问题**：CPU 配额小（比如 1 个核）时，编译线程和应用线程抢同一个核，预热更久。

做法：给 JIT 服务设预热期与就绪探针；测量时区分冷启动和稳态；不要在没有证据的情况下切换 JIT 开关。
