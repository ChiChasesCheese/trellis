## Q
设计目标怎样一步步变成具体的语法和编译器行为？以 Go 追求「大团队、大代码库可读」为例，写出这条因果链。

## A
因果链：目标，约束，特性，代价。

Go 的目标是让成千上万的工程师能读懂彼此的代码，并且构建要快。

1. 约束：同一件事不要有太多写法，语言本身要小。Go 只有 25 个关键字（对比：Python 3.14 有 35 个，Java 约 50 个）。
2. 特性：循环只有一个关键字 `for`；没有继承；没有异常，用返回值报错；`gofmt` 规定唯一的代码格式。
3. 构建速度：不允许出现无用的东西，因为它们拖慢编译也干扰阅读。未使用的变量和导入是编译错误，不是警告：

```go
func main() {
	x := 1
}
```

```console
./unused.go:4:2: declared and not used: x
```

4. 代价：错误处理的样板代码多，抽象手段少（泛型直到 1.18 才加入）。

同样的链条放在 Rust 上：目标是无 GC 的内存安全，约束是编译期必须证明每块内存何时释放，特性是所有权与借用检查，代价是学习曲线陡、编译慢。放在 C++ 上：目标是性能与对硬件的控制，约束是抽象编译后不能留下运行时成本（零开销原则），特性是模板（编译期按类型参数生成代码）、内联和析构函数（对象销毁时自动运行的清理函数），代价是语言不替你检查，越界、悬空引用都成为未定义行为（标准不规定后果）。看懂一门语言的办法，就是对它的每个「怪」设计，都回头找这条链。
