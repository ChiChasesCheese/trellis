## Q
做技术选型时，资深工程师怎样用权衡轴思考，而不是「哪个语言最好」？

## A
方法是把需求翻译成对各条轴的要求，再按组件而不是按整个系统来选。

1. 先写下这个组件最不能妥协的一条轴。交易系统的撮合引擎是延迟与确定性（性能、控制），内部管理后台是开发速度，支付核心是正确性（编译期检查、安全），长期运营的平台是可维护性和向后兼容。
2. 把最重要的一条放在语言最强的一端，其余的接受折中。要极致延迟与无 GC 抖动，选 Rust 或 C++；要团队易上手的网络服务，选 Go；要成熟生态和长寿命的大系统，选 Java；要数据分析和胶水，选 Python。
3. 按组件混用，在边界上用稳定的协议（HTTP、gRPC、消息队列、C ABI）。热点内核用 Rust 或 C，编排和 API 用 Go 或 Java，脚本和分析用 Python。多语言的代价是构建、监控和招聘成本，所以边界越少越好。
4. 把选择理由写下来（ADR）：当时的轴权重是什么，如果权重变了（团队变大、延迟要求变高）就重新评估。
5. 不要为了一个特性（如某语言的并发模型）把整个系统绑上去，先用小范围试点量出真实代价。

何时可以破例：团队已有深厚技能时，选「第二好但团队熟」常常比「最优但没人会」更好；招聘市场和生态成熟度本身也是一条轴。
