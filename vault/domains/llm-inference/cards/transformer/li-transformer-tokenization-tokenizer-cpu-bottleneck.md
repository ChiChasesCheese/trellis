## Q
在高并发推理服务里，分词和反分词为什么可能成为瓶颈？怎么发现和缓解？

## A
**分词（文字 → token 编号）和反分词（编号 → 文字）都在 CPU 上做**，而模型计算在 GPU 等加速器上。加速器越快，CPU 侧的这部分开销占比越大。

**为什么会成为瓶颈：**
- **长输入：** 一个 100K token 的文档，分词可能要几十到上百毫秒，直接加到首 token 延迟（TTFT，从发请求到收到第一个字的时间）里。
- **高并发反分词：** 每个请求每生成一个 token 都要做一次增量反分词。1,000 个并发流、每个每秒 100 个 token，就是每秒 10 万次小解码调用。
- **Python 的全局解释器锁（GIL）：** 如果服务的调度循环和分词在同一个 Python 进程里，分词会占住解释器，拖慢给加速器下发任务的节奏，加速器出现空闲。
- **慢分词器：** Hugging Face 的"慢"分词器是纯 Python 实现，比 Rust 实现的"快"分词器（`tokenizers` 库，`use_fast=True`）慢一个数量级以上。

**怎么发现：**
- 在服务端分段计时：排队、分词、预填充、首 token 返回分别记录。
- 观察加速器利用率随并发数的变化：并发上升而利用率不升，同时 API 进程的 CPU 占用接近 100%，说明 CPU 侧是瓶颈。
- 用 `py-spy top --pid <API 进程>` 或 `py-spy dump` 看 CPU 时间花在哪些函数上。

**缓解：**
- 确认使用快速分词器。
- **分进程：** 把 HTTP 处理、分词和反分词放在独立的进程，与调度和模型执行分离。vLLM 较新的架构就把 API 服务和引擎核心拆成不同进程，通过消息队列通信。
- **批量分词：** 一次调用处理多条文本，减少调用开销。
- **缓存：** 相同的系统提示只分词一次。

**测试：** 性能基准里专门加入"超长输入"和"极高并发、短输出"两类负载，它们最能暴露 CPU 侧瓶颈。
