## Q
平均 TPOT 只有 20 ms，用户却反馈"回答经常卡一下"。用哪些指标能看到这个问题？常见的原因有哪些？

## A
**指标的盲区：** TPOT（每个请求平均每个输出 token 的间隔）是一个请求内的平均值。一个请求里 99 个间隔是 15 ms、1 个是 500 ms，平均仍是 20 ms，但用户明显感到停顿。

**能看到问题的指标：**
- **ITL（相邻 token 间隔）的分布：** 看 P99、P99.9 和最大值。`vllm bench serve --percentile-metrics itl --metric-percentiles 50,99,99.9`。
- **单请求最大间隔：** 每个请求记录"最长的一次停顿"，再看它在所有请求上的分布。比如 5% 的请求出现过 > 300 ms 的停顿。
- **停顿与事件的时间关联：** 把停顿发生时刻和服务端事件（新的长输入开始预填充、抢占、垃圾回收、日志刷盘）放在同一时间轴上。

**常见原因：**
- **长输入预填充：** 同批里有人提交了几万 token 的输入，这一步的计算量暴增，所有正在生成的请求都等这一步结束。缓解：分块预填充（把长输入切成小块，每步只做一块），或把预填充和解码分到不同机器。
- **抢占：** 显存里的 KV 缓存（每个请求历史 token 的中间结果）用满，某些请求被暂停，之后重新计算，用户看到长时间停顿。看缓存使用率指标是否贴近 100%。
- **CPU 侧卡顿：** Python 垃圾回收、分词超长输入、同步写日志，让调度循环晚了几十毫秒，加速卡空等。
- **网络与代理：** 中间层缓冲导致 token 成批到达。
- **多卡通信抖动：** 张量并行每层都要卡间求和，偶发的通信延迟会放大到整步。

**改进的验证方式：** 设计干扰测试：背景是稳定的短请求流，周期性注入长输入，对比改动前后 ITL 的 P99 和"出现过 > 300 ms 停顿的请求比例"。只看平均 TPOT 会认为改动没有效果。
