## Q
测量推理服务的 TTFT 和 TPOT 时，有哪些常见的测量错误会让数字失真？各怎么避免？

## A
**TTFT：** 发出请求到收到第一个 token（文字的最小片段）的时间。**TPOT：** 第一个 token 之后平均每个 token 的间隔。

- **流式响应被中间层缓冲：** Nginx 等反向代理默认会攒一段数据再转发，客户端看到的是一批一批到达的 token：TTFT 虚高、ITL（相邻 token 间隔）呈"长—零—零—长"的锯齿。避免：Nginx 设置 `proxy_buffering off`；测量时同时记录服务端日志的时间戳对比。
- **一个事件里有多个 token：** 开启投机解码（一次接受多个猜测的 token）或服务端合并输出时，一个 SSE 事件可能含有好几个 token。按"事件数"当 token 数，TPOT 就算错。应以 `usage.completion_tokens` 或分词器重新计数为准。
- **用错分词器计数：** 客户端用另一个模型的分词器数 token，吞吐偏差可达 20% 以上。
- **没有预热：** 前几个请求触发编译、CUDA Graph 录制、显存分配，延迟很高。丢弃预热阶段，或单独报告冷启动延迟。
- **客户端成为瓶颈：** 单进程 Python 客户端在高并发下解析 JSON、处理流事件跟不上，测到的是客户端的极限。检查压测机 CPU；用利特尔定律核对实际并发。
- **协同遗漏（coordinated omission）：** 闭环压测（等上一个请求结束才发下一个）在系统变慢时自动少发请求，掩盖了真实用户会遇到的排队。需要开环压测：按固定或泊松分布的到达率发送请求，不管前面的是否完成。
- **样本太少报 P99：** 200 个请求的 P99 只由 2 个样本决定，噪声极大。P99 至少需要几千个样本。
- **输出长度不受控：** 模型提前输出结束标记，实际输出比设定短，吞吐偏低且不可比。基准测试常用 `--ignore-eos` 强制生成到指定长度，但这时生成的内容可能是无意义的重复，只适合测性能，且要在报告中注明。
- **时钟：** 跨机器比较时间戳要求时钟同步；单机内用单调时钟（`time.perf_counter()`），不用会被调整的墙上时钟。
