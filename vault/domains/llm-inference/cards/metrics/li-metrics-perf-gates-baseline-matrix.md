## Q
为推理服务的发布设置性能门限（performance gate）时，基线（baseline）应该按什么维度建立？每条基线记录哪些指标？

## A
**性能门限：** 发布流水线中的一个自动检查：新版本在固定负载下跑基准测试，结果和基线比较，退化超过阈值就阻止发布。

**为什么不能只有一条基线：** 同一次代码改动，可能让某个模型的长输入场景快 10%，同时让另一个模型的短输入高并发场景慢 15%。只看一个平均数，退化会被掩盖。

**基线矩阵的维度：**
- **模型：** 每个上线的模型一行。不同结构（稠密、混合专家）、不同大小对改动的敏感点不同。
- **部署配置：** 并行方式（张量并行度）、数值精度（BF16、FP8）、是否开投机解码、前缀缓存。
- **负载档位：** 至少三档：短输入短输出、长输入短输出、短输入长输出；外加几个并发档位，比如 1、16、64。
- **硬件与底层软件：** GPU（或其他加速器）型号、驱动和固件版本。硬件或驱动换了，基线要重新建立，而不是和旧硬件比。

一个中等规模的服务可能有"10 个模型 × 2 种配置 × 3 档负载 × 3 档并发 = 180 个格子"，每个格子一条基线。要控制总运行时间，可以把格子分成每次提交都跑的少量核心组合和每晚全量跑的完整矩阵。

**每条基线记录：**
- **延迟：** TTFT（首 token 延迟）、TPOT（每 token 间隔）的 P50 和 P99；ITL（相邻 token 间隔）的 P99。
- **吞吐：** 输出 token 每秒、在延迟目标下的 goodput（满足目标的有效吞吐）。
- **资源：** 启动时 KV 缓存（每个请求历史 token 的中间结果）的容量、峰值显存、启动耗时（模型加载时间影响扩容速度）。
- **噪声：** 同一版本重复运行的波动范围，用来设阈值。
- **元数据：** 引擎和模型版本、全部配置参数、硬件快照、负载种子。

**基线怎么更新：** 只有经过评审、确认是有意的改进或可接受的取舍时才更新，并保留历史，便于发现长期缓慢退化。
