## Q
给推理服务开启投机解码（speculative decoding）之前，要做哪些正确性和性能测试？用哪些指标判断？

## A
**投机解码：** 先用便宜的方法猜出后面几个 token，再让大模型一次检查，接受猜对的部分。理论上输出分布不变，速度更快。但它改变了计算方式，必须验证"真的没变"和"真的更快"。

**正确性测试：**
- **贪心等价：** `temperature=0`，几百条覆盖代码、数学、长回答的提示，分别在关闭和开启投机解码下运行，逐字比较输出。期望绝大多数完全一致；不一致的样本要检查分叉点的两个候选概率是否几乎相等（数值误差），如果概率差距明显，就是缺陷。
- **采样分布等价：** 选一个下一个 token 分布清楚的提示，开启和关闭各抽样几千次，用卡方检验比较两边的频率分布。拒绝采样实现错误（比如修正分布算错）只能用这种方法发现。
- **停止条件：** 一次接受多个 token 时，结束标记或停止字符串可能出现在被接受段的中间。必须在那里截断，后面已接受的 token 不能输出，`completion_tokens` 计数也要正确。
- **边界：** `max_tokens` 小于起草长度、上下文剩余空间小于起草长度、和结构化输出（限制只能生成合法 JSON）同时开启。

**性能测试：**
- **接受率：** vLLM 导出计数器 `vllm:spec_decode_num_accepted_tokens_total` 和 `vllm:spec_decode_num_draft_tokens_total`，两者速率之比就是接受率。按流量类型分别统计。
- **每 token 间隔（TPOT）：** 在并发 1、8、32、128 下，对比开启前后。期望低并发明显改善，高并发改善变小甚至变差；找到"不再划算"的并发点，写进部署建议。
- **吞吐和首 token 延迟：** 草稿模型占用显存，KV 缓存（每个请求的历史中间结果）空间变小，最大并发可能下降；首 token 延迟也可能略升。

**发布门限示例：** 贪心等价率 ≥ 99%（不一致样本全部属于数值近似平局）；目标并发下 TPOT 改善 ≥ 20%；吞吐不下降超过 5%。
