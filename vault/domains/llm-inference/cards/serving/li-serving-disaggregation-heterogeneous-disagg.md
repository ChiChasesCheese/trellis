## Q
预填充和解码分离后，可以把两个阶段放在**不同种类的芯片**上。为什么这样搭配有道理？测试这种跨硬件系统时要额外验证什么？

## A
**道理：两个阶段需要的硬件能力相反。**
- **预填充（一次性处理整段输入）：** 大矩阵乘法，每读一次权重做大量计算，需要的是**算力**。适合算力密集的 GPU 或专用训练芯片。
- **解码（每步生成 1 个 token）：** 每步要把全部权重和 KV 缓存（历史 token 每层的键、值向量）读一遍，计算很少，需要的是**内存带宽**。适合带宽极高的芯片，例如把权重全部放在片上 SRAM（直接做在计算芯片里的高速存储，带宽比外部显存高几个数量级）的芯片。
- 用同一种芯片做两件事，总有一种能力在闲置。异构搭配让每种芯片只做自己擅长的阶段。

**流程：** 预填充芯片算出 KV 缓存和第一个 token，通过高速网络把 KV 缓存传给解码芯片，解码芯片接着逐个生成。

**跨硬件系统的额外验证：**
- **两边数值一致性：** 预填充芯片和解码芯片用不同的计算实现、可能不同的数值格式。验证方法：同一请求，"全在 A 芯片"、"全在 B 芯片"、"A 预填充 + B 解码"三种组合，在贪心解码下比较输出和 logprobs（每个 token 的对数概率）。混合组合的差异应不大于两种单一组合之间的差异。
- **KV 缓存格式转换：** 两边的缓存布局（块大小、头的排列、数据类型如 BF16 与 FP8、缩放因子）可能不同，转换代码是新的缺陷来源。专门测试长输入、多轮对话、不同数据类型的组合；用校验和比对转换前后的数据。
- **版本组合：** 两种硬件各有自己的编译器、运行时和固件，版本独立升级。要维护一张"已验证的版本组合"矩阵，任一侧升级都要重跑跨硬件回归。
- **传输故障：** 传输中途网络断开、解码节点崩溃、传输超时时，请求应被重试或明确报错，不能挂住或返回半截结果。
- **延迟拆分：** 端到端的首 token 延迟 = 排队 + 预填充 + 传输 + 解码第一步。分别打点计时，否则无法判断回归发生在哪一侧。
