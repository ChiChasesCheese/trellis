## Q
多卡并行推理有哪些典型故障和数值问题？怎样测试不同并行配置的正确性？

## A
**多卡并行：** 张量并行把每层矩阵切到多张卡上，每层用全体求和（all-reduce：每张卡的部分结果加起来，所有卡都拿到总和）合并；流水线并行按层切，阶段间传中间结果。卡与卡之间的通信通常由 NVIDIA 的 NCCL 库完成。

**典型故障：**
- **挂死（hang）：** 集合通信要求所有卡按相同顺序调用同一个操作。某张卡因为异常提前退出、或走了不同的代码分支（比如只有它遇到了一个特殊请求），其他卡永远在等。表现为 GPU 利用率 100% 但没有任何输出，没有报错。
- **一张卡掉线：** 硬件错误（如 Xid 错误、ECC 不可纠正错误）或网络链路抖动，整组卡全部不可用。一组 8 卡服务的可用性约等于单卡可用性的 8 次方。
- **配置不整除：** 注意力头数、键值头数或词表大小不能被卡数整除，有的实现直接拒绝启动，有的会复制或补齐，补齐逻辑错了就静默算错。
- **跨机器的张量并行：** 误配置成跨节点，性能下降几倍，结果仍然正确，只在性能测试里可见。

**数值差异：** 不同卡数下，部分和的拆分方式和求和顺序不同。浮点加法不满足结合律，`(a + b) + c` 和 `a + (b + c)` 在低精度下可能差最后几位。所以 TP = 1 和 TP = 8 的输出在数值上不会逐位相同，贪心解码在概率非常接近的地方可能分叉。

**测试方法：**
- **并行配置矩阵：** 同一模型、同一组提示，在 TP = 1、2、4、8 以及 TP × PP 的组合下运行，和 TP = 1（或参考实现）比较每个位置的 logprobs（每个 token 的对数概率）差异和 top-1 一致率，阈值根据精度设定。
- **挂死检测：** 设置通信超时（如 `NCCL_TIMEOUT` 或框架自身的超时参数）让挂死变成报错；开启 `NCCL_DEBUG=INFO` 记录初始化和拓扑；挂死时用 `py-spy dump --pid <pid>` 查看每个进程停在哪一行。
- **故障注入：** 运行中杀掉一个工作进程，确认整组服务被健康检查判定为不可用并重启，而不是一直挂着接收请求。
