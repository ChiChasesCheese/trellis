## Q
什么是分块预填充（chunked prefill）？它解决了什么问题，`--max-num-batched-tokens` 该怎么调，怎样测试它的效果？

## A
**问题：** 预填充（一次性处理一个请求的整段输入）和解码（每步为每个请求生成 1 个 token）在同一台机器上混跑。一个 32K token 的长输入一次预填充可能要几百毫秒到几秒，这一步期间，同批所有正在生成的请求都停住，用户看到输出突然卡顿。

**分块预填充：** 把长输入切成固定大小的块（比如每块 2,048 token），每一步只做一块预填充，同时把这一步所有正在解码的请求也带上。
- 每一步的工作量有上限：**这一步所有请求的 token 总数 ≤ `--max-num-batched-tokens`**。解码请求每个占 1 个，剩余的额度给预填充块。
- 调度器通常**先放解码请求，再用剩余额度做预填充**，保证正在生成的用户不被饿死。
- 长输入的预填充被分摊到多步完成，每一步的时间可控。

**调 `--max-num-batched-tokens`：**
- **调小（如 512–2,048）：** 每步时间短，正在生成的请求的每 token 间隔（TPOT，相邻两个输出 token 的时间间隔）更平稳；但长输入要分更多步完成，首 token 延迟（TTFT）变长，矩阵乘法规模小、算力利用率低。
- **调大（如 8,192–16,384）：** 预填充更快，吞吐更高；但每步可能变长，解码的尾延迟上升，中间结果占的显存也更多。
- 原则：按延迟目标选。对话类产品偏重 TPOT 稳定，选小一些；批量离线任务偏重吞吐，选大一些。

**怎样测效果：**
- **干扰测试：** 背景负载是 32 个并发的短对话；每 5 秒插入一个 32K token 的长输入。比较不同 `--max-num-batched-tokens` 下，短对话 TPOT 的 P99 和长输入的 TTFT。
- **预期：** 块越小，短对话的 TPOT P99 越低，长输入的 TTFT 越高，两条曲线画在一起，选满足双方延迟目标的值。
- **正确性：** 分块与不分块，在贪心解码（每步取概率最高的 token）下的输出应一致；块边界恰好落在一个多 token 的特殊标记中间时也要正确。
