## Q
输入截断（truncation）和反分词（detokenization）相关的经典缺陷有哪些？各会导致用户看到什么？

## A
**截断：** 输入超过上下文窗口（模型一次能处理的最大 token 数）时，丢掉一部分内容。**反分词：** 把生成的 token 编号转回文字。

**截断类缺陷：**
- **静默截断：** 服务没有报错，而是悄悄丢掉了超出部分。用户上传了一份长合同，问最后一条条款，模型回答"文中没有提到"，因为最后部分根本没进模型。正确做法是报错（400，并说明上限和实际长度），或者在文档中明确说明截断规则并在响应中标注。
- **截错了方向：** 从右边截会丢掉最新的用户问题，模型回答的是旧问题；从左边截会丢掉系统提示，模型"忘记"了自己的身份和规则。合理的做法是保留系统提示和最新消息，删除中间较旧的对话轮次。
- **截断位置切开了模板：** 在 token 级别截断时，把一个角色标记截了一半，剩下的格式错乱。
- **输出预算被挤占：** 输入接近上限时，留给输出的空间只剩几个 token，回答被截断在半句话，`finish_reason` 是 `length`。

**反分词类缺陷：**
- **多字节字符被切开：** 一个汉字或 emoji 由多个 token 组成，流式输出时逐个 token 转文字，用户看到 `�` 乱码。
- **空格丢失或多出：** 有的分词器用一个特殊符号表示"词首有空格"，单独解码一个 token 时会去掉开头空格，拼接后英文单词粘连在一起。
- **特殊 token 泄漏：** 没有设置跳过特殊 token，用户看到 `<|eot_id|>` 这样的标记；或者反过来，代码里的真实文本恰好像特殊 token，被错误地删掉。
- **最后一段没有冲刷：** 流结束时缓冲区里还有未输出的字符，回答最后一个字丢失。

**测试方法：**
- 构造恰好等于、超出 1、超出很多上下文上限的输入，断言错误码或截断行为与文档一致。
- 用包含中文、emoji、连续空格、代码缩进、看起来像特殊 token 的字符串的回答，比较流式拼接结果和一次性解码结果完全相同。
- 检查所有响应中不出现特殊 token 文本。
