## Q
模型宣称支持 128K 上下文。上线前要怎样验证长上下文在推理平台上真的可用？要测哪些质量、性能和资源指标？

## A
**上下文长度：** 模型一次能处理的输入加输出的 token 总数（token 是文字切成的小片段）。长上下文依赖正确的位置编码配置（如旋转位置编码的缩放参数），也极度消耗显存。

**质量验证：**
- **长度阶梯：** 在 4K、8K（常见的原始训练长度）、8K 之后、16K、32K、64K、128K 各测一组。很多问题只在越过原始训练长度后出现。
- **大海捞针（needle in a haystack）：** 在长文档的不同深度（开头、25%、50%、75%、结尾）插入一句关键信息并提问，画出"长度 × 深度"的成功率表格。中间位置常是薄弱点。
- **更难的长上下文任务：** 如 RULER 基准里的多针检索、变量追踪、聚合统计，比单针更能区分好坏。
- **与参考实现对比：** 在 32K、128K 的序列上做教师强制的逐位置概率对比，按位置分段看差异是否随位置增大。
- **配置核对：** `rope_scaling` 的类型、系数、原始长度和引擎实际使用的值一致；平台的最大长度设置不超过模型真正支持的长度。

**性能验证：**
- **首 token 延迟：** 128K 输入的预填充（一次性处理整段输入）可能要几秒到几十秒，注意力的计算量随长度平方增长。确认是否有分块预填充，避免阻塞其他请求。
- **每 token 间隔：** 解码每步要读完整的 KV 缓存（保存每个历史 token 每层键、值向量），长度越长越慢。
- **对其他请求的影响：** 背景负载下插入长上下文请求，看短请求的尾延迟。

**资源验证：**
- **KV 缓存容量：** 例如 Llama 3.1 8B 每 token 约 128 KB，128K token 约 16 GB，一张卡可能只能同时容纳寥寥几个这样的请求。确认平台在缓存不够时的行为是排队或抢占，而不是崩溃。
- **峰值显存：** 长输入预填充时中间结果的峰值，验证不会内存不足。

**产出：** 在资格报告中写清"验证到多长、在什么并发下"，超出部分标为未验证或限制对外开放的最大长度。
