## Q
为什么会把预填充放在 GPU（或其他算力型芯片）上、把解码放在权重常驻 SRAM 的晶圆上？这种分离部署的收益和要验证的风险分别是什么？

## A
**两个阶段需要的能力不同：**
- **预填充（prefill）：** 一次性处理整段输入，几千个 token 同时做矩阵乘法，每读一次权重做大量运算，受**算力**限制。算力密集、显存容量大的 GPU 擅长这个。
- **解码（decode）：** 每步为每个请求生成 1 个 token，要把全部权重和 KV 缓存（每个请求历史 token 的键、值向量）读一遍，受**内存带宽**限制。权重常驻片上 SRAM 的晶圆带宽高几个数量级，擅长这个。

**为什么不都在晶圆上做：**
- 长输入的预填充计算量很大，片上存储容量也有限：一个 100K token 的输入要在晶圆上一次处理，会长时间占用流水线，挤占正在生成的请求，降低晶圆最擅长的解码吞吐。
- 预填充对带宽不敏感，用 GPU 做性价比更高，把宝贵的 SRAM 和流水线留给解码。

**流程：** GPU 做完预填充，得到这个请求每一层的 KV 缓存和第一个 token；KV 缓存经高速网络传给晶圆；晶圆把它放进对应层所在晶圆的 SRAM，接着逐个生成后续 token。

**收益：** 各自做最擅长的阶段，单位功耗或成本下的 token 数更高；长输入不再阻塞解码，每 token 间隔更平稳。厂商公布的预期是比不分离的方案多出数倍的 token 吞吐，这是厂商的估计，需要按自己的负载实测。

**要验证的风险：**
- **数值一致性：** 两种硬件的计算实现、数值格式不同。"GPU 预填充 + 晶圆解码"的输出，与"全在 GPU"和"全在晶圆"的输出比较，差异不应超过两种单一方案之间的差异。
- **KV 缓存格式转换：** 布局、数据类型（如 BF16 与 8 位）、头的排列、分到哪片晶圆，都要正确映射。错误常常不报错，只让长对话质量下降。用逐位置的概率对比和长上下文任务测试。
- **传输延迟：** 首 token 之后的第二个 token 要等 KV 缓存传完。长输入的 KV 缓存可达 GB 级，要测不同输入长度下的首 token 延迟和第二个 token 的延迟。
- **故障：** 传输中断、目标晶圆忙或故障时的重试与降级路径。
- **版本组合：** 两边的编译器、运行时、驱动独立升级，需要维护组合矩阵并做跨硬件回归。
