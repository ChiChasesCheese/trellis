## Q
编译器或内核库升级后，怎样检测"数值正确但变慢了"的性能回归？设计一套按形状的性能测试。

## A
**问题：** 编译器换了分块策略、某个优化规则失效、自动调优选错了配置，结果仍然正确，但某些形状下变慢了。差分测试（比较数值）完全发现不了。

**设计：**
1. **形状清单来自生产：** 收集线上模型实际出现的算子和形状（隐藏宽度、头数、常见批大小和序列长度），而不是随意挑选。例如矩阵乘法的 (m, k, n) 取 m ∈ {1, 8, 64, 256, 2048}，k、n 取各模型的真实维度。
2. **可靠的计时：** 用 `triton.testing.do_bench` 或 GPU 事件计时，做预热、清空 L2 缓存、多次重复取中位数。固定 GPU 时钟，独占机器。
3. **记录"效率"而不只是时间：** 对每个形状计算理论最短时间 = max(运算次数 ÷ 峰值算力, 读写字节 ÷ 显存带宽)，报告"理论时间 ÷ 实测时间"。效率指标对机器之间的小差异不那么敏感，也直接说明离硬件极限还有多远。
4. **基线与阈值：** 每个形状一条基线。先重复运行测出噪声（比如 ±2%），阈值设为噪声的若干倍（比如 5%）。
5. **两种比较：** 和上一个版本比（发现突变）；和替代实现比，比如自定义内核和 cuBLAS、PyTorch 内置实现比，发现"其实还不如直接用库"的情况。
6. **结果展示：** 按形状画热力图，退化的格子一目了然；很多退化只发生在特定的 m 值（比如 m = 1 的生成阶段），平均数会掩盖它。

**端到端校验：** 内核级的改进或退化最终要反映在每 token 间隔和吞吐上。把内核基准和端到端推理基准对照：内核变慢 10%，端到端是否也变慢；端到端变慢而所有内核都正常，问题就在内核之间（调度、同步、启动开销）。

**定位：** 发现退化后，用 `git bisect run` 配一个只测该形状的脚本二分定位提交；对自动调优类问题，打印两个版本为这个形状选择的配置（分块大小、流水级数），通常一眼就能看出差别。
