## Q
什么是硬件的静默数据损坏（silent data corruption）？在大规模推理集群里怎样发现它？

## A
**静默数据损坏：** 硬件算错了，但不报告任何错误：没有异常、没有错误码、程序照常结束，只是结果不对。原因包括制造时的边缘缺陷、老化、特定温度或电压下才出现的问题。可能只在某一个核心、某一种指令、某种数据模式下出现。

**规模越大越不能忽视：** 大型云厂商公开报告过，在大规模集群里，这类"会算错的芯片"的比例约在千分之一量级，出现在服务器 CPU 中，同样的问题也存在于其他计算硬件上。一个有上千台加速器的推理集群，几乎必然存在少量这样的设备。

**在推理服务里的表现：**
- 某一台机器上的回答质量偶尔下降，或者出现无法解释的乱码；
- 同一请求路由到不同机器，结果差异明显超出正常的数值噪声；
- 很难复现，因为它依赖特定的硬件单元和条件。

**发现方法：**
- **已知答案测试（known-answer test）：** 定期（比如每小时、每次部署时）在每台设备上运行一组固定输入的计算，结果和预先存好的黄金结果比较。包括矩阵乘法、注意力等常用内核，以及一个小模型的完整前向计算。
- **跨机器一致性检查：** 定期把同一组请求发给多台机器，比较输出的概率分布。某台机器的差异持续明显大于其他机器，就把它隔离出来做深入检查。
- **出厂和上线前的老化测试（burn-in）：** 新设备在高负载、高温下连续运行压力测试和诊断（如 NVIDIA 的 `dcgmi diag -r 3`）。
- **硬件计数器和日志：** 可纠正的 ECC 错误计数持续上升，往往是不可纠正错误的前兆。
- **线上质量监控：** 按机器维度统计质量指标（比如结构化输出的解析失败率、用户的负反馈率），找出异常的个体。

**处理：** 一旦确认，立即把设备隔离出服务池，保留现场信息（设备序列号、触发的输入、温度），交给硬件团队；不要只是重启了事。

**测试设计的启示：** 测试结果和线上错误都必须带上硬件标识，否则"只在一台机器上出现"的问题永远会被当成偶发噪声。
