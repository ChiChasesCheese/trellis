## Q
固件、驱动、运行时、编译器、编译产物各自独立发布时，怎样管理和测试它们之间的版本兼容性？用 CUDA 的驱动与工具包关系举例。

## A
**问题：** 一个推理系统由多层软件组成，每层有自己的发布节奏：
- **固件：** 设备上的底层程序；
- **驱动：** 主机操作系统里和设备通信的内核模块；
- **运行时和库：** 加载和执行程序（如 CUDA 运行时、cuBLAS、NCCL）；
- **编译器：** 把模型编译成设备程序；
- **编译产物：** 某个版本的编译器针对某个模型生成的文件；
- **推理引擎和模型：** 在最上层。

任何两层的版本组合都可能出问题，而线上往往同时存在多个版本（滚动升级期间，或不同集群升级进度不同）。

**CUDA 的例子：**
- 每个 CUDA 工具包（运行时和编译器）要求一个最低版本的驱动。驱动太旧时，程序启动就报 "CUDA driver version is insufficient for CUDA runtime version"。
- `nvidia-smi` 右上角显示的 "CUDA Version" 是**这个驱动最高支持的 CUDA 版本**，不是已安装的工具包版本。很多人因此误判。
- 较新的驱动通常向后兼容用旧工具包编译的程序；用新工具包编译的程序一般不能在旧驱动上运行（除非使用专门的兼容包）。
- 编译产物里如果只有针对某些 GPU 架构的机器码、没有中间代码，在更新的架构上就无法运行。

**管理方法：**
- **兼容性政策：** 明确写出"支持哪些组合"，比如"运行时支持当前和上一个版本的驱动"（N 和 N−1），"编译产物必须由不早于某版本的编译器生成"。
- **启动时检查：** 加载时读取各层版本，不在支持表里就拒绝启动并给出清晰的错误，而不是带病运行。
- **测试矩阵：** 不可能测所有组合，按风险选择：每个新版本和其他层的"当前版本"及"上一个版本"组合必测（成对覆盖）；线上实际存在的组合必测；升级路径（从旧组合滚动到新组合的中间状态）必测。
- **编译产物带元数据：** 记录生成它的编译器版本、目标硬件、模型哈希，运行时据此判断能否加载。
- **记录在每条测试和每条线上错误中：** 出现问题时，第一件事就是看它发生在哪个版本组合上。
