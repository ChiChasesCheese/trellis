## Q
加速器的执行为什么是异步的？流（stream）是什么？异步执行给错误定位和计时带来了哪些坑？

## A
**异步执行：** 主机（CPU）把"拷贝数据""启动内核"（在设备上运行的函数）等命令放进队列后立即返回，设备按顺序从队列里取出执行。这样 CPU 可以继续准备下一批工作，CPU 和设备并行工作。

**流（stream）：** 一条命令队列。同一条流里的命令按顺序执行；不同流里的命令可以并行。常见用法：
- 一条流做计算，另一条流同时把下一批数据从主机拷到设备（需要锁页内存）。
- 用事件（event）在流之间建立依赖："第 2 条流等第 1 条流的某个事件完成后再继续"。

**坑 1：错误报在错误的地方。** 一个内核越界访问了内存，CPU 早已返回，继续执行了很多行代码；错误要到之后某次同步时才抛出，比如在一次和出错内核毫无关系的拷贝上抛出 `CUDA error: an illegal memory access was encountered`。
- 定位：设置 `CUDA_LAUNCH_BLOCKING=1`，让每个命令同步执行，错误在真正出错的调用处报出。代价是变慢，只用于调试。
- 设备上的非法访问错误往往会让整个 CUDA 上下文进入不可恢复状态，进程必须重启。推理服务要能检测到这一点，摘掉这个工作进程，而不是继续接收请求。

**坑 2：计时测到的是"提交时间"。** 用 CPU 时钟测一个异步调用，只测到命令入队的时间。要么在计时前后调用 `torch.cuda.synchronize()`，要么用设备事件计时。

**坑 3：隐式同步拖慢性能。** 某些操作会悄悄等待设备完成，比如把张量的值取到 CPU（`.item()`、`.cpu()`、打印张量）、按张量的值做 Python 判断。推理的每一步如果有这样的操作，CPU 和设备就无法重叠。
- 发现：Nsight Systems 时间线上，CPU 端出现长时间的同步等待，设备端出现空隙。PyTorch 还提供 `torch.cuda.set_sync_debug_mode("warn")`，在发生同步时发出警告。

**坑 4：跨流的数据竞争。** 一条流还在读某块内存，另一条流已经开始往里写。缺少事件依赖时结果偶尔错误，只在高负载下出现。

**测试建议：** 调试构建里打开同步调试模式运行全部测试；对偶发的数值错误，先用 `CUDA_LAUNCH_BLOCKING=1` 重跑，看能否稳定复现。
