## Q
在推理服务的路径上，运行时和驱动层有哪些典型故障？每种故障怎样被检测到、服务应该怎样反应？

## A
**典型故障：**
- **设备内存不足（OOM）：** 某个请求的输入比预期长、或者碎片太多。理想反应：拒绝或排队这个请求，不影响其他请求。最坏情况：整个进程崩溃，同批所有请求失败。
- **非法内存访问：** 内核（设备上运行的函数）越界读写。通常让整个设备上下文损坏，进程必须重启。
- **执行超时或挂起：** 某个内核或集合通信（多个设备之间按约定交换数据）一直不返回。进程看起来活着，但不再产出任何结果。
- **硬件错误：** 显存不可纠正的 ECC 错误、设备从总线上掉线、温度过高。NVIDIA GPU 会在系统日志里报告 Xid 错误码。
- **版本不兼容：** 编译产物是用较新的编译器生成的，运行时或驱动版本太旧，加载失败或行为异常。例如 CUDA 程序报 "CUDA driver version is insufficient for CUDA runtime version"。
- **静默数据损坏：** 少数有缺陷的硬件偶尔算错，不报任何错误。

**检测手段：**
- **进程级：** 捕获运行时异常；致命错误后让工作进程退出，由上层重启。
- **心跳和活性探测：** 只检查"进程是否存在"不够。健康检查应该定期发一个极小的推理请求，在超时时间内必须返回正确结果。挂起的进程才能被发现。
- **看门狗（watchdog）：** 每一步设定最长时间，超过就判定为挂起，记录现场（`py-spy dump --pid` 抓所有线程的调用栈），然后重启。
- **硬件监控：** 采集 Xid 错误（`dmesg`）、ECC 计数、温度、功耗，通过 DCGM 等工具导出告警。
- **启动自检：** 加载时校验编译产物、运行时、驱动、固件的版本是否在兼容表中；跑一个已知答案的小计算，结果不对就拒绝上线。

**服务的反应原则：**
- **单个请求的问题不扩散：** 能隔离的错误（单个请求超长、参数非法）只让这个请求失败，返回明确错误。
- **设备级故障快速摘除：** 设备进入不可恢复状态时，立刻停止接收新请求，正在处理的请求明确报错（而不是挂起或静默截断），实例重启或替换。
- **记录可追溯的信息：** 每次故障记录机器、设备序列号、驱动和固件版本、正在执行的模型和请求特征，便于发现集中在某些硬件或某个版本上的问题。

**测试：** 用故障注入覆盖每一类：构造超长输入制造内存不足，`kill -STOP` 暂停工作进程模拟挂起，使用错误版本的编译产物，在测试环境中模拟设备掉线。
