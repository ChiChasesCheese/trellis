## Q
一个模型部署了很多个副本时，请求应该怎样分配到副本上？普通的轮询为什么不适合大模型推理？什么是前缀感知路由（prefix-aware routing）？

## A
**副本（replica）：** 同一个模型的多份完整部署，每份占一组加速卡，各自独立处理请求。路由器（负载均衡器）决定每个请求去哪一份。

**为什么轮询（round-robin）不合适：**
- **请求代价差异巨大：** 一个请求可能是 50 token 输入、10 token 输出，另一个是 100,000 token 输入、4,000 token 输出，代价相差上千倍。按个数平均分，某个副本可能同时堆了好几个超长请求，排队严重，另一个副本空闲。
- **忽略缓存：** 引擎会缓存最近处理过的公共开头（如同一份系统提示、同一段长文档、同一个会话的历史）的 KV 缓存（历史 token 每层的键、值向量），命中时可以跳过这部分的预填充计算。轮询把同一会话的后续请求随机分到不同副本，几乎每次都要从头算。

**更好的策略：**
- **按负载：** 选"在途请求最少"或"排队 token 数最少"的副本。需要从引擎读取实时指标，如 vLLM 的 `vllm:num_requests_running`、`vllm:num_requests_waiting` 和 KV 缓存使用率 `vllm:kv_cache_usage_perc`。
- **前缀感知（缓存感知）：** 路由器记录每个副本最近处理过的前缀，新请求优先发往"缓存里已有它最长开头"的副本。多轮对话的首 token 延迟可以下降数倍。
- **两者结合：** 命中率和负载加权打分。只看缓存会造成热点：某个热门系统提示的所有请求都挤到同一个副本，而其他副本空闲。所以当最优副本负载超过阈值时，退回按负载分配。

**开源实现：** SGLang 的路由器、vLLM 生态的生产部署方案（如 llm-d）都提供缓存感知路由。

**测试要点：**
- **命中率：** 用真实的多轮对话回放流量，比较轮询与前缀感知下的缓存命中率和首 token 延迟分布。
- **热点：** 构造 80% 请求共享同一前缀的偏斜流量，检查各副本负载是否仍然在可接受范围内。
- **副本故障：** 某副本下线时，它的会话被转移到其他副本，首 token 延迟会短暂升高，但请求不能失败。
