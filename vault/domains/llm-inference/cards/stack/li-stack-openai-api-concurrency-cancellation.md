## Q
除了单请求的功能正确性，OpenAI 兼容推理接口还要测试哪些并发、取消和慢客户端的场景？各自会暴露什么缺陷？

## A
**背景：** 推理服务同时处理大量流式连接，每个连接对应引擎里一个正在占用 KV 缓存（每个请求历史 token 每层的键、值向量，常驻显存）和计算资源的请求。连接层和引擎层的状态必须一致，否则就会泄漏资源或串话。

**场景与可能暴露的缺陷：**
- **客户端中途断开：** 发起一个要求生成 4,000 token 的流式请求，读到第 10 块后关闭连接。
  - 期望：服务端在很短时间内中止这个请求，释放它的 KV 缓存。
  - 缺陷：请求继续生成到结束，白白占用资源。高峰期大量用户刷新页面时，有效容量被"幽灵请求"吃掉。
  - 检查：断开后观察引擎的运行中请求数（如 vLLM 的 `vllm:num_requests_running`）是否在一两秒内下降。
- **慢客户端：** 客户端读取极慢（每秒读一块）。
  - 期望：服务端缓冲有上限，不会因为一个慢连接无限占用内存，也不阻塞其他请求的生成。
  - 缺陷：内存持续增长，或整个事件循环被阻塞，所有流一起变慢。
- **高并发流：** 同时打开 1,000 个流式连接。
  - 检查：每个流的块顺序正确、内容不串、全部以 `[DONE]` 结束；没有连接被无故截断。可在每个请求里放一个唯一的随机词并要求复述，校验不串话。
- **取消与重试的竞态：** 客户端超时后立即用相同内容重试。两个请求不应互相影响，计费只算实际产生的 token。
- **长时间排队：** 服务过载时，连接在等待第一个 token 期间不应被代理或负载均衡器的空闲超时切断；如果服务决定拒绝，应尽早返回 429 或 503，而不是让客户端等很久再超时。
- **优雅下线：** 滚动升级时停止一个实例，已在生成的流应该完成或得到明确的错误，新请求不再路由到它。

**工具：** 用 `asyncio` 加 `httpx` 或 OpenAI 的异步客户端写并发脚本；用 Locust、k6 生成持续负载；故障注入时配合 `kill -STOP`（暂停进程）模拟卡死的工作进程。
