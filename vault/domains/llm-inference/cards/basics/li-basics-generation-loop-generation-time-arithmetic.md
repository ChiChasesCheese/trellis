## Q
用 7B 模型在一块 H100 上回答一个"500 token 输入、300 token 输出"的请求，大约要多久？时间都花在哪里？

## A
**已知量（取整数便于手算）：**
- 7B 模型，每参数 2 字节，权重共 14 GB；处理每个 token 约 140 亿次浮点运算（每参数一乘一加）。
- H100：16 位矩阵乘法峰值约 989 万亿次/秒；显存（HBM，芯片旁的高带宽内存）带宽约 3.35 TB/s。

**第一阶段：处理输入（预填充，prefill）。** 500 个输入 token 一次性并行计算。
- 运算量：500 × 140 亿 = 7 万亿次。按峰值约 7 毫秒，按实际 50% 效率约 **15 毫秒**。
- 读权重：14 GB 只读一遍，约 4 毫秒，被 500 个 token 分摊，不是瓶颈。这一步受**算力**限制。
- 结果：得到第一个输出 token。

**第二阶段：逐个生成（解码，decode）。** 每个新 token 都要一次前向计算。
- 运算量：每步只有 140 亿次，约 0.014 毫秒，可以忽略。
- 读权重：每步都要把 14 GB 重读一遍，约 **4.2 毫秒**。这一步受**内存带宽**限制。
- 300 个 token × 约 5 毫秒（含其他开销）≈ **1.5 秒**。

**合计约 1.5 秒，其中 99% 花在解码上。** 用户感受到的两个指标：
- **首 token 延迟（TTFT，time to first token）：** 约 20 毫秒加上排队和网络。
- **每 token 间隔（TPOT，time per output token）：** 约 5 毫秒，即每秒约 200 个 token。

**由此得出的直觉：** 输入长度主要影响首 token 延迟；输出长度主要影响总时长；要让单用户生成更快，就要让每一步读的数据更少（压缩参数）或读得更快（更高带宽的内存）。
