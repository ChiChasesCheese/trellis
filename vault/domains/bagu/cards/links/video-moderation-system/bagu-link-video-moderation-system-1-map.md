## Q
**视频内容审核系统 · 会被追问哪些八股**｜必会

设计视频内容审核系统时，面试官最可能从哪几步下钻到基础知识？每一步问什么，怎么答？

## A
**基本回答。** 这是事件驱动的多阶段流水线。基础是：消息队列解耦与幂等任务、并行打分的超时与降级、处置动作的 outbox 与幂等重试、死信兜底，以及同步初筛和异步深审的分层。

**下钻路线。**
- 发布事件接入 → Kafka 按 videoId 分区，编排器消费，[[a.mq.kafka-architecture|Kafka 整体结构]]
- 重复事件会不会审两次 → 任务键是视频号加版本，消费端幂等，[[b.mq.no-duplicate|重复消费与恰好一次]]
- 某个模型很慢或失败 → 每个调用设超时，到截止时间缺失的分数不能当 0 放行，[[b.protect.timeout|超时时间怎么设置]]
- 模型全挂了 → 事先定好降级：暂缓分发或转人工，不能静默放行，[[b.protect.degrade|降级怎么做]]
- 判定违规后下架 → 判定与待处置记录同事务写入，带幂等键调用域服务，[[a.idem.outbox|本地消息表 / Outbox 与最大努力通知]]
- 下架一直失败 → 退避重试，超限进死信并报警，[[b.mq.dlq-retry|死信队列与重试设计]]
- 峰值积压 → 高风险和新账号走优先队列，先判断积压原因再扩容，[[a.mq.backlog|消息积压怎么办]]
- 评论要不要同样审 → 毫秒内同步初筛，深度审核异步补做，[[a.scenario.live-comment|直播间评论、弹幕与点赞的高并发设计]]

**业务场景。** 视频发布后先限制分发、并行审核；下架请求超时被重发，域服务按幂等键去重，不会重复下架或重复扣信用分。
**系统设计。** [[links.youtube|视频平台（YouTube）]]：同样是上传后的异步流水线，这里多了规则引擎和处置；[[links.fb-live-comments|Facebook 直播评论]]：评论必须在毫秒内同步初筛，不能等深度审核。
