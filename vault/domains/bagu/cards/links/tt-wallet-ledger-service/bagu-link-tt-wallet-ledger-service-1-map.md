## Q
**钱包与复式账本服务（余额、冻结、转账、多币种） · 会被追问哪些八股**｜必会

设计钱包与复式账本服务（余额、冻结、转账、多币种）时，面试官最可能从哪几步下钻到基础知识？每一步问什么，怎么答？

## A
**基本回答。** 这套设计绕不开四个基础：同一笔业务只入账一次（幂等），账本只追加且借贷相等，余额不为负靠条件更新，热点账户靠追加加快照。跨分片转账、冻结和对账是在这之上的补偿与兜底。
**下钻路线。**
- 充值通知重复、乱序、晚到 → 以 (来源, 来源流水号) 为主键，与分录同一个事务，去重表永久保留，[[a.idem.payment-idempotency|支付与扣款接口的幂等设计]]
- 账本怎么建模 → 只追加的借贷分录，余额是投影，扣减用 `WHERE balance >= x` 条件更新，冲正追加反向分录，[[b.scenario.ledger-design|复式账本]]
- 冻结、确认、释放 → 冻结是 Try，确认是 Confirm，超时释放是 Cancel，条件更新让确认与超时只有一个成功，[[a.idem.tcc|TCC]]
- **热点账户只追加分录：** 热点账户每片 723 次/s 对单行 500 次/s → 同步路径只追加分录，余额等于快照加增量，按秒合并净额，[[a.scenario.payment-system|支付系统设计]]
- 跨分片转账 → 不用 2PC，转出方事务借在途账户并写发件箱，转入方用同一个转账号幂等入账，[[b.idem.two-pc-at|2PC / 3PC / XA 与 Seata AT 模式]]
- 账变后通知下游 → 同事务写发件箱，至少一次投递，消费者去重，[[a.idem.outbox|本地消息表 / Outbox]]
- 欧洲用户的钱包 → 用户绑定归属区域，写入都回该区域，[[b.distributed.multi-region|多区域与归属区域写入]]
- 怎么证明账是平的 → 分录重算余额，总额守恒，与渠道结算单核对，[[a.idem.selection-reconciliation|分布式事务选型、最终一致与对账]]

**业务场景。** 观众充值的应用商店通知隔几分钟重发一次，又恰逢主播提现：充值只入账一次，提现前用分录重算余额，与余额字段比对。
**系统设计。** [[links.tt-live-gift-coin-settlement|直播虚拟礼物：金币记账与主播结算]]：钱包之上的热点主播与周结算，那里币是平台预付负债；[[links.payment-batch-processing|支付处理系统（授权冻结 + 每日批量结算）]]：冻结与扣款相同，但多了外部渠道超时未知。
