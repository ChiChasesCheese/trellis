## Q
**框架 vs 直接调 API · 何时引入**｜实践 · 必会

同事想一开始就用 LangChain 之类的框架搭 RAG 应用，理由是「现成的抽象省事」。你怎么回应？

## A
**代价：** 框架会增加抽象层，**遮住实际发给模型的 prompt 和模型的原始回复**。出了错，你看不到模型到底收到了什么，调试变难；也容易在本来简单的场景里叠上不必要的复杂度。

**做法（Anthropic 的建议）：**
1. 先**直接调 model API**，许多模式几行代码就能实现；
2. 引入框架时，先读懂它底层在做什么——「对底层做了错误假设」是常见的出错原因；
3. 进生产时尽量**减少抽象层，用基本组件搭**。

**自检清单：**

| 问题 | 不能回答就别用 |
|---|---|
| 最终发给模型的完整 prompt 是什么？ | 看不到 = 没法调 |
| 重试、超时、解析失败谁处理？ | 默认行为可能不是你要的 |
| 换模型或换检索库时改几处？ | 框架的价值本应在这 |

**折中：** 先写一版裸调用做原型，评测通过后，再判断框架里有哪几块（如文档解析器、向量库适配）值得借用，**按需取用**，不整体绑定。
