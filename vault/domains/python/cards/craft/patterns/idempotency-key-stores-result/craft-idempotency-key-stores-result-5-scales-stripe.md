## Q
**幂等键存结果 · 从内存字典到 Idempotency-Key 请求头**｜架构

一个进程里，幂等键是字典加锁。支付 API 面对成千上万的客户端、多台服务器时，同样的语义怎么实现？键的作用域和保留期要怎么定？

## A
**要点。** 语义完全不变（原子占位 → 执行 → 存结果 → 同键同体返回原结果，异体报错），变的是「原子」由谁提供：内存里靠一把锁，分布式靠存储的唯一约束（或 Redis 的 `SET NX`）。键的作用域是（调用方，键），而不是一个全局命名空间。

```
LeetCode 级:  dict[key] -> result          （冻结值对象，一行 != 判等）
LLD 级:       (client, key) -> Record      （占位、等待者、租约、保留期）
分布式级:     PRIMARY KEY (client, key)    （INSERT 失败 = 别人占了）
```

**为什么作用域要含调用方。** 参考解里一个转账系统的 `client_key` 是全局命名空间：两个客户端碰巧选了同一个键，第二个会被当成重复请求，要么拿到别人的收据，要么被误报冲突。加上调用方前缀，键才只对自己的请求负责。

**保留期。** 太短：重试窗口比保留期长，过期后的重试被当成新请求，重复执行；太长：表无限增长，存储成本上升。通常取比客户端最长重试窗口再大一点，并且只有已完成的记录才会过期，执行中的记录归租约管。

**信号。** 重试、at-least-once 投递、需要 exactly-once 效果；接受这一切的办法是「重复执行也无害」，而不是「保证不重复到达」。
