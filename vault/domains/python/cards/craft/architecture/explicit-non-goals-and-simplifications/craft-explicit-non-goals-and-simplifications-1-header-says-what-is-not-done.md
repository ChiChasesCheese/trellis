## Q
**明说的简化与非目标 · 限流器写完了，面试官问「扩到多机怎么办」，文件头里该提前写什么**｜架构

你用 45 分钟写了一个进程内的限流器：一把锁、一个字典、四种算法。写完后面试官一定会追问：多机呢？时钟漂移呢？持久化呢？不事先说明的话，这些问题看上去都是漏洞。怎样让「没做」变成「有意没做」，并且预先回答追问？

## A
**要点。** 在文件头用几句话写清三件事：做的是什么、**刻意没做**什么（非目标，non-goal）、换成真实版本时**只动哪里**（接缝，seam）。没做的东西没写出来，读者只能猜是遗漏；写出来，它就成了一个被评估过的取舍，追问也有了现成的答案。

```python
"""限流器（Rate Limiter）：进程内的库级组件，不是分布式限流架构。   # 范围 + 非目标
"怎么记住最近的流量"整体做成可替换的 `RateLimitAlgorithm`……          # 接缝：换算法只动这一处
`RateLimiter` 只负责"按 key 隔离状态 + 分片加锁 + 回收闲置 key"……   # 职责边界
"""
```

上面是限流器题解文件头的节选。任务调度器的开头同样先划范围：「进程内的延时/周期任务调度，不是分布式任务队列」，随后说时间只从注入的时钟来，所以调度逻辑不需要真实 sleep 就能测。

**为什么。** 非目标有两重作用：对读者，它标出「这里有意简化」的地方，评审时不会把它当成 bug；对你自己，写下它逼你想清楚边界到底画在哪里。多机限流需要共享存储（如 Redis）和原子计数，这和进程内的算法接口是两个问题，现在不做不会让现有设计变形。

**易错。** 只写「不支持 X」是不够的，要同时写出接缝：换成真实版本时改哪个类、哪个方法。没有接缝的非目标听上去只是借口。也不要把本该做的核心需求写成非目标；非目标应是被有意推迟的、规模上或精度上的扩展。
