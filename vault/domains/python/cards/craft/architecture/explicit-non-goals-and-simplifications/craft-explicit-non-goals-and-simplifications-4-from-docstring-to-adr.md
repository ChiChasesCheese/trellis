## Q
**明说的简化与非目标 · 从一个文件头到分账、发布订阅、再到设计文档里的非目标小节**｜架构

「明说没做什么」在一个函数的注释里、一个组件的文件头里、一份多服务设计文档里，是同一个动作吗？每一层要多写什么，才能让下一个读者不用问你？

## A
**要点。** 是同一个动作，每升一级多写一样东西：**触发条件**，即什么情况出现时这个简化就不够用了。函数级写保证和不保证（分账的贪心）；组件级写范围和换真实版本的接缝（发布订阅的自动提交）；设计文档级写成非目标小节，并附上重新评估的信号。

```python
def read(self, sub_id, max_items=1, timeout=0.0):
    """读一批并推进游标，返回 `(消息, 掉队丢失条数)`。
    游标在读到的瞬间就前进（自动提交）。手动提交能做到"处理成功才前进"、
    从而给出至少一次语义，代价是要多一个 `commit(seq)` 接口和一份未提交区间
    ——进程内组件用不到。"""
```

这是发布订阅题解里的真实注释：写出了没做什么（手动提交）、拿到什么（至少一次语义）、付出什么（接口和未提交区间），最后一句说明为什么这里不需要。

升到设计文档时，同样的内容变成一小节：

```
非目标：不做跨节点复制。         # 没做什么
接缝：Log 接口，换实现不动消费者。  # 换的时候动哪里
重新评估的信号：单机吞吐超过磁盘带宽，或要求节点故障后不丢消息。  # 触发条件
```

**为什么。** 规模每涨一级，读者越不可能直接问到你。函数的读者能看见整个文件，设计文档的读者可能是半年后的接手人，只有把理由和触发条件写下来，「现在不做」才不会被误读成「没想到」。

**易错。** 非目标不能只列清单。「不做多机」不如「单机内存放得下就不做多机；队列深度持续超过内存的一半就重新评估」，后者可以被检验，前者只是一个声明。
