## Q
`git revert` 是怎么撤销一个改动的？撤销一个合并提交（merge commit）为什么要加 `-m 1`？撤销之后想重新合入，要注意什么？

## A
**`git revert <提交>` 不删除历史，而是新建一个"反向"提交**，内容恰好抵消原提交的改动。共享分支上只用 revert，不用 `git reset` 加强制推送，因为后者改写了别人已经拉取的历史。

**撤销普通提交**：`git revert 4f9c2e1`，生成新提交 "Revert ..."，正常走评审和 CI 合入。

**撤销合并提交**：合并提交有两个父提交，Git 不知道"相对谁"来算反向改动。`-m 1` 表示以第一个父提交（合并时所在的分支，通常是主干）为基准，撤销被合并进来的那一侧：

```bash
git revert -m 1 <合并提交>
```

**重新合入的坑**：撤销合并后，Git 认为那条功能分支上的提交"已经合并过了"。修好问题后再次 `git merge feature`，Git 只会带进修复之后的新提交，之前被撤销的那些改动不会回来。正确做法二选一：
- **先撤销那个"撤销提交"**（revert the revert），把原改动恢复，再合入修复；
- 或者把功能分支 rebase 成全新的提交再合入。

**主干开发里的实际流程**：
1. 主干变红，找到嫌疑提交，直接 `git revert`，作者不需要在场；
2. 作者在自己分支上修复，新的改动包含原改动加修复，重新走评审和完整 CI；
3. revert 提交的说明里写清原因和失败链接，方便追踪。

**对 squash 合并的仓库更简单**：一个改动就是一个提交，revert 一个提交就撤销整个改动，不需要 `-m`。这也是很多团队选择 squash 的原因之一。
