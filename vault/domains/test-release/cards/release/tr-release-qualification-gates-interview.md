## Q
面试里被问"你怎么判断一个推理服务的版本可以发布？发布放行检查怎么设计"，怎么答？

## A
先一句话铺垫：推理服务是把训练好的模型（一大组数字参数加一串计算步骤）部署成在线服务；token 是模型处理文字的最小单位。

- **放行检查分三类证据**：正确性（服务行为、接口、输出与参考在容差内一致）、准确率（在有标准答案的题集上答对的比例不下降）、性能（首个 token 延迟、每秒生成的 token 数，与基线比）。再加稳定性（长稳）和已知问题清单。
- **每条标准可检查**：写成数字门限和明确的比较对象，例如"p99 延迟相对上一正式版本退化不超过 5%，每种配置分别检查"；准确率用逐题成对比较判断是否显著，不只看总分。
- **证据绑定版本**：所有结果引用发布候选的制品摘要；最终发布的就是被验证的那一份；放行检查核对期望执行条数，防止"没跑也算过"。
- **准入也要设**：切分支时主干夜间全集通过、特性通过集成就绪，否则发布验证一开始就在排雷。
- **决定流程**：一页报告给出结论、逐条结果、豁免、没覆盖到的风险；发布负责人决定；豁免必须有负责人和到期版本。
- **放行检查之后还有金丝雀**：先给 1–5% 流量，自动对比错误率和延迟，异常回滚。放行检查降低风险，金丝雀兜底真实流量下的问题。

收尾：用逃逸缺陷数和金丝雀回滚次数来检验放行检查本身是否有效，逃逸的每一类问题都要反推到放行检查里补一条。
