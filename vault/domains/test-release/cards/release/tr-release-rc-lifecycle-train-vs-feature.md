## Q
按固定时间发布的"发布列车"（release train）和"功能做完才发布"相比，各有什么优缺点？为什么多组件的软件栈更常用发布列车？

## A
**发布列车**：按固定节奏发车（例如每两周、每四周），到点切分支，没赶上的功能坐下一班。浏览器（Chromium、Firefox）都是这种模式。

**功能驱动发布**：定好这个版本要包含的功能，全部完成并验证后才发布。

| | 发布列车 | 功能驱动 |
|---|---|---|
| 可预期性 | 日期固定，下游可以提前安排 | 日期不断推迟 |
| 单次发布的改动量 | 小、稳定 | 越拖越大，风险越高 |
| 对功能的压力 | 赶不上就等下一班，不会强行塞入 | "就差一个功能"让整个发布等待 |
| 验证 | 每次规模相近，流程可以固化 | 规模不定，验证计划每次重做 |
| 缺点 | 需要功能开关隐藏未完成的功能；节奏本身有固定开销 | 适合确实必须一起发布的大功能 |

**多组件栈为什么偏好列车**：
- 编译器、运行时、固件等多个团队各有进度，按功能等，最慢的那个决定所有人的日期；
- 固定日期让每个团队都知道"切分支那天我的组件必须是绿的"，集成压力被均匀分摊；
- 发布验证团队可以按固定节奏安排硬件时间；
- 跨组件的兼容性按"同一班车上的版本组合"来管理，组合数量有限。

**列车上的大功能怎么办**：提前合入主干但默认关闭（功能开关），在若干班车里逐步打开：先内部、再小范围用户、再全部。功能"上车"和功能"对用户可见"是两件事。

**紧急修复**不等列车：从当前发布分支出补丁版本（例如 1.8.1），走缩短的验证流程。
