## Q
多个组件需要一起升级时（例如运行时和固件），升级顺序怎么定？怎样在发布前验证这个顺序和回滚路径都是安全的？

## A
**原则：先升级"被依赖、且向后兼容"的一方，再升级依赖它的一方**。这样在任何中间状态，组合都在支持范围内。

**例子**：新运行时要用新固件提供的一个新能力。
- **安全的顺序**：先升级固件（新固件仍支持旧运行时的全部调用）→ 观察一段时间 → 再升级运行时 → 最后再打开新能力的开关。
- **危险的顺序**：先升级运行时。新运行时一启动就调用旧固件没有的接口，直接失败；或者更糟，旧固件把不认识的参数忽略，结果静默出错。

真实例子：Kubernetes 规定升级时先升级 API 服务器，再升级控制器和调度器，最后升级各节点的 kubelet，并且不能跳过小版本，原因就是"服务端先兼容新旧客户端"。

**发布前的验证清单**：
1. **每个中间状态都测**：旧旧、新旧（升级到一半）、新新三种组合各跑冒烟和关键回归，而不只是测最终状态。
2. **回滚路径也测**：新新 → 新旧（回滚运行时）是否可用？新旧 → 旧旧（再回滚固件）是否可用？有没有不可逆的步骤（例如固件升级后写入了新的设备配置，旧固件读不懂）？不可逆的步骤要单独标出，放到最后，并在发布说明里写明。
3. **能力探测而不是版本假设**：运行时启动时询问固件支持哪些能力，没有就走旧路径，并打日志；测试要覆盖"能力不存在"的分支。
4. **开关后置**：新能力默认关闭，所有组件升级完成并观察稳定后再打开；测试覆盖开和关两种状态。
5. **演练**：在测试集群上按真实的升级脚本完整执行一遍，包括中途失败、回滚。

**写进发布说明**：支持的升级路径（从哪些版本可以直接升级）、升级顺序、回滚的限制。
