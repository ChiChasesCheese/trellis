## Q
发布验证的准入标准（entry criteria）和准出标准（exit criteria）怎么写才可检查？给一个推理服务发布的例子。

## A
**可检查 = 每一条都能用一个数字或一个是 / 否回答，并且写明数据从哪里来**。"性能没有明显下降"不可检查，"首个 token 延迟 p99 不比上一版本高 5% 以上"可以检查。

先定义几个指标：**token** 是模型处理文字的最小单位；**首个 token 延迟**（TTFT，time to first token）是从请求发出到收到回答第一个 token 的时间；**吞吐**是每秒总共生成的 token 数；**准确率**是模型在一套有标准答案的题目上答对的比例。

**准入（开始发布验证的前提）**：
- 切出的提交上，主干夜间全集通过，无未分诊失败；
- 所有计划进入本版本的特性已通过集成就绪检查；
- 发布候选制品已构建，版本清单完整（编译器、运行时、固件版本都有记录）；
- 验证所需的硬件已预留。

**准出（可以发布的条件，示例数字）**：

| 类别 | 条件 |
|---|---|
| 正确性 | 发布阻断级套件 100% 通过（豁免除外）；无新的崩溃或挂起 |
| 数值 | 与参考实现的输出差异在约定容差内 |
| 准确率 | 每个基准题集上与上一版本的差异不显著（成对检验），且绝对下降不超过 1 个百分点 |
| 性能 | 首个 token 延迟 p50 / p99、吞吐与基线相比退化不超过 5%，在每种支持的配置上分别检查 |
| 稳定性 | 长稳测试 12 小时无内存增长、无错误率上升 |
| 阻断项 | 无未关闭的阻断项；所有豁免有负责人、理由和到期日 |

**写法要点**：
- **按配置分别检查**：不同模型大小、不同硬件型号各有基线，不能只看平均；
- **写明比较对象**：和上一个正式版本比，而不是和上一个 RC 比（否则可以每次退化一点）；
- **写明谁签字**：每一类由谁确认；
- **写明豁免流程**：不满足某条时谁能批准例外、需要什么记录。
