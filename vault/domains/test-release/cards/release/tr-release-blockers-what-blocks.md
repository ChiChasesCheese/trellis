## Q
什么样的问题应该阻断一次发布？以大语言模型推理服务为例，给出判断标准，并说明为什么"静默算错"比"崩溃"更严重。

## A
先说被测系统：推理服务把训练好的模型（一大组数字参数加一串计算步骤）部署成在线服务，收到问题就生成回答。

**阻断发布的常见标准**（满足任一条）：
- **相对上一个正式版本的回归**：用户在旧版本上没问题，升级后出问题。这是最核心的一条，因为"发布"本身让情况变坏了。
- **结果静默出错**：回答内容被截断、乱码、和参考实现差异超出容差，或者准确率（在有标准答案的题集上答对的比例）显著下降。
- **数据或安全问题**：一个用户的请求内容出现在另一个用户的回答里、日志泄露敏感数据、权限校验失效。
- **可用性**：崩溃、挂起、内存持续增长导致服务几小时后不可用。
- **性能大幅退化**：超过约定门限，例如首个字的延迟比上一版本慢 20%，会让下游的超时设置失效。
- **没有绕开的办法**，或绕开的办法对用户不现实。

**通常不阻断**：上一版本就存在、本版本没有变坏的问题（记录为已知问题）；外观和文字问题；只影响未启用功能的问题。

**为什么静默算错比崩溃更严重**：
- **崩溃会被立刻发现**：监控报警、请求失败、客户端重试，影响范围在几分钟内可见，可以回滚。
- **静默算错不会触发任何报警**：服务返回 200，延迟正常，但回答内容是错的。用户可能把错的回答用进自己的产品，几天后才有人发现，影响无法回收。
- **定位更难**：没有错误日志和堆栈，只能靠数值对比和准确率测试发现。

所以推理服务的阻断标准里，正确性和准确率的门限往往比可用性更严格，并且必须在发布前由测试主动发现，而不是指望线上报警。
