## Q
两个 PR 各自的提交前测试都是绿的，也没有合并冲突，先后合入后主干却红了。这是怎么发生的？提交前检查、合并队列和"提交后检查 + 回滚"三种保护各能挡住多少？

## A
**这叫语义冲突（semantic conflict）**：两个改动在文本上不冲突，但组合起来行为不对。

例：
- PR A 把函数 `alloc(size)` 改名为 `alloc_bytes(size)`，并改了所有调用处；
- PR B 新增了一处 `alloc(size)` 调用；
- A 的测试基于不含 B 的主干，B 的测试基于不含 A 的主干，都通过。两个都合入后，B 新增的那行调用了一个不存在的函数，构建失败。

更隐蔽的版本：A 改了某个配置的默认值，B 的新测试依赖旧默认值，编译都没问题，只有测试在组合后失败。

**三种保护的对比**：

| 保护方式 | 能挡住语义冲突吗 | 代价 |
|---|---|---|
| 只有提交前检查 | 不能：测的是旧主干 + 单个 PR | 最便宜 |
| 要求 PR 基于最新主干才能合入 | 能，但每次主干前进所有 PR 都要重跑，繁忙仓库里排不上 | 浪费大量 CI |
| 合并队列 | 能：测的就是要合入的确切组合 | 需要队列基础设施；队列吞吐受 CI 时长限制 |
| 提交后检查 + 回滚 | 事后发现，主干会红一段时间 | 便宜；依赖值班和回滚纪律 |

**实际组合**：提交前检查挡住大部分问题；合并队列挡住组合问题，主干上的每个状态都测过；提交后和夜间测试兜住提交前不跑的慢测试和硬件测试，靠 revert first 快速恢复。

**多仓库的软件栈**还有一层：编译器仓库和运行时仓库之间的语义冲突，单仓库的合并队列看不见。需要跨仓库的集成作业，用"各组件最新的通过版本"组合起来测。
