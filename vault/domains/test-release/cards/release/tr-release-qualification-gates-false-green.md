## Q
发布放行检查全绿，发布后却出了明显问题。放行检查"假绿"有哪些常见原因？各自怎么防？

## A
- **测试根本没跑**：筛选条件写错或测试收集出错，阻断级套件实际执行了 0 条，被当成"无失败"。
  防：放行检查核对"期望执行条数"，少于期望即失败；`pytest` 退出码 5（没有收集到测试）按失败处理。
- **测的不是要发布的那个版本**：验证用的是 RC2，发布的是挑拣过一个修复的 RC3，RC3 没完整验证。
  防：放行检查结果绑定制品摘要；发布流水线只接受有完整证据的那个摘要。
- **基线错了**：性能和准确率（模型在一套有标准答案的题上答对的比例）和"上一个 RC"比，而不是和上一个正式版本比，每个 RC 退化 2%，累计 8% 无人察觉。
  防：基线固定为上一个正式版本，并按配置分别维护。
- **只看平均，不看分布**：平均延迟没变，但 p99 翻倍；总体准确率没变，但某类长输入全部出错。
  防：门限同时包括分位数和分组指标；准确率逐题对比，看变化集中在哪类输入。
- **测试配置和线上不一样**：性能只在单个请求时测，线上是几十个请求一起处理（批处理，batching）；准确率只测短题，线上大量长对话。
  防：用线上流量统计来设计测试负载，至少覆盖线上最常见的几种配置。
- **豁免成了常态**：同一个失败连续五个版本被豁免，最后没人记得原因。
  防：豁免必须有到期版本，到期自动转为阻断；看板展示豁免数量和年龄。
- **flaky 被重试刷绿**：失败自动重试到通过，真实的间歇性缺陷被掩盖。
  防：放行检查报告中单独列出"重试后通过"，阻断级套件不允许无记录的重试。

一句话：放行检查本身也是一段需要测试的代码，要定期检查它能不能被一个故意注入的缺陷触发。
