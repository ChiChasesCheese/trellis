## Q
一次发布从计划的 3 个发布候选变成了 9 个，推迟了两周。这种"RC 反复"（RC churn）通常是什么原因？怎么避免？

## A
**直接原因**：每个新 RC 都带进了新的改动，每次验证又发现新问题，形成循环。

**常见根因**：
- **切分支时主干就不健康**：切出的提交上夜间测试本来就有失败，被当作"已知问题"带进来，验证时才发现其中有真正的阻断项。
- **功能"晚上车"**：功能在切分支后才勉强完成，以"修复"的名义挑拣进来，带着新代码和新缺陷。
- **挑拣的修复不完整**：修复依赖主干上的其他改动，挑拣后引入新的问题，需要再挑拣。
- **验证太晚太集中**：发布验证档只在 RC 上跑，许多问题本该在主干的夜间测试中提前几周发现。
- **阻断标准不清**：什么都被标成阻断，每个都要修；或者标准随时变化。
- **验证本身不稳定**：flaky 测试让每个 RC 都"有新失败"，需要人工逐个确认。

**怎么避免**：
- **切分支的准入标准**：主干在切出的提交上夜间全集通过、无未分诊的失败，不满足就推迟切分支，而不是带病切出。
- **把发布验证的大部分内容前移到主干**：每周（或每晚）在主干上跑一次和发布验证相同的套件，切分支时已经知道结果。
- **挑拣门槛随时间收紧**，新功能一律不挑拣。
- **攒批出 RC**：按天汇总修复，而不是每个修复一个 RC。
- **清晰的阻断标准**和发布负责人的最终裁定权。
- **测试信号稳定**：发布验证档里的 flaky 测试优先治理。

**事后复盘要量化**：每个 RC 带进了多少改动、每个阻断项是哪一天在哪一档本可以被发现。目标是让 RC 数量和挑拣数量逐版本下降。
