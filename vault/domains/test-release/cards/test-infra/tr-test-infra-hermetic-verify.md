## Q
怎么检验一个测试套件真的是隔离、可复现的？给出几种可以放进 CI 的检查。

## A
思路：**故意改变那些"不应该影响结果"的条件，看结果变不变**。

- **跑两遍比结果**：同一提交、同一镜像连续跑两次，结果（以及生成的文件哈希）应完全一样。不一样就说明有时间、随机或外部状态漏进来。
- **打乱顺序**：装上 `pytest-randomly` 插件后，每次运行都随机打乱测试顺序，并在输出开头打印所用种子；失败时用 `--randomly-seed=<种子>` 原样复现。顺序一变就失败，说明测试间有共享状态。
- **单独跑每条测试**：`pytest path::test_name` 单独运行通过、放在套件里失败，或反过来，都是依赖。
- **断网跑**：`docker run --network none ...` 或 `pytest --disable-socket`（`pytest-socket` 插件）。任何偷偷访问网络的测试会立刻报错。
- **换机器、换用户、换时区**：在另一台 CI 机器上以不同用户跑，设 `TZ=Asia/Shanghai` 再跑一次，结果应一致。
- **只读 home 目录**：把 `HOME` 指向一个空的临时目录，发现读写用户配置文件的测试。
- **从干净环境装依赖**：每次 CI 从锁文件新装（`uv sync --locked`），而不是复用上次的虚拟环境，防止"我机器上多装了一个包"。

**放进 CI 的方式**：每晚跑一个"可复现性作业"，用不同种子、不同顺序、不同机器跑同一提交，对比结果；不一致的测试自动开工单。提交前只跑正常顺序，避免拖慢反馈。

这些检查也是排查 flaky 测试的第一步：一条测试在打乱顺序或断网时才失败，根因基本就找到了。
