## Q
一个没有分层的测试框架会在什么时候、以什么方式出问题？举一个具体的失败场景。

## A
**典型场景**：300 条集成测试里，每条都自己写了 `ssh lab-node-17`、自己起服务、自己 `time.sleep(30)` 等它就绪、自己用 `abs(a - b) < 1e-3` 比较结果。

一年后实验室换了一批新机器，同时服务接口从 HTTP 改成 gRPC：
- **改动面爆炸**：300 个文件都要改，一个月改不完，期间大部分测试是红的或被跳过，回归信号等于没有；
- **改漏的地方静默变错**：有人把新机器名改错，测试连到一台旧版本机器，照样"通过"；
- **容差不一致**：各处容差从 `1e-3` 到 `1e-1` 不等，没人知道哪个是对的，真实精度回退从宽松的那几条里漏过去；
- **框架 bug 被当成产品 bug**：等待时间不够导致的失败被报给产品团队，产品团队开始不信测试结果。

**预防**：
- **资源、驱动、判定集中实现**，测试里禁止出现主机名、端口号、裸 `sleep`，可以用一条 lint 规则检查；
- **框架本身有测试**：用一个假的被测系统（fake）跑框架的单元测试，框架改动先过这些测试；
- **框架的失败要和产品失败区分上报**：资源申请失败、驱动超时标为"基础设施错误"，不计入产品失败率；
- **有负责人和版本**：框架作为一个产品维护，变更有发布说明。

一句话：没有分层的框架，维护成本随测试数量线性增长；分层的框架，维护成本只随"变化的种类"增长。
