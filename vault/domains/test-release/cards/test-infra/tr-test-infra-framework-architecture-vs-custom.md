## Q
团队要做一个测试框架，是在 pytest（或 Go 的 `testing`）之上扩展，还是自己写一个测试运行器（runner）？各自的代价是什么？

## A
**默认选扩展现成框架**，自研只在现成框架的模型装不下时才做。

在 pytest 之上扩展能免费拿到：
- **用例发现、参数化、fixture 生命周期**，以及 `-k`、`-m`、`--lf`（只跑上次失败的）、`-x`（第一个失败就停）这些人人会用的命令；
- **生态插件**：`pytest-xdist` 并行、`pytest-timeout` 超时、`pytest-rerunfailures` 重跑、JUnit XML 报告；
- **招来的人直接会用**，IDE 和 CI 都认识它的输出。

自研 runner 的理由通常只有这几种：
- **测试单位不是一个函数**：一次"测试"是在 64 台机器上同时启动的分布式作业，或一个持续 8 小时的长稳运行，需要自己的调度、心跳和部分失败语义；
- **需要跨进程、跨机器协调**，pytest 的单进程模型不合适；
- **结果模型不是通过 / 失败**：性能测试产出的是一组数字，判定要和历史分布比较。

**折中做法**最常见：外层自研编排器负责申请硬件、分发作业、汇总结果；每台机器上执行的仍是 pytest，输出 JUnit XML。这样编排复杂度只在一处，测试作者面对的还是熟悉的 pytest。

**自研的隐藏成本**：报告格式、超时、重跑、并行、选择都要自己做一遍，并为它们写测试；新人要学一套私有概念。一个框架没人维护时，测试开始被绕开写成独立脚本，分层就崩了。
