## Q
一个跑在加速芯片上的推理软件栈，手上有 CPU 上的功能模拟器（几千个实例）和几十台真芯片机器。怎样决定一条测试放在哪个环境跑？

## A
加速芯片（accelerator）是专门做大规模数值计算的芯片；推理（inference）就是用训练好的模型（一大组数字参数加一串计算步骤）回答请求。

**原则：放在"最便宜、又能稳定发现这类风险"的环境**。按风险类型分：

| 风险 | 放在哪 | 理由 |
|---|---|---|
| 计算结果算错（编译器、内核逻辑） | 模拟器为主 | 结果只取决于逻辑，模拟器便宜、确定、能看中间值 |
| 编译产物格式、接口兼容 | 模拟器或纯 CPU | 不需要芯片 |
| 并发、时序、数据传输竞争 | 真芯片 | 模拟器的时序不真实，看不到竞争 |
| 性能和延迟 | 真芯片，固定机型 | 模拟器的速度没有意义 |
| 长时间稳定、内存泄漏、发热 | 真芯片，夜间或发布验证 | 只有真实运行才会积累 |
| 多机通信、故障切换 | 真芯片集群 | 需要真实网络和多台设备 |

（内核（kernel）是在芯片上执行一个基本运算，例如矩阵乘法的小程序。）

**落实到框架里**：
- **同一条测试能在多个环境跑**：驱动层提供统一接口，`--target=sim` 或 `--target=hw` 切换，测试逻辑不变。
- **测试声明它要的最低环境**：`@pytest.mark.needs("hw")` 的测试不会被调度到模拟器。
- **按档位组合**：提交前跑模拟器上的快速子集；提交后加少量真芯片冒烟；夜间和发布验证跑真芯片的完整集合。
- **保留一组"对照测试"**：同样的小计算在模拟器和真芯片上都跑，结果必须一致（在容差内）。它们失败，说明模拟器和芯片对不上，模拟器上的其他测试结果也要打折扣。

稀缺的真芯片时间要留给只有它能发现的问题，而不是用来跑模拟器也能抓到的计算错误。
