## Q
主干上没有任何代码改动，CI 却在某天早上突然大面积失败。和"测试不隔离"有关的常见原因有哪些？怎么定位？

## A
**"代码没变、结果变了"说明有没被钉住的输入变了**。常见几种：

- **依赖没锁**：`requirements.txt` 写的是 `numpy>=1.20`，上游发了大版本。真实例子：NumPy 2.0 在 2024 年 6 月发布，改了一批 API 和类型提升规则，大量没锁版本的项目当天 CI 变红。
- **镜像用了 `latest` 标签**：基础镜像被更新，系统库或 Python 小版本变了。
- **测试时下载外部数据**：从模型仓库按名字下载模型文件（模型就是一大组训练好的数字参数），没有指定版本，上游更新了文件，输出跟着变。
- **时间相关**：证书过期、测试里写死的日期过了、夏令时切换、年份变化。
- **共享环境被别人改了**：共用的测试数据库被清空，共用机器被升级了驱动。

**定位步骤**：
1. **确认代码确实没变**：拿昨天通过的那个提交重跑。它现在也失败，就证明是环境变了，不是代码。这一步也说明对代码做二分（bisect，在提交区间里反复取中点测试，找出引入问题的那个提交）没有用。
2. **对比两次运行的环境清单**：已安装的包版本（`pip freeze`、`uv pip list`）、镜像摘要、驱动版本、机器。差异就是嫌疑。
3. **逐个钉回旧值验证**。

**修复和预防**：
- 锁文件 + `--locked` 安装；镜像用摘要；外部数据按版本或哈希引用；
- 每次运行把完整环境清单存进结果库，下次对比只需一个 diff；
- 依赖升级走正常提交：一个自动开的"升级锁文件"改动，跑完整套件，通过才合入。这样"上游变化"变成"一个可回滚的提交"。
