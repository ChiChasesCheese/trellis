## Q
一份能让负责人直接开始工作的缺陷报告（bug report）应该包含什么？给一个模板。

## A
**标准：负责人读完不需要再来问你任何问题，就能复现并开始分析**。

```text
标题: [运行时] 输入超过 8k token 时，流式响应在第一个分块后挂起
版本: RC3（制品 sha256:ab12…），编译器 4f9c2e1，运行时 77d0b3a，固件 3.8.1
环境: hw-a 型号，机器 lab-07 / lab-12 均可复现；lab 外的模拟器上不复现
复现: uv run pytest tests/serving/test_stream.py::test_long_prompt --target=hw
频率: 10 次中 4 次；输入 4k token 时 0/20
期望: 返回完整回答，结束标记正常
实际: 收到第一个分块后无响应，60 秒后客户端超时
首次: RC3；RC2 上 0/20。两者之间 3 个挑拣（列表见链接）
证据: 挂起时 py-spy 栈、服务日志、dmesg 输出（链接）
影响: 发布验证长稳套件失败；线上长对话用户可能受影响
严重度: S2（建议），是否阻断待发布负责人确认
```

（token 是模型处理文字的最小单位，约等于一个词或词的一部分；流式响应是边生成边分块返回回答。）

**要点**：
- **标题**写组件、条件和现象，而不是"测试挂了"。别人在列表里扫一眼就知道是什么。
- **复现**是一条可以直接复制运行的命令，加上需要的配置；能缩小到最小输入更好。
- **频率**写成具体的次数比，偶发问题尤其重要。
- **期望和实际**分开写；实际结果附原始输出，而不是转述。
- **首次出现和对比**：最后一次正常的版本、第一次出问题的版本、两者之间的改动。这一条常常直接指出原因。
- **证据**用链接，日志不要整段贴进正文。
- **只写事实和明确标注的推测**：推测写成"怀疑……，依据是……"。

一份好报告节省的是负责人的时间，也是整个团队等待修复的时间。
