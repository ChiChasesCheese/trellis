## Q
给 `git bisect run` 写判定脚本时，要处理哪些情况？写一个能应对"编译不过"和"测试偶发失败"的脚本。

## A
**要处理的情况**：
- **构建失败**：中间提交编译不过，和要找的问题无关，应该跳过（退出码 125），而不是判为坏。
- **测试本身偶发失败**：一次失败不代表坏。判坏要更确定：例如跑 N 次，只要失败就判坏；判好则要求 N 次全过。N 由失败率决定。
- **挂起**：给测试加超时，超时算坏（如果找的就是挂起问题）或跳过（如果挂起和本问题无关）。
- **只关心目标问题**：只看目标测试的结果，不看整个套件，否则别的问题会干扰判断。
- **基础设施错误**：设备申请失败之类，退出 125 或者重试，不能当成"坏"。

```bash
#!/usr/bin/env bash
# 用法: git bisect run ./check.sh
make build >/dev/null 2>&1 || exit 125          # 编不过：跳过
for i in $(seq 1 10); do                        # 失败率约 30% 的问题，10 次都不出现的概率约 2.8%
  timeout 600 pytest -q -x tests/test_long_input.py::test_no_hang
  rc=$?
  [ $rc -eq 124 ] && exit 1                     # 超时：要找的就是挂起，判坏
  [ $rc -eq 4 ] || [ $rc -eq 5 ] && exit 125    # 测试文件不存在或没收集到：跳过
  [ $rc -ne 0 ] && exit 1                       # 失败一次即判坏
done
exit 0                                          # 10 次都通过：判好
```

**N 怎么定**：问题在坏提交上的失败概率是 p，跑 N 次都没出现（被误判为好）的概率是 (1 − p)ᴺ。p = 0.3、N = 10 时约 0.028；p = 0.05 时要 N = 60 才能降到约 0.046。失败率越低，二分越贵，所以先尽量找到让问题稳定复现的条件（更大的负载、更长的输入），再二分。

**测试文件不存在的问题**：如果复现测试是新写的，旧提交里没有它。做法是把测试放在仓库外面的固定路径，脚本里引用那个路径，而不是依赖每个提交里自带的测试。
