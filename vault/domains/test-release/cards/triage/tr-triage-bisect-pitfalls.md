## Q
`git bisect` 给出了一个"第一个坏提交"，但这个提交看上去和问题毫无关系。可能是哪里出了错？

## A
**二分结果错误的常见原因**：

- **区间内有两个问题**：提交 A 引入了编译失败（或另一个测试失败），后来被修好；提交 B 引入了要找的回归。判定脚本把"编译失败"也当成"坏"，二分会停在 A。
  对策：编译失败退出 125（跳过）；判定只看目标测试和目标症状，例如检查具体的错误信息，而不是只看"有没有失败"。

- **不稳定的判定**：某次在坏提交上测试碰巧通过，被标成"好"，之后的所有步骤都在错误的半边里走。
  对策：每个点多跑几次；用 `git bisect log` 查看每一步的判定，对可疑的那一步重测，然后编辑日志、`git bisect replay` 修正。

- **"好"的起点其实不好**：所谓好的旧版本，在今天的环境（新驱动、新依赖）下也会失败，那么问题不在代码里。
  对策：开始前先在"好"和"坏"两端各确认一次。

- **掉进合并分支里**：二分进入了一个被合并进来的功能分支的中间提交，那里的代码本来就不完整。
  对策：`git bisect start --first-parent`，只在主干的提交上走。

- **问题出现后又消失过**：二分假设"坏了之后一直坏"。如果中间有一段被某个提交意外遮盖了，结果可能是区间内任意一个变化点。
  对策：对二分结果做确认实验（嫌疑提交失败、它的父提交通过），并检查区间中更多的点。

- **问题依赖于不在仓库里的东西**：模型文件（训练好的一大组数字参数）、测试数据、配置是从外部下载的"最新版"，每个点测的其实不是同一个输入。
  对策：外部输入按版本固定，脚本里显式指定。

- **嫌疑提交只是"暴露"了问题**：例如它改变了内存布局，让一个早就存在的越界读取开始出错。二分结果是对的，但根因在别处。
  对策：把二分结果当成线索，而不是结论；分析这个提交为什么会触发问题。
