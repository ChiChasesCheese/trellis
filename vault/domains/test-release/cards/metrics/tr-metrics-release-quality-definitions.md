## Q
衡量发布质量常用哪些指标？通过率、不稳定率、逃逸缺陷、缺陷逃逸率、MTTD、MTTR 分别怎么定义和计算？

## A
**测试信号类**（测试系统本身是否可信）：
- **通过率（pass rate）**：某一档、某段时间内，通过的测试执行数 ÷ 全部执行数。要说明是否排除了基础设施错误和被隔离的测试，否则数字没法比。
- **不稳定率（flake rate）**：同一构建上结果不一致（既有通过又有失败）的测试执行占比，或"重试后通过"的执行占比。反映信号的噪声。

**结果类**（发布出去的东西好不好）：
- **逃逸缺陷（escaped defect）**：发布之后才被发现（用户、线上监控、下游团队报告）的缺陷，按版本和严重度统计数量。
- **缺陷逃逸率（defect escape rate）**：逃逸缺陷数 ÷（逃逸缺陷数 + 发布前发现的缺陷数）。例：一个版本发布前发现 47 个、发布后发现 3 个，逃逸率 = 3 ÷ 50 = 6%。比单看逃逸数量更能反映测试的拦截能力。
- **按严重度看逃逸**：一个 S1 逃逸比十个 S4 逃逸更说明问题，所以通常单独报告 S1 / S2 的逃逸数。

**时间类**：
- **MTTD（mean time to detect，平均发现时间）**：从缺陷被引入（合入或发布）到被发现的平均时间。越短，修复越便宜。
- **MTTR（mean time to restore / repair，平均恢复时间）**：从发现问题到恢复正常服务（或修复上线）的平均时间。要说清楚 R 指恢复还是修复：回滚恢复服务可能 10 分钟，真正修复可能 3 天。
- 这类时间分布往往偏斜，常用中位数和 p90 代替平均值。

**发布过程类**：
- 每个版本的发布候选数、挑拣数、豁免数，计划发布日期与实际发布日期的偏差。它们反映发布过程是否健康、可预期。

**使用原则**：每个指标都写清楚定义（分子、分母、排除了什么），并且看趋势，而不是看某一次的绝对值。
