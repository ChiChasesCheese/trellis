## Q
CI 里的"缓存"（cache）和"制品"（artifact）有什么区别？缓存的 key 怎么设计？缓存用错会造成什么问题？

## A
**本质区别：缓存是可有可无的加速，制品是必须正确的产出**。

| | 缓存 | 制品 |
|---|---|---|
| 内容 | 依赖目录、编译中间文件 | 构建结果：安装包、镜像、二进制 |
| 不命中时 | 重新下载或重新编译，只是慢 | 后续阶段无法进行，是错误 |
| 正确性要求 | 命中的内容必须等价于重新生成 | 必须可追溯：哪个提交、哪次构建、什么摘要 |
| 保留 | 几天，按 key 淘汰 | 发布用的长期保留 |

**缓存 key 的设计**：key 必须包含"所有会影响缓存内容的输入"。
- 依赖缓存：`key: deps-${{ runner.os }}-${{ hashFiles('uv.lock') }}`，锁文件一变 key 就变。
- 可以配 `restore-keys: deps-${{ runner.os }}-` 做前缀回退：精确 key 不命中时用最近的一份，再增量更新。
- 编译缓存还要包含编译器版本和编译选项。

**用错的后果**：
- **key 漏了输入 → 假绿**：key 只按操作系统区分，没包含锁文件哈希。依赖升级后仍命中旧缓存，CI 测的是旧依赖，合入后在干净环境里才失败。
- **缓存被污染**：一次构建把坏文件写进了缓存（例如中途被杀，写了一半），之后所有命中它的运行都失败或行为异常。对策：只在成功的运行结束时写缓存；提供手动清缓存的入口。
- **把缓存当制品用**：后面的阶段从缓存里拿构建结果，缓存一旦被淘汰，流水线就失败；或者拿到的是别的分支写进去的结果。
- **缓存跨信任边界**：来自外部分支的 PR 写入的缓存被主干构建读取，存在投毒风险。主干只读主干自己写的缓存。

**判断一个缓存是否安全**：把它删掉，结果应该完全一样，只是变慢。做不到这一点，它就不是缓存。
