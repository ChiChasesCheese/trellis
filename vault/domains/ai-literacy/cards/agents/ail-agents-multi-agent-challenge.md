## Q
**挑战。** 一位同事提议："我们做一个六智能体系统来修线上 bug：分析员、编码员、评审员、测试员、文档员、发布员，各管一段，像真实团队一样。"另一位说一个智能体加一份清单就够了。请评审这个提案：什么情况下拆是对的？你会怎么改？

## A
**评分点（答出 3 条算过）：**

1. 指出成本：多智能体 token 约是聊天的 15 倍（单智能体约 4 倍），修一个 bug 的价值未必付得起。
2. 指出结构问题：修 bug 是强依赖、共享同一份代码上下文的任务，拆开后每次交接都会丢信息，编码和测试改同一批文件还会冲突。
3. 说明拆的收益在哪：并行和隔离上下文，只在广度优先、子任务独立时才划算，按角色拆（模仿人类团队）不等于按上下文边界拆。
4. 给出折中：主流程用一个智能体；把"读大量日志、搜索代码库"这类会产生大量中间输出的子任务交给子智能体，只回传结论；评审交给干净上下文的独立会话。
5. 提出验证方式：同一批历史 bug 上对比两种方案的成功率、token 和时间，数据说话。

<details class="pt"><summary>参考答案</summary>六个按角色划分的智能体会把本来需要共享上下文的修 bug 流程拆碎，每次交接都有信息损失，还要付约 15 倍的 token。更合理的是一个主智能体负责修复，只把会产生大量中间输出的任务，比如搜日志、找调用点，交给子智能体并只取结论，评审放在干净的独立会话里做。最后用一批历史 bug 对比两个方案的成功率、成本和耗时来决定。</details>
