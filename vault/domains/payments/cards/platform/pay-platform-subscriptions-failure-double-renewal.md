## Q
订阅续费为什么会重复扣款？请用一次调度事故说明，并说明如何用幂等设计杜绝。

## A
**怎么发生**：平台有一个每日 00:00 的续费调度任务，扫描到期订阅并逐个扣款。任务运行在两台机器上做高可用，但没有做互斥。某天部署新版本时，旧实例还没停，新实例已经启动，两台机器在同一分钟都开始了扫描。

**过程**
1. 两个实例都读到了同样的 100,000 张到期账单。
2. 每个实例为每张账单生成一个**随机幂等键**（例如用 UUID）并调用渠道。
3. 渠道看到的是两个不同的幂等键，视为两笔独立请求，都执行了扣款。
4. 结果：100,000 位用户在同一天被扣两次，平均每笔 10 美元，重复金额约 1,000,000 美元。
5. 平台次日对账发现，大量客诉与拒付随之而来，需要批量退款，渠道费用不退，品牌受损。

**根因**
- 调度任务缺少互斥与分片归属。
- 幂等键随机生成，等于没有幂等。
- 扣款前没有再检查账单当前状态。

**如何杜绝**
1. **幂等键由业务含义决定**：`账单号 + 尝试序号`。两个实例对同一张账单、同一次尝试生成相同的键，渠道只执行一次。
2. **账单上的条件更新抢占**：`UPDATE invoice SET attempt_state='sending' WHERE id=? AND attempt_state='idle'`，只有一个实例能抢到，另一个影响行数为 0 就跳过。
3. **调度分片**：账单按 ID 哈希归属到固定实例，或使用分布式锁/租约。
4. **扣款前重新读取账单状态**：已支付就跳过。
5. **对账告警**：同一张账单在渠道文件里出现多笔成功扣款，立刻告警并自动退款。
6. **灰度发布与滚动部署**：旧实例先优雅下线，避免同时运行。
