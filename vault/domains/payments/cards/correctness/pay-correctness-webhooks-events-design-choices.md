## Q
处理 PSP 状态更新，可以直接信任 webhook、收到后回查、纯轮询，各有什么取舍？大平台怎么组合？

## A
| 方式 | 做法 | 好处 | 代价 |
|---|---|---|---|
| 直接信任 webhook 内容 | 按事件内容更新状态 | 实时、简单 | 乱序、伪造、丢失都会直接伤害状态 |
| 收到后回查 | webhook 只当触发，用 API 取当前状态再推进 | 抗乱序与伪造，状态以 PSP 当前真相为准 | 多一次调用，受 PSP 限流影响 |
| 纯轮询 | 周期性查询未终态的单据 | 不依赖对方推送，不丢 | 延迟高，调用量大 |
| 对账补偿 | 每日用渠道文件修复 | 最终保证 | 延迟到次日 |

**组合**
1. **主路径**：webhook → 验签 → 收件箱 → 异步处理，处理时对关键状态回查。
2. **补偿路径**：对停留在 pending / unknown 超过阈值的单据定时查询（轮询只针对少数卡住的）。
3. **兜底**：对账。

**选择依据**
- 状态的重要度：涉及资金（成功、退款、打款）的，回查加对账；通知类的，直接处理即可。
- PSP 的 API 配额：回查要控制频率，批量或合并查询。
- 延迟要求：用户在等的支付结果，webhook 主推，轮询作为补充，间隔随时间拉长。

**避免**：只靠 webhook 而没有任何补偿；或者每个 webhook 都同步回查拖慢确认。收件箱先确认，回查放在异步处理里。
