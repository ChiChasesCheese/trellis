## Q
两个携带同一个幂等键的请求几乎同时到达，服务端怎么保证只有一个真正执行？进程在处理中途崩溃怎么办？

## A
**并发同键**
1. 两个请求都尝试 `INSERT` 幂等记录，状态为 processing，主键是（商户，键）。
2. 数据库的唯一约束保证只有一个插入成功，另一个收到冲突错误。
3. 成功的那个继续执行业务；失败的那个读取已存在的记录：
   - 状态为 done：返回保存的结果。
   - 状态为 processing：返回 409 并带 Retry-After（让客户端稍后用同一个键重试），或短暂等待后再读。

**处理中崩溃**
- 记录停在 processing，后来的请求永远读到 processing，客户端一直被挡着。
- 解决：记录里保存 `locked_until`（租约到期时间）。过期后新请求可以通过条件更新接管：`UPDATE ... SET locked_until = now + 30s WHERE key = ? AND locked_until < now`，成功者重新执行。
- 重新执行的前提：业务步骤本身也幂等，或者先去渠道查询上一次尝试的结果，不能盲目再发一次扣款。

**为什么不用分布式锁**：Redis 锁会过期、主从切换会丢，持锁者暂停（GC、网络抖动）后锁被别人拿走，两个都执行。唯一约束由数据库保证，是更可靠的单点裁决。

**与业务事务的关系**：幂等记录与业务数据同库同事务，这样不会出现"记录写了业务没做"或"业务做了记录没写"。幂等记录若放在另一个存储，就要接受并处理这种不一致。
