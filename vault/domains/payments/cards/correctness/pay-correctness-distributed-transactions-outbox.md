## Q
Outbox（发件箱）模式是什么？它如何避免"数据库提交了但消息没发出"或"消息发了但事务回滚"？

## A
**两种典型错误**
- 先提交数据库，再发消息：提交之后、发消息之前进程崩溃，业务已成功但下游永远收不到通知。
- 先发消息，再提交数据库：消息发出，事务回滚，下游处理了一个并没有发生的事。

数据库和消息队列是两个系统，无法放进同一个事务。

**Outbox 的做法**
1. 在**同一个数据库事务**里：更新业务数据（支付单状态、分录）并向 `outbox` 表插入一行待发事件。要么都提交要么都回滚。
2. 一个独立的中继进程（relay）轮询 outbox（或订阅数据库变更日志 CDC），把未发送的事件发布到消息队列，成功后标记已发送（或删除）。
3. 中继可能在发布后、标记前崩溃，于是事件会**至少一次**投递；下游必须**幂等消费**（以事件 id 去重）。

**示例**：支付成功事务写入：`payment(state=captured)`、3 行分录、`outbox(event_id=e_501, type=payment.captured, payload=…)`。中继发布 `e_501`，订单服务按 `e_501` 去重后更新订单。

**取舍**
- 好处：简单、强可靠，业务不依赖消息队列的可用性。
- 代价：有延迟（轮询间隔或 CDC 延迟）；outbox 表要清理；事件顺序只保证同一聚合内的有序（按聚合 id 分区）。

**支付里的位置**：几乎所有"状态变化后要通知别人"的地方——订单通知、webhook 出站、发币、风控特征更新——都应该走 outbox。
