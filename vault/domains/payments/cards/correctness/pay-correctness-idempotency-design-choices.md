## Q
幂等的几种实现方式——幂等键表、业务唯一约束、状态机条件更新、Redis 去重——各适合什么场景，怎么组合？

## A
| 方式 | 做法 | 适合 | 局限 |
|---|---|---|---|
| 幂等键表 | 保存键、请求指纹、响应，同事务写入 | 对外 API 的创建类操作，需要回放响应 | 要管理保留期和清理 |
| 业务唯一约束 | 订单号加动作类型建唯一索引 | 创建类内部写入，最可靠 | 只能表达"只做一次"，不能回放响应 |
| 状态机条件更新 | `UPDATE ... WHERE status = 旧状态` | 状态流转，如请款、退款成功 | 只适用有状态的对象 |
| Redis 去重 | `SET NX` 加过期 | 挡掉大部分重复，减轻数据库压力 | 可丢，过期，不能当最终保证 |

**组合**
1. **入口层**：幂等键表，处理客户端重试并回放响应。
2. **业务层**：每个写入动作有业务唯一约束，兜住幂等键表被绕过（如内部直接调用）的情况。
3. **状态流转**：条件更新，防止并发重复推进。
4. **消息消费**：以消息 id 去重，与业务写入同事务；或者靠业务唯一约束天然去重。
5. **Redis**：可选的前置过滤，不作为依据。

**选择依据**：这个操作是否有对外副作用（扣款、发币、发货）？有就必须在数据库里有唯一裁决点；是否需要把第一次的响应原样回放？需要就要幂等键表。
