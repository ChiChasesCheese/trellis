## Q
实现支付状态机时，资深工程师会坚持哪些做法？

## A
1. **转移表集中定义**，写成数据或一个模块，而不是散落的 if 判断；有单元测试覆盖每条合法和非法的边。
2. **所有状态变更走同一个函数**：`transition(entity, from, to, event)`，不允许其他代码直接写 status。
3. **条件更新**：`WHERE state = from`，影响行数判断成败；不要先读后写。
4. **同一事务做三件事**：更新状态、写状态历史、写分录 / outbox 事件，要么都发生要么都不发生。
5. **状态历史追加**：from、to、原因、触发事件 id、时间、操作人（自动或人工）。
6. **终态不可变**：终态没有出边；终态之后的"修正"用新的单据（如退款单）表达，而不是改原单状态。
7. **UNKNOWN 是一等状态**：渠道调用超时置为 unknown / pending_unknown，驱动查询与对账，而不是强行落成成功或失败。
8. **区分重复与冲突**：目标状态已经等于期望状态是幂等重复，静默成功；状态阶位更高是过期事件，忽略并记录；状态阶位冲突（如已失败却来成功）是异常，告警人工。
9. **监控停滞**：停在 pending、requires_action、unknown 超过阈值的单据数量和年龄。
10. **渠道状态映射**：独立的映射层，渠道新增状态时显式处理，不默认当成功。
