## Q
为什么支付单、退款单、打款单要用显式的状态机，而不是随手改一个 status 字段？

## A
**问题**：支付里的事件来自多个异步来源——用户操作、渠道同步响应、webhook、轮询、对账、运营后台——它们会**重复、乱序、并发**到达。如果每个来源都直接把 `status` 改成它认为的值：
- 晚到的"已授权"事件把已请款的订单改回已授权，随后又被请款一次；
- 两个线程同时处理同一单，一个标成功、一个标失败，最终状态取决于谁后写；
- 终态（已退款）被后来的事件覆盖，账与状态对不上；
- 没人知道一笔单是怎么走到当前状态的。

**状态机的做法**
1. 事先定义**合法的状态集合**和**合法的转移**（A 状态只能到 B、C 状态）。
2. 状态只**单调前进**，终态没有出边。
3. 每次转移用**条件更新**（`WHERE status = 旧状态`），并发时只有一个成功。
4. 每次转移**写历史**：从哪来、到哪去、为什么、由哪个事件触发。

**设计空间**
- 单一 status 字段：简单，转移规则散落在代码里。
- 单一 status 加集中的转移表：规则可读可测，推荐。
- 事件溯源：状态由事件序列推导，审计最强，复杂度最高。
- 多维状态（支付状态、请款状态、退款金额）：当一个单据有独立演进的几个侧面时使用。
