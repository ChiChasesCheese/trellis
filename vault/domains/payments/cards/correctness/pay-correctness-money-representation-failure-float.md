## Q
一个把金额乘以 100 再取整的转换，为什么会让某些订单少收一分钱？怎么发生，怎么避免？

## A
**事故过程**
1. 接口接受 JSON 里的金额 `19.99`，转换为最小单位时写成 `int(amount * 100)`。
2. 在 Python 里：`19.99 * 100 = 1998.9999999999998`，`int()` 截断得到 1998，而不是 1999。
3. 订单实际被收取 19.98 美元，少了一分钱。每个这样的订单差一分，对账时渠道金额与内部金额不一致，只在部分金额上出现，难以复现。
4. 反向问题：`round(19.99 * 100)` 得 1999 看似正确，但换成别的金额或语言（如 JS 的 `Math.floor`）仍会出错，且这依赖于运气。

用 Decimal 则精确：`int(Decimal("19.99") * 100)` 等于 1999。

**根因**：用浮点数承载十进制金额，并用截断取整。

**避免**
- 入口处就把金额当字符串解析为 Decimal，或要求客户端直接传整数最小单位；绝不 `float()`。
- 数据库、消息、日志中全部用整数最小单位。
- 代码审查和静态检查禁止对金额变量使用 float 类型。
- 契约测试：用一批"危险金额"（0.1、0.29、19.99、1.005 等）对序列化、反序列化、转换函数做往返测试。
- 对账规则里，金额差恰好为一分的差错单单独分类统计，它们往往指向某个舍入或浮点缺陷。
