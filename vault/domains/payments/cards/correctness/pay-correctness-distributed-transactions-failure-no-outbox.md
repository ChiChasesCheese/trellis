## Q
支付成功后先提交数据库再发消息，导致"用户付了钱但订单一直待支付"。怎么发生的，怎么修？

## A
**事故过程**
1. 支付服务收到渠道的成功通知，在数据库中把支付单置为 captured 并提交事务。
2. 紧接着，代码要向消息队列发布 `payment.captured`，通知订单服务。
3. 就在提交与发布之间，实例被滚动发布终止（或消息队列短暂不可用，发布抛异常被吞掉）。
4. 支付单已成功，分录已记，但订单服务从未收到事件，订单一直是"待支付"，库存到时自动释放。用户付了钱没有订单，投诉。
5. 反过来的顺序（先发消息再提交）更糟：消息发出，数据库提交失败，订单被标成已支付而钱并没有收到。

**根因**：数据库写和消息发布是两个独立动作，中间没有原子性。

**修复**
- 使用 outbox：事件和支付状态同一个事务提交，中继进程保证至少一次投递，订单服务幂等消费。
- 监控：outbox 里未发送事件的数量和最老年龄。
- 兜底的修复任务：定期扫描"支付已 captured 但订单仍待支付"的记录，重新发布事件，或直接修复。
- 对账：订单与支付单的状态一致性对比，每日检查。

**为什么不靠重试发布**：进程崩溃时重试的内存状态也没了；只有落库的事件才能在重启后继续投递。

**附带的设计要点**：订单服务消费事件时同样要幂等（事件 id 去重），否则中继重复投递会重复更新订单。
