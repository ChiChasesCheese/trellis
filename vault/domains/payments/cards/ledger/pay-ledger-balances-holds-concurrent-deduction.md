## Q
账户余额 100 美元，两个请求同时各扣 80 美元，没有保护时发生什么？有哪几种防止透支的做法？

## A
**无保护的流程**
1. 请求 A 读余额 100，判断 100 ≥ 80，通过。
2. 请求 B 读余额 100，判断 100 ≥ 80，通过。
3. A 写回 20。B 写回 20（或各自 `balance = balance - 80` 得到 −60）。
结果：用户花了 160，只有 100，平台损失 60；或者某一个更新丢失，账不平。

**三种做法**
1. **条件更新**（推荐）：`UPDATE account SET balance = balance - 80 WHERE id = ? AND balance >= 80`。数据库对行加锁串行执行，第二个请求发现 20 < 80，影响行数为 0，拒绝。原子、无需额外锁、快。
2. **悲观锁**：`SELECT ... FOR UPDATE` 先锁行再判断再更新。语义直观，但持锁时间长，热点上吞吐低。
3. **乐观锁 / 版本号**：`WHERE version = ?` 失败就重试。冲突少时好用，冲突多时重试风暴。

**同时要写分录**：条件更新和分录插入放在同一个事务里；余额不足时整个事务回滚，不留分录。

**例子**：A 先拿到锁，余额 100 → 20，写入分录；B 的条件更新匹配 0 行，返回"余额不足"。最终花费 80，余额 20，账平。

**注意**：允许透支的账户（如平台自有的应收类科目）不加 `>=` 条件；有这个约束的账户在数据库层再加 CHECK (balance >= 0) 做最后一道防线。
