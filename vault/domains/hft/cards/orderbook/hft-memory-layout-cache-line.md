## Q
订单簿里每笔订单的记录要设计得多大才合适？为什么大家喜欢让它刚好占 32 字节或 64 字节？

## A
**背景：** CPU 从内存读数据，最小单位是缓存行（cache line），在 x86 上通常是 64 字节。读一个字节，也会把它所在的整条 64 字节读进缓存。命中缓存只要约 1 ns，未命中要去内存读，约 100 ns。

**设计原则：**
- **热字段放一起：** 撮合和更新时每次都要用的字段（价格、剩余数量、前后链表指针）紧挨着放，一次读取就够。
- **冷字段分开：** 很少用的字段（比如用于日志的时间戳、客户标识）放到另一个结构里，不要占热数据的缓存空间。
- **大小对齐：** 记录刚好 32 字节，一条缓存行恰好放 2 笔订单，不会有一笔订单跨在两条缓存行上。

**数字例子：** 一笔订单：8 字节编号 + 4 字节价格 + 4 字节数量 + 4 字节 prev + 4 字节 next + 其他 = 32 字节。200 万笔订单共 64 MB。

**反面：** 如果每笔订单是 100 多字节的 Java 对象，再加上散落的位置，同样的工作要读更多缓存行，缓存里能放下的订单数也更少，未命中更频繁。

要点：低延迟代码的瓶颈常常是读内存，而不是算术。
