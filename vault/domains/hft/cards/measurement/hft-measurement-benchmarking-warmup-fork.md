## Q
为什么 Java 微基准必须先“预热”？JMH 里的 `@Warmup`、`@Measurement` 和 `@Fork` 分别在解决什么问题？

## A
Java 代码刚开始是被**解释执行**的，运行一段时间后，被调用够多次的热点方法才被 JIT 编译成机器码（先 C1，再 C2）。C2 的触发门槛大约是**一万次**量级的调用或循环迭代。如果直接计时，测到的是解释器和半优化代码的速度，比稳态慢得多，而且数字在变。

- **`@Warmup`**：先跑若干轮不计分的迭代，让 JIT 把热点编译完成、数据进入缓存；
- **`@Measurement`**：预热后的若干轮才计分，此时代码处于稳态；
- **`@Fork`**：每组测试在一个**全新的 JVM 进程**里运行。因为 JIT 会根据已经看到的类型和分支“做假设”并优化，同一进程里先跑别的测试会留下它的剖析数据，污染后面的测试（例如本来能内联的调用因为见过另一种类型而不能内联）。

例：一个方法首次 1000 次调用平均 800 ns，预热后稳态 40 ns，差 20 倍；只测第一段会得出完全错误的结论。
