## Q
一个交易进程上线后延迟比测试时高了约 30%，排查发现是 NUMA 问题。可能是怎么发生的？如何确认和修复？

## A
典型原因：
1. 进程启动时没绑核，操作系统把交易线程调度到了插槽 1，而它的行情缓冲区和订单簿是启动线程在插槽 0 上第一次写入的。于是热路径上每一次缓存未命中都要去远端取，单次约 140–200 ns，而不是 80–100 ns。
2. 或者网卡挂在插槽 0 的 PCIe 上，处理线程却在插槽 1：收到的包先写进插槽 0 的内存，线程要跨插槽读。

确认：
- `numastat -p <pid>` 看进程的内存分布在哪些节点。
- `perf` 统计远端内存访问的比例，或对比绑核前后的延迟。

修复：用 `numactl --cpunodebind=N --membind=N` 启动，或在代码里把线程固定到网卡所在节点的核，并让交易线程自己初始化内存。修复后延迟回到本地内存的水平。

这类问题的特点是平时看不出来，只在部署环境或机器型号变化时才冒出来，所以上线检查要包含 NUMA 布局。
