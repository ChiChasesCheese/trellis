## Q
策略代码里"是否发单"这个分支，绝大多数时候都不发单，偶尔才发。这对延迟有什么隐患，业界通常怎么处理？

## A
隐患：预测器根据历史学习，这个分支 99.9% 的时候走"不发单"，于是被训练成预测"不发单"。真正需要发单的那一刻，恰恰是**最重要**的时刻，CPU 却会猜错，付出约 15–20 个周期的清空代价。

更糟的是，发单路径的代码和数据平时很少执行，已经不在指令缓存和数据缓存里（冷代码、冷数据），一次要在主内存里取，每次约 100 ns，叠加起来可能多出几百 ns 到几微秒。

处理办法：
- **预热**（warm-up）：空闲时用假数据反复把完整的发单路径走一遍，只在最后一步（真正发到网卡之前）丢掉，保持缓存和预测器是热的。
- **让两条路径形状相同**：尽量让"发"和"不发"的指令序列相近，把判断放在最后，减少路径差异。
- C++ 里用 `[[likely]]` / `[[unlikely]]` 等提示，帮编译器安排代码布局。

要点：优化平均延迟没用，要优化的是"关键时刻的延迟"。
