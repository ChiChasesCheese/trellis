## Q
零垃圾编码的代价是什么？为什么不应该在整个代码库里推行？

## A
代价有三类：
- **正确性风险**：可变对象加手工清理，容易出现脏数据、别名（多处持有同一对象）之类的 bug；
- **工具受限**：Stream、`Optional`、`String.format`、`HashMap<Long, ...>` 这些常用写法大多不能用；
- **可读性**：代码更长、更像 C，评审和维护更难。

收益却只在“被执行极多次且对尾延迟敏感”的路径上才有。所以做法是：只对热路径（比如每条行情、每个订单的处理）做零分配；启动、配置、管理命令这些冷路径照常写；先用 JFR 的分配剖析找到最大的分配源，再动手。每秒执行 100 万次的路径值得改，每天跑一次的不值得。
