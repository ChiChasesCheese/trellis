## Q
Nagle 算法和 TCP 延迟确认（delayed ACK）叠加会出什么问题？为什么交易系统几乎总要设置 `TCP_NODELAY`？

## A
**Nagle 算法**：为了减少网络上的小包，发送方如果还有数据没被对方确认（ACK），就把新的小数据先扣住，等到 ACK 回来，或攒够一个满段再发。
**延迟确认**：接收方收到数据后不立刻回 ACK，而是等一小会儿（Linux 上最多约 40 ms），看有没有数据可以顺便捎带回去。

两者叠加的例子：客户端先发一个 20 字节的消息头，又发 40 字节的消息体。
1. 消息头先发出，等待对方确认；
2. 消息体是小包，被 Nagle 扣住，等消息头的 ACK；
3. 服务端收到消息头，但它还在等消息体才开始处理，于是延迟确认先不回 ACK，等数据或超时；
4. 双方互相等，直到服务端的延迟确认定时器到期，约 **40 ms** 后才继续。

对交易系统，40 ms 是灾难。

解决：设置 `TCP_NODELAY` 关闭 Nagle，写下去立刻发。同时尽量把一条完整消息在一次 `write` 里写出。

Nagle 并非"坏东西"，它对大量连续写小块数据的吞吐有益，但对请求/响应型的交互式小消息有害。
