# AI 辅助开发（AI-Assisted Development）：用 AI 写、审、测代码

读者：资深后端工程师，已经在用 Claude Code、Cursor 之类，想把它用成稳定的工程流程，并能在团队里讲清楚证据与风险。
和 ai-literacy 的分工：work.ai-coding / agents.coding-agents 只给概念与一页总览；这里是可操作的流程、验证方法、安全与度量。
记号：`*` = 帕累托核心；`(需先: …)` = 真依赖。

## 1. 工具形态与心智模型
- * 编程助手的四种形态：补全、对话、智能体、后台异步 — 各自的上下文来源、自主程度、适用任务；从补全到智能体是权责的转移
- * 编程智能体的工作原理：循环、工具、上下文 — 读文件、跑命令、改代码、看结果再继续；能力来自环境反馈，不来自一次写对
- * 上下文窗口是核心稀缺资源 — 窗口越满表现越差；对话里每一次读文件、跑日志都在占用；清理与压缩的时机
- * 模型的能力边界：擅长与不擅长 — 擅长：样板、迁移、测试、解释代码、范围明确的改动；不擅长：隐含约束、跨系统一致性、没有验证手段的任务
- 非确定性与同题多解 — 同一提示每次结果不同；需要把「对不对」交给测试，而不是交给「看起来对」
- 模型与档位选择：何时用强模型、何时用快模型 — 规划用强、批量机械改动用快；成本与吞吐
- 工具对照：终端智能体、IDE 助手、云端异步智能体 — Claude Code、Codex、Cursor、Copilot 的定位差异（只讲类型，不讲界面）

## 2. 工作流：规格、计划、实现、验证
- * 探索 → 计划 → 实现 → 提交 的四段循环 — 先只读探索，再让它写计划，再动手；跳过计划的代价
- * 规格优先（spec-first / spec-driven development）— 先写需求、验收标准、边界条件，再让智能体实现；规格就是评测
- * 给智能体一个可运行的检查：测试、类型、lint、预期输出 — 最高杠杆的一件事；没有检查，「做完了」不可信
- * 写具体的提示：范围、约束、参照物 — 指向文件与现有模式、说明不要做什么；模糊提示换来过度实现
- * 小步提交与可回退 — 每个任务一个检查点；用版本控制当撤销键；大改拆成可审查的块
- 先问后做：让它采访你 — 在需求不清时让模型提问，产出规格
- * 测试驱动配合智能体：先红后绿 — 先让它写失败的测试并确认失败，再实现；防止它为通过测试而改测试
- * 纠偏的时机：中途打断、回滚、重开会话 — 同一错误纠正两次仍不对就清空重来；长对话里的纠偏越积越差
- 无人值守与批处理：脚本化运行、定时与事件触发 — 无头模式、CI 里调用；输出格式、权限与预算上限
- * 并行会话与 Git 工作树（worktree）— 每个会话一个隔离目录；合并冲突与任务切分
- 子智能体：把探索与审查放进独立上下文 — 只回传摘要，保护主上下文；成本的另一面
- 长任务：检查点、进度文件、初始化脚本 — 跨上下文窗口接力；用文件而非对话保存状态

## 3. 上下文文件与可复用配置
- * 项目上下文文件：CLAUDE.md / AGENTS.md — 放命令、约定、坑；每次会话都加载，所以要短；删掉智能体能从代码里读出的内容
- * 写好上下文文件的规则 — 具体可检验、不放空话；过长则规则被忽略；定期修剪；分层（用户级、项目级、子目录级）
- * 确定性规则用钩子与权限，建议性规则用文字 — 「必须」的事交给 hooks、沙箱、权限规则强制；写在提示里只是请求
- 技能（skills）与斜杠命令：把团队流程封装起来 — 按需加载而非常驻；发布、迁移、审查流程
- 连接外部工具：MCP 与命令行 — 优先用已有 CLI；MCP 服务器的上下文开销与信任问题 (需先: 编程智能体的工作原理)
- 上下文文件的跨工具标准：AGENTS.md 与各家文件名 — 多工具共存时单一来源加导入
- 对旧代码库的引导：架构地图、术语表、领域约定 — 让智能体先建立地图；记录「为什么」而非「是什么」

## 4. 验证与代码审查（AI 写的代码怎么信）
- * 验证优先于生成：审查成为瓶颈 — 生成变便宜后，限制产出的是阅读与验证；审查要变成流程而非凭感觉
- * AI 代码的典型缺陷：几乎对但不对、虚构 API、吞掉错误、过度工程、悄悄改测试 — 每类的识别特征与排查办法
- * 小差异审查法：限制变更体量、逐段读 — 大块 AI 差异无人能审；强制拆分
- * 让另一个会话或模型审查（独立审查者）— 新上下文看差异，避免自我认同；审查提示要对照规格
- * 测试作为合同：不要让生成者同时定义「对」 — 人写或人审验收测试；变异测试、属性测试检验测试质量
- * 运行它：真实环境的端到端验证 — 启动服务、请求、看日志与界面；类型检查通过不等于功能正确
- * 依赖与 API 核实：包是否存在、版本是否匹配 — 虚构包名（slopsquatting）与过时用法；锁文件与文档对照
- 性能与复杂度回归 — AI 常写出 O(n²) 或多余查询；基准与查询计划检查
- 可维护性：重复、风格漂移、一致性 — 复制粘贴式生成累积技术债；linter 与架构测试约束
- * 理解债（comprehension debt）：合并了没人读懂的代码 — 规则：不能向同事解释的代码不合并
- 评审礼仪：披露 AI 参与、责任仍归提交者 — 团队约定；开源项目对 AI 贡献的政策

## 5. 用 AI 做测试与质量工作
- * 生成单元测试：覆盖路径与边界 — 好用的前提：被测代码清晰；盯住「只断言实现」的伪测试
- * 用 AI 复现并定位缺陷 — 给日志、复现步骤与失败测试；让它先写复现再改
- 遗留代码的特征测试（characterization tests）— 先固定现有行为，再重构；AI 适合批量生成
- 大规模迁移与重构 — 框架升级、API 替换：脚本化 + 分批验证 + 每批一个检查点
- 端到端与界面测试：浏览器自动化 — 让智能体操作页面并截图验证；脆弱点与成本
- 模糊测试与属性测试辅助 — 让模型提出不变量与输入生成器
- 文档、注释与变更说明 — 生成再校对；文档与代码漂移的检查

## 6. 安全与风险
- * 密钥与敏感数据：不进提示、不进仓库、不进日志 — 环境变量与密钥管理器；让智能体读不到 .env 的权限规则
- * 仓库内容的提示注入（prompt injection via repos）— README、依赖、issue、网页里藏指令；智能体读到即可能执行
- * 权限模型与沙箱 — 允许/询问/拒绝规则、受限目录、网络出口；自动模式与「跳过所有确认」的风险边界
- * 供应链风险：虚构包、恶意包、被投毒的技能与 MCP 服务器 — 先核实再安装；锁版本；审查第三方技能与服务器
- * 「致命三要素」在编程智能体里的体现 — 私有代码或密钥 + 不可信内容 + 能联网；拆掉其中一个
- AI 生成代码的安全缺陷 — 注入、鉴权缺失、弱加密、不安全默认值；静态分析与安全测试并入流程
- 许可证与版权：生成代码的合规 — 训练数据与代码相似度；企业条款与赔偿承诺的范围
- 数据外传与企业合规 — 哪些代码可发往哪个供应商；零保留、私有部署选项
- 破坏性操作的防护 — 删库、强推、生产环境；只给最小权限、备份、人工确认点

## 7. 团队采用与度量
- * 证据 1：METR 2025 随机对照试验 — 16 位有经验的开源开发者、246 个真实任务，允许使用 AI 时平均慢 19%，而他们自己以为快了约 20%；适用范围与局限（样本小、熟悉的大仓库、2025 年初工具）；METR 称结果已过时并发布了后续数据
- * 证据 2：DORA 2025 AI 辅助软件开发报告 — 核心结论：AI 是放大器，放大组织已有的强项与弱点；七项 AI 能力模型；吞吐与稳定性的关系（数字需核对原报告）
- * 证据 3：Stack Overflow 2025 开发者调查 — 84% 使用或计划使用，51% 的专业开发者每天用；信任准确性的只有 33%，最大困扰是「几乎对但不对」（66%）
- * 感知与实测的落差：为什么自我感觉不可靠 — 等待时间、上下文切换、审查成本被忽略；需要实测
- * 该度量什么：周期时间、变更失败率、恢复时间、返工 — 别只数生成的代码行或接受率；先建立基线再比较 (需先: 证据 2)
- * 采用路径：从低风险任务起步 — 测试、迁移、文档；逐步扩大；培训与分享实践
- 团队规范：上下文文件、审查规则、披露约定 — 把个人技巧变成共享资产
- * 成本管理：token 预算、模型分级、子智能体成本 — 用量按人与按任务可见；上限与告警
- 对初级工程师的影响：学习路径与技能退化风险 — 调研显示信心下降的信号；刻意练习不借助 AI 的基本功
- 如何批判地读生产力研究 — 样本、任务类型、度量指标、厂商利益；同一结论不要外推到所有场景

## 8. 资深工程师的角色转变
- * 从写代码到定义问题与验证结果 — 规格、架构边界、验收标准、取舍成为主要产出
- * 架构与判断力的价值上升 — 智能体放大局部产出，系统级一致性仍靠人；评审与决策的杠杆
- 管理一组智能体像带一个小团队 — 任务切分、上下文交接、验收；委派的粒度
- 可读性与可测试性成为「对智能体友好」的设计 — 清晰模块边界、快速测试、类型；也是对人好
- 持续学习：保持手感的做法 — 定期手写、读生成代码、跟踪模型能力变化；每个新模型都重估「它能做什么」
- 面试与招聘中的变化 — 允许使用 AI 的考题、评估重点转向验证与设计（只讲趋势，不押具体公司）

## 不收（out of scope）
- 各 IDE 的快捷键与界面逐项教程 — 变化快，官方文档即可
- 提示词技巧大全与角色扮演 — ai-literacy:use.prompting 覆盖
- 构建面向用户的 LLM 产品（RAG、网关、评测）— 放 ai-eng
- 模型训练与推理内部 — llm-inference
- 具体厂商价格与套餐 — 易变；只讲成本机制
- 「氛围编程」（vibe coding）的娱乐化讨论 — 只在「理解债」一叶出现
- 非编程场景的 AI 使用（写作、数据分析）— 不在范围

## 卡片格式建议
- 场景开头：一次具体的失败（「智能体说测试通过，其实它改了测试」），再给机制与做法；动作要带触发条件。
- 证据卡写清规模与局限：样本数、任务类型、效应大小、是否被后续研究更新；数字必须当次核对原文。
- 做法卡带「做/别做」对照，附一小段命令或配置片段（上下文文件示例、钩子、权限规则）并加行内注释。
- 至少 25% 带图：四段循环、上下文窗口占用曲线、致命三要素、审查瓶颈示意、并行工作树布局。
- 风险卡写清攻击路径的每一步和阻断点，而不是只列名词。
