# Coding rounds — what TikTok / ByteDance asks (2025-10 to 2026-10-24)

Source ids as in `sources.md`. LC numbers: "(stated)" = the source gives the number; otherwise the number is mine from the title and should be re-checked.
Counts come from TrueInterview's catalog [G1] (the only large dated pool I could read in full): 345 ByteDance/TikTok questions, 204 dated, **200 exactly-dated sightings from 2025-10-09 to 2026-10-05** (more are month-only in the OA repo) (algorithm 103, system design 27, blog/oral 48, OOD/LLD 14, SQL 7, AI-coding 1; phone screen 147, onsite 70, OA 17). Every sighting is one candidate report of one question (the same question can be reported several times).

## 1. Format and difficulty

- Hour shape: resume drill (10-45 min) then 1-2 problems; "Problems are mostly medium, often reworded in business terms, with hard follow-ups" [G1]. 2-3 problems per round claimed by [G3]; "3 LC mediums in round 1, 2 in round 2, not including follow-ups" (Blind 2024, background [B-old2]); "solve LC medium to hard in 20 mins" [R1]; "hard problem in 20 minutes" / "2 mediums in 20 minutes" [R3]. **several**
- Difficulty mix of the catalog [G1] (graded questions only): easy / medium / hard = 32 / 174 / 58 overall; OA 18/14/5; phone screen 11/126/40; onsite 5/56/20. So: medium-dominant (66%), hard ~22%; hard is likelier in onsite/HM than in screens. Reddit (Singapore, 2026-09): "upper level medium or lower level hard"; a Blind senior (2025-09): screen was "2 LC easy-medium" [B8]. **several**
- Topic shares of the 179 labelled questions [G1]: graphs 18%, arrays 16%, strings 15%, hashing 13%, backtracking 10%, binary search 9%, sliding window 8%, stack 8%, trees 8%, greedy 7%. 1point3acres (105 threads, 2026 Q2): general coding 67%, system design 10%, ML coding 13%, behavioral/other 10%; top hot topic "Number of Islands and variants" (11 threads), then LRU/LFU with TTL (5) [A1].
- LeetCode company tag (crowd data) [G4]: TikTok 30 days: LRU Cache, Cheapest Flights Within K Stops, Making A Large Island, All Nodes Distance K; 3 months adds Number of Islands, Meeting Rooms II, Block Placement Queries, Spiral Matrix, Decode String, Merge Intervals, Number of Distinct Islands, Find Median from Data Stream, Single-Threaded CPU, Basic Calculator II, Remove Duplicate Letters. Low weight for a senior backend loop but consistent with the interview reports.
- Platform: HackerRank / Lark codepad / (AI-allowed) own IDE; own tests; compile and pass (see `loop.md` §3). No starter class ("Practice in a bare editor with no class stub" [G1]).
- Do they want optimal first? Evidence says "brute force → optimal inside the hour": a brute-force tree path-sum "was not accepted" and the interviewer pushed to O(n) with prefix sums; "find the subarray maximizing min+max: first brute force, then linear time"; "return values > n/3 in a sorted array in sub-linear time"; "after the standard longest-palindrome solution, Manacher" [G1]. No source says the first answer must be optimal; every source says the final answer must be. **two**
- Interviewer style: "curt and efficient", "little to no fumbling", "mostly LC ... bad news is it's mostly LC", problems "slightly repetitive" across interviewers, "interviewers write their own problems and progressively mutate them mid-round" [R4][G3]. Narration matters: "silent correct code is weaker evidence than explained code"; a bug-fix without explaining the in-degree guard was marked down [G1].

## 3. Non-LC / implementation-and-design coding (the part that fits a payments/data-pipeline backend)

These are "business logic" or "build a structure" problems, 30-40 min, with a layered follow-up. They are the closest to senior backend practice and the best place to show production judgment.
- **LRU Cache (146)** — the single most reported item (AI-coding variant 2026-10-01; OOD "LRU Cache III" Oct 2026; *with TTL*, *LFU*, *weighted LRU*, *expiring LRU*, "implement and debug an existing implementation", thread-safety/locking, "what do you do about a **high miss rate**?" — one frontend candidate was rejected for not answering it) [G1][A1 5 threads][P3]. Very high.
- **Seller Task Scheduler**: `receive_task`, `process_next_task`; rotate across sellers, VIP sellers get two tasks per turn, priority then FIFO within each seller (outer round-robin queue + per-seller min-heaps) — Sep 2026. **Removable timestamp-ordered task scheduler**: `addTask`, `removeTask`, `popTask(num)` earliest by timestamp, deterministic tie-breaking; one candidate restarted after assuming `popTask` did not remove the task — Aug 2026 [G1][G3].
- **In-memory key-value store with snapshot and restore** (serialization is the hard part); **Time Based Key-Value Store (981, stated)** onsite Mar 2026; "LRU Cache + sliding windows" onsite Apr 2026; HashMap from scratch; deque with O(1) push/pop/index; circular queue; MinStack/MaxStack; Merge K sorted price streams; in-memory file system (588) — Aug 2026, new-grad VO Apr 2026 [L3]; binary-tree level-order stream iterator; **Contiguous Memory Allocator** (first-fit, split/coalesce, errors for zero/negative/over-capacity, double free; follow-ups: alignment multiple of 8, tracking live allocations to reject invalid frees, realloc, thread-safety, hardware differences) — Jun/Oct 2026 [G1]; AI-assisted `OrderValidator` (rules as a DAG; remove a rule and reconnect predecessors to successors; shipped working code + complete tests is the grade; unfinished tests ended one loop the same day) — Aug 2026 [G1][B5].
- **Idempotent versioned database update** (PracHub, 2026-08-09, locked) and "flag actors exceeding a rate in a sliding window", "distributed rate limiter", "expiring LRU", "cache stampede on a hot key" [P3][P1][G3] — directly adjacent to Chi's payments/data-pipeline experience.
- GPU resource management (job queue + scheduler + monitor, fairness, bin-packing), round-robin load balancer, "Server Investment" (new 2026 OA), hashtag trend detector, comment-tree flattening ("Build a Nested Comment Tree from Flat Records", Aug 2026), content-moderation priority queue, video dedup via hashing, live viewer count at billion scale [G3][G1]. ## 5. What follow-ups look like (interviewer pushes)

- Partial tail group (k-group), unary minus/parentheses (calculator), "don't modify the input", O(1) extra space, streaming input, too-big-for-memory grid, sub-linear on sorted input, Manacher after palindrome, LFU after LRU, TTL after LRU, thread safety, miss-rate, brute-force rejection until prefix sums / hashing, "print the path", "return all values on ties" [G1][L3].
